Reference Architecture — Generic LLM Product

Chahe tum chatbot bana rahe ho ya multi-agent system, almost har production AI product ek similar layered shape follow karta hai. Ye reference architecture samajh lo to teeno worked examples baad mein "isi shape ke variations" lagenge, kuch alag naya nahi.

Generic LLM-backed product — layered architecture
Client (Web / Mobile / Slack bot / CLI)
      │  HTTPS request, ideally streaming-capable (SSE / WebSocket)
      ▼
API Gateway / Backend-for-Frontend
      │  auth, rate limiting, request validation, routing
      ▼
Orchestration Layer   ◄──────────────┐
      │  prompt building               │
      │  RAG retrieval trigger         │  (calls out to:)
      │  tool / agent invocation       │  ┌─ Vector DB (retrieval)
      │  response streaming back       │  ├─ Cache layer (prompt/embed/tool cache)
      ▼                                │  ├─ Tool/Agent execution service
LLM Provider(s)                        │  └─ Observability/logging (traces, tokens, cost)
  (OpenAI / Anthropic / self-hosted)   │
      │  tokens stream back            │
      ▼                                │
Orchestration Layer  ──────────────────┘  (guardrails check response before it leaves)
      │
      ▼
Client  (tokens rendered incrementally / final structured response)

Har layer ki apni specific responsibility hai — inhe alag-alag samajhna zaroori hai kyunki inka scaling aur failure mode bhi alag hota hai:

  1. Client — web app, mobile app, Slack/Teams bot, ya CLI. Ideally streaming-aware hona chahiye (SSE ya WebSocket consume kar sake), kyunki LLM responses token-by-token aate hain aur user ko turant kuch dikhna chahiye — 3-5 second ka blank loading spinner AI products mein especially bura lagta hai kyunki users already "AI slow hota hai" expect karte hain.
  2. API Gateway / Backend-for-Frontend — ye tumhara normal backend hai jo auth verify karta hai, per-user/per-org rate limiting enforce karta hai, request payload validate karta hai, aur request ko orchestration layer tak route karta hai. Ye layer LLM ke baare mein kuch nahi jaanta — isko REST API ki tarah hi treat karo, koi special AI-specific cheez nahi hai yahan.
  3. Orchestration layer — ye asli "AI engineering" ka core hai. Ye layer decide karta hai: konsa prompt banana hai (system prompt + user input + retrieved context), kya RAG retrieval chalani hai, kya tool/agent loop invoke karna hai, aur LLM provider ko call karke response ko stream back karna hai. Ye stateless service hona chahiye (detail #statelessness section mein) taaki horizontally scale ho sake.
  4. LLM provider(s) — Anthropic/OpenAI API, ya self-hosted model (vLLM/TGI ke peeche). Production systems often multiple providers wire karte hain — primary model + fallback model agar primary rate-limited ya down ho (chapter 13 mein detail).
  5. Vector DB — agar RAG use ho raha hai, retrieval yahan se aata hai (Pinecone, Weaviate, pgvector, etc — chapter 4 mein detail).
  6. Cache layer — prompt→response cache, embedding cache, retrieval-result cache (niche caching section mein detail).
  7. Tool/Agent execution service — agar agent tools call kar raha hai (web search, internal APIs, code execution), ye usually ek separate sandboxed service hota hai, orchestration layer ke andar directly nahi (design #3 mein detail).
  8. Observability/logging — har request ka full trace (prompt, retrieved chunks, tool calls, tokens used, latency, cost) capture karna — bina iske production mein debug karna impossible hai (chapter 13 mein poora coverage).
  9. Guardrails — input validation (prompt injection detection) aur output validation (PII leak check, toxicity check) — response client tak jaane se pehle ye check ho sakta hai (chapter 13 mein detail).
📌 Ye ek "reference", ek recipe nahi

Har product ko har layer ki zaroorat nahi hoti — ek simple internal FAQ bot ko vector DB ya tool execution service ki zaroorat nahi. Point ye hai ki jab tumhe koi naya requirement aaye (retrieval, tools, multi-turn memory), tumhe pata ho ki wo kis layer mein fit hota hai, taaki tum orchestration layer ko overload na karo ek "God service" bana ke.

Design #1 — Simple Chatbot/Copilot

Scenario: ek internal support assistant jo company docs ke basis pe employees ke sawaalon ka jawab deta hai, koi tools nahi, koi multi-step actions nahi — sirf conversational Q&A.

Key design decision — stateless per-request vs stateful session: conversation history (previous turns) kahan store hoti hai? Do options hain:

  • Client-side history — frontend har request ke saath poora conversation history bhejta hai (ya at least last N turns). Backend service completely stateless rehta hai — koi server-side session state nahi. Simple internal tools ke liye ye often sabse simple approach hai.
  • Server-side session (DB-backed) — session ID client ko milta hai, history ek DB (Postgres/Redis) mein store hoti hai, backend service history ko session ID se fetch karta hai. Zaroorat padti hai jab history bahut lambi ho jaaye (client payload size limit) ya multi-device continuity chahiye ho (user phone pe shuru kare, laptop pe continue kare).

Dono approaches mein backend service khud stateless rehta hai — state ya to client mein hai ya ek external DB mein, kabhi bhi backend process ke memory mein nahi (isi wajah se agla request kisi bhi server instance pe land ho sakta hai, load balancer round-robin kar sakta hai bina "sticky session" ki zaroorat ke).

Streaming: response client ko SSE (Server-Sent Events) ya WebSocket ke through token-by-token stream hoti hai — user ko turant "AI type kar raha hai" feel milta hai, poore response ka wait nahi karna padta (jo 5-10 seconds tak ho sakta hai lambe answers ke liye).

Minimal infra: is design mein vector DB zaroori nahi (agar retrieval nahi chahiye), tool execution service zaroori nahi, agent loop zaroori nahi. Bas: client → API gateway → orchestration layer (prompt build karo, LLM call karo, stream back karo) → LLM provider. Simplest possible AI product shape — but yahi shape hai jo already production mein 60-70% internal tools cover kar leta hai.

Design #2 — RAG Document Q&A Assistant

Scenario: ek assistant jo company ke internal documents (policies, wikis, PDFs) pe questions answer karta hai, actual document content ko cite karke.

Core architectural insight — ingestion aur query path completely separate concerns hain, alag services ki tarah design karo:

AspectIngestion PipelineQuery Path
TriggerNaya document upload/update hone peUser ka question aane pe
TimingAsync, background job (queue-based)Synchronous, request/response
Latency requirementKuch minutes bhi chalega — koi user isse directly wait nahi kar rahaLow-latency critical — user turant answer chahta hai
StepsParse → chunk → embed → vector DB mein upsertQuery embed → retrieve → rerank → prompt build → LLM call
Failure modeRetry silently, alert on repeated failure — user ko pata bhi nahi chaltaUser-facing error, graceful degradation zaroori

Ye separation kyun zaroori hai? Agar ingestion aur query ek hi synchronous path mein mix ho jaayein (jaise "document upload hote hi turant chunk+embed karo, request response wahi block ho jaaye"), to ek bada PDF upload karne pe user ka request 30+ seconds tak hang ho sakta hai — bahut bura UX. Isliye ingestion ko ek async job queue (SQS, Celery, BullMQ) ke peeche daalo — upload endpoint turant "queued" response return karta hai, actual parsing/chunking/embedding ek background worker mein hoti hai, alag se scale hoti hai (embedding-heavy workload, GPU/API-bound, alag resource profile query path se).

Query path, uske contrast mein, hamesha low-latency optimized hona chahiye — user seedha wait kar raha hai. Isme retrieval (vector DB lookup, usually 10-50ms), optional reranking (50-200ms), aur LLM generation (streaming se perceived latency kam) shaamil hai.

🧠 Senior Dev Note — ingestion/query coupling ek real production mistake hai

Maine ek team dekhi jinhone shuru mein document upload API ko synchronously chunk+embed karke response return karne wala design kiya — chhote test docs ke saath fine chala. Production mein jab users ne 200-page PDFs upload karna shuru kiya, upload endpoint 45+ second timeout hone laga, aur load balancer requests drop karne laga. Fix ye tha ki upload endpoint ko turant "job queued, ID: xyz" return karne wala banaya, aur client ko job status poll karne (ya websocket notification milne) ke liye separate endpoint diya. Lesson: jo bhi operation ka duration unpredictable ho aur user ke direct control mein na ho (LLM call, embedding batch, large file processing), use hamesha async job ki tarah design karo, chahe shuru mein "abhi to fast hai" lage.

Baaki architecture design #1 jaisa hi hai (streaming response, stateless orchestration layer), bas vector DB retrieval step add hota hai query path mein, aur ek poora naya async ingestion subsystem parallel mein chalta hai.

Design #3 — Agentic Backend

Scenario: ek agent jo lookup kar sakta hai (search internal APIs, databases) aur multi-step actions le sakta hai (create ticket, send notification, update record) — jaisa chapter 7-8 mein cover kiya. Ye sabse complex design hai teeno mein.

Do naye architectural requirements aate hain jo pehle designs mein nahi the:

  • Tool-execution sandbox/service layer — agent jo tools call karta hai (especially code execution, ya external API calls jinke side effects hain) unhe orchestration layer ke andar directly execute nahi karna chahiye. Ek alag, sandboxed tool-execution service hona chahiye jo: permissions enforce kare (agent har internal API ko access nahi kar sakta), resource limits lagaaye (timeout, memory cap agar code execution hai), aur audit log rakhe (kaunsa tool kab, kis input ke saath call hua). Ye separation security ke liye critical hai — agent ka LLM-generated tool call agar directly production DB ko hit kar sake bina kisi layer ke, ek prompt injection attack seedha data-modifying action mein convert ho sakta hai.
  • Async job queue for long-running agent tasks vs synchronous request/response — agent loops (ReAct-style, multi-step) 10 seconds se 10 minutes tak le sakte hain depending on kitne tool calls chahiye. Ek simple synchronous HTTP request/response model isme fit nahi baithta — REST timeouts (typically 30-60s) is duration ko handle nahi kar payenge. Isliye pattern ye hota hai: request aata hai → job queue mein daala jaata hai → job ID turant return hota hai → agent background mein multi-step loop chalata hai → client ko progress updates milte hain (niche dekho) → final result ek terminal event ke saath deliver hota hai.

Streaming intermediate "thinking"/progress to client: agar agent 5 tool calls kar raha hai jisme har ek 3-5 seconds leta hai, poore 20-25 seconds tak agar UI blank/frozen dikhe, user confuse ho jaayega — "kya ye hang ho gaya?" Isliye production agentic UIs SSE ya WebSocket connection khula rakhte hain aur intermediate events stream karte hain jaise:

Agent progress events — SSE stream se client ko kya bhejna hai (conceptual)
event: agent_step
data: {"step": "thinking", "text": "Checking user's recent order history..."}

event: agent_step
data: {"step": "tool_call", "tool": "get_order_history", "status": "running"}

event: agent_step
data: {"step": "tool_result", "tool": "get_order_history", "status": "done", "summary": "3 orders found"}

event: agent_step
data: {"step": "thinking", "text": "Order #4521 looks delayed, checking shipping status..."}

event: agent_step
data: {"step": "tool_call", "tool": "check_shipping_status", "status": "running"}

event: final
data: {"answer": "Aapka order #4521 delayed hai, expected delivery 3 din mein."}

Ye events UI ko ek "agent kaam kar raha hai, ye steps le raha hai" wali live progress dikhane dete hain — chat interfaces mein aksar isko collapsible "thinking" section ki tarah render kiya jaata hai jo agent ke complete hote hi collapse ho jaata hai aur final answer highlight hota hai.

⚠️ Long-running agent jobs ke liye "fire and forget" mat karo

Agar client disconnect ho jaaye (browser tab close, network drop) jab agent abhi bhi chal raha hai — agent job ko kill mat karo. Job background mein continue hona chahiye (queue worker isolated hai client connection se), aur result DB mein persist hona chahiye taaki client reconnect kar ke (ya notification/email ke through) final result pa sake. Isko client connection se tightly couple karna common mistake hai jo lambi-running agent tasks ko fragile bana deta hai.

Statelessness Aur Idempotency

Backend LLM-calling services stateless kyun hone chahiye: agar orchestration layer apni in-memory state mein conversation history ya agent state rakhta hai, to ek specific user ka agla request usi specific server instance pe hi jaana zaroori ho jaata hai (sticky sessions) — isse horizontal scaling badly limited ho jaati hai (load balancer flexibly traffic distribute nahi kar sakta), aur agar wo instance crash ho jaaye, poori session state gum ho jaati hai. Isliye session/ conversation history/agent state hamesha ek external store (Postgres, Redis) mein rakho — koi bhi server instance koi bhi request handle kar sake, state DB se fetch karke.

Idempotency for side-effecting tool calls: agent loops kabhi-kabhi retry karte hain — LLM ne ek tool call generate kiya, network timeout hua, agent loop retry logic ne wahi tool call dobara bheja. Agar wo tool call "read-only" hai (jaise search, lookup), retry bilkul safe hai. Lekin agar wo tool "send email", "make payment", "create ticket" jaisa side-effecting action hai, ek retry matlab duplicate action — user ko email do baar mil sakta hai, payment do baar ho sakta hai.

Solution: har side-effecting tool call ko ek idempotency key ke saath design karo — ek unique ID (agent turn ID + tool call ID se derive kiya hua) jo request ke saath bheja jaata hai. Downstream service (payment API, email service) is key ko dekh kar decide karta hai "ye request maine pehle already process kar li thi, same result wapas de do, dobara mat karo". Ye pattern already standard hai payment APIs mein (Stripe idempotency keys), agentic systems mein isi pattern ko tool-call level pe apply karna zaroori hai.

🚨 Idempotency skip karna production incident bana sakta hai

Ek agent jo "send refund confirmation email" tool call karta hai — agar orchestration layer ka retry logic (network blip ki wajah se) isko 2 baar trigger kar de aur tool idempotent na ho, customer ko duplicate refund confirmation emails milenge, ya worse, agar tool "issue refund" ho, customer ko double refund mil sakta hai. Idempotency keys yahan optional nice-to-have nahi hain, ye correctness ka basic requirement hain jaise hi koi tool "write"/ "mutate"/"send" karta hai.

API Design — Streaming, Timeouts, Safe Retries

Traditional REST API design assumptions AI products mein break ho jaate hain — kuch specific adjustments zaroori hain:

  • Streaming (SSE/WebSocket) vs polling for long tasks — simple chatbot responses ke liye SSE ideal hai (unidirectional, HTTP-based, easy to implement, works through most proxies). Agentic multi-step tasks ke liye bhi SSE kaafi hai agar connection lambe samay tak khula rakh sakte ho; agar client mobile app hai jo background/foreground switch karta rehta hai, polling (job status endpoint, client har few seconds poll kare) zyada resilient ho sakta hai kyunki persistent connections mobile networks pe unreliable hote hain.
  • Request timeouts — typical REST APIs 5-30 second timeout assume karte hain. LLM calls (especially agent loops with multiple tool calls) minutes tak le sakte hain. Load balancers, reverse proxies (nginx), aur API gateways sab jagah timeout values explicitly LLM workload ke hisaab se badhaane padte hain (ya streaming use karo jahan connection khula rehta hai aur "timeout" concept differently apply hota hai — chunks continuously flow ho rahe hain).
  • Designing endpoints so retries are safe — client-side retry logic (network failure pe automatic retry) common hai, lekin agar wo retry ek naya LLM call trigger kar de jo paisa kharch karta hai aur potentially side effects create karta hai, ye mehenga aur risky hai. Solution: request creation ko idempotent banao (client ek request ID generate kare, server usi ID ke against dedupe kare) — taaki retry safe ho, duplicate LLM calls ya duplicate actions na ho.

Caching — System-Level View

Caching ka poora depth chapter 12 mein hai, lekin system design level pe teen jagah caching fit hoti hai jo yaad rakhni chahiye jab architecture draw kar rahe ho:

  1. Prompt→response cache — agar exact same (ya semantically-similar) prompt repeat hota hai (common FAQ-type queries), cached response return karo bina LLM call kiye — latency aur cost dono bachte hain.
  2. Retrieval results cache — RAG systems mein, agar same query (ya same query embedding ke close) baar-baar aati hai, vector DB lookup skip karke cached chunks use karo.
  3. Embedding cache — same text ko baar-baar embed karna wasteful hai (embedding calls bhi paisa/latency lagte hain) — content hash ke against embedding cache karo taaki same document chunk dobara embed na ho.

Architecture diagram mein ye cache layer usually orchestration layer aur (LLM provider / vector DB) ke beech ek "check cache first" step ki tarah baithta hai.

💡 Hinglish Tip — teeno designs ko ek line mein yaad rakho

Chatbot = simple pipe (client → orchestration → LLM), history client ya DB mein. RAG assistant = do alag paths (async ingestion + low-latency query), kabhi mix mat karo. Agentic backend = sandboxed tool layer + async job queue + streaming progress events — teeno essentially same reference architecture ke different subsets hain, complexity badhti jaati hai jaise-jaise product ki capability badhti hai.

Key Takeaways

  • Generic LLM product architecture: client → API gateway → orchestration layer (prompt build, RAG, tools) → LLM provider → streaming response, plus vector DB, cache, observability, guardrails as supporting infra.
  • Simple chatbot: stateless service, history client-side ya DB-backed session, streaming response, minimal infra — no vector DB, no tools needed.
  • RAG assistant: ingestion (async, background job queue, latency-tolerant) aur query path (sync, low-latency-critical) architecturally alag concerns hain — inhe mix karna production timeouts create karta hai.
  • Agentic backend: tool execution ek alag sandboxed service hona chahiye (security), long tasks async job queue mein chalte hain, intermediate progress SSE/WebSocket se stream hota hai taaki UI frozen na lage.
  • Backend services stateless hone chahiye (session/history DB mein) for horizontal scaling; side- effecting tool calls ko idempotency keys chahiye kyunki agent retries duplicate actions cause kar sakte hain.
  • API design mein LLM-appropriate timeouts (minutes, seconds nahi), streaming/polling choice, aur safe-retry-friendly endpoint design zaroori hai.
  • Caching teen jagah fit hoti hai: prompt→response, retrieval results, aur embeddings — sab latency aur cost dono bachate hain.

🎯 Interview Questions

Q1. Design a RAG-based internal document assistant for a fintech company — walk through your architecture, especially ingestion vs query path.

Do alag subsystems: (1) Ingestion pipeline — document upload endpoint turant "queued" response deta hai, actual parse/chunk/embed/upsert-to-vector-DB kaam ek async job queue (SQS/Celery) ke peeche background worker mein chalta hai — kyunki large PDFs minutes le sakte hain aur user ko block nahi karna. (2) Query path — user question → embed query → vector DB se top-k retrieve → optional rerank → prompt build with retrieved context → LLM call → streamed response, sab kuch low-latency-optimized (target sub-2s to first token). Fintech-specific considerations: PII/sensitive-doc access control per-user (RBAC on retrieval), audit logging (kaunsa doc kis query ke liye retrieve hua), aur guardrails on output (compliance-sensitive answers flag karna). Caching retrieval results aur embeddings latency/cost dono kam karta hai repeated queries pe.

Q2. Ek agent backend design karo jo customer support tickets create kar sake aur order status check kar sake — kaise ensure karoge ki duplicate tickets na banein agar agent retry kare?

Root cause: agent loops network issues ya transient errors pe retry karte hain, agar "create ticket" tool call idempotent nahi hai, retry duplicate ticket bana dega. Solution — har tool call ek idempotency key ke saath jaaye (agent turn ID + tool call ID se derive), aur ticket-creation service us key ko check kare: agar same key pehle process ho chuki hai, existing ticket ka result wapas do, naya mat banao. "Order status check" jaisa read-only tool retry-safe hai by default, isliye sirf write/side-effecting tools (ticket create, email send) ko explicit idempotency handling chahiye.

Q3. Ek multi-step agent 30+ seconds tak tool calls kar sakta hai — client ko is dauraan UI frozen kaise nahi lagegi, aur agar client beech mein disconnect ho jaaye to kya hoga?

UI frozen na lage is liye backend SSE (ya WebSocket) connection khula rakhta hai aur intermediate "agent_step" events stream karta hai — "thinking", "tool_call running", "tool_result done" — jo client render kar sakta hai as a live progress trace, final "answer" event tak. Disconnect handle karne ke liye — agent job ek async job queue mein chalta hai (client connection se decoupled), so agar client disconnect ho jaaye, background worker job continue karta hai aur result DB mein persist hota hai. Client reconnect karke (ya poll karke, ya notification se) final result fetch kar sakta hai — job kabhi client connection ke upar dependent nahi hona chahiye.

Q4. Ek LLM-backed backend service ko stateless kyun design karna chahiye, aur agar session history in-memory rakh di jaaye to kya problem hogi?

Agar conversation history ya agent state server instance ke in-memory mein rakhi jaaye, to user ke saare requests usi specific instance pe route hone zaroori ho jaate hain (sticky sessions) — ye load balancer ki flexibility kam kar deta hai aur horizontal scaling ko mushkil banata hai (new instances add karne pe traffic evenly distribute nahi ho sakta jab tak state migrate na ho). Agar wo instance crash ho jaaye, poori in-flight session state permanently gum ho jaati hai. Solution — state ko hamesha ek external store (Postgres/Redis) mein rakho, service khud completely stateless rahe — koi bhi instance koi bhi request handle kar sake, state ko DB se fetch/write kar ke.

Q5. LLM API calls ke liye request timeouts normal REST APIs se kaafi zyada lambe kyun rakhne padte hain, aur ye kya practical problems create karta hai infra mein?

Typical REST endpoints 100ms-few seconds mein respond karte hain, isliye standard timeouts (load balancer, reverse proxy, API gateway pe) 5-30 seconds set hote hain. LLM calls — especially agent loops jisme multiple sequential tool calls hote hain — seconds se leke minutes tak le sakte hain. Agar infra ke timeouts is duration ke hisaab se explicitly increase nahi kiye jaayein, requests beech mein hi drop ho jaayengi chahe LLM abhi bhi kaam kar raha ho, aur client ko confusing error milega jabki actual generation successfully complete ho sakta tha. Practical fix — streaming responses use karo jahan possible ho (connection khula rehta hai, "timeout" ka matlab differently apply hota hai kyunki data continuously flow ho raha hota hai), aur long-running agent tasks ke liye synchronous request/response model chhodke async job + polling/streaming-progress model use karo.
