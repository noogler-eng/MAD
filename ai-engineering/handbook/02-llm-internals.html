Tokenization — Model Raw Text Nahi Dekhta

Sabse pehli galat-fehmi jo naye AI Engineers rakhte hain: "model mere sentence ke letters ya words padhta hai." Aisa nahi hota. LLM ke andar sirf ek cheez chalti hai — numbers. Tumhara input text pehle ek tokenizer se guzarta hai jo text ko chhote-chhote chunks (tokens) mein todta hai, aur har token ko ek integer ID assign karta hai. Model sirf in integer IDs ki sequence dekhta hai, kabhi raw characters nahi.

Modern LLMs (GPT, Claude, Llama sab) subword tokenization use karte hain — usually BPE (Byte-Pair Encoding) ya isi family ka koi variant. Idea simple hai: common words ek single token ban jaate hain, lekin rare/complex words multiple sub-word pieces mein toot jaate hain. Isse tokenizer ka vocabulary chhota reh sakta hai (~50k-100k tokens) jabki koi bhi arbitrary word — chahe wo dictionary mein ho ya na ho — represent kiya ja sake, kyunki worst case mein word letter-level tak bhi break ho sakta hai.

Ek practical example — sentence tokens mein kaise toot-ta hai
// Ye purely illustrative hai — exact split model/tokenizer ke hisaab se vary karta hai
// Input sentence: "Unbelievably, tokenization affects your API cost."

// Common/short words aksar ek hi token ban jaate hain:
// "affects" -> [" affects"]        (1 token)
// "your"    -> [" your"]           (1 token)
// "cost"    -> [" cost"]           (1 token)

// Rare/long/compound words multiple sub-word pieces mein todte hain:
// "Unbelievably" -> ["Un", "believ", "ably"]   (~3 tokens)
// "tokenization" -> ["token", "ization"]        (~2 tokens)

// Punctuation apna alag token hota hai:
// "," -> [","]   "." -> ["."]

// Total: ek 8-word English sentence roughly 10-12 tokens ban sakta hai,
// word-count se hamesha thoda zyada — ye hi rule-of-thumb hai jo cost estimate ke kaam aata hai

Rule-of-thumb jo production mein kaam aata hai: English text ke liye roughly 1 token ≈ 4 characters, ya 1 token ≈ 0.75 words. Non-English languages (especially Hindi, Chinese, Japanese) mein ye ratio kaafi worse ho sakta hai — same meaning ke liye zyada tokens lagte hain, kyunki tokenizer vocabulary mostly English-heavy corpus pe train hota hai. Iska direct matlab hai ki agar tumhara product multi-lingual hai, tumhara per-request cost aur context usage language ke hisaab se significantly vary karega.

🧠 Senior Dev Note — Token count estimate karo, guess mat karo

Production mein cost aur context-limit dono token count pe based hote hain, character count pe nahi. Kabhi bhi "text.length / 4" jaisa rough hack production billing ke liye use mat karo — ye systematically wrong hoga especially code, non-English text, ya JSON-heavy payloads ke liye (jinme symbols/whitespace ka density alag hota hai). Har provider ka apna official tokenizer library hota hai (OpenAI ka tiktoken, Anthropic ke paas token-counting API endpoint hai) — request bhejne se pehle usi se count karo, taaki tumhe pata ho request context window mein fit hoga ya nahi, aur tumhara cost dashboard accurate ho. Ye ek chhota utility function hai jo agar skip kiya to production mein silently galat billing estimates aur unexpected 400 errors (context overflow) dega.

Embeddings — Meaning Ko Coordinates Mein Convert Karna

Ek baar text tokenized ho jaaye, model internally har token ko ek vector embedding mein convert karta hai — matlab numbers ki ek list (jaise 1536 ya 3072 numbers ka array), jo us token/phrase ke "meaning" ko multi-dimensional space mein ek coordinate ki tarah represent karta hai. Isko training math ke bina bhi samajhna easy hai agar tum ek analogy use karo: socho har word/sentence ek city hai, aur embedding uska GPS coordinate hai. Cities jo semantically similar hain (jaise "dog" aur "puppy"), unke coordinates bhi ek-dusre ke paas hote hain us space mein. Cities jo unrelated hain (jaise "dog" aur "quarterly revenue"), unke coordinates door hote hain.

Is property ka naam hai semantic similarity — do embeddings jitne "close" hote hain (usually cosine similarity ya dot-product se measure kiya jaata hai), unka meaning utna hi similar hota hai, chahe unke actual words/characters completely different hon. Yahi wo property hai jo aage chapter 4 (RAG) mein critical banegi: agar tumhe apne knowledge base se "user ke sawaal se related documents" dhoondhne hain, tum keyword match pe depend nahi karte — tum query aur documents dono ko embeddings mein convert karte ho aur "nearest" vectors dhoondhte ho. Isi wajah se RAG systems synonyms aur paraphrases bhi samajh paate hain, exact keyword match ki zaroorat nahi hoti.

📌 Do alag cheezein hain — internal embeddings vs embedding API

LLM ke andar jo embeddings generate hote hain (tokens ko vectors mein convert karna), wo model ke internal working ka part hain — tum unhe directly access nahi karte. Jab AI Engineers "embeddings" bolte hain (jaise RAG context mein), wo usually alag se ek embedding model (jaise OpenAI's text-embedding-3 ya similar) ko call kar rahe hote hain jo specifically iss kaam ke liye design hua hai — text lo, ek fixed-size vector wapas do, jo phir vector database mein store/search kiya ja sake. Concept same hai (meaning → coordinates), lekin ye ek separate, purpose-built API call hai jo tum khud invoke karte ho. Detail chapter 4 mein.

Context Window — Model Ki "Working Memory"

Context window = maximum number of tokens jo model ek single request mein "attend" kar sakta hai — aur important baat, ye input + output dono combined hota hai, sirf input nahi. Agar model ka context window 128K tokens hai, aur tumne 120K tokens ka input bheja, model ke paas response generate karne ke liye sirf ~8K tokens ka room bacha — agar tumne max_tokens usse zyada set kiya, ya to request reject hogi ya response beech mein cut jaayega.

Ye engineers ke liye kai practical consequences create karta hai. Pehla — tum ek poora 300-page PDF "dump" nahi kar sakte kisi bhi prompt mein aur assume nahi kar sakte ki sab kaam karega; agar wo PDF context window se bada hai, tumhe ya to chunk karna padega (RAG-style retrieval, chapter 4) ya summarize karke condense karna padega. Doosra — long conversations (chatbots, agents) mein har naya message purana poora conversation history bhi carry karta hai (jab tak explicit trimming na ho) — isliye lambi conversations eventually context limit hit karti hain, aur tumhe strategy chahiye: purane messages summarize karo, ya sirf recent N messages rakho, ya important facts ko separately "memory" mein store karo (detail chapter 9).

🧠 Senior Dev Note — Context overflow "silently" bhi fail ho sakta hai

Kuch providers/SDKs context limit exceed hone pe clean error return karte hain, lekin kai real setups mein — especially jab tum khud history trim kar rahe ho, ya ek middleware/proxy layer use kar rahe ho — overflow silently truncate ho sakta hai (purane messages ya document ka beginning drop ho jaata hai bina kisi warning ke). Agar tumhara RAG ya agent system bade context ke saath kaam karta hai, hamesha explicitly token count karo request bhejne se pehle, aur agar limit ke paas ho to proactively trim/summarize karo — model ke "silent truncation" pe bharosa mat karo, kyunki usme tumhara sabse important context (jaise system prompt ya latest user message) galat jagah se kat sakta hai.

Inference — Response Kaise Generate Hota Hai

Jab tum ek prompt bhejte ho, model autoregressive tareeke se response generate karta hai — matlab ek time pe sirf ek next token predict karta hai, phir usi predicted token ko apne input mein add karke agla token predict karta hai, aur ye loop chalti rehti hai jab tak model ek "stop" condition hit na kare (jaise ek special end-of-turn token, ya koi explicit stop sequence, ya max_tokens limit). Har step pe model actually poori vocabulary (saare possible tokens) ke upar ek probability distribution generate karta hai — "agla token X hone ka probability 40%, Y hone ka 12%, Z hone ka 8%..." — aur phir ek token us distribution se select kiya jaata hai.

Ye "select kaise kiya jaata hai" wala part hi hai jise engineers control kar sakte hain via sampling parameters — aur yahi practically sabse important part hai is chapter ka, kyunki ye tumhare API calls mein directly dikhta hai.

Sampling Params Jo Engineers Actually Touch Karte Hain

  • temperature — kitna "randomness" allow karni hai token selection mein. Low (0–0.3) = deterministic/focused, factual/structured tasks ke liye achha (data extraction, code). High (0.7–1.0+) = zyada creative/varied, brainstorming ya creative writing ke liye achha.
  • top_p (nucleus sampling) — sirf un top tokens mein se choose karo jinka cumulative probability top_p tak add ho (jaise 0.9 = top 90% probability mass wale tokens hi consider honge, lambi tail ke rare/weird tokens discard). Aksar temperature ke saath ya uske alternative ke roop mein use hota hai — dono ek saath aggressively tune karna generally avoid kiya jaata hai.
  • max_tokens — response mein kitne tokens tak generate karne hain, upper limit. Cost aur latency dono control karta hai (zyada tokens = zyada cost, zyada wait time) — aur agar response naturally isse zyada lamba hota, wo beech mein cut ho jaata hai.
  • stop sequences — specific strings jo mile to model turant generation rok deta hai. Structured output parsing mein useful — jaise agar tum "\n\n" ko stop sequence banao taaki model ek hi paragraph ke baad ruk jaaye.
chat_completion_example.py — sampling params explicitly set karke ek call
# chat_completion_example.py — Anthropic-style chat completion call, sampling params ke saath
import anthropic  # official Anthropic Python SDK import karo

client = anthropic.Anthropic(api_key="YOUR_API_KEY")  # client object banao, apni API key ke saath authenticate karo

# response — model se ek single message request bhejo, sab sampling params explicitly set karke
response = client.messages.create(  # create() call shuru — sab sampling params yahan named arguments ke roop mein jaate hain
    model="claude-sonnet-4-5",  # kaunsa model use karna hai, family/version yahan specify hota hai
    max_tokens=500,  # response ki max length — cost aur latency dono ko bound karta hai
    temperature=0.2,  # low temperature — hum factual/deterministic-style answer chahte hain
    top_p=0.9,  # nucleus sampling — sirf top 90% probability mass wale tokens consider karo
    stop_sequences=["\n\nEND"],  # agar model ye exact string generate kare, turant ruk jao
    messages=[  # messages — conversation history list, yahan sirf ek user turn hai
        {"role": "user", "content": "Summarize what a context window is, in 2 lines."}  # actual user prompt, list of message objects mein
    ],  # messages list yahan close hoti hai
)  # create() call yahan close hota hai — ye synchronous call hai, poora response ek saath aayega

print(response.content[0].text)  # response object se pehla content block nikaalo aur uska text print karo
💡 Hinglish Tip — temperature ka mental model

Temperature ko "confidence vs exploration" ka dial samjho. temperature=0 ka matlab "hamesha sabse likely next token chuno" (near-deterministic, same input pe roughly same output). Jaise-jaise temperature badhta hai, model kabhi-kabhi ek less-likely token bhi choose karta hai — isse response variety aati hai lekin factual-accuracy-critical tasks (jaise structured data extraction) ke liye ye risky ho sakta hai, kyunki model "creative" ho sakta hai jahan tumhe predictable output chahiye tha.

Streaming Responses — Token-by-Token Output

Kyunki inference autoregressive hai (ek time pe ek token), providers response ko stream bhi kar sakte hain — matlab poora response complete hone ka wait karne ki jagah, tumhe token-by-token (ya small chunks mein) response milta rehta hai jaise-jaise model unhe generate karta hai. Isse user ko "typing effect" dikhta hai (jaisa ChatGPT/Claude UI mein), aur perceived latency kaafi kam ho jaati hai — user ko poora response complete hone tak blank screen nahi dekhni padti. Streaming ke latency/UX trade-offs ka detailed discussion chapter 12 mein hoga; abhi bas itna samajhna hai ki mechanism kaise consume karte hain code mein.

stream_example.py — streaming response ko consume karna
# stream_example.py — token-by-token streaming response consume karna
import anthropic  # SDK import, same client jo upar use kiya

client = anthropic.Anthropic(api_key="YOUR_API_KEY")  # client authenticate karo

# stream() context manager — ek streaming request open karta hai
with client.messages.stream(  # stream() call shuru — normal create() jaisa hi, bas streaming mode mein
    model="claude-sonnet-4-5",  # same model selection jaise pehle
    max_tokens=500,  # max response length, streaming mein bhi applicable
    messages=[  # messages — conversation history list, yahan sirf ek user turn hai
        {"role": "user", "content": "Explain streaming responses in 2 lines."}  # user prompt
    ],  # messages list yahan close hoti hai
) as stream:  # 'stream' object ab incremental events deta rahega
    for text in stream.text_stream:  # har naya text chunk aane pe loop iterate hota hai
        print(text, end="", flush=True)  # chunk ko turant print karo, naya line na daalo, buffer turant flush karo

    # loop khatam hone ke baad, agar poora final message chahiye (metadata sahit)
    final_message = stream.get_final_message()  # poora accumulated response object nikaalo, e.g. token usage ke liye
    print("\nTokens used:", final_message.usage.output_tokens)  # kitne output tokens actually generate hue, print karo
⚠️ Streaming production mein extra complexity laata hai

Streaming UX ke liye great hai, lekin engineering-wise iska matlab hai tumhe partial/incomplete JSON handle karna padega agar tum structured output stream kar rahe ho (chunk boundary kisi bhi random jagah pe aa sakta hai, valid JSON ke beech mein), connection drop/retry logic alag se likhni padegi (normal request retry se different hai kyunki tumhe pata karna hoga kitna already stream ho chuka), aur cost/token-counting bhi thoda trickier ho jaata hai kyunki usage info aksar sirf stream ke end mein final event ke saath milta hai. Ye sab detail chapter 12 mein.

Key Takeaways

  • LLM raw text nahi, tokens (subword pieces, BPE-style) dekhta hai — English mein roughly 1 token ≈ 4 characters ≈ 0.75 words, but non-English languages mein ye ratio worse ho sakta hai.
  • Embeddings text ke meaning ko ek multi-dimensional coordinate mein represent karte hain — semantically similar text ke embeddings "paas" hote hain, ye hi property RAG (chapter 4) ka foundation hai.
  • Context window = input + output combined token limit. Providers/model families ke beech ranges kaafi vary karte hain (roughly 32K se 1M+ tak) aur time ke saath badalte rehte hain.
  • Inference autoregressive hai — ek time pe ek next-token prediction, jab tak stop condition hit na ho.
  • Engineers jo params directly control karte hain: temperature, top_p, max_tokens, stop_sequences — inka combination output ki predictability, length, aur creativity decide karta hai.
  • Streaming perceived latency kam karta hai (token-by-token output) lekin partial-JSON parsing aur retry-handling jaisi extra engineering complexity bhi laata hai.
  • Production mein token count kabhi guess mat karo — provider ke official tokenizer/token-count API se calculate karo, taaki cost estimate aur context-limit checks dono accurate rahein.

🎯 Interview Questions

Q1. Tokenization kya hai aur LLMs subword tokenization (BPE-style) kyun use karte hain, word-level ya character-level tokenization ki jagah?

Tokenization text ko chhote units (tokens) mein todne ka process hai jinhe integer IDs assign hote hain — model sirf in IDs ki sequence dekhta hai, raw text nahi. Subword tokenization is liye use hoti hai kyunki ye dono extremes ke trade-offs balance karti hai: word-level tokenization ka vocabulary explode ho jaata hai (har naya/rare word ek naya vocabulary entry maangta hai, aur out-of-vocabulary words handle nahi ho paate), jabki character-level tokenization vocabulary chhota rakhti hai lekin sequences bahut lambi ban jaati hain (compute-inefficient). Subword (BPE) approach common words ko single tokens rakhta hai aur rare/complex words ko chhote reusable pieces mein todta hai — chhota vocabulary bhi, aur koi bhi arbitrary word represent bhi ho sakta hai.

Q2. Context window "input + output combined" hota hai — iska practical impact kya hai jab tum ek long conversation ya large document ke saath kaam kar rahe ho?

Iska matlab hai tumhare available "budget" ka ek hissa response generate karne ke liye reserve karna padta hai — agar tumne apna poora context window input se hi bhar diya, model ke paas response likhne ke liye room hi nahi bachega. Long conversations mein har naya turn purana poora history carry karta hai (jab tak trim na kiya jaaye), isliye conversation naturally context limit ki taraf grow karti hai. Practical fix — purane messages ko summarize karna, sirf recent N messages retain karna, ya important facts ko separate memory system mein store karna (agent memory, chapter 9), aur bade documents ke liye pura dump karne ki jagah relevant chunks retrieve karna (RAG, chapter 4).

Q3. temperature aur top_p mein kya difference hai, aur ye dono ek saath aggressively tune karna generally kyun avoid kiya jaata hai?

Temperature poori probability distribution ko "sharpen" ya "flatten" karta hai (low = confident/likely tokens ki taraf bias, high = zyada spread-out/random selection). top_p (nucleus sampling) ek cutoff laga deta hai — sirf un tokens ko consider karta hai jinka cumulative probability ek threshold tak add ho, lambi-tail ke bahut unlikely tokens ko poori tarah discard kar deta hai. Dono ek saath aggressively badalna unpredictable interaction create karta hai (ek doosre ke effect ko amplify ya cancel kar sakta hai), isliye common practice hai ek ko fix rakho (usually top_p default pe) aur primarily temperature adjust karo, ya vice versa.

Q4. Structured data extraction ke liye tum kya sampling params choose karoge, aur kyun?

Low temperature (jaise 0 se 0.3) aur high/default top_p — kyunki structured extraction mein consistency aur predictability chahiye, creativity nahi. Explicit stop_sequences bhi useful hai agar output format ek clear boundary marker ke saath end hota ho. max_tokens ko tightly set karna bhi zaroori hai taaki response accidentally beech mein cut na ho na hi unnecessarily lamba ho jaaye, dono cost aur predictability ke liye.

Q5. Streaming responses production system mein kaunsi extra engineering complexity add karte hain, jo non-streaming request mein nahi hoti?

Sabse bada issue partial/incomplete data handle karna hai — agar structured output (jaise JSON) stream ho raha hai, chunk boundary kisi bhi arbitrary jagah pe aa sakta hai, isliye tumhe incremental parser chahiye ya poora accumulate karke hi parse karna padega. Connection drop/retry logic bhi alag hoti hai kyunki tumhe track karna padta hai stream kahan tak pahuncha tha resume/retry ke liye. Token usage/cost info bhi aksar sirf stream ke end mein final event ke saath milta hai, real-time cost tracking ke liye additional handling chahiye hoti hai.
