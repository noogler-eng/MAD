MCP Deep-Dive

RAG wale chapter mein humne dekha LLM ko data kaise doon. Ab sawaal ye hai — LLM ko tools aur live systems se kaise connect karoon, without har naye tool ke liye custom glue code likhe? Yahi problem Model Context Protocol (MCP) solve karta hai — is chapter mein hum ye samjhenge ki ye andar se kaam kaise karta hai, aur apna khud ka MCP server aur client bhi banayenge.

MCP Kya Hai Aur Kyun Bana

Sabse simple mental model: "HTTP web ke liye jo kaam karta hai, MCP AI context/tools ke liye wahi kaam karta hai." HTTP se pehle, har browser aur har server ko apna khud ka custom protocol invent karna padta — chaos. HTTP ek standard bana diya, aur ab koi bhi browser kisi bhi server se baat kar sakta hai bina custom integration ke. MCP exactly yahi standardization AI tools/data ke liye la raha hai.

Problem jo MCP solve karta hai — usko N×M integration problem kehte hain. Socho tumhare paas N AI applications hain (Claude Desktop, Claude Code, tumhara custom agent, VS Code extension...) aur M tools/data sources hain (GitHub, Postgres, Slack, internal CRM, file system...). MCP se pehle, har application ko har tool ke liye alag custom integration likhni padti thi — matlab N × M integrations. Agar 10 apps aur 20 tools hain, wo 200 custom integrations hain, sab maintain karna, sab break hote rehte hain jab koi API change hoti hai.

MCP is N×M problem ko N+M problem mein convert kar deta hai. Ek tool ek MCP server banata hai (ek baar), aur koi bhi MCP-compatible client (Claude Desktop, Claude Code, custom agent) use kar sakta hai bina us tool ke liye specific code likhe. Tool builder ek baar likhta hai, sab clients isse use kar sakte hain. Anthropic ne ye protocol open-standard ke roop mein release kiya (2024 ke end mein), aur ab OpenAI, Google jaise players bhi MCP support kar rahe hain — matlab ye industry-wide standard ban raha hai, na ki sirf ek company ka proprietary format.

📌 MCP "naya" LLM capability nahi hai

Important clarification — MCP khud koi naya AI capability introduce nahi karta. LLMs already tool calling kar sakte the (chapter 6 mein detail milega). MCP sirf ye standardize karta hai ki tools ko discover kaise kiya jaaye aur expose/transport kaise kiya jaaye — taaki tool-building ecosystem fragment na ho. Ye ek plumbing/protocol layer hai, model intelligence layer nahi.

MCP Architecture — Host, Client, Server

MCP teen components ke around design kiya gaya hai:

  • Host — wo application jisme user directly interact karta hai, jaise Claude Desktop ya Claude Code. Host LLM ko run karta hai aur user-facing UI provide karta hai.
  • Client — host ke andar ek component jo ek specific MCP server ke saath 1:1 connection maintain karta hai. Agar host 3 alag MCP servers se connect hai (e.g. GitHub, Postgres, filesystem), to host ke andar 3 separate client instances honge, har ek apne server ke saath.
  • Server — wo lightweight program jo actual tools/data/prompts expose karta hai. Server GitHub API ko wrap kar sakta hai, ya ek database ko, ya local file system ko — jo bhi capability tum LLM ko dena chahte ho.

Flow kuch is tarah chalta hai — jab user Claude Code mein kuch poochta hai jisme koi tool chahiye (jaise "meri repo ke open issues list karo"), host LLM ko batata hai "ye tools available hain" (client ne pehle hi server se tool discovery karke ye list le li thi — ek list_tools request bhejke). LLM decide karta hai kaunsa tool call karna hai aur kaunse arguments ke saath. Client us call ko server tak forward karta hai (call_tool request), server actual kaam karta hai (jaise GitHub API hit karna), aur result wapas client → host → LLM ke context mein jaata hai. LLM phir us result ko dekhke apna final response banata hai.

🧠 Senior Dev Note — Server ko "dumb" rakho

Achha MCP server design principle — server sirf capability expose karta hai, decision making nahi karta. "Kaunsa tool call karna hai" wala reasoning LLM (host side) karta hai, server sirf jo call kiya gaya wahi execute karta hai aur result return karta hai. Agar tum server ke andar bhi "smart" logic dalna shuru karoge (jaise server khud decide kare ki konsa tool chain karna hai), tum architecture ko confuse kar rahe ho — wo agent ka kaam hai (chapter 7), server ka nahi. Server = capability provider, Agent/LLM = decision maker. Ye separation testing aur debugging dono ko drastically simpler banata hai.

Transport Layer — stdio Aur HTTP/SSE

MCP messages JSON-RPC 2.0 format mein encode hote hain (ek lightweight, well-established RPC spec — request mein method aur params hote hain, response mein result ya error). MCP khud transport-agnostic hai — wo bas JSON-RPC messages ka format define karta hai, unhe actually bhejne ka kaam "transport" layer ka hai. Do primary transports common hain:

TransportKaise kaam karta haiKab use karo
stdioServer ek local subprocess ke roop mein spawn hota hai; client stdin pe likhta hai, server stdout pe reply karta haiLocal tools — filesystem, local scripts, local DB. Claude Desktop/Code ka most common case.
HTTP + SSE / Streamable HTTPServer ek remote HTTP endpoint hai; requests POST hoti hain, responses (streaming ke liye) Server-Sent Events se aate hainRemote/hosted MCP servers — jaise team-wide shared tool server, ya SaaS product ka MCP integration.

Practical mein — jab tum local development kar rahe ho ya ek personal tool bana rahe ho, stdio simplest hai (koi networking setup nahi chahiye, bas ek executable). Jab tum ek tool ko team ya multiple users ke liye share karna chahte ho, HTTP-based transport chahiye hoga taaki server ek jagah host ho sake aur multiple clients usse connect kar sakein.

Tool Metadata — Description Field Kyun Critical Hai

Har tool jo server expose karta hai, teen cheezein declare karta hai:

  • name — unique identifier, jaise fetch_crypto_price.
  • description — natural language mein batata hai tool kya karta hai, kab use karna chahiye.
  • input_schema — JSON Schema jo define karta hai tool ko kaunse arguments chahiye, kis type ke, konse required hain.

Ye teeno LLM ko tool-selection time pe dikhaye jaate hain (context mein inject hote hain jab request LLM ko jaati hai). Isliye description field ki quality directly affect karti hai ki LLM sahi tool pick karega ya nahi — LLM ke paas tool ka actual code dekhne ka koi tareeka nahi hai, usko sirf ye metadata dikhta hai. Agar description vague hai ("gets data") ya do tools ke descriptions overlap karte hain, LLM confuse ho sakta hai aur galat tool call kar sakta hai, ya sahi tool ko galat arguments ke saath call kar sakta hai.

⚠️ Bad vs good description — real difference

Bad: "Gets price" — LLM ko pata nahi kis cheez ka price, kaunsa format, symbol kaise pass karna hai. Good: "Given a cryptocurrency symbol like BTC or ETH, real-time USD price fetch karta hai from a live market data API. Symbol uppercase ticker hona chahiye, full coin naam nahi (BTC, na ki Bitcoin)." — ye specific hai, format bataata hai, edge case (uppercase ticker) clarify karta hai. Ye same principle hai jo tumne prompt engineering (chapter 3) mein seekha — LLM ko jitna precise, unambiguous context doge, utna accurate uska decision hoga.

Practical — Apna MCP Server Banana

Chalo ek minimal MCP server banate hain Python ke official mcp SDK se, FastMCP-style (jo decorators use karke boilerplate kam karta hai). Ye server ek tool expose karega — fetch_crypto_price — jo ek public crypto API (CoinGecko) se live price fetch karega. Har line commented hai:

crypto_mcp_server.py — minimal MCP server ek tool ke saath
# crypto_mcp_server.py — MCP server jo live crypto price fetch karne ka tool expose karta hai
import httpx  # async-capable HTTP client, CoinGecko API call karne ke liye

from mcp.server.fastmcp import FastMCP  # FastMCP — decorators se tool registration handle karta hai

mcp = FastMCP("crypto-prices")  # server instance banao — "crypto-prices" iska display name hai

@mcp.tool()  # decorator — is function ko ek MCP tool banata hai, clients discover/call kar sakte hain
async def fetch_crypto_price(symbol: str) -> dict:  # signature se hi input_schema banta hai
    """Given a crypto ticker symbol (e.g. 'BTC', 'ETH'), fetch its current USD price.
    Symbol must be an uppercase ticker, not the full coin name.
    """  # docstring hi tool ki 'description' banti hai — FastMCP auto-extract karta hai

    symbol_to_id = {"BTC": "bitcoin", "ETH": "ethereum", "SOL": "solana"}  # ticker → CoinGecko coin-id map
    coin_id = symbol_to_id.get(symbol.upper())  # symbol ko uppercase normalize karke lookup karo

    if coin_id is None:  # agar symbol map mein nahi mila
        return {"error": f"Unknown symbol: {symbol}. Try BTC, ETH, or SOL."}  # readable error, exception nahi (LLM ko feedback milta hai)

    async with httpx.AsyncClient() as client:  # async HTTP client — request khatam hote hi cleanup
        response = await client.get(  # CoinGecko simple-price endpoint ko GET request
            "https://api.coingecko.com/api/v3/simple/price",  # base URL
            params={"ids": coin_id, "vs_currencies": "usd"},  # query params — konsa coin, konsi currency
        )  # request call yahan complete hoti hai
        response.raise_for_status()  # non-2xx status pe exception raise karo, silent failure mat hone do

    data = response.json()  # response body JSON dict mein parse karo — e.g. {"bitcoin": {"usd": 61234.5}}
    return {"symbol": symbol.upper(), "usd_price": data[coin_id]["usd"]}  # clean dict — yahi call_tool response ban ke client ko jaata hai

if __name__ == "__main__":  # script directly run hone par (import hone par nahi)
    mcp.run()  # default transport stdio hai — stdin/stdout pe JSON-RPC messages sunega

Notice karo — humne kahin bhi manually JSON-RPC handle nahi kiya, koi schema hand-likha nahi. FastMCP function signature (symbol: str) aur docstring se automatically input_schema aur description generate kar deta hai. Ye wahi principle hai jo pehle discuss kiya — docstring/description quality directly LLM ki tool-selection accuracy ko affect karti hai, isliye yahan bhi ek generic docstring likhne ke bajaye humne format aur edge case explicitly mention kiya.

Practical — Client Se Tool Discover Aur Call Karna

Ab dekhte hain client side se ye kaise dikhta hai — MCP Python SDK ka client hi use karke hum server ko subprocess ke roop mein spawn karenge, uske tools discover karenge, aur ek tool call karenge:

crypto_mcp_client.py — server se connect, tools discover, tool call karna
# crypto_mcp_client.py — minimal MCP client jo upar wale server se baat karta hai
import asyncio  # client/server dono async hote hain, isliye event loop chahiye

from mcp import ClientSession, StdioServerParameters  # session manager + stdio launch-config class

from mcp.client.stdio import stdio_client  # subprocess spawn karke stdin/stdout ko transport banata hai

server_params = StdioServerParameters(  # server ko kaise launch karna hai uski details
    command="python",  # server subprocess kis command se chalega
    args=["crypto_mcp_server.py"],  # us command ko diye jaane wale arguments — script path
)  # params object yahan complete hota hai

async def main():  # async entrypoint, kyunki MCP calls sab awaitable hain
    async with stdio_client(server_params) as (read_stream, write_stream):  # server process spawn, read/write streams milte hain
        async with ClientSession(read_stream, write_stream) as session:  # streams pe session banao — JSON-RPC wrap karta hai
            await session.initialize()  # MCP handshake — protocol version, capabilities exchange

            tools_response = await session.list_tools()  # discovery step — server se poochta hai "kaunse tools hain"
            for tool in tools_response.tools:  # response mein har tool ka name/description/input_schema hota hai
                print(f"Discovered tool: {tool.name} — {tool.description}")  # yahi metadata LLM ko dikhaya jaata hai

            result = await session.call_tool(  # actual tool invoke karo
                "fetch_crypto_price",  # jo tool call karna hai uska registered naam
                arguments={"symbol": "BTC"},  # input_schema ke hisaab se required arguments
            )  # call yahan complete hoti hai
            print(f"Tool result: {result.content}")  # result.content mein tool ka return value milta hai (price dict)

asyncio.run(main())  # event loop start karo aur async main() function run karo

Real-world mein (Claude Desktop, Claude Code), ye discovery-and-call flow automatically host ke andar hota hai — tumhe manually list_tools() aur call_tool() nahi likhna padta, host ye handle karta hai aur discovered tools ko LLM ke context mein inject kar deta hai. Ye example isliye important hai kyunki ye dikhata hai ki protocol level pe actually kya ho raha hai — jo debug karte waqt ya custom host banate waqt kaam aata hai.

MCP vs Plain Function Calling

Ye distinction bahut confusing hoti hai shuru mein, isliye clearly separate kar dete hain (agla chapter, chapter 6, isi function calling mechanism ko deep-dive karega):

  • Function/tool calling ek LLM-level mechanism hai — model ko tools ki ek list dikhayi jaati hai (name/description/schema, chahe wo kahin se bhi aayi ho), aur model decide karta hai "is user request ke liye mujhe konsa tool call karna chahiye, kaunse arguments ke saath". Ye har major LLM provider (Claude, GPT, Gemini) mein built-in capability hai.
  • MCP ek protocol/transport layer hai jo standardize karta hai un tools ko discover kaise karo aur call kaise karo, across different servers aur clients, without custom integration code likhe har baar.

Simplified: function calling batata hai LLM "kya" decide karta hai (kaunsa tool, kaunse args); MCP batata hai wo tools system mein "kahan se aate hain aur kaise wire hote hain". Tum function calling MCP ke bina bhi use kar sakte ho (khud se ek tool list hardcode karke, jaisa agle chapter mein karenge) — MCP sirf isko scale aur reusable banata hai jab tumhare paas multiple tools/servers/clients ka ecosystem ho.

Limitations Aur Mitigations

MCP powerful hai, lekin real production usage mein do common problems face hote hain:

1. Large Tool Results → Context Window Bloat

Agar koi tool ek bada result return karta hai — jaise ek database query jo 500 rows deti hai, ya ek file-read tool jo poori 50-page document return kar deta hai — wo pura result LLM ke context window mein chala jaata hai. Isse context bloat hota hai: cost badh jaati hai (zyada tokens), latency badh jaati hai, aur agar context limit hit ho gaya to model bhool sakta hai purani conversation ke important parts. Mitigation — tool ke andar hi result ko chunk ya summarize karo before return karne ke, ya agar data bada/searchable type ka hai, use vector store mein daal do (RAG pipeline, chapter 4 dekho) aur tool sirf top-relevant chunks return kare, poora dataset nahi.

2. Too Many Tools Exposed → Selection Accuracy Drops

Jab ek host multiple MCP servers se connected hota hai (GitHub + Postgres + Slack + internal tools), LLM ke context mein saare tools ki descriptions ek saath ja sakti hain — kabhi kabhi 50-100+ tools. Research aur practical experience dono batate hain ki jitne zyada tools ek saath dikhaye jaate hain, LLM ki tool-selection accuracy utni hi girti hai (similar tools confuse hote hain, ya model galat tool pick kar leta hai). Mitigations:

  • Tool namespacing/grouping — tools ko logical groups mein organize karo (jaise github.*, db.*) taaki naming clarity rahe aur similar-sounding tools clash na karein.
  • Progressive discovery — sab tools ek saath expose karne ke bajaye, LLM ko pehle ek high-level "which category of tool do I need" decide karne do, aur uske baad hi us category ke specific tools load/expose karo. Ye ek two-step discovery hai — chapter 6 aur 8 mein isko agent design ke context mein aur detail se dekhenge.
  • Sirf wahi MCP servers connect karo jo current task ke liye actually relevant hain — "connect everything by default" anti-pattern hai.
🚨 Security angle bhi yaad rakho

MCP server jo bhi data return karta hai wo LLM ke context mein untrusted input ki tarah treat hona chahiye — agar koi tool external/user-controlled data fetch karta hai (jaise ek webpage ya email), us data ke andar embedded instructions ho sakti hain jo LLM ko manipulate karne ki koshish karein (prompt injection). Ye topic chapter 13 (Production Hardening) mein detail se cover hoga, lekin abhi itna samajh lo — MCP tool result ko "trusted system output" mat maano, wo bhi ek attack surface hai.

Key Takeaways

  • MCP "HTTP for AI tools/context" hai — N×M custom-integration problem ko N+M problem mein convert karta hai, ek open standard ke through.
  • Architecture teen parts mein bant-ta hai — Host (user-facing app), Client (ek server ke saath 1:1 connection), Server (tools/data ko expose karta hai).
  • Messages JSON-RPC 2.0 format mein hote hain; transport stdio (local) ya HTTP/SSE (remote/shared) ho sakta hai.
  • Tool metadata (name, description, input_schema) hi LLM ko dikhta hai — description ki quality directly tool-selection accuracy determine karti hai.
  • MCP aur function calling alag layers hain — function calling LLM-level "kya karna hai" decision hai, MCP protocol-level "tools kahan se aate hain, kaise wire hote hain" hai.
  • Limitations — bade tool results context bloat karte hain (chunk/summarize ya vector-store karo), bahut saare tools ek saath expose karna accuracy girata hai (namespacing/progressive discovery se fix karo).

🎯 Interview Questions

Q1. MCP kya hai aur ye kis problem ko solve karta hai — apne words mein explain karo.

MCP (Model Context Protocol) ek open standard hai jo AI applications ko external tools/data sources se connect karne ka standardized tareeka deta hai — isko "HTTP for AI context/tools" bola ja sakta hai. Ye N×M integration problem (N applications × M tools, sab custom-wired) ko N+M problem mein convert karta hai — tool builder ek MCP server ek baar banata hai, aur koi bhi MCP-compatible client (Claude Desktop, Claude Code, custom agent) usse bina extra integration code ke use kar sakta hai.

Q2. MCP architecture ke teen main components kya hain aur unka role kya hai?

Host — user-facing application jo LLM run karta hai (jaise Claude Desktop). Client — host ke andar ek component jo ek specific MCP server ke saath 1:1 connection maintain karta hai (multiple servers connected hain to multiple client instances honge). Server — lightweight program jo actual tools/data/prompts expose karta hai, jaise GitHub API ya database ko wrap karke. Server sirf capability provide karta hai, decision-making (kaunsa tool kab call karna hai) LLM/host side pe hoti hai.

Q3. Ek MCP tool ki description field itni important kyun hai?

LLM ko tool ka actual code nahi dikhta — usko sirf metadata (name, description, input_schema) dikhta hai tool-selection decision lene ke liye. Agar description vague ya ambiguous hai, ya multiple tools ke descriptions overlap karte hain, LLM galat tool pick kar sakta hai ya sahi tool ko galat arguments ke saath call kar sakta hai. Isliye description ko specific hona chahiye — kya karta hai, kab use karna hai, format/edge-cases kya hain — bilkul waise jaise prompt engineering mein clear/unambiguous instructions important hoti hain.

Q4. MCP aur function calling mein kya difference hai — kya ye same cheez hai?

Nahi, ye alag layers hain. Function/tool calling ek LLM-level mechanism hai jahan model decide karta hai "is request ke liye kaunsa tool call karna hai, kaunse arguments ke saath" — ye capability har major LLM provider mein built-in hai, MCP ke bina bhi use ho sakti hai. MCP ek protocol/transport layer hai jo standardize karta hai un tools ko discover aur call kaise kiya jaaye across different servers/clients, bina custom integration code baar-baar likhe. Function calling batata hai "kya" decide hota hai, MCP batata hai "kahan se tools aate hain aur kaise wire hote hain".

Q5. Production mein bahut saare MCP tools expose karne se kya problem hoti hai, aur kaise fix karoge?

Jab bahut saare tools (50-100+) ek saath LLM ke context mein expose hote hain, tool-selection accuracy girti hai — similar-sounding tools confuse hote hain, model galat tool pick kar sakta hai. Fix karne ke tareeke — tool namespacing/grouping karo (logical prefixes jaise github.*) taaki naming clarity rahe, "progressive discovery" pattern use karo (pehle high-level category decide karo, phir us category ke specific tools hi load karo), aur sirf wahi servers connect karo jo current task ke liye relevant hain — sab kuch by default connect karna anti-pattern hai.
