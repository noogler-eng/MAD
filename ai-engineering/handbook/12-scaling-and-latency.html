Ek LLM Request Ki Latency Anatomy — End to End

Jab tumhara user "Send" dabata hai aur unhe response dikhne mein 3 second lagte hain, wo 3 second ek single block nahi hai — kai alag-alag stages ka sum hai. In stages ko samajhna zaroori hai kyunki har stage ko fix karne ka alag tareeka hai, aur galat stage optimize karne mein time waste karna common mistake hai.

StageKya ho raha haiKis cheez pe control hai
Network round-tripClient → provider server tak request jaana, response wapas aanaMostly provider/CDN — tum region choose kar sakte ho
QueueingProvider ke paas request GPU pe schedule hone se pehle wait karti hai (load ke hisaab se)Tumhare control mein nahi, lekin retry/backoff strategy se manage hota hai
TTFT (Time to First Token)Prefill phase — poora input prompt process hota hai pehle output token generate hone se pehleInput prompt length — chhota prompt = fast TTFT
Inter-token latencyDecode phase — har output token ek-ek karke generate hota haiOutput length (max_tokens), model size
App-level latencyRetrieval (RAG), tool calls, post-processing, guardrail checksPoori tarah tumhare control mein — ye "your code" hai

Zyada beginners sochte hain "LLM latency" ek monolithic number hai jo sirf model ki speed pe depend karta hai. Reality mein aksar biggest latency contributor tumhari apni app hoti hai — RAG retrieval slow hai, sequential tool calls hain, ya prompt itna bada hai ki prefill hi seconds le raha hai. Isliye latency debug karte waqt sabse pehla step hamesha ye hai: end-to-end request ko stages mein break karo aur measure karo har stage individually kitna time le raha hai, guess mat karo.

📌 TTFT vs Total Latency — dono alag metrics hain

TTFT (Time to First Token) batata hai user ko response dikhna kab shuru hoga — ye perceived responsiveness ke liye critical hai. Total latency batata hai poora response complete hone mein kitna time laga — ye batch jobs ya non-streaming use cases ke liye relevant hai. Chapter 11 (System Design) mein hum streaming architecture discuss kar chuke hain — is chapter mein hum kyun TTFT aur inter-token latency alag behave karte hain, wahi samjhenge.

Prefill vs Decode — Alag Kyun Behave Karte Hain

Ye is poore chapter ka sabse important mental model hai, isliye dhyaan se samjho. Ek LLM request internally do phases mein hoti hai, aur ye dono phases fundamentally different compute characteristics rakhte hain:

  • Prefill (input processing) — model poore input prompt (system prompt + context + user message) ko ek saath process karta hai taaki wo samajh sake "context kya hai". Ye step parallelizable hai — GPU ek saath saare input tokens pe attention compute kar sakta hai, kyunki saare input tokens already available hain (koi sequential dependency nahi). Isi wajah se prefill fast hota hai relative to its token count — GPUs parallel compute mein bahot achhe hain.
  • Decode (output generation) — model ek-ek token generate karta hai, aur har naya token generate karne ke liye usse pichhle saare tokens (input + ab tak generate hue output) dekhne padte hain. Ye step inherently sequential hai — token N+1 generate karne se pehle token N ka result pata hona zaroori hai (autoregressive generation). Isliye decode phase parallelize nahi ho sakta across tokens — har token apni baari ka wait karta hai.

Practical implication: longer OUTPUTS latency ko zyada hurt karte hain compared to longer INPUTS, token-count ke hisaab se. 1000 extra input tokens prefill mein parallelize ho jaate hain aur TTFT thoda hi badhaate hain. Lekin 1000 extra output tokens ka matlab hai 1000 additional sequential steps — jo directly total generation time mein add hote hain. Yahi wajah hai ki agar tumhara use case latency-sensitive hai, "output ko concise rakho" (via prompting ya max_tokens) input trimming se aksar zyada impactful lever hota hai.

🧠 Senior Dev Note — "input vs output" latency budget ko explicitly design karo

Jab tum ek AI feature design karo, explicitly socho: "iska output kitna lamba hona chahiye?" Ek summarization feature jiska output 3 lines hai, chahe input 50 pages ho, decode phase short hoga isliye overall latency reasonable rahegi. Lekin ek "generate a detailed report" feature jiska output 2000 tokens hai, wo inherently slow hoga chahe input chhota ho — kyunki decode sequential hai. Agar product requirement allow kare, output length ko structurally chhota rakhna (bullet points ki jagah ek summary field, ya streaming ke saath progressive disclosure) latency ka sabse bada lever hai jo tumhare control mein hai.

KV Cache — Engineering-Level Samajh

Decode phase sequential hone ke bawajood, ek important optimization hai jo isse itna slow hone se bachati hai: KV cache (Key-Value cache). Yahan poori attention math nahi karenge — sirf itna samajhna kaafi hai jo tumhare engineering decisions ko inform kare:

  • Har token ko process karte waqt, model kuch internal tensors compute karta hai (called "keys" aur "values") jo represent karte hain "ye token kis cheez ke baare mein hai". Agar model naya token generate kare aur usse pichhle saare tokens ke liye ye tensors dobara compute karne pade, decode extremely slow ho jaata.
  • Isliye model in key/value tensors ko cache kar leta hai jaise-jaise woh process hote hain — pehli baar compute karo, GPU memory mein store kar do, aur agle token ke liye reuse karo. Har naye token ke liye sirf us naye token ke liye key/value compute karna padta hai, poore conversation ke liye nahi.
  • Yahi mechanism hai jo conversation history reuse ko practically fast banata hai — agar tum ek multi-turn conversation continue kar rahe ho, provider (agar wo cache retain karta hai) ko poori history dobara "samajhni" nahi padti processing ke terms mein.
  • Engineering-relevant side-effect: KV cache GPU memory consume karta hai, aur uska size context length ke proportional hai. Yahi ek reason hai ki lambi context windows provider-side pe expensive hoti hain — sirf "compute" nahi, memory bhi bottleneck banta hai. Ye tumhare liye directly relevant hai kyunki providers isi wajah se lambe context requests ko zyada charge karte hain aur/ya lower rate limits dete hain.
📌 Itna hi samajhna kaafi hai

Tumhe KV cache ki exact math (attention formula) implement nahi karni — tum inference engine nahi bana rahe. Bas ye samajhna hai: "already-processed tokens ka result reusable hai, isliye repeated prefixes ko cache karna latency aur cost dono bachata hai" — aur yahi principle agle section, prompt caching, ka foundation hai.

Prompt Caching — Real Latency + Cost Win

Major provider APIs (Anthropic prompt caching, OpenAI ka automatic prefix caching) ne KV cache ke isi idea ko ek client-facing feature bana diya hai. Agar tumhari app baar-baar ek same prefix bhejti hai (ek lamba system prompt, tool definitions, ya ek RAG document jo multiple queries ke liye reuse hota hai), provider us prefix ka KV-state cache kar sakta hai request-to-request — matlab agli baar wahi prefix aane pe, provider ko usse dobara prefill (process) nahi karna padta.

Ye dono cheezein deta hai: latency (cached prefix ka prefill time skip ho jaata hai — bade system prompts ke liye ye seconds bacha sakta hai) aur cost (cached input tokens providers typically bahot kam rate pe charge karte hain, kabhi-kabhi ~90% discount).

prompt_caching.py — Anthropic-style API mein cacheable system prompt block
# prompt_caching.py — reusable large system prompt ko cache-marked block ke saath bhejna
import anthropic  # anthropic ka official Python SDK import karo

# client — API key env var se automatically pick ho jaati hai (ANTHROPIC_API_KEY)
client = anthropic.Anthropic()  # Anthropic client instance banao

# LARGE_SYSTEM_PROMPT — ye har request mein same rehta hai (tool defs, instructions, style guide)
# isko baar-baar prefill karna wasteful hai, isliye ise cache-mark karenge
LARGE_SYSTEM_PROMPT = """You are a customer support assistant for Acme Corp...
... (lamba, detailed, 2000+ token system prompt, jo shayad hi kabhi change hota hai) ...
"""  # multi-line string mein poora stable system prompt

def ask_with_cached_prompt(user_message: str) -> str:
    # ask_with_cached_prompt — user query bhejta hai, system prompt ko cache-eligible mark karke
    response = client.messages.create(
        model="claude-sonnet-4-5",  # jo bhi model use kar rahe ho
        max_tokens=1024,  # output ko bounded rakho — decode time bachane ke liye
        system=[  # system prompt ko ek list of blocks ke roop mein bhejo (string ki jagah)
            {
                "type": "text",  # block ka type — plain text content
                "text": LARGE_SYSTEM_PROMPT,  # wahi stable, lamba system prompt daalo
                "cache_control": {"type": "ephemeral"}  # is block ko cache karne ke liye mark karo
            }
        ],
        messages=[
            {"role": "user", "content": user_message}  # actual per-request user query — ye change hota rehta hai
        ],
    )
    # agli calls mein agar system prompt exactly same rahe, provider cached KV-state reuse karega
    # — prefill skip, latency kam, aur cached input tokens sasti rate pe charge hote hain
    return response.content[0].text  # model ka text response return karo
⚠️ Don't cache aggressively without an invalidation strategy

Prompt caching sirf tab kaam karta hai jab prefix exactly same rahe — ek single character change bhi cache miss cause kar sakta hai. Ye especially RAG-heavy apps mein risky hai jahan tum retrieved documents ko cacheable block mein daalne ka soch sakte ho — agar underlying document set change hota rehta hai (naye documents add ho rahe hain, purane update ho rahe hain), tumhara "cached context" stale ho sakta hai, ya cache hit rate itna low ho jaayega ki caching se koi fayda hi nahi milega. Rule of thumb: sirf genuinely stable prefixes cache karo (system prompts, tool definitions, static style guides) — dynamic, frequently-changing content (fresh retrieval results, real-time data) ko cache-marked block mein mat daalo, aur agar cache karna hi hai to explicit TTL/invalidation strategy define karo.

Streaming — Perceived Latency Ka Trick

Chapter 11 mein humne streaming ko architecture ke level pe touch kiya tha — yahan iska latency angle samjhte hain. Streaming total generation time ko change nahi karta — agar model ko 500 tokens generate karne mein 5 seconds lagte hain, streaming ke saath bhi 5 seconds hi lagenge. Jo change hota hai wo hai perceived latency — user ko pehla token dikhna shuru ho jaata hai TTFT ke baad hi (typically sub-second se 1-2 second), poore response ka wait karne ke bajaye.

Psychologically ye bahot bada difference hai — ek user jo dekh raha hai text progressively appear ho raha hai, feel karta hai system "kaam kar raha hai" aur responsive hai, jabki wahi user agar 5 second blank screen dekhe (fir poora response ek saath aaye), usse system "hung" ya "slow" lagta hai — chahe total time same ho.

stream_to_client.py — LLM stream consume karke SSE ke through client ko forward karna
# stream_to_client.py — FastAPI endpoint jo LLM se stream leke SSE format mein client ko bhejta hai
from fastapi import FastAPI  # FastAPI framework import karo
from fastapi.responses import StreamingResponse  # chunked response bhejne ke liye class
import anthropic  # Anthropic SDK import karo

app = FastAPI()  # FastAPI app instance banao
client = anthropic.Anthropic()  # Anthropic client instance banao

async def event_generator(user_message: str):
    # event_generator — LLM se token-by-token aane wale chunks ko SSE events mein convert karta hai
    with client.messages.stream(  # streaming mode mein API call kholo (context manager)
        model="claude-sonnet-4-5",  # model choose karo
        max_tokens=1024,  # output length bound karo — rambling se decode time waste na ho
        messages=[{"role": "user", "content": user_message}],  # user ka query bhejo
    ) as stream:  # stream object ko 'stream' naam do
        for text_chunk in stream.text_stream:  # jaise-jaise naye tokens/chunks aate hain, loop karo
            yield f"data: {text_chunk}\n\n"  # SSE format — 'data: ' prefix aur double newline terminator
    yield "event: done\ndata: [DONE]\n\n"  # stream khatam hone pe ek explicit 'done' event bhejo

@app.post("/chat/stream")  # POST route define karo jo streaming response degi
async def chat_stream(user_message: str):
    # chat_stream — endpoint handler jo event_generator ko StreamingResponse mein wrap karta hai
    return StreamingResponse(
        event_generator(user_message),  # generator function pass karo jo chunks yield karega
        media_type="text/event-stream",  # browser ko batao ye SSE stream hai (EventSource API compatible)
    )
    # client-side EventSource ya fetch+ReadableStream se ye chunks progressively receive karega
    # — user ko pehla token TTFT ke turant baad dikhega, poore response ka wait nahi karna padega

Provider-Side Batching Aur Iska Tumpe Impact

Since tum khud inference host nahi kar rahe (chapter scope ke hisaab se), provider apne GPUs pe multiple concurrent requests ko batch karta hai — matlab ek saath kai users ke requests ek GPU pass mein process ho jaate hain, kyunki GPU compute mostly memory-bandwidth-bound hota hai aur batching throughput ko dramatically improve karta hai (per-request cost bhi kam hota hai).

Ye tumhare liye practical implication rakhta hai, chahe tum batching khud implement nahi kar rahe:

  • Rate limits — providers rate limits (requests/min, tokens/min) is liye enforce karte hain taaki unka batching aur capacity planning predictable rahe. Ye tumhari app ke liye ek hard constraint hai jo tumhe design mein account karna hoga.
  • Bursty traffic tumhari khud ki latency ko degrade kar sakta hai — agar tum suddenly 100 requests ek saath fire karte ho (e.g., ek batch job, ya ek viral traffic spike), tum rate limit errors (HTTP 429) hit karoge, jo retries trigger karega, jo further latency add karega — ek cascading slowdown.
  • Isliye recommendation ye hai: apne side pe explicit request queuing/backpressure implement karo — bajaye ki har incoming request seedha provider ko fire ho, ek queue (jaise Redis-backed job queue, ya simple in-process semaphore) se concurrency ko bound karo, taaki tum apni khud ki traffic ko provider ke rate limits ke andar smooth rakho, aur users ko graceful "queued" state dikha sako bajaye raw 429 errors ke.

Apne App-Level Scaling Levers

Ye section sabse actionable hai — kyunki inference internals (KV cache, batching) provider control karta hai, lekin ye levers poori tarah tumhare control mein hain:

  1. Full response caching (semantic, not just exact-match) — agar users similar queries baar-baar poochhte hain ("refund policy kya hai?", "how do I get a refund?"), exact-string matching cache miss dega, lekin embeddings ke through semantic similarity check karke tum cache hit paa sakte ho. Full implementation neeche Practical Code section mein hai.
  2. Independent LLM/tool calls ko parallelize karo — agar tumhare pipeline mein multiple independent steps hain (e.g., 3 alag retrieval sources query karna), unhe sequential await se chalane ki jagah asyncio.gather() se parallel chalao. Sequential teen 500ms calls = 1.5s; parallel teeno = ~500ms.
  3. Speculative/optimistic UI patterns — jab tak final LLM response stream ho raha hai, jo cheezein already available hain (jaise RAG se retrieved source documents) unhe turant dikha do UI mein — "Sources" panel turant populate karo, "Answer" panel streaming ke saath fill ho. User ko feel hota hai system already kaam kar raha hai.
  4. Model tiering/routing — jaisa chapter 10 mein cover kiya, simple/routine requests ko chhote, faster models pe route karo (jinka TTFT aur decode dono fast hote hain), aur complex requests hi bade models tak jaane do. Ye latency aur cost dono ek saath improve karta hai.
  5. Prompt size reduce karo — prefill time (aur cost) input tokens ke proportional scale karta hai. Unnecessary context trim karo, purani conversation history ko summarize karo (chapter 9 ke memory techniques use karke), aur sirf relevant RAG chunks bhejo — bloat directly latency mein translate hota hai.
  6. Appropriate max_tokens set karo — decode sequential hai, isliye model ko rambling se roko. Agar tumhe pata hai response ~200 tokens ka hona chahiye, max_tokens ko unbounded (jaise 4096 default) chhodna galat hai — model rambling continue kar sakta hai aur decode time waste karta hai (aur tokens ke liye tum charge bhi ho rahe ho).
parallel_retrieval.py — sequential awaits ko asyncio.gather se parallelize karna
# parallel_retrieval.py — teen independent retrieval sources ko parallel query karna
import asyncio  # asyncio import karo concurrent coroutines chalane ke liye

async def query_vector_db(query: str) -> list:
    # query_vector_db — vector database se semantic matches fetch karta hai (async I/O call)
    await asyncio.sleep(0.4)  # simulate karo ki ye network call 400ms leti hai
    return ["doc_a", "doc_b"]  # retrieved documents return karo

async def query_sql_db(query: str) -> list:
    # query_sql_db — structured data source se relevant rows fetch karta hai
    await asyncio.sleep(0.3)  # simulate karo ki ye call 300ms leti hai
    return ["row_1"]  # retrieved rows return karo

async def query_web_search(query: str) -> list:
    # query_web_search — external web search tool call karta hai
    await asyncio.sleep(0.5)  # simulate karo ki ye call 500ms leti hai (sabse slow)
    return ["result_x"]  # search results return karo

async def gather_context_slow(query: str):
    # gather_context_slow — ANTI-PATTERN: sequential awaits, total time = 0.4+0.3+0.5 = 1.2s
    a = await query_vector_db(query)  # pehle vector db ka wait karo
    b = await query_sql_db(query)  # fir sql db ka wait karo (a khatam hone ke baad hi shuru hua)
    c = await query_web_search(query)  # fir web search ka wait karo (b khatam hone ke baad)
    return a + b + c  # saare results combine karke return karo

async def gather_context_fast(query: str):
    # gather_context_fast — CORRECT: teeno independent calls ko parallel chalao
    a, b, c = await asyncio.gather(  # asyncio.gather saare coroutines ko concurrently schedule karta hai
        query_vector_db(query),  # in teeno mein koi dependency nahi, isliye parallel chal sakte hain
        query_sql_db(query),  # dusra independent call
        query_web_search(query),  # teesra independent call
    )  # total time = max(0.4, 0.3, 0.5) = 0.5s — 2.4x faster than sequential
    return a + b + c  # saare results combine karke return karo

Apne Backend Ka Horizontal Scaling

Ye lever "model latency" se related nahi hai, lekin equally important hai jab traffic badhta hai — tumhare khud ke backend ko scale karna, jo requests ko orchestrate karta hai (retrieval, LLM calls, post-processing).

  • Stateless services behind a load balancer — tumhara API layer stateless hona chahiye (session state Redis/DB mein, in-memory nahi) taaki tum horizontally scale kar sako — jitna traffic badhe, utne instances spin up kar do, load balancer requests distribute karega.
  • Connection pooling to the LLM provider — har request pe naya HTTP connection establish karna (TLS handshake overhead) wasteful hai. HTTP client libraries (jaise httpx) connection pooling support karti hain — reuse existing connections across requests.
  • Circuit breakers/timeouts — agar LLM provider slow ho jaaye ya down ho jaaye, bina timeout ke tumhare backend threads/connections un slow calls pe hang ho jaayenge — ek cascading failure jo poori app ko down kar sakta hai (thread pool exhaustion). Har external call pe explicit timeout lagao, aur circuit breaker pattern use karo (agar failure rate threshold cross kare, temporarily calls fail-fast kar do bajaye retry karte rehne ke) taaki ek slow dependency poore system ko na le doobe.

Practical Code — Semantic Response Cache

Ye is chapter ka main hands-on example hai. Idea simple hai: agar do queries semantically similar hain (chahe exact words alag ho), unke liye same cached response return kar do — LLM call skip karke latency aur cost dono bacha lo.

semantic_cache.py — embedding-based semantic response cache
# semantic_cache.py — incoming queries ko embed karke similarity-based cache lookup karna
import numpy as np  # numpy import karo vector math (dot product, norm) ke liye
import anthropic  # Anthropic SDK import karo LLM call ke liye
from openai import OpenAI  # embeddings ke liye OpenAI client (ya koi bhi embedding provider)

llm_client = anthropic.Anthropic()  # LLM calls ke liye Anthropic client
embed_client = OpenAI()  # embeddings generate karne ke liye alag client

SIMILARITY_THRESHOLD = 0.92  # cosine similarity threshold — isse upar match "same query" mana jaata hai

# _cache — in-memory store: har entry mein {embedding, query_text, response} rehta hai
# production mein isko Redis/vector DB (Pinecone, pgvector) se replace karo persistence ke liye
_cache: list[dict] = []  # khaali list se shuru karo, requests ke saath grow hoga

def _embed(text: str) -> np.ndarray:  # helper: text -> embedding vector
    # _embed — text ko embedding vector mein convert karta hai (helper function)
    result = embed_client.embeddings.create(  # embeddings API call kholo
        model="text-embedding-3-small",  # chhota, fast embedding model — cache lookup ke liye kaafi hai
        input=text,  # jo text embed karna hai (yahan query)
    )  # API call ke arguments yahan close ho rahe hain
    return np.array(result.data[0].embedding)  # raw embedding list ko numpy array mein convert karke return karo

def _cosine_similarity(a: np.ndarray, b: np.ndarray) -> float:  # helper: do vectors ki similarity
    # _cosine_similarity — do vectors kitne "similar direction" mein hain, 0 se 1 ke beech
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))  # standard cosine similarity formula

def _find_cached_response(query_embedding: np.ndarray) -> str | None:  # helper: cache lookup
    # _find_cached_response — cache mein sabse similar past query dhoondta hai
    best_score = 0.0  # ab tak ka best similarity score track karo
    best_response = None  # corresponding cached response track karo
    for entry in _cache:  # cache ke har entry pe loop karo (production mein ANN index use karo, linear scan nahi)
        score = _cosine_similarity(query_embedding, entry["embedding"])  # is entry se similarity nikaalo
        if score > best_score:  # agar ye ab tak ka best match hai
            best_score = score  # best_score update karo
            best_response = entry["response"]  ># corresponding cached response save karo
    if best_score >= SIMILARITY_THRESHOLD:  # agar best match threshold se upar hai
        return best_response  # cache hit — cached response return karo
    return None  # cache miss — koi close enough match nahi mila

def ask_with_semantic_cache(query: str) -> str:  # main entry point
    # ask_with_semantic_cache — main entry point: cache check karo, warna LLM call karke cache mein daalo
    query_embedding = _embed(query)  # incoming query ko embed karo

    cached = _find_cached_response(query_embedding)  # cache mein similar query dhoondo
    if cached is not None:  # agar match mil gaya
        return cached  # seedha cached response return karo — koi LLM call nahi, near-zero latency

    # cache miss — ab hi actual LLM call karna padega
    response = llm_client.messages.create(  # Anthropic API ko call karo
        model="claude-sonnet-4-5",  # model choose karo
        max_tokens=1024,  # output length bound karo
        messages=[{"role": "user", "content": query}],  ># user ka query bhejo
    )  # API call arguments yahan close
    answer = response.content[0].text  # model ka text response nikaalo

    _cache.append({  # is naye query-response pair ko cache mein add karo future lookups ke liye
        "embedding": query_embedding,  # future similarity comparisons ke liye embedding store karo
        "query_text": query,  # debugging/inspection ke liye original text bhi rakho
        "response": answer,  ># actual cached response
    })  # naya cache entry dictionary yahan close hota hai
    return answer  # fresh response return karo

Notice karo: SIMILARITY_THRESHOLD = 0.92 ek tuning knob hai — bahot high rakhoge to cache hit rate low hoga (fayda kam), bahot low rakhoge to false-positive matches denge (galat cached answer ek different query ko return ho jaayega). Production mein isko apne actual query distribution pe empirically tune karna padega, aur RAG-based answers ke liye especially conservative rehna chahiye (upar warn callout dekho — underlying data change hone pe cache stale ho sakta hai).

🧠 Senior Dev Note — semantic cache ko RAG ke saath carefully combine karo

Agar tumhara response RAG retrieval pe based hai, semantic cache ka response tabhi valid hai jab underlying documents same rahe hon. Practical pattern: cache key mein sirf query embedding nahi, balki retrieved document IDs ka hash bhi shaamil karo — agar retrieval result change ho jaaye (naya document match hua, ya purana update hua), cache automatically invalidate ho jaaye. Isse tum caching ka latency/cost fayda bhi paate ho, aur stale-RAG-answer wala risk bhi avoid karte ho jo warn callout mein discuss kiya gaya tha.

Key Takeaways

  • LLM request latency stages mein break hoti hai — network, queueing, TTFT (prefill), inter-token latency (decode), aur app-level latency (retrieval/tools). Debug karte waqt guess mat karo, har stage individually measure karo.
  • Prefill parallelizable hai (poora input ek saath process), decode sequential hai (har token pichhle pe depend karta hai) — isliye longer outputs latency ko zyada hurt karte hain compared to longer inputs.
  • KV cache model ko pehle-processed tokens ke liye recompute karne se bachata hai — ye conversation reuse aur prompt caching dono ka foundation hai, aur context length ke saath memory cost bhi badhata hai.
  • Prompt caching (Anthropic/OpenAI APIs) stable prefixes (system prompts, tool defs) ke liye prefill skip karta hai — bada latency aur cost win, lekin sirf genuinely stable content ke liye, changing RAG context ke liye nahi.
  • Streaming total generation time change nahi karta, sirf perceived latency improve karta hai — user pehla token TTFT ke baad hi dekhna shuru kar deta hai.
  • Provider batching tumhare liye rate limits ka roop leta hai — bursty traffic apni khud ki latency degrade kar sakta hai, isliye apne side pe request queuing/backpressure implement karo.
  • Sabse actionable levers tumhare app ke andar hain: semantic caching, parallel tool/LLM calls (asyncio.gather), speculative UI, model tiering, prompt trimming, aur bounded max_tokens.
  • Apna backend bhi horizontally scale karna padta hai — stateless services, connection pooling, aur circuit breakers/timeouts taaki ek slow LLM call cascading failure na bane.

🎯 Interview Questions — Senior AI Engineer

Q1. Prefill aur decode phases mein kya difference hai, aur ye latency ko practically kaise affect karta hai?

Prefill mein model poore input prompt ko ek saath process karta hai — ye parallelizable hai kyunki saare input tokens already available hain, GPU unpe ek saath compute kar sakta hai. Decode mein model ek-ek output token generate karta hai, aur har token pichhle saare tokens (input + ab tak generate hue output) pe depend karta hai — ye inherently sequential hai, parallelize nahi ho sakta. Practical implication: longer outputs latency ko token-count ke hisaab se zyada hurt karte hain compared to longer inputs, isliye output length control karna (max_tokens, concise prompting) ek high-leverage latency optimization hai.

Q2. KV cache kya hai, aur ye engineering decisions ko kaise inform karta hai (bina attention math mein jaaye)?

KV cache model ke internal key/value tensors ko store karta hai jaise-jaise tokens process hote hain, taaki agle token generate karte waqt unhe dobara compute na karna pade — sirf naye token ke liye compute hota hai. Iska engineering-relevant implication: (1) repeated prefixes (system prompts, conversation history) ko cache karna fast hai kyunki underlying KV-state reusable hai — yahi prompt caching ka foundation hai; (2) context length ke saath KV cache ka memory footprint bhi badhta hai, isliye providers lambi context windows ko zyada expensive/rate-limited rakhte hain.

Q3. Prompt caching kab use karni chahiye, aur kab NAHI karni chahiye?

Prompt caching tab use karo jab tumhare paas ek genuinely stable prefix ho jo repeatedly reuse hota hai — large system prompts, tool definitions, static style guides. Ye prefill time skip karta hai (latency win) aur cached tokens ko discounted rate pe charge karta hai (cost win). NAHI use karni chahiye jab content frequently change ho — jaise dynamic RAG retrieval results jo underlying document set ke saath badalte rehte hain, kyunki ek single character change bhi cache miss cause karta hai, aur agar tum stale content ko galti se cache-marked block mein daalo, wo ek staleness risk create karta hai (purana context serve ho sakta hai).

Q4. Streaming latency ko "improve" karta hai — kya isme koi nuance hai?

Streaming total generation time ko change NAHI karta — agar model ko poora response generate karne mein 5 seconds lagte hain, streaming ke saath bhi utna hi time lagega. Jo change hota hai wo hai perceived latency — user pehla token TTFT ke turant baad dekhna shuru kar deta hai, poore response ka wait karne ke bajaye. Ye psychologically bahot bada difference hai kyunki progressive text appearance user ko "system kaam kar raha hai" feel karwaata hai, jabki blank-screen-then-full- response pattern "hung/slow" feel karwaata hai — chahe total time same ho.

Q5. Tumhari app pe traffic spike aata hai aur latency degrade ho jaati hai. LLM provider ka fault nahi hai (unka status page green hai) — root cause kya ho sakta hai, aur kaise fix karoge?

Likely cause: provider apne side pe concurrent requests batch karta hai aur rate limits enforce karta hai capacity planning ke liye — bursty traffic se tum rate limit errors (429) hit kar sakte ho, jo retries trigger karta hai aur latency ko cascade karta hai. Fix: apne side pe explicit request queuing/backpressure implement karo (jaise concurrency-bounded queue) taaki provider ko bheji jaane wali traffic smooth rahe, apne backend mein circuit breakers/timeouts lagao taaki slow calls thread/ connection exhaustion cause na karein, aur load balancer ke peeche stateless horizontally-scaled services rakho taaki apna khud ka backend bottleneck na bane.
