Agent Kya Hota Hai — Precise Definition

"Agent" word bahut loosely use hota hai — kabhi koi bas ek chatbot ko bhi "agent" bula deta hai. Precisely define karte hain: ek agent ek system hai jahan LLM ko ek goal aur tools diye jaate hain, aur LLM ek loop mein khud decide karta hai ki next kya karna hai — kaunsa tool call karna hai, kya observe hua uske basis pe kya karna hai — jab tak goal achieve na ho jaaye ya koi stop condition hit na ho.

Key phrase yahaan hai "loop mein khud decide karta hai". Ek single prompt→response call — chahe wo tool calling use kare — agent nahi hai agar developer ne already decide kar rakha hai ki kaunsa tool kab call hoga. Agent tab banta hai jab LLM ka output khud decide karta hai ki control flow mein aage kya hoga — kaunsa tool, kis order mein, kab rukna hai — runtime pe, execution ke dauraan, na ki developer ne pehle se hardcode kiya ho.

📌 Chapter 6 se connection

Chapter 6 mein humne tool calling ka mechanism dekha — schema define karna, LLM ka tool-call request parse karna, result wapas bhejna. Wo mechanism hi hai jo agent ka "Act" step possible banata hai. Is chapter mein hum us mechanism ko ek loop ke andar daalte hain jahan LLM khud decide karta hai kitni baar aur kaunse tools call karne hain — yehi difference hai ek "tool-calling feature" aur ek "agent" ke beech.

Agentic vs Workflow — Control Flow Kaun Decide Karta Hai

Ye distinction production AI engineering mein sabse important architectural decision hai, aur bahut log isse miss kar dete hain kyunki dono mein LLM calls involved hote hain. Fark control flow mein hai:

  • Workflow (fixed pipeline) — developer ne pehle se code mein decide kar rakha hai ki steps kya hain aur kis order mein chalenge: "pehle summarize karo, phir translate karo, phir classify karo". LLM sirf har step ka output generate karta hai — control flow (agla step kaunsa hoga) hardcoded hai, if-else ya sequential function calls mein.
  • Agentic (LLM-driven loop) — developer sirf goal aur available tools deta hai. LLM khud runtime pe decide karta hai ki kaunsa tool call karna hai, kitni baar, aur kab rukna hai. Control flow LLM ke output se emerge hota hai, code mein pehle se likha nahi hota.

Dono approaches LLM calls use karti hain — fark ye hai ki "agla step kya hoga" ye decision kaun le raha hai: developer (workflow) ya LLM khud (agent), runtime pe.

🧠 Senior Dev Note — Kab kaunsa use karo

Workflow use karo jab task predictable hai aur steps pehle se maloom hain — jaise "resume parse karo → structured fields nikaalo → database mein save karo". Ye cheaper hai (fixed number of LLM calls, koi wasted iteration nahi), zyada reliable/auditable hai (tum exactly bata sakte ho ki har run mein kya hoga), aur debug karna easy hai. Agent use karo jab task open-ended hai aur steps unpredictable hain — jaise "is customer complaint ko research karo, relevant policy dhoondo, aur ek resolution propose karo" — jahan zaroori steps request se request badalte hain aur pehle se hardcode nahi kiye ja sakte. Golden rule: agar tum confidently ek flowchart draw kar sakte ho jo har case cover kare, workflow banao. Agar flowchart mein bahut saare "??? depends on what happens" branches hain, agent zaroori hai. Production mein zyadatar teams shuru mein overkill agents banate hain jab simple workflow kaafi hota — agent ka extra flexibility latency, cost, aur unpredictability ki keemat pe aata hai, isliye pehle workflow try karo, agent tab jab genuinely zaroorat ho.

ReAct Pattern — Reason → Act → Observe

Sabse popular agent loop pattern hai ReAct (Reasoning + Acting, 2022 paper se aaya hai). Idea simple hai: agent har action se pehle explicitly reason karta hai (ek reasoning trace generate karta hai — "mujhe X karna hoga kyunki Y"), phir ek action leta hai (tool call), phir action ka result observe karta hai, aur is cycle ko repeat karta hai jab tak answer na mil jaaye.

Ye "plain tool-calling loop" (bas tools call karte jaao jab tak done na ho) se better kyun hai? Kyunki reasoning trace ko explicitly generate karwana model ko apna intent likhne pe majboor karta hai — jo galat assumptions ko surface pe le aata hai before wo ek galat tool call ban jaayein. Agar model directly action pe jump kare bina reasoning ke, wo aksar ambiguous cases mein galat tool ya galat parameters choose kar leta hai. Explicit "Thought:" step model ko force karta hai ki wo pehle plan articulate kare — jo empirically hallucination aur galat tool selection dono kam karta hai, kyunki model apne hi likhe hue reasoning se consistent rehne ki koshish karta hai (yehi chain-of-thought ka core benefit hai, ab tool use ke saath combine kiya hua).

StepKya hota haiKyun zaroori hai
Reason (Thought)Model likhta hai ki abhi situation kya hai aur next kya karna chahiyeIntent explicit banata hai, galat assumptions ko early catch karta hai
Act (Action)Model ek tool call karta hai (specific tool + arguments)Reasoning ko concrete, executable step mein convert karta hai
Observe (Observation)Tool ka result loop mein wapas feed hota haiModel ko real-world data milta hai jo uske internal knowledge se accurate ho sakta hai

Step-by-Step Trace Example

Query: "Eiffel Tower jahan hai wahan ka weather kaisa hai?" — ye query direct answer nahi ho sakti kyunki model ko pehle location resolve karni hai, phir us location ka current weather fetch karna hai (jo model apne training data se nahi jaan sakta — real-time data hai). Trace kuch is tarah dikhega:

react-trace.txt — agent ka internal reasoning trace
Thought 1: User ko Eiffel Tower ki location ka current weather chahiye. Mujhe
           pehle pata karna hoga Eiffel Tower kis city/coordinates mein hai,
           uske baad hi weather tool call kar sakta hoon (weather tool ko
           city name ya lat/long chahiye, "Eiffel Tower" nahi).
Action 1:  search_location(query="Eiffel Tower")  # Reason se decide hui tool call, place-name se location dhoondne ke liye
Observation 1: {city: "Paris", country: "France", lat: 48.8584, lon: 2.2945}  # tool ka result loop mein wapas feed hua

Thought 2: Location mil gayi — Paris, France (48.8584, 2.2945). Ab main
           weather tool ko ye coordinates de sakta hoon current weather ke liye.
Action 2:  get_weather(lat=48.8584, lon=2.2945)  # Observation 1 se mile coordinates ko yahaan use kiya
Observation 2: {temp_c: 19, condition: "Partly cloudy", humidity: 62}  # weather tool ka result — real-time data, model ke training se nahi

Thought 3: Mujhe location aur weather dono data mil chuke hain. Ab main
           final answer compose kar sakta hoon, aur koi tool call nahi chahiye.
Final Answer: Eiffel Tower Paris, France mein hai, jahan abhi 19°C aur partly  # no tool call = stop condition #1 (natural finish)
              cloudy weather hai (humidity 62%).

Notice karo — agar agent directly "call weather tool" pe jump karta bina pehle location resolve kiye (plain tool-loop jisme koi explicit reasoning nahi hota), wo galti se get_weather("Eiffel Tower") jaisa invalid call kar sakta tha, ya worse — apni training data se Paris ka koordinate "yaad" karke hallucinate kar sakta tha bina verify kiye. Explicit "Thought" step ne is dependency (pehle location, phir weather) ko surface kiya before action lene se pehle.

Planning — Single-Shot vs Interleaved Re-planning

ReAct loop mein har step pe reasoning hoti hai, lekin ek separate design decision hai: agent poora plan pehle se bana le, ya step-by-step re-plan karta rahe?

  • Single-shot planning — agent shuru mein hi ek complete plan likhta hai ("Step 1: X karo, Step 2: Y karo, Step 3: Z karo") aur phir usi plan ko execute karta hai bina beech mein reconsider kiye. Trade-off: cheap hai (planning ke liye ek hi LLM call), predictable hai (tum plan ko upfront review/approve kar sakte ho — auditability), lekin brittle hai — agar step 2 ka result unexpected nikla (jaise tool ne error diya, ya data expected se different nikla), agent ke paas plan adapt karne ka built-in mechanism nahi hai jab tak explicitly re-plan trigger na ho.
  • Interleaved re-planning — agent har observation ke baad apna plan reconsider karta hai (yehi ReAct loop naturally karta hai — har "Thought" ek chhota re-plan hai). Trade-off: zyada adaptive hai — reality plan se diverge kare to agent turant adjust kar sakta hai (jaise ek tool fail ho jaaye to alternative approach try kare) — lekin costlier hai (har step pe ek extra LLM call ka reasoning overhead) aur latency zyada hoti hai kyunki agent sequentially step-by-step sochta hai instead of ek baar mein pura plan generate karke parallel-executable steps nikaalna.

Practical middle ground bhi common hai: agent shuru mein ek rough high-level plan banaye (single-shot, cheap), lekin har step ke baad us plan ko ek chhoti reasoning step se revise/confirm kare (interleaved) — isse dono ke benefits milte hain, purely single-shot ki brittleness aur purely interleaved ka full overhead dono avoid ho jaate hain.

Stop Conditions — Agent Ko Rukna Kab Chahiye

Agent loop ek open-ended while loop hai — usse pata hona chahiye kab rukna hai, warna wo infinitely tool calls karta reh sakta hai (cost aur latency dono ke liye disaster). Teen mechanisms combine karke ye handle hota hai:

  1. Model khud final answer deta hai (no more tool calls) — jab model ka response mein koi tool-call request nahi hoti, sirf plain text answer hota hai, ye natural signal hai ki model ne decide kiya hai ki goal achieve ho gaya hai aur ab final answer de raha hai. Primary/expected stop condition.
  2. Explicit "done"/"finish" tool — kuch designs mein ek dedicated tool hota hai jaise finish_task(answer=...) jo model ko explicitly call karna hota hai jab wo done ho — ye zyada structured hai kyunki loop ko exactly pata chalta hai "ye terminal action thi" (bajaye heuristically detect karne ke ki response mein tool call hai ya nahi).
  3. Max iteration guard (safety net) — chapter 6 mein humne ye already dekha tha tool-calling loop mein. Agent loop mein bhi zaroori hai — agar model kisi wajah se (ambiguous goal, buggy tool, model confusion) endlessly tool calls karta rahe, ek hard cap (jaise max_iterations = 10) loop ko force-terminate karta hai. Ye "normal" stop condition nahi hai, ye ek safety net hai jo production mein runaway costs aur infinite loops se bachata hai.
⚠️ Max iteration guard hamesha zaroori hai, chahe kitna bhi "smart" model ho

Ye sochna galti hai ki "hamara model kaafi capable hai, wo khud hi ruk jaayega". Production mein edge cases guaranteed aate hain — ek tool jo baar-baar retry-able error return karta hai, ek ambiguous goal jiska koi clean stopping point nahi, ya model ka koi rare reasoning loop jahan wo apne hi pichhle steps ko repeat karta hai. Max iteration guard bina exception ke non-negotiable hai — isse graceful degradation milta hai (loop terminate hoke ek "I could not complete this task" jaisa response deta hai) instead of silently runaway cost accumulate karne ke.

Practical Code — Scratch Se ReAct Agent Loop

Chalo ek minimal working ReAct agent loop banate hain Python mein — bina kisi heavy agent framework (LangChain, LlamaIndex, etc.) ke, taaki underlying mechanism poora transparent ho. Ye wahi while loop hai jo har production agent framework ke andar chhupa hota hai.

react_agent.py — scratch se minimal ReAct agent loop
# react_agent.py — ek minimal ReAct-style agent loop, kisi framework ke bina
import json  # tool arguments aur results ko JSON mein serialize/parse karne ke liye
from anthropic import Anthropic  # Anthropic ka official Python SDK, LLM calls ke liye

client = Anthropic()  # API client banaya — env var se API key uthaata hai automatically

# --- Step 1: tools define karo jo agent use kar sakta hai ---
def search_location(query: str) -> dict:  # pehla tool — place name se location resolve karta hai
    # real implementation mein ye ek geocoding API (jaise OpenStreetMap Nominatim) call karega
    # yahaan demo ke liye hardcoded response — production mein actual HTTP call hoga
    return {"city": "Paris", "lat": 48.8584, "lon": 2.2945}  # dict return, JSON-serializable hona chahiye

def get_weather(lat: float, lon: float) -> dict:  # doosra tool — coordinates se current weather fetch karta hai
    # real implementation mein ye ek weather API (jaise OpenWeatherMap) call karega
    return {"temp_c": 19, "condition": "Partly cloudy"}  # demo response, production mein live data hoga

# tool name se Python function tak mapping — Action step mein isse hi tool ko actually call karenge
TOOL_REGISTRY = {  # dict literal khulta hai — naam-to-function mapping shuru
    "search_location": search_location,  # string name -> actual callable function
    "get_weather": get_weather,  # string name -> actual callable function
}  # dict literal band — TOOL_REGISTRY ab ready hai lookup ke liye

# --- Step 2: tool schemas define karo jo model ko diye jaayenge (API ke expected format mein) ---
TOOL_SCHEMAS = [  # list of dicts — dono tools ke schemas, API ke expected shape mein
    {  # pehla schema — search_location ke liye
        "name": "search_location",  # model isi naam se tool ko refer karega apne response mein
        "description": "Kisi landmark/place ke naam se uski city aur coordinates dhoondo",  # model isi se decide karta hai kab use karna hai
        "input_schema": {  # is tool ke expected arguments ka JSON Schema
            "type": "object",  # input ek JSON object hoga
            "properties": {"query": {"type": "string", "description": "landmark ya place ka naam"}},  # ek required string field
            "required": ["query"],  # query field mandatory hai
        },  # input_schema dict band
    },  # search_location schema entry band
    {  # doosra schema — get_weather ke liye
        "name": "get_weather",  # dusra tool — weather fetch karne ke liye
        "description": "Diye gaye lat/lon coordinates ka current weather batao",  # model isse samjhega ki ye coordinates leta hai, place-name nahi
        "input_schema": {  # is tool ke expected arguments ka JSON Schema
            "type": "object",  # input ek JSON object hoga
            "properties": {"lat": {"type": "number"}, "lon": {"type": "number"}},  # do numeric fields
            "required": ["lat", "lon"],  # dono coordinates mandatory hain
        },  # input_schema dict band
    },  # get_weather schema entry band
]  # TOOL_SCHEMAS list band — model.create() ke tools= param mein isi ko pass karenge

# --- Step 3: agent loop khud — ye hi core mechanism hai jo har agent framework ke andar chhupa hota hai ---
def run_agent(user_goal: str, max_iterations: int = 8) -> str:  # entry point — goal aur safety cap dono liye
    # messages list — poore conversation ka accumulated history (system ke through user, assistant, tool results sab)
    messages = [{"role": "user", "content": user_goal}]  # pehla message user ka goal hai

    # max_iterations tak loop chalao — ye hamara safety-net stop condition hai (chapter 6 se pattern)
    for iteration in range(max_iterations):  # range(8) matlab max 8 reasoning+action cycles allowed
        # LLM ko call karo — poori accumulated history + available tools ke saath
        response = client.messages.create(  # call khulta hai — arguments neeche
            model="claude-sonnet-4-5",  # jo bhi current model version use karna hai
            max_tokens=1024,  # response ki max length
            tools=TOOL_SCHEMAS,  # model ko batate hain kaunse tools available hain
            messages=messages,  # poori history bhejte hain taaki model ko context mile ki ab tak kya hua
        )  # create() call band — response ab humare paas hai

        # model ka response conversation history mein add karo (taaki agla call isse context mein dekh sake)
        messages.append({"role": "assistant", "content": response.content})  # assistant turn save kiya

        # check karo ki response mein koi tool-call request hai ya nahi
        tool_calls = [block for block in response.content if block.type == "tool_use"]  # sirf tool_use blocks filter kiye

        # --- Stop condition #1: agar koi tool call nahi hai, model final answer de chuka hai ---
        if not tool_calls:  # tool_calls empty list hai matlab model ne plain text answer diya
            final_text = "".join(block.text for block in response.content if block.type == "text")  # saare text blocks joda
            return final_text  # loop se exit — ye normal, expected termination hai

        # --- Act step: har requested tool call ko actually execute karo ---
        tool_results = []  # is iteration ke saare tool results yahaan collect honge
        for call in tool_calls:  # model ek turn mein multiple tools bhi call kar sakta hai
            fn = TOOL_REGISTRY[call.name]  # model ne diya tool-name registry mein lookup karke actual function nikaala
            try:  # tool call fail ho sakta hai (bad args, network error) — isliye guard kiya
                result = fn(**call.input)  # tool ko model ke diye gaye arguments ke saath call kiya
            except Exception as e:  # agar tool fail ho (bad input, network error, etc.)
                result = {"error": str(e)}  # error ko bhi ek result ki tarah wapas bhejenge — crash nahi karenge

            # --- Observe step: result ko tool_result block format mein wrap karo ---
            tool_results.append({  # is call ka result tool_results list mein joda ja raha hai
                "type": "tool_result",  # API ko batata hai ye ek tool ka output hai
                "tool_use_id": call.id,  # model ke original tool-call se match karne ke liye ID
                "content": json.dumps(result),  # result ko JSON string mein serialize kiya
            })  # is tool result dict ka append() call band

        # saare tool results ek "user" turn ki tarah history mein append karo (API convention)
        messages.append({"role": "user", "content": tool_results})  # observations loop ke agle iteration ke liye context bante hain
        # loop yahaan se wapas top pe jaata hai — model ab in observations ko dekhega aur agla Thought/Action banayega

    # --- Stop condition #2: max_iterations exhaust ho gaye bina final answer ke ---
    return "Agent max iterations tak pahunch gaya bina final answer ke — task adhoora chhoda."  # safety-net exit, graceful degradation

# --- Usage ---
answer = run_agent("Eiffel Tower jahan hai wahan ka weather kaisa hai?")  # agent ko goal diya
print(answer)  # final answer print karo — agent ne khud decide kiya kitne aur kaunse tool calls chahiye the

Is code mein teeno cheezein clearly dikh rahi hain jo humne upar discuss ki: loop (for iteration in range(max_iterations)), accumulated message history (messages list jo har turn ke baad grow hoti hai), aur dono stop conditions (no tool calls = natural finish, max_iterations exhausted = safety net). Notice karo ki run_agent function ko bilkul nahi pata ki kitne steps lagenge ya kaunse tools kis order mein call honge — ye sab LLM ke response se runtime pe decide hota hai. Yehi hai wo fundamental difference jo ise ek "workflow" se agent banata hai.

💡 Hinglish Tip — Ek line mein sab kuch

Workflow mein developer control flow likhta hai, agent mein LLM control flow "likhta" hai (apne output se, runtime pe). ReAct pattern isi control flow ko reliable banata hai kyunki har action se pehle ek explicit reasoning step force karta hai. Planning ya to upfront (single-shot, cheap-lekin-brittle) ho sakti hai ya interleaved (adaptive-lekin-costly). Aur agent ko rukna teen tareekon se pata chalta hai — natural finish (no more tool calls), explicit done-tool, ya max-iteration safety net — teeno production mein zaroori hain, sirf pehla wala kaafi nahi.

Key Takeaways

  • Agent ek system hai jahan LLM ko goal + tools milte hain aur wo ek loop mein khud decide karta hai next kya karna hai — single prompt→response call agent nahi hai.
  • Workflow mein control flow developer decide karta hai (predictable, cheaper, auditable); agentic mein LLM runtime pe control flow decide karta hai (flexible, open-ended tasks ke liye zaroori).
  • ReAct pattern (Reason → Act → Observe) explicit reasoning trace force karta hai har action se pehle — ye galat tool selection aur hallucination dono kam karta hai plain tool-loop ke comparison mein.
  • Single-shot planning cheap/predictable hai lekin brittle; interleaved re-planning adaptive hai lekin costly (extra LLM calls, latency).
  • Agent ko teen tareekon se rukna chahiye: model khud final answer de (no tool calls), explicit "done" tool call ho, ya max iteration guard hit ho (safety net, always required).
  • Scratch se ReAct agent loop ek simple while/for loop hai jo accumulated message history ke saath LLM ko repeatedly call karta hai, tool calls execute karta hai, results history mein append karta hai, jab tak stop condition hit na ho.

🎯 Interview Questions

Q1. "Agent" aur "workflow" mein precisely kya fundamental difference hai — dono to LLM calls use karte hain?

Fark ye hai ki control flow kaun decide karta hai. Workflow mein developer pehle se code mein decide kar chuka hota hai ki steps kya hain aur kis order mein chalenge — LLM sirf har step ka output generate karta hai. Agent mein developer sirf goal aur tools deta hai, aur LLM khud runtime pe decide karta hai agla step kya hoga, kaunsa tool call karna hai, aur kab rukna hai. Dono LLM calls involve karte hain, lekin agent mein "agla kya hoga" ye decision LLM ke output se emerge hota hai, workflow mein wo pehle se hardcoded hota hai.

Q2. ReAct pattern mein explicit "Thought" step add karna kyun helpful hai — sirf directly tool call kyun nahi karwa dete?

Explicit reasoning trace model ko force karta hai apna intent likhne ke liye before action lene se pehle — jo ambiguous assumptions ko surface pe le aata hai jo warna silently ek galat tool call ban jaate. Jaise Eiffel Tower weather example mein, "Thought" step ne explicitly identify kiya ki weather tool ko coordinates chahiye, place-name nahi, isliye pehle location resolve karna zaroori hai. Bina explicit reasoning ke, model directly (aur galat tareeke se) weather tool ko "Eiffel Tower" string de sakta tha, ya apni training data se coordinates hallucinate kar sakta tha bina verify kiye.

Q3. Single-shot planning aur interleaved re-planning mein trade-off explain karo — ek real scenario do jahan single-shot fail ho sakta hai.

Single-shot planning cheap aur predictable hai (ek hi upfront LLM call plan ke liye), lekin brittle hai — agar reality plan se diverge kare, agent ke paas adapt karne ka built-in mechanism nahi hota. Jaise agar plan ka step 2 ek external API call kare jo error return kare (rate limit, service down), single-shot agent us error ko handle karne ka koi upfront-planned tareeka nahi rakhta. Interleaved re-planning har observation ke baad plan reconsider karta hai, isliye wo turant alternative approach try kar sakta hai — lekin cost/latency zyada hoti hai kyunki har step pe extra reasoning overhead hai.

Q4. Ek agent loop production mein infinite ho sakta hai kya, aur isse kaise prevent karte ho?

Haan — agar model ambiguous goal, buggy tool response, ya koi rare reasoning loop ki wajah se continuously tool calls karta rahe bina natural "final answer" pe pahunche, loop theoretically infinite chal sakta hai, jo cost aur latency dono ke liye disaster hai. Prevention teen-layer hai: primarily model khud final answer degi jab goal complete ho (no more tool calls), optionally ek explicit "done" tool structured termination ke liye, aur non-negotiable max_iterations guard jo hard cap enforce karta hai chahe upar wale dono na trigger hon — ye safety net hai jo graceful degradation deta hai instead of runaway execution.

Q5. Ek PM tumse poochta hai "hum is feature ko agent banayein ya simple pipeline?" — kaise decide karoge?

Sabse pehle poochunga: kya main confidently ek flowchart draw kar sakta hoon jo har realistic case cover kare? Agar haan — steps predictable hain, order fixed hai, cost/latency predictability important hai — to workflow banaunga, kyunki wo cheaper, faster, aur zyada auditable hoga. Agar flowchart mein bahut saare "depends on what happens" branches hain — task open-ended hai, required steps request-se-request badalte hain, ya external tool results unpredictable hain — to agent zaroori hai kyunki uski runtime flexibility hi asli value hai. Main hamesha pehle simpler workflow approach try karta hoon; agent tab introduce karta hoon jab genuinely evidence ho ki fixed pipeline insufficient hai, kyunki agent ka overhead (latency, cost, unpredictability) free nahi hai.
