Single-Agent Architecture — Recap Aur Limits

Chapter 7 ka agent ek simple shape follow karta tha: ek LLM + ek tool registry + ek loop jo tab tak chalta rehta hai jab tak model final answer na de de (Thought → Action → Observation → repeat). Ye architecture surprisingly far tak le jaata hai — coding assistants, research agents, customer support bots, sab single-agent loop se hi shuru hote hain, aur bahut saare production systems isi shape mein permanently reh jaate hain kyunki unka scope kabhi itna bada nahi hota.

Lekin single-agent shape ke saath structural limits hain jo scope badhne pe surface hote hain:

ProblemKya hota hai
Tool selection confusion Jaise-jaise tool count 20-30+ tak badhta hai, model ke liye har turn pe "sahi tool kaunsa hai" decide karna harder hota jaata hai — similar-sounding tools (jaise search_docs vs search_web vs search_code) confuse karte hain, aur wrong-tool-call rate badh jaata hai.
Unbounded context growth Har tool call ka result conversation history mein add hota jaata hai. Ek long-running task mein (jisme 20+ tool calls ho sakte hain) context window bhar jaata hai, purane observations "push out" ho jaate hain ya aggressively summarize karne padte hain — quality degrade hoti hai.
Single point of failure Agar ek hi LLM call galat reasoning kare ya galat tool choose kare, poora task derail ho sakta hai — koi doosra "check" nahi hai jo catch kare.
Prompt specialization impossible Ek hi system prompt ko "research karo", "code likho", aur "customer ko politely reply karo" — teeno alag-alag behaviors ke liye kaam karna padta hai. Ye prompts ko either bloated (sab kuch cover karne ki koshish) ya generic (kisi ek task mein bhi excel nahi karta) bana deta hai.

Jab in mein se koi bhi problem genuinely bottleneck ban jaaye — tab hi multi-agent architecture consider karna chahiye. Neeche 5 patterns hain jo real production systems (LangGraph, CrewAI, OpenAI Swarm/Agents SDK, AutoGen) mein use hote hain.

1. Orchestrator-Worker (Planner-Executor)

Ek orchestrator LLM incoming task ko dekh kar usko 2-N chhote subtasks mein todta hai, har subtask ko ek specialized worker agent ko delegate karta hai, aur phir sab workers ke results ko wapas combine (aggregate) karke final answer banata hai.

Orchestrator-Worker — flow diagram (text)
          [User Task]
               |
               v
        [ Orchestrator LLM ]   -- task ko subtasks mein todta hai
          /      |      \
         v       v       v
    [Worker A][Worker B][Worker C]   -- parallel ya sequential run
         \       |       /
          v      v      v
        [ Orchestrator — Aggregate ]
               |
               v
          [Final Answer]

Pros: Workers ko independently, parallel mein run kiya ja sakta hai (wall-clock time bachta hai agar subtasks independent hain); har worker ka apna focused prompt ho sakta hai; orchestrator centrally decide karta hai ki kya karna hai, isliye overall flow predictable rehta hai.
Cons: Orchestrator khud ek single point of failure hai (agar galat plan banaye, poora task galat direction mein jaata hai); aggregation step tricky ho sakta hai agar worker outputs conflict karein.
Use case: "Competitor analysis report banao" — orchestrator isko break karta hai: Worker A pricing research kare, Worker B feature comparison kare, Worker C reviews/sentiment summarize kare — teeno parallel chalte hain, phir orchestrator ek unified report mein combine karta hai.

2. Supervisor Architecture (Router/Dispatcher)

Ek supervisor agent har conversational turn ko dekhta hai aur decide karta hai kaunsa specialist sub-agent us turn ko handle karega — phir sub-agent ka response wapas user tak (ya agle turn ke liye supervisor tak) route karta hai. Orchestrator-worker se key difference: yahaan task ek baar mein saare subtasks mein todha nahi jaata — har turn independently route hota hai, aur sub-agents kabhi ek doosre se directly baat nahi karte, sirf supervisor ke through.

Supervisor — flow diagram (text)
   [User Turn 1: "refund chahiye"]     [User Turn 2: "billing date?"]
              |                                    |
              v                                    v
        [ Supervisor ]  -------- routes -------- [ Supervisor ]
              |                                    |
              v                                    v
     [Refunds Sub-Agent]                  [Billing Sub-Agent]
              |                                    |
              v                                    v
          [Reply]                              [Reply]
   (sub-agents ek dusre se kabhi directly baat nahi karte)

Pros: Multi-turn conversations ke liye natural fit (customer support jaise use cases); har specialist ka prompt sirf apne domain pe focused rehta hai (billing agent ko refund logic jaanne ki zaroorat nahi); routing logic centralize hone se debugging easier hai (ek jagah dekho ki kis turn pe kaunsa agent chuna gaya).
Cons: Har turn pe ek extra "routing" LLM call lagta hai (latency/cost overhead); agar routing galat ho (wrong specialist choose ho jaaye), user ko galat/irrelevant answer milta hai.
Use case: Customer support platform jahan ek supervisor decide karta hai ki query "billing", "technical support", ya "returns" specialist ko jaani chahiye — jaisa Intercom/Zendesk style AI copilots aksar structure karte hain.

3. Sequential/Pipeline Multi-Agent

Agents ek fixed, deterministic order mein chain hote hain — Agent A ka output seedha Agent B ka input banta hai, jo aage Agent C ko feed hota hai. Ye ek assembly line jaisa hai — koi dynamic routing nahi, order hamesha same rehta hai.

Sequential Pipeline — flow diagram (text)
[Raw Input]
    |
    v
[Agent A: Extract]  --output-->  [Agent B: Summarize]  --output-->  [Agent C: Translate]
                                                                              |
                                                                              v
                                                                       [Final Output]

Pros: Predictable aur debuggable — order fixed hai, isliye tum exactly jaante ho kaunsa step pe failure hua; har agent ka prompt sirf ek narrow transformation ke liye optimize hota hai, jisse quality per-step high rehti hai.
Cons: Purely sequential hai — koi parallelization nahi, total latency sab agents ke latency ka sum hai; early stage ki galti pura downstream chain corrupt kar deti hai (garbage in, garbage through).
Use case: Document processing pipeline — Agent A raw PDF se structured data extract kare, Agent B usse ek executive summary mein convert kare, Agent C summary ko target language mein translate kare. Har step ka input/output contract clear hai, isliye pipeline shape natural fit hai.

4. Swarm / Peer-to-Peer Handoff

Koi central coordinator nahi hota — agents directly ek doosre ko control handoff kar sakte hain jab unhe lage ki current query unke scope se bahar hai. Ye pattern OpenAI ke Swarm (ab Agents SDK) framework ne popularize kiya — har agent ke paas ek "transfer_to_X" tool hota hai jo conversation control ko doosre agent ko de deta hai.

Swarm / Handoff — flow diagram (text)
[User: "mera order cancel karna hai, aur refund bhi chahiye"]
              |
              v
     [Triage Agent] -- "ye cancellation query hai" --> handoff
              |
              v
   [Cancellation Agent] -- "refund bhi chahiye, uska scope nahi" --> handoff
              |
              v
      [Refund Agent] -- final reply user ko
   (koi central "supervisor" nahi — agents khud decide karte hain kab handoff karna hai)

Pros: Decentralized, isliye naya specialist agent add karna easy hai (bas ek naya handoff target); triage → specialist flow bahut natural feel hota hai jaise real support team mein hota hai (reception se billing team ko transfer).
Cons: Central visibility/control nahi hai — debugging harder ho sakta hai kyunki control flow runtime pe decide hota hai, static diagram se predict nahi ho sakta; agents ke beech "handoff loop" (A → B → A → B) ka risk hota hai agar prompts sahi se scoped na hon.
Use case: Customer support triage — ek general "front-desk" agent pehle query sunta hai, phir usse sahi specialist (sales, billing, technical) ko directly handoff kar deta hai, aur agar beech mein scope change ho (billing se refund tak), specialist khud next specialist ko handoff kar sakta hai bina wapas front-desk se guzre.

5. Blackboard Pattern

Multiple agents ek shared state — "blackboard" — ko read/write karte hain. Koi central controller nahi decide karta ki kaunsa agent kab chalega — har agent independently apna contribution add karta hai jab bhi blackboard ki current state uske liye relevant lage. Ye loosely coupled hai — agents ek doosre ko directly jaante tak nahi.

Blackboard — flow diagram (text)
                    +-------------------------+
                    |     Shared Blackboard    |
                    |  (partial findings state) |
                    +-------------------------+
                     ^     ^      ^      ^
              read/write |  |      |      | read/write
                    [Agent 1] [Agent 2] [Agent 3]
                 (ek agent koi finding likhta hai,
                  doosra usko dekh kar apna contribution add karta hai)

Pros: Highly flexible — naye agents add karna easy hai bina existing flow todhe; parallel exploration ke liye best fit hai jahan tumhe pata nahi kaunsa agent kab useful contribution de sakta hai (jaise multiple diagnostic checks jo independently trigger ho sakte hain).
Cons: Coordination overhead high hai — race conditions possible hain (do agents same cheez pe simultaneously kaam karein); "kab task complete hua" decide karna hard hai kyunki koi central authority nahi (aksar ek separate "monitor" agent chahiye hota hai jo blackboard dekh kar completion detect kare).
Use case: Complex diagnostic/research system — jaise ek incident-investigation agent system jahan ek agent logs check karta hai, doosra metrics, teesra recent deploys — jo bhi anomaly dhoondhta hai wo blackboard pe likh deta hai, aur baaki agents us finding ko dekh kar apni investigation refine karte hain.

Comparison Table — Kaunsa Kab Use Karein

ArchitectureCoordination StyleBest ForDownsides
Orchestrator-Worker Central planner, upfront task decomposition Independent parallel sub-tasks (research, report generation) Orchestrator = single point of failure; aggregation tricky
Supervisor Central router, per-turn dispatch Multi-turn conversations across specialist domains Extra routing call har turn pe; misrouting risk
Sequential Pipeline Fixed deterministic chain Well-defined multi-stage transformations No parallelism; early errors propagate downstream
Swarm / Handoff Decentralized, peer-to-peer Triage-then-specialist support flows Low central visibility; possible handoff loops
Blackboard Shared state, loosely coupled Parallel exploration, uncertain agent relevance Race conditions; unclear completion signal

Har pattern ka ek common thread hai: N agents = N (ya zyada) LLM calls instead of 1. Ye latency aur cost dono ko multiply karta hai, aur debugging complexity bhi badhti hai (ab tumhe multiple prompts, multiple failure points, aur inter-agent communication trace karni padti hai).

⚠️ Multi-agent "silver bullet" nahi hai

Ek naya pattern dekh kar excited hoke seedha multi-agent design mat jump karo. Har extra agent apne saath latency (sequential agents ke liye especially) aur cost (har agent = apna LLM call, aur agar har agent ke paas multiple tool-calling turns hain to cost multiply hi hota hai) dono badhata hai. Ek 3-agent orchestrator-worker system jo sequentially chalta hai easily single-agent se 3-5x slower ho sakta hai agar workers ko parallel run karne ka infra nahi hai.

🧠 Senior Dev Note — Single-agent + good tools se shuru karo

Production mein sabse common mistake ye hai ki team directly multi-agent architecture design karti hai kyunki "ye sophisticated lagta hai", bina pehle verify kiye ki ek single, well-designed agent (achhe tools, clean context management, focused system prompt) kaafi nahi tha. Multi-agent tab justify hota hai jab: (a) tool count/context genuinely unmanageable ho gaya ho ek single agent ke liye, ya (b) independent sub-work ko parallelize karke real wall-clock time bachaya ja sakta ho (jaise 3 independent research streams). Agar dono conditions mein se koi bhi true nahi hai, multi-agent sirf latency, cost, aur coordination bugs add karega bina proportional benefit ke. Rule of thumb: pehle single agent ko iterate karo — better tool descriptions, better context pruning, better prompt — tabhi split karo jab measurable evidence ho ki single agent genuinely struggle kar raha hai.

Practical Code — Orchestrator-Worker Implementation

Neeche ek complete, minimal orchestrator-worker implementation hai Python mein — orchestrator user task ko structured output ke through 2-3 subtasks mein todta hai, har subtask ek independent worker LLM call ko dispatch hoti hai (focused prompt ke saath), aur last mein ek aggregation step sab worker outputs ko final answer mein combine karta hai. Har single line commented hai.

orchestrator_worker.py — orchestrator-worker pattern end-to-end
import json                                          # subtask list ko structured JSON se parse karne ke liye
from anthropic import Anthropic                       # Anthropic SDK client import karo

client = Anthropic()                                       # client instantiate karo (ANTHROPIC_API_KEY env var se uthata hai)
MODEL = "claude-sonnet-4-5"                                # saare agents (orchestrator + workers) is model ko use karenge


def plan_subtasks(user_task: str) -> list[dict]:            # orchestrator step — task ko subtasks mein todta hai
    """Orchestrator: user task ko 2-3 focused subtasks mein decompose karta hai."""  # docstring — function ka purpose
    system_prompt = (                                       # orchestrator ka system prompt — sirf planning karna hai, kaam khud nahi
        "Tum ek task planner ho. User ka task lo aur usse 2-3 independent, "  # instruction: kaam ko todo
        "focused subtasks mein todo. Har subtask ek worker agent ko diya jaayega. "  # instruction: har subtask ek worker ko jaayega
        "Sirf JSON array return karo, koi extra text nahi. Format: "  # strict output format enforce karna
        '[{"id": "t1", "goal": "..."}, {"id": "t2", "goal": "..."}]'  # exact JSON shape example de rahe hain (few-shot style)
    )                                                        # system_prompt string yahin close hota hai

    response = client.messages.create(                     # orchestrator LLM call — subtask breakdown maangna
        model=MODEL,                                        # kaunsa model use karna hai
        max_tokens=512,                                    # planning response chhota hona chahiye, isliye low limit
        system=system_prompt,                               # upar wala planning-only system prompt pass karo
        messages=[{"role": "user", "content": user_task}],  # actual user task ko user message ki tarah bhejo
    )                                                        # API call yahin complete hota hai

    raw_text = response.content[0].text.strip()            # response block se raw text nikaalo aur whitespace trim karo
    subtasks = json.loads(raw_text)                        # raw text ko JSON se Python list-of-dicts mein parse karo
    return subtasks                                       # parsed subtasks list orchestrator ko wapas do


def run_worker(subtask: dict) -> str:                    # worker step — ek focused subtask ko independently solve karta hai
    """Worker: ek single subtask ko apne khud ke focused LLM call se solve karta hai."""  # docstring
    worker_system = (                                       # worker ka system prompt — sirf apna subtask, kuch aur nahi
        "Tum ek focused worker agent ho. Sirf diya gaya subtask solve karo, "  # scope ko narrow rakhna — sirf ye ek subtask
        "concise aur factual answer do. Bahar ka context tumhe nahi pata, "  # worker ko baaki subtasks ka pata nahi hona chahiye (isolation)
        "isliye assumptions clearly state karo agar zaroorat pade."  # edge case handling instruction
    )                                                        # worker_system string yahin close hota hai

    response = client.messages.create(                     # worker LLM call — is subtask ke liye independent call
        model=MODEL,                                        # same model reuse kar rahe hain (chahe to alag/cheaper model bhi de sakte ho)
        max_tokens=400,                                    # worker answer bhi concise rakhna hai, isliye limit chhota
        system=worker_system,                               # worker-specific focused system prompt pass karo
        messages=[{"role": "user", "content": subtask["goal"]}],  # subtask ka "goal" field hi worker ka poora input hai
    )                                                        # API call yahin complete hota hai

    return response.content[0].text.strip()             # worker ka final text answer trim karke return karo


def aggregate_results(user_task: str, subtasks: list[dict], worker_outputs: list[str]) -> str:  # aggregation step
    """Orchestrator: sab worker outputs ko ek coherent final answer mein combine karta hai."""  # docstring
    combined_context = ""                                # empty string se shuru — yahaan sab subtask+output pairs jodenge
    for subtask, output in zip(subtasks, worker_outputs):    # har subtask ko uske corresponding worker output ke saath pair karo
        combined_context += f"Subtask ({subtask['id']}): {subtask['goal']}\n"  # subtask ka goal likho
        combined_context += f"Worker Result: {output}\n\n"  # uska worker result bhi neeche likho, blank line se separate

    aggregation_system = (                                  # aggregation ke liye alag, focused system prompt
        "Tum ek aggregator ho. Neeche diye gaye worker results ko dekh kar "  # instruction: worker results dekho
        "original user task ka ek single, coherent final answer banao. "  # instruction: final unified answer banao
        "Duplicate info hata do, contradictions flag karo agar ho."  # instruction: cleanup aur conflict-detection
    )                                                        # aggregation_system string yahin close hota hai

    response = client.messages.create(                     # aggregation LLM call — final orchestrator call
        model=MODEL,                                        # same model, final synthesis ke liye
        max_tokens=800,                                    # final answer thoda lamba ho sakta hai, isliye limit badi rakhi
        system=aggregation_system,                          # aggregation-specific system prompt pass karo
        messages=[{                                         # user message mein original task + saara combined context bhejo
            "role": "user",                                    # role field — user turn hai
            "content": f"Original task: {user_task}\n\n{combined_context}",  # original task + har worker ka context
        }],                                                  # messages list yahin close hota hai
    )                                                        # API call yahin complete hota hai

    return response.content[0].text.strip()             # final combined answer trim karke return karo


def run_orchestrator_worker(user_task: str) -> str:              # top-level entrypoint — poora flow yahaan se drive hota hai
    """Poora orchestrator-worker flow: plan -> dispatch -> aggregate."""  # docstring
    subtasks = plan_subtasks(user_task)                     # step 1: orchestrator se subtasks ki list maango
    print(f"Planned {len(subtasks)} subtasks: {[t['id'] for t in subtasks]}")  # debug visibility ke liye plan print karo

    worker_outputs = []                                     # empty list — har worker ka output yahaan collect hoga
    for subtask in subtasks:                                  # step 2: har subtask ke liye ek worker chalao
        print(f"Dispatching worker for: {subtask['id']}")   # debug visibility ke liye kaunsa subtask chal raha hai batao
        output = run_worker(subtask)                        # is subtask ko worker function ko dispatch karo (sequential yahaan;
        worker_outputs.append(output)                       # asyncio.gather se parallel bhi kiya ja sakta hai independent subtasks ke liye)

    final_answer = aggregate_results(user_task, subtasks, worker_outputs)  # step 3: sab outputs ko ek final answer mein combine karo
    return final_answer                                    # final aggregated answer caller ko wapas do


if __name__ == "__main__":                                 # script directly run hone pe hi ye block chalega
    task = "Hamare product ke liye competitor analysis banao: pricing, features, reviews"  # example user task
    answer = run_orchestrator_worker(task)                # poora orchestrator-worker flow run karo
    print("\n--- Final Answer ---\n")                    # separator print karo readability ke liye
    print(answer)                                        # final aggregated answer console pe print karo

Notice karo — is example mein orchestrator ka call 1, workers ke calls N (subtask count ke barabar), aur aggregation ka call 1 — total N+2 LLM calls ek single task ke liye, jabki single-agent approach mein wahi task 1 call (ya ek multi-turn tool-loop) mein solve ho sakta tha. Ye exactly wo "cost/latency multiply hota hai" wala trade-off hai jo upar discuss kiya — multi-agent tabhi worth hai jab parallelization ya specialization ka benefit is extra cost se zyada ho.

Key Takeaways

  • Single-agent architecture tab tak sahi hai jab tak tool count, context growth, aur task specialization manageable rahein — zyada tools se tool-selection confuse hota hai, aur context unbounded badhta hai.
  • Orchestrator-worker — central planner subtasks banata hai, specialized workers unhe solve karte hain, orchestrator hi aggregate karta hai. Independent parallel sub-work ke liye best.
  • Supervisor — har turn ko router centrally dispatch karta hai specialist sub-agents ko; sub-agents ek dusre se directly nahi baat karte. Multi-domain conversations ke liye best.
  • Sequential pipeline — deterministic assembly-line order (A→B→C); predictable lekin no parallelism, aur early errors downstream propagate karte hain.
  • Swarm/handoff — decentralized, agents khud control transfer karte hain (jaise OpenAI Swarm); triage-then-specialist flows ke liye natural fit.
  • Blackboard — shared state pe loosely-coupled agents read/write karte hain; parallel exploration ke liye flexible, lekin coordination/completion detection hard hai.
  • Har multi-agent pattern latency aur cost ko multiply karta hai (N agents ≈ N+ LLM calls) — isliye single-agent + good tools se hi shuru karo, aur multi-agent tabhi reach karo jab genuine evidence ho ki single agent struggle kar raha hai.

🎯 Interview Questions — AI/Agent Engineer

Q1. Single-agent architecture kab "break" hoti hai — kaunse specific signals dekh kar tum multi-agent consider karoge?

Chaar signals: (1) tool count itna badh gaya ho (20-30+) ki model wrong-tool-call karne lage kyunki similar tools confuse kar rahe hain; (2) context window unbounded badh raha ho kyunki task lambi chain of tool calls maangta hai; (3) agent ek single point of failure ban raha ho critical multi-step tasks mein; (4) task genuinely distinct specializations maang raha ho (research vs code vs customer tone) jo ek single system prompt mein cleanly fit nahi hote. Agar in mein se koi bhi measurable evidence ke saath present ho, tabhi multi-agent justify hota hai — sirf "sophistication" ke liye nahi.

Q2. Orchestrator-worker aur supervisor architecture mein kya fundamental difference hai?

Orchestrator-worker mein task ko upfront ek baar mein subtasks mein decompose kiya jaata hai, workers parallel/sequential chalte hain, aur ek aggregation step results ko combine karta hai — ye single-task-completion ke liye design hota hai. Supervisor architecture per-turn routing karta hai — har naya conversational turn independently ek specialist ko dispatch hota hai, koi upfront decomposition nahi hoti, aur ye multi-turn, ongoing conversations ke liye design hota hai jahan different turns different domains touch kar sakte hain.

Q3. Swarm/handoff pattern mein central coordinator na hone ka trade-off kya hai?

Benefit — decentralization se naye specialist agents add karna easy hota hai (bas ek naya handoff target), aur triage-then-specialist flow bahut natural feel hota hai. Trade-off — central visibility nahi hoti, isliye debugging harder hai kyunki control flow runtime pe dynamically decide hota hai, static diagram se predict nahi ho sakta. Isse "handoff loops" ka risk bhi badhta hai (Agent A user ko Agent B ko bhejta hai, jo wapas Agent A ko bhej deta hai) agar har agent ka scope clearly defined na ho.

Q4. Blackboard pattern mein "task kab complete hua" decide karna hard kyun hai, aur isse kaise solve karte hain?

Kyunki koi central authority nahi hai jo track kare ki sab agents apna kaam kar chuke — har agent independently blackboard pe contribute karta hai jab relevant lage, isliye koi single "orchestrator" completion signal nahi bhej sakta. Common solution — ek separate lightweight "monitor" ya "arbiter" agent/process add karna jo blackboard state ko periodically check kare (jaise "kya sab expected fields populate ho gaye?" ya "kya N iterations ho chuki hain bina naye contributions ke") aur completion declare kare.

Q5. Multi-agent architecture add karne se pehle, ek senior engineer kya evaluate karega?

Sabse pehle — kya single agent ko better tools, better context pruning, aur ek zyada focused prompt deke fix kiya ja sakta hai, bina architecture change kiye. Agar nahi, to do specific conditions check karega: (a) kya sub-tasks genuinely independent hain jinhe parallelize karke real wall-clock time bachaya ja sake, ya (b) kya tool-set/context genuinely ek single agent ke liye unmanageable ho gaya hai. Agar dono false hain, multi-agent sirf N× latency aur N× cost (extra LLM calls) add karega bina proportional value ke, plus naye coordination bugs (misrouting, aggregation conflicts, handoff loops) introduce karega jo debug karna single-agent se harder hota hai.
