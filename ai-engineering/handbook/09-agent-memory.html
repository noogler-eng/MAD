Agent Memory Systems

LLM ka context window fixed-size hai — usme sirf utna hi fit hoga jitna tum bhejoge. Lekin ek real agent ko multi-turn conversations handle karni hoti hain, sessions ke across kaam yaad rakhna hota hai, aur user ke baare mein personalize hona hota hai. Ye sab context window ke andar akele nahi ho sakta — isi wajah se agents ko explicit memory systems chahiye hote hain, jo context window se bahar bhi state persist kar sakein.

Context Window Se Aage — Memory Kyun Chahiye

Chapter 2 mein humne dekha ki har LLM call stateless hoti hai — model ko koi built-in memory nahi hoti, har request apne aap mein complete honi chahiye. Jo bhi model ko "yaad" rehta hai, wo sirf wahi hota hai jo tum current prompt mein bhejte ho. Ye teen real scenarios mein break ho jaata hai:

  • Multi-turn conversations — ek lambi chat mein agar tum har message ke saath poori history nahi bhejoge, model context kho dega ("pichhle message mein maine kya bola tha?"). Lekin poori history bhejna bhi eventually context window se bade ho jaayega.
  • Long-running tasks across sessions — ek agent jo ek multi-day task pe kaam kar raha hai (jaise ek codebase migrate karna), usse restart hone ke baad bhi yaad rehna chahiye ki kahan tak progress hui thi. Ek naya process spawn hote hi context window khaali ho jaata hai.
  • Personalization across sessions — agar user ne pichhle session mein bataya tha "main metric units use karta hoon" ya "meri company Clear hai", to agent ko agli baar bhi ye pata hona chahiye, bina user ko dobara batana pade.

Solution ye nahi hai ki context window bada karo (chahe kitna bhi bada karo, ek din full ho jaayega, aur bada context slow + expensive bhi hota hai — chapter 12 mein latency angle dekhenge). Solution ye hai ki agent ko ek external memory system do jo context window ke bahar state store kare, aur agent selectively usme se relevant cheezein context window mein inject kare jab zaroorat ho.

📌 Memory ke 4 flavors jo is chapter mein cover honge

Short-term (current conversation, context window ke andar hi rehti hai), long-term (sessions ke across persist, vector store ya DB mein), episodic vs semantic (specific ghatna yaad rakhna vs general fact yaad rakhna), aur working memory/scratchpad (agent ka apna intermediate reasoning state ek single task ke dauraan). Ye chaaron alag problems solve karte hain — production agent aksar in sabka combination use karta hai.

Short-Term Memory — Conversation History Ka Problem

Short-term memory sabse simple concept hai — ye literally conversation ki message history hai, jo context window ke andar hi baithi hoti hai. Har naya turn pe tum poori history (ya uska kuch hissa) model ko bhejte ho taaki wo conversation continue kar sake.

Problem ye hai ki ye history unbounded grow karti hai. Ek lambi conversation (ya agent ke case mein, ek lamba tool-calling loop jisme har tool result bhi history mein add hota hai) eventually do cheezein hit karti hai:

  • Context window limit — model ka hard cap (jaise 200K tokens) ek din exceed ho jaayega, aur request fail hone lagegi.
  • Cost aur latency — har extra token input cost mein add hota hai, aur bade context ko process karna slower hota hai (chapter 12 mein KV cache detail milega) — chahe limit hit na ho, phir bhi practically ye wasteful ho jaata hai.

Is problem ko handle karne ke teen common mitigation strategies hain:

  • Sliding window — sirf last N turns rakho, purane turns ko drop kar do. Simple aur cheap hai, lekin agar koi important fact bahut pehle mention hua tha, wo permanently lost ho jaata hai.
  • Summarization — periodically purane turns ko ek compressed summary mein convert karo (ek chhota LLM call se), aur us summary ko history ke start mein rakho. Detail kam ho jaata hai lekin high-level context preserve rehta hai.
  • Hybrid — recent turns verbatim rakho (full detail, kyunki ye abhi relevant hone ki zyada chance hai) + purane turns ka summary. Ye most production systems ka default approach hai kyunki recent detail bhi milta hai aur long-range context bhi preserve hota hai.
⚠️ Summarization lossy hai

Summarization compression hai — koi bhi compression information loss karta hai. Agar user ne turn 5 mein ek specific number ya exact wording di thi jo baad mein critical ban jaati hai, aur wo turn summary mein compress ho chuka hai, wo detail ja sakta hai. Isliye critical facts (preferences, IDs, decisions) ko sirf short-term summary pe depend mat karo — unhe long-term memory (agla section) mein explicitly store karo jahan wo verbatim persist hon.

Long-Term Memory — Sessions Ke Across Persist Karna

Long-term memory context window ke bahar rehti hai — ek persistent store (database, vector store) jo session khatam hone ke baad bhi zinda rehta hai. Do common implementations hote hain:

  • Vector store (semantic recall) — jaisa chapter 4 (RAG) mein dekha, facts/memories ko embeddings mein convert karke store karte ho, aur query time pe semantic similarity se relevant memories retrieve karte ho. Achha hai jab memories unstructured/free-text hon aur exact keyword match zaroori na ho.
  • Structured key-value / database facts store — jaise {"unit_preference": "metric"} ya {"company": "Clear"} — exact facts jo structured query se lookup ho sakte hain. Achha hai jab facts well-defined categories mein aate hon aur exact retrieval chahiye ho (fuzzy semantic match ki jagah).

Dono approaches ek common pattern follow karte hain — retrieval-at-start-of-turn. Matlab, jab bhi agent ko respond karna hota hai, response generate karne se pehle wo long-term memory store se relevant facts query karta hai, aur unhe system prompt ya context mein inject karta hai. Flow kuch aisa dikhta hai:

  1. User ka naya message aata hai.
  2. Agent us message (ya conversation context) ko query bana ke long-term memory store se relevant memories retrieve karta hai (top-k semantic search, ya structured lookup).
  3. Retrieved memories ko system prompt mein ek "known facts about this user" section ki tarah inject kiya jaata hai.
  4. Ab LLM call hoti hai — model ke paas current message + relevant history + relevant long-term facts, sab available hote hain.
  5. Agar conversation mein koi naya important fact emerge hota hai, agent usse wapas long-term memory mein save bhi kar sakta hai (write path) — taaki agli baar wo bhi retrievable ho.
🧠 Senior Dev Note — Har cheez memory mein mat daalo

Ek common mistake ye hai ki agent har single message ko long-term memory mein save kar de "taaki kuch miss na ho". Ye do problems create karta hai — (1) retrieval noisy ho jaata hai kyunki irrelevant memories bhi top-k mein aa sakti hain, aur (2) storage/embedding cost linearly badhta jaata hai. Production systems mein aksar ek separate lightweight LLM call (ya heuristic) hota hai jo decide karta hai "kya ye fact memory-worthy hai?" — jaise stable preferences, identity facts, ya explicit corrections ("nahi, mera naam Sharad hai, Shard nahi") ko save karo, lekin transient chit-chat ko skip karo. Memory ka quality signal-to-noise ratio pe depend karta hai, sirf volume pe nahi.

Episodic vs Semantic Memory

Cognitive science se udhaar liya gaya ek useful distinction — kuch agent frameworks memory ko do categories mein explicitly split karte hain:

  • Episodic memory — specific past events/interactions ko remember karna. Jaise "last time hum is bug ko debug kar rahe the, fix ye tha ki cache invalidation missing thi" — ye ek specific episode hai, ek particular incident jo happen hua tha, apne context ke saath (kab, kya hua, kya result mila).
  • Semantic memory — general facts, jo kisi specific event se tied nahi hote. Jaise "user Python prefer karta hai JavaScript ke upar" ya "is codebase mein tests pytest se chalte hain" — ye standalone facts hain, kisi particular ghatna ka reference nahi hai.

Ye distinction useful hai kyunki retrieval strategy alag ho sakti hai — episodic memories aksar "similar situation phir se aayi" scenarios mein useful hoti hain (jaise ek coding agent jo ek similar error dobara dekhta hai aur past debugging episode retrieve karta hai), jabki semantic memories har turn pe generically useful ho sakti hain (user preferences jo har response ko shape karte hain). Kuch frameworks (jaise LangGraph ke memory stores, ya Mem0 jaisi libraries) inhe separate namespaces/collections mein store karte hain taaki retrieval logic independently tune ho sake — episodic ke liye recency + situational-similarity weight zyada, semantic ke liye stability aur broad-applicability weight zyada.

Working Memory / Scratchpad

Working memory (ya scratchpad) short-term aur long-term dono se different hai — ye conversation history nahi hai, ye agent ka apna intermediate reasoning/state hai jo ek single task ke dauraan use hota hai. Chapter 7 ke ReAct loop ko yaad karo — agent jab ek multi-step task solve kar raha hota hai, use apni progress track karni padti hai: "maine ye sub-tasks complete kar liye hain, ye baaki hain, ye intermediate result maine pichhle step mein nikaala tha".

Practically, ye aksar ek structured object hota hai — jaise ek todo list jo agent khud maintain karta hai, ya ek JSON blob jisme intermediate variables store hote hain — jise agent read/write karta hai as it works. Kuch agent frameworks isko explicitly ek "scratchpad" tool ke through expose karte hain (jaise ek update_plan ya write_scratchpad tool call), taaki agent ka reasoning state observable aur debuggable ho, sirf uski free-text "thinking" ke andar dabi hui na rahe.

Farak samajhna important hai: conversation history "kya bola gaya" record karti hai, long-term memory "kya persist karna hai across sessions" record karti hai, aur working memory "is task ko complete karne ke liye main abhi kahan hoon" record karti hai — teeno alag purpose serve karte hain, aur ek production agent teeno ko independently manage karta hai.

Practical Code — Vector-Store Backed Long-Term Memory

Chalo ek simple long-term memory system implement karte hain — Chroma (chapter 4 wale RAG setup jaisa) use karke user ke baare mein facts store karenge, aur query time pe top-k relevant memories retrieve karke system prompt mein inject karenge, LLM call se pehle.

agent_memory.py — Vector-store backed long-term memory (save + retrieve-and-inject)
# agent_memory.py — user ke facts ko vector store mein save karna aur query-time pe retrieve karna
import chromadb                                          # Chroma — lightweight open-source vector database
from chromadb.utils import embedding_functions        # Chroma ka built-in embedding function helper
from anthropic import Anthropic                        # Claude API client — final response generate karne ke liye
import uuid                                              # har memory ke liye unique ID banane ke liye
import time                                              # memory save hone ka timestamp record karne ke liye

client = Anthropic()                                            # Anthropic client initialize karo (env var se API key uthayega)

# --- Vector store setup ---
chroma_client = chromadb.PersistentClient(path="./memory_store")  # disk pe persist hone wala Chroma client (session ke baad bhi zinda rahega)

embedder = embedding_functions.SentenceTransformerEmbeddingFunction(  # local sentence-transformer model se text ko embeddings mein convert karna
    model_name="all-MiniLM-L6-v2"                              # chhota, fast embedding model — production mein bada model bhi use kar sakte ho
)

memory_collection = chroma_client.get_or_create_collection(     # collection banao ya agar already exist karti hai to use hi lo
    name="user_memories",                                    # collection ka naam — is user ki saari long-term memories yahan rahengi
    embedding_function=embedder                                 # upar define kiya hua embedder is collection ke saath attach karo
)

# --- Write path: naya fact memory mein save karna ---
def save_memory(user_id: str, fact: str) -> None:            # user_id + fact text leta hai, kuch return nahi karta
    """Ek naya fact user ki long-term memory mein save karta hai."""  # docstring — function ka purpose
    memory_id = str(uuid.uuid4())                             # is memory entry ke liye ek globally unique ID banao
    memory_collection.add(                                       # Chroma collection mein naya document add karo
        ids=[memory_id],                                         # unique ID list mein wrap karke pass karo (Chroma batch API expect karta hai)
        documents=[fact],                                        # actual fact text — isi ko embed karke store kiya jaayega
        metadatas=[{                                              # fact ke saath extra structured info attach karo
            "user_id": user_id,                                # kis user ka fact hai — multi-user filtering ke liye zaroori
            "timestamp": time.time()                            # kab save hua — recency-based filtering/ranking ke liye useful
        }]
    )

# --- Read path: query ke relevant top-k memories retrieve karna ---
def retrieve_memories(user_id: str, query: str, top_k: int = 3) -> list[str]:  # query text ke liye top_k relevant facts dhoondhta hai
    """Current query ke semantically closest memories nikalta hai, sirf isi user ke liye."""  # docstring
    results = memory_collection.query(                          # Chroma se semantic similarity search karo
        query_texts=[query],                                     # query ko bhi embedder automatically embed kar dega
        n_results=top_k,                                         # sirf top-k sabse similar results chahiye, sab nahi
        where={"user_id": user_id}                             # metadata filter — sirf isi user ke facts consider karo, dusron ke nahi
    )
    if not results["documents"] or not results["documents"][0]:      # agar koi match hi nahi mila (naya user, empty memory)
        return []                                            # empty list return karo, error mat throw karo
    return results["documents"][0]                          # Chroma nested list return karta hai — pehle query ke results nikaalo

# --- Inject path: retrieved memories ko system prompt mein daal ke LLM call karna ---
def build_system_prompt_with_memory(user_id: str, user_query: str) -> str:  # final system prompt banata hai, memory-aware
    """Base system prompt ke saath relevant long-term memories append karta hai."""  # docstring
    base_prompt = "Tum ek helpful AI assistant ho jo user ko unke sawaalon mein madad karta hai."  # normal, memory-independent system prompt
    memories = retrieve_memories(user_id, user_query)            # current query ke relevant memories fetch karo (write path se pehle save hui hongi)
    if not memories:                                          # agar koi relevant memory nahi mili
        return base_prompt                                   # plain base prompt hi return karo, extra section mat jodo
    memory_block = "\n".join(f"- {m}" for m in memories)     # har memory ko ek bullet point line mein format karo
    return (                                                   # memory-augmented prompt return karo
        f"{base_prompt}\n\n"                                   # base prompt ke baad ek blank line
        f"Is user ke baare mein pehle se pata hai:\n{memory_block}"  # retrieved facts ko explicit label ke saath inject karo
    )

# --- End-to-end: memory-aware agent turn ---
def agent_turn(user_id: str, user_query: str) -> str:               # ek single conversation turn poora karta hai, memory ke saath
    """Memory retrieve karo, inject karo, LLM call karo, aur response return karo."""  # docstring
    system_prompt = build_system_prompt_with_memory(user_id, user_query)  # respond karne se PEHLE relevant memory inject karo (retrieval-at-start-of-turn)
    response = client.messages.create(                           # ab actual LLM call karo, memory-augmented prompt ke saath
        model="claude-sonnet-4-5",                                # jo bhi model tumhare use-case ke liye sahi ho
        max_tokens=1024,                                       # response ka max length cap
        system=system_prompt,                                    # memory-injected system prompt yahan pass karo
        messages=[{"role": "user", "content": user_query}]         # current turn ka user message
    )
    return response.content[0].text                            # model ka text response nikaal ke return karo

# --- Example usage ---
save_memory("user_123", "User metric units prefer karta hai, imperial nahi.")  # ek preference fact save karo
save_memory("user_123", "User ki company Clear hai, wo DevOps seekh raha hai.")  # ek aur fact save karo
reply = agent_turn("user_123", "Mujhe office se ghar ki distance batao")  # query karo — "metric units" wali memory automatically retrieve + inject hogi
print(reply)                                                # final, memory-aware response print karo

Is example mein save_memory write path hai aur retrieve_memories + build_system_prompt_with_memory read/inject path hai. Real production system mein tum write path ko explicit user-triggered ("mujhe yaad rakho") ke saath-saath ek automatic fact-extraction step bhi bana sakte ho (jaisa senior-dev callout mein discuss kiya), jo conversation se important facts nikaal ke automatically save kare — lekin core retrieval-at-start-of-turn pattern yahi rehta hai.

Context Window Management Strategy — Summary Table

TechniqueKab use kareinTrade-off
Sliding window Short, low-stakes conversations jahan bahut purani cheezein irrelevant ho jaati hain Simple/cheap, lekin purani important detail permanently lost ho jaati hai
Summarization Lambi conversations jinme high-level context zaroori hai lekin exact wording nahi Compression lossy hoti hai — specific numbers/exact phrasing kho sakti hai; extra LLM call ka cost
Long-term retrieval (vector/KV store) Sessions ke across facts persist karne hain — preferences, identity, stable knowledge Infra overhead (vector DB/store maintain karna), retrieval quality embedding/indexing pe depend karti hai
Working memory / scratchpad Ek single multi-step task ke dauraan intermediate progress/state track karna Task-scoped hai, sessions ke across persist nahi hoti (jab tak explicitly long-term mein save na ho)
💡 Hinglish Tip — Ek line mein sab kuch

Short-term memory conversation ke andar hoti hai (grow karti hai, isliye sliding window/summarization se manage karo), long-term memory sessions ke across persist hoti hai (vector store/DB mein, retrieval-at-start-of-turn se inject karo), aur working memory ek single task ke dauraan agent ka apna scratchpad hai. Teeno alag problems solve karte hain — inhe mix mat karo, warna na conversation clean rahegi na long-term facts reliably persist honge.

Key Takeaways

  • Agents ko memory chahiye kyunki context window fixed-size hai aur LLM calls stateless hoti hain — multi-turn conversations, cross-session tasks, aur personalization sab context window ke andar akele sustain nahi ho sakte.
  • Short-term memory conversation history hai jo unbounded grow karti hai — mitigations: sliding window (last N turns), summarization (purane turns compress), hybrid (recent verbatim + purana summary).
  • Long-term memory context window ke bahar persist hoti hai — vector store (semantic recall) ya structured key-value facts store — aur retrieval-at-start-of-turn pattern se query karke system prompt mein inject hoti hai, response generate hone se pehle.
  • Episodic memory (specific past interactions/events) aur semantic memory (general facts) alag purpose serve karte hain — kuch frameworks inhe separate namespaces mein store karte hain taaki retrieval strategy independently tune ho sake.
  • Working memory/scratchpad conversation history se different hai — ye ek single task ke dauraan agent ka apna intermediate reasoning/state hai (jaise todo list), often structured object ki tarah implement hota hai.
  • Har cheez memory mein save mat karo — signal-to-noise ratio matter karta hai; stable facts/preferences/corrections save karo, transient chit-chat skip karo.

🎯 Interview Questions

Q1. Short-term aur long-term memory mein kya farak hai, aur dono kis problem ko solve karte hain?

Short-term memory conversation ki message history hai jo context window ke andar hi rehti hai — current conversation continue karne ke liye zaroori hai, lekin unbounded grow karke context limit ya cost/latency issue create kar sakti hai. Long-term memory context window ke bahar, ek persistent store (vector DB ya structured DB) mein rehti hai, sessions ke across survive karti hai, aur query-time pe selectively relevant facts retrieve karke context mein inject ki jaati hai. Short-term "is conversation mein ab tak kya hua" solve karta hai, long-term "is user/task ke baare mein permanently kya jaanna hai" solve karta hai.

Q2. Conversation history bahut badi ho jaaye to teen mitigation strategies kya hain, aur inka trade-off kya hai?

Sliding window (sirf last N turns rakhna — simple lekin purani detail permanently lost), summarization (purane turns ko compress karke summary bana dena — high-level context preserve hota hai lekin exact detail lossy ho sakti hai), aur hybrid (recent turns verbatim + purane turns ka summary — most production systems ka default, kyunki dono ka balance milta hai). Critical facts ke liye in teeno pe akela depend nahi karna chahiye — unhe explicitly long-term memory mein save karo taaki wo verbatim persist rahein.

Q3. Retrieval-at-start-of-turn pattern kya hai aur ye kaise kaam karta hai?

Ye ek pattern hai jahan agent, response generate karne se pehle, current query/context ko use karke long-term memory store se relevant facts query karta hai (top-k semantic search ya structured lookup), aur unhe system prompt ya context mein inject karta hai. Isse model ko current message ke saath-saath user/task ke relevant persistent facts bhi milte hain, bina poori history ya poora facts-store context window mein daale. Optionally, turn ke end mein agent naye important facts ko wapas memory store mein save bhi kar sakta hai (write path), taaki future turns unhe retrieve kar sakein.

Q4. Episodic memory aur semantic memory mein kya difference hai — example ke saath samjhao.

Episodic memory specific past events/interactions ko remember karti hai, apne context ke saath — jaise "last time is bug ko debug karte waqt fix cache invalidation missing hone se related tha". Semantic memory general, standalone facts hoti hai jo kisi specific event se tied nahi hoti — jaise "user Python prefer karta hai". Kuch agent frameworks inhe alag store karte hain kyunki retrieval strategy alag hoti hai — episodic memories situational-similarity aur recency pe weight karti hain (similar situation dobara aane pe useful), semantic memories har turn pe generically relevant ho sakti hain.

Q5. Ek agent har single message ko long-term memory mein save kar raha hai "taaki kuch miss na ho" — ye kyun problematic approach hai?

Ye do problems create karta hai — pehla, retrieval noisy ho jaata hai kyunki irrelevant/transient memories bhi top-k relevant results mein compete karne lagti hain, jisse actual important facts dab sakte hain. Doosra, storage aur embedding cost linearly (aur eventually unnecessarily) badhta jaata hai. Better approach — ek filtering step (heuristic ya lightweight LLM call) rakho jo decide kare ki kya fact "memory-worthy" hai (stable preference, identity fact, explicit correction), aur sirf wahi save karo, transient chit-chat skip karo. Memory system ka quality signal-to-noise ratio pe depend karta hai, sirf volume pe nahi.
