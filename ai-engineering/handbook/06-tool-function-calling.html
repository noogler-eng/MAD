Function Calling Actually Kya Hai — LLM Code Execute Nahi Karta

Sabse common misconception ye hai ki "LLM ne weather API call kiya". Ye galat hai. LLM ek text-prediction model hai — usko koi network access nahi hai, koi filesystem access nahi hai, koi runtime execution capability nahi hai. Jab tum LLM ko tools "de dete ho" (API request mein tool definitions bhejte ho), model sirf itna kar sakta hai: ek structured output generate karna jo bolta hai "main function X ko in arguments ke saath call karna chahta hoon".

Ye structured output ek JSON object hota hai (function name + arguments), text ki jagah. Model isse return karta hai, aur tumhara code — tumhara Python/Node backend — actually us function ko execute karta hai, result nikaalta hai, aur wo result wapas model ko ek naye message ke roop mein bhejta hai taaki model final answer bana sake. Model sirf "decide" karta hai kaunsa tool chahiye aur kya arguments — execution 100% tumhare control mein hai.

📌 Isliye ye "function calling" hai, "function execution" nahi

Ye distinction security ke liye bhi critical hai — LLM kabhi bhi tumhare database ko directly touch nahi karta, koi file delete nahi karta, koi payment nahi banata. Har action ek middleman se guzarta hai — tumhara execution code — jahan tum validation, permission checks, aur rate-limiting laga sakte ho before actually kuch bhi run karne se pehle. LLM ek "request suggest karne wala" hai, "executor" nahi.

Request/Response Cycle — Step by Step

Chalo poora cycle ek concrete example ke saath dekhte hain — user poochta hai "Delhi mein abhi weather kaisa hai?" aur tumhare paas ek get_weather(city) tool available hai.

tool-calling-cycle.txt — end-to-end flow
// STEP 1 — User apna message bhejta hai + tumhara code tool definitions attach karta hai
//   User: "Delhi mein abhi weather kaisa hai?"
//   + tools=[{name: "get_weather", description: "...", parameters: {...}}]

// STEP 2 — LLM decide karta hai ki koi tool chahiye, aur ek tool_call output karta hai
//   LLM response (structured, text nahi):
//   { type: "tool_use", name: "get_weather", input: { city: "Delhi" } }
//   IMPORTANT: is point pe LLM ne kuch bhi execute NAHI kiya — sirf request output ki hai

// STEP 3 — Tumhara code is response ko parse karta hai aur actual function call karta hai
//   result = get_weather("Delhi")   # ye tumhara real Python function hai, LLM ka nahi
//   result => { temp: 34, condition: "Sunny", humidity: 40 }

// STEP 4 — Tumhara code result ko ek NAYE message ke roop mein history mein append karta hai
//   messages.append({ role: "tool", tool_call_id: "...", content: result })

// STEP 5 — Poori history (original question + tool_call + tool result) LLM ko dobara bhejo
//   LLM ab final natural-language answer generate karta hai — is baar plain text
//   LLM: "Delhi mein abhi 34°C hai, sunny hai, humidity 40% hai."

// STEP 6 — Ye final text answer hi tumhare user ko dikhaya jaata hai

Notice karo — ye do separate API calls hain LLM ko: pehli call mein model tool maangta hai, dusri call mein (tool result ke saath) model final answer deta hai. Agar model ko multiple tools chahiye (e.g. weather + time), ye cycle multiple baar repeat ho sakta hai before model plain text return karta hai — isi wajah se production code mein iske liye ek while loop chahiye hota hai, single if/else nahi.

Tool Schema Design — Name, Description, Parameters

Model ko tool "samajhne" ke liye teen cheezein deni padti hain — ek JSON Schema ki tarah:

  • name — tool ka unique identifier (e.g. get_weather), model isi naam se refer karta hai.
  • description — plain English/natural language mein bataata hai tool kya karta hai aur kab use karna hai. Ye sabse important field hai — model isi text ko padhke decide karta hai ki current user query ke liye ye tool relevant hai ya nahi.
  • parameters — ek JSON Schema object jo required aur optional arguments define karta hai, unke types, enums, aur descriptions ke saath.
⚠️ Vague description = wrong tool selection

Agar description sirf "gets weather" hai, model confuse ho sakta hai ki isse kab call karna hai — kya "mujhe travel plan karna hai Delhi ke liye" jaisi query pe bhi ye trigger hoga? Aur agar parameter description missing hai (sirf city: string, koi hint nahi ki full city name chahiye ya airport code), model galat format mein arguments bhej sakta hai (e.g. "DEL" ki jagah "New Delhi, India" expect karne wale API ko). Vague schema seedha production mein wrong tool calls aur wrong arguments ki shakal mein dikhta hai — ye silent failure hai, koi crash nahi hoga, bas galat data aayega.

Best practices jo actually production mein farak daalte hain:

  • Description mein "when to use" explicitly likho — sirf "what it does" nahi, balki "use this when user asks about current weather conditions for a specific city" jaisa context bhi do.
  • Enums use karo jahan bhi possible ho — agar parameter ki limited valid values hain (e.g. unit: "celsius" | "fahrenheit"), enum se model ko free-text guess karne ki zaroorat nahi padti, aur invalid values bilkul avoid ho jaate hain.
  • Required vs optional clearly mark karo — agar ek parameter optional hai with a sensible default, usko required mat banao — model unnecessarily usko fill karne ki koshish karega (kabhi-kabhi galat value se) jab woh chahiye hi nahi tha.
  • Tool names descriptive rakho, generic nahi — get_weather better hai fetch_data se, jab tumhare paas multiple tools hon jo alag-alag data fetch karte hain.
  • Bahut zyada tools ek saath mat do — agar 50+ tools ek call mein pass karoge, model ki tool-selection accuracy degrade hoti hai (relevant description context window mein dilute ho jaata hai).

Practical Multi-Step Tool Loop — Python Code

Ab ek real working example — do tools (get_weather aur get_current_time) define karenge, user message bhejenge, aur ek while loop likhenge jo tab tak chalta rahe jab tak model plain text final answer na de de.

tool_loop.py — multi-step tool-calling loop
# tool_loop.py — Anthropic Claude API ke saath ek real multi-step tool loop
import json  # tool arguments aur results ko JSON serialize/deserialize karne ke liye
import anthropic  # official Anthropic Python SDK

client = anthropic.Anthropic()  # client banao — env var ANTHROPIC_API_KEY se key uthayega

# --- ACTUAL PYTHON FUNCTIONS jo hum expose karna chahte hain (real implementation) ---

def get_weather(city: str) -> dict:  # real weather function, city naam leta hai
    # normally yahan ek real weather API (e.g. OpenWeatherMap) call hoga
    fake_db = {"Delhi": 34, "Mumbai": 30, "Bangalore": 24}  # demo ke liye hardcoded data
    if city not in fake_db:  # agar city hamare fake DB mein nahi hai
        raise ValueError(f"Unknown city: {city}")  # explicit error raise karo, silently fail mat karo
    return {"city": city, "temp_c": fake_db[city], "condition": "Sunny"}  # structured result return karo

def get_current_time(timezone: str) -> dict:  # real time function, timezone naam leta hai
    import datetime  # yahi function ke andar import — sirf isi function ko chahiye
    # demo ke liye hum bas UTC time return kar rahe hain (real code mein pytz/zoneinfo use karo)
    now = datetime.datetime.utcnow().isoformat()  # current UTC time ko ISO string mein convert karo
    return {"timezone": timezone, "utc_time": now}  # structured result return karo

# --- TOOL SCHEMAS jo model ko bataate hain in functions ke baare mein ---

TOOLS = [  # list of tool definitions jo API request mein bhejenge
    {  # pehla tool object — get_weather
        "name": "get_weather",  # unique tool identifier
        "description": "Current weather ke liye use karo jab user kisi specific city ka weather poochhe.",  # kab use karein — explicit
        "input_schema": {  # JSON Schema jo valid arguments define karta hai
            "type": "object",  # top-level argument object hai
            "properties": {  # individual parameters yahan define hote hain
                "city": {"type": "string", "description": "Full city name, e.g. 'Delhi'"}  # city ek required string hai
            },  # properties block band
            "required": ["city"]  # city ke bina tool call invalid hai
        }  # input_schema band
    },  # pehla tool object band
    {  # dusra tool object — get_current_time
        "name": "get_current_time",  # dusra tool — current time nikaalne ke liye
        "description": "Kisi bhi timezone ka current time nikaalne ke liye use karo.",  # kab use karein
        "input_schema": {  # is tool ka JSON Schema
            "type": "object",  # object type schema
            "properties": {  # parameter definitions yahan se shuru
                "timezone": {  # timezone parameter definition
                    "type": "string",  # string type
                    "enum": ["UTC", "IST", "PST"],  # enum — limited valid values, model ko free-text guess nahi karna padta
                    "description": "Timezone code."  # short but clear description
                }  # timezone parameter definition band
            },  # properties block band
            "required": ["timezone"]  # timezone bhi required hai
        }  # input_schema band
    }  # dusra tool object band
]  # TOOLS list band

# function name ko actual Python callable se map karne wala dictionary — dispatch table
FUNCTION_MAP = {"get_weather": get_weather, "get_current_time": get_current_time}  # naam -> function reference

def run_tool_loop(user_message: str) -> str:  # main entrypoint — user ka message leke final text answer deta hai
    messages = [{"role": "user", "content": user_message}]  # conversation history — pehla message user ka hai

    MAX_ITERATIONS = 5  # infinite loop se bachne ke liye hard cap (senior note — neeche discuss hua hai)
    for _ in range(MAX_ITERATIONS):  # while True ki jagah bounded for loop — safety guard
        response = client.messages.create(  # model ko call karo — poori history + tools ke saath
            model="claude-sonnet-4-5",  # model id
            max_tokens=1024,  # output tokens ki limit
            tools=TOOLS,  # model ko available tools batao
            messages=messages  # poori conversation history bhejo (context ke liye zaroori)
        )  # client.messages.create call band

        if response.stop_reason != "tool_use":  # agar model ne tool maangna band kar diya
            # response.content mein plain text block hoga — usko extract karke return karo
            return "".join(block.text for block in response.content if block.type == "text")  # final answer

        # model ne tool_use bola hai — pehle assistant ka response history mein daalo (raw content block ke saath)
        messages.append({"role": "assistant", "content": response.content})  # exact response history mein append

        tool_results = []  # is turn ke saare tool results yahan collect karenge
        for block in response.content:  # response mein multiple content blocks ho sakte hain
            if block.type != "tool_use":  # sirf tool_use blocks process karo, text blocks skip
                continue  # next block pe jaao

            fn = FUNCTION_MAP.get(block.name)  # requested tool ka actual Python function dhoondo
            try:  # execution ko try/except mein wrap karo — errors crash nahi honi chahiye
                if fn is None:  # agar model ne koi unknown tool naam maanga
                    raise ValueError(f"Unknown tool: {block.name}")  # explicit error raise karo
                result = fn(**block.input)  # model ke diye arguments ke saath actual function call karo
                content_str = json.dumps(result)  # result ko JSON string mein serialize karo
                is_error = False  # success flag
            except Exception as e:  # koi bhi error pakdo (validation, network, unknown tool, etc.)
                content_str = json.dumps({"error": str(e)})  # error ko bhi structured JSON banao
                is_error = True  # error flag — model ko batayenge ki ye fail hua

            tool_results.append({  # is tool call ka result message format mein taiyar karo
                "type": "tool_result",  # block type jo API expect karta hai
                "tool_use_id": block.id,  # original tool_use call se match karne ke liye id
                "content": content_str,  # actual result (ya error) JSON string
                "is_error": is_error  # model ko batata hai ki ye ek error result hai
            })  # tool_results.append call band

        messages.append({"role": "user", "content": tool_results})  # saare tool results ek "user" message ke roop mein history mein daalo

    return "Max tool-call iterations reached — could not resolve request."  # safety fallback agar loop MAX_ITERATIONS tak chala gaya

if __name__ == "__main__":  # script directly run hone par hi ye chale
    answer = run_tool_loop("Delhi ka weather aur UTC time dono batao.")  # dono tools trigger karne wala query
    print(answer)  # final natural-language answer print karo

Is loop mein important cheezein — MAX_ITERATIONS se infinite loop guard, tool results JSON-serialized hoke wapas messages history mein jaate hain (role "user" ke saath, kyunki API perspective se ye "user turn" ka data hai), aur poori history — original question, tool call, tool result — har next API call mein dobara bheji jaati hai (LLM ke paas koi persistent memory nahi hai, har call stateless hai).

🧠 Senior Dev Note — Infinite tool-call loops production mein real risk hain

Agar tum MAX_ITERATIONS guard nahi lagate aur seedha while True chalate ho, ek buggy schema, ambiguous user query, ya model ka koi edge-case reasoning failure tumhe endless loop mein daal sakta hai — model baar-baar tool call karta rahega, kabhi plain text return nahi karega. Ye seedha tumhara API bill explode kar dega (har iteration ek paid API call hai) aur user request timeout ho jaayegi. Production mein hamesha ek hard iteration cap rakho (typically 3-10, use-case pe depend karta hai), aur cap hit hone pe user ko ek graceful fallback message do ("main ye abhi resolve nahi kar paaya, dobara try karo ya support contact karo") — silent infinite retry se kahin better hai.

Error Handling — Tool Fail Hone Pe Kya Karein

Real world mein tools fail hote hain — network timeout, invalid arguments jo model ne galat bheje, third-party API down hai, rate limit hit hua. Naive approach ye hoga ki exception uncaught chhod do aur poora request crash ho jaaye — lekin ye bahut brittle hai.

Better pattern (jo upar wale code mein bhi use hua) — error ko bhi ek structured tool result ki tarah model ko wapas bhejo, crash karne ki jagah. Model ko pata chal jaata hai ki tool fail hua, aur wo intelligently react kar sakta hai — retry kar sakta hai different arguments ke saath, user ko explain kar sakta hai "abhi weather data available nahi hai", ya koi alternate tool try kar sakta hai. Ye human customer-support agent jaisa hi hota hai — agar ek system down hai, wo crash nahi karta, wo user ko batata hai aur alternative dhoondta hai.

error_pattern.py — structured error jo model ko wapas jaata hai
# structured error pattern — real network call ke case mein
try:  # tool execution ko try block mein wrap karo
    result = call_external_weather_api(city)  # actual network call jo fail ho sakta hai
except TimeoutError:  # specific exception type catch karo — generic catch-all se better
    result = {"error": "timeout", "message": "Weather service timed out, try again"}  # model-readable structured error
except KeyError:  # agar city hi invalid thi (model ne galat naam bheja)
    result = {"error": "invalid_city", "message": "City not recognized, ask user for a valid city name"}  # model ko retry-hint bhi do

Notice karo — error message mein hint bhi diya gaya hai ("try again", "ask user for a valid city name") — ye model ko batata hai next step kya hona chahiye, sirf "kuch fail hua" nahi. Ye chhota sa detail retry-loops ko zyada intelligent banata hai.

Parallel Tool Calls

Modern models (Claude included) ek hi turn mein multiple tool calls simultaneously request kar sakte hain — jaise agar user poochhe "Delhi aur Mumbai dono ka weather batao", model ek hi response mein do tool_use blocks bhej sakta hai (get_weather("Delhi") aur get_weather("Mumbai") dono ek saath), sequential do turns lene ke bajaye.

Engineering implication — agar tumhara execution code sequentially har tool ko ek-ek karke chalata hai (for loop mein synchronous calls), tum unnecessary latency add kar rahe ho. Independent tool calls ko concurrently execute karna chahiye — Python mein asyncio.gather se, ya thread pool se agar tools I/O-bound hain (network calls). Upar wale example mein hamara for block in response.content loop sequential tha (simplicity ke liye) — production mein agar ek turn mein 3+ independent tool calls aate hain, unhe async gather karke total latency significantly kam ki ja sakti hai, especially jab har tool call ek slow external API hit karta ho.

Key Takeaways

  • LLM khud kabhi code execute nahi karta — wo sirf ek structured "call this function with these arguments" request output karta hai; actual execution tumhare code ki responsibility hai.
  • Poora cycle do (ya zyada) separate API calls mein hota hai — pehli call mein model tool maangta hai, execution ke baad dusri call mein model final text answer deta hai.
  • Tool schema quality directly accuracy affect karti hai — clear "when to use" description, enums for constrained values, aur correct required/optional marking se wrong tool selection aur wrong arguments avoid hote hain.
  • Production tool loop ek bounded loop hona chahiye (while/for with a max-iteration cap), infinite while True nahi — cost aur latency dono risk mein hain.
  • Tool errors ko crash karne ki jagah structured error result ke roop mein model ko wapas bhejo — model retry ya graceful explanation de sakta hai.
  • Models ek turn mein multiple tools ek saath request kar sakte hain — independent tool calls ko concurrently execute karo (asyncio.gather) taaki unnecessary sequential latency na ho.

🎯 Interview Questions

Q1. "Function calling" mein LLM actually kya karta hai — kya wo khud API call karta hai?

Nahi. LLM sirf ek structured output generate karta hai jo bolta hai "main function X ko in arguments ke saath call karna chahta hoon" — ye ek JSON object hota hai, text ki jagah. Actual execution (network call, DB query, etc.) hamesha application ke apne code mein hota hai. LLM ka role sirf "decide karna" hai ki kaunsa tool chahiye aur kya arguments — "run karna" nahi.

Q2. Ek vague tool description production mein kya problems create kar sakti hai?

Do main problems — wrong tool selection (model confuse ho jaata hai ki current query ke liye ye tool relevant hai ya nahi, isliye galat context mein bhi call kar sakta hai ya relevant hone par bhi call nahi karta) aur wrong arguments (agar parameter descriptions missing/vague hain, model galat format ya galat values bhej sakta hai — e.g. city code ki jagah full name, ya invalid enum value). Dono silent failures hain, koi crash nahi hota, bas output galat aata hai jo debug karna mushkil hai.

Q3. Ek production tool-calling loop mein max-iteration guard kyun zaroori hai?

Bina bounded loop ke, edge-case reasoning failure ya ambiguous query model ko baar-baar tool calls request karne pe majboor kar sakti hai bina kabhi plain text final answer diye — ye endless loop banata hai jo API costs explode kar deta hai (har iteration ek paid call hai) aur request ko timeout tak le jaata hai. Ek hard cap (e.g. 5-10 iterations) rakhna zaroori hai, saath mein cap hit hone pe ek graceful fallback message.

Q4. Tool call fail ho jaaye (network error ya invalid arguments) to kya karna chahiye — crash ya kuch aur?

Crash nahi karna chahiye. Best practice — error ko bhi ek structured tool result ki tarah model ko wapas bhejo (e.g. {"error": "timeout", "message": "..."}), taaki model intelligently react kar sake — retry kar sakta hai, alternate approach try kar sakta hai, ya user ko clearly explain kar sakta hai ki kya problem hui. Ye application ko resilient banata hai, ek single tool failure poori conversation crash nahi karti.

Q5. Parallel tool calls kya hote hain, aur inka engineering implication kya hai?

Model ek hi response turn mein multiple independent tool calls request kar sakta hai (e.g. do alag cities ka weather ek saath maangna). Agar execution code inhe sequentially, ek-ek karke chalata hai, unnecessary latency add hoti hai. Sahi approach hai in independent calls ko concurrently execute karna — Python mein asyncio.gather jaise tools se — taaki total wait time sabse slow individual tool call jitna ho, sabke sum jitna nahi.
