Choosing a Model

"Konsa model use karein" — ye probably sabse zyada bar poocha jaane wala AI engineering sawaal hai, aur sabse zyada bar galat answer diya jaane wala bhi ("bas sabse bada/latest wala use karo"). Latency — Time-to-First-Token vs Total Generation

Jab log "model X slow hai" kehte hain, actually do alag cheezein maapte hain jo confuse ho jaate hain:

  • Time-to-First-Token (TTFT) — request bhejne se lekar pehla token wapas aane tak ka time. Ye largely model ke "thinking/setup" overhead se decide hota hai — bada model, lamba system prompt, bada context — sab TTFT badhate hain.
  • Total generation time — poora response complete hone tak ka time. Ye output tokens × per-token generation speed se roughly decide hota hai — agar model 1000 tokens generate kar raha hai aur uski speed 50 tokens/sec hai, total generation ~20 seconds lega, TTFT alag se.

Practical implication — streaming (jahan tokens generate hote hi user ko dikhte jaate hain, poora response complete hone ka wait nahi) TTFT ko user-perceived latency mein kaafi hide kar deta hai, kyunki user ko lagta hai response "turant shuru ho gaya", chahe poora response lambe samay tak generate ho raha ho. Lekin streaming total latency ko kam nahi karta — agar tumhe poora structured JSON response chahiye pehle kisi downstream step ko trigger karne ke liye (jaise ek tool call ya database write), tumhe poora generation complete hone tak wait karna hi padega, streaming se koi fayda nahi.

Ek general rule — bade/zyada capable models generally slower hote hain kyunki unke paas zyada parameters activate hote hain per-token (ya agar mixture-of-experts architecture hai to bhi routing overhead hota hai), aur wo often lambe, zyada "thought-out" responses generate karte hain. Isliye agar tumhara use-case latency-sensitive hai (real-time chat widget, voice assistant), chhota/faster model tier consider karna zaroori hai, chahe wo thoda kam "smart" ho.

🧠 Senior Dev Note — Latency budget pehle decide karo, phir model choose karo

Model choose karne se pehle apne product ka latency budget likh ke rakho — jaise "voice assistant ke liye TTFT 500ms se kam hona chahiye" ya "batch job ke liye latency matter nahi karta, sirf throughput matter karta hai". Iske bina tum reverse order mein kaam karoge — pehle "best" model pick karoge, phir latency problem discover karoge production mein, phir scramble karoge downgrade karne ke liye. Latency requirement ek input honi chahiye model selection process mein, ek output nahi.

Context Window Size — Bigger Hamesha Better Nahi

Context window batata hai model ek single request mein kitna input (system prompt + conversation history + retrieved documents + user query) process kar sakta hai. Marketing mein "huge context window" ek headline feature ban gaya hai, lekin practical engineering mein iska matlab hamesha "better" nahi hota — teen reasons se:

  • Cost scales with tokens — chahe context window 1 million tokens support kare, agar tum har request mein 500K tokens bhejte ho, tum har request pe utne hi tokens ke liye pay bhi kar rahe ho. "Available" context aur "should-use" context alag cheezein hain.
  • "Lost in the middle" problem — research consistently dikhata hai ki bahut lambe contexts mein, model context ke beginning aur end mein di gayi information ko zyada reliably use karta hai, beech mein buried information ko often miss ya under-weight kar deta hai. Matlab sirf isliye ki tumne 50 relevant documents context mein daal diye, model unme se sabko equally acha use nahi karega — retrieval quality (kitne relevant chunks bheje, RAG chapter dekho) matter karta hai zyada, raw quantity se.
  • Latency bhi badhta hai — zyada input tokens process karne mein zyada time lagta hai (TTFT badhta hai), especially agar prompt caching set up nahi hai.

Practical approach — apne task ke liye realistically kitna context chahiye ye estimate karo (system prompt + relevant retrieved chunks + recent conversation turns), aur usi ballpark ke liye size karo, sirf "zyada context window available hai to sab kuch bhar do" mat karo. RAG mein aggressive reranking/filtering (chapter 4 dekho) ek chhota, high-precision context window aksar ek bade, noisy context se better results deta hai.

Cost Per Token — Input vs Output, Agent Loops Mein Compounding

Har provider input tokens aur output tokens ko alag rate pe charge karta hai, aur output tokens generally input tokens se zyada mehenge hote hain (often 3-5x) — kyunki output generation compute-intensive hai (har token sequentially generate hota hai, autoregressively), jabki input tokens ek hi forward pass mein parallel process ho jaate hain.

Iska practical implication — agar tumhara task lambi, detailed responses generate karta hai (jaise code generation, long-form writing), cost primarily output tokens se drive hoga. Agar tumhara task chhota response generate karta hai lekin lamba context read karta hai (jaise RAG-based Q&A jahan 10 documents context mein hain lekin answer 2 lines ka hai), cost primarily input tokens se drive hoga.

Sabse important cost trap — agent loops mein cost compound hota hai fast. Ek single agent task jo 5 tool-calling round-trips leta hai, matlab 5 alag LLM calls, aur har call mein poora conversation history (pichle sab tool calls + results) context mein wapas bhejna padta hai (chapter 7/9 dekho, agent loop aur memory management). Matlab N-th round-trip ka input token count roughly N ke saath linearly badhta hai — ek 5-step agent loop ka total cost ek single LLM call se kai guna zyada ho sakta hai, sirf isliye ki history repeatedly re-sent ho rahi hai.

⚠️ Pricing/specs hamesha check karo, memorize mat karo

Is chapter mein hum koi exact price ya token number quote nahi kar rahe — ye har provider update ke saath badalte hain (naye models launch hote hain, prices drop hote hain, context windows expand hote hain). Production mein model decision commit karne se pehle hamesha current provider documentation check karo (OpenAI, Anthropic, Google, ya jo bhi provider) — outdated pricing assumption pe cost estimate banana ek real production risk hai, especially agar tum ek fintech jaisi cost-sensitive company mein kaam kar rahe ho.

Capability/Reasoning Depth — Har Task Ko Flagship Nahi Chahiye

Ye sabse under-appreciated axis hai — engineers often reflexively sabse capable (aur sabse mehenga, sabse slow) model use karte hain har task ke liye, jab ki actually zyada tasks simple hote hain:

  • Classification / intent detection — "ye email spam hai ya nahi", "ye support ticket kis category mein aata hai" — in tasks mein deep multi-step reasoning nahi chahiye, ek chhota/fast model usually equally accurate hota hai, kaafi kam cost aur latency pe.
  • Extraction — structured data nikalna (naam, date, amount) unstructured text se — again, pattern-matching-heavy task hai, flagship-level reasoning ki zaroorat rarely hoti hai.
  • Simple conversational responses — FAQ answering, basic customer support chat — chhota model often sufficient hai agar prompt well-engineered hai.
  • Complex multi-step reasoning — multi-hop analysis ("in 3 documents ko compare karke conflicting clauses dhoondo"), code generation/debugging, ya agentic planning jahan model ko decide karna hai "next step kya lena hai" — in tasks mein flagship-tier models clearly better perform karte hain, kyunki inme deeper reasoning chains involve hoti hain jahan chhote models galtiyan compound kar dete hain.

Rule of thumb — task ki actual reasoning depth ke hisaab se model choose karo, na ki "safe side pe rehne ke liye sabse bada model daal do" ke hisaab se. Ye sirf cost-saving nahi hai — chhote models often faster bhi hote hain, matlab better user experience bhi milta hai simple tasks ke liye.

Rate Limits & Availability

Production reliability ke liye ek axis jo aksar tab tak ignore hota hai jab tak problem na ban jaaye — rate limits (requests-per-minute, tokens-per-minute) aur availability (provider ka uptime, regional latency). Ek naya/smaller provider ya naya model tier often tighter rate limits ke saath launch hota hai jab tak capacity scale nahi hoti. High-traffic production systems ke liye ye directly impact karta hai:

  • Peak traffic ke time requests queue/throttle ho sakte hain agar tum rate limit ke close chal rahe ho — matlab user-facing latency spike.
  • Single-provider dependency ek availability risk hai — agar provider ka API down ho jaaye ya degrade ho jaaye, tumhara poora product affected hota hai jab tak fallback na ho (production hardening chapter 13 mein fallback patterns dekhenge).
  • Higher-tier/enterprise API plans usually higher rate limits aur SLAs offer karte hain — agar production volume high hai, ye ek real consideration hai jab provider choose kar rahe ho.

Multimodality — Vision/Audio Support

Agar product ko images, PDFs (visually), audio, ya video samajhna hai — jaise "is invoice screenshot se amount nikaalo", ya "is customer call recording ko summarize karo" — model ka multimodal support ek hard filter ban jaata hai, na ki ek nice-to-have. Sab models equally strong multimodal capability nahi rakhte — kuch text-only hain, kuch vision support karte hain lekin audio nahi, kuch dono support karte hain lekin varying quality levels pe. Agar tumhara use-case multimodal hai, ye pehle filter karo model shortlist se pehle hi (latency/cost compare karne se pehle) — kyunki agar model modality support hi nahi karta, baaki sab comparison irrelevant hai.

Model Ladder Pattern — Routing/Fallback

Ek real production cost-saving technique jo directly upar wale "capability" axis se nikalti hai — model routing. Idea simple hai: har request ko blindly flagship model pe mat bhejo, pehle ek chhota/fast router step (khud ek chhota model, ya even simpler — rule-based heuristics) decide kare ki request kitni complex hai, phir uske hisaab se sahi tier ko route karo.

Example flow — ek customer support system socho jahan incoming messages pehle ek chhota/fast model (jaise Haiku-tier) se classify hote hain: "simple FAQ" vs "complex/ambiguous query". Simple FAQs turant usi chhote model se answer ho jaati hain (fast + cheap). Complex queries escalate hoti hain bade model (Opus-tier) ko, jahan deeper reasoning available hai. Result — bulk of traffic (jo usually simple hota hai) cheap/fast path se serve hota hai, aur expensive flagship model sirf tab invoke hota hai jab actually zaroorat ho.

modelRouter.js — task complexity ke hisaab se model tier choose karna
// modelRouter.js — ek simple router jo request complexity dekh ke sahi model tier chunta hai

// MODEL_TIERS — har tier ka naam aur uska "cost/capability level" (production mein real model IDs honge)
const MODEL_TIERS = {
  // FAST — chhota/cheapest model, simple classification/FAQ ke liye
  FAST: 'fast-tier-model',
  // BALANCED — mid-tier model, moderate complexity ke liye
  BALANCED: 'balanced-tier-model',
  // FLAGSHIP — sabse capable/expensive model, complex reasoning ke liye
  FLAGSHIP: 'flagship-tier-model',
};

// classifyComplexity — ek cheap heuristic jo bina LLM call ke bhi kaam kar sakta hai
// (ya isko khud ek chhoti LLM call bhi bana sakte ho agar heuristics insufficient hon)
function classifyComplexity(userMessage, context) {
  // agar message chhota hai aur koi multi-step keyword nahi hai, treat as simple
  const isShort = userMessage.length < 200;
  // complex reasoning tasks mein aksar ye words milte hain — "compare", "analyze", "why", etc.
  const hasComplexSignal = /compare|analy|why|explain in detail|debug/i.test(userMessage);
  // agar context mein pichle tool calls fail hue hain, escalate karna better hai
  const hadPriorFailure = context?.priorToolFailures > 0;

  // koi bhi complex signal ho to seedha FLAGSHIP tier pe jao
  if (hasComplexSignal || hadPriorFailure) return 'complex';
  // chhota, simple-looking message ho to FAST tier ke liye eligible
  if (isShort) return 'simple';
  // baaki sab default BALANCED tier mein jaate hain
  return 'moderate';
}

// routeToModel — complexity label ko actual model tier mein map karta hai
function routeToModel(userMessage, context) {
  // pehle complexity classify karo
  const complexity = classifyComplexity(userMessage, context);

  // complexity label ke hisaab se sahi tier return karo
  if (complexity === 'simple') return MODEL_TIERS.FAST;
  if (complexity === 'moderate') return MODEL_TIERS.BALANCED;
  // complex query ya prior tool failure — flagship model ko escalate karo
  return MODEL_TIERS.FLAGSHIP;
}

// usage — request handle karte waqt sahi model tier pehle decide karo, phir call karo
const chosenModel = routeToModel(incomingMessage, requestContext);
// chosenModel ab actual LLM API call mein use hoga — cost/latency dono save hote hain bulk traffic ke liye

Ye pattern especially agent architectures mein powerful ban jaata hai (chapter 8 dekho) jahan har step ek LLM call hai — agar orchestrator/planning steps ke liye bada model use karo lekin repetitive worker/sub-task steps ke liye chhota model, overall cost significantly kam ho sakta hai without quality loss on the parts that actually need deep reasoning.

Self-Hosted Open-Weight Models — Kab Sense Banta Hai

Open-weight models (Llama, Mistral, DeepSeek) tumhe apne infra pe self-host karne ka option dete hain, hosted API ki jagah. Ye ek real trade-off hai, silver bullet nahi:

Self-hosting kab sense banta hai:

  • Data residency/compliance — agar tum ek fintech jaisi regulated industry mein ho jahan customer data kisi third-party provider ko bhejna compliance issue create karta hai, self-hosting (apne VPC ke andar) ye concern eliminate kar deta hai.
  • Very high volume — agar tumhara request volume itna high hai ki per-token API cost infra cost se zyada ho jaaye, self-hosting cost amortize ho jaata hai scale pe (lekin ye break-even point calculate karna zaroori hai, assume mat karo).
  • Fine-tuning/customization — agar tumhe model weights khud modify karne hain (domain-specific fine-tuning), open-weight models ye allow karte hain, closed APIs nahi.

Hosted APIs kab jeetein:

  • No infra burden — GPU provisioning, scaling, model serving optimization (batching, KV cache management — chapter 12 dekho) sab provider handle karta hai.
  • Always latest model — hosted API providers continuously naye models release karte hain, tumhe khud kuch update nahi karna padta.
  • Elastic scaling — traffic spike ho to hosted API automatically scale karta hai (rate limits ke andar), self-hosted infra ko tumhe khud provision/scale karna padta hai.

(Actual self-hosted deployment — GPU choice, serving frameworks jaise vLLM, quantization — is chapter ka scope nahi hai; ye ek separate deployment topic hai. Yahan sirf "kab consider karo" wala decision framework cover kiya hai.)

Practical Decision Checklist

Chalo teen concrete scenarios se dekhte hain ki upar wale axes practically kaise combine hote hain:

  1. Real-time customer chat widget (website pe live chat, users turant response expect karte hain) → Fast/cheap tier. Latency-sensitive hai (TTFT matter karta hai), high volume hai (matlab cost per-request bhi matter karta hai), aur zyadatar queries simple FAQ-type hoti hain. Router pattern use karo — sirf genuinely complex/escalated queries ko bade model tak bhejo.
  2. Internal document analysis agent (multi-step reasoning — jaise legal/finance documents ko cross-reference karke insights nikalna) → Flagship tier. Yahan latency itni critical nahi hai (internal tool, users kuch seconds/minutes wait kar sakte hain), lekin reasoning depth critical hai — galat conclusion nikalna (jaise fintech mein compliance document misread karna) sasti model se bachaye gaye paison se zyada costly ho sakta hai.
  3. Batch classification of thousands of support tickets (offline job, real-time nahi) → Cheapest/fastest tier, aur self-hosting consider karo agar volume genuinely large hai. Task simple hai (classification), latency matter nahi karta (batch job), lekin volume high hai — matlab per-token cost total bill mein multiply hoke bahut bada number ban sakta hai. High-volume, low-complexity, latency-insensitive — ye exactly wo combination hai jahan self-hosted open-weight model economics favorable ban sakti hai.

Har scenario mein pattern same hai — latency requirement + reasoning depth needed + expected volume teeno ko pehle likho, phir in teeno ke intersection se model tier decide karo. Kabhi bhi "default" model use mat karo bina in axes explicitly through karne ke.

💡 Hinglish Tip — Ek line mein sab kuch

"Har task ko flagship model mat do — task ki latency zaroorat, reasoning depth, aur expected volume dekho, phir sabse chhota/sasta model choose karo jo wo kaam reliably kar sake, aur zaroorat pade to router pattern se escalate karo." Ye ek baar sochne ki cheez nahi hai, har naye feature/task ke liye repeat karne wali habit honi chahiye.

Key Takeaways

  • Latency ke do parts hain — TTFT aur total generation time. Streaming TTFT ko user-perceived latency mein hide karta hai, lekin total generation time ko kam nahi karta.
  • Bigger context window hamesha better nahi hota — cost tokens ke saath scale karta hai, aur "lost in the middle" ki wajah se bahut lambe contexts mein retrieval quality gir sakti hai.
  • Output tokens input tokens se generally mehenge hote hain, aur agent loops mein cost fast compound hota hai kyunki har round-trip poora conversation history re-send karta hai.
  • Har task ko flagship model ki zaroorat nahi — classification/extraction/simple chat chhote, fast models pe reliably chal sakte hain; complex reasoning/coding flagship se better perform karte hain.
  • Rate limits aur availability production reliability ke liye real considerations hain, especially high-traffic systems mein.
  • Model ladder pattern (jaise Claude ka Opus/Sonnet/Haiku) providers deliberately design karte hain — routing/fallback se bulk traffic cheap tier pe serve karo, sirf complex requests escalate karo.
  • Self-hosted open-weight models data residency, very high volume, aur fine-tuning needs ke liye sense banate hain; hosted APIs infra-free, always-latest, elastic scaling ke liye jeetein.
  • Exact pricing/specs frequently badalte hain — production decision lene se pehle hamesha current provider docs verify karo.

🎯 Interview Questions — AI Engineer

Q1. TTFT aur total generation time mein kya difference hai, aur streaming kisko address karta hai?

TTFT (Time-to-First-Token) request bhejne se pehla token aane tak ka time hai, largely model size aur input context length se driven. Total generation time poora response complete hone tak ka time hai, roughly output tokens × per-token speed. Streaming TTFT ko user-perceived latency mein hide kar deta hai (user ko lagta hai response turant shuru ho gaya), lekin total generation time ko kam nahi karta — agar downstream logic ko poora structured response chahiye (jaise ek JSON parse karke tool call trigger karna), streaming ka latency benefit nahi milta wahan.

Q2. Kyun bada context window hamesha "better" nahi hota — do concrete reasons do.

Pehla — cost tokens ke saath directly scale karta hai, matlab zyada context bhejna hamesha zyada expensive hai, chahe window support kare. Doosra — "lost in the middle" phenomenon, jahan model context ke beginning/end mein di gayi information ko zyada reliably use karta hai, beech mein buried information ko under-weight kar sakta hai — matlab sirf zyada documents context mein daalne se answer quality automatically better nahi hoti, precise retrieval/reranking (kam but relevant chunks) often ek bade noisy context se better result deta hai.

Q3. Ek agent loop mein cost kyun fast compound ho jaata hai, aur isko kaise control karoge?

Har tool-calling round-trip ek naya LLM call hai jisme poora pichla conversation history (pichle tool calls + results) input context mein wapas bhejna padta hai — matlab N-th round-trip ka input token count roughly N ke saath badhta hai. Control karne ke tareeke — context/memory management (chapter 9 mein discuss kiya — purani, irrelevant history ko summarize/prune karo), aur model routing (chhote steps ke liye chhota model, sirf critical planning steps ke liye flagship model use karo).

Q4. Model routing/ladder pattern kya hai, aur ise ek production system mein kaise implement karoge?

Ye ek pattern hai jahan har request blindly flagship model ko nahi bheja jaata — pehle ek cheap router step (chhota model ya heuristics) request ki complexity classify karta hai, phir uske hisaab se sahi tier (fast/balanced/flagship) ko route karta hai. Example — customer support system mein simple FAQs chhote/fast model se directly answer ho jaati hain, complex/ambiguous queries flagship model ko escalate hoti hain. Ye bulk traffic (jo usually simple hota hai) ko cheap path se serve karta hai, cost aur latency dono significantly reduce karta hai without quality loss on genuinely complex requests.

Q5. Ek fintech company mein tumhe decide karna hai — hosted API use karein ya open-weight model self-host karein customer support ticket classification ke liye jo daily 50,000 tickets process karta hai. Kya factors consider karoge?

Pehle task complexity dekho — classification generally simple task hai, deep reasoning nahi chahiye, matlab chhota model bhi sufficient hoga (flagship ki zaroorat nahi). Phir volume dekho — 50,000/day high volume hai, matlab per-token hosted API cost significant ho sakta hai scale pe, self-hosting economics favorable ho sakti hain agar break-even calculation favorable aaye. Phir compliance dekho — fintech mein customer data third-party API ko bhejna data residency/compliance concern ho sakta hai, jo self-hosting (apne VPC ke andar) ke favor mein strong argument hai. Lekin infra burden bhi weigh karo — self-hosting GPU provisioning, scaling, serving optimization ki team capacity maangta hai. Agar team ke paas wo capacity hai aur volume+compliance dono self-hosting favor karte hain, wo better choice hai; warna hosted API (jo elastic scaling aur zero infra burden deta hai) safer starting point hai.

Q6 (bonus/context). Claude ka Opus/Sonnet/Haiku (ya GPT ka flagship/mini) tiering kis engineering problem ko solve karta hai?

Ye deliberately ek quality-vs-speed-vs-cost ladder banata hai ek hi provider ke andar, taaki engineers apne specific task ki complexity ke hisaab se sahi tier pick kar sakein — bina provider switch kiye. Isse model routing pattern practically feasible ban jaata hai — ek hi API family ke andar simple requests fast/cheap tier pe, complex requests capable tier pe route ki ja sakti hain, consistent API interface ke saath.
