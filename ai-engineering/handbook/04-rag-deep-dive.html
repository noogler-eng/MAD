RAG Deep-Dive

RAG (Retrieval-Augmented Generation) ka high-level idea sabko pata hai — "apna data LLM ko context mein de do". Lekin production mein RAG fail hone ke 90% cases engineering decisions ki wajah se hote hain — bad chunking, wrong embedding model, weak retrieval, koi reranking nahi. Is chapter mein hum RAG training/ML angle se nahi, ek engineering pipeline ki tarah dekhenge — har stage ke trade-offs, aur end mein ek full working code example.

RAG Recap — 3 Steps

RAG teen simple steps ka pipeline hai: (1) Retrieval — user ke query se related documents/chunks apne knowledge base se dhoondo. (2) Augmentation — un retrieved chunks ko prompt ke context mein inject karo. (3) Generation — LLM ko us augmented prompt ke saath call karo taaki wo grounded, up-to-date answer de sake, bina apne parametric memory pe purely depend kiye (jisme hallucination aur staleness dono risk hote hain).

Conceptually ye simple lagta hai, lekin production mein RAG quality 90% retrieval quality pe depend karti hai — agar galat chunks retrieve hue, LLM chahe kitna bhi smart ho, wrong context se wrong answer generate karega ("garbage in, garbage out"). Isliye is chapter ka focus retrieval pipeline ki engineering pe hai, generation part (jo pehle se chapter 3 mein cover ho chuka hai) pe nahi.

Chunking Strategies

Document ko chhote pieces ("chunks") mein todna pehla aur sabse underrated decision hai — chunk size aur boundary galat hone se retrieval permanently kharab rehta hai, chahe embedding model kitna bhi acha ho. Common strategies:

  • Fixed-size chunking — har N characters/tokens pe cut karo (e.g. 500 tokens). Simplest, but sentences/paragraphs ke beech mein cut ho sakta hai, jisse chunk ka meaning incomplete ho jaata hai.
  • Sentence/paragraph-aware chunking — natural boundaries (sentence ya paragraph end) pe cut karo, taaki koi mid-sentence break na ho. Better semantic coherence, thoda zyada implementation complexity.
  • Semantic chunking — consecutive sentences ke embeddings compute karo, aur jahan similarity drop hoti hai (topic shift) wahan chunk boundary banao. Sabse "smart" approach, lekin compute-expensive hai (embedding calls chunking ke waqt hi lagte hain) aur harder to debug.
  • Chunk overlap — consecutive chunks ke beech kuch tokens overlap rakho (e.g. 50 tokens), taaki agar koi important info chunk boundary pe split ho jaaye, wo dono neighbouring chunks mein partially present rahe.
StrategyProsConsKab use karo
Fixed-sizeSimple, fast, predictable chunk countSentences beech mein cut ho sakte hainQuick prototype, unstructured logs
Sentence/paragraph-awareSemantic coherence betterChunk sizes uneven ho sakte hainDocs, articles, knowledge base — most common default
Semantic chunkingTopic-boundary-aware, best retrieval precisionExtra embedding calls, slower indexingHigh-value corpora jahan retrieval quality critical hai
Chunk overlap (any strategy ke saath)Boundary info loss kam hota haiIndex size aur storage cost badhta haiAlmost always thoda overlap (10-20%) rakhna safe default hai
⚠️ Chunk size ka trade-off samajh lo

Bahut chhote chunks (e.g. 100 tokens) — precise retrieval milta hai lekin context incomplete reh sakta hai (surrounding info miss ho jaata hai). Bahut bade chunks (e.g. 2000 tokens) — zyada context milta hai lekin embedding "diluted" ho jaati hai (ek chunk mein multiple unrelated topics mix ho jaate hain, jisse similarity search kam precise hoti hai). Sweet spot generally 300-800 tokens ke around hota hai, but hamesha apne document type aur query patterns pe eval karke tune karo — koi universal "best" number nahi hai.

Embeddings for Retrieval

Retrieval ke liye tumhe ek embedding model train nahi karna — bas ek existing embedding API call karke text ko vector mein convert karna hai (e.g. OpenAI text-embedding-3-small, Cohere embed-v3, ya open-source jaise BAAI/bge-small-en). Har chunk ko embed karo, aur query ko bhi usi model se embed karo — dono ko same embedding model se pass karna zaroori hai, kyunki alag models ka vector space alag hota hai, unke beech similarity meaningless hoti hai.

Similarity typically cosine similarity se measure hoti hai — do vectors ke beech ka angle, jitna chhota angle utni zyada similarity. Retrieval query ka embedding nikaal ke, vector DB mein stored chunk embeddings ke saath cosine similarity compute karke top-k closest chunks return kiye jaate hain.

📌 Embedding model consistency — silent bug source

Agar tumne apna index ek embedding model se banaya (e.g. text-embedding-3-small), aur baad mein model version/provider switch kar diya bina re-indexing kiye — retrieval silently degrade ho jaayega, koi error nahi aayega, bas results irrelevant lagne lagenge. Embedding model change karna = poora index rebuild karna padega, ye ek migration event hai, casual config change nahi.

Vector Databases

Vector database ek specialized storage system hai jo high-dimensional vectors ko efficiently store aur query karta hai — specifically "given a query vector, mujhe top-k nearest vectors do" (nearest neighbor search). Naive approach — har stored vector ke saath query vector ko compare karo (brute force) — millions of vectors ke saath bahut slow ho jaata hai. Isliye vector DBs ANN (Approximate Nearest Neighbor) algorithms use karte hain (jaise HNSW — Hierarchical Navigable Small World graphs) jo approximate lekin bahut fast results dete hain — thoda accuracy trade-off karke massive speed gain milta hai.

Popular options: pgvector (Postgres extension — agar already Postgres use kar rahe ho, no new infra), Pinecone (fully managed, easy setup), Qdrant (open-source, self-hosted ya managed dono), Chroma (lightweight, local-first, great for prototyping), Weaviate (open-source, built-in hybrid search support).

Vector DBTypeKab pick karo
pgvectorSelf-hosted (Postgres extension)Already Postgres use ho raha hai, extra infra avoid karna hai, moderate scale
PineconeFully managedFast setup chahiye, scaling/infra khud manage nahi karni, budget available hai
QdrantSelf-hosted or managedOpen-source chahiye but production-grade performance bhi, flexibility
ChromaSelf-hosted (local-first)Prototyping, small-to-medium apps, simplicity priority

General rule: managed (Pinecone) chuno jab team chhoti hai aur infra ops overhead avoid karna hai — pay-per-use, koi scaling headache nahi. Self-hosted (pgvector/Qdrant) chuno jab data residency/cost control zaroori hai, ya already relevant infra (Postgres) exist karta hai jisme naya moving part add karna avoid karna hai.

Reranking — Top-K Se Aage

Vector similarity search (cosine similarity pe based top-k) ek fast but approximate filter hai — embeddings semantic similarity capture karte hain, lekin hamesha "actual relevance to this specific query" ka perfect proxy nahi hote. Top-k=20 mein aksar kuch chunks aise honge jo superficially similar dikhte hain (same topic ke keywords) lekin query ka actual answer nahi rakhte.

Reranking ek second, zyada precise step hai — ek cross-encoder model (jo query aur chunk ko ek saath input leke relevance score deta hai, unlike bi-encoder embeddings jo query aur chunk ko independently embed karte hain) top-k candidates ko re-score karta hai, aur sirf top-3/5 ko final context mein bheja jaata hai. Cross-encoders bi-encoders se slower hote hain (isliye sabhi documents pe nahi chalaye ja sakte, sirf top-k candidates pe), lekin significantly zyada accurate relevance judgment dete hain. Popular option — Cohere Rerank API, ya open-source cross-encoder models (jaise ms-marco-MiniLM).

🧠 Senior Dev Note — Retrieve-then-rerank ek standard production pattern hai

Production RAG systems almost hamesha two-stage retrieval use karte hain: Stage 1 — vector search se broad recall (top-20 ya top-50 candidates, fast, approximate). Stage 2 — cross-encoder rerank se precision (top-20 ko top-3/5 tak narrow karo, slower but accurate). Ye classic information retrieval "recall then precision" pattern hai — agar sirf stage 1 (vector search) use karte ho, tumhe recall to milega lekin precision compromise hogi, jisse LLM ko irrelevant chunks context mein milte hain aur answer quality gir jaati hai. Reranking add karna aksar sabse high-ROI single improvement hai jo tum ek RAG pipeline mein kar sakte ho.

End-to-End Practical Code

Chalo ek complete, chhota lekin realistic RAG pipeline banate hain — document chunk karna, embed karna, Chroma (local vector store) mein upsert karna, query ke liye top-k retrieve karna, simplified rerank karna, aur phir LLM ko augmented context ke saath call karna. Reader ke explicit request pe — har single line commented hai.

rag_pipeline.py — End-to-end RAG: chunk → embed → store → retrieve → rerank → generate
# rag_pipeline.py — chhota lekin complete RAG pipeline, Chroma ko local vector store ki tarah use karke

import chromadb  # Chroma client — local, lightweight vector database
from openai import OpenAI  # OpenAI SDK — embeddings aur chat completion dono ke liye

# OpenAI client banao — env var OPENAI_API_KEY se automatically key uthayega
client = OpenAI()  # client object — baaki saare API calls isi se honge

# chunk_text — document ko fixed-size, overlap ke saath chunks mein todta hai
def chunk_text(text, chunk_size=500, overlap=50):
    # final chunks store karne ke liye empty list
    chunks = []
    # start pointer 0 se shuru karo
    start = 0
    # jab tak poora text cover na ho jaaye, loop chalao
    while start < len(text):
        # end pointer — chunk_size characters aage
        end = start + chunk_size
        # text ka slice le lo start se end tak — ye ek chunk hai
        chunk = text[start:end]
        # chunk ko list mein add karo (leading/trailing whitespace strip karke)
        chunks.append(chunk.strip())
        # next start — end se overlap kam karke, taaki boundary info dono chunks mein aaye
        start = end - overlap
    # saare chunks ki list return karo
    return chunks

# embed_texts — texts ki list leke, OpenAI embedding API se unke vectors nikaalta hai
def embed_texts(texts):
    # embeddings.create call karo — model aur input texts pass karke
    response = client.embeddings.create(
        model="text-embedding-3-small",  # chhota, fast, sasta embedding model
        input=texts,  # texts ki list — batch mein embed ho jaayenge
    )  # API call close — response object mein sabhi embeddings aa jaate hain
    # response.data list mein har item ka .embedding field hota hai — sabko extract karo
    return [item.embedding for item in response.data]

# build_index — document ko chunk + embed karke Chroma collection mein upsert karta hai
def build_index(document_text, collection):
    # document ko chunks mein todo
    chunks = chunk_text(document_text)
    # har chunk ka embedding vector nikaalo (ek hi batch API call mein)
    embeddings = embed_texts(chunks)
    # har chunk ke liye ek unique ID banao (chunk-0, chunk-1, ...)
    ids = [f"chunk-{i}" for i in range(len(chunks))]
    # Chroma collection mein ek saath upsert karo — ids, embeddings, aur original text (documents)
    collection.upsert(
        ids=ids,  # har chunk ka unique identifier
        embeddings=embeddings,  # corresponding vector representations
        documents=chunks,  # original chunk text — retrieval ke baad LLM ko dikhane ke liye
    )  # upsert call close — Chroma collection ab query karne ke liye ready hai
    # kitne chunks index hue, wo return kar do (logging/debugging ke liye)
    return len(chunks)

# retrieve_top_k — query ko embed karke vector DB se top-k nearest chunks nikaalta hai
def retrieve_top_k(query, collection, k=10):
    # query ka embedding nikaalo (single-item list mein wrap karke embed_texts call kiya)
    query_embedding = embed_texts([query])[0]
    # Chroma se query karo — top-k nearest neighbors chahiye query_embedding ke
    results = collection.query(
        query_embeddings=[query_embedding],  # query vector, list mein wrapped (batch API hai)
        n_results=k,  # kitne nearest chunks chahiye
    )  # query call close — results ek dict hai jisme ids/documents/distances hote hain
    # results['documents'] ek nested list hoti hai (per-query) — pehla query ka result nikaalo
    return results["documents"][0]

# simple_rerank — simplified cross-encoder-style rerank: LLM khud relevance score deta hai
# (production mein isko Cohere Rerank API se replace karo — yahan concept dikhane ke liye simplified hai)
def simple_rerank(query, candidate_chunks, top_n=3):
    # scored chunks store karne ke liye list
    scored = []
    # har candidate chunk ke liye loop chalao
    for chunk in candidate_chunks:
        # chhota LLM call — chunk ko query ke against 0-10 relevance score do
        response = client.chat.completions.create(
            model="gpt-4o-mini",  # sasta/fast model, sirf scoring ke liye
            messages=[
                {"role": "system", "content": "Reply with only a number 0-10: relevance of the passage to the query."},  # strict output instruction
                {"role": "user", "content": f"Query: {query}\nPassage: {chunk}"},  # query aur candidate chunk dono ek saath pass — cross-encoder jaisa behavior
            ],  # messages list close — system + user, dono roles diye gaye
        )  # chat.completions.create call close
        # response se score text nikaalo aur float mein convert karo (fallback 0 agar parse fail ho)
        try:  # model kabhi non-numeric text bhi de sakta hai, isliye safe parsing
            score = float(response.choices[0].message.content.strip())  # raw text ko strip karke float mein convert karo
        except ValueError:  # agar conversion fail ho (model ne number nahi diya)
            score = 0.0  # agar model ne number nahi diya, safe default
        # (chunk, score) tuple ko list mein add karo
        scored.append((chunk, score))
    # score ke hisaab se descending sort karo (highest relevance pehle)
    scored.sort(key=lambda pair: pair[1], reverse=True)
    # top_n sabse relevant chunks (sirf text, score chhod ke) return karo
    return [chunk for chunk, score in scored[:top_n]]

# answer_with_context — reranked chunks ko context banake LLM se final answer generate karwata hai
def answer_with_context(query, context_chunks):
    # saare context chunks ko double newline se joinkar ek single context string banao
    context = "\n\n".join(context_chunks)
    # final generation call — system prompt mein grounding instruction, user prompt mein context + query
    response = client.chat.completions.create(
        model="gpt-4o",  # final answer ke liye stronger model
        messages=[
            {"role": "system", "content": "Answer only using the provided context. If the answer isn't in the context, say you don't know."},  # hallucination control — sirf context se answer do
            {"role": "user", "content": f"Context:\n{context}\n\nQuestion: {query}"},  # augmented prompt — context + original query
        ],  # messages list close
    )  # chat.completions.create call close — response mein final generated answer hai
    # generated answer text return karo
    return response.choices[0].message.content

# --- pipeline chalane ka example ---
if __name__ == "__main__":  # script directly run hone pe hi ye block chalega, import hone pe nahi
    # Chroma ka in-memory (ephemeral) client banao — local prototyping ke liye
    chroma_client = chromadb.EphemeralClient()  # koi disk persistence nahi — process restart pe data gone
    # ek collection banao (ya existing ko get karo) jisme chunks store honge
    collection = chroma_client.get_or_create_collection("docs")

    # sample document text — real use case mein ye PDF/markdown parsing se aayega
    document = """Our refund policy allows returns within 30 days of purchase.
    Refunds are processed within 5-7 business days. Digital products
    are non-refundable once downloaded. Shipping costs are non-refundable
    unless the item arrived damaged."""

    # document ko index karo — chunk + embed + upsert
    num_chunks = build_index(document, collection)
    # kitne chunks bane, print karo (sanity check)
    print(f"Indexed {num_chunks} chunks")

    # user ka query
    query = "Can I get a refund on a digital product I already downloaded?"
    # stage 1 — vector search se broad recall (top-10 candidates)
    candidates = retrieve_top_k(query, collection, k=10)
    # stage 2 — rerank karke top-3 sabse relevant chunks nikaalo
    top_chunks = simple_rerank(query, candidates, top_n=3)
    # final answer generate karo, reranked chunks ko context ki tarah use karke
    answer = answer_with_context(query, top_chunks)
    # answer print karo
    print(f"Answer: {answer}")

Notice karo pipeline ka shape — index-time (chunk → embed → upsert, jo ek baar ya periodically chalta hai) aur query-time (embed query → retrieve → rerank → generate, jo har user request pe chalta hai) clearly separate hain. Ye separation production mein important hai kyunki dono ka scaling/latency profile bahut different hota hai — indexing batch/async ho sakta hai, query-time path latency-sensitive hai.

Common Failure Modes Aur Fixes

  • Irrelevant chunks retrieve ho rahe hain — usually bad chunking (boundaries galat) ya embedding model domain-mismatch (e.g. generic embedding model legal/medical jargon pe weak) ki wajah se. Fix — chunking strategy revisit karo, aur domain-specific ya fine-tuned embedding model try karo.
  • "Lost in the middle" problem — LLMs context window ke start aur end mein di gayi information ko middle se better recall karte hain. Agar tumne 20 chunks context mein daal diye, middle wale chunks ka info answer mein miss ho sakta hai chahe wo relevant ho. Fix — sirf top-k (reranked, small — 3-5) chunks pass karo, bulk-dump mat karo; important-most chunk ko start ya end ke paas rakho.
  • Stale index — source documents update hote rehte hain, lekin agar vector index ko re-index nahi kiya to retrieval outdated info return karega. Fix — ek re-indexing pipeline banao (scheduled job ya event-driven — document update hote hi trigger), aur stale chunks ko delete/replace karo, sirf append mat karte raho.
  • Exact-match queries fail ho jaate hain — pure semantic/vector search exact keywords, IDs, error codes, product SKUs jaisi cheezein miss kar sakta hai kyunki embeddings "meaning" capture karte hain, "exact string" nahi. Fix — hybrid search use karo (keyword/BM25 search + vector search dono, results ko combine/re-rank karo) — Weaviate aur Qdrant jaise DBs isko built-in support karte hain.

Jab RAG Wrong Tool Hai

RAG har problem ka solution nahi hai. Do common cases jahan RAG overkill ya wrong fit hota hai:

  • Document itna chhota hai ki context window mein fit ho jaaye — agar tumhara knowledge base 5-10 pages hai, seedha poora document system prompt mein daal do. Retrieval pipeline (chunking, embedding, vector DB) banane ka overhead is case mein unnecessary complexity hai.
  • Real-time, single-fact lookup chahiye — jaise "aaj ka stock price kya hai" ya "mera order kahan hai". Ye information kisi static indexed knowledge base mein nahi hoti, aur constantly change hoti hai. Isके liye RAG nahi, ek tool/function call (live API hit karna) sahi approach hai — ye chapter 6 mein detail mein cover hoga.
💡 Hinglish Tip — Ek line mein sab kuch

RAG ka core skill "LLM ko documents dikhana" nahi hai — core skill hai sahi documents reliably retrieve karna. Chunking, embedding model choice, vector DB, aur reranking — ye sab isi ek goal ki taraf point karte hain. Agar retrieval weak hai, generation kitna bhi acha model use karo, output bhi weak hi rahega.

Key Takeaways

  • RAG ke 3 steps (retrieval, augmentation, generation) simple hain, lekin production quality retrieval engineering pe depend karti hai, generation model pe nahi.
  • Chunking strategy (fixed-size, sentence-aware, semantic) aur overlap directly retrieval precision ko affect karte hain — koi universal "best" size nahi, apne corpus pe eval karo.
  • Query aur stored chunks same embedding model se embed hone chahiye — model switch karna = full re-index required.
  • Vector DBs ANN search (jaise HNSW) use karte hain speed ke liye — managed (Pinecone) vs self-hosted (pgvector/Qdrant/Chroma) choice team size aur infra control priorities pe depend karta hai.
  • Reranking (cross-encoder, e.g. Cohere Rerank) ek high-ROI second stage hai — top-k vector search ke baad top-3/5 ko precisely re-score karke context quality significantly improve hoti hai.
  • Failure modes — irrelevant chunks (bad chunking/embedding mismatch), lost-in-the-middle (bahut zyada chunks pass karna), stale index (re-indexing pipeline missing), exact-match misses (hybrid search se fix hota hai).
  • RAG wrong tool hai jab document already chhota hai (seedha context mein daalo) ya jab real-time single-fact chahiye (tool call use karo, chapter 6).

🎯 Interview Questions — AI Engineer

Q1. Chunk size choose karte waqt kya trade-offs consider karoge?

Bahut chhote chunks precise retrieval dete hain lekin context incomplete ho sakta hai — surrounding info miss ho jaata hai. Bahut bade chunks zyada context dete hain lekin embedding "diluted" ho jaati hai kyunki ek chunk mein multiple unrelated ideas mix ho jaate hain, jisse similarity search kam precise hoti hai. Practical default 300-800 tokens ke around hai with some overlap (10-20%), lekin final answer hamesha apne document type aur real query patterns pe eval karke tune karna chahiye — koi universal number kaam nahi karega.

Q2. Vector similarity search (top-k cosine similarity) akela kyun sufficient nahi hota, aur reranking kya solve karta hai?

Vector search bi-encoder embeddings use karta hai — query aur chunk independently embed hote hain, jo fast hai but approximate. Top-k mein aksar superficially-similar-lekin-actually-irrelevant chunks aa jaate hain. Reranking ek cross-encoder use karta hai jo query aur chunk ko ek saath input leke sahi relevance score deta hai — slower hai (isliye sirf top-k candidates pe chalta hai, sabhi documents pe nahi), lekin accuracy significantly better hoti hai. Ye "recall then precision" ka classic two-stage retrieval pattern hai.

Q3. Managed vector DB (Pinecone) vs self-hosted (pgvector/Qdrant) — kaise decide karoge?

Managed chuno jab team chhoti hai, fast setup chahiye, aur infra ops overhead avoid karna hai — cost thoda zyada hoga but operational simplicity milegi. Self-hosted (pgvector agar already Postgres use ho raha hai, ya Qdrant agar dedicated open-source solution chahiye) chuno jab data residency/cost control zaroori hai, ya existing infra mein naya managed service add karna avoid karna hai. Scale aur compliance requirements bhi factor hote hain — bahut large scale ya strict data residency wale cases mein self-hosted zyada control deta hai.

Q4. "Lost in the middle" problem kya hai, aur RAG pipeline design mein isse kaise avoid karoge?

LLMs context window ke start aur end mein diye gaye information ko middle ke content se better recall karte hain — agar bahut saare chunks (e.g. 15-20) ek saath context mein daal diye, middle wale chunks ka info answer generation mein effectively "lost" ho sakta hai chahe wo relevant ho. Fix — reranking se sirf sabse relevant top-3/5 chunks pass karo (bulk-dump avoid karo), aur agar multiple chunks pass karne hi hain to sabse important chunk ko prompt ke start ya end ke paas position karo.

Q5. Ek user complain karta hai ki RAG system exact product SKU/error-code queries pe galat/irrelevant results deta hai jabki general questions pe theek kaam karta hai — kya ho raha hai aur kaise fix karoge?

Pure vector/semantic search embeddings pe based hota hai jo "meaning" capture karta hai, exact strings/IDs/codes nahi — isliye SKU ya error-code jaise exact-match queries pe weak hota hai (semantically similar lekin wrong SKU wale chunks retrieve ho sakte hain). Fix — hybrid search implement karo, keyword/BM25-based search (exact match ke liye strong) ko vector search ke saath combine karo, aur dono ke results ko merge/rerank karo. Weaviate aur Qdrant jaise vector DBs isko built-in support karte hain, jisse ek hi query dono retrieval modes se benefit leti hai.
