Lazy Load Images and iframe Elements

Below-the-fold cheezon ko turant load karne ka koi matlab nahi — user ne unhe dekha bhi nahi. Is chapter mein dekhenge native loading="lazy" browser internally kaise kaam karta hai, Intersection Observer se manual control kaise milta hai, aur third-party embeds (YouTube/ads/maps) ka facade pattern se cost kaise 90% tak kaat sakte ho.

1. Lazy loading kyun zaroori hai

Ek typical e-commerce ya blog page mein 20-50 images ho sakti hain, lekin user apne pehle scroll mein sirf 3-4 dekhta hai. Agar saari images page load ke time hi fetch ho jaayen, toh:

  • Network bandwidth un images pe waste hoti hai jo shayad user dekhega hi nahi.
  • Critical resources (jaise above-the-fold CSS, hero image, fonts) ke saath connection contention hoti hai — browser ke paas limited parallel HTTP connections hote hain.
  • Mobile data users ke liye ye directly cost hai — unnecessary MBs download ho rahe hain.
  • Main thread aur memory bhi extra images decode/paint karne mein busy hoti hai.

Lazy loading ka core idea simple hai: resource ko tab fetch karo jab wo viewport ke "near" ho, na ki page load hote hi. Do tareeke hain isko implement karne ke — native browser attribute, ya JavaScript se manual (Intersection Observer).

2. Native loading="lazy" — andar se kaise kaam karta hai

<img> aur <iframe> dono ka loading attribute do values leta hai:

ValueBehavior
eagerDefault. Resource turant, page parse hote hi fetch hota hai.
lazyResource tab fetch hota hai jab wo viewport se "set distance" ke andar aa jaaye.

Ye "set distance" (yaani lazy-load threshold) browser-specific hota hai — spec isko fix number nahi karta. Chrome jaise browsers internally ek distance-from-viewport calculation karte hain, aur ye factors pe depend kar sakta hai jaise effective connection type (4G vs slow-3G) aur image ka type. Idea ye hai ki threshold itna bada rakha jaaye ki jab tak user scroll karke wahan pahunche, image already load ho chuki ho — taaki visually koi "pop-in" na dikhe.

Best part: ye purely browser-managed hai — zero JavaScript chahiye. Browser khud decide karta hai kab fetch karna hai, kab decode karna hai. Support bhi ab universal hai (sab major browsers mein <img> aur <iframe> dono pe).

Native lazy loading — below-the-fold image aur embedded map
<!-- Ye image page ke bottom section mein hai, fold ke bahar -->
<img
  src="team-photo.jpg"
  <!-- loading="lazy" — browser ko batata hai ki jab tak ye viewport ke
       "near" na aaye tab tak fetch mat karo. Andar se koi JS event nahi
       lagta, browser ka internal scheduler distance-from-viewport check
       karke khud network request trigger karta hai -->
  loading="lazy"
  <!-- decoding="async" — main thread ko block kiye bina image ko
       decode karne ki permission deta hai, taaki paint smooth rahe -->
  decoding="async"
  <!-- width/height dena zaroori hai — browser ko layout space pehle se
       pata chal jaata hai, isliye CLS (layout shift) nahi hota jab image
       later load hoti hai -->
  width="480"
  height="320"
  alt="Team photo — office offsite 2025"
>

<!-- Ek embedded Google Map, jo aksar page ke footer/contact section mein
     hota hai — user tab hi scroll karke wahan pahunchega jab use address
     dekhna ho, isliye lazy loading perfect fit hai -->
<iframe
  src="https://maps.example.com/embed?q=clear-office"
  <!-- loading="lazy" iframe pe bhi same tarah kaam karta hai — Chrome
       is dauran ek placeholder space reserve kar leta hai taaki layout
       shift na ho jab iframe actually load ho -->
  loading="lazy"
  width="600"
  height="400"
  <!-- referrerpolicy/title accessibility aur privacy ke liye best
       practice hai, lazy loading se directly related nahi -->
  title="Office location map"
></iframe>
⚠️ LCP element ko kabhi lazy mat karo

Ye sabse common real-world mistake hai: developer poore page ki saari <img> tags pe blindly loading="lazy" laga deta hai — including hero image jo LCP (Largest Contentful Paint) candidate hai. Ye seedha ulta result deta hai.

Wajah root-level: agar viewport ke andar dikh rahi <img> pe loading="lazy" hai, toh browser usse tab tak fetch nahi karega jab tak saari CSS download, parse aur apply na ho jaaye — kyunki lazy-loaded image ko pehle layout complete hone ka wait karna padta hai taaki browser confirm kar sake ki uski final position viewport ke andar hai ya nahi. Iska matlab hai image ka network request artificially delay ho jaata hai — exactly wahi resource jiska LCP timing sabse zyada matter karta hai. Result: LCP score worse ho jaata hai, kabhi kabhi 500ms-1s tak degrade.

Rule: hero images ya kisi bhi element jo likely above-the-fold hai, usse loading="lazy" attribute mat lagao — ya toh attribute omit karo (default eager), ya explicitly loading="eager" + fetchpriority="high" use karo taaki browser usse sabse pehle fetch kare.

3. Intersection Observer API — manual fallback

Native loading="lazy" sirf <img> aur <iframe> pe kaam karta hai. Lekin kai cheezein is scope se bahar hain:

  • <video> elements aur unke poster images
  • CSS background-image se load hone waali images (ye browser-level lazy loading feature nahi hai)
  • Custom widgets jinhe tum khud control karna chahte ho (custom root margin, priority order, analytics events on visibility, etc.)

Isliye libraries jaise lazysizes aur yall.js internally Intersection Observer API use karti hain (aur agar page ka HTML dynamically change hota hai, toh saath mein Mutation Observer bhi) — taaki pata chale element kab viewport mein enter kar raha hai. Pattern ye hota hai: real attribute (src) ki jagah ek non-standard placeholder attribute (data-src) rakha jaata hai, aur jab element intersect ho jaata hai, JS usse swap karke asli attribute set karta hai — tab jaake network request fire hoti hai.

3.1 Intersection Observer ka mental model

IntersectionObserver ek browser-native API hai jo tumhe ek callback deta hai jab koi target element apne "root" (default: viewport) ke saath intersect (overlap) karna shuru ya band karta hai — bina scroll event listener ke. Ye important hai kyunki traditional scroll event listener + getBoundingClientRect() polling main thread pe bahut expensive hota hai (har scroll frame pe layout recalculation force karta hai — "layout thrashing"). Intersection Observer ye calculation browser ke compositor thread pe async karta hai, isliye scroll performance pe zero impact padta hai.

4. CSS background-image lazy loading — full implementation

Ye classic use-case hai jahan native loading="lazy" kaam nahi karega, kyunki wo sirf <img>/<iframe> tags pe applicable hai, CSS property pe nahi. Neeche ek complete, production-style implementation hai — har line commented.

HTML — placeholder markup
<!-- Real image URL ko data-* attribute mein rakha hai, actual "src" ya
     "background-image" abhi set NAHI kiya — taaki browser abhi request
     fire na kare -->
<div
  class="lazy-bg"
  data-bg="/images/hero-banner-section2.jpg"
  <!-- Placeholder ke liye chhota blurred/low-res background ya solid
       color CSS mein already laga sakte ho, taaki layout shift na ho -->
  style="min-height: 400px; background-color: #262524;"
>
  <h2>Featured Collection</h2>
</div>
JavaScript — Intersection Observer se background-image lazy load
// 1. Saare ".lazy-bg" elements ko DOM se select kar rahe hain jinke
//    background-image ko lazy load karna hai
const lazyBgElements = document.querySelectorAll(".lazy-bg");

// 2. Observer callback — ye function tab call hota hai jab observed
//    elements ki intersection status change hoti hai (viewport ke
//    andar aaye ya bahar gaye)
const onIntersect = (entries, observer) => {
  // 3. "entries" ek array hai — har entry ek observed element ke baare
  //    mein current intersection info deta hai
  entries.forEach((entry) => {
    // 4. isIntersecting true tabhi hota hai jab element root (viewport)
    //    ke saath overlap kar raha ho — yaani ab visible ho raha hai
    if (entry.isIntersecting) {
      // 5. entry.target = wahi DOM element jo intersect hua hai
      const el = entry.target;

      // 6. data-bg attribute se real image URL nikal rahe hain
      const bgUrl = el.getAttribute("data-bg");

      // 7. Ab actual background-image CSS property set kar rahe hain —
      //    yehi line network request trigger karti hai, image ab
      //    download hogi
      el.style.backgroundImage = `url("${bgUrl}")`;

      // 8. Ek class add kar rahe hain taaki CSS transition (fade-in
      //    effect) trigger ho sake — purely visual polish
      el.classList.add("bg-loaded");

      // 9. CRITICAL cleanup step: is element ko observer se unobserve
      //    kar rahe hain. Agar ye step miss kiya toh observer element
      //    ko forever track karta rahega — memory leak aur unnecessary
      //    callback firing (jaise user scroll up/down karta rahe)
      observer.unobserve(el);
    }
    // 10. Agar isIntersecting false hai (abhi viewport se bahar hai),
    //     kuch nahi karte — bas wait karte hain agle intersection tak
  });
};

// 11. Observer instance banate hain — pehla argument callback function
//     hai, dusra ek "options" object hai jo threshold/rootMargin
//     control karta hai
const observer = new IntersectionObserver(onIntersect, {
  // 12. root: null matlab default viewport ko intersection container
  //     bana rahe hain (kisi custom scrollable div ke bajaye)
  root: null,

  // 13. rootMargin: viewport ke "virtual boundary" ko expand karta hai.
  //     "200px 0px" ka matlab hai top aur bottom mein 200px ka extra
  //     margin add ho gaya — yaani element viewport mein actually aane
  //     se 200px PEHLE hi "intersecting" maana jaayega. Isse image ko
  //     preload karne ka thoda extra time milta hai, taaki jab tak user
  //     scroll karke wahan pahunche, image already load ho chuki ho
  rootMargin: "200px 0px",

  // 14. threshold: kitna % element visible hona chahiye callback fire
  //     hone ke liye. 0 ka matlab hai — even 1 pixel bhi visible/near
  //     ho (rootMargin ke combined saath) toh trigger ho jaayega
  threshold: 0,
});

// 15. Har ek lazy-bg element ko observer ke saath register kar rahe
//     hain — ab observer inhe track karna shuru karega
lazyBgElements.forEach((el) => {
  observer.observe(el);
});
⚙️ rootMargin ko production mein kaise tune karein

rootMargin ka best value network speed pe depend karta hai. Fast connections (WiFi/4G) pe 200-300px reasonable hai. Slow connections pe zyada margin (600-800px) rakhna better hota hai taaki loading ka time mile — is decision ke liye navigator.connection.effectiveType check karke dynamically rootMargin adjust kar sakte ho. Yehi wo "custom control" hai jo native loading="lazy" nahi deta — browser apna fixed heuristic use karta hai, tum apna khud define nahi kar sakte.

5. Third-party iframe embeds lazy loading

Real-world apps mein sabse bada perf killer aksar apna khud ka code nahi hota — third-party embeds hote hain: YouTube video embed, Google Maps, ads, chat widgets, social share buttons. Ye har ek apna khud ka JS bundle, CSS, aur network requests laata hai — often 100s of KB, jo page load ke time hi fire ho jaate hain agar lazy load nahi kiya.

Concrete numbers: ek average YouTube <iframe> embed ko lazy load karna initial page load se 500+ KiB bacha sakta hai. Facebook "Like" button plugin ko lazy load karna 200+ KiB bachata hai — jisme se zyadatar JavaScript hota hai.

Solution simple hai — same native loading="lazy" attribute jo images pe use kiya, wahi <iframe> pe bhi laga do:

YouTube embed — native lazy loading
<!-- Ye iframe below-the-fold hai (video article ke middle/end mein) -->
<iframe
  width="560"
  height="315"
  src="https://www.youtube.com/embed/VIDEO_ID"
  <!-- loading="lazy" — Chrome jab tak ye iframe viewport ke near nahi
       aata, YouTube ka poora player JS/CSS download hi nahi karega.
       Iske saath Chrome placeholder space bhi reserve kar leta hai
       taaki jab iframe load ho, koi layout shift (CLS) na ho -->
  loading="lazy"
  title="Demo video"
  frameborder="0"
  allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture"
  allowfullscreen
></iframe>

Rule of thumb: jab bhi koi <iframe> fold ke neeche hai aur upfront load karna critical nahi hai, strongly consider karo usse lazy load karna. Ads ke case mein bhi yahi apply hota hai — sirf visible ad slots ko load karo, baaki lazy.

6. Facade pattern — click-to-load

🧠 Senior Dev Note — Facade pattern for heavy embeds

loading="lazy" sirf load ko defer karta hai — jab element viewport ke near aayega, poora heavy embed (JS bundle, tracking scripts, player code) still download hoga. Agar embed genuinely heavy hai (jaise YouTube player, jo apna khub sara JS aur ads-related tracking laata hai), toh better strategy hai facade pattern: real iframe ki jagah ek static, lightweight placeholder (jaise YouTube ka thumbnail image + play button icon) dikhao. Sirf tab jab user usse interact kare (click ya hover-hold), tab actual iframe ko DOM mein inject karo.

Fayda: agar user video kabhi play hi nahi karta (jo bahut common hai — bahut log scroll karke aage nikal jaate hain), toh us heavy resource ka network aur JS cost kabhi lagta hi nahi. Ye lazy loading se ek level aage hai — lazy loading "jab visible ho tab load karo", facade "jab user chahe tab hi load karo". Production mein khud implement karne ke bajaye battle-tested libraries use karo — lite-youtube-embed YouTube ke liye, lite-vimeo-embed Vimeo ke liye. Chat widgets (Intercom/Drift jaise) ke liye same pattern apply hota hai — ek fake "Start Chat" button dikhao, real widget sirf meaningful interaction (click ya pointer-hold) pe load karo.

Facade pattern — minimal vanilla JS implementation
<!-- Real iframe ki jagah ek lightweight div — sirf ek thumbnail image
     aur play button, koi YouTube JS load nahi ho raha -->
<div
  class="yt-facade"
  data-video-id="VIDEO_ID"
  style="background-image:url('https://i.ytimg.com/vi/VIDEO_ID/hqdefault.jpg');"
>
  <button class="play-btn" aria-label="Play video">▶</button>
</div>

<script>
  // 1. Saare facade elements select kar rahe hain
  document.querySelectorAll(".yt-facade").forEach((facade) => {
    // 2. Har facade pe ek click listener laga rahe hain
    facade.addEventListener("click", () => {
      // 3. data-video-id se actual video ID nikal rahe hain
      const videoId = facade.getAttribute("data-video-id");

      // 4. Ab asli YouTube iframe ka element banate hain — ye tabhi
      //    banta hai jab user ne explicitly click kiya ho, isliye
      //    YouTube ka JS/CSS/network cost sirf ab lagega
      const iframe = document.createElement("iframe");
      iframe.src = `https://www.youtube.com/embed/${videoId}?autoplay=1`;
      iframe.allow = "autoplay; encrypted-media";
      iframe.allowFullscreen = true;
      iframe.width = "560";
      iframe.height = "315";

      // 5. Facade div ko real iframe se replace kar rahe hain — user ko
      //    seamless lagta hai, video turant play hone lagta hai
      facade.replaceWith(iframe);
    });
  });
</script>

Key Takeaways

  • loading="lazy" <img> aur <iframe> dono pe kaam karta hai, zero JS ke saath — browser khud distance-from-viewport threshold decide karta hai (connection type, image type jaise factors se influenced).
  • Hero/LCP images pe kabhi loading="lazy" mat lagao — lazy image ka fetch tab tak delay hota hai jab tak CSS fully parse/apply na ho jaaye, jo LCP ko directly worsen karta hai.
  • Jo cheezein native attribute cover nahi karta (CSS background-image, <video>, custom root margins) — unke liye Intersection Observer API use karo, jo scroll-event polling se kaafi zyada performant hai.
  • Har Intersection Observer implementation mein observer.unobserve() cleanup call karna non-negotiable hai — nahi toh memory leak aur unnecessary re-firing hoti rahegi.
  • Below-the-fold third-party <iframe> embeds (YouTube, maps, ads) ko lazy load karna 100s of KB directly bacha sakta hai.
  • Heavy embeds ke liye facade pattern (static thumbnail → click-to-load real iframe) lazy loading se ek level aage hai — resource sirf tab lagta hai jab user genuinely interact kare.

🎯 Interview Questions

  • Q: Native loading="lazy" ka distance threshold browser kaise decide karta hai?
    Hint: Spec fixed number nahi deta — browser-specific heuristic hai, jisme effective connection type aur resource type jaise factors involve ho sakte hain. Purpose: user scroll karke pahunche tab tak resource ready ho.
  • Q: Hero image pe loading="lazy" lagane se LCP kyun worsen hota hai?
    Hint: Lazy image ka fetch tab tak trigger nahi hota jab tak CSS fully download/parse/apply na ho jaaye — kyunki browser ko layout confirm karna padta hai ki element viewport ke andar hai. Ye delay LCP-critical resource ko late kar deta hai.
  • Q: Intersection Observer scroll event + getBoundingClientRect() se better kyun hai?
    Hint: Scroll listener + getBoundingClientRect() har frame pe forced synchronous layout recalculation karta hai (layout thrashing), main thread block karta hai. Intersection Observer async hai, compositor thread pe kaam karta hai.
  • Q: rootMargin aur threshold options mein kya difference hai?
    Hint: rootMargin viewport ke virtual boundary ko expand/shrink karta hai (early trigger ke liye). threshold define karta hai element ka kitna % visible hona chahiye callback fire hone ke liye.
  • Q: Facade pattern lazy loading se kaise better hai heavy third-party embeds ke liye?
    Hint: Lazy loading "jab visible ho tab load karo" — resource phir bhi load hota hai eventually. Facade "jab user interact kare tab hi load karo" — agar user interact hi nahi karta, resource ka cost kabhi lagta hi nahi.
  • Q: Intersection Observer callback mein unobserve() call na kare toh kya production issue aayega?
    Hint: Observer element ko forever track karta rahega — memory leak, aur agar element repeatedly intersect/un-intersect hota hai (scroll up-down), callback baar baar unnecessarily fire hoga.
