Code-split JavaScript

Bada bundle kyun hurt karta hai

Jab tum saara app ka JS ek single bundle.js mein ship karte ho, to browser ko us poore file ka cost pay karna padta hai — chahe user us page pe abhi sirf home screen dekh raha ho. Cost teen stages mein aata hai, aur teeno hi bytes ke proportional hain, matlab unused code bhi cost lagata hai:

  • Download — network pe bytes transfer, jo mobile/3G pe already slow hai.
  • Parse + Compile — V8 (ya koi bhi JS engine) ko poori file ko syntax-check karke bytecode mein convert karna padta hai, sirf wo functions ka jo actually call honge nahi — saari file ka.
  • Execute — top-level code (module initializers, side effects) run hota hai.

Yahi wajah hai ki bada JS bundle seedha INP (Interaction to Next Paint) aur LCP dono ko hurt karta hai — main thread busy rehta hai parsing/compiling mein, aur jab tak wo free nahi hota, click/tap events queue mein atke rehte hain. Lighthouse isko explicitly flag karta hai: agar JS execution 2 seconds se zyada leta hai to warning, 3.5 seconds se zyada pe fail. Aur ye sabse zyada matter karta hai initial load pe, kyunki wahi time hai jab user sabse zyada interact karne ki koshish karta hai — lekin main thread already busy hota hai tumhare bundle ko chew karne mein.

📌 Root cause: parse/compile time bytes se scale karta hai

Ek common misconception hai ki "unused code free hai kyunki wo call nahi ho raha." Galat. JS engine ko us code ko compile-time pe parse karna hi padta hai taaki wo syntax-valid hai ye confirm ho sake, aur modern engines (V8) baseline compilation bhi kar dete hain speculative optimization ke liye. Matlab bytes jo download hue, unka cost lagbhag guaranteed hai — chahe wo code kabhi execute ho ya na ho. Isliye "tree-shaking + code-splitting" combo itna powerful hai: dono milke sirf wahi bytes browser tak bhejte hain jo actually chahiye is moment pe.

Dynamic import() — browser-native primitive

Har bundler (webpack, Rollup, Parcel, esbuild, Vite) ke splitting feature ke peeche ek hi underlying browser API hai: import() function-call syntax, jo ES2020 se native JavaScript ka part hai. Ye static import statement se fundamentally different hai:

  • Static import (import x from 'y') — module aur uske saare dependencies parse + execute hone chahiye before parent module run ho sake. Ye top-level pe hi likhna padta hai, conditionally nahi chala sakte.
  • Dynamic import() — ek function call jo Promise return karta hai, jo tumhe kisi bhi point pe — event handler ke andar, condition ke andar — module load karne deta hai. Bundler isi call ko dekh kar us module ko alag chunk mein daal deta hai, jo tab tak network pe fetch nahi hota jab tak wo line actually execute na ho.
dynamic-import-on-click.js — plain browser-native example
// Ek button jiska click hone par hi hume "confetti" animation library chahiye —
// baaki poore page ke liye ye library kabhi zaroorat nahi hai.
const celebrateBtn = document.querySelector('#celebrate-btn'); // DOM se button element pakड़te hain

// 'click' event listener register kar rahe hain, aur handler ko 'async' bana rahe hain
// taaki uske andar 'await' use kar sakein.
celebrateBtn.addEventListener('click', async () => {
  // Button pe click hone ke baad hi disable kar dete hain, taaki double-click se
  // duplicate import request na chale (network waste aur race condition dono avoid).
  celebrateBtn.disabled = true;

  // Yahan asli magic hai: dynamic import(). Ye ek Promise return karta hai jo
  // module load hone ke baad us module ka "namespace object" resolve karta hai.
  // 'await' se hum us Promise ke resolve hone tak ruk jaate hain.
  const confettiModule = await import('./confetti.mjs');
  // NOTE: '.mjs' extension jaan-boojh kar use kiya — browser aur bundler dono ise
  // ES module maan kar V8 ki "streaming compilation" ka fayda uthate hain, jo
  // '.js' extension pe production mein opt-out ho jaata hai.

  // Module se named export 'launchConfetti' nikaal rahe hain (destructuring).
  const { launchConfetti } = confettiModule;

  // Ab jaake actual animation function call kar rahe hain — is point tak
  // confetti.mjs ka network request ho chuka, parse ho chuka, execute ho chuka.
  launchConfetti();

  // Kaam ho gaya, button wapas enable kar dete hain agle celebration ke liye.
  celebrateBtn.disabled = false;
}, { once: false }); // 'once: false' explicit rakha hai — hum chahte hain har click pe chale,
                      // browser cache dusri baar se import() ko instant bana dega (same URL).

Is example mein confetti.mjs ka byte, parse aur execute cost — teeno — sirf tab pay hota hai jab user actually button click karta hai. Agar user kabhi click nahi karta, to wo chunk kabhi download hi nahi hota. Yahi core idea hai jo aage React.lazy aur route splitting dono build karte hain.

🧠 Bundler ke andar kya hota hai

Jab webpack tumhare code mein import() call dekhta hai, uska SplitChunksPlugin automatically ek naya "async chunk" bana deta hai. Default config (chunks: 'async') sirf dynamic imports ko split karta hai; chunks: 'all' set karne se static aur dynamic dono imports ke beech shared dependencies bhi common chunk mein nikal jaate hain — jo duplicate code (jaise ek helper function do jagah bundle hona) avoid karta hai. Agar tum galti se splitChunks: false set kar do, to shared modules har chunk mein duplicate ho jaate hain — bundle size chupke se badh jaata hai.

Component-based splitting — React.lazy + Suspense

React apps mein hum dynamic import() ko directly likhne ke bajaye React ka React.lazy() abstraction use karte hain. Andar se ye still same dynamic import() hi call karta hai — bundler (webpack/Vite) ko wahi chunk-splitting signal milta hai — bas React isse component tree ke saath integrate kar deta hai, aur <Suspense> loading state handle karta hai.

Classic use-case: ek dashboard jisme multiple tabs hain, aur "Analytics" tab ek heavy charting library (jaise recharts/chart.js wrapper) use karta hai jo shaayad 100+ KB ki hai. Agar user kabhi Analytics tab open hi nahi karta, to wo 100 KB kabhi load nahi honi chahiye.

AnalyticsChart.jsx — heavy component jo lazy-load hoga
// Ye file khud bhi heavy imports rakhti hai (charting library), lekin isse
// entry bundle mein import NAHI karenge — isliye ye apne aap ek alag chunk
// mein compile hogi jab bundler is file tak dynamic import() se pahunchega.

import { LineChart, Line, XAxis, YAxis, Tooltip } from 'heavy-chart-lib'; // bhaari dependency

// Named export nahi, DEFAULT export use kar rahe hain — React.lazy() ko
// default export chahiye hota hai jo module resolve hone par milta hai.
export default function AnalyticsChart({ data }) {
  // 'data' prop parent se aata hai — jaise revenue-by-month array.
  return (
    // heavy-chart-lib ka LineChart component, jo tabhi paint hoga jab
    // ye file already load ho chuki hogi (Suspense boundary ke andar).
    <LineChart width={600} height={300} data={data}>
      <XAxis dataKey="month" />   {/* X-axis month field se draw hoga */}
      <YAxis />                    {/* Y-axis auto-scale */}
      <Tooltip />                  {/* hover pe tooltip dikhayega */}
      <Line type="monotone" dataKey="revenue" stroke="#d97757" />
      {/* revenue field ko smooth curve mein plot kar rahe hain, accent color ke saath */}
    </LineChart>
  );
}
Dashboard.jsx — parent jo tab-based lazy loading karta hai
import React, { useState, Suspense, lazy } from 'react';
// 'lazy' aur 'Suspense' dono React core se hi aate hain — koi extra library nahi chahiye.

// React.lazy() ko ek function pass karte hain jo dynamic import() call karke
// Promise return kare. Ye call yahan turant nahi chalta — React isse "remember"
// kar leta hai aur sirf pehli baar render hone ki koshish par actually import() trigger karta hai.
const AnalyticsChart = lazy(() => import('./AnalyticsChart.jsx'));
// NOTE: iske equivalent plain dynamic import() hota: await import('./AnalyticsChart.jsx')
// bas React ismein "loading ke dauraan kya dikhayein" ka logic bhi wrap kar deta hai.

export default function Dashboard() {
  // 'activeTab' state track karta hai user abhi kaunsa tab dekh raha hai — default 'overview'.
  const [activeTab, setActiveTab] = useState('overview');

  return (
    <div className="dashboard">
      {/* Tab buttons — inme koi heavy import nahi, ye sab entry bundle mein hi rehte hain */}
      <nav>
        <button onClick={() => setActiveTab('overview')}>Overview</button>
        <button onClick={() => setActiveTab('analytics')}>Analytics</button>
        {/* Analytics button click hone tak AnalyticsChart.jsx ka chunk kabhi fetch nahi hoga */}
      </nav>

      {activeTab === 'overview' && <OverviewPanel />}
      {/* OverviewPanel normal (non-lazy) import hai — ye light hai, entry bundle mein rehne mein
          koi harm nahi, isliye ise split karne ka fayda nahi (over-splitting avoid kar rahe hain) */}

      {activeTab === 'analytics' && (
        // Suspense boundary — jab tak AnalyticsChart ka chunk network se aa nahi jaata aur
        // execute nahi ho jaata, React 'fallback' prop mein diya gaya UI dikhata rahega.
        <Suspense fallback={<div className="chart-skeleton">Chart load ho raha hai…</div>}>
          <AnalyticsChart data={monthlyRevenueData} />
          {/* Ye line hi actual trigger hai — jab React ise render karne ki koshish karta hai,
              tab jaake 'lazy()' ke andar wala import() Promise chalta hai. */}
        </Suspense>
      )}
    </div>
  );
}

Result: AnalyticsChart.jsx aur uska heavy charting dependency ek alag JS chunk (jaise AnalyticsChart.a1b2c3.chunk.js) mein compile hote hain, jo tabhi network request banta hai jab user "Analytics" tab pe click karta hai. Overview tab dekhne wale users ke liye wo bytes kabhi download hi nahi hote — LCP aur main-thread cost dono kam.

Route-based splitting

Component-level (React.lazy) splitting granular control deta hai, lekin sabse common aur highest-leverage split boundary hoti hai route — kyunki user ek time pe ek hi route dekhta hai, aur har route ka JS baaki routes se largely independent hota hai.

router.jsx — React Router ke saath route-level splitting
import { lazy, Suspense } from 'react';
import { createBrowserRouter, RouterProvider } from 'react-router-dom';

// Har route ka component apne aap ek separate chunk banega, kyunki har ek
// yahan dynamic import() ke through lazily declare kiya gaya hai.
const HomePage     = lazy(() => import('./pages/HomePage.jsx'));     // route: '/'
const CheckoutPage = lazy(() => import('./pages/CheckoutPage.jsx')); // route: '/checkout' — payment SDK jaisi heavy libs yahin honge
const SettingsPage = lazy(() => import('./pages/SettingsPage.jsx')); // route: '/settings'

// Router config — har route object ka 'element' Suspense ke andar wrap karte hain
// taaki navigation ke dauraan fallback dikh sake jab tak us route ka chunk fetch ho raha ho.
const router = createBrowserRouter([
  {
    path: '/', // root path
    element: (
      <Suspense fallback={<div>Loading…</div>}>
        <HomePage />
      </Suspense>
    ),
  },
  {
    path: '/checkout', // checkout ka JS (payment SDK etc.) home page load karne walon ko kabhi nahi milega
    element: (
      <Suspense fallback={<div>Loading…</div>}>
        <CheckoutPage />
      </Suspense>
    ),
  },
  {
    path: '/settings',
    element: (
      <Suspense fallback={<div>Loading…</div>}>
        <SettingsPage />
      </Suspense>
    ),
  },
]);

export default function App() {
  // RouterProvider poore app ko is router config se drive karta hai.
  return <RouterProvider router={router} />;
}

Next.js app router — automatic route splitting

Frameworks jaise Next.js (app router) ye pattern by default enforce karte hain — tumhe manually React.lazy likhna hi nahi padta har route ke liye. app/ directory mein har page.tsx file apne aap ek separate JS chunk banati hai, aur navigation ke time Next.js sirf us target route ka chunk (aur uske shared layout chunks) fetch karta hai.

app/checkout/page.tsx — Next.js app router example
// File-based routing: 'app/checkout/page.tsx' apne aap '/checkout' route ban jaata hai.
// Manually lazy() likhne ki zaroorat nahi — Next.js build-time pe hi
// is file ko iske apne chunk mein isolate kar deta hai.

import PaymentForm from './PaymentForm'; // ye bhi checkout route ke saath hi bundle hoga

// Default export hi Next.js ke liye page component hota hai.
export default function CheckoutPage() {
  return (
    <main>
      <h1>Checkout</h1>
      <PaymentForm /> {/* payment SDK jaisa heavy code sirf yahan load hoga */}
    </main>
  );
}
// '/checkout' visit karne wale user ko hi ye chunk milta hai — '/' ya '/settings'
// dekhne walon ke initial bundle mein iska ek byte bhi nahi jaata.
// Bas dhyaan rahe: agar 'PaymentForm' bahut heavy hai (jaise 3rd-party payment
// widget), to usse is page ke andar bhi further React.lazy() se split kar sakte ho
// taaki wo sirf tab load ho jab user actually "Pay" button ke paas scroll kare.

Tradeoff: zyada requests vs kam wasted bytes

Code-splitting free lunch nahi hai — ye ek explicit tradeoff hai:

Ek bada bundleMultiple chunks
1 hi HTTP request, better compression ratio (gzip/brotli badi files pe zyada efficient hote hain) Multiple HTTP requests (HTTP/2 multiplexing se cheap hain, but zero-cost nahi)
Poora bundle re-download hota hai chhoti si bhi code change pe (cache invalidation) Sirf changed chunk invalidate hota hai — baaki chunks browser cache se serve hote hain
Unused route/component ka JS bhi parse+compile hota hai initial load pe Sirf visited route/opened component ka JS parse+compile hota hai

Short version: hum "compression efficiency + fewer requests" ko thoda trade kar rahe hain "kam wasted bytes on initial load + better long-term caching" ke liye. Zyadatar real-world apps ke liye ye trade worth hai, kyunki initial-load JS jitna kam hoga utna tez INP/LCP milega — lekin isko extreme tak le jaana bhi apna hi cost laata hai (neeche dekho).

⚠️ Common mistake: over-splitting (waterfall problem)

"Zyada splitting = zyada better" nahi hai. Agar tum har chhote component, har chhote util function ko apna alag import() chunk bana doge, to end result ye hota hai ki browser ko dozens of tiny network requests ek ke baad ek fire karne padte hain — jinme se har ek ka apna round-trip latency, TCP/TLS overhead (agar connection reuse na ho), aur HTTP header overhead hai. Agar ye chunks ek-doosre pe dependent hain (chunk B load hone ke baad hi pata chalta hai chunk C chahiye), to ye ek request waterfall ban jaata hai — total load time individual chunk sizes se zyada in-between round-trips se determine hota hai. Practical rule: chunk boundaries wahi rakho jahan real user-interaction boundary hai (route, tab, modal, heavy optional widget) — random file-per-component splitting mat karo. Bahut chhoti files (few KB) ko group karke ek "vendor" ya "common" chunk mein rakhna behtar hota hai compression aur request-count dono ke liye.

Split candidates dhundhna — bundle analysis tools

🧠 Blind splitting mat karo — pehle measure karo

Production mein code-splitting decisions "guess" se nahi, actual bundle composition dekh kar lene chahiye:

  • source-map-explorer — production build ke source maps use karke ek treemap dikhata hai ki final bundle mein kaunsi library/module kitni jagah le rahi hai. CLI se: npx source-map-explorer build/static/js/*.js
  • webpack-bundle-analyzer — webpack config mein plugin add karke interactive zoomable treemap milta hai, module-level gzip size ke saath. Best for spotting "ye ek 200 KB library sirf ek button ke liye import ho rahi hai" jaise cases.
  • Next.js built-in analyzer — @next/bundle-analyzer package wrap kar deta hai next.config.js ko, aur ANALYZE=true next build chalane par per-route bundle breakdown khud-ba-khud khul jaata hai browser mein.

Pattern dhoondo: koi heavy dependency jo sirf ek rarely-visited route ya rarely-opened component ke liye use ho rahi hai — wahi tumhara best split candidate hai. Agar koi dependency har route mein already common hai, usse split karne ka koi fayda nahi (upar se over-splitting ka risk hi milega).

Key Takeaways

  • JS parsing/compiling/executing ka cost bytes ke proportional hai — unused code bhi is cost ko pay karta hai agar wo download hua hai.
  • import() ek browser-native, Promise-returning function-call syntax hai — sab bundlers (webpack, Vite, Rollup, esbuild) isi signal pe automatic chunk-splitting karte hain.
  • React.lazy() + <Suspense> component-level splitting ke liye React ka abstraction hai — andar se still dynamic import() hi hai.
  • Route-based splitting sabse highest-leverage boundary hai — Next.js jaise frameworks isse by default deliver karte hain, file-based routing ke through.
  • Tradeoff hamesha hai: chunks jitne zyada, utne zyada requests — over-splitting se waterfall problem create hoti hai jo net-negative ban sakti hai.
  • Split candidates guess mat karo — source-map-explorer / webpack-bundle-analyzer / Next.js analyzer se actual bundle composition dekho.

🎯 Interview Questions

  • Q: Static import aur dynamic import() mein kya fundamental difference hai?
    Hint: static import top-level hai, parse-time pe hi resolve hota hai, poori dependency chain execute hone tak parent module block rehta hai. Dynamic import() runtime pe kabhi bhi call ho sakta hai, Promise return karta hai, aur bundlers ise chunk-split signal ki tarah treat karte hain.
  • Q: Bada JS bundle specifically INP ko kaise hurt karta hai, sirf load time nahi?
    Hint: main thread parsing/compiling mein busy rehta hai, isliye user interactions (click/tap) event queue mein delay hoti hain — ye "input delay" hai jo INP metric mein directly count hota hai.
  • Q: React.lazy() ke andar actually kya ho raha hai?
    Hint: ek function jo dynamic import() call karke default-export module return karta hai; React usse memoize karke sirf first-render-attempt pe trigger karta hai, aur Suspense boundary uske pending state ko handle karta hai.
  • Q: Route-based aur component-based splitting mein kab kaunsa choose karoge?
    Hint: route-based default/baseline hona chahiye (highest leverage, framework often free deta hai); component-based tab jab ek single route ke andar hi ek heavy, conditionally-visible UI-piece (modal, tab, chart) ho.
  • Q: Over-splitting kaise identify aur fix karoge?
    Hint: Network tab mein bahut saare chhote (few KB) sequential/waterfall requests dikhna signal hai; fix — chunk boundaries ko user-interaction boundaries tak consolidate karo, chhoti shared utils ko common/vendor chunk mein group karo (webpack chunks: 'all').
  • Q: .js ke bajaye .mjs extension use karne ka performance impact kya hai?
    Hint: .mjs se browser/V8 confidently ES module maan kar "streaming compilation" enable karta hai (download ke saath-saath parse/compile start ho jaata hai); production mein .js extension ke saath ye optimization opt-out ho sakta hai.
