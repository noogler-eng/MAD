CSS aur Critical Path ka rishta

CSS by default ek render-blocking resource hai. Iska matlab: jab tak browser CSS file download aur parse karke CSSOM (CSS Object Model) nahi bana leta, tab tak wo screen pe kuch bhi paint nahi karega — chahe HTML parsing already complete ho chuki ho.

Ye design intentional hai. Agar browser CSS ka wait kiye bina hi HTML ko paint kar de, toh user ko pehle unstyled markup dikhega, phir achanak styles apply honge — isse FOUC (Flash of Unstyled Content) kehte hain. Browser jaan-bujh kar rendering ko block karta hai taaki ye jhatka (flash) na ho — because showing broken/unstyled UI aur phir usse "fix" karna, showing nothing thoda der ke liye, is se worse UX hai.

📌 Root-level: Kyun render-blocking?

Render Tree banane ke liye DOM + CSSOM dono chahiye (Chapter 3 mein detail hai). Agar CSSOM incomplete hai aur browser phir bhi paint kar de, toh usko baad mein CSSOM complete hone pe re-paint/re-layout karna padega — jo extra work hai aur visually jarring bhi. Isliye spec ne CSS ko render-blocking banaya: ek hi baar correct state mein paint karo, bar-bar nahi.

CSS Delivery Strategies

Teen core strategies hain CSS ka blocking-impact kam karne ke liye:

1. Minification

Whitespace, comments, aur unnecessary characters hata do. Ye download time kam karta hai (smaller file over network) — lekin parsing/CSSOM-construction cost pe zyada asar nahi dalta, sirf transfer size kam karta hai.

before-after.css — Minification example
/* BEFORE: readable, 45 bytes+ whitespace */
h1 {
  font-size: 2em;      /* har property apni line pe */
  color: #000000;   /* 6-hex color, redundant */
}

/* AFTER: minifier ne whitespace/comments/redundant hex hata diya */
h1{font-size:2em;color:#000}
/* #000000 -> #000 shorthand, no spaces, no newlines, no comments */

2. Unused CSS hatao

Chrome DevTools ke Coverage tab se pata chalta hai ki current page pe kaun se CSS rules actually use ho rahe hain aur kaun se dead code hain. Unused CSS hatane ke do fayde hain: (1) download size kam hoti hai, aur (2) — jyada important — render tree construction fast hota hai, kyunki browser ko kam rules process karne padte hain jab wo har DOM node pe matching CSS selectors evaluate karta hai.

3. @import avoid karo

CSS ke andar @import url('another.css') use karna ek anti-pattern hai — ye sequential/chained requests banata hai. Browser pehle outer stylesheet download+parse karega, tabhi usse pata chalega ki ek aur file @import se chahiye — aur wo request tab jaake start hoga. Matlab requests waterfall ban jaati hain, parallel nahi.

bad-vs-good.html — @import vs <link>
<!-- BAD: style.css download hone ke BAAD hi browser ko pata chalega ki -->
<!-- fonts.css bhi chahiye — sequential/chained request, slow -->
<style>
  @import url('style.css'); /* style.css ke andar phir ek aur @import ho sakta hai */
</style>

<!-- GOOD: dono <link> tags HTML parse hote hi discover ho jaate hain -->
<!-- preload scanner inhe turant dekh leta hai, requests PARALLEL jaati hain -->
<link rel="stylesheet" href="style.css">
<link rel="stylesheet" href="fonts.css">
⚠️ Common Mistake

Bahut se legacy codebases mein @import chains milte hain — ek CSS file doosri ko import karti hai, jo teesri ko. Har extra @import level ek aur round-trip add karta hai critical path mein. Lighthouse ka "Avoid chaining critical requests" audit exactly isi cheez ko flag karta hai. Fix: sab imports ko top-level <link> tags mein flatten karo, ya build-time pe bundle karke ek single CSS file bana do.

Critical CSS Inline karna

"Critical CSS" wo minimal set of styles hai jo above-the-fold content (jo user ko pehli screen pe bina scroll kiye dikhta hai) ko correctly render karne ke liye chahiye. Is CSS ko <head> mein directly <style> tag ke andar inline kar do — isse extra network round-trip ki zaroorat nahi padti, aur pehla paint fast hota hai. Baaki (non-critical) CSS ko normal <link> se, ya asynchronously, load karo.

critical-css-inline.html — Above-the-fold styles inline
<head>
  <!-- Critical CSS: sirf above-the-fold ke liye — hero heading ka size/color -->
  <!-- Network round-trip ki zaroorat nahi, HTML ke saath hi aa jaata hai -->
  <style>
    h1,h2{color:#000}   /* dono headings ka color, minified */
    h1{font-size:2em}     /* h1 ka size */
    h2{font-size:1.5em}   /* h2 ka size */
  </style>
</head>
<body>
  <!-- Non-critical CSS: rest of the page (footer, modals, below-fold sections) -->
  <!-- ye render-blocking hai lekin above-fold content already paint ho chuka hai -->
  <link rel="stylesheet" href="non-critical.css">
</body>

Agar non-critical CSS ko bhi fully non-blocking banana ho (bilkul render ko block hi na kare), toh ek classic trick hai: media="print" + onload swap. Idea ye hai ki browser media="print" wale stylesheets ko low priority pe fetch karta hai aur render ko block nahi karta (kyunki wo sirf print ke time apply hote hain) — lekin download hone ke baad hum JS se media attribute ko "all" mein switch kar dete hain, taaki wo turant apply ho jaaye.

media-print-swap.html — Non-blocking CSS load trick
<!-- media="print" ki wajah se browser ise render-blocking NAHI maanta -->
<!-- but background mein download to ho hi raha hai -->
<link rel="stylesheet" href="non-critical.css" media="print"
      onload="this.media='all'">
      <!-- onload fire hote hi (download complete), media ko 'all' bana do -->
      <!-- ab styles apply honge but tab tak page already paint ho chuka tha -->

<!-- Fallback: agar JS disabled hai, noscript se normal load ensure karo -->
<noscript>
  <link rel="stylesheet" href="non-critical.css">
</noscript>

JS Parser-Blocking Kaise Hota Hai

Jab HTML parser ek plain <script> tag (bina async/defer ke) encounter karta hai, toh wo HTML parsing ko pause kar deta hai, script ko download karta hai (agar external hai), execute karta hai, aur tabhi aage HTML parse karna resume karta hai.

Ye by-design hai — kyunki script DOM ko access ya modify kar sakta hai (jaise document.write()) jabki DOM abhi bhi construct ho raha hai. Browser ko guarantee chahiye ki jab script chale, tab tak jo bhi DOM parse ho chuka hai wo stable/consistent state mein ho. Isi wajah se <script> tags ko traditionally <body> ke end mein rakha jaata tha — taaki wo poore DOM ke baad load ho aur parsing ko block na kare.

🧠 Senior Note: Client-Side Rendering ka hidden cost

Agar aapka markup JavaScript se render hota hai (jaise pure CSR React app, bina SSR ke), toh wo content preload scanner ko bilkul dikhta hi nahi — kyunki preload scanner sirf raw HTML source ko scan karta hai, JS-generated DOM ko nahi. Isका matlab: agar aapki LCP image ya critical resource client-rendered markup ke andar hai, toh uski discovery tab tak delay hogi jab tak JS download+parse+execute na ho jaaye. Yahi ek core reason hai ki SSR/SSG apps CSR se better LCP dete hain — server se aaya HTML preload scanner ko turant sab kuch dikha deta hai.

async vs defer vs module — Exact Semantics

Teeno attributes HTML parsing ko block hone se bachate hain (script ka download parallel chalta hai), lekin unka execution timing aur order alag-alag hai — ye difference production bugs ka bahut bada source hai.

Plain <script> (no attribute)

Parser rukta hai → script download hota hai (agar external) → script turant execute hota hai → parsing resume hoti hai. Fully blocking, sequential.

async

Script download parallel hota hai HTML parsing ke saath (parsing block nahi hoti download ke liye). Lekin jaise hi download complete hota hai, parser turant ruk jaata hai aur script ko execute karta hai — chahe HTML parsing beech mein ho. Execution order guaranteed nahi hai: agar do async scripts hain aur dusra pehle download ho jaaye, toh dusra pehle execute hoga.

defer

Script download parallel hota hai, lekin execution HTML parsing complete hone ke baad hota hai — DOMContentLoaded event fire hone se theek pehle. Multiple defer scripts document order mein hi execute hote hain, chahe unki download speed kuch bhi ho.

type="module"

ES modules (<script type="module">) by default deferred hote hain — matlab bina kisi extra attribute ke, ye defer jaisa hi behave karte hain: parsing block nahi karte, aur document parsing complete hone ke baad, document order mein execute hote hain. Agar aap explicitly async add karte ho module script pe, toh wo async ki tarah behave karega (order guarantee chali jaayegi).

script-loading.html — defer me migrate karna (before/after)
<!-- BEFORE: blocking script <head> mein — parser yahin ruk jaata hai -->
<!-- pura HTML parsing tab tak pause rahega jab tak analytics.js load+run na ho -->
<head>
  <script src="analytics.js"></script>
</head>

<!-- AFTER: defer attribute add kiya -->
<!-- ab download parallel hoga, execution DOMContentLoaded se pehle, -->
<!-- document order maintain hoga — analytics.js dusre defer scripts se pehle chalega -->
<head>
  <script src="analytics.js" defer></script>
</head>
module-example.html — type="module" is deferred by default
<!-- Ye already "defer" jaisa behave karega — koi extra attribute nahi chahiye -->
<script type="module" src="app.js"></script>
<!-- Parsing block nahi hoga, aur ye DOMContentLoaded se pehle, document order mein chalega -->

<!-- Agar explicitly async chahiye module pe (order guarantee chhod ke): -->
<script type="module" src="analytics-module.js" async></script>
/* is case mein ye jaldi jaldi execute ho sakta hai, doosre modules se pehle ya baad — no order guarantee */

Comparison Table — async vs defer vs module vs plain

Attribute Blocks HTML Parser? Kab Execute Hota Hai Execution Order Guaranteed?
Plain <script> Haan — download + execute dono ke liye ruk jaata hai Turant, jaise hi mile (inline parsing ke beech mein) Haan (document order, kyunki sequential hi chalta hai)
async Nahi (download parallel) — but execute hote waqt parser rukta hai Jaise hi download complete ho, turant (kabhi bhi, mid-parsing) Nahi — jo pehle download ho, wo pehle chalta hai
defer Nahi Parsing complete hone ke baad, DOMContentLoaded se pehle Haan — document order mein
type="module" (default) Nahi Parsing complete hone ke baad (defer jaisa behavior) Haan — document order mein
type="module" async Nahi Jaise hi download + module graph resolve ho jaaye Nahi
⚠️ Common Mistake: async ka galat use

Sabse common production bug: do scripts jinme dependency hai (jaise jquery.js aur ek plugin jo jQuery global expect karta hai) — dono ko async laga do "performance ke liye". Result: race condition. Zyaadatar waqt sahi order mein load ho jaate hain (jquery.js chhota hai, jaldi download hota hai), lekin kabhi-kabhi network conditions badalte hain (CDN slow, cache miss) aur plugin pehle execute ho jaata hai — Uncaught ReferenceError: jQuery is not defined. Ye bug intermittent hota hai, isliye QA mein miss ho jaata hai aur production mein randomly fail hota hai. Fix: agar order matter karta hai, defer use karo (ya module imports, jo dependency graph khud resolve karte hain) — async sirf un scripts ke liye jo fully independent hain (jaise analytics, ads).

Bundling & Minification Basics

Bundling multiple JS/CSS files ko ek (ya kuch) files mein combine karta hai — isse HTTP request count kam hota hai. Minification whitespace/comments hata deta hai; JS ke liye ek extra step hai uglification — jisme variable/function names ko chhote, meaningless names se replace kar diya jaata hai (kyunki humans ko readability nahi chahiye production build mein, sirf browser ko parse karna hai).

uglify-example.js — Uglification (variable renaming)
// BEFORE: readable variable name, developer ke liye
const scriptElement = document.createElement('script');
// yahan 'scriptElement' naam se pata chalta hai ye kya hai

// AFTER: uglifier ne 'scriptElement' ko 't' bana diya — bytes kam
const t=document.createElement("script");
// functionality same hai, sirf naam chhota — parser/network ke liye faster,
// lekin ab ye source maps ke bina debug karna mushkil hai

Modern bundlers (Webpack, esbuild, Rollup, Vite) ye sab automatically karte hain build step mein — tree shaking (unused exports hata dena), code splitting, aur minification sab ek saath.

🧠 Senior Note: Next.js/Vite manual HTML control se kaise alag hai

Jab aap raw HTML likhte ho, aapko khud decide karna padta hai — kaunsa script defer hoga, konsi CSS critical hai, @import avoid karna hai ya nahi. Modern frameworks ye sab automate kar dete hain:

  • Next.js: next/script component ek strategy prop deta hai (beforeInteractive, afterInteractive, lazyOnload) jo internally defer/async decide karta hai. CSS Modules aur built-in CSS optimization automatically critical CSS ko per-route extract karke inline kar sakta hai (with the right config), aur unused CSS ko route-level code-split karta hai.
  • Vite: dev mode mein native ES modules use karta hai (type="module", jo already deferred hai — isliye dev server itna fast feel hota hai). Production build mein Rollup use karke automatically bundling, minification, aur CSS code-splitting karta hai — chunk ke hisaab se <link rel="modulepreload"> tags bhi auto-inject karta hai.

Interview mein ye samajhna important hai: framework "magic" nahi kar raha — wo bas inhi primitives (defer, type="module", @import avoidance, minification) ko build-time pe automatically apply kar raha hai jo hum yahan manually kar rahe hain. Agar aapko pata hai ye sab andar se kaise kaam karta hai, toh aap framework ke output ko debug/tune kar paoge jab default config kaafi na ho.

Key Takeaways

  • CSS render-blocking hai — CSSOM complete hue bina browser paint nahi karta, taaki FOUC na ho.
  • @import chains sequential requests banate hain — hamesha <link> tags use karo, ya build-time pe bundle karo.
  • Critical (above-the-fold) CSS ko inline karo <head> mein; baaki CSS ko normal link ya media="print" + onload swap trick se non-blocking banao.
  • Plain <script> parser ko fully block karta hai — download bhi, execute bhi.
  • async: download parallel, execute turant jaise hi mile — order guaranteed nahi.
  • defer: download parallel, execute parsing ke baad, document order maintained.
  • type="module" by default deferred hai — same guarantees jo defer deta hai.
  • Dependency wale scripts pe kabhi async mat lagao — race condition ka risk hai; defer ya modules use karo.
  • Client-side rendered markup preload scanner ko invisible hota hai — SSR/SSG isi wajah se LCP mein better hota hai.
  • Bundling + minification + uglification request count aur transfer size dono kam karte hain; frameworks ye automate karte hain build step mein.

🎯 Interview Questions

  • Q1. async aur defer mein exact difference kya hai — sirf "jaldi load hota hai" nahi, mechanism batao.
    Hint: dono download ko parallel karte hain, lekin execution timing/order alag hai — async turant execute karta hai download hote hi (parser ko interrupt karke), defer parsing complete hone ke baad, document order mein execute karta hai.
  • Q2. type="module" script by default async hai ya defer? Kyun?
    Hint: Default deferred hota hai — spec design decision taaki module dependency graph predictably, document order mein resolve ho.
  • Q3. CSS ko render-blocking kyun banaya gaya hai — kya browser CSSOM ke bina paint nahi kar sakta?
    Hint: Technically kar sakta hai, lekin FOUC avoid karne ke liye jaan-bujh kar block kiya jaata hai — ek hi correct paint, multiple re-paints nahi.
  • Q4. @import CSS mein anti-pattern kyun maana jaata hai?
    Hint: Sequential/chained requests — outer file download+parse hue bina browser ko pata hi nahi chalta ki aur ek file chahiye, isliye parallel fetch nahi hota.
  • Q5. Ek page pe do async scripts hain jinme dependency hai (A, B jo A pe depend karta hai). Production mein kabhi-kabhi crash hota hai. Kyun, aur fix kya hai?
    Hint: async mein execution order guaranteed nahi — network conditions ke hisaab se B, A se pehle load ho sakta hai. Fix: defer use karo ya ES modules (import) jo dependency graph khud resolve karte hain.
  • Q6. Next.js jaisa framework "automatically" performance optimize karta hai — iska matlab kya hai andar se? Interview mein sirf "framework handles it" bolna kyun weak answer hai?
    Hint: Framework internally wahi primitives use karta hai (defer/module/critical CSS extraction/minification) jo manually HTML mein likhe jaate — samajhna ki "kaise" zaroori hai taaki default config fail hone pe aap debug kar sako.
