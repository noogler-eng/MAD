Prefetching, Prerendering, and Service Worker Precaching

Ab tak humne dekha ki resources ko deferred ya lazy kaise load karein taaki initial page fast dikhe. Lekin uska side-effect hai — jab user actually us deferred resource ko chahiye (agla page click kare, ya scroll kare), tab thoda delay aata hai. Ye chapter us gap ko close karta hai: browser ko time se pehle guess karwana ki user aage kya karega, aur us guess ke basis pe resources ya poore pages ko background mein taiyaar rakhna — taaki jab user actually navigate kare, to experience instant lage.

Core tension: defer vs speculate

Pichle chapters mein hum resources ko defer, lazy, ya code-split karke "abhi mat load karo" bol rahe the — kyunki critical rendering path ko block nahi karna tha. Lekin har deferral ka ek cost hai: jis resource ko defer kiya, wo kabhi na kabhi chahiye hoga, aur tab uska load time user ko dikhega (jaise route change pe naya JS bundle fetch hona, ya next page ka HTML fetch hona).

Speculative loading is tension ko solve karta hai: browser ko idle time mein, ya jab user "intent" dikhaye (hover, viewport mein link aana), tab background mein wo cheezein pehle se fetch/render/cache kar do — bina current page ke critical path ko touch kiye. Teen tools hain jo alag-alag depth pe ye karte hain: prefetch (sirf resource fetch), prerender (poora page fetch + render + JS execute), aur Service Worker precache (install-time pe app shell cache karna, offline-first).

Resource Prefetching — <link rel="prefetch">

Sabse lightweight technique. Ye browser ko batata hai: "ye resource near-future mein chahiye ho sakta hai, lekin abhi urgent nahi — jab bandwidth free ho (lowest priority queue mein), tab fetch kar lena aur HTTP cache mein rakh dena."

HTML — next-page resources ko prefetch karna
<head>
  <!-- date-picker.js ko lowest priority pe idle time mein fetch karo -->
  <!-- as="script" batata hai resource type, taaki browser sahi Accept header aur -->
  <!-- content-security-policy bucket use kare -->
  <link rel="prefetch" as="script" href="/date-picker.js">

  <!-- isi tarah CSS bhi prefetch ho sakta hai -->
  <!-- as="style" se browser ko pata chalta hai ye stylesheet hai, image ya font nahi -->
  <link rel="prefetch" as="style" href="/date-picker.css">
</head>

Root-level mechanics: rel="prefetch" resource ko network layer mein lowest priority pe daalta hai — browser ka resource scheduler pehle critical CSS/JS/fonts ko priority dega, aur jab network thread free ho tabhi prefetch request jaayegi. Browser is hint ko ignore bhi kar sakta hai — agar user ka data saver mode on hai, ya connection slow hai (2G/3G), ya device already resource-constrained hai, to browser silently prefetch skip kar dega. Ye ek "hint" hai, "command" nahi.

HTML — poore document (next page) ko prefetch karna
<!-- as="document" ka matlab hai poora HTML page prefetch ho raha hai, -->
<!-- sirf ek asset nahi. Ye HTTP cache mein store hoga. -->
<link rel="prefetch" href="/product/123" as="document">

Important caveat (root-level gotcha): cross-origin documents ko prefetch mat karo — us case mein browser do baar request bhejta hai (ek prefetch ke liye, ek actual navigation ke liye) kyunki cross-origin prefetched response ko browser directly navigation ke liye reuse nahi kar pata (double-fetch cache-key mismatch ki wajah se). Same-origin personalized pages (jaise "/cart" ya "/account") bhi prefetch mat karo — ye typically uncached responses hote hain (Cache-Control: no-store type), to prefetch ka fayda hi nahi milega, sirf bandwidth waste hoga.

Speculation Rules API

<link rel="prefetch"> declarative hai lekin limited — ek link, ek resource. Chromium browsers (Chrome, Edge) mein ek zyada powerful, JSON-based API hai: Speculation Rules API. Isse tum multiple URLs ko ek saath declare kar sakte ho, aur ye prefetch aur prerender dono ke liye kaam aata hai.

HTML — Speculation Rules se multiple pages prefetch karna
<!-- type="speculationrules" batata hai browser ko ki is script tag ke andar -->
<!-- JavaScript nahi, balki ek JSON config hai jo speculative loading rules define karta hai -->
<script type="speculationrules">
{
  "prefetch": [{
    // source: "list" ka matlab hai neeche diye gaye URLs ki explicit array use karo
    // (dusra option "document" hai, jo current page ke <a> links ko auto-scan karta hai)
    "source": "list",

    // ye dono URLs ko browser lowest-priority background fetch karega
    // aur result ko IN-MEMORY cache mein rakhega (HTTP cache se bhi fast retrieval)
    "urls": ["/page-a", "/page-b"]
  }]
}
</script>

Speculation Rules se prefetch kiya gaya content <link rel="prefetch"> se ek level upgrade hai: ye response ko in-memory cache mein rakhta hai, jo disk-based HTTP cache se bhi fast retrieve hota hai — kyunki disk I/O bilkul avoid ho jaata hai.

Prerendering — poora page render karna

Prefetch sirf bytes la ke rakhta hai — HTML/CSS/JS ka raw response cache mein hota hai, lekin browser use parse/render/execute nahi karta jab tak navigation actually na ho. Prerender isse ek step aage le jaata hai: browser background mein poora naya page fetch, parse, render, aur JavaScript execute karta hai — bilkul waise jaise agar user ne already navigate kar diya ho, bas ye tab abhi invisible hai. Jab user actual click kare, browser bas is already-rendered page ko instantly swap kar deta hai — feel karta hai jaise navigation zero-cost thi.

HTML — Speculation Rules se pages prerender karna
<script type="speculationrules">
{
  "prerender": [{
    // same "list" source pattern — explicit URLs jo confident hain ki user visit karega
    "source": "list",

    // in dono pages ko browser background mein POORA render karega —
    // HTML parse, CSSOM build, JS execute, sab kuch — jaise ek hidden tab mein
    "urls": ["/page-a", "/page-b"]
  }]
}
</script>
⚠️ Prerender ka trade-off — bandwidth aur battery ka waste

Prerendering sabse powerful hai lekin sabse mehenga bhi — kyunki poora JS execute ho raha hai, network requests fire ho rahe hain, analytics beacons tak fire ho sakte hain (side-effects!) — sab kuch ek page ke liye jise user shaayad kabhi click hi na kare. Agar guess galat nikla, to wo saara CPU, memory, aur especially mobile data bekar gaya. India jaise market mein jahan bahut users limited/prepaid data plans pe hain, ye directly unke paison ka nuksaan hai. Isliye:

  • Prerender sirf tab karo jab confidence high ho — jaise search result ka top link, ya pagination ka "next page" jisko log almost hamesha click karte hain.
  • navigator.connection.saveData check karo — agar user ne browser mein "Data Saver" mode on kiya hai, to prefetch/prerender dono skip kar do.
  • navigator.connection.effectiveType check karo — "2g" ya "slow-2g" pe speculative loading band rakho.
JavaScript — saveData respect karte hue conditionally speculation rules inject karna
// navigator.connection Network Information API hai — ye batata hai
// user ki current connection quality aur unki data-saving preference
const conn = navigator.connection;

// agar connection info available nahi (Safari jaisa browser support nahi karta),
// ya user ne explicitly Data Saver mode ON kiya hai (saveData === true),
// ya connection slow hai (2g/slow-2g) — to hum speculative loading skip karte hain
const shouldSpeculate =
  conn &&                                   // API available honi chahiye
  !conn.saveData &&                         // user ne data-saver on nahi kiya ho
  !["slow-2g", "2g"].includes(conn.effectiveType); // connection kaafi fast ho

// sirf tab hi speculation rules ko page mein inject karo jab conditions favourable hon
if (shouldSpeculate) {
  // ek naya <script> element banaya JS se, kyunki hum runtime pe decide kar rahe hain
  const script = document.createElement("script");

  // type attribute set karna zaroori hai taaki browser ise speculation rules JSON maane
  script.type = "speculationrules";

  // JSON.stringify se rules object ko text content ke roop mein daala
  script.textContent = JSON.stringify({
    prefetch: [{ source: "list", urls: ["/page-a", "/page-b"] }]
  });

  // document.body mein append karte hi browser rules ko parse aur apply kar dega
  document.body.append(script);
}

Legacy note: Chrome ka purana <link rel="prerender"> (non-Speculation-Rules version) ab actually poora render nahi karta — Chrome ne ise "NoState Prefetch" mein downgrade kar diya hai (sirf resources fetch hote hain, render nahi) — kyunki full prerender ke abuse aur resource-waste issues bahut zyada the. Speculation Rules API is problem ko explicit opt-in aur eviction rules (memory pressure pe auto-cancel) ke saath fix karta hai.

Service Worker Precaching

Prefetch aur prerender dono "is session ke liye, is navigation ke liye" speculative hain — tab cache clear ya browser band, sab gaya. Service Worker precaching alag league mein hai: ye ek persistent, JavaScript-controlled cache hai (Cache API ke through) jo service worker ke install event pe explicitly bharta hai, aur repeat visits pe —chahe offline ho ya online— instantly serve karta hai.

Root-level mechanism: Service Worker ek separate thread hai jo browser aur network ke beech proxy ki tarah baithta hai. Jab pehli baar site visit hoti hai, SW install event fire karta hai — us waqt hum "app shell" (HTML skeleton, critical CSS, core JS, logo) ko caches.open() se ek named Cache object mein daal dete hain. Uske baad, har fetch request SW ke fetch event se guzarta hai, jahan hum decide karte hain: cache se do, ya network pe jao. Cache-only strategy mein hum sirf cache se serve karte hain (network sirf install ke waqt use hota hai) — matlab repeat visits zero network round-trip ke saath load hote hain, offline bhi.

sw.js — Service Worker install handler jo app shell precache karta hai
// cache ka naam version ke saath rakho — jab bhi app shell update karo,
// version number badal do (v1 -> v2), taaki purana cache invalidate ho sake
const CACHE_NAME = "app-shell-v1";

// ye array "app shell" define karta hai — wo minimum files jo site ko
// kaam karne ke liye chahiye, chahe network available ho ya na ho
const APP_SHELL_URLS = [
  "/",                     // root document — offline pe bhi kuch dikhna chahiye
  "/index.html",           // main HTML skeleton
  "/styles/main.css",      // critical CSS jo layout ke liye chahiye
  "/scripts/app.js",       // core JS bundle jo app ko bootstrap karta hai
  "/assets/logo.svg",      // branding asset jo har page pe dikhta hai
  "/offline.html"          // fallback page jo tab dikhega jab kuch aur na mile
];

// "install" event tab fire hota hai jab browser is service worker file ko
// PEHLI BAAR register karta hai, ya jab file content change hone se
// naya SW version detect hota hai
self.addEventListener("install", (event) => {
  // event.waitUntil() browser ko batata hai: "jab tak ye promise resolve na ho,
  // install ko 'complete' mat maano" — isse hum guarantee karte hain ki
  // caching poori hone se pehle SW activate na ho
  event.waitUntil(
    // caches.open() ek named Cache object return karta hai (Promise ke through)
    // — agar wo naam already exist nahi karta, naya bana deta hai
    caches.open(CACHE_NAME).then((cache) => {
      // cache.addAll() har URL ko fetch karta hai AUR response ko cache mein
      // store karta hai — sab ek saath, atomically (koi ek bhi fail hui to
      // poora addAll() reject ho jaata hai, taaki partial/broken cache na bane)
      return cache.addAll(APP_SHELL_URLS);
    })
  );
});

// "activate" event tab fire hota hai jab naya SW purane SW ki jagah control
// leta hai — yahan hum purane cache versions ko cleanup karte hain
self.addEventListener("activate", (event) => {
  event.waitUntil(
    // saare existing cache names ki list nikalo
    caches.keys().then((cacheNames) => {
      return Promise.all(
        cacheNames
          // sirf wo caches filter karo jo current CACHE_NAME se match nahi karte
          // (matlab ye purane versions hain — v0, ya koi stale cache)
          .filter((name) => name !== CACHE_NAME)
          // har purane cache ko delete kar do, storage free karne ke liye
          .map((name) => caches.delete(name))
      );
    })
  );
});

// "fetch" event HAR network request ke liye fire hota hai jo is SW ke
// scope ke andar aata hai — yahan hum cache-first strategy implement karte hain
self.addEventListener("fetch", (event) => {
  // event.respondWith() se hum browser ke default network fetch ko
  // override karke apna response de sakte hain
  event.respondWith(
    // pehle cache mein dhoondo ki is exact request ka match hai kya
    caches.match(event.request).then((cachedResponse) => {
      // agar cache mein mil gaya, wahi return karo — network ko touch mat karo
      // (isliye ye "cache-only for precached URLs" pattern kehlata hai)
      // agar nahi mila, tab hi network pe jao (runtime fallback)
      return cachedResponse || fetch(event.request);
    })
  );
});
app.js (main page) — Service Worker ko register karna
// pehle check karo ki current browser Service Worker API support karta hai —
// (purane browsers ya kuch restricted webviews mein ye undefined hoga)
if ("serviceWorker" in navigator) {
  // window ka "load" event use karo, taaki SW registration critical
  // rendering path ko block na kare — page pehle fully load ho jaaye,
  // uske baad hi hum SW registration ka background kaam shuru karein
  window.addEventListener("load", () => {
    // register() ko sw.js file ka path do — browser is file ko
    // fetch karega aur ek naya Service Worker thread spin up karega
    navigator.serviceWorker
      .register("/sw.js")
      .then((registration) => {
        // registration object se hume scope aur state milta hai — debugging ke liye useful
        console.log("Service Worker registered, scope:", registration.scope);
      })
      .catch((error) => {
        // registration fail ho sakta hai — jaise HTTPS na ho (SW sirf secure
        // context mein chalta hai, localhost exception ke saath), ya file 404 de
        console.error("Service Worker registration failed:", error);
      });
  });
}

Production mein ye sab hath se likhna maintenance-heavy hai — har baar file hash change hone pe APP_SHELL_URLS array manually update karna padega. Isliye real-world projects Workbox (Google ki library) use karte hain, jo build-time pe automatically ek precache manifest generate karta hai (file ka content-hash "revision" ban jaata hai), aur workbox.precaching.precacheAndRoute([...]) se saara install/fetch boilerplate handle ho jaata hai — cache invalidation bhi automatic, kyunki hash change hote hi naya URL ban jaata hai.

Teeno mein WHEN ka farak — root-level timing model

Ye teeno tools ek hi lagte hain ("cheez ko pehle se laao") lekin unka trigger point bilkul alag hai — aur yahi unka sabse important architectural difference hai:

  • Prefetch (rel="prefetch" / Speculation Rules prefetch): current page ka load poora hone ke baad, browser ke idle time mein trigger hota hai (low-priority background queue). Koi explicit user signal ki zaroorat nahi — bas declare karo, browser apni marzi se, jab bandwidth free ho, fetch kar lega.
  • Prerender: zyada tar ek intent signal ke saath trigger hota hai — jaise link pe hover, touchstart (mobile pe "pointer down" jaisa hi intent), ya viewport mein aana. Frameworks (Next.js) isko "on hover/viewport" heuristic se automate karte hain. Manually declare kiye gaye Speculation Rules bhi ho sakte hain jo page-load pe hi register ho jaate hain, lekin actual heavy rendering work tabhi shuru hota hai jab browser confidence high maane (aur ye eager ya moderate eagerness config se control hota hai).
  • Service Worker precache: ek bilkul different lifecycle event pe trigger hota hai — SW install time par, jo pehli visit pe (ya SW code update hone pe) hota hai. Ye "user ke agle click" ka wait nahi karta — ye "site ke saath pehli mulakat" pe hi critical assets ko permanently cache mein daal deta hai, taaki sabhi future visits (aaj, kal, offline, kabhi bhi) instant ho.

Risk vs Reward — kab kya use karein

Jitna aage tum in teeno mein badhte ho (prefetch → prerender → SW precache), utna zyada reward milta hai (faster future navigation) lekin utna hi zyada risk/cost bhi (bandwidth, CPU, storage, complexity):

  • Prefetch = low risk, low-medium reward. Galat guess ka cost sirf kuch KB bandwidth hai — koi rendering/JS execution waste nahi hua.
  • Prerender = high risk, high reward. Galat guess ka cost poora page render + JS execution + possibly side-effect network calls hai — sabse expensive galti.
  • SW precache = one-time cost, permanent reward. Install-time pe ek baar cost bharta hai, lekin uske baad har visit free hai — is investment ka ROI sabse zyada hai agar user repeat visitor hai. First-time-only visitors ke liye ye net negative hai (extra install-time network calls jo kabhi reuse nahi hongi).
⚠️ Over-prefetching/prerendering ka real cost — India-specific

Ye teeno techniques "speculative" hain — matlab inka fundamental nature hi galat guess ka risk carry karta hai. Agar tum har link ko prefetch/prerender kar doge "just in case," to:

  • User ka mobile data waste hota hai un pages ke liye jo wo kabhi visit hi nahi karega — prepaid/limited-data users (jo India mein bahut bade user-base hain) ke liye ye directly unke paison ka nuksaan hai.
  • Battery aur CPU waste hote hain, especially prerender mein jahan poora JS execute hota hai background mein.
  • Server/CDN pe unnecessary load aata hai — real user traffic ke saath compete karta hai speculative traffic.

Isliye hamesha navigator.connection.saveData aur navigator.connection.effectiveType check karo before speculative loading trigger karne se pehle (jaisa upar code example mein dikhaya). Ye ek non-negotiable production practice honi chahiye, sirf ek "nice to have" nahi — kyunki iska direct impact user ke real-world paison aur data plan pe padta hai.

🧠 Senior Dev Note — frameworks in primitives ko kaise abstract karte hain

Modern frameworks in raw browser APIs ke upar convenient abstractions banate hain, taaki developers ko manually Speculation Rules JSON likhna na pade:

  • Next.js <Link>: jab component viewport mein aata hai (Intersection Observer se detect), Next.js automatically us route ke JS chunk ko prefetch kar deta hai — production build mein by default. Ye conceptually humare "Speculation Rules prefetch on list" jaisa hi hai, bas framework internally handle karta hai aur route-level code-splitting (Chapter 9) ke saath tightly integrated hai.
  • Astro View Transitions: Astro ka <ClientRouter /> hover pe (ya viewport-enter pe, config se) target page ko prefetch karta hai, aur navigation ko View Transitions API ke saath animate karta hai — feel karta hai jaise SPA navigation, lekin underlying mechanism wahi resource-hint/speculation primitives hain jo humne is chapter mein dekhe.
  • Dono cases mein framework ka kaam hai heuristic decide karna (kab, kise prefetch karna hai) — underlying browser mechanism wahi rehta hai jo tumne raw HTML/JS mein likha hota. Framework internals padhte waqt yahi lens use karo: "ye kaunsa primitive (prefetch/prerender/SW cache) ko wrap kar raha hai?"

Key Takeaways

  • Prefetch sirf resource ke raw bytes ko low-priority background fetch karta hai aur HTTP (ya in-memory, Speculation Rules ke case mein) cache mein rakhta hai — koi render/execute nahi hota.
  • Prerender poora page fetch + render + JavaScript execute karta hai hidden background mein — near-instant navigation deta hai, lekin galat guess ka cost sabse zyada hai.
  • Service Worker precaching install-time pe app shell ko Cache API mein explicitly daalta hai — persistent, offline-capable, aur cache-only strategy se network round-trip completely eliminate karta hai repeat visits pe.
  • Teeno ka trigger point alag hai: prefetch = idle time, prerender = intent signal (hover/ viewport), SW precache = install lifecycle event.
  • Har speculative technique bandwidth/CPU/battery ka risk carry karti hai — hamesha navigator.connection.saveData aur effectiveType respect karo, especially mobile-heavy, data-cost-sensitive markets jaise India ke liye.
  • Frameworks (Next.js, Astro) in raw primitives ko automate karte hain — samajhna zaroori hai ki underlying mechanism wahi <link rel="prefetch"> / Speculation Rules / Service Worker hi hai.

🎯 Interview Questions

  • Prefetch aur prerender mein fundamental difference kya hai?
    Hint: prefetch sirf bytes laata hai (fetch only), prerender poora page render + JS execute karta hai background mein — cost aur risk dono prerender mein zyada hote hain.
  • Cross-origin document ko prefetch karna problematic kyun hai?
    Hint: browser cache-key mismatch ki wajah se prefetched response ko navigation ke liye reuse nahi kar paata, isliye do baar request jaati hai — ulta bandwidth waste.
  • Service Worker ka Cache API aur browser ka HTTP cache — dono same hain kya?
    Hint: nahi. HTTP cache Cache-Control headers se server-controlled hota hai; Cache API JavaScript se explicitly control hota hai (SW ke andar) — dono independent storage layers hain.
  • Speculative loading implement karte waqt kaunsa API check karna chahiye taaki data-conscious users ka data waste na ho?
    Hint: navigator.connection.saveData aur navigator.connection.effectiveType — Network Information API.
  • Chrome ka legacy <link rel="prerender"> ab actually kya karta hai?
    Hint: full render nahi karta — Chrome ne ise "NoState Prefetch" mein downgrade kar diya hai (resources fetch hote hain, render nahi) kyunki full prerender ka abuse/waste zyada tha.
  • SW precaching production mein hath se maintain karna mushkil kyun hai, aur Workbox kya solve karta hai?
    Hint: file hashes change hone pe manual URL-array update karna padta, cache invalidation bug-prone hota; Workbox build-time pe revision manifest auto-generate karke ye automate karta hai.
