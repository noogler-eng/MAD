An Overview of Web Workers

JavaScript by default sirf ek thread pe chalti hai — main thread. Us thread pe scripting, layout, paint, aur user input sab compete karte hain. Jab koi heavy computation is thread ko block karti hai, page "jam" ho jaata hai — clicks late respond karte hain, scroll jank hota hai, INP (Interaction to Next Paint) kharab ho jaata hai. Web Workers is bottleneck ka escape hatch hain: JS ka ek alag OS-level thread jahan heavy kaam chal sakta hai, bina main thread ko touch kiye.

Main thread bottleneck kyun hai

Browser ke andar ek renderer process hota hai, aur us process ke andar main thread woh jagah hai jahan bahut saara kaam sequentially (ek ke baad ek) chalta hai:

  • JS execution — tumhara application code, event handlers, timers, promises.
  • HTML parsing — DOM construction jab document stream ho raha hota hai.
  • CSS parsing aur style calculation — CSSOM banana, matching selectors.
  • Layout (reflow) — element ke exact position/size calculate karna.
  • Paint aur compositing — pixels ko screen pe draw karna.
  • User input handling — click, tap, keypress, scroll events ko process karna.

Ye sab ek hi thread pe, ek hi call stack pe, cooperative-scheduling se chalte hain — matlab jab tak JavaScript ka ek task chal raha hai, browser kuch aur nahi kar sakta. Agar tumhara task 50ms se zyada le raha hai, wo ek "long task" ban jaata hai, aur us duration mein koi bhi user input queue mein atka rehta hai. Yehi directly INP (Interaction to Next Paint) ko kharab karta hai — jitna zyada main thread busy, utna zyada delay click se visual response tak.

⚠️ Root-level insight

JS single-threaded hai iska matlab hai — heavy computation (JSON parse of 10MB file, image processing, complex sorting/filtering, crypto operations) agar main thread pe chalayi, toh chahe woh "async" code ho bhi (jaise fetch().then()), .then() ke andar ka synchronous compute abhi bhi main thread ko block karega. Async sirf I/O wait ko non-blocking banata hai, CPU-bound work ko nahi. Isiliye heavy CPU work ke liye Promise kaafi nahi, actual dusra thread chahiye — Web Worker.

Web Worker kya hai

Web Worker ek JavaScript file hai jo browser ek alag OS thread pe run karta hai, apne khud ke global execution context ke saath. Kuch key architectural points:

  • Worker ka global scope self hota hai — window nahi. Isliye worker ke andar window.document, window.location jaisi DOM-related cheezein exist nahi karti.
  • Worker DOM ko directly access ya manipulate nahi kar sakta — DOM single-threaded design hai (thread-safety issues avoid karne ke liye), toh sirf main thread hi DOM ko touch kar sakta hai.
  • Worker ke paas apni khud ki memory heap hoti hai, alag se garbage collected. Main thread se koi variable share nahi hota — sab kuch message ke through jaata hai (details neeche).
  • Worker ke paas access hai: JS primitives (Array, Map, Promise, etc.), fetch/XHR, IndexedDB, WebSocket, timers (setTimeout), crypto API, aur importScripts() se dusre scripts load karna.
  • Worker ko instantiate karte waqt browser ek naya thread spawn karta hai — ye zero-cost nahi hai (thread creation ka apna overhead hai), isliye workers ko dispose/reuse karna matter karta hai.

postMessage aur Structured Clone Algorithm

Chunki worker aur main thread alag memory spaces mein rehte hain, wo variables directly share nahi kar sakte. Communication ek message-passing pipeline se hoti hai:

  • worker.postMessage(data) — main thread se worker ko (ya worker se main thread ko) data bhejna.
  • worker.addEventListener('message', handler) ya onmessage — dusri taraf se aaya hua data receive karna.

Jab tum postMessage call karte ho, browser data ko structured clone algorithm se serialize karta hai — ye JSON.stringify se zyada powerful hai (Date, Map, Set, ArrayBuffer, Blob, RegExp support karta hai; functions aur DOM nodes support nahi karta). Important root detail: ye data COPY hota hai, share nahi. Matlab agar tum ek 50MB ka array bhejte ho, browser uski poori copy banayega aur worker thread ko bhejega — jo bade payloads ke liye slow aur memory-expensive ho sakta hai.

📌 Structured clone vs Transferable vs SharedArrayBuffer

Teen tareeke hain data cross-thread bhejne ke: (1) Structured clone (default) — copy banti hai, safe hai par bade data ke liye slow. (2) Transferable objects — ownership transfer hoti hai (copy nahi), original thread us object ko access nahi kar sakta uske baad — bahut fast, zero-copy. (3) SharedArrayBuffer — actual memory dono threads ke beech shared hoti hai (real shared memory, atomics ke saath) — sabse powerful par sabse zyada careful handling maangta hai (race conditions possible), aur cross-origin isolation headers chahiye hote hain.

Basic Example — Worker Create karna, Data Bhejna, Result Lena

Neeche do files hain — main thread ka script jo worker create karke usse kaam saumpta hai, aur worker.js jo actual heavy computation karta hai (yahan example ke liye ek simple "sum of large array" — real duniya mein ye JSON parsing, image processing, ya encryption jaisa kuch bhi ho sakta hai).

main.js — main thread se worker banana aur use karna
// main.js — ye code browser ke MAIN THREAD pe chalta hai (jahan DOM/UI hai)

// 'new Worker()' browser ko batata hai: ek naya OS thread spawn karo,
// aur usme 'worker.js' file ko load karke run karo. Path relative hota hai
// current HTML document se, ya module-based bundlers mein import.meta.url se.
const worker = new Worker('worker.js');

// Worker se print/PROGRESS ya FINAL result wapas aane pe ye listener trigger hoga.
// 'message' event ka payload 'event.data' mein hota hai — jo worker ne postMessage() kiya tha.
worker.addEventListener('message', (event) => {
  // event.data woh object hai jo worker ne bheja — structured-clone se copy hoke aaya hai.
  const { type, payload } = event.data;

  // Hum apne khud ke protocol se 'type' field use kar rahe hain taaki
  // ek hi worker se multiple kisam ke messages differentiate ho sakein.
  if (type === 'RESULT') {
    // Result mil gaya — ab ye DOM update main thread pe safely kar sakte hain,
    // kyunki worker khud DOM ko touch nahi kar sakta tha.
    console.log('Sum from worker:', payload.sum);
    document.querySelector('#result').textContent = payload.sum;
  }

  if (type === 'ERROR') {
    // Worker ke andar agar koi custom error condition hui, hum use bhi
    // message ke through wapas bhej sakte hain (worker crash se alag).
    console.error('Worker reported an error:', payload.message);
  }
});

// Worker ke andar agar koi UNCAUGHT exception throw hoti hai (jaise
// syntax error ya runtime error), 'error' event yahan fire hota hai.
worker.addEventListener('error', (event) => {
  // event.message, event.filename, event.lineno debug info dete hain.
  console.error('Worker crashed:', event.message, 'at', event.filename, ':', event.lineno);
});

// Ek bada array generate karte hain jise worker ko sum karne ke liye bhejenge.
// Ye array MAIN thread pe hi bana hai — jab postMessage() karenge, iski COPY
// worker thread ko jaayegi (structured clone algorithm ke through).
const bigArray = Array.from({ length: 10_000_000 }, (_, i) => i);

// postMessage() se worker ko data bhejte hain. Hum bhi apna 'type' protocol
// follow kar rahe hain taaki worker ko pata chale kya karna hai.
worker.postMessage({ type: 'SUM_ARRAY', payload: { numbers: bigArray } });

// IMPORTANT: postMessage() call ke turant baad bhi main thread AAGE chal
// sakta hai — ye call asynchronous hai, worker ka result aane tak main
// thread block NAHI hota. Yehi poore pattern ka core benefit hai.
console.log('Worker ko kaam de diya, main thread ab FREE hai aur UI responsive rahega.');
worker.js — worker thread pe chalne wala code
// worker.js — ye file browser ek ALAG OS THREAD pe run karta hai.
// Yahan 'window' object EXIST nahi karta — DOM ko touch karne ki
// koshish (jaise document.querySelector) yahan turant error dega.

// Worker ke andar global scope ka naam 'self' hota hai (ya use omit bhi
// kar sakte ho kyunki worker scope mein ye implicit hai).
self.addEventListener('message', (event) => {
  // Main thread se jo bheja gaya woh event.data mein milta hai —
  // ye already structured-clone se COPY hoke is thread mein aa chuka hai.
  const { type, payload } = event.data;

  // Apna simple message-type protocol check kar rahe hain.
  if (type === 'SUM_ARRAY') {
    try {
      // Yahan se heavy computation shuru — ye loop MAIN THREAD ko
      // bilkul BLOCK nahi karega, kyunki hum worker thread pe hain.
      let sum = 0;

      // 10 million numbers ka sum — CPU-intensive kaam, jo agar main
      // thread pe hota toh UI ko seconds ke liye freeze kar deta.
      for (let i = 0; i < payload.numbers.length; i++) {
        sum += payload.numbers[i];
      }

      // Result wapas main thread ko bhej rahe hain — apna protocol follow karte hue.
      // Ye bhi structured-clone se copy hoke wapas jaayega.
      self.postMessage({ type: 'RESULT', payload: { sum } });
    } catch (err) {
      // Agar computation ke beech koi error aayi, use bhi gracefully
      // message ke through report karte hain (crash hone ke bajaye).
      self.postMessage({ type: 'ERROR', payload: { message: err.message } });
    }
  }
});

Notice karo — is example mein main thread aur worker ke beech koi shared variable nahi hai. Sab kuch explicit postMessage calls ke through, ek defined "protocol" (type/payload shape) follow karte hue ho raha hai. Ye pattern production code mein bahut common hai kyunki debug karna aasan rehta hai.

Transferable Objects — Copy ka Cost Avoid Karna

Upar wale example mein bigArray ek plain JS array tha — uski poori copy worker ko bhejni padi. Agar data bahut bada hai (jaise raw binary image data, audio buffers), copy karna expensive hai — dono CPU time aur double memory. ArrayBuffer jaisi binary types ko Transferable ke roop mein bheja ja sakta hai — jisme ownership transfer hoti hai, copy nahi banti.

transfer-example.js — ArrayBuffer ko zero-copy transfer karna
// main.js (relevant part) — ArrayBuffer ko TRANSFER karke bhejna, copy nahi.

// Ek 100MB ka raw binary buffer bana rahe hain (jaise image ya audio data).
const buffer = new ArrayBuffer(100 * 1024 * 1024); // 100 MB

// postMessage() ka DOOSRA argument ek array hai jisme woh objects list
// karte hain jinhe TRANSFER karna hai (copy nahi karna). Browser ab
// 'buffer' ki memory ko literally worker thread ko HAND OVER kar dega —
// koi duplicate memory allocate nahi hogi, isliye ye operation ~instant hai
// chahe buffer kitna bhi bada ho.
worker.postMessage({ type: 'PROCESS_BUFFER', payload: { buffer } }, [buffer]);

// CRITICAL GOTCHA: transfer ke baad, 'buffer' is (main) thread pe
// USELESS ho jaata hai — uski byteLength 0 ho jaati hai. Ownership
// worker ko chali gayi. Agar tum yahan buffer ko access karne ki
// koshish karoge, tumhe empty/detached buffer milega.
console.log(buffer.byteLength); // 0 — buffer 'neutered'/detached ho chuka hai

// Worker se wapas processed buffer chahiye toh worker ko bhi
// self.postMessage(result, [result.buffer]) se transfer karna hoga.
⚠️ Transfer vs Clone — kab kya use karo

Agar sender ko data ke baad zaroorat nahi hai (one-way handoff, jaise "yeh buffer process karo aur bhool jao"), Transferable use karo — bahut fast. Agar sender ko apni copy bhi chahiye (dono taraf data use hoga), normal structured clone use karo, ya explicitly buffer ko .slice() karke ek copy transfer karo taaki original safe rahe.

Typical Use Cases

  • Heavy computation — complex math, physics simulations, ya large-dataset sorting/filtering jo main thread pe janky feel hoti.
  • Large JSON/CSV parsing — API se MB-scale response aaya, aur usse parse+transform karna hai bina scroll jank ke.
  • Image/video processing — pixel manipulation, filters, thumbnail generation, EXIF metadata extraction (agla chapter isi pe hai).
  • Encryption/hashing — client-side crypto operations jo CPU-intensive hote hain (password hashing, data encryption before upload).
  • Real-time data processing — WebSocket se aane wale high-frequency updates ko process karna bina UI ko block kiye.
🧠 Senior Dev Note — Comlink aur "kab worker overkill hai"

Raw postMessage/onmessage protocol likhna quickly boilerplate-heavy ho jaata hai — message types define karna, request/response ko correlate karna, error handling — sab manually. Comlink (Google Chrome team ka hi ek chhota library, ~1.1KB) is boilerplate ko hata deta hai — worker ke exposed functions ko normal async function calls jaisa feel karata hai, RPC-style, under the hood postMessage use karke:

const api = Comlink.wrap(worker); const sum = await api.sumArray(bigArray); — bas, no manual message-type juggling.

Par yahan ek important senior judgment call hai: worker reach for karna premature optimization ban sakta hai. Worker spawn karna thread-creation overhead rakhta hai, aur message-passing ka bhi apna serialization cost hota hai — chhote/fast operations ke liye worker add karna performance ko better nahi, worse bana sakta hai. Sahi approach: pehle Chrome DevTools Performance panel ya PerformanceObserver se actual long tasks profile karo, INP data dekho — agar koi specific function repeatedly 50ms+ ka block create kar raha hai, tab worker justified hai. Sirf "ye heavy lagta hai" ke assumption pe worker mat daalo.

Key Takeaways

  • Main thread pe JS execution, layout, paint, aur user input — sab compete karte hain; long tasks INP kharab karte hain.
  • Web Worker ek alag OS thread hai apne khud ke global scope (self) ke saath, jise DOM access nahi milta.
  • Communication postMessage/onmessage se hoti hai; data copy hota hai (structured clone algorithm se), share nahi — jab tak Transferable objects ya SharedArrayBuffer use na karo.
  • Transferable objects (jaise ArrayBuffer) ownership transfer karte hain — zero-copy, bahut fast, par original reference detached ho jaata hai.
  • Workers ke paas fetch, IndexedDB, crypto, WebSocket, timers hain — par DOM aur window nahi.
  • Comlink jaisi libraries postMessage boilerplate ko async function-call syntax mein convert kar deti hain.
  • Worker sirf tabhi use karo jab profiling se real long-task bottleneck confirm ho — premature optimization avoid karo.

🎯 Interview Questions

  • Q: Web Worker aur main thread memory share karte hain kya?
    Hint: Nahi by default — structured clone se copy hoti hai. SharedArrayBuffer real shared memory deta hai, par cross-origin isolation headers (COOP/COEP) chahiye.
  • Q: Worker DOM access kyun nahi kar sakta?
    Hint: DOM thread-safe nahi hai; multi-thread access se race conditions/corruption ho sakti hai, isliye browser design se hi restrict karta hai.
  • Q: async/await CPU-bound work ko main thread block hone se kyun nahi bachaata?
    Hint: async sirf I/O wait ko non-blocking banata hai (event loop mein yield karta hai); synchronous CPU-heavy code (loop, parsing) chahe Promise ke andar ho, execute hote waqt abhi bhi call stack occupy karta hai.
  • Q: Transferable object use karne ke baad original reference ka kya hota hai?
    Hint: Detached/neutered ho jaata hai (byteLength 0) — sender ke paas ab access nahi rehta, ownership receiver ko chali gayi.
  • Q: Worker kab use nahi karna chahiye, chahe operation "heavy" lage?
    Hint: Jab actual profiling (DevTools Performance / INP metrics) long task confirm na kare — worker spawn + message serialization ka apna overhead hai jo chhoti operations ke liye net-negative ho sakta hai.
  • Q: Comlink kya problem solve karta hai?
    Hint: Raw postMessage/onmessage boilerplate (message types, correlation, error propagation) ko hata ke worker functions ko normal async function calls jaisa expose karta hai, RPC-style, using Proxy under the hood.
