Assist the Browser with Resource Hints

Browser bahut smart hai, lekin wo future dekh nahi sakta. Woh HTML ko top-to-bottom parse karte hue hi resources discover karta hai — jab tak parser kisi <link> ya <img> tak nahi pahunchta, uska origin ka DNS bhi resolve nahi hua hota. Resource hints ek chhota sa API hai jisse hum browser ko "abhi se pata hai, tujhe aage ye chahiye hoga" wala signal de sakte hain — network layer ke exact stages (DNS → TCP → TLS → fetch) ko manually pre-warm karke.

Network connection ke stages — root cause samjho

Resource hints samajhne se pehle ye samajhna zaroori hai ki jab browser ek cross-origin resource fetch karta hai, to network layer mein sequentially kya hota hai. Har hint in stages mein se kitne stages ko pre-warm karta hai — yehi unka core differentiator hai:

  1. DNS Lookup — domain name (jaise fonts.gstatic.com) ko IP address mein resolve karna. Ye ek round-trip hai, typically 20-120ms (recursive resolver, ISP, geography pe depend karta hai).
  2. TCP Handshake — client aur server ke beech connection establish karna (SYN → SYN-ACK → ACK). Ek aur round-trip.
  3. TLS Negotiation — agar HTTPS hai (aaj-kal almost hamesha), to certificate exchange aur cipher negotiation. HTTP/1.1/2 pe ye 1-2 extra round-trips leta hai (TLS 1.3 mein thoda kam).
  4. Request + Response (actual fetch) — asli resource bytes download hote hain.

Ek naye cross-origin connection ke liye ye pehle 3 stages hi 100-500ms tak le sakte hain — resource ka ek single byte download hone se pehle. Resource hints ka pura game ye hai ki in stages ko browser ke idle time mein, actual discovery se pehle hi complete kar liya jaaye.

📌 Root mechanism: Priority Hints List

Har resource hint internally browser ke networking stack ko ek instruction bhejta hai jo normal HTML-parsing-driven resource discovery se independent hai. Yani <link rel="preconnect"> parser ko block nahi karta — ye ek side-channel request hai jo turant background mein fire ho jaata hai, jabki main parsing continue rehti hai.

dns-prefetch — sirf DNS lookup

dns-prefetch sabse halka (cheapest) hint hai — ye sirf stage 1 (DNS lookup) pre-resolve karta hai. TCP handshake ya TLS negotiation nahi hota. Result browser ke DNS cache mein store ho jaata hai, taaki jab actual request fire ho, DNS lookup skip ho jaaye.

dns-prefetch usage
<!-- Kisi external analytics/social embed domain ke liye -->
<link                                    <!-- <link> tag: resource hint declare karne ka standard tareeka -->
  rel="dns-prefetch"                     <!-- rel="dns-prefetch": sirf DNS resolve karo, connection nahi banao -->
  href="https://www.google-analytics.com" <!-- href: jis origin ka DNS pre-resolve karna hai (path nahi, sirf origin) -->
>

<!-- Multiple third-party origins ke liye — sabse common real-world use case -->
<link rel="dns-prefetch" href="https://ads.example.com">   <!-- ad network domain -->
<link rel="dns-prefetch" href="https://cdn.example-widget.com"> <!-- widget CDN domain -->

Use-case: jab tumhare paas bahut saare third-party origins hain (5-10+), jinme se sab critical nahi hain (e.g. footer social links, analytics beacons), to har origin pe full preconnect lagana overkill hai — kyunki preconnect ek open TCP+TLS connection maintain karta hai jo agar use hi nahi hua to resources waste karta hai. Wahan dns-prefetch zyada safe, cheap default hai.

preconnect — DNS + TCP + TLS, teeno

preconnect teeno connection-setup stages complete karta hai — DNS lookup, TCP handshake, aur TLS negotiation (agar HTTPS hai) — lekin actual resource fetch nahi karta. Jab HTML parser baad mein us origin se koi resource maangega, connection already garam (warm) hoga, so sirf request+response stage bachta hai.

preconnect usage
<!-- Case 1: non-CORS resource (jaise ek CDN se generic JS/CSS) -->
<link
  rel="preconnect"                <!-- rel="preconnect": DNS+TCP+TLS teeno abhi complete karo -->
  href="https://cdn.example.com" <!-- jis origin se resource baad mein aayega uska base URL -->
>

<!-- Case 2: CORS resource — fonts.gstatic.com jahan se font FILES CORS ke saath aate hain -->
<link
  rel="preconnect"
  href="https://fonts.gstatic.com"
  crossorigin              <!-- ZAROORI: CORS resources ke liye connection anonymous mode mein khulna chahiye -->
>
⚠️ crossorigin bhoolna = wasted preconnect

Browser ek origin ke liye do alag connection pools maintain karta hai — ek anonymous (no-CORS) mode ke liye, ek credentialed/CORS mode ke liye. Agar crossorigin attribute chhod diya aur actual resource (jaise font file via @font-face) CORS mode mein fetch hota hai, to browser preconnect wale connection ko reuse nahi karega — ek naya connection banayega from scratch. Matlab tumne jo DNS+TCP+TLS pehle se kiya, wo bilkul waste ho gaya, aur ulta ek extra unused connection ka overhead bhi laga.

Root cause: crossorigin attribute browser ko batata hai ki request CORS mode (anonymous credentials) mein bhejni hai. Fonts hamesha CORS mode mein fetch hote hain (spec requirement hai, chahe same-origin ho ya nahi), isliye font preconnects pe ye attribute hamesha chahiye.

⚠️ Zyada preconnect bhi bura hai

Har open TCP/TLS connection browser aur OS dono pe resource consume karta hai (memory, socket limits, CPU for TLS handshake). Sirf un 3-4 sabse critical cross-origin domains ke liye preconnect use karo jinse render-blocking ya LCP-critical resources aa rahe hain — baaki ke liye dns-prefetch use karo.

preload — DNS + TCP + TLS + actual fetch

preload sabse aggressive hint hai — ye sirf connection nahi banata, balki resource ko abhi download karna shuru kar deta hai, uss priority ke saath jo tum specify karte ho, bina HTML parser ke us point tak pahunchne ka wait kiye. Isliye ye un resources ke liye best hai jo late-discovered hain — matlab jinka reference HTML/CSS ke deep andar chhupa hai (jaise CSS ke andar @font-face se referenced font file, ya JS se conditionally load hone wali CSS background-image).

preload basic syntax
<link
  rel="preload"                       <!-- rel="preload": resource ko abhi high priority pe fetch karo -->
  href="/hero-image.webp"          <!-- jo file preload karni hai uska exact URL -->
  as="image"                      <!-- as: ZAROORI — browser ko resource type batata hai -->
  fetchpriority="high"            <!-- optional: is fetch ko explicitly high priority queue mein daalo -->
>
⚠️ Root cause: as attribute kyun mandatory hai

Browser ke andar har resource type ka apna alag cache partition aur request priority queue hota hai (image queue, font queue, style queue, script queue — inki priorities alag hain, aur CORS mode bhi type ke hisaab se differ karta hai). as attribute ke bina browser ko pata nahi hota ki resource kis queue/priority/CORS-mode mein jaayega, so wo generic priority pe fetch kar leta hai. Jab baad mein asli consumer (e.g. <img> tag ya CSS) usi URL ko sahi as-equivalent context ke saath maangta hai, browser ye match nahi kar paata ki ye wahi resource hai — result: resource do baar download hota hai. Chrome DevTools console mein iske liye ek warning bhi dikhta hai: "was preloaded using link preload but not used within a few seconds."

Font preload — crossorigin gotcha
<link
  rel="preload"
  href="/fonts/inter-var.woff2"  <!-- self-hosted variable font file ka path -->
  as="font"                 <!-- as="font": browser ko batata hai ye font-loading priority queue mein jaaye -->
  type="font/woff2"          <!-- MIME type dena optional but recommended — unsupported format ho to browser skip kar sakta hai -->
  crossorigin                <!-- ZAROORI: fonts hamesha CORS mode mein fetch hote hain, SAME-ORIGIN font ke liye bhi -->
>

<!-- Agar crossorigin attribute yahaan chhoot gaya, to CSS ka -->
<!-- @font-face { src: url(/fonts/inter-var.woff2) } wala fetch is preload se MATCH nahi karega -->
<!-- kyunki font requests spec ke hisaab se hamesha anonymous-CORS mode mein jaate hain, -->
<!-- aur preload agar crossorigin ke bina hua to wo no-CORS mode mein tha — mismatch = double download -->

Ye font wala gotcha bahut common hai kyunki intuitively lagta hai ki same-origin font ko crossorigin ki zaroorat nahi — lekin font fetching spec ka rule hai ki font requests hamesha CORS mode mein bhejte hain, chahe origin same ho ya nahi. Iska matlab preload aur actual usage dono jagah crossorigin consistent hona chahiye.

Responsive image preload — imagesrcset
<link
  rel="preload"
  as="image"
  href="/hero-800.webp"                          <!-- fallback URL — jo browsers imagesrcset support nahi karte unke liye -->
  imagesrcset="/hero-400.webp 400w, /hero-800.webp 800w, /hero-1200.webp 1200w"
                                                <!-- imagesrcset: <img srcset> jaisa hi syntax, viewport ke hisaab se sahi variant preload hota hai -->
  imagesizes="100vw"                        <!-- imagesizes: <img sizes> ka equivalent — layout width ka hint -->
>
<!-- Bina imagesrcset ke, preload sirf href wali single image download karta, -->
<!-- lekin actual <img srcset> kisi aur variant ko select kar sakta — phir double download -->

prefetch — future navigation ke liye, low priority

prefetch bhi puri fetch karta hai (DNS+TCP+TLS+download) jaise preload, lekin do fundamental differences hain: (1) ye lowest priority pe queue hota hai — current page ke resources ke baad, browser ke idle network time mein; aur (2) ye current navigation ke liye nahi, agli (future) navigation ke liye hai — speculative hai, ho sakta hai user wahan jaaye hi na.

prefetch usage
<!-- Checkout flow: cart page pe hone par, agla likely step hai payment page -->
<link
  rel="prefetch"                  <!-- rel="prefetch": low-priority speculative fetch -->
  href="/payment.css"          <!-- future page ka critical CSS -->
  as="style"                 <!-- as attribute yahaan bhi zaroori — same double-fetch problem se bachne ke liye -->
>

Use sirf tab karo jab tumhare paas analytics/data ho jo confidently predict kare ki user is next step pe jaayega (e.g. multi-step checkout, ya "next article" jisko 80%+ users click karte hain). Random prefetching data waste karta hai — aur Save-Data header wale users (jo explicitly kam data consume karna chahte hain) ke liye ye disable karna chahiye.

modulepreload — JS module graph ke liye

ES modules (<script type="module">) ek dependency tree banate hain — ek module doosre module ko import karta hai, jiska pata browser ko tab chalta hai jab wo parent module ko fetch aur parse kar leta hai. Ye sequential discovery latency add karta hai. modulepreload is poore module graph ko upfront fetch (aur parse/compile bhi) karwa deta hai.

modulepreload usage
<link
  rel="modulepreload"              <!-- rel="modulepreload": ES module ko fetch + parse dono abhi karo -->
  href="/js/app.js"              <!-- entry module ka path — iske andar ke imports bhi discover honge -->
>
<script type="module" src="/js/app.js"></script>
                                       <!-- actual execution — preload ke saath match hoga to double-fetch nahi hoga -->

Farak preload as="script" se: modulepreload sirf network fetch nahi karta, module ko parse aur compile bhi kar deta hai, aur uske static imports ko bhi recursively discover kar leta hai — jo plain preload nahi karta.

Real example: third-party font + hero image combo

Ek typical marketing landing page socho: font Google Fonts (fonts.gstatic.com) se aa raha hai (cross-origin), aur hero image LCP element hai jo CSS background-image se set hota hai (isliye HTML parser ko late pata chalta hai). Sahi combination:

index.html <head> — sahi order
<head>
  <!-- Step 1: font ORIGIN ke liye connection warm karo (fetch nahi, sirf connect) -->
  <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
  <!-- crossorigin zaroori hai kyunki font files CORS mode mein fetch hoti hain -->

  <!-- Step 2: font FILE ko directly preload karo (fonts.googleapis.com ka CSS wait karne ki zaroorat nahi) -->
  <link
    rel="preload"
    href="https://fonts.gstatic.com/s/inter/v12/inter-latin.woff2" <!-- direct .woff2 URL, Google Fonts CSS inspect karke nikala hua -->
    as="font"
    type="font/woff2"
    crossorigin
  >

  <!-- Step 3: hero image ko preload karo — CSS background-image parser ke discovery se pehle hi -->
  <link
    rel="preload"
    href="/images/hero-1600.webp"
    as="image"
    fetchpriority="high"   <!-- ye LCP element hai, explicit high priority se aur fast bana do -->
  >

  <!-- Step 4: normal font CSS bhi load hoga, lekin ab uske andar ka font file -->
  <!-- already preloading/preloaded hoga, so render-blocking wait kam hoga -->
  <link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=Inter&display=swap">

</head>
<style>
  .hero {
    background-image: url("/images/hero-1600.webp"); /* URL preload ke href se EXACTLY match hona chahiye, warna double-fetch */
  }
</style>

Note: preconnect aur direct preload dono font ke liye use kiye — ye redundant nahi hai. Preconnect turant fire hota hai (connection ke liye), aur agar direct .woff2 URL pehle se pata hai (Google Fonts CSS ko inspect karke), to preload use kar sakte ho taaki font file fetch bhi jaldi shuru ho, na ki font-CSS ke download+parse ka wait kare.

Bonus: Fetch Priority API

fetchpriority attribute <link>, <img>, aur <script> pe kaam karta hai — browser ke default priority-calculation ko override karne ke liye:

fetchpriority examples
<!-- LCP image ko high priority — jaldi discover + jaldi fetch ho -->
<img src="/hero.webp" fetchpriority="high">

<!-- Below-the-fold thumbnail ko low priority — bandwidth LCP ko milne do -->
<img src="/thumbnail.webp" fetchpriority="low">

Root mechanism: browser resources ko do broad phases mein load karta hai — pehla phase render-critical (HTML, CSS, fonts, viewport images) ke liye reserved hota hai. Bina hint ke, images generally is high-priority window mein nahi aatin. fetchpriority="high" explicitly image ko us pehle phase mein daal deta hai.

⚠️ Common mistake: har cheez preload karna

Preload ek zero-sum resource hai — network bandwidth aur HTTP/2-3 connection slots limited hain. Agar tum apni har CSS, font, script, aur image ko preload kar doge, to browser ke paas "critical vs non-critical" ka koi signal nahi bachta — sab kuch high priority ban jaata hai, jo effectively koi priority nahi hota. Isse asli LCP-critical resource (jaise hero image) ko utna bandwidth share nahi milta jitna milna chahiye tha, kyunki wo 10 doosre "preloaded" resources ke saath compete kar raha hota hai. Result: LCP better hone ki jagah worse ho jaata hai. Rule of thumb: preload ka use tab karo jab resource (a) critical ho AND (b) HTML parser ko late discover ho — dono conditions saath.

🧠 Senior Dev Note: frameworks ye automatically kar dete hain

Next.js ka next/font build-time pe fonts ko self-host kar leta hai aur automatically matching <link rel="preload"> tags inject karta hai — tumhe manually crossorigin ya as="font" yaad rakhne ki zaroorat nahi. Isi tarah next/image jab priority prop set karte ho (LCP image ke liye), to wo automatically fetchpriority="high" aur ek <link rel="preload" as="image"> dono generate kar deta hai, page's <head> mein. Ye framework-level automation exactly wahi mistakes prevent karta hai jo humne upar discuss kiye — missing as, missing crossorigin, over-preloading. Lekin samajhna zaroori hai ki andar kya ho raha hai, kyunki agar tum manually custom fonts/images use kar rahe ho (jo framework ke optimized components se bypass karte hain), to ye hints tumhe khud lagane padenge.

Key Takeaways

  • dns-prefetch = sirf DNS resolve, cheapest hint, bahut saare non-critical third-party origins ke liye.
  • preconnect = DNS + TCP + TLS, connection ready but no fetch — 2-4 critical cross-origin domains tak limit rakho.
  • preload = poora fetch abhi, high priority — sirf late-discovered critical resources ke liye, as attribute mandatory hai warna double-download hota hai.
  • Fonts ke saath preload/preconnect dono jagah crossorigin attribute chahiye — font requests spec-mandated CORS mode mein jaate hain, same-origin ho tab bhi.
  • prefetch = future navigation ke liye speculative fetch, lowest priority, sirf high-confidence predictions pe use karo, aur Save-Data respect karo.
  • modulepreload = ES module fetch + parse + import-graph discovery, plain preload se zyada powerful for JS modules.
  • Overuse of preload bandwidth contention create karta hai aur LCP ko hurt kar sakta hai — sab kuch "high priority" ban jaana matlab kuch bhi priority nahi.
  • Next.js jaise frameworks (next/font, next/image) ye hints automatically emit karte hain, but underlying mechanism samajhna debugging aur custom cases ke liye zaroori hai.

🎯 Interview Questions

  • preconnect aur dns-prefetch mein kya farak hai, aur dono ek saath kyun likhe jaate hain (fallback pattern)?
    Hint: preconnect DNS+TCP+TLS karta hai but sirf ~6 concurrent hi effective hain (browser limit); dns-prefetch sirf DNS karta hai, wider browser support, unlimited practically — dono saath likhna ek graceful degradation pattern hai.
  • as attribute preload mein kyun mandatory hai — agar chhod diya to internally kya hota hai?
    Hint: resource type-specific priority queue aur CORS-mode match nahi ho paata, so browser dusri baar fetch karta hai jab actual consumer usse maangta hai.
  • Font preload mein crossorigin attribute kyun chahiye, chahe font same-origin ho?
    Hint: font fetch spec ke hisaab se hamesha anonymous CORS mode use karta hai, isliye preload request bhi usi mode mein hona chahiye taaki dono match karke resource reuse ho.
  • preload aur prefetch mein priority aur use-case ka farak batao.
    Hint: preload = current page, high priority, critical; prefetch = future navigation, lowest/idle priority, speculative.
  • Bahut zyada preload use karne se LCP kaise worse ho sakta hai?
    Hint: bandwidth ek fixed resource hai; agar sab kuch high-priority preload ho jaaye, to actual LCP resource ko utna bandwidth share nahi milta — priority signal dilute ho jaata hai.
  • modulepreload plain preload as="script" se better kyun hai JS modules ke liye?
    Hint: modulepreload sirf fetch nahi karta, parse/compile bhi karta hai aur static import graph ko recursively discover karta hai — plain preload sirf bytes download karta hai.
