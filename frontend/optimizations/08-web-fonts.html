Optimize Web Fonts

Web fonts free mein achha typography deti hain, lekin galat use karo to ye render-blocking resource ban jaati hain aur FOIT/layout-shift jaisi problems create karti hain. Font Discovery — Browser Ko Pata Kab Chalta Hai Ki Font Chahiye

Yaha ek subtle cheez samajhna zaroori hai: browser koi bhi web font tabhi download karta hai jab use confirm ho jaaye ki wo font actually kisi visible text ke liye chahiye. Ye confirmation Render Tree ban jaane ke baad milta hai — yaani CSSOM complete ho, DOM ke saath match ho, aur pata chale ki kaunsa element kaunsa font-family use kar raha hai. Isiliye font requests hamesha late shuru hote hain — CSS parse hone ke baad, tab jaake font fetch start hota hai.

Ye "late discovery" hi root cause hai FOIT/FOUT problem ka. Do tarike hain isko jaldi trigger karne ke:

  • Resource hint preload — <link rel="preload" as="font"> se browser ko bola jaata hai ki ye font zaroor chahiye hoga, abhi hi fetch shuru kar do (detail neeche).
  • Inline @font-face in <head> — agar @font-face rule external stylesheet ke bajaye directly HTML ke <head> mein inline ho, to browser ko external CSS file wait nahi karna padta us rule ko parse karne ke liye. Lekin font download phir bhi tab tak nahi hoga jab tak baaki saare render-blocking resources (jaise external CSS) resolve nahi ho jaate — kyunki render tree tabhi complete banta hai.
📌 Root-level: kyun itni der lagti hai

Timeline yaad rakho — HTML parse → DOM banta hai, CSS parse → CSSOM banta hai, DOM + CSSOM combine hoke Render Tree banta hai, Render Tree se pata chalta hai kaunsa text kis font mein render hoga, tab jaake font ka actual network request fire hota hai. Yani font request, critical rendering path ke bhi baad ka event hai — image ya script se bhi late. Yahi wajah hai ki fonts preload karna itna high-impact optimization hai.

FOIT vs FOUT — Do Failure Modes

Jab tak web font load ho raha hai, browser ko decide karna padta hai text ka kya karna hai. Do classic patterns hain:

  • FOIT (Flash of Invisible Text) — browser text ko completely invisible rakhta hai jab tak font load nahi ho jaata. User ko lagta hai page "blank" hai ya content missing hai — ye bahut bura UX hai, especially slow networks pe (LCP badly affect hota hai).
  • FOUT (Flash of Unstyled Text) — browser turant fallback system font mein text dikha deta hai, aur jab web font ready ho jaata hai to text "swap" ho jaata hai us font mein. Content turant visible hota hai (accha for LCP/readability) lekin agar fallback font ke metrics (width, line-height) web font se bahut different hain, to swap hone pe layout shift (CLS) ho sakta hai.

Dono hi trade-offs hain — invisible text vs jump/shift. font-display property se hum decide karte hain ki konsa behavior chahiye, aur kitni der tak.

font-display — Timeline Control Karne Wali Property

font-display ek @font-face descriptor hai jo font-loading timeline ko teen phases mein todta hai:

  1. Block period — is window mein agar font load nahi hua, to text invisible rehta hai (FOIT). Font load hote hi turant use ho jaata hai.
  2. Swap period — is window mein agar font abhi bhi load nahi hua, browser fallback font se text render kar deta hai. Jab web font aayega, swap ho jaayega (FOUT).
  3. Failure period — is point ke baad agar font load nahi hua, browser use "failed" maan leta hai aur permanently fallback font hi use karta hai — even if font baad mein load ho jaaye.

Har value in teeno periods ki duration alag set karti hai:

ValueBlock periodSwap periodBehaviorKab use karein
auto (default) Browser-dependent Browser-dependent Mostly block jaisa hi treat hota hai — unpredictable, browser pe depend karta hai. Kabhi nahi explicitly — hamesha ek explicit value do.
block ~3s (Chromium/Firefox), unlimited (Safari) Infinite FOIT — text 3 second tak (ya zyada) invisible, phir web font se render. Icon fonts jahan fallback glyph bilkul galat dikhega (par ideally SVG use karo, icon font hi mat use karo).
swap ~0ms (negligible) Infinite FOUT — turant fallback text dikhta hai, jab bhi web font aaye swap ho jaata hai, chahe kitni bhi der lage. Body text / content-heavy pages jaha readability priority #1 hai.
fallback ~100ms (bahut chhota) ~3s Bahut chhota block, phir fallback dikhta hai; agar web font 3s ke andar aa jaaye to swap, warna permanently fallback hi rehta hai us session ke liye. Fast, reliable networks — jab tumhe pata hai font almost hamesha jaldi load hoga.
optional ~100ms 0ms (no swap period) Sabse "safe" — agar font 100ms ke andar cache/network se mil jaaye to use karo, warna is page-load ke liye fallback hi use hoga (koi swap nahi, koi layout shift nahi). Browser decide karta hai connection speed dekh ke ki font future visits ke liye download kare ya na kare. Jab layout stability (CLS) sabse zyada important ho, aur font ka visual difference "nice to have" ho, must-have nahi.
🧠 Senior Dev Note — sahi choice kaise karein

Zyada tar production apps ke liye swap safe default hai — content turant visible rehta hai. Lekin agar tumhara fallback font aur web font ke metrics (x-height, average character width) bahut alag hain, to swap ke time visible "jump" hoga jo CLS ko hurt karega. Us case mein size-adjust, ascent-override, descent-override jaise @font-face descriptors use karke fallback font ke metrics ko web font ke jitna close bana sakte ho — isse swap ka jump minimal ho jaata hai. Next.js ka next/font ye automatically karta hai (neeche detail mein).

woff2 — Ek Hi Format Kaafi Hai

Modern browsers (jo aaj production traffic ka almost 100% cover karte hain) sab WOFF2 support karte hain. WOFF2, WOFF ke comparison mein up to 30% chhota hota hai — better compression algorithm (Brotli-based) use karta hai. Matlab agar tum sirf modern browsers target kar rahe ho (jo aajkal default hai), to sirf woff2 file serve karna kaafi hai — TTF, EOT, ya original WOFF jaise legacy formats include karne ki zaroorat nahi, wo sirf extra bytes hain jo kabhi use hi nahi honge.

@font-face — swap + woff2 + subsetting
/* Custom font ke liye @font-face rule define kar rahe hain */
@font-face {
  /* font-family naam jo baad mein font-family: 'Inter' se reference hoga */
  font-family: 'Inter';

  /* sirf woff2 serve kar rahe hain — modern browsers ke liye kaafi hai,
     format('woff2') hint browser ko batata hai file ka format kya hai bina download kiye */
  src: url('/fonts/inter-latin-400.woff2') format('woff2');

  /* is weight variant ke liye sirf 400 (regular) match hoga */
  font-weight: 400;

  /* normal style — italic ke liye alag @font-face block chahiye hoga */
  font-style: normal;

  /* FOUT strategy: turant fallback text dikhao, web font aate hi swap kar do,
     chahe kitni bhi der lage — content kabhi invisible nahi hota */
  font-display: swap;

  /* SUBSETTING: browser ko batate hain ki is font file mein sirf basic Latin
     characters (U+0000 se U+00FF tak) hain — agar page pe koi Cyrillic ya Devanagari
     character aata hai, browser is font ko use hi nahi karega us character ke liye.
     Isse font file bhi chhoti banti hai (subset karke) aur browser ko clarity milti hai
     ki ye file kis range ke liye responsible hai */
  unicode-range: U+0000-00FF, U+0131, U+0152-0153;
}

Self-Hosting vs Google Fonts

Fonts serve karne ke do broad approach hain — third-party service (jaise Google Fonts) se load karna, ya apne server/CDN se serve karna (self-hosting). Dono ke trade-offs hain:

AspectGoogle Fonts (third-party)Self-hosting
Extra connection Alag origin (fonts.gstatic.com) — matlab ek extra DNS lookup + TCP + TLS handshake, jab tak preconnect nahi use karte. Same origin ya same CDN jo already connected hai — koi extra connection setup nahi.
Caching control Google ke cache headers pe depend karte ho, apna control limited hai. Apne cache headers, CDN, aur invalidation strategy fully control kar sakte ho.
Privacy User ka IP address Google ke server ko jaata hai har page load pe — kai regions (EU/GDPR) mein isse compliance issue ban sakta hai (famous German court ruling isi wajah se). Koi third-party ko data nahi jaata — full privacy control apne haath mein.
Convenience Ek <link> tag daalo, sab weights/subsets automatically milte hain, updates bhi automatic. Khud subsetting, hosting, versioning manage karni padti hai — zyada setup, zyada control.
Performance (typical) Extra round-trip ki wajah se generally slower, especially agar preconnect miss ho. Generally fast — no extra DNS/connection overhead, especially jab HTTP/2+ aur CDN edge caching use ho.

Agar Google Fonts hi use karna hai (kisi constraint ki wajah se), to kam se kam connection overhead minimize karo:

Google Fonts ke liye preconnect
<!-- fonts.googleapis.com pe CSS file hoti hai jisme @font-face rules hote hain -->
<link rel="preconnect" href="https://fonts.googleapis.com">

<!-- fonts.gstatic.com pe actual woff2 font files hoti hain — ye alag origin hai
     isliye isko bhi separately preconnect karna padta hai. crossorigin zaroori hai
     kyunki font files CORS-protected resource maani jaati hain -->
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>

Google Fonts subsetting bhi support karta hai query parameter se, jaise ?subset=latin, jo unwanted glyphs strip kar deta hai. Self-hosting mein ye kaam tools jaise glyphhanger ya subfont se manually karna padta hai (build step mein).

Subsetting — Sirf Wahi Characters Jo Chahiye

Ek full font file mein hundreds ya thousands of glyphs hote hain — Latin, Cyrillic, Greek, symbols, sab. Zyada tar sites ko sirf ek chhota subset chahiye hota hai (jaise sirf basic Latin + kuch punctuation). Subsetting ka matlab hai font file se sirf zaroori glyphs rakhna aur baaki hata dena — isse file size drastically reduce hota hai (aksar 70-90% tak, especially agar original font mein CJK ya multi-script support ho).

CSS mein unicode-range descriptor se browser ko batate hain ki ye particular @font-face block kis character range ke liye hai. Browser sirf tab us font file ko download karega jab page pe us range ka koi actual character present ho — matlab agar tumhare pas Latin aur Devanagari dono ke alag subset files hain, aur page pe sirf Latin text hai, to Devanagari wali file kabhi download hi nahi hogi.

Multiple subsets — unicode-range se selective loading
/* Latin subset — sirf basic English/European characters */
@font-face {
  font-family: 'Inter';
  src: url('/fonts/inter-latin.woff2') format('woff2');
  /* U+0000-00FF = basic Latin + Latin-1 supplement range */
  unicode-range: U+0000-00FF;
  font-display: swap;
}

/* Devanagari subset — Hindi text ke liye, alag file, alag range */
@font-face {
  font-family: 'Inter';
  src: url('/fonts/inter-devanagari.woff2') format('woff2');
  /* U+0900-097F = Devanagari Unicode block */
  unicode-range: U+0900-097F;
  font-display: swap;
}

/* Dono blocks same font-family name use karte hain — browser khud decide karega
   kaunsa file download karni hai based on jo characters page pe actually mile */
💡 Practical tip

Agar tumhara app bilingual hai (jaise MAD app Hinglish content dikhata hai), to Latin aur Devanagari ko alag subset files mein todo. English-only user kabhi Devanagari font file download hi nahi karega — automatic savings, koi extra JS logic ki zaroorat nahi, pura kaam browser khud handle karta hai unicode-range ke through.

Variable Fonts — Ek File, Multiple Weights

Traditionally, agar tumhe Regular (400), Medium (500), Semibold (600), aur Bold (700) chahiye, to 4 alag font files download karni padti thi — har weight ek separate file. Variable fonts is problem ko solve karte hain: ek hi font file mein multiple weights (aur kabhi kabhi width, slant bhi) ke "axes" encode hote hain, aur CSS font-weight se koi bhi value us range ke andar pick kar sakte ho — 400 ho, 450 ho, 587 ho, sab ek hi file se render hoga.

Trade-off ye hai ki ek variable font file individual static file se thodi badi hoti hai — lekin agar tumhe 3-4+ weights chahiye, to ek variable font file total mein un sab static files se chhoti padti hai (kyunki glyph outlines share hote hain, sirf interpolation data alag hota hai). Plus, sirf ek hi HTTP request lagta hai instead of 3-4.

@font-face — variable font with weight range
/* Variable font declare kar rahe hain — ek hi file, weight range specify karenge */
@font-face {
  font-family: 'Inter Variable';

  /* woff2-variations format hint modern browsers ko batata hai ki ye variable
     font hai — 'wght' axis (weight) support karega */
  src: url('/fonts/inter-var.woff2') format('woff2-variations');

  /* single number ke bajaye range diya — 100 (Thin) se 900 (Black) tak koi bhi
     weight is ek file se render ho sakta hai, browser interpolate karta hai */
  font-weight: 100 900;

  font-style: normal;
  font-display: swap;
  unicode-range: U+0000-00FF;
}

/* Ab CSS mein kahin bhi koi bhi weight use karo, sab ek hi file se aayega */
.heading { font-family: 'Inter Variable'; font-weight: 650; } /* koi extra request nahi */
.body-text { font-family: 'Inter Variable'; font-weight: 400; } /* same file, alag weight */

Preloading Critical Font — Discovery Delay Ko Skip Karna

Jaisa upar discuss kiya, browser font ko tab tak fetch nahi karta jab tak render tree confirm nahi kar deta ki wo font chahiye. Agar tumhara primary heading ya body font hero content ke liye critical hai, to <link rel="preload"> se browser ko is delay ko bypass karne ka signal de sakte ho — ye request bahut early (HTML parsing ke dauraan hi) fire ho jaata hai, discovery ka wait nahi karna padta.

index.html — critical font preload karna
<head>
  <!-- as="font" browser ko batata hai ye resource kis type ka hai, taaki
       priority aur request headers sahi set ho (Accept header font ke liye) -->
  <link
    rel="preload"
    href="/fonts/inter-var.woff2"
    as="font"
    type="font/woff2"
    crossorigin
  >
</head>
⚠️ Classic Gotcha — crossorigin same-origin fonts ke liye bhi chahiye

Fonts spec ke according, font files hamesha anonymous-mode CORS request ke through fetch hote hain — chahe wo file same-origin ho ya third-party. Agar <link rel="preload" as="font"> pe crossorigin attribute missing hai, browser preload request ko ek "credentialed" fetch samjhega jabki actual @font-face request "anonymous" mode mein jaayega — ye do requests browser ke liye do alag resources maane jaate hain (credentials mode mismatch), matlab preload cache miss ho jaayega aur font silently dobara download hoga. Koi console error bhi nahi aata — bas preload ka fayda zero ho jaata hai. Isliye crossorigin daalna hamesha mandatory hai font preload ke liye, same-origin case mein bhi.

Senior Dev Note — next/font Ye Sab Automatically Karta Hai

🧠 next/font internals

Agar tum Next.js use kar rahe ho, next/font (jaise next/font/google ya next/font/local) upar diye sab optimizations build-time pe automatically apply karta hai:

  • Self-hosting — Google Fonts use karne pe bhi, build ke time font files download karke apne .next/static output mein self-host kar deta hai. Runtime pe koi third-party request nahi jaata — privacy issue (Google ko IP jaana) bhi solve, aur extra connection bhi avoid ho jaati hai.
  • Automatic subsetting — sirf specify kiye gaye subsets (jaise ['latin']) ke glyphs include karta hai.
  • Auto preload injection — jo page/layout us font ko use kar raha hai, uske liye khud <link rel="preload"> tag inject kar deta hai (crossorigin sahit) — developer ko manually likhna hi nahi padta.
  • Layout shift avoidance via size-adjust — fallback font ke metrics ko (size-adjust, ascent-override, descent-override, line-gap-override descriptors ke through) web font ke jitna match karta hai, taaki font-display: swap ke time visible layout jump minimal ho — CLS score improve hota hai without manual tuning.

Yani next/font is poore chapter ka "just use this" answer hai agar Next.js stack use kar rahe ho — lekin interview mein andar kya ho raha hai ye samajhna hi asli signal hai ki tum root-level developer ho, na ki sirf "next/font use karo" bol dena.

Key Takeaways

  • Browser font ko sirf render tree complete hone ke baad discover karta hai — isliye fonts naturally "late" load hote hain, preload isi delay ko bypass karta hai.
  • FOIT (invisible text) aur FOUT (fallback → swap) do trade-offs hain; font-display in ke beech control deta hai via block/swap/failure period timing.
  • font-display: swap zyada tar production sites ke liye safe default hai; optional jab CLS priority #1 ho.
  • Sirf woff2 serve karo modern browsers ke liye — 30% chhota WOFF se, legacy formats ki zaroorat nahi.
  • Self-hosting generally third-party (Google Fonts) se fast hota hai — extra DNS/connection overhead nahi hota, aur privacy bhi better rehti hai.
  • unicode-range subsetting se browser sirf wahi glyph file download karta hai jo page pe actually use ho rahi hai.
  • Variable fonts multiple static weight files ko ek file mein consolidate karte hain — kam requests, often kam total bytes.
  • crossorigin attribute font preload ke liye hamesha zaroori hai, same-origin fonts ke liye bhi — warna preload silently waste ho jaata hai.
  • Next.js ka next/font self-hosting + subsetting + preload + layout-shift fix sab automatically handle karta hai.

🎯 Interview Questions

  • Q: Browser web font ka request kab fire karta hai, aur ye late kyun hota hai?
    Hint: Render tree complete hone ke baad hi — DOM + CSSOM combine hoke pata chalta hai kaunsa text kis font mein render hoga, tabhi actual font fetch trigger hota hai.
  • Q: font-display: swap vs optional — kab kaunsa use karoge?
    Hint: swap = content turant visible priority (readability), lekin layout shift risk; optional = CLS priority, font "nice to have" treat hota hai, no shift.
  • Q: unicode-range descriptor kaise file size aur network requests dono optimize karta hai?
    Hint: Browser sirf wahi subset file download karta hai jiske range mein page ke actual characters match karte hain — baaki subsets fetch hi nahi hote.
  • Q: Font preload pe crossorigin attribute kyun zaroori hai, even same-origin ke liye?
    Hint: Fonts hamesha anonymous CORS mode mein fetch hote hain spec ke hisaab se; attribute missing hone se preload aur actual fetch alag credential-mode requests ban jaate hain, cache match fail, font dobara download hota hai silently.
  • Q: Variable fonts kab better hote hain static weight files se, aur kab nahi?
    Hint: Better jab 3+ weights chahiye ho (total bytes kam, requests kam); agar sirf ek hi weight chahiye to ek single static file chhoti ho sakti hai variable font se.
  • Q: next/font internally CLS kaise reduce karta hai without changing font-display value?
    Hint: Fallback font ke metrics (size-adjust, ascent/descent-override) ko web font ke metrics se match karke swap ke time visible jump minimize karta hai — font-display value change nahi karta, sirf fallback ko "web font jaisa dikhne wala" bana deta hai.
