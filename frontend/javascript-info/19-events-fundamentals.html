Events Fundamentals

Browser ka har interaction — click, keypress, scroll, form submit — ek "event" hai. Ye chapter events ke root-level mechanics cover karta hai: handler attach karne ke teen tareeke, DOM tree mein event kaise travel karta hai (capture → target → bubble — full W3C 3-phase model), event delegation (ek sabse powerful real-world pattern jo har senior dev ko pata hona chahiye), preventDefault vs stopPropagation ka classic confusion, aur apne khud ke custom events banake dispatch karna.

Event handler model — on-property vs addEventListener

Ek event handler attach karne ke teen tareeke hain, lekin production code mein practically do hi matter karte hain. Root difference ye hai ki DOM element ke andar internally kitne "slots" hote hain ek particular event type ke liye.

onclick jaisa on-property ek single property slot hai — element ke object pe literally ek property hai jiska naam onclick hai. Agar tum ise do baar assign karo, to dusri assignment pehli ko overwrite kar degi, kyunki ye ek normal object property assignment hai (elem.onclick = fn), koi list nahi. addEventListener internally ek alag listener list maintain karta hai per event-type — isliye multiple independent handlers same event ke liye register ho sakte hain, bina ek doosre ko overwrite kiye.

on-property: sirf ek handler, overwrite hota hai
const elem = document.querySelector('#btn'); // button element pakdo DOM se

elem.onclick = function() {          // pehla handler assign kiya onclick property pe
  alert('Handler 1');              // ye pehle chalta tha
};

elem.onclick = function() {          // dusra assignment — SAME property slot
  alert('Handler 2');              // ab sirf ye chalega
};
// click karne pe sirf "Handler 2" alert aayega — Handler 1 poora gaya, overwrite ho gaya
addEventListener: multiple independent handlers
function handler1() {              // named function — isliye baad mein remove bhi kar sakte hain
  alert('Handler 1');              // ye chalega
}

function handler2() {              // dusra alag function
  alert('Handler 2');              // ye bhi chalega
}

elem.addEventListener("click", handler1);  // listener list mein handler1 push hua
elem.addEventListener("click", handler2);  // listener list mein handler2 bhi push hua
// click karne pe DONO chalte hain, registration order mein — "Handler 1" phir "Handler 2"

elem.removeEventListener("click", handler1); // SAME function reference chahiye remove karne ke liye
// anonymous function pass kiya tha to hata nahi sakte — reference kho jaata hai
⚠️ removeEventListener ka gotcha

removeEventListener ko wahi function reference chahiye jo addEventListener mein pass kiya tha. Agar tumne inline anonymous arrow function diya (elem.addEventListener("click", () => {...})), to us reference ko kabhi remove nahi kar sakte — har baar naya function object banta hai. Isliye jab remove karna ho, to function ko ek variable mein store karo, phir dono jagah wahi reference use karo.

Event object — browser jo data deta hai

Jab bhi koi event fire hota hai, browser ek event object banata hai jisme us event ke baare mein sab detail hoti hai — ye automatically handler ke pehle argument ke roop mein pass hota hai.

Event object ke common properties
elem.onclick = function(event) {       // browser event object handler ko pass karta hai
  alert(event.type);              // "click" — event ka naam
  alert(event.currentTarget);     // jis element pe handler registered hai (yahaan elem)
  alert(event.clientX + ":" + event.clientY); // viewport-relative cursor coordinates
};

Object bhi handler ban sakta hai — agar us object ke andar handleEvent method ho, to addEventListener events pe wahi method call karega, event ko pehle argument ke roop mein pass karke. Ye tab useful hai jab handler logic ko ek class ke andar encapsulate karna ho.

handleEvent — object as handler
let obj = {
  handleEvent(event) {              // addEventListener automatically ise call karega
    alert(event.type + " at " + event.currentTarget); // event type + target dikhaya
  }
};

elem.addEventListener('click', obj);  // function nahi, POORA OBJECT diya — internally obj.handleEvent call hoga

Bubbling + Capturing — full 3-phase model

Ye is chapter ka sabse important root-level concept hai. Jab ek DOM element pe koi event (jaise click) hota hai, wo event akela us element tak limited nahi rehta — poore DOM tree mein ek defined path travel karta hai, jise W3C DOM Events spec 3 phases mein define karta hai:

  1. Capturing phase — event window/document se shuru hoke, tree ke top se target ki taraf neeche travel karta hai, har ancestor ko touch karte hue.
  2. Target phase — event apne actual target element pe pahunchta hai, wahaan handlers chalte hain.
  3. Bubbling phase — event target se wapas upar document tak bubble karta hai, phir se har ancestor ko touch karte hue, is baar reverse order mein.

Default behavior mein addEventListener se register kiye handlers bubbling phase mein chalte hain — isiliye zyada tar tutorials sirf "bubbling" ka zikar karte hain. Lekin capturing phase hamesha pehle hoti hai, chahe koi capturing handler ho ya na ho — browser internally wo phase silently traverse karta hai.

Nested DOM pe pura 3-phase trace
<form id="form">FORM
  <div id="div">DIV
    <p id="p">P</p>
  </div>
</form>

<script>
  for (let elem of document.querySelectorAll('*')) {   // HAR element pe do handlers lagao
    elem.addEventListener("click", e => console.log(`Capturing: ${elem.tagName}`), true);
    // 3rd argument "true" = ye handler CAPTURING phase mein chalega (top-down)
    elem.addEventListener("click", e => console.log(`Bubbling: ${elem.tagName}`));
    // 3rd argument default (false) = ye handler BUBBLING phase mein chalega (bottom-up)
  }
</script>

// <p> pe click karne ka poora console output, EXACT order:
// Capturing: HTML  → top se shuru
// Capturing: BODY
// Capturing: FORM
// Capturing: DIV
// Capturing: P     → target tak neeche pahunche (capturing phase khatam)
// Bubbling: P      → target phase pe dono ready, bubbling handler pehle chalega P pe hi
// Bubbling: DIV    → ab wapas upar bubble karna shuru
// Bubbling: FORM
// Bubbling: BODY
// Bubbling: HTML   → document tak wapas pahunch gaya
🧠 Senior Dev Note: 3rd argument {capture: true} kyun matter karta hai

addEventListener(type, handler, options) ka teesra argument boolean (true/false) ya object ({capture: true}) ho sakta hai. Ye internally browser ke event dispatch algorithm ko batata hai ki handler ko konsi phase ke listener-list mein register karna hai — capturing list ya bubbling list. Practical use-case: jab tumhe ek parent ka handler child ke handler se PEHLE chalana ho — normal bubbling mein ye ulta hota hai (child pehle chalta hai, phir parent). Ek real scenario: modal/dropdown ke "outside click" detection mein, ek document-level capturing listener use karke tum guarantee kar sakte ho ki tumhara check sabse pehle chale, kisi bhi child ke stopPropagation() call karne se PEHLE — kyunki capturing phase bubbling se pehle hoti hai.

event.target vs this (currentTarget)

Ye do properties bahut confuse karti hain, lekin difference simple hai: event.target wo innermost element hai jispe user ne actually click kiya (poori propagation ke dauran ye fixed/unchanged rehta hai), jabki this (event.currentTarget ke barabar) wo element hai jispe abhi handler chal raha hai — ye har phase mein badalta rehta hai jaise event travel karta hai.

target (fixed) vs currentTarget (changing)
form.onclick = function(event) {   // ye handler FORM pe registered hai, but bubbling se div/p ke click bhi yahaan aayenge
  event.target.style.backgroundColor = 'yellow';
  // target = jispe user ne asal mein click kiya (p ya div ho sakta hai, form nahi)

  console.log("target = " + event.target.tagName);       // e.g. "P" — jaha click hua
  console.log("this = " + this.tagName);              // "FORM" — jaha handler registered hai, hamesha fixed
};

stopPropagation vs stopImmediatePropagation

event.stopPropagation() event ko aage travel karne se rok deta hai (chahe capturing ho ya bubbling), lekin current element pe agar aur handlers registered hain (multiple addEventListener calls), wo sab phir bhi chalte hain. event.stopImmediatePropagation() dono karta hai — propagation bhi rokta hai aur current element ke baaki bache handlers ko bhi skip kar deta hai.

stopPropagation — ek button ka click body tak nahi jaayega
document.body.onclick = () => alert("bubbling yahaan tak nahi pahunchna chahiye");

button.onclick = function(event) {
  event.stopPropagation();    // upward bubbling yahi rok do — body.onclick kabhi nahi chalega
  alert("button click");
};
⚠️ preventDefault aur stopPropagation DO ALAG cheezein hain

Ye sabse common confusion hai junior devs mein. preventDefault() browser ke default action ko rokta hai (jaise link navigate karna, form submit hona, checkbox toggle hona) — isse event propagation pe koi effect nahi padta, event ab bhi upar bubble karega. stopPropagation() event ko DOM tree mein aage travel karne se rokta hai (ancestors ke handlers nahi chalenge) — isse browser ka default action pe koi effect nahi padta, agar preventDefault call nahi hua to link phir bhi navigate karega. Dono completely unrelated mechanisms hain jo sirf naam se related lagte hain — ek event ko rok sakte ho dono se independently, ya dono ek saath bhi call kar sakte ho.

stopPropagation ko avoid karo jab possible ho. Real-world architectures mein events ko intentionally poore document tak bubble hone diya jaata hai taaki outer analytics handlers, delegation patterns, ya global click-outside detectors kaam kar sakein. stopPropagation() is chain ko silently break kar deta hai — kal koi aur developer ek outer delegated handler add karega aur wonder karega ki wo kyun fire nahi ho raha.

Event delegation — deep dive

Delegation, bubbling ka sabse powerful practical application hai. Core insight: agar child elements ke events apne aap parent tak bubble ho jaate hain, to humein har child pe alag handler lagane ki zaroorat nahi — sirf ek handler parent pe lagao, aur event.target check karke pata karo ki asal mein kaunse child pe click hua.

🧠 Senior Dev Note: "1000 buttons, 1 listener" — real perf argument

Socho ek table hai jisme 1000 rows hain, har row mein ek "Delete" button hai. Naive approach: 1000 alag addEventListener calls, matlab browser ko 1000 separate listener-list entries maintain karni padengi — memory overhead, aur agar rows dynamically add/remove hoti rahein (infinite scroll, live data), to har naye row ke liye phir se listener attach karna padega aur purane rows ke liye removeEventListener call karke cleanup bhi karna padega (warna memory leak). Delegation approach: sirf ek listener table pe — chahe 10 rows ho ya 100,000, listener count wahi rehta hai. Naye rows automatically kaam karte hain without any extra code, kyunki unka click bubble hoke table tak pahunch jaata hai. Ye exactly wo pattern hai jo React jaisi libraries internally use karti hain (root container pe ek hi native listener, synthetic event system uske upar built hota hai).

Delegated table row action handler — real pattern
<table id="users-table">
  <tr data-id="101">
    <td>Sharad</td>
    <td><button data-action="edit">Edit</button>
        <button data-action="delete">Delete</button></td>
  </tr>
  <!-- ... 999 aur rows, bilkul isi structure ke, koi individual handler nahi -->
</table>

<script>
  const table = document.getElementById('users-table'); // parent, jispe SIRF ek listener lagega

  table.addEventListener('click', function(event) {
    const button = event.target.closest('button[data-action]');
    // closest(): agar click kisi button ke ANDAR ke icon/span pe hua ho, phir bhi
    // nearest matching ancestor button dhoondh leta hai — sirf exact target check karne se zyada robust

    if (!button) return;       // click kisi button pe hua hi nahi (row/td pe hua hoga) — ignore karo

    if (!table.contains(button)) return; // safety check: agar delegation kisi outer document-level listener se ho raha ho

    const row = button.closest('tr');       // button se uska parent <tr> nikalo
    const userId = row.dataset.id;          // data-id attribute se row ki identity nikali
    const action = button.dataset.action;    // data-action se pata chala "edit" ya "delete" tha

    if (action === 'delete') {
      deleteUser(userId);          // API call ya local state update — sirf ek listener se poore table ka delete kaam
      row.remove();              // row ko DOM se hata do — koi listener cleanup ki zaroorat NAHI, kyunki row pe koi listener tha hi nahi
    } else if (action === 'edit') {
      openEditModal(userId);       // edit flow trigger karo, wahi userId use karke
    }
  });
</script>

Ye pattern rows ko dynamically add/remove karne ke saath bhi seamlessly kaam karta hai — koi naya row insert karo (server se data aane pe, infinite scroll mein, waghera), uske button pe koi handler attach karne ki zaroorat nahi, kyunki click automatically table tak bubble hoke us ek listener tak pahunch jaayega.

📌 Delegation ki limitations

Delegation sirf un events ke liye kaam karta hai jo bubble karte hain — kuch events (jaise focus, blur, purane mouseenter/ mouseleave) bubble nahi karte by default. Aur agar koi low-level child handler galti se event.stopPropagation() call kar de, to wo event tumhare delegated parent handler tak kabhi nahi pahunchega — isliye delegation-heavy codebases mein stopPropagation() ka use bahut soch-samajh ke karna chahiye.

preventDefault + browser default actions

Bahut se events browser ke apne "default actions" trigger karte hain jo humare JS handler ke independent hote hain — link click pe navigate karna, form submit pe page reload/network request bhejna, checkbox click pe check-state toggle hona, right-click pe context menu khulna. event.preventDefault() is default action ko cancel kar deta hai — lekin event ka normal propagation (bubbling) affect nahi hota, jaisa upar discuss kiya.

Link ka default navigation rokna + context menu control
link.onclick = function(event) {
  event.preventDefault();         // browser ko wahaan navigate karne se roka
  alert(link.getAttribute('href')); // custom logic — SPA router ko URL handover, waghera
};

elem.oncontextmenu = function(event) {
  event.preventDefault();         // native browser right-click menu ko yahaan rok diya
  alert("Custom menu for this element");  // apna custom context menu dikha do
};

document.oncontextmenu = function(event) {
  if (event.defaultPrevented) return; // agar element-level handler ne already prevent kar diya, dobara kuch mat karo
  event.preventDefault();         // document-level fallback custom menu
  alert("Document-wide custom menu");
};
// event.defaultPrevented true hota hai agar KAHIN bhi handler ne preventDefault() call kiya —
// isse stopPropagation() bina bhi "already handled" ka signal pass ho jaata hai bubbling ke through

on<event> handlers mein return false bhi preventDefault jaisa kaam karta hai (sirf inline/property-based handlers ke liye — addEventListener mein ye kaam nahi karta, wahaan sirf event.preventDefault() hi chalega).

Ek performance-related option bhi hai — {passive: true}, jo browser ko batata hai ki handler kabhi preventDefault() call nahi karega. Ye especially touchmove/wheel jaisi high-frequency scroll events ke liye important hai — browser handler ka wait kiye bina turant scroll render kar sakta hai, kyunki use pata hai default action cancel nahi hoga.

passive: true — scroll performance hint
elem.addEventListener('touchmove', function(event) {
  console.log('touch move detected'); // sirf analytics/logging, preventDefault kabhi call nahi hoga
}, { passive: true });
// browser ab main thread ka wait kiye bina scroll turant render kar sakta hai — jank kam

Custom events — CustomEvent aur dispatchEvent

Sirf browser ke built-in events (click, keydown, etc.) tak limited nahi rehna — apne khud ke events banake DOM elements pe fire kar sakte ho. Ye especially useful hai jab tum ek reusable component (jaise custom widget) bana rahe ho jise apne consumers ko events ke through "notify" karna hai.

CustomEvent + detail data pass karna
const widget = document.querySelector('#my-widget'); // jispe custom event dispatch karna hai

widget.addEventListener('item-selected', function(event) {
  // ZAROORI: custom event types pe addEventListener use karo — on<event> property
  // (jaise widget.onitemselected) sirf browser ke BUILT-IN events ke liye kaam karta hai
  console.log('Selected:', event.detail.itemId); // detail = custom data ka standard container
});

function selectItem(itemId) {
  const event = new CustomEvent('item-selected', {
    detail: { itemId },       // detail: apna arbitrary custom data yahaan daalo (koi bhi object)
    bubbles: true,            // bubbles: true — ye event upar tak bubble karega, delegation possible
    cancelable: true          // cancelable: true — listener preventDefault() call karke ise cancel kar sakta hai
  });

  const notCancelled = widget.dispatchEvent(event);
  // dispatchEvent SYNCHRONOUSLY sab matching handlers ko call karta hai, phir returns
  // return value false hoga AGAR kisi handler ne preventDefault() call kiya, warna true

  if (notCancelled) {
    console.log('Selection proceeded'); // koi handler ne cancel nahi kiya, aage badho
  }
}
Bubbling option ka effect — plain Event bnam bubbling Event
document.addEventListener("hello", function(event) {
  alert("Hello from " + event.target.tagName); // document-level listener, delegation jaisa hi
});

const evt = new Event("hello", { bubbles: true }); // bubbles: true bina ye sirf elem tak hi limited rehta, document tak nahi pahunchta
elem.dispatchEvent(evt);  // elem se fire kiya, bubbling ki wajah se document tak pahunch jaayega
📌 Nested dispatch — event flow synchronous hai

Normal browser-generated events ek queue mein process hote hain, lekin agar tum khud ek event ke andar se doosra event dispatchEvent karo, to wo naya event turant, synchronously poora process hota hai — outer handler ka execution beech mein pause ho jaata hai, nested event ke sab handlers chalte hain, phir outer handler resume hota hai. Agar tumhe asynchronous chahiye (queue mein defer karna), to dispatchEvent ko setTimeout mein wrap karo.

Key Takeaways

  • on-property = ek slot, overwrite hota hai; addEventListener = list, multiple independent handlers.
  • Har event 3 phases mein travel karta hai: capturing (top→target), target, bubbling (target→top). Default handlers bubbling phase mein chalte hain; capturing ke liye 3rd argument true/{capture:true} chahiye.
  • event.target fixed rehta hai (jahan click hua), this/event.currentTarget badalta hai (jahan handler chal raha hai).
  • stopPropagation() propagation rokta hai but same-element ke aur handlers chalte hain; stopImmediatePropagation() unhe bhi skip kar deta hai.
  • Event delegation: ek parent listener + event.target.closest() — memory efficient, dynamic elements ke liye auto-works, "N buttons, 1 listener" ka classic perf win.
  • preventDefault() aur stopPropagation() completely unrelated hain — ek default browser action rokta hai, doosra DOM traversal rokta hai.
  • CustomEvent + detail se apna data pass karke dispatchEvent() se fire karo — bubbles/cancelable options control karte hain propagation aur preventDefault-ability.
  • Custom event types pe hamesha addEventListener use karo — on<name> shortcut sirf built-in events ke liye reserved hai.

🎯 Interview Questions

  • Event propagation ke 3 phases explain karo. Default mein addEventListener kaunsi phase use karta hai?
    Hint: capturing (top→target) → target → bubbling (target→top); addEventListener default bubbling phase (3rd arg false/omitted).
  • event.target aur event.currentTarget mein kya farak hai?
    Hint: target = jahan actual click hua (fixed), currentTarget/this = jahan handler abhi execute ho raha hai (phase ke hisaab se changing).
  • Event delegation kya hai aur ye 1000 individual listeners se better kyun hai?
    Hint: ek parent listener + event.target check; memory/listener-count constant rehta hai chahe children kitne bhi ho, dynamically added elements bhi automatically kaam karte hain.
  • preventDefault() aur stopPropagation() mein kya farak hai — dono ko confuse kyun kiya jaata hai?
    Hint: preventDefault browser ke default action (navigation, submit) ko rokta hai; stopPropagation DOM traversal ko rokta hai — dono independent, ek doosre ko affect nahi karte.
  • stopPropagation() aur stopImmediatePropagation() mein kya farak hai?
    Hint: stopPropagation sirf aage travel rokta hai (same element ke baaki handlers chalte hain); stopImmediatePropagation same element ke remaining handlers ko bhi skip karta hai.
  • Delegation kab fail ho sakta hai — kaunse events bubble nahi karte, aur kya cheez delegation ko silently break kar sakti hai?
    Hint: focus/blur jaise events bubble nahi karte; kisi child handler ka stopPropagation() call karna event ko parent tak pahunchne se rok deta hai.
  • CustomEvent kaise dispatch karte ho aur data kaise pass karte ho? on-property se kyun listen nahi kar sakte?
    Hint: new CustomEvent(type, {detail, bubbles, cancelable}) + elem.dispatchEvent(); on<name> sirf spec-defined built-in events ke liye browser reserve karta hai, custom types ke liye addEventListener zaroori hai.
  • addEventListener ka teesra argument {capture: true} kab practically use karoge?
    Hint: jab parent ka handler child ke handler se pehle chalna chahiye — jaise outside-click detection jo kisi child ke stopPropagation() se pehle hi guaranteed run ho.
