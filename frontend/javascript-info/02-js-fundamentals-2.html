Operators & Math

JavaScript mein har operator ek precedence number ke saath define hota hai — ye number decide karta hai ki multiple operators ek expression mein kis order mein evaluate honge. Ye sirf trivia nahi hai — production bugs (especially string+number concatenation ke around) is precedence table ki misunderstanding se aate hain.

Basic arithmetic operators
let a = 5, b = 2;                  // do numbers declare kiye

console.log(a + b);              // 7 — addition
console.log(a - b);              // 3 — subtraction
console.log(a * b);              // 10 — multiplication
console.log(a / b);              // 2.5 — division (integer division nahi hoti, JS mein sab float hai)
console.log(a % b);              // 1 — remainder: 5 ko 2 se divide karne ke baad jo bacha
console.log(a ** b);             // 25 — exponentiation: 5 ka power 2 (5*5)
console.log(4 ** (1/2));       // 2 — fractional power = square root, ** sirf integers tak limited nahi

Binary + ka dual-personality — string concat vs addition

Root cause samajhna zaroori hai: + operator JS engine ke andar ek algorithm follow karta hai — "agar dono operands mein se koi ek bhi string hai, to dusre ko bhi string mein convert karo aur concatenate karo. Warna dono ko number bana ke add karo." Ye rule sirf + pe apply hota hai — -, *, / hamesha dono operands ko number mein convert karte hain, string hone ka koi special case nahi hai.

+ operator ka type coercion gotcha
console.log('1' + 2);              // "12" — ek operand string hai, so dusra bhi string ban gaya
console.log(2 + 2 + '1');          // "41" — left-to-right eval: pehle 2+2=4 (dono number), phir 4+'1'="41"
console.log('1' + 2 + 2);          // "122" — left-to-right: pehle '1'+2="12" (string ban gaya), phir "12"+2="122"
console.log(6 - '2');              // 4 — minus operator string-aware nahi, '2' number mein convert ho gaya
console.log('6' / '2');            // 3 — same, division bhi dono operand ko number bana deta hai
🧠 Senior Dev Note — unary + ka real use-case

Unary + (ek operand pe apply hone wala plus, jaise +"5") internally Number(...) hi call karta hai — bas syntax chhota hai. Production mein ye tab critical ban jaata hai jab HTML form inputs, prompt(), ya query params se values aati hain — wo hamesha strings hoti hain, chahe user ne "42" type kiya ho. +prompt("Number?") + +prompt("Number?") likhna zaroori hai, warna dono strings concatenate ho jaayenge ("2" + "3" = "23") instead of adding (5). Ye ek real-world bug class hai jo har "form input ka sum nikalo" feature mein dikhta hai.

Precedence, assignment ka return value, aur chaining

Assignment (=) bhi ek operator hai, jiski precedence sabse kam (2) hai — matlab pehle right-hand side poora evaluate hota hai, phir assignment hota hai. Aur ek subtle fact: assignment khud ek value return karta hai — wahi value jo assign hui.

Assignment returns a value + chaining
let a, b, c;

// right-to-left evaluate hota hai: pehle c = 2+2 (4), uska return value b ko, uska a ko
a = b = c = 2 + 2;
console.log(a, b, c);       // 4 4 4 — teeno mein same value chali gayi

let x = 2, y = 1;
// (y = x + 1) khud "3" return karta hai kyunki assignment ka return value assigned value hoti hai
let z = 3 - (y = x + 1);
console.log(y, z);          // y=3, z=0 — 3 - 3 = 0

Increment/decrement — prefix vs postfix

++counter (prefix) pehle increment karta hai, phir new value return karta hai. counter++ (postfix) bhi increment karta hai, lekin old value return karta hai — increment expression evaluate hone ke baad hota hai, is order ko engine internally guarantee karta hai.

Prefix vs postfix — return value differs
let counter = 1;
let a = ++counter;          // prefix: pehle counter 2 hua, phir a = 2 (new value)
console.log(a, counter);    // 2 2

counter = 1;                    // reset kiya reuse ke liye
let d = counter++;          // postfix: d = 1 (old value), FIR counter 2 hua
console.log(d, counter);    // 1 2
⚠️ Ek statement mein multiple ops mat mix karo

let x = 2 * counter++; jaisa code technically valid hai (postfix ki old value multiply hogi), lekin readability ke liye pehle counter increment karo alag line pe, phir expression likho. Comma operator ((1+2, 3+4) jo sirf last value return karta hai) similarly rarely useful hai — code-golf mein dikhta hai, production mein avoid karo.

Comparisons & Type Coercion

Comparison operators (>, <, >=, <=, ==, !=) hamesha boolean return karte hain. Root-level pe interesting cheez ye hai ki jab do different types compare hote hain, JS engine internally values ko numbers mein convert karta hai (strict equality ke case ko chhod ke).

String comparison — Unicode order, dictionary nahi
console.log('Z' > 'A');         // true — character-by-character Unicode code compare hota hai
console.log('Glow' > 'Glee');   // true — 'G','l' match, 3rd char pe 'o' > 'e' hai, wahin decide ho gaya
console.log('Bee' > 'Be');       // true — prefix match ho gaya, jo lamba hai wo bada mana jaata hai
console.log('a' > 'A');         // true — lowercase ka Unicode code uppercase se bada hota hai, true dictionary order nahi
Loose (==) vs strict (===) equality
console.log(0 == false);       // true — == dono ko number mein convert karta hai: false -> 0, phir 0==0
console.log(0 === false);      // false — === koi conversion nahi karta, type differ karti hai (number vs boolean) so seedha false
console.log('' == false);      // true — '' number mein convert hoke 0 banti hai, false bhi 0, so equal
console.log('2' > 1);         // true — comparison operators (> < >= <=) string ko number mein convert karte hain
🧠 Root cause — kyun 0 == false par 0 === false nahi

== (loose equality) ka spec algorithm agar dono operands ka type mismatch ho, to unhe coerce karta hai (usually numbers mein) phir compare karta hai — false hamesha 0 mein convert hota hai comparisons ke liye. Isliye 0 == false true hai. Lekin === (strict equality) spec ke first hi step mein type check karta hai — agar type match nahi, to turant false, koi conversion nahi hoti. Yehi wajah hai production code review guidelines almost hamesha === mandate karte hain — == ka coercion behavior non-obvious aur bug-prone hai (jaise famous [] == false bhi true hai kyunki empty array pehle string "" mein convert hota hai, phir 0 mein).

null aur undefined ke special comparison rules
console.log(null === undefined);  // false — strict equality types check karti hai, ye do alag types hain
console.log(null == undefined);   // true — spec ka special-case rule: == mein ye dono sirf ek dusre ke barabar hote hain

console.log(null > 0);          // false — mathematical comparison mein null number(0) banta hai, aur 0 > 0 false hai
console.log(null >= 0);         // true — null -> 0, aur 0 >= 0 true hai
console.log(null == 0);          // false — ye == hai (equality), aur == mein null sirf undefined/null ke barabar hota hai, kisi aur value ke nahi

console.log(undefined > 0);     // false — undefined mathematical context mein NaN banta hai
console.log(undefined == 0);     // false — special rule sirf null ke saath match karta hai, 0 se nahi
⚠️ NaN kabhi apne aap ke barabar nahi hota

undefined comparisons mein NaN mein convert hota hai, aur NaN ki spec-defined property ye hai: koi bhi comparison jisme NaN shamil ho — chahe >, <, ya khud NaN === NaN — hamesha false return karta hai. Isi wajah se undefined > 0, undefined < 0, aur undefined == 0 — teeno false hain, jo intuitively confusing lagta hai. Production check ke liye Number.isNaN(x) use karo, kabhi x === NaN nahi — wo hamesha false milega.

if / else / Ternary

if(...) apne parentheses ke andar ki value ko boolean mein convert karta hai (same rule jo Boolean(x) follow karta hai). Falsy values hain: 0, "", null, undefined, NaN — baaki sab truthy hai, including string "0" jo bahut logon ko surprise karta hai.

if/else if/else chain + ternary
let year = 2026;                  // variable jise multiple conditions se test karenge

if (year < 2015) {              // pehla condition check
  console.log('Too early...');   // agar year 2015 se kam hai to ye chalega
} else if (year > 2015) {       // pehla false hua to ye check hoga
  console.log('Too late');       // year 2026 hai, so 2015 se zyada hai — ye run hoga
} else {                        // dono conditions false hue to fallback
  console.log('Exactly!');        // sirf tab jab year === 2015
}

// ternary — value produce karta hai, statement nahi
let access = (year > 2000) ? 'allowed' : 'denied'; // condition ? truthy-case : falsy-case
console.log(access);            // "allowed"

// chained ternaries — multiple ? ek line mein, if-else-if ka compact equivalent
let age = 25;
let msg = (age < 3) ? 'Hi, baby!' :
  (age < 18) ? 'Hello!' :          // pehla false, second check
  (age < 100) ? 'Greetings!' :      // age=25 yahaan match hoga (25 < 100)
  'What an unusual age!';            // fallback agar upar koi match na kare
console.log(msg);              // "Greetings!"
💡 Ternary ka sahi use — value select karo, execute mat karo

Ternary ka purpose ek value return karna hai, koi side-effecting code run karna nahi. Isliye company === 'X' ? doSomething() : doSomethingElse() jaisa "action-dispatch" pattern avoid karo — is ke liye plain if/else use karo, kyunki multi-line code blocks single horizontal ternary se zyada readable hote hain, especially jab team review karega.

Logical Operators — &&, ||, !

Ye JS ki sabse misunderstood cheez hai: && aur || boolean return nahi karte — wo operands mein se ek ki actual value return karte hain. Boolean sirf internal decision-making ke liye use hota hai, final return value original (uncoerced) hoti hai.

|| — first truthy value return karta hai
console.log(null || 1);          // 1 — null falsy hai, so || agla operand check karta hai aur "1" (number) return karta hai, "true" nahi

let firstName = "";            // empty string — falsy
let lastName = "";             // empty string — falsy
let nickName = "SuperCoder";   // non-empty string — truthy

// left-to-right evaluate, jo pehla truthy mile wahi return, sab falsy ho to last operand return
console.log(firstName || lastName || nickName || "Anonymous"); // "SuperCoder"

true || alert("skipped");       // short-circuit — pehla operand truthy hai, dusra kabhi evaluate hi nahi hota
&& — first falsy value return karta hai
console.log(1 && 5);           // 5 — dono truthy hain, so && last operand return karta hai (not just "true")
console.log(1 && null && 2);    // null — jaise hi falsy mila (null), wahin ruk jaata hai, 2 evaluate hi nahi hota

false && alert("skipped");      // short-circuit — pehla operand hi falsy, alert() kabhi call hi nahi hota

// precedence: && ki precedence || se zyada hai, isliye parentheses ke bina bhi ye grouping implicit hai
console.log(null || 2 && 3 || 4); // 3 — (null) || (2 && 3) || (4) => null || 3 || 4 => 3
! NOT operator + double NOT (!!) for boolean conversion
console.log(!true);              // false — direct inversion
console.log(!0);                 // true — 0 falsy hai, ! usko boolean bana ke invert karta hai

// !! trick: pehla ! boolean mein convert karke invert karta hai, dusra ! wapas invert karke pure boolean deta hai
console.log(!!"non-empty");       // true — Boolean("non-empty") ke barabar, lekin chhota syntax
console.log(!!null);              // false
⚠️ && ko if ka replacement mat banao

(x > 0) && alert('Positive!') technically kaam karta hai (agar x>0 hai to alert chalega), lekin ye "clever" code hai jo readability kam karta hai. Explicit if (x > 0) alert('Positive!') use karo — intent turant clear hoti hai, aur code review mein next developer ko guess nahi karna padta ki && yahan control-flow ke liye use ho raha hai ya normal boolean logic ke liye.

Nullish Coalescing (??) vs ||

?? ES2020 mein isliye add hua kyunki || "falsy" ki definition bahut broad hai — 0, "", false sab falsy hain, lekin ye legitimate, meaningful values hain (jaise height=0, ya empty-but-valid string). ?? sirf null aur undefined ko "missing" maanta hai — baaki sab, chahe falsy ho, "defined" maana jaata hai.

?? vs || — zero-height wala classic bug
let height = 0;                // ye ek VALID value hai — user ne explicitly 0 set kiya

console.log(height || 100);     // 100 — BUG: || sirf truthy check karta hai, 0 falsy hai so 0 ignore ho gaya
console.log(height ?? 100);     // 0 — CORRECT: ?? sirf null/undefined ko replace karta hai, 0 defined value hai so wahi return hui

let u;                          // undefined — actually "missing"
console.log(u ?? "Anonymous"); // "Anonymous" — yahaan ?? sahi kaam kar raha hai kyunki u genuinely undefined hai
?? ki precedence + && || ke saath mandatory parentheses
let height2 = null, width = null;

// ?? ki precedence low hai (arithmetic se kam), isliye grouping explicit karna zaroori hai
let area = (height2 ?? 100) * (width ?? 50); // (null??100)=100, (null??50)=50, 100*50
console.log(area);            // 5000

// let x = 1 && 2 ?? 3; -> SYNTAX ERROR, JS spec ye combination bina parens allow hi nahi karta
let x = (1 && 2) ?? 3;       // explicit parens ke saath valid — (1&&2)=2, phir 2??3=2
console.log(x);                // 2
📌 && / || ke saath ?? mixing ban kyun hai

Ye purely developer-safety ke liye hai — jab log || se ?? migrate karte hain, precedence confusion bahut easily silent bugs create karti hai (jaise a ?? b || c ka matlab kya hai — ambiguous lagta hai). JS spec ne isliye &&/|| ko ?? ke saath directly mix karna hi SyntaxError bana diya, jab tak explicit parentheses na ho — compiler-level hi force karta hai ki tum apna intent clearly likho.

while / for Loops + Labels

Teen primary loop constructs hain, condition check karne ke timing mein differ karte hain: while pehle check karta hai (0 iterations bhi ho sakti hain), do..while baad mein check karta hai (kam se kam 1 iteration guaranteed), for ek structured 3-part header deta hai.

while, do-while, for — teeno ka comparison
let i = 0;
while (i < 3) {              // condition PEHLE check hota hai, false ho to body kabhi na chale
  console.log(i);              // 0, 1, 2 print karega
  i++;                       // increment manually karna padta hai, warna infinite loop
}

let j = 5;
do {
  console.log(j);              // 5 — chalta hai even though condition already false hai
} while (j < 3);            // condition BAAD mein check hota hai — body kam se kam ek baar guaranteed run karti hai

for (let k = 0; k < 3; k++) {    // begin(k=0) ek baar; condition(k<3) har iteration se pehle; step(k++) body ke baad
  console.log(k);              // 0, 1, 2
}
// k yahaan accessible nahi hai — let ka scope loop ke andar tak hi limited hai
break, continue, aur labeled loops (nested exit)
for (let i = 0; i < 10; i++) {
  if (i % 2 == 0) continue;   // even numbers skip — remaining body chhod ke seedha step pe jaata hai
  console.log(i);              // 1, 3, 5, 7, 9 — sirf odd numbers
}

// nested loops se ek saath bahar nikalne ke liye label chahiye — plain break sirf innermost loop todta
outer: for (let i = 0; i < 3; i++) { // "outer:" ye loop ka label hai
  for (let j = 0; j < 3; j++) {
    if (i === 1 && j === 1) break outer; // dono loop ek saath break, sirf inner nahi
    console.log(i, j);          // (0,0)(0,1)(0,2)(1,0) print karega, phir (1,1) pe outer break
  }
}
🧠 Senior Dev Note — for ka internal execution algorithm

Engine for(begin; condition; step) ko is exact order mein run karta hai: begin ek baar → phir loop: condition check (false ho to exit) → body → step → wapas condition check. Isliye begin ya step ko chhod sakte ho (for (; i < 3;)) — dono semicolons zaroori hain structure define karne ke liye, lekin expressions optional hain. for(;;) ek infinite loop hai jisme sab teen parts missing hain — ye production code mein "run until break" pattern ke liye deliberately use hota hai (jaise event-loop-driven servers, retry logic).

switch Statement

switch multiple if (x === value) checks ka descriptive replacement hai. Root-level cheez ye hai: switch hamesha strict equality (===) use karta hai, comparison mein koi type coercion nahi hoti.

switch — strict equality aur fall-through ka effect
let a = 2 + 2;                // a = 4

switch (a) {
  case 3:                     // internally if (a === 3) jaisa hai
    console.log('Too small');
    break;                   // break zaroori — warna next case mein "fall-through" ho jaayega
  case 4:                     // a===4 match karta hai, yahin se execution start hota hai
    console.log('Exactly!');       // ye print hoga
    break;                   // yahaan break hai so aage nahi jaayega
  case 5:
    console.log('Too big');
    break;
  default:                   // koi case match na ho to ye fallback chalega
    console.log("I don't know such values");
}
Grouping cases (intentional fall-through)
let a = 3;

switch (a) {
  case 4:
    console.log('Right!');
    break;
  case 3:                     // is case ka apna code nahi — break bhi nahi hai, so 5 ke code tak "fall through" karega
  case 5:                     // 3 aur 5 dono yahaan land karte hain — intentional grouping
    console.log('Wrong!');          // a=3 ke liye ye chalega
    break;
  default:
    console.log('The result is strange.');
}
⚠️ Strict equality ka gotcha — string "3" vs number 3

Kyunki switch hamesha === use karta hai, agar user input (jo hamesha string hoti hai, e.g. prompt() se) directly kisi number-literal case se compare hoti hai, to match kabhi nahi hoga. case 3: tab tak kabhi nahi chalega jab tak switch-expression khud number 3 na ho — string "3" chahe value se "same" dikhe, type mismatch ki wajah se silently default block mein chala jaata hai. Isse bachne ke liye switch-expression ko explicitly convert karo (Number(arg)) ya cases ko strings hi rakho consistently.

Key Takeaways

  • + ka special-case hai — agar koi bhi operand string hai to concatenation, warna dono operands number mein coerce hoke arithmetic; baaki sab arithmetic operators (-, *, /) hamesha number-coerce karte hain.
  • Assignment = ek expression hai jo assigned value return karta hai — isliye chaining (a = b = c) aur inline assignment (x = (y = 5)) possible hai.
  • == type coercion karta hai (spec algorithm ke through), === nahi karta — production code mein hamesha === prefer karo, null == undefined ke special case ke alawa jahan intentional ho.
  • null/undefined ka comparison behavior inconsistent lagta hai — == mein special rule hai, mathematical comparisons (< >) mein coercion (null→0, undefined→NaN) alag rules follow karti hai.
  • && aur || boolean nahi, operand values return karte hain — || pehli truthy, && pehli falsy value.
  • ?? sirf null/undefined ko "missing" treat karta hai — 0, "", false jaisi legitimate falsy values ke liye || se zyada correct default hai.
  • switch hamesha strict (===) comparison karta hai — type mismatch silently default block mein gir jaata hai.
  • Labels (outer:) nested loops se ek saath break/continue karne ka only tareeka hain — arbitrary code jump ke liye nahi.

🎯 Interview Questions

  • 0 == false hai lekin 0 === false nahi — root cause kya hai? Hint: spec algorithm difference — coercion vs type-check-first.
  • NaN !== NaN kyun hai? Hint: IEEE 754 spec definition, aur ise check karne ka sahi tareeka (Number.isNaN).
  • console.log(1 + '2' + 2) aur console.log(1 + 2 + '2') ka output kya hoga aur kyun differ karta hai? Hint: left-to-right evaluation + + ka type-dependent behavior.
  • height || 100 aur height ?? 100 mein kab different result aayega? Hint: jab height = 0 ya "" ho.
  • && aur || sirf true/false kyun nahi return karte? Hint: short-circuit ka implementation detail — default-value patterns kaise possible hote hain isi wajah se.
  • switch statement mein case '3': aur case 3: alag kyun behave karte hain? Hint: strict equality, type matters.
  • Nested loops se ek saath bahar nikalne ka correct tareeka kya hai, aur kyun ek flag variable use karna bura idea hai? Hint: labeled break vs manual flag-checking readability/perf tradeoff.
  • 1 && 2 ?? 3 likhne pe kya hota hai? Hint: SyntaxError — explain kyun spec ne ye restriction rakhi.
