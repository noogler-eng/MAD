DOM · Geometry · Layout

Sizes, Scrolling, Coordinates

DOM tree navigate karna aur attributes modify karna seekh liya — ab agla root-level skill hai: ek element kahan hai, kitna bada hai, aur kitna scroll hua hai ye exactly nikalna. Ye sab drag-drop, tooltips, custom scrollbars, infinite scroll, aur "sticky header" jaisi cheezon ka foundation hai. Upar se ek bahut important perf gotcha bhi hai — ye properties padhna khud ek synchronous layout trigger kar sakta hai.

Element geometry properties

Har DOM element ke paas ek set of read-only (mostly) numeric properties hote hain jo uska size aur border/padding/scroll layout batate hain. Inhe samajhne ka best tareeka ek concrete box socho: ek element jiska CSS width: 300px, padding: 20px, border: 25px hai.

Geometry box — CSS setup
<div id="example" style="width:300px; padding:20px; border:25px solid;">
  ...content yahaan...
</div>
<!-- box-sizing: content-box (default) maan ke chal rahe hain -->

Is box ke liye geometry properties kya return karengi:

geometry-read.js
const elem = document.getElementById('example'); // hamara test element pakda

// offsetWidth/offsetHeight — SABSE BAAHAR ki dimension: content + padding + border
console.log(elem.offsetWidth);  // 390 → 300 (content) + 40 (padding 20+20) + 50 (border 25+25)
console.log(elem.offsetHeight); // content height + padding + border (content ki height content pe depend karti)

// clientWidth/clientHeight — border EXCLUDE, padding INCLUDE, scrollbar bhi exclude
console.log(elem.clientWidth);  // 340 → 300 (content) + 40 (padding) — 50px border yahan count nahi hota

// clientTop/clientLeft — bas border ki thickness (offset se client tak ka gap)
console.log(elem.clientTop);   // 25 → top border ki width (LTR languages mein clientLeft bhi bas border hi hota)

// scrollWidth/scrollHeight — poore CONTENT ka size, chahe overflow ki wajah se hidden ho
console.log(elem.scrollHeight); // agar content clientHeight se bada hai, scrollHeight us poore content ko batayega

// scrollTop/scrollLeft — INHI DO ko set bhi kiya ja sakta hai (baaki sab read-only hain)
console.log(elem.scrollTop);  // 0 abhi — kitna content upar se "scroll ho ke chhup gaya" hai
⚠️ display:none wale element ki geometry saari 0 hoti hai

Agar element ya uska koi ancestor display:none hai, to offsetWidth, offsetHeight, offsetParent sab 0/null return karte hain — root cause: browser ne is element ke liye layout hi nahi compute kiya, isliye geometry exist hi nahi karti. Isi property ka use "is this element actually visible" check karne ke liye hota hai: if (!elem.offsetWidth && !elem.offsetHeight) { /* hidden hai */ }. Note: visibility:hidden se ye trick kaam nahi karega, kyunki wahan layout space reserved rehta hai — sirf display:none ke liye reliable hai.

Comparison table — offset vs client vs scroll

Ye teeno families ka farak root mein "kya include hota hai" ka hai:

PropertyContentPaddingBorderScrollbarHidden overflow content
offsetWidth/Height ✅✅✅✅ (agar reserved space le raha ho)❌
clientWidth/Height ✅✅❌❌ (scrollbar space subtract ho jaata)❌
scrollWidth/Height ✅ (POORA content, visible ho ya na ho)✅❌❌✅

Yaad rakhne ka mental model: offset = sabse outer box (jaisa browser use screen pe render karta hai, border ke saath), client = "visible inner" area (jahan content dikhta hai, scroll ho ya na ho), scroll = "total inner" area (agar content itna bada hai ki scroll karna pade, to poora content ka size).

Common use-case — scroll ke bottom tak kitna baaki hai check karna:

scroll-remaining.js
const scrollBottom = elem.scrollHeight - elem.scrollTop - elem.clientHeight;
// scrollHeight = poora content, scrollTop = kitna upar se chhup gaya, clientHeight = kitna abhi visible
// teeno mila ke pata chalta hai neeche kitna aur scroll karna baaki hai

if (scrollBottom === 0) {          // agar 0 hai, matlab user bilkul bottom tak scroll kar chuka
  console.log('Bottom pe pahunch gaye — next page load karo'); // e.g. infinite scroll pagination trigger
}

Forced synchronous layout — root perf gotcha

Ye geometry properties innocent nahi hain — inhe padhna free operation nahi hai. Root mechanism: browser lazily layout compute karta hai. Jab tum DOM/CSS badalte ho (style set karna, class add karna, node insert karna), browser turant layout recompute nahi karta — wo isse ek "dirty" flag maar ke queue mein daal deta hai aur agle animation frame tak batch karta hai (performance ke liye).

Lekin jaise hi tum offsetWidth, clientHeight, getBoundingClientRect() jaisi koi bhi geometry property padhte ho, browser ko turant, synchronously, us pending layout ko force-compute karna padta hai — kyunki tumhe ek accurate number chahiye, aur wo tabhi de sakta hai jab layout up-to-date ho. Isko "forced synchronous layout" ya "layout thrashing" kehte hain.

BAD — layout thrashing (read-write-read-write loop)
const boxes = document.querySelectorAll('.box'); // 100 boxes maan lo

boxes.forEach((box) => {
  const width = box.offsetWidth;       // READ: layout force-compute (pehli baar) — abhi ke liye theek
  box.style.width = width + 10 + 'px'; // WRITE: is se layout dobara "dirty" ho gaya
  // agli iteration ke offsetWidth read pe browser ko FIR SE layout recompute karna padega —
  // kyunki pichhli write ne dirty kar diya. 100 boxes = 100 forced synchronous layouts!
});
GOOD — batch reads, then batch writes
const boxes = document.querySelectorAll('.box');

// Step 1: SAB reads pehle karo — sirf ek hi forced layout lagega (pehli read pe)
const widths = Array.from(boxes).map((box) => box.offsetWidth);
// ab layout "clean" hai, aur humare paas cached widths array mein hain

// Step 2: SAB writes baad mein karo — koi read beech mein nahi, isliye recompute trigger nahi hota
boxes.forEach((box, i) => {
  box.style.width = widths[i] + 10 + 'px'; // WRITE-only, cached width use kiya
});
// Result: 100 forced layouts ki jagah sirf 1 — DevTools Performance tab mein ye
// "Recalculate Style" / "Layout" purple blocks repeatedly dikhega agar tum ye pattern na follow karo
⚠️ Kaunsi properties layout ko force karti hain

Sirf geometry-related properties/methods hi is trap mein daalte hain: offsetWidth/Height/Left/Top, clientWidth/Height/Left/Top, scrollWidth/Height/Left/Top, getBoundingClientRect(), getComputedStyle() (kuch properties ke liye), aur window.getSelection() jaise kuch aur. Simple property read (jaise elem.className) ya style set karna isse trigger nahi karta — sirf jab tumhe ek layout-dependent number chahiye, tabhi browser force karta hai. Production mein isko "layout thrashing" bolte hain aur ye scroll handlers, resize handlers, aur loops mein sabse zyada visible hota hai (janky scroll/drag).

scrollTop/scrollLeft: programmatic element scroll

Geometry family mein scrollTop aur scrollLeft hi aise properties hain jo writable bhi hain — inhe set karna element ko scroll kar deta hai:

element-scroll.js
elem.scrollTop = 0;          // scrollTop = 0 set karna → element ko top tak scroll kar deta hai
elem.scrollTop += 100;       // current scroll se 100px neeche scroll karo (relative increment)
elem.scrollTop = 1e9;        // bahut bada number daalo → browser khud clamp karke bottom tak le jaayega

Root cause ki wajah se ye smooth nahi hota by default — ye instant jump hai. Smooth scroll ke liye CSS scroll-behavior: smooth use karo ya Element.scrollTo() method ko behavior: 'smooth' option ke saath.

Window ka size: innerWidth vs documentElement.clientWidth

Window (poora browser viewport) ke liye do alag APIs hain, aur inka farak scrollbar hai — root gotcha yahi hai:

window-size.js
// window.innerWidth/innerHeight — SCROLLBAR ko bhi include karta hai apni width mein
console.log(window.innerWidth);  // e.g. 1920 — agar vertical scrollbar 15px le raha hai, wo bhi count hai

// document.documentElement.clientWidth/clientHeight — scrollbar EXCLUDE karta hai
console.log(document.documentElement.clientWidth); // e.g. 1905 — actual usable content width, scrollbar minus
// FARAK = scrollbar ki width. Agar tum kisi cheez ko "poora viewport content area" ke
// hisaab se position/size karna chahte ho (jaise ek full-width overlay), clientWidth sahi hai —
// innerWidth use karoge to overlay scrollbar ke neeche thoda chhup jaayega ya overflow karega
⚠️ documentElement.offsetWidth mat use karo window size ke liye

Kai developers galti se document.documentElement.offsetWidth use kar lete hain — lekin <html> element ke liye offsetWidth spec-wise reliably "poore viewport" ko represent nahi karta cross-browser. Window size ke liye sirf do sahi options hain: window.innerWidth/innerHeight (scrollbar included) ya documentElement.clientWidth/clientHeight (scrollbar excluded) — jo tumhare use-case ke hisaab se sahi ho.

Poore document (page content, jo viewport se bada ho sakta hai) ka total size nikalna aur bhi tricky hai kyunki purane WebKit browsers mein inconsistency thi — isliye Math.max se sabse safe multiple sources ka max liya jaata hai:

full-document-height.js
let scrollHeight = Math.max(
  document.body.scrollHeight, document.documentElement.scrollHeight, // dono body aur html check
  document.body.offsetHeight, document.documentElement.offsetHeight, // fallback source
  document.body.clientHeight, document.documentElement.clientHeight  // ek aur fallback
);
// root cause: Chrome/Safari/Opera mein agar scroll hi nahi hai, to documentElement.scrollHeight
// kabhi kabhi clientHeight se bhi KAM aa sakta hai — isliye single property pe bharosa nahi karte

Window scroll: pageXOffset/pageYOffset aur scroll methods

Current scroll position padhne ke liye window.pageXOffset aur window.pageYOffset use karo (ye window.scrollX/scrollY ke read-only aliases hain, purane naam backward-compat ke liye zinda hain):

read-scroll.js
console.log('Vertical scroll:', window.pageYOffset); // kitna neeche scroll hua hai, pixels mein
console.log('Horizontal scroll:', window.pageXOffset); // kitna right scroll hua hai
// documentElement.scrollLeft/scrollTop se READ mat karo — purane WebKit (Safari) browsers
// mein iske liye document.body chahiye tha, documentElement nahi — pageXOffset/pageYOffset
// ye historical inconsistency abstract kar deta hai, isliye reading ke liye ye hi safe hai

Scroll karne ke liye teen main tools hain:

window-scroll-methods.js
// scrollTo(x, y) — ABSOLUTE document coordinates pe jump karta hai
window.scrollTo(0, 0);              // document ke bilkul top pe le jao
window.scrollTo({ top: 500, behavior: 'smooth' }); // 500px se smooth animate karke jao

// scrollBy(x, y) — RELATIVE, current position se itna aur scroll karo
window.scrollBy(0, 100);            // jahan ho wahan se 100px neeche scroll karo

// elem.scrollIntoView(top) — kisi specific element ko viewport mein le aao
const section = document.getElementById('pricing');
section.scrollIntoView(true);   // true (default) → element ka TOP viewport ke top se align hoga
section.scrollIntoView(false);  // false → element ka BOTTOM viewport ke bottom se align hoga
section.scrollIntoView({ behavior: 'smooth', block: 'center' }); // modern options-object form

Scroll ko poori tarah rokna (e.g. modal open hone pe) is trick se hota hai:

disable-scroll.js
document.body.style.overflow = 'hidden'; // scroll disable — page apni current scroll position pe FREEZE ho jaata hai
// gotcha: scrollbar gayab ho jaata hai, jisse content thoda right shift ho sakta hai (reflow)
// fix: pehle scrollbar ki width measure karo (offsetWidth - clientWidth trick se), phir utna
// padding-right body pe add kar do taaki total width same rahe aur layout shift na ho

document.body.style.overflow = '';       // modal close hote hi wapas normal overflow restore karo

Coordinate systems: viewport vs document-relative

JavaScript mein element ki "position" do fundamentally alag coordinate systems mein express ki ja sakti hai — dono hi valid hain, bas reference point alag hai:

  • Window-relative (viewport) coordinates — clientX/clientY jaisa, measure hota hai visible window ke top-left corner se. CSS position: fixed jaisa behavior — scroll karo to ye coordinates change ho jaate hain kyunki element viewport ke relative move hua.
  • Document-relative coordinates — pageX/pageY jaisa, measure hota hai poore document ke top-left se (jo viewport se bada ho sakta hai). CSS position: absolute (document root pe) jaisa behavior — scroll karo to ye same rehte hain, kyunki element document ke relative move nahi hua.

In dono ka relation seedha hai: pageY = clientY + (scrolled-out vertical part ki height). Jitna scroll ho chuka hai, document-relative coordinate utna hi zyada hota hai viewport-relative se.

getBoundingClientRect() — viewport-relative geometry

Kisi element ki exact position/size nikalne ka primary tool elem.getBoundingClientRect() hai. Ye ek DOMRect object return karta hai — aur yaad rakho, ye hamesha viewport-relative hota hai, document-relative nahi:

gbcr-shape.js
const elem = document.getElementById('target');
const rect = elem.getBoundingClientRect(); // FORCED SYNCHRONOUS LAYOUT trigger hoti hai yahan

console.log(rect.x, rect.y);          // x,y = rectangle ka origin (top-left), viewport ke top-left se
console.log(rect.width, rect.height); // element ki actual rendered width/height (fractional ho sakta hai)
console.log(rect.top, rect.left);   // top === y, left === x — derived, convenience ke liye
console.log(rect.bottom, rect.right); // bottom = y + height, right = x + width — bhi derived
// NOTE: agar element viewport se upar scroll ho chuka hai, top/y NEGATIVE bhi ho sakta hai —
// ye "off-screen upar" ko represent karta hai, error nahi
🧠 Senior Dev Note: rect scroll ke saath badalta rehta hai

getBoundingClientRect() ek snapshot hai us exact moment ka jab tum ise call karte ho — ye live/reactive nahi hai. Agar page scroll ho, tumhare purane rect.top ki value stale ho jaati hai. Isliye scroll-tracking UI (jaise "sticky highlight jab section viewport mein aaye") ke liye har scroll event pe dobara call karna padta hai — jo expensive hai (forced layout, upar dekha). Production mein iske liye IntersectionObserver API prefer kiya jaata hai, jo browser ko async, batched, non-blocking tareeke se "element ab viewport mein aaya/gaya" notify karne deta hai, bina manual scroll-listener + rect-read loop ke.

Document-relative coordinates chahiye ho (jaise position:absolute se koi tooltip document ke root pe place karna hai, jo scroll ke saath page ke saath move ho), to pageXOffset/pageYOffset add karna padta hai:

to-document-coords.js
function getCoords(elem) {            // viewport-relative rect ko document-relative mein convert karta hai
  const box = elem.getBoundingClientRect();  // pehle viewport-relative rect nikalo

  return {
    top: box.top + window.pageYOffset,     // viewport-top + jitna scroll upar se chhupa = document-top
    left: box.left + window.pageXOffset,  // same logic horizontal ke liye
    bottom: box.bottom + window.pageYOffset,
    right: box.right + window.pageXOffset
  };
}

// Usage: kisi element ke exact "document space" mein neeche ek tooltip absolute-position karna
function showTooltipUnder(elem, html) {
  const tooltip = document.createElement('div'); // naya div banaya tooltip ke liye
  tooltip.style.cssText = 'position:absolute;'; // absolute so ki document coords se match ho

  const coords = getCoords(elem);       // document-relative coordinates nikale upar wale function se
  tooltip.style.left = coords.left + 'px'; // left position document ke hisaab se set
  tooltip.style.top = coords.bottom + 'px';  // top = element ke bottom se thoda neeche
  tooltip.innerHTML = html;          // tooltip ka actual content daal do

  document.body.append(tooltip);       // body mein append — ab ye page ke saath scroll bhi hoga (absolute hai)
  return tooltip;
}

Iska ulta bhi useful hai — document.elementFromPoint(x, y) viewport coordinates deke wahan pe sabse "nested" (innermost) element return karta hai:

element-from-point.js
const centerX = window.innerWidth / 2;  // viewport ka horizontal center nikala
const centerY = window.innerHeight / 2; // viewport ka vertical center nikala

const el = document.elementFromPoint(centerX, centerY); // VIEWPORT coords chahiye, document-relative nahi
console.log(el); // jo bhi element screen ke bilkul beech mein render ho raha hai
// gotcha: agar (x,y) visible viewport ke bahar hai, ye null return karta hai — kabhi kabhi
// negative ya bahut bada coordinate accidentally pass ho jaaye to null-check zaroor karo

Key Takeaways

  • offsetWidth/Height = content + padding + border (sabse outer box); clientWidth/Height = content + padding, border/scrollbar excluded; scrollWidth/Height = poora content, chahe overflow ki wajah se hidden ho.
  • Sirf scrollTop/scrollLeft writable hain geometry family mein — inhe set karke element ko programmatically scroll karte hain.
  • Geometry properties (offsetWidth, getBoundingClientRect(), etc.) padhna ek forced synchronous layout trigger karta hai — DOM writes ke beech-beech mein inhe read karne se "layout thrashing" hota hai. Fix: sab reads ek saath batch karo, phir sab writes.
  • Window size ke liye window.innerWidth/innerHeight (scrollbar included) vs documentElement.clientWidth/clientHeight (scrollbar excluded) — use-case ke hisaab se choose karo, documentElement.offsetWidth avoid karo.
  • Current window scroll padhne ke liye window.pageXOffset/pageYOffset use karo (scrollX/scrollY ke aliases), scrolling ke liye scrollTo, scrollBy, elem.scrollIntoView().
  • getBoundingClientRect() hamesha viewport-relative hota hai — scroll hone pe values change hoti rehti hain. Document-relative coordinates chahiye ho to + window.pageYOffset/pageXOffset karo.
  • Frequent rect-reads ke liye (scroll-triggered visibility checks) IntersectionObserver prefer karo — manual rect-polling se better performance.

🎯 Interview Questions

  • offsetWidth, clientWidth, aur scrollWidth mein exact farak batao ek example ke saath.
    Hint: offset = border+padding+content; client = padding+content (no border/scrollbar); scroll = poora content chahe hidden ho — element jiska overflow hai wahan scrollWidth > clientWidth hoga.
  • "Forced synchronous layout" kya hota hai aur ye kaise perf issue create karta hai? Fix kya hai?
    Hint: geometry reads pending layout ko synchronously force-compute karte hain; DOM writes ke beech reads dalne se repeated recompute hota hai (layout thrashing); fix = batch reads, phir batch writes.
  • getBoundingClientRect() viewport-relative hai ya document-relative? Document-relative coordinates kaise nikaalte ho?
    Hint: viewport-relative (scroll ke saath badalta rehta hai) — document-relative ke liye rect.top/left mein window.pageYOffset/pageXOffset add karo.
  • window.innerWidth aur document.documentElement.clientWidth mein kab-kaunsa use karoge?
    Hint: farak scrollbar hai — innerWidth scrollbar include karta hai, clientWidth exclude karta hai; content-area-accurate sizing ke liye clientWidth better.
  • display:none element ki geometry properties kya return karti hain, aur kyun?
    Hint: sab 0/null — browser ne layout compute hi nahi kiya kyunki element render tree mein hai hi nahi; visibility:hidden se ye trick kaam nahi karta kyunki space reserved rehta hai.
  • scroll ke bottom tak kitna baaki hai, ye kaise calculate karoge sirf geometry properties se?
    Hint: scrollHeight - scrollTop - clientHeight; result 0 hone pe element fully bottom-scrolled hai — infinite scroll pagination trigger ke liye common pattern.
  • Scroll-triggered "element visible ho gaya" detection ke liye getBoundingClientRect() polling ke bajaye kya use karna chahiye, aur kyun?
    Hint: IntersectionObserver — async, browser-batched, main thread block nahi karta, jabki manual scroll-listener + rect read forced layout ko repeatedly trigger karta hai.
