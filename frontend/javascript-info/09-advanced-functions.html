Recursion aur call stack

Recursion tab useful hai jab task "usi kaam ka chhota version" mein tod sakte ho. Har function call ek naya execution context banata hai — jisme uske local variables aur "abhi kahaan execute ho raha hoon" wala pointer store hota hai. Nested call hone par current context ek internal execution context stack pe push ho jaata hai, naya context top pe aata hai; jab wo call return karta hai, uska context pop hota hai aur pichla resume hota hai — bilkul function calls ke Array-jaisa LIFO structure.

pow(x, n) — loop vs recursion
// Iterative version — sirf EK execution context reuse hota hai, memory O(1)
function powLoop(x, n) {
  let result = 1;            // accumulator — abhi tak ka answer
  for (let i = 0; i < n; i++) {  // n baar loop chalao
    result *= x;          // result ko x se multiply karo, har iteration
  }
  return result;            // final power return karo
}

// Recursive version — HAR call apna alag execution context banata hai
function powRec(x, n) {
  if (n == 1) {       // BASE CASE — yahin recursion rukta hai, warna infinite chalega
    return x;          // x^1 = x, trivial answer seedha return
  }
  return x * powRec(x, n - 1); // RECURSIVE STEP — x * (x ka n-1 power), problem chhota ho raha hai
}

powRec(2, 3); // 8 — internally: 2*powRec(2,2) -> 2*(2*powRec(2,1)) -> 2*(2*2)

powRec(2, 3) chalne pe stack literally aisa dikhta hai — context: n=3 ke andar context: n=2 ke andar context: n=1. Jab n==1 hit hota hai, sabse andar wala context return karta hai, uske outer wala apna pending multiplication complete karta hai, aur aise stack unwind hoti hai top-to-bottom. Iska matlab: recursion depth ke proportional memory lagta hai — n = 10000 ke around JS engines "Maximum call stack size exceeded" de sakte hain, jabki loop version constant memory mein chalta rehta.

Nested structure traversal — company departments
let company = {
  sales: [{salary: 100}, {salary: 160}],  // leaf: employees ka array
  development: {                          // non-leaf: aage subdepartments hain
    sites: [{salary: 100}],
    internals: [{salary: 40}]
  }
};

function sumSalaries(department) {
  if (Array.isArray(department)) {       // BASE CASE: array mila matlab leaf level, seedha sum karo
    return department.reduce(
      (prev, curr) => prev + curr.salary, 0 // running total mein har employee ki salary jodo
    );
  } else {
    let sum = 0;                       // is level ka running total
    for (let subdep of Object.values(department)) { // har subdepartment pe iterate
      sum += sumSalaries(subdep);       // RECURSIVE STEP — subdep khud object ho sakta hai ya array
    }
    return sum;                       // saare subdepartments ka combined total
  }
}

console.log(sumSalaries(company)); // 400 — depth arbitrary ho sakti hai, recursion isliye natural fit hai

Linked list bhi conceptually recursive structure hai — har node { value, next } hai jahaan next khud ek chhota linked list (ya null) hai. Isliye reverse order print karna ek-line recursion se ho jaata hai:

Linked list — reverse traversal
let list = { value: 1, next: { value: 2, next: { value: 3, next: null } } };

function printReverse(node) {
  if (node.next) {              // agar aage aur node hai...
    printReverse(node.next);       // ...pehle usko print karao (stack pe pending rehta hai ye call)
  }
  console.log(node.value);          // stack unwind hote waqt print — isliye reverse order aata hai: 3,2,1
}
printReverse(list);
⚠️ Recursion "free" nahi hai

Har recursive call ek naya stack frame allocate karta hai. Deep recursion (bade array/tree pe) memory-heavy ho sakti hai aur stack overflow de sakti hai. Rule of thumb: agar recursion depth input-size ke saath unbounded grow kar sakti hai (jaise ek bade flat array ko process karna), to loop use karo. Agar depth naturally bounded hai (tree height, jo generally log(n) hoti hai — balanced structures mein), recursion safe aur zyada readable hai.

Rest parameters vs spread syntax

Dono same ... syntax use karte hain lekin opposite direction mein kaam karte hain — rest values ko ek array mein "gather/collect" karta hai (function parameters mein use hota hai), spread ek iterable ko individual values mein "expand/spread" karta hai (function calls / array-object literals mein use hota hai).

Rest parameters — gather karna
function sumAll(...args) {    // ...args: jitne bhi extra arguments aayein, ek Array mein collect ho jaayenge
  let sum = 0;                // running total
  for (let a of args) sum += a; // args real Array hai — for-of, map, reduce sab chalega
  return sum;
}
sumAll(1, 2, 3); // 6

// Named params ke saath rest — rest hamesha LAST hona chahiye, warna SyntaxError
function showName(firstName, lastName, ...titles) {
  console.log(firstName, lastName); // pehle do named params normally bind honge
  console.log(titles);            // baaki sab titles array mein — ["Consul", "Imperator"]
}
showName("Julius", "Caesar", "Consul", "Imperator");

Legacy arguments object bhi sabhi non-arrow functions ko available hai — array-like hai (index + length) lekin real Array nahi (koi .map()/.filter() nahi milega bina convert kiye), aur sabse important: arrow functions ka apna arguments nahi hota — wo enclosing normal function se arguments inherit karte hain (isi property ka use decorators section mein forwarding ke liye hoga).

Spread syntax — expand karna
let arr = [3, 5, 1];
console.log(Math.max(...arr));       // 5 — arr ke elements individual arguments ban gaye
console.log(Math.max(1, ...arr, 25)); // 25 — normal args ke saath bhi mix kar sakte ho

let merged = [0, ...arr, 2];    // array literal ke andar bhi spread chalta hai — [0, 3, 5, 1, 2]
let arrCopy = [...arr];       // SHALLOW copy — naya array, same top-level values
let objCopy = { ...arr};       // objects mein bhi spread — shallow merge/copy

let str = "Hi";
console.log([...str]);          // ["H","i"] — string iterable hai, spread character-by-character todta hai

Array.from aur spread dono iterables ko array mein convert karte hain, lekin Array.from array-likes (jaise arguments, ya {0:'a',1:'b',length:2}) pe bhi kaam karta hai jinke paas Symbol.iterator nahi hota, jabki spread sirf real iterables pe chalta hai — non-iterable array-like pe spread TypeError dega.

Closures — Lexical Environment se samjho (root-level)

"Function apna outer scope yaad rakhta hai" — ye statement technically sahi hai lekin agar isse aage nahi socha to interview mein "why?" pe atak jaoge. Asli mechanism ek internal spec object hai jise Lexical Environment kehte hain. Har running function, block, aur script ka apna Lexical Environment hota hai, jisme do parts hote hain:

  • Environment Record — ek internal object jisme us scope ke saare local variables key: value pairs ki tarah store hote hain (plus kuch metadata, jaise this).
  • Outer reference — parent Lexical Environment ka pointer, jo ek chain banata hai upar tak, global environment tak.

Ek "variable" ka access actually is Environment Record ki property access hai. Jab code kisi variable ko padhta hai, engine current environment ke Record mein dhoondta hai; nahi mila to outer reference follow karke parent mein dhoondta hai, aur ye chain global tak chalti hai — nahi mila to (strict mode mein) ReferenceError.

🧠 Senior Dev Note: [[Environment]] — asli closure mechanism

Har function, banate hi (declaration/expression evaluate hote hi), ek hidden internal property store karta hai: [[Environment]] — jo us Lexical Environment ki reference hai jahaan function CREATE hua tha, na ki jahaan wo CALL hota hai. Ye reference permanent hai, function ki poori life tak fixed rehta hai. Jab bhi function call hota hai, ek naya (chhota) Lexical Environment banta hai us call ke local variables ke liye, aur uska outer pointer seedha function ke [[Environment]] ki taraf set ho jaata hai — call-site ke scope se koi lena-dena nahi. Isi wajah se JS lexical (static) scoping language hai, dynamic scoping nahi — variable resolution function ke likhe jaane ki jagah se decide hoti hai, uske call hone ki jagah se nahi.

Closure — step by step Lexical Environment chain
function makeCounter() {
  let count = 0;          // makeCounter() ke Lexical Environment ka Record: { count: 0 }

  return function() {       // ye inner function CREATE ho raha hai YAHIN — [[Environment]] = makeCounter ka LE
    return count++;        // count is inner function ke local environment mein nahi mila
  };                       // ...so engine outer reference follow karta hai -> makeCounter LE -> count mil gaya
}

let counter = makeCounter();   // makeCounter() run ho chuka, RETURN ho chuka — lekin uska LE zinda hai
                              // kyunki 'counter' variable us returned function ko reference karta hai,
                              // aur us function ka [[Environment]] makeCounter LE ko reachable rakhta hai
console.log(counter());       // 0 — count 0 se 1 hua
console.log(counter());       // 1 — SAME environment reuse ho raha, isliye state persist hui

let counter2 = makeCounter();  // EK NAYA makeCounter() call = EK NAYA, independent Lexical Environment
console.log(counter2());      // 0 — counter2 ka apna alag count hai, counter se koi connection nahi

Is definition se ek important corollary nikalta hai jo javascript.info bhi explicitly kehta hai: "JS mein sabhi functions naturally closures hote hain" — kyunki har function ke paas apne creation-site ke Lexical Environment ka [[Environment]] reference hota hi hai, chahe wo outer variables actually use kare ya nahi. "Closure" koi special syntax nahi, ye normal function creation ka hi side-effect hai.

Practical closure: filter ke saath range check
function inBetween(a, b) {
  return function(x) {     // returned function ka [[Environment]] = inBetween ka LE, jahaan a,b hain
    return x >= a && x <= b; // a aur b yahaan bina explicitly pass kiye available hain — closure
  };
}

let arr = [1, 2, 3, 4, 5, 6, 7];
console.log(arr.filter(inBetween(3, 6))); // [3,4,5,6] — har call apna a,b closure mein rakhta hai

Garbage collection: Lexical Environments normally function return hote hi memory se hat jaate hain — jab tak koi unhe reachable na rakhe. Agar returned function (jaise upar counter) usually ek variable mein store hoti hai, uska [[Environment]] parent LE ko reachable rakhta hai, isliye GC use nahi hata sakta. Jab counter = null kar do, aur koi aur reference bhi na bache, tabhi GC us environment ko clean karta hai.

V8 (Chrome ka engine) ek smart optimization karta hai — agar closure kisi outer variable ko use hi nahi karta, engine use environment se drop kar sakta hai memory bachane ke liye, chahe theoretically wo "accessible" ho. Practical implication: DevTools mein breakpoint laga ke aisa variable inspect karo jo closure mein referenced nahi hai, to wo missing ya kisi outer scope ki value dikha sakta hai — ye bug nahi, engine optimization hai jo debugging session ko thoda confusing bana sakta hai.

⚠️ Classic gotcha: loop + var + setTimeout ("army of functions")

var function-scoped hai, matlab loop ke andar declare kiya var i loop ke baahar ke scope mein reh jaata hai — saari iterations ek hi shared variable use karti hain. Neeche wale example mein saare timeouts ek hi i ko closure mein pakadte hain, aur jab tak wo actually run karte hain, loop already khatam ho chuka hota hai, so i apni final value pe hoti hai.

var vs let closure behavior
// BUGGY: var — saare 3 setTimeouts SAME 'i' ko closure mein pakadte hain
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0); // loop khatam hone ke baad chalte hain — sab 'i' ko 3 dekhte hain
} // output: 3, 3, 3 (kyunki loop ke baad var i = 3 pe reh gaya)

// FIXED: let — har iteration apna ALAG lexical environment banata hai
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log(j), 0); // har closure apna independent 'j' pakadta hai
} // output: 0, 1, 2 — har iteration ka apna snapshot

var ka function-scoping aur hoisting

var aur let/const mein teen fundamental differences hain, aur teeno "root cause" ek hi hai — var ES5-era ka hai, jab JS mein block scope hi nahi tha, sirf function scope tha.

var: no block scope, redeclare allowed, hoisting
// 1) var block se leak karta hai — sirf function (ya global) scope respect karta hai
if (true) {
  var test = true;    // 'if' block mein declare kiya
}
console.log(test);          // true — block khatam hone ke baad bhi visible hai! (let se ReferenceError aata)

// 2) redeclaration silently ignore hota hai — koi error nahi
var user = "John";
var user = "Pete";   // let hota to SyntaxError, var mein ye bas ek reassignment hai

// 3) hoisting: DECLARATION function ke top pe uth jaati hai, ASSIGNMENT apni jagah rehta hai
function sayHi() {
  console.log(phrase);      // undefined — error NAHI aata, kyunki var phrase already declared ho chuka top pe
  var phrase = "Hello"; // assignment yahin execute hoti hai, jahaan likhi hai
}
sayHi();

Engine ke andar jo actually hota hai: script/function chalne se pehle ek preparation pass mein saari var declarations function ke top pe "hoist" ho jaati hain (value undefined ke saath) — lekin assignment statement wahin rehta hai jahaan likha gaya tha, aur wo assignment sirf execution ke us point pe chalta hai. Function declarations (function foo(){}) is se ek level aage hoisted hoti hain — pura function body bhi available hota hai, isliye unhe declaration se pehle call kar sakte ho; function EXPRESSIONS (var foo = function(){}) sirf variable ki tarah hoist hoti hain, value nahi.

Historically, block scope na hone ki wajah se developers IIFE (Immediately Invoked Function Expression) pattern use karte the artificial scope banane ke liye — (function() { var message = "Hello"; })(); — taaki message global scope pollute na kare. let/const aane ke baad ye pattern mostly obsolete ho gaya, lekin legacy codebases aur bundler-generated code mein aaj bhi dikhta hai.

Global object — window / globalThis

Har JS environment ka ek global object hota hai jo built-in aur environment-provided functions/variables ko hold karta hai. Browser mein iska naam window hai, Node.js mein global. Cross-environment consistency ke liye modern JS globalThis deta hai — jo har jagah (browser, Node, workers) same object ko refer karta hai.

Global object — var/let farak, polyfill pattern
alert("Hi");          // ye actually window.alert("Hi") hi hai — global functions window ki properties hain

var gVar = 5;
console.log(window.gVar);  // 5 — TOP-LEVEL var global object ki property BAN JAATA hai

let gLet = 5;
console.log(window.gLet);  // undefined — let/const kabhi window ki property nahi bante (deliberate spec choice)

// feature-detection + polyfill pattern — real-world use case
if (!window.Promise) {          // check: kya is environment mein Promise built-in available hai?
  window.Promise = MyPromisePolyfill; // nahi hai to apna implementation global object pe attach kar do
}

Ye asymmetry (var global object property banta hai, let/const nahi) ek common trivia interview question hai — root cause ye hai ki ES6 mein let/ const ke liye ek naya, separate "Script" record concept design kiya gaya taaki modules/newer code global namespace ko unnecessarily pollute na kare, jabki var backward compatibility ke liye purane behavior pe hi rehta hai.

Function objects, name/length, Named Function Expressions

JS mein functions "callable objects" hain — matlab wo invoke bhi ho sakte hain aur unpe normal object ki tarah properties bhi set/read kar sakte ho.

Function ki built-in properties: name, length
let sayHi = function() { alert("Hi"); };
console.log(sayHi.name);   // "sayHi" — anonymous function expression ko bhi variable name se "contextual name" mil gaya

function f1(a) {}
function many(a, b, ...rest) {}
console.log(f1.length);    // 1
console.log(many.length);  // 2 — rest parameter COUNT nahi hota length mein

// custom property directly function object pe — closure ka alternative (lekin externally mutable)
function sayHi2() {
  alert("Hi");
  sayHi2.counter++;      // function object ki apni property increment karo — local variable NAHI hai
}
sayHi2.counter = 0;      // property function ke BAHAR se set ki, function object pe attach hoti hai

Ek subtle-but-senior topic: Named Function Expressions (NFE). Normal function expression ko internally ek naam do (function func(){...}), to us naam se do special cheezein milti hain — (1) function apne aap ko reliably call kar sakta hai us naam se, chahe outer variable overwrite ho jaaye; (2) wo naam sirf function ke andar visible hai, bahar se nahi.

NFE — recursion safety jab outer variable badal jaaye
// BUGGY: naam-less function expression, self-reference outer 'sayHi' pe depend karta hai
let sayHi = function(who) {
  if (who) {
    alert(`Hello, ${who}`);
  } else {
    sayHi("Guest");     // closure se OUTER 'sayHi' variable dhoondta hai
  }
};
let welcome = sayHi;
sayHi = null;            // outer 'sayHi' ab null hai
welcome();                // TypeError: sayHi is not a function — internal call sayHi(null) pe fail hua

// FIXED: NFE — internal name 'func' hamesha CURRENT function object ko point karta hai
let sayHi2 = function func(who) { // 'func' — internal name, sirf is function ke andar visible
  if (who) {
    alert(`Hello, ${who}`);
  } else {
    func("Guest");     // engine ne 'func' ke liye ek special extra Lexical Environment banaya jo NEVER external reassign se affect hota
  }
};
let welcome2 = sayHi2;
sayHi2 = null;
welcome2();               // "Hello, Guest" — kaam karta hai, kyunki func outer sayHi2 pe depend nahi karta

new Function — string se function banana

Rarely used, lekin exist karta hai un cases ke liye jab function ka source runtime pe kisi string se aa raha ho (server-generated code, template compilation).

new Function syntax + closure limitation
let sum = new Function('a', 'b', 'return a + b'); // args names + body, sab strings
console.log(sum(1, 2));          // 3

function getFunc() {
  let value = "test";
  let func = new Function('alert(value)'); // [[Environment]] normal closure ki tarah NAHI banta
  return func;
}
getFunc()();              // ReferenceError: value is not defined — sirf GLOBAL lexical env se resolve karta hai

Ye special-case behavior zaroori hai, na ki bug — new Function se banaye gaye function ka [[Environment]] hamesha global Lexical Environment ko point karta hai, local scope ko nahi jahaan wo actually create hua. Isse minifiers safe rehte hain (agar local variable renamed ho jaaye, string-based code us naye naam se match nahi karega, so spec ne isse explicitly disallow kar diya) — aur developer ko explicit params pass karne pe force karta hai.

setTimeout / setInterval, aur "zero delay" gotcha

Basic scheduling API
let timerId = setTimeout(() => console.log("once"), 1000); // 1000ms baad ek baar chalega
clearTimeout(timerId);                            // cancel — ab kabhi nahi chalega

// setInterval: repeated, LEKIN precise gap guarantee nahi karta
let intId = setInterval(() => console.log("tick"), 2000);
setTimeout(() => clearInterval(intId), 10000);   // 10s baad interval band

// Nested setTimeout — BETTER control: agli call, callback KHATAM hone ke baad schedule hoti
let nestedId = setTimeout(function tick() {
  console.log("tick");
  nestedId = setTimeout(tick, 2000);  // callback execution ke BAAD hi agla schedule hota — actual gap kabhi 2000 se kam nahi
}, 2000);
🧠 Senior Dev Note: setTimeout(fn, 0) turant kyun nahi chalta

delay = 0 (ya delay omit karna) ka matlab "abhi execute karo" nahi hai — matlab hai "jaldi se jaldi, jab main thread free ho". setTimeout callback ek macrotask hai. Scheduler use tabhi run karta hai jab: (1) current synchronously executing script poora khatam ho chuka ho, AND (2) us point tak queue mein pending saare microtasks (Promise callbacks, queueMicrotask) drain ho chuke hon. Yani priority order hamesha hai: synchronous code → microtask queue → macrotask queue (jisme setTimeout hai). Full event loop mechanics chapter 23 (Misc Browser) mein detail mein hai, lekin ye ordering abhi samajhna zaroori hai kyunki ye ek bahut common "what does this log?" interview question hai.

Ordering: sync → microtask → macrotask
console.log("1: sync");                       // synchronous — turant chalta hai

setTimeout(() => console.log("4: macrotask"), 0); // macrotask queue mein jaata hai, LAST run hoga

Promise.resolve().then(() =>
  console.log("3: microtask")                // microtask queue mein — macrotask se PEHLE chalega
);

console.log("2: sync");                       // abhi bhi current script hi chal raha hai

// ACTUAL OUTPUT ORDER: "1: sync", "2: sync", "3: microtask", "4: macrotask"
⚠️ setTimeout function reference ko garbage collect nahi hone deta

Scheduler internally callback function ko ek reference save karke rakhta hai, jab tak wo fire na ho jaaye ya clearTimeout/clearInterval se cancel na ho. Iska matlab wo callback function (aur uska pura closure chain — [[Environment]] ke through) garbage-collected nahi hoga jab tak timer pending hai. setInterval ke saath ye risk zyada real hai — agar clear nahi kiya, callback aur uska closure indefinitely memory mein reh sakte hain, effectively ek memory leak.

Decorators — call/apply se call forwarding

Decorator ek function hai jo doosre function ko "wrap" karta hai — original function ka behavior badle bina, naya feature add karta hai (jaise caching). Classic example: memoization.

cachingDecorator — this-safe version
function cachingDecorator(func) {
  let cache = new Map();       // closure — 'cache' is decorator instance ke liye persist rehta hai

  return function(x) {          // wrapper function — bahar se yehi function call hoga original ki jagah
    if (cache.has(x)) {    // agar ye input pehle bhi aaya hai...
      return cache.get(x);    // ...seedha cached result return karo, original function CALL hi nahi hota
    }
    let result = func.call(this, x); // ZAROORI: .call(this, x) — 'this' explicitly forward karo original func ko
    cache.set(x, result);    // result ko cache mein store karo agli baar ke liye
    return result;
  };
}

let worker = {
  someMethod() { return 1; },
  slow(x) {
    console.log("expensive call");
    return x * this.someMethod(); // slow() ko apna 'this' (worker) chahiye kaam karne ke liye
  }
};

worker.slow = cachingDecorator(worker.slow); // original slow ko wrapper se replace kar diya
console.log(worker.slow(2));       // "expensive call" print hoke 2 — pehli baar, cache miss
console.log(worker.slow(2));       // seedha 2 — cache hit, "expensive call" print NAHI hota

Agar worker.slow = cachingDecorator(worker.slow) ke baad wrapper ke andar func(x) plain call karte (bina .call ke), to slow ke andar this undefined ho jaata — kyunki wrapper function ab worker object se detached hai, plain function ki tarah invoke ho raha hai. func.call(this, x) explicitly bata deta hai: "wrapper jis this ke saath call hua, wahi original function ko bhi do".

call vs apply — same kaam, different argument format
// call: context + INDIVIDUAL arguments, comma-separated
func.call(context, arg1, arg2);

// apply: context + ARRAY (ya array-like) of arguments
func.apply(context, [arg1, arg2]);

// method borrowing — Array.prototype.join ko array-like arguments pe "udhaar" liya
function hash() {
  return [].join.call(arguments); // arguments Array nahi hai, lekin join() sirf 'this' pe generically kaam karta hai
}
console.log(hash(1, 2, 3));          // "1,2,3" — multi-arg caching key banane ke liye kaam aata hai

Function.prototype.bind

Method ko object se alag karke pass karte hi (callback ki tarah) this kho jaata hai — yehi sabse common real-world this bug hai.

this loss aur bind se fix
let user = {
  firstName: "John",
  sayHi() {
    console.log(`Hello, ${this.firstName}`); // 'this' method call site pe decide hota hai
  }
};

setTimeout(user.sayHi, 1000); // BUG: "Hello, undefined" — sayHi user se detach hoke plain function ki tarah call hua

let boundSayHi = user.sayHi.bind(user); // bind() ek NAYA function return karta hai, 'this' PERMANENTLY user pe fix
setTimeout(boundSayHi, 1000); // FIXED: "Hello, John" — bound function ka this kabhi override nahi hota, .call() se bhi nahi
Partial application — kuch args bhi preset kar sakte ho
function mul(a, b) {
  return a * b;
}
let double = mul.bind(null, 2);  // this=null (irrelevant here) + FIRST arg 'a' preset to 2
console.log(double(3));          // 6 — double(3) internally mul(2, 3) call karta hai
console.log(double(5));          // 10

// bindAll pattern — jab poore object ke saare methods safe-pass karne hon
for (let key in user) {
  if (typeof user[key] == 'function') { // sirf function properties pe kaam karo
    user[key] = user[key].bind(user); // har method ko permanently 'user' se bind kar do, in-place replace
  }
}
⚠️ Method callback pass karte waqt hamesha check karo: this kho to nahi raha

obj.method ko kisi bhi jagah (event listener, setTimeout, .then(), array callback) directly reference ki tarah pass karna hamesha this loss ka risk carry karta hai — kyunki JS mein this call-site pe decide hota hai, definition-site pe nahi. Fix: .bind(obj), ya arrow function wrapper () => obj.method(), ya class fields (method = () => {...}, jo chapter 11 mein cover hoga).

Arrow functions revisited

Arrow functions sirf "chhota syntax" nahi hain — inki teen structural limitations hain jo unhe specifically kuch use-cases ke liye designed banati hain:

  • Apna this nahi hota — access karne pe lexically enclosing scope se liya jaata hai (bilkul kisi bhi normal variable ki tarah — outer Lexical Environment se resolve hota hai).
  • Apna arguments nahi hota — enclosing normal function ka arguments use hota hai.
  • new ke saath use nahi ho sakti — constructor nahi ban sakti (no [[Construct]] internal method), aur super bhi nahi hota.
Classic bug: regular function vs arrow function callback
let group = {
  title: "Our Group",
  students: ["John", "Pete", "Alice"],

  // BUGGY version — regular function callback
  showListBug() {
    this.students.forEach(function(student) {
      // forEach is anonymous function ko PLAIN function ki tarah call karta hai — this = undefined (strict mode)
      console.log(this.title + ': ' + student); // TypeError: Cannot read properties of undefined
    });
  },

  // FIXED — arrow function callback
  showListFixed() {
    this.students.forEach(student => {
      // arrow fn ka apna 'this' nahi — showListFixed() ke 'this' (= group) ko LEXICALLY use karta hai
      console.log(this.title + ': ' + student); // "Our Group: John" ...
    });
  }
};

group.showListFixed();

Root cause: arrow function ka koi this-binding step hota hi nahi jab wo invoke hoti hai — engine ke liye this bilkul kisi normal free variable jaisa hai, jo scope chain (Lexical Environment ke outer references) follow karke resolve hota hai. Isliye arrow function ka this hamesha wahi hoga jo us jagah tha jahaan arrow function likhi gayi thi — ye bhi ultimately closures wale [[Environment]] mechanism ka hi extension hai.

Arrow function decorator — arguments forwarding
function defer(f, ms) {
  return function(...args) {       // outer wrapper NORMAL function hai — iska apna 'this'/'arguments' hoga
    setTimeout(() => f.apply(this, args), ms); // arrow fn: 'this' aur 'args' outer wrapper se lexically inherit
  };                              // agar ye normal function hota, apna alag 'this' hota — args bhi manually pass karna padta
}

Isi wajah se arrow functions object methods ki tarah use nahi karni chahiye — obj = { count: 0, inc: () => this.count++ } mein this obj nahi hoga (jaisa expect kiya jaata hai), balki jahaan obj literal khud define hua uska outer this hoga (aksar module/global scope, jo undefined ya kuch aur hota hai). Arrow functions best hain short, lexically-scoped callbacks ke liye — array methods, event handlers jinme outer this chahiye, decorators.

Key Takeaways

  • Recursion depth ke proportional stack memory lagta hai — deep/unbounded recursion loop se convert karo.
  • Rest (...args params mein) gather karta hai, spread (...arr calls/literals mein) expand karta hai — dono same token, opposite direction.
  • Closures = har function apne [[Environment]] ke through apne creation-site Lexical Environment ko reference karta hai — permanent aur lexical, call-site se independent.
  • var function-scoped hai (block se leak karta hai), redeclare-tolerant hai, aur "hoisted" hota hai (declaration top pe, assignment apni jagah).
  • Sirf top-level var (aur function declarations) global object (window) ki property bante hain — let/const nahi.
  • Functions objects hain — name, length built-in properties, custom properties bhi attach ho sakti hain; NFE internal self-reference guarantee deta hai.
  • new Function ka closure sirf global environment tak hota hai, local scope tak nahi.
  • setTimeout(fn, 0) "abhi" nahi, "sync code + microtasks ke baad jaldi se jaldi" chalta hai — macrotask queue mein jaata hai.
  • call/apply ek-baar-ke-liye this forward karte hain (args syntax differ karta hai), bind permanently naya function banata hai fixed this (+ optional preset args) ke saath.
  • Arrow functions ka apna this/arguments nahi hota (lexical inherit), constructor nahi ban sakti — object methods ke liye unsuitable, short lexical callbacks ke liye ideal.

🎯 Interview Questions

  • Closure kya hai — sirf "function apna scope yaad rakhta hai" se aage jaake explain karo.
    Hint: har function ka hidden [[Environment]] property hota hai jo uske creation-site Lexical Environment ko point karta hai; ye permanent reference hai, call-site independent — spec-level object model.
  • Ye code kya print karega? 
    for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
    Hint: 3, 3, 3 — var function-scoped hai, saare closures ek hi shared i pakadte hain jo loop khatam hone tak 3 ho chuka hota hai; let use karte to 0,1,2 aata (har iteration apna environment).
  • Ye code kya order mein print karega, aur kyun? 
    console.log("A");
setTimeout(() => console.log("B"), 0);
Promise.resolve().then(() => console.log("C"));
console.log("D");
    Hint: A, D, C, B — sync code pehle (A, D), phir microtask queue (C — Promise), phir macrotask queue (B — setTimeout).
  • Regular function callback ke bajaye arrow function forEach mein use karna kyun ek object method ko fix karta hai?
    Hint: arrow function ka apna this hota hi nahi — wo definition-site ke lexical scope se inherit karta hai, jo yahaan enclosing method ka this (asli object) hota hai; regular function callback ko forEach plain call karta hai, so uska this = undefined.
  • call, apply, aur bind mein kya farak hai?
    Hint: call/apply immediately invoke karte hain custom this ke saath (args: comma-list vs array); bind invoke nahi karta, ek NAYA function return karta hai jiska this permanently fix ho chuka hai.
  • Named Function Expression (NFE) mein internal function name kyun use karte hain, sirf outer variable pe recursion kyun risky hai?
    Hint: outer variable reassign/null ho sakta hai, jisse recursive call fail hoga; NFE ka internal naam ek separate, immutable binding hai jo hamesha current function object ko point karta hai.
  • setTimeout(fn, 0) ka actual behavior kya hai — "immediately" kyun nahi chalta?
    Hint: macrotask hai — pehle poora current synchronous script khatam hota hai, phir saari pending microtasks drain hoti hain, tabhi jaake macrotask queue se ye callback uthta hai.
  • Kya arrow function ko constructor (new) ki tarah use kar sakte ho? Kyun/kyun nahi?
    Hint: nahi — arrow functions ke paas internal [[Construct]] method hi nahi hota, spec-level restriction; new ArrowFn() seedha TypeError deta hai.
