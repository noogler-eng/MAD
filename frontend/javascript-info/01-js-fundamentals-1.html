JavaScript kya hai — engines andar se kaise kaam karte hain

JavaScript originally banaya gaya tha web pages ko "alive" banane ke liye — HTML ke andar embed hone wale scripts jo page load hote hi automatically execute ho jaate. Naam marketing gimmick tha (Java tab popular tha), lekin language ka actual spec hai ECMAScript — Java se koi runtime relation nahi hai. Aaj JavaScript sirf browser tak limited nahi — Node.js jaise runtimes ke through server pe bhi chalta hai, kyunki koi bhi environment jisme JS engine embed hai, JS run kar sakta hai.

Har browser vendor apna alag engine maintain karta hai: Chrome/Edge/Opera mein V8, Firefox mein SpiderMonkey, Safari mein JavaScriptCore (Nitro). Root-level pe engine teen phases mein kaam karta hai:

  1. Parse — source code ko tokens mein todke ek Abstract Syntax Tree (AST) banaya jaata hai.
  2. Compile — AST ko machine code mein convert kiya jaata hai (JIT — Just-In-Time compilation).
  3. Execute + Optimize — machine code run hota hai, aur engine runtime data flow ko observe karke code ko baar-baar re-optimize karta rehta hai (hot paths ko further specialize karta hai).

Yani JS na purely "interpreted" hai na purely "compiled" — modern engines dono ka hybrid use karte hain (interpret first for fast startup, phir JIT-compile hot code paths ko speed ke liye). Isi wajah se same function baar-baar call hone pe progressively fast hoti jaati hai.

In-browser JavaScript kya kar sakta hai: HTML content/styles modify karna, user events (click, keypress, mouse move) handle karna, AJAX/network calls, cookies aur local storage manage karna, files download/upload karna. Lekin security ke liye kuch cheezein deliberately restrict hain — disk pe arbitrary files access nahi kar sakta, OS functions call nahi kar sakta, camera/mic bina explicit permission ke access nahi kar sakta, aur Same-Origin Policy ke wajah se ek origin ki tab dusre origin (alag domain/port/protocol) ke data ko directly touch nahi kar sakti.

📌 Languages "over" JavaScript

TypeScript (strict typing, Microsoft), CoffeeScript (syntactic sugar), Dart (Google, apna engine bhi hai), Flow (Facebook) — ye sab languages hain jo transpile hoke JavaScript ban jaati hain browser mein run hone se pehle. Inhe use karte waqt bhi underlying JS samajhna zaroori hai — kyunki transpiled output hi actually engine run karta hai.

Hello World — <script> tag ki anatomy

JavaScript HTML document mein almost kahin bhi <script> tag ke through insert ho sakta hai. Browser jaise hi is tag tak pahunchta hai, andar ka code automatically execute karta hai.

Basic HTML page with inline script
<!DOCTYPE HTML>                     <!-- doctype: browser ko batata hai ki HTML5 standards mode use karo -->
<html>                            <!-- root element: poora document isi ke andar -->
<body>                            <!-- visible content yahan se shuru hota hai -->

  <p>Before script</p>          <!-- ye paragraph script se PEHLE render hoga (top-to-bottom parsing) -->

  <script>                        <!-- script tag: JS code yahan ya src attribute se load hota hai -->
    alert('Hello, world!');    // browser parser yahan pahunchte hi ye line turant execute karta hai
  </script>

  <p>After script</p>           <!-- ye paragraph tab tak render nahi hoga jab tak alert() dismiss na ho -->

</body>
</html>

Purane HTML4-era code mein type="text/javascript" ya language="javascript" attributes milte the — dono aaj obsolete hain, modern HTML mein JavaScript default hai, likhna zaroori nahi.

External script — src attribute
<!-- Bade codebases ke liye alag .js file use karo, inline nahi -->
<script src="/path/to/script.js"></script>
                                     <!-- src: file ka absolute/relative path, browser ise separately fetch karta hai -->

<!-- INVALID: ek hi tag mein src AND inline code dono nahi ho sakte -->
<script src="file.js">
  alert(1);              // src ho to ye inline code SILENTLY ignore ho jaata hai
</script>

External script use karne ka root-level fayda: browser caching. Ek baar /path/to/script.js download ho gaya, to same URL wale sab pages usi cached copy ko reuse karte hain — bandwidth aur load-time dono bachte hain.

Code structure — statements, semicolons, comments

Statements syntax constructs hain jo actions perform karte hain (jaise alert(...) ek call statement hai). Convention hai unhe readability ke liye alag lines pe likhna, semicolon se terminate karke.

Semicolons — Automatic Semicolon Insertion (ASI) ka gotcha
alert("Hello")          // semicolon nahi hai, phir bhi engine newline dekh ke ASI trigger karta hai
alert("World")          // ye bhi apne aap terminate ho jaata hai — usually safe

// LEKIN — square bracket ke pehle ASI FAIL karta hai:
let a = 3                // semicolon missing
[1, 2].forEach(alert)  // engine isko "3[1, 2].forEach(alert)" padhta hai — ERROR!
// root cause: JS ko pata nahi ki previous statement khatam hua ya "3" ko index kiya ja raha hai

// SAFE fix: explicit semicolons hamesha likho — beginners ke liye best practice
let b = 3;               // explicit semicolon — ambiguity khatam
[1, 2].forEach(alert); // ab ye clearly ek naya independent statement hai
⚠️ Root cause: ASI kaam kaise karta hai

JS parser ek line ke end pe dekhta hai ki agar semicolon na daalein to syntax error aayega ya nahi — agar error aata hai, to wo automatically semicolon insert kar deta hai. Lekin [...] (indexing syntax bhi ho sakta hai) aur (...) (function call syntax bhi ho sakta hai) jaise ambiguous cases mein parser next line ko current statement ka hi continuation maan leta hai — kyunki syntactically dono valid interpretations hain. Isliye production codebases mein linters (ESLint) ya explicit semicolons se ye class of bug hamesha ke liye avoid kiya jaata hai.

Comments — single-line, multi-line, aur ek trap
// Single-line comment — is line ke end tak sab ignore
let x = 1;                // inline comment bhi chal sakta hai statement ke baad

/* Multi-line comment
   ye jitni bhi lines cover kare, sab ignore ho jaayengi
   jab tak closing */
let y = 2;

/* NESTED comments FAIL:
   /* ye andar wala comment */ alert('World'); /* ye extra */
// root cause: pehla "*/" hi poore multi-line comment ko close kar deta hai,
// baaki text ko engine normal code samajhne ki koshish karta hai — syntax error

Comments runtime pe koi cost nahi lagate — production build tools (minifiers) inhe strip kar dete hain deploy se pehle, isliye liberally comment karna free hai.

"use strict" — semantics kaise badalte hain

ES5 (2009) mein language mein naye features add hue, lekin backward compatibility todhne se bachne ke liye purana behavior default rakha gaya. "use strict" directive explicitly opt-in karta hai modern, stricter semantics mein.

"use strict" placement — TOP par hona zaroori hai
"use strict";              // script ke bilkul top pe — sirf comments ise precede kar sakte hain

let num = 5;          // is line se aage poora script strict mode mein chalega

// GALAT placement — strict mode ENABLE hi nahi hoga:
alert("some code");  // koi bhi real statement pehle aa gaya
"use strict";              // ye ab sirf ek harmless string literal hai, directive nahi
Function-scoped strict mode
function strictFn() {
  "use strict";            // sirf isi function ke andar strict mode active hoga
  let local = 1;       // local variable, strict semantics ke saath
}
// yahan bahar strict mode nahi hai (jab tak file-level directive na ho)
💡 Console gotcha

Browser DevTools console mein "use strict" pehli line pe likhna by default kaam nahi karta kyunki console default non-strict mode mein run hota hai. Fix: Shift+Enter se multi-line mode mein directive ko top pe rakho, ya poore code ko ek IIFE ((function(){ "use strict"; ... })()) ke andar wrap karo.

Important: strict mode ek baar activate hone ke baad disable nahi ho sakta — koi opposite directive exist nahi karta. Modern JS mein class aur ES module syntax automatically strict mode use karte hain, isliye unke saath directive likhna zaroori nahi. Lekin jab tak tum classes/modules exclusively use nahi kar rahe, top pe explicitly likhna hi safe default hai.

Variables — let/const/var, naming, aur ek hoisting preview

Modern JS mein variable declare karne ka default tareeka let hai. const same hai lekin reassignment allow nahi karta. var legacy keyword hai jiske scoping rules let se different hain (function-scoped vs block-scoped) — full detail Chapter 9 (Advanced Functions) mein milega, lekin abhi ke liye samajh lo ki var declarations apne function ke top pe "hoist" ho jaati hain (declaration upar chali jaati hai, assignment wahin rehta hai) — isi wajah se purana code mein var use se pehle bhi accessible dikh sakta hai (value undefined ke saath).

let vs const vs var — naming rules ke saath
let userName = "Sharad";     // camelCase — multi-word variable ka standard convention
let $element = null;       // $ aur _ valid pehla character hain (jQuery-style convention)
let _private = 1;         // underscore prefix, "internal use" signal karne ke liye convention

const COLOR_RED = "#F00";   // UPPER_SNAKE_CASE: hard-coded, run-time se pehle hi known constant
const pageLoadTime = Date.now();
                                    // lowercase const: value run-time pe CALCULATE hoti hai, hard-coded nahi

// GALAT: repeated let declaration — SyntaxError
let age = 20;
// let age = 25;   // Uncaught SyntaxError: Identifier 'age' has already been declared

// GALAT: const ko reassign karna — TypeError
const myBirthday = "18.04.1982";
// myBirthday = "01.01.2001"; // Uncaught TypeError: Assignment to constant variable
🧠 Senior Dev Note: var hoisting production mein kab bite karta hai

var ka hoisting behavior legacy codebases ya third-party scripts debug karte waqt confusing bugs create karta hai — e.g. ek if block ke andar declared var outside bhi accessible ho jaata hai (block scope nahi hota), jabki let/const strictly block-scoped hain. Modern linting configs (no-var ESLint rule) is entire class of bugs ko root pe hi disallow kar dete hain. Agar kabhi purana codebase migrate kar rahe ho, var → let/const switch karte waqt scope-leak wale edge cases carefully check karo.

8 Data Types aur typeof ke quirks

JavaScript dynamically typed hai — variable ka type value assign hone pe decide hota hai, aur runtime pe badal bhi sakta hai. Language mein total 8 data types hain: 7 primitive + 1 non-primitive (object).

Saare 8 types — ek nazar mein
let n = 123;              // Number: integers aur floats dono, ek hi type
n = 1 / 0;                  // Infinity — "kisi bhi number se bada" special value
n = "str" / 2;              // NaN — computational error, "sticky" hai (aage bhi NaN hi rahega)

let big = 123n;            // BigInt: 'n' suffix, ±(2^53-1) se bade integers ke liye

let str = `Hello ${n}`;   // String: backtick template literal, ${...} se expression embed hoti hai

let bool = true;          // Boolean: sirf true/false, comparisons ka result bhi yehi type deta hai

let age = null;          // null: "value KNOWN hai ki empty hai" — explicit "kuch nahi" assignment

let x;                       // undefined: declared but value assign nahi hui — engine default deta hai

let id = Symbol();      // Symbol: guaranteed-unique identifier, object keys ke liye use hota hai

let user = { name: "Sharad" };
                                // Object: sirf non-primitive type — collections/complex entities store karta hai
typeof — do famous historical quirks
typeof undefined;      // "undefined" — expected behavior
typeof 0;              // "number"
typeof true;           // "boolean"
typeof "foo";         // "string"
typeof Symbol();    // "symbol"

typeof null;           // "object"  ← QUIRK #1: officially-acknowledged language BUG,
                          // kept for backward compatibility from JS ke earliest days

typeof alert;          // "function" ← QUIRK #2: functions technically objects hain,
                          // lekin typeof convenience ke liye alag "function" string deta hai

Browser dialogs — alert / prompt / confirm

Ye teeno functions modal hain — jab tak user dismiss nahi karta, baaki page ka JS execution pause rehta hai aur user page ke saath interact nahi kar sakta. Ye browser-level UI hai, page ke CSS/DOM se completely disconnected — isliye style customize nahi kar sakte.

alert, prompt (default value ke saath), confirm
alert("Hello");       // sirf ek message dikhata hai, OK click hone tak execution ruka rehta hai

let age = prompt("Aapki age?", 18);
                            // 1st arg: title text; 2nd arg: default input value — ISE HAMESHA DO
                            // (purane IE mein bina 2nd arg ke literal "undefined" text bhar jaata tha)
// Cancel/Escape dabane pe prompt() null return karta hai, OK pe typed string

let isAdmin = confirm("Continue?");
                            // question dikhata hai, OK pe true, Cancel pe false return karta hai
⚠️ Production mein alert/prompt/confirm ka use limited hai

Position browser decide karta hai (usually center), styling zero customization allow nahi karti, aur ye synchronous blocking calls hain — production UI mein iske jagah custom modal components use hote hain. Ye teeno mostly debugging, prototyping, ya learning ke liye useful hain.

Type Conversion — implicit vs explicit rules

JavaScript operators aur functions apni marzi se values ko dusre type mein convert kar dete hain — isi ko implicit (type coercion) kehte hain. Root-level in teen conversions ko samajhna zaroori hai: String, Number, Boolean.

Explicit conversion — String(), Number(), Boolean()
String(false);        // "false" — straightforward: value ka readable string form
String(null);         // "null"

Number(undefined);    // NaN — "value hi nahi hai" ko meaningfully number nahi bana sakte
Number(null);         // 0 — null ko "empty" treat karke zero diya jaata hai
Number(true);         // 1
Number(false);        // 0
Number("   123   ");  // 123 — leading/trailing whitespace trim ho jaata hai (space/tab/newline)
Number("");          // 0 — empty string "no value" ke jaisa treat hoti hai
Number("123z");       // NaN — koi bhi invalid trailing content pura parse fail kar deta hai

Boolean(0);          // false — falsy value #1
Boolean("");         // false — falsy value #2 (empty string)
Boolean("0");        // true  ← GOTCHA: non-empty string hamesha truthy, chahe content "0" ho
Boolean(" ");        // true  — space bhi non-empty string hai, so truthy
⚠️ Famous gotchas: [] + [] aur [] + {}

Ye classic interview trick questions hain jo implicit coercion ki root mechanics test karte hain. [] + [] pehle dono arrays ko String() se convert karta hai (kyunki + operator objects pe string-conversion prefer karta hai jab tak dono numeric na hon) — empty array ka string form "" hai, so result "" + "" = "" (empty string). Doosri taraf [] + {} — array "" banta hai, plain object "[object Object]" banta hai (uska default toString()), so result "[object Object]" ek string hai. Root cause: + operator dono operands ko pehle "primitive" mein convert karta hai (ToPrimitive abstract operation), aur objects/arrays ke liye default hint "default" hota hai jo valueOf() try karta hai (jo objects/arrays ke liye kuch useful nahi deta, so fallback toString() pe jaata hai).

Debugging console mein verify karo
console.log([] + []);     // "" — dono empty arrays "" mein convert hote hain, phir concatenate
console.log([] + {});     // "[object Object]" — {} ka default toString() ye string deta hai
console.log(1 + "2");     // "12" — number string ke saath mile to number bhi string ban jaata hai
console.log("5" - 1);     // 4 — '-' operator sirf numeric context mein kaam karta hai, string coerce ho jaati hai
🧠 Senior Dev Note: implicit coercion se production mein bachna

Real-world codebases mein == (loose equality) aur implicit + coercion bahut saare subtle bugs ka source hote hain — jaise API se aayi "0" string ko truthy check karte waqt accidentally true treat kar lena. Isi liye senior teams strict equality (===) enforce karti hain, TypeScript jaisi tools use karti hain (jo implicit coercion ko compile-time pe flag karti hain), aur explicit conversions (Number(x), String(x), !!x) prefer karti hain taaki intent code mein saaf dikhe, engine ke internal rules pe implicitly depend na karna pade.

Key Takeaways

  • JS engines (V8, SpiderMonkey, JavaScriptCore) parse → JIT-compile → execute-and-optimize cycle follow karte hain; language purely interpreted ya compiled nahi hai.
  • In-browser JS Same-Origin Policy aur explicit permissions se security-restricted hai — disk/OS/camera direct access allowed nahi.
  • <script src> aur inline code ek hi tag mein saath nahi ho sakte; external scripts caching ka fayda dete hain.
  • Semicolons technically ASI se optional hain, lekin [...]/(...) ke pehle ASI fail hota hai — production code mein explicit semicolons safest hain.
  • "use strict" file/function ke bilkul TOP pe hona zaroori hai, irreversible hai, aur classes/modules mein automatic hai.
  • let/const block-scoped hain, var function-scoped + hoisted hota hai — legacy code debug karte waqt ye difference critical hai.
  • 8 data types: number, bigint, string, boolean, null, undefined, symbol, object — typeof null === "object" aur typeof function === "function" dono historical quirks hain.
  • Type conversion rules memorize karne se zyada important hai kyun samajhna: numeric conversion whitespace trim karta hai, boolean conversion sirf 5 falsy values maanta hai (0, "", null, undefined, NaN), aur + operator object-coercion mein string ko prefer karta hai.

🎯 Interview Questions

  • JS engine ke andar teen phases kya hain, aur JIT compilation ka role kya hai?
    Hint: Parse (AST banana) → Compile (JIT se machine code) → Execute+Optimize (runtime data dekh ke hot paths ko re-optimize karna); isi wajah se JS "hybrid" hai, purely interpreted ya compiled nahi.
  • typeof null "object" kyun return karta hai?
    Hint: JS ke earliest implementation mein ek bug tha jo backward compatibility ki wajah se aaj tak fix nahi kiya gaya — officially acknowledged language quirk hai.
  • ASI (Automatic Semicolon Insertion) kab fail hota hai, aur kaise avoid karein?
    Hint: line ki agli statement [ ya ( se shuru ho to engine previous line ka continuation maan leta hai; explicit semicolons se avoid karo.
  • var aur let mein scoping ka fundamental difference kya hai?
    Hint: var function-scoped + hoisted (declaration top pe chali jaati hai, value undefined rehti hai use se pehle); let block-scoped, temporal dead zone mein hota hai use se pehle.
  • [] + [] aur [] + {} ka result kya hoga aur kyun?
    Hint: + operator objects ko ToPrimitive se convert karta hai (default hint), jo valueOf() fail hone pe toString() use karta hai — empty array "" banti hai, plain object "[object Object]" banta hai.
  • Boolean("0") aur Number("0") alag result kyun dete hain?
    Hint: Boolean conversion sirf empty string ko falsy maanta hai, non-empty content wali koi bhi string truthy hai — chahe wo "0" text hi kyun na ho; Number conversion actual numeric parsing karta hai.
  • "use strict" ko file ke top pe hi kyun likhna zaroori hai?
    Hint: parser directive ko sirf tab recognize karta hai jab wo pehla real statement ho (sirf comments allowed pehle); kisi bhi executable statement ke baad likhne se ye sirf ek harmless string literal ban jaata hai.
  • Production codebases implicit type coercion (==, +) se kyun bachte hain?
    Hint: subtle bugs (jaise API se aayi "0" string ko truthy treat karna) create karta hai; strict equality (===) aur explicit conversions (Number(), String()) intent ko readable aur predictable banate hain, TypeScript jaisi tools bhi compile-time pe isse catch karti hain.
