Network II — XHR/WS/SSE

Chapter 26 mein humne fetch() dekha tha — modern, Promise-based, clean. Lekin fetch har network use-case ko cover nahi karta. Agar tumhe real upload progress chahiye (jaise file upload UI mein progress bar), fetch ke paas native way nahi hai — is gap ko XMLHttpRequest fill karta hai. Agar tumhe server se push chahiye (server pehle data bhejta hai, client request nahi karta), to teen options hain: long polling (pre-WebSocket era ka hack), WebSocket (full duplex persistent connection), aur Server-Sent Events (one-way server→client stream, HTTP par hi). Ye chapter in sabka root-level breakdown hai — kaunsa tool kab use karna hai, aur andar se kaise kaam karta hai.

XMLHttpRequest abhi bhi kyun zaroori hai

Naam "XML" ka hai kyunki ye 1999 mein IE5 ke ActiveX object se born hua tha jab XML hi de-facto data format tha — aaj ye kisi bhi data (JSON, text, binary) ke saath kaam karta hai. fetch() aaj default choice hai, lekin XHR ko purani codebase ke alawa ek genuine root-level reason se aaj bhi use kiya jaata hai:

🧠 Senior Dev Note: fetch mein upload progress natively nahi hai

fetch() ka Response object response.body ke through download progress track karne deta hai (ReadableStream reader se), lekin upload progress ke liye koi native, cross-browser, stable event nahi hai. Jab tum ek badi file (video, dataset, image) upload kar rahe ho aur user ko "45% uploaded" wala progress bar dikhana hai, fetch se ye reliably possible nahi — XHR ke xhr.upload.onprogress event ke bina ye UI feature banana mushkil hai. Yahi single reason hai jiski wajah se production file-upload code aaj bhi XHR use karta hai, sirf legacy support ke liye nahi.

XHR basics — open / send / events

XHR ka core object-lifecycle 3-step hai: object banao, open() se configure karo (ye sirf method/URL set karta hai, connection abhi nahi khulti — naam misleading hai), phir send() se actual request fire hoti hai.

XHR basic GET request
// Step 1: naya XHR object banao — har request ke liye ek naya instance chahiye, reuse nahi hota
let xhr = new XMLHttpRequest();

// Step 2: open() sirf METHOD aur URL configure karta hai — connection abhi NAHI khulti
// teesra param 'true' = asynchronous mode (default bhi true hi hai, explicit likhna best practice)
xhr.open('GET', '/api/users', true);

// load event: response fully aa chuka hai (chahe status 200 ho ya 404 — 'load' fire hota hai HTTP error pe bhi)
xhr.onload = function() {
  // xhr.status: HTTP status code (200, 404, 500, etc.)
  if (xhr.status !== 200) {
    console.error(`Error: ${xhr.status}`); // non-2xx bhi 'load' hi hai, error event NAHI
  } else {
    // xhr.response: parsed response body (responseType ke hisaab se), xhr.responseText raw text ke liye
    console.log('Done: ' + xhr.response);
  }
};

// error event: sirf tab fire hota hai jab request hi execute NAHI ho paayi (network down, CORS block, DNS fail)
xhr.onerror = function() {
  console.error('Network request failed entirely'); // yaha status code ka koi matlab nahi, request pahunchi hi nahi
};

// progress event: DOWNLOAD ke dauran periodically fire hota hai (jab response bytes aa rahe hon)
xhr.onprogress = function(event) {
  // event.loaded: ab tak kitne bytes download hue; event.total: Content-Length se pata chala total (agar server ne bheja)
  console.log(`Downloaded ${event.loaded} of ${event.total}`);
};

// Step 3: ab actual request fire hoti hai — GET ke liye body null pass karte hain
xhr.send();

Root-level: XHR internally readyState naam ki state machine se guzarta hai — UNSENT(0) → OPENED(1) → HEADERS_RECEIVED(2) → LOADING(3) (ye state response ke har chunk ke liye repeat hota hai) → DONE(4). Purana code onreadystatechange listener laga ke readyState === 4 check karta tha — modern code isse avoid karta hai kyunki load/error/progress events zyada readable aur specific hain.

xhr.upload.onprogress — real upload progress

Ye XHR ka sabse important unique feature hai. xhr.upload ek alag sub-object hai jispe sirf upload-direction ke events fire hote hain — progress, load, error, abort. Iska root reason: normal xhr object pe lage onprogress download track karta hai, jabki xhr.upload pe laga onprogress outgoing request body track karta hai.

File upload with real progress bar
let xhr = new XMLHttpRequest();
xhr.open('POST', '/upload', true);

// xhr.upload.onprogress: sirf UPLOAD (request body jaana) ke bytes track karta hai
xhr.upload.onprogress = function(event) {
  // event.loaded: kitne bytes ab tak network socket ko diye ja chuke (OS-level buffer tak)
  // event.total: File.size se pata chala total upload size
  const percent = Math.round((event.loaded / event.total) * 100); // 0-100 % nikala
  progressBar.style.width = percent + '%'; // UI progress bar update
};

// upload.onload: request body poora bhej diya gaya (browser ne — server tak pahuncha ye guarantee NAHI)
xhr.upload.onload = function() {
  console.log('Upload finished, waiting for server response...');
};

// upload.onerror: network fail hua upload ke dauran hi
xhr.upload.onerror = function() {
  console.error('Upload failed');
};

// FormData: multipart/form-data body banane ka standard tareeka, file input se seedha use hota hai
let formData = new FormData();
formData.append('file', fileInput.files[0]); // user ne select ki hui file object

xhr.send(formData); // yahi call se upload.onprogress trigger hona shuru hota hai
⚠️ upload.onprogress = "browser ne bheja", "server ne receive kiya" nahi

Root cause samajhna zaroori hai: event.loaded sirf ye batata hai ki browser ne kitne bytes apne local network stack (TCP send buffer) mein daal diye — ye guarantee nahi deta ki server ne unhe actually receive kar liya hai, disk pe likh diya hai, ya process crash nahi hui. Isliye ye event visual feedback ke liye perfect hai, lekin resume-after- failure logic ke liye bharosemand nahi — us guarantee ke liye server se explicitly poochna padta hai (agla section: resumable upload).

Synchronous XHR mode — kabhi use mat karo

xhr.open() ka teesra parameter false set karne se XHR synchronous ban jaata hai — matlab xhr.send() call tab tak return hi nahi karega jab tak poora response na aa jaaye, aur is dauran poora JS thread block rehta hai (UI freeze, koi bhi click/scroll/render nahi ho sakta).

Synchronous XHR — sirf dikhane ke liye, PRODUCTION mein NAHI
let xhr = new XMLHttpRequest();
xhr.open('GET', '/api/data', false); // 3rd arg 'false' = SYNCHRONOUS — main thread yahin ruk jaayega
try {
  xhr.send(); // is line pe JS THREAD FREEZE ho jaata hai jab tak response na aaye
  if (xhr.status == 200) {
    console.log(xhr.responseText); // send() ke baad hi response ready hoga, synchronously
  }
} catch (err) {
  console.error('Sync request failed'); // sync mode mein errors try/catch se aate hain, event se nahi
}
⚠️ Root cause: JS single-threaded hai, aur sync XHR event loop ko bypass karta hai

Browser ka rendering aur JS execution ek hi thread pe hota hai (main thread). Async operations (fetch, async XHR, setTimeout) event loop ke through non-blocking hote hain — call turant return ho jaata hai, result baad mein callback/Promise se aata hai. Synchronous XHR is model ko todta hai: send() call khud blocking hai, andar se browser ek nested event loop chala ke response ka wait karta hai — is dauran koi bhi UI update, click handler, ya doosra script execute nahi ho sakta. Isi wajah se sabhi major browsers ne main thread pe synchronous XHR ko deprecate kar diya hai (console warning aati hai), aur naye features jaise timeout ya cross-origin requests sync mode mein kaam hi nahi karte. Real use-case sirf ek hai: worker thread ke andar (jahan blocking se main UI thread affect nahi hota) — kabhi bhi main thread pe iska use mat karo.

Resumable file upload pattern

Bade files (video, backups) upload karte waqt network beech mein girna common hai. Naive approach — pura upload dobara shuru karna — bandwidth aur time dono waste karta hai. Resumable upload pattern server ko yaad rakhne deta hai ki kitna already receive ho chuka hai, aur client sirf baaki hissa bhejta hai.

🧠 Senior Dev Note: upload.onprogress resume ke liye kaafi kyun nahi

Jaisa upar dekha, upload.onprogress sirf "browser ne bheja" batata hai — server crash ho sakta hai, buffer drop ho sakta hai, ya connection beech mein reset ho sakta hai bina client ko turant pata chale. Isliye resumable upload ka source of truth server hai, progress event nahi — client ko explicitly server se poochna padta hai "tumhare paas is file ke kitne bytes already hain?" phir wahi se aage bhejna hai.

Resumable upload — client-side logic (XHR + Blob.slice)
async function uploadResumable(file) {
  // fileId: filename + size + last-modified timestamp se ek stable unique key banaya —
  // taaki same file ko dobara upload karne pe server pehchaan sake, session crash ke baad bhi
  const fileId = `${file.name}-${file.size}-${file.lastModified}`;

  // Step 1: server se poochho ki is fileId ke kitne bytes already stored hain (resume point)
  let startByte = 0;
  const statusRes = await fetch('/upload-status', {
    headers: { 'X-File-Id': fileId } // custom header — server iski file lookup karega
  });
  if (statusRes.ok) {
    startByte = await statusRes.json(); // server return karta hai: kitne bytes already hain (0 = naya upload)
  }

  if (startByte === file.size) {
    console.log('File already fully uploaded'); // pura already ho chuka — kuch aur karne ki zaroorat nahi
    return;
  }

  // Step 2: XHR use kiya (fetch nahi) kyunki humein upload.onprogress chahiye baaki-bacha-hissa track karne ke liye
  let xhr = new XMLHttpRequest();
  xhr.open('POST', '/upload', true);
  xhr.setRequestHeader('X-File-Id', fileId);            // kaunsi file hai
  xhr.setRequestHeader('X-Start-Byte', startByte);   // server yahaan se validate karega ki continuity sahi hai

  xhr.upload.onprogress = (event) => {
    // total progress = jo pehle se ho chuka (startByte) + is chunk mein ab tak bheja gaya (event.loaded)
    const totalLoaded = startByte + event.loaded;
    const percent = Math.round((totalLoaded / file.size) * 100);
    console.log(`${percent}% uploaded`);
  };

  // Step 3: Blob.slice(startByte) — file ke sirf BAAKI bacha hissa hi bhejo, shuru se nahi
  const remainingChunk = file.slice(startByte); // Blob.slice(start): naya Blob jo original ka sirf ek portion hai
  xhr.send(remainingChunk); // yahi request body mein sirf remaining bytes jaate hain, poori file nahi
}

Server-side responsibility: X-Start-Byte header ko apne stored byte-count se match karna (agar mismatch hai, matlab beech mein kuch corrupt hua — reject kar do aur pura restart maango), phir incoming bytes ko existing file ke end mein append karna. Ye pattern chunked upload libraries (jaise tus, resumable.js) ka foundation hai — bade production systems mein chunk-size fixed (jaise 5MB) rakhi jaati hai taaki ek chunk fail ho to sirf wahi retry ho, pura file nahi.

Long polling — pre-WebSocket server push

Server "push" (server pehle bolta hai, client request nahi karta) achieve karne ka sabse purana aur simplest tareeka. Regular polling (har N second pe poochna) mein do problems hain: fresh data ka delay (up to N seconds), aur jab kuch naya nahi hai tab bhi server pe unnecessary requests. Long polling dono fix karta hai.

Long polling — client-side loop
async function subscribe() {
  let response = await fetch("/subscribe"); // server ye request ko turant reply NAHI karega — hold karke rakhega

  if (response.status == 502) {
    // 502 = connection timeout error, ye long-poll ke liye NORMAL hai (server/proxy ne connection band kiya)
    // koi problem nahi — turant dobara subscribe karo
    await subscribe();
  } else if (response.status != 200) {
    // koi aur error — thoda ruk ke retry karo (crash-loop se bachne ke liye backoff)
    console.error(response.statusText);
    await new Promise(resolve => setTimeout(resolve, 1000)); // 1 second wait
    await subscribe();
  } else {
    // success — asli message mila hai server se
    let message = await response.text();
    showMessage(message); // UI mein render karo
    await subscribe(); // ZAROORI: message milte hi turant naya subscribe call karo, taaki agla push miss na ho
  }
}

subscribe(); // pehli baar loop start karo

Server-side ka core idea: request aane pe response object ko turant close mat karo — memory mein pending list mein daal ke rakh lo. Jab koi naya message aaye (kisi doosre event se trigger hoke), us list ke sabhi pending responses ko reply bhejo aur unhe close karo. Client foran naya subscribe request bhejta hai, so overall "connection" continuous lagta hai chahe technically har baar naya HTTP request/response cycle hai.

⚠️ Long polling sirf rare messages ke liye theek hai

Har message ke baad ek naya HTTP request+response cycle hota hai — poore headers, cookies, authentication check dobara. Agar messages frequent hain (jaise chat mein fast typing indicators, ya real-time game state), ye overhead significant ban jaata hai. Frequent bidirectional traffic ke liye WebSocket zyada efficient hai.

WebSocket — full duplex persistent connection

WebSocket (RFC 6455) ek alag protocol hai jo HTTP se upgrade hoke shuru hota hai, phir ek single TCP connection dono directions mein khula rehta hai — client aur server dono kabhi bhi, bina naya request/response cycle banaye, data bhej sakte hain. Isse "full duplex" kehte hain.

WebSocket handshake — HTTP Upgrade request
// Client browser jab new WebSocket() banata hai, ye HTTP GET request bhejta hai (raw form):
// GET /chat HTTP/1.1
// Host: example.com
// Upgrade: websocket          <- browser bata raha hai "mujhe protocol switch karna hai"
// Connection: Upgrade         <- HTTP connection ko websocket mein upgrade karo
// Sec-WebSocket-Key: dGhlIHNhbXBsZQ==   <- random value, server isse hash karke wapas bhejta hai (handshake verify)
// Sec-WebSocket-Version: 13   <- protocol version

// Agar server WebSocket support karta hai, wo normal 200 OK NAHI, balki ye special response deta hai:
// HTTP/1.1 101 Switching Protocols   <- 101 = "main HTTP se websocket protocol pe switch kar raha hoon"
// Upgrade: websocket
// Connection: Upgrade
// Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=   <- Sec-WebSocket-Key ka hashed proof

// Is point ke baad TCP connection ab HTTP nahi hai — ye raw WebSocket frames carry karta hai
WebSocket client API
// wss:// = encrypted WebSocket (TLS ke saath) — production mein hamesha ye use karo, ws:// nahi
// (kai proxies ws:// ke unfamiliar headers ko block/mangle kar dete hain, wss:// safe hai)
let socket = new WebSocket("wss://example.com/chat"); // constructor call hote hi connection attempt SHURU ho jaata hai

// open: handshake successful, connection ab live hai
socket.onopen = function(event) {
  console.log("Connected");
  socket.send("Hello server!"); // send(): text ya binary (Blob/ArrayBuffer) bhej sakte ho, kabhi bhi, dono directions se
};

// message: server se koi bhi data aaya — kisi bhi time, koi request-response pairing nahi
socket.onmessage = function(event) {
  console.log("Received: " + event.data); // event.data: string ya Blob/ArrayBuffer (binaryType pe depend)
};

// close: connection band ho gaya — chahe normal ho ya error se
socket.onclose = function(event) {
  if (event.wasClean) {
    console.log(`Closed cleanly, code=${event.code}`); // code 1000 = normal closure
  } else {
    console.log("Connection died"); // e.g. code 1006 = abnormal, network gaya
  }
  // NOTE: yahaan pe manual reconnect logic likhni padegi — WebSocket khud reconnect NAHI karta
};

// error: connection-level problem (close bhi automatically fire hoga error ke baad)
socket.onerror = function(error) {
  console.log("Error: " + error.message);
};

// rate limiting: bufferedAmount batata hai kitne bytes abhi queue mein hain (socket ne network ko pass nahi kiye)
function sendIfReady(data) {
  if (socket.bufferedAmount == 0) { // 0 matlab pichla data flush ho chuka, slow connection ko flood mat karo
    socket.send(data);
  }
}

WebSocket protocol khud reconnection, authentication, ya heartbeat jaisi high-level concerns handle nahi karta — ye sab application-level responsibility hai (ya library jaise socket.io use karo jo inhe wrap karti hai).

Server-Sent Events (SSE) — one-way server → client stream

SSE ek middle-ground hai: WebSocket jitna heavy nahi (plain HTTP par chalta hai, alag protocol upgrade nahi chahiye), lekin long polling se zyada efficient (ek hi connection persistent rehta hai). Limitation: sirf server → client direction — client se data bhejna ho to normal fetch/XHR use karna padta hai.

EventSource client
// EventSource: browser ka built-in SSE client — normal HTTP GET request karta hai jo persistent stream deta hai
let eventSource = new EventSource("/events");

// message: default event type — koi bhi 'event:' field na ho to yahi fire hota hai
eventSource.onmessage = function(event) {
  console.log("New message: " + event.data); // event.data: server ke 'data:' field ka content
  console.log("Last id: " + eventSource.lastEventId); // last-seen 'id:' field, reconnect ke liye internally use hota hai
};

// custom event type: agar server ne 'event: username' bheja hai to us naam se listener lagao
eventSource.addEventListener("username", function(event) {
  console.log("Username event: " + event.data);
});

// error: fire hota hai jab connection drop ho — LEKIN EventSource khud reconnect karega, tumhe kuch nahi karna
eventSource.onerror = function() {
  if (eventSource.readyState == EventSource.CONNECTING) {
    console.log("Reconnecting..."); // state 0: browser khud dobara connect try kar raha hai
  } else if (eventSource.readyState == EventSource.CLOSED) {
    console.log("Connection permanently closed"); // state 2: server ne 204 bheja ya fatal error — ab reconnect nahi hoga
  }
};
Server response format — text/event-stream
// HTTP response headers server ko ye bhejne chahiye:
// Content-Type: text/event-stream    <- browser ko batata hai "ye SSE stream hai"
// Cache-Control: no-cache
// Connection: keep-alive

// Body format — plain text, line-based, do newlines se message end hota hai:
id: 1                           // is message ka unique id — reconnect ke baad Last-Event-ID isi se bhejega
data: {"user":"John","text":"Hi"}  // actual payload — JSON string common hai, escape karke
                                 // (khaali line = message ka end, browser isi pe parse trigger karta hai)

event: username                 // custom event type — client ke addEventListener("username") isse match hota hai
data: John

retry: 10000                    // server batata hai: agar connection tootey, 10 second baad reconnect try karo
data: heartbeat
🧠 Senior Dev Note: automatic reconnect + Last-Event-ID = built-in resume

SSE ka sabse underrated feature: connection kabhi bhi drop ho (network blip, server restart), browser khud-ba-khud reconnect karta hai (default ~3 seconds baad, ya server ke retry: field se override), aur reconnect request mein automatically ek Last-Event-ID HTTP header attach karta hai jiski value last-received id: hoti hai. Server is header ko dekh ke exactly wahin se aage ka data bhej sakta hai — matlab resume-from-disconnect logic WebSocket mein manually likhni padti hai (apna id-tracking + reconnect loop), jabki SSE mein ye protocol-level built-in hai. Ye ek genuine reason hai SSE choose karne ka jab tumhe sirf server→client stream chahiye aur reliable resume bhi chahiye, bina custom reconnection code likhe.

Agar server HTTP status 204 No Content return kare, EventSource permanently reconnect karna band kar deta hai (server ka signal: "is stream ka ab koi future nahi").

Comparison: Long Polling vs WebSocket vs SSE

PropertyLong PollingWebSocketServer-Sent Events
Direction Client→Server request-response (fake push) Bidirectional (full duplex) Server→Client only (one-way)
Protocol Plain HTTP, repeated requests Alag protocol (ws/wss), HTTP Upgrade se shuru Plain HTTP, single persistent connection
Protocol overhead High — har message pe naye headers, auth, TCP handshake possible Low — ek baar handshake, phir sirf frames (2-14 byte overhead/msg) Low — ek connection, text-based simple format
Auto-reconnect Manual (khud recursive call likhna hai) Manual (onclose mein khud reconnect logic) Built-in — browser automatically reconnect karta hai
Resume after disconnect N/A (naya request hi hai) Manual (apna sequence/id tracking likhna padta hai) Built-in — Last-Event-ID header automatically bhejta hai
Binary data Ha (normal HTTP body) Ha (Blob/ArrayBuffer native support) Nahi — sirf text/UTF-8
Browser connection limit Normal HTTP limit lagta hai (6 per origin HTTP/1.1) Separate — apna limit hai, HTTP requests se conflict nahi HTTP/1.1 pe 6-connection limit se conflict ho sakta hai (HTTP/2 pe nahi)
Best use case Rare messages, koi WS/SSE infra nahi, simplest fallback Chat, multiplayer games, live trading, collaborative editing Live feeds, notifications, stock tickers, log streaming, progress updates
📌 Kaunsa choose karein — decision shortcut

Agar client ko bhi server ko continuously data bhejna hai (chat, game, collab editor) → WebSocket. Agar sirf server se ek-tarfa (one-way) updates chahiye (notifications, live scores, log tail, progress) aur automatic resume chahiye bina extra code ke → Server-Sent Events. Agar infra constraints hain (proxy WebSocket support nahi karta, ya bahut simple/rare updates hain) aur naya protocol setup nahi karna → long polling reasonable fallback hai. Real systems (jaise Socket.IO) internally WebSocket try karte hain, fail ho to long polling pe automatically fallback kar jaate hain.

Key Takeaways

  • XHR aaj bhi zaroori hai kyunki xhr.upload.onprogress se real upload progress milta hai — fetch ke paas iske liye native event nahi hai.
  • Synchronous XHR (open() ka 3rd arg false) main thread ko block karta hai — sirf worker context mein use karne layak, kabhi bhi main thread pe nahi.
  • Resumable upload mein server hi source-of-truth hai (kitne bytes already receive hue) — upload.onprogress sirf visual feedback deta hai, resume-guarantee nahi.
  • Long polling = client request bhejta hai, server jab tak message na ho tab tak response hold karta hai — rare-message scenarios ke liye simplest server-push technique.
  • WebSocket ek HTTP Upgrade handshake se shuru hokar ek persistent, full-duplex TCP connection banata hai — bidirectional real-time apps ke liye best.
  • SSE (EventSource) plain HTTP par one-way server→client stream deta hai, auto-reconnect aur Last-Event-ID header se resume-after-disconnect built-in milta hai.
  • WebSocket mein reconnection/resume manually likhni padti hai; SSE mein wo protocol-level pehle se available hai — lekin SSE bidirectional nahi hai aur sirf text data support karta hai.

🎯 Interview Questions

  • fetch() hote hue bhi XMLHttpRequest ka ek genuine modern use-case batao.
    Hint: real upload progress tracking — xhr.upload.onprogress, jo fetch native provide nahi karta.
  • Synchronous XHR se main thread pe kya problem hoti hai, aur root cause kya hai?
    Hint: JS single-threaded hai; sync send() internally nested event loop chala ke block karta hai, isliye UI freeze hoti hai — deprecated hai, sirf worker context mein theek hai.
  • upload.onprogress ka event.loaded reliably batata hai ki server ne data receive kar liya?
    Hint: Nahi — ye sirf browser ke local send buffer tak ka status hai, server-level acknowledgment nahi. Isi wajah se resumable upload mein server se explicitly status poochna padta hai.
  • Long polling regular (interval-based) polling se better kyun hai?
    Hint: server response tab tak hold karta hai jab tak message na ho — isse fixed-interval delay khatam hota hai aur empty-check requests kam hoti hain.
  • WebSocket handshake technically kya hai — HTTP request hai ya nahi?
    Hint: Ye ek HTTP GET request hi hai jisme Upgrade: websocket aur Connection: Upgrade headers hote hain; server 101 Switching Protocols return karta hai aur usi TCP connection par phir WebSocket frames chalte hain.
  • SSE mein Last-Event-ID header kaise kaam karta hai, aur ye WebSocket se kaise alag hai?
    Hint: SSE mein browser khud last-received id: ko reconnect request mein Last-Event-ID header se bhej deta hai — server-side resume automatic hai. WebSocket mein aisa koi built-in mechanism nahi, developer ko khud sequence-id tracking likhni padti hai.
  • SSE aur WebSocket mein se kab kaunsa choose karoge?
    Hint: sirf server→client updates aur auto-resume chahiye (notifications, live feed) → SSE; bidirectional real-time (chat, game) chahiye → WebSocket.
  • WebSocket ka bufferedAmount property kis problem ko solve karta hai?
    Hint: slow ya congested connection pe agar tum bina check kiye continuously send() karte raho, data local queue mein backlog ho jaata hai — bufferedAmount === 0 check karke hi agla chunk bhejna rate-limiting/backpressure implement karta hai.
