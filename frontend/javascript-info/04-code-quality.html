Chrome DevTools mein debugging — root-cause workflow

console.log chhidwana debugging nahi hai, wo sirf ek "guess and print" loop hai. Real debugging Chrome ke Sources panel mein hoti hai, jiske teen hisse hote hain: File Navigator (left — HTML/JS/CSS files), Code Editor (center — source dikhata hai), aur JS Debugging pane (right — breakpoints, watch, call stack, scope).

Jab tum line-number pe click karte ho, ek breakpoint set hota hai — execution us line pe pahunchte hi pause ho jaati hai (before wo line run ho). Right-click karke conditional breakpoint bhi laga sakte ho — sirf tab pause hoga jab tumhara diya hua expression truthy ho, jaise i === 5 — loop ke 5th iteration tak baar-baar F8 dabane se bachne ka tareeka.

debugger statement — code-level breakpoint
function calculateDiscount(price, userTier) {              // function jo price pe discount lagati hai userTier ke hisaab se
  let discount = 0;                                        // discount ka default value 0 — agar koi tier match na kare

  if (userTier === "gold") {                        // gold tier ke liye alag discount rate
    discount = 0.2;                                      // 20% discount gold users ko
  } else if (userTier === "silver") {                // silver tier ke liye kam discount
    discount = 0.1;                                      // 10% discount silver users ko
  }

  debugger;                                              // DevTools khula ho to execution YAHIN pause ho jaayegi
  // yahaan pause karke Watch panel mein "discount" aur "price" ki values check kar sakte hain

  return price - (price * discount);                    // final discounted price return karo
}

calculateDiscount(1000, "gold");                              // isko call karte hi debugger line pe automatic pause hoga

Jab execution pause hoti hai (breakpoint ho ya debugger statement), teen panels active ho jaate hain:

  • Watch — koi bhi expression type karo (jaise discount * 2), wo har step pe recalculate hoke value dikhayega.
  • Call Stack — kaunsi functions kis order mein call hue taaki tum yahaan pahunche, bottom-most caller se top-most current function tak.
  • Scope — local variables (current function ke) aur global variables, current values ke saath; source code mein bhi highlighted dikhte hain.

Step-through toolbar ke buttons (in exact order jab kaam aate hain):

ButtonShortcutKya karta hai
ResumeF8Agla breakpoint aane tak normal execution continue karo
StepF9Sirf next statement execute karo (ek line aage badho)
Step overF10Next statement run karo, lekin agar wo function call hai to uske andar mat jao
Step intoF11Step jaisa hi, lekin async calls (promises) ke andar bhi ja sakta hai

🧠 Senior Dev Note: Step Over vs Step Into

Ye distinction production debugging mein bahut matter karta hai. Agar tumhe pata hai ki bug tumhare current function ke logic mein hai, na ki kisi library function (jaise lodash.cloneDeep) ke andar, to hamesha Step Over (F10) use karo — warna tum third-party library ke internals mein bhatak jaoge, jahan bug nahi hai. Step Into (F11) sirf tab use karo jab tumhe apne khud ke helper function ke andar ka logic verify karna ho. Aur "Continue to here" (right-click on any line) ek underrated feature hai — loop ke beech kisi specific iteration tak jaldi pahunchne ke liye, bina baar-baar F8 dabaye.

console.log() apni jagah hai — execution pause kiye bina values print karta hai, production mein bhi safe hai (agar remove kar do baad mein). Lekin real root-cause investigation ke liye breakpoints + scope inspection zyada reliable hai, kyunki tumhe pata rehta hai exact moment pe variable ki value kya thi, aur call stack se pata chalta hai kaise wahan pahunche.

Coding style — team-readable code

Style rules ka goal readability hai, "sahi" ya "galat" nahi — lekin ek team mein consistency zaroori hai taaki koi bhi kisi ka bhi code padh sake bina mental context-switch ke.

style rules — before vs after
// ❌ BAD — inconsistent braces, no spacing, deep nesting, no early return
function showPrice(user,item)
{
  if(user)
  {
    if(item){
      if(item.price>0)
        return item.price;
    }
  }
}

// ✅ GOOD — Egyptian braces (opening brace same line), early returns, flat structure
function showPrice(user, item) {            // opening { usi line pe, ek space ke baad — "Egyptian style"
  if (!user) return;                          // early return — special case pehle nikaal do, nesting mat badhao
  if (!item) return;                          // dusra early return — ab humein pata hai item exist karta hai
  if (item.price <= 0) return;            // teesra early return — invalid price ka case

  return item.price;                              // ab yahan sirf "main" logic bacha hai, ek hi nesting level pe
}

Kuch aur core rules jo javascript.info recommend karta hai:

  • Line length — bahut lambi horizontal line padhna mushkil hota hai; team-agreed max (typically 80-120 chars) se zyada ho to break karo multiple lines mein.
  • Indent — 2 ya 4 spaces consistently; tabs se zyada spaces common hain kyunki alignment predictable rehta hai across editors.
  • Vertical spacing — logical blocks ke beech blank line do; 9 lines se zyada bina break ke ek function mein rakhna readability hurt karta hai.
  • Semicolons — har statement ke baad lagao, chahe ASI (automatic semicolon insertion) unhe optional bana de — kuch edge-cases mein ASI galat jagah semicolon insert kar deta hai aur silent bugs create karta hai.
  • Function placement — generally "code pehle, helper functions neeche" pattern better hai, kyunki reader pehle purpose samajhta hai, phir implementation detail — top-down reading flow.
📌 Linters — style ko automate karo

Manually style follow karna scale nahi karta. ESLint jaisa linter code style check karta hai aur bugs bhi pakadta hai (jaise typo se bana hua undefined variable use karna). Setup: Node.js install karo, ESLint install karo, .eslintrc config file banao (ya popular style guide extend karo — Airbnb, Google, StandardJS), editor plugin lagao jo save-on-type errors dikhaye. Team mein CI pipeline mein bhi lint-check add karna common practice hai.

Comments — sirf "why", "what" nahi

Root principle: "agar code itna unclear hai ki usse samajhne ke liye comment chahiye, to shayad code hi rewrite hona chahiye." Comments jo batate hain code kya kar raha hai, generally ek symptom hain ki code khud self-explanatory nahi hai.

bad comment vs refactored self-documenting code
// ❌ BAD — comment "what" explain kar raha hai, code khud confusing hai
for (let i = 2; i <= Math.sqrt(n); i++) {  // check divisors up to sqrt(n)
  if (n % i === 0) return false;              // not prime if divisible
}
return true;

// ✅ GOOD — function name khud batata hai "what", comment ki zaroorat nahi
function isPrime(n) {                                       // naam se hi clear hai ye kya check karta hai
  for (let i = 2; i <= Math.sqrt(n); i++) {    // sqrt(n) tak hi check karna kaafi hai (math property)
    if (n % i === 0) return false;              // ek bhi divisor mila to prime nahi hai
  }
  return true;                                          // koi divisor nahi mila, matlab prime hai
}

// ✅ GOOD comment — "why", explains a non-obvious design decision
/**
 * Retry queue ko FIFO order mein process karta hai, LIFO nahi —
 * kyunki agar LIFO use kiya to ek baar-baar-failing request
 * baaki sab requests ko starve kar sakta hai (production incident #482 dekho)
 */
function processRetryQueue(queue) { /* ... */ }

Comments kab likhne chahiye — teen legitimate cases:

  • Architecture / bird's-eye-view — file/module ke top pe, components kaise interact karte hain uska high-level overview.
  • JSDoc for functions — params, return type, usage — taaki caller ko implementation dekhne ki zaroorat na pade.
  • Design decisions ("why") — jab ek non-obvious approach choose kiya gaya ho, taaki future dev usse "clean up" karke bug reintroduce na kare.

"Ninja code" — anti-patterns jo bachne chahiye

Ye article satirical hai — ye "tips" deta hai ki code ko maximum confusing kaise banaya jaaye (taaki koi aur usse touch na kar sake). Har "ninja trick" ek real anti-pattern hai jo production codebases mein aksar milta hai.

ninja code refactor — before / after
// ❌ NINJA CODE — single-letter vars, nested ternary, no comments, cryptic abbreviation
function c(a, l) {
  a = a ? a < 0 ? Math.max(0, l + a) : a : 0;
  return a;
}

// ✅ REFACTORED — descriptive names, no unnecessary reassignment, flat logic, doc comment
/**
 * Array index ko normalize karta hai — negative index ko end-relative bana deta hai,
 * jaise Python slicing mein hota hai. Example: normalizeIndex(-1, 5) => 4
 * @param {number} rawIndex - user-provided index, negative ho sakta hai
 * @param {number} arrayLength - array ki total length
 * @returns {number} valid non-negative index (clamp kiya hua 0 tak)
 */
function normalizeIndex(rawIndex, arrayLength) {          // naam se hi function ka intent clear hai
  if (!rawIndex) {                                    // agar 0, undefined, ya falsy — default 0 return karo
    return 0;
  }

  if (rawIndex < 0) {                                // negative index ko end-relative treat karo
    return Math.max(0, arrayLength + rawIndex); // clamp karo 0 se neeche na jaaye
  }

  return rawIndex;                                     // positive index — waise hi return karo
}

Sabse common ninja anti-patterns jo real codebases mein milte hain:

  • Single-letter / abbreviated names — lst, ua, a, x — codebase mein search karna namumkin ho jaata hai, aur intent gayab.
  • Abstract generic names — data, value, obj, item — koi semantic info nahi dete.
  • Confusingly similar names — date aur data ek saath — typo-prone, misreading-prone.
  • Inconsistent synonyms — kabhi display..., kabhi show..., kabhi render... same kaam ke liye — pattern-matching todta hai.
  • Mid-function variable reuse — loop ke andar same variable ko baar-baar naye purpose ke liye reassign karna, bina track kiye "abhi is variable mein kya hai".
  • Misleading function names — checkPermission() jo dikhta hai pure check hai, par actually side-effect bhi karta hai (jaise DB write) — caller ka mental model todta hai.
⚠️ "Clever" code = expensive code

Ninja code ka core lesson ye hai: code likhne mein jo "cleverness" lagti hai, wo padhne mein usse zyada cost karti hai — aur code likha ek baar jaata hai, padha dus baar (code review, debugging, future features). Optimize karo readability ke liye, brevity ke liye nahi.

Automated testing — Mocha, Chai, Sinon (BDD)

Manual testing scale nahi karta — ek bug fix karte waqt kisi doosre case ko silently todna bahut aasan hai. Automated tests test-code ko implementation se alag rakhte hain, taaki function ko systematically alag-alag inputs ke saath run karke expected output se compare kiya ja sake.

BDD (Behavior Driven Development) teen cheezein combine karta hai: tests, documentation, aur usage examples — ek hi jagah. Teen building blocks:

  • describe(title, fn) — related tests ko ek human-readable group mein rakhta hai.
  • it(title, fn) — ek individual test case, jiska title describe karta hai kya expected hai.
  • assert.equal(actual, expected) (Chai se) — compare karta hai, mismatch pe test fail karta hai.

Neeche ek full TDD (test-driven-development) cycle hai — pow(x, n) function ko tests pehle likh ke, phir implementation ko step-by-step spec ke against build karte hue:

Step 1: spec likho (implementation se pehle) — pow.test.js
describe("pow", function() {                       // "pow" function se related sab tests ka group

  it("raises to n-th power", function() {       // pehla test case — basic behavior
    assert.equal(pow(2, 3), 8);                     // pow(2, 3) === 8 hona chahiye (2*2*2)
  });

});
Step 2: minimal implementation jo pehla test pass kare — pow.js
function pow(x, n) {
  return 8;                                              // ❌ hardcoded — sirf ek test case pass karta hai, ye galat hai but jaanbujh kar
}
// intent: dikhana ki "test pass hona" aur "implementation sahi hona" alag cheezein hain —
// isliye humein AUR test cases add karne padenge jo isse expose karein
Step 3: aur test cases add karo — deficiency expose karo
describe("pow", function() {

  it("2 raised to 3 is 8", function() {
    assert.equal(pow(2, 3), 8);
  });

  it("3 raised to 4 is 81", function() {              // naya case — hardcoded 8 wala implementation isse FAIL karega
    assert.equal(pow(3, 4), 81);                    // 3*3*3*3 = 81
  });

});
Step 4: real implementation likho jo sab tests pass kare — pow.js
function pow(x, n) {                                    // x ki n-th power nikalne wala real implementation
  let result = 1;                                        // accumulator — 1 se start (multiplicative identity)

  for (let i = 0; i < n; i++) {                       // n baar loop chalao
    result *= x;                                      // har iteration mein x se multiply karo
  }

  return result;                                       // final power value return karo
}
Step 5: edge cases + nested describe + hooks
describe("pow", function() {

  before(function() {                                   // sab tests SHURU hone se pehle EK BAAR chalta hai
    console.log("testing started — pow suite");       // e.g. global setup, test DB connection, etc
  });

  after(function() {                                    // sab tests KHATAM hone ke baad EK BAAR chalta hai
    console.log("testing finished — pow suite");      // e.g. teardown, close connections
  });

  beforeEach(function() {                              // HAR individual test se PEHLE chalta hai
    console.log("before a test");                 // e.g. fresh mock data reset karna, taaki tests ek-doosre pe depend na karein
  });

  afterEach(function() {                               // HAR individual test ke BAAD chalta hai
    console.log("after a test");                  // e.g. cleanup
  });

  describe("raises x to positive integer power", function() {  // nested describe — related sub-cases group karta hai

    it("2^3 = 8", function() {
      assert.equal(pow(2, 3), 8);                 // EK hi assertion per test — fail hone pe reason clear rehta hai
    });

    it("3^4 = 81", function() {
      assert.equal(pow(3, 4), 81);
    });

  });

  it("for negative n the result is NaN", function() {       // edge case — negative exponent handle nahi hota basic loop mein
    assert.isNaN(pow(2, -1));                    // assert.isNaN — specifically NaN check karta hai
  });

});
Sinon spy — call tracking ke liye
function notifyUser(sendEmailFn, user) {              // production function jo email-sending dependency leti hai
  if (user.isActive) {                              // sirf active users ko notify karna hai
    sendEmailFn(user.email);                          // dependency ko call karo — test mein isse spy se replace karenge
  }
}

it("sends email only for active users", function() {
  const emailSpy = sinon.spy();                     // ek fake function jo calls track karta hai, real email nahi bhejta

  notifyUser(emailSpy, { isActive: true, email: "a@x.com" }); // active user ke saath call karo

  assert.isTrue(emailSpy.calledOnce);               // verify karo ki spy exactly ek baar call hua
  assert.isTrue(emailSpy.calledWith("a@x.com"));    // verify karo ki sahi argument ke saath call hua
});
🧠 Senior Dev Note: ek assertion per test kyun?

Jab ek test mein multiple assert calls hoti hain, aur pehli hi fail ho jaati hai, to Mocha test ko turant terminate kar deta hai — baaki assertions kabhi run hi nahi hoti. Matlab agar teen cheezein galat hain, tumhe sirf pehli ka pata chalega, dusri- teesri chhupi rahengi jab tak pehli fix na ho. Isliye ek test = ek behavior verify karna best practice hai — failure output tumhe exactly batata hai kya toota, without guessing.

Polyfills aur Transpilers — Babel + core-js

JavaScript specification continuously evolve hoti hai, lekin har browser/engine naye features ko alag speed pe implement karta hai. Do tools is gap ko bridge karte hain:

  • Transpiler — modern syntax ko purani syntax mein convert karta hai (source-to-source compiler). Babel sabse popular hai.
  • Polyfill — missing built-in functions/methods ko implement karta hai (syntax nahi badalta, sirf feature add karta hai jo engine mein nahi hai). core-js sabse comprehensive library hai.
Babel transpilation — modern syntax se old syntax
// SOURCE — modern syntax jo purane engines samajh nahi paate (nullish coalescing, ES2020)
function getHeight(config) {
  return config.height ?? 100;                    // ?? = nullish coalescing, sirf null/undefined pe fallback deta hai (0 pe nahi)
}

// BABEL OUTPUT — same behavior, old-syntax-compatible
function getHeight(config) {
  var _height;                                     // temp variable — Babel intermediate values ke liye generate karta hai
  return (_height = config.height) !== null && _height !== undefined
    ? _height                                    // agar null/undefined nahi hai to value use karo
    : 100;                                       // warna fallback 100 use karo — bilkul same semantics, old syntax mein
}
core-js polyfill — missing method ko manually check + implement
if (!Math.trunc) {                                // check karo: kya is engine mein Math.trunc already exist karta hai?
                                                       // (purane engines mein ye method missing tha)
  Math.trunc = function(number) {            // agar nahi hai, to hum khud implement karke Math object pe attach karte hain
    // Math.trunc decimal part hata deta hai — round nahi karta, sirf truncate karta hai
    return number < 0 ? Math.ceil(number) : Math.floor(number);
                                                     // negative ke liye ceil (0 ki taraf), positive ke liye floor (0 ki taraf)
  };
}

Math.trunc(4.9);                                        // ab ye kaam karega — 4 return karega — chahe native ho ya polyfilled
Real-world build setup — babel.config.json + core-js import
{
  "presets": [
    [
      "@babel/preset-env",                       // preset-env: target browsers ke hisaab se automatic syntax transform
      {
        "targets": "> 0.25%, not dead",       // browserslist query — kaunse browsers support karne hain (usage-based)
        "useBuiltIns": "usage",              // "usage": sirf wahi core-js polyfills include karo jo code mein actually use ho rahe hain
        "corejs": "3.30"                       // core-js ka kaunsa version target karna hai — polyfill library
      }
    ]
  ]
}

// is config ke saath, webpack/vite build ke time Babel automatically dono kaam karta hai:
// 1) syntax transpile (?? , optional chaining, arrow functions, etc)
// 2) core-js se sirf zaroori polyfills inject (Array.flat, Promise.allSettled, etc)
⚠️ Transpiler vs Polyfill — confuse mat karo

Transpiler syntax problem solve karta hai (jaise ?? operator jo engine parse hi nahi kar sakta — SyntaxError aayega). Polyfill missing feature problem solve karta hai (jaise Array.prototype.flat jo valid syntax hai, bas engine mein method exist nahi karta — TypeError aayega). Dono ek saath chahiye hote hain kyunki modern code dono cheezon ka mix use karta hai — isliye Babel + core-js ek combo mein use hote hain.

Key Takeaways

  • Chrome DevTools Sources panel mein breakpoints/debugger statement se execution pause karke Watch, Call Stack, aur Scope panels se root-cause investigate karo — console.log se zyada reliable hai.
  • Step Over (F10) apne code ke liye, Step Into (F11) tab jab library/helper ke andar dekhna ho — galat button use karna time waste karta hai.
  • Coding style (Egyptian braces, early returns, consistent indent) ka goal team-readability hai; ESLint jaisa linter isse automate aur enforce karta hai.
  • Comment "what" nahi, "why" likho — agar code samajhne ke liye comment chahiye, code ko refactor karo (function extract karo, better naam do).
  • Ninja code anti-patterns (single-letter vars, abstract names, mid-function reuse, misleading function names) readability ko directly hurt karte hain — inhe consciously avoid karo.
  • BDD testing (describe/it/assert) tests ko documentation ki tarah readable banata hai; ek test = ek assertion, taaki failure output clear rahe.
  • Hooks (before/after/beforeEach/afterEach) setup/teardown ko duplicate hone se bachate hain aur tests ko isolated rakhte hain.
  • Transpiler (Babel) syntax problem solve karta hai, polyfill (core-js) missing-feature problem — dono zaroori hain cross-browser compatibility ke liye.

🎯 Interview Questions

  • Step Over aur Step Into mein kya farak hai, aur kab kaunsa use karoge?
    Hint: Step Over next line run karta hai bina nested function calls ke andar jaaye; Step Into unke andar bhi jaata hai. Apna code debug karte waqt Step Over, third-party helper ke internal logic verify karna ho to Step Into.
  • "Agar code ko samajhne ke liye comment chahiye, to code hi galat hai" — is statement ko explain karo.
    Hint: comments jo "what" describe karte hain, unclear code ka symptom hain — better solution hai code ko refactor karna (extract function, better naming) taaki wo self-documenting ho jaaye.
  • Ek test mein multiple assertions likhna kyun risky hai?
    Hint: pehli assertion fail hote hi test terminate ho jaata hai, baaki assertions kabhi run nahi hoti — matlab multiple bugs ek saath ek hi test-run mein nahi pakde jaate.
  • beforeEach aur before mein kya farak hai?
    Hint: before ek baar sabse pehle chalta hai (poore describe block ke liye), beforeEach har individual test se pehle chalta hai — isolation ke liye beforeEach zyada common hai.
  • Transpiler aur polyfill mein fundamental difference kya hai?
    Hint: transpiler syntax convert karta hai (source-to-source, SyntaxError avoid karta hai), polyfill missing built-in methods/objects implement karta hai (TypeError avoid karta hai).
  • Sinon spy ka use-case kya hota hai testing mein?
    Hint: real dependency (jaise email-sending function) ko fake function se replace karta hai jo calls track karta hai — bina real side-effect (actual email bhejna) kiye verify kar sakte ho ki function sahi tareeke se, sahi arguments ke saath call hua.
  • ninja code mein "misleading function name" ka kya matlab hai, example do.
    Hint: function jaisa naam ho — jaise checkPermission() — lekin actually side-effect bhi kare (state modify kare) ya unexpected type return kare; caller ka mental model todta hai aur bugs create karta hai.
  • useBuiltIns: "usage" ka Babel config mein kya role hai?
    Hint: sirf wahi core-js polyfills bundle mein include karta hai jo code actually use kar raha hai — bundle size ko unnecessary polyfills se bloat hone se bachata hai.
