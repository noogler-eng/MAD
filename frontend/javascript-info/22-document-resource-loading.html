Document & Resource Loading

Page load ek single moment nahi hai — ye ek sequence of events hai jo alag-alag timing pe fire hoti hain: pehle HTML parse hoti hai, phir scripts (kab? kaise? order kya hai?), phir images/stylesheets load hoti hain, aur finally page "complete" hoti hai. Is chapter mein hum DOMContentLoaded, load, beforeunload, unload — char lifecycle events ka exact contract samjhenge, async/defer ka precise execution-order model dekhenge, aur individual resources (images, scripts, stylesheets) ke apne onload/onerror events explore karenge.

DOMContentLoaded — exact guarantee kya hai

DOMContentLoaded event document object pe fire hota hai jab browser ne HTML fully parse kar li ho aur DOM tree ban chuka ho — lekin external resources jaise <img> aur stylesheets zaroori nahi ki load ho chuke hon. Iska root-level matlab: is point pe tum DOM ko safely query/manipulate kar sakte ho (elements exist karte hain, attributes set hain), lekin agar tumhe kisi image ka width/height chahiye, ya kisi stylesheet se aane wale computed style pe depend karna hai, to wo abhi guaranteed nahi hai.

DOMContentLoaded basic listener
document.addEventListener("DOMContentLoaded", () => {  // document pe listener — event ka naam exact string case-sensitive hai
  console.log("DOM ready hai, HTML fully parsed");  // yahan DOM elements guaranteed exist karte hain
  const img = document.querySelector("img");  // img element milega (DOM node exist karta hai)
  console.log(img.offsetWidth);  // ⚠️ ye 0 ho sakta hai — image ka pixel data abhi download nahi hua
});

Scripts DOMContentLoaded ko kyun block karte hain

Root cause: HTML parser jab ek <script> tag ke upar pahunchta hai (bina async/defer ke), to wo parsing ruk jaata hai aur script ko download (agar external hai) + execute karta hai, tabhi aage badhta hai. Isko "parser-blocking script" kehte hain. Ye precaution isliye hai kyunki script ke andar document.write() ho sakta hai jo current parsing position pe naya HTML inject kar sakta hai — browser ko pehle se pata nahi ki script DOM modify karega ya nahi, isliye safe side pe wo hamesha wait karta hai.

Isi wajah se agar tumhare page mein bada external script hai (jaise ek analytics library), to DOMContentLoaded tab tak fire nahi hoga jab tak wo script pura download + execute nahi ho jaata — chahe script DOM se related kuch bhi na kare.

Blocking script demo
document.addEventListener("DOMContentLoaded", () => {  // ye listener page load ke shuru mein hi register ho gaya
  console.log("DOM ready — is line ka fire hona script ke NEECHE hai");  // ye tabhi chalega jab neeche wala script pura load ho chuka ho
});

<script src="https://cdnjs.cloudflare.com/ajax/libs/lodash.js/4.3.0/lodash.js"></script>
<!-- ⬆ async/defer nahi hai, isliye parser yahan RUKTA hai, lodash ko download+execute karta hai -->
<!-- tab tak DOMContentLoaded fire NAHI hoga, chahe lodash DOM ko touch bhi na kare -->

Stylesheets ka nuanced ordering effect

Ye sabse confusing part hai, isliye carefully samjho: external stylesheet khud DOMContentLoaded ko block NAHI karta — browser CSS load hone ka wait kiye bina HTML parsing continue rakh sakta hai. Lekin agar stylesheet ke baad koi <script> tag aata hai, to wo script us stylesheet ke load hone tak wait karega — kyunki script ke andar CSSOM query ho sakti hai (jaise getComputedStyle), aur browser ko pehle CSSOM complete banana padta hai script chalane se pehle. Result: stylesheet indirectly parsing ko delay kar deta hai, sirf isliye kyunki uske baad wala script uska wait karta hai.

Stylesheet → script ordering
<link type="text/css" rel="stylesheet" href="style.css">
<!-- ⬆ ye khud parsing ko block nahi karta — HTML parser aage badh sakta hai -->

<script>
  // lekin ye script style.css ke load hone ka WAIT karega,
  // kyunki getComputedStyle ko accurate CSSOM chahiye
  console.log(getComputedStyle(document.body).marginTop);  // style.css apply hone ke baad hi accurate value milega
</script>
<!-- chain effect: stylesheet → blocks this script → jo aage HTML parsing ko block karta hai -->
<!-- to net result: is order mein stylesheet load hone tak DOMContentLoaded bhi delay ho sakta hai -->
🧠 Senior Dev Note: ordering ka practical impact

Ye chaining effect (stylesheet → blocks next script → blocks parsing) hi ek reason hai ki production sites <link rel="stylesheet"> ko hamesha <head> mein sabse pehle rakhte hain aur uske baad koi inline/blocking script nahi daalte — taaki parser jaldi se jaldi CSSOM build kar sake bina kisi script ke intermediate mein wait kiye. Agar tumhe script chahiye bhi hai jo styles read kare, use stylesheet se pehle mat rakho — ya better, defer use karo taaki wo parsing complete hone ke baad hi chale, jab CSSOM already ready ho.

Browser autofill aur DOMContentLoaded

Firefox, Chrome aur Opera browser saved form data (username/password) ko exactly DOMContentLoaded ke time pe autofill karte hain. Chunki DOMContentLoaded khud blocking scripts ka wait karta hai (upar dekha), agar tumhare page mein bahut saare render-blocking scripts hain, to login form ka autofill bhi utna hi late hoga — user ko lagega page "slow" hai jabki asal mein wo script-loading delay hai.

window.onload — sab kuch complete

load event window object pe fire hota hai jab poora page load ho chuka ho — HTML, saare stylesheets, saari images, sab kuch. Ye DOMContentLoaded se hamesha baad (ya same time pe, agar koi external resource hi na ho) fire hoga.

window.onload example
window.onload = function() {  // window pe handler assign — ye "complete" state pe chalega
  const img = document.querySelector("img");  // same img jo upar 0 width de raha tha
  console.log(`Image size: ` + img.offsetWidth + "x" + img.offsetHeight);  // ab guaranteed non-zero accurate dimensions
};

document.readyState — teen states

document.readyState property loading progress ko track karti hai, teen possible values ke saath:

  • "loading" — document abhi parse ho raha hai (initial state)
  • "interactive" — DOM complete ban chuka hai (ye DOMContentLoaded ke saath coincide karta hai)
  • "complete" — document + saare resources load ho chuke hain (ye window.onload ke saath coincide karta hai)
readyState-based safe listener registration
function work() {  // actual kaam jo DOM ready hone par karna hai
  console.log("DOM ready, kaam shuru");  // safe hai DOM access karna
}

if (document.readyState == 'loading') {  // abhi tak parsing chal rahi hai — event ka wait karna hoga
  document.addEventListener('DOMContentLoaded', work);  // event fire hone par work() call hoga
} else {  // script itna late load hua ki DOM already ready hai
  work();  // event kabhi nahi fire hoga (already fire ho chuka), isliye directly call karo
}
// ye pattern zaroori hai jab script dynamically ya deferred load hota hai —
// warna addEventListener kabhi trigger na hone wale event ka wait karta reh jaayega

async vs defer — timeline comparison

Dono attributes sirf external scripts (src wale) pe kaam karte hain — agar src nahi hai to dono ignore ho jaate hain. Dono ka common goal: HTML parsing ko block mat karo. Lekin execution-order guarantee bilkul alag hai.

AspectPlain <script>asyncdefer
HTML parsing Block karta hai (download+execute dono ke liye) Block nahi karta (parallel download) Block nahi karta (parallel download)
Execution order Document order (guaranteed) Jo pehle download ho jaaye (order guaranteed NAHI) Document order (guaranteed, jaise plain scripts)
Execution timing Turant jahan tag hai wahin, synchronously Download complete hote hi, turant (parsing beech mein ruk jaati hai us waqt) Sirf HTML parsing complete hone ke baad
DOMContentLoaded se relation Isse pehle chalta hai (block karta hai) Independent — pehle ya baad, kuch bhi ho sakta hai Hamesha DOMContentLoaded se pehle chalta hai
Best use-case Chhote critical inline scripts Independent third-party code — analytics, ads, widgets App logic jo pura DOM aur ek dusre se order-dependent ho
defer — document order guarantee
<script defer src="long-script.js"></script>
<!-- long-script.js download background mein shuru ho jaata hai, parsing block nahi hoti -->
<script defer src="small-script.js"></script>
<!-- small-script.js pehle download ho sakta hai (chhota hai), -->
<!-- LEKIN execution order document order hi follow karega: -->
<!-- long-script.js PEHLE execute hoga, small-script.js uske baad, -->
<!-- chahe download kaunsa pehle complete hua ho -->
<!-- aur dono, HTML parsing complete hone ke baad, DOMContentLoaded se PEHLE run honge -->
async — load-order, no guarantee
<script async src="analytics.js"></script>
<!-- ye script poori tarah INDEPENDENT hai — koi doosra script iska wait nahi karta, -->
<script async src="ads.js"></script>
<!-- aur ye bhi kisi ka wait nahi karta -->
<!-- jo bhi pehle download ho jaaye — chahe ads.js pehle likha ho ya baad mein — -->
<!-- wo PEHLE execute hoga. Order network speed pe depend karta hai, code order pe nahi -->
<!-- aur DOMContentLoaded inn dono se pehle ya baad mein, kabhi bhi fire ho sakta hai -->

Dynamically created scripts

Jab tum document.createElement('script') se runtime pe script banate ho, to uska default behavior async jaisa hi hota hai — matlab wo apne aap independent load hoga, koi document order guarantee nahi. Agar tumhe order chahiye (jaise multiple dynamic scripts ek sequence mein chalane hain), to explicitly script.async = false set karna padta hai.

Dynamic script — order enforce karna
function loadScript(src) {  // helper function — src diya, script tag bana ke inject karega
  let script = document.createElement('script');  // naya <script> element create kiya, abhi DOM mein nahi hai
  script.src = src;  // src set karte hi browser background download shuru kar deta hai
  script.async = false;  // ZAROORI: default async=true ko override karke document-order execution force kiya
  document.head.append(script);  // script ko DOM mein daala — ab wo actually load/execute hoga
}

loadScript("/js/module-a.js");  // pehla call — is order mein execute hoga
loadScript("/js/module-b.js");  // dusra call — chahe module-a se pehle download ho jaaye, execute BAAD mein hoga
// async=false set kiye bina, dono scripts jo bhi pehle download ho wo pehle chalega —
// jo module-b agar module-a pe depend karta hai to crash ho sakta hai

beforeunload — confirmation dialog

beforeunload event tab fire hota hai jab user page se navigate away karne wala ho (tab close, reload, ya kisi aur URL pe jaana). Iska primary use-case: unsaved changes ke liye user ko warn karna. Handler mein value return karne se browser ek native confirmation dialog dikhata hai.

beforeunload — unsaved changes warning
window.addEventListener("beforeunload", (event) => {  // window pe listener, event object milta hai
  if (!hasUnsavedChanges()) {  // custom check — agar kuch unsaved nahi hai
    return;  // kuch mat karo, silently navigate hone do
  }
  event.preventDefault();  // spec ke hisaab se ye chahiye hota hai, lekin real effect returnValue se hota hai
  event.returnValue = "";  // ZAROORI: returnValue set karna hi actual trigger hai dialog dikhane ka
});
// Note: modern browsers custom string show nahi karte security reasons se —
// sirf ek generic browser-controlled message dikhta hai ("Changes you made may not be saved")
// tumhara custom text dialog mein show hi nahi hota, ye deliberate browser restriction hai
⚠️ beforeunload pe browser restrictions

Modern browsers beforeunload ka misuse (spammy "are you sure" popups) rokne ke liye strict hain: (1) tumhara custom message string ignore ho jaata hai — browser apna generic text use karta hai; (2) dialog sirf tab dikhta hai jab user ne page ke saath kabhi interact kiya ho (ek click ya keypress) — pure passive page-load pe dialog suppress ho jaata hai; (3) alert()/confirm() jaisi custom UI is event ke andar allowed nahi hai, sirf native returnValue-based dialog chalta hai.

unload aur sendBeacon

unload event tab fire hota hai jab user actually page chhod raha ho (already committed navigation). Is point pe koi delay-causing operation (alert, confirm, ya async fetch jiska response wait karna ho) allowed nahi hai — browser bas page destroy kar dega. Analytics jaise "last-moment data bhejna" use-cases ke liye navigator.sendBeacon() use hota hai, jo background mein POST request fire-and-forget style bhejta hai, page transition ko block kiye bina.

unload + sendBeacon — analytics pattern
let analyticsData = { timeOnPage: 42, scrollDepth: 0.8 };  // gather kiya hua session data

window.addEventListener("unload", function() {  // page destroy hone se theek pehle chalta hai
  navigator.sendBeacon("/analytics", JSON.stringify(analyticsData));  // non-blocking POST, page navigate hone ko rokta nahi
});
// sendBeacon ke fayde: background mein POST bhejta hai; navigation ko delay nahi karta;
// max ~64kb data allowed hai per beacon
📌 Load-sequence, top se bottom

Typical order: (1) readyState → "interactive", (2) DOMContentLoaded fire, (3) individual resources (images, iframes) apne load events fire karte rehte hain jaise-jaise complete hote hain, (4) readyState → "complete", (5) window.onload. Navigation ke time: beforeunload (cancellable, dialog) → user confirm karta hai → unload (final, non-cancellable) → page destroyed.

Resource loading: img/script/link onload/onerror

Individual resources (images, dynamically loaded scripts, stylesheets, iframes) apne khud ke load aur error events fire karte hain — independent of DOMContentLoaded ya window.onload. Ye tab useful hai jab tumhe kisi specific resource ke ready hone ka wait karna ho.

Dynamic script — onload/onerror
let script = document.createElement('script');  // naya script element
script.src = "https://cdnjs.cloudflare.com/ajax/libs/lodash.js/4.3.0/lodash.js";  // external CDN URL set kiya
document.head.append(script);  // DOM mein daala — download shuru

script.onload = function() {  // script load + execute successfully hone par
  console.log(_.VERSION);  // ab lodash ka global _ safely accessible hai
};

script.onerror = function() {  // loading fail (404, network down, etc.)
  console.error("Error loading " + this.src);  // "this" script element ko refer karta hai, uska src print
};
// ⚠️ IMPORTANT: onload/onerror sirf LOADING track karte hain, execution errors nahi —
// agar script mein syntax error hai lekin download successful hua, onload phir bhi chalega
⚠️ Cross-origin scripts — error details hidden

Agar script cross-origin hai (different domain), to security policy ke wajah se error ke andar ka detail (stack trace, exact message) browser hide kar deta hai — sirf generic "Script error." milta hai window.onerror mein. Isse fix karne ke liye <script crossorigin="anonymous" src="..."> add karo, aur remote server ko Access-Control-Allow-Origin header ke saath respond karna hoga. Bina iske, production error-tracking tools (Sentry, etc.) third-party script crashes ka useful stack trace nahi de paate.

Image onload/onerror
let img = document.createElement('img');  // naya img element, abhi src nahi hai

img.onload = function() {  // image download complete hone par
  console.log(`Image loaded, size ` + img.width + "x" + img.height);  // natural pixel dimensions ab accurate hain
};

img.onerror = function() {  // 404 ya invalid image data
  console.error("Image load failed");  // fallback UI dikhane ka trigger yahan lagta hai
};

img.src = "https://js.cx/clipart/train.gif";  // ⚠️ ZAROORI: images ka loading src set hone PAR shuru hota hai
// (jabki scripts/stylesheets ka loading generally DOM mein INSERT hone par shuru hota hai) —
// isliye onload/onerror handlers src set karne se PEHLE attach karne chahiye,
// warna race condition mein event miss ho sakta hai agar image cache se instantly load ho jaaye

Same load/error pattern <link rel="stylesheet"> aur <iframe> pe bhi kaam karta hai. Ek historical quirk: iframe hamesha onload fire karta hai — chahe uske andar ka content successfully load hua ho ya error page dikha ho — kyunki iframe apne aap mein ek complete document hai jo "load" ho gaya, chahe uska content 404 hi kyun na ho.

Key Takeaways

  • DOMContentLoaded = HTML parsed, DOM ready, images/stylesheets guaranteed nahi. Blocking scripts (bina async/defer) ise delay karte hain.
  • Stylesheet khud DOMContentLoaded ko block nahi karta, lekin uske baad wale script ko block karta hai (CSSOM dependency) — jo indirectly parsing delay kar sakta hai.
  • Browser autofill DOMContentLoaded pe hota hai — script-heavy pages pe delayed autofill isi wajah se hota hai.
  • window.onload = sab kuch complete — images, stylesheets, sab loaded. Accurate dimensions ke liye ye chahiye, DOMContentLoaded nahi.
  • defer = document order guaranteed, DOMContentLoaded se pehle chalta hai. async = load-order (koi guarantee nahi), DOMContentLoaded se independent timing.
  • Dynamically created scripts default async=true hote hain — order chahiye to explicitly script.async = false set karo.
  • beforeunload confirmation dialog de sakta hai (event.returnValue set karke), lekin custom message browsers ignore karte hain aur user-interaction requirement hai.
  • unload mein delay-causing operations allowed nahi — navigator.sendBeacon() use karo background analytics ke liye.
  • Resource-level onload/onerror sirf loading track karte hain, execution errors nahi. Images ke liye handlers src set karne se pehle attach karo.

🎯 Interview Questions

  • DOMContentLoaded aur window.onload mein exact farak kya hai?
    Hint: DOMContentLoaded = HTML parsed + DOM built (images/CSS guaranteed nahi); load = sab kuch complete including all external resources.
  • Ek external stylesheet, jo khud DOMContentLoaded ko block nahi karta, kaise indirectly parsing ko delay kar sakta hai?
    Hint: agar stylesheet ke baad script hai jo computed styles read karta hai, wo script stylesheet ka wait karega, jo aage parsing ko block karega.
  • async aur defer dono parsing ko block nahi karte — to inka fundamental farak kya hai?
    Hint: defer document order preserve karta hai aur DOMContentLoaded se pehle chalta hai; async load-order (unpredictable) mein chalta hai, DOMContentLoaded se independent hai.
  • Dynamically createElement se banaya gaya script default kaunsa behavior follow karta hai, aur order enforce kaise karoge?
    Hint: default async=true jaisa hai; explicitly script.async = false set karke document order enforce karte hain.
  • beforeunload event mein custom confirmation message kyun show nahi hota modern browsers mein?
    Hint: spam/abuse prevent karne ke liye browsers deliberately generic message use karte hain aur dialog sirf user-interaction ke baad allow karte hain.
  • unload event mein async fetch ka response wait kyun nahi kar sakte, aur iska solution kya hai?
    Hint: unload ke time browser page destroy kar raha hota hai, delay-causing operations allowed nahi; navigator.sendBeacon() background POST bhejta hai bina block kiye.
  • Image ke onload/onerror handlers ko src set karne se pehle kyun attach karna chahiye?
    Hint: image loading src assign hote hi turant shuru ho jaata hai (especially cache se); agar handler baad mein attach hua, race condition mein load event miss ho sakta hai.
