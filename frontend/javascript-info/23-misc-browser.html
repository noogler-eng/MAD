MutationObserver — DOM changes ko watch karna

MutationObserver ek built-in object hai jo DOM tree mein hone wale changes ko observe karta hai — koi child add/remove hua, koi attribute badla, ya text content change hua — aur har change ke baad ek callback fire karta hai. Ye rich text editors, third-party widget integrations, aur "DOM tumhare control se bahar badal raha hai" wale scenarios mein use hota hai. Root mechanism: ye synchronously polling nahi karta — browser internally jab bhi DOM tree mutate hoti hai, ek record push karta hai, aur ye records ek microtask ke through deliver hote hain (isliye MutationObserver callback event loop ke microtask queue ke through fire hota hai, setTimeout jaisa macrotask nahi).

MutationObserver basic setup
const observer = new MutationObserver(function(mutationRecords) {  // naya observer object banaya, callback function pass kiya
  // mutationRecords ek array hai — ek batch mein multiple changes ho sakte hain
  console.log(mutationRecords);          // batch of MutationRecord objects print karo
});

observer.observe(document.body, {          // document.body ko observe karna shuru karo
  childList: true,              // direct children add/remove hone pe fire karo
  subtree: true,                // pure descendant tree bhi cover karo, sirf direct children nahi
  attributes: true,             // kisi bhi attribute ke change hone pe bhi fire karo
  attributeFilter: ['class', 'style'],  // sirf inhi specific attributes ko track karo, baaki ignore
  attributeOldValue: true,       // callback ko purana value bhi do (attributes: true ke saath mandatory)
  characterData: true,          // text node ke andar text content change hone pe bhi fire karo
  characterDataOldValue: true  // text ka purana value bhi do
});

// jab observation band karni ho (memory leak avoid karne ke liye zaroori hai)
// observer.disconnect();

// agar disconnect se pehle un-delivered records bhi chahiye:
// let pendingRecords = observer.takeRecords();

Har MutationRecord object mein type ("childList", "attributes", ya "characterData"), target (jis node pe change hua), addedNodes/removedNodes (NodeList), aur oldValue (agar respective *OldValue option on ho) hota hai. Root cause ki batch delivery microtask-based hai isliye agar tum ek hi synchronous block mein 5 DOM mutations karo, callback ek hi baar fire hoga with 5 records ke array ke saath — na ki 5 alag calls.

📌 Batching kyun hoti hai

MutationObserver callback microtask queue ke through fire hota hai, aur microtasks current synchronous execution ke khatam hone ke baad hi run hote hain (event loop section mein isko detail se samjhenge). Isliye agar loop mein 100 DOM elements insert kar rahe ho, browser sabko internally collect karta rehta hai, aur jab call stack empty hota hai, tab ek hi batched callback fire hota hai — performance ke liye ye critical hai, warna har mutation pe synchronous callback firing se page freeze ho sakta tha.

Real use-case: third-party script DOM injection detect karna

Common production scenario: ek third-party analytics/ad/chat-widget script tumhare page mein apna DOM inject karta hai — kabhi kabhi unwanted banners, popups, ya broken layout wale elements. Tumhare paas us script ke internal timing/hooks ka access nahi hota (third-party code hai), lekin MutationObserver se tum reactively detect kar sakte ho ki kab DOM mein naya content aaya, aur uspe action le sakte ho.

Third-party injected banner ko detect + remove karna
function watchForThirdPartyInjection() {              // ek setup function banaya jo observer initialize karega
  const observer = new MutationObserver(records => { // naya observer, arrow function callback
    for (const record of records) {          // is batch ke har MutationRecord pe loop
      for (const node of record.addedNodes) {  // is record mein jitne bhi naye nodes add hue unpe loop
        if (                                       // condition check: kya ye suspicious third-party element hai?
          node.nodeType === 1 &&            // nodeType 1 matlab ye ek Element hai, text/comment node nahi
          node.matches('.third-party-banner, [id^="ad-"]') // class ya id-prefix se pehchano
        ) {
          console.warn('Third-party element injected:', node); // debugging ke liye log karo
          node.remove();                          // unwanted element ko DOM se hata do
        }
      }
    }
  });

  observer.observe(document.body, {              // pure body subtree ko watch karo
    childList: true,                       // naye nodes add/remove hone ka signal chahiye
    subtree: true                          // script kahin bhi deep inject kare, phir bhi pakda jaaye
  });

  return observer;                              // observer reference return karo taaki baad mein disconnect ho sake
}

const watcher = watchForThirdPartyInjection();    // watching shuru karo
// page unload ke time cleanup zaroor karo:
window.addEventListener('beforeunload', () => watcher.disconnect()); // listener register

Isi pattern se rich text editors (jaise Google Docs-style contenteditable widgets) bhi apna internal state sync karte hain — jab browser ka native contenteditable behavior DOM ko directly mutate kar deta hai (user ne type kiya, paste kiya), editor ka observer un changes ko pick karke apni internal document model (JSON representation) update karta hai.

Selection aur Range APIs

Browser mein user jab mouse se text drag karke select karta hai, ya JS programmatically kisi text ko highlight karna chahta hai, uske peeche do related APIs kaam karte hain: Range (ek arbitrary contiguous region define karta hai DOM ke andar) aur Selection (jo actual visible, user-facing selection ko represent karta hai — ek ya zyada Range objects se bana hota hai).

Range object startContainer/startOffset aur endContainer/endOffset se define hota hai. Agar container ek text node hai, offset uska character position hai; agar container ek element node hai, offset uska child-index hai. Ye distinction root-level samajhna zaroori hai warna range boundaries galat set ho jaate hain.

Range banake DOM content nikalna
// maan lo HTML hai: <p id="para">Hello beautiful world</p>
const p = document.getElementById('para');       // paragraph element ka reference liya
const textNode = p.firstChild;              // uska pehla child hi text node hai ("Hello beautiful world")

const range = new Range();                      // ek naya empty Range object banaya
range.setStart(textNode, 6);              // text node ke andar character index 6 se start ("beautiful" ka 'b')
range.setEnd(textNode, 15);                // index 15 tak end ("beautiful" ka 'l' ke baad)

console.log(range.toString());              // "beautiful" print hoga — range ke andar ka plain text
console.log(range.collapsed);            // false — start aur end alag positions pe hain

const span = document.createElement('span');   // ek naya span element banaya jo wrapper banega
span.className = 'highlight';              // span pe CSS class laga di highlighting style ke liye
range.surroundContents(span);          // range ke content ko span ke andar wrap kar diya — DOM update ho gaya
// ab HTML ban gaya: <p>Hello <span class="highlight">beautiful</span> world</p>

Selection object ye represent karta hai ki user ne actually kya select kiya hai screen pe (visually highlighted text) — isse window.getSelection() se access karte hain. Ek Selection internally ek ya zyada Range se bana hota hai (Chrome mein practically hamesha 1 range, Firefox multi-range selection support karta hai Ctrl+click se). anchorNode/anchorOffset wahan hai jahan se user ne selection shuru kiya (mouse-down point), aur focusNode/focusOffset jahan selection khatam hua (mouse-up point) — agar user ne right-to-left drag kiya, anchor focus ke baad bhi aa sakta hai, isliye ye start/end se different concept hai.

Real example: "Highlight selected text" feature

Ye pattern kaafi products mein milta hai — Medium, Google Docs comments, PDF annotators — jahan user text select karke ek button click karta hai aur wo text highlight ho jaata hai:

User selection ko highlight span mein wrap karna
document.getElementById('highlight-btn').addEventListener('click', () => { // button ka click listener
  const selection = window.getSelection();       // current page selection ka Selection object nikala

  if (!selection.rangeCount || selection.isCollapsed) { // koi selection nahi ya empty (cursor only) hai
    alert('Pehle kuch text select karo');        // user ko batao pehle text select kare
    return;                                    // yahin se function exit — aage nahi jaayenge
  }

  const range = selection.getRangeAt(0);       // selection ka pehla (aur usually sole) range nikala

  try {
    const mark = document.createElement('mark'); // semantic <mark> tag — highlighting ke liye native element
    mark.dataset.userHighlight = 'true'; // data attribute se marker lagaya (baad mein sab highlights query karne ke liye)
    range.surroundContents(mark);        // range ke content ko mark ke andar wrap karo
  } catch (err) {
    // surroundContents fail hota hai agar range partial-overlap element boundaries ko cross kare
    // (e.g. selection ek <li> ke andar shuru hokar doosre <li> mein khatam ho — non-well-formed wrap)
    const contents = range.extractContents(); // fallback: content ko extract karo (DOM se hata bhi diya)
    const mark = document.createElement('mark'); // naya mark element
    mark.appendChild(contents);          // extracted fragment ko mark ke andar daal do
    range.insertNode(mark);             // aur mark ko wapas range ki jagah insert kar do
  }

  selection.removeAllRanges();            // highlight ke baad visual selection clear kar do (UX cleanliness)
});

Root cause samjho: surroundContents internally assume karta hai ki range ke andar ka content ek well-formed subtree hai — matlab agar range kisi element ko sirf aadha cross karta hai (start ek <li> ke andar, end doosre <li> ke andar), to wrap karna ek invalid tree bana dega, isliye browser exception throw karta hai. extractContents + manual insertNode wala fallback isse handle kar leta hai kyunki wo DocumentFragment level pe operate karta hai.

Event Loop — full internal model

Ye sabse important browser-internals topic hai jo interview mein bhi sabse zyada pucha jaata hai. JavaScript single-threaded hai — ek waqt mein sirf ek hi cheez execute ho sakti hai. Lekin phir bhi setTimeout, network requests, event listeners sab "asynchronously" kaam karte lagte hain. Ye magic event loop ke through hota hai — jo four core pieces coordinate karta hai:

  1. Call Stack — jahan currently executing synchronous code ka LIFO (last-in-first-out) stack hota hai. Jab tak call stack empty nahi hoti (matlab sab synchronous code khatam nahi ho jaata), engine kuch aur nahi karega — na koi microtask, na koi macrotask, na render.
  2. Web APIs (browser-provided, JS engine ka part nahi) — jab tum setTimeout, fetch, DOM event listener, ya file I/O jaisa async operation call karte ho, JS engine turant us operation ko browser ke hawale kar deta hai (ye alag thread/subsystem pe chalta hai, jaise timer thread, network thread), aur call stack se turant hat jaata hai — non-blocking. Jab wo operation complete hota hai, uska callback ek queue mein daal diya jaata hai (call stack mein directly nahi jaata).
  3. Macrotask Queue (aka "task queue" / callback queue) — yahan jaate hain: setTimeout/setInterval callbacks, DOM events (click, mousemove), poora <script> execution khud bhi ek macrotask hai, I/O callbacks (Node.js mein), UI rendering events. Ek time mein sirf ek macrotask hi run hota hai poori tarah, phir agla uthaya jaata hai.
  4. Microtask Queue — yahan jaate hain: Promise.then/catch/finally handlers, queueMicrotask() se manually queued callbacks, aur async/await ka continuation (jo internally Promise hi hai). Ye macrotask queue se higher priority rakhti hai.

Event loop ka algorithm exactly ye hai — ye sequence hi sabse important cheez hai poore chapter mein, ise ratt lo:

Event loop algorithm — pseudo-code
while (true) {                                // event loop hamesha chalta rehta hai jab tak tabs/process zinda hai

  // Step 1: macrotask queue se EK task uthao aur poori tarah run karo
  const task = macrotaskQueue.dequeue();    // sabse oldest waiting macrotask nikalo (FIFO)
  execute(task);                            // isko call stack pe daal ke pura chalao — jab tak khatam na ho

  // Step 2: microtask queue ko POORI TARAH drain karo — sab microtasks, ek-ek karke
  while (!microtaskQueue.isEmpty()) {    // jab tak microtask queue mein kuch bhi bacha hai
    const microtask = microtaskQueue.dequeue(); // agla microtask nikalo
    execute(microtask);                    // use run karo — agar isne NAYA microtask queue kiya,
                                              // wo bhi isi while loop mein consume ho jaayega (drain complete tabhi maana jaayega)
  }

  // Step 3: agar render karne ka time hai (browser decide karta hai, usually ~60fps target)
  if (shouldRender()) {                  // browser internally decide karta hai — har macrotask ke baad zaroori nahi
    runRAFCallbacks();                    // requestAnimationFrame callbacks pehle chalte hain
    recalculateStyle();                 // CSS recalculation (style)
    layout();                            // layout/reflow pass
    paint();                             // actual pixels screen pe draw karo — YAHIN user ko visual change dikhta hai
  }

  // Step 4: loop wapas Step 1 pe — agla macrotask uthao, repeat
}

Sabse important root-level insight: microtask queue macrotask queue se hamesha pehle, poori tarah drain hoti hai — sirf ek microtask nahi, saare pending microtasks, jismein wo microtasks bhi shamil hain jo abhi-abhi run ho rahe microtask ne khud queue kiye. Agar ek microtask apne andar se ek aur microtask schedule karta rahe (infinite chain), macrotask queue aur render dono starve ho jaayenge — page freeze ho jaayega, kyunki event loop kabhi Step 2 se bahar hi nahi nikalega.

Traced example: exact output order samjho

Ye classic interview example hai jo console.log, setTimeout, Promise.then, aur async/await sab mix karta hai. Pehle code padho, phir line-by-line trace samjho:

Mixed sync + macrotask + microtask + async/await
console.log('1: sync start');                    // synchronous — turant call stack pe execute, sabse pehle print

setTimeout(() => {                             // timer Web API ko saunpa gaya, callback macrotask queue mein baad mein jaayega
  console.log('2: setTimeout callback');       // ye tab tak nahi chalega jab tak sab sync code + saare microtasks khatam na ho
}, 0);                                          // delay 0ms bhi ho, phir bhi ye macrotask hi rahega — turant nahi chalega

Promise.resolve().then(() => {              // already-resolved promise — .then callback microtask queue mein jaata hai
  console.log('3: promise.then');             // current sync code khatam hote hi ye setTimeout se PEHLE chalega
});

async function asyncFlow() {                       // async function define ki (call hone tak kuch nahi hota)
  console.log('4: async fn start');            // jab call hoga, yahan tak SYNCHRONOUSLY chalega (jaise normal function)
  await null;                                     // await yahan se function ko "pause" kar deta hai —
                                              // baaki ka function body ek microtask ban jaata hai
  console.log('5: async fn after await');     // ye microtask queue ke through, baad mein chalega
}
asyncFlow();                                       // function call kiya — 'await' tak turant chalega (sync part)

console.log('6: sync end');                      // baaki bachi hui synchronous code, isse continue chalti hai

// EXACT OUTPUT ORDER:
// 1: sync start          -> poora sync code pehle top-to-bottom (call stack empty hone tak)
// 4: async fn start      -> asyncFlow() call hote hi await tak sync chala
// 6: sync end            -> sync code ka aakhri statement
// 3: promise.then        -> ab call stack empty — microtask queue drain shuru,
//                            ye pehle queue hua tha (async/await ke continuation se pehle)
// 5: async fn after await -> ye doosra microtask tha, wahi order mein chala
// 2: setTimeout callback -> microtask queue poori tarah drain hone ke baad hi
//                            agla macrotask (setTimeout) uthaya gaya

Root logic: sabse pehle poora synchronous code (jo khud bhi ek "macrotask" hi hai — pura script) call stack pe chalta hai top-to-bottom, jab tak call stack empty na ho jaaye (isme asyncFlow() ka await se pehle wala hissa bhi shamil hai — kyunki wo synchronously chalta hai jab tak await hit na ho). Uske baad event loop microtask queue ko poora drain karta hai — pehle jo microtask pehle queue hua (FIFO within microtasks) wo pehle chalta hai, isliye promise.then (jo turant sync code mein queue hua) async fn after await se pehle chalta hai. Sabse aakhir mein, microtask queue khali hone ke baad hi engine agla macrotask (yahan setTimeout) uthaata hai — chahe delay 0 ho, wo hamesha sabse last chalega in is scenario mein.

Render step — macrotask aur microtask ke beech ka rishta

Browser rendering (style recalculation → layout → paint) ek task ke beech mein kabhi nahi hoti — na macrotask ke beech, na microtask ke beech. Rendering sirf tab consider hoti hai jab: (a) current macrotask poora chal chuka ho, AND (b) uske baad generate hue saare microtasks poori tarah drain ho chuke hon. Browser phir decide karta hai ki render karna hai ya nahi (usually screen refresh rate ke hisaab se, ~16.6ms per frame @ 60fps) — agar haan, to render step chalta hai, phir hi event loop agle macrotask ki taraf badhta hai.

Isi wajah se agar tum ek loop mein DOM ko 1000 baar modify karo (bina koi await/setTimeout ke), user ko beech ke koi bhi intermediate states dikhenge hi nahi — sirf final state render hogi, kyunki poora loop ek hi macrotask/synchronous block ke andar hai aur render us block ke beech mein interrupt nahi kar sakta.

Progress indicator ke liye CPU-heavy kaam ko split karna
function countHeavy(i, total) {              // i = current progress, total = kitna karna hai
  if (i >= total) return;              // base case — kaam khatam ho gaya to ruk jao

  let chunkEnd = Math.min(i + 1000000, total); // ek "chunk" mein sirf 1 million iterations karenge
  for (; i < chunkEnd; i++) {       // chunk ke andar hi normal synchronous loop
    // (yahan kuch heavy CPU calculation hoti — example ke liye khaali chhod diya)
  }

  document.getElementById('progress').innerText = i; // progress UI update karo (abhi paint nahi hoga)

  if (i < total) {                     // agar aur kaam baaki hai
    setTimeout(() => countHeavy(i, total), 0); // agla chunk NAYE macrotask ke roop mein schedule karo
  }                                            // (Promise.then use karte to ye kabhi render hi nahi hone deta —
                                              // kyunki microtask render ko block karta hai jab tak drain na ho)
}

countHeavy(0, 5000000);                              // 50 lakh iterations ko chunks mein todke start karo

Ye setTimeout ka ek non-obvious practical use hai: sirf "delay" ke liye nahi, balki current macrotask ko yahin khatam kar do, aur agla chunk naye macrotask ke roop mein schedule kar do — taaki uske beech mein render step ko chance mile chalne ka, aur user ko progress bar update hota hua dikhe. Agar isi kaam ko Promise.then/microtask se chain karte, render kabhi beech mein nahi aata kyunki microtask queue jab tak empty na ho, render step start hi nahi hota — matlab UI freeze dikhega jab tak sab kaam khatam na ho jaaye.

⚠️ Long synchronous task render ko block kar deta hai

Kyunki rendering sirf task boundaries ke beech hoti hai (macrotask khatam + microtasks drain ke baad), agar tumhara koi single synchronous function 500ms leta hai (heavy loop, JSON.parse bahut bade payload pe, blocking regex), to us poore duration mein browser kuch bhi paint nahi kar sakta — na scroll respond karega, na click, na koi animation frame chalega. Isse "jank" / frozen-page feeling hoti hai, aur Core Web Vitals mein ye Total Blocking Time (TBT) / Interaction to Next Paint (INP) ko directly hurt karta hai. Solution: heavy kaam ko chunks mein todo (upar wale pattern se), ya Web Worker pe move karo (jo main thread block hi nahi karta).

🧠 Senior Dev Note: microtask starvation ek real production bug hai

Agar recursive Promise chaining ho jaaye — jaise ek function jo har baar apne end pe khud ko Promise.resolve().then(() => recurse()) se call kare — to ye ek infinite microtask loop ban jaata hai jo kabhi macrotask queue ko chance hi nahi deta, aur render bhi kabhi nahi hota. Page completely frozen dikhega (koi error console mein bhi nahi aayega), lekin CPU 100% pe hoga. Ye bug production mein debug karna mushkil hota hai kyunki normal "infinite loop" detection tools (jaise long-task observer) is pattern ko clean task boundaries na hone ki wajah se miss kar sakte hain. Fix simple hai: recursion ko setTimeout ya requestAnimationFrame se break karo taaki wo macrotask ban jaaye, microtask nahi. Isi tarah, MutationObserver callbacks bhi microtask-based hone ki wajah se agar unke andar hi DOM ko mutate karte raho triggering condition ke saath, similar starvation ho sakta hai — is chapter ke pehle section se connect karke socho.

Key Takeaways

  • MutationObserver DOM changes ko batched, microtask-based callback ke through report karta hai — childList/subtree/attributes/characterData options se scope control hota hai.
  • MutationObserver callbacks synchronous nahi hote — call stack empty hone ke baad, ek batch (array of records) ke roop mein aate hain.
  • Range ek DOM region define karta hai (startContainer/startOffset se endContainer/endOffset tak); Selection user ke actual visible selection ko represent karta hai, jo internally ek ya zyada Range se bana hota hai.
  • surroundContents well-formed subtree assume karta hai — partial element boundaries cross karne pe fail hota hai; extractContents + insertNode fallback zyada robust hai.
  • Event Loop: call stack se sync code chalta hai → async operations Web APIs ko handover hote hain → completion pe callbacks macrotask ya microtask queue mein jaate hain → engine har macrotask ke baad microtask queue poori tarah drain karta hai → phir render (agar due ho) → phir agla macrotask.
  • Microtasks (Promise.then, async/await continuation, queueMicrotask) macrotasks (setTimeout, DOM events) se hamesha pehle chalte hain, chahe delay 0 ho.
  • Rendering sirf task boundaries ke beech hoti hai — kabhi macrotask ya microtask ke beech mein nahi. Isliye heavy synchronous code render ko block kar deta hai (jank/frozen UI).
  • Heavy CPU work ko chunks mein todke setTimeout se schedule karna (Promise chaining se nahi) render ko beech mein chance deta hai.

🎯 Interview Questions

  • Ye code trace karo aur exact console output order batao: console.log('a'); setTimeout(() => console.log('b'), 0); Promise.resolve().then(() => console.log('c')); console.log('d');
    Hint: sync code (a, d) pehle poora chalega, phir microtask queue drain hoga (c), phir macrotask (b) — output: a, d, c, b.
  • setTimeout(fn, 0) turant kyun nahi chalta?
    Hint: setTimeout callback macrotask queue mein jaata hai, jo tabhi process hota hai jab call stack empty ho aur current microtask queue poori tarah drain ho chuki ho — "0ms" sirf minimum delay hai, guaranteed immediate execution nahi.
  • Microtask queue macrotask se pehle kyun run hoti hai, aur ye "poori tarah drain" hone ka kya matlab hai?
    Hint: spec design choice hai taaki Promise chains consistently, predictably resolve hon before any new task starts; "poori tarah drain" matlab agar microtask khud naya microtask queue kare, wo bhi isi cycle mein consume ho jaata hai, agle macrotask se pehle.
  • Rendering event loop mein kahan fit hoti hai — kya wo har macrotask ke baad guaranteed hoti hai?
    Hint: nahi guaranteed har baar — render sirf task boundary (macrotask + poori microtask queue drain) ke baad ho sakti hai, aur browser decide karta hai ki actually render karni hai ya nahi (frame budget ke hisaab se). Kabhi bhi ek task ke beech mein render nahi hoti.
  • MutationObserver callback microtask hai ya macrotask, aur isse kya practical implication hai?
    Hint: microtask hai — matlab current synchronous block khatam hone ke turant baad batch mein fire hoga, setTimeout se pehle, lekin agar callback ke andar hi observer ko trigger karne wale mutations karte raho to starvation ho sakta hai.
  • Long-running synchronous function (jaise 2 second ka heavy loop) UI ko kaise affect karta hai, aur iska fix kya hai?
    Hint: poore 2 seconds tak render/paint/input handling block rehta hai (single-threaded call stack busy hai) — fix: kaam ko chunks mein todo setTimeout se, ya Web Worker pe move karo taaki main thread free rahe.
  • surroundContents() kab fail hota hai aur uska alternative kya hai?
    Hint: fail hota hai jab range partial/non-well-formed element boundaries cross karta hai; alternative: extractContents() se content nikalo, naye wrapper mein appendChild karo, phir insertNode() se wapas daalo.
  • Recursive Promise.then chaining se page freeze kaise ho sakta hai bina kisi console error ke?
    Hint: har .then call apne andar naya microtask schedule karta hai jo abhi wali drain-loop mein hi consume ho jaata hai — event loop kabhi macrotask/render step tak pahunch hi nahi paata, so page frozen dikhta hai but CPU busy rehta hai, koi stack-overflow ya error nahi aata kyunki har microtask apna alag call stack use karta hai.
