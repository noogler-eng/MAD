Map vs plain object — root-level farak

Plain object bhi key-value pairs store karta hai, to Map kyun chahiye? Do fundamental differences hain jo root mechanism se aate hain: (1) key ka type aur (2) iteration order ki guarantee.

Plain object mein har key internally string ya Symbol mein convert ho jaati hai — chahe tum object key ke roop mein number ya object pass karo, engine use toString() karke string bana deta hai. Map internally ek hash table jaisi structure use karta hai jo key ki identity (same reference/same primitive value) preserve karti hai — koi implicit stringification nahi hoti, isliye key ka original type (number, boolean, object reference, function) bilkul waisa hi rehta hai jaisa set kiya tha.

Object vs Map — key type coercion
let obj = {};                    // plain object banaya
obj[1] = "num-key";            // key 1 (number) diya — internally "1" string mein convert hoga
obj["1"] = "str-key";          // key "1" (string) diya — same "1" hi bantа hai, so ye overwrite ho jaata hai
console.log(obj[1]);              // "str-key" — dono keys clash ho gayi kyunki dono "1" ban gayi

let map = new Map();            // naya Map instance banaya
map.set(1, "num-key");       // key 1 (number type) ke against value set kiya
map.set("1", "str-key");     // key "1" (string type) — DIFFERENT key hai, koi clash nahi
console.log(map.get(1));       // "num-key" — number key apni identity retain karta hai
console.log(map.size);            // 2 — dono keys alag-alag treat hui

Doosra bada advantage: Map objects ko bhi key ban sakte hain, aur equality reference-based hoti hai (same object reference tabhi match karega). Ye Map ko ek natural fit banata hai un cases ke liye jahan tumhe "kisi object ke against extra metadata attach karni ho, without touching that object" — jaise DOM element ke against click-count store karna.

Map with object keys
let john = { name: "John" };   // ek user object
let visitsCountMap = new Map(); // object ki key ban sakti hai aisa Map

visitsCountMap.set(john, 123);  // john OBJECT (reference) ko key banaya, value 123 hai
console.log(visitsCountMap.get(john)); // 123 — same reference se lookup ho gaya

// plain object mein aisa nahi kar sakte — john automatically string mein coerce ho jaata,
// aur "[object Object]" banta, jisse DIFFERENT objects bhi same key pe collide kar jaate

Iteration order bhi guaranteed hai — Map insertion order follow karta hai (spec-mandated), jabki plain object ka key order historically integer-like keys ko numeric ascending order mein pehle rakhta hai, phir string keys ko insertion order mein — ye subtle inconsistency Map mein exist hi nahi karti.

Map — core API + iteration
let recipeMap = new Map([    // array-of-pairs se directly Map initialize kiya
  ['cucumber', 500],          // pehla [key, value] pair
  ['tomatoes', 350]          // doosra [key, value] pair
]);

console.log(recipeMap.size);         // 2 — total entries ka count
console.log(recipeMap.has('cucumber')); // true — key exist karti hai?
recipeMap.delete('cucumber');       // key-value pair remove kiya

for (let vegetable of recipeMap.keys()) {  // sirf keys pe iterate — insertion order guaranteed
  console.log(vegetable);            // har key print
}

for (let [key, value] of recipeMap) {       // Map khud iterable hai (entries() implicit) — [key,value] destructure hota hai
  console.log(key, value);        // key aur value dono ek saath mil gaye
}

// Object <-> Map conversions — real-world interop ke liye zaroori
let obj = { name: "John", age: 30 };
let fromObj = new Map(Object.entries(obj)); // Object.entries obj ko [[k,v],...] array deta hai, Map us se ban jaata hai
let backToObj = Object.fromEntries(fromObj);  // wapas plain object mein convert — Map iterable hai, fromEntries directly accept karta
🧠 Senior Dev Note: Map kab use karo, plain object kab

Rule of thumb: agar keys runtime pe dynamically add/remove hoti hain (jaise cache, ya per-object metadata), Map use karo — frequent add/delete pe Map internally better optimized hai kyunki engine ko "is ye ek dictionary hai" hint mil jaata hai, jabki plain object "shape" (hidden class) ke around optimize hota hai aur dynamic keys add/delete karna us shape ko baar-baar invalidate karta hai (V8 mein "dictionary mode" mein fallback ho jaata hai, jo slower hai). Fixed, known-at-authoring-time keys (jaise config, DTOs) ke liye plain object better hai — JSON-serializable bhi hota hai directly, jo Map nahi hai (JSON.stringify(map) {} deta hai, tumhe Object.fromEntries se convert karna padega).

Set — uniqueness guarantee, hash-based

Set ek collection hai jisme har value sirf ek baar exist kar sakti hai. Root mechanism Map jaisa hi hai — internally ek hash-table-like structure jo value ki equality (=== semantics, thoda tweaked for NaN) check karke duplicate insert ko silently ignore kar deta hai.

Set — core API
let set = new Set();          // naya empty Set

set.add("apple");          // "apple" add kiya
set.add("apple");          // dobara "apple" — ye NO-OP hai, Set already isse hold kar raha
set.add("banana");         // naya unique value add hua

console.log(set.size);       // 2 — duplicate count nahi hua
console.log(set.has("apple"));  // true — membership check O(1) hai (array ke .includes() jaisa O(n) nahi)

function unique(arr) {       // array se duplicates hatane ka one-liner utility
  return Array.from(new Set(arr)); // arr se Set banaya (auto-dedupe), phir wapas array mein spread
}

console.log(unique(["Hare", "Krishna", "Hare"])); // ["Hare", "Krishna"]

Set bhi insertion order maintain karta hai, aur iterable hai (for..of, spread, Array.from sab kaam karte hain). set.forEach((value, valueAgain, set) => {...}) ka signature Map ke saath compatible rakhne ke liye value ko do baar deta hai — historical/API-consistency reason hai, real use mein doosra argument generally ignore hota hai.

WeakMap/WeakSet — garbage-collection-friendly references

Ye samajhne ke liye pehle GC ka basic model yaad karo: JavaScript ka garbage collector kisi bhi value ko memory mein tab tak rakhta hai jab tak wo reachable hai — matlab kisi root (global scope, currently-executing function ki call stack) se koi chain of references us tak pahunch sakti hai. Jaise hi last reference hat jaata hai, engine us memory ko free kar sakta hai.

Regular Map apni keys (aur values) ko strong reference se hold karta hai — matlab agar tum kisi object ko Map ki key banao, aur baad mein us object ka poora baaki application se reference hata bhi do, Map abhi bhi use hold kiye rahega, isliye GC use clean nahi kar sakta. Ye ek silent memory leak ban sakta hai agar tum "per-object metadata" jaisa pattern use kar rahe ho aur wo objects poori application life mein baar-baar create/discard hote hain.

Map memory leak vs WeakMap auto-cleanup
// --- Regular Map: LEAK scenario ---
let john = { name: "John" };   // object banaya
let map = new Map();
map.set(john, "some metadata"); // john ko key banaya — Map ab STRONG reference hold karta hai

john = null;              // "outside" wala reference hata diya
// PHIR BHI john ka original object memory mein zinda hai, kyunki map[key] abhi bhi
// use reference kar raha hai internally — GC isse clean nahi kar sakta

// --- WeakMap: auto-cleanup scenario ---
let jane = { name: "Jane" };
let weakMap = new WeakMap();
weakMap.set(jane, "some metadata"); // jane WEAK reference se hold hoti hai

jane = null;              // last "real" reference gaya
// ab jane object ke pass koi reachable strong reference nahi bacha (WeakMap gin nahi ke)
// so GC engine ki marzi se (kab, deterministic nahi) is entry ko WeakMap se bhi hata dega

Isi weak-reference property ki wajah se WeakMap/WeakSet jaan-boojh kar apni API restrict karte hain: no size, no clear(), no iteration (keys()/values()/entries()/for..of koi nahi chalta). Root reason — GC kab actual collection karega ye engine-dependent aur non-deterministic hai (spec ise define nahi karta), so agar iteration allowed hota, to "iterate karte time entry beech mein hi GC ho jaana" jaisa race condition create hota, aur size bhi ek pal true, doosre pal false ho sakta tha — ye unpredictable API design hoti. Isliye sirf set/get/has/delete (WeakMap) aur add/has/delete (WeakSet) available hain — sab operations jinke liye tumhe key ka reference already chahiye hota hai (blind iteration ki zaroorat nahi).

WeakMap real use case — caching without leaks
let cache = new WeakMap();       // object -> computed-result cache

function process(obj) {
  if (!cache.has(obj)) {    // pehli baar dekha ye obj?
    let result = obj.data * 2; // (dummy) expensive computation
    cache.set(obj, result);  // result cache mein daal diya, obj ke against
    return result;
  }
  return cache.get(obj);       // pehle se computed — cache se seedha return
}

let obj = { data: 21 };
process(obj);                    // pehli call — compute + cache
process(obj);                    // doosri call — direct cache hit

obj = null;                   // obj discard kar diya (e.g. component unmount ho gaya)
// regular Map hota to cached entry hamesha ke liye memory mein reh jaati (leak)
// WeakMap hone se, obj GC hote hi cache entry bhi apne aap saaf ho jaati hai
⚠️ WeakSet/WeakMap sirf OBJECT keys accept karte hain

Primitives (string, number, boolean) ko key ke roop mein use nahi kar sakte — root reason simple hai: primitives value-semantics follow karte hain (ek naya "abc" string literal aur purana "abc" effectively "same" treat hote hain, koi unique memory address nahi jise weakly-reference kiya ja sake), jabki objects reference-semantics follow karte hain (har {} apni alag memory identity rakhta hai) — weak referencing ka concept sirf reference-semantics values pe hi meaningful hai.

Object.keys/values/entries + iterating objects

Array/Map/Set ke .keys()/.values()/.entries() instance methods hote hain, lekin plain object ke liye ye static methods hain — Object.keys(obj), na ki obj.keys(). Root reason: object JavaScript ke har complex structure ka base hai — agar keys() ko instance method banate, to koi bhi custom object jo khud apna .keys property/method define karta hai (jaise ek data object jisme business-logic values() method ho), wahan naming clash ho jaata. Static form (Object.keys(obj)) is ambiguity ko completely avoid karta hai kyunki wo obj ke apne namespace ko touch hi nahi karta.

Object.keys/values/entries + transform pattern
let prices = {
  banana: 1,                   // key: banana, value: 1
  orange: 2,                   // key: orange, value: 2
  meat: 4                     // key: meat, value: 4
};

console.log(Object.keys(prices));   // ["banana", "orange", "meat"] — REAL array (Map jaisa iterable nahi)
console.log(Object.values(prices)); // [1, 2, 4]
console.log(Object.entries(prices)); // [["banana",1], ["orange",2], ["meat",4]]

// Step 1-2-3 pattern: object -> array (transform) -> object
let doublePrices = Object.fromEntries(   // step 3: array-of-pairs ko wapas object mein convert
  Object.entries(prices)                // step 1: object -> [[key,value], ...] array
    .map(([key, value]) => [key, value * 2]) // step 2: array method (map/filter) apply — object khud [] nahi rakhta
);

console.log(doublePrices.meat);            // 8 — meat: 4 * 2

Ek subtle detail: Object.keys/values/entries, for..in ki tarah, Symbol keys ko skip kar dete hain — sirf string keys return hoti hain. Agar Symbol keys bhi chahiye, to Object.getOwnPropertySymbols(obj) ya Reflect.ownKeys(obj) (jo dono — string aur symbol — deta hai) use karo.

Destructuring — position-vs-name matching ka exact mechanism

Destructuring "unpack" karne ka syntax hai — lekin array aur object destructuring ka underlying matching mechanism fundamentally different hai, aur ye samajhna zaroori hai taaki bugs na ho:

  • Array destructuring — position-based hai. let [a, b] = arr mein a ko arr ka pehla iterated value milta hai, b ko doosra — chahe unke naam kuch bhi ho. Internally ye array ke iterable protocol (Symbol.iterator) se driven hota hai, isliye kisi bhi iterable (string, Set, generator) pe kaam karta hai.
  • Object destructuring — name-based hai. let {width, height} = options mein engine options.width aur options.height property lookup karta hai — property ka order object mein matter nahi karta.
Array destructuring — position-based matching
let arr = ["John", "Smith"];
let [firstName, surname] = arr;  // index 0 -> firstName, index 1 -> surname (POSITION se)
console.log(firstName);            // "John"

let [first, , third] = ["Julius", "Caesar", "Consul"]; // khaali comma se ek position SKIP kar diya
console.log(third);                // "Consul" — index 2

let [a, b] = "ab".split("");  // string bhi iterable hai, so ye bhi array-jaisa destructure hota hai
Object destructuring — name-based matching, order irrelevant
let options = {
  title: "Menu",
  width: 100,
  height: 200
};

let { height, title, width } = options; // order badla hua hai LHS mein, phir bhi correctly match hoga — NAME se lookup
console.log(width);              // 100 — kyunki "width" property se match hua, position se nahi

let { width: w, height: h } = options; // "propertyName: localVarName" — rename karte hue destructure
console.log(w, h);              // 100 200 — local variable names w/h hain, lekin values width/height se aayi
Defaults, rest, nested destructuring
// --- Defaults: sirf tab lagte hain jab value undefined ho (missing key ya missing array slot) ---
let { width = 100, title } = { title: "Menu" }; // width object mein hai hi nahi -> default 100 use hua
console.log(width);                 // 100

// --- Rest: baaki bache hue properties ek naye object/array mein collect ---
let { title: t, ...rest } = { title: "Menu", width: 100, height: 200 };
console.log(rest);                  // { width: 100, height: 200 } — title consume ho gaya, baaki rest mein

let [name1, ...others] = ["Julius", "Caesar", "Consul"]; // array rest — remaining elements ka array
console.log(others);                // ["Caesar", "Consul"]

// --- Nested destructuring: structure ko exactly mirror karo ---
let settings = {
  size: { width: 100, height: 200 }, // nested object
  items: ["Cake", "Donut"]          // nested array
};
let {
  size: { width, height },              // settings.size ke andar se width/height nikaale
  items: [item1, item2]          // settings.items array ke pehle 2 elements
} = settings;
console.log(width, item1);          // 100 "Cake"

Real-world sabse common use: function parameters ke saath. Config-object-style parameters ko directly destructure karna caller ko named-argument jaisa ergonomics deta hai (order matter nahi karta, defaults free milte hain):

Smart function parameters — object destructuring
function showMenu({
  title = "Untitled",      // param object mein title na ho to "Untitled" default
  width = 200,            // width ka default
  height = 100,           // height ka default
  items = []              // items ka default — empty array
} = {}) {                // = {} zaroori: agar caller koi argument hi na de, destructure {} pe hoga (crash nahi)
  console.log(`${title} ${width}x${height}`); // template literal se sab ek saath print
}

showMenu({ title: "My Menu", items: ["Item1"] }); // width/height defaults se aayenge, order matter nahi karta
showMenu();                          // koi argument nahi — sab defaults use honge, error nahi aayega
⚠️ Object destructuring bina let/const ke — parentheses zaroori

{title, width} = obj; likhoge to JS engine line-start pe { ko code block samajh leta hai (statement, expression nahi), aur syntax error de deta hai. Fix: ({title, width} = obj); — parentheses se engine ko batate ho ki ye expression hai, block nahi.

Date object — internals + timezone gotchas

Date internally ek single number store karta hai — Unix epoch se milliseconds (1 Jan 1970, 00:00:00 UTC se). Har getFullYear(), getMonth(), etc. call is internal number ko local timezone ke hisaab se decode karke deta hai (UTC variants — getUTCFullYear() etc. — bina timezone-adjustment ke deते hain).

Date creation — 4 tareeke
let now = new Date();              // current date+time (system clock se)

let epoch = new Date(0);            // 0 ms since epoch = 1 Jan 1970, 00:00:00 UTC
let dayAfter = new Date(24 * 3600 * 1000); // 1 din baad = 86400000 ms se banaya

let fromStr = new Date("2017-01-26"); // ISO string se parse — local timezone mein interpret hota hai

// year, month(0-11!), day, hours, min, sec, ms — components se
let fromParts = new Date(2024, 0, 15, 10, 30); // month=0 matlab JANUARY, 15 Jan 2024 10:30
⚠️ Month zero-indexed hai — sabse common Date bug

getMonth() aur constructor ka month-param 0 se 11 tak hota hai — January = 0, December = 11. Root reason historical hai (Java's original Date API se inherited convention, jo JS ke earliest versions mein carry ho gaya aur ab backward-compat ke liye badal nahi sakte). Bug pattern: new Date(2024, 3, 1) April 1 dega, March 1 nahi — bahut developers month ko human-month (1-12) samajh ke off-by-one bug daal dete hain. Isi tarah getDay() bhi 0-6 return karta hai, jahan 0 = Sunday (day-of-MONTH ke liye getDate() use karo, jo 1-31 hai).

Autocorrection + Date arithmetic
let date = new Date(2013, 0, 32); // Jan 32 out-of-range hai — engine AUTO-CORRECT karta hai
console.log(date);                  // 1 Feb 2013 — overflow agle month mein carry ho gaya

let feb28 = new Date(2016, 1, 28); // 28 Feb 2016 (leap year hai)
feb28.setDate(feb28.getDate() + 2); // 28 + 2 = 30, jo Feb mein exist nahi karta — auto overflow into March
console.log(feb28);                  // 1 Mar 2016 — is leap-year-aware manual calculation ki zaroorat khatam

// --- Date -> number conversion, subtraction ---
let start = new Date();
for (let i = 0; i < 100000; i++) { } // kuch busy-work
let end = new Date();
console.log(end - start);            // dono Dates ko unary "-" implicit number banata hai -> ms difference

// --- Date.now(): benchmarking ke liye BEHTAR — intermediate Date object nahi banata ---
let t0 = Date.now();            // current timestamp (number), no object allocation overhead
// ... work ...
let elapsed = Date.now() - t0;    // ms elapsed

Timezone gotcha: new Date("2017-01-26") jaisa date-only ISO string diya jaaye to spec ke hisaab se ye UTC midnight maana jaata hai — lekin display/getters (getHours() etc.) tumhari machine ke local timezone mein show hote hain. Agar tum UTC-negative timezone (jaise US) mein ho, to new Date("2017-01-26").getDate() kabhi-kabhi 25 print kar sakta hai, na ki 26 — kyunki UTC midnight local time mein pichle din ki shaam thi. Ye ek notorious production bug source hai; date-only strings ko handle karte waqt hamesha explicit rehna chahiye ki UTC use kar rahe ho ya local.

JSON.stringify/parse — exact serialization rules

JSON.stringify(value, replacer, space) value ko JSON text mein convert karta hai, lekin JSON format JS ke har construct ko represent nahi kar sakta — spec explicitly kuch cheezein silently skip karta hai:

  • Function properties (methods) — completely ignore ho jaati hain
  • Symbol keys aur Symbol values — dono skip
  • undefined valued properties — key hi drop ho jaati hai
Stringify skip-rules demo
let user = {
  sayHi() { },          // method — SKIP hogi
  [Symbol("id")]: 123,       // symbol key — SKIP hogi
  something: undefined,    // undefined value — SKIP hogi
  name: "John"            // normal string — INCLUDE hoga
};

console.log(JSON.stringify(user)); // '{"name":"John"}' — sirf serializable data bacha
replacer — function form (filter/transform) aur array form
let room = { number: 23 };
let meetup = {
  title: "Conference",
  room,                       // shorthand — room: room
  participants: ["john", "ann"]
};
meetup.self = meetup;          // circular reference (self-pointer) — plain stringify yahaan CRASH karega

// --- Array replacer: sirf listed keys hi include hongi (whitelist) ---
let json1 = JSON.stringify(meetup, ['title', 'participants']); // "room" aur "self" (circular) dono skip ho jaate

// --- Function replacer: har [key, value] pair ke liye call hota hai, undefined return = skip ---
let json2 = JSON.stringify(meetup, function replacer(key, value) {
  return (key == 'self') ? undefined : value; // "self" key hit hone pe undefined -> circular ref se bacha, warna value as-is
});

// --- space param: readability ke liye indentation ---
console.log(JSON.stringify(room, null, 2)); // 2-space indent — replacer nahi chahiye to null do
toJSON — custom serialization hook
let room = {
  number: 23,
  toJSON() {                // agar object mein toJSON() method mile, JSON.stringify use ISE call karta hai
    return this.number;       // poore object ki jagah sirf ye return value serialize hogi
  }
};
console.log(JSON.stringify(room));   // "23" — {number:23} nahi, kyunki toJSON() ne override kar diya

// Date built-in objects mein already toJSON() define hai — isliye Date directly stringify hoti hai
let meetup = { date: new Date(Date.UTC(2017, 10, 30)) };
console.log(JSON.stringify(meetup)); // '{"date":"2017-11-30T00:00:00.000Z"}' — Date.toJSON() ISO string deta hai
JSON.parse + reviver — Date strings ko wapas Date banao
let str = '{"title":"Conference","date":"2017-11-30T12:00:00.000Z"}';

// bina reviver ke — date sirf ek plain STRING hi rahegi, Date object nahi ban paayega automatically
let plain = JSON.parse(str);
console.log(typeof plain.date);  // "string" — .getDate() jaisa Date method call karoge to CRASH

// reviver: har [key, value] pair pe recursively call hota hai (deepest nodes pehle, phir parent)
let meetup = JSON.parse(str, function(key, value) {
  if (key == 'date') return new Date(value); // "date" key mile to string -> real Date object mein convert
  return value;                    // baaki sab as-is return
});

console.log(meetup.date.getDate());  // works! — ab ye ek asli Date instance hai, method call safe hai
🧠 Senior Dev Note: JSON round-trip data loss production mein

API responses/localStorage se aane wala JSON kabhi bhi apne-aap Date, Map, Set, ya Symbol nahi banata — sab kuch primitives (string/number/boolean/null) aur plain objects/arrays mein flatten ho jaata hai. Ye sabse common source hai un bugs ka jahan "backend se aayi date .getMonth() pe crash karti hai" — kyunki wo ek string hai, Date object nahi. Production apps mein isliye ya to consistent reviver/replacer pair maintain karo (jaise upar), ya boundary layer (API client) mein explicitly parse karo before data app ke andar propagate ho.

Key Takeaways

  • Map: koi bhi type key ban sakta hai (objects included), insertion order guaranteed, string coercion nahi hoti — dynamic/frequently-mutating key-value data ke liye plain object se behtar.
  • Set: unique values ka collection, add() duplicate pe silently no-op karta hai, membership check O(1) hai.
  • WeakMap/WeakSet: sirf object keys, weak references rakhte hain isliye keys unreachable hote hi GC-eligible ban jaate hain — iski wajah se hi iteration/size/clear API se hata diye gaye hain (non-deterministic GC timing ke saath unreliable hote).
  • Object.keys/values/entries static methods hain (namespace clash avoid karne ke liye), real array return karte hain, Symbol keys skip karte hain.
  • Array destructuring position-based hai (iterable protocol driven), object destructuring name-based hai (property lookup driven) — dono defaults aur rest (...) support karte hain.
  • Date internally epoch-ms number store karta hai; getMonth() 0-indexed hai (Jan=0) — sabse common Date bug source.
  • JSON.stringify functions/symbols/undefined silently skip karta hai, toJSON() method ho to use call karta hai (Date mein built-in hai), replacer function/array se custom filtering ho sakti hai.
  • JSON.parse ka reviver zaroori hai custom types (Date, etc.) wapas reconstruct karne ke liye — plain parse sab kuch string/number/boolean/plain-object/array tak hi degrade karta hai.

🎯 Interview Questions

  • Map plain object se better kyun hai kuch scenarios mein?
    Hint: koi bhi type key ban sakta hai bina stringification ke, guaranteed insertion-order iteration, frequent add/delete pe better optimized (V8 dictionary-mode fallback avoid).
  • WeakMap mein iteration aur size property kyun nahi hote?
    Hint: garbage collection timing non-deterministic/engine-dependent hai — agar size/iteration allowed hote, to result unpredictable hota (entries kabhi bhi silently disappear ho sakti thin mid-iteration).
  • WeakMap ka ek real production use-case batao.
    Hint: per-object metadata/cache jo automatically cleanup ho jaaye jab wo object discard ho — jaise DOM element ke against listener state, ya memoization cache.
  • Array destructuring aur object destructuring ke matching mechanism mein exact farak kya hai?
    Hint: array = position/iteration-order based (iterable protocol se driven); object = property-name based (order irrelevant, lookup by key).
  • new Date(2024, 3, 1) kaunsa month dega, aur kyun?
    Hint: April — month parameter 0-indexed hai (0=Jan...11=Dec), historically Java Date API se inherited convention.
  • JSON.stringify function properties aur undefined values ko kyun skip karta hai?
    Hint: JSON format spec sirf primitives + plain objects/arrays represent kar sakta hai — functions/undefined/symbols JSON mein koi valid representation nahi rakhte, isliye silently drop hote hain (arrays mein undefined "null" ban jaata hai, objects mein poori key hi gayab ho jaati hai).
  • toJSON method kya karta hai, aur Date isse kyun use karta hai?
    Hint: JSON.stringify agar object pe toJSON() method paata hai to poore object ki jagah uska return value serialize karta hai — Date isse apna ISO-string representation dene ke liye use karta hai, warna Date ka default JSON representation meaningless hota.
  • JSON round-trip (stringify phir parse) ke baad ek Date field ka type kya hoga, aur isse kaise fix karte hain?
    Hint: type "string" ban jaata hai (Date object nahi), fix ke liye JSON.parse ka reviver function use karo jo specific keys ko wapas new Date(value) mein convert kare.
