Numbers & Strings

Primitives (number, string, boolean) "lightweight" hote hain — koi property, koi method nahi rakh sakte, direct object nahi hain. Fir bhi "abc".toUpperCase() kaam kyun karta hai? Iske peeche ek internal trick hai — temporary wrapper object. Is chapter mein hum ye trick, Number ka IEEE-754 binary representation (jisse 0.1 + 0.2 !== 0.3 aata hai), aur String ka UTF-16 internal encoding — sab root-level samjhenge.

Object wrapper trick — primitives pe methods kaise chalte hain

Ye JS ke design mein ek fundamental contradiction lagta hai: primitives ko "lightweight" hona chahiye (no properties, no methods — sirf raw value), lekin developer experience ke liye str.toUpperCase() jaisi calls chahiye. Spec is contradiction ko ek clever trick se resolve karta hai — jab bhi tum kisi primitive pe method call karte ho, engine ek temporary wrapper object banata hai, method usi object pe run hota hai, aur turant wo object discard ho jaata hai.

Wrapper trick — step by step
let str = "hello"; // str ek PRIMITIVE hai — object nahi, koi method physically iske saath attached nahi

str.toUpperCase(); // jab engine ye line dekhta hai, andar ye hota hai:
// 1. ek special String wrapper object banta hai: new String(str)
// 2. toUpperCase() method us wrapper object pe call hota hai, jo "HELLO" return karta hai
// 3. wrapper object turant destroy ho jaata hai (garbage collected)
// str variable khud abhi bhi original primitive "hello" hi hai — unchanged

console.log(typeof str); // "string" — proof ki str ab bhi primitive hi hai, object nahi bana

Ye exact same mechanism Number aur Boolean primitives ke liye bhi chalta hai. Har primitive type ka apna corresponding wrapper constructor hai: String, Number, Boolean, Symbol, BigInt — in sab par methods define hain, aur wahi methods primitives ko "borrow" milte hain wrapper ke through.

📌 null aur undefined exception hain

null aur undefined ke liye koi corresponding wrapper object exist nahi karta. Isliye null.toString() ya undefined.length jaisa kuch bhi likhoge to seedha TypeError: Cannot read properties of null milega — engine ke paas wrap karne ke liye koi wrapper hi nahi hai.

new Number()/new String() ke gotchas

Chunki wrapper constructors (String, Number, Boolean) publicly accessible hain, tum manually bhi new Number(5) likh sakte ho — lekin ye strongly discouraged hai kyunki isse actual object ban jaata hai, primitive nahi, aur uska behavior surprising hota hai.

new Number() ka trap
let zero = new Number(0); // "new" ke saath call karne se ek REAL OBJECT banta hai, primitive nahi

console.log(typeof zero); // "object" — number nahi! ye bahut confusing bug source hai

if (zero) {                    // object hamesha truthy hota hai in if-checks mein, chahe value 0 ho
  console.log("zero is truthy!!"); // YE line chalti hai — obviously wrong intuition ke against
}

let num = Number("123");   // BINA "new" ke — ye sirf TYPE CONVERSION hai, safe aur recommended
console.log(typeof num);    // "number" — primitive hi bana, conversion ke through
Primitive pe property assign karna — silently fail hota hai
let str = "Hello"; // primitive string

str.test = 5;    // ye internally: (1) temp wrapper banta hai, (2) uspe test=5 set hota hai,
                // (3) wrapper turant discard ho jaata hai — property kabhi save hi nahi hoti

console.log(str.test); // undefined — original str primitive pe kabhi test property thi hi nahi
// strict mode ("use strict") mein ye line assignment ek TypeError throw karti hai, silent fail nahi hoti
🧠 Senior Dev Note: engines actual wrapper skip kar dete hain

Spec-level pe har method call ek wrapper object create/destroy karta hai, lekin real engines (V8, SpiderMonkey) is allocation ko optimize away kar dete hain jab tak observable behavior spec ke identical rahe — matlab tumhare code ko chalane mein har baar heap allocation nahi ho rahi hoti, JIT compiler ye "as-if" rule follow karte hue skip kar deta hai. Ye samajhna zaroori hai kyunki string/number methods "expensive" nahi hote practice mein, jaisa naively wrapper-per-call model se lagta hai.

Number internals — IEEE 754 binary float

JavaScript mein sirf ek numeric primitive type hai — number — jo internally 64-bit IEEE-754 double-precision floating point format mein store hota hai. 64 bits is tarah divide hote hain: 1 bit sign ke liye, 11 bits exponent (decimal point kahan hai) ke liye, aur 52 bits mantissa/fraction (actual digits) ke liye. Isi wajah se JS mein integer aur float ek hi type hain — 5 aur 5.5 dono "number" hi hain.

52-bit mantissa ka direct consequence hai safe integer limit: Number.MAX_SAFE_INTEGER = 2^53 - 1 = 9007199254740991. Isse bada koi integer bina precision loss ke represent nahi ho sakta — do consecutive integers (jaise 2^53 aur 2^53 + 1) same binary pattern share karne lagte hain.

Safe integer limit ka proof
console.log(Number.MAX_SAFE_INTEGER); // 9007199254740991 — isse aage precision guaranteed nahi

let big = 9007199254740991 + 1; // MAX_SAFE_INTEGER + 1
let bigger = 9007199254740991 + 2; // MAX_SAFE_INTEGER + 2

console.log(big === bigger); // true !! — dono ek hi binary pattern mein round ho gaye, precision khatam

// Iske liye BigInt use karo — ek alag primitive type jo arbitrary-precision integers store karta hai
let reallyBig = 9007199254740993n; // trailing "n" suffix = BigInt literal, exact precision

0.1 + 0.2 !== 0.3 — root cause

Ye JS ka sabse mashhoor "gotcha" hai, lekin ye JS-specific bug nahi hai — ye IEEE-754 binary floating point ka fundamental limitation hai (Python, Java, C — sabme same behavior hota hai). Root cause: 0.1 aur 0.2 ko binary (base-2) fractions mein exactly represent nahi kiya ja sakta — bilkul waise hi jaise decimal (base-10) mein 1/3 ko exactly likhna impossible hai (0.333... infinitely chalta hai).

Floating point imprecision — dekho aur samjho
console.log(0.1 + 0.2);         // 0.30000000000000004 — expected 0.3 nahi mila
console.log(0.1 + 0.2 === 0.3); // false — root: dono operands binary mein hi approximate the

// WHY: 0.1 decimal mein binary fraction hai 0.0001100110011... (repeating, infinite)
// 52-bit mantissa mein sirf FIXED number of bits fit hote hain, so ye truncate/round hota hai
// stored 0.1 asal mein 0.1000000000000000055511151231257827021181583404541015625 hai (bahut close, exact nahi)
// jab do aise approximated numbers add hote hain, rounding errors accumulate ho jaate hain

// FIX 1: toFixed se display-level round karo (result string return karta hai)
console.log((0.1 + 0.2).toFixed(2)); // "0.30" — string hai, number nahi, display ke liye theek

// FIX 2: comparison ke liye epsilon (chhota threshold) use karo
console.log(Math.abs(0.1 + 0.2 - 0.3) < Number.EPSILON); // true — "close enough" check

// FIX 3: money/currency jaisi cheezein — integers (paise/cents) mein store karo, floats mein nahi
let priceInPaise = 1050; // ₹10.50 ko 1050 paise ke roop mein — integer math mein no precision loss
⚠️ Production mein ye kahan bite karta hai

E-commerce cart totals, financial calculations, ya kisi bhi jagah decimal currency add/subtract ho rahi ho — agar directly floats use kiye to rounding errors accumulate ho kar galat totals dikha sakte hain (jaise ₹19.999999999999996 instead of ₹20). Root fix: currency ko hamesha smallest integer unit (paise/cents) mein store aur calculate karo, sirf display ke time decimal mein convert karo.

Number likhne ke tareeke

e-notation, underscore separator, hex/octal/binary
let billion = 1e9;          // 1 * 10^9 = 1000000000 — "e9" matlab 9 zeros aage
let microsecond = 1e-6;    // 1 * 10^-6 = 0.000001 — negative exponent, decimal point 6 places left

let readable = 1_000_000_000; // underscore sirf readability ke liye — engine ignore karta hai, value same billion hai

let hex = 0xff;          // hexadecimal (base 16): 0x prefix, ff = 255 decimal
let binary = 0b11111111; // binary (base 2): 0b prefix, same value 255
let octal = 0o377;       // octal (base 8): 0o prefix, same value 255

console.log((255).toString(16));  // "ff" — toString(base) kisi bhi number ko given base mein convert karta hai (2-36)
console.log((255).toString(2));   // "11111111" — base 2, useful for bitwise debugging
// note: (255).toString() mein extra parens/space zaroori — warna "255." se JS ise decimal point samajhega

Rounding — toFixed, toPrecision, Math functions

Rounding methods comparison
console.log(Math.floor(3.6));    // 3 — hamesha neeche round (towards -Infinity)
console.log(Math.ceil(3.1));     // 4 — hamesha upar round (towards +Infinity)
console.log(Math.round(3.5));    // 4 — nearest integer, .5 upar jaata hai
console.log(Math.trunc(3.9));    // 3 — sirf decimal part hata do, koi rounding nahi

let num = 12.3456;
console.log(num.toFixed(2));    // "12.35" — exactly n digits AFTER decimal, string return karta hai, trailing zeros bhi rakhta hai
console.log(num.toPrecision(4)); // "12.35" — TOTAL 4 significant digits (not just after decimal), string return
console.log((5).toFixed(2));  // "5.00" — trailing zeros pad ho jaate hain, useful for currency display

parseInt/parseFloat aur isNaN/isFinite

String → Number parsing aur validity checks
console.log(parseInt("100px"));    // 100 — leading numeric part padhta hai, "px" pe ruk jaata hai (Number() would give NaN)
console.log(parseFloat("12.5em")); // 12.5 — decimal point tak parse karta hai, "em" ignore
console.log(parseInt("ff", 16)); // 255 — second arg = radix/base, hex string ko decimal mein convert
console.log(parseInt("abc"));    // NaN — koi bhi leading digit nahi mila, parse hi nahi ho paya

console.log(isNaN("abc"));          // true — global isNaN() PEHLE argument ko Number() se convert karta hai, phir check
console.log(Number.isNaN("abc"));   // false — strict version, koi coercion nahi, direct type+value check (string !== NaN)
console.log(Number.isNaN(NaN));      // true — actual NaN value pe hi true deta hai

console.log(isFinite("15"));        // true — coerce karke check karta hai ki NaN/Infinity/-Infinity toh nahi
console.log(Number.isFinite("15")); // false — strict version, string ko convert nahi karta, sirf actual number type check
💡 Rule of thumb

Production code mein hamesha Number.isNaN aur Number.isFinite ko prefer karo — global isNaN/isFinite ka implicit type coercion confusing bugs de sakta hai (jaise isNaN("abc") true hai but string kabhi number thi hi nahi).

String internals — UTF-16 code units

JavaScript strings internally UTF-16 encoding mein stored hote hain — matlab har character ko ek ya do 16-bit "code units" mein represent kiya jaata hai. .length property actual "characters" ka count nahi deti, balki UTF-16 code units ka count deti hai — ye distinction advanced Unicode characters ke saath important ho jaata hai (aage surrogate pairs section mein dekhenge).

length property — escape sequences count hote hain as one unit
let str = "My\n"; // M, y, aur \n (newline) — teen characters, \n ek hi special char hai
console.log(str.length); // 3 — \n do characters nahi (backslash + n), ek hi code unit hai

String immutability — proof

Strings JavaScript mein immutable hain — ek baar bana lene ke baad, uske andar ka koi bhi character direct modify nahi ho sakta. Ye array se fundamentally different hai. Immutability ka faayda: strings safely share ho sakti hain (memory mein duplicate nahi karna padta) aur multiple references ke beech koi accidental mutation nahi ho sakti.

Immutability ka direct proof
let str = "Hi";

str[0] = "h";  // index pe direct assignment try karo — silently fails (non-strict mode mein error bhi nahi aati)
console.log(str); // "Hi" — kuch change nahi hua, "H" bilkul waisa hi hai jaisa tha

// SAHI tareeka: naya string banao, poori tarah reassign karo
str = str[0].toLowerCase() + str.slice(1);
// str[0] = "H", .toLowerCase() se "h" mila; str.slice(1) = "i" (index 1 se end tak)
// dono ko concat karke ek NAYA string "hi" bana, phir variable str usko point karne laga
console.log(str); // "hi" — original "Hi" string object memory mein untouched hi hai, ye ek naya hai
🧠 Senior Dev Note: repeated concatenation ka cost

Immutability ka ek performance implication hai — loop mein baar-baar str += char karna har iteration pe ek naya string object allocate karta hai (O(n) copy har baar), so ek n-length string build karne mein O(n²) time lag sakta hai naive concatenation se. Bade strings build karne ke liye array mein pieces push karo aur end mein ek baar arr.join('') karo — ye O(n) hota hai. Modern engines chhote concatenations ko optimize (rope/cons-string internally) kar dete hain, lekin bade loops mein ye pattern abhi bhi matter karta hai.

Surrogate pairs — Unicode ka andhera pehlu

UTF-16 encoding mein 16 bits (ek code unit) sirf U+0000 se U+FFFF tak ke characters cover karte hain — ye "Basic Multilingual Plane" (BMP) kehlata hai, jisme most common characters aa jaate hain (Latin, Devanagari, Cyrillic, etc). Lekin emojis, kuch rare CJK characters, aur mathematical symbols jaise 𝒳 is range se bahar hain — unhe represent karne ke liye do 16-bit code units ka pair use hota hai, jise "surrogate pair" kehte hain.

Surrogate pair — length aur indexing break ho jaate hain
let emoji = "𝒳"; // ye ek hi VISUAL character hai — script capital X (U+1D4B3), BMP se bahar

console.log(emoji.length); // 2 — ek character, lekin DO code units (surrogate pair: high + low surrogate)

console.log(emoji[0]); // half-broken character dikhega — index[0] pura character nahi deta, sirf pehla code unit

// Sahi tareeka: codePointAt() jo pura Unicode code point return karta hai, code unit nahi
console.log(emoji.codePointAt(0)); // 120499 — full code point number, surrogate pair ko combine karke

// for...of loop surrogate pairs ko SAHI se iterate karta hai, index access nahi karta
for (let char of emoji) { // for...of Unicode-aware hai — surrogate pair ko ek hi "character" treat karta hai
  console.log(char); // "𝒳" — pura correct character milega, ek hi baar loop chalega
}
⚠️ Real bug: string truncation surrogate pair beech mein tod sakta hai

Agar tum str.slice(0, 10) jaisa naive truncation karte ho (jaise bio/tweet character-limit enforce karne ke liye) aur cut point exactly ek surrogate pair ke beech mein gira, to ek "broken" character bach jaata hai — jo UI mein ek garbled box/question-mark dikhega. Emoji-heavy user-generated content handle karte waqt hamesha Array.from(str) ya [...str] use karo (ye dono Unicode-aware split karte hain) truncation se pehle.

Common string methods aur comparison rules

Searching, extracting, comparing
let str = "Widget with id";

console.log(str.indexOf("id"));     // 1 — "id" "Widget" ke andar "id" pe pehla match, position 1 se shuru
console.log(str.includes("id"));     // true — sirf boolean, koi position nahi deta
console.log(str.startsWith("Wid"));  // true — beginning check
console.log(str.endsWith("id"));    // true — ending check

console.log(str.slice(0, 6));    // "Widget" — start se end tak (end EXCLUDED), NEGATIVE index bhi allowed
console.log(str.slice(-2));      // "id" — negative index = end se count, last 2 characters
console.log(str.substring(0, 6)); // "Widget" — slice jaisa, lekin negative index ko 0 treat karta hai, args swap ho sakte

// Template literals — backtick strings, expression embed + multiline dono
let name = "Sharad";
let greet = `Hello, ${name}!
Multiline bina \n ke.`; // ${...} ke andar koi bhi JS expression evaluate hoke string mein interpolate hota hai

// Comparison — UTF-16 code unit ke hisaab se lexicographic, case-sensitive
console.log("a" > "Z"); // true — lowercase letters ka code point uppercase se BADA hota hai ("a"=97, "Z"=90)
console.log("Österreich".localeCompare("Zurich")); // language-aware comparison, "correct" alphabetical order deta hai

Key Takeaways

  • Primitives pe method call karne se ek temporary wrapper object banta hai, method run hota hai, object turant discard ho jaata hai — primitive khud lightweight rehta hai.
  • new Number()/new String() se banaye gaye actual objects use mat karo — typeof "object" ban jaata hai aur wo hamesha truthy hote hain (chahe value 0/"" ho).
  • Numbers 64-bit IEEE-754 float mein store hote hain — safe integer limit 2^53 - 1 hai, isse aage BigInt use karo.
  • 0.1 + 0.2 !== 0.3 kyunki decimal fractions binary mein exactly represent nahi hote — money/currency ke liye integer (paise/cents) math use karo.
  • Strings immutable hain — koi character direct edit nahi ho sakta, hamesha naya string banta hai. Bade loop mein concatenation ki jagah array + join use karo.
  • String internally UTF-16 hai — .length code units count karta hai, characters nahi. BMP se bahar ke characters (emoji, rare symbols) surrogate pairs (2 code units) lete hain, jisse naive indexing/truncation break ho sakta hai.
  • Number.isNaN/Number.isFinite global versions se better hain kyunki wo implicit type coercion nahi karte.

🎯 Interview Questions

  • "abc".toUpperCase() kaam kaise karta hai jab string ek primitive hai, object nahi?
    Hint: temporary wrapper object banta hai method call ke time, method run hota hai, wrapper turant discard ho jaata hai — original primitive unaffected rehta hai.
  • new Number(0) aur Number(0) mein kya farak hai?
    Hint: new ke saath actual object banta hai (typeof "object", hamesha truthy); bina new ke sirf type conversion hoti hai, result primitive number hota hai.
  • 0.1 + 0.2 === 0.3 false kyun hai? Ye JS-specific bug hai kya?
    Hint: IEEE-754 binary floating point limitation hai, JS-specific nahi — decimal fractions binary mein exactly represent nahi hote, rounding error accumulate hota hai.
  • Number.MAX_SAFE_INTEGER kya hai aur isse aage kya problem aati hai?
    Hint: 2^53 - 1, jo 52-bit mantissa se derive hota hai; isse aage consecutive integers same binary pattern share kar sakte hain (precision loss) — BigInt use karo.
  • Strings JavaScript mein immutable kyun hain, aur str[0] = "x" kyun fail hota hai silently?
    Hint: string primitive internally modify nahi ho sakta; assignment temporary wrapper pe hota hai jo discard ho jaata hai — naya string banakar reassign karna padta hai.
  • String.length aur actual "characters" count mein kab farak aata hai?
    Hint: length UTF-16 code units count karta hai; BMP se bahar ke characters (emoji) surrogate pairs (2 code units, 1 character) lete hain — length aur visible character count mismatch ho jaata hai.
  • isNaN("abc") aur Number.isNaN("abc") ka result different kyun hai?
    Hint: global isNaN pehle argument ko Number() se coerce karta hai (NaN ban jaata hai, so true); Number.isNaN koi coercion nahi karta, strict type+value check karta hai (string kabhi NaN nahi hoti, so false).
  • Emoji-heavy user text ko truncate karte waqt str.slice(0, n) use karna risky kyun hai?
    Hint: cut point exactly surrogate pair ke beech gir sakta hai, jisse ek broken/garbled character bach jaata hai — Array.from(str) ya [...str] se Unicode-aware split karke truncate karna chahiye.
