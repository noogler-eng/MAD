RegExp II — Quantifiers/Groups

Chapter 32 mein humne regex ke atoms — character classes, anchors, escaping — cover kiye. Ab hum un atoms ko repeat karna (quantifiers), group karna (capturing/ non-capturing groups), unhe naam dena (named groups), pattern ke andar hi ek matched cheez ko dobara reference karna (backreferences), aur multiple options mein se ek choose karna (alternation) seekhenge. Ye sab combine karke real-world regex — email, dates, HTML tags, repeated words detect karna — likh paoge. Sabse important root concept jo yahan hai: greedy matching + backtracking — regex engine internally kaam kaise karta hai, wo samjhe bina tum apne hi patterns ke unexpected behavior se confuse hote rahoge.

Quantifiers — kitni baar repeat karna hai

Quantifier ek atom (character, group, character class) ke baad laga ke batata hai ki wo atom kितni baar repeat ho sakta hai. Base syntax {n,m} hai — baaki sab (+ * ?) uske shorthand hain.

Quantifier syntax — full table
// {n} — bilkul n baar. Exact count.
/\d{5}/.test("12345");          // true — exactly 5 digits chahiye, na kam na zyada (well, substring match to hoga)

// {n,m} — n se m baar (inclusive range)
/\d{3,5}/.exec("1234567");   // match "12345" — 5 digits le lega kyunki greedy hai (aage discuss karenge)

// {n,} — n ya usse zyada (upper bound koi nahi)
/\d{3,}/.test("12");          // false — sirf 2 digits hain, minimum 3 chahiye the

// + — {1,} ka shorthand — "one or more"
/\d+/.exec("abc123xyz");       // match "123" — kam se kam 1 digit zaroori hai

// * — {0,} ka shorthand — "zero or more" (poori tarah absent bhi ho sakta hai)
/\d0*/.exec("5000 rupees"); // match "5000" — ek digit phir jitne bhi zeros (0 bhi ho sakte the)

// ? — {0,1} ka shorthand — "zero or one", matlab optional
/colou?r/.test("color");    // true — "u" optional hai, US spelling match ho gayi
/colou?r/.test("colour");   // true — UK spelling bhi match, kyunki "u" 0 ya 1 baar dono chalta hai

Real-world pattern examples — quantifiers combine hoke practical regex banate hain:

Real patterns using quantifiers
// Decimal number: ek ya zyada digits, phir literal dot, phir ek ya zyada digits
const decimalRe = /\d+\.\d+/;       // \. escaped hai kyunki plain "." koi bhi character match karta
decimalRe.test("3.14");                // true

// HTML opening tag: "<", ek lowercase letter, phir letters/digits jitne bhi, phir ">"
const tagRe = /<[a-z][a-z0-9]*>/;   // [a-z0-9]* zero-or-more hai kyunki "
" jaisa single-letter tag bhi valid hai
tagRe.test("<h1>");                // true

// Hex color code: "#" phir exactly 6 hex digits
const hexColorRe = /#[a-f0-9]{6}/i;  // {6} exact count — kam ya zyada digits allow nahi
hexColorRe.test("#FF5733");            // true — "i" flag se uppercase F-A bhi match ho gaya

Greedy matching — root-level algorithm + backtracking walkthrough

Ye is chapter ka sabse important root-level concept hai. Default mein har quantifier greedy hota hai — matlab regex engine pehle zyada se zyada characters consume karne ki koshish karta hai, aur sirf tab kam karta hai jab match fail ho raha ho. Isko "greedy + backtrack" algorithm kehte hain, aur ye internally exactly aise kaam karta hai:

  1. Engine string ke position 0 (ya jahan se match start hoti hai) pe pattern try karta hai.
  2. Quantifier wale atom (jaise .+) ke liye, engine string ke bilkul end tak jitna consume kar sakta hai kar leta hai — bina ye check kiye ki baaki pattern match hoga ya nahi.
  3. Ab engine pattern mein aage badhta hai — agle atom ko match karne ki koshish karta hai us position se jahan greedy consumption ruki.
  4. Agar agla atom match nahi hota, engine backtrack karta hai — greedy quantifier ne jo last character consume kiya tha use "return" kar deta hai (ek character chhod deta hai), aur phir se agla atom try karta hai.
  5. Ye step 4 repeat hota hai — one character at a time backtrack — jab tak ya to match mil jaaye, ya quantifier ka minimum count (jaise + ke liye 1) bhi violate ho jaaye, jisse poora match fail ho jaata hai us starting position se.
Backtracking — step-by-step walkthrough
const str = 'a "witch" and her "broom" is one'; // do quoted phrases hain isme
const re = /".+"/;                          // greedy: ek quote se shuru, .+ kuch bhi, phir ek quote

// STEP 1: engine pehla `"` position 2 pe dhoondta hai — literal match, aage badho
// STEP 2: `.+` ab GREEDY hai — bilkul END of string tak sab kuch consume kar leta hai
//         (kyunki "." newline ke alawa kuch bhi match karta hai, aur "+" as much as possible)
//         is point pe .+ ne "witch" and her "broom" is one  -- (poora baaki string) le liya
// STEP 3: ab pattern mein agla atom hai closing `"` — engine end-of-string pe check karta hai
//         wahan `"` nahi hai (string "one" pe end hoti hai) → FAIL, backtrack shuru
// STEP 4: engine .+ se EK character wapas deta hai (last char 'e' chhod deta hai), phir check
//         karta hai kya ab us naye position pe `"` hai — nahi, "n" hai → FAIL, aur backtrack
// STEP 5: ye har position pe repeat hota hai, right-to-left, jab tak ek `"` naa mil jaaye
//         → jo pehla `"` milta hai (right se scan karte hue) wo "broom" ke BAAD wala hai
//         kyunki backtracking RIGHTMOST se hoti hai, LEFTMOST se nahi!

str.match(re)[0]; // '"witch" and her "broom"' — DONO quotes ke beech ka sab kuch, ek match ke roop mein!
// Yehi surprising result hai jo greedy quantifier deta hai — humne socha tha sirf "witch" milega
⚠️ Greedy-by-default = classic "regex for HTML tags" gotcha

Ye exactly wahi reason hai jiske wajah se /<.+>/ se HTML tags parse karna disaster hai. String <h1>title</h1> pe ye pattern poora <h1>title</h1> match kar lega — ek single tag nahi, balki opening se leke closing tag tak ka sab kuch — kyunki .+ greedy hai aur last > tak backtrack karega. Fix: ya to [^>]+ use karo (explicitly > ko exclude karke — best practice), ya lazy quantifier .+? use karo (neeche discuss). Production rule of thumb: HTML/XML ko regex se parse mat karo, ek proper parser (DOMParser, cheerio) use karo — regex sirf simple, well-defined string patterns ke liye hai.

Lazy quantifiers — +? *? ?? — minimum match, first success pe ruk jao

Kisi bhi greedy quantifier ke baad ek extra ? laga do (+?, *?, ??, {n,m}?) to wo lazy ban jaata hai. Lazy mode mein algorithm reverse hota hai: engine minimum characters consume karta hai (jaise +? ke liye sirf 1), phir turant baaki pattern check karta hai. Agar match fail ho, tab hi ek-ek character aage badhta hai (expand karta hai) — first successful match milte hi ruk jaata hai.

Lazy vs greedy — same string, different result
const str = 'a "witch" and her "broom" is one';

// GREEDY — as much as possible, phir backtrack
str.match(/".+"/g);   // [ '"witch" and her "broom"' ] — ek hi bada match

// LAZY — minimum possible, first success pe stop
str.match(/".+?"/g);  // [ '"witch"', '"broom"' ] — do alag matches, jo humein chahiye tha
// "?" ke baad "+" ko lazy bana diya: `.` sirf 1 character leke turant closing " check karta hai
⚠️ Lazy hamesha "sahi" solution nahi hai

Lazy quantifiers step-by-step incrementally match karte hain (1 char try, fail, 2 chars try, fail, ...) — bade strings pe ye greedy se zyada backtracking steps le sakta hai agar delimiter door hai. Zyadatar production code mein [^"]+ (character class jo explicitly quote ko exclude karta hai) .+? se better hai — kyunki [^"]+ ko backtrack karne ki zaroorat hi nahi padti, wo directly quote tak match karta hai, ek hi pass mein. Lazy quantifier tab use karo jab exclusion character class likhna impractical ho (jaise multiple stop-characters).

Capturing groups — (...) aur match()/exec()/matchAll()

Parentheses (...) do kaam karte hain: (1) quantifier ko poore group pe apply karne dete hain (jaise (go)+ — "go" repeat), aur (2) us matched substring ko capture kar lete hain — result array mein separate item ban jaata hai. Groups left-se-right, opening bracket ke order mein numbered hote hain, index 1 se (index 0 hamesha full match hota hai).

Capturing groups — numbering aur access
const str = "<h1>";
const re = /<(.+?)>/;    // group 1 = tag name, lazy .+? kyunki greedy poori string tak jaata

const result = str.match(re);
result[0];  // "
" — index 0 hamesha FULL match hota hai, group na ho tab bhi
result[1];  // "h1"   — pehle (aur yahan sirf ek) capturing group ka content

// NESTED groups — numbering opening "(" ke sequence se hoti hai, left-to-right
const nestedRe = /<(([a-z]+)\s*([^>]*))>/;
// group 1 = poora "tagname attrs", group 2 = sirf tagname, group 3 = sirf attrs
"<a href=x>".match(nestedRe);
// [0]="" [1]="a href=x" [2]="a" [3]="href=x"

// exec() — ek baar mein ek match deta hai, lastIndex track karta hai "g" flag ke saath
const gre = /\d+/g;
let m;
while ((m = gre.exec("a1 b22 c333")) !== null) {
  console.log(m[0], m.index); // har call pe agla match — "1" 1, "22" 4, "333" 8
}

// matchAll() — modern iterator-based tareeka, groups bhi preserve karta hai (match() with "g" nahi karta)
const matches = [..."a1 b22".matchAll(/([a-z])(\d+)/g)]; // spread iterator array mein
matches[0][1]; // "a" — group 1, first match ka
matches[1].index; // 3   — matchAll ka har result .index aur .input bhi deta hai
🧠 Senior Dev Note: match() with "g" flag groups DROP kar deta hai

Ye ek bahut common bug source hai. str.match(/pattern/g) — agar g flag hai — sirf full match strings ka array deta hai, koi groups nahi. Agar tumhe groups aur multiple matches dono chahiye, use matchAll() (ES2020+) ya phir exec() ko manually loop mein call karo (jaisa upar dikhaya). Interview mein ye bahut common trick question hai: "match() with g flag groups kyun nahi deta?" — answer: design decision hai, kyunki with g flag ka use-case typically "sab occurrences dhoondo" hota hai, aur multiple matches ke groups ko ek flat array mein represent karna ambiguous hota — isliye alag API (matchAll) banaya gaya jo iterator of full-result-objects deta hai.

Named groups — (?<name>...)

Numbered groups (result[1], result[2]...) readability kill karte hain jab pattern complex ho jaaye — kaunsa number kis cheez ka hai, yaad rakhna mushkil hota hai. Named groups (?<name>...) syntax se semantic naam dete hain, aur match result ke .groups object mein accessible hote hain.

Named groups — date parsing
// (?...) — "year" naam ka group, (?...) aur (?...) bhi
const dateRe = /(?<year>[0-9]{4})-(?<month>[0-9]{2})-(?<day>[0-9]{2})/;

const match = "2026-08-13".match(dateRe);
const groups = match.groups;       // .groups — named groups object, agar koi named group nahi to undefined

groups.year;   // "2026" — plain property access, index nahi
groups.month;  // "08"
groups.day;    // "13"

// replace() mein bhi named group use kar sakte ho: $
"2026-08-13".replace(dateRe, '$<day>/$<month>/$<year>'); // "13/08/2026" — DD/MM/YYYY format

Non-capturing groups — (?:...)

Kabhi-kabhi tumhe sirf quantifier ko group pe apply karna hai — us group ka content capture nahi karna. Har capturing group ek chhota internal overhead rakhta hai (engine ko uska start/end position track karna padta hai), aur agar tum use kabhi access nahi karoge to wo result array mein bas noise add karta hai. (?:...) syntax exactly grouping deta hai without capturing.

Non-capturing group — grouping without indexing overhead
// (?:go)+ — "go" ko ek unit ki tarah treat karo aur repeat allow karo, LEKIN capture mat karo
const re = /I love (?:HTML|CSS)/;
"I love HTML".match(re)[0]; // "I love HTML" — full match theek se aata hai
"I love HTML".match(re)[1]; // undefined — koi group 1 hai hi nahi, (?:...) count nahi hota numbering mein

// Compare with a capturing version, jahan array bloat hota hai jab humein use nahi karna:
const reCapturing = /I love (HTML|CSS)/; // yahan group 1 bhi capture hoga, agar zaroorat na ho to waste hai

Backreferences — \N aur \k<name> — pattern ke andar hi "wahi text dobara"

Backreference ek pehle-capture-kiye-gaye group ke content ko pattern ke andar hi dobara reference karta hai — matlab "yahan bilkul wahi text hona chahiye jo group N mein match hua tha", literal regex syntax nahi. Numbered group ke liye \N, named group ke liye \k<name>. (Note: pattern ke andar backslash syntax hai; replace() strings mein dollar syntax — $1, $<name> — hota hai, dono confuse mat karo.)

Backreference — matching quotes + repeated words
// Quoted string jahan opening aur closing quote MATCH karna chahiye (dono ' ya dono ")
const quoteRe = /(['"])(.*?)\1/g;
// group 1 = jo bhi quote char pehle mila (' ya "), \1 = wahi character dobara chahiye closing pe

`He said: "She's the one!".`.match(quoteRe);
// ['"She's the one!"'] — poori double-quoted phrase, apostrophe (') ke beech mein hone ke bawajood
// bina backreference ke, engine galti se pehla ' ko hi closing quote maan leta aur galat jagah rukta

// Named version — same logic, zyada readable jab multiple backreferences ho
const namedQuoteRe = /(?<quote>['"])(.*?)\k<quote>/g;

// Classic use-case: repeated consecutive word detect karna (typo jaise "the the")
const repeatedWordRe = /\b(\w+)\s+\1\b/i;
// \b word boundary, (\w+) ek word capture karo, \s+ whitespace, \1 SAME word dobara, \b boundary
repeatedWordRe.test("this is the the bug"); // true — "the the" caught
⚠️ Non-capturing group ko backreference nahi kar sakte

(?:...) group content capture hi nahi karta, isliye \1 ya \k<name> se use reference karne ka koi tareeka nahi hai — logically bhi makes sense, kyunki backreference ko "kya match hua tha" yaad rakhna padta hai, aur non-capturing group ye information store hi nahi karta. Agar tumhe kisi group ko backreference karna hai, wo zaroor capturing (numbered ya named) hona chahiye.

Alternation — | — "OR", lekin LOWEST precedence

| pattern ke multiple alternatives try karta hai, left-to-right, jo pehla match kare wahi use hota hai. Character class [ae] se fundamentally different hai — character class sirf ek single character ke options deta hai, jabki alternation poori sub-expressions ke options deta hai.

Alternation basics — character class vs alternation
// Character class — sirf EK character ke options
/gr[ae]y/.test("gray");  // true — "a" ya "e" us ek slot mein

// Alternation — poore SUB-PATTERNS ke options
/gra|ey/.test("grey");  // true — lekin "gra" YA "ey" ki poori string match ho rahi, gray/grey wala use-case nahi hai

// Multi-language OR
const langRe = /html|php|css|java(script)?/gi; // case-insensitive, global — "(script)?" optional suffix
"I know HTML and JavaScript".match(langRe); // ["HTML", "Java" ... wait: "javascript" matches "java"+optional "script"]
⚠️ Precedence gotcha: | sabse LOW precedence hai poore pattern mein

Ye alternation ka sabse bada gotcha hai. | ka scope poora pattern hai (jab tak group na ho) — sirf immediate neighbours nahi. Matlab /I love HTML|CSS/ ka matlab "I love HTML" YA "CSS" hai, na ki "I love HTML" ya "I love CSS". Fix explicit grouping se: /I love (?:HTML|CSS)/.

Precedence gotcha — real bug in a time regex
// Buggy: time format HH:MM match karna chahte hain, 00-23 ghante, 00-59 minute
const buggyRe = /[01]\d|2[0-3]:[0-5]\d/;
// | ka scope POORA pattern hai: ([01]\d) YA (2[0-3]:[0-5]\d)
// matlab "00-19 ghanta, minute ke bina bhi match" YA "20-23 ghanta with minute" — asymmetric bug!
buggyRe.test("14");   // true — bina minute ke bhi match ho gaya, jo humara intent nahi tha!

// Fixed: group laga ke sirf hour-alternatives ko isolate karo, minute part common rakho
const fixedRe = /([01]\d|2[0-3]):[0-5]\d/;
// ab | sirf group ke ANDAR scoped hai: (hour-option-1 YA hour-option-2), phir hamesha :MM
fixedRe.test("14");   // false — correctly fail, minute part missing hai
fixedRe.test("14:30"); // true

Doosra common pitfall — alternative ordering. Alternation left-to-right try karta hai aur pehla match milte hi ruk jaata hai, poora string scan karke "best" match nahi dhoondta. Agar chhota alternative pehle likha aur wo ek prefix hai bade wale ka, to bada alternative kabhi try hi nahi hoga.

Ordering matters — shorter-first prefix bug
// BUGGY order: "Java" pehle hai, jo "JavaScript" ka bhi prefix hai
const buggyOrder = /Java|JavaScript|C|C\+\+|PHP/;
"JavaScript".match(buggyOrder)[0]; // "Java" — "Java" alternative pehle match kar gaya, "Script" kabhi try hi nahi hua

// FIX 1: longer alternative ko pehle rakho
const fixedOrder = /JavaScript|Java|C\+\+|C|PHP/;

// FIX 2: optional suffix se merge kar do — root cause hi khatam ho jaata hai
const mergedRe = /Java(Script)?|C(\+\+)?|PHP/; // "(Script)?" optional group — greedy hai to "Script" mile to le lega
🧠 Senior Dev Note: greedy + backtracking hi catastrophic backtracking ki root cause hai

Jo backtracking algorithm humne upar step-by-step dekha, wahi mechanism — agar tum nested quantifiers ambiguously likh do, jaise (a+)+b — exponential ho sakta hai. Har outer + repetition ke andar inner a+ ke multiple tareeke hote hain string ko split karne ke, aur jab final b match nahi hota, engine har combination try karta hai — jo string length ke saath exponentially grow karta hai (ReDoS — Regular Expression Denial of Service). Ye chapter 34 mein detail mein cover hoga, lekin root cause samajhna zaroori hai abhi: greedy quantifier ke andar doosra greedy quantifier nested ho jab dono overlapping character sets match kar sakte hain, tab backtracking combinatorially explode hoti hai. Production regex likhte waqt — especially user-input validate karne wale — hamesha socho: "agar ye match fail ho, to kitni backtrack paths possible hain?"

Key Takeaways

  • Quantifiers: {n,m} base syntax hai; + = {1,}, * = {0,}, ? = {0,1}.
  • Greedy (default) = zyada se zyada consume karo, phir backtrack ek-ek character right-se-left jab tak baaki pattern match na ho jaaye.
  • Lazy (+?, *?, ??) = minimum consume karo, first successful match pe ruk jao — but bade strings pe zyada steps le sakta hai; [^x]+ character-exclusion aksar better alternative hai.
  • Capturing groups (...) numbered hote hain opening-paren order mein; match() with g flag groups DROP kar deta hai — matchAll() ya exec() loop use karo groups ke liye.
  • Named groups (?<name>...) readability ke liye — match.groups.name se access, $<name> replace() mein.
  • Non-capturing groups (?:...) grouping deta hai bina numbering/capture overhead ke.
  • Backreferences \N / \k<name> pattern ke andar "wahi text dobara" match karte hain — sirf capturing groups ko reference kar sakte ho, non-capturing ko nahi.
  • Alternation | ka precedence pattern mein sabse LOW hai — poore pattern ko span karta hai jab tak explicit group na ho; longer/specific alternatives pehle likho.
  • Greedy + nested quantifiers ambiguous overlapping patterns mein exponential backtracking (ReDoS) create kar sakte hain — root cause hai jo chapter 34 mein detail mein aayegi.

🎯 Interview Questions

  • Greedy quantifier internally kaise kaam karta hai — algorithm explain karo.
    Hint: maximum consume karo pehle, phir agar aage ka pattern fail ho to ek-ek character right-se-left backtrack karo jab tak match mil jaaye ya minimum count violate ho jaaye.
  • /<.+>/ HTML tags parse karne ke liye kyun risky hai?
    Hint: greedy .+ multiple tags ke beech ka sab kuch bhi consume kar lega (last > tak), ek single tag ki jagah — fix hai [^>]+ ya proper HTML parser.
  • match() with g flag groups kyun return nahi karta, aur uska alternative kya hai?
    Hint: g flag "sab occurrences" ka use-case hai jahan multiple groups ko flat array mein represent karna ambiguous hota — matchAll() use karo jo iterator of full result objects deta hai.
  • Non-capturing group (?:...) ka use-case kya hai, aur usse backreference kyun nahi kar sakte?
    Hint: quantifier scope ke liye grouping chahiye but capture nahi karna — indexing overhead avoid hota hai; backreference ko matched content yaad rakhna padta hai jo non-capturing group store hi nahi karta.
  • Alternation | ka precedence pattern mein kya hai — real example do jahan ye bug create kar sakta hai.
    Hint: lowest precedence, poore pattern ko span karta hai; [01]\d|2[0-3]:[0-5]\d minute ko sirf second alternative se attach karta hai — fix grouping ([01]\d|2[0-3]):[0-5]\d.
  • Backreference \1 se repeated word (jaise "the the") kaise detect karoge?
    Hint: /\b(\w+)\s+\1\b/i — group capture karo word, phir \1 se same word ki repetition check karo.
  • Nested quantifiers jaise (a+)+b se ReDoS kaise hoti hai?
    Hint: overlapping character sets wale nested greedy quantifiers exponential number of backtracking paths generate karte hain jab final match fail hota hai — string length ke saath exponentially grow karta hai.
