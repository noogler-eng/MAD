Proxy & Reflect — object operations ko intercept karna

Proxy ek object ke around ek "wrapper" banata hai jo us object pe hone wale fundamental operations — get, set, has, deleteProperty, function call, aur bahut saare aur — ko intercept kar sakta hai. Root mechanism: JS engine ke andar har object operation (property read, write, delete, etc.) internal spec-level "trap" methods ko invoke karta hai. Proxy in traps ko override karne ka public API deta hai.

Basic Proxy — get/set traps
const target = { name: "Sharad" }; // original object jise wrap karna hai

const handler = { // handler object — isme traps define hote hain
  get(obj, prop) { // get trap — property READ hone par fire hota hai
    console.log(`Reading prop: ${prop}`); // side-effect: har read ko log karo
    return prop in obj ? obj[prop] : 37; // agar prop exist nahi karta to default 37 return karo
  },
  set(obj, prop, value) { // set trap — property WRITE hone par fire hota hai
    if (typeof value !== "string") { // validation: sirf strings allowed
      throw new TypeError("name must be a string"); // invalid type pe error throw karo
    }
    obj[prop] = value; // actual write target object pe karo
    return true; // true return karna MANDATORY hai — false = silent/strict-mode error
  }
};

const p = new Proxy(target, handler); // proxy banao — target aur handler dono chahiye

console.log(p.name);    // "Reading prop: name" log hoga, phir "Sharad" print hoga
console.log(p.age);     // prop "age" exist nahi karta target mein, so 37 (default) milega
p.name = 123;      // TypeError throw hoga — set trap ne number reject kar diya

Sabse common traps: get (read), set (write), has (in operator ke liye), deleteProperty (delete keyword ke liye), ownKeys (Object.keys/for...in), aur apply/construct (function call / new).

Real example: validation proxy for a "positive numbers only" array
function createValidatedArray() { // factory function jo ek validated proxy array return karega
  return new Proxy([], { // underlying target ek empty array hai
    set(arr, prop, value) { // set trap — push/index-assign dono isse guzarte hain
      if (prop !== "length" && isNaN(prop) === false) { // prop numeric index hai (array element hai), "length" nahi
        if (typeof value !== "number" || value <= 0) { // non-number ya <=0 reject karo
          throw new RangeError("Only positive numbers allowed"); // clear error message
        }
      }
      arr[prop] = value; // valid hai to actual array pe set karo (length auto-update hoga)
      return true; // success signal
    }
  });
}

const nums = createValidatedArray(); // naya validated array banao
nums.push(5);          // push internally arr[0]=5 karta hai — set trap fire hoga, pass hoga
nums.push(-1);         // RangeError throw hoga — negative number reject

Reflect Proxy ka companion object hai — ye same operations (get, set, has, deleteProperty, etc.) ko function calls ke roop mein perform karta hai, jo default/original behavior deliver karte hain. Root reason ye exist karta hai: jab tum ek trap ke andar "original behavior fallback" karna chahte ho, obj[prop] likhna edge cases mein buggy ho sakta hai (jaise inherited getters ka this galat bind hona), jabki Reflect.get(obj, prop, receiver) spec-correct semantics guarantee karta hai.

Reflect ke saath correct forwarding
const user = { _name: "Sharad", get name() { return this._name; } }; // getter jo "this" use karta hai

const proxy = new Proxy(user, {
  get(target, prop, receiver) { // receiver = proxy khud (ya jisne property access kiya)
    return Reflect.get(target, prop, receiver); // receiver pass karna zaroori — getter ka "this" proxy bane, target nahi
  }
});

console.log(proxy.name); // "Sharad" — agar target[prop] likhte to bhi kaam karta, lekin
                       // inheritance/getter chains mein Reflect zyada robust hai
🧠 Senior Dev Note: invariants aur limited engine optimization

Proxy powerful hai lekin free nahi — har intercepted operation ek extra function call layer se guzarta hai, jo V8 jaise engines ke inline-caching/hidden-class optimizations ko bypass kar deta hai. Hot paths (tight loops, high-frequency property access) mein Proxy avoid karo. Bhi Proxy "invariants" enforce karta hai — jaise agar target ki koi property configurable: false hai, to get trap usse different value return nahi kar sakta (engine TypeError throwega) — ye traps ko silently object ke real semantics todne se rokta hai. Production mein Proxy ka real use: Vue 3 ki reactivity system, ORM-style validation layers, aur API mocking/logging wrappers.

eval() aur uska danger

eval(code) ek string ko JS code ki tarah run karta hai, current scope mein. Modern JS mein ye almost hamesha avoid kiya jaata hai — do root reasons hain: security aur performance.

eval basic behavior
let code = 'console.log("hello from eval")'; // code ek plain string hai
eval(code); // string ko parse+execute karta hai, "hello from eval" print hoga

let a = 1; // outer scope variable
function f() {
  let a = 2; // local scope variable — same naam se
  eval('console.log(a)'); // direct eval — current LOCAL scope access karta hai, so 2 print hoga
}
f(); // call karo — output: 2
⚠️ eval() security aur performance dono ke liye danger hai

Security: agar eval ke andar ka string kisi user input se (even indirectly) aata hai, to attacker arbitrary code inject karke run karwa sakta hai — classic code-injection vulnerability, XSS ka ek variant. Scope pollution: "direct eval" (jab call literally eval(...) dikhta hai, kisi variable mein assign kiye bina) current scope ke variables ko read/modify kar sakta hai, jo minifiers aur bundlers ko confuse karta hai — wo safely variable names rename nahi kar paate kyunki unhe pata nahi eval ke andar kya reference ho raha hai. Performance: JS engines (V8, etc.) code ko ahead-of-time analyze karke JIT-optimize karte hain — lekin eval() ke andar ka code runtime pe generate hota hai, engine use pre-optimize nahi kar sakta, aur jis function mein eval hai use bhi de-optimize kar deta hai kyunki uska scope ab "unpredictable" ho gaya. Modern alternatives: JSON.parse (data ke liye), dynamic import() (code ke liye), new Function(...) (agar sandboxed execution chahiye — ye global scope mein hi run hota hai, local scope pollute nahi karta).

Currying & Partial Application

Currying ek transformation hai jisse f(a, b, c) jaisa multi-argument function f(a)(b)(c) ban jaata hai — matlab ek function jo arguments ek-ek karke leta hai, aur har call pe ek naya function return karta hai jab tak saare arguments collect na ho jaayein.

Manual curry() implementation
function curry(fn) { // curry ek higher-order function hai — fn leke curried version return karta hai
  return function curried(...args) { // curried — rest params se jitne bhi args diye gaye collect karo
    if (args.length >= fn.length) { // fn.length = original function ke declared params ki count
      return fn.apply(this, args); // enough args mil gaye — original fn ko call karo aur result return karo
    } else {
      return function(...args2) { // kam args diye — ek naya function return karo jo baaki args lega
        return curried.apply(this, args.concat(args2)); // old args + new args merge karke curried ko recursively call karo
      };
    }
  };
}

function sum(a, b, c) { // original 3-argument function
  return a + b + c; // teeno add karo
}

let curriedSum = curry(sum); // curried version banao

console.log(curriedSum(1, 2, 3)); // 6 — ek hi call mein saare args, seedha fn.apply chala
console.log(curriedSum(1)(2, 3)); // 6 — pehle 1 args=[1], phir 2,3 merge hoke [1,2,3] complete
console.log(curriedSum(1)(2)(3)); // 6 — teen alag calls, har baar ek naya wrapper function

Practical use case: partial application — ek generic function se specific, reusable variants banana. Jaise const double = curriedMultiply(2) — double ab ek one-argument function hai jo hamesha 2 se multiply karta hai. React/Redux mein mapStateToProps(state)(dispatch) jaisa pattern, ya logging utilities (log(level)(module)(message)) is idiom ka common real-world use hain.

Reference Type — "this" kaise chupke se lose ho jaata hai

Ye ek subtle spec-internal mechanism hai jo bahut senior devs ko bhi confuse karta hai. Jab tum obj.method() likhte ho, JS engine internally ek special intermediate value banata hai jise spec "Reference Type" kehta hai — ye sirf value nahi, balki (base, propertyName, strict) ka ek triplet hota hai. Jab is reference pe () call hota hai, engine base (yaani obj) ko this ke roop mein use karta hai.

Reference Type lose hone ka classic case
let user = {
  name: "Sharad", // property
  hi() { console.log(this.name); } // method jo "this.name" use karta hai
};

user.hi(); // "Sharad" — obj.method() syntax: Reference Type (user, "hi") ban ke this=user bind hua

let hi = user.hi; // property ko variable mein assign — sirf FUNCTION VALUE copy hoti hai, Reference Type nahi
hi(); // TypeError (strict mode) ya "undefined" — this ab user nahi, kyunki "base" info kho gayi

let { hi: hi2 } = user; // destructuring bhi wahi karta hai — sirf value nikalti hai, reference nahi
hi2(); // same problem — this.name fail hoga, kyunki "this" ab undefined/global hai

Root cause explanation: obj.method() ka syntax do steps ka combined operation nahi hai (property-get + call) jaise dikhta hai — property access khud ek Reference (with base = obj) return karta hai, aur () call directly usi Reference pe hota hai, jisse engine ko pata chalta hai this kya bind karna hai. Lekin jaise hi tum us function value ko kisi bhi variable mein assign karte ho (chahe simple assignment ho ya destructuring), sirf function value copy hoti hai — Reference Type ka base discard ho jaata hai. Isliye assign/destructure karne ke baad call karne pe this lost ho jaata hai.

⚠️ Fix: bind() ya arrow function wrapper

const hi = user.hi.bind(user) — explicit binding karo taaki this hamesha user rahe, chahe function kahin bhi call ho. Ya class methods ko class fields (arrow function) ke roop mein define karo: hi = () => console.log(this.name) — arrow functions apna khud ka this nahi rakhte, wo lexical scope se le lete hain (class constructor time ka this), so destructure/pass-as-callback karne pe bhi safe rehta hai. Yehi reason hai ki React class components mein event handlers aksar arrow-function class fields ke roop mein likhe jaate the — onClick={this.handleClick} pass karne pe method ka reference nikal jaata tha, so plain method hota to this undefined ho jaata.

BigInt — arbitrary-precision integers

Regular JS numbers IEEE-754 double-precision float hain — safely sirf ±(2^53 - 1) (Number.MAX_SAFE_INTEGER) tak ke integers represent kar sakte hain. Isse aage precision loss hone lagta hai. BigInt ek separate primitive type hai jo arbitrarily large integers ko exactly represent kar sakta hai.

BigInt basics
const big = 1234567890123456789012345678901234567890n; // trailing "n" suffix = BigInt literal
console.log(typeof big); // "bigint" — number se alag type

const alsoBig = BigInt(123); // BigInt() function se bhi bana sakte ho, regular number se convert

console.log(big + 10n); // arithmetic works — dono operands BigInt hone chahiye

try {
  console.log(big + 10); // TypeError — BigInt aur regular Number ko mix nahi kar sakte
} catch (e) {
  console.log(e.message); // "Cannot mix BigInt and other types" jaisa message
}

console.log(big > 100); // true — comparison operators exception hain, ye mixing allow karte hain

Root reason mixing disallowed hai: BigInt exact integer arithmetic ke liye hai, aur Number floating-point approximation ke liye — inhe silently mix karne se precision-loss bugs chhup jaate, jo BigInt ke poore purpose (exactness) ko hi defeat kar deta. Isliye spec explicitly deliberate conversion maangta hai (Number(big) ya BigInt(num)). Real use-cases: cryptography, high-precision timestamps (nanoseconds), financial calculations jahan cent-level precision zaroori hai, database IDs jo 64-bit se bade ho sakte hain.

Unicode & String Internals

JS strings internally UTF-16 encoding use karte hain — har character 1 ya 2 "code units" (16-bit each) se represent hota hai. Basic Multilingual Plane (BMP) ke characters (jaise Latin, Devanagari, most common symbols) sirf 1 code unit lete hain. Lekin emoji, kuch rare CJK characters, aur mathematical symbols jaise BMP ke bahar (astral plane) ke characters ko 2 code units — ek "surrogate pair" — chahiye hote hain.

Surrogate pairs ka effect string operations pe
let str = "😂"; // ek emoji — visually ek character dikhta hai

console.log(str.length); // 2 — kyunki internally ye 2 UTF-16 code units (surrogate pair) hai

for (let ch of str) { // for...of iterable protocol — Unicode-code-point-aware hai, code-unit-aware nahi
  console.log(ch); // pura emoji ek hi baar print hota hai — for...of surrogate pair samajhta hai
}

console.log(str[0]); // GARBAGE — sirf pehla code unit milega, ek broken/lone surrogate
console.log(str.codePointAt(0)); // 128514 — codePointAt() surrogate pair ko decode karke SAHI code point deta hai

Isi wajah se legacy string methods (str[i], .charAt(), .charCodeAt()) astral-plane characters pe "reh jaate" hain, jabki modern Unicode-aware methods (.codePointAt(), String.fromCodePoint(), for...of, spread [...str]) correctly handle karte hain.

Normalization — same visual character, different byte representation
let s1 = "é";        // "é" — ek single precomposed Unicode code point
let s2 = "é";       // "e" + combining accent mark — DO code points, same visual result

console.log(s1 === s2); // false — byte-level representation alag hai, so strict equality fail
console.log(s1.normalize() === s2.normalize()); // true — normalize() dono ko canonical form mein le aata hai

Root cause: Unicode ek hi visual character ko multiple valid representations deta hai (precomposed vs decomposed). User-generated text (forms, search, dedup logic) compare karte waqt hamesha .normalize() se guzaarna chahiye — warna do "same-dikhne-wale" strings silently unequal treat ho jaate hain.

WeakRef & FinalizationRegistry

Normally jab tum kisi object ko reference karte ho (variable, array element, object property mein), wo reference garbage collector ko "strong" signal deta hai: object ko GC karna mana hai jab tak koi reachable reference exist karti hai. WeakRef ek "weak" reference banata hai — object ko alive rakhta hai jab tak koi aur strong reference exist karti hai, lekin khud GC ko object collect karne se rokta nahi.

WeakRef basic usage — caching use case
function getCachedUser(id, cache) { // cache = Map<id, WeakRef>
  const ref = cache.get(id); // cache se WeakRef nikalo (agar exist karta hai)
  if (ref) { // agar cache mein entry mili
    const obj = ref.deref(); // deref() — agar object abhi bhi alive hai to return karega, warna undefined
    if (obj) return obj; // cache HIT — object abhi memory mein hai, seedha return karo
  }
  const freshUser = { id, name: `User ${id}` }; // cache MISS — naya object banao (yahaan DB call hota real app mein)
  cache.set(id, new WeakRef(freshUser)); // weak reference store karo — cache khud object ko alive nahi rakhega
  return freshUser; // fresh object return karo
}

Is pattern ka fayda: agar koi aur part of the app freshUser ko use nahi kar raha (no strong reference bachi), to GC use collect kar sakta hai — cache Map khud memory leak nahi banta, kyunki WeakRef object ko force-alive nahi rakhta. Regular Map ke saath ye cache hamesha memory leak hota, kyunki Map ki key/value dono strong references hoti hain.

FinalizationRegistry — cleanup callback on GC
const registry = new FinalizationRegistry((heldValue) => { // callback jo GC hone par (kabhi na kabhi) fire ho SAKTA hai
  console.log(`Cleaned up: ${heldValue}`); // heldValue = registration ke time diya gaya identifier
});

function register(obj, id) {
  registry.register(obj, id); // obj ko track karo, id ko heldValue ke roop mein store karo
}
⚠️ FinalizationRegistry ka timing non-deterministic hai — critical logic ke liye kabhi use mat karo

Spec explicitly guarantee nahi karta ki finalization callback kab (ya agar bhi) chalega. GC engine ki apni marzi se, kabhi bhi, ya kabhi nahi bhi chal sakta — page unload ho jaaye to bhi callback guarantee nahi. Isse resource cleanup (file handles, network connections, database transactions), UI state updates, ya kisi bhi "must-happen" logic ke liye use mat karo. Sahi use-case sirf optional, best-effort diagnostics hai — jaise memory leak debugging mein "kya ye object actually collect hua ya nahi" track karna. Critical cleanup ke liye hamesha explicit methods use karo (.close(), .dispose(), try/finally) — GC pe kabhi depend mat karo.

🧠 Senior Dev Note: WeakRef bhi rarely-needed hai

MDN aur TC39 spec authors khud warn karte hain: WeakRef aur FinalizationRegistry advanced, niche APIs hain jo mostly library/framework authors ke liye hain (caching layers, DOM-node tracking tools, WASM memory bridges) — application-level code mein inki zaroorat kam hi padti hai. Agar seedha caching chahiye jisme entries "kabhi na kabhi" evict ho jaayein, WeakMap/WeakSet (chapter 8 mein cover kiya) simpler aur zyada predictable choice hote hain jab tak explicit "deref + freshly-check" semantics ki zaroorat na ho. WeakRef reach for tab karo jab tumhe object ko access bhi karna ho (agar abhi alive hai) AND uski lifetime ko control bhi na karna ho.

Key Takeaways

  • Proxy object operations (get/set/has/deleteProperty/etc.) ko intercept karta hai via traps; Reflect unhi operations ka default/spec-correct implementation deta hai — forwarding ke liye saath use karo.
  • eval() security risk (code injection) aur performance risk (JIT de-optimization, scope pollution) dono deta hai — JSON.parse, dynamic import(), ya new Function() se replace karo.
  • Currying multi-arg function ko chained single-arg calls mein todta hai — fn.length aur recursive wrapper se implement hota hai; real use: partial application, reusable specialized functions.
  • Reference Type ek internal spec triplet hai (base, propertyName, strict) jo sirf obj.method() syntax mein exist karta hai — assign ya destructure karte hi base (aur this) kho jaata hai.
  • BigInt arbitrary-precision integers deta hai (123n syntax) — regular Number ke saath directly mix nahi ho sakta, explicit conversion chahiye.
  • JS strings internally UTF-16 hain — astral-plane characters (emoji, etc.) 2 code units (surrogate pair) lete hain, jisse .length aur indexing misleading ho sakte hain; .normalize() visual-duplicate strings ko canonical form mein laata hai.
  • WeakRef object ko GC-eligible rakhte hue bhi access allow karta hai (caching use case); FinalizationRegistry ka timing non-deterministic hai — sirf best-effort diagnostics ke liye, kabhi critical logic ke liye nahi.

🎯 Interview Questions

  • Proxy ke get trap mein Reflect.get use karne ka reason kya hai, seedha target[prop] return karne ke bajaye?
    Hint: getters/inheritance chains mein "receiver" argument pass karna zaroori hai taaki this sahi bind ho — target[prop] ye guarantee nahi deta.
  • eval() JIT optimization ko kaise affect karta hai?
    Hint: engine ahead-of-time code analyze karke optimize karta hai; eval() ka code runtime pe generate hota hai aur scope ko "unpredictable" bana deta hai, jisse containing function bhi de-optimize ho jaati hai.
  • const {method} = obj; method() — this kyun undefined hota hai, jabki obj.method() kaam karta hai?
    Hint: obj.method() syntax ek Reference Type (base+propName) create karta hai jisse this bind hota hai; destructuring sirf function VALUE copy karta hai, base info discard ho jaata hai.
  • BigInt aur Number ko direct arithmetic mein mix karne pe error kyun aata hai, comparison operators mein kyun nahi?
    Hint: arithmetic mein silent precision loss chhup sakta hai (BigInt ka poora purpose defeat), isliye spec explicit conversion maangta hai; comparisons safe hain kyunki wo koi naya numeric value produce nahi karte.
  • Emoji jaise character ka .length 2 kyun aata hai, jabki visually ek character hai?
    Hint: JS strings UTF-16 use karte hain; BMP ke bahar ke characters (astral plane) ko represent karne ke liye 2 code units (surrogate pair) chahiye hote hain, .length code-unit count hai, character count nahi.
  • WeakRef-based cache regular Map-based cache se kaise better hai memory ke liye?
    Hint: Map value ko strong reference se hold karta hai (kabhi collect nahi hota, memory leak), WeakRef object ko GC-eligible rehne deta hai jab tak koi aur strong reference exist na kare.
  • FinalizationRegistry ko production cleanup logic (jaise closing a DB connection) ke liye kyun use nahi karna chahiye?
    Hint: spec callback ki timing ya execution guarantee nahi karta — GC ki marzi se chalta hai, kabhi bhi nahi bhi chal sakta; critical cleanup ke liye explicit dispose/close pattern use karo.
