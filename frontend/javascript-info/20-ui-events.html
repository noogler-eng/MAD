UI Events

Events fundamentals (bubbling, capturing, delegation) part 19 mein cover ho chuke hain — ab hum actual UI event families mein utrenge: mouse, pointer, keyboard, aur scroll. Ye wo events hain jo real interactive UI banane mein use hote hain — drag'n'drop, custom sliders, game controls, infinite scroll. Root-level pe samjhenge ki browser internally in events ko kaise fire karta hai, aur kahan classic gotchas chhupe hain (mouseover bubbling, keypress deprecation, scroll preventDefault fail hona).

Mouse Events — basics

Mouse events ka ek pura family hai — sab alag-alag moment pe fire hote hain. Click ek single event nahi hai — wo teen niche-level events ka composite result hai:

  • mousedown / mouseup — button press/release hone par, kisi bhi button (left/middle/right) ke liye.
  • click — sirf tab fire hota hai jab left button se mousedown+mouseup same element pe complete ho.
  • dblclick — do rapid clicks (aaj-kal rarely used, kyunki UX conventions badal gaye hain).
  • contextmenu — right button press par (browser ka context menu trigger karta hai).
  • mousemove — pointer move hote waqt continuously fire hota hai.

Sequence hamesha ye hoti hai: mousedown → mouseup → click. Agar mousedown aur mouseup alag-alag elements pe hue (user ne button dabaya, drag kiya, kisi aur jagah release kiya), to click bilkul fire hi nahi hoga — ye ek common confusion point hai.

event.button — kaunsa button dabaya gaya
button.addEventListener('mousedown', function(event) {  // mousedown listener — button press ke exact moment pe fire hota hai
  if (event.button === 0) {              // 0 = left/primary button — most common case
    console.log('Left button pressed');  // left-click specific logic yahan
  } else if (event.button === 1) {       // 1 = middle/auxiliary button — scroll-wheel click
    console.log('Middle button pressed'); // e.g. "open link in new tab" gesture ka source
  } else if (event.button === 2) {       // 2 = right/secondary button — normally contextmenu event bhi saath fire hota hai
    console.log('Right button pressed');  // 3 = back (X1), 4 = forward (X2) — extra mouse buttons wale mice ke liye
  }
});

// Modifier keys — kaunsi keyboard key saath dabi thi
button.onclick = function(event) {          // onclick property assignment — sirf ek handler allow karta hai
  if (event.altKey && event.shiftKey) {  // altKey aur shiftKey dono boolean properties — pressed the?
    alert('Hooray!');                          // custom keyboard-shortcut-like click behavior
  }
  // Cross-platform Ctrl/Cmd check ka pattern — Mac pe metaKey (Cmd), Windows/Linux pe ctrlKey
  if (event.metaKey || event.ctrlKey) {       // dono check karna zaroori hai — single platform-check bug hai
    console.log('Cmd/Ctrl + click');          // e.g. multi-select ya "open in new tab" jaisa custom intent
  }
};

Coordinates do flavor mein aate hain, aur inko confuse karna production bugs ka common source hai:

clientX / clientYViewport (visible window)Scroll se change NAHI hota — window ke top-left se fixed distance
pageX / pageYPoora documentScroll ke saath grow hota hai — document ke top-left se absolute distance
⚠️ Galat coordinate use karna = positioning bug

Agar tum position: fixed wale element ko position kar rahe ho (jo viewport-relative hota hai), to clientX/clientY use karo. Agar position: absolute wale element ko document ke andar position kar rahe ho, to pageX/pageY chahiye. In dono ko swap karna scroll hone par element ko galat jagah "jump" karwa deta hai — chapter 18 mein humne document vs viewport coordinates detail mein dekhe the, yahi concept mouse events pe apply hota hai.

mouseover/mouseout vs mouseenter/mouseleave — classic gotcha

Ye do event-pairs superficially same lagte hain (dono "enter/leave" detect karte hain) lekin internally bilkul alag mechanism follow karte hain — aur interview mein ye ek favorite trick question hai.

  • mouseover / mouseout — bubble karte hain, aur har descendant boundary crossing pe fire hote hain.
  • mouseenter / mouseleave — bubble nahi karte, sirf tab fire hote hain jab pointer poore element (uske saare children samet) ke andar/bahar jaata hai — exactly ek baar.

Root cause samjho: jab pointer ek parent se uske child element ke andar move karta hai, browser ye maanta hai ki pointer pehle parent se "out" hua (child boundary cross karte hi) aur phir child mein "over" hua. mouseout event child ke mouseover event ki tarah hi bubble karke parent tak pahunchta hai — matlab agar tumne naively parent pe mouseout listener laga rakha hai, wo child boundary cross karte hi bhi fire ho jaayega, jaise pointer poore parent se bahar chala gaya ho — jabki actually wo sirf ek child ke andar gaya hai.

relatedTarget se real "left the parent" detect karna
parent.onmouseout = function(event) {              // parent pe mouseout — child transitions ke liye bhi fire hoga
  // relatedTarget = jahan pointer JAA raha hai (mouseout ke liye "destination")
  let related = event.relatedTarget;          // null bhi ho sakta hai agar pointer window se hi bahar chala gaya

  // Check: kya related target abhi bhi parent ke andar (ya khud parent) hai?
  if (related && parent.contains(related)) {  // contains() — DOM tree traversal se ancestor-check
    return;  // pointer sirf child mein gaya hai, parent se "actually" nahi nikla — ignore karo
  }

  // Yahan tak pahunche matlab pointer genuinely parent (aur uske saare children) se bahar gaya
  parent.classList.remove('highlighted');  // highlight hataao — real "leave" hua
};

// mouseenter/mouseleave se yehi kaam bina manual filtering ke ho jaata:
parent.onmouseenter = () => parent.classList.add('highlighted');    // sirf ek baar fire, children ignore
parent.onmouseleave = () => parent.classList.remove('highlighted'); // sirf ek baar fire, children ignore

Toh mouseenter/mouseleave hamesha better hai? Nahi — kyunki wo bubble nahi karte, event delegation (chapter 19 wala pattern — ek listener document/parent pe, sab children ke liye) inke saath kaam nahi karta. Agar tumhe 500 table cells pe delegated hover-detection chahiye, to mouseover/mouseout hi option hai — relatedTarget filtering ke saath, jaise upar dikhaya.

📌 Fast mouse movement — elements skip ho sakte hain

Browser har pixel ke liye event fire nahi karta — periodically mouse position check karta hai (performance ke liye). Agar pointer bahut fast move kare, to beech ke koi child elements ka mouseover/mouseout bilkul fire hi nahi hoga — pointer directly ek distant descendant pe "land" kar sakta hai. Isliye kabhi assume mat karo ki path mein har element ko event milega.

Mouse events se Drag'n'Drop banana

Native HTML5 dragstart/dragover/drop API exist karta hai, lekin uski limitations significant hain — tum dragging ko kisi specific area tak restrict nahi kar sakte, horizontal/vertical-only drag nahi bana sakte, aur mobile support historically weak raha hai. Isliye production drag'n'drop UIs (Trello-style boards, sliders, sortable lists) zyada tar manually mousedown + mousemove + mouseup se implement hote hain — full control milta hai.

Algorithm teen steps mein:

  1. mousedown — element ko position: fixed banao, z-index se top pe le aao, shift calculate karo.
  2. mousemove (document pe) — element ko pointer ke saath move karo, shift maintain karte hue.
  3. mouseup — handlers hata do, drop-target detect karke finalize karo.
Manual drag'n'drop — position:fixed + shift technique
ball.ondragstart = function() {            // browser ka NATIVE drag'n'drop disable karo
  return false;                                    // warna image-ghost-drag ka default visual artifact aayega
};

ball.onmousedown = function(event) {       // Step 1: press hote hi drag session start

  // shiftX/shiftY = pointer aur element ke top-left corner ke beech ka offset
  let shiftX = event.clientX - ball.getBoundingClientRect().left;  // horizontal offset — ye maintain rakhna hai warna ball center-jump karega
  let shiftY = event.clientY - ball.getBoundingClientRect().top;   // vertical offset — same reason

  ball.style.position = 'fixed';            // fixed positioning — viewport-relative, so clientX/Y directly use kar sakte hain
  ball.style.zIndex = 1000;               // baaki sab content ke upar render ho
  document.body.append(ball);              // body ka direct child bana do — parent ke overflow:hidden se bachne ke liye

  function moveAt(pageX, pageY) {          // helper: ball ko diye gaye coordinates pe (shift adjust karke) rakho
    ball.style.left = pageX - shiftX + 'px';  // shift subtract karke — pointer wahi grab-point pe rahega jahan pehle tha
    ball.style.top = pageY - shiftY + 'px';
  }
  moveAt(event.pageX, event.pageY);       // initial position turant set — warna pehla mousemove tak ball old jagah dikhega

  let currentDroppable = null;          // track karo ki currently kis droppable ke upar hover kar rahe hain

  function onMouseMove(event) {       // Step 2: har move pe ball follow kare
    moveAt(event.pageX, event.pageY);     // naya position set karo

    ball.hidden = true;              // ball ko temporarily chhupao — warna elementFromPoint ball ko hi detect karega
    let elemBelow = document.elementFromPoint(event.clientX, event.clientY);  // ball ke NEECHE actual element kaunsa hai (clientX/Y — viewport-relative API hai)
    ball.hidden = false;             // ball wapis dikhao

    let droppableBelow = elemBelow?.closest('.droppable');  // closest ancestor jo ".droppable" class rakhta ho (ya khud element)

    if (currentDroppable != droppableBelow) {  // target change hua hai kya (naya droppable ya null)
      if (currentDroppable) {              // agar pehle koi droppable highlighted tha
        currentDroppable.classList.remove('hovered');  // uska highlight hatao — ball wahan se nikal gaya
      }
      currentDroppable = droppableBelow;     // naya current target set karo (ho sakta hai null ho)
      if (currentDroppable) {              // agar naya target valid droppable hai
        currentDroppable.classList.add('hovered');     // highlight karo — visual feedback user ko
      }
    }
  }

  document.addEventListener('mousemove', onMouseMove);  // DOCUMENT pe listen karo — sirf ball pe nahi, kyunki pointer ball se bahar bhi nikal sakta hai

  ball.onmouseup = function() {              // Step 3: release hote hi drag session end
    document.removeEventListener('mousemove', onMouseMove);  // ZAROORI cleanup — warna listener leak hoke agli drag ko bhi affect karega
    ball.onmouseup = null;              // khud ko bhi hata do
    if (currentDroppable) {                // agar drop kisi valid target pe hua
      console.log('Dropped into:', currentDroppable);  // yahan actual drop-logic likho — e.g. DOM move, API call
      currentDroppable.classList.remove('hovered');  // highlight hatao, drag session finish
    }
  };
};
🧠 Senior Dev Note: document pe listen karna hi kyun

mousemove listener ball pe nahi, document pe lagaya gaya hai — ye intentional hai. Fast dragging mein pointer easily ball ke bounding box se bahar nikal sakta hai (ball follow karne mein hamesha ek frame ka lag hota hai), aur agar listener sirf ball pe hota, to jaise hi pointer ball se bahar gaya, drag "atak" jaata. Document-level listening ensure karta hai ki pointer window ke andar kahin bhi ho, drag continue rahe. Yahi reason hai ki Pointer Events wale setPointerCapture approach isse zyada elegant hai — niche dekhenge.

Pointer Events — modern unified API

Historically web ke paas sirf mouse events the. Phir touchscreens aaye, aur alag touchstart/touchmove/touchend family add hui. Result: ek hi interaction (jaise drag'n'drop) ko support karne ke liye developers ko do parallel event systems likhne padte — mouse ke liye aur touch ke liye — plus stylus/pen devices apni khud ki quirks laate. Pointer Events spec ne ye fragmentation solve kiya: ek hi event family, sab input devices ke liye (mouse, touch, pen) — pointerdown, pointerup, pointermove, pointerover, pointerout, pointerenter, pointerleave — mouse events ke naam-mapping equivalent, lekin device-agnostic.

Extra properties jo mouse events mein nahi hote: pointerId (multi-touch mein har finger ki unique ID), pointerType ("mouse"/"touch"/"pen"), isPrimary (multi-touch mein first pointer), aur pressure (pen devices ke liye force).

Pointer capture — slider drag bina document listener ke
thumb.onpointerdown = function(event) {   // pointerdown — mouse click ho ya touch tap ho, DONO ke liye same handler

  thumb.setPointerCapture(event.pointerId);  // ROOT MECHANISM: is pointerId ke saare future events ab thumb ko hi milenge
  // matlab agar pointer thumb ki boundary se bahar bhi nikal jaaye, events yahin aate rahenge — document listener ki zaroorat khatam

  thumb.onpointermove = function(event) {  // capture ke baad, ye directly thumb pe hi fire hoga chahe pointer kahin bhi ho
    let newLeft = event.clientX - slider.getBoundingClientRect().left;  // slider ke andar relative position calculate karo
    thumb.style.left = newLeft + 'px';  // thumb ko naye position pe move karo
  };

  thumb.onpointerup = function(event) {    // release — capture automatically release ho jaata hai pointerup pe
    thumb.onpointermove = null;       // handler cleanup — memory leak se bachne ke liye
    thumb.onpointerup = null;         // khud ko bhi hata do
  };
};

// Native drag interference se bachne ke liye — dono zaroori hain touch devices pe
thumb.ondragstart = () => false;       // native HTML drag disable karo

setPointerCapture ka use isliye better hai upar wale manual drag'n'drop example se — wahan humein document pe listener lagana pada tha aur manually cleanup karna pada tha. Pointer capture ke saath, saare events directly target element pe hi retarget ho jaate hain, code cleaner ho jaata hai, aur accidental trigger doosre elements ke pointer handlers pe nahi hota.

📌 pointercancel — jab browser interaction cheen leta hai

Ye event fire hota hai jab ongoing pointer interaction browser khud abort kar deta hai — jaise device orientation change (tablet rotate), ya browser ka apna native drag-and-drop/zoom-pan gesture activate ho jaana. Isse bachne ke liye ondragstart = () => false aur CSS touch-action: none element pe lagana chahiye.

Keyboard Events

Sirf do events yaad rakhne zaroori hain: keydown (key press hote hi) aur keyup (release hote hi). keypress event, aur uske saath keyCode/charCode/which properties, spec se deprecated hain — cross-browser inconsistencies itni thi ki spec authors ne inhe replace karna hi better samjha modern key/code properties se.

event.key vs event.code ka farak samajhna critical hai:

  • event.key — human-readable character jo actually produce hua, layout-dependent. Z key US layout pe "z"/"Z" deta hai, German QWERTZ layout pe wahi physical key "y" deta hai.
  • event.code — physical key ka location, layout-independent. Wahi Z-position wali key hamesha "KeyZ" deti hai, chahe layout kuch bhi ho.
WASD game controls — event.code kyun zaroori hai
const pressedKeys = new Set();  // currently-held keys ka set — game loop isse read karega

document.addEventListener('keydown', function(event) {  // key press hote hi
  // event.code use kiya — event.key NAHI, kyunki code physical position deta hai
  if (['KeyW', 'KeyA', 'KeyS', 'KeyD'].includes(event.code)) {  // physical WASD position check
    // AZERTY (French) keyboard pe yehi physical keys ZQSD "type" karte hain,
    // lekin event.code hamesha 'KeyW'/'KeyA'/'KeyS'/'KeyD' hi rahega — layout kuch bhi ho
    pressedKeys.add(event.code);  // set mein add karo — game loop movement direction yahan se derive karega
    event.preventDefault();  // browser ke default scroll/behavior ko rokna (e.g. space-bar page-scroll)
  }

  // Agar hum event.key use karte, to AZERTY user ke liye "W" physical key ka key value 'z' hota — bug!

  if (event.repeat) {  // repeat property — key ko dabaye rakhne se browser auto-fire karta hai keydown
    return;  // game loop already Set se continuous movement handle kar raha, duplicate work skip karo
  }
});

document.addEventListener('keyup', function(event) {    // key release hote hi
  pressedKeys.delete(event.code);  // set se hatao — ab wo direction move nahi karegi
});

// Hotkey pattern — Ctrl/Cmd+Z (undo). Yahan bhi code use kiya kyunki hotkeys layout-independent hone chahiye
document.addEventListener('keydown', function(event) {
  if (event.code == 'KeyZ' && (event.ctrlKey || event.metaKey)) {  // physical Z key + Ctrl(Win)/Cmd(Mac)
    alert('Undo!');  // undo logic yahan trigger hoga
  }
});
⚠️ event.key ya event.code — kab kaunsa

Rule of thumb: text input ke liye event.key (jo character user actually type kar raha hai wahi chahiye, chahe layout kuch bhi ho), aur physical shortcuts/game-controls ke liye event.code (WASD, hotkeys — jahan physical key position matter karta hai, produced character nahi). Special keys jaise Shift, Enter, F1 ke liye event.key aur event.code almost same hote hain (koi printable character produce nahi hota).

Scroll Events + throttling

scroll event tab fire hota hai jab page (ya koi scrollable element) scroll hota hai — do main use-cases: (1) scroll position ke hisaab se UI elements show/hide karna (jaise "back to top" button, sticky header), aur (2) infinite scrolling — bottom ke paas pahunchte hi zyada content load karna.

⚠️ scroll pe preventDefault() kaam nahi karta

scroll event scroll ho chuke hone ke baad fire hota hai — isliye event.preventDefault() yahan koi effect nahi karta, scroll already ho chuka hota hai. Agar scrolling actually rokni hai (jaise Page-Down key se), to scroll ko cause karne wale event (e.g. keydown) pe hi preventDefault() lagana padega — ya CSS overflow: hidden use karo.

Scroll bahut high-frequency fire hota hai — ek continuous scroll gesture mein dozens of events per second. Agar tumhara handler har baar heavy DOM reads/writes karta hai (jaise getBoundingClientRect, layout recalculation trigger karne wali cheezein), to ye janky scrolling aur frame drops ka direct cause banta hai.

requestAnimationFrame-based scroll throttle
function throttleWithRAF(callback) {          // higher-order function — koi bhi callback wrap kar sakta hai
  let scheduled = false;                     // flag: kya ek frame already schedule ho chuka hai

  return function(...args) {              // wrapped function jo actual event listener banega
    if (scheduled) return;          // agar already ek frame pending hai, naya schedule mat karo — ye hi throttle ka core hai
    scheduled = true;                    // flag set — agla event isse skip karega jab tak ye frame process na ho

    requestAnimationFrame(() => {       // browser ke next paint cycle se pehle callback run karo — max 1 baar per frame (~60fps)
      callback(...args);            // asli kaam yahan — latest args ke saath (purane intermediate scroll events discard ho gaye)
      scheduled = false;                // flag reset — agla scroll event ab naya frame schedule kar sakta hai
    });
  };
}

function checkInfiniteScroll() {              // actual scroll-handling logic (heavy — layout read karta hai)
  const rect = document.documentElement.getBoundingClientRect();  // poore document ka viewport-relative bounding box
  const distanceFromBottom = rect.bottom - window.innerHeight;  // document ka bottom edge, viewport bottom se kitna door hai

  if (distanceFromBottom < 300) {       // 300px threshold — bottom ke paas pahunchte hi trigger karo, exact bottom pe nahi
    loadMoreContent();                // naya content fetch/append karo (API call ya DOM insert)
  }
}

// Naked handler ki jagah throttled version register karo
window.addEventListener('scroll', throttleWithRAF(checkInfiniteScroll));  // ab heavy logic max 60 baar/sec chalega, chahe scroll event 200+ baar fire ho

Ye requestAnimationFrame-based throttle isliye better hai plain setTimeout throttle se — kyunki ye browser ke actual paint cycle ke saath sync hota hai. Agar tum setTimeout(fn, 100) use karte, to fixed 100ms interval hota hai jo device ki refresh rate se independent hai (kabhi extra work, kabhi janky). rAF ensures ki callback exactly utni baar chale jitni baar browser actually naya frame paint kar raha hai — na zyada, na kam.

🧠 Senior Dev Note: passive listeners aur scroll performance

Scroll (aur touchmove) listeners ke liye { passive: true } option pass karna production mein important hai: window.addEventListener('scroll', handler, { passive: true }). Ye browser ko batata hai ki handler kabhi preventDefault() call nahi karega, isliye browser scroll ko turant process kar sakta hai, handler ke complete hone ka wait kiye bina. Bina passive flag ke, browser ko har scroll frame se pehle handler complete hone ka wait karna padta hai (kyunki wo preventDefault call kar sakta hai) — jo scroll ko janky bana deta hai, especially mobile devices pe. Chrome jaise browsers touch listeners ke liye passive ko default bhi bana chuke hain, but scroll listeners pe explicit karna best practice hai.

Key Takeaways

  • Click sequence hamesha: mousedown → mouseup → click — agar dono alag elements pe hue, click fire nahi hoga.
  • clientX/Y = viewport-relative (scroll-independent), pageX/Y = document-relative (scroll ke saath badhta hai).
  • mouseover/mouseout bubble karte hain aur child-boundary crossings pe bhi fire hote hain — relatedTarget se filter karo. mouseenter/mouseleave bubble nahi karte, sirf ek baar fire hote hain, but delegation ke saath incompatible hain.
  • Manual drag'n'drop = mousedown (position:fixed + shift calculate) → mousemove on document (element move + elementFromPoint se droppable detect) → mouseup (cleanup + finalize).
  • Pointer Events ek hi API se mouse/touch/pen sab handle karte hain — setPointerCapture events ko ek element pe "pin" kar deta hai, document-level listeners ki zaroorat khatam kar deta hai.
  • event.key = human-readable character (text input ke liye), event.code = physical key position, layout-independent (hotkeys/game-controls ke liye).
  • keypress, keyCode, charCode, which deprecated hain — keydown/keyup + key/code use karo.
  • scroll event pe preventDefault() kaam nahi karta (scroll already ho chuka hota hai) — causing event pe rokna padta hai. High-frequency handlers ko requestAnimationFrame se throttle karo, aur { passive: true } lagao.

🎯 Interview Questions

  • click event kab fire NAHI hoga, bawajood mousedown aur mouseup dono ke fire hone ke?
    Hint: jab mousedown aur mouseup alag-alag elements pe complete hue ho (drag karke button se bahar release karna) — click sirf same-element completion pe fire hota hai.
  • mouseover parent element pe unexpectedly kyun fire hota hai jab pointer sirf ek child ke andar jaata hai?
    Hint: child ka mouseover event bubble karke parent tak pahunchta hai — event.target check karke ya relatedTarget se parent.contains() filter karke asli "enter" detect karna padta hai.
  • mouseenter/mouseleave se event delegation kyun kaam nahi karta?
    Hint: ye events bubble hi nahi karte, isliye ek parent-level listener child elements ke enter/leave events kabhi receive hi nahi karega — delegation ka pura mechanism bubbling pe depend karta hai.
  • Manual drag'n'drop implementation mein mousemove listener document pe kyun lagate hain, dragged element pe kyun nahi?
    Hint: fast dragging mein pointer easily element ke bounding box se aage nikal jaata hai (element hamesha ek-frame-lag se follow karta hai) — element-level listener se drag beech mein atak jaata.
  • Pointer Events ne separate mouse aur touch event handling ki problem kaise solve ki, aur setPointerCapture kya fayda deta hai?
    Hint: ek hi event family (pointerdown/move/up) sab input types ke liye; setPointerCapture events ko specific element pe retarget kar deta hai, chahe pointer element se bahar chala jaaye — document-level listeners ki zaroorat khatam.
  • event.key aur event.code mein farak batao ek concrete example ke saath.
    Hint: event.key = produced character, layout-dependent (German layout pe Z-position 'y' deta hai); event.code = physical position, hamesha same (us position ka code hamesha "KeyZ" hi rahega).
  • keypress event kyun deprecated hai?
    Hint: keypress aur uske saath aane wali properties (keyCode, charCode, which) mein cross-browser inconsistencies itni thi ki spec ne unhe replace kar diya modern key/code se.
  • scroll event pe preventDefault() call karne se scroll kyun nahi rukta?
    Hint: scroll event scroll ho chuke hone KE BAAD fire hota hai (post-facto notification), isliye us point tak preventDefault ka koi effect nahi — scrolling ko cause karne wale original event (jaise keydown) pe hi rokna padta hai.
