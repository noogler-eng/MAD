Binary Data & Files

Ab tak humne strings, numbers, objects — sab "high-level" JS types dekhe. Lekin browser ke andar, network se aane wale bytes, ek image file, ya ek <input type="file"> se select ki hui PDF — ye sab raw binary data hai, koi structure inherently attached nahi. Is chapter mein hum root se dekhenge ki JS raw memory (ArrayBuffer) ko kaise "views" ke through interpret karta hai, strings ko bytes mein kaise convert karta hai (TextEncoder/TextDecoder), aur file-like binary objects (Blob, File) ko kaise handle karta hai.

ArrayBuffer — raw fixed-length memory

Root-level sabse important baat: ArrayBuffer khud kuch bhi "type" nahi jaanta. Ye sirf ek fixed-length, contiguous raw memory area ka reference hai — bytes ka ek chunk, sab zero se initialize hota hai. Isme koi [] indexing method nahi hai, koi .map() nahi, kuch nahi — sirf ek .byteLength property. Memory allocate ho gayi hai, lekin usko "kaise padhna hai" (1 byte ek number? 2 bytes ek number? 4 bytes?) ye decide karne ke liye tumhe ek view chahiye.

ArrayBuffer banate hain
let buffer = new ArrayBuffer(16); // 16 bytes ki raw memory allocate hui, sab zero se bhari

alert(buffer.byteLength); // 16 — total bytes, yehi is buffer ki sirf "readable" property hai

// buffer[0] = 1;  // ❌ isse kuch nahi hota — ArrayBuffer par direct indexing/assignment allowed hi nahi hai
// buffer khud "dumb" hai — ye sirf bytes ka container hai, koi interpretation nahi karta

Isko ek khaali plot of land samjho — zameen allocate ho chuki hai, size fix hai (16 bytes), lekin uspar "building" (interpretation) banane ke liye tumhe ek architect (view) chahiye.

TypedArrays — views into the buffer

TypedArrays ArrayBuffer ke "lens" hain — wo khud memory allocate nahi karte (agar tum seedha length se banao to internally ek buffer auto-create ho jaata hai), balki ek existing buffer ko ek specific numeric format ke through expose karte hain. Har typed array batata hai: (a) har element kitne bytes ka hai, (b) us byte-group ko kaise interpret karna hai (signed/unsigned integer, float).

TypeBytes per elementRange
Int8Array1-128 se 127
Uint8Array10 se 255
Uint8ClampedArray10 se 255, out-of-range values clamp hoti hain (truncate nahi)
Int16Array / Uint16Array2±32768 / 0-65535
Int32Array / Uint32Array4±2^31 / 0-2^32
Float32Array / Float64Array4 / 8floating point
ArrayBuffer ko Uint32Array view se access karna
let buffer = new ArrayBuffer(16);          // 16 raw bytes, koi format nahi

let view = new Uint32Array(buffer);       // same 16 bytes ko 4-byte chunks ke roop mein dekho

alert(Uint32Array.BYTES_PER_ELEMENT); // 4 — har element 4 bytes leta hai
alert(view.length);            // 4 — kyunki 16 bytes / 4 bytes-per-element = 4 elements
alert(view.byteLength);        // 16 — view ka total byte span (jitna underlying buffer hai)

view[0] = 123456;              // pehle 4 bytes mein 123456 ko 32-bit integer ke roop mein likha

for (let num of view) {       // TypedArrays iterable hain — for..of directly chalta hai
  alert(num);              // 123456, 0, 0, 0 — baaki 3 elements abhi bhi zero hain
}

Note: new Uint32Array(buffer) koi copy nahi banata — ye same underlying memory ko dekhta hai. Agar tum view[0] change karte ho, to actual bytes buffer mein modify hote hain, koi naya allocation nahi hota.

Ek buffer, do views — ek saath (root diagram)

Ye wo concept hai jo interview mein baar-baar puchha jaata hai: ek hi ArrayBuffer ko multiple views se ek saath dekha ja sakta hai — bilkul waise jaise ek hi file ko Notepad (text) aur Hex Editor (bytes) dono ek saath khol ke dekh sakte ho, aur ek mein change karo to doosre mein bhi reflect hota hai (kyunki underlying disk data same hai).

4-byte buffer socho. Ek Uint8Array view isko 4 separate elements ke roop mein dikhayega (har byte apna element), jabki ek Uint16Array view usi 4-byte buffer ko 2 elements ke roop mein dikhayega (har element = 2 bytes combine karke): 

Raw bytes in buffer (4 bytes total):     [ B0 ][ B1 ][ B2 ][ B3 ]

Uint8Array view  (1 byte/element, len=4): [B0]  [B1]  [B2]  [B3]
                                           idx0  idx1  idx2  idx3

Uint16Array view (2 bytes/element, len=2): [B0 B1]     [B2 B3]
                                             idx0        idx1
Same buffer, do alag views — ek modify karo, doosre mein dikhta hai
let buffer = new ArrayBuffer(4);        // sirf 4 raw bytes ki memory

let bytes = new Uint8Array(buffer);  // view #1: har byte ek alag element (length 4)
let words = new Uint16Array(buffer); // view #2: har 2 bytes ek element (length 2) — SAME memory

bytes[0] = 255;                    // byte 0 ko 255 (0xFF) set kiya, sirf Uint8Array API se
bytes[1] = 1;                      // byte 1 ko 1 set kiya

alert(words[0]);                // 511 (little-endian machine par) — byte0+byte1 ko 16-bit number ki tarah combine kiya
// yahi proof hai ki bytes aur words EK HI memory ko access kar rahe the — koi copy nahi thi
🧠 Senior Dev Note: byte-length mismatch ek silent bug source hai

Agar tum ek 5-byte ArrayBuffer par Uint32Array view banane ki koshish karo (jo 4-byte chunks maangta hai), to browser RangeError throw karega — kyunki 5 bytes clean 4-byte groups mein divide nahi hote. Ye production mein tab aata hai jab tum network se ek arbitrary-length payload receive karte ho aur bina length check kiye directly new Float64Array(receivedBuffer) laga dete ho. Root cause: view ka constructor internally buffer.byteLength % BYTES_PER_ELEMENT === 0 validate karta hai — agar fail hua to exception. Isliye WebSocket/fetch se aane wale binary payloads ko parse karte waqt DataView zyada safe hota hai (neeche dekho), kyunki wo per-byte-offset padhta hai, strict alignment force nahi karta.

TypedArray methods aur out-of-bounds behavior

TypedArrays regular Array jaise lagte hain (map, slice, find, reduce sab available hain, aur ye iterable bhi hain), lekin fixed-length hone ki wajah se push, pop, splice, unshift nahi hote — memory size badal/ghata nahi sakte.

set() aur subarray() — copy vs view
let arr8 = new Uint8Array(10);         // 10 bytes, sab zero se initialize

arr8.set([1, 2, 3], 0);       // index 0 se start karke [1,2,3] COPY kiye — arr8 = [1,2,3,0,0,0,0,0,0,0]

let sub = arr8.subarray(0, 3);       // index 0..3 ka NAYA VIEW — koi copy nahi, same underlying buffer
sub[0] = 99;                     // sub ko modify kiya...
alert(arr8[0]);                // 99 — original arr8 bhi change ho gaya, kyunki subarray ne copy nahi banayi thi

let tooBig = new Uint8Array(1);       // sirf 1 byte ka array, 8-bit unsigned
tooBig[0] = 256;                // 256 ek 8-bit unsigned range (0-255) se bahar hai
alert(tooBig[0]);              // 0 — silently truncate hua (sirf rightmost 8 bits rakhe, koi error nahi aaya!)
⚠️ Overflow silently truncate hota hai, throw nahi karta

Ye ek common gotcha hai — Uint8Array mein 256 daalne pe koi error nahi aata, bas value chup-chaap wrap ho jaati hai (256 → 0, 257 → 1, aur so on — modulo 256 behavior). Sirf Uint8ClampedArray exception hai: wo values ko range ke andar clamp karta hai (256 → 255, -10 → 0) — isliye image pixel data (Canvas ImageData) ke liye specifically use hota hai, jahan overflow se pixel corrupt hone ke bajaye saturate hona chahiye.

DataView — mixed-type reading

Real binary formats (jaise file headers, network protocols) mein alag-alag fields alag-alag sizes ke hote hain — kabhi ek byte ek flag, agle 4 bytes ek integer, agle 8 bytes ek float. Ek single TypedArray isko handle nahi kar sakta (wo fixed element-size maanta hai). Yahan DataView kaam aata hai — ye ek "untyped" view hai jisme format har read/write call ke time specify karte ho, construction time pe nahi.

DataView se mixed-type buffer padhna
let buffer = new Uint8Array([255, 255, 255, 255]).buffer;
                                                    // 4 bytes, sab 0xFF — .buffer se underlying ArrayBuffer nikala

let dataView = new DataView(buffer);       // untyped view — format har call mein alag se batayenge

let byte1 = dataView.getUint8(0);       // offset 0 se 1 byte, unsigned integer ki tarah padha → 255
let short1 = dataView.getUint16(1);     // offset 1 se 2 bytes, 16-bit integer ki tarah padha (bytes 1&2 overlap karte hain byte1 se)
let long1 = dataView.getUint32(0);       // offset 0 se 4 bytes, 32-bit integer ki tarah — SAME memory, alag interpretation

alert(byte1.toString(16));       // "ff"
alert(short1.toString(16));      // "ffff"
alert(long1.toString(16));       // "ffffffff"

dataView.setUint32(0, 0);         // offset 0 pe 4 bytes ko 0 se overwrite kar diya (writing bhi supported hai)
📌 DataView vs TypedArray — kab kaunsa

TypedArray tab use karo jab tumhara data uniform ho (sab elements ek hi type, jaise ek grayscale image ke pixels — sab Uint8). DataView tab use karo jab format heterogeneous ho (jaise ek binary file header: 1 byte version + 4 byte length + 8 byte timestamp) — DataView tumhe exact byte offsets pe control deta hai bina alignment restrictions ke.

TextEncoder / TextDecoder — string ↔ binary

Strings JS engine ke andar UTF-16 mein store hoti hain, lekin network/file/storage layer pe hum almost hamesha UTF-8 bytes chahte hain (compact, web-standard). TextEncoder aur TextDecoder ye conversion karte hain — string se bytes, aur bytes se string.

TextEncoder — string se Uint8Array bytes
let encoder = new TextEncoder();        // UTF-8 encoder — ye sirf UTF-8 support karta hai, koi doosra encoding nahi

let uint8Array = encoder.encode("Hello"); // string ko UTF-8 bytes mein encode karke Uint8Array return karta hai

alert(uint8Array);              // 72,101,108,108,111 — har char ka UTF-8 byte code (ASCII range mein 1 char = 1 byte)
TextDecoder — bytes se string
let uint8Array = new Uint8Array([72, 101, 108, 108, 111]);
                                          // ye bytes "Hello" ke UTF-8 codes hain

let decoder = new TextDecoder();      // default encoding "utf-8" — label pass karke big5/windows-1251 bhi diya ja sakta hai

alert(decoder.decode(uint8Array)); // "Hello" — bytes ko wapas readable string mein decode kiya

let partial = decoder.decode(uint8Array.subarray(0, 2));
                                          // subarray() = koi copy nahi, so partial decode bhi memory-efficient hai
alert(partial);                  // "He" — sirf pehle 2 bytes decode hue
🧠 Senior Dev Note: streaming decode — multi-byte character split hona

Jab bade files ya network streams ko chunks mein decode karte ho (jaise ReadableStream se ek chunk-at-a-time), ek problem aati hai: UTF-8 mein non-ASCII characters 2-4 bytes lete hain, aur ek chunk boundary exactly beech mein aa sakti hai — matlab ek character ke bytes do alag chunks mein split ho sakte hain. Agar tum har chunk ko independently decode() karoge, to split hue character ke liye replacement character (�) aa jaayega. Fix: decoder.decode(chunk, {stream: true}) — ye incomplete trailing bytes ko internally buffer kar leta hai aur agli call mein prepend kar deta hai, taaki koi character corrupt na ho. Last chunk pe stream: true mat do (ya explicitly decoder.decode() bina argument call karo) taaki final buffered bytes bhi flush ho jaayein.

Blob — immutable binary object with a MIME type

Blob (Binary Large Object) ek high-level, file-like object hai jo raw binary data ko ek MIME type ke saath wrap karta hai. Jahan ArrayBuffer/TypedArray "raw memory manipulate karo" ka layer hai, wahan Blob "is data ko ek file/resource ki tarah treat karo" ka layer hai — download links, uploads, aur network APIs ke liye designed.

Blob banate hain — string aur binary parts se
let blob1 = new Blob(["<html>…</html>"], {type: 'text/html'});
                                            // blobParts array mein ek string diya, type "text/html" set kiya

let hello = new Uint8Array([72, 101, 108, 108, 111]); // "Hello" ke UTF-8 bytes

let blob2 = new Blob([hello, ' ', 'world'], {type: 'text/plain'});
                                            // blobParts mixed ho sakti hain: TypedArray + strings ek saath — sab concatenate ho jaate hain

alert(blob2.size);                     // total bytes ("Hello" + " " + "world" ke UTF-8 bytes ka sum)
alert(blob2.type);                     // "text/plain"

Blob immutable hai — ek baar bana lene ke baad uski content directly modify nahi kar sakte. Agar tumhe ek naya "version" chahiye (jaise pehle N bytes hata do), to slice() use karke ek naya Blob banate ho, existing wala untouched rehta hai:

Blob.slice() — immutability ke saath naya blob
let blob = new Blob(["Hello, world!"], {type: 'text/plain'});

let piece = blob.slice(0, 5, 'text/plain');  // byteStart=0, byteEnd=5, naya optional contentType — original blob unchanged

// slice() Array.slice() jaisa hi hai — negative indices bhi supported hain (end se count)
// "blob" khud kabhi mutate nahi hota — sirf naye Blob instances banate hain

Blob se URL — download links aur object URLs

URL.createObjectURL(blob) ek internal reference banata hai — ek special blob: scheme wala URL jo browser memory mein us exact Blob object ko point karta hai. Ye URL <a href>, <img src>, ya kisi bhi jagah use ho sakta hai jahan normal URL chalta hai — bina data ko base64 encode kiye (jo bahut bada overhead hota hai).

Blob se download link trigger karna
let blob = new Blob(["Hello, world!"], {type: 'text/plain'});

let link = document.createElement('a');    // ek <a> element in-memory banaya (DOM mein add nahi kiya)
link.download = 'hello.txt';     // download attribute: browser ko force karta hai ki navigate na kare, file save kare
link.href = URL.createObjectURL(blob);
                                       // browser memory mein blob ko register karke ek "blob:https://..." URL diya

link.click();                    // programmatically click simulate karke download trigger kiya

URL.revokeObjectURL(link.href); // ZAROORI: internal reference clear kiya taaki blob garbage-collect ho sake
⚠️ revokeObjectURL bhoolna = memory leak

createObjectURL jo mapping banata hai wo document ke lifetime tak browser memory mein rehti hai — tab tak jab tak explicitly revokeObjectURL() na call karo, chahe blob ka koi aur reference kahin bhi na ho. Ek SPA (single-page app) jo baar-baar large files (images, videos) ke object URLs banata hai lekin revoke nahi karta, uska memory footprint gradually grow karta rehta hai — page reload tak kabhi free nahi hota. Rule: jaise hi download/preview ka kaam ho jaaye (ya <img> ka onload fire ho jaaye), turant revokeObjectURL call karo.

Blob se wapas raw bytes bhi mil sakte hain — await blob.arrayBuffer() (async, Promise return karta hai) se ArrayBuffer, ya blob.stream() se ek ReadableStream jise chunk-by-chunk pump kiya ja sakta hai (bade files ke liye memory-efficient — pura file ek saath memory mein load nahi karna padta).

File — Blob + filesystem metadata

File object Blob se inherit karta hai — matlab jo bhi Blob kar sakta hai (size, type, slice), File bhi kar sakta hai, plus filesystem-related extra properties: name (filename) aur lastModified (timestamp). Practically, File objects tum khud rarely construct karte ho — ye usually browser deta hai jab user <input type="file"> se file select kare ya drag-and-drop kare.

File input se File object access karna
<input type="file" onchange="showFile(this)">

<script>
function showFile(input) {            // input = <input> DOM element jo change event fire kar raha hai
  let file = input.files[0];       // .files ek FileList hai (array-like) — [0] = pehli selected file

  alert(`File name: ${file.name}`);       // File-specific property — Blob ke paas ye nahi hota
  alert(`Last modified: ${file.lastModified}`); // integer timestamp (ms) — OS filesystem se aaya metadata
  alert(`Size: ${file.size}`);            // inherited from Blob — bytes mein size
  alert(`Type: ${file.type}`);            // inherited from Blob — MIME type (browser ne extension se guess kiya)
}
</script>

Manually construct karna ho (rare — usually testing ya generated files ke liye) to syntax: new File(fileParts, fileName, options) — bilkul Blob constructor jaisa, bas extra fileName parameter aur options mein optional lastModified.

FileReader — async reading pattern

File/Blob ke paas content padhne ka koi synchronous method nahi hai — disk se data laana time leta hai, isliye FileReader ek event-based async API deta hai. Root pattern: reading method call karo (jo turant return ho jaata hai), phir events attach karo jo baad mein fire honge jab actual read complete/fail ho.

MethodResult format
readAsArrayBuffer(blob)raw ArrayBuffer — binary processing ke liye (jaise image parsing)
readAsText(blob, [encoding])string — default UTF-8, chahe to doosra encoding specify karo
readAsDataURL(blob)base64-encoded data: URL — directly <img src> mein daalne layak
FileReader — onload/onerror/onprogress pattern
<input type="file" onchange="readFile(this)">

<script>
function readFile(input) {
  let file = input.files[0];          // user ne select ki hui File
  if (!file) return;              // koi file select nahi hui to kuch mat karo (guard clause)

  let reader = new FileReader();     // ek naya reader instance — reusable hai, but ek time pe ek hi read

  reader.onloadstart = function() {
    console.log('Reading started...'); // reading process shuru hua — turant fire hota hai
  };

  reader.onprogress = function(event) {
    if (event.lengthComputable) {       // kabhi-kabhi total size pata nahi hota (streaming source)
      let percent = Math.round((event.loaded / event.total) * 100);
                                              // loaded/total ke ratio se percentage nikala
      console.log(`Progress: ${percent}%`);  // large files (jaise video upload preview) ke liye useful
    }
  };

  reader.onload = function() {          // reading successfully complete hui
    console.log(reader.result);        // .result mein final data — yahan text hoga kyunki readAsText use kiya
  };

  reader.onerror = function() {         // read fail hua (permission issue, file removed mid-read, etc.)
    console.log('Error: ' + reader.error); // .error mein DOMException detail
  };

  reader.onloadend = function() {       // success YA failure — dono cases mein hamesha fire hota hai (cleanup ke liye)
    console.log('Read finished (success or fail)');
  };

  reader.readAsText(file);          // actual read trigger — async hai, ye line turant return ho jaati hai
  // reader.abort();  // agar chahiye to kabhi bhi pending read cancel kar sakte ho — 'abort' event fire hoga
}
</script>
🧠 Senior Dev Note: readAsDataURL vs createObjectURL for image preview

Ek common task hai: user ne image select ki, usko <img> mein preview dikhana hai. Do approaches — reader.readAsDataURL(file) jo base64 string return karta hai (memory mein ~33% overhead, kyunki base64 binary se bada hota hai, aur poori file synchronously JS heap mein encoded form mein aati hai), vs URL.createObjectURL(file) jo turant (synchronous, no FileReader needed) ek lightweight reference URL de deta hai bina file content ko actually memory mein load/encode kiye. Production mein createObjectURL almost hamesha better hai for previews — FileReader ka use tab karo jab tumhe actual raw bytes/text chahiye ho processing ke liye (jaise CSV parse karna, ya binary header read karna), sirf display ke liye nahi.

Key Takeaways

  • ArrayBuffer = raw fixed-length memory, khud koi method/interpretation nahi rakhta — sirf .byteLength.
  • TypedArrays (Uint8Array, Uint16Array, etc.) aur DataView "views" hain — ek hi buffer ko multiple formats mein ek saath dekh sakte ho, bina data copy kiye.
  • TypedArrays fixed-length hain (no push/pop/splice); numeric overflow silently truncate hota hai (sirf Uint8ClampedArray clamp karta hai, throw nahi).
  • DataView mixed-type/heterogeneous binary formats (headers, protocols) ke liye best hai — per-offset format control deta hai.
  • TextEncoder string→UTF-8 bytes, TextDecoder bytes→string; streaming decode ke liye {stream: true} use karo taaki multi-byte chars chunk boundaries pe corrupt na ho.
  • Blob ek immutable, MIME-typed binary object hai — slice() naya Blob banata hai, original untouched rehta hai; createObjectURL/revokeObjectURL pair yaad rakho (memory leak se bachne ke liye).
  • File Blob se inherit karta hai + name/lastModified add karta hai — usually input.files se milta hai.
  • FileReader async event-based API hai (onload/onerror/onprogress/onloadend) — readAsText/readAsArrayBuffer/readAsDataURL; sirf preview ke liye createObjectURL zyada efficient hai.

🎯 Interview Questions

  • ArrayBuffer aur TypedArray mein exact farak kya hai?
    Hint: ArrayBuffer sirf raw memory hai, koi method/type interpretation nahi; TypedArray us memory ko ek specific numeric format ke through "view" karta hai — data copy nahi hoti.
  • Ek hi ArrayBuffer par Uint8Array aur Uint16Array view banao — inka length alag kyun hoga?
    Hint: length = byteLength / BYTES_PER_ELEMENT; Uint8 ke liye 1, Uint16 ke liye 2 — same bytes, alag grouping.
  • DataView kab use karoge TypedArray ke bajaye?
    Hint: jab data heterogeneous ho (mixed field sizes/types within one buffer), jaise binary protocol headers — DataView per-offset explicit get/set deta hai, alignment force nahi karta.
  • TextDecoder ke stream:true option ka kya purpose hai?
    Hint: chunked/streamed binary data decode karte waqt multi-byte UTF-8 characters chunk boundary pe split ho sakte hain — stream:true incomplete trailing bytes ko internally buffer karke agli chunk se combine karta hai.
  • Blob "immutable" hai — iska matlab practically kya hai, aur slice() kaise kaam karta hai?
    Hint: Blob ka content kabhi in-place change nahi hota; slice() ek naya Blob instance return karta hai jo original data ke ek portion ko reference karta hai, koi mutation original pe nahi.
  • createObjectURL ke baad revokeObjectURL kyun call karna zaroori hai?
    Hint: createObjectURL internal browser memory mapping banata hai jo document lifetime tak rehti hai chahe blob reference kahin na ho — na revoke karne se memory leak hota hai, especially SPAs mein repeated large-file previews ke saath.
  • Image preview ke liye readAsDataURL better hai ya createObjectURL(file)? Kyun?
    Hint: createObjectURL synchronous, no encoding overhead, lightweight reference; readAsDataURL base64-encode karta hai jisse ~33% memory overhead aata hai aur async FileReader round-trip lagta hai — production mein createObjectURL preferred hai sirf preview ke liye.
