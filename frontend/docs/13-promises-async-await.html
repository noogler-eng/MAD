Promises, Async/Await

Ye chapter async JavaScript ka core hai — interviews mein sabse zyada poocha jaane wala topic. Hum callback hell se shuru karenge, phir Promise ka internal state machine root-level samjhenge, chaining/error-propagation dekhenge, Promise API ke sab combinators (all/allSettled/race/any), promisification, aur sabse important — microtask queue ka exact mechanism jo decide karta hai ki async code kis order mein chalta hai. Aakhir mein async/await, jo in sab promises ke upar syntactic sugar hai.

Callback hell — problem jo Promises solve karti hain

JavaScript single-threaded hai, lekin async operations (network request, timer, file read) ko block-nahi-karte hue handle karna hai. Traditional tareeka tha callbacks — ek function jo async operation complete hone par call hoga. Problem tab aati hai jab multiple async operations ek-doosre par depend karte hain — nested callbacks ek "pyramid of doom" ban jaate hain:

Callback hell example
loadScript('/step1.js', function(error1, script1) {  // step1 load hone ka wait, callback fire hoga
  if (error1) {                                     // agar step1 fail hua
    handleError(error1);                             // error handle karo aur ruk jaao
  } else {                                          // step1 success hua to
    loadScript('/step2.js', function(error2, script2) { // step2 shuru, phir se callback
      if (error2) {                                   // agar step2 fail hua
        handleError(error2);                           // error handle karo
      } else {                                        // step2 success
        loadScript('/step3.js', function(error3, script3) { // step3, nesting aur badh gayi
          if (error3) {                                 // error check phir se
            handleError(error3);                         // error path
          } else {                                      // finally sab load ho gaye
            console.log('sab scripts load ho gaye');  // yahaan tak pahunchne mein 3 levels nesting
          }
        });
      }
    });
  }
});

Har naya async step ek naya nesting level add karta hai — error handling repeat hoti hai, code right-ward "drift" karta hai, aur control-flow (loop/try-catch) likhna almost impossible ho jaata hai. Promises isi structural problem ko solve karte hain — nesting ki jagah flat chaining deke.

Promise internals — state machine root-level

Ek Promise object internally ek state machine hai jiske paas do internal (spec-internal, JS code se directly access nahi ho sakti) slots hote hain: [[PromiseState]] aur [[PromiseResult]]. State teen values le sakta hai:

  • pending — initial state, result abhi pata nahi.
  • fulfilled — operation successfully complete, ek value ke saath.
  • rejected — operation fail hua, ek error/reason ke saath.

pending se fulfilled ya rejected mein transition ko "settling" kehte hain. Ye transition executor function karta hai — wo function jo tum new Promise((resolve, reject) => {...}) mein pass karte ho. Constructor call hote hi executor synchronously, turant chal jaata hai (Promise object ka creation wait nahi karta).

Promise state machine — basic anatomy
const promise = new Promise(function(resolve, reject) { // executor: constructor ke andar hi turant chalta hai
  // resolve aur reject dono JS engine ke diye hue functions hain — hum inhe khud nahi banate
  setTimeout(function() {                          // async operation simulate: 1 second baad
    const success = true;                        // dummy condition — kya operation successful raha
    if (success) {                             // success case
      resolve("done!");                       // state: pending -> fulfilled, result = "done!"
    } else {                                   // failure case
      reject(new Error("kuch galat ho gaya")); // state: pending -> rejected, result = Error object
    }
  }, 1000);                                     // 1000ms delay — asynchronous, executor turant return ho jaata hai
});

// promise.[[PromiseState]] abhi "pending" hai (executor ke andar setTimeout abhi fire nahi hua)
// 1 second baad ye "fulfilled" ho jaayega, result "done!" ke saath
⚠️ Root rule: Promise sirf EK BAAR settle ho sakta hai

Ye state machine ka sabse important invariant hai — ek baar pending se fulfilled ya rejected mein transition ho gaya, to state permanently fix ho jaata hai. Agar executor resolve() call karne ke baad phir reject() ya dobaara resolve() call kare, to wo calls silently ignore ho jaati hain — koi error nahi throw hota, bas kuch nahi hota. Ye intentional spec design hai: ek baar result decide ho gaya (chahe success ho ya failure), wo result immutable hai. Isi wajah se Promises "future value ka reliable, tamper-proof container" hote hain — koi bhi consumer jo .then() attach karta hai, guaranteed hai ki result sirf ek baar milega, aur badlega nahi.

resolve(value) ka ek subtlety hai — agar value khud ek "thenable" (yaani jiske paas .then method hai) ho, to outer promise turant settle nahi hota; wo us inner thenable ke settle hone ka wait karta hai aur uska result adopt kar leta hai. Ye promise chains ko "flatten" karta hai — nested promises kabhi bhi promise-of-a-promise nahi bante.

.then/.catch/.finally — chaining ka root mechanism

.then(onFulfilled, onRejected) ek settled ya pending promise pe handlers register karta hai. Sabse important root-level fact: .then() hamesha ek NAYA promise return karta hai — original promise ko modify nahi karta. Ye naya promise settle hota hai handler ke return value ke basis pe:

  • Agar handler ek normal value return kare → naya promise usi value se fulfilled.
  • Agar handler koi error throw kare → naya promise us error se rejected.
  • Agar handler khud ek promise return kare → naya promise us returned promise ke settle hone tak wait karta hai aur uska state/result adopt karta hai.
.then returns a NEW promise — chaining works because of this
Promise.resolve(1)                          // ek turant-fulfilled promise, result = 1
  .then(function(result) {              // result = 1 yahaan aata hai
    console.log(result);                   // prints 1
    return result * 2;                    // return value = 2 -> naya promise fulfilled(2) banega
  })
  .then(function(result) {              // ye handler pichle .then() ke NAYE promise pe attached hai
    console.log(result);                   // prints 2
    return new Promise(function(resolve) { // ek naya promise return kiya (async chain ke liye)
      setTimeout(() => resolve(result * 10), 500); // 500ms baad resolve(20)
    });
  })
  .then(function(result) {              // ye chain outer promise ke settle hone ka wait karta hai
    console.log(result);                   // 500ms baad prints 20
  });

.catch(onRejected) ek syntactic shortcut hai .then(null, onRejected) ka — sirf rejection handle karta hai. .finally(fn) ek callback register karta hai jo chahe fulfill ho ya reject, hamesha chalta hai (fn ko result/error nahi milta — ye sirf cleanup ke liye hai, jaise loading spinner hide karna) — aur ye original result/error ko unchanged aage pass kar deta hai.

⚠️ Forgetting to `return` inside a .then — sabse common production bug

Agar tum ek .then() handler ke andar koi async operation start karte ho lekin uska returned promise return nahi karte, to chain us operation ka wait nahi karega — agla .then() turant chal jaayega, us operation ke complete hone se pehle:

BUG: missing return breaks the chain
fetch('/api/user')
  .then(response => {
    response.json();              // BUG: return missing! ye promise chain se disconnect ho gaya
  })
  .then(data => {
    console.log(data);              // data yahaan "undefined" hoga — .json() ka result kabhi wire nahi hua
  });

Root cause: .then() ke handler ka return value hi next promise ka fulfillment value/adoption-target decide karta hai. Return nahi kiya matlab implicit return undefined, aur agla handler undefined ke saath chalta hai — chahe andar koi promise pending ho ya ho hi rahi ho. Fix seedha hai: return response.json();

Error propagation through chains

Promise chains mein error handling ka model try/catch jaisa hi hai, bas async version. Jab kisi bhi .then() handler mein error throw hoti hai (ya promise reject hoti hai), control turant chain mein aage ke sab .then() ko skip karke agle .catch() tak "jump" karta hai — bilkul waise jaise synchronous try/catch mein exception nearest catch tak bubble karta hai.

Error propagation — skip karta hua nearest .catch tak
fetch('/api/data')                          // step 1: network request
  .then(response => {
    if (!response.ok) {              // fetch khud 404/500 pe reject NAHI karta — manually check
      throw new Error(`HTTP ${response.status}`); // throw yahaan chain ko reject state mein daal deta hai
    }
    return response.json();              // success path: JSON parse karke aage return
  })
  .then(data => {
    processData(data);                  // agar upar throw hua tha, ye handler SKIP ho jaata hai
  })
  .then(() => {
    console.log('done');              // ye bhi skip ho jaata hai agar error hua tha
  })
  .catch(error => {                    // error yahaan "land" karta hai — network fail YA HTTP error YA processData ka koi bug
    console.error('Failed:', error.message); // single catch, chain mein kahin bhi hua error yahaan aayega
  })
  .finally(() => {
    hideLoader();                    // chahe success ho ya fail, ye hamesha chalega
  });

Ye ek bahut important benefit hai callback-hell ke muqaable — ek hi centralised .catch() chain ke kisi bhi step mein hui error ko pakad leta hai, chahe wo network failure ho, manual throw, ya koi unrelated bug processing logic mein.

⚠️ Unhandled rejections

Agar ek promise reject hoti hai aur chain mein koi .catch() nahi hai jo use handle kare, to JS engine ise "unhandled rejection" maanta hai. Browser mein window pe unhandledrejection event fire hota hai (console mein warning dikhti hai), Node.js mein bhi similar event hota hai aur newer versions process ko crash bhi kar sakte hain. Engine ye detect karne ke liye microtask queue poori tarah drain hone ka wait karta hai (taaki late-attached .catch() ko bhi chance mile) — isliye ye detection turant nahi, thodi der baad hoti hai.

Promise.all / allSettled / race / any

Jab multiple promises parallel mein chalani hon (sequential await ki jagah), Promise API ke static combinator methods use hote hain. In sabka behavior settle hone ke conditions mein differ karta hai:

Promise.all vs allSettled — Q&A style comparison
// Q: 3 API calls parallel mein chalani hain, sabka result chahiye — agar EK bhi fail ho to poora operation fail treat karna hai
const urls = ['/api/user', '/api/posts', '/api/comments']; // teen endpoints

Promise.all(urls.map(url => fetch(url)))  // har url ke liye fetch, array of promises banaya
  .then(responses => {
    // A: sab 3 successful hue TABHI yahaan aayega — responses array SAME ORDER mein hai jo input tha
    console.log('sab successful:', responses);
  })
  .catch(error => {
    // A: FAIL-FAST behavior — jaise hi PEHLA promise reject hota hai, .all() TURANT reject ho jaata hai
    // baaki abhi-bhi-pending promises ka result IGNORE ho jaata hai (wo silently background mein chalte rehte hain)
    console.error('kam se kam ek fail hua:', error);
  });

// Q: mujhe HAR request ka result chahiye — chahe kuch fail bhi ho jaayein, poora operation abort nahi karna
Promise.allSettled(urls.map(url => fetch(url)))
  .then(results => {
    // A: allSettled KABHI reject nahi hota — sab promises settle (fulfill YA reject) hone ka WAIT karta hai
    results.forEach(result => {
      if (result.status === 'fulfilled') { // har result object mein status field hoti hai
        console.log('ok:', result.value);     // fulfilled -> .value mein result
      } else {
        console.log('fail:', result.reason);    // rejected -> .reason mein error
      }
    });
  });
MethodSettle kab hota haiFail behaviorUse-case
Promise.allSab fulfilled → fulfilled(array)Fail-fast: pehla reject turant poore ko reject kar deta haiSab results zaroori hain, ek bhi fail = poora invalid
Promise.allSettledSab settle (kisi bhi status) → hamesha fulfilledKabhi reject nahi hotaHar result chahiye, partial failure OK hai
Promise.raceJo bhi PEHLE settle ho (fulfill ya reject)Pehle settled promise ka outcome adopt karta haiTimeout pattern — jo pehle aaye: data ya timeout error
Promise.anyJo bhi PEHLE fulfill hoSab reject ho jaayein tabhi reject (AggregateError ke saath)Multiple mirrors/fallback sources — pehla success chahiye

Promisification of callback-based APIs

Purane Node.js-style APIs error-first callback pattern use karte hain: fn(args..., (err, result) => {}). "Promisify" karna matlab ek wrapper banana jo isi function ko Promise-returning banaye — taaki modern .then()/await ke saath use ho sake.

Generic promisify wrapper
function promisify(fn) {                        // fn: error-first callback style function
  return function(...args) {                  // naya function return — jitne bhi args aayein, capture karo
    return new Promise(function(resolve, reject) { // Promise mein wrap karke return
      function callback(err, result) {      // original API ko diya jaane wala callback
        if (err) {                          // error-first convention: pehla arg error hota hai
          reject(err);                     // error mila to Promise reject karo
        } else {
          resolve(result);                  // success to Promise resolve karo result ke saath
        }
      }

      args.push(callback);                // callback ko args list ke aakhir mein add karo (convention)
      fn.apply(this, args);              // original function ko sahi `this` ke saath call karo
    });
  };
}

// Usage: Node.js ka fs.readFile ko promisify karna
const readFilePromise = promisify(fs.readFile);  // naya promise-returning version
readFilePromise('/etc/hosts')
  .then(data => console.log(data));       // ab .then() chain use kar sakte hain

Production mein khud likhne ki bajaye Node.js ka built-in util.promisify use hota hai, jo yahi pattern implement karta hai (plus multi-value callback support via util.promisify.custom).

Microtask queue — sabse important root mechanism

Ye JS event loop ka wo hissa hai jo directly decide karta hai promise callbacks kab chalte hain. JS engine ke paas do alag internal queues hain:

  • Macrotask queue (task queue) — setTimeout, setInterval, UI events, I/O callbacks yahaan jaate hain.
  • Microtask queue — Promise .then/.catch/.finally handlers, queueMicrotask(), aur MutationObserver callbacks yahaan jaate hain.

Event loop ka rule simple lekin critical hai: har macrotask complete hone ke baad, agla macrotask uthaane se PEHLE, poori microtask queue empty hone tak drain ki jaati hai (agar koi microtask khud naye microtasks queue kare, wo bhi isi drain cycle mein chalte hain). Sirf jab microtask queue poori tarah khaali ho jaaye, tab engine agle macrotask ki taraf badhta hai (jisme rendering bhi ho sakta hai, browser mein).

Classic execution-order trace — A, D, C, B
console.log('A');                                    // (1) sync code — turant chalta hai, call stack pe

setTimeout(() => console.log('B'), 0);          // (2) callback MACROTASK queue mein jaata hai — abhi hi nahi chalta, 0ms bhi guaranteed nahi

Promise.resolve()                                 // (3) already-resolved promise banaya (sync)
  .then(() => console.log('C'));            // (4) .then callback MICROTASK queue mein jaata hai — sync execution turant nahi hota

console.log('D');                                    // (5) sync code — call stack abhi khaali nahi hua tha, ye turant chalta hai

// STEP-BY-STEP kya hota hai:
// i.   'A' print hota hai — synchronous, call stack pe direct execution
// ii.  setTimeout callback MACROTASK queue mein daala jaata hai (abhi execute NAHI hota)
// iii. Promise.resolve().then() ka callback MICROTASK queue mein daala jaata hai
// iv.  'D' print hota hai — abhi bhi call stack khaali nahi hua tha (sync code chal raha hai top-to-bottom)
// v.   ab call stack KHAALI ho gaya (poora sync script chal chuka) — event loop check karta hai: microtask queue mein kuch hai?
// vi.  HAAN — 'C' wala callback hai. Macrotask (setTimeout) ka wait NAHI kiya jaata, microtask ko priority milti hai
// vii. 'C' print hota hai, microtask queue ab khaali
// viii.ab engine agla MACROTASK uthata hai — setTimeout ka callback
// ix.  'B' print hota hai
//
// FINAL OUTPUT ORDER: A, D, C, B

Root reasoning: setTimeout(fn, 0) ka matlab "0ms baad chalao" nahi hai — matlab hai "sync code aur SAARI microtasks khatam hone ke baad, jab bhi agla macrotask cycle aaye, tab chalao". Isi liye microtasks (Promises) hamesha macrotasks (setTimeout) se pehle chalti hain, chahe donon "same time pe queue" hue lagte hon.

🧠 Senior Dev Note: microtask starvation

Agar ek microtask apne andar hi naya microtask queue karta rahe (jaise ek .then() chain jo recursively khud ko phir se .then() karta rahe), to event loop kabhi bhi agle macrotask (rendering included!) tak nahi pahunch payega — microtask queue kabhi khaali hi nahi hoti. Ye "microtask starvation" kehte hain, aur real production bug ban sakta hai jahan UI freeze ho jaata hai jabki call stack technically khaali hai (koi long-running sync loop nahi). Isliye recursive `.then()` chains ya recursive `queueMicrotask()` calls likhte waqt hamesha ek termination condition zaroor rakho.

async/await — sugar over promises

async function declare karne se do cheezein guarantee hoti hain: (1) function hamesha ek Promise return karta hai (agar tum ek plain value return karo, JS use automatically Promise.resolve(value) mein wrap kar deta hai); (2) uske andar await keyword use kar sakte ho.

await promise ka mechanism: function ka execution us line pe pause ho jaata hai (call stack se function nikal jaata hai — thread block NAHI hoti, baaki JS engine free rehta hai aur doosra kaam kar sakta hai), aur jab promise settle hoti hai (fulfilled ya rejected), execution resume hota hai — value ke saath (fulfilled) ya throw ke saath (rejected). Internally ye almost exactly waisa hi kaam karta hai jaise ek generator function promises ke saath drive ki jaaye — await ek "yield point" hai jahan control engine ko wapas mil jaata hai, aur jab promise settle hoti hai, engine us point se function ko resume karta hai (jo internally ek microtask ke through hi hota hai).

async/await — same logic, promise chain ke bina
async function loadUserData(userId) {          // async keyword: ye function hamesha Promise return karega
  try {                                            // try/catch normal sync code jaisa hi kaam karta hai yahaan
    const response = await fetch(`/api/users/${userId}`);
                                                    // await: function yahaan PAUSE hoti hai jab tak fetch ka promise settle na ho
    if (!response.ok) {                        // resume hone ke baad normal sync-jaisa code
      throw new Error(`HTTP ${response.status}`);       // throw yahaan — catch block ise pakdega (jaise sync throw)
    }

    const user = await response.json();          // ek aur await — dusra pause point, JSON parse hone tak
    const posts = await fetchPosts(user.id); // teesra await — user data ke baad related posts

    return { user, posts };                    // return value automatically Promise.resolve({user, posts}) ban jaata hai
  } catch (error) {                              // koi bhi awaited promise reject ho, ya koi throw ho — yahaan aayega
    console.error('load failed:', error);          // centralized error handling, promise chain ke .catch() jaisa
    throw error;                                    // re-throw: caller ko bhi pata chale ki fail hua (Promise reject hoga)
  }
}

// Caller side — async function bhi ek Promise hi hai, isliye .then/.catch YA await dono use ho sakte hain
loadUserData(42)
  .then(result => console.log(result))       // normal promise consumption bhi kaam karega
  .catch(err => console.error(err));

Sequential await calls automatically serial ho jaate hain — agar operations independent hain aur parallel chal sakti hain, unhe alag-alag start karke Promise.all ke saath await karna chahiye, warna galti se poora waterfall bana doge:

Serial (slow) vs Parallel (fast) await pattern
// SLOW: har await agla start hone se PEHLE poora complete hone ka wait karta hai — total time = sum of all
const user = await fetchUser();                // 200ms — poora wait ho ke tabhi agli line chalti hai
const posts = await fetchPosts();              // 300ms — independent hai user se, phir bhi sequential chal raha hai
const comments = await fetchComments();       // 150ms — total = 200+300+150 = 650ms

// FAST: teeno ek saath start karo (promises turant fire ho jaate hain, await sirf result ke liye)
const userPromise = fetchUser();              // call turant hota hai, promise object milta hai — await NAHI kiya abhi
const postsPromise = fetchPosts();            // ye bhi turant fire ho gaya, pehle wale ka wait nahi kiya
const commentsPromise = fetchComments();      // teeno ab parallel chal rahe hain

const [user, posts, comments] = await Promise.all(
  [userPromise, postsPromise, commentsPromise]  // sab results ka ek saath wait — total = max(200,300,150) = 300ms
);

Key Takeaways

  • Promise ek state machine hai — pending → fulfilled/rejected, aur ye transition sirf ek baar ho sakti hai (baad ke resolve/reject calls silently ignore hoti hain).
  • .then() hamesha ek naya promise return karta hai — chaining isi wajah se possible hai. Andar se return na kiya to chain "disconnect" ho jaata hai (sabse common production bug).
  • Error kisi bhi step pe throw/reject ho, wo aage ke .then() skip karke nearest .catch() tak jump karti hai.
  • Promise.all = fail-fast, sab chahiye; allSettled = kabhi reject nahi, har result chahiye; race = jo pehle settle ho; any = jo pehle fulfill ho.
  • Promisification purane error-first callback APIs ko modern promise-based interface deta hai.
  • Microtask queue (Promises) hamesha macrotask queue (setTimeout) se pehle drain hoti hai — har macrotask ke baad, agle macrotask se pehle poori microtask queue khaali ki jaati hai.
  • async/await promises ke upar syntactic sugar hai — await function ko pause karta hai (thread block kiye bina), aur try/catch normal sync errors jaisa hi async errors handle kar leta hai.
  • Independent async operations ko sequential await se serial mat banao — pehle sab start karo, phir Promise.all se ek saath await karo.

🎯 Interview Questions

  • Promise sirf ek baar kyun settle ho sakta hai — is design decision ka kya benefit hai?
    Hint: immutability guarantee — jo bhi consumer .then() attach kare, use hamesha ek hi reliable, tamper-proof result milega, race conditions se bacha jaata hai.
  • Ye code trace karo aur exact console output order batao: console.log('A'); setTimeout(()=>console.log('B'),0); Promise.resolve().then(()=>console.log('C')); console.log('D')
    Hint: sync code (A, D) pehle poora chalta hai, phir microtask queue (C) poori tarah drain hoti hai, tab jaake macrotask queue (B) uthai jaati hai. Answer: A, D, C, B.
  • .then() se naya promise kaise banta hai — agar handler ek value return kare vs error throw kare vs promise return kare, teeno cases mein kya hota hai?
    Hint: value → naya promise usi value se fulfilled; throw → rejected us error se; promise return → outer naya promise us returned promise ke settle hone tak wait karke uska state adopt karta hai.
  • Promise.all aur Promise.allSettled ka fail behavior kaise differ karta hai, aur kab kaunsa use karoge?
    Hint: all = fail-fast (ek reject = poora reject, baaki results discard); allSettled = har status ke saath wait karta hai, kabhi reject nahi hota — partial failures OK hon to allSettled.
  • async function ka return type kya hota hai agar tum ek plain non-promise value return karo?
    Hint: JS engine automatically use Promise.resolve(value) mein wrap kar deta hai — async function hamesha Promise return karta hai, chahe andar await ho ya na ho.
  • await ke time pe actual thread kya karti hai — kya JS engine block ho jaata hai?
    Hint: nahi, thread block nahi hoti. Function execution ek "pause point" pe suspend hota hai, call stack se hat jaata hai, aur engine baaki kaam (dusre callbacks, rendering) continue karta hai; jab promise settle hoti hai, function resume hota hai microtask ke through.
  • Unhandled promise rejection kya hota hai, aur engine ise "unhandled" kaise decide karta hai jab immediately hi conclusion nahi nikal sakta?
    Hint: engine microtask queue poora drain hone tak wait karta hai (taaki late .catch() attach hone ka chance mile), tab bhi agar koi handler nahi mila to unhandledrejection event fire hota hai.
  • Sequential await calls ko parallel kaise banaoge jab operations independent hon, aur kyun ye zaroori hai?
    Hint: pehle sab async calls ko bina await kiye start karo (promises variable mein store karo), phir Promise.all se ek saath await karo — total time serial-sum ki jagah max() ban jaata hai.
  • Microtask starvation kya hai aur ye production mein kaise problem create kar sakta hai?
    Hint: agar microtasks recursively naye microtasks queue karte rahen, event loop kabhi macrotask queue (jisme rendering bhi shamil hai) tak nahi pahunch payega — UI freeze ho sakti hai chahe call stack khaali ho.
