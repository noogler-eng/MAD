Attributes & Modifying DOM

Attributes vs Properties — root cause samjho

Ye do alag cheezein hain jo mostly ek jaisi dikhti hain, isliye confusion hoti hai. Attribute wo hai jo HTML source mein likha hai — plain text, hamesha string. Property wo hai jo DOM object (JavaScript object) pe live hai — kisi bhi type ka ho sakta hai (boolean, object, number). Jab browser HTML parse karta hai, wo ek DOM node object banata hai, aur standard attributes ke liye corresponding property automatically create kar deta hai (initial value ke saath). Iske baad wo do independent cheezein hain jo kabhi-kabhi ek-doosre se sync hoti hain, kabhi nahi.

DOM node ek plain JS object hai — kuch bhi attach kar sakte ho
// document.body ek DOM element object hai — normal object ki tarah custom property bhi le sakta hai
document.body.myData = {          // koi bhi naya property name assign karo — browser rokta nahi
  name: 'Caesar',          // arbitrary nested value bhi chal jaayega
  title: 'Imperator'
};

alert(document.body.myData.title); // "Imperator" — pura JS object hai, sirf string nahi

// methods bhi assign kar sakte ho — 'this' andar hamesha wo element hoga jispe call hua
document.body.sayTagName = function() {
  alert(this.tagName);          // this = document.body, tagName built-in property hai
};

document.body.sayTagName();              // "BODY" — tagName hamesha UPPERCASE hota hai HTML documents mein
Standard vs non-standard attribute → property mapping
<!-- HTML: -->
<body id="test" something="non-standard">

script:
alert(document.body.id);          // "test" — id STANDARD attribute hai, isliye matching property mil gayi
alert(document.body.something);   // undefined — non-standard hai, browser ne koi property banayi hi nahi

// "standard" bhi element-specific hota hai — 'type' input ke liye standard hai, body ke liye nahi:
// <input id="input" type="text">   input.type === "text"  (standard, property mili)
// <body type="...">                body.type === undefined (body pe 'type' standard nahi)

Root cause: browser ke andar HTML spec ne har element type ke liye ek fixed set of "known" attributes define kiya hai. Parser jab element node banata hai, wo sirf usi list ke against check karta hai. Agar attribute list mein hai to matching property (sahi type ke saath — boolean, string, etc.) create hoti hai. Agar list mein nahi hai (chahe wo kisi doosre element pe standard ho), koi property nahi banti — attribute sirf raw HTML text ke roop mein reh jaata hai, jisse sirf getAttribute/setAttribute se access kar sakte ho.

Non-standard attributes ke liye universal methods
// ye 4 methods HAR attribute (standard ho ya na ho) ke liye kaam karte hain — property se independent
document.body.hasAttribute('something');              // true — check karta hai attribute exist karta hai ya nahi
document.body.getAttribute('something');           // "non-standard" — hamesha STRING return karta hai
document.body.setAttribute('something', 'new');    // attribute ki value badal do (ya naya attribute bana do)
document.body.removeAttribute('something');       // attribute HTML se hata do

// document.body.attributes — sabhi attributes ka ek iterable/array-like collection (Attr objects)
for (let attr of document.body.attributes) {
  alert(`${attr.name} = ${attr.value}`);  // har Attr object ka .name aur .value hota hai
}

// attributes hamesha CASE-INSENSITIVE hain (HTML spec ki wajah se), properties CASE-SENSITIVE hain

Attribute → Property sync mechanics — ye gotcha bahut common hai

Standard attributes aur unki matching property usually dono directions mein sync hoti hain — attribute badlo to property bhi badal jaati hai, aur ulta bhi. Lekin ye guarantee nahi hai har property ke liye — root mechanism ye hai ki har property ka apna getter/setter hota hai jo internally decide karta hai ki attribute se sync karna hai ya nahi.

Normal bidirectional sync (id attribute)
let input = document.querySelector('input');

// attribute → property direction
input.setAttribute('id', 'id');   // attribute badla
alert(input.id);            // "id" — property automatically update ho gayi

// property → attribute direction
input.id = 'newId';       // property badli
alert(input.getAttribute('id')); // "newId" — attribute bhi automatically update ho gaya
🧠 Senior Dev Note: value attribute ka one-way sync gotcha

Ye sabse common real-world form bug ka root cause hai. <input> ke value property ka sync sirf ek direction mein kaam karta hai: attribute → property haan, lekin property → attribute nahi. Iska matlab: agar user input mein type karta hai ya tum JS se input.value = "..." set karte ho, to getAttribute('value') hamesha wahi original HTML value return karega jo page load ke time thi. Ye browser ka intentional design hai — taaki "original/default value" recover ki ja sake (jaise form reset ke liye), current live value se independent. Bahut developers is behaviour ko bug samajhte hain jab woh getAttribute('value') se current form state padhne ki koshish karte hain aur stale data milta hai — sahi tareeka hamesha input.value (property) use karna hai current state ke liye, aur getAttribute('value') sirf original default ke liye.

value ka one-way sync — demo
let input = document.querySelector('input');

// attribute → property: ye direction kaam karta hai
input.setAttribute('value', 'text');
alert(input.value);               // "text" — property update ho gayi (starting sync hui)

// property → attribute: ye direction NAHI kaam karta (value ke liye special case)
input.value = 'newValue';   // property badal di (jaise user ne type kiya ho)
alert(input.getAttribute('value')); // "text" — UNCHANGED! attribute abhi bhi purani (original) value dikhata hai

Aur ek dimension: properties typed hote hain, attributes hamesha string. Checkbox ka checked attribute empty-string hoke bhi property mein true/ false boolean deta hai. style attribute ek string hai lekin elem.style property ek poora CSSStyleDeclaration object hai. Aur href jaisi URL properties resolved (full, absolute) URL return karti hain jabki attribute exact wahi text deta hai jo HTML mein likha tha (relative ho sakta hai).

Typed properties vs string attributes
<!-- <input id="input" type="checkbox" checked> -->
alert(input.getAttribute('checked'));  // "" — HTML mein sirf attribute present tha, value empty string
alert(input.checked);              // true — property BOOLEAN type mein normalize ho gayi

<!-- <a id="a" href="#hello">link</a> -->
alert(a.getAttribute('href'));      // "#hello" — exactly jo HTML mein likha tha (relative)
alert(a.href);                  // "http://site.com/page#hello" — property RESOLVED absolute URL deti hai

Non-standard attributes — HTML se JS/CSS tak data pass karna

Custom (non-standard) attributes historically use hote the arbitrary data HTML mein embed karne ke liye — jaise ek attribute jo batata ho ek div mein user ka konsa field dikhana hai, ya CSS selector ke through element ki "state" style karne ke liye:

Custom attribute se data-driven rendering
<!-- HTML: kaunsa field dikhana hai wo attribute mein hi likha hai -->
<div show-info="name"></div>
<div show-info="age"></div>

script:
let user = { name: "Pete", age: 25 };  // jo data render karna hai

// attribute selector [show-info] se sabhi matching divs dhoondo
for(let div of document.querySelectorAll('[show-info]')) {
  let field = div.getAttribute('show-info');  // is div ko konsa field dikhana hai
  div.innerHTML = user[field];       // user object se dynamic property lookup karke render kar do
}

Problem ye hai ki future HTML spec versions naye standard attributes add kar sakte hain, aur agar tumhara custom attribute name kabhi standard ban jaaye, unexpected behaviour aa sakta hai. Isi risk ko avoid karne ke liye HTML5 ne data-* namespace reserve kiya — koi bhi data- se shuru hone wala attribute guaranteed hamesha custom rahega, aur spec kabhi usme conflict nahi karegi.

data-* attributes aur dataset API

data-* attributes DOM node ki dataset property ke through accessible hote hain — jo ek convenient object hai. Multiword attribute names (dash-separated) automatically camelCase mein convert ho jaate hain.

dataset — read aur write dono directions
<!-- HTML: -->
<body data-about="Elephants">

script:
alert(document.body.dataset.about);  // "Elephants" — data-about → dataset.about

<!-- multiword attribute: data-order-state -->
<div id="order" data-order-state="new"></div>

script:
alert(order.dataset.orderState);  // "new" — dash-case automatically camelCase ban jaata hai

order.dataset.orderState = "pending";  // dataset property likho — underlying HTML attribute bhi update ho jaata hai
// upar wale se HTML ban jaata hai: <div id="order" data-order-state="pending">

Ye pattern CSS ke saath bhi seamlessly kaam karta hai — kyunki underlying attribute normal HTML attribute hi hai, CSS selectors ([data-order-state="pending"]) usse directly target kar sakte hain, aur JS dataset se readable/writable API milta hai — dono worlds ke liye best of both.

Creating elements — createElement aur createTextNode

Naya DOM node banane ke liye do primary factory methods hain, dono document object pe. Zaroori baat: dono sirf node create karte hain — jab tak tum explicitly insert nahi karte, wo tree mein kahin bhi nahi dikhte (memory mein floating rehte hain).

createElement + createTextNode
// document.createElement(tag) — ek naya ELEMENT node banata hai, tree se abhi disconnected
let div = document.createElement('div');  // tag name pass karo — case-insensitive hota hai

// document.createTextNode(text) — ek naya TEXT node banata hai (koi tags nahi, sirf raw text)
let textNode = document.createTextNode('Here I am');

// dono abhi kahin bhi visible nahi — appendChild/append jaisa insertion method chahiye

Practice mein createTextNode rarely direct use hota hai kyunki append/ textContent jaise modern methods automatically string ko safe text node mein convert kar dete hain (age dekhenge).

Inserting nodes — modern insertion methods

Naye elements ko tree mein sahi jagah daalne ke liye 5 modern methods hain, jo koi bhi node ya plain string (jo automatically text node bana di jaati hai) accept karte hain — multiple arguments bhi ek saath le sakte hain:

  • node.append(...nodes) — node ke end mein insert karo (last child ke baad)
  • node.prepend(...nodes) — node ke start mein insert karo (first child se pehle)
  • node.before(...nodes) — node se pehle, uske sibling ke roop mein insert karo
  • node.after(...nodes) — node ke baad, uske sibling ke roop mein insert karo
  • node.replaceWith(...nodes) — node ki jagah naye nodes se replace kar do
Modern insertion methods — sab ek saath
// maan lo <ol id="ol"><li>0</li><li>1</li><li>2</li></ol> page mein hai
let ol = document.getElementById('ol');

ol.before('before');          // string 'before' → text node ban ke <ol> se PEHLE (sibling) insert hui
ol.after('after');            // string 'after' → <ol> ke BAAD (sibling) insert hui

let liFirst = document.createElement('li');  // naya <li> element banao
liFirst.innerHTML = 'prepend';       // uska content set karo
ol.prepend(liFirst);          // ol ke CHILDREN list ke SHURU mein daalo (first child se pehle)

let liLast = document.createElement('li');
liLast.innerHTML = 'append';
ol.append(liLast);            // ol ke CHILDREN list ke END mein daalo (last child ke baad)

// result DOM order: "before", <ol>[prepend, 0, 1, 2, append]</ol>, "after"

Ye legacy method appendChild se strictly better hai — sirf ek node lene ki jagah multiple nodes/strings ek saath accept karta hai, aur strings ko automatically escape kiya jaata hai (koi HTML injection risk nahi, unlike innerHTML +=).

insertAdjacentHTML — string se direct HTML insert karna

Jab tumhare paas already-formed HTML string hai (jaise server se aaya template) aur node-by-node create karna overkill lagta hai, insertAdjacentHTML(where, html) best option hai — innerHTML += ki tarah nahi ye poore element ko re-parse nahi karta, sirf naya HTML parse karke sahi jagah insert karta hai (existing children/event listeners safe rehte hain).

insertAdjacentHTML ke 4 positions
// where ke 4 valid values hain — element ke relative:
// "beforebegin" → element se PEHLE (sibling)
// "afterbegin"  → element ke ANDAR, first child se pehle
// "beforeend"   → element ke ANDAR, last child ke baad
// "afterend"    → element ke BAAD (sibling)

div.insertAdjacentHTML('beforebegin', '<p>Hello</p>');  // div se pehle naya <p> sibling insert ho gaya
div.insertAdjacentHTML('afterend', '<p>Bye</p>');     // div ke baad naya <p> sibling insert ho gaya

// related variants — same 4 positions, alag input type:
// div.insertAdjacentText(where, text)    → plain text insert karo (auto-escaped)
// div.insertAdjacentElement(where, elem) → ek already-existing element node insert karo
// in dono ka use rare hai — insertAdjacentHTML sabse zyada use hota hai
⚠️ Layout thrashing: loop ke andar repeated DOM read+write

Agar tum ek loop mein baar-baar DOM ko likhte ho (append/insertAdjacentHTML) aur beech-beech mein padhte bhi ho (jaise offsetHeight, getBoundingClientRect()), to browser ko har read se pehle pending layout changes ko force-flush karna padta hai — isse ek hi frame mein dozens of synchronous reflows trigger ho sakte hain ("layout thrashing"). Fix: pehle saare writes karo (ya DocumentFragment use karo — neeche dekho), phir saare reads ek saath karo — write-then-read ko interleave mat karo.

DocumentFragment — batch insertion ka correct tareeka

Jab tumhe loop mein multiple nodes insert karne hain, naive approach hai har iteration mein directly parent.appendChild(node) call karna — lekin ye har baar live DOM ko touch karta hai, jisse browser potentially har call pe reflow/re-render trigger kar sakta hai (particularly agar beech mein koi layout read ho). DocumentFragment ek special lightweight container node hai jo tree ka hissa nahi hota — usme jitne bhi children daalo, wo sab off-DOM rehte hain. Jab fragment ko finally parent mein insert karte ho, uske saare children ek hi single DOM operation mein move ho jaate hain (fragment khud "blend in" ho jaata hai, khud insert nahi hota) — result: ek hi reflow, N nahi.

DocumentFragment — N appends ki jagah 1 reflow
function getListContent() {
  let fragment = new DocumentFragment();  // off-DOM lightweight container banao

  for (let i = 1; i <= 3; i++) {
    let li = document.createElement('li');  // naya <li> banao
    li.append(i);                     // number ko andar text content ki tarah daalo (auto text-node)
    fragment.append(li);               // live DOM ko touch nahi karta — sirf fragment ke andar jud raha hai
  }

  return fragment;                    // poora fragment return karo, individual nodes nahi
}

ul.append(getListContent());  // ek hi call — fragment ke 3 <li> children ek saath ul mein move ho jaate hain, fragment khud gayab
🧠 Senior Dev Note: fragment kab zaroori hai, kab nahi

Modern spread-syntax methods (parent.append(...arrayOfNodes)) internally already batch insertion karte hain — ek hi call mein multiple nodes single reflow ke saath insert ho jaate hain, isliye chhote cases mein explicit DocumentFragment zaroori nahi. Fragment ka real use-case hai jab tumhare paas ek function hai jo nodes generate karta hai aur unhe ek unit ke roop mein return karna hai (jaise upar wala getListContent()) — fragment ek clean "bundle of nodes" abstraction deta hai jo caller ko internal loop count se decouple karta hai. Bade lists (100s of rows) ke liye ye pattern still relevant hai kyunki naive for loop mein parent.appendChild(node) repeat karna — especially agar beech mein koi layout-triggering read ho — multiple forced reflows create kar sakta hai.

Removing aur cloning nodes

Node hatane ka modern tareeka simple hai — legacy parentElem.removeChild(node) ki zaroorat nahi:

remove() aur cloneNode()
setTimeout(() => div.remove(), 1000);
// node.remove() — parent ki zaroorat nahi bataani, khud apne aap ko tree se hata leta hai

// IMPORTANT: agar insertion methods (append/before/after) ek node pe call karte ho jo pehle se
// kahin aur DOM mein attached hai, wo automatically OLD location se hata ke NAYI jagah move ho jaata hai —
// explicit remove() call karne ki zaroorat NAHI (ek node ek hi jagah exist kar sakta hai)

// cloneNode(true) — DEEP clone: saare attributes + saare descendant children copy hote hain
let div2 = div.cloneNode(true);
div2.querySelector('strong').innerHTML = 'Bye there!';  // clone independent hai, original affect nahi hota
div.after(div2);  // clone ko original ke baad insert kar do

// cloneNode(false) — SHALLOW clone: sirf element khud, children copy NAHI hote

Styles & Classes — className, classList, style, getComputedStyle

Element ki CSS class access karne ke do tareeke hain — className jo poore class-string ko ek single string ki tarah treat karta hai (isliye replace risky hai), aur classList jo individual class names manage karne ke liye special object hai (add/remove/toggle without touching baaki classes).

className vs classList
<!-- <body class="main page"> -->

alert(document.body.className);  // "main page" — poora string, ek hi property

// className = "..." assign karna SAARI existing classes OVERWRITE kar deta hai — dhyan se!
// document.body.className = "new-class"; // yahan 'main' aur 'page' dono gayab ho jaate

// classList individual classes ke saath surgical operations deta hai:
document.body.classList.add('article');     // sirf ek naya class add karta hai, baaki untouched
alert(document.body.className);  // "main page article" — dekh sakte ho ki original classes safe hain

// classList iterable hai — for-of se loop kar sakte ho:
for (let name of document.body.classList) {
  alert(name);  // "main", phir "page", phir "article"
}
classList ke 4 core methods
elem.classList.add("active");       // class add karo — agar already hai to no-op (duplicate nahi banega)
elem.classList.remove("active");    // class hatao — agar nahi hai to no-op (error nahi)
elem.classList.toggle("active");    // agar hai to remove, agar nahi hai to add — ek hi call mein switch
elem.classList.contains("active");  // true/false — check karo class present hai ya nahi

// forced toggle: ek boolean condition ke hisaab se explicitly add/remove karna hai (common UI pattern)
elem.classList.toggle("active", someCondition);  // 2nd arg true→force add, false→force remove

Manually className string ko concatenate/split/regex karke class manage karna (elem.className += ' active') technically kaam karta hai lekin fragile hai — duplicate class names, extra spaces, aur "already present hai kya" check karne ke liye manual string parsing chahiye hoti. classList ye sab internally handle karta hai, isliye production code mein hamesha classList preferred hai.

elem.style — sirf INLINE styles ka object

elem.style HTML ke style attribute ka JS-object equivalent hai. Multi-word CSS properties (jinme dash hota hai) camelCase mein likhi jaati hain:

CSS property → JS style property naming
// CSS dash-case               → JS camelCase
// background-color            → elem.style.backgroundColor
// z-index                     → elem.style.zIndex
// border-left-width           → elem.style.borderLeftWidth

document.body.style.backgroundColor = 'green';  // directly is element ke inline style attribute mein likh diya

// vendor-prefixed properties bhi wahi convention follow karte hain:
button.style.MozBorderRadius = '5px';   // -moz-border-radius
button.style.WebkitBorderRadius = '5px';  // -webkit-border-radius
Style reset: empty string, delete NAHI
document.body.style.display = "none";  // element hide kar do (display: none inline style set hua)

setTimeout(() => document.body.style.display = "", 1000);
// EMPTY STRING assign karo remove karne ke liye — CSS engine ko default/stylesheet value use karne deta hai

// alternative: removeProperty() explicit method — same effect, alag syntax:
document.body.style.background = 'red';
setTimeout(() => document.body.style.removeProperty('background'), 1000);

delete elem.style.display jaisa syntax kaam nahi karta kyunki style ek special CSSStyleDeclaration object hai jo getter/setter ke through kaam karta hai — normal object delete semantics apply nahi hoti.

cssText — multiple styles ek saath (LEKIN replace karta hai)
div.style.cssText = `color: red !important;
  background-color: yellow;
  width: 100px;
  text-align: center;
`;
// IMPORTANT: cssText SAARE existing inline styles ko REPLACE karta hai (add nahi karta) —
// agar div pe pehle se koi aur inline style thi jo yahan list nahi ki, wo GAYAB ho jaayegi
// use case: jab tumhe pura style block ek hi baar mein set karna ho (template se, computed string se)
⚠️ Numeric values bina CSS unit ke silently ignore hote hain

Style properties ko plain number assign karna kaam nahi karta — CSS ko hamesha ek unit chahiye (px, %, em, etc.), aur agar missing hai to browser assignment ko silently ignore kar deta hai (no error thrown):

CSS unit mandatory hai
// galat: bina unit ke
document.body.style.margin = 20;       // number 20 pass kiya — INVALID CSS value
alert(document.body.style.margin);  // '' — empty! assignment silently REJECT ho gayi, koi error nahi

// sahi: unit ke saath string
document.body.style.margin = '20px';   // px unit explicitly diya
alert(document.body.style.margin);  // '20px' — set ho gaya
alert(document.body.style.marginTop);  // '20px' — shorthand 'margin' set karne se longhand properties bhi auto-populate hoti hain

getComputedStyle — resolved styles, sirf inline nahi

elem.style ek fundamental limitation ke saath aata hai: ye sirf inline style="..." attribute dekhta hai — kisi bhi <style> block ya external stylesheet se aayi CSS rules usme reflect nahi hoti, chahe wo actually element pe apply ho rahi ho. Actual "final rendered" style value jaanne ke liye getComputedStyle(elem) use karna padta hai — ye browser se poochta hai "sab CSS rules (stylesheet + inline + browser default) apply karne ke baad is property ki final resolved value kya hai".

getComputedStyle — stylesheet-applied values bhi dikhta hai
<style> body { color: red; margin: 5px } </style>

script:
// getComputedStyle(element, pseudo) — 2nd arg optional (jaise "::before")
let computedStyle = getComputedStyle(document.body);

alert(computedStyle.marginTop);  // "5px" — <style> block se aaya, INLINE style mein kahin nahi hai ye
alert(computedStyle.color);      // "rgb(255, 0, 0)" — RESOLVED format mein, "red" keyword nahi

// document.body.style.marginTop yahan "" hota — kyunki elem.style sirf INLINE dekhta, stylesheet nahi

Zaroori nuance: naam "computed" style hai, lekin actual return value resolved value hoti hai (jaise geometry properties px mein normalize ho jaati hain, colors rgb() format mein). Return object read-only hai — isse direct assign nahi kar sakte.

🧠 Senior Dev Note: getComputedStyle bhi ek layout-read hai

getComputedStyle internally browser ko force karta hai ki wo pending style recalculations ko turant flush kare (jaise offsetHeight ya getBoundingClientRect() bhi karte hain) — isliye ye bhi layout thrashing ka source ban sakta hai agar DOM writes ke beech mein interleave kiya jaaye. Best practice: agar multiple elements ke computed styles chahiye, pehle saare DOM writes complete karo, phir ek batch mein saare reads karo — kabhi write→read→write→read pattern loop mein mat chalao.

Key Takeaways

  • Attribute = HTML source ka raw text (hamesha string). Property = DOM object ki live value (typed). Standard attributes ke liye dono usually sync hote hain, non-standard ke liye sirf attribute exist karta hai.
  • value property ka sync sirf attribute→property direction mein kaam karta hai — getAttribute('value') hamesha original HTML default deta hai, current form state nahi.
  • Non-standard attributes ke liye getAttribute/setAttribute/hasAttribute/removeAttribute use karo; custom data ke liye data-* + dataset preferred hai (future-proof, dash-case auto camelCase).
  • Node banane ke liye createElement/createTextNode; insert karne ke liye modern methods append/prepend/before/after/replaceWith — multiple args accept karte hain, strings auto-escape hoti hain.
  • insertAdjacentHTML(where, html) string-based HTML insert karne ka safe, non-destructive tareeka hai (existing DOM/listeners intact rehte hain).
  • DocumentFragment loop mein multiple nodes ko off-DOM batch karta hai — final insertion ek hi reflow trigger karta hai, N nahi.
  • classList (add/remove/toggle/contains) individual classes surgically manage karta hai; className poora string replace karta hai — risky manual concatenation avoid karo.
  • elem.style sirf inline styles dekhta hai; getComputedStyle(elem) resolved final value deta hai (stylesheet + inline + defaults sab combine karke) — dono hi layout-forcing reads hain, batch karo.

🎯 Interview Questions

  • Attribute aur property mein fundamental farak kya hai, aur ye kab diverge (out-of-sync) ho sakte hain?
    Hint: attribute = HTML source string, property = typed DOM object value; standard attributes usually bidirectionally sync hote hain lekin har property ka apna getter/setter hai jo decide karta hai — value jaise cases mein sync sirf ek direction mein hota hai.
  • Ek form ka current input value padhne ke liye getAttribute('value') use karna kyun galat hai?
    Hint: value attribute→property sync sirf ek-baar (parse time) ya explicit setAttribute call pe hota hai — user typing ya .value = assignment attribute ko update nahi karta, isliye stale/original default milta hai.
  • data-* attributes kyun banaye gaye, aur dataset kaise naming convert karta hai?
    Hint: future HTML spec collisions avoid karne ke liye reserved namespace; multiword dash-case attributes camelCase mein dataset property banti hain (data-order-state → dataset.orderState).
  • Loop mein N baar appendChild call karne se kya problem hoti hai, aur DocumentFragment kaise fix karta hai?
    Hint: har call live DOM ko touch karta hai jo potential reflow trigger kar sakta hai (especially agar beech mein layout read ho); fragment sabhi nodes ko off-DOM collect karta hai, phir ek single insertion operation mein sab move hote hain — ek hi reflow.
  • classList vs manual className string manipulation — production code mein classList kyun preferred hai?
    Hint: classList duplicate-check, whitespace handling, aur individual add/remove/toggle/contains internally handle karta hai; className manual concatenation fragile hai (duplicate classes, extra spaces, poori string overwrite ka risk).
  • elem.style.margin aur getComputedStyle(elem).margin mein farak batao.
    Hint: elem.style sirf INLINE style attribute dekhta hai; getComputedStyle sabhi applicable CSS rules (stylesheet + inline + UA defaults) combine karke final resolved value deta hai, aur ye read-only hai.
  • insertAdjacentHTML, innerHTML += string ke comparison mein kyun better hai?
    Hint: innerHTML += poore element ko re-parse karta hai (existing children destroy-recreate hote hain, event listeners aur input state loss ho sakta hai); insertAdjacentHTML sirf naya HTML parse karke specific position pe insert karta hai, existing content untouched rehta hai.
