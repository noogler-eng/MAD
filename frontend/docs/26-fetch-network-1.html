Fetch & Network I

fetch() aaj-kal har network request ka default tareeka hai — lekin uske andar ek two-stage promise resolution chhupa hai jo bahut logon ko surprise karta hai: promise headers aane par hi resolve ho jaata hai, body abhi bhi stream ho rahi hoti hai. Is chapter mein hum fetch ke poore surface area ko root-level samjhenge — request/response lifecycle, FormData se file upload, download progress track karna (bina kisi native progress event ke), AbortController se cancellation, aur CORS ka poora preflight mechanism.

fetch() basics aur two-stage promise — root gotcha

fetch(url, options) ek promise return karta hai. Yahan sabse important root-level fact ye hai: ye promise tab resolve hota hai jab server ke response HEADERS aa jaate hain — poora response body download hone ka wait nahi karta. Body abhi bhi network se stream ho rahi ho sakti hai (bade JSON payload, large files). Isliye body ko access karne ke liye ek second async step chahiye hota hai — response.json(), response.text(), waghera — jo khud bhi ek promise return karte hain.

fetch — two-stage resolution
async function loadCommits() {                        // async function taaki await use kar sakein
  // Stage 1: promise resolve hote hi hamare paas Response object hai —
  // isme status, headers already available hain, LEKIN body abhi nahi aaya
  let response = await fetch('https://api.github.com/repos/javascript-tutorial/en.javascript.info/commits');

  // yahan tak sirf headers guaranteed hain — status check yahin karna sahi hai
  console.log(response.status);              // e.g. 200 — HTTP status code
  console.log(response.headers.get('Content-Type')); // header Map-like interface se read

  // Stage 2: body ka full download + parse — ye ek ALAG await hai,
  // isliye is line tak execution ruk jaayega jab tak poora body na aa jaaye
  let commits = await response.json();          // json() body-stream ko poora consume karke parse karta hai

  console.log(commits[0].author.login); // ab data available hai, first commit ka author print
}
⚠️ fetch() 404/500 pe REJECT nahi karta

Ye sabse common production gotcha hai: fetch() ka promise sirf network failure pe reject hota hai — DNS fail ho jaaye, server unreachable ho, CORS block ho jaaye. Agar server valid HTTP response deta hai (chahe status 404 ho ya 500), to promise successfully resolve hota hai — kyunki technically ek response mila hai, network level pe kuch galat nahi hua. Isliye status check karna tumhari responsibility hai — response.ok (true jab status 200-299 ho) ya response.status khud dekho. Agar ye check bhool gaye, to try/catch se 404 wagera silently pass ho jaayenge aur tum response.json() ko ek error page ka HTML parse karwa doge — jo alag hi confusing error dega.

response.ok check — mandatory pattern
let response = await fetch('/api/user/999');  // maan lo user 999 exist nahi karta

if (response.ok) {                          // ok = true sirf 200-299 range ke liye
  let user = await response.json();       // safe hai, hume pata hai valid JSON aayega
} else {
  // server ne 404 diya — ye promise reject NAHI hua, isliye else branch mein aaye
  console.error(`HTTP-Error: ` + response.status); // yahan status code se apna error handling karo
}

Response body methods — json/text/blob/formData

Response body ko padhne ke liye multiple promise-based methods hain — sab ek hi underlying ReadableStream ko consume karte hain, isliye sirf ek hi method ek response pe call ho sakta hai. Dusri baar call karoge to error milega ("body stream already read").

Response body methods overview
let response = await fetch('/data');

// in paanchon mein se sirf EK use karo — har ek body stream ko fully consume karta hai
await response.text();        // plain text/HTML string ke liye
await response.json();        // JSON.parse() internally chalake JS object return
await response.blob();        // binary Blob — images, files, ArrayBuffer wrap kiya hua
await response.formData();    // multipart/form-data response ko FormData object mein parse
await response.arrayBuffer(); // lowest-level raw binary — jab custom byte parsing karni ho

// response.body khud ek ReadableStream hai — isse manually chunk-by-chunk padh sakte ho
// (progress tracking section mein isko detail mein dekhenge)

POST request aur JSON body bhejna

POST with JSON body
let user = { name: 'John', surname: 'Smith' };   // plain JS object jo backend ko bhejna hai

let response = await fetch('/article/fetch/post/user', {
  method: 'POST',                            // default GET hota hai, isliye method explicitly dena
  headers: {
    'Content-Type': 'application/json;charset=utf-8' // server ko batao body JSON hai
  },
  body: JSON.stringify(user)                // body ALWAYS string/Blob/FormData/BufferSource hona chahiye — object nahi
});

let result = await response.json();              // server ka JSON response parse karo

FormData — multipart form submission aur file upload

FormData HTML form data ko represent karta hai, aur network layer isse hamesha Content-Type: multipart/form-data encoding mein bhejta hai — ye encoding hi files bhejne ko support karti hai (JSON string mein binary file nahi ja sakti, isliye multipart chahiye).

FormData constructor + methods
// existing <form> element se auto-capture karke bana sakte ho
let formData = new FormData(formElem);   // formElem ke saare input fields automatically add ho jaate hain

// ya khali banake manually fields add karo
let fd = new FormData();              // empty FormData instance

fd.append('firstName', 'John');       // naya field add karo — same name doubara append ho to DONO reh jaate hain
fd.set('firstName', 'Jane');          // set() same name ke saare fields hata ke ek naya daal deta hai

console.log(fd.get('firstName'));      // 'Jane' — ek value read karo
console.log(fd.has('firstName'));      // true — field exist karta hai ya nahi
fd.delete('firstName');             // field completely hata do
File upload via FormData
let formData = new FormData();                        // naya empty FormData

formData.append("firstName", "John");            // simple text field
formData.append("image", imageBlob, "image.png"); // 3rd arg = filename, imageBlob ek Blob/File object hai

await fetch('/upload', {
  method: 'POST',
  body: formData                              // Content-Type header MANUALLY mat set karo
});
// browser khud Content-Type: multipart/form-data; boundary=... set karta hai —
// boundary ek random string hai jo fields ko separate karti hai, hume nahi pata hota isliye
// header manually set karna GALAT hai, ye browser ka kaam hai
🧠 Senior Dev Note: Content-Type manually mat lagao

FormData body ke saath Content-Type header khud set karna sabse common mistake hai. Multipart encoding ek unique boundary string use karti hai fields ko separate karne ke liye (e.g. boundary=----WebKitFormBoundary7MA4YWx...) jo browser runtime pe generate karta hai. Agar tum khud Content-Type: multipart/form-data set karoge bina boundary ke, server body ko parse hi nahi kar payega. Isliye jab bhi body: formData ho, headers mein Content-Type chhod do — browser ko khud set karne do.

Download progress track karna — response.body ka ReadableStream

XHR (XMLHttpRequest) mein ek native progress event hota hai, lekin fetch ke paas ye nahi hai — root reason: fetch design se low-level stream-based API hai, aur progress tracking ka concern deliberately body-consumption layer pe chhod diya gaya hai. Trick ye hai ki response.json() jaisa convenience method use karne ki jagah, response.body (jo khud ek ReadableStream hai) ko manually getReader() se chunk-by-chunk padho.

Download progress loop
let response = await fetch('https://example.com/large-file.json'); // headers aa gaye, body abhi stream ho rahi hai

const reader = response.body.getReader();          // stream ko manually iterate karne wala reader object

// Content-Length header se total expected size nikal lo (agar server ne bheja hai)
const contentLength = +response.headers.get('Content-Length'); // '+' string ko number mein convert karta hai

let receivedLength = 0;          // ab tak kitne bytes aa chuke hain, running counter
let chunks = [];              // har chunk (Uint8Array) yahan collect karenge, baad mein merge karne ke liye

while (true) {                // infinite loop — break tab hoga jab stream khatam ho
  const {done, value} = await reader.read(); // agla chunk aane tak await karo

  if (done) {              // done=true matlab stream fully consumed ho chuki hai
    break;                 // loop se bahar niklo
  }

  chunks.push(value);        // value ek Uint8Array chunk hai, array mein store karo
  receivedLength += value.length; // running total badhao is chunk ki length se

  // yahan progress % calculate kar sakte ho aur UI update kar sakte ho
  console.log(`Received ` + receivedLength + ` of ` + contentLength);
}

// saare chunks ko ek single Uint8Array mein concat karo
let chunksAll = new Uint8Array(receivedLength); // final buffer, poori length pehle se allocate
let position = 0;
for (let chunk of chunks) {       // har collected chunk ko crmt position pe copy karo
  chunksAll.set(chunk, position);
  position += chunk.length;
}

let result = new TextDecoder("utf-8").decode(chunksAll); // bytes ko UTF-8 string mein decode karo
let data = JSON.parse(result);                    // aur agar JSON hai to parse bhi kar lo
⚠️ Upload progress fetch se possible nahi hai

Ye ulta gotcha hai: fetch se download progress (upar wala pattern) track kar sakte ho, lekin upload progress (bade file ko server ko bhejte waqt) fetch ke paas track karne ka koi built-in tareeka nahi hai. Agar tumhe file upload progress bar chahiye (jaise koi upload widget), tumhe purana XMLHttpRequest use karna padega, jiska xhr.upload.onprogress event hota hai. Ye chapter 27 mein cover hoga.

AbortController — request cancellation

AbortController ek generic cancellation primitive hai (sirf fetch tak limited nahi — kisi bhi custom async task ke saath use ho sakta hai). Isme ek signal property hoti hai jo ek event emitter hai, aur ek abort() method jo signal pe "abort" event fire karta hai.

AbortController basic mechanism
let controller = new AbortController();   // naya controller instance
let signal = controller.signal;          // iska signal fetch ko diya jaayega

signal.addEventListener('abort', () => console.log("aborted!")); // listener manually bhi laga sakte ho

controller.abort();                        // ye event trigger karta hai — "aborted!" print hoga
console.log(signal.aborted);              // true — signal permanently aborted state mein chala gaya
fetch ke saath AbortController + try/catch
let controller = new AbortController();

// signal option mein pass karo — fetch internally isse "abort" listen karega
let fetchPromise = fetch('/long-request', { signal: controller.signal });

setTimeout(() => controller.abort(), 5000); // 5 second ke baad automatically cancel — timeout pattern

try {
  let response = await fetchPromise;       // yahan await karte waqt agar abort() call ho jaaye
  let data = await response.json();
} catch(err) {
  if (err.name == 'AbortError') {    // fetch promise AbortError naam ke saath reject hota hai
    console.log("Request cancelled"); // isse network error se differentiate karna zaroori
  } else {
    throw err;                    // koi aur real error hai to rethrow karo
  }
}
Ek controller se multiple fetches cancel karna
let urls = ['/api/a', '/api/b', '/api/c'];   // teen parallel requests chalani hain
let controller = new AbortController();       // ek hi controller sabke liye

// same signal teeno fetch calls mein pass — abort() sabko ek saath cancel karega
let fetchJobs = urls.map(url => fetch(url, { signal: controller.signal }));

let results = await Promise.all(fetchJobs);      // saare parallel resolve hone ka wait
// agar kisi bhi point pe controller.abort() call hoga, TEENO fetches turant reject ho jaayenge

CORS — simple vs preflighted requests

Jab tumhara fetch ek different origin (alag protocol/domain/port) ko target karta hai, browser CORS (Cross-Origin Resource Sharing) rules enforce karta hai. Spec do categories define karta hai — simple (safe) requests aur everything else jo preflight trigger karte hain.

Ek request "safe" tabhi hai jab dono conditions satisfy hon: (1) method sirf GET, POST, ya HEAD ho, aur (2) custom headers sirf in tak limited hon — Accept, Accept-Language, Content-Language, aur Content-Type (lekin sirf value application/x-www-form-urlencoded, multipart/form-data, ya text/plain ke saath). Koi bhi custom header (jaise Authorization) ya JSON Content-Type add karte hi request unsafe ban jaati hai.

🧠 Senior Dev Note: preflight kyun exist karta hai

Root reason ye hai ki browser CORS aane se pehle bhi cross-origin "simple" requests (<form> submit, <img> src) allowed the — legacy web ka part the. CORS ne unhe backward-compatible rakha, lekin har naya unsafe pattern (custom headers, JSON body via fetch/XHR, PATCH/DELETE methods) ek naya attack surface hai jo purane servers ko "surprise" na kare, isliye browser pehle ek silent OPTIONS preflight bhejta hai — "agar main ye actual request bheju, tum allow karoge?" — aur sirf server ke "haan" (sahi Access-Control-Allow-* headers) ke baad hi asli request bheji jaati hai.

Unsafe request → automatic preflight
// ye request UNSAFE hai — PATCH method + custom Content-Type + custom header
await fetch('https://api.example.com/user/1', {
  method: 'PATCH',                       // PATCH safe methods list mein nahi hai
  headers: {
    'Content-Type': 'application/json', // JSON safe value list mein nahi hai
    'X-Auth-Token': 'secret123'       // custom header hamesha unsafe
  },
  body: JSON.stringify({ name: 'Jane' })
});

// browser is fetch() se PEHLE khud-ba-khud ye bhejta hai (tumhare code mein kahin nahi likha):
// OPTIONS /user/1 HTTP/1.1
// Access-Control-Request-Method: PATCH
// Access-Control-Request-Headers: content-type,x-auth-token
// Origin: https://myapp.com
//
// server ko is OPTIONS request ka jawab dena hoga (status 200) in headers ke saath:
// Access-Control-Allow-Methods: PATCH, GET, POST
// Access-Control-Allow-Headers: Content-Type, X-Auth-Token
// Access-Control-Max-Age: 86400   (optional — preflight result cache karo, 24hr)
// tabhi jaake browser ASLI PATCH request bhejega
Credentials (cookies) ke saath cross-origin request
await fetch('https://api.example.com/profile', {
  credentials: 'include'  // default 'same-origin' hai — 'include' cross-origin pe bhi cookies bhejta hai
});

// server ko RESPOND karna hoga in do headers ke saath, warna browser response block kar dega:
// Access-Control-Allow-Origin: https://myapp.com   (wildcard * YAHAN ALLOWED NAHI hai)
// Access-Control-Allow-Credentials: true
⚠️ Credentials ke saath wildcard origin ban hai

Jab credentials: 'include' use karte ho, spec explicitly Access-Control-Allow-Origin: * ko prohibit karta hai — server ko exact requesting origin specify karna hi hoga (e.g. Access-Control-Allow-Origin: https://myapp.com). Root reason security hai: agar wildcard + credentials dono allowed hote, to koi bhi random website tumhare authenticated cookies ke saath tumhare API se data chura sakti thi. Ye combination browser level pe hard-blocked hai.

URL object aur URLSearchParams

Manual string concatenation se URL banane ke bajaye (jo encoding bugs ka source hota hai), built-in URL class use karo — ye parsing aur encoding dono khud handle karta hai.

URL object — parsing
let url = new URL('https://javascript.info:8080/path/page?q=test#hash');

console.log(url.protocol);   // "https:" — scheme, colon ke saath
console.log(url.hostname);   // "javascript.info" — port ke bina
console.log(url.host);       // "javascript.info:8080" — port ke saath
console.log(url.port);       // "8080"
console.log(url.pathname);   // "/path/page"
console.log(url.search);     // "?q=test" — leading ? ke saath
console.log(url.hash);       // "#hash" — leading # ke saath
console.log(url.origin);     // "https://javascript.info:8080" — scheme+host+port

// relative URL banane ke liye base pass karo — second arg
let relativeUrl = new URL('/profile/admin', 'https://javascript.info');
console.log(relativeUrl.href); // "https://javascript.info/profile/admin" — dono combine ho gaye
URLSearchParams — query string build karna
let url = new URL('https://google.com/search'); // base URL, abhi koi query nahi

url.searchParams.set('q', 'test me!');    // key add/update — value automatically encode ho jaata hai
console.log(url.href);  // "https://google.com/search?q=test+me%21" — space→+, !→%21

url.searchParams.append('tag', 'js');     // append: existing keys ko preserve karke naya add — set() unhe replace karta
url.searchParams.append('tag', 'web');    // same key 'tag' do baar — duplicate allowed via append

console.log(url.searchParams.getAll('tag')); // ["js", "web"] — same-name saare values ek array mein
console.log(url.searchParams.has('q'));     // true
url.searchParams.delete('tag');            // dono 'tag' entries hata do

// Map jaisa hi iterable hai — decoded key/value pairs milte hain
for (let [name, value] of url.searchParams) {
  console.log(`${name}=${value}`);  // "q=test me!" — yahan value ALREADY decoded milta hai
}

// fetch/XHR ko URL object directly pass kar sakte ho — string mein convert khud ho jaata hai
await fetch(url);

Manual string URLs banate waqt (jab URL object use nahi kar rahe), encoding khud karni padti hai — encodeURIComponent() query params ke liye best hai kyunki ye &, =, ? jaise reserved characters bhi encode karta hai (jo encodeURI() nahi karta, kyunki wo poori URL ke liye designed hai jahan ye characters structural hote hain).

encodeURIComponent vs encodeURI
let query = 'Rock&Roll';                          // user input jisme reserved char '&' hai

let safe = encodeURIComponent(query);        // "Rock%26Roll" — & bhi encode hua, sahi hai
let url1 = `https://google.com/search?q=${safe}`; // ?q=Rock%26Roll — ek hi param, sahi parse hoga

let broken = encodeURI(query);              // "Rock&Roll" — & encode NAHI hua (encodeURI ka scope alag hai)
let url2 = `https://google.com/search?q=${broken}`; // ?q=Rock&Roll — server isse DO params (q, Roll) samjhega, BUG

Key Takeaways

  • fetch() ka promise headers aane pe resolve hota hai, body pe nahi — body ke liye response.json()/text() jaisa second await zaroori hai.
  • fetch() sirf network failure pe reject hota hai — 4xx/5xx status pe nahi. Har response pe response.ok ya response.status manually check karo.
  • FormData multipart/form-data encoding use karta hai jo file upload ko support karta hai — Content-Type header manually set mat karo, boundary browser generate karta hai.
  • Download progress response.body.getReader() se manual chunk-by-chunk loop se track hota hai — fetch mein native progress event nahi hai (XHR mein hota hai).
  • Upload progress fetch se track nahi ho sakta — us case mein XMLHttpRequest use karo.
  • AbortController.signal ko fetch options mein pass karo cancellation ke liye; abort hone pe promise AbortError naam ke saath reject hota hai — ek hi controller multiple fetches cancel kar sakta hai.
  • CORS: safe (GET/POST/HEAD + safe headers) requests directly jaati hain; koi bhi custom header/method/JSON body unsafe ban jaati hai aur browser automatically ek OPTIONS preflight bhejta hai.
  • credentials: 'include' use karne pe server ko exact origin specify karna hoga — Access-Control-Allow-Origin: * credentials ke saath allowed nahi hai.
  • URL aur URLSearchParams use karo query strings build/parse karne ke liye — encoding automatically handle hoti hai, manual string concatenation se bugs bachte hain.

🎯 Interview Questions

  • fetch() ka promise kab resolve hota hai — poore response body ke aane pe ya sirf headers pe? Isse kya implication hai?
    Hint: sirf headers pe resolve hota hai; body access karne ke liye ek alag async method call (json/text/etc) chahiye, jo khud bhi ek promise hai.
  • fetch() 404 ya 500 status pe reject karta hai ya resolve? Production code mein isse kya bug ban sakta hai?
    Hint: resolve karta hai (sirf network failure pe reject) — agar response.ok check na karo to error responses silently valid data ki tarah treat ho jaate hain.
  • FormData body bhejte waqt Content-Type header khud set karna kyun galat hai?
    Hint: multipart encoding ko ek unique boundary string chahiye jo browser runtime pe generate karta hai; khud set karne se boundary missing/galat hoga aur server parse nahi kar payega.
  • Fetch se download progress kaise track karte ho jab koi native progress event nahi hai?
    Hint: response.body.getReader() se manual loop, reader.read() se {done, value} milta hai, Content-Length header se total size, chunks accumulate karke % calculate.
  • AbortController se ek hi request cancel hoti hai ya multiple? Kaise?
    Hint: ek hi controller.signal multiple fetch() calls mein pass kiya ja sakta hai — abort() call hote hi sab ek saath reject ho jaate hain AbortError ke saath.
  • Konsi cheezein ek fetch request ko "unsafe" bana deti hain aur preflight OPTIONS request trigger karti hain?
    Hint: non-simple method (PUT/PATCH/DELETE), custom headers (jaise Authorization), ya Content-Type jo application/x-www-form-urlencoded/multipart/text-plain se alag ho (jaise application/json).
  • credentials: 'include' use karte waqt Access-Control-Allow-Origin: * kyun kaam nahi karta?
    Hint: spec-level security restriction — credentialed cross-origin requests ke liye server ko exact origin specify karna zaroori hai, wildcard prohibited hai taaki koi bhi random site cookies ke saath data na chura sake.
  • encodeURIComponent aur encodeURI mein farak kya hai, aur query param values ke liye kaunsa use karna chahiye?
    Hint: encodeURIComponent zyada characters encode karta hai (&, =, ?, / bhi) isliye individual param values ke liye sahi hai; encodeURI poori URL ke liye hai aur structural characters ko preserve karta hai.
