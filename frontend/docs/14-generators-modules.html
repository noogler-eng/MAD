Generators & Modules

Generators ek function ko pause aur resume karne ki power dete hain — ye pura custom iterators, lazy sequences, aur async streaming ka foundation hai. Aur ES Modules JavaScript ko finally ek proper, browser-native dependency system dete hain — har module apni scope, apna singleton cache, apna strict mode. Is chapter mein dono ko root-level samjhenge: generator ke andar execution state kaise freeze/unfreeze hota hai, aur module system internally URL-based caching kaise kaam karta hai.

Generator functions — function*, yield, .next()

Normal function ek value return karke khatam ho jaata hai. Generator function is se alag hai — wo multiple values time ke saath produce kar sakta hai, beech mein pause hoke. Syntax: function name ke pehle ek * lagta hai.

Basic generator
function* generateSequence() {          // function* — asterisk hi is function ko "generator" banata hai
  yield 1;                                // yield 1: yahaan execution pause ho jaayega, 1 return hoga
  yield 2;                                // yield 2: agli baar resume hoga to yahaan tak chalega
  return 3;                               // return 3: generator ko fully khatam kar deta hai, done:true
}

let generator = generateSequence();   // call karne se function BODY execute nahi hota, sirf ek "generator object" milta hai
console.log(generator);          // [object Generator] — suspended state, body abhi tak run hi nahi hua

let one = generator.next();       // .next() — body run karo pehle yield tak
console.log(JSON.stringify(one)); // {"value":1,"done":false} — value = yield ki value, done = generator khatam hua ya nahi

let two = generator.next();       // dubara .next() — pichle yield SE resume, agle yield TAK
console.log(JSON.stringify(two)); // {"value":2,"done":false}

let three = generator.next();     // return 3 tak pahunch gaya — ab generator "done" ho jaata hai
console.log(JSON.stringify(three)); // {"value":3,"done":true} — return ki value bhi value field mein aati hai

Do form valid hain — function* foo() {} ya function *foo() {}; convention pehla wala hai kyunki asterisk function-type denote karta hai, function-name ka part nahi.

Root-level: pause/resume andar se kaise kaam karta hai

Ye samajhna zaroori hai ki generator koi "async" cheez nahi hai — sab kuch synchronous hi hota hai. Andar se, generator engine ek generator function ko call karte hi turant execute nahi karta. Instead, JS engine us function call ke liye ek suspended execution context allocate karta hai — call stack, local variables, aur "abhi kahaan tak pahuncha hoon" wala instruction pointer, sab kuch memory mein freeze karke rakh diya jaata hai.

Jab tum .next() call karte ho, engine us frozen context ko wapas call stack pe restore karta hai aur code ko usi exact point se chalana shuru karta hai jahan pichli baar yield pe rukka tha. Jaise hi agla yield milta hai, engine current state (variables, position) ko dubara freeze kar deta hai aur control caller ko wapas de deta hai. Ye ek cooperative coroutine jaisa mechanism hai — normal function calls mein control sirf return pe wapas jaata hai, lekin generator mein control multiple baar, explicitly yield points pe, wapas-forward hota rehta hai.

Isi wajah se generator ka .next() ek special iterator jaisa behave karta hai — normal iterator ka next() ek fixed logic chalata hai har baar, lekin generator ka next() "jahan chhoda tha wahan se code chalao" karta hai. Yehi core mental model hai: generator function = ek iterator jiska body khud likha hua hai, aur jiske "next" call par actual JS statements execute hoti hain (na ki koi fixed algorithm).

📌 Generator object hi Iterable + Iterator dono hai

Generator jo object return karta hai, uske paas Symbol.iterator method bhi hota hai jo khud this return karta hai. Isliye generator object dono iterable (for..of mein use ho sakta hai) aur iterator (khud .next() rakhta hai) — dono hai. Isi property ki wajah se for (let x of generatorObj) seedha kaam karta hai, bina kisi extra wrapping ke.

Generators as iterables — custom range banate hain

Chapter 7 mein humne manual Symbol.iterator implement karna dekha tha — jahan khud ek object banake uske next() method mein state (jaise current variable) manually track karna padta tha. Generator ke saath ye massively simpler ho jaata hai, kyunki state ko manually track karne ki zaroorat nahi — generator ka apna execution position hi state hai.

range object — generator-based Symbol.iterator
let range = {
  from: 1,                              // range ki starting value
  to: 5,                                // range ki ending value (inclusive)

  *[Symbol.iterator]() {              // computed method name + generator (*) — object literal shorthand
    for (let value = this.from; value <= this.to; value++) {
                                          // normal for loop — from se to tak, ek-ek karke
      yield value;                    // har iteration pe pause + current value emit karo
    }
  }
};

console.log([...range]);           // spread operator range ke Symbol.iterator ko call karta hai
                                       // output: [1, 2, 3, 4, 5]

for (let num of range) {              // for..of bhi seedha kaam karta hai — same mechanism
  console.log(num);               // 1, phir 2, phir 3... one at a time print hoga
}

Compare karo: manual Symbol.iterator version mein tumhe current jaisa variable object pe store karna padta, aur next() ke andar manually {value, done} object return karna padta. Generator version mein ye sab for-loop ke andar chhupa hua hai — engine khud state track karta hai.

yield* — generator composition

Ek generator ke andar doosre generator ko delegate karne ke liye yield* use hota hai — ye nested generator ke saare yields ko transparently outer generator ke through pass kar deta hai.

yield* delegation
function* generateSequence(start, end) {  // reusable helper generator — start se end tak yield karta hai
  for (let i = start; i <= end; i++) yield i; // har number ko yield karo
}

function* generatePasswordCodes() {       // outer generator jo teeno ranges ko compose karta hai
  yield* generateSequence(48, 57);    // yield*: '0'-'9' ke char codes delegate karo
  yield* generateSequence(65, 90);    // yield*: 'A'-'Z' ke char codes delegate karo
  yield* generateSequence(97, 122);   // yield*: 'a'-'z' ke char codes delegate karo
}

let str = '';                          // result string accumulate karne ke liye
for (let code of generatePasswordCodes()) {  // outer generator ko normal for..of se consume karo
  str += String.fromCharCode(code); // char code ko actual character mein convert karke jodo
}
console.log(str);                    // "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz"

yield* ke bina bhi kaam ho sakta tha (nested for-of loop se manually forward karke), lekin yield* use karne se caller ko lagta hai jaise ek hi flat generator chal raha hai — nesting ka detail abstract ho jaata hai.

Two-way communication — next(), throw(), return()

yield ek two-way channel hai — sirf value bahar nahi bhejta, .next(arg) ke through value andar bhi le sakta hai. Jab generator let x = yield something pe pause hota hai, agli baar .next(value) call karne pe wahi value us paused yield expression ka result ban jaata hai.

next(value) — ping-pong communication
function* gen() {
  let result = yield "2 + 2 = ?";  // yield question OUT, aur agle next() ki value ANDAR result mein aayegi
  console.log(result);          // jo bhi answer next() se aayega wahi yahaan print hoga
}

let generator = gen();
generator.next();                     // pehla next() sirf "2 + 2 = ?" tak chalata hai, andar koi value nahi bhej sakta
generator.next(4);                    // 4 ANDAR jaata hai — result = 4, phir console.log(4) chalta hai
throw() aur return()
function* gen() {
  try {
    let result = yield "2 + 2 = ?";  // yahaan pause — throw() se error yahaan inject ho sakti hai
  } catch(e) {
    console.log(e.message);          // normal try/catch se generator ke andar hi error handle ho jaati hai
  }
}

let generator = gen();
generator.next();                             // yield "2 + 2 = ?" tak chalao
generator.throw(new Error("Not found")); // error ko exact us yield point pe throw karta hai, jaise wahin likhi ho

function* gen2() { yield 1; yield 2; yield 3; } // simple 3-value generator
const g = gen2();
g.next();                                // {value: 1, done: false}
g.return('foo');                       // return(): generator ko FORCE-terminate karta hai — {value: "foo", done: true}
g.next();                                // {value: undefined, done: true} — ab permanently done, yield 2/3 kabhi nahi milenge
🧠 Senior Dev Note: generators ka real production use

Direct generators production code mein kam dikhte hain, lekin unki design har jagah hai — async/await ka desugar-form internally ek generator + promise-driven runner hai (Babel jaise transpilers async functions ko generator-based state machines mein compile karte the/karte hain). Redux-Saga jaisi libraries generators ko explicitly use karti hain taaki complex async workflows ko testable, pausable sequences ki tarah likha jaa sake — har yield ek "effect" describe karta hai jise saga middleware intercept karta hai, actual side-effect khud generator nahi karta. Ye pattern samajhna async architecture debug karne mein directly kaam aata hai.

Async iterators — Symbol.asyncIterator

Normal iterator synchronously value deta hai. Lekin agar data network se, ya kisi delay ke baad aana hai (jaise paginated API), to normal Symbol.iterator kaam nahi karta — uska next() promise return nahi kar sakta while staying spec-compliant for for..of. Iske liye alag protocol hai: Symbol.asyncIterator, jiska next() ek promise return karta hai jo {value, done} resolve karta hai.

Symbol.asyncIterator manually
let range = {
  from: 1, to: 5,                     // range boundaries

  [Symbol.asyncIterator]() {       // Symbol.iterator ki jagah Symbol.asyncIterator — async protocol
    return {
      current: this.from,              // manual state tracking (jaise sync iterator mein tha)
      last: this.to,

      async next() {                  // async next() — automatically ek Promise return karta hai
        await new Promise(resolve => setTimeout(resolve, 1000));
                                            // simulate network delay: 1 second ruko
        if (this.current <= this.last) {
          return { done: false, value: this.current++ };
                                            // current value do, phir agli baar ke liye increment karo
        } else {
          return { done: true };       // range khatam — done: true bhej do
        }
      }
    };
  }
};

(async () => {
  for await (let value of range) {   // for AWAIT of — plain for..of async iterators ke saath kaam nahi karta
    console.log(value);            // 1 second gap se 1, 2, 3, 4, 5 print honge
  }
})();

Async generators — for await...of ke saath streaming

Jaise generator ne manual Symbol.iterator ko simple banaya, async function* manual Symbol.asyncIterator ko simple banata hai — promises aur generators ko combine karke. Andar await bhi use kar sakte ho aur yield bhi — dono ek hi function ke andar.

async function* — streaming async data
async function* generateData(start, end) {    // async + generator dono ek saath, isliye "async function*"
  for (let i = start; i <= end; i++) {
    await new Promise(resolve => setTimeout(resolve, 500));
                                              // await: real async work simulate karo (e.g. ek DB/network call)
    yield i;                              // yield: value emit karo aur PAUSE karo agle .next() tak
  }
}

(async () => {
  for await (let value of generateData(1, 5)) {
    console.log(value);            // 500ms gap se 1, 2, 3, 4, 5 — code ekdum simple, delegation engine ke bharose
  }
})();

Real-world use-case: paginated API se data stream karna — jaise GitHub commits, jahan har page fetch karke uske andar ke items ek-ek karke yield kiye jaate hain, aur jab tak "next page" URL milta rahe, loop chalta rehta hai. Consumer ko ye pata bhi nahi hota ki pagination internally ho rahi hai — usse bas ek flat async stream milta hai.

paginated API ko async generator se abstract karna
async function* fetchCommits(repo) {
  let url = `https://api.github.com/repos/${repo}/commits`;
                                              // starting page ka URL banao
  while (url) {                          // jab tak "next page" ka url mile, loop chalao
    const response = await fetch(url);
                                              // await: is page ka data fetch hone tak generator pause rehta hai
    const body = await response.json();
                                              // response body ko JSON array mein parse karo (commits ka array)

    let nextPage = response.headers.get('Link');
                                              // Link header mein "next page" ka URL hota hai (GitHub API convention)
    url = nextPage;                    // (yahaan simplify kiya — real code mein regex se URL extract hota)

    for(let commit of body) {       // is page ke saare commits pe loop
      yield commit;                    // har commit ko individually yield karo — consumer ko page boundary nahi dikhti
    }
  }
}
⚠️ for..of (bina await) async iterator pe silently fail hoga

Agar galti se plain for..of use kar diya kisi async iterable pe, to error nahi aayega — lekin value ek unresolved Promise object hoga, actual data nahi. Ye debug karna mushkil hota hai kyunki koi crash nahi hota, bas output galat aata hai. Hamesha for await (... of ...) use karo jab data source async iterable ho, aur ye tabhi use kar sakte ho jab tum khud kisi async function ke andar ho (ya top-level module mein).

ES Modules — core features

Module bas ek file hai — "one script is one module". Farak ye hai ki module explicitly bataata hai ki wo kya expose karega (export) aur kya use karega (import). Kuch core rules jo module scripts ko regular scripts se fundamentally alag banate hain:

  • Hamesha strict mode — module code hamesha implicitly "use strict" mein chalta hai, chahe tumne likha ho ya nahi. Undeclared variable assign karne pe error milega.
  • Apni-apni top-level scope — module ke andar declare kiya gaya let/const/function doosre module mein automatically leak nahi hota. Global namespace pollute nahi hota.
  • Top-level this undefined hai — regular script mein top-level this window/globalThis hota, module mein undefined.
  • Deferred by default (browser) — <script type="module"> automatically defer-jaisa behave karta hai: download parallel, execution DOM parse hone ke baad.
  • import.meta — current module ke baare mein metadata deta hai, jaise uska URL (import.meta.url).
index.html — module script include karna
<script type="module">    <!-- type="module" — browser ko batata hai ye ES module hai, defer + strict mode automatic -->
  import { sayHi } from './say.js';  // relative path REQUIRED — bare module names allowed nahi browsers mein
  sayHi('Sharad');                // imported function use kar rahe hain
</script>

Modules singleton-cached-by-URL hote hain

Ye sabse important root-level fact hai jo interview mein aksar miss hota hai: agar ek hi module do jagah se import ho raha hai, uska code sirf ek baar execute hota hai — us module ka pehla import trigger karta hai, uske baad module engine internally ek cache maintain karta hai jo module ke resolved URL se key hota hai. Baad ke saare imports us same already-executed module object ka reference paate hain.

module singleton — config sirf ek baar init hota hai
// 📁 admin.js
export let config = { };                // module-level state — sabhi importers isi ek object ko share karenge
export function sayHi() {
  alert(`Ready to serve, ${config.user}!`);
}

// 📁 init.js
import { config } from './admin.js';       // SAME config object import kiya — new copy nahi mili
config.user = "Sharad";              // mutate kiya — kyunki reference same hai, ye sab jagah reflect hoga

// 📁 another.js
import { sayHi } from './admin.js';       // admin.js DUBARA execute nahi hoga — cache se aayega
sayHi();                                // "Ready to serve, Sharad!" — init.js wala mutation yahaan bhi dikha

Isi wajah se modules ek natural singleton pattern provide karte hain — agar tumhe ek shared config, ek shared cache, ya ek shared connection-pool object chahiye jo poore app mein ek hi instance ho, module-level state hi use kar lo, koi singleton-class design pattern implement karne ki zaroorat nahi.

🧠 Senior Dev Note: URL-based caching ka gotcha

Cache key resolved URL hoti hai, module ka naam nahi. Agar same file do alag paths se import ho (jaise ./utils.js aur ../src/utils.js jo dono resolve ho ke same file pe point karte hain lekin string-wise alag URLs hain), engine unhe do alag modules treat karega — do baar execute hoga, aur do alag singleton instances milenge. Monorepos mein symlinks ya multiple bundler-aliases ki wajah se ye subtle bug production mein aksar dikhta hai — "same class ke do instances kyun bane" jaisa debugging session isi root cause pe khatam hota hai.

export/import syntax variants

Export declare karne ke do tareeke — declaration ke saath inline, ya alag se batch mein:

export — inline vs batch
// Variant 1: declaration ke pehle hi export likh do
export let months = ['Jan', 'Feb', 'Mar']; // named export — ye variable named "months" ke naam se export hui

export function sayHi(user) {       // export function — ye ab bhi ek normal function declaration hai, sirf exported
  alert(`Hello, ${user}!`);
}

// Variant 2: pehle declare karo, phir ek jagah export karo
function sayBye(user) {              // normal function, abhi export nahi
  alert(`Bye, ${user}!`);
}
export { sayBye };                    // batch export — file ke top ya bottom pe ek list dikhana readability ke liye acha
import — named, star, aliasing
import { sayHi, sayBye } from './say.js'; // specific named imports — sirf jo chahiye wahi

import * as say from './say.js';     // saara module ek namespace object "say" mein import karo
say.sayHi('John');                    // namespace object se access karo

import { sayHi as hi } from './say.js'; // import ke waqt rename — local naam conflict avoid karne ke liye
hi('John');                            // ab "hi" naam se call hoga, "sayHi" se nahi
export default aur re-export
// 📁 user.js
export default class User {          // "default" export — module mein SIRF ek default ho sakta hai
  constructor(name) { this.name = name; }
}

// 📁 main.js
import User from './user.js';          // curly braces NAHI — default import ka naam import karte waqt tum khud chunte ho
new User('John');

// 📁 auth/index.js — "barrel" file: doosre modules ko re-export karta hai
export { login, logout } from './helpers.js';
                                          // helpers.js ke named exports ko forward kar diya, bina yahaan import kiye
export { default as User } from './user.js';
                                          // default export ko named "User" ke naam se re-export — special syntax zaroori hai

Note: export User from './user.js' jaisi shortcut syntax invalid hai — default re-export ke liye export {default as User} from ... hi likhna padta hai. Aur re-exported cheezein current file ke andar directly available nahi hoti — sirf forward hoti hain.

Named vs default exports — tree-shaking ka farak

Ye choice sirf syntax preference nahi hai — iska real bundling impact hai. Named exports ke naam statically fixed hote hain (module ke source code mein literal string ki tarah likhe hote hain), isliye bundler (Webpack/Rollup/esbuild) build-time pe static analysis karke exactly bata sakta hai ki kaunsa named export kahin use ho raha hai aur kaunsa nahi — unused named exports ko safely tree-shake (dead-code-eliminate) kar sakta hai.

Default export ka koi fixed "naam" nahi hota (importer jo chahe naam de sakta hai), aur agar default export ek poora object/module ho (jaise export default { a, b, c, d }), to bundler ke liye ye determine karna mushkil ho jaata hai ki object ke andar se sirf kaunse keys actually use ho rahe hain — safe side lene ke liye wo poora object bundle mein rakh leta hai, chahe tumne usme se sirf ek property use ki ho.

tree-shaking friendly vs unfriendly
// 📁 utils.js — GOOD: named exports, har function alag se static-analyzable
export function formatDate(d) { /* ... */ }
export function parseDate(s) { /* ... */ }

// consumer.js
import { formatDate } from './utils.js';
                                          // bundler ko exactly pata hai parseDate kahin import nahi hua — usko drop kar dega

// 📁 utils-bad.js — BAD: sab kuch ek default object mein bandled
export default {
  formatDate(d) { /* ... */ },
  parseDate(s) { /* ... */ }
};

// consumer2.js
import utils from './utils-bad.js';
utils.formatDate(new Date());       // sirf formatDate use ho raha hai, lekin bundler poora object safe nahi drop kar sakta
                                          // kyunki property access dynamic hai — parseDate bhi bundle mein reh jaayega

Practical rule: utility modules, component libraries, aur design systems mein named exports prefer karo. Default export tab thik hai jab module ki ek hi clear "main thing" ho (jaise ek React component file jisme sirf ek default component export ho raha ho) aur naming consistency team convention se maintain ho.

Dynamic import() — code-splitting

Static import/export sirf module ke top-level pe likhe jaa sakte hain — condition ke andar ya function ke andar nahi. Dynamic import() ye restriction hata deta hai: ye ek expression hai (function jaisa dikhta hai lekin super() jaisa special syntax hai), jo kahin bhi call ho sakta hai aur ek Promise return karta hai jo module object resolve karta hai.

import() — runtime pe module load karna
let modulePath = './say.js';          // path runtime pe bhi decide ho sakta hai — static import mein aisa nahi hota

import(modulePath)
  .then(module => {              // resolved value = module ka poora namespace object
    module.sayHi('Sharad');          // named export ko module.NAME se access karo
  })
  .catch(err => console.error('Load failed:', err));
                                          // promise hai isliye normal .catch() se error handle hota hai

// async/await ke saath, aur zyada clean
let { hi, bye } = await import('./say.js');
                                          // destructure directly — named exports await ke turant baad mil jaate hain

let { default: say } = await import('./say.js');
                                          // default export namespace object mein "default" key ke andar milta hai
Real use-case: route-based code splitting
button.addEventListener('click', async () => {
                                          // click hone tak ye heavy module bilkul download hi nahi hoga
  const { default: openModal } = await import('./modal-heavy.js');
                                          // lazy-load: sirf tab fetch hota hai jab user ko actually chahiye
  openModal();                       // ab module ready hai, use kar lo
});

Bundlers (Webpack, Vite/Rollup) import() calls ko automatically ek separate chunk file mein split kar dete hain — initial bundle chhota rehta hai, aur heavy/rarely-used code (modals, charts, admin panels, editors) sirf actual need pe download hote hain. Ye poora "code splitting" ka mechanism hai, aur ye sirf dynamic import() se hi possible hai — static imports ko bundler compile-time pe hi resolve karta hai, unhe conditionally split nahi kar sakta.

📌 import() type="module" tak limited nahi

Dynamic import() regular (non-module) scripts mein bhi kaam karta hai — isko use karne ke liye <script type="module"> hona zaroori nahi. Ye isliye possible hai kyunki ye ek runtime expression hai, static declarative syntax nahi — engine ko usse handle karne ke liye poore file ko module-mode mein parse karne ki zaroorat nahi padti.

Key Takeaways

  • Generator = ek function jiska execution engine yield points pe freeze/unfreeze kar sakta hai — .next() body ko agle yield tak chalata hai.
  • Generator object khud iterable + iterator dono hai, isliye for..of mein seedha use ho sakta hai.
  • Custom iterable banane ke liye generator use karna manual Symbol.iterator se kaafi simpler hai — state manually track nahi karni padti.
  • yield* se ek generator doosre generator ko transparently delegate kar sakta hai — composition ke liye.
  • .next(value), .throw(err), .return(val) se generator ke andar do-tarfa communication ho sakti hai.
  • Async generator (async function*) promises + generators combine karta hai — andar await aur yield dono chalte hain, consumer for await...of use karta hai.
  • ES modules hamesha strict mode mein chalte hain, apni scope rakhte hain, aur top-level this undefined hota hai.
  • Ek module URL ke hisaab se sirf ek baar execute hota hai — baad ke saare imports usi cached instance ka reference paate hain (natural singleton).
  • Named exports tree-shaking-friendly hain (static, per-name analyzable); default exports/object-bundles bundler ke liye harder to analyze hote hain.
  • Dynamic import() ek Promise return karta hai, kahin bhi call ho sakta hai, aur bundler code-splitting ka primary mechanism yahi hai.

🎯 Interview Questions

  • Generator function ke andar internally kya hota hai jab .next() call hota hai?
    Hint: engine call ka execution context (variables, instruction pointer) freeze karke rakhta hai; next() call pe usi point se resume karta hai, agle yield tak chalata hai, phir dubara freeze.
  • Generator object khud ek iterator kaise ban jaata hai for..of ke liye?
    Hint: generator object ke paas ek Symbol.iterator method hai jo khud this return karta hai — isliye iterable aur iterator dono ek hi object hai.
  • yield* aur normal yield mein kya farak hai?
    Hint: yield* ek pura doosra generator (ya iterable) delegate karta hai — uske saare yields sequentially outer generator ke through pass hote hain, jaise ek hi flat generator chal raha ho.
  • Async generator mein await aur yield dono ek saath kaise kaam karte hain?
    Hint: async function* async function ki tarah await pe promise resolve hone tak pause karta hai, AUR generator ki tarah yield pe consumer ko value dekar bhi pause karta hai — for await...of dono ko handle karta hai.
  • Agar same module do alag components se import ho, kya uska code do baar chalega?
    Hint: nahi — module resolved URL se cache hota hai, sirf pehli baar execute hota hai, baad ke imports same cached exports object share karte hain (singleton behavior).
  • Named export aur default export mein tree-shaking ka farak kyun hai?
    Hint: named exports statically-named hote hain isliye bundler exact usage track kar sakta hai aur unused ko drop kar sakta hai; default export (especially ek object) ka static analysis harder hota hai, poora bundle mein reh sakta hai.
  • Dynamic import() code-splitting kaise enable karta hai jo static import nahi kar sakta?
    Hint: static imports compile-time pe resolve hote hain (fixed dependency graph), lekin import() ek runtime Promise-returning expression hai jise bundler automatically alag chunk mein split kar sakta hai aur sirf actual call hone pe fetch karta hai.
