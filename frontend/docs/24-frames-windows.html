Frames & Windows

Ek browser tab sirf ek window nahi hota — usme iframes ho sakte hain, wo popups khol sakta hai, aur ye sab windows ek doosre ko dekh/access kar sakte hain — lekin sirf jab tak same-origin policy allow kare. Is chapter mein hum root-level dekhenge ki window.open() internally kaise kaam karta hai, browser cross-origin windows ke beech access ko kaise block karta hai, postMessage is restriction ko safely kaise bypass karne ka designed tareeka hai, aur clickjacking — ek real attack jo inhi frame mechanics ko exploit karta hai.

window.open() — popup kholna

Popup windows purana technique hai, lekin OAuth login flows (jaise "Sign in with Google") jaisi jagah aaj bhi zinda hai — kyunki popup ka apna alag window object hota hai jo parent se independent navigate ho sakta hai, aur parent ko result postMessage ya window.opener se bata sakta hai.

window.open() syntax
// window.open(url, name, params) — teen parameters, teeno optional
let win = window.open(
  'https://javascript.info/', // url: naye window mein kaunsa page load hoga
  'jsinfoWindow',          // name: window ka naam — agar ye naam pehle se exist karta hai, naya window nahi khulta, WAHI reuse hota hai
  'width=600,height=400'  // params: comma-separated feature string (koi space nahi honi chahiye beech mein)
);

// return value: naye window ka Window object reference, ya null agar block ho gaya
if (!win) {
  console.log('Popup block ho gaya browser ne'); // ye case handle karna zaroori hai, silently fail nahi karna
}

name parameter ka ek subtle root-level behavior hai: ye <a target="name"> ke exact semantics follow karta hai. Agar same name wala window already open hai, open() naya window nahi banata — usi window mein navigate kar deta hai. Isi wajah se hum har baar unique-ish naam use karte hain jab humein har call pe naya popup chahiye hota hai.

Popup blocking rules — root cause

Browser ka popup blocker ek simple heuristic follow karta hai: "kya ye open() call direct user gesture (click/keypress) ke response mein, synchronously chal rahi hai?" Agar haan, allow. Agar setTimeout, Promise callback, ya async delay ke baad chali, block — kyunki attacker page load hote hi ya user ke interact kiye bina spam popups khol sakta tha.

Allowed vs blocked
// ALLOWED: onclick handler ke andar SYNCHRONOUSLY call ho raha hai
button.onclick = () => {
  window.open('https://javascript.info'); // user ka click hi trigger hai, browser trust karta hai
};

// BLOCKED: setTimeout ke andar — user gesture aur open() call ke beech "trust" toot jaata hai
button.onclick = () => {
  setTimeout(() => window.open('https://javascript.info'), 3000); // 3 sec baad tak "user activation" flag expire ho chuka hota hai
};
⚠️ "User activation" ek time-bound internal flag hai

Spec-level pe iska naam transient activation hai — click event ke baad browser kuch seconds ke liye ek internal flag set rakhta hai jo "user abhi active tha" batata hai. Sirf isi window ke andar open(), autoplay, fullscreen jaisi APIs allow hoti hain. Ek chained fetch().then(() => window.open(...)) bhi async gap ki wajah se fail ho sakta hai agar fetch slow hai — isliye OAuth popups mein log button click pe turant open("about:blank") khol dete hain, phir baad mein us window ka location set karte hain, taaki activation window miss na ho.

Window features string

Teesra parameter ek comma-separated string hai — spaces allowed nahi hain beech mein. Ye window chrome (browser UI: toolbar, menubar, scrollbars) aur position/size control karta hai.

Minimalistic popup — sirf content, koi chrome nahi
let params = `scrollbars=no,resizable=no,status=no,location=no,toolbar=no,menubar=no,
width=600,height=300,left=100,top=100`;
// scrollbars/resizable/status/location/toolbar/menubar=no  → browser chrome ke sab optional parts hide
// width/height  → popup ka pixel size (bahut chhota diya to browser minimum size force kar deta hai)
// left/top      → screen ke top-left se popup ka position

open('/', 'test', params); // naya window in exact features ke saath khulta hai

Root-level default rule: koi feature specify na kiya jaaye to wo no (disabled) maana jaata hai — sirf left/top/width/height exception hain, jo omit hone par browser pichhle khule window ke paas rakh deta hai (missing left/top to naya window last-opened window ke thoda offset pe khulta hai). Modern browsers is poore feature-string API ko heavily restrict karte hain (chhote/off-screen popups se malicious tricks rokne ke liye) — treat this as a hint, not a guarantee.

Popup pe methods — focus, close, closed

Popup lifecycle — open se close tak
let newWin = open('/', 'example', 'width=300,height=300'); // popup khola, reference newWin mein store
newWin.focus(); // popup ko foreground mein le aao — kai browsers already-open popup ko background rakh dete hain

newWin.onload = function() {
  // popup ka document load ho chuka hai, ab safe hai DOM touch karna
  let html = `<div style="font-size:30px">Welcome!</div>`; // inject karne ka HTML
  newWin.document.body.insertAdjacentHTML('afterbegin', html); // popup ke document mein insert (SAME-ORIGIN hone par hi allowed)

  setTimeout(() => {
    newWin.close();            // 3 sec baad popup band karo — sirf ye kaam karta hai jab window open() se banaya gaya ho
    console.log(newWin.closed); // true — closed property hamesha check karne layak hai before touching newWin further
  , 3000);
};

win.close() sirf un windows pe reliably chalta hai jo script se window.open() ke through khule ho — normal user-opened tabs pe browsers isse silently ignore kar dete hain (security ke liye, taaki koi site user ka tab forcibly band na kar de). Isi tarah moveTo/moveBy/resizeTo/resizeBy bhi sirf script-opened popups pe kaam karte hain, maximized windows pe nahi.

Same-origin policy — exact definition

Ye poore chapter ka foundation hai — bina isse samjhe na cross-window access, na postMessage, na clickjacking defense samajh aayega. Do URLs "same-origin" tabhi kehlate hain jab teeno match karein:

Same-origin criteria — teeno match chahiye
// http://site.com  aur  http://site.com/path  → SAME origin (protocol=http, domain=site.com, port=default 80)
// http://site.com  vs   https://site.com       → DIFFERENT (protocol http vs https)
// http://site.com  vs   http://site.com:8080   → DIFFERENT (port 80 vs 8080)
// http://site.com  vs   http://www.site.com    → DIFFERENT (subdomain bhi domain ka hissa hai)
// http://site.com  vs   http://site.org         → DIFFERENT (TLD/domain hi alag)

Root cause ye rule kyun hai: origin browser ka "trust boundary" hai. Agar sirf domain match karna kaafi hota (port/protocol ignore), to same server pe chalne wala koi bhi HTTP service (dev server, admin panel kisi weird port pe) production HTTPS site ke saath directly interact kar paata — jo isolation todta hai. Isliye teeno criteria strict hain.

Cross-origin access ka reality check

Same-origin windows (chahe popup ho ya iframe) ek doosre ke document, variables, DOM sab kuch directly read/write kar sakte hain. Cross-origin windows ke liye browser almost sab kuch block kar deta hai — sirf ek exception hai: location property pe write allowed hai (redirect karne ke liye), lekin read nahi.

Cross-origin iframe access — kya allowed, kya nahi
<iframe src="https://example.com" id="iframe"></iframe>

<script>
iframe.onload = function() {
  let iframeWindow = iframe.contentWindow; // OK — Window reference khud accessible hai, cross-origin ho tab bhi

  try {
    let doc = iframe.contentDocument; // FAILS — cross-origin document read blocked
  } catch(e) {
    console.error(e); // SecurityError throw hota hai
  }

  try {
    let href = iframe.contentWindow.location.href; // FAILS — location READ bhi blocked cross-origin
  } catch(e) {
    console.error(e);
  }

  iframe.contentWindow.location = '/'; // OK — location WRITE allowed hai, redirect karwa sakte ho
};
</script>

Root cause is ek exception (location writable but not readable) ka: parent ko itna control dena useful hai (e.g. ek login iframe ko redirect karna), lekin read allow karne se parent iframe ki current URL se sensitive info (query params mein session tokens, search terms) chura sakta tha — isliye sirf one-way write channel khula rakha gaya hai.

🧠 Senior Dev Note: window.frames, parent, top

Navigation ke liye teen references yaad rakho: window.frames (child iframe windows ka collection — index ya name se access), window.parent (immediate parent), aur window.top (sabse bahar wala window). Ye teeno cross-origin frames ke liye bhi accessible hain (sirf reference, content nahi) — isliye if (window === top) check "kya main topmost window hoon ya kisi frame ke andar hoon" reliably batata hai, chahe embedding cross-origin ho. Yehi check clickjacking defense ka core building block hai (neeche dekho).

window.postMessage — safe cross-origin messaging

Same-origin policy ne cross-origin windows ke beech direct access poori tarah band kar diya — lekin legit use-cases hain jaha do different-origin windows ko baat karni hoti hai (payment gateway iframe, OAuth popup, chat widget). Uske liye spec ne ek explicit, controlled channel banaya: postMessage. Ye direct object access nahi deta — sirf messages pass karta hai (structured clone algorithm se data copy hota hai, reference nahi).

Sending — postMessage(data, targetOrigin)
let win = window.frames[0]; // target window ka reference (yahan pehla child iframe)

// targetOrigin ZAROORI hai — browser message tabhi deliver karega jab target window ka
// ACTUAL origin is string se match kare. Ye check message SEND karte waqt hota hai, receive pe nahi.
win.postMessage({ type: 'greet', payload: 'hello' }, 'https://trusted-child.com');

// '*' matlab "kisi bhi origin ko bhej do" — DANGEROUS, sirf tab use karo jab data truly non-sensitive ho
win.postMessage('public data', '*');
Receiving — message event listener
window.addEventListener("message", function(event) {
  // event.origin: message bhejne wale window ka ACTUAL origin — SIRF isi se trust decide karo
  if (event.origin !== 'https://trusted-parent.com') {
    return; // unknown origin se aaya message — ignore karo, kabhi bhi blindly trust mat karo
  }

  // event.data: bheja gaya actual payload — structured clone se aaya hai, ISKA SHAPE bhi validate karo
  if (typeof event.data !== 'object' || event.data.type !== 'greet') {
    return; // malformed ya unexpected shape — trust mat karo, silently drop karo
  }

  console.log(`Received: ${event.data.payload}`); // ab safe hai payload use karna

  // event.source: sender window ka reference — reply bhejne ke liye useful, cross-origin ho tab bhi
  event.source.postMessage('ack', event.origin); // reply — targetOrigin yahan bhi explicit rakho, event.origin se
}); // addEventListener use karo — window.onmessage= sirf ek handler allow karta hai aur overwrite ho sakta hai
⚠️ targetOrigin: '*' ka real danger

Agar tum win.postMessage(data, '*') likhte ho aur beech mein win navigate ho chuka hai (user ne link click kar diya, ya attacker ne apne iframe ko us URL pe redirect kar diya jaha tumhara code message bhej raha tha), to message jahan bhi wo window ab pahunch chuka hai wahin deliver ho jaata hai — chahe wo koi malicious third-party page ho. Agar data mein session token, user email, ya koi bhi sensitive info hai, ye directly attacker ko leak ho sakta hai. Root fix: hamesha exact targetOrigin do jab data sensitive ho — '*' sirf truly-public data ke liye.

Clickjacking attack — full walkthrough

Clickjacking exactly wahi frame mechanics exploit karta hai jo humne abhi dekhi — ek page (attacker ka) doosre origin ke page ko <iframe> mein embed kar sakta hai (jab tak target site ise explicitly block na kare), aur CSS se us iframe ko invisible bana sakta hai. User ko lagta hai wo attacker ke fake button pe click kar raha hai — asal mein wo click invisible iframe ke andar target site ke real button tak "chala jaata" hai.

Clickjacking — invisible iframe overlay
<style>
  .iframe-container {
    width: 400px;       /* target site ke real button ke around ka size match karta hai */
    height: 100px;
    position: absolute; /* fake button ke exact upar precisely position karne ke liye */
    top: 5px; left: -14px; /* target ke real "Delete Account" button ke upar align */
    opacity: 0;       /* KEY: poora invisible — user ko iframe dikhta hi nahi */
    z-index: 1;      /* fake button ke upar stack karo, taaki click iframe ko hi mile */
  }
</style>

<div>Click to get a free prize:</div>              <!-- decoy text jo user ko lure kare -->
<iframe class="iframe-container" src="https://victim-bank.com/transfer-confirm"></iframe>
                                                                       <!-- REAL target page, poori tarah invisible -->
<button>Click here!</button>                                            <!-- FAKE visible button, invisible iframe ke NEECHE, click "through" jaata hai -->

User dekhta hai sirf "Click here!" button — jab wo click karta hai, actual click coordinate pe z-index se upar wala invisible iframe hota hai, so browser click ko us iframe ke andar (real bank site ke real "Confirm Transfer" button) ko deliver kar deta hai. Result: user apni marzi ke bina, apne already-logged-in session se, ek real transaction confirm kar deta hai — bina kabhi bank ka page dekhe.

⚠️ Ye sirf mouse clicks pe kaam karta hai, lekin utna hi dangerous hai

Keyboard input clickjack karna mushkil hai (user ko realize ho jaata agar text field mein type karte waqt characters screen pe na dikhein) — lekin single clicks (delete account, confirm payment, "like"/"follow" jaisi social actions, permission grant dialogs) is attack ka prime target hain kyunki inka feedback minimal hota hai. 2008-09 mein Twitter, Facebook, aur Adobe Flash settings panel tak is attack se compromise hue the.

Defense: X-Frame-Options aur CSP frame-ancestors

Purana defense tha "frame busting" — JS se check karna ki page kisi frame ke andar to nahi (if (top != window) top.location = window.location). Ye obsolete hai kyunki attacker parent page pe onbeforeunload handler laga ke navigation ko cancel-prompt karwa sakta hai, ya iframe ko sandbox="allow-scripts" (bina allow-top-navigation ke) se embed karke JS ko top navigate karne se hi rok sakta hai. Modern defense server-side HTTP headers hain, jinhe browser guaranteed respect karta hai HTML load hone se pehle hi.

X-Frame-Options header — server response mein
# DENY: page KABHI bhi kisi frame ke andar load nahi hoga, chahe same-origin bhi ho
X-Frame-Options: DENY

# SAMEORIGIN: sirf apni hi origin ke frame ke andar embed hone do — sabse common default
X-Frame-Options: SAMEORIGIN

# ALLOW-FROM: legacy, sirf ek specific origin allow — poorly supported hai, mat use karo
X-Frame-Options: ALLOW-FROM https://partner-site.com
CSP frame-ancestors — modern replacement
# frame-ancestors 'none' — X-Frame-Options: DENY ke equivalent, koi bhi origin embed nahi kar sakta
Content-Security-Policy: frame-ancestors 'none'

# frame-ancestors 'self' — SAMEORIGIN ke equivalent
Content-Security-Policy: frame-ancestors 'self'

# frame-ancestors ke saath MULTIPLE trusted origins list ho sakte hain — X-Frame-Options mein ye possible nahi tha
Content-Security-Policy: frame-ancestors 'self' https://partner-site.com https://checkout.partner-site.com

frame-ancestors CSP directive X-Frame-Options ka officially recommended successor hai — zyada flexible (multiple origins list kar sakte ho, wildcards support karta hai) aur sabhi modern browsers isse respect karte hain. Best practice: dono headers bhejo — frame-ancestors primary defense ke liye, X-Frame-Options: SAMEORIGIN/DENY fallback ke liye un ancient browsers ke liye jo CSP nahi samajhte.

🧠 Senior Dev Note: SameSite cookies — ek aur defense layer

Clickjacking attack sirf tab kaam karta hai jab victim already target site pe logged in ho (uska session cookie invisible iframe ke saath automatically bhej diya jaata hai). Set-Cookie: sessionId=xyz; SameSite=Lax (ya Strict) is cross-site cookie-sending ko hi block kar deta hai — cookie sirf tabhi bhejta hai jab request same-site navigation se aaya ho, cross-origin iframe embed se nahi. Ye frame-ancestors/X-Frame-Options ka replacement nahi hai (public/non-authenticated content ab bhi framing se vulnerable rehta hai), balki defense-in-depth ka extra layer hai — modern production apps mein dono ek saath use hote hain.

Key Takeaways

  • window.open(url, name, params) — name agar existing window se match kare to naya window nahi khulta, reuse hota hai. Popup sirf synchronous user-gesture handler ke andar reliably khulta hai — async delay ke baad "transient activation" expire ho jaata hai.
  • Same-origin policy: protocol + domain + port teeno match hone chahiye. Cross-origin windows/iframes ke beech sirf location WRITE allowed hai, sab kuch aur (document, variables, location READ) blocked hai.
  • postMessage(data, targetOrigin) hi cross-origin communication ka designed, safe channel hai — data structured-clone hokar copy hota hai, direct reference nahi milta.
  • targetOrigin: '*' khatarnak hai agar data sensitive ho — window navigate ho chuka ho to message wrong (potentially malicious) origin ko chala jaata hai.
  • Receiving side pe hamesha event.origin validate karo — event.data attacker-controlled ho sakta hai, blindly trust mat karo.
  • Clickjacking = invisible iframe overlay jo real button ke upar precisely position hota hai, user ka click "through" real site ke button tak jaata hai.
  • Frame busting (if (top != window) top.location = ...) obsolete hai — onbeforeunload se defeat ho jaata hai. Real defense: X-Frame-Options + Content-Security-Policy: frame-ancestors HTTP headers, plus SameSite cookies defense-in-depth ke liye.

🎯 Interview Questions

  • window.open() popup blocker se kab bachta hai aur kab block hota hai?
    Hint: sirf tab jab call synchronously, direct user-gesture event handler (click/keypress) ke andar ho — koi async gap (setTimeout, awaited fetch) transient activation expire kar deta hai.
  • Same-origin policy ki exact definition kya hai?
    Hint: protocol, domain, aur port — teeno match hone chahiye. Subdomain bhi domain ka hissa maana jaata hai (www.site.com != site.com).
  • Cross-origin window pe location property ka special behavior kya hai?
    Hint: WRITE allowed hai (redirect ke liye), READ blocked hai — one-way exception, taaki parent kisi child ki current URL se sensitive info steal na kar sake.
  • postMessage mein targetOrigin: '*' kab dangerous ban jaata hai?
    Hint: agar target window beech mein navigate ho chuka ho, message us naye (potentially attacker-controlled) origin ko deliver ho jaata hai — sensitive data leak ho sakta hai.
  • Message receive karte waqt security ke liye kya-kya validate karna chahiye?
    Hint: event.origin ko whitelist ke against check karo, aur event.data ka shape/type bhi validate karo — kabhi blindly trust mat karo, chahe origin match bhi kare.
  • Frame busting technique (top.location reassignment) ko attacker kaise defeat kar sakta hai?
    Hint: parent page pe onbeforeunload handler laga ke navigation prompt trigger karta hai, ya iframe ko sandbox="allow-scripts" (allow-top-navigation ke bina) se embed karta hai.
  • X-Frame-Options aur CSP frame-ancestors mein kya farak hai, aur dono ek saath kyun bheje jaate hain?
    Hint: frame-ancestors zyada flexible hai (multiple origins list kar sakta hai) aur modern standard hai; X-Frame-Options legacy fallback hai un browsers ke liye jo CSP support nahi karte — defense-in-depth ke liye dono bhejte hain.
