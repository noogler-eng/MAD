Classes

Chapter 10 mein humne dekha tha ki prototypal inheritance kaise kaam karta hai — F.prototype, [[Prototype]] chain, sab manual tha. class keyword us sab pe ek clean syntax layer hai — lekin "syntax sugar" ka matlab "sirf cosmetic" nahi hai. Engine ke andar class ek function hi banata hai, par kuch extra internal flags ke saath jo behavior ko subtly but meaningfully change karte hain. Class basic syntax

Basic class declaration ek constructor aur kuch methods rakhti hai. new ke saath instantiate karne pe constructor() automatically chal jaata hai:

Basic class
class User {                          // class keyword se class declare karte hain, User naam hai
  constructor(name) {              // constructor: new User(...) call hone pe ye method chalta hai
    this.name = name;          // naya banaye gaye object pe name property set karo
  }

  sayHi() {                        // sayHi: ek "method" — ye shorthand method syntax hai
    alert(this.name);      // this yahaan calling instance ko point karega
  }
}

let user = new User("Sharad");       // new: object banao, constructor chalao, this bind karo
user.sayHi();                      // -> "Sharad" alert hoga

Class body ke andar aur bhi cheezein likh sakte ho — getters/setters, computed method names, aur class fields (instance properties directly class body mein):

Getters/setters + computed names + class fields
class User {
  name = "Anonymous";          // class field: har naye instance pe DIRECTLY set hoga (prototype pe nahi)

  get upperName() {            // get: getter — property jaisa access hoga, method jaisa nahi
    return this.name.toUpperCase(); // this.name ko uppercase karke return karo
  }

  set upperName(value) {       // set: setter — user.upperName = "x" karne pe ye chalega
    this.name = value;       // incoming value ko this.name mein store karo
  }

  ["say" + "Hi"]() {          // computed method name: [expr]() -> runtime pe "sayHi" ban gaya
    alert(this.name);      // simple greet
  }
}

Class field important hai kyunki wo per-instance hota hai, prototype pe nahi — ye chapter 9 wale "losing this" problem ko arrow-function class fields se solve karne ke liye use hota hai (kyunki arrow function apne definition scope ka this capture karta hai, aur field har naye instance ke constructor execution ke time create hoti hai).

Class asal mein hai kya — desugaring proof

Yahaan se root-level part start hota hai. class keyword ek naya runtime primitive nahi hai — ye ek function banata hai (constructor banta hai us function ka body), aur baaki sab methods us function ke .prototype pe non-enumerable properties ke roop mein daal deta hai. Neeche proof hai:

class ka manual equivalent — dono functionally same hain
// ==== Version A: class syntax ====
class User {
  constructor(name) { this.name = name; } // constructor body
  sayHi() { alert(this.name); }          // method
}

// ==== Version B: hand-written equivalent, jo engine internally karta hai ====
function UserFn(name) {            // plain function -> constructor ka role nibhayegi
  this.name = name;            // same body jo class constructor mein tha
}

UserFn.prototype.sayHi = function() {   // method ko prototype pe manually assign kiya
  alert(this.name);
};

// Object.getOwnPropertyDescriptor se prove karo Version A ka sayHi
// bhi UserFn.prototype.sayHi jaisa hi ek prototype property hai:
console.log(typeof User);              // -> "function"  (class khud ek function hai!)
console.log(User === User.prototype.constructor); // -> true, jaisa normal function constructor

Lekin identical nahi — spec-level pe kuch internal flags alag hote hain jo class ko function se distinguish karte hain:

  • [[IsClassConstructor]]: true — class internally is flag ke saath marked hoti hai. Isi wajah se User() (bina new ke) call karna TypeError: Class constructor User cannot be invoked without 'new' deta hai — plain function ke saath aisa nahi hota, wo bina new ke bhi chal jaati (bas this galat bind hoga).
  • Non-enumerable methods — class body ke andar define hue saare methods automatically enumerable: false ke saath prototype pe set hote hain. Isliye for...in loop ek object pe chalane se class methods leak nahi hote — sirf apni khud ki (own, enumerable) properties dikhti hain. Manual UserFn.prototype.sayHi = function(){} se banai property by default enumerable: true hoti — ye class syntax ka ek deliberate cleanliness fix hai.
  • Automatic strict mode — class body ke andar sab kuch implicitly strict mode mein chalta hai, chahe file ke top pe "use strict" ho ya nahi.
🧠 Senior Dev Note: "syntax sugar" ka matlab galat mat samjho

Bahut jagah class ko "just syntax sugar over prototypes" bola jaata hai, aur runtime object-shape ke hisaab se ye largely sach hai — User.prototype abhi bhi wahi mechanism hai jo chapter 10 mein cover kiya tha. Lekin behaviorally class ek strictly-typed superset hai: [[IsClassConstructor]] flag, non-enumerable methods, aur (derived classes ke case mein) constructor call-ordering rules — ye teeno cheezein plain function-based "class pattern" mein manually replicate karni padti hain. Production code review karte waqt agar koi bole "class to bas function hi hai", to yaad rakho: runtime shape same hai, lekin **enforcement semantics** alag hain — aur wahi enforcement hi bugs ko compile/runtime pe catch karta hai jo function-pattern mein silently through ho jaate.

Inheritance: extends aur super

class Child extends Parent do prototype links set karta hai — ek instance-level (Child.prototype.__proto__ = Parent.prototype) aur ek class-level, jo hum static section mein dekhenge:

extends — prototype chain proof
class Animal {
  constructor(name) {
    this.speed = 0;       // har animal ki initial speed 0
    this.name = name;     // naam store karo
  }
  run(speed) {
    this.speed = speed;    // speed update karo
    alert(`${this.name} runs at ${speed}.`); // template literal se log
  }
}

class Rabbit extends Animal {     // extends: Rabbit.prototype ko Animal.prototype se link karo
  hide() {
    alert(`${this.name} hides!`); // Rabbit ka apna extra method
  }
  run(speed) {                // override: Animal.run ko re-define kiya
    super.run(speed);       // super.run: parent ka run() call karo, replace nahi extend kiya
    this.hide();          // run karne ke baad turant chhup jao — extra behavior
  }
}

let rabbit = new Rabbit("White Rabbit");
rabbit.run(5);                   // -> "White Rabbit runs at 5." phir "White Rabbit hides!"

console.log(Rabbit.prototype.__proto__ === Animal.prototype); // -> true, root proof

Method lookup rabbit.run() call karne pe: (1) rabbit khud check hota hai (nahi mila), (2) Rabbit.prototype check hota hai (mila — override wala run). Andar super.run() ka matlab hai "ek level upar ja ke, Animal.prototype pe, wahaan ka run dhoondo, but this ko current rabbit hi rehne do."

super() ka call-ordering constraint — root cause

Jab tum constructor override karte ho ek derived class mein, ek hard rule hai: super() ko this access karne se pehle call karna hi hoga. Ye arbitrary restriction nahi hai — ye is baat se aata hai ki base aur derived classes ke constructors ka internal [[ConstructorKind]] flag alag value rakhta hai:

  • Normal (base) class constructor: [[ConstructorKind]]: "base". Jab new ke saath call hota hai, engine pehle ek khaali object banata hai, use this bind karta hai, phir constructor body chalta hai.
  • Derived class constructor (extends wali): [[ConstructorKind]]: "derived". Yahaan engine object khud nahi banata — wo expect karta hai ki parent constructor (super() ke through) object banaye aur initialize kare. Jab tak super() call nahi hota, this ek uninitialized state mein reh jaata hai — literally "not yet created".
super() se pehle this access — TypeError proof
class Animal {
  constructor(name) { this.name = name; }  // base ctor -> object khud banata hai
}

class Rabbit extends Animal {
  constructor(name, earLength) {
    // this.earLength = earLength;   // <- agar ye line yahaan uncomment karo,
    // ReferenceError aayega: "Must call super constructor before accessing 'this'"
    super(name);              // super(): parent constructor ko call karo, YE object banayega/init karega
    this.earLength = earLength; // ab this exist karta hai — safe to touch
  }
}

let r = new Rabbit("White", 10);   // name super() se set hua, earLength Rabbit ke apne ctor se
alert(r.name + " " + r.earLength); // -> "White 10"

Ek subtle related rule: agar derived class explicitly constructor hi nahi likhti, to engine automatically ek generate kar deta hai jo bas sab args ko super(...args) ke through pass kar deta hai — constructor(...args) { super(...args); }. Isliye agar tumhare paas custom logic nahi hai, constructor omit karna bilkul safe hai.

⚠️ Derived constructor mein return value ka rule

Base class constructor agar bina value ke return karta hai (ya bilkul nahi karta), to this hi return hota hai — normal. Lekin derived constructor mein agar tum kisi object ko explicitly return karo, to wahi object use ho jaata hai (this discard). Aur agar primitive return karo, to wo ignore ho jaata hai aur this hi return hota hai — jaisa normal functions mein bhi hota hai. Ye edge case rarely use hota hai, lekin factory-style derived constructors likhte waqt ye behavior surprise de sakta hai.

[[HomeObject]] — super internally kaam kaise karta hai

super.method() resolve karne ke liye engine this.__proto__ use nahi karta — kyunki agar karta, to multi-level inheritance ya method-copying ke case mein infinite loop ban sakta tha. Iske bajaye har method jo class body ya object literal mein method shorthand syntax se define hota hai, ek internal [[HomeObject]] property store karta hai — jo us object/prototype ko point karta hai jahaan method originally define hua tha. super.foo() internally [[HomeObject]].__proto__.foo ke roop mein resolve hota hai, current this ke saath call hoke.

⚠️ Root gotcha: super wale methods copy nahi kiye ja sakte

[[HomeObject]] ek method ke liye fixed hota hai — jahaan wo define hua, wahin se bound rehta hai, chahe method ko baad mein kisi doosre object pe copy kar do. Matlab agar tum ek super-using method ko Object.assign se kisi aur object pe copy karo, uska super reference abhi bhi purane [[HomeObject]] ki taraf point karega — galat parent resolve hoga. Ye mixins likhte waqt (neeche dekho) ek practical trap hai: super use karne wale methods mixin mein mat rakho.

Static properties & methods

static keyword se define hui properties/methods class ke instances pe nahi, class function pe khud attach hoti hain — "functionality jo class ke 'as a whole' belong karti hai", jaise comparison ya factory functions.

static members + static inheritance
class Article {
  constructor(title, date) {
    this.title = title;   // instance property
    this.date = date;     // instance property
  }

  static compare(articleA, articleB) { // static: Article pe hi rehta hai, instance pe nahi
    return articleA.date - articleB.date; // sort comparator return karo
  }

  static createTodays() {        // static factory method
    return new this("Today's digest", new Date()); // static ke andar this = class khud (Article)
  }

  static publisher = "MAD Press";   // static field — class pe ek property, sab instances shared nahi karte, Article pe hi hai
}

alert(Article.publisher);       // -> "MAD Press", instance se access nahi hoga (article.publisher undefined)

class SpecialArticle extends Article {} // koi extra code nahi, sirf inherit
alert(SpecialArticle.publisher); // -> "MAD Press" -- static bhi inherit hua!
console.log(SpecialArticle.__proto__ === Article); // -> true: CLASS-level prototype link, statics ke liye

Yaani extends ek dual link banata hai: Rabbit.prototype.__proto__ === Animal.prototype (instance methods ke liye) aur Rabbit.__proto__ === Animal (statics ke liye, class-function-to-class-function). Isi wajah se static members bhi inherit hote hain.

Private (#field) aur protected (_field)

Do encapsulation levels hain, aur inka farak samajhna interview-critical hai.

Protected — sirf convention, koi enforcement nahi

Underscore prefix (_balance) ek team convention hai — "isse bahar se mat chuo" — lekin engine level pe koi restriction nahi hai. Ye subclasses ko access dene ke liye deliberately open rakha jaata hai.

Private — #field, language-enforced

#private fields — real enforcement
class CoffeeMachine {
  #waterLimit = 200;          // # prefix: TRUE private field, sirf is class ke andar accessible

  #fixWaterAmount(value) {       // # prefix method bhi private ho sakta hai
    if (value < 0) return 0; // negative amount ko clamp karo
    if (value > this.#waterLimit) return this.#waterLimit; // limit se zyada mat jaane do
    return value;              // valid value wapas
  }

  setWaterAmount(value) {       // public method — private ke saath interact karne ka legal raasta
    this.water = this.#fixWaterAmount(value); // private method call karke result public field pe daalo
  }
}

let machine = new CoffeeMachine();
machine.setWaterAmount(1000);   // legal path -> internally clamp ho jaayega

// machine.#waterLimit;        // <- SyntaxError: Private field '#waterLimit' must be declared in an enclosing class
// machine["#waterLimit"];     // <- ye bhi kaam NAHI karega — sirf undefined milega!
// yehi asli farak hai _protected se: bracket-notation escape hatch bhi block hai
⚠️ Private ki असली taakat: this["#name"] block hai

Normal properties ke saath, agar kisi trick se property naam obfuscate bhi kar do (jaise Symbol), Object.getOwnPropertySymbols se reflect karke access mil sakta hai. Private fields ke saath aisa koi reflection-based escape hatch nahi hai — #name ek dedicated lexical binding hai jo sirf class body ke andar hi parse-time pe resolve hoti hai. this["#name"] syntactically ek alag cheez hai (ek string-keyed property lookup), aur wo simply undefined dega, kyunki #name object ki enumerable/string-keyed properties mein hai hi nahi. Yehi wo root reason hai jiski wajah se # ko "true private" bola jaata hai aur _ ko "convention-only private."

Ek limitation yaad rakho: subclasses parent ke private fields directly access nahi kar sakte — private fields sirf usi class tak scoped hain jahaan declare hue, inheritance chain tak bhi nahi propagate hote jaise protected karta hai. Subclass ko public getter/setter ke through hi interact karna padega.

Built-in classes extend karna — Array aur Symbol.species

Array, Map, Error jaise built-ins ko extends karna technically valid hai — instance methods inherit ho jaate hain. Lekin ek subtle gotcha hai jab built-in methods naye instances internally create karte hain, jaise .filter() ya .map():

Array extend karna — .filter() ka default behavior
class PowerArray extends Array {      // Array ko extend kiya — sab Array methods PowerArray ko milte hain
  isEmpty() {
    return this.length === 0; // custom helper method
  }
}

let arr = new PowerArray(1, 2, 5, 10, 50);
let filteredArr = arr.filter(item => item > 10); // .filter() naya array-jaisa instance return karta hai

console.log(filteredArr.isEmpty); // -> function (yaani DEFAULT mein filteredArr bhi PowerArray hi hai!)
console.log(filteredArr instanceof PowerArray); // -> true

Root mechanism: .filter(), .map(), .slice() jaise methods result return karte waqt this.constructor use karte hain naya instance banane ke liye — aur agar this.constructor mein ek static Symbol.species defined ho, to wo use hota hai instead:

Symbol.species se opt-out karna
class PowerArray extends Array {
  isEmpty() {
    return this.length === 0;
  }

  static get [Symbol.species]() {   // static getter Symbol.species pe — internal "kis constructor se banao" hook
    return Array;            // plain Array batao, PowerArray nahi
  }
}

let arr = new PowerArray(1, 2, 5, 10, 50);
let filteredArr = arr.filter(item => item > 10);

console.log(filteredArr.isEmpty); // -> undefined -- ab filteredArr sirf plain Array hai, isEmpty inherit nahi hua

Jab tum Symbol.species define nahi karte (default case), .map() aur .filter() tumhari subclass ke instances hi return karte hain — jo kabhi-kabhi wanted hota hai (chained custom methods), lekin kabhi-kabhi unwanted, jaise agar tumhare subclass constructor ne kuch extra invariant assume kiya ho jo ek "auto-generated" filtered array satisfy nahi karta. Isliye Symbol.species ek explicit opt-out mechanism hai — production mein agar tum Array extend kar rahe ho, isse consciously decide karo.

⚠️ Built-in classes statics inherit nahi karti — Error extend karte waqt bhi dhyaan

Ek aur exception: normal user classes extends se statics bhi inherit karti hain (jaisa upar static section mein dekha), lekin built-in classes ye rule nahi follow karti. Jaise Array, Object se statics inherit nahi karta — Array.keys ek alag cheez hai Object.keys se, aunki apni cross-hierarchy static inheritance nahi hai. Isi tarah agar tum class MyError extends Error {} likhte ho, environment ke hisaab se error.stack aur message ka behavior thoda different feel ho sakta hai — transpilers (Babel jaisi tools) ES5 target pe compile karte waqt instanceof checks todh sakti hain agar properly configured na ho. Chapter 12 (Error Handling) mein hum custom Error classes detail mein cover karenge.

instanceof ka internal algorithm

obj instanceof Class ek simple-lagne wala operator hai, lekin andar ek proper algorithm chalta hai — jo customize bhi ho sakta hai:

instanceof default behavior — prototype chain walk
class Animal {}
class Rabbit extends Animal {}

let rabbit = new Rabbit();

console.log(rabbit instanceof Animal); // -> true

// internally engine ye karta hai:
// step 1: rabbit.__proto__ === Animal.prototype?  -> nahi, ye Rabbit.prototype hai
// step 2: rabbit.__proto__.__proto__ === Animal.prototype?  -> HAAN, match mil gaya
// -> true return

Agar Symbol.hasInstance class pe static method ke roop mein defined ho, engine usi ko priority deta hai — default prototype-walk algorithm bypass ho jaata hai:

Symbol.hasInstance se instanceof override
class Animal {
  static [Symbol.hasInstance](obj) {  // Symbol.hasInstance: instanceof ke behavior ka custom hook
    if (obj.canEat) return true; // prototype chain bhool jao — sirf ye check karo
    return false;
  }
}

console.log({ canEat: true } instanceof Animal); // -> true, koi prototype link nahi hai fir bhi!

Alternative type-checking mechanism Object.prototype.toString.call(value) hai, jo Symbol.toStringTag respect karke "[object ClassName]" jaisa string return karta hai — array/number/null/undefined jaise primitives ke liye bhi reliable hai jahaan instanceof kaam nahi karta.

Mixins — single inheritance ka workaround

JS mein ek class sirf ek hi parent extend kar sakti hai — single [[Prototype]] chain hai. Jab ek class ko multiple, unrelated sources se behavior chahiye (e.g. "event-emittable" + "serializable" + "loggable"), mixins ka use hota hai — plain objects jinke methods copy kar diye jaate hain target ke prototype pe:

eventMixin — Object.assign se copy
let eventMixin = {
  on(eventName, handler) {       // on: kisi event ke liye handler subscribe karo
    if (!this._eventHandlers) this._eventHandlers = {}; // lazy-init storage object (protected convention)
    (this._eventHandlers[eventName] ||= []).push(handler); // array me handler push karo (nullish default)
  },

  off(eventName, handler) {      // off: subscription hatao
    let handlers = this._eventHandlers?.[eventName]; // optional chaining -- agar handlers hi nahi hain to skip
    if (!handlers) return;       // kuch bhi subscribe hi nahi tha
    this._eventHandlers[eventName] = handlers.filter(h => h !== handler); // filter karke us handler ko hatao
  },

  trigger(eventName, ...args) {   // trigger: event fire karo, rest args extra data ke liye
    if (!this._eventHandlers?.[eventName]) return; // koi listener nahi to no-op
    this._eventHandlers[eventName].forEach(handler => handler.apply(this, args)); // har handler ko this + args ke saath call karo
  }
};

class Menu {
  choose(value) {
    this.trigger("select", value); // mixin se aaya trigger method use kiya
  }
}
Object.assign(Menu.prototype, eventMixin); // mixin ke saare methods Menu.prototype pe copy kar diye

let menu = new Menu();
menu.on("select", value => alert(`Selected: ${value}`)); // subscribe
menu.choose("123");       // -> "Selected: 123" alert hoga

Note: Object.assign(Menu.prototype, eventMixin) — extend nahi kiya, sirf copy kiya prototype pe. Isliye Menu abhi bhi apni khud ki koi aur class extend kar sakti hai, aur multiple mixins ek saath apply ho sakte hain — ye vahi limitation solve karta hai jo single-inheritance chain ke saath nahi ho sakta tha.

🧠 Senior Dev Note: mixin vs inheritance — kab kya choose karo

Inheritance ("is-a" relationship) use karo jab subclass logically parent ka specialized version ho — Rabbit extends Animal. Mixin ("has-a-capability") use karo jab behavior orthogonal ho aur multiple unrelated classes mein reusable ho — jaise event-emitting ya serialization. Real-world frameworks (React ke purane mixins pattern, Vue ke composables/HOC patterns) is exact tension pe evolve hue hain — deep inheritance chains debug karna mushkil ho jaata hai ("fragile base class problem"), jabki mixins flat aur composable rehte hain. Agar tumhe apni class hierarchy mein 3+ levels ka inheritance dikhe, wahaan ruk ke socho ki kya wo actually ek mixin/composition problem hai.

Key Takeaways

  • class runtime pe ek function hi banati hai — methods non-enumerable prototype properties ban jaate hain, aur constructor ko [[IsClassConstructor]]: true flag milta hai jo bina new ke call hone se roakta hai.
  • Derived class constructors ka [[ConstructorKind]]: "derived" hota hai — this tab tak "uninitialized" rehta hai jab tak super() call na ho, isliye super() se pehle this touch karna ReferenceError deta hai.
  • super.method() internally [[HomeObject]] use karta hai, this.__proto__ nahi — isliye super-using methods safely copy nahi kiye ja sakte.
  • Statics extends se inherit hote hain user classes ke beech (class-to-class prototype link ke through) — lekin built-in classes (Array, Object, etc.) ye statics-inheritance rule follow nahi karti.
  • _protected sirf convention hai, koi enforcement nahi; #private language-level enforced hai — this["#name"] bracket notation bhi kaam nahi karta.
  • Array jaisi built-ins extend karte waqt .map()/.filter() default mein subclass instance return karte hain — Symbol.species static getter se ye behavior explicitly override kiya ja sakta hai.
  • instanceof default mein prototype chain walk karta hai; Symbol.hasInstance defined ho to wahi priority pe use hota hai.
  • Mixins Object.assign(Target.prototype, mixin) se implement hote hain — single-inheritance ki limitation ke around ek composition-based workaround.

🎯 Interview Questions

  • class ek "syntax sugar" hai — ye statement kahaan sach hai aur kahaan galat?
    Hint: runtime object-shape (function + prototype) same hai, lekin [[IsClassConstructor]], non-enumerable methods, aur constructor call-ordering (derived classes) jaise enforcement semantics function-pattern se strictly zyada hain.
  • Derived class constructor mein super() se pehle this access karne pe error kyun aata hai?
    Hint: derived constructor ka [[ConstructorKind]]: "derived" hai — object khud nahi banata, parent (super) se banwata/init karwata hai; jab tak super() nahi chala, this exist hi nahi karta.
  • super.method() resolve kaise hota hai internally — this.__proto__ se ya kuch aur se?
    Hint: [[HomeObject]] internal property, method jahaan define hua wahi fixed reference — copy karne pe bhi wahi rehta hai, jisse super-using methods safely copy nahi ho sakte.
  • Array ko extend karne par .filter() se aaya result subclass ka instance kyun hota hai, aur ise kaise control karte ho?
    Hint: built-in methods this.constructor use karte hain naya instance banane ke liye, jab tak Symbol.species override na ho — usse explicitly Array (ya koi aur constructor) specify kar sakte ho.
  • #private field aur _protected convention mein exact difference batao, ek concrete escape-hatch example ke saath.
    Hint: this["#name"] bracket notation private field ke liye kaam nahi karta (undefined milta hai), jabki this["_name"] protected ke liye normally kaam karta hai — # ek separate lexical binding hai, string-keyed property nahi.
  • instanceof custom kaise kar sakte ho, aur ye default prototype-walk se kaise differ karta hai?
    Hint: static [Symbol.hasInstance](obj) method define karo class pe — ye default __proto__ chain walk ko completely bypass kar deta hai, custom logic (e.g. duck-typing check) allow karta hai.
  • Static members extends se inherit hote hain — kaise, aur built-in classes iska exception kyun hain?
    Hint: Child.__proto__ === Parent (class-function-to-class-function link) — user classes mein ye set hota hai, lekin built-ins (Array, Object, etc.) ye link maintain nahi karti apas mein.
  • Mixin approach single inheritance ki limitation ko kaise solve karta hai, aur super-using methods ko mixin mein rakhna kyun risky hai?
    Hint: Object.assign se prototype pe copy karke multiple sources se behavior mila sakte ho bina ek hi parent chain mein locked hue; lekin [[HomeObject]] fixed hone ki wajah se super() wale methods copy hone ke baad galat parent resolve kar sakte hain.
