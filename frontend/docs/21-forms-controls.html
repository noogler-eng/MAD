Forms & Controls

Form ek "mini DOM" hai — document.forms se leke form.elements tak sab live named collections hain. Form navigation — document.forms, form.elements

Har <form> automatically document.forms naam ki ek special collection ka member ban jaata hai — ye collection named aur indexed dono tarah se access hoti hai, kyunki ye ek HTMLCollection hai jo name attribute ke basis pe named lookup bhi support karta hai. Similarly, form ke andar ke controls form.elements collection mein aa jaate hain.

document.forms + form.elements
<form name="my">                        <!-- name="my" ke wajah se ye document.forms.my ban jaata hai -->
  <input name="one" value="1">        <!-- name="one" — form.elements.one se access hoga -->
  <input name="two" value="2">        <!-- name="two" — form.elements.two se access hoga -->
</form>

<script>
  let form = document.forms.my;              // document.forms se named access — form DOM node milta hai
  let form2 = document.forms[0];          // same collection indexed access bhi support karta hai (document order)

  let elem = form.elements.one;          // form.elements — form ke andar ke sab controls ki live named collection
  alert(elem.value);                    // "1" — input.value property se actual current value milti hai

  // shorter notation — form.elements chhod ke seedha form pe property access
  alert(form.one.value);              // "1" — form.one bhi wahi element deta hai (form.elements.one ka shortcut)
</script>

form.elements ek live collection hai — root-level pe ye HTMLFormControlsCollection type ka hota hai, jo document ke actual DOM se backed hai. Iska matlab agar tum runtime pe koi <input> add/remove karo, collection automatically update ho jaati hai — ye ek static array/snapshot nahi hai. Ye same "live collection" pattern hai jo childNodes, getElementsByTagName waghera mein bhi dikhta hai — DOM APIs ka ek consistent design decision.

Same-name elements — radio buttons ka collection

Jab multiple elements same name share karte hain (jaise radio button group), to form.elements[name] ek single element nahi, balki ek sub-collection deta hai:

Radio group — form.elements.age ek collection hai
<form name="my">
  <input type="radio" name="age" value="10"> <!-- pehla radio, same name="age" -->
  <input type="radio" name="age" value="20"> <!-- dusra radio, same name="age" -->
</form>

<script>
  let form = document.forms.my;
  let ageElems = form.elements.age;       // duplicate name ki wajah se ye ek RadioNodeList collection hai, single node nahi

  alert(ageElems[0]);              // pehla <input type="radio"> element

  // RadioNodeList ka .value getter bhi special hai — jo radio checked hai uska value seedha deta hai
  alert(ageElems.value);              // jo bhi radio abhi checked hai uska value — checked radio dhoondhne ka loop nahi likhna padta
</script>

Root-level: form.elements.age internally ek RadioNodeList return karta hai — ye HTML spec ka ek dedicated type hai, jisme .value getter checked radio ka value directly deta hai. Ye ek chhota lekin practical detail hai jo manually querySelectorAll('input:checked') likhne se bachata hai.

🧠 Senior Dev Note: backreference aur fieldset

Har form control ka apna .form property hota hai jo waapas parent form ko point karta hai — input.form === form. Ye bidirectional navigation useful hai jab tumhe ek input event handler ke andar poore form tak access chahiye, bina DOM traverse kiye (event.target.form). Agar form ke andar <fieldset> hai, to fieldset khud ek "subform" jaisa behave karta hai — uska apna .elements hota hai jisme sirf uske andar ke controls hote hain, lekin outer form.elements mein bhi wahi controls flat list mein aate hain. Renaming: agar tum name attribute badal do, purana naam turant kaam karna band nahi karta — browser thodi der backward-compat rakhta hai, lekin production code mein isपे depend mat karo.

focus/blur events aur methods

focus event tab fire hota hai jab element focus paata hai, blur tab jab wo focus khota hai. In dono ka classic use-case hai validate-on-leave pattern:

Validate on blur, clear error on focus
input.onblur = function() {          // jab user field se hat ke kahin aur click/tab kare
  if (!input.value.includes('@')) {   // value mein "@" nahi hai — invalid email
    input.classList.add('invalid');       // visually error state dikhane ke liye CSS class add karo
    error.innerHTML = 'Sahi email daalo.'; // user-facing error message dikhao
  }
};

input.onfocus = function() {         // jab user wapas field pe click/tab kare
  if (this.classList.contains('invalid')) { // agar pehle se invalid marked hai
    this.classList.remove('invalid');   // error class hatao — user retry kar raha hai
    error.innerHTML = "";        // error message bhi clear kar do
  }
};

Programmatically focus control karne ke liye elem.focus() aur elem.blur() methods hain. Ek common pattern hai user ko invalid field se bahar jaane se rokna, focus() wapas call karke:

Focus wapas force karna on invalid data
input.onblur = function() {
  if (!this.value.includes('@')) {   // invalid value hai
    this.classList.add("error");      // error styling do
    input.focus();                  // force karo focus wapas isी field pe aa jaaye
  } else {
    this.classList.remove("error");   // valid hai to error class hata do
  }
};
⚠️ event.preventDefault() blur ko cancel nahi kar sakta

Root cause: onblur handler us waqt run hota hai jab element already focus kho chuka hota hai — ye "after the fact" notification hai, "about to happen" wala intercept-able event nahi. Isliye event.preventDefault() ka yahan koi asar nahi hota. Agar tumhe user ko field mein "trap" karna hai, to sirf ek hi tareeka hai — jaise upar diya, khud se focus() call karke user ko waapas la do.

autofocus ek HTML attribute hai jo page load pe hi kisi element pe focus daal deta hai — <input autofocus>. Isse form pe seedha typing shuru ho sakti hai bina user ko click karne ki zaroorat ke.

tabindex — kisi bhi element ko focusable banana

By default sirf interactive elements (input, button, a href waghera) focusable hote hain — elem.focus() ek plain <div> pe kaam nahi karta, focus/blur events fire hi nahi hote. Ye badalne ke liye tabindex attribute lagate hain:

tabindex order — root mechanism
<ul>
  <li tabindex="1">One</li>      <!-- positive tabindex: explicit order mein sabse pehle aate hain (1 se badhte hue) -->
  <li tabindex="0">Zero</li>     <!-- tabindex="0": focusable ban gaya, lekin document-order-based (positive ke baad) -->
  <li tabindex="2">Two</li>      <!-- positive tabindex: 1 ke baad number 2 aata hai -->
  <li tabindex="-1">Minus one</li> <!-- negative: Tab key se skip hota hai, sirf elem.focus() se hi focus milega -->
</ul>
<!-- Tab-key press order: One(1) -> Two(2) -> Zero(0), fir document order wale baaki elements -->

Root-level semantics: positive values ek explicit numeric priority set karte hain (chhote number pehle, browser inhe sabse pehle Tab-cycle karta hai); tabindex="0" element ko document-flow order mein focusable bana deta hai (jaise wo naturally interactive ho, bas custom position add nahi karta); aur tabindex="-1" Tab-key navigation se element ko hata deta hai lekin elem.focus() call se programmatic focus abhi bhi kaam karta hai — ye pattern accessibility mein bahut use hota hai (jaise modal open hone pe usе focus() se le jaana, lekin background content Tab se skip ho).

focus/blur bubble NAHI karte — focusin/focusout use karo

⚠️ Real gotcha: event delegation focus/blur pe kaam nahi karega

focus aur blur events bubble nahi karte. Agar tum form pe ek single onfocus/onblur listener laga ke expect karo ki wo child inputs ke focus/blur events ko catch karega (event delegation ki tarah jaise click pe hota hai), wo kaam nahi karega — event sirf us exact element tak limited rehta hai jisne focus paaya/khoya. Solution: focusin aur focusout events use karo — ye same cheez track karte hain lekin bubble karte hain, aur inhe sirf addEventListener se attach kar sakte ho, on<event> property se nahi (elem.onfocusin jaisa kuch nahi hota).

focusin/focusout — form-level delegation
<form id="form">
  <input type="text" name="name" value="Name">       <!-- pehla input -->
  <input type="text" name="surname" value="Surname"> <!-- dusra input -->
</form>

<style> .focused { outline: 1px solid red; } </style>

<script>
  // focusin sirf addEventListener se attach hota hai — form.onfocusin bilkul kaam nahi karega
  form.addEventListener("focusin", () => form.classList.add('focused'));
  // koi bhi child input focus paaye — event bubble ho ke form tak pahunchta hai, class add ho jaati hai

  form.addEventListener("focusout", () => form.classList.remove('focused'));
  // child input focus khoye — bubble hoke class remove ho jaati hai
  // NOTE: agar user ek input se dusre input mein Tab kare (dono form ke andar),
  // to focusout+focusin dono fire honge, lekin class remove-then-add hone se koi flicker nahi dikhta
  // kyunki browser same microtask/synchronous cycle mein handle karta hai
</script>

Root cause ye hai: bubbling events "target se document tak" propagate hote hain taaki ancestors unhe suno saken. focus/blur ko spec-writers ne intentionally non-bubbling banaya kyunki agar ye bubble karte, to nested focusable elements ke case mein (jaise ek contenteditable ke andar ek input) bahar ke saare ancestors bhi "focus paaya" event receive karte, jo confusing hota. focusin/focusout baad mein add kiye gaye taaki delegation use-case explicitly serve ho sake.

input vs change — root-level timing difference

Ye do events bahut confuse karte hain naye developers ko, kyunki dono "value change hone pe" fire hote lagte hain — lekin unka timing fundamentally alag hai:

  • input — har single character/value modification pe turant fire hota hai — keyboard se type karo, mouse se paste karo, ya voice-to-text — jo bhi actual value change kare. Ye "live" event hai.
  • change — sirf tab fire hota hai jab value "committed" ho — text input/textarea ke liye ye blur (focus loss) par hota hai (agar value badla ho), aur select/checkbox/radio ke liye turant selection change hone par (kyunki wahan koi intermediate "typing" state hoti hi nahi).
Contrast: live character counter (input) vs validate-on-commit (change)
<label>Bio (live counter uses <b>input</b>):</label>
<textarea id="bio" maxlength="140"></textarea>
<span id="counter">140</span> characters left

<label>Username (validate uses <b>change</b>):</label>
<input type="text" id="username">
<span id="usernameStatus"></span>

<script>
  // ===== Part 1: input event — LIVE character counter =====
  const bio = document.getElementById('bio');       // textarea reference lo
  const counter = document.getElementById('counter'); // counter span reference lo

  bio.addEventListener('input', () => {       // har keystroke/paste pe fire hoga — is wajah se "live" hai
    const remaining = 140 - bio.value.length; // har call pe fresh length nikaalo
    counter.textContent = remaining;       // counter turant update — user ko real-time feedback
    counter.style.color = remaining < 10 ? 'red' : ''; // limit ke paas ho to red warning
  });
  // AGAR yahan 'change' use karte, to counter tab tak update hi nahi hota jab tak user
  // textarea se blur na kare — jo ek "live" counter ke liye bilkul useless UX hota

  // ===== Part 2: change event — validate-on-COMMIT, harek keystroke pe nahi =====
  const username = document.getElementById('username'); // input reference
  const status = document.getElementById('usernameStatus'); // status span

  username.addEventListener('change', () => {   // sirf blur pe (ya Enter dabane pe) fire hoga, na ki har character pe
    // simulate karo ek "check-username-availability" API call — ye expensive hoti hai
    status.textContent = `Checking "${username.value}"...`; // commit hone ke baad hi ek baar call trigger hota hai
    // agar yahan 'input' use karte, to server pe har keystroke pe ek expensive availability-check
    // request jaati — bina debounce ke ye network aur backend dono ko overload kar dega
  });
</script>
🧠 Senior Dev Note: kab kya use karo

Root-level rule of thumb: UI jo turant respond karna chahiye (character counters, live search-as-you-type suggestions, real-time formatting/masking, enabling/disabling a submit button based on current text) — wahan input. Expensive ya commit-semantics wala kaam (server validation, analytics event, triggering a recalculation that's costly) — wahan change, ya input ko manually debounce karke. Select/checkbox/radio jaise "discrete choice" controls mein input aur change practically same waqt fire hote hain (koi intermediate typing state nahi hoti), isliye wahan farak matter nahi karta — differences sirf free-text fields (text/textarea) mein critical hote hain. Ek aur gotcha: input event ke andar event.preventDefault() ka koi effect nahi hota, kyunki ye event value change ho chuke hone ke baad fire hota hai — action already commit ho chuka.

cut, copy, paste events

Ye teeno ClipboardEvent class ke instances hain aur clipboard data tak access dete hain — aur ye cancellable hain (unlike input), matlab preventDefault() se action rok sakte ho:

Paste block/inspect karna
<input type="text" id="input">

<script>
  input.onpaste = function(event) {          // paste hone se pehle fire hota hai
    const pasted = event.clipboardData.getData('text/plain'); // clipboardData se plain text nikaalo
    alert("paste: " + pasted);            // jo copy hua tha wo dikhao
    event.preventDefault();                // actual paste ko cancel kar do — input mein text nahi aayega
  };

  input.oncut = input.oncopy = function(event) { // dono cut aur copy ke liye same handler
    alert(event.type + '-' + document.getSelection()); // selected text dikhao (event.type se pata chalega cut ya copy)
    event.preventDefault();                // clipboard operation cancel — copy/cut nahi hoga
  };
</script>
⚠️ cut/copy handler ke andar clipboardData khaali milta hai

oncut/oncopy ke andar event.clipboardData.getData(...) call karoge to empty string milegi. Root cause: ye events data actual clipboard mein jaane se pehle fire hote hain — us waqt tak OS-level clipboard update hua hi nahi hota. Isliye cut/copy mein tumhe data document.getSelection() se khud nikaalna padta hai (jaise upar example mein), event.clipboardData se nahi — sirf onpaste mein clipboardData reliably populated hota hai kyunki wahan data already source se aa chuka hai.

submit event aur form submission

submit event tab fire hota hai jab form submit ho raha ho — do tareeke se trigger hota hai: (1) <input type="submit">/button pe click, ya (2) kisi text input mein focus ke saath Enter dabana (jo internally submit button pe ek synthetic click event trigger karta hai).

submit event intercept karna
<form id="myForm">
  <input type="text" name="query" value="text"> <!-- Enter dabane se bhi submit trigger hoga -->
  <input type="submit" value="Submit"> <!-- click se bhi submit trigger hoga -->
</form>

<script>
  myForm.onsubmit = function(event) {       // submit event handler — event object milta hai
    alert('submit!');                    // koi validation ya custom logic yahan
    return false;                        // return false = preventDefault() ka shorthand — page reload nahi hoga
  };
</script

form.submit() method se programmatically bhi submit kar sakte ho — lekin ye submit event fire nahi karta:

form.submit() — event bypass hota hai
let form = document.createElement('form');   // naya form element runtime pe banaya
form.action = 'https://example.com/search'; // kahan submit karna hai
form.method = 'GET';                // GET method use karo

form.innerHTML = '<input name="q" value="test">'; // ek hidden-jaisa input daala

document.body.append(form);          // DOM mein daalna zaroori hai submit karne ke liye

form.submit();                     // direct submit — onsubmit handler CALL NAHI hoga, browser seedha navigate karega

Root cause: form.submit() spec ke hisaab se ek "programmer already validate kar chuka" signal maana jaata hai — browser assume karta hai ki tum ye method jaan-boojh ke call kar rahe ho after doing your own checks, isliye redundant validation-hook (submit event) skip kar deta hai. Iske contrast mein form.requestSubmit() (newer API) hai — ye ek "real" user-initiated submit ki tarah behave karta hai, matlab submit event normally fire hota hai (aur agar koi <button type="submit"> pass karo to uski validity bhi check hoti hai) — jab tumhe "jaise user ne submit button dabaya waisa hi trigger karo, lekin code se" chahiye, tab requestSubmit() zyada correct choice hai submit() ke bajaye.

Real example: AJAX-based form submit (page reload roknA)

Modern SPA-style forms full page reload nahi karte — submit event ko intercept karke fetch se background mein data bhejte hain:

preventDefault + fetch — no page reload
<form id="loginForm" action="/api/login" method="POST">
  <input name="email" type="email" required>   <!-- required: HTML5 built-in validation bhi chalti hai submit se pehle -->
  <input name="password" type="password" required>
  <button type="submit">Login</button>
</form>

<script>
  const form = document.getElementById('loginForm');   // form reference

  form.addEventListener('submit', async (event) => { // async handler taaki fetch await kar sakein
    event.preventDefault();          // SABSE PEHLE ye — warna browser default full-page GET/POST navigation kar dega

    const formData = new FormData(form); // form ke sab named fields ko FormData object mein pack karo

    try {
      const res = await fetch(form.action, {  // form.action attribute se URL uthaya — HTML aur JS ek hi source of truth share karte hain
        method: form.method,       // form.method attribute se HTTP method uthaya (yahan "POST")
        body: formData             // fetch FormData ko seedha samajhta hai — multipart body auto-serialize hoti hai
      });

      if (!res.ok) throw new Error(`Login failed: ${res.status}`); // non-2xx status pe manually error throw karo

      const data = await res.json();   // response body ko JSON parse karo
      alert(`Welcome, ${data.name}!`);  // no page reload — SPA mein state update ya redirect JS se karo
    } catch (err) {
      alert('Error: ' + err.message); // network/HTTP error ko user ko dikhao, form reset mat karo taaki wo retry kar sake
    }
  });
</script>

Ye pattern form.action/form.method attributes ko hi source-of-truth rakhta hai (progressive enhancement ke liye achha — JS disabled ho to bhi form normal HTML submit kar sakta hai server-side), lekin JS enabled hone par preventDefault() se default navigation rok ke, wahi data fetch se background mein bhej deta hai — bina full page reload ke.

Key Takeaways

  • document.forms aur form.elements live named+indexed collections hain — DOM change hone par apne aap update hoti hain.
  • Same-name elements (radio groups) ke liye form.elements[name] ek RadioNodeList collection deta hai, jiska .value checked radio ka value directly return karta hai.
  • focus/blur bubble nahi karte — delegation ke liye focusin/focusout use karo (sirf addEventListener se attach hote hain).
  • onblur mein preventDefault() kaam nahi karta kyunki event focus chale jaane ke baad fire hota hai — trap karna ho to focus() wapas call karo.
  • tabindex="0" = document-order focusable, positive value = explicit numeric priority, tabindex="-1" = sirf programmatic focus, Tab se skip.
  • input = har value-change pe turant (live UI ke liye); change = sirf commit (blur/Enter) pe (expensive/validation logic ke liye).
  • cut/copy handler ke andar clipboardData khaali hota hai (data abhi clipboard mein gaya nahi); paste mein reliably populated hota hai.
  • form.submit() submit event skip karta hai; user-triggered submit jaisa behavior chahiye to form.requestSubmit() use karo.
  • AJAX form pattern: submit event pe preventDefault(), phir FormData + fetch se background submission.

🎯 Interview Questions

  • form.elements aur document.forms live collections kyun hain, static array kyun nahi?
    Hint: ye directly DOM tree se backed hain — DOM APIs ka consistent pattern (childNodes, getElementsByTagName bhi live hote hain) taaki har baar manually re-query na karna pade.
  • focus/blur events bubble kyun nahi karte, jabki click karta hai?
    Hint: agar bubble karte to nested focusable elements (jaise contenteditable ke andar input) ke case mein saare ancestors "focus paaya" event receive karte — confusing hota; delegation ke liye alag focusin/focusout events specifically add kiye gaye.
  • input aur change event ka fundamental timing difference kya hai, aur kab kaunsa use karoge?
    Hint: input = har modification pe turant (live UI, character counters); change = commit pe (blur/Enter) ya discrete-choice controls pe turant — expensive/validation logic ke liye behtar.
  • oncut/oncopy handler ke andar event.clipboardData.getData() khaali kyun aata hai?
    Hint: ye events data actual OS clipboard mein jaane se PEHLE fire hote hain — onpaste mein hi clipboardData reliably populated hota hai kyunki data already source se aa chuka hota hai.
  • form.submit() aur form.requestSubmit() mein kya farak hai?
    Hint: submit() spec ke hisaab se ek "already-validated" programmer signal maana jaata hai isliye submit event skip karta hai; requestSubmit() ek real user-click jaisa behave karta hai, submit event normally fire hota hai aur button validity bhi check hoti hai.
  • Enter key se form submit hone par internally kya hota hai?
    Hint: focused text input mein Enter dabane se browser internally us form ke <input type="submit"> pe ek synthetic click event trigger karta hai, jo phir normal submit flow follow karta hai.
  • tabindex="-1" ka practical use-case kya hai?
    Hint: Tab-key navigation se element hata deta hai (keyboard users usse naturally skip karte) lekin elem.focus() se programmatic focus abhi bhi kaam karta hai — modals/dialogs mein initial focus set karne ke liye common pattern.
