RegExp I — Syntax

Regex sirf ek "pattern matching syntax" nahi hai — ye ek chhota compiled finite-state-ish engine hai jo pattern ko internally instructions mein compile karta hai aur input string pe character-by-character run karta hai. Is chapter mein hum syntax ki surface se shuru karke, root mein jaake dekhenge ki flags actual engine behavior kaise badalte hain — matching algorithm ke level tak.

Literal /pattern/flags vs new RegExp()

JavaScript mein regex banane ke do tareeke hain. Dono ka final result same object type hota hai — RegExp instance — lekin unki parse-time behavior alag hai.

regex-syntax.js
// Literal syntax — engine ye pattern ko compile-time pe hi parse kar leta hai
// jab JS file load hoti hai, tab hi regex object ban jaata hai (function body ke andar bhi)
const re1 = /hello/i;              // re1: pattern "hello", flag i = case-insensitive

// Constructor syntax — pattern runtime pe ek STRING ke roop mein pass hota hai
// isliye ye dynamic patterns ke liye zaroori hai (variable interpolation ke saath)
const userInput = "hello";              // userInput: runtime pe pata chalne wali value (jaise search box se aayi)
const re2 = new RegExp(`${userInput}`, "i");
                                       // re2: same pattern, lekin build hua ek template string se — YE literal syntax se possible NAHI
                                       // kyunki /${userInput}/i mein ${} sirf literal text treat hota, interpolate nahi hota

re1.test("Hello World");               // true — case-insensitive match hua "Hello" se
re2.test("Hello World");               // true — dono ka behavior identical hai, sirf construction ka tareeka alag

Root cause jo isse important banata hai: literal syntax mein pattern parse-time literal hai — JS engine source code parse karte waqt hi regex-specific tokens ko validate/compile kar leta hai (ek chhota optimization bhi hai kyunki repeated calls pe re-parse nahi hota agar regex ek hi jagah declare hai). Constructor syntax mein pattern ek plain string hai jo runtime pe regex compiler ko pass hoti hai — isliye har baar new RegExp(...) call hone par fresh compilation hoti hai, aur string escaping ka ek extra layer bhi involve hota hai (neeche "Escaping" section mein detail).

Flags: g i m s u y — engine ke andar kya badalta hai

Flags sirf "options" nahi hain — har flag matching algorithm ke ek specific stage ko modify karta hai. Neeche har flag ka root-level effect:

  • g (global) — Engine ek match milne ke baad lastIndex position ko update karta hai aur wahin se agla match dhoondhta rehta hai, poori string scan hone tak. Bina g ke, engine pehla match milte hi ruk jaata hai. Ye lastIndex property regex object pe hi store hoti hai — isliye same global regex instance ko reuse karna stateful hai (gotcha: agar tum ek hi /pattern/g object ko baar-baar .test() pe call karo, har call agli position se start hoti hai, na ki shuru se).
  • i (case-insensitive) — Character comparison stage mein, engine har character ko match karne se pehle case-fold karta hai (uppercase/lowercase dono ko same "canonical" form mein normalize karke compare karta hai) — actual string modify nahi hoti, sirf comparison logic case ko ignore karta hai.
  • m (multiline) — ^ aur $ anchors ke "boundary definition" ko badalta hai: default mein sirf poori string ka start/end boundary count hota hai, m ke saath har \n ke aas-paas bhi ek naya boundary create hota hai (detail neeche).
  • s (dotall) — . (dot) character class ki definition badalta hai: normally dot "kuch bhi except \n" match karta hai; s flag ke saath dot literally kuch bhi match karta hai, newline included.
  • u (unicode) — Engine ke internal "character iteration unit" ko UTF-16 code-unit se badal ke Unicode code-point kar deta hai — matlab 4-byte characters (surrogate pairs) ko ek single character treat karta hai, do nahi. Ye \p{...} property escapes ko bhi enable karta hai.
  • y (sticky) — g jaisa hi lastIndex-based hai, lekin strict hai: match exactly lastIndex position se start hona chahiye, agar wahan match na mile to engine aage scan nahi karta (jabki g string mein aage search karta rehta hai jab tak match na mile).
flags-demo.js
// g flag — lastIndex stateful behavior dikhane ke liye
const re = /\d+/g;                    // re: ek ya zyada digits dhoondo, globally
const str = "a1 b22 c333";       // str: test string jisme 3 number groups hain
console.log(re.exec(str)[0]);    // "1" — pehla match, aur re.lastIndex ab 2 pe set ho gaya
console.log(re.exec(str)[0]);    // "22" — engine ne 2nd exec() index 2 se shuru kiya, shuru se nahi
console.log(re.lastIndex);       // 7 — object khud apni "state" carry kar raha hai, ye common bug source hai

// s flag — dot ka default behavior override
const withoutS = /a.b/;          // dot bina s flag ke — \n ko match NAHI karega
const withS = /a.b/s;              // dot s flag ke saath — ab \n bhi match karega
console.log(withoutS.test("a\nb")); // false — newline ke beech dot break ho gaya
console.log(withS.test("a\nb"));    // true — s flag ne dot ki definition expand kar di

// y flag — strict position-locked match
const sticky = /foo/y;              // sticky: sirf exactly lastIndex se match karega
sticky.lastIndex = 3;            // manually search-start position set kiya
console.log(sticky.test("xxxfoo")); // true — index 3 pe exactly "foo" mila
sticky.lastIndex = 2;            // position 2 pe reset kiya (jahan "foo" nahi hai)
console.log(sticky.test("xxxfoo")); // false — g hota to aage scan karke mil jaata, y ne mana kar diya
📌 g flag ka statefulness ek common bug hai

Kyunki lastIndex regex object pe store hoti hai (string pe nahi), agar tum ek module-level shared /pattern/g regex ko multiple unrelated strings pe reuse karte ho, to results unpredictable ho sakte hain — kyunki har call previous call ki lastIndex se continue karti hai. Fix: .test()/.exec() loop khatam hone pe manually re.lastIndex = 0 reset karo, ya har baar naya regex literal banao.

Character classes: \d \w \s aur negations

Ye "shorthand character classes" hain — har ek internally ek bade character set ka shorthand hai (neeche [...] syntax dekhoge, ye shorthands usi ka compressed form hain):

  • \d — koi bhi digit. Equivalent to [0-9].
  • \D — koi bhi non-digit. Equivalent to [^0-9].
  • \s — koi bhi whitespace: space, tab \t, newline \n, aur rare cases \v, \f, \r. Equivalent to ek internal set jisme ye sab characters hain.
  • \S — koi bhi non-whitespace character.
  • \w — "word character": Latin letter (a-z, A-Z), digit (0-9), ya underscore (_). Equivalent to [a-zA-Z0-9_].
  • \W — koi bhi cheez jo \w mein nahi hai.
char-classes.js
// \D use karke phone number se sab non-digit characters strip karna
let str = "+7(903)-123-45-67"; // str: raw phone number formatting ke saath
str = str.replace(/\D/g, "");  // \D global match — har non-digit ko empty string se replace, matlab hata do
console.log(str);              // "79031234567" — sirf digits bache

// \w vs \W: identifier-jaisa token nikalna
const text = "user_1 @ email.com"; // text: mixed content string
console.log(text.match(/\w+/g)); // ["user_1", "email", "com"] — @ aur . word char nahi hain, so break points ban gaye

// IMPORTANT: \w mein sirf Latin letters hain — Devanagari/Cyrillic jaisi scripts include NAHI hoti
const hindi = "नमस्ते world";  // hindi: Devanagari text ke saath English word
console.log(hindi.match(/\w+/g)); // ["world"] — Devanagari characters \w se poori tarah miss ho gaye

Unicode flag u aur \p{...} property escapes

Ye is chapter ka sabse "root-level" gotcha hai. JavaScript strings internally UTF-16 encoded hain — matlab har character ek ya do "code units" (16-bit blocks) leta hai. Basic Multilingual Plane ke characters (English letters, common symbols) ek code unit lete hain. Lekin emoji jaise 😄, ya kuch rare mathematical symbols jaise 𝒳, 4 bytes ke hote hain — do 16-bit code units mein encode hote hain, jinhe surrogate pair kehte hain.

Bina u flag ke, regex engine (aur .length jaisi string operations) har 16-bit code unit ko ek "character" maan leti hain — matlab ek emoji ko galti se do characters gin lete hain. u flag engine ke internal iteration unit ko code-unit se code-point pe shift kar deta hai, taaki surrogate pair ko ek hi logical character treat kare.

unicode-flag.js
// Root problem: emoji ka .length 2 aata hai, 1 nahi
console.log('😄'.length);      // 2 — kyunki ye ek surrogate pair hai (do UTF-16 code units)

// dot (.) character class bina u flag ke: sirf ek code unit match karta hai
let str = '😄';            // str: single emoji character (do code units internally)
console.log(str.match(/./)[0].length); // 1 — BUG: sirf half surrogate pair match hui (broken character)
console.log(str.match(/./u)[0].length); // 2 — CORRECT: u flag ne poori surrogate pair ko ek unit treat kiya

// \p{...} property escapes — u flag ke bina ye syntax hi INVALID hai
const mixedLetters = "A ब ㄱ";  // mixedLetters: Latin, Devanagari, aur Korean letters mixed
console.log(mixedLetters.match(/\p{L}/gu)); // ["A","ब","ㄱ"] — \p{L} = koi bhi Unicode "Letter" category, script-agnostic
                                       // yaad rahe: \w yahan Devanagari/Korean skip kar deta, \p{L} nahi karta

// Hex digit detection Unicode property se
const hexRe = /x\p{Hex_Digit}\p{Hex_Digit}/u; // pattern: literal 'x' + 2 hex-digit-property characters
console.log("number: xAF".match(hexRe)[0]); // "xAF" — matched successfully

// Currency symbol detection — real-world use: multi-currency price parsing
console.log("Prices: $2, €1, ¥9".match(/\p{Sc}\d/gu)); // ["$2","€1","¥9"] — \p{Sc} = Unicode "Currency Symbol" category
🧠 Senior Dev Note: u flag production mein kab kaatega

User-generated content (bio, chat messages, usernames) jahan emoji common hai, wahan koi bhi regex-based character-counting, truncation, ya validation logic silently corrupt ho sakti hai bina u flag ke — jaise ek emoji ko "2 characters" gin ke half-surrogate pe string truncate kar dena, jisse ek broken/invalid Unicode character render hota hai (typically "�" jaisa glyph). Rule of thumb: agar tum arbitrary user text pe regex chala rahe ho jisme non-ASCII content ho sakta hai, u flag default se lagao — cost near-zero hai, benefit correctness hai.

Anchors ^ aur $

^ aur $ "zero-width assertions" hain — ye actual characters match nahi karte, sirf ek position test karte hain (jaise "kya hum string ke start pe hain?"). Isliye ye matched result mein koi character add nahi karte, sirf ek condition validate karte hain.

  • ^ — default mein sirf string ke bilkul shuru pe match karta hai (index 0).
  • $ — default mein sirf string ke bilkul end pe match karta hai.
anchors.js
const str1 = "Mary had a little lamb"; // str1: test string for start check
console.log(/^Mary/.test(str1)); // true — string "Mary" se hi shuru ho rahi hai

const str2 = "its fleece was white as snow"; // str2: test string for end check
console.log(/snow$/.test(str2)); // true — string "snow" pe hi end ho rahi hai

// Combine karke poori string ka strict format validate karna — bahut common pattern
const timeRe = /^\d\d:\d\d$/;       // timeRe: exactly "digit digit : digit digit", pura string
console.log(timeRe.test("12:34"));   // true — exact format match
console.log(timeRe.test("12:345"));  // false — $ ke wajah se extra "5" ke saath match fail ho gaya
console.log(timeRe.test("x12:34")); // false — ^ ke wajah se leading "x" ke saath match fail ho gaya

Multiline mode ka effect ^ $ pe

m flag anchors ki "boundary definition" ko expand karta hai. Default mein ^ aur $ sirf poori string ke absolute start/end pe match karte hain. m flag ke saath, engine har \n ke around bhi ek naya boundary treat karta hai — matlab string boundaries ki jagah line boundaries use hoti hain.

multiline.js
const text = `1st place: Winnie
2nd place: Piglet
3rd place: Eeyore`;                     // text: multi-line template literal, 3 lines, har line ek digit se shuru

// Bina m flag ke: ^ sirf poori string ke shuru mein match karta hai
console.log(text.match(/^\d/g));    // ["1"] — sirf pehli line ka digit mila

// m flag ke saath: ^ har line ke start pe bhi match karta hai
console.log(text.match(/^\d/gm));   // ["1","2","3"] — teeno lines ke leading digits mile

// $ ka behavior bhi symmetric hai — har line-end pe test hota hai
console.log(text.match(/e$/gm));     // letter "e" jo kisi line ke end pe ho — sirf "Eeyore" match karta (line 3)

// Important farak: \n aur $ dono line-end dhoondh sakte hain, lekin \n MATCHED text mein shaamil ho jaata hai
console.log(text.match(/\w\n/g).length); // 2 — sirf un lines pe match jinke baad ACTUAL \n character hai (last line ke baad nahi)
console.log(text.match(/\w$/gm).length); // 3 — $ zero-width hai, character consume nahi karta, teeno lines ke end match hue including last
⚠️ $ zero-width hai — ye result mein character add NAHI karta

Ye common confusion hai: \n ek literal character hai jo matched string mein shamil ho jaata hai (aur agar last line ke baad koi \n nahi hai to wo line miss ho jaati hai); $ sirf ek position-test hai jo poori string ke last line ko bhi cover karta hai bina uske baad literally koi newline hone ki zaroorat ke. Isliye line-ending detection ke liye generally $ (with m flag) zyada robust choice hai \n literal se.

Word boundary \b — exact definition

\b bhi ^/$ jaisa ek zero-width position test hai, lekin common misconception ye hai ki log isse "space" samajh lete hain. Ye galat hai. Exact definition: ek position jahan ek taraf \w (word character) ho aur doosri taraf "not \w" ho — ya string ka start/end ho jab wahan word character ho. Space isme incidentally involve hota hai kyunki space \w nahi hai, lekin boundary sirf spaces tak limited nahi — punctuation, string-start, string-end, sab qualify karte hain.

word-boundary.js
// \b ek standalone word "Java" dhoondta hai, "JavaScript" ke andar wale "Java" ko nahi
console.log("Hello, Java!".match(/\bJava\b/));       // ["Java"] — dono taraf "not \w" hai (comma-space aur '!')
console.log("Hello, JavaScript!".match(/\bJava\b/)); // null — "Java" ke baad "S" ek \w character hai, so wahan boundary nahi hai

// \b sirf letters tak limited nahi — digits pe bhi kaam karta hai
const nums = "1 23 456 78";    // nums: mixed-length number groups
console.log(nums.match(/\b\d\d\b/g)); // ["23","78"] — exactly-2-digit standalone groups; "456" 3-digit hai so andar ke 2 digits boundary-fail

// CRITICAL LIMITATION: \w mein sirf Latin letters/digits/underscore hain, isliye \b non-Latin scripts pe fail hota hai
const hindi = "नमस्ते दुनिया";     // hindi: do Devanagari words, space se separated
console.log(hindi.match(/\b\w+\b/g)); // null (ya empty) — Devanagari characters \w mein count hi nahi hote, boundary bilkul detect nahi hota
🧠 Senior Dev Note: multilingual text mein \b use mat karo

Production codebase mein agar tum non-English user content (names, addresses, Hindi/regional language content) pe \b-based word-matching use kar rahe ho, ye silently fail hoga — kyunki \w ki definition Latin-only hai. Iske liye better approach hai Intl.Segmenter (word segmentation ke liye proper Unicode-aware API) ya \p{L} based custom boundary logic use karna, jo hum RegExp III chapter (lookaround) mein explore karenge.

Escaping special characters

In characters ka regex syntax mein special meaning hai, isliye inhe literally match karne ke liye backslash se escape karna padta hai: [ ] { } ( ) \ ^ $ . | ? * +

escaping.js
// Literal dot escape karna — bina escape ke "." koi bhi character match kar leta
console.log("Chapter 5.1".match(/\d\.\d/)[0]); // "5.1" — \. ne literal dot ko match kiya, kisi bhi character ko nahi

// / character ko escape karna zaroori hai literal syntax mein (pattern delimiter clash)
const pathRe = /\/api\/v1/;       // pathRe: literal "/api/v1" match karta hai — har / ko \/ escape karna pada
console.log(pathRe.test("/api/v1/users")); // true

// new RegExp() ke saath double-escaping gotcha — string literal pehla backslash layer consume kar leta hai
const wrong = new RegExp("\d\.\d");  // GALAT: string "\d\.\d" processing ke baad ban jaata hai "d.d" (backslash consume ho gaya)
const right = new RegExp("\\d\\.\\d"); // SAHI: double backslash — string ban ke "\d\.\d" hi banega, sahi regex pattern
console.log(right.test("5.1"));          // true
console.log(wrong.test("5.1"));          // false — pattern actually "d.d" ban gaya tha, "5.1" mein literal "d" nahi hai
⚠️ Root cause: string escaping aur regex escaping do alag layers hain

new RegExp("string") ka argument pehle ek JS string literal ke roop mein parse hota hai (jahan \d jaisi sequence ko JS engine "unknown escape" treat kar ke usually literal d bana deta hai), aur uske baad wo resulting string regex compiler ko pass hoti hai. Isliye har backslash jo tum regex ke liye chahte ho, use string layer se surviving rakhne ke liye double karna padta hai. Literal /pattern/ syntax mein ye extra layer hai hi nahi — backslash directly regex compiler tak jaata hai.

Character sets aur ranges [...] / [^...]

Square brackets ek "set" define karte hain — engine us position pe exactly ek character match karega jo set ke andar diye options mein se koi ho.

char-sets.js
// Basic set — [tm]op matches "top" ya "mop", "t" ya "m" mein se koi ek
const words = "Mop top hop";   // words: teen similar words
console.log(words.match(/[tm]op/gi)); // ["Mop","top"] — "hop" match nahi hua, "h" set mein nahi tha

// Range syntax — hyphen se interval specify hota hai
const hexColor = /^#[0-9A-F]{6}$/i; // pattern: # ke baad exactly 6 hex characters (digit ya A-F)
console.log(hexColor.test("#d97757")); // true — 0-9 range aur A-F range combine ho gaye ek set mein

// Negated set — [^...] "in aksharo ke ALAWA kuch bhi" match karta hai
const noVowels = "sky".match(/[^aeiou]/gi); // [^aeiou]: koi bhi character jo vowel NAHI hai
console.log(noVowels);          // ["s","k","y"] — "sky" mein koi vowel hai hi nahi, so sab characters match hue

// [^0-9] practically \D ka expanded/explicit equivalent hai
console.log("a1b2".match(/[^0-9]/g)); // ["a","b"] — same result jo \D deta

// Special characters ke sets ke ANDAR ka behavior — j.a.d.a permissive hai
const special = /[.+()]/g;          // set ke andar . + ( ) apni special meaning KHO dete hain — literal ban jaate hain
console.log("a.b+c(d)".match(special)); // [".","+","(",")"] — bina escape kiye hi literally match hue

// EXCEPTION: ] hamesha escape chahiye set ke andar, warna set close ho jaayega galat jagah
// EXCEPTION: - sirf escape chahiye agar range banane ki niyat nahi hai (edges pe nahi to safe hai)
// EXCEPTION: ^ sirf agar set ke bilkul start mein hai to escape chahiye (warna negation ban jaayega)
⚠️ Surrogate pairs sets ke andar bhi u flag maangte hain

Agar tum kisi character set mein ek surrogate-pair character (jaise 𝒳 ya emoji) include karte ho bina u flag ke, engine use do alag code units treat karega — jisse set ka behavior unpredictable ho sakta hai (galat characters match ho sakte hain, ya set corrupt ho sakta hai). Yehi Unicode consistency rule hai jo poore is chapter mein repeat ho raha hai: jahan bhi non-ASCII content involve ho, u flag lagao.

Key Takeaways

  • Literal /pattern/flags compile-time parse hota hai; new RegExp() runtime string se banta hai — dynamic patterns ke liye zaroori, lekin backslash double-escaping chahiye.
  • g flag regex object pe lastIndex state maintain karta hai — shared/reused global regex ek common statefulness bug source hai.
  • s flag sirf dot (.) ki definition expand karta hai (newline included); m flag sirf ^/$ ki boundary definition change karta hai.
  • u flag engine ke internal character-iteration unit ko UTF-16 code-unit se Unicode code-point pe shift karta hai — emoji/rare symbols ko sahi se ek character count karne ke liye zaroori.
  • \d \w \s shorthand classes hain, expanded character sets ke — aur \w sirf Latin letters/digits/underscore tak limited hai, non-Latin scripts miss ho jaate hain.
  • \b "space" nahi, balki "\w se non-\w transition (ya string boundary)" detect karta hai — non-Latin text pe silently fail hota hai.
  • Character sets [...] ke andar zyadatar special characters literal ban jaate hain — sirf ], edge-position -, aur leading ^ ko escape/position-care chahiye.

🎯 Interview Questions

  • Literal regex syntax aur new RegExp() constructor mein kab kaunsa use karoge, aur inki internal difference kya hai?
    Hint: literal compile-time parse hoti hai (dynamic interpolation possible nahi), constructor runtime string se banta hai (dynamic patterns ke liye zaroori, lekin har backslash double karna padta hai string-escaping ki wajah se).
  • Ek shared /pattern/g regex object ko multiple independent strings pe reuse karne mein kya bug ho sakta hai?
    Hint: lastIndex regex object pe stored hoti hai, string pe nahi — agli call previous call ki position se continue hoti hai jab tak manually reset na karo.
  • u flag ke bina emoji jaisa 4-byte character regex mein kaise problem create karta hai?
    Hint: emoji UTF-16 mein surrogate pair (2 code units) hai; bina u ke engine har code unit ko alag character treat karta hai, so . jaisa pattern sirf half-character match karega, aur .length bhi 2 aayega, 1 nahi.
  • Multiline mode (m flag) exactly kya badalta hai anchors mein — aur ye \n literal character se kaise different hai line-detection ke liye?
    Hint: m flag ^/$ ko har \n ke around bhi match karne deta hai (line boundaries); \n ek literal consuming character hai jo matched result mein aata hai aur last line (jiske baad newline nahi) ko miss kar sakta hai, jabki $ zero-width hone ki wajah se usse bhi cover karta hai.
  • \b ka exact definition kya hai, aur log ise "space" kyun maan lete hain incorrectly?
    Hint: \b ek position hai jahan ek taraf \w ho aur doosri taraf non-\w ho (ya string start/end); space isme incidentally involve hota hai kyunki wo non-\w hai, lekin punctuation aur string boundaries bhi equally qualify karte hain.
  • Character set [...] ke andar kaunse characters ko escape karna zaroori hai, aur kaunse automatically literal ban jaate hain?
    Hint: ] hamesha escape chahiye, - sirf agar range intent nahi hai aur edges pe nahi, ^ sirf leading position pe (warna negation ban jaata) — lekin . + ( ) jaise operators set ke andar automatically literal ho jaate hain, escape ki zaroorat nahi.
  • Kyun \w-based word boundary detection multilingual (non-Latin) content pe fail hota hai, aur iska better alternative kya hai?
    Hint: \w spec ke hisaab se sirf Latin letters/digits/underscore include karta hai; better approach hai \p{L}-based custom logic ya Intl.Segmenter jo proper Unicode-aware word segmentation deta hai.
