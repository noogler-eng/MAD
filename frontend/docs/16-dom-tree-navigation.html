DOM Tree & Navigation

Ab tak humne pure JS language padha — koi browser involved nahi tha. Ab Part 2 shuru hota hai: browser environment. Browser humein ek window object deta hai jiske andar poora page ek tree of objects ke roop mein represent hota hai — DOM. Ye chapter root-level samjhata hai ki ye tree kaise bana hai, class hierarchy kaisi hai (Node → Element → HTMLElement), tree ko kaise walk karte hain, elements kaise search karte hain, aur innerHTML/textContent jaise properties internally kya karte hain — performance aur security dono angle se.

Browser environment: window, DOM, BOM

Browser mein JavaScript engine (V8, SpiderMonkey, etc.) akela nahi hota — usse ek host environment milta hai jo extra objects aur functions provide karta hai jo pure language spec ka hissa nahi hain. Browser ke case mein us host environment ka root object hai window. Ye do roles play karta hai ek saath:

  1. Ye JavaScript ka global object hai — top-level var aur global functions window ke properties ban jaate hain.
  2. Ye "browser window" ko represent karta hai — window.innerHeight, window.open(), etc. iske through browser control hota hai.
window: global object + browser window, dono ek saath
function sayHi() {          // top-level function declaration — global scope mein define ho rahi hai
  alert("Hello");    // simple alert call
}

window.sayHi();       // proof: global function automatically window ki property ban gayi — global object hai isliye

alert(window.innerHeight); // yahaan window "browser window" ke role mein hai — viewport height batata hai

Root-level pe browser environment 3 pillars pe khada hai:

  • DOM (Document Object Model) — page ka pura content (HTML) objects ke tree ke roop mein represent karta hai. Entry point hai document. Standard maintain karta hai DOM Living Standard — matlab ye sirf JS ka feature nahi, ek independent cross-language spec hai (Python, PHP se bhi DOM manipulate ho sakta hai agar binding available ho).
  • CSSOM (CSS Object Model) — stylesheets aur rules ko represent karta hai, separate spec.
  • BOM (Browser Object Model) — document ke alawa browser jo kuch bhi deta hai: navigator (browser/OS info), location (current URL, redirect), alert/confirm/prompt. BOM ka koi alag formal spec nahi hai — HTML spec ke andar hi cover hota hai ("HTML spec sirf tags/attributes ke baare mein nahi, bahut se browser-specific objects/methods bhi define karta hai").
DOM aur BOM ka farak — ek quick demo
document.body.style.background = "red"; // DOM manipulation — page content/style badla

alert(location.href);            // BOM — current page ka URL, DOM se koi lena-dena nahi
location.href = "https://wikipedia.org"; // BOM — browser ko naye URL pe navigate karwa diya
📌 Root mechanism: DOM sirf HTML ke liye nahi hai

DOM spec generically "any structured document" ke liye bana hai — HTML aur XML dono is model se represent hote hain. Browser HTML parser jo bhi parse karta hai, wo isi generic tree model mein convert hota hai. Isliye document.querySelector jaisi APIs XML documents pe bhi kaam karti hain (jaise SVG, jo XML-based hai) — kyunki wo DOM ke upar operate karti hain, HTML-specific nahi hain.

DOM tree ka structure — node types

Browser HTML ko parse karke ek tree of node objects banata hai — is tree ka formal naam hai DOM. Har HTML tag ek element node banta hai, aur tags ke andar ka text ek text node banta hai. Root object document hai.

Ek simple HTML aur uska DOM tree
<!DOCTYPE html>
<html>
<head>
  <title>About elk</title>  <!-- text node "About elk" title ke andar -->
</head>
<body>
  The <a href="http://ya.ru">elk</a> lives.
  <!-- Comment -->                        <!-- ye bhi ek node hai — comment node, DOM tree ka part banta hai -->
</body>
</html>

Practice mein 4 node types matter karte hain:

  • Document node — poore tree ka root, JS mein document object.
  • Element nodes — har HTML tag (<html>, <body>, <a>, ...).
  • Text nodes — tags ke beech ka text, including whitespace/newlines. "Spaces aur newlines bhi valid characters hain" — inse bhi text node bante hain. Isliye <head> ke andar <title> se pehle indentation ka whitespace bhi ek separate #text node hota hai.
  • Comment nodes — <!-- ... --> bhi tree ka part banta hai, "har cheez HTML mein, comments tak, DOM ka hissa ban jaati hai." Screen pe render nahi hota, lekin document.body.childNodes mein dikhega.
🧠 Senior Dev Note: browser HTML ko autocorrect karta hai

Jo tree banta hai wo tumhare likhe hue raw HTML se match nahi karta — browser ka HTML parser malformed ya incomplete markup ko silently fix kar deta hai. Agar <html>, <head>, <body> missing hain, wo automatically insert ho jaate hain. Agar tumne <table> likha bina <tbody> ke, HTML spec ke rules ke mutabik parser khud <tbody> insert kar dega. Iska practical impact: jab tum table.children access karoge, ek extra <tbody> level milega jo tumne source mein likha hi nahi tha — bahut common confusion point hai naye devs ke liye.

Node class hierarchy — DOM sirf "objects ka tree" nahi, ek real class system hai

Root-level samajhna zaroori hai: DOM nodes plain objects nahi hain, ye ek proper JS class hierarchy ke instances hain (specification mein defined). Har node type apni class se aata hai, aur ye classes inherit karti hain ek dusre se:

  • EventTarget — sabse upar, sirf events ke liye (addEventListener capability).
  • Node — isse saare node types inherit karte hain (Element, Text, Comment, Document). parentNode, childNodes jaisi properties yahin define hain.
  • Element — sirf element nodes ke liye base class. children, querySelector, closest yahin define hain.
  • HTMLElement — HTML-specific elements ke liye, innerHTML, hidden, style yahaan define hote hain.
  • Aur phir tag-specific classes jaise HTMLInputElement, HTMLAnchorElement — jinke apne specific properties hote hain (input.value, a.href).
Inheritance chain ko console mein dekho
let elem = document.body;              // <body> element node reference le liya

alert(elem.constructor.name);       // "HTMLBodyElement" — sabse specific class jo body tag ko represent karti hai

alert(elem instanceof HTMLBodyElement); // true — exact class match
alert(elem instanceof HTMLElement);     // true — chain mein upar HTMLElement se inherit karta hai
alert(elem instanceof Element);          // true — aur upar Element se bhi
alert(elem instanceof Node);             // true — sabse upar Node se bhi
alert(elem instanceof EventTarget);      // true — root class, event listeners yahin se milte hain

Isi hierarchy ki wajah se children, closest() sirf Element nodes pe available hain (text/comment nodes pe nahi — unke paas ye method hi nahi hota, prototype chain mein missing hai), jabki parentNode, childNodes sab node types pe kaam karte hain kyunki wo Node level pe define hain — ye pure OOP design hai, arbitrary rule nahi.

Walking the DOM — parentNode, children, siblings

DOM navigation properties do categories mein bat jaate hain: "all nodes" properties (text/comment bhi include) aur "element only" properties (sirf tags).

All-node navigation vs element-only navigation
// ---- ALL NODES (Node class se aati hain — text/comment bhi count hote hain) ----
document.body.parentNode;          // immediate parent node (koi bhi type ho sakta hai)
document.body.childNodes;          // LIVE collection — elements + text nodes + comment nodes, sab kuch
document.body.firstChild;          // pehla child, chahe wo whitespace text node hi kyun na ho
document.body.lastChild;           // aakhri child node

// ---- ELEMENT ONLY (Element class se aati hain — sirf tags, koi text/comment nahi) ----
document.body.children;            // LIVE collection — sirf element children, whitespace filter ho gaya
document.body.firstElementChild; // pehla ELEMENT child (text node skip ho jaata hai)
document.body.lastElementChild;  // aakhri element child

let elem = document.querySelector('li'); // koi ek <li> element pakad liya reference ke liye
elem.nextElementSibling;        // agla sibling ELEMENT (agle whitespace text node ko ignore karke)
elem.previousElementSibling;    // pichla sibling element
elem.parentElement;              // parent — lekin sirf agar wo Element ho (document nahi)
⚠️ children vs childNodes — real gotcha jo bugs deta hai

Ye difference sirf naming convention nahi hai — production bugs ka ek common source hai. Agar tum element.childNodes[0] use karke "pehla child element" pakadne ki koshish karoge, aur us element ke andar HTML source mein indentation/newline hai (jo almost hamesha hota hai jab tum HTML ko readable format mein likhte ho), to childNodes[0] ek whitespace text node hoga, koi element nahi. Result: .tagName access karne pe undefined, ya silent wrong behavior. Rule: jab tumhe sirf elements chahiye (manipulation, styling, structure ke liye), children /firstElementChild use karo. Jab tumhe text content bhi chahiye ho (parsing, jaise text nodes ko directly modify karna), tabhi childNodes use karo.

Table elements extra convenience properties dete hain jo underlying tree navigation ka shortcut hain — ye bhi Element hierarchy ke specific subclasses (HTMLTableElement, HTMLTableRowElement) pe define hote hain:

Table-specific navigation shortcuts
let table = document.querySelector('table');  // table element pakda

let td = table.rows[0].cells[1];      // rows[0]: pehli <tr>, phir cells[1]: usme dusra <td>/<th>
td.style.backgroundColor = 'red';       // ab uss specific cell ka background change kar diya

// table.rows automatically <tbody>/<thead>/<tfoot> ke andar se rows nikaal deta hai,
// manually .querySelector('tbody').children se navigate karne ki zaroorat nahi

Searching elements — querySelector, getElementBy*, closest, matches

Direct tree-walking (children, firstElementChild) chhote, known-shape structures ke liye theek hai, lekin real apps mein hum usually seedha ek specific element ya set of elements search karte hain.

Search methods — ek comparison
// getElementById — sirf document pe call hota hai, single element, sabse fast
let elem = document.getElementById('main'); // id="main" wala element, ya null agar exist nahi karta

// querySelectorAll — koi bhi CSS selector, STATIC NodeList return karta hai
let items = document.querySelectorAll('ul > li:last-child');
                                            // har <ul> ke andar aakhri <li> — powerful CSS selector syntax

// querySelector — pehla match, querySelectorAll(sel)[0] ke barabar lekin FASTER
let first = document.querySelector('.card');   // pehla .card class wala element, ya null

// getElementsByClassName / TagName / Name — LEGACY, LIVE collection return karte hain
let cards = document.getElementsByClassName('card'); // sab .card elements, live HTMLCollection
closest() aur matches() — event delegation ki foundation
// matches(selector): current element khud us selector se match karta hai kya, boolean return
if (elem.matches('a[href$="zip"]')) { // href .zip pe end hota hai kya, check
  alert("zip link!");              // tab hi ye chalega
}

// closest(selector): khud se shuru karke UPWARD walk karta hai jab tak selector match na ho
let chapter = elem.closest('.chapter'); // elem khud ya uska nearest ancestor jo .chapter class rakhta ho

// EVENT DELEGATION pattern — closest() ka sabse bada real-world use case (Chapter 19 mein detail)
document.body.addEventListener('click', function(event) {
  let button = event.target.closest('.btn');
                    // click chahe button ke andar ke <span> icon pe hua ho, closest() khud button tak upar chala jaata hai
  if (!button) return;       // agar click .btn ke bahar hua (koi ancestor match nahi), ignore kar do
  console.log('button clicked:', button); // ek hi listener, saare buttons ke liye — chahe DOM mein baad mein add hue hon
});

closest() internally almost matches() ko har ancestor pe repeatedly call karne jaisa hi kaam karta hai — ye hi mechanism hai jo event delegation ko possible banata hai: ek single listener parent pe laga do, aur andar event.target.closest(selector) se pata karo ki actual click kis logical element pe tha, chahe DOM structure kitna bhi nested ho.

Live vs static collections — modify-while-iterate gotcha

Ye ek core distinction hai jo har senior dev ko yaad hona chahiye: getElementsBy* family live collections return karti hai, jabki querySelectorAll static collection deta hai (ek snapshot, uss moment ka). childNodes / children bhi live hote hain (Node/Element class level pe defined).

Live collection ka real gotcha — infinite loop tak ban sakta hai
let divs = document.getElementsByTagName('div'); // LIVE HTMLCollection — DOM se hamesha sync rehta hai

for (let i = 0; i < divs.length; i++) {
  let clone = divs[i].cloneNode(true);    // har div ka deep clone banaya
  document.body.appendChild(clone); // naya div DOM mein daal diya
  // BUG: divs.length ab AUR BADH GAYA hai (naya div bhi 'div' tag hai, live collection mein turant aa gaya)
  // so loop kabhi khatam nahi hoga jab tak koi limit na ho — practically infinite loop!
}

// FIX 1: static collection use karo, jo iteration ke beech DOM change se unaffected rahe
let staticDivs = document.querySelectorAll('div'); // snapshot loop start hone se pehle liya gaya, baad ke changes reflect nahi honge

// FIX 2: agar live hi use karna hai, to pehle Array mein convert kar lo (khud static ban jaayega)
let arr = Array.from(divs);          // snapshot le liya, ab safely iterate kar sakte hain, map/filter bhi use kar sakte hain
⚠️ Live collections read-only hain, but "reactive"

childNodes[i] = something jaisa direct assignment kaam nahi karta — collections array nahi hain, unke paas push/splice jaise methods bhi nahi hote. Sirf DOM structure badalne se (appendChild, removeChild) ye automatically update hoti hain — ye "reactive" hain lekin "mutable via index assignment" nahi. Array methods chahiye to Array.from(collection) ya spread [...collection] use karo.

Node type/tag/content properties

Har node object kuch core properties expose karta hai jo uska type aur content batate hain — inheritance hierarchy ke exact level pe defined (Node vs Element vs HTMLElement, jaisa upar discuss kiya).

nodeType, nodeName vs tagName
alert(document.body.nodeType); // 1 — ELEMENT_NODE constant (numeric, read-only, purani style checking)
alert(document.nodeType);       // 9 — DOCUMENT_NODE, document khud bhi ek node hai (root)

alert(document.body.tagName); // "BODY" — sirf Element nodes pe available (Element class ki property)
alert(document.tagName);       // undefined — document Element nahi hai, isliye tagName exist hi nahi karta

alert(document.body.nodeName); // "BODY" — nodeName Node class pe defined hai, HAR node type pe kaam karta hai
alert(document.nodeName);       // "#document" — non-element nodes ke liye descriptive string milti hai
innerHTML vs outerHTML vs textContent — internals aur perf
// innerHTML: element ke ANDAR ka HTML string ke roop mein — reading aur writing dono
alert(document.body.innerHTML);     // current markup string ke roop mein padh liya
document.body.innerHTML += "<div>new</div>";
      // DANGER: += ka matlab "purana + naya" ko STRING ban ke phir se PARSE karo
      // pura subtree destroy hoke naye sirse banta hai — images reload, event listeners LOST, scroll reset,
      // selection/focus lost — expensive re-parse + re-render, sirf ek div add karne ke liye

// outerHTML: element SAMET uska HTML — assign karne pe DOM mein element REPLACE ho jaata hai
let div = document.querySelector('div');
div.outerHTML = "<p>New</p>"; // DOM mein purana <div> hat gaya, naya <p> aa gaya
// GOTCHA: 'div' variable ab bhi PURANE (ab DOM se disconnected) element ko point karta hai —
// JS reference update nahi hota, sirf actual DOM tree replace hota hai

// textContent: sirf PLAIN TEXT — koi HTML parsing nahi, tags literally text ban jaate hain
let userInput = "<img src=x onerror=alert(1)>"; // maan lo ye kisi user ne type kiya

elem.innerHTML = userInput;  // DANGEROUS: browser is string ko HTML samajh ke parse karega — img tag ban jaayega, onerror FIRE hoga → XSS
elem.textContent = userInput; // SAFE: string literal text ban jaata hai, "<img...>" as-is screen pe dikhega, code execute nahi hoga
⚠️ innerHTML + user input = XSS risk

Root cause samjho: innerHTML assign karte hi browser us string ko ek HTML parser se guzarta hai — string mein jo bhi valid HTML tags/attributes hain, wo real DOM nodes ban jaate hain, event handler attributes (onerror, onclick) samet. Agar wo string kisi bhi tarah user-controlled hai (form input, URL query param, API response jo kisi aur user ne likha), attacker apna JS inject kar sakta hai — classic stored/reflected XSS. Note: agar tum directly <script> tag innerHTML ke through insert karo, browser use HTML ka part to bana deta hai lekin execute nahi karta (spec-level protection) — par onerror/onload jaisi inline event attributes wale tags (img, svg, etc.) isse bach nikalte hain aur turant fire ho jaate hain. Rule: user-supplied ya untrusted content ke liye hamesha textContent use karo, ya agar HTML render karna hi hai to ek sanitization library (DOMPurify) se pehle clean karo.

🧠 Senior Dev Note: innerHTML+= ka real perf cost — production framework ka jaisa hi

Jab tum innerHTML ko read karte ho, browser current DOM subtree ko wapas HTML string mein serialize karta hai. Jab tum assign karte ho, wo string ko phir se parse karke ek naya subtree banata hai, aur purana poora subtree destroy kar deta hai — chahe tumne sirf ek chhota sa change kiya ho. Yehi wajah hai ki React/Vue jaisi frameworks raw innerHTML += se bachti hain aur ek virtual DOM diffing layer use karti hain — taaki sirf actual changed nodes update ho, poora subtree nahi. Agar tum vanilla JS mein bade DOM subtrees frequently update kar rahe ho, seedha innerHTML += use karne ki jagah targeted appendChild/ textContent updates ya DocumentFragment batching use karo — ye agla chapter (17) mein cover hoga.

Key Takeaways

  • window = global object + browser window control, dono ek saath; DOM/CSSOM/BOM teeno milke browser environment banate hain.
  • DOM ek real class hierarchy hai — Node → Element → HTMLElement → tag-specific classes. Property kis level pe available hai, ye batata hai kaunsa node type usse use kar sakta hai.
  • children (elements only) vs childNodes (elements + text + comments, whitespace samet) — HTML indentation ki wajah se production bugs ka common source.
  • getElementsBy* family live collections deti hai — iterate karte hue DOM modify karna infinite-loop-jaisa bug bana sakta hai. querySelectorAll static snapshot deta hai.
  • closest()/matches() event delegation ki foundation hain — ek listener, dynamic child elements.
  • innerHTML re-parse + rebuild karta hai (expensive, listeners/state lose hote hain); textContent plain text ke liye fast aur XSS-safe hai.
  • User-controlled data ko kabhi seedha innerHTML mein mat daalo — textContent use karo ya sanitize karo.

🎯 Interview Questions

  • children aur childNodes mein farak samjhao, aur ek real bug scenario batao jaha ye farak matter karta hai.
    Hint: childNodes text/comment nodes bhi include karta hai (whitespace se bane), children sirf elements. childNodes[0] pe blindly access karna bahut baar whitespace text node de deta hai.
  • Live aur static collections mein kya farak hai? Ek scenario batao jahan live collection bug create kar sakta hai.
    Hint: getElementsByTagName live hai — loop ke andar naye elements add karne se collection.length badhta rehta hai, potential infinite loop.
  • closest() internally kaise kaam karta hai, aur ye event delegation mein kyun critical hai?
    Hint: khud se shuru karke ancestors ki taraf upar walk karta hai jab tak selector match na ho; ek listener parent pe lagakar bhi specific dynamic children ko target kar sakte hain.
  • innerHTML ke through user input insert karna kyun dangerous hai, aur exact mechanism kya hai jisse XSS hota hai?
    Hint: innerHTML string ko HTML parser se guzarta hai, jismein inline event attributes (onerror, onload) turant fire ho sakte hain; script tag khud execute nahi hota par attribute-based vectors bach nikalte hain.
  • innerHTML += "..." expensive kyun hai, chahe tum sirf ek chhota element add kar rahe ho?
    Hint: pura subtree serialize hota hai to string, phir poora naya subtree parse+build hota hai, purana completely destroy — listeners/state/scroll sab lost.
  • nodeName aur tagName mein farak batao — kaunsi node types pe kaunsi available hai aur kyun?
    Hint: tagName sirf Element class pe defined hai (isliye document jaise non-element pe undefined), nodeName Node class pe hai isliye sab node types (text, comment, document) pe kaam karta hai.
  • parentNode aur parentElement mein ek exception case batao jahan ye alag result dete hain.
    Hint: document.documentElement (<html>) ka parentNode document hai, lekin document Element nahi hai (Document node hai), isliye documentElement.parentElement null return karta hai.
