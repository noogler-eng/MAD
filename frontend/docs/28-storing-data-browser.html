Cookies · localStorage/sessionStorage · IndexedDB

Storing Data in Browser

Browser mein data store karne ke teen fundamentally different tareeke hain — aur teeno alag trade-off lekar aate hain: document.cookie (HTTP protocol ka hissa, har request ke saath server tak jaata hai), localStorage/sessionStorage (client-side hi rehta hai, synchronous API, chhota storage), aur IndexedDB (async, transactional, large structured data ke liye). Ye chapter root-level samjhata hai ki har API internally kaise kaam karta hai, aur production mein kaunsa API kab use karna hai.

Cookies — ye storage API nahi, HTTP protocol ka hissa hai

Sabse pehli aur sabse important cheez samajhne wali: cookies koi "browser storage feature" nahi hain jo baad mein add kiya gaya — ye HTTP protocol level pe define hain (RFC 6265). Server response mein Set-Cookie header bhejta hai, browser use store kar leta hai, aur uske baad us domain ke matching har request mein browser automatically Cookie request header attach kar deta hai — chahe wo request <img> tag ho, CSS file ho, ya fetch call ho.

⚠️ Root-level perf cost: cookies har request ke saath jaate hain

Ye localStorage se sabse bada structural difference hai. localStorage ka data sirf client-side rehta hai — server ko kabhi automatically nahi bhejta. Lekin cookie ka data har matching request ke Cookie header mein serialize hoke jaata hai. Agar tumne 4KB ka cookie set kar diya, aur us domain se 50 static assets (images, fonts, JS chunks) load ho rahe hain, to wahi 4KB har ek request ke header mein baar-baar upload ho raha hai — real bandwidth cost, especially slow uplink (mobile networks) pe. Isliye production rule: cookies mein sirf wahi rakho jo server ko chahiye (session ID, auth token) — baaki client-side UI state localStorage mein rakho.

document.cookie se read aur write

document.cookie ek normal data property nahi hai — ye ek accessor property (getter/setter) hai. Iska matlab jab tum ise read karte ho, browser internally saare cookies ko ek "name1=value1; name2=value2" format ki string mein serialize karke deta hai. Aur jab tum ise write karte ho, browser sirf us ek cookie ko update karta hai jiska naam string mein diya — baaki saare cookies untouched rehte hain (ye counter-intuitive lagta hai kyunki normal property assignment poori value replace kar deta hai).

document.cookie — read aur write
// Ek naya cookie set karna — sirf iss "user" naam wale cookie ko touch karega
document.cookie = "user=Sharad"; // baaki existing cookies safe rehte hain, ye write "merge" jaisa behave karta hai

// Cookie name aur value mein special characters (space, ;, =) allowed nahi hote raw form mein
// isliye encodeURIComponent se encode karna best practice hai
let name = encodeURIComponent("my name"); // "my%20name" — space ko percent-encode kiya
let value = encodeURIComponent("Sharad Poddar"); // space wala value bhi encode karo
document.cookie = `${name}=${value}`; // template literal se "my%20name=Sharad%20Poddar" bana

// Reading — poori cookie string ek saath milti hai, khud parse karna padta hai
console.log(document.cookie); // "user=Sharad; my%20name=Sharad%20Poddar" jaisi ek semicolon-separated string

// Ek helper function jo specific cookie nikalta hai naam se
function getCookie(name) { // name param: jis cookie ka value chahiye
  let matches = document.cookie.match( // regex se cookie string ke andar match dhoondo
    new RegExp( // dynamic regex banate hain kyunki name variable hai
      "(?:^|; )" + name.replace(/([\.$?*|{}\(\)\[\]\\\/\+^])/g, '\\$1') + "=([^;]*)" // name ke regex-special chars escape karke pattern banaya
    )
  );
  return matches ? decodeURIComponent(matches[1]) : undefined; // match mila to decode karke return, warna undefined
}

// Cookie delete karna — koi delete() method nahi hai, past date set karke expire karte hain
document.cookie = "user=; expires=Thu, 01 Jan 1970 00:00:00 GMT"; // past date = browser turant is cookie ko delete kar deta hai
⚠️ Hard limits jo yaad rakhne hain

Ek baar mein sirf ek cookie set ho sakta hai (multiple ke liye multiple writes chahiye), har cookie ka size encoding ke baad max ~4KB hai, aur browser per domain sirf ~20+ cookies allow karta hai (exact limit browser-dependent). Ye limits hi ek strong signal hain ki cookies bulk client data store karne ke liye designed nahi hain — wo identifier/token carry karne ke liye hain.

Cookie attributes — scope aur lifetime control

Cookie set karte waqt document.cookie string mein attributes append kiye ja sakte hain — ye attributes cookie ki visibility scope aur lifetime control karte hain:

Cookie attributes ka full set
document.cookie = `session_id=abc123; 
  path=/;                           // path=/: is cookie ko poore site ke har URL path pe visible banao (default: current path)
  domain=site.com;                  // domain: sub-domains (forum.site.com) ke saath bhi share karo — default sirf exact domain
  expires=Fri, 12 Sep 2026 00:00:00 GMT;  // expires: absolute GMT date — is date tak persist karega, browser close hone pe bhi
  max-age=3600;                      // max-age: relative seconds (yahan 1 ghanta) — expires se zyada convenient, clock-skew-safe
  secure;                            // secure: cookie SIRF HTTPS request ke saath jayega, plain HTTP pe kabhi nahi
  samesite=lax`;                    // samesite: cross-site request ke saath ye cookie jaaye ya nahi, iska control (neeche detail)

// Attribute na diya expires/max-age to ye ek "session cookie" ban jaata hai —
// browser (poori window, sirf tab nahi) band hote hi delete ho jaata hai
document.cookie = "temp_flag=1"; // no expires/max-age given, so ye session-only cookie hai

Root cause samajhna zaroori hai: path aur domain dono milkar decide karte hain ki ek incoming request ke saath ye cookie Cookie header mein attach hoga ya nahi — matching algorithm request URL ke path/host ko cookie ke stored path/domain se compare karta hai. expires/max-age sirf storage duration control karte hain, matching logic ko affect nahi karte.

secure aur samesite — security-critical attributes

secure simple hai — plain HTTP connection pe cookie transmit hi nahi hota, isse network sniffing attacks (man-in-the-middle) se protect hota hai. samesite zyada interesting hai kyunki ye CSRF (Cross-Site Request Forgery) attacks ko root level pe mitigate karta hai.

🧠 Senior Dev Note: SameSite CSRF ko kaise rokta hai

CSRF attack mein, ek malicious site (evil.com) tumhare browser se bank.com ko ek request bhejwata hai (jaise ek auto-submitting form ya <img src="bank.com/transfer?...">). Bina samesite ke, browser us request ke saath bank.com ka session cookie automatically attach kar deta — kyunki browser ko sirf domain-match dekhna hai, request kahan se initiate hui ye matter nahi karta. samesite=strict is cookie ko kisi bhi cross-site request ke saath bhejne se rokta hai — chahe navigation ho ya sub-resource load. samesite=lax (modern browsers ka default agar attribute diya hi na ho) thoda relaxed hai: top-level navigation (user link click karke aata hai) ke saath GET request mein cookie jaata hai, lekin background POST/fetch/image jaisi cross-site requests mein nahi jaata. Yani lax normal "user ne link click kiya aur login state carry hui" use-case ko preserve karta hai, jabki hidden CSRF POST requests ko block karta hai.

httpOnly — cookies jo JavaScript se invisible hain

httpOnly attribute sirf server set kar sakta hai (Set-Cookie HTTP header ke through) — JavaScript se document.cookie ke through ye attribute add nahi kiya ja sakta, aur yehi iska poora point hai.

🧠 Senior Dev Note: session tokens httpOnly cookie mein rakho, localStorage mein nahi

Ye ek extremely common production mistake hai: auth/session token ko localStorage mein store karna kyunki "access karna easy hai". Root problem: agar tumhari site pe kahin bhi ek XSS vulnerability hai (third-party script, user-generated content, dependency vulnerability), to attacker ka injected JavaScript localStorage.getItem("token") call karke token directly chura sakta hai aur apne server ko exfiltrate kar sakta hai — poora account compromise. Lekin agar token httpOnly cookie mein hai, to document.cookie is cookie ko dikhata hi nahi — getItem jaisa koi equivalent access XSS script ke paas nahi hota. Cookie sirf HTTP request/response cycle mein hi transparently browser ke through travel karta hai, JS runtime se completely isolated. Isliye: session/auth tokens → httpOnly + secure + samesite cookie mein. Non-sensitive UI state (theme, draft form data, feature flags) → localStorage bilkul theek hai, wahan XSS token-theft ka risk nahi hai.

localStorage / sessionStorage — client-side key-value store

Ye dono Storage interface implement karte hain — ek simple synchronous key-value API jo sirf strings store karta hai (numbers/objects automatically string mein convert ho jaate hain, jaise object → "[object Object]", isliye complex data ke liye JSON.stringify/JSON.parse chahiye hota hai).

localStorage — full API
// setItem: key-value pair store/update karta hai
localStorage.setItem("theme", "dark"); // key "theme", value "dark" — dono strings hone chahiye

// getItem: key se value nikalta hai, na mile to null (undefined nahi!)
let theme = localStorage.getItem("theme"); // "dark" return hoga

// removeItem: ek specific key delete karta hai
localStorage.removeItem("theme"); // "theme" key hata do

// clear: poora storage empty kar deta hai (is origin ka)
localStorage.clear(); // sab kuch wipe — careful, irreversible hai

// Complex data ke liye JSON serialize karna padta hai
let user = { name: "Sharad", role: "dev" }; // ek plain object
localStorage.setItem("user", JSON.stringify(user)); // object ko JSON string bana ke store kiya
let restored = JSON.parse(localStorage.getItem("user")); // string wapas parse karke object bana liya

// Object-like access bhi kaam karta hai, LEKIN avoid karo
localStorage.test = 2; // ye "kaam" karta hai lekin storage event trigger nahi karta, aur "length" jaisi keys clash ho sakti hain

// length aur key(): saare stored keys ke through iterate karne ke liye
for (let i = 0; i < localStorage.length; i++) { // length = total stored keys count
  let key = localStorage.key(i); // index se key name nikalo
  console.log(key, "=", localStorage.getItem(key)); // key aur uska value print karo
}

sessionStorage ka API identical hai, lekin scope alag hai: localStorage origin (protocol + domain + port) ke andar saare tabs/windows mein shared hai aur browser restart ke baad bhi persist karta hai; sessionStorage sirf us ek tab tak scoped hai (naya tab khola to fresh/empty milega, chahe same URL ho) aur tab close hote hi delete ho jaata hai. Dono ki storage limit typically 5-10MB hai (browser-dependent), jo cookies ke 4KB se kaafi zyada hai.

Synchronous blocking nature — real perf gotcha

localStorage ka API synchronous hai — getItem/setItem call turant, blocking fashion mein return karti hai, koi Promise ya callback nahi.

⚠️ Root cause: main thread block hota hai

Kyunki localStorage synchronous hai, ye JavaScript ke main thread pe hi disk I/O perform karta hai (browser internally is data ko disk pe persist karta hai). Chhote reads/writes (kuch KB) mein farak nahi padta, lekin agar tum bade JSON blobs (sabse bade allowed limit ke close, jaise 1-2MB ka serialized state) baar-baar setItem/getItem kar rahe ho — jaise ek large form draft ya cached API response — to har call ke duration tak poora page frozen rehta hai: koi animation, koi click handler, kuch bhi respond nahi karega. Ye especially bura hai jab localStorage access kisi hot path mein ho (jaise har keystroke pe draft save karna). Mitigation: debounce/throttle karo writes ko, ya bade/frequent data ke liye IndexedDB use karo jo async hai aur main thread block nahi karta.

storage event — tabs ke beech state sync karna

Jab localStorage (method-based, object-property-based nahi) change hota hai, browser same origin ke doosre saare open windows/tabs mein (jis window ne change kiya usko chhod ke) ek storage event fire karta hai — ye cross-tab communication ka built-in, zero-dependency mechanism hai.

storage event — cross-tab sync example
// Tab A mein: user logout karta hai, localStorage se auth token clear kiya
localStorage.removeItem("authToken"); // Tab A mein hua ye change

// Tab B (same origin, doosra open tab) mein ye listener already registered tha:
window.addEventListener("storage", function(event) { // "storage" event listen karo window pe (localStorage change hone par)
  console.log(event.key);        // "authToken" — jo key change hui uska naam
  console.log(event.oldValue);  // purana value (jo delete se pehle tha)
  console.log(event.newValue);  // null hoga kyunki removeItem hua tha (clear() pe key bhi null hota hai)
  console.log(event.url);       // Tab A ka URL — jahan se ye change hua

  if (event.key === "authToken" && !event.newValue) { // agar authToken hi delete hua ho
    location.reload(); // is tab ko bhi logged-out state mein le aao — page reload karke
  }
});

Ye pattern real production mein bahut use hota hai: "user ne ek tab mein logout kiya to saare open tabs mein bhi logout ho jaaye", ya "ek tab mein cart update hua to doosre tab ka cart badge bhi turant update ho". Note: event sirf doosre tabs mein fire hota hai, jis tab ne change kiya usme nahi (waha tumhe pata hi hai ki tumne kya kiya) — aur ye sirf method-based (setItem/removeItem/clear) changes pe fire hota hai, object-property-style assignment (localStorage.x = 1) pe nahi.

IndexedDB — async, transactional, large structured storage

Jab data localStorage ke 5-10MB limit se bada ho, ya structure complex ho (nested objects, binary blobs, dates), ya tumhe query karna ho (range, index se search), to IndexedDB sahi tool hai. Ye ek full client-side database hai — object stores (tables jaisa), keys, indexes, aur ACID transactions ke saath, aur poora API asynchronous (event-based) hai — main thread block nahi karta.

Full IndexedDB example — open, create store, add, get

IndexedDB — database open karke record add/get karna
// Step 1: database open/create karo — naam "notesDB", version 1
let openRequest = indexedDB.open("notesDB", 1); // open() sync return nahi karta, ek "request" object deta hai jispe events lagte hain

// Step 2: upgradeneeded — pehli baar DB banaya ja raha ho, ya version number badha ho, to fire hota hai
openRequest.onupgradeneeded = function(event) { // yehi sirf jagah hai jahan schema (object stores) banaya ja sakta hai
  let db = openRequest.result; // db connection object yahin se milta hai upgrade ke andar

  if (!db.objectStoreNames.contains("notes")) { // agar "notes" store abhi tak nahi bana, to hi banao (idempotent)
    db.createObjectStore("notes", { keyPath: "id" }); // keyPath: "id" — har record ke "id" property ko primary key bana diya
  }
};

// Step 3: error — connection fail hone par
openRequest.onerror = function(event) { // e.g. user ne permission deny ki, ya storage quota exceed
  console.error("DB open error:", openRequest.error); // error object openRequest.error pe milta hai
};

// Step 4: success — DB ready hai, ab operations kar sakte hain
openRequest.onsuccess = function(event) { // upgradeneeded ke baad, ya agar version already latest thi to seedha yahan aata hai
  let db = openRequest.result; // ye db object ab saari future queries ke liye use hoga

  // Kisi doosre tab ne DB version upgrade kiya to purane connections ko close hona chahiye
  db.onversionchange = function() { // dusre tab mein naya version open ho raha hai
    db.close(); // is stale connection ko band karo taaki doosra tab upgrade kar sake
    console.log("DB outdated, please reload"); // user ko batao page refresh kare
  };

  // --- WRITE: ek record add karna ---
  let writeTx = db.transaction("notes", "readwrite"); // "notes" store pe readwrite transaction shuru kiya
  let notesStore = writeTx.objectStore("notes"); // us store ka reference nikala transaction ke andar se

  let addRequest = notesStore.add({ id: 1, title: "Root cause debugging", tag: "devops" }); // add() = insert only, "id":1 already exist hua to ConstraintError

  addRequest.onsuccess = function() { // individual request ka success — record insert ho gaya
    console.log("Note added"); // yahan tak transaction commit nahi hua, sirf ye request pura hua
  };

  writeTx.oncomplete = function() { // poora transaction commit ho chuka (durable, disk pe likha gaya)
    console.log("Write transaction committed"); // yahan se data guaranteed persisted hai
  };

  writeTx.onerror = function(event) { // transaction-level error — koi request fail hui to poori tx abort hoti hai (atomic)
    console.error("Write failed:", event.target.error); // error event.target.error se detail milti hai
  };

  // --- READ: same key se record wapas nikalna ---
  // NOTE: naya transaction — pehle wale ke complete hone ka wait nahi kiya, IndexedDB isse handle kar leta hai
  let readTx = db.transaction("notes", "readonly"); // readonly = multiple concurrent readonly tx allowed (readwrite exclusive hota)
  let getRequest = readTx.objectStore("notes").get(1); // key=1 wala record maango

  getRequest.onsuccess = function() { // get() ka result async milta hai
    console.log(getRequest.result); // { id: 1, title: "Root cause debugging", tag: "devops" } — ya undefined agar na mila
  };
};

Notice karo onupgradeneeded, onsuccess, aur onerror — IndexedDB ka har operation ek request object return karta hai jispe events lagte hain, Promise-based nahi hai natively (chahe modern wrapper libraries jaise idb ise promisify kar dete hain). Version number (open("notesDB", 1) mein 1) schema versioning ke liye hai — jab bhi tumhe schema change karna ho (naya object store, naya index), version number badhao, tab hi onupgradeneeded phir se fire hoga.

⚠️ "Inactive transaction" gotcha

IndexedDB transactions auto-commit ho jaate hain jab saari queued requests complete ho jaayein aur microtask queue drain ho jaaye — matlab transaction sirf tab tak "active" rehta hai jab tak tum synchronously (ya microtask ke andar) naye requests queue karte raho. Agar beech mein await fetch(...) ya setTimeout jaisa koi macrotask aa gaya, to us gap mein transaction already close ho chuka hoga — aur uske baad koi request try karoge to "transaction is inactive" error milega. Fix: pehle saara async/network work complete karo, uske baad IndexedDB transaction shuru karo — transaction ke andar sirf DB operations rakho, koi external async call nahi.

Key Takeaways

  • Cookies HTTP protocol ka hissa hain — har matching request ke saath automatically server ko jaate hain, isliye size/perf cost hai localStorage ke muqable.
  • document.cookie ek accessor property hai — write per-cookie merge karta hai, poori string replace nahi karta.
  • samesite attribute (strict/lax) cross-site requests ke saath cookie bhejne ko control karke CSRF attacks mitigate karta hai.
  • httpOnly cookies ko JavaScript se completely invisible bana deta hai — session tokens ke liye ye XSS token-theft se best protection hai; localStorage mein tokens rakhna anti-pattern hai.
  • localStorage/sessionStorage synchronous hain — bade/frequent reads-writes main thread ko block kar sakte hain, ye ek real perf gotcha hai.
  • storage event doosre same-origin tabs ko localStorage changes ke baare mein notify karta hai (method-based changes pe hi) — cross-tab sync ka zero-dependency tareeka.
  • IndexedDB async, transactional, large structured data ke liye designed hai — object stores, keyPath, indexes, versionchange lifecycle ke saath.
  • IndexedDB transactions macrotasks (fetch/setTimeout) ke beech aane pe auto-commit ho jaate hain — async work transaction shuru hone se pehle complete karo.

🎯 Interview Questions

  • Cookie aur localStorage mein sabse fundamental difference kya hai jo perf ko affect karta hai?
    Hint: cookies HTTP request ke saath server ko automatically jaate hain (har matching request pe), localStorage sirf client-side rehta hai — bandwidth cost ka farak.
  • samesite=lax aur samesite=strict mein practical farak kya hai, aur CSRF ko kaise rokta hai?
    Hint: strict kabhi bhi cross-site request pe cookie nahi bhejta; lax top-level GET navigation pe bhejta hai but background cross-site POST/fetch pe nahi — CSRF forged requests usually background/hidden hoti hain isliye lax bhi unhe rok deta hai.
  • httpOnly cookie session tokens ke liye kyun better hain localStorage se?
    Hint: httpOnly cookie JS se document.cookie ke through read hi nahi ho sakta, isliye ek XSS vulnerability bhi token ko directly exfiltrate nahi kar sakti; localStorage har JS code (including injected malicious script) ko fully accessible hai.
  • localStorage synchronous hone ka kya downside hai, aur kab ye real problem banta hai?
    Hint: main thread block hota hai disk I/O ke duration tak; bade ya frequent (hot-path) reads/writes pe UI freeze ho sakta hai — mitigation debounce ya IndexedDB.
  • storage event kis window mein fire NAHI hota, aur kis type ke changes pe trigger hota hai?
    Hint: jis window/tab ne khud change kiya usme fire nahi hota, sirf doosre same-origin tabs mein; sirf method-based (setItem/removeItem/clear) changes pe fire hota hai, object-property assignment pe nahi.
  • IndexedDB mein onupgradeneeded kab fire hota hai, aur schema changes sirf yahin kyun karne hote hain?
    Hint: jab DB pehli baar banta hai ya version number pehle se stored version se zyada diya jaata hai; ye ek special "versionchange" transaction hai jisme exclusive access guarantee hota hai, isliye object stores/indexes safely modify ho sakte hain.
  • "transaction is inactive" error IndexedDB mein kyun aata hai?
    Hint: transaction auto-commit ho jaata hai jab saari queued requests + microtasks complete ho jaayein; agar beech mein macrotask (fetch/setTimeout) aa jaaye to transaction pehle hi close ho chuka hota hai us gap mein.
  • add() aur put() mein IndexedDB ka farak kya hai?
    Hint: add() sirf naya record insert karta hai, agar key already exist karti hai to ConstraintError deta hai; put() insert-or-replace karta hai, existing key ho to overwrite kar deta hai.
