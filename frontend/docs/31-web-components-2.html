Web Components II

Pichle chapter mein humne Shadow DOM banana seekha — apna alag, encapsulated DOM tree jo custom element ke andar chhupa hota hai. Lekin ek real component (jaise <custom-menu> ya <user-card>) ko caller se content accept karna padta hai, styling ke liye externally control-points expose karne padte hain, aur uske andar fire hone wale events ko outside world se properly interact karna padta hai. Ye teeno cheezein — slots, Shadow DOM styling, aur Shadow DOM events — root level pe samajhte hain, kyunki inke internal mechanics mein hi saare production gotchas chhupe hain.

Light DOM vs Shadow DOM — "flattened DOM" ka concept

Ek custom element ke do separate DOM trees hote hain jo saath render hote hain: light DOM (jo caller ne <user-card>...</user-card> ke andar likha — ye normal document ka part hai) aur shadow DOM (jo component ne khud attachShadow() karke banaya — internal template). Browser in dono ko visually combine karke ek "flattened DOM" banata hai — lekin ye sirf render aur event-bubbling ke liye ek virtual view hai. JavaScript se element.children query karoge to tumhe wahi original, unflattened structure milega — light DOM ke elements literally shadow tree ke andar move nahi hote.

📌 Root mechanism

Slot distribution DOM ko mutate nahi karta — ye sirf render-time pe ek "assignment" hai: kaunsa light DOM node kaunse <slot> ki jagah visually render hoga. Isiliye node.parentNode abhi bhi original light DOM parent hi dikhayega, shadow tree ka element nahi.

Named slots aur distribution algorithm

Named slot ek specific insertion point define karta hai. Shadow DOM template mein <slot name="x"> likhte ho, aur light DOM ke direct children jinke paas slot="x" attribute hai, wahaan render ho jaate hain. Distribution algorithm ye hai: browser shadow tree ke har <slot> ko scan karta hai, uske name se match karne wale light-DOM direct children dhoondta hai, aur unhe us slot ki jagah insert kar deta hai — agar ek se zyada elements same name match karein, sab sequentially us ek slot mein append ho jaate hain.

custom-menu — named slot distribution
customElements.define('custom-menu', class extends HTMLElement { // naya custom element define karo
  connectedCallback() {                          // jab element document mein attach ho, ye chale
    this.attachShadow({ mode: 'open' });          // open shadow root banao — JS se outside se inspect ho sake
    this.shadowRoot.innerHTML = `              // shadow tree ka template string-based render
      <div class="menu">
        <slot name="title"></slot>       <!-- title-named slot: sirf ek matching child yahan aayega -->
        <ul><slot name="item"></slot></ul> <!-- item-named slot: SAB matching children yahan sequentially append honge -->
      </div>
    `;
  }
});
Light DOM usage — caller ka HTML
<custom-menu>                                     <!-- custom element ka usage, light DOM yahin se shuru -->
  <span slot="title">Candy menu</span>          <!-- DIRECT child, slot="title" — sirf DIRECT children hi eligible hain -->
  <li slot="item">Lollipop</li>              <!-- item-slot #1 -->
  <li slot="item">Fruit Toast</li>          <!-- item-slot #2 — same slot name, sequential append hoga -->
  <li slot="item">Cup Cake</li>             <!-- item-slot #3 -->
</custom-menu>

Flattened render output ek proper <ul> list banega jisme teeno <li slot="item"> sequentially hain — magar DOM tree mein woh li elements actual mein <custom-menu> ke hi direct children rehte hain, <ul> ke andar physically move nahi hote.

⚠️ Sirf DIRECT children eligible hain

slot attribute sirf shadow host ke direct children pe kaam karta hai. Agar <custom-menu><div><li slot="item">X</li></div></custom-menu> likha — ye li distribution mein ignore ho jaayega, kyunki uska direct parent custom-menu nahi, div hai. Slot distribution ek shallow (one-level) mechanism hai, deep tree-walk nahi karta.

Default slot + fallback content

<slot> jisme name attribute nahi hai, wo default slot ban jaata hai — jo bhi light DOM children ke paas slot attribute nahi hai, wo sab yahaan flow hote hain. Aur agar ek slot ke liye koi matching light DOM element hi nahi mila, to <slot> tag ke andar likha hua content fallback ki tarah render hota hai.

Default slot + fallback
shadowRoot.innerHTML = `
  <div>Name: <slot name="username">Anonymous</slot></div> <!-- agar slot="username" nahi mila, "Anonymous" dikhega -->
  <fieldset>
    <legend>Other info</legend>
    <slot></slot>                            <!-- name-less = default slot, jo bhi slot attribute NAHI wale children hain, sab yahan -->
  </fieldset>
`;

Fallback content DOM mein hamesha exist karta hai shadow tree ke andar — bas render hokar dikhta tab hai jab actual assignment empty ho. Ye pattern component APIs ke liye bahut useful hai: caller ko default UI free mein milta hai, override karna optional rehta hai.

slotchange event

Jab kisi slot ki assigned nodes list change hoti hai (naya element add/remove/replace hua), browser us <slot> element pe slotchange event fire karta hai. Note: agar assigned element ke andar ka text ya child change hota hai (structural slot assignment nahi badla), to slotchange nahi chalega — uske liye MutationObserver chahiye.

slotchange + assignedElements() se live items sync
class CustomMenu extends HTMLElement {
  connectedCallback() {
    this.attachShadow({ mode: 'open' });
    this.shadowRoot.innerHTML = `<div class="menu"><slot name="item"></slot></div>`;

    // firstElementChild = wrapper div; addEventListener slot-level events yahan bubble hoke pakde jaate hain
    this.shadowRoot.firstElementChild.addEventListener('slotchange', e => {
      let slot = e.target;                     // e.target = wahi <slot> jiski assignment badli
      if (slot.name == 'item') {            // sirf "item" slot ke changes track karo (multi-slot components mein useful)
        // assignedElements(): current assigned elements ka live array snapshot
        this.items = slot.assignedElements().map(el => el.textContent);
        console.log('items synced:', this.items);  // component ki internal state ko light-DOM changes ke saath sync rakho
      }
    });
  }
}

Root mechanism: node.assignedSlot property se koi bhi light-DOM node reverse-query kar sakta hai ki wo abhi kaunse slot mein assigned hai. Aur slot.assignedNodes({flatten: true}) nested components ke case mein deep-nested slots aur fallback content bhi expose kar deta hai — default (flatten: false) sirf direct assignments deta hai.

:host aur :host() — component apni khud ki wrapper ko style karta hai

Shadow DOM ke andar likha CSS normally sirf shadow tree ke elements pe apply hota hai — light DOM ya host element pe nahi. :host is boundary ka apwaad (exception) hai: ye host element khud (jaise <custom-dialog> tag) ko target karta hai, shadow DOM ke andar se.

:host — basic self-styling
<template id="tmpl">
  <style>
    :host {                       /* :host = <custom-dialog> element khud, shadow ke andar se target */
      position: fixed;            /* fixed positioning — dialog viewport ke relative center hoga */
      left: 50%; top: 50%;       /* viewport center point pe le jaao */
      transform: translate(-50%, -50%); /* element ke apne size ka half wapas shift, exact centering */
      display: inline-block;    /* default custom elements inline hote hain, dialog ko box banao */
      border: 1px solid red;
      padding: 10px;
    }
  </style>
  <slot></slot>
</template>

:host() ek functional variant hai — parentheses ke andar ek selector deke conditional host-styling deta hai. Selector host element pe khud match hona chahiye (attribute, class, ya pseudo-class):

:host(selector) — attribute-based conditional style
:host {
  display: inline-block;       /* base style — hamesha apply */
  border: 1px solid red;
}

:host([centered]) {            /* SIRF tab apply jab host pe "centered" attribute ho */
  position: fixed;
  left: 50%; top: 50%;
  transform: translate(-50%, -50%);
  border-color: blue;
}

<!-- usage: -->
<custom-dialog centered>Centered dialog!</custom-dialog> <!-- caller "centered" laga ke behavior toggle karta hai -->

:host-context() — ancestor ke context pe based styling

:host-context(selector) uss selector se match karta hai jo shadow host ke kisi bhi ancestor pe ho (document tree mein upar) — is tarah component apna style parent page ke context (jaise <body class="dark-theme">) ke hisaab se adapt kar sakta hai, bina caller ko explicit attribute pass kiye.

:host-context(.dark-theme) — ancestor-driven theming
:host-context(.dark-theme) {     /* agar KISI bhi ancestor pe class="dark-theme" mile (body, html, wrapper div...) */
  background: #222;
  color: #eee;
}
/* Iska matlab: <body class="dark-theme">...<custom-widget>...</custom-widget>...</body> */
/* pe automatically dark styles apply ho jaayenge — bina component ko koi prop diye. */

::slotted() — sirf top-level slotted node target hota hai

Slotted elements light DOM se aate hain, isliye by default wo document/page ke styles inherit karte hain, shadow DOM ke styles nahi. Do tareeke hain unhe style karne ke: (1) slot ko style karo — sirf CSS-inheritable properties (jaise font-weight) slotted children tak pahunchengi, non-inherited (jaise background) nahi. (2) ::slotted() pseudo-element use karo — ye directly slotted element ko target karta hai.

::slotted(selector) usage
::slotted(div) {            /* koi bhi <div> jo directly slot ke through render hua ho */
  border: 1px solid red;
}
⚠️ Gotcha: ::slotted() sirf TOP-LEVEL slotted node ko match karta hai

::slotted() ki ek hard limitation hai jo bahut logon ko surprise karti hai — ye sirf uss element ko target kar sakta hai jo directly slot mein assign hua hai, uske descendants ko nahi. ::slotted(div) span ya ::slotted(div span) — dono invalid hain aur kuch bhi select nahi karenge. Matlab agar light DOM mein <div slot="x"><span>text</span></div> hai, to ::slotted(div) us div ko style kar sakta hai, lekin uske andar ke span ko shadow-side CSS se kabhi target nahi kar sakte — chahe kitna bhi nested selector likho. Sirf ek level deep tak hi selector reach hai (::slotted(*) se bhi sirf top-level assigned nodes match honge, unke children nahi). Isi wajah se real components (design systems mein) apne "slot content" ko simple, shallow markup rakhne ki recommend karte hain, ya phir CSS custom properties wale theming-hook pattern pe switch karte hain.

CSS custom properties — shadow boundary cross karne ka SANCTIONED channel

Jab ::slotted() ki reach kam pade, ya jab tumhe shadow tree ke kisi deeply-nested internal element (jo light DOM se accessible hi nahi) ko externally style karna ho, to CSS custom properties (--my-var) hi ek design-mandated escape hatch hain. Ye single mechanism hai jo shadow boundary ko explicitly, deliberately cross karta hai — isliye ye component "theming API" ka standard tareeka ban gaya hai.

Custom property "hook" — internal styling ka public API
/* SHADOW DOM ke andar — component author ye likhta hai */
.field {
  color: var(--user-card-field-color, black); /* var(name, fallback): agar caller ne set nahi kiya, "black" default */
}

/* DOCUMENT (light DOM) ke andar — caller/consumer ye likhta hai */
user-card {
  --user-card-field-color: green;  /* is host element pe custom property set — shadow tree ke andar tak percolate hoti hai */
}

Root cause ye hai ki custom properties inherited hote hain — inheritance shadow-DOM boundary se rukti nahi (jabki normal CSS rules shadow tree ke andar isolated rehte hain by design). Isliye ye behaviour spec-level pe deliberately allow kiya gaya hai, taaki component authors ek documented "styling contract" expose kar sakein — bilkul waise jaise ek class method/prop ek behavior contract expose karta hai, custom property ek visual contract expose karta hai, bina component ke internal DOM structure ko leak kiye.

🧠 Senior Dev Note: theming API design karte waqt

Production design systems (jaise Shoelace, Material Web Components) apne components ke saath ek documented list of --component-* custom properties dete hain — exactly is pattern ka scaled-up version. Rule of thumb jo follow karo: (1) har custom property ko ek fallback value do (var(--x, default)) taaki component custom property set kiye bina bhi kaam kare, (2) property names ko component-namespaced rakho (--user-card-field-color, na ki generic --color) taaki naming clash na ho jab multiple custom elements same page pe ho, (3) sirf visual/theming properties expose karo custom properties se — behavior/logic ke liye attributes ya JS properties use karo, ye teeno alag-alag "API surfaces" hain aur inhe mix nahi karna chahiye.

Event retargeting — encapsulation ke liye event.target rewrite hota hai

Jab shadow DOM ke andar koi event fire hoti hai (jaise button click), aur wo event bubble hoke document tak pahunchti hai, to browser event.target ko rewrite kar deta hai — outside listeners ko internal shadow structure kabhi dikhta nahi, unhe sirf host element target ki tarah dikhta hai. Isse component ka internal DOM implementation detail rehta hai, kabhi leak nahi hota.

Retargeting demo — inner vs outer target
customElements.define('user-card', class extends HTMLElement {
  connectedCallback() {
    this.attachShadow({ mode: 'open' });
    this.shadowRoot.innerHTML = `<p><button>Click me</button></p>`; // internal shadow tree, ek button

    // SHADOW-INTERNAL listener — actual DOM element dekhta hai
    this.shadowRoot.firstElementChild.onclick =
      e => alert("Inner target: " + e.target.tagName); // "Inner target: BUTTON" — actual internal element
  }
});

// DOCUMENT-LEVEL listener — bubble hoke yahan pahunchega, par target REWRITE ho chuka hai
document.onclick =
  e => alert("Outer target: " + e.target.tagName); // "Outer target: USER-CARD" — host element, BUTTON nahi

Retargeting ka exception: slotted elements. Agar click kisi <span slot="username"> pe hui jo actually light DOM ka part hai (sirf slot ke through render ho raha hai), to us par retargeting apply nahi hoti — dono internal aur external listeners ko wahi span hi target dikhega, kyunki wo element genuinely document tree mein hi exist karta hai, shadow tree mein nahi.

Full internal path (shadow-crossing elements sahit) access karne ke liye event.composedPath() hai — flattened DOM ke ancestor chain ko return karta hai. Ek closed shadow tree ({mode: 'closed'}) ke case mein, ye path host element se upar hi shuru hota hai — internal shadow details completely conceal ho jaate hain, even composedPath() se bhi.

composed flag — kaunse events boundary cross karte hain

Har event ka ek composed boolean property hai jo decide karta hai ki wo shadow DOM boundary cross karke bahar bubble ho sakti hai ya nahi. Zyaadatar native UI events (click, mousedown, focus, input, keydown, touch/pointer events) composed: true hote hain — cross karte hain. Kuch events jaanbujh kar composed: false hote hain — mouseenter, mouseleave, load, unload, select, aur khud slotchange bhi — ye component ke andar hi confined rehte hain.

Custom event: bubbles + composed dono chahiye boundary cross karne ke liye
// inner = shadow DOM ke andar ka koi element
inner.dispatchEvent(new CustomEvent('test', {
  bubbles: true,       // bubbles: event upar (parent chain mein) travel kare — is-tree ke andar
  composed: true,      // composed: shadow boundary bhi cross kare — dono TRUE tabhi document tak pahunchega
  detail: "composed"     // detail: custom payload jo listener e.detail se read kar sakta hai
}));                    // -> document.addEventListener('test', ...) is event ko PAKDEGA

inner.dispatchEvent(new CustomEvent('test', {
  bubbles: true,       // bubbles true hai, lekin...
  composed: false,     // composed false — shadow root pe hi ruk jaayega, aage nahi jayega
  detail: "not composed"
}));                    // -> document.addEventListener('test', ...) ISE NAHI PAKDEGA
⚠️ Default CustomEvent options: dono false hote hain

new CustomEvent('name', {detail: x}) — agar bubbles aur composed explicitly na do, dono default false hain. Matlab tumhara custom event by default sirf usi element tak limited rahega jispe dispatch hua — na bubble karega, na shadow boundary cross karega. Component-to-parent communication ke liye (jaise <my-input> ka "value-changed" event outer app tak pahunchana), tumhe explicitly { bubbles: true, composed: true } dena hoga — ye accidental default nahi, spec ka deliberate "opt-in to encapsulation-breaking" design hai.

Key Takeaways

  • Flattened DOM = sirf render/event-bubbling ke liye virtual view; JS se light aur shadow DOM alag-alag trees hi rehte hain, nodes physically move nahi hote.
  • Named slots ek "shallow" distribution algorithm follow karte hain — sirf host ke DIRECT children match hote hain, slot attribute wale multiple children same-named slot mein sequentially append hote hain.
  • Default (unnamed) slot un light-DOM children ko pakadta hai jinke paas slot attribute nahi hai; <slot> ke andar likha content sirf tab render hota hai jab koi matching assignment na ho (fallback).
  • slotchange sirf assignment-level structural changes pe fire hota hai, andar-ke-content changes ke liye MutationObserver chahiye.
  • :host = host element khud; :host(sel) = conditional (host pe attribute/class check); :host-context(sel) = ancestor tree mein kahin bhi match ho to apply — page-level theming ke liye useful.
  • ::slotted() sirf top-level assigned node ko target karta hai, uske descendants ko kabhi nahi — deeper styling ke liye CSS custom properties use karo.
  • CSS custom properties (--x) hi ek deliberate, spec-sanctioned channel hain jo shadow boundary cross karke internal elements ko style kar sakte hain — component theming API ka standard.
  • Event retargeting shadow-internal events ke event.target ko outside listeners ke liye host element bana deta hai — internal implementation detail hide karta hai (slotted elements is retargeting se exempt hain).
  • composed: true chahiye kisi bhi custom event ko shadow boundary cross karne ke liye — default false hai, explicit opt-in zaroori hai.

🎯 Interview Questions

  • Named slot distribution algorithm kaise kaam karta hai, aur ye light DOM ko mutate karta hai kya?
    Hint: browser shadow tree ke slots scan karta hai, matching direct-children ko unke naam se link karta hai render-time pe; ye sirf visual/flattened-DOM assignment hai, actual parentNode light DOM hi rehta hai.
  • slot attribute nested (non-direct) child pe kyun ignore ho jaata hai?
    Hint: distribution algorithm shallow hai — sirf shadow host ke direct children hi eligible hote hain, deep tree-walk nahi hota.
  • ::slotted(div span) invalid kyun hai? ::slotted() ki exact reach kya hai?
    Hint: ::slotted() sirf top-level slotted node ko match karta hai, uske descendants ko kabhi nahi — koi bhi compound/descendant selector andar invalid hai.
  • CSS custom properties shadow boundary kyun cross kar paate hain jabki normal rules nahi?
    Hint: custom properties inherited hote hain by spec, aur inheritance shadow-DOM isolation se independent hai — normal selector-based rules shadow tree ke andar isolated rehte hain by design.
  • Event retargeting kya hai aur ye kis problem ko solve karta hai?
    Hint: shadow-internal element pe event fire ho to outside listeners ko event.target host element dikhta hai, actual internal element nahi — internal DOM structure ko implementation detail ki tarah encapsulate karta hai.
  • Slotted elements event retargeting se exempt kyun hain?
    Hint: wo genuinely light DOM (document tree) ka part hote hain, sirf slot ke through render hote hain — isliye unpe wahi target dikhta hai jo actually hai, koi rewriting nahi.
  • CustomEvent default options kya hote hain, aur parent-communication ke liye kya explicitly set karna padta hai?
    Hint: bubbles aur composed dono default false hain — component-to-page communication ke liye dono explicitly true karne padte hain, warna event shadow root pe hi ruk jaata hai.
