Objects: The Basics

Objects JavaScript ka sabse fundamental data structure hai — primitives ke alawa jo kuch bhi hai (arrays, functions, dates, sab), wo internally object hi hai. Is chapter mein hum root-level dekhenge: objects memory mein kaise store hote hain (reference type), garbage collector unhe kab free karta hai (mark-and-sweep), this keyword call-time pe kaise resolve hota hai, new operator internally kya karta hai, optional chaining ka short-circuit mechanism, Symbol ki uniqueness guarantee, aur object-to-primitive conversion ka exact algorithm.

Object literals & property access

Object {} curly-brace syntax se banta hai — key-value pairs ka collection, jahan key hamesha string (ya Symbol) hoti hai aur value kuch bhi ho sakti hai. Property access do tareeke se hota hai: dot notation (obj.key) jo sirf valid identifier keys ke liye kaam karta hai, aur square bracket notation (obj["key"]) jo runtime pe kisi bhi string expression se access de deta hai — including computed property names.

object literal, dot vs bracket access
let user = {          // object literal syntax — curly braces mein key: value pairs
  name: "John",     // "name" key, string value — string key hone ke bawajood quotes optional hain (valid identifier hai)
  age: 30            // "age" key, number value
};

console.log(user.name);       // dot notation — sirf tab kaam karta hai jab key valid JS identifier ho (koi space/hyphen na ho)

user["likes birds"] = true;  // bracket notation — key mein space hai, dot notation yahan syntax error dega
console.log(user["likes birds"]); // true — bracket se dobara read

delete user["likes birds"]; // delete operator — property ko object se hi hata deta hai (value undefined set karne se alag hai)

let key = "age";       // key ek variable mein hai — dot notation se ye access nahi kar sakte (user.key galat hoga)
console.log(user[key]);   // 30 — bracket ke andar variable expression evaluate hoke key ban jaata hai

Object literal ke andar bhi computed property names bracket syntax se ban sakte hain, aur agar property naam ek existing variable ke naam se match kare, to property value shorthand use karke key: key ki jagah sirf key likh sakte ho.

computed properties + shorthand
function makeUser(name, age) {  // factory function jo do parameters leta hai
  return {                       // naya object literal return kar rahe hain
    name,                     // shorthand: parameter "name" ka naam hi key ban gaya — name: name ke barabar
    age                       // shorthand: age: age ke barabar
  };
}

let fruit = "apple";     // runtime pe pata chalne wali key ka naam
let bag = {
  [fruit]: 5                 // computed property name — [fruit] evaluate hoke "apple" key ban jaata hai literal ke andar hi
};
console.log(bag.apple);  // 5 — bag ke andar actual key "apple" bani, "fruit" nahi

Property naam ke liye koi restriction nahi hai — reserved words (for, let, class) bhi valid keys hain, aur non-string keys automatically ToString convert ho jaate hain (0 key internally "0" ban jaati hai). Ek exception: __proto__ special hai kyunki wo prototype chain ka legacy accessor hai — usmein non-object value store karne se silently ignore ho jaata hai.

"in" operator vs undefined check
let user = { name: "John", age: undefined }; // age property EXISTS, value undefined hai

console.log(user.age === undefined); // true — is check se pata nahi chalta ki key exist karti hai ya nahi
console.log("age" in user);        // true — "in" operator explicitly key ke existence ko check karta hai, value se independent
console.log("salary" in user);     // false — "salary" key hi object mein nahi hai
⚠️ for...in ordering — integer keys sort hoti hain

Har key ka type (integer-like string ya nahi) iteration order decide karta hai. Integer keys (jaise "1", "49" — koi string jo bina leading zero/sign ke wapas number mein convert ho sakti hai) hamesha ascending numeric order mein pehle aati hain, chahe insert order kuch bhi ho. Baaki (non-integer) keys apne insertion/creation order mein aati hain. Ye ek engine-level spec rule hai (ECMA-262 OrdinaryOwnPropertyKeys), na ki koincidence. Fix: numeric-looking key ko non-integer banane ke liye ek prefix jod do (jaise "+49"), phir wo insertion order follow karegi.

Objects reference type hain — memory model

Ye is poore chapter ka sabse root-level concept hai. Primitives (number, string, boolean etc.) "by value" store hote hain — jab tum ek variable ko copy karte ho, poori value literally duplicate ho jaati hai, aur dono variables independent ho jaate hain. Objects alag tarah kaam karte hain: variable object ka actual data apne andar nahi rakhta — wo sirf ek reference (memory address ka pointer) rakhta hai jo heap mein kahin store hue actual object data ki taraf point karta hai.

Jab tum let admin = user likhte ho, koi naya object nahi banta — sirf reference ki value (pointer) copy hoti hai. Ab user aur admin dono variables heap mein same memory location ki taraf point kar rahe hain.

reference copy — dono variables same object share karte hain
let user = { name: "John" };  // heap mein naya object banta hai, "user" variable uska reference (pointer) hold karta hai

let admin = user;          // COPY: naya object nahi bana — sirf reference (pointer value) copy hui, heap object same hai

admin.name = "Pete";    // "admin" ke through mutate kiya, lekin ye wahi heap object hai jo "user" bhi point karta hai

console.log(user.name);   // "Pete" — "user" bhi change dikhta hai kyunki dono ek hi object ko point karte hain

let a = {};              // naya object #1, heap address X pe
let b = a;               // b bhi X ko point karta hai — reference copy
console.log(a == b);      // true — "==" objects ke liye reference (address) compare karta hai, content nahi

let c = {};              // naya object #2, heap address Y pe — content same hai lekin address alag
let d = {};              // naya object #3, heap address Z pe
console.log(c == d);      // false — do alag address (Y != Z), content identical hone se koi farak nahi padta
🧠 Senior Dev Note: const object mutate ho sakta hai

const sirf binding (variable name → reference) ko freeze karta hai, heap mein baithe actual object ko nahi. const user = {} ka matlab hai "user naam ab kisi doosri jagah point nahi kar sakta" — lekin jis object ko wo point kar raha hai, uski properties bilkul mutable hain (user.name = "Pete" valid hai). Sirf user = {} (poori reference reassign karna) error dega. Ye JS interviews mein bahut common confusion hai — const immutability guarantee nahi deta, sirf reference-reassignment protection deta hai. Real immutability ke liye Object.freeze() chahiye (shallow) — jo alag chapter mein cover hota hai.

Cloning: shallow vs deep, structuredClone

Kyunki assignment sirf reference copy karta hai, agar tumhe genuinely ek independent duplicate chahiye (jisme changes original ko affect na karein), to explicit cloning chahiye. Object.assign(target, ...sources) sabse common shallow-clone tareeka hai — ye sources ke enumerable own properties ko target mein copy karta hai (existing keys overwrite ho jaati hain).

Object.assign — shallow clone, nested objects break ho jaate hain
let user = {
  name: "John",              // top-level primitive property
  sizes: { height: 182 } // NESTED object — ye khud bhi ek heap reference hai
};

let clone = Object.assign({}, user); // {} target hai, user ki saari own enumerable keys usmein copy hoti hain

console.log(clone === user);       // false — top-level object naya hai, independent
console.log(clone.sizes === user.sizes); // true! — sirf reference copy hui, sizes wahi heap object hai — SHALLOW copy ka side-effect

user.sizes.height = 200;  // original ke nested object ko mutate kiya
console.log(clone.sizes.height); // 200 — clone bhi change dikha raha hai, kyunki dono same nested object share karte hain

Is problem ka fix deep clone hai — recursively har nested object ka bhi naya copy banana. Manual recursion likhne ki jagah, modern JS engines mein built-in structuredClone(value) function hai jo deep clone karta hai, circular references bhi handle karta hai (structured clone algorithm — wahi jo postMessage/IndexedDB internally use karte hain).

structuredClone — true deep clone
let user = {
  name: "John",
  sizes: { height: 182 }
};

let clone = structuredClone(user);  // engine-level recursive clone — nested objects bhi fresh heap allocations paate hain

console.log(clone.sizes === user.sizes); // false — ab sizes ka bhi independent naya object hai

user.sizes.width = 60;   // original ko mutate karo
console.log(clone.sizes.width); // undefined — clone bilkul unaffected hai, true isolation

let circular = {};
circular.self = circular;  // object khud ko hi reference kar raha hai — circular reference
let clonedCircular = structuredClone(circular); // structuredClone circular refs correctly handle karta hai (JSON.stringify yahan crash karta)
console.log(clonedCircular.self === clonedCircular); // true — clone ke andar bhi wahi circular structure preserve hui
⚠️ structuredClone functions clone nahi kar sakta

structuredClone function values, DOM nodes, aur kuch host objects (jaise window) pe DataCloneError throw karta hai — kyunki functions closures hold karte hain jo memory-address-specific hain, unhe serialize karna well-defined nahi hai. Agar object mein methods hain jo clone karne hain, ya bahut fine-grained control chahiye (specific keys skip karna, custom merge logic), to lodash ka _.cloneDeep() ya manual recursive clone function likhna padega.

Garbage collection & mark-and-sweep

JS engine memory management manually nahi karwata — ek garbage collector (GC) background mein chalta hai jo automatically wo memory free karta hai jo ab use nahi ho rahi. Core concept hai reachability: koi value tab tak memory mein rehti hai jab tak wo kisi "root" se — directly ya chain of references se — reach ki ja sake.

Roots hamesha reachable maane jaate hain:

  • Currently executing function ke local variables aur parameters
  • Call stack mein baaki nested calls ke variables/parameters
  • Global variables
reference lost → object unreachable → GC eligible
let user = { name: "John" }; // heap object banta hai; "user" (root/global) ek reference hold kar raha hai — object REACHABLE hai

user = null;          // "user" ab kisi aur cheez ko point kar raha hai (null) — heap object ka koi reference nahi bacha
                            // object ab UNREACHABLE hai → GC agli sweep mein ye memory free kar dega

let a = { name: "John" };
let b = a;              // dusra reference bana — same heap object ab 2 roots se reachable hai
a = null;             // ek reference gaya, lekin "b" abhi bhi point kar raha hai
console.log(b.name);   // "John" — object abhi bhi ALIVE hai kyunki kam se kam ek reference bacha hua hai

Ek subtle case: interlinked objects collectively unreachable ban sakte hain, chahe wo ek-doosre ko reference kar rahe hon (unke aapas ke references count nahi hote agar koi root path unhe reach na kare):

unreachable island — aapas mein linked lekin koi root path nahi
function marry(man, woman) {
  woman.husband = man;   // woman object se man object ki taraf reference
  man.wife = woman;      // man object se woman object ki taraf reference — dono ek doosre ko point karte hain
  return {
    father: man,          // wrapper object dono ko reference karta hai
    mother: woman
  };
}

let family = marry({name: "John"}, {name: "Ann"}); // "family" (root) se man aur woman dono reachable hain

family = null;          // root reference tod diya — ab family/man/woman teeno "island" ban gaye
                          // man aur woman abhi bhi ek-doosre ko reference karte hain, lekin koi ROOT unhe reach nahi kar sakta
                          // isliye poora cluster ek saath unreachable → mark-and-sweep dono ko collect kar dega

Naive approach — reference counting (har object pe uske references ka count rakho, 0 hote hi delete karo) — is circular case mein fail ho jaata hai, kyunki man aur woman ek-doosre ko count karte reh jaate hain (count kabhi 0 nahi hota) chahe wo poori tarah unreachable hon. Isi limitation ki wajah se modern engines mark-and-sweep algorithm use karte hain.

🧠 Mark-and-sweep — step by step

Algorithm periodically ye steps chalata hai: (1) Mark roots — sab root objects (global variables, active call stack ke locals) ko "reachable" mark karo. (2) Traverse aur mark references — har marked object ke andar jitne bhi references hain unhe follow karo aur unhe bhi mark karo (agar pehle se marked nahi hain). (3) Recurse — step 2 tab tak repeat karo jab tak koi naya reachable object na mile — effectively roots se "paint spill" hota hai poore reference graph mein. (4) Sweep — jo objects is process mein mark nahi hue (kisi bhi root se unreachable), unhe delete kar do aur memory free kar do. Man/woman jaise circular islands automatically is process mein miss ho jaate hain kyunki koi root path unhe touch nahi karta — isliye ye reference-counting se strictly better hai.

Engines is base algorithm pe kai practical optimizations lagate hain:

  • Generational collection — objects ko "new" (short-lived) aur "old" (long-lived) generations mein split karte hain; naye objects ko zyada frequently scan karte hain kyunki zyadatar objects jaldi hi garbage ban jaate hain (weak generational hypothesis).
  • Incremental collection — poore heap ko ek single "stop-the-world" pause mein scan karne ke bajaye, GC ko chhote-chhote chunks mein todte hain taaki UI/execution zyada der block na ho.
  • Idle-time collection — GC ko CPU ke idle periods mein preferentially chalate hain, jab execution pe uska visible impact minimal ho.

Methods aur this keyword

Object property mein stored function ko method kehte hain. Method ke andar object ki apni properties access karne ke liye this keyword use hota hai — jo call-time pe us object ki taraf point karta hai jispe method call hua.

method shorthand + this
let user = {
  name: "John",
  sayHi() {              // method shorthand — "sayHi: function() {...}" ka short form
    console.log(this.name); // this = "object jispe method call hua" — hardcoded "user" naam se better hai
  }
};

user.sayHi();  // "John" — call syntax "user.sayHi()" mein "user" hi this ban jaata hai (dot se pehle wala object)
🧠 this "late binding" hai — definition-time nahi, call-time pe decide hota hai

JS ke this ka behavior most OOP languages se fundamentally different hai. Function jahan define hui hai wo matter nahi karta — this ki value poori tarah is baat pe depend karti hai ki function ko kaise call kiya gaya. Yehi wajah hai ki ek hi function reference alag-alag objects pe alag this resolve kar sakta hai.

same function, different this — call site决定 karta hai
function sayHi() {
  console.log(this.name);  // ye function DEFINITION-time pe kisi object se linked nahi hai
}

let user = { name: "John" };
let admin = { name: "Admin" };

user.f = sayHi;   // SAME function reference dono objects pe assign — koi copy nahi hui, sirf pointer
admin.f = sayHi;

user.f();    // "John" — call site "user.f()" hai, isliye this = user
admin.f();   // "Admin" — call site "admin.f()" hai, isliye this = admin — same function, different this!

sayHi();       // koi object ke bina direct call — this = undefined (strict mode mein, jo modules/classes default hai)
              // non-strict mode mein this = global object (window) ban jaata — accidental global leaks ka common source

Arrow functions is rule ka exception hain — unka apna this hota hi nahi, wo lexically enclosing scope se this "inherit" karte hain (jahan wo likhe gaye hain, wahi wale scope ka this use karte hain). Isliye arrow function ke andar this call-site pe depend nahi karta.

arrow function — apna this nahi hota, outer se uthata hai
let user = {
  firstName: "Ilya",
  sayHi() {                    // ye ek regular method hai — call ke waqt this = user milega
    let arrow = () => console.log(this.firstName);
                                    // arrow function ke andar "this" khud resolve nahi hota —
                                    // ye lexically enclosing "sayHi" method ka this use karta hai
    arrow();                    // arrow() ko koi object ke through call nahi kiya, phir bhi this sahi milega
  }
};

user.sayHi(); // "Ilya" — arrow ne "sayHi" ke this (jo user tha) ko capture kiya, khud ka this nahi banaya

Constructor functions aur new

Jab similar structure wale multiple objects banane hon, repeat-repeat likhna avoid karne ke liye constructor functions use hote hain. Convention: naam Capital letter se shuru hota hai, aur ise sirf new ke saath call kiya jaata hai.

constructor function basic usage
function User(name) {     // capital "U" — convention batata hai ye new ke saath call hona chahiye
  this.name = name;   // naye object (this) pe name property set
  this.isAdmin = false; // default property naye object pe
}

let user = new User("Jack"); // "new" keyword function call ka behavior fundamentally badal deta hai

console.log(user.name);    // "Jack"
console.log(user.isAdmin); // false
🧠 new internally exactly 4 steps karta hai

Jab tum new Fn(args) likhte ho, engine ye sequence follow karta hai: (1) Ek naya empty object banao aur usse implicitly this assign kar do. (2) Us naye object ka internal [[Prototype]] Fn.prototype pe set karo (isliye baad mein Fn.prototype pe defined methods bhi is object se accessible hote hain — prototype chapter mein detail). (3) Function body execute karo — jo bhi this.xxx = ... statements hain wo usi naye object ko mutate karte hain. (4) Agar function explicitly koi object return karta hai to wahi return hota hai, warna implicitly this (wahi naya banaya object) return ho jaata hai — bina explicit return likhe bhi.

return rules — object override karta hai, primitive ignore hota hai
function BigUser() {
  this.name = "John";       // naye this object pe property set
  return { name: "Godzilla" }; // EXPLICIT object return — rule: object return hua to wahi jeetega, this discard ho jaata hai
}
console.log((new BigUser()).name); // "Godzilla" — this ({name:"John"}) discard hua, returned object mila

function SmallUser() {
  this.name = "John";
  return;                       // PRIMITIVE (undefined) return — rule: primitive returns IGNORE hote hain
}
console.log((new SmallUser()).name); // "John" — implicit this hi wapas milta hai, "return;" ka koi effect nahi

Constructor ke andar new.target check karke pata chal sakta hai ki function new ke saath call hua ya normal function ki tarah — regular call mein ye undefined hota hai, new ke saath ye khud function ko point karta hai. Isse constructor "self-correct" ho sakta hai agar koi galti se new bhool jaaye. Arguments ke saath parentheses omit bhi ki ja sakti hain (new User), lekin ye readability ke liye avoid karna chahiye.

Optional chaining ?.

Deeply nested properties access karte waqt agar beech ka koi property missing (null/ undefined) hua to error aata hai. Optional chaining is problem ko elegantly solve karta hai: ?. evaluation ko turant stop kar deta hai aur undefined return kar deta hai agar bayan taraf ki value null ya undefined ho — warna normal property access ki tarah continue karta hai.

?. property access — traditional check ka replacement
let user = {};            // user ke paas "address" property hi nahi hai

console.log(user.address.street); // TypeError — user.address undefined hai, uski .street access karna crash karta hai

console.log(user?.address?.street); // undefined, koi error nahi —
                                    // "user?." check karta hai user null/undefined to nahi, phir "address?." check karta hai wo bhi
🧠 Short-circuit sirf beech ke expression ko rokta hai — poore chain ko nahi

?. ek chain ke ek hi point pe short-circuit karta hai, lekin uska effect us puri expression tak fail hota hai jiska wo hissa hai — right-hand side ka koi bhi function call bhi evaluate hi nahi hota agar left side missing ho. Ye side-effects (jaise x++) ke liye critical hai.

short-circuit — right side bilkul evaluate hi nahi hota
let user = null;
let x = 0;

user?.sayHi(x++);       // "user" null hai, isliye poori expression turant undefined ho jaati hai —
                        // x++ ARGUMENT hai jo function call ke andar hai, aur wo call kabhi hota hi nahi

console.log(x);            // 0 — x++ execute hi nahi hua, ye proof hai ki short-circuit sach mein evaluation rokta hai

let key = "firstName";
let u1 = { firstName: "John" };
console.log(u1?.[key]);    // "John" — ?.[...] variant, dynamic key ke saath safe bracket access

let userGuest = {};       // "admin" method exist hi nahi karta
userGuest.admin?.();    // ?.() variant — method exist karta hai to hi call hota hai, warna silently kuch nahi hota
⚠️ Overuse mat karo — ye assignment ke liye bhi nahi chalta

?. sirf reading (aur delete) ke liye hai — user?.name = "John" jaisa assignment syntactically invalid hai, kyunki agar left side undefined nikla to assign kise karoge? Aur ?. ko har jagah lagana ek anti-pattern hai: jahan tumhare business logic ke hisaab se koi property hamesha honi chahiye, wahan normal dot access hi use karo — taaki agar wo missing ho to turant loud error mile (silent undefined propagation se debugging harder ho jaati hai). Technically ye ek operator nahi, ek "special syntax construct" hai, aur agar undeclared variable pe use kiya (jaise someUndeclaredVar?.prop) to bhi ReferenceError aayega — variable ka declared hona zaroori hai, sirf uski value null/undefined ho sakti hai.

Symbol type & uniqueness

Symbol JS ka ek primitive type hai jiski har instance guaranteed unique hoti hai — chahe do symbols ka description bilkul identical kyun na ho, wo kabhi equal nahi honge. Object keys ke liye sirf do primitive types allowed hain: string aur Symbol.

symbol uniqueness + hidden property use-case
let id1 = Symbol("id");  // naya unique symbol, "id" sirf description/label hai (debugging ke liye), koi identity nahi deta
let id2 = Symbol("id");  // dusra symbol, bilkul same description ke saath

console.log(id1 == id2); // false — engine har Symbol() call pe ek naya, bilkul unique primitive banata hai

let user = { name: "John" };  // third-party code ka object socho — hum uski normal properties se collide nahi karna chahte
let id = Symbol("id");     // hum apni khud ki "hidden" key banate hain
user[id] = 1;          // bracket syntax zaroori hai — symbol ko computed key ki tarah use karna padta hai

for (let key in user) {  // for...in symbolic keys ko DELIBERATELY skip karta hai
  console.log(key);       // sirf "name" print hoga, hamara symbol id kabhi nahi dikhega
}

Ye "hidden property" pattern ka classic use-case hai — kisi third-party/library object pe apna metadata attach karna without collision risk, kyunki wo library ka code sirf string keys ke saath kaam karta hai aur tumhare symbol ke baare mein "jaanta" hi nahi. Global sharing chahiye ho (same symbol multiple files mein consistently milna chahiye) to Symbol.for(key) registry use karo — same string key ke saath call karne pe hamesha wahi symbol wapas milta hai.

Symbol.for — global registry
let id = Symbol.for("id");      // registry mein "id" naam ka symbol dhoondo, agar na mile to naya banao aur store karo
let idAgain = Symbol.for("id"); // "id" registry mein pehle se hai, so registered same symbol return hota hai — naya nahi banta

console.log(id === idAgain); // true — normal Symbol("id") ke bilkul opposite behavior

console.log(Symbol.keyFor(id)); // "id" — reverse lookup, sirf registry symbols ke liye kaam karta hai (local Symbol() pe undefined)

Object-to-primitive conversion

Jab kisi object ko math operation, string context, ya comparison mein use kiya jaata hai (jaise alert(obj), obj + 1, +obj), engine ko usse ek primitive value mein convert karna padta hai — kyunki koi bhi operator "object" return nahi kar sakta. Is process ko ToPrimitive algorithm control karta hai, jo teen "hints" mein se ek use karta hai:

  • "string" — jab object ko explicitly string chahiye (jaise property key ki tarah use ho raha ho, ya alert(obj)).
  • "number" — math operations mein (+obj, subtraction, Number(obj)).
  • "default" — ambiguous cases mein, jaise binary + (jo string concat ya numeric add dono ho sakta hai) ya == comparisons.
🧠 ToPrimitive lookup order — 3-step fallback chain

Engine ye order follow karta hai: (1) agar object pe obj[Symbol.toPrimitive](hint) method exist karta hai, to use hi call karo — ye sabse high-priority override hai, aur ek hi method teeno hints handle kar sakta hai. (2) agar wo nahi hai, to hint ke hisaab se order badalta hai: "string" hint ke liye pehle toString() try hota hai, phir fallback valueOf(). (3) "number" aur "default" hints ke liye ulta order — pehle valueOf(), phir fallback toString(). In dono methods ko primitive hi return karna hoga — agar object return kiya, to wo result silently ignore ho jaata hai aur chain ka agla method try hota hai.

Symbol.toPrimitive — single method, saare hints handle
let user = {
  name: "John",
  money: 1000,

  [Symbol.toPrimitive](hint) {       // well-known symbol ko computed key ki tarah method-define karna
    console.log(`hint: ${hint}`); // engine ne kaunsa hint bheja, debug ke liye print
    return hint == "string"
      ? `{name: "${this.name}"}`   // "string" hint ke liye readable string return
      : this.money;              // "number"/"default" dono ke liye numeric value return
  }
};

console.log(`${user}`);  // hint: string -> {name: "John"}
console.log(+user);       // hint: number -> 1000 (unary plus number hint bhejta hai)
console.log(user + 500);   // hint: default -> 1500 (binary + ambiguous, default hint use karta hai)
toString/valueOf fallback — zyada common, without Symbol.toPrimitive
let user = {
  name: "John",
  money: 1000,

  toString() {                      // "string" hint ke liye primary; "number"/"default" ke liye fallback (agar valueOf na ho)
    return `{name: "${this.name}"}`;
  },

  valueOf() {                      // "number"/"default" hint ke liye primary — pehle try hota hai in dono cases mein
    return this.money;
  }
};

console.log(`${user}`);  // {name: "John"} — toString() se aaya
console.log(+user);       // 1000 — valueOf() se aaya
console.log(user + 500);   // 1500 — default hint mein bhi valueOf() pehle try hua
⚠️ ToPrimitive ke baad bhi ek aur conversion round ho sakta hai

ToPrimitive sirf object ko primitive banata hai — final result guaranteed number ya string nahi hota (kyunki JS mein "default"/"number" hint ka matlab "koi bhi primitive" hai, zaroori nahi number hi ho). Agar tumhara valueOf() koi string return kare aur wo context math operation mein use ho raha ho, to us primitive pe ek alag, standard ToNumber ya ToString conversion apply hoti hai — jaisa normal primitive-to-primitive coercion (chapter 2 wale rules) mein hota hai. Practical rule of thumb: zyaadatar cases mein sirf ek toString() define kar dena kaafi hota hai, kyunki wo "string" ke saath-saath "number"/"default" ka bhi fallback ban jaata hai jab valueOf() missing ho.

Key Takeaways

  • Objects reference type hain — variable heap object ka data nahi, sirf reference (pointer) hold karta hai; assignment reference copy karta hai, deep data nahi.
  • == objects ke liye reference (identity) compare karta hai, content nahi — do structurally-identical objects == false denge agar alag heap addresses hon.
  • const sirf reference-reassignment block karta hai, object ki properties mutable rehti hain.
  • Shallow clone (Object.assign) nested objects ke references share karta hai; deep clone (structuredClone) sab levels pe independent copies banata hai, circular refs bhi handle karta hai, functions/DOM nodes clone nahi kar sakta.
  • Garbage collection reachability pe based hai; roots se traverse na ho paane wale objects — chahe wo aapas mein linked hon — mark-and-sweep unhe collect kar deta hai.
  • this ki value call-time pe decide hoti hai (dot se pehle wala object), definition-time pe nahi; arrow functions apna this nahi banate, lexical scope se inherit karte hain.
  • new 4 steps karta hai: naya object banao → this assign karo → function body run karo → object return hua to wahi, warna implicit this return hota hai.
  • ?. reading/deleting ke liye hai, short-circuit poori right-side expression ko skip kar deta hai (side-effects included); assignment ke liye use nahi hota.
  • Symbols guaranteed unique hain (collision-proof hidden keys); Symbol.for() global registry se explicit sharing milta hai.
  • ToPrimitive order: Symbol.toPrimitive > (hint ke hisaab se) toString/valueOf fallback chain — dono ko strictly primitive return karna hota hai.

🎯 Interview Questions

  • Objects "reference type" hain — iska memory model pe exact matlab kya hai, aur ye == comparison ko kaise affect karta hai?
    Hint: variable heap object ka pointer hold karta hai; assignment reference copy karta hai; == reference/address compare karta hai, deep-equality nahi.
  • const object ko mutate kyun kiya ja sakta hai?
    Hint: const sirf binding (variable→reference) freeze karta hai, heap object ki properties immutable nahi banata — sirf reference-reassignment error deta hai.
  • Object.assign se shallow clone lene ke baad nested object mutate karne pe original bhi kyun change hota hai?
    Hint: shallow clone sirf top-level properties copy karta hai; nested object property ki value bhi ek reference hi hai, jo as-is copy ho jaati hai — dono clone/original same nested heap object share karte hain.
  • Reference counting garbage collection circular references ke saath kyun fail hota hai, aur mark-and-sweep ise kaise solve karta hai?
    Hint: circular refs mein count kabhi 0 nahi hota chahe unreachable ho; mark-and-sweep root se traverse karke sirf reachable objects mark karta hai, jo bhi root-path se disconnect hai wo collect ho jaata hai chahe uske apne internal references hon.
  • Ek hi function ko do alag objects pe assign karke call karne se different "this" kyun milta hai?
    Hint: this call-time pe "call syntax se pehle wala object" resolve karta hai (late binding), function definition se independent — same function reference, different call site, different this.
  • Arrow function methods object literals ke andar avoid kyun kiye jaate hain?
    Hint: arrow function apna this nahi banata, lexical (surrounding) scope se this uthata hai — object literal ke andar directly define kiya arrow ka this object nahi, balki outer scope (usually global/undefined) hoga.
  • "new" operator internally kya 4 steps execute karta hai, aur agar constructor explicitly ek object return kare to kya hota hai?
    Hint: naya object banao, this assign karo, body run karo, phir agar explicit return object hai to wo jeetega (this discard), primitive return ignore hoke implicit this hi return hota hai.
  • Optional chaining user?.getData() mein agar user null hai to kya getData() ka argument evaluate hota hai?
    Hint: nahi — short-circuit poori expression ko turant undefined bana deta hai, arguments ke andar ke side-effects (jaise x++) execute hi nahi hote.
