Property Config & Prototypes

Ab tak humne objects ko surface level pe use kiya — obj.key = value. Is chapter mein hum andar jaake dekhenge ki ek property sirf ek "value" nahi hoti, balki uske saath 3 hidden flags (writable/enumerable/configurable) attach hote hain jo control karte hain ki property kaise behave karegi. Phir hum inheritance ke asli internal engine — [[Prototype]] chain — ko step by step walk karenge, samjhenge F.prototype vs instance ka [[Prototype]] wala classic confusion, aur dekhenge ki Array.prototype jaisi native prototypes ko modify karna production mein danger kyun hai.

Property flags — har property ke 3 hidden switches

Jab tum obj.name = "John" likhte ho, JS engine sirf ek value store nahi karta — wo property descriptor banata hai jisme value ke saath 3 boolean flags hote hain: writable (value change ho sakti hai?), enumerable (loops mein dikhegi?), configurable (flags change/delete ho sakte hain?). Normal object-literal syntax se banayi gayi property mein teeno flags default true hote hain — isliye ye internals normally invisible rehte hain.

Object.getOwnPropertyDescriptor — flags dekhna
let user = {              // simple object, normal property creation
  name: "John"            // name property, literal syntax se — flags sab default true honge
};

let descriptor = Object.getOwnPropertyDescriptor(user, 'name');
                                       // (obj, propName) — sirf OWN property ka descriptor deta hai, inherited nahi

console.log(JSON.stringify(descriptor, null, 2));
/* output:
{
  "value": "John",       // actual stored value
  "writable": true,      // value reassign ho sakti hai
  "enumerable": true,    // for..in / Object.keys mein dikhegi
  "configurable": true   // delete ho sakti hai, flags change ho sakte hain
}
*/

Object.defineProperty — flags manually control karna

Object.defineProperty(obj, propName, descriptor) ek property create/update karta hai jisme tum har flag explicitly control kar sakte ho. Root gotcha: is method se naya property banane par, jo flags tum descriptor mein nahi dete, wo sab default false ho jaate hain — literal syntax ke opposite.

writable: false — read-only property
let user = { name: "John" };  // mutable property se shuru karte hain

Object.defineProperty(user, "name", {
  writable: false            // sirf writable flag update kar rahe hain — baaki flags jo already the wahi rahenge (existing property update case)
});

"use strict";            // strict mode zaroori hai taaki violation par actual error throw ho
user.name = "Pete";       // TypeError: Cannot assign to read only property — non-strict mode mein ye SILENTLY fail hota, koi error nahi
enumerable: false — loops se hide karna
let user = {
  name: "John",              // normal enumerable property
  toString() {              // custom toString method, object literal ke andar shorthand syntax
    return this.name;        // this = user (jo bhi is method ko call karega dot ke pehle)
  }
};

Object.defineProperty(user, "toString", {
  enumerable: false           // ab ye property for..in aur Object.keys se GAAYAB ho jaayegi
});

for (let key in user) console.log(key);  // sirf "name" print hota hai — toString hidden
console.log(Object.keys(user));              // ["name"] — ye bhi enumerable flag hi check karta hai
configurable: false — flags aur delete lock, VALUE change nahi
let user = { name: "John" };

Object.defineProperty(user, "name", {
  configurable: false         // SIRF configurable false kiya, writable abhi bhi true hai
});

user.name = "Pete";       // KAAM KARTA HAI — configurable value-change ko block nahi karta, sirf structural changes ko
delete user.name;        // FAIL — configurable:false hone se delete allowed nahi
Object.defineProperty(user, "name", { enumerable: false });
                                // FAIL — enumerable flag bhi change nahi ho sakta jab configurable false ho

// EXCEPTION: ek hi one-way transition allowed hai — writable ko true se false karna,
// tab bhi jab configurable false ho (extra "downgrade only" safety valve)
⚠️ writable vs configurable: dono alag cheez lock karte hain

Yahi sabse common confusion hai. writable: false sirf value ko lock karta hai. configurable: false descriptor structure (flags themselves, aur delete-ability) ko lock karta hai — value nahi. Ek truly-constant property banane ke liye dono flags false chahiye. Math.PI ka descriptor exactly isi wajah se dono false hai — na overwrite ho sakta hai, na delete.

defineProperties + getOwnPropertyDescriptors — bulk aur clone
// bulk mein multiple properties ek call mein define karna
Object.defineProperties(user, {
  name: { value: "John", writable: false },  // har key ke liye ek full descriptor object
  surname: { value: "Smith", writable: false }
});

// FLAGS-preserving clone — normal spread/assign flags copy NAHI karta, ye karta hai
let clone = Object.defineProperties(
  {},                                        // target: fresh empty object
  Object.getOwnPropertyDescriptors(user)      // source ke SAARE descriptors (value+flags) ek object mein
);
// { ...user } se ye better hai kyunki ye non-enumerable aur symbol properties bhi copy karta hai,
// aur flags bhi preserve hote hain — spread sirf enumerable own keys ke plain values copy karta hai

Object-level sealing — poore object ko lock karna

Individual property flags ke upar, 3 global methods poore object ko restrict karte hain:

MethodNaya property add?Existing delete?Value change?
Object.preventExtensions(obj)❌✅✅
Object.seal(obj)❌❌✅
Object.freeze(obj)❌❌❌

Corresponding check karne ke liye Object.isExtensible, Object.isSealed, Object.isFrozen hain. Practice mein ye rarely use hote hain — ek immutable config object banane ke liye Object.freeze sabse common case hai.

Getters/setters — accessor properties

JS mein 2 property types hain: data properties (jo humne abhi dekhi — value + flags), aur accessor properties, jo function pairs (get/set) ke through kaam karte hain lekin bahar se normal property jaisi dikhti hain.

get/set — computed fullName property
let user = {
  name: "John",                       // asli backing data — pehla naam
  surname: "Smith",                   // asli backing data — last naam

  get fullName() {                    // getter: jab bhi user.fullName PADHA jaayega ye chalega
    return `${this.name} ${this.surname}`;  // name+surname ko concat karke return — koi separate storage nahi
  },

  set fullName(value) {              // setter: jab bhi user.fullName = "..." LIKHA jaayega ye chalega, value = RHS
    [this.name, this.surname] = value.split(" ");
                                       // space se split karke array-destructuring se dono fields update
  }
};

console.log(user.fullName);          // "John Smith" — getter call hua, bina () ke
user.fullName = "Alice Cooper"; // setter call hua, name="Alice", surname="Cooper" ban gaye
Validation ke liye getter/setter — private-by-convention backing field
let user = {
  get name() {
    return this._name;              // _name (underscore prefix = convention, "iske bahar se mat chhedo")
  },

  set name(value) {
    if (value.length < 4) {        // validation check — assignment ke waqt hi guard laga diya
      console.log("Name too short");
      return;                       // invalid ho to silently bail — _name update hi nahi hoga
    }
    this._name = value;            // valid ho tabhi actual backing field update
  }
};

user.name = "Pete";              // 4 chars, passes → this._name = "Pete"
user.name = "";                  // 0 chars, "Name too short" print, _name unchanged
📌 Root rule: ek property ya data ya accessor, dono nahi

Descriptor mein value/writable vs get/set ek saath define karna error deta hai — engine ke andar ek property slot ya toh direct value store karta hai ya function pair, dono simultaneously nahi ho sakte. enumerable aur configurable dono types mein common flags hain.

[[Prototype]] chain — property lookup ka asli internal mechanism

Ab asli root-level part: jab tum obj.someProp padhte ho, engine sirf ek object mein nahi dekhta — wo ek chain follow karta hai. Har object ke paas ek hidden internal slot hota hai [[Prototype]] (double square brackets specification notation hai, ye koi normal accessible property nahi) jo null ya kisi doosre object ko point karta hai. Legacy accessor __proto__ is slot ko read/write karne ka getter/setter hai.

3-level chain banate hain: longEar → rabbit → animal
let animal = {
  eats: true,                    // animal ka OWN property
  walk() {                     // animal ka OWN method
    console.log("Animal walk");
  }
};

let rabbit = {
  jumps: true,                   // rabbit ka OWN property
  __proto__: animal              // rabbit ka [[Prototype]] = animal — literal ke andar hi set kar rahe hain
};

let longEar = {
  earLength: 10,                // longEar ka OWN property
  __proto__: rabbit               // longEar ka [[Prototype]] = rabbit
};

// Chain ban gayi: longEar --[[Prototype]]--> rabbit --[[Prototype]]--> animal --[[Prototype]]--> null

longEar.walk();  // "Animal walk" — 3 hops mein resolve hua, neeche step-by-step dekho

longEar.walk() call hone par engine internally exactly ye steps karta hai:

  1. Step 1 — longEar khud check karo: kya longEar ki apni (own) property walk hai? Nahi — ismein sirf earLength hai.
  2. Step 2 — longEar.[[Prototype]] pe jao: jo rabbit hai. Kya rabbit ki own property walk hai? Nahi — ismein sirf jumps hai (aur uska apna [[Prototype]] link).
  3. Step 3 — rabbit.[[Prototype]] pe jao: jo animal hai. Kya animal ki own property walk hai? Haan — found. Search yahin ruk jaati hai.
  4. Step 4 — call karo, lekin this bind karo original object se: method animal mein defined hai, lekin jab call hota hai to this = longEar (jis object pe call kiya gaya tha), na ki animal. Ye "this is always the object before the dot" rule hai — chain sirf lookup ke liye use hoti hai, execution context ke liye nahi.

Agar koi bhi level pe property nahi milti aur chain null tak pahunch jaati hai (Object.prototype.__proto__ === null hai — chain yahin terminate hoti hai), to result undefined hota hai.

Writing bypasses the chain — sirf reading walk karta hai
longEar.walk = function() {
  console.log("LongEar bounce!");
};
// Ye chain mein UPAR search nahi karta — seedha longEar pe NAYI own property bana deta hai.
// animal.walk bilkul untouched raha, sirf longEar object apne aap se ab "shadow karta hai" parent ko

longEar.walk();  // "LongEar bounce!" — ab step 1 pe hi own property mil gayi, chain traverse hi nahi hui

// EXCEPTION: accessor properties (get/set) is rule ko break karte hain — unka SETTER
// chain mein upar defined ho sakta hai lekin call phir bhi hota hai, kyunki assignment
// ek function-call hai, ek plain memory-write nahi

for...in vs Object.keys — inherited enumerable properties

Ye ek bahut common interview/production confusion hai. for...in loop poori prototype chain ke enumerable properties ko traverse karta hai — sirf own properties nahi. Object.keys(), Object.values(), aur Object.entries() sab sirf own enumerable properties dete hain.

for..in inherited dikhata hai, Object.keys nahi
for (let prop in rabbit) console.log(prop);
// "jumps" (own) aur "eats" (inherited from animal) — DONO print hote hain

console.log(Object.keys(rabbit));
// ["jumps"] — SIRF own property, "eats" nadaarad

// Agar sirf own properties chahiye for..in ke andar, guard lagao:
for (let prop in rabbit) {
  const isOwn = rabbit.hasOwnProperty(prop);
                                // hasOwnProperty khud Object.prototype se INHERIT hua method hai,
                                // lekin ye check karta hai ki 'prop' rabbit ki APNI property hai ya nahi
  if (isOwn) console.log(`Own: ${prop}`);
}

Root reason: for...in historically prototype-aware design hai (bahut purana feature, jab prototypal-inheritance JS ka primary object model tha), jabki Object.keys/values/entries baad mein add hue aur explicitly "own-data-only" semantics ke saath design hue — modern code mostly yehi prefer karta hai kyunki inherited enumerable properties accidentally leak hone ka risk nahi hota.

F.prototype vs instance ka [[Prototype]] — precise clarification

Ye naam ki wajah se sabse zyada confuse karne wala topic hai — do bilkul alag cheezein ek jaisa naam share karti hain:

  • F.prototype — ye function F ki apni ek normal, regular property hai jiska naam literally "prototype" hai. Har normal function ke paas by default ye hota hai — engine automatically ise create karta hai as { constructor: F }. Ye function ke upar baithi hui ek object reference hai.
  • Instance ka [[Prototype]] — ye har object ke andar wo hidden internal slot hai jo uski prototype chain define karta hai (jise __proto__ se access karte hain).

Connection sirf ek single moment pe banta hai: new F() call hote waqt. Us waqt engine F.prototype ki current value ko naye banaye gaye instance ke [[Prototype]] mein copy kar deta hai. Uske baad dono independent ho jaate hain.

new F() ke andar — kya exactly hota hai
function Rabbit(name) {
  this.name = name;           // constructor body — "this" naya banaya jaa raha object hoga
}

console.log(Rabbit.prototype);
// { constructor: Rabbit } — engine ne DEFAULT prototype auto-create kiya hai, tumne kuch nahi likha

let rabbit1 = new Rabbit("White");
// internally: 1) naya empty object banaya  2) uska [[Prototype]] = Rabbit.prototype (US MOMENT ki value)
// 3) constructor function ko this=naya-object ke saath call kiya  4) this return kiya (implicitly)

console.log(rabbit1.__proto__ === Rabbit.prototype);  // true — link ban gaya

// AB Rabbit.prototype ko badal do NAYE object se:
Rabbit.prototype = { eats: true };  // Rabbit.prototype ab ek DIFFERENT object point karta hai

console.log(rabbit1.eats);          // undefined! rabbit1 ka [[Prototype]] abhi bhi PURANE object ko point karta hai
                                       // (F.prototype sirf 'new' call ke US MOMENT pe use hota hai, retroactive nahi)

let rabbit2 = new Rabbit("Black");
console.log(rabbit2.eats);          // true — rabbit2 NAYE Rabbit.prototype se banaya gaya, isliye naya link mila
🧠 Senior Dev Note: constructor property ki fragility

F.prototype ka default value { constructor: F } hota hai — isse tum obj.constructor se hi ek naya same-type instance bana sakte ho (new obj.constructor()), bina class ka naam hardcode kiye. Lekin ye purely convention hai, JS engine isko enforce nahi karta. Jaise upar dikhaya, jis moment tum Rabbit.prototype = { eats: true } jaisa poora object replace karte ho (ek naya literal assign karke, existing prototype ko mutate karne ke bajaye), constructor link automatically toot jaata hai — kyunki naye literal mein wo property hi nahi hai. Agar tum poora prototype replace karna chahte ho, manually constructor wapas add karna zaroori hai: Rabbit.prototype = { eats: true, constructor: Rabbit }; — warna kisi library ya framework code jo .constructor pe depend karta hai wo silently break ho jaayega.

Native prototypes — Array.prototype, Object.prototype aur unse door rehna

Jab tum {} ya [1,2,3] likhte ho, engine automatically inka [[Prototype]] respective native prototype pe set kar deta hai — Object.prototype ya Array.prototype. Chain hamesha Object.prototype pe end hoti hai (jiska khud ka [[Prototype]] null hota hai), kyunki JS mein sab kuch (functions, arrays, dates) ultimately object hi hain.

Array → Object → null chain
let arr = [1, 2, 3];

console.log(arr.__proto__ === Array.prototype);          // true — arr ka direct prototype Array.prototype hai
console.log(arr.__proto__.__proto__ === Object.prototype); // true — Array.prototype khud Object.prototype se inherit karta hai
console.log(arr.__proto__.__proto__.__proto__);          // null — chain khatam

// isi wajah se arr.toString() sahi kaam karta hai — Array.prototype.toString mila,
// jo Object.prototype.toString ko override karta hai kyunki wo chain mein CLOSER hai (step 1 pe hi mil gaya)
console.log(arr.toString());  // "1,2,3" — comma-joined, Array.prototype ka version
Method borrowing — array-like object pe Array method use karna
let obj = {
  0: "Hello",      // numeric-index-jaisi keys, lekin ye ek plain object hai, actual Array nahi
  1: "world!",
  length: 2         // Array methods ko length property chahiye hoti hai kaam karne ke liye
};

obj.join = Array.prototype.join;
                            // Array.prototype.join method ko obj pe SEEDHA property ke roop mein daal diya
                            // (Array.prototype ko obj ka actual prototype banaye bina)

console.log(obj.join(','));  // "Hello,world!" — join internally 'this' ko generic array-like treat karta hai
⚠️ Native prototypes ko modify karna — production mein danger

Technically tum Array.prototype.myMethod = ... likh sakte ho, lekin ye ek global, shared, single-source-of-truth object hai jo tumhare pure app ke saare arrays (aur tumhare dependencies ke arrays bhi) share karte hain. Root problem collision risk hai: agar tumhari codebase mein 2 libraries (ya tumhara khud ka code + ek dependency) dono Array.prototype.flattenDeep naam ka method define kar dein, to jo baad mein load hota hai wo pehle wale ko silently overwrite kar deta hai — koi warning nahi milta, bug production mein hi surface hota hai, aur reproduce karna mushkil hota hai kyunki behavior load-order pe depend karta hai. Ek future JS spec version bhi same naam ka native method add kar sakta hai (jaise Array.prototype.flat add hua), jo tumhare custom method se directly clash kar sakta hai. Ek hi acceptable exception hai: polyfilling — jab spec mein method defined hai but current runtime purana hai, aur tum if (!String.prototype.repeat) jaisa guard laga ke sirf missing implementation add karte ho.

Modern prototype methods vs legacy __proto__

__proto__ historically de-facto standard tha, lekin spec mein sirf browsers ke liye "Annex B" (legacy compatibility) section mein hai — modern code ke liye 3 explicit methods recommended hain:

Object.create / getPrototypeOf / setPrototypeOf
let animal = { eats: true };

// Object.create(proto): NAYA object banata hai jiska [[Prototype]] = proto
let rabbit = Object.create(animal);
console.log(rabbit.eats);  // true — animal se inherit hua

// second (optional) argument — property descriptors ke saath, defineProperties jaisa
let rabbit2 = Object.create(animal, {
  jumps: { value: true }  // yahan explicit descriptor chahiye, plain value nahi
});

// getPrototypeOf — read (function form, __proto__ getter ka equivalent)
console.log(Object.getPrototypeOf(rabbit) === animal);  // true

// setPrototypeOf — write (function form, __proto__ setter ka equivalent)
Object.setPrototypeOf(rabbit, {});  // rabbit ka prototype ab kisi aur cheez ko point karta hai
Object.create(null) — "very plain" dictionary object
let dict = Object.create(null);
                                // [[Prototype]] = null seedha — Object.prototype se bhi INHERIT NAHI karega

dict.hello = "world";
console.log(dict.toString);          // undefined — koi inherited toString hi nahi hai, kyunki Object.prototype chain mein nahi hai

// SAFE case: user-controlled keys store karna, jisme "__proto__" bhi key ho sakta hai
let normalObj = {};
normalObj["__proto__"] = "hacker-value";
// DANGER: normal object mein "__proto__" as a KEY likhne se ye setter trigger ho sakta hai
// (attempt to reset actual [[Prototype]]) instead of storing a plain data property — surprising bug

let safeDict = Object.create(null);
safeDict["__proto__"] = "just a normal string value";
// SAFE — kyunki safeDict ke chain mein __proto__ getter/setter waala Object.prototype hai hi nahi,
// isliye "__proto__" bilkul ek NORMAL key ki tarah treat hota hai
console.log(safeDict["__proto__"]);  // "just a normal string value"
⚠️ __proto__ ki slow-path problem

obj.__proto__ = ... ya Object.setPrototypeOf se runtime pe prototype change karna V8-jaisa engines ke internal hidden class / shape optimizations ko break kar deta hai — engine assume karta hai ki ek given "shape" ka object hamesha same prototype rakhega, taaki property access ko fast-path le sake. Isse ye operation object creation ke baad "on-the-fly" karna significantly slow hai. Best practice: prototype ko object creation ke waqt hi finalize karo (Object.create(proto) se, ya class syntax se) — baad mein badalna avoid karo.

Key Takeaways

  • Har property ke 3 flags hote hain: writable, enumerable, configurable — literal syntax se sab true, defineProperty se sab default false.
  • writable:false = value lock; configurable:false = descriptor-structure aur delete lock — dono independent hain, ek constant ke liye dono chahiye.
  • Accessor properties (get/set) aur data properties (value/writable) mutually exclusive hain ek hi property slot mein.
  • [[Prototype]] chain lookup step-by-step upar traverse karti hai jab tak property mile ya null aaye; this hamesha calling object hota hai, chain mein jahan method mila wahan nahi.
  • Writing/deleting properties chain ko bypass karta hai — direct object pe operate karta hai, sirf accessor setters exception hain.
  • for...in inherited enumerable properties include karta hai; Object.keys/values/entries sirf own properties dete hain.
  • F.prototype ek regular property hai jo sirf new F() ke moment pe instance ke [[Prototype]] mein copy hoti hai — baad mein F.prototype badalne se existing instances affect nahi hote.
  • Native prototypes (Array.prototype etc.) modify karna collision-risk ki wajah se dangerous hai — sirf spec-defined polyfilling exception hai.
  • Object.create/getPrototypeOf/setPrototypeOf modern standard hain; __proto__ legacy hai aur runtime-mutation slow bhi hai.
  • Object.create(null) se "clean" dictionary object banta hai jisme __proto__ jaisi keys safe rehti hain, kyunki koi inherited getter/setter hi nahi hai.

🎯 Interview Questions

  • writable:false aur configurable:false mein exact farak kya hai?
    Hint: writable value-reassignment control karta hai; configurable descriptor-flags-change aur delete control karta hai. Configurable:false hote hue bhi writable:true→false ek-tarfa transition allowed hai.
  • Object.defineProperty se property create karne par default flags kya hote hain, aur literal syntax se kyun alag hain?
    Hint: defineProperty se sab flags default false; literal object syntax se sab true — history/design choice hai, defineProperty "explicit control" ke liye hai isliye safe-default (sab restricted) rakha gaya.
  • [[Prototype]] chain mein property lookup step-by-step explain karo — 3 level ki chain lo aur batao "this" kya resolve hota hai.
    Hint: har level pe own-property check, na mile to upar jao, mile to search ruk jaati hai; this hamesha dot ke pehle wala object hota hai chahe method jahan bhi defined ho.
  • for...in aur Object.keys mein enumerable-inheritance ka farak kyun hota hai?
    Hint: for..in historically prototype-chain-aware hai (poori chain traverse karta hai), Object.keys/values/entries baad mein explicitly "own-only" design ke saath aaye.
  • F.prototype ko new object banane ke baad change karo — existing instances affect honge?
    Hint: nahi — F.prototype sirf 'new F()' call ke exact moment pe instance ke [[Prototype]] mein copy hota hai, baad ka change retroactive nahi hai.
  • Array.prototype pe custom method add karna kyun risky maana jaata hai?
    Hint: global shared object hai — naming collision risk (dusri library/future spec version ke saath), silent overwrite, load-order-dependent bugs.
  • Object.create(null) kis situation mein zaroori hota hai?
    Hint: jab object ko pure key-value dictionary ki tarah use karna ho aur keys user-controlled ho sakti hain (jaise "__proto__" as a key) — normal object mein ye Object.prototype ke __proto__ setter ko trigger kar sakta hai.
  • __proto__ ko runtime pe change karna slow kyun hai, jabki Object.create(proto) fast hai?
    Hint: engines (V8 etc.) hidden-class/shape optimizations use karte hain jo assume karte hain object ka prototype stable rahega; on-the-fly change se ye optimization invalidate ho jaata hai, jabki create-time prototype fixed rehta hai.
