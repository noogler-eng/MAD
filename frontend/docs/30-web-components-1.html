Web Components I

React, Vue, Angular — sab apne apne component model laate hain, but browser khud bhi ek native component system deta hai jo kisi framework pe depend nahi karta. Web Components overview — framework-independent reusable UI

Web Components koi single API nahi hai — ye 4 alag-alag browser standards ka combo hai jo saath milke ek reusable, encapsulated UI element banate hain, bina kisi build-step ya runtime library (React/Vue) ke:

  1. Custom Elements — naya HTML tag define karne ka spec (jaise <time-formatted>), apne lifecycle callbacks ke saath.
  2. Shadow DOM — component ke andar ek private, encapsulated DOM+CSS tree, jo page ke baaki hisse se isolated rehta hai.
  3. Template element — inert HTML markup jo tab tak render nahi hota jab tak explicitly clone na kiya jaaye.
  4. ES Modules — component ki definition (class + registration) ko ek self-contained .js file mein package karna, jo import se kahin bhi reuse ho sake.

Root-level motivation: React ka <Button /> sirf React app ke andar kaam karta hai — uske virtual DOM, reconciliation, aur JSX compile step ke bina wo component "chalta" nahi. Web Components iska ulta approach lete hain — component ki definition browser ke native DOM API mein compile hoti hai, so ek baar customElements.define() ho jaaye, uske baad <my-button> tag kisi bhi jagah kaam karega — plain HTML page mein, Vue app ke andar, Angular template mein, ya legacy jQuery codebase mein — kyunki ye ab browser ke apne tag registry ka hissa ban chuka hai, kisi runtime library ka nahi.

📌 In 4 technologies ka relationship

In char mein se koi bhi ek akela use ho sakta hai (e.g. sirf Shadow DOM kisi normal div pe), lekin "Web Component" pattern tab banta hai jab sab combine hote hain: Custom Element class define karti hai lifecycle + behavior, uske connectedCallback ke andar Shadow DOM attach hota hai encapsulation ke liye, us shadow root ke andar template se cloned markup insert hota hai, aur poora package ek ES module ke through export/import hota hai. Is chapter mein hum pehle 3 (Custom Elements, Shadow DOM, Template) cover karenge — 4th (module packaging) already Chapter 14 mein cover ho chuka hai.

Custom Elements — do types

Custom Elements spec do tarah ke custom tags define karne deta hai:

  • Autonomous custom elements — bilkul naya tag, HTMLElement se directly extend karta hai. Jaise <time-formatted> ya <easy-tabs> — koi existing HTML semantic nahi le raha.
  • Customized built-in elements — ek existing built-in element (jaise <button>) ko extend karta hai, uska sara native behavior (accessibility, keyboard nav, form submission) retain karte hue. Registration mein extends option deni padti hai.
Autonomous custom element — minimal registration
class MyGreeting extends HTMLElement {  // HTMLElement se extend — ye "autonomous" custom element banata hai
  constructor() {                     // constructor — element create hote hi call hota hai (DOM mein attach hone se PEHLE)
    super();                          // ZAROORI: HTMLElement ka constructor call karo, warna error aayega
  }

  connectedCallback() {            // jab element document mein insert hota hai to ye call hota hai
    this.innerHTML = "Hello!"; // yahan render karna safe hai — attributes ab tak parse ho chuke hain
  }
}

customElements.define("my-greeting", MyGreeting);
// customElements.define(tag-name, class) — tag registry mein register karta hai
// naam mein hyphen (-) MANDATORY hai — spec ye guarantee deta hai ki future native tags kabhi collide nahi karenge
Customized built-in element — extends + is
class HelloButton extends HTMLButtonElement { // HTMLButtonElement se extend — native <button> ka behavior milta hai
  connectedCallback() {
    this.addEventListener("click", () => alert("Hello!")); // custom behavior add kiya, native click/focus/tab-order bina touch kiye
  }
}

customElements.define("hello-button", HelloButton, { extends: "button" });
// third argument {extends: "button"} — browser ko batata hai ye <button> ka customization hai
Customized built-in — usage in HTML
<button is="hello-button">Click me</button>
<!-- is="hello-button" — normal <button> tag rehta hai, sirf enhanced behavior ke saath -->
<!-- naya tag <hello-button> NAHI likhte — original semantic tag preserve rehta hai -->
🧠 Senior Dev Note: customized built-ins ka Safari problem

Customized built-in elements (is="..." syntax) Safari/WebKit mein kabhi implement nahi hue aur WebKit team ne officially "won't implement" bol diya hai — spec-level disagreement hai ki ye pattern accessibility tree ko confuse karta hai. Isliye production mein bijness-critical UI ke liye almost hamesha autonomous custom elements use kiye jaate hain (jaise <time-formatted>), aur agar native button/input jaisa behavior chahiye to usko manually re-implement kiya jaata hai shadow DOM ke andar (ARIA roles + keyboard handlers khud likh ke) — customized built-ins pe depend nahi kiya jaata.

Lifecycle callbacks — root-level trace

Custom Element class mein ye "special methods" define karo to browser inhe apne-aap, sahi moment pe call karta hai — bilkul React ke componentDidMount/componentWillUnmount jaisa, lekin native browser API hai, koi library nahi:

  • constructor() — element create hote hi. Too early — attributes ya child nodes yahan reliably available nahi hote, sirf basic init (jaise internal state variables) yahan karo.
  • connectedCallback() — element document mein insert hote hi. Attributes ab available hain, so actual rendering yahan karo. Note: element DOM mein multiple baar move ho to ye har baar call ho sakta hai.
  • disconnectedCallback() — element document se remove hote hi. Cleanup ke liye: timers clear karo, event listeners hatao (agar window/document pe laga rakhe the), subscriptions cancel karo.
  • attributeChangedCallback(name, oldValue, newValue) — jab koi observed attribute change hoti hai. Sirf un attributes ke liye fire hota hai jo observedAttributes mein list ki gayi hon (performance ke liye — har attribute ko watch karna expensive hota).
  • adoptedCallback() — jab element ek document se doosre document mein move hota hai (document.adoptNode se) — rarely use hota hai, sirf multi-document/iframe scenarios mein.
observedAttributes — sirf listed attributes hi watch hote hain
class MyElement extends HTMLElement {
  static get observedAttributes() {  // static getter — class define hote hi, instance banne se pehle hi read ho jaata hai
    return ["datetime", "locale"]; // sirf ye 2 attributes change hone pe attributeChangedCallback fire hoga
  }

  attributeChangedCallback(name, oldValue, newValue) {
    console.log(name, oldValue, "->", newValue); // name: kaunsi attribute; oldValue/newValue: pehle/baad ki value
  }
}
⚠️ Root cause: attributeChangedCallback constructor se PEHLE bhi fire ho sakta hai

Agar HTML mein element already attributes ke saath likha hai (jaise <time-formatted datetime="...">), to browser initial parse ke time attributeChangedCallback ko constructor ke turant baad, connectedCallback se pehle bhi fire kar sakta hai un initial attribute values ke liye. Isliye attributeChangedCallback ke andar kabhi bhi aisi state access mat karo jo sirf connectedCallback mein set hoti hai — null-check ya guard clauses lagao.

Real example: <time-formatted> jo datetime badalne pe re-render hota hai

Ye ek complete autonomous custom element hai jo datetime attribute ko human-readable localized format mein render karta hai, aur attribute change hone pe khud-ba-khud re-render ho jaata hai — bina kisi manual re-render call ke:

time-formatted.js — full lifecycle example
class TimeFormatted extends HTMLElement {  // naya autonomous element, HTMLElement se extend

  static get observedAttributes() {
    return ["datetime"];            // sirf datetime attribute ko watch karo, baaki sab ignore
  }

  connectedCallback() {
    if (!this.rendered) {       // guard: pehli baar hi render karo (attributeChangedCallback bhi render call karega)
      this.render();          // initial render — DOM mein insert hote hi ek baar
      this.rendered = true;  // flag set — dobara render() se avoid duplicate work
    }
  }

  attributeChangedCallback(name, oldValue, newValue) {
    if (!this.isConnected) return; // guard: agar element abhi DOM mein hi nahi hai to render skip karo (perf)
    this.render();              // attribute badla -> re-render, ye hi "reactive" behavior hai
  }

  render() {
    const date = new Date(this.getAttribute("datetime")); // current attribute value se Date object banaya
    this.innerHTML = new Intl.DateTimeFormat("default", {
      year: "numeric",            // formatting options — Intl API browser-native localization deta hai
      month: "long",
      day: "numeric"
    }).format(date);       // .format(date) — locale ke hisaab se human-readable string banata hai
  }
}

customElements.define("time-formatted", TimeFormatted); // registry mein register — ab tag kahin bhi use ho sakta hai
Usage — attribute badlo, element khud re-render karega
<time-formatted datetime="2019-12-01"></time-formatted>
<!-- browser parse karte hi constructor -> attributeChangedCallback -> connectedCallback chalte hain -->

<script>
  const el = document.querySelector("time-formatted");
  setInterval(() => {
    el.setAttribute("datetime", new Date().toISOString());
    // setAttribute call hote hi browser observedAttributes check karta hai,
    // "datetime" list mein hai, so attributeChangedCallback fire hota hai -> render() chalta hai
  }, 1000);       // har second mein element apna text khud update kar lega, koi manual DOM query nahi lagi
</script>

Shadow DOM — real encapsulation

Ek plain <div> mein tum jo bhi HTML daalo, wo light DOM ka hissa ban jaata hai — page ke global CSS usko style karte hain, aur page ka document.querySelector usko access kar sakta hai. Shadow DOM iska structurally different alternative deta hai: element ke andar ek separate, hidden DOM tree attach hota hai jo apna khud ka style scope aur query scope rakhta hai.

attachShadow — encapsulated subtree banana
customElements.define("show-hello", class extends HTMLElement {
  connectedCallback() {
    const shadow = this.attachShadow({ mode: "open" });
    // attachShadow({mode}) — is element pe ek NAYA hidden DOM tree ka root banata hai, ek baar hi call ho sakta hai

    shadow.innerHTML = `
      <style> p { color: blue; } </style>
      <!-- ye <style> SIRF is shadow tree ke andar ke <p> ko affect karega -->
      <p>Hello, ${this.getAttribute("name")}</p>
    `;                        // template literal — shadow ke andar ka markup + scoped style ek saath
  }
});

Root-level mein kya ho raha hai: attachShadow call hote hi element ko do parallel subtree mil jaate hain — ek light DOM (jo tum HTML mein directly likhte ho, ya JS se this.appendChild karte ho) aur ek shadow tree (jo shadow.innerHTML/shadow.appendChild se banta hai). Browser ka rendering engine dono ko combine karke final visual output banata hai (jise "flattened tree" kehte hain), lekin ye combination sirf rendering ke liye hai — DOM API level pe dono strictly separate rehte hain.

  • Styles andar se bahar leak nahi hote — shadow root ke andar ka <style> sirf usi shadow tree ke elements ko target karta hai, page ke baaki hisse ko touch nahi karta.
  • Styles bahar se andar leak nahi hote — page ka global CSS (jaise p { color: red; } body mein kahin likha ho) shadow tree ke andar ke <p> ko affect nahi karta (kuch inheritable properties jaise font-family/color ka default inheritance exception hai, but selectors match nahi karte).
  • querySelector cross nahi karta — document.querySelector("p") shadow tree ke andar ke <p> ko dhoondh hi nahi payega. Andar jaane ke liye explicitly element.shadowRoot.querySelector(...) karna padta hai.
  • id namespace alag hai — shadow tree ke andar id="header" aur light DOM mein bhi id="header" ek saath exist kar sakte hain, koi collision nahi.
🧠 Senior Dev Note: ye encapsulation plain div se fundamentally alag hai

Ek plain <div class="widget"> "encapsulation" sirf naming convention (BEM, CSS Modules, styled-components ke scoped class names) se fake karta hai — build-time pe class names ko unique bana diya jaata hai, but runtime pe wo sab ek hi flat DOM tree aur ek hi global stylesheet cascade mein rehte hain. Shadow DOM ye guarantee browser engine level pe enforce karta hai — CSS specificity war, accidental selector collision, third-party widget ka CSS tumhare page ko todna — ye sab structurally impossible ho jaate hain, kisi naming convention discipline pe depend kiye bina. Yahi wajah hai ki YouTube, GitHub (<relative-time>), aur browser extensions apne injected UI ke liye Shadow DOM use karte hain — host page ka CSS unhe todh nahi sakta, aur unka CSS host page ko todh nahi sakta.

open vs closed mode — trade-off

attachShadow({mode}) mein do options hain, aur ye sirf ek JS-level access control hai — DOM/CSS encapsulation dono modes mein equally strong hoti hai:

open vs closed — shadowRoot accessibility
const openRoot = elem1.attachShadow({ mode: "open" });
console.log(elem1.shadowRoot); // -> #shadow-root (open) : koi bhi outside script isko access kar sakta hai
console.log(openRoot === elem1.shadowRoot); // -> true, same reference

const closedRoot = elem2.attachShadow({ mode: "closed" });
console.log(elem2.shadowRoot); // -> null : bahar se koi bhi property se access nahi mil sakta
// closedRoot variable ke through component ke apne code ke paas hi reference bacha rehta hai (closure ke andar)

Native browser elements jaise <input type="range"> ya <video> (jinke apne internal controls hain — slider thumb, play/pause button) internally closed shadow roots use karte hain, kyunki browser vendors nahi chahte ki koi website page JS se unke native controls ki internal structure ko manipulate kare.

⚠️ Practice mein closed mode ~99% avoid kyun kiya jaata hai

Closed mode security boundary nahi hai — ye sirf convenience-level access control hai. Koi bhi determined script Element.prototype.attachShadow ko monkey-patch karke (component load hone se pehle) shadow root ka reference chura sakta hai. To asli "protection" ye deta hai: DevTools mein casual inspection thoda harder ho jaata hai, aur galti se koi outside code tumhare component ka internal DOM query/modify nahi kar paata. Lekin iski keemat bahut zyada hai — testing libraries (Testing Library, Cypress), analytics tools, aur accessibility auditors jo shadowRoot traverse karke content verify karte hain, wo closed mode ke saath kaam nahi kar paate bina hacky workarounds ke. Isliye almost har production web component library (Lit, Stencil, etc.) default open mode use karti hai — encapsulation ka asli kaam DOM/CSS scoping already kar deta hai, JS-level hiding ka marginal benefit uske debugging/testing cost ko justify nahi karta.

<template> element — inert HTML jo clone hoke jeeta hai

<template> ek built-in HTML tag hai jiska content browser parse to karta hai (syntax validity check hoti hai), lekin render bilkul nahi karta — ye "out of the document" treat hota hai jab tak explicitly JS se clone na kiya jaaye.

template — content DOM mein show nahi hota
<template id="tmpl">
  <style> p { font-weight: bold; } </style> <!-- ye style page pe APPLY NAHI hoga jab tak clone na ho -->
  <p>Hello from template</p>       <!-- ye <p> page pe kahin render nahi hoga -->
  <img src="heavy.png">              <!-- image tab tak load NAHI hogi jab tak clone karke document mein na daali jaaye -->
</template>

Root mechanism: template.content property ek DocumentFragment return karti hai — ek lightweight, "parent-less" container jisme wo saara markup DOM node form mein already parsed pada hai, but jo kabhi bhi rendered document ka hissa nahi bana. DocumentFragment ki special property ye hai: jab tum use kisi real element mein appendChild karte ho, to fragment khud insert nahi hota — sirf uske children move ho jaate hain, fragment khaali reh jaata hai.

cloneNode(true) — content copy karke insert karna
const tmpl = document.getElementById("tmpl"); // template element ka reference nikala

const clone1 = tmpl.content.cloneNode(true);
// .content -> DocumentFragment; .cloneNode(true) -> DEEP clone (saare nested children samet)
// deep clone isliye zaroori hai kyunki har use pe alag independent DOM nodes chahiye, same reference nahi

document.body.append(clone1);
// append() hote hi fragment ke andar ke <style> aur <p> ab REAL document ka hissa ban jaate hain
// isi moment se style apply hoga, image load hogi — pehle ye sab "inert" tha

const clone2 = tmpl.content.cloneNode(true); // same template se dusra independent clone
document.body.append(clone2);          // ek hi template se multiple, independent instances banaye — reuse ka pura point yahi hai
importNode — cross-document clone (alternative)
const imported = document.importNode(tmpl.content, true);
// importNode(node, deep) — cloneNode jaisa hi kaam karta hai, lekin CROSS-DOCUMENT scenarios ke
// liye design hua tha (e.g. iframe se node current document mein laana) — same-document mein cloneNode ke barabar hi hai

shadow.append(imported);  // shadow root ke andar template content insert kiya

Web Components ka most common real-world pattern: Custom Element ke connectedCallback ke andar attachShadow karo, phir ek pehle-se-defined <template> (jo ya to page mein pada ho, ya JS string se banaya ho) ka content clone karke shadow root mein append karo — isse markup + scoped styles ek saath, efficiently (bina baar-baar innerHTML string parse kiye) reusable ban jaate hain.

Key Takeaways

  • Web Components = 4 native browser standards (Custom Elements, Shadow DOM, Template, ES Modules) — koi framework runtime dependency nahi, jahan bhi register ho wahan chalta hai.
  • Autonomous custom elements bilkul naya tag banate hain (<my-tag>); customized built-in existing tag extend karte hain (is="...") — but Safari support na hone ki wajah se practice mein autonomous zyada common hai.
  • Lifecycle order: constructor → (initial attrs ke liye) attributeChangedCallback → connectedCallback; baad mein attribute change hote hi sirf attributeChangedCallback, remove hote hi disconnectedCallback.
  • observedAttributes ek static getter hai jo batata hai kaunsi attributes hi watch honi hain — perf optimization, sab attributes watch nahi hoti.
  • Shadow DOM real encapsulation deta hai — CSS aur querySelector dono directions mein cross nahi karte, kisi naming convention discipline pe depend nahi karta.
  • open mode mein elem.shadowRoot accessible hai; closed mode mein null milta hai — but ye security nahi, sirf convenience hai, isliye 99% cases mein open use hota hai (testing/debugging tools ke liye).
  • <template> ka content ek DocumentFragment hai — inert (styles/scripts/images kuch bhi active nahi) jab tak cloneNode(true)/importNode se explicitly document mein insert na ho.

🎯 Interview Questions

  • Web components framework-independent kyun hote hain — React component ke saath compare karke batao.
    Hint: component definition browser ke native customElements registry mein compile hoti hai, kisi virtual-DOM/runtime library pe depend nahi karti — jahan bhi tag likho wahan kaam karega.
  • connectedCallback mein render karna best practice kyun hai, constructor mein kyun nahi?
    Hint: constructor bahut early call hota hai — attributes aur child nodes reliably available nahi hote; connectedCallback tak DOM insertion ho chuki hoti hai.
  • observedAttributes kya karta hai, aur agar isse skip kar diya to attributeChangedCallback ka kya hoga?
    Hint: static getter jo watch-list return karta hai; list mein na hone wali attribute change hone pe callback bilkul fire hi nahi hoga, chahe attribute actually badal jaaye.
  • Shadow DOM ki encapsulation ek plain div + scoped CSS class naming (jaise BEM) se fundamentally kaise alag hai?
    Hint: Shadow DOM engine-level guarantee hai (structurally impossible to leak), naming convention sirf discipline pe depend karta hai aur runtime pe koi real isolation nahi deta.
  • open aur closed shadow mode mein real difference kya hai, aur closed mode production mein kam kyun use hota hai?
    Hint: sirf JS-level shadowRoot access control hai, DOM/CSS isolation dono mein same hai; closed mode testing/debugging tools ko break kar deta hai bina koi real security add kiye.
  • template.content DocumentFragment kyun hai, aur append() karte time fragment khud kyun disappear ho jaata hai?
    Hint: DocumentFragment ek lightweight "parent-less" container hai — insert hote time uske children move hote hain, fragment khud kabhi document ka node nahi banta.
  • cloneNode(true) vs cloneNode(false) — deep clone kyun zaroori hai template content ke liye?
    Hint: false sirf top-level node clone karta, nested children chhod deta — template ka pura markup nested elements ka hi collection hota hai, isliye deep clone (true) mandatory hai.
