Zero-width assertions — root concept

Ab tak jitne bhi regex constructs dekhe (quantifiers, groups, character classes), sab consume karte hain — matlab wo characters ko match ke andar "kha" lete hain, aur regex engine ka cursor un characters ke aage badh jaata hai. Lookahead aur lookbehind is rule ko todte hain: ye sirf check karte hain ki aage ya peeche kya hai, lekin cursor ko wahan se aage nahi badhate aur match ke result string mein bhi include nahi hote. Isi wajah se inhe "zero-width" bola jaata hai — ye pattern mein 0 characters ka "width" occupy karte hain, sirf ek boolean condition ki tarah kaam karte hain.

Ye distinction capturing groups se bilkul alag hai: (abc) ek capturing group hai jo abc ko match aur consume dono karta hai, wo result string mein bhi hota hai. Jabki (?=abc) sirf check karta hai ki "abc" aage hai ki nahi — match mein include nahi hota, cursor bhi wahin ka wahin rehta hai.

Lookahead — (?=...) aur (?!...)

Positive lookahead X(?=Y) — X ko tabhi match karta hai jab uske turant baad Y ho, lekin Y match ke result mein shaamil nahi hota. Classic example: price ka number nikalna sirf tab jab uske baad $ ho, bina $ ko match mein include kiye.

Positive lookahead — price before $ sign, without $
let str = "Laptop costs 45000$, mouse costs 500 rupees"; // input string — dono numbers hain, lekin sirf ek ke baad $ hai

let regexp = /\d+(?=\$)/; // \d+ = ek ya zyada digits (consume hoga); (?=\$) = lookahead — check karo aage $ hai
                          // $ ko regex mein escape karna pada (\$) kyunki $ khud ek anchor metachar hai

console.log(str.match(regexp)[0]); // "45000" — sirf number match hua, $ result mein NAHI aaya
                                    // "500" match nahi hua kyunki uske baad $ nahi tha (baad mein "rupees" text hai)

Negative lookahead X(?!Y) — iska ulta: X ko tabhi match karta hai jab uske baad Y NA ho.

Negative lookahead — number jiske baad $ NAHI hai
let str = "Laptop costs 45000$, mouse costs 500 rupees"; // wahi input string

let regexp = /\d+\b(?!\$)/g; // \b = word boundary (digits ke turant baad khatam ho); (?!\$) = $ NAHI hona chahiye aage

console.log(str.match(regexp)); // ["500"] — sirf ye number match hua, kyunki 45000 ke baad $ tha

Lookbehind — (?<=...) aur (?<!...)

Lookbehind lookahead jaisa hi hai, bas direction opposite hai — ye check karta hai ki pehle (behind) kya tha, na ki aage kya hai. (?<=Y)X = positive lookbehind, X ko tabhi match karo jab pehle Y ho. (?<!Y)X = negative lookbehind.

Lookbehind — $ ke baad ka number nikalna, $ ko match mein shaamil kiye bina
let str = "Total: $45000, discount: 500 rupees"; // input — pehla number $ ke BAAD, doosra nahi

let regexp = /(?<=\$)\d+/; // (?<=\$) = lookbehind — check karo PEHLE $ tha; \d+ = fir digits match/consume karo

console.log(str.match(regexp)[0]); // "45000" — $ khud match mein nahi aaya, sirf uske baad ka number aaya

let negRegexp = /(?<!\$)\b\d+/g; // (?<!\$) = negative lookbehind — pehle $ NAHI hona chahiye
console.log(str.match(negRegexp)); // ["500"] — sirf ye, kyunki 45000 ke pehle $ tha
⚠️ Lookbehind browser support

Lookbehind (?<=...) / (?<!...) Safari ke purane versions aur IE mein support nahi hai — sirf V8-based engines (Chrome, Node.js, Edge) mein full support hai. Agar tumhara code Safari targets karta hai (production web app), to lookbehind se bachke equivalent logic capture-group + post-processing se likho, ya feature-detect karo.

Capturing groups lookaround ke andar

Lookaround khud consume nahi karta, lekin uske andar agar ek capturing group (...) daal do, to us group ka content capture ho jaata hai — bas match ke overall string mein include nahi hota. Ye useful hai jab tumhe "condition check karni hai aur uska ek part bhi nikalna hai".

Lookahead ke andar capturing group — currency symbol bhi nikalo
let str = "45000$, 3000₹, 800 plain"; // alag alag currency symbols wali string

let regexp = /\d+(?=(\$|₹))/g; // lookahead ke ANDAR ek capturing group (\$|₹) — dono symbols allowed

let matches = [...str.matchAll(regexp)]; // matchAll se poora match array + groups milte hain (aage detail mein)

matches.forEach(m => { // har match object pe loop
  console.log(m[0], "+", m[1]); // m[0] = number (main match), m[1] = symbol (lookahead ka captured group)
});
// Output: "45000" + "$"   "3000" + "₹"   (800 skip ho gaya — koi symbol match nahi hua)
🧠 Senior Dev Note: lookaround = validation, capturing = extraction

Root-level mental model: lookahead/lookbehind ka use karo jab tumhe context validate karna ho bina us context ko result mein chahiye ("number tabhi valid hai jab uske baad currency symbol ho, lekin symbol khud nahi chahiye"). Normal capturing groups ka use karo jab tumhe value extract karni ho. In dono ko mix karke — jaise upar wale example mein — tum ek hi regex se "conditional extraction" kar sakte ho, jo do-pass approach (pehle filter, fir extract) se zyada efficient aur readable hai. Production mein ye pattern email validation, password strength checks (positive lookahead se multiple conditions ek saath check karna, jaise "kam se kam ek digit ho AND ek uppercase ho"), aur log-parsing mein bahut common hai.

Catastrophic backtracking — root cause

Regex engine (JS ka backtracking engine) jab kisi quantifier se match try karta hai aur aage fail ho jaata hai, to wo backtrack karta hai — pehle try kiye hue characters chhod ke ek chhota match try karta hai. Normally ye fast hota hai. Lekin agar pattern mein nested quantifiers hain jinke beech ambiguity hai — matlab input ko multiple tareeko se split karke same result mil sakta hai — to engine har possible split try karta hai, aur combinations ki ginti exponentially badh jaati hai.

Classic example: pattern (a+)+b ko ek aisi string pe match karo jisme sirf a's hain aur end mein b nahi hai (jaise "aaaaaaaaaaaaaaaaaaaaaaaaa!" — 25 'a's, phir '!'). Trace karte hain ki andar kya hota hai:

Catastrophic backtracking demo — DON'T run in production without timeout
let regexp = /(a+)+b/; // outer (...)+ ke andar inner a+ — DOUBLY nested quantifier, ambiguous split

let str = "aaaaaaaaaaaaaaaaaaaaaaaaa!"; // 25 'a's phir '!' — 'b' kabhi milega hi nahi, so match guaranteed FAIL hoga

// WARNING: neeche wali line browser tab ko FREEZE kar degi — sirf trace samajhne ke liye, mat run karo
// console.log(regexp.test(str)); // engine hang ho jaayega kyunki har combination try karega

Kyun exponential? Outer group (a+)+ ka matlab hai "ek ya zyada groups, har group ke andar ek ya zyada a's". 25 'a's ko outer groups mein baantne ke liye 224 se zyada tareeke hain — jaise sab 25 ek hi group mein, ya 24+1 split, ya 1+1+...+1 (25 groups), ya har combination beech mein. Har split try karne ke baad engine 'b' dhoondhta hai, fail hota hai, phir agla split try karta hai. n characters ke liye combinations ~2n hain — n=20 pe ~1 million combinations, n=30 pe ~1 billion. CPU 100% pe chala jaata hai aur practically hang ho jaata hai — kabhi terminate hi nahi hoga (well, technically hoga, lekin universe ke heat death se pehle nahi).

🚨 ReDoS — ye production security risk hai, sirf performance bug nahi

Ye sirf ek "slow regex" ka issue nahi hai — ye ek real, named attack class hai jise ReDoS (Regular Expression Denial of Service) kehte hain. Agar tumhara server-side code kabhi bhi user-controlled input ko ek vulnerable regex pattern se match karta hai (jaise email validation, username format check, log parsing pattern jo request headers pe chalta hai), to ek attacker jaan-bujhkar aisi input bhej sakta hai (jaise 30 'a's + koi non-matching character) jo tumhare Node.js process ko single-threaded event loop pe hi block kar degi — Node mein regex matching synchronous hai, so wo poora process (sab requests, sab users) tab tak freeze rehta hai jab tak wo ek match complete nahi karta, jo practically kabhi nahi hoga. Ye ek single crafted HTTP request se poore server ko down kar sakta hai — CVE database mein isi tarah ke real-world ReDoS vulnerabilities kai popular npm packages mein report ho chuke hain (jaise moment.js, validator.js ke purane versions).

Production mein bachne ke tareeke: (1) Kabhi bhi nested ambiguous quantifiers mat likho jaise (a+)+, (a*)*, (a|a)* — inner aur outer quantifier ke beech ambiguity ko explicitly resolve karo (jaise a+ sirf, ya mandatory separator daalo). (2) Third-party/user-supplied regex patterns ko kabhi directly trust mat karo — agar accept karna hi ho, to timeout ke saath sandboxed worker mein run karo (jaise vm2 ya separate worker thread jisko kill kar sako). (3) Regex linting tools use karo (jaise eslint-plugin-security ka detect-unsafe-regex rule, ya safe-regex npm package) jo CI mein hi catastrophic patterns detect kar lein commit hone se pehle. (4) Simple validations ke liye regex ki jagah manual string methods (startsWith, includes) ya established validated libraries use karo jo already ReDoS-audited hain.

Fix ka pehla tareeka — pattern rewrite karo taaki ambiguity khatam ho jaaye. Jaise ^(\w+\s?)*$ (jisme space optional hai, so "word" aur "word+space" split overlap karte hain) ko ^(\w+\s)*\w*$ mein badlo — ab space mandatory hai within repetition, har character ko match karne ka sirf ek hi tareeka bachta hai, ambiguity gayab.

Fix option 1 — pattern rewrite, ambiguity hatao
// BAD: \s? optional hai, so ek "word " ko "word" + " " do tareeko se treat kar sakte ho
let bad = /^(\w+\s?)*$/; // nested quantifier + optional separator = ReDoS risk

// GOOD: space ko is repeated group ke andar MANDATORY bana diya, aakhri word alag se optional
let good = /^(\w+\s)*\w*$/; // ab har character ka position match karne ka EK hi tareeka hai — no ambiguity

Fix ka doosra tareeka — lookahead se backtracking hi rok do. Ye technique thodi advanced hai — ek named capturing group ke saath lookahead combine karke engine ko force karte hain ki wo poore word ko atomically match kare, partial splits try hi na kare.

Fix option 2 — lookahead se atomic-group jaisa behavior
let regexp = /^((?=(?<word>\w+))\k<word>\s?)*$/;
// (?=(?<word>\w+)) = lookahead jo poora word ek named group "word" mein capture karta hai, bina consume kiye
// \k<word> = backreference — jo lookahead ne dekha wahi poora word yahaan CONSUME karo, ek hi piece mein
// \s? = optional trailing space
// Result: engine ab word ko todke alag-alag tareeko se try nahi karta — lookahead ne already "poora word" commit kar diya

Sticky flag "y" vs global flag "g"

g flag wale regex, lastIndex se search shuru karte hain — agar exact position pe match nahi milta, to engine aage scan karta rehta hai jab tak match nahi milta ya string khatam nahi hoti. y (sticky) flag iske bilkul against hai: match exactly lastIndex position pe hi hona chahiye — agar nahi hai, to null return hota hai, engine aage scan bilkul nahi karta.

g vs y — same position, different behavior
let str = "let varName"; // position 3 pe space hai ("let" ke baad), position 4 se "varName" shuru hota hai

let gRegexp = /\w+/g;              // global flag
gRegexp.lastIndex = 3;         // search yahin se "shuru" karo, lekin aage scan bhi kar sakta hai
console.log(gRegexp.exec(str)); // "varName" mila — engine ne position 3 (space) skip karke position 4 tak scan kiya

let yRegexp = /\w+/y;              // sticky flag
yRegexp.lastIndex = 3;         // match EXACTLY position 3 pe hona chahiye
console.log(yRegexp.exec(str)); // null — position 3 pe space hai, \w+ wahan match nahi hota, aage scan nahi hua

Real use-case: tokenizer / lexical analyzer. Jab tum ek programming language ya template syntax ko incrementally parse karte ho — token by token, sequentially, bina kisi gap ke — to y flag exactly wahi guarantee deta hai jo chahiye: "agla token yahin se, bilkul yahin se shuru hona chahiye, warna input invalid hai".

Mini tokenizer using sticky flag
let str = "let x = 10"; // jise hume token-by-token parse karna hai

let wordRegexp = /\w+/y;       // sticky — identifier/number tokens ke liye
let spaceRegexp = /\s+/y;      // sticky — whitespace tokens ke liye
let eqRegexp = /=/y;          // sticky — "=" operator ke liye

let pos = 0;                 // current parse position — hum khud track karte hain
let tokens = [];            // yahan tokens accumulate honge

while (pos < str.length) {  // jab tak poori string consume nahi ho jaati
  spaceRegexp.lastIndex = pos;              // har regex ka lastIndex current pos pe sync karo
  let spaceMatch = spaceRegexp.exec(str); // try karo whitespace token
  if (spaceMatch) { pos += spaceMatch[0].length; continue; } // mila to pos aage badhao, whitespace token skip karo

  eqRegexp.lastIndex = pos;
  let eqMatch = eqRegexp.exec(str);       // try karo "=" operator token
  if (eqMatch) { tokens.push({ type: "eq", value: "=" }); pos++; continue; }

  wordRegexp.lastIndex = pos;
  let wordMatch = wordRegexp.exec(str);   // try karo word/number token
  if (wordMatch) {
    tokens.push({ type: "word", value: wordMatch[0] }); // token push karo
    pos += wordMatch[0].length;              // pos ko token ki length jitna aage badhao
    continue;
  }

  throw new Error(`Unexpected token at pos ${pos}`); // koi bhi regex match nahi hua = invalid syntax, error throw karo
}

console.log(tokens); // [{word,"let"}, {word,"x"}, {eq,"="}, {word,"10"}]

Agar yahaan y ki jagah g use karte, to koi bhi malformed/unexpected character silently skip ho jaata — engine bas aage scan karke agla valid token dhoond leta, error kabhi throw hi nahi hota, aur tumhara parser galat tokens produce karta rehta bina crash hue. y flag "fail fast, fail loud" guarantee deta hai jo parsers ke liye correctness ke liye zaroori hai.

RegExp / String method surface

JS mein regex ke saath kaam karne ke liye 7 major methods hain — kuch RegExp.prototype pe hain, kuch String.prototype pe. Har ek ka return type aur use-case alag hai.

test / exec / match / matchAll / replace / replaceAll / split
// 1. regexp.test(str) — sirf boolean chahiye ki match hai ya nahi
let hasDigit = /\d/.test("abc123"); // true — fastest method for existence check
// GOTCHA: agar regex mein "g" flag hai, to test() lastIndex update karta hai —
// same global regexp ko baar-baar test() karoge to results alternate ho sakte hain

// 2. regexp.exec(str) — ek match ka full detail (groups, index) chahiye, ya loop mein sab chahiye
let m = /(\d+)/.exec("abc123"); // m[0]="123", m[1]="123" (group), m.index=3
// "g" flag ke saath repeated calls lastIndex se aage badhte hain — manual loop tokenizing ke liye useful

// 3. str.match(regexp) — WITHOUT g: pehla match, groups+index sahit (exec jaisa)
let single = "abc123".match(/\d+/); // ["123", index: 3, input: "abc123", groups: undefined]

// 3b. str.match(regexp) — WITH g: sab matches, sirf strings ka array, groups/index GAYAB
let all = "a1 b22 c333".match(/\d+/g); // ["1", "22", "333"] — sirf full matches, koi group detail nahi
// No match milne pe match() null return karta hai — [] NAHI

// 4. str.matchAll(regexp) — g flag MANDATORY, sab matches + har ek ke groups bhi (best of match+exec)
let iterator = "a1 b22 c333".matchAll(/(\w)(\d+)/g); // iterable milta hai, array nahi — lazy evaluation
let arr = [...iterator]; // spread se array bana lo agar length/random-access chahiye
// arr[0] = ["a1","a","1", index:0, ...], arr[1] = ["b22","b","22", index:3, ...] — full detail, sab matches

// 5. str.replace(pattern, replacement) — string pattern ho to SIRF PEHLA occurrence replace hota hai
let r1 = "a-b-c".replace("-", "_"); // "a_b-c" — sirf pehla "-" badla, doosra as-is reh gaya
let r2 = "a-b-c".replace(/-/g, "_"); // "a_b_c" — regex + g flag = sab occurrences
let r3 = "John Smith".replace(/(\w+) (\w+)/, "$2 $1"); // "Smith John" — $1/$2 = captured groups reference

// 6. str.replaceAll(pattern, replacement) — string pattern ho to bhi SAB occurrences replace
let r4 = "a-b-c".replaceAll("-", "_"); // "a_b_c" — string pattern ke saath bhi sab replace, replace() se yahi farak hai
// GOTCHA: regexp pattern do to "g" flag COMPULSORY hai, warna TypeError throw hoga

// 7. str.split(pattern, limit) — string ko regex/substring ke basis pe todke array banao
let parts = "12,  34,56".split(/,\s*/); // ["12","34","56"] — comma + optional spaces ko flexible delimiter treat kiya

Comparison table — kab kaunsa method use karna hai, jaldi decide karne ke liye:

MethodReturn typeg flag ka effectKab use karo
test() Boolean lastIndex track hota hai — repeated calls pe gotcha Sirf "match hai ki nahi" check karna hai, value nahi chahiye
exec() Array (groups+index) ya null lastIndex se next match — manual loop possible Ek match ka full detail, ya legacy manual iteration loop
match() Array ya null Without g: full detail (exec jaisa). With g: sirf strings, no groups Bina g: single match with groups. Sang g: bas saare matched strings chahiye
matchAll() Iterable (spread se array) Mandatory — bina g TypeError Sab matches + har ek ke groups+index chahiye — modern replacement for exec loop
replace() Naya string String pattern: sirf pehla. Regex bina g: sirf pehla. Regex with g: sab Pehla ya sab replace, groups reference ($1) ya callback function ke saath
replaceAll() Naya string Regex pattern ho to g mandatory (warna error) Sab occurrences replace — string pattern ke saath bhi (replace() isme fail karta)
split() Array of strings N/A — split hamesha sab delimiters pe todta hai String ko flexible/regex-based delimiter pe tokenize/break karna hai
⚠️ test() aur exec() ka lastIndex gotcha

Agar regex mein g flag hai, to test() aur exec() dono internally regex object ke lastIndex property ko update karte hain — jo agli call ko affect karta hai. Ye tab dangerous hota hai jab tum same regex object ko multiple alag-alag strings pe reuse karte ho (e.g. ek validation function jo module-level regex use karti hai): pehli call match kar degi, doosri call fail kar sakti hai kyunki lastIndex pichhli call se non-zero reh gaya. Fix: har baar naya regex banao, ya g flag hi hatao agar tumhe sirf single test chahiye, ya explicitly regexp.lastIndex = 0 reset karo har use se pehle.

Key Takeaways

  • Lookahead (?=...)/(?!...) aur lookbehind (?<=...)/(?<!...) zero-width assertions hain — check karte hain, consume ya capture (result string mein) nahi karte.
  • Lookaround ke andar agar capturing group ho, to uska content capture hota hai — sirf overall match mein include nahi hota.
  • Lookbehind Safari/IE mein historically unsupported tha — production cross-browser code mein caution zaroori.
  • Catastrophic backtracking nested ambiguous quantifiers (jaise (a+)+) se hota hai — combinations exponentially (2^n) badhte hain.
  • Ye sirf performance issue nahi, ek real ReDoS security vulnerability hai — user-controlled input pe vulnerable regex chalana poore server ko block kar sakta hai (Node ka single-threaded event loop).
  • Fix: pattern rewrite karke ambiguity hatao, ya lookahead+backreference se atomic-group jaisa behavior force karo, ya user-supplied regex ko timeout/sandbox mein run karo.
  • Sticky flag "y" match sirf exact lastIndex position pe force karta hai — "g" ki tarah aage scan nahi karta. Tokenizers/parsers ke liye zaroori.
  • 7 methods: test (boolean), exec (single match, loop-capable with g), match/matchAll (multiple matches, groups), replace/replaceAll (substitution), split (tokenize by delimiter).

🎯 Interview Questions

  • Lookahead aur capturing group mein fundamental farak kya hai?
    Hint: dono match ke against condition check karte hain, lekin capturing group consume + result mein include hota hai, lookahead sirf check karta hai — zero-width, result se bahar.
  • (a+)+b pattern ek non-matching string pe catastrophic backtracking kyun karta hai? Root cause samjhao.
    Hint: input ko outer groups mein baantne ke exponentially many (2^n) tareeke hain, engine har ek try karta hai fail hone se pehle 'b' na milne ki wajah se.
  • ReDoS attack production mein kaise exploit hota hai, aur kaise prevent karoge?
    Hint: user input ek vulnerable regex se match hone pe Node ka single-threaded event loop block ho jaata hai; prevention = ambiguous quantifiers avoid karo, timeout/worker sandbox use karo, regex linting.
  • Sticky flag "y" aur global flag "g" ka behavior kaise differ karta hai jab lastIndex set ho?
    Hint: g flag lastIndex se search karta hai (aage scan kar sakta hai), y flag sirf exact lastIndex position pe match force karta hai, warna null.
  • str.match() ka return type "g" flag ke saath aur bina "g" flag ke kaise alag hota hai?
    Hint: bina g = single match array with groups+index (exec jaisa); with g = sirf matched strings ka array, groups/index gayab.
  • matchAll() ko exec() ke manual loop se better kyun consider kiya jaata hai?
    Hint: matchAll ek clean iterable deta hai jisme har match ke groups+index milte hain, jabki exec loop manually lastIndex track karna padta hai aur infinite-loop bug ka risk hota hai agar regex "g" flag bhool jaaye.
  • replace() aur replaceAll() mein string pattern ke case mein kya farak hai?
    Hint: replace() string pattern ke saath sirf pehla occurrence replace karta hai, replaceAll() sab — regex pattern ke saath replaceAll ko "g" flag mandatory chahiye warna TypeError.
