Error Handling

Production code mein cheezein fail hongi hi — network down ho sakta hai, JSON malformed aa sakta hai, user ka input garbage ho sakta hai. Farak achhe aur bure engineer mein ye hai ki error hone par program crash hota hai ya gracefully recover karta hai. Is chapter mein try/catch/finally ka exact execution model, Error object ke andar kya hota hai, aur ek proper layered custom-error hierarchy kaise banayein — root-level, senior-dev depth ke saath dekhte hain.

try/catch mechanics — root-level flow

try...catch ka basic idea simple hai: try block ke andar wala code execute hota hai, aur agar beech mein koi runtime exception throw hoti hai, to JS engine turant us block ke andar aage ka execution rok deta hai aur control seedha catch block mein jump kar deta hai — error object ke saath.

try/catch basic flow
try {                                  // try block: yahan wo code jo fail ho sakta hai
  console.log("start");              // ye line normally chalti hai, print hoga "start"
  let result = undefined.x;   // undefined.x — TypeError throw karega yahan
  console.log("never reached"); // engine yahan tak kabhi nahi pahunchega — try turant abort ho gaya
} catch (err) {                    // catch(err): error object yahan milta hai jaise hi try fail ho
  console.log("caught: " + err.message); // "caught: Cannot read properties of undefined..."
}
// agar try mein koi error na aati, catch block ka pura body skip ho jaata — bilkul run hi nahi hota

Root-level pe important cheez: agar error na aaye to catch block execute hi nahi hota — sirf error-path mein wo triggered hota hai. Ye ek control-flow branch hai jo normal execution se completely alag hai (exception unwinding), function calls ke beech-beech mein bhi kaam karta hai — agar try ke andar ek deep nested function call throw karti hai, to bhi wahi catch catch karega, bashart beech mein koi aur try/catch na ho jo pehle intercept kar le.

⚠️ Sirf runtime errors — parse-time errors nahi

try/catch ka mechanism sirf valid, syntactically-correct code pe kaam karta hai jo runtime pe fail hota hai. Agar tumhare try block ke andar hi syntax error hai (jaise ek missing closing brace), JS engine code ko parse hi nahi kar payega — aur ye ek parse-time failure hai jo pura script load hone se pehle hi hota hai. Iska matlab try/catch ye catch nahi kar sakta, kyunki engine ne abhi tak us code ko "samjha" hi nahi.

Error object — name, message, stack

Jab bhi koi built-in error throw hoti hai (ya tum khud new Error(...) banate ho), result object teen standard properties leke aata hai. Root cause: JS engine ke andar built-in Error constructor approximately is tarah kaam karta hai —

Error ka internal shape (conceptual)
class Error {                          // built-in Error class ka mental model — asli spec-defined hai, ye simplified hai
  constructor(message) {              // constructor sirf "message" leta hai
    this.message = message;       // message: human-readable description jo humne pass kiya
    this.name = "Error";          // name: default "Error" — subclasses (TypeError etc) ise override karte hain
    this.stack = <call stack>;  // stack: non-standard lekin sab engines support karte hain — call chain string
  }
}
Error properties inspect karna
try {
  lalala;                          // undeclared variable ko reference kiya — ReferenceError guaranteed
} catch(err) {
  console.log(err.name);        // "ReferenceError" — error ka exact type/class naam
  console.log(err.message);     // "lalala is not defined" — human-readable detail
  console.log(err.stack);       // nested call trace with line numbers — debugging ke liye gold hai
  console.log(err);            // pura object as-is — devtools mein pretty-printed dikhta hai
}

stack technically ECMA-262 spec ka part nahi hai, lekin V8 (Chrome/Node), SpiderMonkey (Firefox), aur JavaScriptCore (Safari) — sab isko de dete hain, isliye practically de-facto standard hai. Production logging/monitoring (Sentry jaise tools) is stack trace pe hi depend karte hain root cause pinpoint karne ke liye.

throw operator — aur non-Error values kyun avoid karo

throw literally kuch bhi throw kar sakta hai — string, number, plain object, ya ek proper Error instance. Lekin sirf Error (ya uski subclass) throw karna hi convention hai:

throw ke saath sahi vs galat pattern
// GALAT: plain string throw karna
throw "Something broke";      // technically valid JS hai, lekin ismein .stack, .name kuch nahi hoga

// SAHI: Error (ya subclass) throw karna
throw new Error("Something broke"); // stack trace milta hai, instanceof checks kaam karte hain
throw new TypeError("Expected a number"); // built-in specific types bhi use kar sakte ho jab appropriate ho
⚠️ Non-Error throw karne se debugging nightmare banta hai

Agar tum throw "some string" karte ho, to catch block mein err.stack undefined hoga — call trace gaya. Agar koi upstream code assume karta hai ki err instanceof Error true hoga (jo ek reasonable assumption hai), aur tumne string throw kar di, to wo check silently fail ho jaayega aur error ka type-checking logic bypass ho jaayega. Har production codebase mein rule hona chahiye: hamesha Error ya uski subclass hi throw karo, kabhi raw value nahi.

finally ka execution guarantee — return/throw ke saath bhi

finally block hamesha chalta hai — chahe try normally complete ho, chahe error aaye aur catch use handle kare, ya chahe try ke andar hi return ya throw ho jaaye. Ye guarantee root mechanism hai resource-cleanup (file handles, DB connections, locks) ke liye.

finally: return ke baad bhi guaranteed run
function test() {
  try {
    console.log("try: start");   // pehle ye print hoga
    return "try-value";          // return yahan trigger ho gaya — lekin function turant exit NAHI hota
  } finally {
    console.log("finally: cleanup"); // return ke baad bhi ye chalta hai, function exit se PEHLE
  }
  // engine ka exact order: try ka return VALUE compute + "park" hota hai,
  // finally poora run hota hai, aur TAB parked value actually return hota hai
}

console.log(test());
// Output order: "try: start" -> "finally: cleanup" -> "try-value"

Root-level detail jo bahut log log miss karte hain: agar try ke andar return X hai, engine X ko turant return nahi karta — pehle finally poora execute hota hai, phir parked return value ke saath function actually exit hota hai. Isi tarah agar try ke andar exception throw hui aur catch use rethrow karta hai, to bhi finally beech mein chalega, error propagate hone se pehle.

finally: rethrow ke saath bhi guaranteed
function riskyOp() {
  try {
    throw new Error("db connection lost"); // try ke andar hi error throw ho gayi
  } finally {
    console.log("closing connection..."); // ye phir bhi chalega — catch hai hi nahi yahan, par finally chalega
  }
  // finally ke baad, original error ab bhi propagate hoti hai upar wale caller tak —
  // finally usse "consume" nahi karta jab tak khud koi return/throw na kare
}
⚠️ finally ke andar khud return/throw karna = original error/value overwrite

Agar finally block ke andar khud return ya throw hai, to wo try/catch ke original outcome ko silently override kar deta hai — chahe try mein error hui ho ya normal return. Ye ek classic bug source hai (jaise finally mein galti se return false reh jaana), isliye finally ko strictly cleanup ke liye use karo, control-flow (return/throw) ke liye nahi.

try/catch async code ko catch kyun nahi karta

Ye sabse common senior-level gotcha hai. try/catch sirf synchronous code ko cover karta hai jo usi call-stack frame ke andar directly execute hota hai. Agar try block ke andar setTimeout ya koi Promise callback schedule kiya, to us callback ka actual execution baad mein, ek naye call stack ke saath hota hai — us waqt tak original try/catch ka scope already khatam ho chuka hota hai (call stack unwind ho chuka hota hai), so wahan hui error ko wapas catch karne ka koi rasta nahi bachta.

Galat: setTimeout ke andar throw try/catch se bahar hai
try {
  setTimeout(function() {       // setTimeout callback: engine ye baad mein, event loop se schedule karta hai
    null.foo;                  // yahan TypeError throw hogi — LEKIN ek naye call stack mein
  }, 1000);
} catch (err) {
  console.log("never runs");     // ye kabhi trigger hi nahi hoga — synchronously try/catch turant khatam ho gaya
}
// Result: uncaught TypeError, seedha console mein crash-like error dikhega
Sahi: try/catch ko async callback ke ANDAR rakho
setTimeout(function() {
  try {                              // try/catch ab wahi call stack frame ke andar hai jahan error throw hogi
    null.foo;                  // TypeError throw
  } catch (err) {
    console.log("caught: " + err.message); // ab sahi se catch ho jaayega
  }
}, 1000);

Promises ke liye equivalent solution alag hai — direct try/catch Promise constructor executor ke andar chalti hai (kyunki wo synchronously execute hota hai), lekin Promise rejection ko handle karne ka sahi tareeka .catch() hai, ya async/await ke saath try/catch (jahan await effectively rejection ko throw mein convert karta hai — ye Chapter 13 mein detail se cover hoga).

⚠️ Global handlers safety-net hain, primary strategy nahi

Browser mein window.onerror / window.addEventListener("error", ...) aur unhandled promise rejections ke liye window.addEventListener("unhandledrejection", ...) milte hain — ye "last resort" global catch hain (logging/monitoring ke liye, jaise Sentry). Inpe depend karke normal error handling skip mat karo — ye sirf ek safety net hai jab kuch slip ho jaaye, actual recovery logic yahan se nahi likhi jaati.

Rethrowing pattern — catch specific, rethrow unknown

Ek catch block sirf un errors ko handle kare jinke baare mein use pata hai — baaki sabko rethrow kar de. Ye pattern bugs ko silently swallow hone se bachata hai; agar tum har error ko blindly "handle" kar doge, to genuine programming bugs (jaise typo se undefined access) bhi silently ignore ho jaayenge, aur debug karna nightmare ban jaayega.

Rethrow: sirf expected error type handle karo
function readUser(json) {
  let user = JSON.parse(json);    // malformed JSON pe ye khud SyntaxError throw kar dega

  if (!user.age) {            // business-rule validation: age field missing
    throw new Error("No field: age"); // generic Error — ideally custom class hoga (aage dekhenge)
  }

  return user;
}

try {
  let user = readUser('{ bad json'); // intentionally malformed input
} catch (err) {
  if (err instanceof SyntaxError) { // case 1: JSON.parse fail hua — hume iska pata hai, handle karo
    console.log("Invalid JSON: " + err.message);
  } else {
    throw err;                    // case 2: kuch aur (unexpected bug) — hume iske baare mein pata nahi, RETHROW karo
  }                                // rethrow karne se ye ek OUTER try/catch (agar exist kare) tak propagate hogi
}

Yahan err instanceof SyntaxError use kiya, err.name === "SyntaxError" nahi — kyunki instanceof inheritance chain ko respect karta hai. Jaise hi hum apni custom error classes banayenge (jo Error se extend hongi), instanceof checks automatically parent classes ke against bhi true return karenge — string comparison (.name) ye guarantee nahi deta agar naming kahin typo ho jaaye.

Custom error hierarchy banana — extending Error

Real applications mein generic Error kaafi nahi hota — humein pata hona chahiye ki kis kism ki error hai: validation fail hui, ya required field missing hai, ya network fail hua. Iske liye hum Error ko extend karke apni class hierarchy banate hain.

Level 1: ValidationError extends Error
class ValidationError extends Error {    // built-in Error class se inherit — subclassing pattern
  constructor(message) {
    super(message);              // super(): parent Error constructor call karna ZAROORI hai —
                                    // isi se this.message set hota hai aur this.stack generate hota hai
    this.name = "ValidationError"; // super() ke baad name reset karo — warna "Error" hi reh jaayega
  }
}

function test() {
  throw new ValidationError("Whoops!"); // custom error instance throw kiya
}

try {
  test();
} catch(err) {
  console.log(err.message);       // "Whoops!"
  console.log(err.name);          // "ValidationError"
  console.log(err instanceof ValidationError); // true
  console.log(err instanceof Error);      // true — chain ke through parent bhi match karta hai
}

Ab isse aage badhate hain — ek deeper hierarchy jahan PropertyRequiredError, ValidationError ka hi ek more-specific subtype hai. Ye real production pattern hai: broad category (ValidationError) se lekar specific reason (PropertyRequiredError) tak.

Level 2: PropertyRequiredError extends ValidationError
class ValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = "ValidationError";
  }
}

class PropertyRequiredError extends ValidationError { // ab ValidationError se hi extend kar rahe hain — 2-level chain
  constructor(property) {            // constructor ka signature alag hai — property name leta hai, message nahi
    super("No property: " + property); // message KHUD construct karke parent (ValidationError) ko diya
    this.name = "PropertyRequiredError"; // name ko is level pe phir se override kiya
    this.property = property;       // extra custom data — kaunsa property missing tha, structured field mein
  }
}

function readUser(json) {
  let user = JSON.parse(json);          // bad JSON pe engine khud SyntaxError throw karega

  if (!user.age) {
    throw new PropertyRequiredError("age"); // specific subtype throw kiya, generic ValidationError nahi
  }
  if (!user.name) {
    throw new PropertyRequiredError("name");
  }

  return user;
}

try {
  let user = readUser('{ "age": 25 }'); // "name" field missing hai isme
} catch (err) {
  if (err instanceof ValidationError) {   // broad category check — PropertyRequiredError bhi isme MATCH karega,
                                          // kyunki wo chain mein ValidationError se hi extend hota hai
    console.log("Invalid data: " + err.message); // "Invalid data: No property: name"
    console.log(err.name);              // "PropertyRequiredError" — exact subtype yahan preserved hai
    console.log(err.property);          // "name" — custom field jo humne add kiya tha
  } else if (err instanceof SyntaxError) { // JSON.parse ki apni error — alag branch
    console.log("JSON Syntax Error: " + err.message);
  } else {
    throw err;                      // unknown error type — rethrow karo, mat swallow karo
  }
}

Har level pe this.name manually likhna repetitive hai. Ek clean pattern: ek base MyError class banao jo automatically this.constructor.name se name derive kare — is trick se child classes ko sirf apna logic likhna padta hai, name assignment repeat nahi karna padta.

DRY pattern: MyError base class
class MyError extends Error {
  constructor(message) {
    super(message);
    this.name = this.constructor.name; // this.constructor: jo bhi asli class instantiate hui uska reference —
                                        // chahe MyError ho, ValidationError ho, ya kisi bhi depth ka subclass —
                                        // .name automatically class ka sahi naam de deta hai, hardcode nahi karna padta
  }
}

class ValidationError extends MyError { }  // khaali body — sirf naming ke liye ek intermediate layer hai

class PropertyRequiredError extends ValidationError {
  constructor(property) {
    super("No property: " + property); // message chain ke through MyError tak jaata hai
    this.property = property;       // name yahan set karne ki zaroorat nahi — MyError ka constructor already kar chuka
  }
}

console.log(new PropertyRequiredError("field").name); // "PropertyRequiredError" — automatically correct
🧠 Senior Dev Note: transpiled/older environments mein extends Error tootta tha

Babel jaise transpilers (ES5 target ke saath) mein class X extends Error ka naive downleveling historically broken hota tha — instanceof checks fail ho jaate the aur custom properties (this.name, custom fields) parent constructor ke baad set hote hue bhi kabhi-kabhi lost ho jaate the. Root cause: ES5 mein built-in classes (Error, Array) properly subclass nahi ho sakte the kyunki unka internal [[Construct]] behavior native tha, jabki transpiled code plain function + prototype-chain simulate karta tha — super(message) call se return hua object asal mein wahi instance nahi hota jispe tum aage properties set kar rahe ho. Fix: modern TypeScript/Babel setups mein target ko ES2015+ rakho, ya agar ES5 target zaroori hai to explicitly Object.setPrototypeOf(this, X.prototype) constructor ke andar call karo taaki prototype chain manually fix ho jaaye. Node.js aur modern browsers (native ES2015+ classes) mein ye problem exist hi nahi karta — sirf legacy transpile targets mein aata hai, lekin agar tum ek library maintain kar rahe ho jo purane bundlers/browsers support karti hai, ye trap yaad rakhna zaroori hai.

Wrapping exceptions pattern

Jab ek function multiple different types ki low-level errors throw kar sakta hai (jaise JSON parse fail, ya validation fail), to caller ko har low-level type individually handle karne ke bajaye, ek single high-level wrapper error do jo original error ko cause property mein preserve kare. Ye caller-side handling ko drastically simplify karta hai.

ReadError: low-level errors ko wrap karna
class ReadError extends Error {
  constructor(message, cause) {       // do params: apna message, aur original error (cause)
    super(message);
    this.cause = cause;            // cause: original low-level error ko yahan store kiya — kuch lose nahi hota
    this.name = "ReadError";
  }
}

function validateUser(user) {
  if (!user.age) throw new PropertyRequiredError("age");
  if (!user.name) throw new PropertyRequiredError("name");
}

function readUser(json) {
  let user;

  try {
    user = JSON.parse(json);            // stage 1: parsing — SyntaxError yahan aa sakti hai
  } catch (err) {
    if (err instanceof SyntaxError) {
      throw new ReadError("Syntax Error", err); // original SyntaxError ko cause ke roop mein wrap karke throw
    } else {
      throw err;                    // koi anjaan error — rethrow, wrap mat karo
    }
  }

  try {
    validateUser(user);              // stage 2: business validation — ValidationError family aa sakti hai
  } catch (err) {
    if (err instanceof ValidationError) {
      throw new ReadError("Validation Error", err); // isko bhi wrap kiya — caller ko sirf ReadError dikhega
    } else {
      throw err;
    }
  }

  return user;
}

try {
  readUser('{bad json}');
} catch (e) {
  if (e instanceof ReadError) {    // caller sirf EK type check karta hai — ReadError
    console.log(e);                // "ReadError: Syntax Error"
    console.log("Original: " + e.cause); // underlying SyntaxError bhi accessible hai .cause se, drop nahi hua
  } else {
    throw e;
  }
}

Note: modern JS (ES2022+) mein native Error constructor khud bhi ek second argument ke roop mein { cause: err } option accept karta hai (new Error("msg", { cause: err })), jo yahi cause convention standardize karta hai — lekin custom class mein manually property set karna older environments mein bhi kaam karta hai aur zyada explicit hai.

Key Takeaways

  • try/catch sirf synchronous code cover karta hai — setTimeout/Promise callbacks ke andar try/catch khud us callback ke andar hona chahiye.
  • finally hamesha chalta hai — chahe try normal complete ho, error ho, ya try ke andar return/throw ho. Return value finally ke poora hone ke baad hi actually return hoti hai.
  • finally ke andar khud return/throw karna original outcome ko silently override kar deta hai — sirf cleanup ke liye use karo.
  • Hamesha Error (ya subclass) throw karo, raw string/object nahi — warna .stack aur instanceof checks kaam nahi karenge.
  • Rethrowing pattern: sirf jaana-pehchana error type handle karo, baaki throw err se propagate hone do — bugs silently swallow mat karo.
  • Custom errors banate waqt super(message) call karna mandatory hai, aur uske baad this.name set karo (ya this.constructor.name trick use karo).
  • instanceof ko .name string comparison se prefer karo — inheritance chain ke saath correctly kaam karta hai.
  • Wrapping exceptions (cause property) multi-source errors ko ek single high-level type mein consolidate karta hai, caller-side handling simplify karta hai.

🎯 Interview Questions

  • try/catch ke andar setTimeout mein throw hui error kyun catch nahi hoti?
    Hint: setTimeout callback ek naye call stack frame mein, baad mein execute hota hai — us waqt tak original try/catch ka scope already unwind ho chuka hota hai.
  • finally aur try ke andar return dono ho, to execution order aur return value kya hoga?
    Hint: try ka return value pehle compute/park hota hai, phir finally poora chalta hai, uske baad hi parked value actually return hoti hai — order hamesha finally return se pehle poora complete hota hai.
  • finally ke andar khud return/throw karne se kya problem ho sakti hai?
    Hint: ye try/catch ka original outcome (chahe normal ho ya error) silently overwrite kar deta hai — classic subtle bug source.
  • Custom error class mein super(message) call karna kyun mandatory hai?
    Hint: parent Error constructor hi this.message set karta hai aur this.stack generate karta hai — super() call kiye bina ye missing rahenge, aur JS engine subclass constructor mein this ko super() se pehle use karne bhi nahi dega.
  • err.name === "ValidationError" check karne ke bajaye err instanceof ValidationError kyun better hai?
    Hint: instanceof inheritance chain ko respect karta hai — subclasses (jaise PropertyRequiredError) bhi automatically match karengi; string comparison brittle hai aur naming typo se silently fail ho sakta hai.
  • Wrapping exceptions pattern (cause property) kis problem ko solve karta hai?
    Hint: jab ek function multiple low-level error types throw kar sakta hai, caller ko har type individually handle karne ke bajaye sirf ek high-level wrapper error check karni padti hai, original error cause mein preserved rehta hai.
  • Babel/ES5-target transpiled environments mein extends Error historically kyun break hota tha?
    Hint: native built-ins ka [[Construct]] internal behavior transpiled prototype-chain simulation se properly replicate nahi hota tha — instanceof aur constructor ke baad set kiye properties lost ho sakti thin; fix hai target ES2015+ rakhna ya Object.setPrototypeOf manually call karna.
