Testing — Jest, React Native Testing Library & Maestro E2E

Testing ek aisi cheez hai jo zyaadatar RN developers "baad mein karenge" bolke skip kar dete hain — aur phir production mein ek silent regression aata hai jo QA bhi miss kar jaata hai. Is chapter mein hum dekhenge ki RN apps ke liye testing pyramid kaisi dikhni chahiye, Jest se leke unit tests kaise likhte hain, native modules ko kaise mock karte hain, React Native Testing Library se components ko "user ki tarah" kaise test karte hain, hooks aur async logic kaise test karte hain, aur Maestro se full end-to-end flows kaise automate karte hain — plus CI mein sab kuch wire karna.

1. Testing Pyramid for React Native

Testing pyramid ek mental model hai jo batata hai ki tumhare test suite mein kaunse type ke tests kitni matra mein hone chahiye. RN apps ke liye ye especially important hai kyunki har layer ki cost (speed, flakiness, setup complexity) bahut alag hai — web ke comparison mein bhi zyada extreme, kyunki native build involve hoti hai.

LayerToolKya test karta haiSpeedConfidence
UnitJestPure functions, utility logic, reducers — isolated, koi rendering nahiBahut fast (ms)Low-medium
Integration/ComponentJest + RNTLComponent ka behavior user perspective se — render, interact, assertFast (sec)Medium-high
E2EMaestroPoora app, real device/simulator pe, full user flow (login → home)Slow (minutes)Highest

Classic pyramid shape ka matlab hai: bahut saare unit tests (foundation, fast feedback), kaafi integration/component tests (middle layer), aur bahut kam E2E tests (sirf critical user journeys — login, checkout, onboarding). Jitna upar jaoge pyramid mein, utna zyada confidence milta hai ki app actually kaam kar rahi hai, lekin utna hi zyada cost bhi lagta hai.

🧠 Senior Dev Note — RN mein E2E-only strategy kyun fail hoti hai

Web apps ke liye E2E-heavy strategy (Cypress/Playwright sab jagah) chal jaati hai kyunki browser instantly reload hota hai. RN mein ye assumption tootti hai — E2E tests ko ek real native build chahiye (simulator/emulator/device pe install hone wali actual app), aur native build times 2-10 minutes tak le sakte hain (especially iOS pe, ya jab native dependencies change hui hon). Agar tumhara pura test suite E2E-based hai, toh har chhota logic change bhi ek 5+ minute build-then-test cycle trigger karega — CI minutes explode ho jaate hain, aur developers locally test hi nahi karenge kyunki wait bahut lamba hai. Isse zyada bada issue: E2E tests flaky hote hain — animation timing, network latency, simulator slowness — sab combine hoke false failures dete hain, aur team dheere-dheere "red build ignore karo, phir se run karo" ki habit develop kar leti hai, jo poore CI pipeline ka trust hi khatam kar deti hai. Isliye rule of thumb: business logic aur component behavior ko Jest/RNTL se cover karo (fast, no native build needed, run har save pe), aur Maestro sirf un 5-10 "must never break" user journeys ke liye reserve karo.

💡 Quick Tip

Ek practical heuristic: agar tumhara test expo-secure-store, camera, ya kisi aur native module ko chhoo raha hai bina mock ke, ya agar test ka goal "poora flow end-to-end kaam karta hai ya nahi" hai — wo E2E candidate hai. Agar test ka goal "ye function sahi output deta hai" ya "ye component sahi render hota hai given props" — wo unit/integration candidate hai.

2. Jest Setup and Unit Testing

Expo projects ke liye Jest setup ka starting point jest-expo preset hai — ye Babel transforms, module resolution, aur Expo/RN-specific mocks (jaise expo-asset, expo-font) ko pehle se configure kar deta hai, taaki tumhe khud se Metro-jaisa transform pipeline set up na karna pade.

Install
npx expo install jest-expo jest @testing-library/react-native @testing-library/jest-native --dev

# jest: actual test runner

  },

    ],

  }

Sabse pehla aur sabse asaan test kya likhna chahiye? Pure functions — jo koi rendering involve nahi karte, sirf input leke output dete hain. Ye tests sabse fast likhne mein aate hain, sabse kam flaky hote hain, aur "TDD-friendly" hote hain. Neeche ek formatCurrency() utility ka example hai jo poori tarah se comment kiya hua hai.

utils/formatCurrency.ts
// Ek pure function — sirf number leke formatted string deta hai, koi side effect nahi
export function formatCurrency(amount: number, currency: string = "INR"): string {
  if (Number.isNaN(amount)) { // agar amount NaN hai (invalid input) toh
    throw new Error("Invalid amount"); // explicit error throw karo, silently galat output mat do
  }
  const formatter = new Intl.NumberFormat("en-IN", { // Indian numbering system (lakh/crore commas) use karo
    style: "currency", // currency style — symbol ke saath format karega
    currency, // dynamic currency code, default INR
  }); // formatter object ban gaya
  return formatter.format(amount); // number ko formatted currency string mein convert karke return karo
} // function close
utils/formatCurrency.test.ts
import { formatCurrency } from "./formatCurrency"; // jis function ko test karna hai use import kiya

describe("formatCurrency", () => { // related tests ko ek group mein daala, "describe" block
  it("formats a positive INR amount correctly", () => { // ek specific test case, "it" naam se readable sentence banta hai
    const result = formatCurrency(1000); // function ko 1000 ke saath call kiya, default currency INR
    expect(result).toBe("₹1,000.00"); // assert kar rahe hain ki output exactly ye string ho
  }); // test case close

  it("formats large amounts with Indian comma grouping", () => { // Indian numbering system (lakh grouping) test karne ke liye
    const result = formatCurrency(1000000); // 10 lakh pass kiya
    expect(result).toBe("₹10,00,000.00"); // Indian grouping "10,00,000" honi chahiye, na ki "1,000,000"
  }); // test case close

  it("supports a different currency code", () => { // currency param override test karne ke liye
    const result = formatCurrency(50, "USD"); // USD currency explicitly pass kiya
    expect(result).toBe("$50.00"); // USD symbol expect kar rahe hain
  }); // test case close

  it("throws on NaN input", () => { // edge case — invalid input pe error throw hona chahiye
    expect(() => formatCurrency(Number("abc"))).toThrow("Invalid amount"); // function ko wrap karke throw check karte hain, direct call nahi
  }); // test case close
}); // describe block close
🧠 Senior Dev Note

expect(() => fn()).toThrow() pattern zaroori hai — agar tum direct expect(fn()).toThrow() likhoge, function turant call ho jaayega aur error test framework ke andar catch hone se pehle hi throw ho jaayegi (test crash karega, "throw hua" assert nahi hoga). Function ko ek arrow function ke andar wrap karna Jest ko control deta hai ki wo kab call kare aur exception ko safely catch kare.

3. Mocking Native Modules

Jest tests Node.js environment mein chalte hain, na ki actual iOS/Android device pe. Iska matlab: koi bhi module jo native bridge/JSI ke through real platform APIs ko call karta hai — AsyncStorage, expo-secure-store, expo-camera, push notifications, haptics, sab kuch — Node mein exist hi nahi karte. Jab tum in modules ko import karogi Jest ke andar, ya toh import silently fail hoga, ya method call pe crash aayega ("native module not found" jaisa error), kyunki underlying native binding wahan hai hi nahi.

Solution: mocking — hum in modules ko ek fake JS implementation se replace kar dete hain jo sirf test ke liye kaafi hai (jaise ek in-memory object jo get/set simulate kare), taaki jo code in modules ko use karta hai wo bina crash hue test ho sake.

jest.mock() — inline mock example
jest.mock("expo-secure-store", () => ({ // "expo-secure-store" module ko poora replace kar rahe hain
  getItemAsync: jest.fn(() => Promise.resolve(null)), // fake getItemAsync — default null return karega jab tak override na ho
  setItemAsync: jest.fn(() => Promise.resolve()), // fake setItemAsync — kuch bhi store nahi karega, bas resolve hoga
  deleteItemAsync: jest.fn(() => Promise.resolve()), // fake deleteItemAsync — same tarah resolve
})); // mock factory function close

Ye pattern kaam karta hai lekin har test file mein repeat karna padega. Better approach: ek dedicated __mocks__ folder banao jisse Jest automatically pick kare jab bhi wo module import ho.

__mocks__/expo-secure-store.js
// Jest convention: agar root ya module-adjacent __mocks__ folder mein isi naam ki file ho,
// aur jest.mock("expo-secure-store") call ho (ya automock on ho), ye file automatically use hogi

const store = new Map(); // ek in-memory Map jo real SecureStore ki jagah data hold karega test ke duration

export const getItemAsync = jest.fn((key) => // fake getItemAsync jo actually kuch state maintain karta hai
  Promise.resolve(store.get(key) ?? null) // Map se value nikaalo, na mile toh null resolve karo (real API jaisa behavior)
); // getItemAsync definition close

export const setItemAsync = jest.fn((key, value) => { // fake setItemAsync
  store.set(key, value); // Map mein value store karo, taaki baad mein getItemAsync se milе
  return Promise.resolve(); // void promise resolve karo, real API jaisa
}); // setItemAsync definition close

export const deleteItemAsync = jest.fn((key) => { // fake deleteItemAsync
  store.delete(key); // Map se key hata do
  return Promise.resolve(); // void promise resolve
}); // deleteItemAsync definition close
AuthContext.test.tsx (using the mock)
jest.mock("expo-secure-store"); // bina factory ke call kiya — Jest automatically __mocks__/expo-secure-store.js pick karega

import * as SecureStore from "expo-secure-store"; // ye ab mocked version import karega, real nahi

it("stores the token after sign in", async () => { // async test kyunki signIn promise-based hai
  await SecureStore.setItemAsync("session_token", "abc123"); // mock function ko call kiya jaise real code karega
  expect(SecureStore.setItemAsync).toHaveBeenCalledWith("session_token", "abc123"); // assert — sahi arguments ke saath call hua
}); // test close
⚠️ Gotcha

jest-expo preset khud kai common Expo native modules (jaise expo-font, expo-asset) ko already mock kar deta hai — lekin sab modules nahi. Har naye native module (third-party ya Expo ka) ko add karne ke baad ek baar check kar lo ki uska test-environment behavior predictable hai ya nahi — agar test crash ho raha hai "native module cannot be null" jaisi error ke saath, 99% chances hain wo module ko manually mock karna padega.

4. React Native Testing Library (RNTL)

RNTL ki core philosophy ek line mein: "test like a user, not implementation details." Matlab tumhare tests ko component ke internal state, props, ya class names ko directly access nahi karna chahiye — balki wahi cheez query karni chahiye jo ek real user screen pe dekh sakta hai ya interact kar sakta hai: visible text, accessibility role, ya ek explicit testID.

Isse fayda kya hota hai? Agar tum component ka internal implementation refactor karte ho (jaise useState se useReducer mein switch karna) bina user-facing behavior change kiye, tumhare tests pass hote rehte hain — kyunki wo implementation detail ko jaante hi nahi the. Ye tests ko refactor-resistant banata hai, jo long-term maintenance ke liye bahut valuable hai.

APIKaam
render()Component ko virtual RN tree mein render karta hai, testing environment mein
screenGlobal query object — render ke baad screen pe jo bhi hai use query karne ke liye
fireEventLow-level event simulation — press, changeText, scroll
userEventHigher-level, real user interaction ke zyada kareeb (async, sequential steps)
waitForAsync UI update ka wait karta hai — jab state update ke baad DOM/tree change ho

Ab ek full example — ek LoginForm component aur uska test, dono line-by-line commented.

components/LoginForm.tsx
import { useState } from "react"; // local form state ke liye useState chahiye
import { View, TextInput, Text, Pressable } from "react-native"; // core RN components

type Props = { // component ke props ka type
  onSubmit: (email: string, password: string) => Promise<void>; // parent se aane wala async submit handler
}; // Props type close

export function LoginForm({ onSubmit }: Props) { // LoginForm component, onSubmit prop destructure kiya
  const [email, setEmail] = useState(""); // email input ka state
  const [password, setPassword] = useState(""); // password input ka state
  const [error, setError] = useState(""); // validation/submit error message ka state

  const handleSubmit = async () => { // submit button dabane pe chalne wala async handler
    if (!email) { // agar email khaali hai
      setError("Email required"); // error message set karo
      return; // aage mat badho, API call mat karo
    } // if block close
    try { // error handling ke liye try block
      await onSubmit(email, password); // parent ka submit handler call karo, await karo kyunki async hai
      setError(""); // success pe purana error clear kar do
    } catch { // agar onSubmit reject ho (jaise galat password)
      setError("Invalid credentials"); // user ko readable error dikhao
    } // try/catch close
  }; // handleSubmit close

  return ( // JSX return
    <View> // wrapper container
      <TextInput // email input field
        testID="email-input" // stable identifier tests ke liye (implementation-independent)
        placeholder="Email" // placeholder text
        value={email} // controlled input — value state se bound
        onChangeText={setEmail} // har keystroke pe state update
      />
      <TextInput // password input field
        testID="password-input" // password field ka stable id
        placeholder="Password" // placeholder
        secureTextEntry // characters ko mask karega (dots dikhega)
        value={password} // controlled value
        onChangeText={setPassword} // keystroke pe update
      />
      <Pressable onPress={handleSubmit}> // submit button, press pe handleSubmit call
        <Text>Submit</Text> // button ka visible text — user isse hi dhoondega
      </Pressable>
      {error ? <Text>{error}</Text> : null} // error hone pe hi error text render karo
    </View>
  ); // return close
} // component function close
components/LoginForm.test.tsx
import { render, screen, fireEvent, waitFor } from "@testing-library/react-native"; // RNTL ke core utilities import kiye
import { LoginForm } from "./LoginForm"; // jis component ko test karna hai

describe("LoginForm", () => { // sab LoginForm tests ko group kiya
  it("shows error when email is empty", async () => { // validation test case
    const onSubmit = jest.fn(); // fake onSubmit prop, taaki actual API call na ho
    render(<LoginForm onSubmit={onSubmit} />); // component ko virtual tree mein render kiya

    const button = screen.getByText("Submit"); // Submit button ko uske visible text se dhoondha, jaise user dhoondta
    fireEvent.press(button); // button pe press event simulate kiya (email khaali hai)

    const errorText = await screen.findByText("Email required"); // findByText async hai, state update ka wait khud karta hai
    expect(errorText).toBeTruthy(); // assert — error message screen pe mil gaya
    expect(onSubmit).not.toHaveBeenCalled(); // assert — validation fail hone pe API call bilkul nahi hui
  }); // test case close

  it("submits with entered credentials", async () => { // happy-path test case
    const onSubmit = jest.fn().mockResolvedValue(undefined); // onSubmit ko resolve karne wala mock banaya (success simulate)
    render(<LoginForm onSubmit={onSubmit} />); // render karo

    fireEvent.changeText(screen.getByTestId("email-input"), "sharad@clear.in"); // email input mein text simulate karke type kiya
    fireEvent.changeText(screen.getByTestId("password-input"), "secret123"); // password input mein text daala
    fireEvent.press(screen.getByText("Submit")); // submit button press kiya

    await waitFor(() => { // waitFor — async state update poora hone tak retry karta rehta hai
      expect(onSubmit).toHaveBeenCalledWith("sharad@clear.in", "secret123"); // assert — sahi values ke saath call hua
    }); // waitFor close
  }); // test case close

  it("shows error when onSubmit rejects", async () => { // failure-path test case
    const onSubmit = jest.fn().mockRejectedValue(new Error("401")); // onSubmit ko reject karne wala mock (galat credentials simulate)
    render(<LoginForm onSubmit={onSubmit} />); // render karo

    fireEvent.changeText(screen.getByTestId("email-input"), "sharad@clear.in"); // email bhara
    fireEvent.press(screen.getByText("Submit")); // submit dabaya

    expect(await screen.findByText("Invalid credentials")).toBeTruthy(); // assert — catch block wala error message dikha
  }); // test case close
}); // describe block close
⚠️ Gotcha — getBy vs findBy vs queryBy

getByX turant throw karega agar element nahi mila (sync). findByX async hai — andar hi andar waitFor use karta hai, isliye state update ke baad aane wale elements ke liye ye sahi choice hai. queryByX throw nahi karta, null return karta hai — isko use karo jab tum assert kar rahe ho ki koi element absent hai (expect(screen.queryByText("Error")).toBeNull()).

5. Testing Hooks and Async Logic

Custom hooks ko test karna thoda tricky hota hai kyunki hooks sirf component ke andar hi call ho sakte hain (React ke "rules of hooks" ke wajah se). RNTL ka renderHook ek minimal, invisible wrapper component banata hai jisme hook ko mount karta hai, taaki tum hook ke return value aur uske state changes ko directly test kar sako — bina koi UI likhe.

hooks/useFetchUser.ts
import { useEffect, useState } from "react"; // state aur lifecycle ke liye

type User = { id: string; name: string }; // user shape ka type

export function useFetchUser(userId: string) { // custom hook, userId leta hai
  const [user, setUser] = useState<User | null>(null); // fetched user data
  const [isLoading, setIsLoading] = useState(true); // loading flag, initially true
  const [error, setError] = useState<string | null>(null); // error message, null jab tak error na ho

  useEffect(() => { // side effect — userId change hone pe fetch trigger karega
    let cancelled = false; // stale response ignore karne ke liye flag (component unmount/id-change race)
    setIsLoading(true); // naye fetch ke shuru mein loading true karo

    fetch(`https://api.myapp.com/users/${userId}`) // actual network call (test mein mock hoga)
      .then((res) => res.json()) // response ko JSON mein parse karo
      .then((data) => { // success callback
        if (!cancelled) setUser(data); // sirf tab set karo jab request cancel nahi hui
      })
      .catch((err) => { // failure callback
        if (!cancelled) setError(err.message); // error message state mein daalo
      })
      .finally(() => { // dono cases mein chalega
        if (!cancelled) setIsLoading(false); // loading khatam
      }); // promise chain close

    return () => { // cleanup function
      cancelled = true; // agar userId change ho ya unmount ho jaaye, purani response ignore karo
    }; // cleanup close
  }, [userId]); // dependency — userId badalne pe re-run

  return { user, isLoading, error }; // hook ka public return value
} // hook close
hooks/useFetchUser.test.ts
import { renderHook, waitFor } from "@testing-library/react-native"; // renderHook hooks ko isolation mein test karne deta hai
import { useFetchUser } from "./useFetchUser"; // jis hook ko test karna hai

beforeEach(() => { // har test se pehle chalega
  global.fetch = jest.fn(); // global fetch ko ek fresh jest mock function se replace kiya
}); // beforeEach close

it("returns user data after successful fetch", async () => { // happy path test
  (global.fetch as jest.Mock).mockResolvedValue({ // fetch ka resolved value define kiya
    json: () => Promise.resolve({ id: "1", name: "Sharad" }), // .json() bhi ek promise return kare, real Response jaisa
  }); // mockResolvedValue close

  const { result } = renderHook(() => useFetchUser("1")); // hook ko invisible wrapper component mein mount kiya

  expect(result.current.isLoading).toBe(true); // turant ke baad loading true hona chahiye (fetch abhi resolve nahi hua)

  await waitFor(() => expect(result.current.isLoading).toBe(false)); // jab tak loading false na ho jaaye, poll karte raho

  expect(result.current.user).toEqual({ id: "1", name: "Sharad" }); // assert — final user state sahi hai
  expect(result.current.error).toBeNull(); // assert — koi error nahi hui
}); // test close

it("sets error state when fetch fails", async () => { // failure path test
  (global.fetch as jest.Mock).mockRejectedValue(new Error("Network down")); // fetch ko reject karne ke liye configure kiya

  const { result } = renderHook(() => useFetchUser("2")); // hook mount kiya different userId ke saath

  await waitFor(() => expect(result.current.error).toBe("Network down")); // error set hone ka wait karo
  expect(result.current.user).toBeNull(); // assert — user null hi raha, fetch fail hua tha
}); // test close
🧠 Senior Dev Note — act() warnings

Agar tumhe console mein "An update to X inside a test was not wrapped in act(...)" jaisi warning dikhe, iska matlab hai component/hook ka state update test assertion ke baad, bina waitFor/act ke wrap kiye, ho raha hai. RNTL ke waitFor, findBy*, aur renderHook ke result updates already internally act() use karte hain — isliye zyada tar cases mein manually act() likhne ki zaroorat nahi padti, bas async assertions ko sahi API (waitFor/findBy) se wrap karo.

6. Maestro E2E Testing

Maestro ek open-source E2E testing framework hai jo specifically mobile apps (iOS + Android, React Native ya native dono) ke liye bana hai. Sabse bada differentiator: tests plain YAML mein likhe jaate hain — koi native test code (Espresso/XCUITest) likhne ki zaroorat nahi. Maestro internally accessibility tree read karta hai (jaisa RNTL karta hai component tree ke liye, lekin ye poori running app pe, real gestures ke through), aur automatically retries/waits karta hai jab tak element screen pe render nahi ho jaata — isse animation-timing-based flakiness kaafi kam ho jaati hai compared to raw Appium/Detox scripts.

Install Maestro
curl -Ls "https://get.maestro.mobile.dev" | bash # official install script, Maestro CLI ko system pe install karta hai
maestro --version # verify karo installation successful hui ya nahi
.maestro/login-to-home.yaml
# appId — kaunsi app pe ye flow chalega, bundle identifier/package name se match hona chahiye
appId: com.mycompany.myapp
---
# --- launchApp: app ko fresh state mein launch karta hai (state clear karke) ---

    clearState: true # purana app data clear karo, taaki test hamesha "logged out" state se shuru ho

# --- assertVisible: check karta hai ki given text/element screen pe dikh raha hai ---
- assertVisible: "Login" # confirm karo ki hum login screen pe hi hain

# --- tapOn: given text/testID wale element pe tap simulate karta hai ---
- tapOn:
    id: "email-input" # RNTL wale testID se match hota hai (accessibilityLabel/testID ke through)

# --- inputText: currently focused field mein text type karta hai ---
- inputText: "sharad@clear.in" # email field mein credentials type karo

- tapOn:
    id: "password-input" # password field pe tap karo focus shift karne ke liye

- inputText: "secret123" # password type karo

- tapOn: "Submit" # Submit button ko uske visible text se tap karo

# --- extendedWaitUntil: fixed sleep() ki jagah condition-based wait karta hai ---
- extendedWaitUntil:
    visible: "Home" # jab tak "Home" text screen pe na aaye (login network call complete hone tak)
    timeout: 10000 # max 10 seconds tak wait karega, phir fail mark karega

# --- assertVisible: final assertion — humein home screen pe pahuncha ya nahi ---
- assertVisible: "Welcome back" # home screen ka koi unique greeting text confirm karo

maestro studio command ek local UI kholta hai jahan tum running app ke accessibility tree ko live inspect kar sakte ho aur interactively element pe click karke uska sahi selector (id/text) copy kar sakte ho — isse YAML likhna kaafi fast ho jaata hai, especially jab pata nahi ki kisi element ka accessible identifier kya hai.

7. CI Integration

Tests likhna tab hi valuable hai jab wo automatically, har PR pe run hon — koi manually yaad rakh ke "test chalao" nahi bhoolega. Jest tests har GitHub Actions run pe seconds mein chal jaate hain (no native build needed), jabki Maestro tests ko ek actual build artifact chahiye hota hai, isliye unhe typically EAS Build ke baad ek separate step/job mein chalate hain.

.github/workflows/test.yml
# workflow ka naam, GitHub Actions UI mein dikhega
name: Test
# kab trigger ho — har pull_request pe (main branch ke against)
on:
  pull_request:
    branches: [main] # sirf main ke against banne wale PRs pe chalega

jobs:
  unit-tests: # pehla job — Jest unit + component tests
    runs-on: ubuntu-latest # Linux runner kaafi hai, Jest ko native build nahi chahiye
    steps:
      - uses: actions/checkout@v4 # repo code ko runner mein checkout karo
      - uses: actions/setup-node@v4 # Node.js environment setup karo
        with:
          node-version: 20 # Node version pin kiya, consistency ke liye
      - run: npm ci # exact lockfile versions install karo, "npm install" se zyada deterministic
      - run: npm test -- --ci --coverage # Jest ko CI mode mein chalao, coverage report bhi generate karo

  e2e-tests: # dusra job — Maestro E2E, build artifact pe depend karta hai
    needs: unit-tests # pehle unit tests pass hone chahiye, tabhi ye job chalega (fast-fail)
    runs-on: macos-latest # iOS simulator chahiye toh macOS runner mandatory hai
    steps:
      - uses: actions/checkout@v4 # repo checkout
      - name: Install Maestro # Maestro CLI ko runner pe install karne ka step
        run: curl -Ls "https://get.maestro.mobile.dev" | bash # same install script jo local pe use kiya tha
      - name: Download EAS build artifact # pehle se bana hua build download karna
        run: eas build:download --platform ios --latest # latest iOS simulator build download karo EAS se
      - name: Run Maestro flows # actual E2E tests chalane ka step
        run: maestro test .maestro/ # saare flows sequentially run karo
🧠 Senior Dev Note

Notice karo needs: unit-tests — ye ek deliberate ordering hai. Unit/component tests seconds mein fail ho jaate hain agar kuch basic tut gaya, jabki E2E job ko ek naya build banwa ke download karne mein hi minutes lag sakte hain. Fast, cheap checks pehle chalao taaki obvious breakage jaldi pakda jaaye — is pattern ko "fail fast" bolte hain, aur ye expensive CI minutes (macOS runners especially costly hote hain) bachane ka sabse simple tarika hai.

8. Real-World Gotchas

⚠️ Stale snapshot tests — blindly update karna anti-pattern hai

Jest ke snapshot tests (expect(tree).toMatchSnapshot()) tempting lagte hain kyunki likhna easy hai — bas render karo aur snapshot le lo. Lekin practically, jab bhi koi chhota unrelated style change hota hai, snapshot test fail ho jaata hai, aur developers habit bana lete hain jest --updateSnapshot blindly chala dene ki, bina diff dekhe ki kya actually change hua. Isse snapshot tests apni poori value kho dete hain — wo sirf "kuch change hua" batate hain, "sahi change hua ya nahi" nahi. Snapshot tests ko sirf tab use karo jab tumhe exactly output ka structure freeze karna ho (jaise ek design-system component library), aur har snapshot update pe diff carefully review karo — kabhi bhi CI mein "update aur commit" ko automate mat karo.

⚠️ Flaky E2E tests — sleep() ki jagah waitFor use karo

Animation transitions, network latency, aur splash screen delays — ye sab E2E tests ko unpredictable bana dete hain agar tumne fixed sleep(2000) jaisi wait daali hai. Slow CI runner pe 2 second kaafi nahi honge, aur fast local machine pe wo wasted time hai. Hamesha condition-based wait use karo — Maestro mein extendedWaitUntil, RNTL mein waitFor/findBy* — jo element/condition ke actual hone tak poll karte hain, na ki ek arbitrary fixed duration tak block karte hain.

⚠️ Navigation/Theme providers wrap na karna — crash ya galat render

Agar tumhara component useNavigation(), theme context, ya safe-area context use karta hai, toh use directly render(<MyComponent />) karne se crash aayega ("no navigation context found" jaisa error) — kyunki test environment mein wo providers exist hi nahi karte by default. Solution: ek custom render wrapper utility banao jo har test ke liye zaroori providers automatically wrap kar de.

test-utils/render.tsx
import { render as rtlRender, RenderOptions } from "@testing-library/react-native"; // RNTL ka original render, alag naam se import kiya taaki clash na ho
import { NavigationContainer } from "@react-navigation/native"; // navigation context provider
import { ThemeProvider } from "../context/ThemeContext"; // app ka apna theme provider

function AllProviders({ children }: { children: React.ReactNode }) { // wrapper component jo saare providers combine karta hai
  return ( // JSX return
    <ThemeProvider> // theme context provide karo
      <NavigationContainer>{children}</NavigationContainer> // navigation context provide karo, andar actual component render hoga
    </ThemeProvider>
  ); // return close
} // wrapper close

function customRender(ui: React.ReactElement, options?: RenderOptions) { // custom render function jo default export banega
  return rtlRender(ui, { wrapper: AllProviders, ...options }); // RNTL render ko AllProviders wrapper ke saath call karo
} // customRender close

export * from "@testing-library/react-native"; // screen, fireEvent, waitFor sab re-export kiye taaki ek hi jagah se import ho sake
export { customRender as render }; // customRender ko "render" naam se export kiya, tests mein normal render jaisa hi dikhega

Ab tests mein import { render, screen } from "../test-utils/render" karke normal render(<MyComponent />) likh sakte ho, aur providers automatically wrap ho jaayenge — bina har test file mein manually boilerplate repeat kiye.

🧠 Senior Dev Note — har prop combination test mat karo

Diminishing returns ek real cheez hai testing mein. Agar ek component ke 5 boolean props hain, unke 32 possible combinations banate hain — lekin usse pura test karna time-waste hai aur maintenance burden badhata hai. Instead, focus karo critical user flows pe: login/signup, checkout, data submission jahan bug directly revenue ya trust ko hit karta hai. Kam-important edge cases (jaise ek rarely-used prop combination) ko manual QA ya exploratory testing pe chhod do. Senior dev ka signal yahi hai — pura coverage chase nahi karna, balki right coverage chase karna, jahan failure ka business impact sabse zyada hai.

9. Advanced Deep-Dive — Beyond the Basics

Section 8 mein humne dekha ki providers wrap na karne se crash aata hai, aur ek basic test-utils/render.tsx banaya jo Theme + Navigation wrap karta hai. Ek senior-level app mein usually isse zyada providers hote hain — Redux/Zustand store, gesture-handler root view, safe-area context, query client (React Query) — aur har test ko har provider ka apna alag setup nahi likhna chahiye. Yahan hum us pattern ko production-grade banayenge, phir Reanimated/gesture testing, visual regression, aur CI mein performance profiling — ye 4 topics cover karenge jo ek senior RN interview mein testing depth judge karne ke liye common hain.

9.1 Custom Render Utility — Full Provider Stack + Preloaded State

Section 8 ka customRender sirf static providers wrap karta tha (koi per-test configuration nahi thi). Ek real app mein Redux store aur React Query client ko har test ke liye alag state ke saath inject karna padta hai (jaise "user already logged in" wala test vs "user logged out" wala test). Neeche wo full, production-style version hai jo ek options object accept karta hai taaki har test apna preloaded state pass kar sake, bina naya wrapper likhe.

test-utils/render.tsx (advanced — full provider stack)
import type { ReactElement, ReactNode } from "react"; // type-only imports, JSX ke liye React ki type info chahiye
import { render as rtlRender, type RenderOptions } from "@testing-library/react-native"; // RNTL ka original render, renamed taaki naam clash na ho
import { NavigationContainer } from "@react-navigation/native"; // navigation context provider, app-wide zaroori hai
import { GestureHandlerRootView } from "react-native-gesture-handler"; // gesture-handler ko bhi root view chahiye, warna gestures silently fail hote hain
import { SafeAreaProvider } from "react-native-safe-area-context"; // safe-area insets use karne wale components ke liye zaroori
import { Provider as ReduxProvider } from "react-redux"; // Redux store ko component tree mein inject karne wala provider
import { configureStore } from "@reduxjs/toolkit"; // har test ke liye ek fresh, isolated store banane ke liye
import { rootReducer, type RootState } from "../store/rootReducer"; // app ka actual reducer tree — real reducers use karo, mock nahi (integration-level confidence ke liye)
import { ThemeProvider } from "../context/ThemeContext"; // app ka apna custom theme context

type ExtendedRenderOptions = Omit<RenderOptions, "wrapper"> & { // RenderOptions extend kiya, "wrapper" ko exclude kiya kyunki wo hum khud provide karenge
  preloadedState?: Partial<RootState>; // optional — test apna khud ka initial Redux state de sakta hai
  store?: ReturnType<typeof configureStore>; // optional — agar test ko poora custom store chahiye (rare case)
}; // ExtendedRenderOptions type close

function customRender( // naya customRender jo options accept karta hai
  ui: ReactElement, // jo component render karna hai
  {
    preloadedState = {}, // default — koi preloaded state nahi, store apni default initial state se shuru hoga
    store = configureStore({ reducer: rootReducer, preloadedState }), // har render call pe ek fresh store banao — tests ek dusre ka state share NAHI karne chahiye
    ...renderOptions // baaki saare RNTL options (jaise "wrapper" ke alawa sab) as-is pass kar do
  }: ExtendedRenderOptions = {} // pura options object hi optional hai, default empty object
) {
  function Wrapper({ children }: { children: ReactNode }) { // inline wrapper component jo saare providers ek saath nest karta hai
    return ( // JSX return
      <GestureHandlerRootView style={{ flex: 1 }}> // gesture-handler root — outermost, flex:1 taaki poora screen area cover ho
        <SafeAreaProvider> // safe-area insets context
          <ReduxProvider store={store}> // is test ke liye banaya gaya isolated Redux store inject karo
            <ThemeProvider> // app ka custom theme context
              <NavigationContainer>{children}</NavigationContainer> // navigation context — sabse andar, actual component yahin render hoga
            </ThemeProvider>
          </ReduxProvider>
        </SafeAreaProvider>
      </GestureHandlerRootView>
    ); // return close
  } // Wrapper close

  return { // return object — RNTL ka normal result + store reference bhi expose kar rahe hain
    store, // test ko store expose kiya — kabhi kabhi test ko `store.getState()` se assert karna padta hai
    ...rtlRender(ui, { wrapper: Wrapper, ...renderOptions }), // asli RNTL render call, humara Wrapper pass kar diya
  }; // return close
} // customRender close

export * from "@testing-library/react-native"; // screen, fireEvent, waitFor sab re-export — ek hi import path se sab milega
export { customRender as render }; // "render" naam se export — test files mein normal render jaisa hi use hoga
ProfileScreen.test.tsx (using preloadedState)
import { render, screen } from "../test-utils/render"; // custom render import kiya, RNTL se directly nahi
import { ProfileScreen } from "./ProfileScreen"; // jo component test karna hai, wo useSelector se logged-in user padhta hai

it("shows the logged-in user's name", () => { // test case — logged-in state ke saath render karna hai
  render(<ProfileScreen />, { // component render kiya options ke saath
    preloadedState: { auth: { user: { name: "Sharad" } } }, // is test ke liye Redux store ko already "logged in" state se seed kiya
  }); // render call close — koi manual dispatch/login flow simulate nahi karna pada

  expect(screen.getByText("Sharad")).toBeTruthy(); // assert — user ka naam screen pe dikh raha hai
}); // test close
🧠 Senior Dev Note — ye pattern kyun matter karta hai

Bina is pattern ke, har test file mein tumhe manually <Provider>, <NavigationContainer>, aur baaki wrappers repeat karne padenge — jo na sirf boilerplate hai, balki agar kabhi ek naya app-wide provider add hota hai (jaise React Query), tumhe har existing test file mein jaake update karna padega. Ek centralized render utility ka matlab hai ye change ek jagah hoti hai, aur saare tests automatically naye provider ke saath render hone lagte hain. Ye exactly wahi principle hai jo humne DRY components ke liye use kiya tha (ch.2) — bas ab test infrastructure pe apply ho raha hai. Bade codebases mein ye file usually jest.config.js ke setupFilesAfterEach ya ek shared test-utils package ke through poore monorepo mein reuse hoti hai.

9.2 Testing Reanimated aur Gesture-Driven Code

Reanimated ka poora fayda hi ye hai ki uske worklets UI thread pe, JSI ke through, native C++ runtime mein directly chalte hain (ch.5 mein detail mein dekha tha). Jest tests Node.js environment mein chalte hain — wahan koi UI thread nahi hai, koi native Reanimated runtime nahi hai. Iska matlab worklets Jest ke andar bilkul differently execute hote hain (JS thread pe hi, synchronously ya mocked timers ke through), jo real device behavior se kaafi door hai.

⚠️ Gotcha — Reanimated bina mock ke crash karega

Agar tum Reanimated use karne wale component ko bina setup ke test karogi, error milega jaisa "Native module 'ReanimatedModule' not found" — kyunki underlying native binding Node mein exist nahi karti. Solution: Reanimated khud ek official Jest mock deta hai jo isse handle karta hai.

jest.config.js — Reanimated ka official mock wire karna
module.exports = { // Jest config ka export
  preset: "jest-expo", // existing Expo preset (jaisa section 2 mein setup kiya tha)
  setupFilesAfterEach: [ // har test file ke run hone ke baad automatically load hone wali setup files
    "@testing-library/jest-native/extend-expect", // pehle se add kiya hua matcher setup
    "react-native-reanimated/jestSetup", // Reanimated ka official mock — worklets ko Jest-safe fake implementation se replace karta hai
  ], // setup array close
}; // module.exports close

Ye official mock useSharedValue, withTiming, withSpring jaisi cheezon ko "fake" versions se replace kar deta hai jo turant (synchronously, bina actual animation timing ke) apni final value pe pahunch jaate hain — taaki test crash na ho. Lekin isse ek important limitation aati hai: tum animated visual values (jaise beech ka interpolated opacity 0.5 pe hai ya nahi) reliably assert nahi kar sakte, kyunki mock animation ki real timing/easing curve simulate nahi karta.

🧠 Senior Dev Note — animation values test mat karo, LOGIC test karo

Ek senior engineer ka pragmatic approach: animated visual values ko assert karne ki koshish chhod do (wo brittle aur mock-dependent hote hain), aur uske bajaye us business logic pe focus karo jo animation ke through trigger hoti hai. Swipe-to-delete component (ch.5 mein banaya tha) ka example lo — real question ye nahi hai "kya opacity 0 tak animate hui", balki "kya swipe threshold cross karne ke baad delete callback call hua ya nahi". Neeche wahi approach code mein:

SwipeToDelete.test.tsx (testing the callback, not the animation)
import { render, screen, fireEvent } from "../test-utils/render"; // section 9.1 wala custom render — gesture-handler root chahiye hoga
import { SwipeToDelete } from "./SwipeToDelete"; // ch.5 wala component jo pan gesture pe delete trigger karta hai

it("calls onDelete when the delete button is pressed", () => { // gesture ki jagah, exposed testID button ko test kar rahe hain
  const onDelete = jest.fn(); // fake callback, assert karne ke liye ki wo call hua ya nahi
  render(<SwipeToDelete onDelete={onDelete}>Item 1</SwipeToDelete>); // render kiya, item text bhi pass kiya

  // NOTE: Pan gesture ko RNTL mein reliably simulate karna mushkil/flaky hai (native gesture-handler internals),
  // isliye component mein ek "hidden" testID-wala delete trigger expose karna practical hai — jise gesture
  // swipe complete hone pe internally wahi function call karta hai jo ye button bhi call karta hai
  fireEvent.press(screen.getByTestId("delete-trigger")); // wahi internal handler trigger kiya jo swipe-threshold cross hone pe chalta

  expect(onDelete).toHaveBeenCalledTimes(1); // assert — LOGIC (callback fire hua) verify hua, VISUAL animation nahi
}); // test close

Actual pan gesture ke "kitna swipe hua, threshold kaisi feel hoti hai" wala experience — wo Maestro E2E ke through real device/simulator pe (real touch events ke saath) verify karo, kyunki wahan asli gesture recognizer aur asli animation dono chal rahe hote hain. Yahi teen-layer split hai: unit/component test se logic verify karo, E2E se real feel verify karo, aur visual value assertions ko chhod do.

9.3 Visual Regression Testing

Visual regression testing ka concept simple hai: component/screen ka ek rendered image capture karo (baseline/reference screenshot), aur future runs mein naya screenshot le ke pixel-by-pixel (ya perceptual diff algorithm se) baseline ke against compare karo. Agar difference threshold se zyada hai, test fail hota hai aur ek visual diff dikhata hai — ye catch karta hai wo bugs jo functionally sahi hain (koi crash nahi, koi wrong data nahi) lekin visually galat hain — jaise ek padding change se layout shift, ya ek color token galat map ho jaana.

Tool/ApproachKaam karta hai kaise
Chromatic / Percy-style servicesStorybook (ya component previews) ko cloud pe render karke, cross-browser/device baseline snapshots maintain karte hain, PR pe visual diff review UI dete hain
Maestro screenshot testingE2E flow ke beech mein takeScreenshot/assertVisible ke saath real device/simulator pe screenshots leta hai, running app ka actual visual state capture karta hai
jest-image-snapshotJest ke andar hi image-diffing matcher add karta hai, lekin RN mein rendering environment (Node) real UI paint nahi karta, isliye typically ek native/E2E layer ke saath combine hota hai
⚠️ Trade-off — powerful lekin noisy ho sakta hai

Visual regression testing bahut effective hai unintended visual changes catch karne mein, lekin agar carefully maintain na kiya jaaye toh flaky ho jaata hai — different CI runners pe font rendering, anti-aliasing, ya even OS-level date/time widgets thoda different pixels render kar sakte hain, jisse "false positive" diffs aate rehte hain jo actual regression nahi hain. Isse team dheere-dheere diffs ko bina dekhe approve karne lagti hai (jaise snapshot tests wala anti-pattern jo humne upar dekha), jisse tool ki poori value khatam ho jaati hai. Practical mitigation: har CI run same fixed runner/OS version use kare (consistency ke liye), threshold ko thoda tolerant rakho (jaise 0.1% pixel diff allowed), aur is technique ko sirf high-value, visually-critical screens (checkout, onboarding, design-system components) pe use karo — poori app pe nahi.

9.4 Performance Testing / Profiling in CI

Ab tak humne sirf functional correctness test ki hai — "kya sahi output aaya". Ek senior-level test strategy mein ek aur dimension hoti hai: performance regression detection — kya ek naya PR app ko slow bana raha hai, bina kisi functional bug ke. Ye especially important hai kyunki performance regressions (extra re-renders, ek heavy computation jo render path mein aa gayi) aksar functional tests pass ho jaate hain kyunki output sahi hai, sirf slow hai.

Reassure — render performance ko CI mein track karna
import { measurePerformance } from "reassure"; // Reassure — Callstack ki library jo render performance ko baseline ke against track karti hai
import { ProductList } from "./ProductList"; // jo component profile karna hai (jaise ek bada FlatList wala screen)

test("ProductList render performance", async () => { // Reassure ka test normal Jest test jaisa hi dikhta hai
  await measurePerformance(<ProductList items={mockItems} />); // component ko kai baar render karta hai aur render duration measure karta hai
}); // test close — Reassure current run ko pichhli baseline (main branch) se compare karega

CI mein ye typically main branch ke against ek baseline run karke store hota hai, aur har PR pe naya run us baseline se statistically compare hota hai (mean render duration ka difference, with noise tolerance). Agar koi PR render time ko significantly badha deta hai, Reassure PR comment mein flag kar deta hai — exactly jaise functional test failure flag hota hai, bas metric "sahi/galat" ki jagah "fast/slow" hai.

🧠 Senior Dev Note — performance testing ko "nice to have" mat samjho

Bade product teams mein app startup time aur interaction responsiveness directly retention/revenue se correlate karte hain (well-documented industry data hai iske baare mein). Functional tests ye guarantee nahi karte ki app fast hai — sirf ye guarantee karte hain ki wo sahi hai. Performance regressions chhote-chhote PRs mein slowly accumulate hote hain (death by a thousand cuts) jab tak koi user complain na kare "app slow ho gaya hai" — us waqt tak root cause dhoondhna bahut mushkil ho jaata hai kyunki 50 PRs ke beech kahin regression aaya tha. CI mein ek continuous performance baseline maintain karna is problem ko wahi PR pe hi catch kar leta hai jahan wo introduce hui thi — bilkul functional test failure ki tarah, jaldi aur cheaply.

10. 🎯 Interview Questions — Senior React Native Developer

Neeche kuch questions hain jo senior/staff-level RN interviews mein testing depth judge karne ke liye poochhe jaate hain — philosophy, trade-offs, debugging scenarios, aur practical implementation, sab mix kiya hai.

Q1. React Native Testing Library components ke internal state/instance ko query karne se actively discourage kyun karti hai? Underlying testing philosophy kya hai?

RNTL jaan-boojhkar wrapper.state() ya instance() jaisi APIs provide nahi karti (jo Enzyme provide karta tha, RNTL ka predecessor). Philosophy ye hai: tests ko component ke implementation se decouple hona chahiye, aur sirf uske user-facing contract se couple hona chahiye. Ek user (ya screen reader) ko kabhi pata nahi hota ki component useState use kar raha hai ya useReducer, ya ki internal variable ka naam kya hai — unhe sirf itna dikhta hai ki screen pe kya text/element hai aur wo usse kaise interact kar sakte hain. Agar tests implementation detail ko test karte hain, toh har refactor (chahe behavior same rahe) tests todega — jo developers ko refactoring se hi darwa deta hai ("tests todenge" ka fear), jo bilkul opposite hai testing ka actual purpose hone ke. RNTL ka model — getByText, getByRole, getByTestId — force karta hai ki test sirf wahi assert kare jo genuinely observable/actionable hai, jisse test suite refactor-resistant aur regression-focused dono banti hai.

Q2. Ek naye RN feature ke liye unit vs E2E tests ka right ratio kaise decide karogi, aur kyun?

Ye decision feature ki nature pe depend karta hai, ek fixed formula nahi hai — lekin decision framework ye hoga: pehle pucho ki failure ka cost/likelihood kya hai, aur wo layer kaunsa hai jahan bug sabse cheaply aur reliably catch ho sakta hai. Pure business logic (pricing calculation, form validation rules, data transformation) — ye 100% unit-testable hai, koi rendering involve nahi, isliye yahan heavy unit coverage lagao (fast feedback, zero flakiness). Component-level interaction (button dabane pe sahi callback fire hona, conditional rendering) — RNTL se cover karo, kyunki real user-perspective interaction verify karna zaroori hai lekin native build ki zaroorat nahi. E2E — sirf tab jab ek flow multiple screens/systems ko cross karta hai jinka integration hi risk hai (login → token storage → protected route redirect, ya payment flow jahan backend + native SDK dono involve hain) — aur wo bhi sirf "must never break" journeys ke liye, kyunki E2E cost (native build + flakiness) sabse zyada hai. Practically main aim karta hoon: 70% unit, 20% component/integration, 10% E2E — lekin ye ratio feature ki risk profile ke hisaab se shift hota hai, ratio khud goal nahi hai, confidence-per-cost optimize karna goal hai.

Q3. Tumhara E2E test suite flaky hai aur team "delete kar do" bol raha hai — kaise diagnose karogi ki problem tests mein hai ya app mein, aur plan kya hoga?

Sabse pehle main flaky tests ko delete karne se mana karunga bina root-cause diagnose kiye — kyunki flakiness kabhi kabhi ek real, intermittent bug ko expose kar rahi hoti hai (race condition, unhandled promise rejection), aur test delete karna sirf symptom hide karta hai. Diagnosis plan:

  1. Failure logs categorize karo — kya failure hamesha ek hi step pe ho raha hai (specific element/assertion), ya random hai? Consistent failure point ek real timing issue point karta hai.
  2. Fixed sleeps dhoondo — agar YAML/test code mein sleep(N) jaisi fixed waits hain (na ki extendedWaitUntil/waitFor), ye sabse common flakiness source hai — CI runner slow hone pe fixed wait kaafi nahi padta.
  3. Local vs CI reproduce karo — agar test locally 100% pass hoti hai lekin CI pe fail, suspect resource contention (CI runner underpowered/shared) ya environment difference (different simulator OS version).
  4. Failure rate track karo — pichhle 20-30 CI runs ka failure rate nikaalo per test. Jo tests 20%+ fail rate pe hain unhe priority pe fix karo, baaki ko temporarily quarantine (skip, but tracked ticket ke saath) karo — poore suite ko delete karne se bahut better hai selective quarantine.
  5. App-side bug ka signal — agar failure ek genuine race condition dikhata hai (jaise button 2 baar rapid-tap hone pe double-submit ho raha hai), ye actually production mein bhi hoga — is case mein test "flaky" nahi hai, app buggy hai, aur test ne apna kaam kiya.

Team ko main ye pitch karta hoon: "delete karna" long-term mein zyada expensive hai kyunki wahi regressions wapas production mein pahunchengi jo E2E catch kar raha tha — instead ek focused 1-2 din ka investigation sprint karo flaky tests fix/quarantine karne ke liye, phir suite ko trust-worthy state mein wapas lao.

Q4. Tumne khud ek custom native module banaya hai (Expo Modules API ya TurboModule) — usse unit tests ke liye kaise mock karogi, jab wo Node environment mein exist hi nahi karta?

Approach same hai jo third-party native modules ke liye use karte hain (section 3), lekin apne module ke liye tumhe khud decide karna hota hai ki mock kitna realistic hona chahiye. Steps:

__mocks__/my-custom-native-module.ts
// Jest apne aap ye file pick karega jab bhi "my-custom-native-module" import ho aur jest.mock() call ho

export const getBatteryLevel = jest.fn(() => // real module ka native function, yahan fake version
  Promise.resolve(0.75) // default fake value — 75% battery, deterministic test data
); // getBatteryLevel mock close

export const addBatteryListener = jest.fn((callback) => { // event-listener wala native API mock kar rahe hain
  // real device pe ye native event emitter subscribe karta; test mein hum khud control karte hain kab callback chale
  return { remove: jest.fn() }; // real API jaisa hi ek "subscription" object return karo jisme remove() ho
}); // addBatteryListener mock close

Important principle: mock ko real module ke exact same shape/API contract follow karna chahiye (same function names, same return types/Promise shape) — taaki jo code is module ko consume karta hai, wo bina kisi change ke test aur production dono mein kaam kare. Main apne native modules ke liye mock ko module ke saath hi ship karta hoon (my-module/jest-mock.ts) taaki dusre teams jo is module ko use karte hain, unhe khud mock likhna na pade — ye same "shared test-utils" principle hai jo section 9.1 mein render utility ke liye use kiya. Agar module ka behavior test ke liye critical hai (jaise edge case: "battery listener fire hone pe UI update ho"), main mock ko controllable banata hoon — jaise addBatteryListener ka mock ek module-level array mein saare registered callbacks store kare, aur test ek helper function (__triggerBatteryChange(0.1)) call karke unhe manually fire kar sake.

Q5. Snapshot testing ke baare mein tumhara stance kya hai — kab use karogi, kab avoid karogi?

Snapshot tests (toMatchSnapshot()) mera default choice nahi hain kyunki (jaisa section 8 mein discuss kiya) wo "kuch change hua" batate hain, "sahi change hua ya nahi" nahi — aur team habitually --updateSnapshot chala deti hai bina diff review kiye, jisse wo signal-less ho jaate hain. Main unhe specifically use karta hoon jab output ka exact structure freeze karna genuinely goal ho — jaise ek design-system component library ka public API shape, ya ek complex serialized object (API response transformer ka output) jahan manual assertions likhna impractical hoga. Har baaki case mein (component behavior, user interaction) main explicit expect(screen.getByText(...)) jaisi targeted assertions prefer karta hoon — kyunki failure message directly batata hai kya galat hai, jabki snapshot diff sirf ek text/JSON dump deta hai jise developer ko manually interpret karna padta hai.

Q6. Ek component jo AsyncStorage se data read karta hai aur render pe conditionally kuch dikhata hai — usse test karte waqt kya-kya edge cases cover karogi?

Main teen buckets mein sochta hoon: (1) happy path — data mila aur sahi shape mein hai, component sahi render hua. (2) empty/first-time state — AsyncStorage.getItem() null return karta hai (naya user, kabhi data save nahi hua) — component ko crash nahi karna chahiye, ek sensible default/empty-state dikhana chahiye. (3) malformed data — agar AsyncStorage mein corrupt JSON hai (app crash beech mein hua tha jab write ho raha tha, ya app version update se schema change hua), JSON.parse() throw karega — component ko is case mein bhi gracefully handle karna chahiye (try/catch + fallback), na ki white-screen crash. Ye teesra case aksar miss ho jaata hai lekin production mein sabse zyada crash reports isi se aate hain — is liye ek senior test suite mein explicitly ek test hona chahiye jo AsyncStorage ko intentionally invalid JSON return karne ke liye mock kare aur assert kare ki app crash nahi hoti.

Q7. CI mein Jest tests toh fast hain, lekin Maestro E2E suite grow karte-karte 25 minutes le raha hai — is bottleneck ko kaise address karogi?

Pehla step: measure karo ki time kahan ja raha hai — build time (native build banane mein) vs actual flow-execution time. Agar build time bottleneck hai, solution hai build artifact ko cache/reuse karna — agar us PR mein native code change hi nahi hua (sirf JS/TS), toh purana build hi reuse karo (Expo Update ke through JS bundle push kiya ja sakta hai us build pe, agar CI setup allow kare) — naya native build har PR pe zaroori nahi. Agar execution time bottleneck hai, solutions: flows ko parallelize karo (Maestro Cloud ya multiple simulators pe flows split karke ek saath chalao, na ki sequentially), flow scope narrow karo (kuch E2E flows actually component-level integration tests ho sakte the — unhe RNTL mein migrate karke E2E suite se hata do), aur redundant setup steps eliminate karo (agar har flow "launchApp → login" se shuru hota hai, ek shared "pre-authenticated" app state/deep-link se seedha relevant screen pe pahuncho, poora login flow repeat mat karo har baar). Goal hai suite ko itna fast rakhna ki team use ignore/skip karne ka temptation na ho.

Q8. Testing pyramid ke against ek "testing trophy" (Kent C. Dodds ka model, jisme integration tests sabse zyada weight lete hain) ka argument sunaogi kya, aur RN ke liye kaunsa zyada applicable hai?

Testing trophy ka core argument ye hai: pure unit tests (isolated functions) aksar itni "confidence per effort" nahi dete jitna integration tests dete hain, kyunki real bugs usually components ke beech ke interaction mein hote hain, isolated logic mein nahi — isliye trophy shape mein integration layer sabse mota hota hai, unit sabse patla. RN context mein main ye view partially agree karta hoon: RNTL wale "component/integration" tests (jo multiple child components + hooks + context ko ek saath render karke test karte hain) genuinely high confidence-to-cost ratio dete hain, isliye main bhi apna suite unki taraf weighted rakhta hoon. Lekin RN mein ek extra factor hai jo web mein utna nahi hota: native module boundary — kaafi saara "integration risk" native bridge/JSI ke through aata hai (permissions, camera, storage), jo Jest/RNTL layer bilkul bhi nahi cover kar sakta chahe wo integration-style ho ya nahi — us risk ko sirf E2E cover karta hai. Isliye practically main pyramid aur trophy dono se ek hybrid use karta hoon: unit tests sirf genuinely-isolated pure logic ke liye rakho (thin layer, jaisa pyramid kehta hai), integration/component tests ko sabse mota layer banao (jaisa trophy kehta hai), aur E2E ko RN-specific native-boundary risk ke liye reserve karo.

Q9. Tum ek naye developer ko onboard kar rahi ho jo apna pehla PR bhej raha hai bina kisi test ke, aur kehta hai "manual QA kar li hai, feature kaam kar raha hai". Kaise respond karogi?

Main pehle acknowledge karunga ki manual QA valuable hai — lekin uska scope limited hai: wo sirf ek point-in-time verification deta hai, ye guarantee nahi deta ki future changes (kisi aur developer ke, 3 mahine baad) is feature ko silently todenge nahi. Test suite ka asli purpose hi ye "regression safety net" hai, na ki "feature abhi kaam karta hai" prove karna — wo toh manual QA se bhi pata chal jaata hai. Main unhe explain karunga ki minimum bar kya hona chahiye is feature ke liye: agar pure logic hai, ek unit test; agar user-facing component hai, ek RNTL test jo core interaction cover kare (happy path + ek edge case); aur agar ye ek critical flow hai (payment, auth), suggest karunga ki Maestro flow mein bhi add karein. Main isse blocking requirement banaunga PR merge karne se pehle (via CI check), lekin pairing offer karunga test likhne mein agar wo naye hain RNTL/Jest patterns se — goal hai standard maintain karna bina onboarding experience ko harsh banaye.
