Publishing Overview: EAS Submit vs Manual Publishing

Ek reasonable sawal ye hai: agar Chapter 11 mein hum eas submit se ek command mein sab kuch automate kar chuke hain, to manual publishing seekhna kyun zaroori hai? Answer ye hai ki automation ek abstraction hai, magic nahi — aur jab abstraction leak karti hai (fail hoti hai, confusing error deti hai, ya kisi edge case ko handle nahi karti), aapko underlying process samajhna hi padta hai debug karne ke liye. Ye bilkul wahi principle hai jo humne EAS Build (Chapter 10) mein dekha tha — EAS Build bhi wahi xcodebuild/Gradle commands chalata hai jo aap locally chalate, bas cloud pe.

Kuch concrete scenarios jaha manual flow zaroori ban jaata hai:

  • EAS Submit fail ho raha hai aur error message vague hai — jaise "Invalid binary" ya "Asset validation failed" jaisi generic errors. Xcode Organizer mein manually upload karne par aapko exact validation error milta hai (missing icon size, invalid Info.plist entry, wrong architecture) — jo CLI output mein kabhi utna detailed nahi hota.
  • Full control chahiye Xcode-level archive/upload steps par — jaise custom entitlements debug karna, ya ek specific provisioning profile force karna jo EAS ka automatic credential resolution galat pick kar raha hai.
  • Team abhi EAS Submit set up nahi kar payi — chhoti teams ya freelance projects mein kabhi EAS account ka submit-level access nahi hota (sirf build access), to manual upload hi option bachta hai.
  • App Store Connect ka metadata/listing management — ye part hum aage dekhenge, EAS Submit sirf binary upload karta hai, store listing (screenshots, description, "what's new") separate kaam hai jo har team ko kabhi na kabhi manually karna padta hai, chahe binary EAS se hi upload ho.
🧠 Senior Dev Note

Is chapter ko "EAS Submit ka pehla-principles model" ki tarah socho — jab aap samajh jaate ho ki eas submit actually Xcode Organizer ke Transporter API ko hi internally hit kar raha hai (same underlying Apple upload mechanism), debugging kaafi aasan ho jaati hai. Aap literally same steps manually reproduce kar sakte ho aur exactly dekh sakte ho kaha fail ho raha hai.

Publishing with Xcode (Manual iOS Flow)

Manual iOS publishing ke liye sabse pehle aapko ek native ios/ project chahiye — agar aap purely EAS Build ke cloud-only flow use kar rahe ho (jaha native folders kabhi locally generate nahi hote, sab kuch cloud pe hota hai), to pehle npx expo prebuild chalana padega taaki native project locally materialize ho. Ye command app.json/app.config.ts aur config plugins ko read karke actual Xcode project generate karta hai (wahi step jo EAS Build cloud pe internally chalata hai, bas ab locally).

Terminal
# Agar ios/ folder abhi tak generate nahi hua (ya .gitignore mein hai), pehle prebuild chalao
npx expo prebuild --platform ios # app.config se native Xcode project generate karta hai ios/ folder mein

# Generated project ko Xcode mein directly kholna hai (workspace file, .xcodeproj nahi, kyunki CocoaPods use ho raha hai)
open ios/*.xcworkspace # .xcworkspace kholna zaroori hai — CocoaPods dependencies sirf isi mein resolve hoti hain

Xcode khulne ke baad, poora manual flow ye hai:

  1. Scheme aur device select karo — top bar mein apna app target select karo aur destination ko "Any iOS Device (arm64)" par set karo. Simulator select hone par Archive option disabled rehta hai — Apple ko sirf real-device-compatible binary chahiye.
  2. Product → Archive — Xcode poora release build compile karta hai (debug nahi, release configuration — optimized, no dev tools bundled) aur ek .xcarchive file banata hai. Ye wahi step hai jo EAS Build cloud pe xcodebuild archive command se karta hai.
  3. Xcode Organizer khulta hai automatically — archive complete hone ke baad Organizer window mein aapka naya archive listed dikhega, top pe (date/time ke saath).
  4. "Distribute App" click karo — ek wizard khulta hai jaha aapko distribution method choose karna hai: App Store Connect (jo humein chahiye), TestFlight-internal-only, Ad Hoc, ya Enterprise.
  5. Signing options — "Automatically manage signing" (Xcode khud certificate/provisioning profile resolve karta hai, aapke Apple Developer account se) ya "Manually manage signing" (aap specific profile pick karte ho — enterprise setups mein common jaha central team profiles issue karti hai).
  6. Upload — Xcode binary ko validate karta hai locally (icon sizes, missing architectures, Info.plist required keys) before upload — ye wahi validation hai jiske vague errors aapko EAS Submit se milte hain, lekin yaha Xcode exact file/field bata deta hai jo problem hai. Validation pass hone ke baad, binary Apple ke Transporter service ke through upload hota hai.
  7. Processing wait — upload ke baad Apple server-side processing karta hai (few minutes se le kar an hour tak) — iske baad hi build App Store Connect mein "TestFlight" tab ke under select karne ke liye available hota hai.

Agar aap curious ho ki npx expo prebuild actually kya generate karta hai, neeche ek annotated tree hai — samajhna zaroori hai kyunki manual Xcode flow mein aap directly isi generated project ke saath kaam karte ho (EAS Build ke cloud flow mein ye sab background mein hota hai, kabhi dikhta nahi):

ios/ (generated by expo prebuild)
ios/
├── MyApp.xcworkspace/          // CocoaPods integration ke baad ka "combined" project — ISE hi kholna hai, .xcodeproj nahi, kyunki Pods target bhi isi workspace ke andar hota hai
├── MyApp.xcodeproj/            // Raw Xcode project (targets, build settings, schemes) — prebuild ne app.config se generate kiya, hand-edit karne se agla prebuild overwrite kar dega
├── MyApp/                      // Actual native app source — Info.plist, AppDelegate, entry point, assets
│   ├── AppDelegate.swift       // App lifecycle entry point — RN bridge/JS engine yahin se boot hota hai
│   ├── Info.plist              // Permissions strings, bundle identifier, orientation config — config plugins isi file ko generate/patch karte hain
│   ├── Images.xcassets/        // App icon + launch screen assets — 1024px icon yahin se App Store Connect ko bhi resolve hota hai
│   └── PrivacyInfo.xcprivacy   // Apple ka "privacy manifest" — declare karta hai app/SDK kaunse "required reason" APIs use karte hain (App Privacy label ke sath cross-checked hota hai)
├── Podfile                     // CocoaPods dependency list — native modules ke iOS pods yahan se resolve hote hain "pod install" ke through
└── .xcode.env                  // Node binary path jo Xcode build script ko batata hai kaunsa node use karna hai (React Native build phase ke liye zaroori)
⚠️ Native folder ko commit karna ya nahi

Agar aap purely EAS Build cloud flow use kar rahe ho, convention hai ios//android/ ko .gitignore mein rakhna (EAS har build pe fresh prebuild khud chalata hai). Lekin agar aap manual Xcode publishing regularly karte ho — ya koi custom native code hai jo config plugin se express nahi ho sakta — team ko in folders ko commit karna padta hai taaki sab developers same generated project dekhein. Dono approaches valid hain, bas team-wide consistent hona chahiye.

eas metadata command store listing metadata (description, keywords, "what's new", support URL, etc.) ko ek local JSON file se App Store Connect / Play Console push karne deta hai — screenshots jaisi binary assets abhi bhi manually upload karni padti hain, lekin text-based metadata ko version-control mein rakhna aur CI se automate karna possible ho jaata hai:

store.config.json (eas metadata pattern — teaching comments, real JSON support nahi karta)
{
  "configVersion": 0, // eas metadata schema version — EAS CLI isse validate karta hai file ka format
  "apple": { // Apple-specific store listing metadata block
    "info": { // Locale-keyed metadata — multi-language store listings support karta hai
      "en-US": { // US English locale ke liye listing content

        "subtitle": "Track expenses effortlessly", // Title ke neeche chhota tagline
        "description": "MyApp helps you...", // Full description — search indexing mein limited weight, lekin conversion ke liye important
        "keywords": "expense,budget,finance,tracker", // iOS-specific dedicated search field — comma separated, directly ranking affect karta hai

      } // en-US block close
    } // info block close
  } // apple block close
} // root object close
Terminal
# Existing App Store Connect listing ko local JSON file mein pull karna (naya project onboard karte waqt useful)
eas metadata:pull # store.config.json ko current live metadata se populate kar deta hai

# Local JSON file se App Store Connect listing update push karna
eas metadata:push # store.config.json ka content App Store Connect API ke through upload hota hai
ℹ️ Binary upload ≠ Store listing complete

Yaha ek critical distinction samajhna zaroori hai: upload karna sirf binary submit karna hai — jaise ek courier ko package de dena. Actual "store pe kya dikhega" — screenshots, description, keywords, "what's new in this version", pricing — ye sab App Store Connect ki website par separately fill karna padta hai. Chahe binary EAS Submit se upload hui ho ya manually Xcode se, listing metadata management ek alag, largely manual step hai (EAS ka eas metadata command isko partially automate karta hai — ek JSON file se metadata push kar sakta hai, lekin screenshots jaisi visual assets aur pehli baar ka store listing setup still mostly manual/App-Store-Connect-UI-driven hota hai in most teams).

Isliye teams jo EAS Build + EAS Submit dono use karti hain, unhe bhi App Store Connect UI (ya eas metadata) se familiar hona padta hai — kyunki har naye version ke saath "what's new" text update karna, ya har naye feature ke saath screenshots refresh karna, ek recurring manual (ya semi-automated) task hai jo pure build automation se solve nahi hota.

💡 Hinglish Tip

Android ka equivalent manual flow android/ folder ko Android Studio mein khol ke Build → Generate Signed Bundle/APK karna hai — concept same hai (local native tool se signed artifact banana), bas UI/terminology alag hai. Android side pe manual flow generally kam use hota hai kyunki Gradle command-line se hi (./gradlew bundleRelease) same output easily mil jaata hai bina IDE ke.

App Store Submission — Full Checklist

Ye checklist wahi cheezein cover karti hai jo senior devs pehle se verify kar lete hain submit karne se pehle — kyunki har rejection cycle mein Apple review team se dobara turn milne mein 1-3 din lag sakte hain, aur "sirf ek chhoti si cheez missing thi" wali rejection avoid karna hi sabse bada time-saver hai.

ItemDetailCommon mistake
App Icons — all sizes 1024×1024 App Store icon (no alpha channel, no rounded corners — Apple khud mask lagata hai) plus in-app sizes jo Xcode asset catalog auto-generate kar sakta hai. 1024px icon mein transparency/alpha channel hona — Apple isse silently reject kar deta hai validation step pe hi.
Privacy Policy URL Mandatory — har app ko ek live, publicly accessible privacy policy URL chahiye, chahe app koi personal data collect na kare. URL 404 dena, ya localhost/staging link daal dena jo review team access na kar paye.
App Privacy "nutrition label" App Store Connect ka questionnaire jaha declare karna hota hai app kaunsa data collect karta hai (contact info, usage data, identifiers, etc.) aur kis purpose ke liye (analytics, advertising, functionality). Sabse common rejection/flag reason — SDK (analytics, crash reporting, ads) jo data collect karte hain unko declare na karna. Apple ab automated binary scanning se actual SDK usage detect kar leta hai aur mismatch flag karta hai.
Screenshots — all device sizes 6.9" (iPhone 16 Pro Max class) aur 13" iPad required hain agar app universal/iPad-compatible hai; baaki sizes optional but recommended for better presentation. Sirf ek size upload karke sochna ki baaki auto-scale ho jayenge — Apple kuch sizes ke liye specific uploads maangta hai.
App Review Information Agar app login-gated hai, ek working demo account (username/password) dena zaroori hai reviewer ke liye, plus koi special notes (e.g. "OTP ke bajaye ye static code use karein: 123456"). Demo account expire ho jaana ya password change ho jaana submission ke baad — reviewer login hi nahi kar paata, straight rejection.
Age Rating Questionnaire Content types declare karna (violence, gambling references, user-generated content, etc.) — isse final age rating (4+, 12+, 17+) determine hota hai. User-generated content (chat, comments, profiles) wale apps "Unrestricted Web Access" ya moderation questions galat answer kar dete hain.
🔒 Common Rejection Reasons

Kuch specific rejection patterns jo baar-baar dikhte hain: (1) crash on launch during review — reviewer ka test device/iOS version aapke dev/QA devices se differ kar sakta hai, isliye release build ko multiple iOS versions pe test karna zaroori hai, sirf latest pe nahi. (2) broken links — privacy policy, support URL, ya in-app links jo 404 dete hain. (3) incomplete metadata — missing "what's new" text, placeholder screenshots, ya description jo abhi tak "Lorem ipsum" hai. (4) Guideline 4.2 "Minimum Functionality" — Apple thin/template-generated apps ko reject karta hai jinme substantial functionality nahi hai (jaise sirf ek webview wrapper koi meaningful native feature ke bina) — ye specifically un apps ko target karta hai jo "app store spam" jaisa lagte hain, to agar aapka app genuinely value-add karta hai, isse bachne ke liye review notes mein clearly explain karo ki app kya unique karta hai.

Play Store Submission — Full Checklist

Google Play ka process conceptually similar hai lekin details differ karte hain — aur kuch areas mein Google actually zyada strict hai post-launch enforcement mein (jaise hum Gotchas section mein dekhenge).

ItemDetailCommon mistake
Data Safety form Google ka version of App Privacy label — declare karna hota hai kaunsa data collect/share hota hai, encryption in transit hai ya nahi, aur users data delete request kar sakte hain ya nahi. Ye bhi utna hi commonly galat/forgotten hota hai jitna iOS wala — aur Play Store inaccurate Data Safety declarations ke liye apps ko reject ya bina warning ke remove kar deta hai, chahe app already live ho.
Content Rating Questionnaire IARC (International Age Rating Coalition) questionnaire fill karna — violence, sexual content, gambling, user interaction (chat/UGC) ke sawalon ke jawab dete hain jo automatically per-region rating generate karte hain. Questionnaire ko jaldi mein galat answer karna — jaise "user-generated content" ko "no" bol dena jab app mein comments/chat feature hai.
Target API level Google har saal minimum target SDK version enforce karta hai (naye apps aur existing app updates dono ke liye) — purani SDK target karne wale builds submit hi nahi ho paate. Ek purana React Native/Expo SDK version use kar rahe ho jiska Android target level ab outdated ho chuka hai — submission "target API level too low" error ke saath reject hoti hai.
Staged Rollout Play Console mein aap production release ko ek % users tak limit kar sakte ho (jaise 10%, phir 50%, phir 100%) — issues catch karne ka senior practice, especially major version changes ke liye. Har release seedha 100% pe push karna — agar koi crash-inducing bug slip ho jaye, poore user base ko affect karta hai instantly, staged rollout se sirf chhota % affect hota.
Testing tracks Internal testing (small team, instant), Closed testing (specific tester group, review lagta hai first time), Open testing (public opt-in beta) — production se pehle in tracks se guzarna recommended hai. Directly production track pe upload karna without kabhi kisi testing track se guzre — real device fragmentation ke issues sirf production mein pata chalte hain.
🔒 Data Safety Mismatches — Post-Launch Risk

Ye ek non-obvious risk hai jo naye developers ko surprise karta hai: Data Safety declaration sirf submission-time check nahi hai — Google periodically re-scan karta hai already-live apps ko aur agar actual app behavior (jaise ek naya analytics SDK add kiya but Data Safety form update nahi kiya) declared data safety se mismatch karta hai, Google app ko bina warning ke suddenly remove ya suspend kar sakta hai — chahe app mahino se stable live ho. Senior practice: har baar jab koi naya third-party SDK (analytics, ads, crash reporting) add karo, Data Safety form ko turant review/update karne ka checklist item bana lo — ise "one-time submission task" mat samjho.

Testing tracks ka structure samajhna bhi zaroori hai — production pe seedha jaane se pehle ye teen tracks available hain, aur senior teams generally sabko sequentially use karti hain:

TrackAudienceReview neededBest for
Internal testing Up to 100 specific testers (email list) No review — almost instant availability Daily dev/QA builds, fastest iteration loop
Closed testing Larger tester groups (Google Group / email list, thousands possible) First submission needs a light review Beta programs, pre-release feedback from real external users
Open testing Anyone via public opt-in link on the Play Store listing itself Standard review applies Public beta, gathering feedback at scale before full production
Production (staged) General public, % rollout controlled by you Standard review applies Final release — start small % and increase gradually
💡 Hinglish Tip

Ek promotable build ka concept bhi hai — agar aapne ek build closed testing track mein already thoroughly test kar liya hai aur wo stable nikla, Play Console mein usi build ko "promote to production" kar sakte ho bina naya artifact upload kiye — ye guarantee karta hai ki jo binary production mein ja raha hai, wo exactly wahi hai jo testers ne already use kiya tha, koi last-minute rebuild ka risk nahi.

Store Listing Optimization (Brief Senior Notes)

Store listing optimization ek poora field hai apne aap mein (ASO — App Store Optimization), lekin senior level pe kuch practical points jaanna kaafi hai:

  • App Store Connect keywords field — ye iOS-specific hai, ek dedicated comma-separated keywords field hota hai (visible sirf App Store Connect mein, users ko nahi dikhta) jo directly search ranking affect karta hai. Description text khud search indexing mein utna weight nahi rakhta jitna is dedicated field mein.
  • Play Store — description-based indexing — Google ka algorithm fundamentally different hai: yaha koi dedicated "keywords" field nahi hota, search ranking mostly title + short description + full description ke natural text se derive hoti hai (jaise ek search engine SEO). Isliye Play Store listing likhte waqt keywords ko naturally description mein weave karna better strategy hai, keyword field stuff karna nahi (jo iOS approach hai).
  • A/B testing store listings — Play Console mein built-in "Store listing experiments" feature hai jisse aap different icons/screenshots/descriptions ko live traffic ke against test kar sakte ho, conversion rate compare karke. iOS side pe Apple ka "Product Page Optimization" similar functionality deta hai (App Store Connect ke andar).
  • Over-optimization ka trade-off — listing ko itna "sell" mat karo ki actual app experience se expectation mismatch ho jaye. Isse users disappointed feel karte hain install karne ke baad, jo directly bad reviews aur high uninstall rate mein convert hota hai — jo long-term ranking ko listing ke short-term conversion boost se zyada nuksan pahunchata hai.
💡 Hinglish Tip

Practical senior advice: listing copy likhte waqt socho "agar main is app ko pehli baar dekh raha hota, kya ye text mujhe accurately batata ki app kya karta hai" — overselling se short-term downloads badh sakte hain, lekin retention aur rating dono girte hain jo long-term organic discovery ko hurt karta hai (dono stores ka ranking algorithm retention/rating ko heavily weight karta hai).

Real-World Gotchas

⚠️ App Store review time — unpredictable

Apple review time officially "usually within 24 hours" bola jaata hai, lekin practically ye kuch ghanto se le kar kai din tak vary kar sakta hai — especially holiday seasons (jaise December) mein ya jab koi major iOS release hoti hai (submission volume spike hota hai). Senior practice: stakeholders ko kabhi exact launch date promise mat karo jab tak app already "Ready for Sale" status mein na ho — instead ek range communicate karo ("submission ke 1-4 din baad live hone ki expectation rakho") aur agar hard deadline hai (jaise ek marketing event), submission kam se kam 5-7 din pehle kar do buffer ke liye.

⚠️ Data Safety mismatch — sudden removal even after being live

Jaise upar discuss kiya, ye sirf submission-time issue nahi hai — Google periodic re-checks karta hai. Ek real scenario: team ne app launch ke 6 mahine baad ek naya crash-reporting SDK add kiya (jo device identifiers collect karta hai), lekin Data Safety form update karna bhool gaye — kuch hafte baad Google ne mismatch detect kiya aur app ko Play Store se remove kar diya bina prior warning ke, jab tak form correct nahi kiya gaya. Iska direct impact hota hai revenue aur existing users pe (update nahi mil paate) — isliye har dependency update ke saath Data Safety review ek CI/release-checklist item hona chahiye, sirf ek onboarding-time task nahi.

⚠️ Version code/build number conflicts after a rejection fix

Jab ek submission reject hoti hai aur aap fix karke resubmit karte ho, dono stores demand karte hain ki naya build ka version code/build number strictly greater ho purane se — chahe purana build kabhi live hua hi na ho (sirf review mein reject hua tha). Agar aap manually version manage kar rahe ho aur bhool jaate ho ki reject-hui build ne bhi ek versionCode "consume" kar liya tha, resubmission fail ho jaati hai duplicate version error ke saath. Yaha wahi autoIncrement: true practice (Chapter 10) kaam aati hai — ye is class of error ko automatically avoid kar deta hai kyunki har build attempt (chahe reject ho ya accept) naya number leta hai.

⚠️ Certificates/provisioning profiles expiring

Agar aapki team EAS-managed credentials use nahi kar rahi (self-managed certificates/profiles), ye artifacts ek fixed expiry date rakhte hain (iOS distribution certs typically 1 year, provisioning profiles bhi similar). Agar ye expire ho jaye aur kisi ko pata hi na ho, agli production build/submission suddenly fail hone lagti hai signing errors ke saath — aur naya certificate generate karne mein aur poori team ko distribute karne mein unexpected time lag sakta hai agar urgently chahiye ho (jaise ek critical bugfix release ke waqt). Senior practice: agar EAS-managed credentials use nahi kar rahe, ek calendar reminder/team process banao jo expiry dates se kam se kam ek mahina pehle alert kare — ye exactly wo class of "silent time bomb" hai jo teams ko surprise leta hai.

Advanced Deep-Dive — Beyond the Basics

Ye section un cheezon ko cover karta hai jo checklist-level knowledge se aage senior-level judgment maangti hain — kab ek rollout ruko, kaise metadata ko engineering discipline ki tarah treat karo (manual UI clicks nahi), aur ek app jab multiple markets mein grow karta hai to store presence kaise scale karta hai.

Phased Release Strategies — In Depth

Humne upar dono stores ke staged rollout ka basic mention kiya, lekin dono ka underlying mechanism aur control level fundamentally different hai — aur ye difference senior-level incident response planning ko directly affect karta hai.

AspectApple — Phased ReleaseGoogle Play — Staged Rollout
Applies to Sirf updates ke liye — pehli baar submit ho rahi app pe available hi nahi (naya app seedha 100% users ko milta hai jaise hi "Ready for Sale" hota hai). Dono naye app releases aur updates ke liye available — har production release ke liye rollout % control kar sakte ho.
Ramp mechanism Automatic, fixed 7-day schedule: Day 1 → 1%, Day 2 → 2%, Day 3 → 5%, Day 4 → 10%, Day 5 → 20%, Day 6 → 50%, Day 7 → 100%. Aap in exact percentages ko change nahi kar sakte. Fully manual — aap khud har % choose karte ho (jaise 5% → 20% → 50% → 100%) aur khud decide karte ho next % kab push karna hai. Koi fixed schedule nahi hai, aap indefinitely ek % pe ruk sakte ho.
Halt control App Store Connect mein "Pause" available hai — current % pe freeze ho jaata hai (aage nahi badhta), lekin already-updated users ka rollback nahi hota. Pause ke baad resume ya poori update hi remove karni padti hai (naya build submit karke). "Halt rollout" se turant rollout ruk jaata hai at current %, aur aap direct ek purani, stable release pe rollback bhi kar sakte ho — naye users ko purani version milne lagti hai turant, bina naya build submit kiye.
Senior implication Apple ka fixed schedule ka matlab hai aapke paas kam control window hai — agar metrics Day 3 (5%) tak clean lag rahe hain, Day 4 pe automatically 10% ho jaayega chahe aap ready ho ya na ho. Isliye dashboard monitoring cadence ko is fixed schedule ke against align karna padta hai. Google ka manual control zyada senior-friendly hai crisis situations ke liye — aap indefinitely ek safe % pe ruk sakte ho jab tak confidence na aa jaaye, aur rollback ka direct button hai jo Apple ke paas nahi hai.
🧠 Senior Dev Note — Rollout ke dauraan kya dekhna hai

Sirf "% badha do" mental model se kaam nahi chalta — har phase ke beech ek senior engineer specific metrics dashboard pe active nazar rakhta hai: crash-free session rate (Sentry/Crashlytics se, previous version ke baseline ke against compare karke — koi bhi drop >0.5% typically red flag hai), ANR rate (Android-specific — "Application Not Responding" spikes), key funnel conversion (jaise checkout completion rate agar payment flow touch hua ho is release mein), aur backend error rate (agar naya API contract shipped hua hai, malformed requests spike ho sakti hain naye client version se). Sabse important senior practice: rollout start karne se pehle ek explicit "halt criteria" likh lo (jaise "crash-free rate 1% se zyada girta hai → immediately halt aur rollback") — is decision ko incident ke beech mein panic state mein banane se bahut better hai calm state mein pehle se plan kar lena.

App Store Connect API Automation for Metadata

eas metadata (jo humne pehle dekha) internally App Store Connect API ko hi hit karta hai — ye ek convenient wrapper hai. Lekin senior teams ke liye ye samajhna zaroori hai ki underlying API directly bhi accessible hai, aur bade teams (jaha custom CI pipelines hain, ya jaha eas metadata ka schema kisi specific field ko support nahi karta) directly App Store Connect API use karte hain. Core idea same rehta hai: store listing ko version-controlled config ki tarah treat karo, na ki har release pe App Store Connect ki website pe jaake manually description/keywords retype karna — manual entry typo-prone hai, review-less hai (koi PR review nahi hoti), aur history track nahi hoti (kisne kab kya change kiya, pata nahi chalta).

generate-token.js — App Store Connect API ke liye JWT banana
// App Store Connect API ek JWT (JSON Web Token) based auth use karta hai — username/password kabhi nahi
const jwt = require('jsonwebtoken'); // JWT sign karne ke liye standard npm library
const fs = require('fs'); // .p8 private key file disk se read karne ke liye

// App Store Connect → Users and Access → Keys se download ki gayi private key file
const privateKey = fs.readFileSync('./AuthKey_XXXXXXXXXX.p8'); // buffer mein raw key content aata hai

const token = jwt.sign(
  {}, // payload empty rakha — Apple ko sirf header + expiry claims chahiye, body claims nahi
  privateKey, // isi key se signature verify hoga Apple ke server pe
  {
    algorithm: 'ES256', // Apple sirf ES256 (elliptic curve) signing algorithm accept karta hai, RS256 nahi
    expiresIn: '20m', // Apple ka hard max limit 20 minute hai — isse zyada purana token turant reject ho jaata hai
    issuer: 'ISSUER_ID', // App Store Connect "Keys" page se milne wala team-level issuer identifier
    header: { alg: 'ES256', kid: 'KEY_ID' }, // kid = kaunsi specific key se sign hua (team ke paas multiple keys ho sakti hain)
  }
); // token ab ek short-lived, single-use-window JWT string ban chuka hai

console.log(token); // isi output ko CI step mein env var (e.g. $ASC_TOKEN) mein capture karenge
Terminal — generated JWT se metadata fetch karna
# Pehle upar wala script chalao aur output ko ek env var mein capture karo
ASC_TOKEN=$(node generate-token.js) # JWT ab is shell session ke liye ready hai

# Us JWT ko Bearer token ki tarah use karke app-level metadata GET karna
curl -H "Authorization: Bearer $ASC_TOKEN" \ # auth header mein humara short-lived JWT
  "https://api.appstoreconnect.apple.com/v1/apps/APP_ID/appInfos" # app-level metadata endpoint — naam, primary category, waghera return karta hai

Practically, senior teams isse raw curl se nahi, balki ek thin CI script (ya eas metadata jaisa tool) se wrap karte hain jo store.config.json-jaisi file ko PR review process se guzarti hai — koi bhi listing change (jaise ek naya keyword add karna, ya ek locale ka description update karna) ab ek normal code change ki tarah trackable, revertible, aur reviewable ban jaata hai, exactly jaise koi feature code change hota.

Localization at Scale

Ek app jab 1-2 languages se 10-15+ locales tak grow karta hai (jo common hota hai jab app multiple regions mein organically discover hoti hai — App Store/Play Store dono automatically visitor ki device language ke hisaab se matching locale ki listing dikhate hain, agar wo locale configured hai), listing management ek alag class ka problem ban jaata hai:

  • Translation workflow — senior teams generally ek "source of truth" locale (typically en-US) maintain karte hain aur baaki locales ko usse derive karte hain, ya to professional translation service se ya in-house native speakers se. Raw machine translation (Google Translate copy-paste) ko directly production listing mein daalna risky hai — idioms, cultural context, aur even basic grammar galat ho sakte hain jo native speakers ko turant "cheap/untrustworthy app" signal dete hain.
  • Screenshots ka localization — sirf text translate karna kaafi nahi, screenshots mein agar UI text hai (jaise onboarding screens ke captions), un screenshots ko bhi per-locale generate karna padta hai — ye ek non-trivial asset pipeline problem hai jo scale ke saath automate karna zaroori ho jaata hai (screenshot generation tools jaise Fastlane's snapshot/screengrab is exact problem ko solve karte hain).
  • Consistency ka maintenance overhead — jab bhi "what's new" text change hota hai ek release ke saath, sabhi 15 locales ke liye update karna padta hai — agar sirf en-US update hokar baaki purana reh jaata hai, users ko ek stale/inconsistent experience milta hai (jaise ek Hindi user ko purana release-note dikhna jab feature already available ho chuka hai).
  • Review scrutiny ka risk — Apple/Google dono ke paas automated aur human reviewers hain jo listing quality bhi implicitly judge karte hain. Inconsistent ya machine-translated-looking listings (grammatically broken, ya locale ke against culturally off) low-effort/spam app ka signal de sakte hain — especially agar wahi pattern App Store Guideline 4.2 (Minimum Functionality) jaisi checks ke saath combine ho jaaye, jisse ek borderline app ka reject hone ka chance aur badh jaata hai.
🧠 Senior Dev Note — Localization ROI framework

Har naye locale ko add karna free nahi hai — translation cost, ongoing maintenance cost (har release ke saath), aur QA cost (kya translated text UI mein overflow to nahi kar raha, especially German jaise longer-word languages mein) sab factor karte hain. Senior practice: pehle analytics se dekho konsi countries se already organic installs/traffic aa raha hai (chahe app us locale mein na ho, users ab bhi default/English listing dekh ke install kar rahe honge) — un top countries ko prioritize karo localization ke liye, blanket "sab languages add kar do" approach lene ke bajaye. Ek half-maintained, stale locale koi locale na hone se bhi bura signal de sakta hai users ko.

🎯 Interview Questions — Senior React Native Developer

Neeche wahi tarah ke sawaal hain jo senior RN role ke interviews mein publishing/release process pe pooche jaate hain — process knowledge, risk judgment, aur real incident handling teeno cover karte hue.

1. Walk me through your full release checklist from feature-complete to live in both stores.

Ek senior-level answer sequence mein hota hai, har step ka "why" explain karte hue: (1) version code/build number bump verify karo (ya autoIncrement: true confirm karo eas.json mein — Chapter 10) taaki duplicate version error na aaye. (2) release build ko multiple device/OS versions pe test karo, sirf latest pe nahi — kyunki review team ka test environment differ kar sakta hai. (3) App Privacy label (iOS) aur Data Safety form (Android) ko current SDK usage ke against re-verify karo — koi naya analytics/crash SDK add hua ho to declaration update karo. (4) store listing metadata (screenshots, description, "what's new") review/update karo — eas metadata:push ya App Store Connect UI se. (5) EAS Build se production binary banao, EAS Submit (ya manual Xcode/Android Studio flow) se upload karo. (6) Android side pe pehle internal → closed testing track se guzaro before production. (7) production release ko staged rollout/phased release ke saath launch karo, halt criteria pehle se defined rakh ke. (8) rollout ke dauraan crash-free rate/key metrics dashboard active monitor karo har phase ke beech.

2. An update just got rejected for Guideline 4.2 (Minimum Functionality) — what's your response plan, both immediate and long-term?

Immediate: pehle Apple ka exact rejection reasoning carefully padho (Resolution Center mein) — 4.2 rejections generic template text ke saath aate hain, isliye specific reviewer notes dhoondo jo bataye kya missing lag raha hai unhe. Agar genuinely lagta hai app substantial hai but reviewer ne misunderstand kiya, ek clear, specific reply likho Resolution Center mein — exactly explain karo app kya unique/native functionality provide karta hai (screenshots/video attach karke agar zaroori ho), sirf "please reconsider" jaisa vague reply mat bhejo. Agar app genuinely thin hai, ye ek signal hai ki actual product gap hai, sirf ek metadata fix se nahi solve hoga. Long-term: team ke saath ek review karo ki app mein kya substantial native value-add hai (offline support, push notifications, device integration, meaningful business logic) — agar app sirf ek webview wrapper jaisa lagta hai, roadmap mein genuine native features prioritize karo taaki future submissions is risk se bachein. Bhi ek internal process banao ki naye features/screens add karte waqt hamesha socho "kya ye reviewer ko clearly dikhega ki ye substantial hai" — taaki next submission mein surprise na aaye.

3. How would you decide whether to use a phased rollout vs releasing to 100% immediately for a given release?

Ye ek risk-based judgment call hai, blanket rule nahi. Factors jo main consider karunga: blast radius — agar release mein core flow (login, payment, main navigation) touch hua hai, phased rollout mandatory hai; agar sirf ek isolated, low-traffic screen ka minor UI tweak hai, risk kam hai. Test coverage confidence — agar Maestro E2E suite (Chapter 7) aur closed testing track dono clean pass hue hain aur changes well-covered hain, confidence zyada hota hai fast rollout ke liye. Native vs OTA-fixable — agar koi bug OTA update (EAS Update, Chapter 12) se turant fix ho sakta hai bina naye store submission ke, risk tolerance thodi badh sakti hai kyunki rollback fast hai; agar native code change hai jo sirf naye store submission se fix hoga, staged rollout zaroori hai kyunki rollback slow hai. Urgency — agar ek critical security patch hai jo sabko turant chahiye, kabhi kabhi fast 100% rollout justified hota hai risk accept karke, especially jab not-fixing ka risk rollout-risk se zyada ho. Overall main default staged rollout ko rakhta hun, aur sirf specific, justified reasons se 100%-immediate ko choose karta hun, opposite nahi.

4. What's the actual difference between what EAS Submit automates and what still requires manual App Store Connect / Play Console work?

EAS Submit sirf binary upload aur submission-trigger automate karta hai — ye credentials resolve karta hai, binary ko Transporter API (iOS) ya Play Developer API (Android) ke through upload karta hai, aur (optionally) submission ko "for review" trigger kar sakta hai. Ye automate nahi karta: store listing content (screenshots, description, keywords — jab tak eas metadata explicitly use na karo), App Privacy/Data Safety questionnaire answers, age rating questionnaire, demo account info for reviewers, aur pricing/availability settings. Senior interview mein ye distinction clearly bolna important hai kyunki bahut log galti se assume karte hain "EAS Submit = poora publishing automate ho gaya" — jab actual reality ye hai ki binary pipeline automate hui hai, listing/compliance pipeline largely separate concern hai jo apni khud ki discipline maangti hai.

5. A build got rejected, you fixed the issue, and now resubmission is failing with a duplicate version error — what happened and how do you prevent it?

Dono stores demand karte hain ki har naya build attempt — chahe wo accept hua ho ya reject — ek unique, strictly-increasing version code/build number consume kare. Jab pehli build reject hui, uska version number "used up" ho chuka tha, chahe wo kabhi live na hui ho. Agar aap manually version numbers maintain kar rahe the aur ye fact bhool gaye, resubmission usi purane number ke saath try hogi aur duplicate error dega. Prevention: eas.json mein "autoIncrement": true set karo (Chapter 10 se) — ye guarantee karta hai har build (chahe reject ho ya accept) apna khud ka fresh, unique number leta hai, automatically, bina kisi manual tracking ke.

6. How do you handle the risk of Google Play's post-launch Data Safety re-scanning removing your app without warning?

Sabse pehle iska mental model samajhna zaroori hai: Data Safety declaration ek one-time submission task nahi hai, ye ek ongoing compliance contract hai jo Google periodically re-verify karta hai against actual app binary behavior. Senior mitigation: (1) har baar jab koi naya third-party SDK (analytics, ads, crash reporting, even a new payment SDK) add ya upgrade hota hai, ek explicit checklist item banao "Data Safety form review/update karo" — isko PR template ya release checklist mein hardcode karo, kisi ke memory pe depend mat karo. (2) ideally ek internal audit script rakho jo app ke dependencies scan kare aur flag kare agar koi naya SDK add hua hai jo data collect karta hai (many SDKs ke known data-collection profiles publicly documented hote hain). (3) agar app suddenly removed ho jaaye, fastest recovery path hai Data Safety form ko turant correct karna aur Play Console se resubmit/appeal karna — is downtime ko minimize karne ka best tarika hai ye scenario kabhi hone hi na dena, proactive checklist discipline se.

7. Why might a senior engineer choose to manage store metadata via App Store Connect API / eas metadata instead of the web UI, even though the web UI works fine?

Manual web UI editing kaam to karta hai, lekin ismein kai engineering-discipline gaps hain jo scale pe problem banate hain: no version history — kisne kab kya text change kiya, UI mein track nahi hota; no review process — koi bhi directly production listing edit kar sakta hai bina kisi second pair of eyes ke, jabki wahi text bug-jaisa hi user-facing impact rakhta hai; no reproducibility — agar aap ek naya locale add kar rahe ho aur usi structure ko doosre app ke liye bhi replicate karna hai, UI se copy-paste error-prone hai. Config-as-code approach (store.config.json + eas metadata:push, ya direct API calls CI se) inn sabko solve karta hai — listing changes ab normal code changes ki tarah PR-reviewed, git-blame-able, aur CI-automatable ban jaate hain. Trade-off ye hai ki initial setup cost thoda zyada hai aur schema ki limitations (jaise screenshots abhi bhi largely manual hain) samajhni padti hain.

8. If you had to launch a major redesign (breaking visual/UX change) to production, what release strategy would you use across both platforms?

Ek major redesign high user-visible risk carry karta hai (negative reviews spike ho sakte hain agar users change pasand na karein, chahe koi technical bug na ho), isliye strategy purely technical rollout se aage badhkar hoti hai: (1) pehle ek closed/open testing track (Android) ya TestFlight external testing (iOS) se real user feedback lo, sirf internal QA se nahi. (2) Android pe ek slow staged rollout use karo (jaise 5% → 10% → 25% → 50% → 100%, har step ke beech kuch din ruk ke) taaki agar negative sentiment/uninstall rate spike ho, halt kar sako fast. (3) iOS pe kyunki phased release ka fixed 7-day schedule hai aur control kam hai, main initial launch ko ek "soft announcement" ke saath karta hun (marketing push delay karke) taaki agar early negative feedback aaye, hume respond karne ka time mile before full visibility. (4) dono platforms pe in-app feedback mechanism ya analytics events add karta hun specifically redesign ke reception track karne ke liye (jaise "reverted to old UI" button agar feature-flagged rollback possible ho — OTA update, Chapter 12, se ye flag control ho sakta hai bina naye store submission ke). Overall goal: technical rollout safety aur user sentiment monitoring dono ek saath, kyunki redesign ka risk sirf crash-rate se measure nahi hota.
