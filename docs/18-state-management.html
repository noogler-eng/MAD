State Management — Context Se Aage, Zustand/Redux/Jotai Tak

Chapter 2 mein humne useState aur useContext dekhe the — chhote apps ke liye wo kaafi hain. Lekin jaise-jaise app grow karta hai (zyada screens, zyada shared state, zyada frequently-updating data), ek point aata hai jahan "context + prop drilling" architecture khud ek maintenance aur performance problem ban jaata hai. Ye chapter senior-level state management ka poora landscape cover karta hai — Zustand, Redux Toolkit, Jotai — kab kaunsa choose karna hai, aur unke internals actually kaise kaam karte hain, sirf syntax nahi.

1. Kyun State Management Ek Separate Topic Hai

Ek chhoti app mein useState aur agar zaroorat pade useContext — bas itna hi chahiye hota hai. Ek login screen apna khud ka form state rakh sakta hai, ek toggle apna khud ka boolean rakh sakta hai. Problem tab shuru hoti hai jab state ko multiple, unrelated screens ke beech share karna padta hai — jaise cart items, logged-in user, theme preference, ya ek multi-step form jiska data 4 alag screens mein spread hai.

Prop drilling — pehla symptom

Agar tumhe App se 5 levels neeche ek component tak ek value pahunchani hai, aur beech ke saare 4 components ko sirf isliye us prop ko accept + forward karna padta hai kyunki wo bhi render tree mein beech mein baithe hain — yehi prop drilling hai. Ye components ko unnecessarily coupled banata hai (beech wale components ko ek prop ki "knowledge" honi padti hai jo unhe khud kabhi use hi nahi karni), aur refactoring painful ho jaata hai.

Single large Context — dusra symptom (recap ch.2)

Chapter 2 mein humne dekha tha ki Context iska "official" fix hai — lekin ek naya trap hai ek hi bade Context mein sab kuch daal dena (user, theme, cart, notifications — sab ek object mein). Jab is Context ki value change hoti hai (chahe sirf ek field badla ho), har consumer re-render hota hai, chahe usne us specific field ko read kiya ho ya nahi — kyunki Context ka re-render model "value reference badli, sab consumers ko notify karo" hai, field-level granularity nahi hai. Ch.2 mein humne iska fix "Context splitting" dekha tha (alag-alag Context per concern) — yahan hum us limitation ko ek level upar le jaake dekhte hain: jab splitting bhi kaafi na pade.

Teesra symptom — predictability aur debuggability

Jab state kaafi saare jagah se update ho sakta hai (multiple screens, multiple event handlers), ek genuine production bug track karna mushkil ho jaata hai: "ye value achanak undefined kaise ho gayi?" Iska answer dhoondhne ke liye tumhe poori codebase mein har jagah dhoondhna padta hai jahan se wo state update ho sakta hai. Dedicated state libraries (Zustand/Redux/Jotai) is problem ko solve karte hain centralizing state updates ek predictable, traceable pattern mein — kaunsi action state ko kaise badalti hai, ye ek jagah se clearly dikhta hai (especially Redux DevTools ke saath, jo har state change ko time-travel-debuggable banata hai).

🧠 Senior Dev Note

State management library "add" karna koi default best-practice nahi hai — ye ek trade-off hai (extra dependency, thodi learning curve, thoda boilerplate) jo tabhi worth hota hai jab prop drilling/Context-based approach genuinely pain de raha ho. Ek chhoti app mein Redux daalna over-engineering hai; ek 50-screen app mein sirf Context pe rely karna under-engineering hai. Section 6 ka decision framework isi judgment ko structure karta hai.

2. React Context — When It's Enough, When It's Not

Context ek built-in React feature hai — koi extra dependency nahi chahiye, aur genuinely sahi tool hai kuch specific cases ke liye. Senior-level decision ye hai: Context ka use-case identify karna seekho, na ki "Context bad hai, hamesha library use karo" jaisa blanket rule follow karna.

Context achha fit hai jab:

  • Value rarely update hoti hai — jaise theme (light/dark), locale (language), ya logged-in user object jo login/logout pe hi change hota hai, per-keystroke nahi.
  • Value app-wide hai — matlab bahut saare, unrelated components isse read karte hain, isliye ek single Provider poore tree ke top pe rakhna natural hai.
  • Tumhe koi extra dependency nahi chahiye — chhote projects, prototypes, ya jahan bundle size ek genuine constraint hai (jaise ek super lightweight widget/SDK).

Context weak fit hai jab:

  • State frequently update hota hai — jaise ek text input ki value, scroll position, ya real-time data (chat messages, live cursor position). Har update pe poore subtree ka re-render trigger hona (Context ka default behavior) yahan visible performance problem ban jaata hai.
  • Bahut saare unrelated consumers ko state ke alag-alag slices selectively subscribe karna hai — jaise ek app mein 20 components hain jo ek bade store se sirf apna-apna ek field padhte hain. Context isme "sab ya kuch nahi" model deta hai (poori Context value badli ya nahi), field-level selective subscription ke liye designed nahi hai.
  • Tumhe state ko component tree ke bahar se bhi read/update karna ho (jaise ek utility function mein, ya ek non-component module mein) — Context sirf render tree ke andar accessible hota hai (useContext hook ke through), jabki Zustand jaisa store kahin se bhi (store.getState()) access ho sakta hai.
💡 Quick Tip — Mental Shortcut

Poochho khud se: "Kya ye value din mein kuch hi baar badalti hai (login, theme toggle), ya har second multiple baar (typing, animation, live data)?" Pehla case Context, doosra case ek dedicated store (Zustand/Redux/Jotai) — yahi sabse fast senior heuristic hai.

3. Zustand Deep-Dive

Zustand (German word for "state") React Native community mein senior devs ka favorite banta ja raha hai — wajah simple hai: minimal boilerplate, koi <Provider> wrap karne ki zaroorat nahi, aur out-of-the-box selector-based subscriptions jo unnecessary re-renders ko automatically avoid karti hain, bina extra memoization code likhe.

Kyun no Provider chahiye

Zustand internally store ko ek module-level variable (external to React tree) mein rakhta hai, React state mein nahi. Ye store apna khud ka subscription system rakhta hai — jab set() call hoti hai, Zustand sirf un components ko notify karta hai jinhone specific slice subscribe kiya tha (via selector function), poore tree ko re-render trigger karne ke bajaye ek Context value change karke. Isi wajah se koi Provider tree mein wrap karne ki zaroorat nahi — store khud independently exist karta hai, components sirf ek hook se usse "connect" hote hain.

Installation aur store banana

terminal — install
npx expo install zustand # Zustand ka core package install kar rahe hain, RN/Expo ke saath compatible
store/useCartStore.ts
import { create } from "zustand"; // Zustand ka main function — isi se store banate hain

type CartItem = { id: string; name: string; price: number; qty: number }; // ek cart item ka shape

type CartState = { // poore store ka shape — state fields + actions dono isi type mein
  items: CartItem[]; // cart mein currently kaunse items hain
  addItem: (item: CartItem) => void; // naya item cart mein add karne ka action
  removeItem: (id: string) => void; // id se item remove karne ka action
  clearCart: () => void; // poora cart empty karne ka action
  totalPrice: () => number; // derived value — total price compute karne ka helper (state mein store nahi karte, section 8/advanced dekho)
};

export const useCartStore = create<CartState>((set, get) => ({ // create() ek hook return karta hai jo components use karenge; set = state update karne ka function, get = current state read karne ka function
  items: [], // initial state — khaali cart se shuru

  addItem: (item) => set((state) => ({ // set ek updater function accept karta hai, jaise useState ka functional update
    items: [...state.items, item], // immutably naya array banaya, purane items + naya item
  })), // closing addItem

  removeItem: (id) => set((state) => ({ // remove bhi similarly immutable update hai
    items: state.items.filter((i) => i.id !== id), // matching id wala item filter out kiya, naya array return hua
  })), // closing removeItem

  clearCart: () => set({ items: [] }), // object update — updater function ke bina bhi set() seedha partial state accept karta hai

  totalPrice: () => get().items.reduce((sum, i) => sum + i.price * i.qty, 0), // get() se current state padha, total compute kiya — ye state mein store NAHI hota, on-demand calculate hota hai
})); // create() call close, hook export ho gaya

Component mein use karna — selector-based subscription

Yahan sabse important senior detail hai: store ko poora destructure mat karo agar sirf ek field chahiye — selector function pass karo taaki component sirf us specific slice ke change pe re-render ho.

components/CartBadge.tsx
import { Text } from "react-native"; // UI primitive import kiya
import { useCartStore } from "../store/useCartStore"; // hamara Zustand store hook import kiya

function CartBadge() {
  // SELECTOR PATTERN: sirf items.length subscribe kiya, poora items array nahi — component sirf
  // tab re-render hoga jab length actually badlega, kisi item ki price update hone pe nahi
  const itemCount = useCartStore((state) => state.items.length); // selector function — state se sirf ek derived number nikaala

  return <Text>{itemCount} items in cart</Text>; // count render kar diya
}

export default CartBadge; // export kiya reuse ke liye
components/AddToCartButton.tsx
import { Button } from "react-native"; // UI primitive
import { useCartStore } from "../store/useCartStore"; // store hook import

function AddToCartButton({ product }: { product: { id: string; name: string; price: number } }) {
  // yahan sirf addItem action chahiye, koi state field nahi — actions stable reference hoti hain,
  // isliye ye selector kabhi re-render trigger nahi karega jab tak store khud recreate na ho
  const addItem = useCartStore((state) => state.addItem); // sirf action function ko select kiya

  return (
    <Button
      title="Add to Cart"
      onPress={() => addItem({ ...product, qty: 1 })} // click pe store action call ki, qty default 1
    />
  );
}

export default AddToCartButton; // export kiya
🧠 Senior Dev Note — Actions Store Ke Andar Hi Kyun

Notice karo addItem/removeItem functions store definition ke andar define hue hain (component ke andar nahi). Ye Zustand ka recommended pattern hai — state aur uski update-logic dono ek hi jagah colocated rehte hain, jisse koi bhi component sirf action call karta hai, business logic duplicate nahi hoti alag-alag components mein. Ye conceptually Redux ke reducer pattern jaisa hi hai, bas kaafi kam boilerplate ke saath.

4. Redux Toolkit Deep-Dive

Zustand jitna simple hone ke baad bhi, Redux Toolkit (RTK) — jo modern "official" Redux hai — bahut saari large-scale production apps mein still sahi choice hai. Iski wajah samajhna zaroori hai, kyunki "Redux purana/verbose hai" jaisa oversimplified take senior interviews mein weak jawaab lagta hai.

Redux Toolkit still sahi choice kab hai

  • Large teams — Redux ka strict, opinionated pattern (actions → reducers → store, sab ek predictable shape mein) large teams mein consistency enforce karta hai. Naya developer bhi codebase mein aake turant pattern samajh jaata hai, kyunki "Redux way" ek hi hai, Zustand mein flexibility zyada hone ki wajah se har team apna alag convention bana sakti hai.
  • Complex state graphs — jab bahut saari entities hain jo ek-doosre se related hain (users, posts, comments, likes — sab normalized state chahte hain), Redux ka ecosystem (normalizr, RTK ke createEntityAdapter) isko structured way se handle karta hai.
  • RTK Query — Redux Toolkit ka built-in data-fetching + caching layer, jo server-state (API se aane wala data) ko automatically cache, invalidate, aur refetch karta hai — bina manual useEffect + useState fetch logic likhe (section advanced deep-dive mein isko TanStack Query se compare karenge).
  • Redux DevTools — time-travel debugging — har single state change ek dispatched "action" ke through hoti hai, jo DevTools mein ek timeline ki tarah dikhti hai. Tum kisi bhi purani action pe "jump" kar sakte ho aur dekh sakte ho state us waqt kaisi thi — ye debugging superpower hai jo complex bugs (jaise "state kis sequence of actions se is corrupt state mein pahuncha") reproduce karne mein directly help karta hai.

Internal mental model — single store + pure reducers

Redux ka core idea hai: ek hi global store, aur state ko badalne ka sirf ek hi tareeka — ek action dispatch karo, aur ek pure reducer function purane state + action lekar naya state return karta hai ((state, action) => newState). "Pure" ka matlab hai reducer koi side-effect nahi karta aur same input se hamesha same output deta hai — is guarantee ki wajah se Redux DevTools time-travel possible hai (kyunki kisi bhi point pe state ko deterministically replay kiya ja sakta hai), aur predictable state transitions milte hain — koi bhi state change ek traceable action se aata hai, ad-hoc random mutation se nahi.

Installation aur ek slice banana

terminal — install
npx expo install @reduxjs/toolkit react-redux # RTK core + React bindings, dono chahiye hote hain
store/cartSlice.ts
import { createSlice, PayloadAction } from "@reduxjs/toolkit"; // createSlice = reducer+actions ek saath generate karne wala helper; PayloadAction = action ka TS type

type CartItem = { id: string; name: string; price: number; qty: number }; // ek cart item ka shape
type CartState = { items: CartItem[] }; // is slice ka state shape

const initialState: CartState = { items: [] }; // initial khaali cart

const cartSlice = createSlice({ // slice = ek feature ka state + reducers + auto-generated actions
  name: "cart", // slice ka naam, action types mein prefix ki tarah use hota hai (e.g. "cart/addItem")
  initialState, // upar define kiya hua starting state
  reducers: { // har key ek reducer function hai jo automatically ek action creator bhi generate karti hai
    addItem: (state, action: PayloadAction<CartItem>) => {
      // RTK Immer use karta hai internally — yahan "state.items.push" DIRECT MUTATION jaisa dikhta hai
      // lekin Immer isse safely ek naya immutable state mein convert kar deta hai (advanced deep-dive mein detail)
      state.items.push(action.payload); // naya item array mein push kiya (Immer-safe)
    },
    removeItem: (state, action: PayloadAction<string>) => {
      // action.payload yahan item ki id hai
      state.items = state.items.filter((i) => i.id !== action.payload); // matching id wala item hataya, naya array assign kiya
    },
    clearCart: (state) => {
      state.items = []; // poora cart empty kar diya
    },
  },
});

export const { addItem, removeItem, clearCart } = cartSlice.actions; // auto-generated action creators export kiye — components inhe dispatch karenge
export default cartSlice.reducer; // reducer function export kiya, store mein register hoga
store/index.ts — store setup
import { configureStore } from "@reduxjs/toolkit"; // RTK ka store-creation helper — DevTools + middleware defaults already configured
import cartReducer from "./cartSlice"; // hamara cart slice ka reducer import kiya

export const store = configureStore({ // poora app ka single Redux store bana rahe hain
  reducer: {
    cart: cartReducer, // "cart" key ke neeche cart slice ka state rahega — state.cart.items se access hoga
  },
});

export type RootState = ReturnType<typeof store.getState>; // poore store ka TS type, useSelector mein type-safety ke liye
export type AppDispatch = typeof store.dispatch; // dispatch function ka type, useDispatch mein type-safety ke liye

Ab root component ko store ke saath wrap karna hoga — yahan Redux ko genuinely ek Provider chahiye (Zustand ke opposite):

app/_layout.tsx
import { Provider } from "react-redux"; // react-redux ka Provider component
import { store } from "../store"; // hamara configured store
import { Stack } from "expo-router"; // Expo Router ka navigator

function RootLayout() {
  return (
    <Provider store={store}> // poore app tree ko store se wrap kiya — ab har component neeche se store access kar sakta hai
      <Stack /> // Expo Router ka navigator, Provider ke andar
    </Provider>
  );
}

export default RootLayout; // export kiya, ye root layout hai

Component mein useSelector aur useDispatch

components/CartScreen.tsx
import { useSelector, useDispatch } from "react-redux"; // hooks — state read karne ke liye aur actions dispatch karne ke liye
import { View, Text, Button, FlatList } from "react-native"; // UI primitives
import { removeItem } from "../store/cartSlice"; // action creator import kiya
import type { RootState, AppDispatch } from "../store"; // type-safety ke liye types import kiye

function CartScreen() {
  // SELECTOR: sirf state.cart.items nikaala poore store se — component sirf tab re-render hoga jab
  // ye specific slice reference change ho (Redux shallow-equality check karta hai)
  const items = useSelector((state: RootState) => state.cart.items); // selector function, RootState type se type-safe
  const dispatch = useDispatch<AppDispatch>(); // dispatch function nikaala, actions bhejne ke liye

  return (
    <View>
      <FlatList
        data={items}
        keyExtractor={(item) => item.id}
        renderItem={({ item }) => (
          <View>
            <Text>{item.name} — ₹{item.price}</Text>
            <Button
              title="Remove"
              onPress={() => dispatch(removeItem(item.id))} // action creator call ki, uska result dispatch kiya — yahi Redux ka "action" hai
            />
          </View>
        )}
      />
    </View>
  );
}

export default CartScreen; // export kiya

5. Jotai — Atomic State Model

Jotai (Japanese word for "state") ek fundamentally different mental model deta hai — ek bade central store ke bajaye, state ko chhote-chhote independent "atoms" mein todte hain. Har atom apna khud ka piece of state hai, aur components sirf unhi atoms ko subscribe karte hain jo unhe chahiye.

Ye mental model shift kyun matter karta hai

Zustand/Redux mein tumhare paas ek "store object" hota hai jisme saara related state ek saath rehta hai, aur selector functions use karke tum granularity manually manage karte ho (jaisa section 3/4 mein dikha). Jotai isse invert kar deta hai — granularity by default hai, kyunki har atom apne aap mein ek independent, isolated subscription unit hai. Iska matlab agar ek component sirf ek atom read karta hai, wo sirf tabhi re-render hoga jab exact wahi atom change ho — bina kisi selector function likhe, kyunki architecture khud hi fine-grained hai.

Ye especially achha fit hai jab tumhare paas derived/computed state bahut zyada ho — Jotai mein ek atom directly doosre atoms se "compute" ho sakta hai, aur Jotai automatically track karta hai ki kaunse atoms pe depend karta hai, bilkul React ke apne dependency-tracking jaisa (spreadsheet cells ki tarah socho — ek cell doosre cell se formula se derive hota hai, aur base cell change hote hi automatically recompute hota hai).

Installation aur basic example

terminal — install
npx expo install jotai # Jotai ka core package, koi extra peer dependency zaroori nahi
store/cartAtoms.ts
import { atom } from "jotai"; // atom() function se hi ek naya independent state unit banta hai

type CartItem = { id: string; name: string; price: number; qty: number }; // item ka shape

export const cartItemsAtom = atom<CartItem[]>([]); // PRIMITIVE atom — ek independent piece of state, initial value khaali array

// DERIVED atom — koi naya state store nahi ho raha, ye sirf cartItemsAtom se compute hota hai
export const totalPriceAtom = atom((get) => { // read-only derived atom, get() se dusre atoms padhte hain
  const items = get(cartItemsAtom); // cartItemsAtom ki current value nikaali — Jotai automatically dependency track karta hai
  return items.reduce((sum, i) => sum + i.price * i.qty, 0); // total compute kiya — jab bhi cartItemsAtom badlega, ye automatically recompute hoga
}); // closing totalPriceAtom

// WRITE-ONLY derived atom — state change karne ka "action" jaisa pattern, Zustand ki action jaisa
export const addItemAtom = atom(
  null, // pehla argument null = ye atom khud kuch "read" nahi karta, sirf write karta hai
  (get, set, newItem: CartItem) => { // set function state update karne ke liye, get current values padhne ke liye
    const current = get(cartItemsAtom); // current items nikaale
    set(cartItemsAtom, [...current, newItem]); // naya immutable array set kiya cartItemsAtom mein
  }
); // closing addItemAtom
components/CartTotal.tsx
import { useAtomValue, useSetAtom } from "jotai"; // useAtomValue = sirf padhne ke liye, useSetAtom = sirf likhne ke liye (read/write ko decouple karta hai)
import { Text, Button } from "react-native"; // UI primitives
import { totalPriceAtom, addItemAtom } from "../store/cartAtoms"; // atoms import kiye

function CartTotal() {
  // ye component SIRF totalPriceAtom subscribe karta hai — agar koi doosra atom app mein badle,
  // ye component bilkul re-render nahi hoga, sirf jab derived total actually badlega tab hoga
  const total = useAtomValue(totalPriceAtom); // derived atom ki current computed value padhi
  const addItem = useSetAtom(addItemAtom); // write-only atom ka setter function nikaala, value read nahi ki (kyunki chahiye hi nahi)

  return (
    <>
      <Text>Total: ₹{total}</Text> // computed total render kiya
      <Button
        title="Add Sample Item"
        onPress={() => addItem({ id: "1", name: "Item", price: 100, qty: 1 })} // write-atom call kiya naya item ke saath
      />
    </>
  );
}

export default CartTotal; // export kiya
💡 Quick Tip

useAtomValue (sirf read) aur useSetAtom (sirf write) ka split intentional hai — agar ek component sirf state update karta hai (jaise upar wala Add button), usse value read karne ki zaroorat hi nahi, isliye useSetAtom use karne se wo component atom ki value change hone pe bhi re-render nahi hoga — sirf action-trigger karne ki responsibility hai usme.

6. Senior Decision Framework: Which One, When

Ab in teeno (+ Context) ko ek comparison table mein daal ke ek clear decision logic banate hain:

DimensionContextZustandRedux ToolkitJotai
Boilerplate Low (built-in) Very low Medium (slices, store setup, Provider) Low (atoms are tiny)
Learning curve Trivial (core React) Very easy Medium-high (actions, reducers, middleware concepts) Easy, but atomic mental model needs a mindset shift
DevTools None dedicated Basic (Redux DevTools support via middleware) Excellent — full time-travel debugging Basic (Jotai DevTools available, less mature)
Re-render control Manual (Context splitting) Built-in via selectors Built-in via useSelector Built-in by design (per-atom)
Best for Rarely-changing app-wide values (theme, auth, locale) Small-to-mid apps, solo/small teams, fast iteration Large teams, complex async flows, need RTK Query caching Fine-grained reactivity, derived-state-heavy UIs
🧠 Senior Recommendation Logic

Solo dev/small team, simple-to-medium app → Zustand ya Context (Zustand jaise hi state frequently update hone lage ya cross-screen sharing badhe). Large team, complex async flows, aur server-state caching genuinely chahiye (RTK Query ka caching/invalidation layer) → Redux Toolkit — iski strict conventions large team consistency ke liye directly help karti hain. Fine-grained atomic reactivity, bahut saara derived/computed state (dashboards, forms with interdependent fields, spreadsheet-jaisi UIs) → Jotai. Aur agar state genuinely rarely badalta hai aur app-wide hai (theme, locale, auth user) → plain Context, kisi library ki zaroorat hi nahi.

7. Persisting State — MMKV and AsyncStorage

Ab tak jo state dekha wo sab in-memory tha — app restart hote hi gayab ho jaata hai. Real apps mein tumhe kai cheezein persist karni padti hain: user preferences (dark mode toggle), auth tokens, cached data jo offline-first feel deta hai. Iske liye do main options hain RN mein.

MMKV vs AsyncStorage

Aspectreact-native-mmkvAsyncStorage
Execution model Synchronous — ek native key-value store (Tencent ka MMKV, jo memory-mapped file use karta hai) directly JS thread se read/write hoti hai, koi Promise/await zaroorat nahi Asynchronous — har operation ek Promise return karta hai, JS aur native ke beech bridge cross karna padta hai har call pe
Speed Bahut fast — benchmarks mein AsyncStorage se roughly 30x tak faster reported hota hai, kyunki memory-mapped file ka direct access hai, serialization overhead bhi kam hai Slower — har read/write bridge round-trip + JSON serialization involve karta hai
Setup friction Native module hai — Expo mein expo-dev-client/prebuild chahiye (Expo Go mein kaam nahi karega, kyunki custom native code hai) Zero native-linking friction — bahut simple install, Expo Go mein bhi chalta hai

Zustand store ko MMKV ke saath persist karna

Zustand ka built-in persist middleware kisi bhi storage engine ko "storage adapter" ki tarah accept karta hai — hum MMKV ko wrap karke pass karenge.

terminal — install
npx expo install react-native-mmkv # MMKV native module install kiya
npx expo install zustand # Zustand already install ho toh skip, persist middleware isi package ke andar hai
store/usePreferencesStore.ts
import { create } from "zustand"; // Zustand ka main function
import { persist, createJSONStorage, StateStorage } from "zustand/middleware"; // persist middleware + storage adapter helpers
import { MMKV } from "react-native-mmkv"; // MMKV native storage engine

const mmkv = new MMKV(); // ek MMKV instance banaya — ye default storage "id" use karega

// Zustand ka persist middleware ek StateStorage interface expect karta hai (getItem/setItem/removeItem,
// sab STRING-based). MMKV synchronous hai, isliye hum in functions ko plain (non-async) rakh sakte hain.
const mmkvStorage: StateStorage = {
  setItem: (name, value) => {
    mmkv.set(name, value); // MMKV mein key-value synchronously likh diya, koi await nahi chahiye
  },
  getItem: (name) => {
    const value = mmkv.getString(name); // MMKV se string synchronously padhi
    return value ?? null; // agar key exist nahi karti, undefined aata hai — usse null mein normalize kiya (interface ki requirement)
  },
  removeItem: (name) => {
    mmkv.delete(name); // key ko MMKV se hata diya
  },
};

type PreferencesState = { // store ka shape
  isDarkMode: boolean; // dark mode on/off
  toggleDarkMode: () => void; // toggle karne ka action
};

export const usePreferencesStore = create<PreferencesState>()( // create ke baad extra () — jab middleware wrap karna ho, ye TS ke liye curry syntax hai
  persist( // persist middleware se store ko wrap kiya
    (set) => ({ // actual store definition, jaisa pehle dekha tha
      isDarkMode: false, // default light mode
      toggleDarkMode: () => set((state) => ({ isDarkMode: !state.isDarkMode })), // current value flip kiya
    }),
    {
      name: "preferences-storage", // storage mein is store ka data kis key naam se save hoga
      storage: createJSONStorage(() => mmkvStorage), // hamara MMKV adapter pass kiya, createJSONStorage isse JSON serialize/deserialize karna sikhata hai
    }
  )
); // create() call close

Yahan se aage app restart hone pe bhi isDarkMode automatically MMKV se rehydrate ho jaayega — koi manual load/save code likhne ki zaroorat nahi, persist middleware ye poora lifecycle khud handle karta hai (app start pe read, har set() ke baad write).

💡 AsyncStorage Version

Agar Expo Go mein chalana hai (MMKV native module ki wajah se possible nahi), sirf storage: createJSONStorage(() => AsyncStorage) use karo — AsyncStorage already Zustand ke StateStorage interface ko match karta hai (uska API bhi getItem/setItem/ removeItem hai), toh koi wrapper likhne ki zaroorat nahi padti jaisa MMKV ke liye padi.

8. Selector Patterns and Preventing Re-renders

Selectors ka poora point ek hi core idea hai: component sirf us slice ko subscribe kare jo wo actually use kar raha hai, poora store nahi. Ye concept humne section 3/4/5 mein bikhra hua dekha, ab isse ek concrete before/after example se consolidate karte hain.

Before — over-subscribing (bad pattern)

❌ over-subscribed component — poore store pe re-render hoga
function UserGreeting() {
  // POORA store object destructure kar liya — user.name sirf chahiye tha, lekin store ke
  // KISI BHI field (jaise cart.items, notifications, preferences) badalne pe bhi ye component
  // re-render hoga, kyunki poora state object select kiya, ek specific slice nahi
  const state = useCartStore((s) => s); // ⚠️ poora state return karne wala selector — kabhi mat likho aisa

  return <Text>Hi, {state.userName}</Text>; // sirf userName use ho raha hai, baaki poora state waste subscribe hua
}

After — narrow selection (good pattern)

✅ narrowly-selected component — sirf relevant field pe re-render hoga
function UserGreeting() {
  // SIRF userName field select kiya — Zustand internally is value ka pichla aur naya value
  // compare karta hai (Object.is se), aur sirf tabhi re-render trigger karta hai jab ye specific
  // value actually badle — cart items badalne se is component ka koi lena-dena nahi
  const userName = useCartStore((s) => s.userName); // ✅ narrow selector — sirf ek primitive field return kiya

  return <Text>Hi, {userName}</Text>; // same output, lekin re-render surface area bahut chhota hai
}

Memoized selectors — Reselect (Redux) aur Zustand ke built-in selectors

Jab selector koi derived, computed value return karta hai (jaise ek filtered/sorted array), naive selector har render pe ek naya array/object bana sakta hai (chahe underlying data same ho) — aur ye naya reference automatically re-render trigger kar deta hai, kyunki reference equality check fail ho jaata hai. Iska fix memoization hai — same input pe same reference wapas do.

  • Redux mein: Reselect library ka createSelector use karte hain — ye input selectors ke result ko cache karta hai, aur sirf tabhi recompute karta hai jab input actually badla ho, warna cached reference wapas deta hai.
  • Zustand mein: selector ko simple/primitive rakho jab possible ho, ya derived arrays ke liye useMemo ka use karo component ke andar, ya Zustand ke useShallow helper se shallow-equality comparison use karo (jab selector ek object/array return karta hai jiske fields individually same hain, lekin reference alag hai).

9. Real-World Gotchas

⚠️ State ko Directly Mutate Karna (bina store update mechanism ke)

Zustand/plain-object state ke saath ek bahut common bug hai direct mutation — jaise useCartStore.getState().items.push(newItem) likh dena set() ke bina. Ye "kaam kar jaata hai" JS level pe (array actually mutate ho jaata hai), lekin React ko iski koi khabar nahi milti — kyunki React/Zustand re-render trigger karne ke liye reference change detect karte hain, aur direct mutation reference ko same rakhta hai. Result: state internally badal gaya, lekin UI stale reh jaata hai jab tak koi unrelated re-render na ho jaaye. Hamesha set() ke through hi update karo, jo naya reference banata hai.

Redux Toolkit is problem se safe hai by design — RTK ke andar Immer library baked-in hai, jisse tum reducers mein state.items.push(...) jaisa "mutating" syntax likh sakte ho, lekin Immer under the hood ek naya immutable state tree generate karta hai (via a proxy-based diffing mechanism), reference correctly badalti hai. Ye RTK ka ek genuine ergonomic advantage hai plain Zustand ke against.

⚠️ Non-Serializable Values Ko Persisted Store Mein Rakhna

Agar tum apne persisted store (section 7) mein koi function, class instance, ya Map/Set jaisi non-plain-JSON value store karte ho, persist middleware jab isse JSON string mein serialize karega (disk pe likhne ke liye), ye values silently corrupt ho jaayengi ya poori tarah gayab ho jaayengi — kyunki JSON.stringify functions ko drop kar deta hai aur class instances ko plain objects mein flatten kar deta hai. Jab app restart hoke rehydrate karega, tumhe wo class methods ya functions wapas nahi milenge, sirf plain data milega — agar code un methods pe depend karta hai, runtime crash ho sakta hai. Rule: sirf plain, JSON-serializable data (`string`/`number`/`boolean`/ plain object/array) hi persisted store mein rakho.

⚠️ Har Cheez Global State Banana (Senior Anti-Pattern)

Ek bahut common junior-to-mid-level mistake ye hai ki har state ko global store mein daal dena — chahe wo sirf ek form ke andar ek input field ho, ya ek modal ka open/close boolean jo sirf ek hi component tree mein use hota hai. Isse do problems hoti hain: (1) unnecessary coupling — poori app ko ab us global store ki "existence" ka pata hona padta hai kisi aisi cheez ke liye jo genuinely local thi; (2) debugging harder ho jaata hai — global store mein jitne zyada unrelated fields honge, utna hi mushkil hai samajhna ki koi specific field kis liye/kaha use ho raha hai. Senior heuristic simple hai: agar state sirf ek component (ya uske direct children) tak simit hai aur kisi aur screen/component ko iski zaroorat nahi, plain useState hi sahi choice hai — global store mein daalna unnecessary indirection hai.

10. Advanced Deep-Dive — Beyond the Basics

Ab tak humne "kaunsi library kab use karo" dekha. Ye section teen aur advanced concepts cover karta hai jo genuinely complex apps mein zaroori ban jaate hain — invalid states ko structurally prevent karna, server-state ko client-state se properly separate karna, aur derived state ko sahi tarike se model karna.

10.1 State Machines with XState — jab simple store kaafi nahi hai

Ek plain store (Zustand/Redux) mein state ka koi bhi combination technically possible hota hai — jaise agar tumhare paas isLoading, isError, aur data teen separate booleans/fields hain, kuch bhi tumhe isLoading: true aur isError: true dono ek saath set hone se nahi rokta — jo logically ek invalid state hai (ek operation loading bhi ho aur error bhi ho, ek saath, doesn't make sense). Complex multi-step flows mein (checkout, onboarding wizard, multi-stage upload) aisi invalid state combinations bugs ka bahut bada source hote hain.

XState is problem ko finite state machines se solve karta hai — state ko ek "boolean soup" ki jagah ek explicit, named set of states (jaise "idle", "loading", "success", "error") ke roop mein model karte hain, aur sirf explicitly-defined transitions (events) hi ek state se doosre state mein move kar sakte hain. Isse invalid combinations structurally impossible ho jaate hain — machine sirf ek state mein ho sakta hai kisi bhi waqt, aur sirf wahi transitions allowed hain jo tumne explicitly define ki hain (jaise "loading" se sirf "success" ya "error" pe ja sakte ho, seedha "idle" pe wapas nahi ja sakte bina kisi defined event ke).

Checkout flow jaisa multi-step process (address → payment → review → confirm) ek classic XState use-case hai — har step ka apna explicit state hai, aur "user payment step pe hai lekin address abhi fill nahi hui" jaisi invalid combination machine definition mein hi impossible bana di jaati hai, runtime check se nahi.

10.2 RTK Query vs TanStack Query — Client State vs Server State

Ye ek core senior-level architectural distinction hai jo bahut mid-level devs miss karte hain: client state (UI state jaise "is this modal open", form input values, theme) aur server state (data jo kisi API se fetch hui hai — users list, product catalog) do fundamentally different cheezein hain, chahe dono "state" hi kehlaate hon.

  • Client state — tumhare paas hi "owned" hai, sirf tumhare app ke andar exist karta hai, aur tum jab chaho update kar sakte ho.
  • Server state — kisi aur system (backend) ka "owned" hai, tumhare paas sirf ek snapshot/cache hai jo stale ho sakta hai (koi aur user/device ne backend pe data change kar diya ho), jisko refetch/invalidate/re-sync karna padta hai, aur jo async fetch lifecycle (loading/error/success, retries, background refetch) ke saath aata hai.

Iss wajah se server state ko ek plain Zustand/Redux store mein "seedha daal dena" (jaise ek useEffect se fetch karke setUsers(data) karna) ek common architectural mistake hai — kyunki tumhe manually cache invalidation, staleness tracking, retry logic, deduplication (agar 2 components same data ek saath fetch kar rahe hain) sab khud implement karna padta hai. Yehi gap RTK Query (Redux Toolkit ke andar built-in) aur TanStack Query (standalone, framework-agnostic) bharte hain — dono hi ek dedicated caching layer dete hain jo automatically stale data ko background mein refetch karta hai, same query ko multiple components se dedupe karta hai, aur loading/error states ko ek consistent hook API (useQuery) ke through expose karta hai.

Senior pattern: client state ke liye Zustand/Redux/Jotai, server state ke liye RTK Query/ TanStack Query — dono ko alag rakho, ek dusre ka substitute mat banao. RTK Query already Redux Toolkit ke andar hai, isliye agar tum Redux use kar rahe ho, RTK Query natural choice hai; agar tum Zustand/Jotai use kar rahe ho (jo server-state caching provide nahi karte), TanStack Query ko saath mein add karna standard practice hai.

10.3 Derived/Computed State — mat store karo, compute karo

Section 3 ke Zustand example mein totalPrice() ek function tha jo on-demand compute hota tha (get().items.reduce(...)), state field ki tarah store nahi hua tha. Ye intentional tha — agar tum totalPrice ko ek separate state field ki tarah store karte (aur har addItem/removeItem ke saath manually update karte), do independent values create ho jaati hain jo out of sync ho sakti hain agar kahin bhi update logic miss ho jaaye (jaise ek naya action add kiya jo items badalta hai lekin totalPrice update karna bhool gaya).

Senior principle: derived values ko store mat karo, unhe compute karo (memoized selector se, jaisa Reselect/Jotai derived atoms/Zustand getter functions section 8 mein dikhaya) — is tarah sirf ek "source of truth" (raw items array) hoti hai, aur derived value hamesha automatically correct rehti hai kyunki wo directly usi source se calculate ho rahi hai, kabhi manually "sync" nahi karni padti.

11. 🎯 Interview Questions — Senior React Native Developer

Ye questions state management ke around senior/staff-level RN interviews mein common hain — internals, trade-offs, "why", aur scenario-based sab mix hai.

Q1. Zustand bina Provider/Context ke re-renders ko selectively kaise avoid karta hai?

Zustand ka store ek module-level (React tree ke bahar) mutable object hota hai jo apna khud ka pub-sub subscription system rakhta hai. Jab koi component useStore(selector) call karta hai, Zustand internally us selector ko run karke ek value nikaalta hai aur usse subscribe kar leta hai. Jab bhi set() call hoti hai, Zustand naye state pe wahi selector dobara run karta hai aur naye result ko purane result se Object.is se compare karta hai — sirf tabhi component ko re-render trigger karta hai jab ye comparison false aaye (matlab value genuinely badli). Context ka default model iske opposite hai — Context Provider ki value badalte hi saare consumers (jo useContext call karte hain) re-render hote hain, chahe unhone kisi specific field ko select kiya ho ya nahi, kyunki React Context field-level granularity natively support nahi karta.

Q2. Ek naye project ke liye, Zustand ki simplicity ke bawajood, kab Redux Toolkit choose karoge?

Main RTK choose karunga jab (a) team bada hai aur strict, uniform conventions genuinely help karengi onboarding aur code-review consistency mein — Zustand ki flexibility large teams mein har developer ko apna alag pattern banane deti hai, jo drift create kar sakti hai; (b) app mein genuinely complex server-state caching zaroorat hai jo RTK Query provide karta hai out-of-the-box (agar main Zustand use karta toh separately TanStack Query add karna padta, jo bhi valid hai lekin ek extra dependency decision hai); (c) time-travel debugging/Redux DevTools ek genuine requirement hai (jaise bahut complex state transitions wale bugs debug karne ke liye); ya (d) organization mein already Redux expertise/tooling exist karta hai aur naya pattern introduce karne ka cost > benefit hai. Chhote-medium apps ke liye, jahan ye factors apply nahi hote, Zustand ki lower boilerplate genuinely faster iteration deti hai.

Q3. Server-state aur client-state ko ek hi global store mein mix karna anti-pattern kyun mana jaata hai?

Dono ka fundamentally different lifecycle aur ownership model hai (section advanced deep-dive 10.2). Client state tumhare app ke andar hi "born" hota hai aur tumhare control mein hai — ek boolean flip karna bas ek synchronous update hai. Server state ek external system ka snapshot hai jo independently stale ho sakta hai — agar tum isse ek plain store mein manually daal dete ho (via ek-baar-fetch- karke-setState), tumhe khud implement karna padega: staleness detection, background refetching, retry-on- failure, request deduplication (agar 2 components same data chahte hain), aur cache invalidation jab related data (jaise ek mutation ke baad) change ho. Ye sab ek dedicated data-fetching library (RTK Query/ TanStack Query) already solve kar chuki hai — inhe reinvent karna, aur unke sath plain client-state ko mix karna, dono concerns ko messy bana deta hai (jaise "is user list stale hai?" jaisa logic tumhare apne UI-state reducers mein bikhar jaata hai).

Q4. Ek component har store update pe re-render ho raha hai, jabki usse sirf ek field chahiye — kya galat hai, kaise fix karoge?

Ye classic over-subscription bug hai (section 8). Root cause almost hamesha ye hoti hai ki selector poora state object return kar raha hai (jaise useStore((s) => s), ya destructuring pattern jo internally poori state ko access karta hai), instead of ek specific narrow field/derived-value select karne ke. Fix: selector ko sirf wahi field return karne ke liye narrow karo jo component actually use karta hai (useStore((s) => s.specificField)). Agar selector ek naya object/array return karta hai (jaise ek filter/map ka result), toh additionally memoization chahiye hoga (Reselect Redux ke liye, ya Zustand ke useShallow/component-level useMemo) taaki har render pe naya reference na bane, jo khud ek re-render trigger kar sakta hai chahe underlying data same ho.

Q5. Redux Toolkit "mutating" syntax (state.items.push(...)) allow karta hai jabki Redux ka core principle immutability hai — ye contradiction kaise resolve hota hai?

RTK ke reducers Immer library ke through wrap hote hain. Jab tum reducer ke andar state.items.push(x) likhte ho, actually tum ek Immer Proxy object ke saath interact kar rahe ho, real state object ke saath nahi. Immer in "mutations" ko record karta hai, phir automatically ek naya immutable state tree produce karta hai jisme sirf wahi paths change hue hain jo tumne touch kiye, baaki sab reference-equal rehta hai (structural sharing). Isliye syntax-level pe ye mutation jaisa lagta hai (jo developer ergonomics ke liye achha hai — array/object manipulation ka natural syntax), lekin runtime pe actual result still ek naya, immutable state object hi hai — Redux ka core "state is never mutated directly" guarantee intact rehta hai.

Q6. Jotai ke atomic model mein derived atom kaise "automatically" recompute hota hai jab uski dependency badalti hai — kya ye reactive framework jaisa hai?

Haan, conceptually bahut close hai. Jab ek derived atom define hota hai (jaise atom((get) => get(baseAtom) * 2)), Jotai us function ko turant ek baar run karta hai aur track karta hai kaunse atoms uske andar get() se access hue — yehi uski dependency list ban jaati hai (dynamic dependency tracking, spreadsheet formulas jaisa). Jab bhi baseAtom update hota hai, Jotai apne internal dependency graph mein dekhta hai kaunse derived atoms is base atom pe depend karte hain, aur unhi ko selectively invalidate/recompute karta hai — poore app ka koi global "recompute everything" pass nahi chalta. Isi wajah se ye fine-grained hai — sirf directly-affected computed atoms hi kaam karte hain, unrelated atoms untouched rehte hain.

Q7. MMKV synchronous hai aur AsyncStorage asynchronous — ye difference practically kab matter karta hai?

Practically ye tab sabse zyada matter karta hai jab tumhe app launch ke bilkul shuru mein (splash screen khatam hone se pehle) persisted state chahiye ho — jaise "kya user logged in hai" ya "kaunsa theme select tha" — taaki first render hi correct UI ke saath ho, ek flash-of-wrong-state (jaise pehle light theme flash hoke phir dark mode load hona) na dikhe. AsyncStorage ke saath ye read inherently async hai, isliye tumhe ek loading state handle karni padti hai before pehla "real" render. MMKV ke saath, kyunki read synchronous hai, tum store ko module-load-time pe hi synchronously rehydrate kar sakte ho, aur first render already correct state ke saath ho sakta hai. Iske alawa, high-frequency writes (jaise ek analytics buffer jo har event pe disk pe likhta hai) mein MMKV ki speed genuinely measurable difference deti hai — AsyncStorage ke bridge overhead se bottleneck ban sakta hai agar writes bahut frequent hon.

Q8. Ek complex checkout flow (address → payment → review) build kar rahe ho — plain Zustand store ya XState, kaunsa choose karoge aur kyun?

Depends on flow ki complexity aur invalid-state risk pe. Agar steps simple hain aur linear hain (bas ek "currentStep" number/string field hai jo sequentially badalta hai, aur har step independent data collect karta hai), ek plain Zustand store already kaafi hai — XState yahan overkill ho sakta hai. Lekin agar flow mein genuinely complex branching hai (jaise "agar guest checkout hai toh payment step skip nahi ho sakta bina address ke, lekin agar saved card hai toh review step directly ja sakte ho", multiple conditional paths, aur invalid combinations ka real risk hai jo production mein confusing bugs create kar sakti hain), XState ka explicit state machine model use karunga — kyunki wahan invalid state combinations ko runtime checks se prevent karne ke bajaye, machine definition mein hi structurally impossible banana zyada robust hai, especially jab multiple developers is flow ko maintain kar rahe hon aur ek naya edge-case add karte waqt kisi purani invalid-state-prevention check ko accidentally break karne ka risk ho.

Q9. Persisted Zustand store rehydrate hone ke baad expected value nahi de raha — kaise debug karoge?

Systematic order: (1) Check karo kya store mein koi non-serializable value hai (function, class instance, Map/Set) — JSON.stringify aisi values ko silently drop/corrupt kar deta hai (section 9 gotcha), isliye pehle store shape ko purely-JSON-serializable confirm karo. (2) Check karo persist ka name option consistent hai across app versions — agar tumne kabhi store ka shape badla (jaise ek field rename kiya) bina migrate option use kiye, purana persisted data naye shape ke saath mismatch ho sakta hai. (3) Confirm karo storage adapter (MMKV/ AsyncStorage) sahi se initialize ho raha hai — jaise MMKV ka multiple instance/id confusion, ya AsyncStorage ka import path galat hona. (4) Check karo rehydration synchronous assumption kahin galat toh nahi ban rahi — AsyncStorage-backed persist async hota hai, isliye agar app ka pehla render hi persisted value pe depend karta hai bina "has hydrated" state check kiye, tumhe transient default value dikh sakti hai jo baad mein "flip" hoti hai — ye bug nahi, ye expected async behavior hai jise handle karna padta hai (Zustand persist ka onRehydrateStorage callback isi liye use hota hai).

Q10. Ek junior dev ne ek modal ka "isOpen" boolean apne global Zustand store mein daal diya. Ye code review mein kya feedback doge?

Main flag karunga ye as a likely anti-pattern (section 9) — agar modal sirf ek specific screen/component tree ke andar hi open/close hota hai aur koi doosra unrelated component/screen isko control ya read nahi karta, ye state genuinely local hai, global store mein hone ki zaroorat nahi. Global store mein daalne se do downsides hain: (a) poori app ko ab ek aisi state field ki "existence" ka pata hai jo unse related hi nahi hai, jo cognitive overhead badhata hai jab koi naya dev store explore karta hai; (b) agar future mein 2 alag jagah ye hi modal (ya similar naam ka field) use hota hai, naming collision/confusion ka risk hai. Feedback: const [isOpen, setIsOpen] = useState(false) use karo jab tak genuinely proof na ho ki iss state ko kisi doosri screen/component se access/control karna hai — "future mein zaroorat pad sakti hai" premature globalization ka valid reason nahi hai (YAGNI).
