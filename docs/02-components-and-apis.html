1. Core Components Deep-Dive

Chalo sabse pehle ek cheez clear kar lete hain — React Native ke "components" HTML elements nahi hain. Jab tum <View> likhte ho, ye ek JS object return karta hai jo React ke reconciler ko batata hai ki "is jagah ek native view chahiye". Fir React Native ka renderer (Fabric, new architecture mein) us instruction ko actual native UIView (iOS) ya android.view.View (Android) mein convert karta hai. Yehi wajah hai ki RN components web ke divs jaise dikhte hain lekin unke peeche poora native rendering pipeline chal raha hota hai.

View aur Text — sabse basic building blocks

View ek non-scrollable container hai — flexbox ke default rules ke saath (display: flex, flexDirection: column — web se ulta!). Internally ye native side pe ek plain container view bind karta hai jiska koi apna default styling nahi hota (na padding, na border) — jo bhi style dikh raha hai wo tumhare StyleSheet se aa raha hai.

Text thoda special hai — RN mein sirf Text ke andar hi raw string render ho sakti hai. Agar tum View ke andar directly text daaloge to error aayega ("Text strings must be rendered within a <Text> component"). Ye isliye kyunki native text layout (line height, font metrics) iOS/Android pe bahut alag hote hain, aur RN ko explicitly janna padta hai ki kaunsa node "text measurement" wala hai taaki wo Yoga (RN ka flexbox layout engine, C++ mein likha hua) ko sahi measurement de sake.

🧠 Senior Dev Note

Yoga layout engine ek separate C++ library hai jo Facebook ne banayi thi flexbox ko cross-platform consistent banane ke liye. Har render pe RN, JS tree ko shadow tree mein convert karta hai, Yoga us shadow tree pe layout calculate karta hai (measure + layout pass), aur fir wahi computed frames (x, y, width, height) native views ko commit hote hain. Isliye deeply nested Views ka cost sirf "extra native views" nahi hai — Yoga ko unke liye extra layout calculations bhi karni padti hain.

ScrollView vs FlatList vs FlashList — ye asli test hai

Ye ek classic interview question hai aur production mein sabse zyada galat use hone wala pattern bhi. Chalo internals se samajhte hain.

ScrollView apne saare children ko eagerly render karta hai — matlab jitne bhi items tumne diye hain, sab ek saath mount ho jaate hain, chahe screen pe visible ho ya na ho. 20 items ke liye ye bilkul fine hai. Lekin 500 items ke liye ye disaster hai — har item ka native view create hoga, uska layout calculate hoga, uski memory allocate hogi — sab kuch upfront, even before user scroll kare. Isse app ka initial render time bahut badh jaata hai aur memory usage explode ho jata hai.

FlatList is problem ko solve karta hai virtualization (a.k.a windowing) se. Internally FlatList sirf un items ko render karta hai jo current viewport ke andar hain, plus ek chhota sa "overscan" buffer (upar aur neeche thoda extra, taaki fast scroll pe blank gaps na dikhein — ye windowSize prop se control hota hai, default 21, matlab ~10 viewport heights upar aur neeche). Jaise hi user scroll karta hai aur koi item viewport se bahut door chala jaata hai, FlatList uska native view unmount kar deta hai aur naya visible item mount karta hai. Ye sab ek internal VirtualizedList component ke through hota hai jise FlatList wrap karta hai — VirtualizedList hi actual windowing logic maintain karta hai (kaunse indices currently rendered hain, kab recycle karna hai).

ProductList.tsx
import { FlatList, View, Text } from 'react-native';

type Product = {
  id: string;
  title: string;
  price: number;
};

function ProductList({ products }: { products: Product[] }) {
  return (
    <FlatList
      data={products}
      keyExtractor={(item) => item.id}
      renderItem={({ item }) => (
        <View style={{ padding: 12 }}>
          <Text>{item.title}</Text>
        </View>
      )}
      {/* fixed height item => skip measurement pass entirely */}
      getItemLayout={(_data, index) => ({
        length: 56,
        offset: 56 * index,
        index,
      })}
      windowSize={10}
      initialNumToRender={8}
    />
  );
}

FlashList (Shopify ne banaya hai) FlatList ka modern replacement hai jo same virtualization idea pe based hai lekin bahut better perform karta hai. Wajah — FlatList ka biggest bottleneck ye hai ki jab bhi naya item render hota hai, uska measurement hona padta hai (jab tak tum manually getItemLayout na do), aur ye measurement JS thread pe expensive hai. FlashList ek technique use karta hai jise cell recycling kehte hain (jaise Android ka RecyclerView ya iOS ka UITableView karta hai) — matlab jab ek item screen se bahar jata hai, uska native view destroy nahi hota, balki reuse hota hai naye data ke liye. Isse view creation/destruction ka overhead almost zero ho jaata hai. FlashList apne aap average item size ko estimate bhi karta hai (estimatedItemSize) taaki tumhe manually har item ka exact height na dena pade.

ComponentRendering strategyBest for
ScrollViewEager — sab kuch upfront renderShort, fixed lists (< 20 items)
FlatListWindowing/virtualization, view unmount+remountMedium-large lists, default choice
FlashListWindowing + cell recycling (recycler pattern)Large lists, feed-like UIs, perf-critical screens
⚠️ Common Mistake

Log flow mein ScrollView ke andar .map() se list render karna sabse common anti-pattern hai jo naye devs karte hain. Chhote list ke liye chalta hai, lekin as soon as data grows (chat messages, product catalog, feed), app janky ho jaata hai. Agar list scrollable hai aur size unbounded ho sakta hai — FlatList/FlashList use karo, ScrollView nahi.

Pressable vs TouchableOpacity vs old Touchable* APIs

RN ki history mein pehle TouchableHighlight, TouchableOpacity, TouchableWithoutFeedback, aur TouchableNativeFeedback (Android-only ripple) the — har ek apna alag feedback style deta tha but API inconsistent thi, aur inka gesture handling RN ke purane (aur limited) touch responder system pe based tha.

Pressable in sabko replace karne ke liye laaya gaya — ek unified, configurable API jo press state ko as a function expose karta hai (({'{'} pressed {'}'}) => ...), taaki tum khud decide kar sako feedback kaisa dikhna chahiye (opacity change, scale animation, background color) instead of ek fixed built-in behavior lene ke. Internally Pressable, RN ke Pressability API pe based hai jo touch start/move/end/cancel ko zyada precisely handle karta hai — jaise onLongPress, delayLongPress, hit slop (hitSlop), aur press-out-of-bounds detection (agar finger element ke bahar move ho jaaye to press cancel ho jata hai).

PressableExample.tsx
<Pressable
  onPress={handleSubmit}
  hitSlop={{ top: 8, bottom: 8, left: 8, right: 8 }}
  style={({ pressed }) => [
    styles.button,
    pressed && { opacity: 0.7 },
  ]}
>
  <Text>Submit</Text>
</Pressable>
💡 Quick Tip

Naya code likh rahe ho to hamesha Pressable use karo. TouchableOpacity abhi bhi deprecated nahi hai aur legacy codebases mein milega, lekin Meta ka direction clearly Pressable ki taraf hai — future gesture improvements (jaise Gesture Handler ke saath integration) usi pe focus karenge.

Image aur expo-image — caching ka asli game

RN ka built-in Image component basic disk caching karta hai (URL ke basis pe), lekin ye platform ke default HTTP cache pe depend karta hai — jo predictable nahi hai, especially Android pe. Har baar image URL change hone pe ya cache-headers missing hone pe, image dobara download ho sakti hai. Isme koi memory cache bhi nahi hai by default — matlab same image dobara render hone pe bhi kabhi kabhi decode dobara hota hai.

expo-image is problem ko properly solve karta hai. Ye do-level caching implement karta hai — memory cache (already decoded bitmap, instant render) aur disk cache (downloaded file, decode karna padega but network call nahi). Isse scroll karte waqt images "pop-in" nahi karti, aur same image baar baar use hone pe (jaise avatar list mein) network hit hi nahi hota. Ye blurhash placeholders bhi support karta hai — ek compact string (~20-30 chars) jo image ka blurred preview encode karta hai, taaki actual image load hone tak user ko ek smooth blurred version dikhe, blank white box nahi.

Avatar.tsx
import { Image } from 'expo-image';

const blurhash = 'L6PZfSi_.AyE_3t7t7R**0o#DgR4';

function Avatar({ uri }: { uri: string }) {
  return (
    <Image
      source={{ uri }}
      placeholder={{ blurhash }}
      cachePolicy="memory-disk"
      transition={200}
      style={{ width: 48, height: 48, borderRadius: 24 }}
    />
  );
}
🧠 Senior Dev Note

Production apps mein — especially jinme image-heavy feeds hain (e-commerce, social) — expo-image ko default bana do, plain Image se migrate kar do. Ye Facebook ke Yoga-independent native layer (SDWebImage on iOS, Glide on Android) use karta hai jo already battle-tested caching libraries hain — tum wheel reinvent nahi kar rahe, tum industry-standard cache reuse kar rahe ho.

2. Building Custom Reusable Components

Ab hum apna khud ka component design karenge — jaise ek library author (e.g. React Native Paper, Tamagui ke devs) karte hain. Sochne ka tareeka simple hai: props ek API contract hain. Jo bhi prop tum expose karte ho, wo ek promise hai consumer ke saath — agar tum badle mein kal usse remove/rename karoge, breaking change hoga. Isliye props design karte waqt sochna padta hai — "kya ye prop generic enough hai?", "kya do props ek dusre ko contradict kar sakte hain?".

Discriminated unions se invalid states ko impossible banana

Ek common mistake hai loosely-typed props dena, jaise variant?: string — isse consumer kuch bhi type kar sakta hai aur typo runtime tak pakda nahi jaata. Better approach — TypeScript discriminated unions use karke sirf valid combinations allow karo.

Button.types.ts
import type { PressableProps } from 'react-native';

export type ButtonVariant = 'primary' | 'secondary' | 'danger';
export type ButtonSize = 'sm' | 'md' | 'lg';

// Discriminated union — "loading" state ke saath "disabled" combine nahi
// karna padta manually check, TypeScript khud enforce karega valid shape.
type BaseButtonProps = {
  label: string;
  variant?: ButtonVariant;
  size?: ButtonSize;
  onPress: () => void;
} & Omit<PressableProps, 'onPress' | 'style'>;

type IdleButtonProps = BaseButtonProps & {
  loading?: false;
  disabled?: boolean;
};

type LoadingButtonProps = BaseButtonProps & {
  // jab loading true ho, disabled prop dena hi nahi chahiye — button auto-disabled
  loading: true;
  disabled?: never;
};

export type ButtonProps = IdleButtonProps | LoadingButtonProps;

Isse ye galti compile-time pe hi pakdi jaayegi: <Button loading disabled label="Save" /> — TypeScript error dega kyunki loading: true ke saath disabled allowed hi nahi hai (type never hai). Ye "invalid states ko unrepresentable banao" wali philosophy hai jo senior-level TypeScript ka core idea hai.

Full Button implementation

Button.tsx
import { ActivityIndicator, Pressable, Text } from 'react-native';
import type { ButtonProps } from './Button.types';
import { styles } from './Button.styles';

export function Button({
  label,
  variant = 'primary',
  size = 'md',
  loading,
  disabled,
  onPress,
  ...rest
}: ButtonProps) {
  const isDisabled = loading || disabled;

  return (
    <Pressable
      accessibilityRole="button"
      accessibilityState={{ disabled: isDisabled }}
      disabled={isDisabled}
      onPress={onPress}
      style={({ pressed }) => [
        styles.base,
        styles[variant],
        styles[size],
        isDisabled && styles.disabled,
        pressed && !isDisabled && styles.pressed,
      ]}
      {...rest}
    >
      {loading ? (
        <ActivityIndicator color="#fff" />
      ) : (
        <Text style={styles.label}>{label}</Text>
      )}
    </Pressable>
  );
}

forwardRef — jab tumhara component ek input hai

Agar tum ek reusable TextField bana rahe ho, to consumer ko kabhi kabhi zaroorat padegi underlying native TextInput pe direct ref (e.g. .focus() call karne ke liye, jab form validation fail ho aur pehla invalid field pe focus laana ho). Agar tumne apna component plain function component banaya, to ref prop uspe kaam nahi karega by default — React refs ko function components pass nahi karta jab tak explicitly forward na kiya jaaye.

TextField.tsx
import { forwardRef } from 'react';
import { TextInput } from 'react-native';
import type { TextInputProps } from 'react-native';

type TextFieldProps = TextInputProps & {
  errorMessage?: string;
};

// forwardRef<RefType, PropsType> — RefType ye batata hai .current pe kya milega
export const TextField = forwardRef<TextInput, TextFieldProps>(
  ({ errorMessage, ...rest }, ref) => (
    <>
      <TextInput ref={ref} {...rest} />
      {errorMessage && <Text style={{ color: 'red' }}>{errorMessage}</Text>}
    </>
  )
);

TextField.displayName = 'TextField';

// consumer side:
// const inputRef = useRef<TextInput>(null);
// inputRef.current?.focus();
🧠 Senior Dev Note

Composition over configuration — jab tumhe lagne lage ki ek component ko 15 boolean props chahiye (showIcon, iconPosition, hasSubtitle...), rukho. Ye "props explosion" ek red flag hai. Iski jagah children/composition use karo — <Card><Card.Icon /><Card.Title>...</Card.Title></Card> — jo agle section mein hum discuss karenge (compound components). Library authors (Radix, shadcn, React Native Paper) sab isi principle pe move kar chuke hain.

3. Advanced Custom Component Patterns

Compound Components — Context ke through implicit state sharing

Compound components pattern mein parent component internally ek React Context banata hai, aur uske "sub-components" (jaise Card.Header, Card.Body) us context ko consume karte hain. Isse consumer ko explicitly props pass nahi karne padte har child ko — state parent se implicitly flow karta hai. Ye pattern tab useful hai jab tumhare components ka ek fixed "family" ho jo hamesha saath use hota hai lekin layout flexible rehna chahiye.

Card.tsx
import { createContext, useContext, type ReactNode } from 'react';
import { View, Text } from 'react-native';

type CardContextValue = { variant: 'flat' | 'elevated' };

// null default => agar Card.Header, <Card> ke bahar use hua to hume pata chal jaayega
const CardContext = createContext<CardContextValue | null>(null);

function useCardContext() {
  const ctx = useContext(CardContext);
  if (!ctx) throw new Error('Card.* must be used inside <Card>');
  return ctx;
}

function CardRoot({ variant = 'flat', children }: {
  variant?: CardContextValue['variant'];
  children: ReactNode;
}) {
  return (
    <CardContext.Provider value={{ variant }}>
      <View style={{ borderRadius: 12, backgroundColor: '#262524' }}>
        {children}
      </View>
    </CardContext.Provider>
  );
}

function CardHeader({ children }: { children: ReactNode }) {
  const { variant } = useCardContext(); // shared state without prop drilling
  return (
    <View style={{ padding: 16, borderBottomWidth: variant === 'elevated' ? 1 : 0 }}>
      {children}
    </View>
  );
}

function CardBody({ children }: { children: ReactNode }) {
  return <View style={{ padding: 16 }}>{children}</View>;
}

// namespace pattern — object pe static properties attach karna
export const Card = Object.assign(CardRoot, { Header: CardHeader, Body: CardBody });

// usage: <Card variant="elevated"><Card.Header>...</Card.Header><Card.Body>...</Card.Body></Card>

Render props vs custom hooks

Render props pattern (component ek function-as-children accept karta hai) purane React mein logic share karne ka standard tareeka tha, before hooks existed. Aaj ke RN codebase mein 90% cases mein custom hooks better hain — same logic reuse ho jaati hai bina extra component nesting ke (jo "wrapper hell" create karta hai aur React DevTools mein debug karna mushkil banata hai).

Render props abhi bhi useful hain jab tumhe rendering control deni ho, sirf data nahi — jaise FlatList ka renderItem khud ek render prop hai: list component data manage karta hai, but actual UI kaisi dikhegi wo consumer decide karta hai. Agar tumhe sirf state/logic share karni hai (jaise useDebounce, useKeyboardHeight), custom hook likho.

Controlled vs uncontrolled components

Controlled component mein value parent ke state se aati hai aur parent hi update karta hai (value + onChangeText pattern) — single source of truth React state mein hai. Uncontrolled mein component apni internal state khud maintain karta hai aur sirf zaroorat padne pe ref ke through value expose karta hai. RN forms mein controlled zyada common hai kyunki validation, formatting (jaise phone number masking) turant chahiye hoti hai — lekin high-frequency inputs (jaise ek search box jisme har keystroke pe re-render mehenga hai) ke liye uncontrolled + debounced callback better perform karta hai.

Polymorphic components ("as" prop) — ek advanced technique

Web React mein as prop pattern common hai (jaise <Box as="button">) jisse ek hi component different underlying HTML element render kar sake. RN mein iska use bahut kam hota hai kyunki native elements HTML jaise interchangeable nahi hain (View aur Text fundamentally different native views hain). Fir bhi advanced design systems mein tum ise use kar sakte ho jab tumhara component Pressable ya View ya TouchableOpacity kisi bhi ek ko underlying render element ke roop mein le sake — generic types ke saath (as?: React.ComponentType<any>). Ye zyada tar library-building context mein milta hai, day-to-day feature code mein rarely zaroorat padti hai.

4. Performance: memo, useMemo, useCallback in RN Context

Web pe re-render "sasta" hota hai relatively — DOM diffing fast hai, browser highly optimized hai. React Native mein historically (old bridge architecture, pre-Fabric) har re-render jo native side ko kuch bhi communicate karta tha, JSON-serialize hoke async bridge se paar jaata tha — ye serialization cost non-trivial thi, especially bade objects/arrays ke liye. New Architecture (JSI + Fabric) ne is cost ko kaafi kam kar diya hai (synchronous, shared-memory-jaisa access), lekin fir bhi layout recalculation ka cost real hai — har render pe agar layout-affecting props change hote hain, Yoga ko dobara measure+layout pass chalana padta hai. Isliye unnecessary re-renders avoid karna RN mein web se zyada matter karta hai, especially lists aur animations mein jaha 60fps maintain karna hota hai.

React.memo aur custom comparison

React.memo ek component ko wrap karta hai taaki React uska render skip kar de agar props shallow-equal hain previous render se. Default comparison shallow hai (Object.is har prop pe) — agar tumhare props mein nested objects/arrays hain jo har render pe naye reference se create ho rahe hain, memo useless ho jaata hai. Tab custom comparison function do.

ProductCard.tsx
import { memo } from 'react';

type ProductCardProps = {
  id: string;
  title: string;
  price: number;
  onPress: (id: string) => void;
};

function ProductCardBase({ id, title, price, onPress }: ProductCardProps) {
  // ... render logic
  return null;
}

// custom comparator — sirf price change pe re-render karo, id/title/onPress ignore
export const ProductCard = memo(ProductCardBase, (prev, next) => {
  return prev.price === next.price && prev.title === next.title;
});

useCallback — stable references memoized children ke liye

Agar parent ek inline arrow function pass karta hai memoized child ko (onPress={() => doSomething(id)}), har render pe naya function reference banega — aur memo bekaar ho jaayega, kyunki shallow comparison fail hogi. useCallback us function reference ko stable rakhta hai jab tak dependencies change na ho.

ProductListScreen.tsx
import { useCallback, useState } from 'react';
import { FlatList } from 'react-native';
import { ProductCard } from './ProductCard';

function ProductListScreen({ products }: { products: any[] }) {
  const [selected, setSelected] = useState<string | null>(null);

  // stable across renders — dependency array empty because setSelected is stable too
  const handlePress = useCallback((id: string) => {
    setSelected(id);
  }, []);

  const renderItem = useCallback(({ item }: { item: any }) => (
    <ProductCard {...item} onPress={handlePress} />
  ), [handlePress]);

  return (
    <FlatList
      data={products}
      renderItem={renderItem}
      keyExtractor={(item) => item.id}
    />
  );
}
⚠️ Common Mistake

Sabse zyada dikhne wali mistake — style={'{{'} marginTop: 10 {'}}'} jaisa inline object literal directly JSX mein pass karna kisi memoized child ko. Har render pe ye ek naya object reference banayega, aur memo useless ho jaayega. Isse bahar nikalo — StyleSheet.create mein define karo (jo ek stable reference deta hai) ya useMemo mein wrap karo agar dynamic hai.

getItemLayout — measurement pass ko skip karna

Jab FlatList ko pata nahi hota ki item ki height kya hogi, wo pehle render karta hai, fir measure karta hai (async layout callback ke through), tab jaake scroll position calculations accurate hoti hain. Agar tumhare items fixed height hain, tum getItemLayout de sakte ho jo directly batata hai har index ki length aur offset — isse FlatList ko measurement ka wait hi nahi karna padta, aur scrollToIndex jaise operations bhi instant ho jaate hain (measurement-dependent nahi rehte).

5. Scalable Component Folder Structure

Jaise codebase badhta hai, ek single components/ folder mein sab kuch daalna quickly messy ho jaata hai. Har component ko apna khud ka folder do jisme uske sab related files colocated hon.

folder structure
src/
├── ui/                          # shared design-system components — app-wide reusable, kyunki 2+ features inhe use karte hain
│   ├── Button/                  # har component apna khud ka folder — reason: styles/types/tests colocated rehte hain, isse dhoondhna aasan
│   │   ├── index.ts             # barrel export — "export * from './Button'" — consumer ko internal file split ka pata nahi chalta (encapsulation)
│   │   ├── Button.tsx           # actual component logic + JSX — sirf rendering concern, koi styling object yahan nahi
│   │   ├── Button.types.ts      # props ke TypeScript types — alag file isliye taaki type contract ko component logic se independently review kar sakein
│   │   ├── Button.styles.ts     # StyleSheet.create() yahan — style aur logic alag rakhne se component ka JSX padhna easier hota hai
│   │   └── Button.test.tsx      # unit test colocated — component move/delete karo to test bhi saath chala jaata hai, orphan test nahi bachta
│   ├── Card/                    # same shape jitna possible — consistency se naye developer ko pattern samajhna easy hota hai
│   │   ├── index.ts             # barrel export
│   │   ├── Card.tsx             # component logic
│   │   └── Card.styles.ts       # styles alag — Card simple hai isliye types.ts skip kiya, over-engineering se bacha
│   └── TextField/               # teesra shared component — "rule of three" ke baad hi ui/ mein promote kiya jaata hai
│       ├── index.ts             # barrel export
│       ├── TextField.tsx        # forwardRef wala input component — ref forwarding ke liye alag logic chahiye, isliye apna file
│       └── TextField.styles.ts  # styles
│
└── features/                    # feature-local components — sirf ek feature ke liye, ui/ mein isliye nahi kyunki dusri feature reuse nahi karegi
    └── checkout/                # checkout feature ka apna self-contained folder — delete karo to koi orphan file kahin aur nahi bachta
        ├── components/          # sirf checkout ke liye specific UI — global ui/ mein nahi daala kyunki generic reuse-case nahi hai
        │   ├── OrderSummaryCard.tsx  # checkout-specific presentation — kahin aur use nahi hoga isliye colocated
        │   └── PromoCodeInput.tsx    # checkout-specific input — TextField (shared) ko internally use kar sakta hai, khud reusable nahi hai
        ├── hooks/               # feature-scoped hooks — global hooks/ mein nahi kyunki sirf checkout flow ki state hai
        │   └── useCheckoutFlow.ts    # checkout ka multi-step state machine yahan — component se alag taaki logic independently testable ho
        └── CheckoutScreen.tsx   # feature ka entry screen — Expo Router se yahan import hoga, khud route file nahi hai
ui/Button/index.ts
// barrel export — consumer sirf 'ui/Button' se import karta hai,
// internal file structure ka pata hi nahi chalta (encapsulation)
export * from './Button';
export type { ButtonProps, ButtonVariant } from './Button.types';

Kab colocate karo, kab centralize? Agar component sirf ek feature ke andar use hota hai aur uska koi generic reuse-case nahi hai (jaise PromoCodeInput jo sirf checkout mein chahiye), usse feature ke andar hi rakho — ye "colocation" hai, jisse feature ko delete/refactor karna easy hota hai (sab ek jagah hai). Lekin agar 2+ features same component use karne lagein (jaise Button, Card, Avatar), usse ui/ folder mein promote karo — ab wo tumhara design system ka part hai.

💡 Quick Tip

Rule of thumb: "Rule of three" follow karo — jab tak ek component teesri baar reuse na ho raha ho, usse premature abstract mat karo. Do jagah copy-paste chalta hai; teesri jagah pe refactor karke ui/ mein move karo.

6. Real-World Gotchas & Crashes

🔴 Crash: "Cannot read property 'X' of undefined"

Ye sabse common production crash hai RN apps mein. Ye tab hota hai jab tum list render karte waqt API data pe directly nested property access karte ho bina null-check ke — e.g. item.user.name jab item.user hi undefined ho (deleted user, incomplete API response, ya race condition jaha data abhi fully load nahi hua). FlatList jab bulk render karta hai, ek bhi bad item poora list crash kar sakta hai. Hamesha optional chaining (item.user?.name ?? 'Unknown') use karo aur API response ko Zod/Yup jaisi library se runtime validate karo, sirf TypeScript types pe trust mat karo (TypeScript compile-time hi hai, runtime pe koi guarantee nahi deta jab data external API se aa raha ho).

⚠️ Missing "key" prop — sirf warning nahi, real bug

List render karte waqt key prop missing hona sirf console warning nahi hai — ye React ke reconciliation algorithm ko confuse karta hai. Bina stable key ke, React index-based matching use karta hai — agar list reorder ho, item beech mein insert/delete ho, to React galat DOM/native node ko galat item se associate kar sakta hai. Isse subtle bugs aate hain jaise: TextInput mein type kiya hua text galat row pe dikhna, animation state galat item pe jump karna, ya checkbox ka checked state swap ho jaana jab list filter/sort ho. Hamesha stable unique ID use karo key ke liye, array index nahi (index tab bhi problematic hai jab list reorder/filter hoti hai).

🔴 Memory leak: subscriptions cleanup na karna

Agar tum useEffect ke andar ek event listener, WebSocket subscription, ya Keyboard.addListener jaisa kuch register karte ho aur cleanup function return nahi karte, har baar jab component mount/unmount hota hai (navigation ke through baar baar), naya listener add hota rehta hai bina purane hataye. Kuch navigations ke baad tumhare paas dozens duplicate listeners hain — memory grow karti rehti hai, aur unmounted component ke callback ke andar setState call hone se crash bhi aa sakta hai ("Can't perform a React state update on an unmounted component" — jo newer React mein silently ignore hota hai but underlying leak abhi bhi hai).

useKeyboardHeight.ts
import { useEffect, useState } from 'react';
import { Keyboard } from 'react-native';

export function useKeyboardHeight() {
  const [height, setHeight] = useState(0);

  useEffect(() => {
    const showSub = Keyboard.addListener('keyboardDidShow', (e) => {
      setHeight(e.endCoordinates.height);
    });
    const hideSub = Keyboard.addListener('keyboardDidHide', () => setHeight(0));

    // CRITICAL: cleanup, warna har mount pe naya listener stack hota jaayega
    return () => {
      showSub.remove();
      hideSub.remove();
    };
  }, []);

  return height;
}
⚠️ Deeply nested inline style objects

style={'{{'} flex: 1, padding: 16, backgroundColor: theme.bg {'}}'} jaisa inline object literal directly render mein likhna — har render pe ek naya JS object allocate hota hai, jo garbage collector pe pressure daalta hai aur memo/PureComponent optimizations ko break karta hai (jaisa upar discuss kiya). StyleSheet.create use karo — ye ek stable reference deta hai jo component lifetime mein change nahi hoti, aur old architecture mein ye styles ID mein resolve hoke native side pe cache bhi ho sakte the (matlab sirf ek chhota integer bridge cross karta tha, poora object nahi).

📌 Extra Context

In sab crashes/gotchas ka ek common thread hai — RN apps web apps se zyada "fragile" feel hote hain kyunki ek JS-side unhandled error poori app ko crash kar sakta hai (red screen ya silent crash production mein), jabki web pe browser aksar isolated errors ko gracefully handle kar leta hai. Isliye Error Boundaries lagana, Sentry/Bugsnag jaisa crash reporting set up karna, aur defensive coding (null checks, runtime validation) RN mein "nice to have" nahi, zaroori hai.

7. Advanced Deep-Dive — Beyond the Basics

Ye section un devs ke liye hai jo already comfortable hain components use karne mein, aur ab jaanna chahte hain ki "hood ke neeche" kya chal raha hai — jo bilkul wahi level hai jaha senior/staff interviews actually test karte hain. Hum chaar cheezein cover karenge: React aur Fabric ke beech ka relationship, Context ke re-render traps, useSyncExternalStore, aur profiling ka real workflow.

Reconciliation aur Fabric ke shadow tree ka internals

Pehle confusion clear karte hain — React ka reconciler aur Fabric do alag cheezein hain jo saath mein kaam karti hain. React ka reconciler (Fiber architecture) sirf ye decide karta hai ki "JS level pe kya change hua" — ye purani aur nayi fiber tree (React elements ka in-memory representation) ko diff karta hai aur nikalta hai ki kaunse nodes add/update/remove karne hain. Isko koi idea nahi hota ki native side pe kya render hoga — ye purely JS-level algorithm hai jo React DOM (web) aur React Native dono mein same hai.

Jab React reconciler decide kar leta hai ki "ye host components change hue hain" (View, Text, Image jaise host nodes — non-composite elements), tab Fabric ka kaam start hota hai. Fabric internally apna khud ka shadow tree maintain karta hai — ye ek C++ mein likha hua tree hai jo har host node ke liye ek corresponding ShadowNode object rakhta hai. React ka fiber tree "kya render karna hai" describe karta hai; Fabric ka shadow tree "kaise layout aur render karna hai, thread-safely" describe karta hai. Dono trees alag isliye hain kyunki React ka reconciliation JS thread pe chalta hai (ya concurrent mode mein multiple priorities pe), jabki actual layout aur native mounting alag thread(s) pe hona chahiye taaki UI thread kabhi block na ho.

Poora flow teen stages mein hota hai — inhe samajhna zaroori hai kyunki "commit" word interviews mein bahut use hota hai:

  1. Render phase — React reconciler fiber tree diff karta hai (JS thread, ya concurrent mode mein interruptible). Isi phase mein Fabric ke corresponding ShadowNodes clone/create hote hain — purana shadow tree mutate nahi hota, ek naya immutable shadow tree bana ke complete kiya jaata hai. Ye immutability hi thread-safety ki wajah hai — koi bhi thread purana tree padh sakta hai bina kisi lock ke, kyunki wo kabhi mutate hi nahi hoga.
  2. Commit phase — jab naya shadow tree fully ban jaata hai, Fabric ise "commit" karta hai — matlab is naye immutable shadow tree ko "current" tree ke roop mein atomically swap kar deta hai. Isi commit ke andar Yoga (C++ layout engine) shadow tree pe layout calculate karta hai — har node ki final x/y/width/height nikalta hai flexbox rules apply karke.
  3. Mount phase — computed layout ke saath, Fabric ab "mounting instructions" generate karta hai (kaunsa native view create/update/delete/move karna hai) aur inhe native UI thread pe apply karta hai — iOS pe UIView hierarchy update hoti hai, Android pe corresponding native View hierarchy. Ye step hamesha main/UI thread pe hota hai kyunki OS ka rendering sirf usi thread se safe hai.
🧠 Senior Dev Note — do trees kyun?

Ye two-tree model (React ka fiber tree + Fabric ka shadow tree) ka poora point concurrent rendering ko thread-safe banana hai. Old architecture (pre-Fabric) mein sirf ek tree tha aur render/commit synchronously ek hi bridge call mein hota tha — kaam chal jaata tha lekin priority-based rendering (React 18 ke concurrent features, jaise useTransition) possible nahi thi bina race conditions ke risk ke. Fabric ka immutable shadow tree isse solve karta hai: React JS thread pe background mein ek naya tree bana sakta hai (high-priority update ko beech mein interrupt karke bhi) bina current visible UI ko touch kiye, aur jab ready ho tab hi ek atomic commit se swap hota hai. Layout thread aur JS thread ab independently, apni apni speed pe kaam kar sakte hain — dono ek dusre ko block nahi karte.

Context re-render pitfalls — ek Context, saare consumers re-render

Ye ek bahut common senior-level mistake hai jo mid-level devs karte hain: ek bada single AppContext banana jisme user, theme, notifications, cart — sab kuch daal do. Problem ye hai ki React Context ka fundamental rule hai — jab bhi Provider ka value change hota hai, us Context ke SAARE consumers re-render hote hain, chahe wo consumer sirf us value ke ek chhote se hisse pe depend kyun na karta ho. React ye check nahi karta ki "consumer ne kaunsa field actually use kiya" — ye sirf reference equality check karta hai poore value object pe.

Matlab agar tumhara AppContext mein {'{'} user, theme, cartItems {'}'} hai, aur sirf cartItems update hua (jaise ek item add hua), to har wo component jo sirf theme use kar raha tha bhi re-render hoga — bilkul unnecessary. Chhoti app mein ye unnoticed reh jaata hai, lekin bade app mein (deep tree, expensive children) ye janky UI aur wasted CPU cycles ka source ban jaata hai.

contexts-before.tsx
// ANTI-PATTERN — ek hi giant context mein sab kuch, alag concerns bhi mixed
type AppContextValue = {
  user: User | null;       // auth state — kabhi kabhi change hota hai (login/logout)
  theme: 'light' | 'dark'; // UI preference — rarely change hota hai
  cartItems: CartItem[]; // frequently changes — har "add to cart" pe naya array
};

const AppContext = createContext<AppContextValue | null>(null);

// PROBLEM: cartItems update hote hi, sirf theme use karne wala
// koi bhi deep-nested component bhi re-render ho jaayega — wasteful.

Senior pattern — Context ko concern ke hisaab se split karo, na ki "sab data ek jagah" ke hisaab se. Alag-alag update-frequency wali cheezein alag Context mein rakho, taaki ek unrelated update doosre consumers ko touch na kare.

contexts-after.tsx
import { createContext, useContext, useMemo, useState, type ReactNode } from 'react';

// alag context — sirf auth-related data, rarely updates
const UserContext = createContext<User | null>(null);

// alag context — sirf theme data, apna independent update cycle
const ThemeContext = createContext<'light' | 'dark'>('dark');

// alag context — cart, jo sabse zyada frequently change hota hai
const CartContext = createContext<CartItem[]>([]);

function ThemeProvider({ children }: { children: ReactNode }) {
  const [theme, setTheme] = useState<'light' | 'dark'>('dark');

  // value ek primitive string hai isliye yahan useMemo zaroori nahi —
  // lekin agar value ek OBJECT hoti ({ theme, setTheme }), useMemo zaroori ho jaata:
  return (
    <ThemeContext.Provider value={theme}>{children}</ThemeContext.Provider>
  );
}

// jab value ek naya object ho (functions + state milake), useMemo lagana zaroori hai —
// warna har parent re-render pe ek naya { } reference banega aur SAARE consumers
// re-render honge, chahe underlying values same hi kyun na hon.
function CartProvider({ children }: { children: ReactNode }) {
  const [items, setItems] = useState<CartItem[]>([]);

  // useMemo ke bina, har CartProvider render pe { items, setItems } ka naya
  // object banta — memo(Consumer) bhi bekaar ho jaata, kyunki value reference hamesha badalta
  const value = useMemo(() => ({ items, setItems }), [items]);

  return (
    <CartContext.Provider value={value}>{children}</CartContext.Provider>
  );
}
🧠 Senior Dev Note

useMemo on the Provider's value sirf tab kaam karta hai jab dependency array sahi ho — agar tum items ke saath koi aur inline value (jaise {'{'} items, count: items.length {'}'}) daaloge to wo bhi recompute hoga, jo fine hai. Real mistake tab hoti hai jab log value={'{{'} items, setItems {'}}'} directly inline likh dete hain JSX mein bina useMemo ke — is case mein object literal {'{'} } syntax har render pe guaranteed naya reference banata hai, chahe items khud same kyun na ho. Aur split-context approach ka real benefit sirf tab milega jab consumers bhi React.memo ho — warna parent re-render hone pe children to re-render honge hi, Context se independent.

useSyncExternalStore — concurrent-safe external state subscription

React 18 se pehle, agar tumhe kisi external mutable source (jaise Redux se bahar ka custom store, ya ek native event emitter jaise NetInfo, ya browser/RN ka Dimensions API) ko subscribe karna hota tha, log usually useState + useEffect ka combo use karte the — external store pe listener lagao, callback mein setState call karo. Ye kaam to karta hai, lekin React 18 ke concurrent rendering mein ek subtle bug create kar sakta hai jise "tearing" kehte hain — matlab ek hi render ke andar UI ke different parts external store ki DIFFERENT values dikha sakte hain, kyunki concurrent render beech mein interrupt ho sakta hai aur store value render ke dauraan change ho sakti hai.

useSyncExternalStore is exact problem ke liye design kiya gaya hook hai — ye React ko guarantee deta hai ki ek external store ko subscribe karte waqt bhi, ek single render ke andar sabhi components ko SAME, consistent snapshot value milegi, chahe concurrent rendering ke beech mein store update ho jaaye. Ye internally React ko batata hai "is value ko concurrent-safe tarike se read karo" — agar render ke dauraan store change ho jaaye, React us render ko discard karke dobara sync tareeke se render karega.

useNetworkStatus.ts
import { useSyncExternalStore } from 'react';
import NetInfo from '@react-native-community/netinfo'; // native connectivity event source

// module-level mutable variable — ye "external store" hai, React ke bahar rehta hai
let isConnected = true;

// subscribe: React ko batata hai "jab bhi store change ho, ye callback chalao"
// return value ek unsubscribe function honi chahiye — React cleanup ke liye use karega
function subscribe(callback: () => void) {
  const unsubscribe = NetInfo.addEventListener((state) => {
    isConnected = !!state.isConnected; // external store ko mutate karo
    callback(); // React ko batao "re-check karo, kuch badla hai"
  });
  return unsubscribe; // cleanup — component unmount pe React ye call karega
}

// getSnapshot: current value synchronously return karna hai — no side effects allowed yahan
function getSnapshot() {
  return isConnected;
}

// server-side rendering ke liye fallback snapshot (RN mein rarely relevant, but hook signature isse maangta hai)
function getServerSnapshot() {
  return true; // SSR pe assume connected, hydration ke baad real value aayegi
}

export function useNetworkStatus() {
  // React guarantee karta hai — concurrent render ke andar bhi ye value tear nahi hogi
  return useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot);
}

// usage: const isOnline = useNetworkStatus(); — bilkul useState jaisa lagta hai use karne mein

Practically, agar tum koi state management library use kar rahe ho (Zustand, Jotai, ya even Redux ke naye bindings), unke internals mein already useSyncExternalStore use ho raha hai — tumhe khud isse directly likhna kam hi padta hai. Lekin jab tum khud ek custom store banate ho (jaise upar wala network status example, ya ek native module se aane wala event stream), ye tumhara go-to primitive hona chahiye — useState + manual useEffect listener pattern se concurrent-safe.

Profiling with React DevTools Profiler — actual senior workflow

"Meri app slow hai" — ye sabse vague bug report hai jo tumhe milega, aur senior dev ka job hai isse specific bana dena. React DevTools ka Profiler tab exactly isi ke liye hai. Real workflow kuch aisa dikhta hai:

  1. Record a session — Profiler mein "Record" dabao, jo interaction slow lag raha hai wo perform karo (jaise list scroll, ya ek filter toggle), fir "Stop" dabao. Ye tumhe har commit ka ek flame graph dega.
  2. Flame graph padhna — har bar ek component represent karta hai; bar ki width batati hai us component (aur uske children) ko render karne mein kitna time laga, aur color (yellow se red gradient, DevTools ki default color scale mein) batata hai relative render duration — jitna zyada saturated color, utna zyada time. Agar ek chhota sa state update (jaise ek checkbox toggle) ek bahut wide, deep flame graph produce kar raha hai jisme dozens unrelated components bhi shaamil hain, wahi tumhara signal hai ki "kuch over-rendering ho raha hai".
  3. "Why did this render?" feature — har component bar pe click karke DevTools ye batata hai ki us specific commit mein wo component kyun re-render hua — "Props changed", "State changed", "Hooks changed", ya "Parent component rendered". Ye sabse actionable info hai — agar "Parent rendered" wajah hai aur props/state khud same hain, to iska matlab hai ye component React.memo ka candidate hai.
  4. Ranked view — commit ke andar components ko unke render duration ke hisaab se sort karke dikhata hai (sabse slow upar). Isse tumhe pata chalta hai "in in sab renders mein se, actually expensive kaunsa hai" — kabhi kabhi ek chhota component bahut baar re-render ho raha hota hai (jaise FlatList ka ek renderItem), jabki koi bada component sirf ek baar render hota hai but har baar heavy computation karta hai — dono alag problems hain, alag fixes chahiye.

Iske alawa Settings → "Highlight updates when components render" checkbox on karke tum LIVE app ke upar rectangles blink hote dekh sakte ho jab bhi koi component re-render hota hai — quick visual sanity check ke liye useful hai bina Profiler session record kiye, especially scroll performance debug karte waqt.

🧠 Senior Dev Note

Interview mein agar tumse pucha jaaye "app slow hai, kya karoge" — sirf "memo laga dunga" mat bolo. Correct answer sequence hai: (1) Profiler se record karke reproduce karo aur confirm karo ki re-render hi problem hai, na ki kuch aur (jaise ek heavy synchronous computation, ya bridge/JSI serialization cost, ya Yoga layout thrashing bade nested trees mein); (2) "why did this render" se root cause identify karo; (3) tabhi targeted fix lagao — memo, useCallback, useMemo, context split, ya list virtualization tuning. Guessing-first approach (bina measure kiye optimize karna) senior interviews mein turant flag ho jaata hai — "premature optimization" ka classic trap.

8. 🎯 Interview Questions — Senior React Native Developer

Ye questions us level ke hain jo actual senior/staff RN interviews mein pucha jaata hai — sirf "API kaise use karte ho" nahi, balki "internally kya ho raha hai" aur "trade-off kya hai" wale angle se. Answers confidently aur specifically likhe gaye hain, jaise ek strong senior engineer interview mein bolega.

1. Explain exactly how FlatList decides what to render and unmount as you scroll — what is "windowing"?

FlatList khud rendering logic nahi rakhta — ye internally VirtualizedList ko wrap karta hai, jo actual "windowing" (a.k.a virtualization) implement karta hai. Concept simple hai: poori list ko ek saath mount karne ke bajaye, sirf ek "window" of items mount rakho — jo currently viewport ke andar hain, plus ek buffer.

Practically ye teen props se control hota hai: initialNumToRender (pehla render kitne items se start hoga — isse "time to first paint" fast rehta hai), windowSize (default 21 — units "viewport heights" mein hain, matlab 21 ka matlab ~10 viewport heights upar aur ~10 neeche current position se, plus current viewport), aur maxToRenderPerBatch (ek scroll batch mein max kitne naye items render honge — isse ek hi frame mein bahut zyada work nahi hota, jo jank cause karta). VirtualizedList internally scroll position track karta hai, calculate karta hai kaunse indices ab window ke bahar chale gaye, unke native views ko unmount karta hai (state loss ke saath — ye important hai, scroll wapas aane pe wo item fresh mount hoga), aur naye visible-ho-rahe indices ko mount karta hai. Ye sab async batches mein hota hai (InteractionManager-jaisi scheduling ke through) taaki scroll gesture ka JS thread response block na ho.

2. When would you reach for FlashList over FlatList, and what's the actual mechanism that makes it faster?

FlatList aur FlashList dono windowing use karte hain — fark view lifecycle mein hai. FlatList jab item viewport se bahar jaata hai, uska native view literally destroy kar deta hai, aur naya item viewport mein aane pe ek bilkul naya native view create karta hai. View creation/destruction native side pe expensive hai — memory allocate/deallocate, native layout tree mein insert/remove, sab cost hai.

FlashList (Shopify) cell recycling use karta hai — jaise Android ka RecyclerView ya iOS ka UITableView/UICollectionView internally karte hain. Jab ek item screen se bahar jaata hai, uska native view destroy nahi hota — usse ek pool mein rakh diya jaata hai, aur jab naya item viewport mein aata hai, FlashList ek existing view ko reuse karta hai (sirf uska content/data update karta hai) instead of naya banane ke. Isse view creation ka overhead almost eliminate ho jaata hai — sirf data binding ka cost bachta hai, jo bahut sasta hai. Iske alawa FlashList apna layout estimation smarter tarike se karta hai (estimatedItemSize ke through auto-averaging) taaki manual getItemLayout ki zaroorat kam pade.

Reach for FlashList jab: list bahut lambi ho (thousands of items, feed-like UI), items visually similar template share karte hon (recycling ka fayda tabhi milta hai jab views ka shape consistent ho), aur scroll performance genuinely measured problem ho — Profiler se confirm karo, sirf assumption pe migrate mat karo, kyunki FlashList ka apna migration cost (thoda different API surface, kuch edge cases jaise dynamic-height items ke saath) bhi hai.

3. A list of 5000 items is janky on scroll — walk me through your diagnostic process.

Pehla step guessing nahi hai — measurement hai. Main in order karunga:

  • Confirm virtualization ho hi rahi hai — check karo ki ScrollView ke andar .map() to nahi use ho raha (sabse common root cause). Agar FlatList use ho raha hai, check karo koi accidental prop (jaise pura data array as extraData pass karna jo unnecessary re-render trigger kare) to nahi lagi.
  • renderItem ki cost check karo — React DevTools Profiler se record karo scroll ke dauraan, dekho renderItem kitni baar aur kitni der chal raha hai. Agar har item render mein koi expensive computation hai (jaise inline date formatting, ya heavy style calculation jo memoized nahi hai), wahi bottleneck hai.
  • getItemLayout hai ya nahi — agar items fixed height hain aur getItemLayout missing hai, FlatList ko measurement pass ka wait karna padta hai jo scroll ke response ko slow kar sakta hai, especially scrollToIndex jaise operations mein.
  • Images check karo — agar list mein images hain aur plain Image use ho raha hai (na ki expo-image), har scroll pe re-decode ho sakta hai — memory cache missing hai. Isse frame drops hote hain jab naye images mount hote hain.
  • renderItem ko memo + stable reference do — confirm karo item component React.memo hai, aur parent se pass ho rahe callbacks (onPress waghera) useCallback se stable hain. Agar nahi, har render pe naya function reference banega aur memo defeat ho jaayega.
  • Agar sab kiya aur abhi bhi jank hai — tab FlashList migration consider karo, kyunki ab bottleneck fundamentally view creation/destruction cost hai jo sirf recycling se fix hota hai, tuning se nahi.

4. Why does an inline arrow function passed as a prop defeat React.memo, even if the function does the exact same thing every render?

React.memo default comparison shallow reference equality use karta hai har prop pe (Object.is) — ye function ke behavior ko compare nahi karta, sirf uski memory reference ko. JavaScript mein () => doSomething() jaisa arrow function literal jab bhi JSX ke andar likha jaata hai, har render pe ek bilkul naya function object allocate hota hai — even agar us function ka body character-by-character identical hai previous render se. Do functions "same kaam karte hain" iska koi matlab nahi hai JS engine ke liye jab tak wo literally same object reference na hon.

Isliye memoized child ko onPress={'{'}() => doSomething(id){'}'} pass karna memo ko automatically defeat kar deta hai — har parent render pe child ko "prop changed" dikhega (kyunki reference change hui hai), aur memo ka comparison fail ho jaayega, child re-render hoga chahe uska real behavior same hi kyun na ho. Fix — useCallback se function reference ko stabilize karo (dependencies change na hone tak same reference milta rahega), ya function ko parent se pass karne ke bajaye ek stable ID pass karo aur child khud apna handler internally resolve kare.

5. Explain the difference between the old Bridge architecture and JSI/Fabric, and why it matters for component performance.

Old architecture mein JS aur native side do completely separate runtimes the jo sirf ek async, batched, JSON-serialized "Bridge" ke through communicate karte the. Har cross-side call — chahe wo ek native module function ho ya ek UI update — pehle JSON string mein serialize hota tha, bridge cross karta tha asynchronously, fir doosri taraf deserialize hota tha. Ye cost real hai, especially large payloads (jaise ek bade array ya nested object) ke liye — aur crucially, ye asynchronous tha, matlab tum kabhi bhi synchronously native side se kuch query nahi kar sakte the (jaise "is view ki current width kya hai") bina ek round-trip promise ke.

JSI (JavaScript Interface) ye poora model badal deta hai — ab JS aur native code same memory space share kar sakte hain via direct C++ bindings, bina serialization ke aur bina async round-trip ke. Fabric (naya renderer) aur TurboModules (naye native modules) dono JSI ke upar bane hain. Component performance ke liye iska matlab hai — render commits ab synchronous ho sakte hain jaha zaroorat ho, layout measurements instant query ho sakte hain, aur bade props payloads ka serialization overhead essentially khatam ho gaya hai. Practically — deeply nested component trees jo pehle bridge-bound the, ab kaafi zyada headroom rakhte hain before performance issues aate hain — lekin Yoga layout cost (flexbox calculation) abhi bhi real hai, kyunki wo architecture-independent hai.

6. What's the difference between a controlled and uncontrolled TextInput, and which would you pick for a search box with 10k+ item filtering?

Controlled TextInput mein value React state se drive hoti hai — value={'{'}query{'}'} + onChangeText={'{'}setQuery{'}'}. Har keystroke pe: native side event fire karta hai, JS state update hota hai, React re-render trigger hota hai, aur naya value wapas native input ko commit hota hai. Ye single-source-of-truth deta hai (React state hamesha accurate hai) but har keystroke ek full render cycle trigger karta hai.

10k+ item filtering wale search box ke liye, agar tum naive tarike se har keystroke pe poore 10k items ko filter kar rahe ho synchronously render ke andar, ye lag introduce karega — user ko typing lag mehsoos hoga kyunki render aur filter dono same JS thread pe compete kar rahe hain. Best approach — input ko uncontrolled ya locally-controlled rakho (input apni khud ki state maintain kare, ya ek separate fast-updating local state), aur actual filtering logic ko debounce karo (jaise 200-300ms) — matlab filter sirf tab chale jab user typing pause kare, har single keystroke pe nahi. Isse input responsiveness (jo user turant feel karta hai) aur filtering cost (jo expensive hai) decouple ho jaate hain.

7. Why does splitting a large Context into multiple smaller contexts actually help performance — walk me through the mechanism?

React Context ka re-render trigger rule simple hai: jab Provider ka value reference change hoti hai, us Context.Consumer/useContext ko use karne wale SAARE components re-render hote hain — regardless of kya unhone value ke kis field ko actually use kiya. Ye field-level granularity track nahi karta, sirf poore value object ki reference dekhta hai.

Agar tumhara Context ek bada object hai jisme multiple unrelated concerns hain (user, theme, cart), to koi bhi ek concern update hone se (jaise cart) baaki sab consumers (jo sirf theme use kar rahe the) bhi re-render honge — kyunki unhe pata hi nahi ki "sirf cart badla hai, mera wala field same hai". Jab tum Context ko split karte ho (separate UserContext, ThemeContext, CartContext), har Context apna independent value reference rakhta hai. Ab cart update hone pe sirf CartContext ka reference change hota hai — ThemeContext aur UserContext completely untouched rehte hain, isliye unke consumers re-render hi nahi honge. Ye mechanism pure reference-identity based hai, isliye splitting directly is granularity problem ko solve karta hai without kisi extra library ke.

8. What problem does useSyncExternalStore solve that useState + useEffect couldn't?

useState + useEffect se external store subscribe karna React 17 tak fine tha kyunki rendering hamesha synchronous aur non-interruptible thi — ek render start hota, complete hota, commit hota, bina beech mein kisi aur priority ke interfere kiye. React 18 ke concurrent features (useTransition, automatic batching ke saath concurrent rendering) is guarantee ko todte hain — ek render beech mein pause ho sakta hai, kisi aur high-priority update ko process karne ke liye, aur phir resume ho sakta hai. Agar is beech mein external store ki value change ho jaaye, alag-alag components ek hi logical render ke andar store ki DIFFERENT values dekh sakte hain — ye "tearing" hai, aur ye ek bahut subtle, hard-to-reproduce bug class hai (UI ke different parts inconsistent state dikhate hain, jaise ek badge count kahin 5 dikhaye aur kahin 6, same render mein).

useSyncExternalStore React ko explicitly batata hai "ye value ek external, React ke bahar ka mutable source hai" — React internally ensure karta hai ki ek render ke dauraan agar store change ho jaaye, to React us render ko discard karke synchronously dobara render kare taaki consistency guaranteed rahe. Ye poore concurrent rendering model ke saath compatibility ka safety-net hai jo manual useEffect-based subscription kabhi guarantee nahi kar sakta tha.

9. Explain the two-tree model in Fabric (React's fiber tree vs the shadow tree) — why can't React just directly manipulate native views?

React ka fiber tree ek pure JS data structure hai jo describe karta hai "logically kya render hona chahiye" — ye completely platform-agnostic hai, same reconciler web aur native dono mein use hota hai. Fabric ka shadow tree ek C++ data structure hai jo describe karta hai "ye kaise physically layout aur mount hona chahiye" — is mein Yoga layout results, native view configs, sab kuch hota hai.

React seedhe native views ko directly manipulate nahi kar sakta kyunki (a) native view manipulation sirf UI/main thread pe safe hai, jabki React reconciliation kisi bhi thread pe (ya multiple priorities mein interleaved) ho sakti hai concurrent mode mein, aur (b) agar reconciliation directly mutable native state ko touch kare, to ek interrupted/discarded render (jo concurrent mode mein normal hai) ek half-applied, inconsistent UI state chhod sakta hai. Shadow tree ek immutable intermediate representation ke roop mein kaam karta hai — React JS thread pe (kisi bhi priority se, freely) naya shadow tree bana sakta hai bina current visible UI ko touch kiye, aur sirf jab wo tree fully complete ho jaaye, ek atomic "commit" operation se real native views ko UI thread pe update kiya jaata hai. Ye separation hi guarantees deta hai ki user ko kabhi bhi ek "half-rendered" ya inconsistent frame nahi dikhega.

10. You inherit a codebase where every component uses `React.memo` and every callback uses `useCallback`, but the app is still slow. What's your first hypothesis?

Ye ek classic "over-engineering without measurement" symptom hai, aur mera pehla hypothesis hoga ki memo/useCallback khud hi problem ban gaye hain, fix nahi. Do concrete possibilities: pehli — useCallback ki dependency array khud unstable hai (jaise ek object jo parent mein har render pe naya banta hai dependency mein hai), jisse callback phir bhi har render pe naya bin raha hai — memo ka poora point defeat ho gaya lekin extra hook overhead add ho gaya bina fayde ke. Doosri — team ne har component ko memo kiya, chahe uski render cost trivial ho — memo khud free nahi hai, ye ek shallow comparison run karta hai har render attempt pe; agar comparison khud costly hai (bahut saare props) aur component ka actual render cheap hai, memo net-negative ho sakta hai.

Real fix hamesha same hai — Profiler khol ke actual bottleneck measure karo. Zyadatar cases mein asli culprit kuch aur hota hai jo memo/useCallback bilkul touch nahi karte — jaise ek bada, unsplit Context jiska value reference har render pe badalta hai (memo ke bawajood consumers re-render honge kyunki context change khud memo se bypass ho jaata hai), ya list mein missing getItemLayout, ya heavy synchronous work render ke andar (jaise JSON parsing, date formatting bina memoization ke), ya simply bahut zyada deeply nested Views jisse Yoga layout pass khud expensive ho gaya hai — jisska memo se koi lena dena nahi.
