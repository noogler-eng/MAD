What EAS Build Actually Does

Sabse pehle ek fundamental confusion clear karte hain jo bahut logo ko hoti hai: EAS Build koi magic cloud service nahi hai jo "kuch alag tarah se" app banata hai — ye literally wahi native build process run karta hai jo aap apne local machine pe karte, bas ek remote server pe. iOS ke liye ye cloud mein ek macOS machine spin karta hai, us par xcodebuild chalata hai (exactly wahi Xcode toolchain jo aapke Mac pe chalta), aur ek signed .ipa file generate karta hai. Android ke liye ye ek Linux (ya macOS) machine pe ./gradlew chalata hai (Gradle build, wahi jo Android Studio internally chalata hai), aur ek .apk ya .aab (Android App Bundle) file generate karta hai.

To phir isme naya kya hai? Root level pe iska matlab ye hai ki aapko compile-time native toolchain ki zaroorat nahi — aur ye ek bahut bada practical unlock hai:

  • iOS build ke liye Mac ki zaroorat nahi — ye sabse bada reason hai jo log EAS Build use karte hain. Xcode sirf macOS pe chalta hai (Apple ki licensing restriction), to agar aap Windows ya Linux pe develop kar rahe ho, local pe iOS build banana literally impossible tha pehle. EAS ka macOS cloud runner ye problem solve karta hai — aap kahin se bhi eas build --platform ios chala sakte ho, real Apple-signed hardware pe nahi, lekin Apple ke required macOS environment mein.
  • Consistent, reproducible build environment — "works on my machine" ka native version bhi hota hai: alag Xcode version, alag CocoaPods version, alag Android SDK/NDK version — sab alag results de sakte hain. EAS ek pinned, versioned build image use karta hai (aap eas.json mein image field se specific version bhi pin kar sakte ho), to poori team — aur CI — same environment mein build karti hai, "mere pe kaam kar raha tha" wali class of bugs kaafi kam ho jaati hai.
  • Credentials aur signing centrally handle hote hain — iOS signing certificates, provisioning profiles, Android keystores — ye sab sensitive files hain jo normally har developer ke local machine pe manually manage karne padte the (aur aksar galat tarike se — Slack pe bhej diya, .gitignore bhool gaye). EAS in credentials ko securely apne server pe store kar sakta hai aur build ke time automatically apply kar deta hai — hum ise Section 6 mein detail se dekhenge.
  • Aapka local machine free rehta hai — native builds CPU aur RAM heavy hote hain (especially iOS builds jo 10-20 min tak le sakte hain). Cloud pe offload karne se aap us waqt kaam continue kar sakte ho, aur team ke saare developers parallel builds trigger kar sakte hain bina apne laptops ko heat kiye.

Ab isko contrast karte hain local native build commands se — expo run:ios aur expo run:android. Ye commands bhi native build hi karte hain, lekin completely local machine pe — matlab aapke paas Xcode (macOS pe) ya Android Studio + SDK/NDK (kisi bhi OS pe) installed hona zaroori hai. Ye tab useful hote hain jab aap active development kar rahe ho aur fast iteration chahiye (native module add kiya, turant test karna hai, cloud round-trip ka wait nahi karna), ya jab aap offline/restricted-network environment mein ho. Lekin ye aapke local environment pe depend karte hain — agar aapka Xcode outdated hai ya kisi teammate ka Android SDK config alag hai, results differ kar sakte hain.

iOS pe kaamSirf macOS machine seKisi bhi OS se (Windows/Linux bhi)
SpeedFast iteration (no queue, no upload)Build queue + upload/download time
ConsistencyAapke local env pe depend karta haiPinned, versioned cloud image

🧠 Senior Dev Note

Practical senior workflow ye hota hai: local native build use karo jab aap active native module development kar rahe ho (fast iteration chahiye), aur EAS Build use karo jab build ko share karna hai (QA, stakeholders), CI pipeline mein automate karna hai, ya store pe submit karna hai. Dono mutually exclusive nahi hain — same project mein dono use hote hain, alag purpose ke liye.

eas.json aur Build Profiles

eas.json project ke root mein rehta hai aur ye define karta hai ki build profiles kya hain — har profile ek named configuration hai jo batata hai ki us build ka distribution type kya hoga, dev client include hoga ya nahi, environment variables kya honge, aur build kis platform ke liye ho raha hai. Jab aap eas build --profile production chalate ho, EAS us naam ke profile ko eas.json mein dhoondta hai aur uski settings apply karta hai. Ye concept powerful isliye hai kyunki ek hi command (eas build) se aap completely different tarah ke builds generate kar sakte ho — bas profile ka naam badal ke.

Standard convention teen profiles rakhne ka hai: development (local iteration ke liye dev-client wala build), preview (QA/stakeholders ke liye internal distribution, production jaisi native config), aur production (store submission ke liye final build). Neeche ek fully annotated example hai:

(comments added for teaching — remove them in your real eas.json since JSON doesn't support comments)

eas.json
{
  "cli": { // "cli" block — EAS CLI ke behaviour ko control karta hai
    "version": ">= 12.0.0", // Minimum EAS CLI version jo is config ke saath compatible hai
    "appVersionSource": "remote" // Version state EAS servers pe track hoga, local app.json mein nahi (Section 7 mein detail)
  }, // cli block close
  "build": { // "build" key ke andar saare named build profiles define hote hain
    "development": { // "development" profile — local dev/testing ke liye
      "developmentClient": true, // expo-dev-client wala build banega (custom native code allowed + fast refresh)
      "distribution": "internal", // Sirf directly install hoga (link/QR se), App Store/Play Store review nahi
      "ios": { // iOS-specific overrides is profile ke liye
        "simulator": false // false = real device ke liye build banega (true karo to Simulator build milta hai, code-signing skip hoti hai)
      }, // ios override close
      "android": { // Android-specific overrides
        "buildType": "apk" // APK generate hoga (directly installable), AAB nahi (jo sirf Play Store ke liye hota hai)
      } // android override close
    }, // development profile close
    "preview": { // "preview" profile — QA/stakeholder testing ke liye, production-like
      "distribution": "internal", // Store review ke bina directly share hota hai (link se install)
      "channel": "preview", // EAS Update channel bind hota hai isi naam se (future OTA updates iss build ko target karenge)
      "android": { // Android override for preview
        "buildType": "apk" // Testers ko direct APK deni hai, easy install ke liye
      } // android override close
    }, // preview profile close
    "production": { // "production" profile — store submission ke liye final build
      "distribution": "store", // App Store / Play Store submission ke liye configured
      "autoIncrement": true, // Har production build pe versionCode/buildNumber apne aap bump hoga (Section 7)
      "android": { // Android override for production
        "buildType": "app-bundle" // AAB format — Play Store ab isi format ko mandatory require karta hai
      } // android override close
    } // production profile close (no trailing comma — last key)
  } // build key close
} // root object close

Key-by-key legend agar upar ka JSON confusing laga:

  • cli.version — CLI version constraint, taaki purana CLI galat config na apply kare.
  • cli.appVersionSource — "remote" matlab EAS version numbers ko apne server pe track karta hai (team-safe), "local" matlab app.json mein manually maintain karna hoga.
  • developmentClient — true hone par build mein expo-dev-client bundle hota hai, jisse custom native modules ke saath bhi fast-refresh JS iteration milta rehta hai.
  • distribution — "internal" (direct install, no store review) vs "store" (App Store/Play Store submission ke liye packaged).
  • channel — EAS Update se link hota hai; batata hai ki ye build kaunse OTA update channel ko subscribe karega.
  • autoIncrement — production builds mein version/build number automatically bump karta hai.
  • ios.simulator — true karne par Simulator-compatible build banta hai jo bina code-signing ke chal jaata hai (quick local testing ke liye handy).
  • android.buildType — "apk" (directly installable file) vs "app-bundle" (Play Store-only optimized format).
💡 Hinglish Tip

Profile ka naam kuch bhi ho sakta hai — "development", "preview", "production" sirf convention hain, EAS ko koi special meaning nahi pata inki. Aap chahe to "staging" ya "client-demo" jaisa custom profile bhi bana sakte ho — bas eas build --profile <naam> se usko reference karna hoga.

Development Builds

Development build wo build hai jisme developmentClient: true set hota hai — iska matlab ye build mein expo-dev-client package bundled hota hai, jo essentially ek custom Expo Go jaisa hai lekin aapke apne native code ke saath compiled. Yaad rakho Expo Go ek generic app hai jo Expo store se download hoti hai aur usme sirf wahi native modules hote hain jo Expo pehle se bundle karta hai — agar aapko koi third-party native module (jaise react-native-ble-plx ya koi custom native module) chahiye jo Expo Go mein included nahi hai, Expo Go usse load nahi kar sakta. Development build isi limitation ko todta hai: ye aapka khud ka native binary hai jisme aapke saare native dependencies compiled hain, lekin phir bhi JS bundle Metro se live load hota hai — matlab aapko har native change ke baad rebuild nahi karna padta, sirf naya native module add karne par.

terminal
# Development build create karne ke liye expo-dev-client install karna zaroori hai pehle
npx expo install expo-dev-client # Ye dependency development client ka runtime add karti hai

# Android ke liye development profile se build trigger karo
eas build --profile development --platform android # eas.json ke "development" profile ki settings use hongi

# iOS ke liye bhi same profile, alag platform
eas build --profile development --platform ios # Real device ke liye signed .ipa banega (kyunki simulator:false set hai)

# Build complete hone ke baad, JS bundler ko separately start karo
npx expo start --dev-client # Development build isi Metro server se connect hoke JS load karega

Build complete hone ke baad EAS aapko ek download link + QR code deta hai. Android pe ye direct .apk hoti hai jo aap seedha device pe install kar sakte ho (Play Store ki zaroorat nahi). iOS pe ye ek .ipa hoti hai — lekin iOS pe internal distribution ke liye device ko pehle "registered" hona padta hai EAS credentials ke through (ad-hoc provisioning profile ki wajah se — iOS by design kisi bhi random device pe app install nahi hone deta bina explicit registration ke, chahe wo App Store se bahar hi kyun na ho). Ye artifact ek installable binary hai — end user (aap, ya QA teammate) isse directly apne phone pe install karta hai, koi store review involved nahi.

ℹ️ distribution: internal ka matlab

"distribution": "internal" ka matlab hai build App Store/Play Store review process se bilkul bypass ho jata hai — sirf un logo ko milta hai jinke paas download link/QR hai. Team ke andar share karne ke liye perfect hai, lekin end users tak isse distribute nahi kar sakte (wo store-only hota hai).

Preview Builds

Preview build bhi distribution: "internal" use karta hai (matlab store review nahi lagta, directly install hoti hai) — lekin isme sabse bada difference ye hai ki ye dev client include nahi karta. Preview build production ke bilkul kareeb ka native configuration use karta hai — no dev menu, no fast refresh, JS bundle build-time pe hi permanently embed ho jata hai (Metro se live connect nahi hota). Isliye preview build ka behaviour exactly wahi hota hai jo end user ko milega, sirf distribution channel alag hai (link se milta hai, store se nahi).

Ye QA aur stakeholder testing ke liye ideal profile hai — jab aapko client ko "yaha dekho feature X kaisa dikh raha hai" dikhana ho bina App Store review ka wait kiye (jo 1-3 din le sakta hai), ya jab QA team ko ek stable, production-jaisa build test karna ho jisme dev-only cheezein (dev menu, red-box errors, Reactotron connections) na dikhein.

🧠 Senior Dev Note

Bahut teams galti se sirf development build banate hain aur QA ko wahi de dete hain — problem ye hai ki dev client ka behaviour (extra JS bridge overhead, dev-only warnings, red-box crashes on JS errors jo production mein silently handle hote) production se differ karta hai. Preview build banane mein extra 5 minute lagta hai, lekin isse QA "real" bugs pakadta hai, dev-environment-only artifacts nahi.

Production Builds

Production profile wo hai jo actually App Store aur Play Store pe submit hota hai. Ismein distribution: "store" set hota hai — jiska matlab hai build store submission format mein packaged hota hai (Android ke liye .aab/App Bundle, jo Play Store ab mandatory require karta hai; iOS ke liye distribution-certificate-signed .ipa). Iske saath autoIncrement: true rakhna almost hamesha zaroori hota hai (Section 7 mein detail se dekhenge kyun).

eas.json (production block only)
"production": { // production profile ka poora block
  "distribution": "store", // App Store / Play Store submission ke format mein package hoga
  "autoIncrement": true, // versionCode (Android) / buildNumber (iOS) auto-bump har build pe
  "env": { // Production-only environment variables yahan define kar sakte ho
    "APP_ENV": "production" // Runtime pe app.config.ts ye value read karke prod-specific settings use karega
  }, // env block close
  "android": { // Android-specific production overrides
    "buildType": "app-bundle" // Play Store ke liye mandatory AAB format
  } // android override close
} // production profile close
terminal
# Dono platforms ke liye production build ek saath trigger karna (agar dono ready hain)
eas build --profile production --platform all # "all" iOS aur Android dono queue mein daal deta hai

# Ya sirf ek platform ke liye alag se
eas build --profile production --platform ios # Sirf iOS distribution-signed .ipa banega

# Build ka status non-interactively check karna (CI mein useful)
eas build:list --limit 1 --json # Latest build ka JSON status output milta hai, scripting ke liye

Ye output — signed .aab ya .ipa — hi wo file hai jo aap (ya EAS Submit, Chapter 11 mein) Play Console / App Store Connect pe upload karte ho for review.

Credentials Management

Har mobile platform apni app ko cryptographically "sign" karwana mandatory karta hai — taaki OS aur store dono verify kar sakein ki app ka publisher legit hai aur binary tamper nahi hui hai. iOS mein isme do cheezein lagte hain: ek signing certificate (aapki developer identity prove karta hai) aur ek provisioning profile (batata hai kaunse devices/capabilities is build ke saath allowed hain). Android mein ek hi cheez lagti hai — ek keystore (ek file jisme signing key store hoti hai, password-protected).

Traditionally ye sab manually manage karna padta tha — Xcode mein certificates generate karna, Apple Developer portal pe provisioning profiles banana, keystores ko securely kahin store karna. EAS iska poora lifecycle automate kar sakta hai:

terminal
# Interactive credentials manager kholta hai — view/generate/remove certs & keystores
eas credentials # CLI aapse platform (iOS/Android) aur profile poochega, phir options dikhayega

# Specific platform ke credentials directly manage karna
eas credentials --platform android # Sirf Android keystore-related options dikhega

eas credentials chalane par aapke paas do options hote hain: "Expo manages credentials for me" (recommended default — EAS certificates/keystores generate karta hai aur apne encrypted servers pe securely store karta hai, aur automatically har build mein apply karta hai), ya "I want to handle my own credentials" (aap apna existing certificate/keystore upload karte ho, ya local credentials.json file se reference karte ho jab aapko full manual control chahiye — jaise enterprise environments jahan certificates ek central security team issue karti hai).

credentials.json (local credentials pattern)
{
  "android": { // Android ke liye local keystore reference
    "keystore": { // keystore file ki details
      "keystorePath": "credentials/release.keystore", // Repo ke andar (gitignored) local path
      "keystorePassword": "$ANDROID_KEYSTORE_PASSWORD", // Env var se resolve hota hai, plaintext nahi rakhte
      "keyAlias": "my-app-key", // Keystore ke andar specific key ka alias name
      "keyPassword": "$ANDROID_KEY_PASSWORD" // Us specific key ka password, phir se env var se
    } // keystore block close
  } // android block close
} // root object close
🔒 Android Keystore Loss = Catastrophic

Ye sabse critical warning hai is poore chapter mein: agar aap apni production Android keystore kho dete ho, aap kabhi bhi us hi package name ke under app ko update nahi kar sakte. Google Play strictly enforce karta hai ki har update same signing key se signed ho jisse original app submit hui thi — ye ek security measure hai taaki koi attacker aapki app ka fake update na push kar sake. Agar keystore lost ho gaya (koi backup nahi, EAS-managed hone ke bawajood agar aapne kabhi export nahi kiya, ya self-managed tha aur disk crash ho gaya), sirf ek hi option bachta hai — naye package name ke saath bilkul nayi app listing banao — matlab aapke saare existing users, reviews, aur ranking history permanently kho jaate hain. Senior dev practice: eas credentials se keystore ko download karke encrypted backup (jaise ek password manager ya secure vault) mein multiple jagah store karo — sirf ek insaan ke laptop pe nahi.

iOS mein consequence thoda kam severe hai (Apple certificate revoke/regenerate karna aasan hai, provided aapke paas Apple Developer account ka access hai), lekin phir bhi agar poori team ka access lost ho jaye (jaise jisne account banaya wo company chhod de aur 2FA recovery na ho), signing chain rebuild karne mein significant downtime lag sakta hai. Isliye EAS-managed credentials generally recommended hain — Expo infrastructure encrypted storage + team-level access control provide karta hai, jo "ek developer ke laptop pe pdf/file" se zyada reliable hai.

Automating App Version Code

Har app store ek unique, monotonically-increasing internal version number require karta hai har build ke liye — Android mein ise versionCode kehte hain (ek integer, user ko kabhi nahi dikhta), aur iOS mein buildNumber (usually incrementing string). Ye versionName/CFBundleShortVersionString (jo "1.2.0" jaisa human-readable version hai, users ko dikhta hai) se alag hai — versionCode/buildNumber sirf stores ke liye internal bookkeeping hai, lekin ismein duplicate value use karna store submission ko fail kar deta hai ("this version code has already been used" jaisi error).

Manually inko track karna — especially jab team mein multiple developers builds trigger kar rahe hon — error-prone hai. Isi liye eas.json ke production profile mein autoIncrement: true set karte hain:

eas.json (version automation snippet)
"cli": { // Top-level cli config
  "appVersionSource": "remote" // Version state EAS ke servers pe centrally track hota hai, app.json mein nahi
}, // cli block close
"build": { // build profiles block
  "production": { // production profile
    "autoIncrement": true // Har production build trigger hone par versionCode/buildNumber +1 ho jayega
  } // production block close
} // build block close

appVersionSource: "remote" ka concept samajhna zaroori hai: iska matlab hai EAS khud latest version numbers ko apne server pe track karta hai (per project, per platform) — matlab agar developer A ne subah ek production build banayi (versionCode 42 → EAS ne use bump karke 43 kar diya server pe), aur developer B shaam ko dusre laptop se build banaye, EAS use pata hai last value 43 thi, to wo 44 se start karega. Agar aap iske bajaye "local" use karte (purana default), version number app.json/app.config.ts mein manually maintain hota — aur do developers ka concurrent build trigger karna easily version collision create kar sakta tha (dono ne apne local repo se same base version padha, dono ne alag builds banayi, dono same versionCode ke saath submit karne ki koshish ki). Remote tracking is race condition ko poori tarah eliminate karta hai — multi-developer teams ke liye ye hamesha safer choice hai.

💡 Hinglish Tip

Current remote version state check karne ke liye eas build:version:get chala sakte ho, aur agar kabhi manually override karna ho (jaise migration ke baad) to eas build:version:set use hota hai. Normal flow mein inko touch karne ki zaroorat nahi padti — autoIncrement khud sab handle kar leta hai.

Real-World Gotchas

⚠️ Version code bump bhool jaana

Sabse common submission-blocking mistake: agar aap autoIncrement use nahi kar rahe aur manually version bump karna bhool jaate ho, App Store Connect ya Play Console submission ko seedha reject kar dega ("This version code has already been used, try another one"). Fix simple hai — autoIncrement: true production profile mein permanently set kar do, aur is problem class ko permanently khatam kar do.

⚠️ Build queue wait times — free vs paid tier

EAS ke free tier pe builds ek shared queue mein jaate hain, aur peak hours mein wait time 20-40+ minutes tak ja sakta hai — especially iOS builds (macOS runners limited hote hain, expensive infra hai). Paid plans (Production/Enterprise) priority builds dete hain jo queue skip karte hain aur almost immediately start hote hain. Agar aapki team CI mein frequently builds trigger karti hai (jaise har PR pe preview build), free tier ka queue time development velocity ko sensibly slow kar sakta hai — ye budget planning mein factor karna senior-level consideration hai.

⚠️ "Works locally, fails on EAS Build"

Ye sabse frustrating class of bugs hai. Expo Go mein aapka app perfectly chal raha tha, local expo run:android bhi pass hua — lekin EAS Build fail ho gaya native compile step pe. Common causes: (1) ek native dependency ka version aapke local node_modules cache mein purana pinned tha lekin fresh EAS environment ne latest resolve kiya jo incompatible nikla, (2) koi native module jisko config plugin setup chahiye (jaise Android permissions ya iOS Info.plist entries add karna) — Expo Go usse silently ignore kar deta hai kyunki wo prebuild step run hi nahi karta, lekin EAS Build prebuild zaroor chalata hai aur missing config ki wajah se native compile fail ho jaata hai. Root cause: Expo Go aapko native layer se fully insulate karta hai — isliye native-level misconfigurations sirf real native build (local ya EAS) ke time surface hoti hain, Expo Go mein kabhi nahi.

⚠️ Local vs EAS config drift

Agar aapne apne local machine pe manually ios//android/ native folders edit kar diye (bina config plugin banaye), wo changes sirf aapke local prebuild output mein exist karte hain. EAS Build har baar fresh prebuild chalata hai app.json/app.config.ts + config plugins se — matlab aapke manual native edits EAS build mein completely gayab ho jayenge. Sahi approach: koi bhi native-level change ek proper config plugin ke through express karo (ya expo-build-properties jaisi existing plugin use karo), taaki wo change deterministically har build (local ho ya EAS) mein reproduce ho.

Advanced Deep-Dive — Beyond the Basics

Ab tak humne dekha ki EAS Build kya karta hai — profiles, credentials, version automation. Ab thoda root level neeche jaate hain aur dekhte hain ki cloud pe build kaise fast hota hai (caching internals), bade monorepo setups mein isko kaise configure karte hain, build lifecycle ke beech custom logic kaise inject karte hain (hooks), aur sabse important — jab native dependency resolution fail hoti hai to ek senior dev systematically debug kaise karta hai (na ki panic mein node_modules delete karke pray karta hai).

Build Caching Internals

Pehli baar jab aap koi build trigger karte ho, EAS ek completely fresh virtual machine pe npm install / yarn install (JS dependencies ke liye) aur iOS ke liye pod install (CocoaPods native dependencies ke liye) chalata hai — dono hi steps slow hote hain kyunki packages registry se download ho rahe hote hain. Speed improve karne ke liye EAS ek remote cache maintain karta hai jisme wo node_modules aur CocoaPods' Pods/ directory ko (aur kuch cases mein Gradle ka dependency cache bhi) build ke baad upload kar deta hai, key ke against.

Cache key lockfile ke hash se derive hoti hai — matlab package-lock.json, yarn.lock, ya Podfile.lock jab tak byte-for-byte same rehte hain, agli build usi cached node_modules/Pods ko restore kar leti hai aur poora install step skip ho jaata hai — sirf naye/changed packages hi resolve hote hain. Jaise hi aap koi dependency add/remove/upgrade karte ho, lockfile ka hash change ho jaata hai, aur EAS automatically samajh jaata hai ki purani cache ab invalid hai — fresh install trigger hota hai us build ke liye (sirf us build ke liye, next build phir se naye lockfile hash pe cache banayegi).

⚠️ Jab caching hi problem ban jaaye — stale dependency issue

Kabhi kabhi ek edge case hoti hai: aapne koi native config change kiya (jaise ek config plugin add kiya jo Podfile ko indirectly affect karta hai) lekin lockfile khud nahi badla — is case mein cache key same rehti hai aur EAS purani, ab-stale Pods/ directory restore kar deta hai, jo aapke naye native config ke saath mismatch ho sakti hai. Symptom aksar ek confusing CocoaPods error hota hai jo "makes no sense" lagta hai kyunki aapne to koi dependency change nahi ki. Fix: build ko explicitly clean cache ke saath force karo.

terminal
# Ye flag EAS ko batata hai ki is build ke liye remote dependency cache ignore karo
eas build --profile production --platform ios --clear-cache # Fresh pod install + npm install poori tarah se hoga, cache-related staleness eliminate ho jaati hai

Senior-level heuristic: agar build fail ho raha hai kisi aisi error ke saath jo "impossible" lagti hai (jaise "module not found" jab module clearly package.json mein hai), --clear-cache ke saath ek retry pehla cheap diagnostic step hona chahiye — isse aap turant reject kar dete ho ki ye stale-cache issue hai ya actual code/config problem.

Monorepo Builds with EAS

Agar aapka Expo app repo ke root pe nahi hai — jaise ek Turborepo/Yarn Workspaces monorepo mein apps/mobile/ ke andar, aur packages/ui/, packages/api-client/ jaise shared packages sibling directories mein hain — EAS Build isko handle kar sakta hai, lekin senior-level consideration ye hai ki build ka "working directory" kya hai aur dependency installation kahan se resolve hoti hai.

Repo structure (monorepo)
my-monorepo/                     // Repo ka root — yahan pe workspace-level lockfile (yarn.lock) rehta hai jo saare packages ki versions lock karta hai
├── apps/                         // Saare deployable apps yahan group hain — packages/ se alag isliye taaki "kya publish/deploy hota hai" clearly separate ho "kya shared logic hai" se
│   └── mobile/                   // Actual Expo RN app — EAS CLI isi directory ke andar se chalega, root se nahi
│       ├── eas.json              // eas.json app directory ke andar rehta hai (root mein nahi) kyunki build profiles is specific app ke liye hain, poore monorepo ke liye nahi
│       ├── app.json              // Is app ka Expo config — sirf mobile app ko affect karta hai
│       └── package.json          // Is app ke direct dependencies + workspace ke shared packages ka reference (jaise "ui": "workspace:*")
├── packages/                     // Shared code jo multiple apps use kar sakte hain — separate isliye taaki reusability enforce ho aur app-specific logic yahan leak na ho
│   ├── ui/                       // Shared design-system components — mobile app aur (agar ho) web app dono isse import karte hain
│   └── api-client/                // Shared API/networking layer — ek jagah maintain, sab jagah reuse, taaki API contract drift na ho alag implementations ke beech
└── package.json                  // Root package.json — workspaces field define karta hai ("workspaces": ["apps/*", "packages/*"]), poore monorepo ki dependency graph ka entry point

Senior consideration #1 — working directory: EAS CLI ko app directory ke andar se hi run karna chahiye (cd apps/mobile && eas build ...), taaki uska local eas.json aur app.json pick ho. Senior consideration #2 — dependency installation ka context: yarn/npm workspaces mein dependencies ka actual resolution root lockfile ke through hota hai (hoisting) — matlab EAS ko root lockfile tak "climb up" karna padta hai correct versions install karne ke liye, sirf app directory ke package.json se kaafi nahi hota. Modern EAS CLI ye automatically detect kar leta hai (workspace root ka lockfile dhoond ke), lekin agar aapka CI runner ya custom Docker setup involved hai, ye assumption explicitly verify karna senior-level due diligence hai.

apps/mobile/eas.json (monorepo-aware profile)
{
  "cli": { // CLI-level config, app directory ke andar hi scoped
    "version": ">= 12.0.0" // Monorepo workspace resolution ke liye recent CLI version zaroori hai
  }, // cli block close
  "build": { // Build profiles — inka scope sirf is "mobile" app tak limited hai
    "production": { // production profile
      "distribution": "store", // Store submission format
      "env": { // Env vars is build ke liye
        "EXPO_MONOREPO_ROOT": "../.." // Custom hook scripts ko batane ke liye monorepo root kitna upar hai (relative path), agar koi shared asset copy karna ho hooks mein
      } // env block close
    } // production profile close
  } // build block close
} // root object close
🧠 Senior Dev Note

Bade monorepos mein sabse common mistake ye hai ki team CI system (jaise GitHub Actions) ko root se eas build chalane deti hai bina explicitly app directory mein cd kiye — CLI confusing errors deta hai ya galat eas.json pick karne ki koshish karta hai. Senior practice: CI job ke pehle hi step mein explicitly cd apps/mobile karo, aur agar shared packages/ mein koi change hua hai jisse app affect hota hai, CI ko turborepo/nx jaisa tool use karke pehle detect karna chahiye "kya mobile app rebuild trigger karna zaroori hai" — taaki har unrelated commit pe unnecessary EAS build queue mein na jaye (paid build minutes bachte hain).

Custom Build Hooks / Scripts

EAS Build lifecycle ke specific points pe automatically kuch reserved npm script names ko detect karke run kar deta hai, agar wo aapke package.json ke scripts mein defined hon — inhe build hooks kehte hain. Sabse commonly used do hain eas-build-pre-install (dependencies install hone se pehle chalta hai) aur eas-build-post-install (install hone ke baad, lekin native compile shuru hone se pehle). Inke alawa eas-build-pre-build, eas-build-post-build, aur eas-build-on-success/eas-build-on-error bhi available hain, jo respectively native build se pehle/baad aur build ke final outcome pe chalte hain.

Real-world use case: maan lo aapko ek build-time-generated file chahiye — jaise ek version.json jisme exact git commit hash aur build timestamp embed ho (crash reports mein "kaunsi build thi ye" trace karne ke liye), ya ek custom code-signing step jo third-party enterprise MDM tool ke saath integrate karta hai.

package.json (hook scripts)
{
  "scripts": { // npm scripts block — EAS in reserved naamon ko dhoondta hai
    "eas-build-pre-install": "echo 'Starting install for commit '$EAS_BUILD_GIT_COMMIT_HASH", // Install se pehle chalta hai — EAS built-in env vars (jaise commit hash) yahan available hote hain
    "eas-build-post-install": "node ./scripts/generate-build-info.js" // Install ke baad, native compile se pehle — custom Node script chalata hai jo version.json generate karta hai
  } // scripts block close (baaki scripts jaise "start", "test" yahan already hote hain, ye do naye add hue)
} // root object close
scripts/generate-build-info.js
// Ye script eas-build-post-install hook se automatically chalta hai, native compile se theek pehle
const fs = require("fs"); // Node ka built-in filesystem module — file likhne ke liye chahiye

const buildInfo = { // Object jo hum JSON file mein serialize karenge
  commit: process.env.EAS_BUILD_GIT_COMMIT_HASH, // EAS automatically ye env var inject karta hai — current commit ka full hash
  profile: process.env.EAS_BUILD_PROFILE, // Kaunsa build profile use ho raha hai (development/preview/production) — EAS-injected env var
  builtAt: new Date().toISOString(), // Build ka exact UTC timestamp, human-readable ISO format mein
}; // buildInfo object complete

fs.writeFileSync( // Synchronous write use kiya kyunki hook script ko complete hone tak build agla step start nahi karega
  "./assets/version.json", // App bundle ke andar accessible location — runtime pe app isse import/require kar sakti hai
  JSON.stringify(buildInfo, null, 2) // Object ko pretty-printed JSON string mein convert kiya (2-space indent, readability ke liye)
); // writeFileSync call complete — file ab native build ke andar bundle hogi

console.log("Generated version.json for build:", buildInfo); // EAS build logs mein ye print hoga — debugging ke liye useful confirmation
⚠️ Hooks silently fail ho sakte hain

Agar hook script mein error throw hoti hai (non-zero exit code), EAS poori build ko fail kar deta hai — ye good hai (silent corruption se better hai), lekin error message kabhi kabhi build logs mein bahut neeche scroll karne ke baad milta hai. Senior habit: hook scripts ko eas build --local se pehle apne local machine pe hi manually test karo, taaki cloud queue mein wait karke fail hone ka cycle avoid ho.

Troubleshooting Native Dependency Resolution Failures

Ye wo skill hai jo actually "senior" React Native developer ko differentiate karti hai — jab build ek CocoaPods (iOS) ya Gradle (Android) dependency conflict ke saath fail ho, panic mein rm -rf node_modules && npm install chala ke "shayad theek ho jaayega" wali approach lena anti-pattern hai. Systematic approach ye hoti hai:

  1. Actual error line dhoondo, poora stack trace scroll mat karo bas. EAS build logs mein CocoaPods error ka format aksar hota hai "[!] CocoaPods could not find compatible versions for pod 'X'" — ye exact bata deta hai kaunsi library aur kaunse do version constraints conflict kar rahe hain (jaise ek dependency X ~> 2.0 chahti hai, dusri X ~> 3.0). Gradle mein similarly "Could not resolve com.example:lib:1.2.0" ya "Duplicate class found" jaisi specific error milti hai.
  2. Check karo ki ye ek known issue hai kisi specific package version ka. Us library ke GitHub repo pe "Issues" tab search karo exact error message ke saath — native dependency conflicts extremely common hain jab ek library kisi outdated peer dependency pe pin hoti hai. Expo GitHub discussions aur Stack Overflow bhi first stop honi chahiye, dobara research se pehle.
  3. npx expo install --check chalao. Ye command Expo SDK ke against saare installed packages ki versions verify karti hai aur flag karti hai koi bhi jo known-incompatible hai us SDK version ke saath — bahut saari native conflicts root cause mein "galat Expo SDK ke liye galat library version" hoti hain, aur ye tool exactly wahi catch karne ke liye bana hai.
  4. Local repro try karo (agar possible ho). Agar Mac available hai, npx expo prebuild --clean chala ke local ios/android folders fresh generate karo aur wahi error locally reproduce karne ki koshish karo — local pe iteration cycle EAS build queue se kaafi fast hota hai, debugging loop tez ho jaata hai.
  5. Sabse last resort: caches clear karo. eas build --clear-cache (EAS-side cache), aur locally cd ios && pod deintegrate && pod install ya cd android && ./gradlew clean — lekin ye tab try karo jab pehle 4 steps se root cause samajh mein aa chuka ho ki ye ek stale-state issue hai, na ki blindly hoping ki "kuch delete karne se theek ho jaayega".
🔒 "Delete node_modules and pray" anti-pattern

Blindly node_modules, lockfile, aur caches delete karke reinstall karna kabhi kabhi accidentally problem "fix" kar deta hai (naya lockfile alag versions resolve kar deta hai) — lekin isse aapko root cause kabhi pata nahi chalta, aur wahi issue future mein kisi aur teammate ke machine pe ya CI mein phir se surface ho sakta hai bina warning ke. Senior debugging discipline ka core principle: samjho pehle, fix baad mein — chahe fix simple ho, understanding shortcut nahi lena chahiye.

🎯 Interview Questions — Senior React Native Developer

Neeche wo interview questions hain jo senior React Native / mobile infra roles mein EAS Build ke topic pe commonly poochhe jaate hain — internals, debugging scenarios, aur architecture trade-offs ka mix.

1. Walk me through the full lifecycle of an EAS Build — from running eas build to an installable binary existing.

Sabse pehle EAS CLI local project ko tarball mein compress karta hai (aapki source code, .gitignore-respecting — matlab node_modules jaisi cheezein exclude hoti hain) aur ise EAS ke servers pe upload karta hai. Server side pe ek build job queue mein jaata hai — agar aapka tier priority builds support karta hai, ye queue jaldi clear hoti hai, warna shared queue mein wait hota hai. Ek baar worker machine assign hone par (iOS ke liye macOS runner, Android ke liye Linux/macOS), EAS pehle project ko unpack karta hai, phir prebuild chalata hai (agar managed workflow hai) — ye app.json/config plugins se native ios//android folders generate karta hai from scratch. Uske baad eas-build-pre-install hook (agar defined hai), phir dependency install (npm/yarn install + iOS ke liye pod install, cache se ya fresh), phir eas-build-post-install hook, phir actual native compile step (xcodebuild ya ./gradlew), phir credentials apply karke binary ko code-sign kiya jaata hai, aur finally output artifact (.ipa/.apk/.aab) EAS ke storage pe upload hota hai aur aapko download link + QR code mil jaata hai.

2. "Prebuild" step exactly kya karta hai, aur ye Expo Go vs EAS Build ke behaviour mein difference kyun create karta hai?

Prebuild (npx expo prebuild, jo EAS internally automatically chalata hai managed projects ke liye) app.json/app.config.ts aur installed config plugins ko read karke actual native ios/ aur android/ source folders generate karta hai — Info.plist, AndroidManifest.xml, Xcode project files, Gradle build files, sab kuch is step mein banta hai. Expo Go ye step kabhi nahi chalata — Expo Go ek pre-built generic app hai jo already store se install hoti hai, isliye wo app.json ke custom permissions, custom native config plugins, ya kisi bhi native-level customization ko silently ignore kar deta hai (kyunki uska native layer already fixed hai, build-time pe generate nahi ho raha). Isi wajah se ek bug jo purely native config-level hai (jaise missing camera permission entry) sirf real native build (local ya EAS) ke prebuild step ke baad hi surface hota hai, Expo Go mein kabhi dikhega hi nahi.

3. Build expo run:ios se local machine pe pass ho raha hai, lekin EAS Build pe dependency error ke saath fail ho raha hai — environments mein kya different ho sakta hai, aur aap kaise debug karoge?

Sabse common root causes: (1) Local node_modules/Pods stale ho gaye hain — aapke local machine pe purani resolved versions cached hain jo kabhi kaam kar rahi thi, lekin fresh EAS environment lockfile se re-resolve karta hai aur ek naya incompatible version le aata hai (ye tab hota hai jab lockfile properly commit nahi hua ya ^/~ range use ho rahi hai kisi dependency mein). (2) Xcode/CocoaPods/Android SDK version mismatch — aapke local machine pe alag toolchain version installed hai jo EAS ke pinned build image se differ karta hai. (3) Env variables missing hain EAS side pe jo local .env file mein the (EAS Secrets set nahi kiye gaye). Debug approach: pehle exact error message compare karo (Gradle/CocoaPods dono verbose error dete hain), phir eas.json mein image field check karo ki kaunsa build image pin hai aur uska Xcode/SDK version apne local se match karo, phir lockfile commit-status verify karo (git status se dekho ki package-lock.json/Podfile.lock committed aur up-to-date hai), aur agar sab match kar raha hai to eas build --clear-cache se ek fresh retry lo taaki stale cache eliminate ho.

4. Build caching internally kaam kaise karta hai, aur aap kab explicitly cache clear karoge?

EAS node_modules aur CocoaPods' Pods/ ko ek remote cache mein store karta hai, key lockfile ke content-hash se derived hoti hai. Jab tak lockfile same rehta hai, agli build cached dependencies restore kar leti hai aur install step largely skip ho jaata hai — bahut faster. Cache clear karne ka legitimate use case tab hota hai jab aapko lockfile-independent koi cheez change hui ho jo dependency resolution ko affect kar sakti hai — jaise ek naya config plugin add kiya jo Podfile generation ko change karta hai, ya aapko suspect hai ki cached state corrupt/stale hai aur error "impossible" lag raha hai given current code. Command: eas build --clear-cache. Isko habitually har build pe use karna anti-pattern hai — isse aap caching ka poora speed benefit chhod dete ho; ye ek targeted diagnostic/fix tool hai, default behaviour nahi.

5. Aapki team ek Turborepo monorepo mein migrate kar rahi hai jisme Expo app root pe nahi, apps/mobile/ ke andar hai. EAS Build setup mein aap kya consider karoge?

Sabse pehle, eas.json ko app directory ke andar rakhna hoga (root mein nahi), kyunki build profiles is specific app ke liye scoped hain. CI pipeline ko explicitly app directory mein cd karke eas build chalana hoga, root se nahi. Dependency resolution ke liye — yarn/npm workspaces hoisting ki wajah se actual versions root lockfile se resolve hoti hain, isliye ye ensure karna hoga ki EAS ka build environment monorepo root tak "climb up" kar sake lockfile dhoondne ke liye (modern EAS CLI ye automatically karta hai). Ek aur important consideration: selective triggering — agar sirf packages/ui mein ek unrelated change hui hai jo mobile app ko affect nahi karta, CI ko Turborepo ke dependency graph analysis (turbo run build --filter=mobile...[HEAD^1] jaisa) use karke decide karna chahiye ki actually EAS build trigger karna zaroori hai ya nahi — warna paid build minutes waste hote hain har unrelated commit pe.

6. Build hooks (eas-build-pre-install, eas-build-post-install) kya hote hain, aur ek real use case do jaha ye zaroori ho?

Ye reserved npm script names hain jo package.json ke scripts block mein define karne par EAS automatically build lifecycle ke specific points pe chala deta hai — eas-build-pre-install dependency install se pehle, eas-build-post-install install ke baad lekin native compile se pehle. Real use case: build-time pe ek version.json file generate karna jisme exact git commit hash (EAS_BUILD_GIT_COMMIT_HASH env var se) aur timestamp embed ho — production mein crash reports ko exact build ke saath correlate karne ke liye extremely useful (Sentry jaisa crash reporting tool isse tag kar sakta hai). Ek aur real scenario: enterprise apps jinhe custom internal code-signing step chahiye hota hai jo standard EAS credentials flow se bahar hai — wo logic eas-build-post-install hook mein inject kiya ja sakta hai.

7. Ek team kab apni khud ki self-hosted build infrastructure choose karegi, EAS Build ke cloud service ke bajaye?

Ye ek classic build-vs-buy trade-off hai. Self-hosting (jaise apne CI runners pe macOS machines rakhna, Fastlane ke saath) tab justify hota hai jab: (1) Build volume extremely high hai — agar team roz sainkdon builds trigger karti hai, EAS ke usage-based pricing se apna khud ka infra (fixed cost) cheaper pad sakta hai break-even ke baad. (2) Extreme compliance/security requirements — kuch enterprise/regulated industries (banking, healthcare) source code ko kisi third-party cloud pe bhejne ki policy allow hi nahi karti, chahe wo encrypted/ephemeral hi kyun na ho. (3) Highly custom build pipeline jo standard EAS hooks se bahar hai — jaise multi-stage internal artifact signing workflows jo bahut specific internal tools pe depend karte hain. (4) Queue time is a hard blocker aur paid EAS priority tier bhi acceptable nahi lag raha given cost structure. Trade-off ye hai ki self-hosting ke saath aapko khud macOS machine provisioning, OS/Xcode updates, credential security, aur scaling manage karni padti hai — jo non-trivial ongoing engineering cost hai. Zyadatar teams (especially mid-size tak) ke liye EAS Build ka managed convenience is cost se zyada value deta hai; self-hosting sirf specific scale/compliance triggers pe hi senior-level justified choice banta hai.

8. Android production keystore lost ho gaya hai aur koi backup nahi hai. Kya options hain, aur is scenario ko prevent karne ke liye aap kya architecture set karte?

Agar keystore permanently lost hai aur EAS-managed bhi tha lekin kabhi export/backup nahi kiya gaya, sirf ek hi option bachta hai: naye package name ke saath bilkul nayi Play Store listing banana — jiska matlab hai saare existing users, ratings, reviews, aur search ranking history permanently kho jaate hain (users ko manually naye app pe migrate karna padega, jo bahut users lose karwa deta hai). Prevention architecture: EAS-managed credentials use karo (Expo ka encrypted, access-controlled storage manual laptop storage se zyada reliable hai), aur additionally eas credentials se keystore ko periodically export karke ek team-level secure vault (jaise 1Password/Vault, sirf senior engineers/leads access ke saath) mein encrypted backup rakho — single point of failure (ek insaan ka laptop) kabhi na ho. Agar Google Play App Signing enroll kiya hai (jo ab Play Store naye apps ke liye mandatory bhi karta hai), Google khud aapki "app signing key" securely manage karta hai aur aap sirf ek "upload key" use karte ho jise agar kho bhi diya, Google ke identity-verification process se reset karwaya ja sakta hai — ye legacy pure-manual keystore management se significantly safer architecture hai.

9. EAS build image pinning (eas.json ke image field) kyun matter karta hai, aur agar aap ise pin nahi karte to kya risk hai?

image field specific karta hai ki build kis versioned combination of Xcode/Android SDK/Node/CocoaPods (aur baaki toolchain) pe chalegi — EAS periodically naye default images release karta hai jab Apple/Google naye Xcode/SDK versions release karte hain. Agar aap image explicitly pin nahi karte, aapki build silently EAS ke current default image use karti hai — jo kabhi bhi EAS ki taraf se change ho sakta hai (naya default rollout hone par), bina aapke eas.json mein kuch change kiye. Isse ek subtle risk create hota hai: aaj jo build successfully pass ho rahi thi, kal EAS ka default image update hone ke baad (naya Xcode version jo koi behavior change laaya) wahi build fail ho sakti hai — bina aapke codebase mein koi change kiye. Senior practice: eas.json mein explicitly image pin karo (jaise "image": "latest" ki jagah ek specific tagged version), aur upgrade ko ek deliberate, tested step banao — na ki EAS ki taraf se ek silent, untested toolchain change ho jaaye production build pipeline mein.
