What OTA (Over-The-Air) Updates Actually Are

Sabse pehle root question: ye possible kaise hai ki koi app apna code update kar le bina App Store ya Play Store ke review process se guzre? Iska answer React Native ke fundamental execution model mein chhupa hai, isliye pehle wahi samjhte hain.

Ek pure native app (jaise Swift/Kotlin mein likha gaya) mein saara logic compile-time pe hi native binary ke andar bake ho jaata hai — jab aap Xcode/Android Studio se build karte ho, saara code machine code mein convert hoke .ipa/.apk ke andar permanently embed ho jaata hai. Isliye ek single line change karne ke liye bhi — chahe wo ek button ka color hi kyun na ho — aapko poora naya binary banana padta hai, aur store pe naya review submit karna padta hai.

React Native alag tarike se kaam karta hai. Aapka JS/TS code compile hoke native machine code nahi banta — ye ek JS bundle (ek bada .js file, Metro bundler se generate) banta hai, jo native binary ke andar ek asset ke roop mein embed hota hai (ya remote se fetch hota hai). Jab app launch hoti hai, native runtime (Hermes engine) is JS bundle ko parse aur execute karta hai — bilkul waise jaise browser ek webpage ka JS load karke chalata hai. Native binary sirf ek "shell" hai jo JS engine, native modules, aur rendering infrastructure (Fabric) provide karta hai — actual app logic (screens, business logic, UI tree construction) JS bundle ke andar hoti hai jo runtime pe load hoti hai.

Yahi wo fundamental fact hai jispe EAS Update poora tika hua hai: agar JS bundle runtime pe load hota hai (compile-time pe binary ke andar hardcoded nahi hota), to iska matlab hai ki agar hum is JS bundle ko binary banne ke baad bhi replace kar dein — user ke device pe already installed binary ko chhue bina — app ka behaviour change ho jayega, bina naya native binary banaye. EAS Update exactly yahi karta hai: ye aapka naya JS bundle + updated assets (images, fonts) EAS ke servers pe upload karta hai, aur jab user ka app agli baar launch/foreground hota hai, wo apne current runtime ke liye available naya update check karta hai, download karta hai, aur agli launch se naya JS bundle use karta hai — sab kuch bina store review ke, kyunki store ne jo binary approve kiya tha wo bilkul waisa hi hai, sirf uske andar ka "content" (JS bundle) badla hai.

ℹ️ Web analogy jo click karwati hai

Iske baare mein aise socho: ek website deploy karne ke baad aapko browser vendors se koi review nahi maangni padti — aap seedha naya HTML/JS/CSS server pe daal dete ho aur next page load pe user ko naya version mil jaata hai. React Native mein bhi JS bundle conceptually waisa hi "content" hai jo runtime pe fetch/load hota hai — bas yahan "server" EAS ka update server hai aur "next page load" app ka next launch hai.

Technically, EAS Update ek manifest-based delivery system hai: har published update ke liye ek manifest (JSON metadata — kaunsa JS bundle, kaunse assets, kaunsa runtime version target hai) generate hota hai. App launch pe expo-updates native module ye manifest EAS server se fetch karta hai, compare karta hai currently-installed update se, aur agar naya available hai to bundle download karke local storage mein cache kar leta hai. Ye poora process background mein hota hai — user ko koi "installing update..." wala popup nahi dikhta by default, bas agli app open pe naya version silently active ho jaata hai.

The Critical Boundary: What OTA CAN'T Update

Ab is chapter ka sabse important concept — aur ye wahi cheez hai jo bahut teams (including experienced developers) galat samajhte hain, aur is galat samajh ki wajah se production incidents create karte hain.

🔒 OTA Updates SIRF JS/Assets Update Kar Sakte Hain — Kabhi Native Code Nahi

EAS Update sirf wahi cheez badal sakta hai jo runtime pe JS engine load karta hai — matlab JS/TS code aur uske assets (images, fonts, JSON data). Ye kabhi bhi ye cheezein nahi kar sakta:

  • Naya native module add karna — agar aapne react-native-ble-plx jaisi ek nayi native dependency install ki jisme native (Swift/Kotlin) code hai, ye code sirf compile-time pe binary ke andar link hota hai. OTA update se ye module device pe kabhi nahi pahunch sakta — device ka installed binary literally us native code ko contain hi nahi karta.
  • Native permissions change karna — camera, location, bluetooth jaisi permissions Info.plist (iOS) ya AndroidManifest.xml (Android) mein declare hoti hain, jo compile-time pe binary mein bake hoti hain. Naya permission add karna OTA se impossible hai.
  • App icon ya splash screen (native level) change karna — ye native resources hain jo binary ke andar compiled asset catalogs (iOS) ya resource files (Android) ke roop mein store hote hain.
  • Native config level changes — jaise Info.plist/AndroidManifest.xml ke andar koi bhi entry, deep link scheme registration, native background modes, etc.
  • Expo SDK ya React Native version upgrade karna — ye upgrades native runtime ke core hi change karte hain (Hermes version, Fabric renderer version, native dependency versions) — ye fundamentally ek naya binary hai, JS-level change nahi.

In sab cases mein ek fresh native build (EAS Build) aur naya store submission mandatory hai. Sabse dangerous misunderstanding jo teams karte hain: production mein ek native-level crash aata hai (jaise ek native module crash kar raha hai kisi permission ki wajah se), aur team panic mein "hotfix" ke liye eas update chala deti hai — jo kaam hi nahi karega, kyunki bug native layer mein hai aur JS bundle replace karne se native code touch hi nahi hota. Ye realization production incident ke beech mein aana bahut costly hota hai — is boundary ko pehle se samajhna zaroori hai.

Ek helpful mental model: OTA update sirf wahi cheez badal sakta hai jo aap bina naya native build banaye local machine pe bhi change kar sakte the aur sirf JS reload/fast-refresh se dekh sakte the (jaise ek screen ka layout, ek business logic bug, ek API call, ek string). Agar change ke liye eas build chalana padta — matlab OTA se bhi nahi ho sakta.

Change TypeOTA Update se Possible?
JS/TS logic fix (bug fix, business logic)Haan
UI/styling change (StyleSheet, layout)Haan
Image/font/JSON asset replaceHaan
API endpoint URL change (JS-level config)Haan
Naya native module add karnaNahi — naya native build chahiye
Naya permission (camera/location) add karnaNahi — naya native build chahiye
App icon/splash (native) change karnaNahi — naya native build chahiye
Expo SDK / RN version upgradeNahi — naya native build chahiye

Runtime Versions — How Compatibility Is Enforced

Ab agla sawal: agar OTA sirf JS update kar sakta hai, to EAS kaise ensure karta hai ki jo JS update aap publish kar rahe ho wo actually us device ke installed native binary ke saath compatible hai? Sochiye — agar aapne apne code mein ek naya native module use karna start kiya (jo sirf naye binary mein hai), aur galti se wo JS update purane binary wale users ko bhi mil gaya jinke paas wo native module hai hi nahi — app seedha crash karegi launch pe, kyunki JS us native module ko call karne ki koshish karega jo exist hi nahi karta.

Isi problem ko solve karne ke liye runtimeVersion concept hai. Runtime version ko ek "fingerprint" of your native code samjho — ye ek string/value hai jo batata hai ki is binary ka native surface area (native modules, native config) kya hai. EAS Update ek strict rule follow karta hai: ek JS update sirf un devices ko deliver hoga jinka installed binary ka runtime version, update ke target runtime version se exactly match karta ho. Agar match nahi karta, EAS us update ko us device ko bilkul bhi nahi bhejta — device apna purana JS bundle hi chalata rehta hai, jab tak use koi compatible update na mile.

Runtime version compute karne ke do main policies hain, jo app.json/app.config.ts mein set hoti hain:

  • "policy": "sdkVersion" — runtime version simply installed Expo SDK version ke basis pe set hota hai (jaise "exposdk:51.0.0"). Simple hai, lekin coarse-grained — agar aapne SDK version change kiye bina bhi ek naya native module add kiya (jaise npx expo install se koi third-party native package), ye policy usse detect nahi karegi, kyunki SDK version wahi raha. Matlab ek incompatible JS update galti se same-runtime-version wale purane binary ko bhi mil sakta hai — aur crash kar sakta hai.
  • "policy": "fingerprint" — ye zyada precise approach hai: ye actually aapke native project ka ek cryptographic hash compute karta hai — native dependencies, config plugins, native config files (sab kuch jo prebuild ke time native project banata hai) ko scan karke. Iska matlab agar aap koi native-level change karte ho (naya native module, config plugin change, native permission add) — chahe SDK version wahi rahe — fingerprint automatically change ho jaayega, aur EAS us purane runtime version wale devices ko naya (incompatible) JS update bhejna band kar dega. Ye zyada safe hai isliye modern projects mein "fingerprint" hi recommended default hai.

(comments added for teaching — real JSON doesn't support them, remove before use)

app.json (runtimeVersion policy)
{
  "expo": { // "expo" root config key
    "name": "my-app", // App ka display name
    "slug": "my-app", // URL-safe project identifier, EAS project se link karta hai
    "runtimeVersion": { // runtimeVersion object — native code ka "fingerprint" define karta hai
      "policy": "fingerprint" // native project (deps + config plugins) ka hash use hoga fingerprint ke roop mein
    }, // runtimeVersion block close
    "updates": { // "updates" block — EAS Update client (expo-updates) ka runtime behaviour control karta hai
      "url": "https://u.expo.dev/your-project-id", // EAS Update manifest server ka endpoint, jaha app update check karega
      "fallbackToCacheTimeout": 0 // 0ms = agar naya update available hai to fetch complete hone tak wait mat karo, cached version se launch karo (non-blocking)
    } // updates block close
  } // expo block close
} // root object close
🧠 Senior Dev Note

"policy": "sdkVersion" purana default tha aur simple projects ke liye kaam chala leta hai, lekin jaise hi aapki team native dependencies frequently add/change karti hai (jo real production apps mein normal hai), "fingerprint" policy migrate karna strongly recommended hai — ye silent-crash class ke bugs ko structurally prevent karta hai, kyunki EAS khud detect kar leta hai ki native surface change hua hai, aapko manually track nahi karna padta.

Practically iska matlab ye hai: jab bhi aap ek naya native build banate ho (chahe SDK version same ho), us build ka runtime version compute hota hai us waqt ke native project state se. Jab aap eas update chalate ho, EAS aapke current local project se bhi wahi runtime version compute karta hai aur update ko usi runtime version "bucket" mein publish karta hai — sirf wahi devices jinka installed binary us exact bucket mein hai, wo update receive karenge.

Update Channels

Runtime version compatibility ensure karta hai ki JS update crash na kare — lekin ek aur layer chahiye: aap kaunse builds ko kaunsa update dena chahte ho, deliberately. Jaise aap nahi chahte ki QA testing ke liye publish kiya gaya ek experimental update accidentally production users tak pahunch jaaye — chahe unka runtime version match bhi karta ho. Isi ke liye channels hain.

Ek channel bas ek named "stream" hai — jaise production, preview, development — jisse aap updates publish karte ho. Har build profile (eas.json mein) ek specific channel se bind hota hai (build time pe hi ye binding binary ke andar embed ho jaati hai). Jab wo binary launch hoti hai, wo sirf apne bound channel pe published updates check karti hai — kisi aur channel ke updates use dikhte hi nahi.

(comments added for teaching — real JSON doesn't support them, remove before use)

eas.json (channels wired to build profiles)
{
  "cli": { // CLI-level config, minimum version enforce karta hai
    "version": ">= 12.0.0" // Is config format ke saath compatible minimum EAS CLI version
  }, // cli block close
  "build": { // har build profile define hota hai yahan
    "development": { // local dev iteration ke liye profile
      "developmentClient": true, // expo-dev-client bundled hoga is build mein
      "distribution": "internal", // Directly install hoga, store review nahi
      "channel": "development" // Is build ka binary sirf "development" channel ke updates check karega
    }, // development profile close
    "preview": { // QA/stakeholder testing ke liye profile
      "distribution": "internal", // Link/QR se direct install
      "channel": "preview" // Is build ka binary sirf "preview" channel ke updates check karega — production se isolated
    }, // preview profile close
    "production": { // store submission ke liye profile
      "distribution": "store", // App Store/Play Store submission format
      "channel": "production" // Is build ka binary sirf "production" channel ke updates check karega — real users yahi hain
    } // production profile close (no trailing comma, last key)
  } // build block close
} // root object close

Is setup ka practical flow: jab aap eas build --profile production chalate ho, us binary ke andar channel: "production" hardcode ho jaata hai (build time pe). Jab aap baad mein eas update --channel production chalate ho, wo update sirf usi channel se bound saare installed binaries (jinka runtime version bhi match karta ho) ko milta hai — preview ya development channel wale binaries ko bilkul nahi milta, chahe unka runtime version same hi kyun na ho.

💡 Hinglish Tip

Channel aur runtime version dono independent dimensions hain jo mil ke ek update ki "audience" define karte hain: channel batata hai "kaunse build stream ke liye hai" (deliberate, aapke control mein), aur runtime version batata hai "kaunse native binary shape ke saath safe hai" (automatic safety check). Dono match hone chahiye tabhi update deliver hota hai.

Deploying an Update

Ab actual deploy karte hain. Command hai eas update — is command ko chalane par step-by-step ye hota hai: (1) local machine pe Metro bundler chalke aapka current JS code + assets ka production bundle banata hai (jaisa build time pe hota, bas ab standalone), (2) is bundle ko EAS ke servers pe upload karta hai, (3) EAS server ek naya "update" record banata hai jisme is bundle ka reference, current runtimeVersion, aur specified channel included hota hai, aur channel ka manifest is naye update ko point karne lagta hai, (4) jab bhi ek matching device (same channel + same runtime version) agli baar app open/foreground karta hai, wo naya manifest fetch karta hai, dekhta hai ki update available hai, bundle download karke local cache mein store karta hai, aur agli launch se naya bundle active ho jaata hai (current running session turant nahi badalta, restart chahiye hota hai — jab tak aap explicitly reload trigger na karo code se).

terminal
# eas-cli install/updated hona chahiye pehle (global ya npx se)
npx eas-cli --version # Confirm karo ki CLI installed hai aur version eas.json ki requirement se match karta hai

# Production channel pe ek naya JS update publish karna, ek human-readable message ke saath
eas update --branch production --message "fix login bug" # --branch yahan channel ke naam jaisa treat hota hai (branch aur channel default mein same naam se linked hote hain)

# Explicitly kis platform ke liye publish karna hai bhi specify kar sakte ho
eas update --branch production --platform android --message "android-only asset fix" # Sirf Android devices is update ko dekhenge, iOS untouched

# Publish hone ke baad, published updates ki list dekhna (kaunse runtime version pe kaunsa gaya)
eas update:list --branch production # Har update ka ID, message, runtime version, aur publish time dikhega
ℹ️ "Branch" vs "Channel" confusion

EAS Update mein technically ek "branch" hai jaha updates actually publish hote hain (ek ordered history of updates, git branch jaisa concept), aur ek "channel" hai jo binary-facing naam hai jise builds subscribe karte hain. Default setup mein branch aur channel same naam se ek-dusre se linked hote hain (jaise production branch → production channel), isliye zyadatar practical use mein aap dono naam ko interchangeably treat kar sakte ho — lekin advanced setups mein aap ek channel ko different branches ke beech switch kar sakte ho bina naya build banaye (rollback ke liye exactly yahi use hota hai, next section mein dekhenge).

Naya update device tak turant nahi pahunchta — expo-updates module by default app launch/foreground event pe hi manifest check karta hai (background polling nahi, battery-friendly design hai). Isliye agar aapne eas update chalaya, aur ek user ka phone tabhi background mein pada hai, use naya update tabhi milega jab wo app dobara open karega.

Reverting a Bad Update

Ab sochiye aapne ek update publish kiya aur usme bug nikla — production users ko crash ho raha hai. Kya karein? Command hai eas update:rollback (ya conceptually equivalent: purani update ko dobara publish/point karna) — lekin isko samajhne ke liye ek important mental model clear karna hoga: "rollback" ka matlab literally "undo" nahi hai — EAS Update mein har published update permanently stored rehta hai apne poore bundle ke saath. Rollback actually karta hai ye: channel ke pointer ko wapas ek known-good, purani update pe point kar deta hai. Naya JS koi generate nahi hota — bas channel ab bataata hai "sabse latest 'active' update wo hai jo pehle publish hua tha", aur naye matching devices ko wahi purana (working) bundle serve hota hai.

terminal
# Pehle dekho production branch pe kaunse updates published hain, kis order mein
eas update:list --branch production # Har entry ka update-group ID milega, ye rollback target select karne ke liye chahiye

# Channel ko ek specific (purani, known-good) update pe wapas point karna
eas channel:rollback production # Interactive prompt aayega, jisse aap list se purana working update choose kar sakte ho

# Ya directly ek specific update ko channel pe re-publish/point karna (non-interactive, scriptable)
eas channel:edit production --branch production # Channel ko explicitly ek branch se (re-)link karta hai, CI scripts ke liye useful

Iska practical implication ye hai ki rollback almost instant hai — koi naya bundle build ya upload nahi karna padta, bas ek server-side pointer change hota hai. Agli baar jab matching device launch hoga, use naya manifest milega jo purani (safe) update ko point karta hai, aur wo download karke us pe switch ho jaayega. Ye speed hi EAS Update ke sabse bade practical advantages mein se ek hai — ek buggy native build ko fix karne mein hours/days lag sakte hain (naya build, naya store review), lekin ek buggy OTA update ko rollback karne mein minutes.

🧠 Senior Dev Note

Isi rollback speed ki wajah se, senior teams ka non-negotiable practice hota hai: har update pehle preview channel pe publish karo, kuch ghante/din real device pe test karo, aur sirf confident hone ke baad wahi build production channel pe publish karo. Directly production pe publish karna "chalo try karte hain" wali mentality hai jo bilkul avoid karni chahiye — rollback fast hai, lekin ek crash-causing update kuch minutes ke liye bhi live rehne se real users ko crash ka experience mil chuka hota hai, jo trust aur reviews damage karta hai.

Real-World Gotchas

⚠️ Users jo app dobara nahi kholte, stuck reh jaate hain

Agar koi user apni app hafton/mahino tak nahi kholta, uska binary us waqt ke runtime version pe hi "frozen" rehta hai. Agar aapne beech mein naya native build (naya runtime version) bhi release kar diya ho, purane users us naye runtime version target karne wale updates kabhi receive nahi karenge — unhe sirf tab tak purane runtime-version-matching updates milte rahenge jab tak wo app open karte rahein, ya jab tak wo store se ek fresh naya native build install na karein (jo unhe khud initiate karna padega, store update ke through). Isliye OTA updates ko "sabhi users tak turant pahunch jaayega" maan lena galat hai — active users fast update pate hain, inactive/dormant users significantly lag sakte hain.

⚠️ Update check timing — instant nahi hota

Update checks by default sirf app launch ya foreground event pe hote hain, koi continuous background polling nahi hoti (battery consideration se by design). Matlab agar aap eas update chalate ho, aur ek user ki app already open hai aur wo use kar raha hai, use update turant nahi milega — tab tak nahi jab tak wo app close/background karke dobara open na kare (ya aap explicitly programmatic check trigger karo Updates.checkForUpdateAsync() se, jo aap khud call kar sakte ho app ke andar kisi useful moment pe, jaise app-foreground listener mein).

⚠️ Runtime version mismatch silently ignore hota hai, error nahi deta

Ye ek confusing debugging experience create karta hai jo bahut developers ko pehli baar surprise karta hai: agar aap ek update publish karte ho jiska runtimeVersion device ke installed binary se match nahi karta, EAS koi error nahi dikhata — update bas silently us device ko deliver hi nahi hota, jaise koi naya update exist hi nahi karta. Aapko koi failure log, koi crash, kuch nahi dikhega — sirf "update kaam nahi kar raha" jaisa symptom milega. Jab bhi update apply nahi ho raha lage, sabse pehle check karo: (1) channel match kar raha hai kya, (2) runtime version match kar raha hai kya (eas update:list se published update ka runtime version, aur test device pe installed binary ka runtime version compare karo). Zyadatar "update nahi aa raha" issues yahi turn out hote hain.

⚠️ App Store / Play Store review guidelines — OTA ki limits

OTA updates technically review-free hain, lekin isko misuse karna platform guidelines violate kar sakta hai. Apple ke App Store Review Guidelines mein specifically language hai jo restrict karti hai ki OTA/ "hot code push" mechanisms sirf bug fixes aur minor JS-level feature improvements ke liye use ho — inhe app ke core purpose ya primary functionality ko significantly badalne ke liye use nahi karna chahiye (jaise ek completely different app "disguise" karke serve karna, ya paid-feature-gating ko OTA se bypass karna). Google Play mein bhi similar spirit hai, halaki enforcement historically kam strict raha hai. Senior-level practice: OTA updates ko unhi cheezon ke liye use karo jo genuinely "same app, thoda behtar/fixed" ke daayre mein aati hain — agar change itna bada hai ki app ka fundamental behaviour badal raha hai, wo ek naya store submission deserve karta hai, chahe technically OTA se push karna possible bhi ho.

Advanced Deep-Dive — Beyond the Basics

Ab tak humne EAS Update ka mental model, boundary, aur day-to-day flow cover kar liya. Ye section un internals ko explore karta hai jo ek senior-level understanding ke liye zaroori hain — ki manifest resolution actually kaise hota hai byte-level pe, production rollouts ko safely kaise stage karte hain, aur update delivery ko cryptographically secure kaise banate hain.

1. Update Manifest Resolution Algorithm — Actual Mechanism

Pehle humne kaha tha "app naya manifest fetch karta hai aur update download karta hai" — ab is exact algorithm ko step-by-step deconstruct karte hain, kyunki interview mein "explain exactly" wale sawal yahi expect karte hain.

Jab app launch/foreground hoti hai, expo-updates native module ye sequence follow karta hai:

  • Step 1 — Request construct karna: App apne bound channel aur compute kiye hue runtimeVersion ko HTTP headers mein daalke EAS update server (jo expo.updates.url pe hai) ko ek request bhejta hai — matlab request khud hi bata deta hai "mujhe kaunsi audience ka manifest chahiye".
  • Step 2 — Server manifest resolve karta hai: Server us channel ke current branch pe dekhta hai ki us exact runtime version ke liye latest published update kya hai, aur uska manifest (JSON — update ID/hash, asset list with hashes, launch asset reference, extra metadata) wapas bhejta hai.
  • Step 3 — Comparison, naye bundle ke liye nahi, update ID ke liye: Client ye naya manifest ka update ID apne currently-running (locally embedded ya pehle se cached/installed) update ke ID se compare karta hai. Agar dono same hain — matlab already latest pe ho — koi download hota hi nahi, process yahin stop ho jaata hai (network pe sirf ek chhota manifest fetch hua, kuch aur nahi).
  • Step 4 — Asset-level diffing (ye wahi part hai jo bahut log miss karte hain): Agar update ID different hai (naya update available hai), client naye manifest ke andar list kiye gaye har asset (JS bundle chunks, images, fonts) ka hash dekhta hai aur apne local asset cache (jo already-downloaded assets store karta hai unke hash ke against) se compare karta hai. Sirf wahi assets download hote hain jinka hash match nahi karta — matlab agar naye update mein sirf ek chhota JS chunk change hua hai (jaise ek single screen ka logic), baaki saare unchanged assets (fonts, images, unchanged JS chunks) re-download nahi hote, wo local cache se hi reuse ho jaate hain. Ye conceptually bilkul waise hai jaise ek CDN/browser cache content-hash-based filenames use karta hai — content same hai to hash same hai to re-fetch ki zaroorat nahi.
  • Step 5 — Atomic activation: Jab saare naye/changed assets download ho jaate hain, client ek complete naya "update" local storage mein commit karta hai — is process ke beech mein agar app crash bhi ho jaaye, purana working update hi active rehta hai (partial/corrupt update kabhi activate nahi hota, ye atomicity crash-safety ke liye critical hai). Agli launch pe naya update use hota hai.
ℹ️ Ye "delta update" jaisa kyun feel hota hai

Bahut developers isko galat samajhte hain ki "OTA update matlab poora bundle phir se download hota hai". Actually mechanism content-addressed hai — har asset uske hash se identify hota hai, na ki uske naam se. Isliye agar aapne sirf ek chhoti si business-logic change ki hai (jaise ek validation rule), sirf us JS chunk ka hash badlega jisme wo code hai, aur download size us change ke proportional hoga — poore app ka bundle nahi. Ye especially large apps (jinke assets MBs mein hote hain) ke liye bandwidth aur update-speed dono ke liye bada practical advantage hai.

2. Rollout Percentage Strategies — Staged OTA Releases

Native app releases mein staged rollout ek well-known safety practice hai (App Store/Play Store dono support karte hain "release to X% users first"). EAS Update mein bhi wahi concept hai — rollout percentage — jisse aap ek update ko turant 100% users ko na bhejke, pehle ek chhote percentage (jaise 10%) ko bhejte ho, kuch der monitor karte ho, phir gradually ramp-up karte ho.

🔒 OTA rollout risk native rollout se BHI zyada critical kyun hai

Native store releases mein Apple/Google ka review process ek (weak lekin non-zero) safety net hota hai — obviously-crashing builds kabhi-kabhi review mein hi reject ho jaate hain, ya at least submission-to-live ke beech kuch din ka buffer milta hai jisme internal testing ho sakti hai. OTA updates is safety net ko completely bypass karte hain — eas update chalate hi minutes ke andar aapka code matching sabhi devices tak pahunch sakta hai, bina kisi external review ke. Iska matlab hai ki agar aapka OTA update mein koi crash-causing bug hai (jaise ek undefined variable jo ek specific screen pe hit hota hai), aur aapne use directly 100% production pe publish kar diya — saare active users ek saath crash experience karte hain, turant, bina kisi buffer ke. Yahi wajah hai ki rollout percentage OTA context mein native se bhi zyada important safety mechanism ban jaata hai.

Practical flow: aap eas update ko ek --rollout-percentage flag ke saath publish karte ho (ya EAS dashboard se rollout adjust karte ho). Jitne bhi matching devices hain (same channel + same runtime version), unmein se sirf specified percentage hi is naye update ko dekhega — baaki devices apna current (purana, already-verified) update hi chalate rahenge. Ye assignment per-device consistent hota hai (ek device ek baar "in" bucket mein aaya to wahi rehta hai, flip-flop nahi karta) taaki testing/monitoring consistent rahe.

terminal — staged rollout flow
# Step 1: Naya update sirf 10% matching devices ko publish karna (conservative first step)
eas update --branch production --message "perf fix — staged rollout" --rollout-percentage 10 # Sirf 10% eligible devices is naye bundle ko dekhenge, baaki 90% purana chalate rahenge

# Step 2: Kuch ghanton tak crash-free rate aur key metrics monitor karo (Sentry/crash reporting dashboard se)
# -- ye step CLI command nahi hai, ye manual observation phase hai --

# Step 3a: Agar sab theek laga — rollout percentage ko badhao (ramp-up)
eas update:edit --branch production --group "<update-group-id>" --rollout-percentage 50 # Wahi update ab 50% devices tak, bina naya bundle publish kiye

# Step 3b: Agar sab confident lage — 100% tak le jao (full rollout)
eas update:edit --branch production --group "<update-group-id>" --rollout-percentage 100 # Ab saare matching devices is update ko receive karenge

# Alternative: agar Step 2 mein crash-rate spike dikha — turant rollback (0% tak le jao ya pehla-wala rollback command use karo)
eas update:edit --branch production --group "<update-group-id>" --rollout-percentage 0 # Naye update ko turant freeze karo, saare devices purane (safe) update pe hi rahenge
🧠 Senior Dev Note

Rollout percentage sirf "manual staged deploy" ke liye nahi — ye ek monitoring workflow demand karta hai. Rollout percentage badhane se pehle aapke paas ek automated crash-free-rate ya error-rate dashboard (Sentry, Bugsnag, ya custom) hona chahiye jisse aap "10% users pe kya crash rate hai" ko objectively daikh sako — sirf "lag raha hai theek hai" wali gut-feeling se ramp-up karna effectively poora rollout skip karne jaisa hi risky hai. Senior teams ek defined threshold rakhte hain (jaise "crash-free rate 99.5% se neeche na jaaye"), aur agar threshold cross ho jaaye, rollout ko auto-pause/rollback karne ka process (manual ya scripted) predefine karte hain — decide karne mein der na lage jab production mein already users affected ho rahe hon.

3. Code Signing for Updates — Security Model

Ab ek security-critical concept: agar app kisi bhi manifest/bundle ko blindly trust karke download aur execute kar le jo update server se aaya, to ek attacker jo network path (CDN, ISP, compromised proxy/MITM) ko control kar le, wo apna khud ka malicious JS bundle serve kar sakta hai jo app blindly run kar legi — ye poori tarah se app ka control le sakta hai (JS engine ke through user data exfiltrate karna, phishing screens dikhana, etc.), kyunki JS bundle ke paas app ke andar full logic-level access hota hai.

🔒 Threat model: Compromised CDN / MITM attack

Concrete attack scenario: koi attacker EAS ke CDN infrastructure ko compromise kar leta hai (ya kisi corporate/public WiFi pe MITM position le leta hai jaha app ka update-check traffic guzarta hai), aur jab app manifest request bhejti hai, attacker ek fake manifest + malicious JS bundle return kar deta hai jo bilkul valid dikhta hai — same format, plausible update ID. Agar app ke paas is bundle ki authenticity verify karne ka koi tarika nahi hai (sirf "manifest mila, download kar liya, run kar diya"), app is malicious code ko silently execute kar degi — user ko kabhi pata bhi nahi chalega ki unki app compromise ho chuki hai.

Isi threat ko defend karne ke liye code signing hai. EAS Update updates ko cryptographically sign kar sakta hai — publish time pe ek private key (jo aapki organization ke paas securely hoti hai, EAS ke servers pe nahi) se manifest pe ek digital signature generate hoti hai. App ke andar (build time pe embed hone wala) corresponding public key hota hai. Jab app ek naya manifest fetch karti hai, wo signature ko public key se verify karti hai — agar signature valid nahi hai (matlab content aapki private key se sign nahi hua tha), app us update ko reject kar deti hai aur download hi nahi karti — chahe manifest format sahi dikhta ho.

Iska practical matlab: sirf aapki organization ka private key hold karne wala hi ek "valid" update publish kar sakta hai jo app accept karegi. Agar CDN compromise ho bhi jaaye aur attacker apna fake manifest serve kare, us fake manifest pe valid signature nahi hogi (kyunki attacker ke paas private key nahi hai) — app us update ko silently reject kar degi, exactly waise jaise runtime version mismatch pe reject karti hai.

(comments added for teaching — real JSON doesn't support them, remove before use)

app.json (code signing configuration)
{
  "expo": { // "expo" root config key
    "updates": { // updates block — code signing config yahin jaata hai
      "url": "https://u.expo.dev/your-project-id", // Manifest server endpoint (as before)
      "codeSigningCertificate": "./certs/certificate.pem", // Build ke andar embed hone wala certificate — public key contain karta hai jo signature verify karega
      "codeSigningMetadata": { // Signature algorithm metadata
        "keyid": "main", // Key identifier — multiple signing keys rotate karne ke liye use hota hai
        "alg": "rsa-v1_5-sha256" // Signing algorithm — kaunsa cryptographic scheme use ho raha hai signature ke liye
      } // codeSigningMetadata close
    } // updates block close
  } // expo block close
} // root object close
terminal — generating signing keys + signed publish
# Private + public keypair generate karna — private key ko secure rakho (CI secret store mein), commit mat karo
npx expo-updates codesigning:generate # Ye private key file (keep secret) aur public certificate file (embed in app) generate karta hai

# Normal publish command hi kaam karega — agar app.json mein codeSigningCertificate set hai, EAS automatically sign karega
eas update --branch production --message "signed release" # Manifest publish hote hi private key se sign hoke jaayega, jise app apne embedded public cert se verify karegi
🧠 Senior Dev Note

Code signing OTA delivery ko waise hi treat karta hai jaise app store binaries ko treat kiya jaata hai — signed artifact hi trusted artifact hai. Ye especially high-stakes apps (banking, healthcare, enterprise) ke liye near-mandatory practice honi chahiye — agar aapki app sensitive data handle karti hai, code signing ke bina EAS Update use karna ek unnecessary attack surface open rakhna hai. Private key ka secure storage bhi utna hi critical hai jitna native signing keystore ka — agar private key leak ho jaaye, attacker apne khud ke "valid-signed" malicious updates publish kar sakta hai, isliye ise CI secrets manager mein rakho, kabhi repo mein commit mat karo.

🎯 Interview Questions — Senior React Native Developer

Ye section un questions ko cover karta hai jo senior/staff-level React Native interviews mein EAS Update/OTA topic pe commonly puche jaate hain — internals, risk management, security, aur trade-offs ke mix ke saath.

Q1. Explain exactly how the app decides whether to download an available OTA update — what's compared against what?

Do cheezein alag-alag compare hoti hain, do alag levels pe. Pehle, eligibility level pe: request ke headers mein app apna current channel aur runtimeVersion bhejta hai — server sirf usi channel/runtime-version combination ke liye latest manifest resolve karta hai (ye ek server-side filter hai, client isse download nahi karta, bas sahi manifest hi milta hai). Doosra, jab manifest mil jaata hai, client us manifest ka update ID apne currently-active update ke ID se compare karta hai — agar same hai, koi download nahi hota. Agar different hai, tab asset-level hash comparison hoti hai: naye manifest ke har asset ka hash local cache ke hashes se compare hota hai, aur sirf mismatched-hash assets hi download hote hain. Total teen comparisons hain: channel/runtime (server-side eligibility), update ID (client-side "kuch naya hai kya?"), aur per-asset hash (client-side "kya specifically naya hai?").

Q2. You just published an OTA update and users start reporting a crash — what's your immediate action, and why is "just push a fix" not always fast enough?

Immediate action hai rollback, fix nahi — eas channel:rollback chalake channel ko wapas last known-good update pe point karo. Ye seconds mein hota hai kyunki koi naya bundle build/upload nahi hota, sirf server-side pointer change hota hai. "Just push a fix" slow hai kyunki: (1) aapko pehle root cause diagnose karna padega (jo production crash logs se time leta hai), (2) fix likhna, test karna, phir publish karna — ye poora cycle minutes se hours tak le sakta hai, aur is poore waqt buggy update live rehta hai, active users ko crash continue hota rahega. Rollback ek "stop the bleeding" move hai jo diagnosis se independent hai — pehle crash rokna, phir root cause pe kaam karna, phir ek properly-tested fix ko fresh publish karna (staged rollout ke saath, directly 100% nahi).

Q3. What would happen if EAS Update had no code signing — describe a concrete attack.

Bina code signing ke, app sirf ye check karti hai ki manifest "well-formed" hai (sahi JSON shape, expected fields) — content ki authenticity verify nahi hoti. Concrete attack: ek attacker jo network path control karta hai (compromised WiFi router, DNS poisoning jo update-server domain ko apne server pe redirect kare, ya EAS CDN infra compromise) app ke manifest request ko intercept karke apna khud ka manifest + malicious JS bundle return kar deta hai. App bina kisi verification ke ye download karke run kar degi — malicious JS ab full app-level access ke saath chal raha hai, matlab wo AsyncStorage/SecureStore se tokens read kar sakta hai, fake login screens dikha sakta hai (credential phishing), ya background mein user data exfiltrate kar sakta hai. Code signing isse defend karta hai kyunki attacker ke paas organization ki private signing key nahi hoti, isliye uska fake manifest signature verification mein fail ho jaata hai aur app use silently reject kar deti hai.

Q4. Give a real example of a bug that CANNOT be fixed via OTA update, and explain precisely why not.

Example: production mein pata chalta hai ki ek naya native permission (jaise Bluetooth) declare nahi kiya gaya Info.plist/AndroidManifest.xml mein, aur ek feature usi permission pe depend karta hai — app us feature ko access karte hi crash ya silently fail ho rahi hai. Ye OTA se fix nahi ho sakta kyunki permission declaration compile-time pe native binary ke andar bake ho chuki hai — Info.plist/AndroidManifest.xml JS runtime ka hissa nahi hain, wo native build artifacts hain jo sirf eas build (naya native compile) se regenerate hote hain. OTA sirf JS bundle aur JS-loadable assets replace kar sakta hai — jo bhi compile-time pe binary mein permanently embed ho chuka hai (permissions, native modules, config plugins ka output), wo runtime pe touch hi nahi ho sakta chahe aap kitna bhi JS-level "workaround" try karo.

Q5. What's the difference between "sdkVersion" and "fingerprint" runtimeVersion policies, and why would a senior dev push their team to migrate?

sdkVersion policy runtime version ko sirf installed Expo SDK number se derive karta hai — coarse-grained, matlab agar aap SDK version change kiye bina bhi ek naya native dependency add karte ho, runtime version wahi rehta hai, isliye EAS ye incompatibility detect hi nahi kar payega aur ek incompatible JS update purane binary ko bhej sakta hai (crash risk). fingerprint policy actually native project (dependencies + config plugins + native config files) ka cryptographic hash compute karta hai — koi bhi native-level change automatically fingerprint badal deta hai, chahe SDK version same rahe. Senior dev migrate karne ka push isliye karega kyunki ye ek structural, silent bug class ko eliminate karta hai — aapko manually track nahi karna padta "kya is native change ne compatibility break ki?", system khud detect karta hai.

Q6. Why does rollout percentage matter more for OTA updates than for native store rollouts?

Native store rollouts mein Apple/Google ka review process ek weak-lekin-non-zero safety net provide karta hai — plus submission-to-live ke beech ek natural delay hota hai jisme internal QA ho sakti hai. OTA updates is safety net ko poora bypass karte hain — publish karte hi minutes ke andar code matching sabhi devices tak pahunch sakta hai. Agar rollout staged (jaise pehle 10%) na ho aur update mein crash bug ho, saare active users ek saath, turant crash experience karte hain — koi buffer nahi hai jo damage limit kare. Rollout percentage OTA context mein hi safety net ka role play karta hai jo native mein store review partially provide karta hai — isliye ye "nice to have" nahi, near-mandatory practice honi chahiye.

Q7. A user reports "I'm not getting the latest update" but everything looks correctly published — what's your debugging checklist?

Order mein check karo: (1) Channel match — user ke build ka bound channel (build profile se) us channel se match karta hai jispe update publish hua? (2) Runtime version match — eas update:list se published update ka runtime version, aur user ke device ke installed binary ka runtime version — ye dono exact match hone chahiye, mismatch silently ignore hota hai, koi error nahi milta. (3) Launch/foreground timing — update sirf app launch/foreground pe check hota hai, background polling nahi — user ne app close-reopen kiya ya nahi. (4) Rollout percentage — agar staged rollout active hai, ho sakta hai ye specific user abhi bhi "excluded" percentage mein ho. (5) Dormant user problem — agar user hafton se app nahi khola, uska binary purane runtime version pe frozen ho sakta hai, aur naya runtime-version-targeting update use milega hi nahi jab tak wo fresh native build install na kare.

Q8. Why doesn't a runtime version mismatch throw an error — and is that a good design decision?

Mismatch silently ignore hota hai (update simply deliver nahi hota, jaise koi naya update exist hi nahi karta) kyunki EAS ka design philosophy hai "fail safe, fail silent" — agar mismatch pe error throw hoti, aur wo error app ke normal update-check flow ko crash kar deti, to ye khud ek reliability issue ban jaata (ek "no compatible update" scenario, jo completely normal hai — jaise ek naye build ke turant baad, jab tak koi matching update publish na ho — app ko crash karwa dena). Design trade-off ye hai: false negatives (developer confuse hota hai "update kyun nahi aa raha") accept kiye gaye hain taaki false positives (normal no-update-available state ko error treat karke app crash karna) avoid ho sakein. Practical implication: developers ko proactively eas update:list se runtime versions compare karne ki habit banani padti hai, kyunki system khud warn nahi karega.

Q9. Walk through what happens internally if an OTA download is interrupted midway (app killed, network drop) — can this corrupt the app?

Nahi, corrupt nahi karta — is wajah se ki expo-updates ka commit process atomic hai. Jab tak saare naye/changed assets (jinke hash match nahi hue the) fully download nahi ho jaate, naya update "staged" state mein rehta hai — currently-active/running update touch hi nahi hota. Sirf jab poora set successfully download ho chuka ho, tabhi client atomically naye update ko "active" mark karta hai apne local metadata store mein. Agar beech mein app kill ho jaaye ya network drop ho jaaye, agli baar app launch hone pe wo bas dubara try karega (ya jahan tak already-hashed assets download ho chuke the, unhe skip karke resume-jaisa behavior milega) — lekin purana working update hamesha safe rehta hai jab tak naya poora verified na ho jaaye. Ye crash-safety guarantee hi OTA ko production-safe banati hai, warna ek half-downloaded corrupt bundle se poori app hi unbootable ho sakti thi.
