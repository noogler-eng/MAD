1. Push Notifications Architecture Overview

Sabse pehla mental model fix karo: tumhara app kabhi bhi direct kisi doosre device ko notification "send" nahi karta, aur tumhara backend server bhi kabhi seedha kisi user ke phone ko notification "push" nahi karta. Har notification hamesha OS vendor ke apne push infrastructure se hoke guzarti hai — iOS ke liye Apple ka APNs (Apple Push Notification service), Android ke liye Google ka FCM (Firebase Cloud Messaging).

Iska reason simple hai: jab app killed ho ya background mein ho, tumhara app ka JS process already band ho chuka hai — koi socket open nahi hai, koi listener chal nahi raha. Agar har app apna khud ka persistent connection maintain karta backend se (jaise ek permanent WebSocket), toh phone ki battery minutes mein khatam ho jaati kyunki radio (cellular/wifi chip) ko baar-baar wake karna padta. Iski jagah OS ek hi system-level persistent connection maintain karta hai apne push service se (APNs/FCM) — chahe 100 apps installed ho ya 5, connection ek hi rehta hai, battery cost shared hoti hai. Jab bhi koi notification aati hai, OS us single connection pe receive karta hai aur phir target app ko specifically wake karta hai (chahe wo killed hi kyun na ho) — bas notification deliver karne ke liye, poora app process launch kiye bina.

Notice karo — step (2) mein "Expo Push Service" ek optional proxy layer hai jo tumhare liye FCM aur APNs dono ke alag-alag payload formats, auth mechanisms aur retry logic ko ek single unified API ke peeche abstract kar deta hai. Tum chaaho toh Expo ko skip karke seedha FCM/APNs se baat kar sakte ho — lekin tab tumhe khud dono platforms ke alag payload shapes, auth tokens, aur error handling likhni padegi. Ye trade-off agla section mein detail se dekhenge.

🧠 Senior Dev Note

Ye poora architecture isliye zaroori hai kyunki battery efficiency aur reliability sirf OS-level se hi guarantee ho sakti hai. Third-party app-level solution (jaise custom polling ya persistent socket) na toh reliable hoga jab app killed ho, na hi battery-friendly hoga jab app background mein ho. Yahi wajah hai ki Apple/Google dono ne apna khud ka push infra banaya aur third-party apps ko force karte hain isi ke through jaana — ye koi arbitrary restriction nahi hai, ye ek fundamental OS design decision hai jo poore device ke battery/network ko optimize karta hai.

2. Expo Notifications vs OneSignal vs Raw FCM/APNs

Teen options hain notification bhejne ke liye, aur senior dev ka kaam hai sahi trade-off pick karna based on team size, feature needs, aur budget — na ki hamesha "sabse powerful" wala uthana.

OptionComplexityFeaturesKab use karo
Expo Notifications Sabse kam — expo-notifications package + Expo ka push service Basic send/receive, scheduling, badges — Expo Application Services (EAS) ke saath tight integration Most apps ke liye default choice. MVP, startups, jab tak tumhe heavy analytics/segmentation nahi chahiye
OneSignal Medium — apna SDK add karna padta hai, apna dashboard setup Rich analytics, A/B testing, audience segmentation, in-app messaging, drip campaigns Jab marketing/growth team ko dashboard chahiye bina engineering involvement ke, ya complex segmentation campaigns chalani hain
Raw FCM/APNs Sabse zyada — khud dono platforms ka payload format, auth, retries, error handling likhna padta hai Full control — koi bhi custom feature, koi rate limit nahi (apni FCM/APNs quota ke andar), koi third-party dependency nahi Bahut large-scale apps, ya jab compliance/data-residency requirements third-party proxy allow nahi karti

Expo Notifications ke saath ek practical limit yaad rakhni chahiye — Expo push service pe rate limits hain (roughly bulk sends chunks mein bhejni padti hain, ~100 notifications per request), aur ye ek additional hop hai (tumhara server → Expo → FCM/APNs) jo thoda extra latency add karta hai (usually negligible, but at massive scale it matters). In-most apps ke liye ye trade-off completely acceptable hai kyunki dev velocity ka fayda bahut zyada hai.

💡 Quick Tip

Senior dev ka default answer: Expo Notifications se start karo. Jab tumhe actually feel ho ki marketing team ko segmentation/campaign dashboard chahiye ya scale itni badh gayi hai ki Expo ka proxy layer bottleneck ban raha hai — tabhi OneSignal ya raw FCM pe migrate karo. Premature optimization yahan bhi utni hi galat hai jitni kahin aur.

3. Permission Flows (iOS vs Android)

Dono platforms pe permission model alag hai, aur ye difference recently aur bhi zyada important ho gaya hai:

  • iOS: Hamesha se explicit runtime permission prompt chahiye hota hai kisi bhi notification dikhane se pehle — requestPermissionsAsync() call karke user se manually poochna padta hai. Agar user deny kar de, koi notification kabhi nahi dikhegi jab tak wo Settings app mein jaake manually enable na kare.
  • Android (13 se pehle, API 32 aur neeche): Permission automatically granted hoti thi — koi prompt nahi dikhta tha, app install hote hi notifications kaam karti thi.
  • Android 13+ (API 33+): Ab yahan bhi POST_NOTIFICATIONS naam ka ek runtime permission chahiye — bilkul iOS jaisa explicit prompt. Ye ek bahut common gotcha hai jab team purane Android behavior ke assumption pe code likhti hai aur newer devices pe silently notifications nahi dikhti kyunki permission hi nahi maanga gaya.

UX ka bhi ek important rule hai: app launch hote hi permission mat maango. User ko pata hi nahi ki tumhara app notifications kis cheez ke liye use karega, isliye deny kar dega — aur ek baar deny karne ke baad OS dobara automatically prompt nahi dikhata (user ko khud Settings mein jana padega). Isliye best practice hai — context ke saath maango, jaise jab user pehli baar kisi order ko "track" karna chahta hai, tab poocho "order updates ke liye notifications on karo".

lib/notifications/permissions.ts
import * as Notifications from "expo-notifications"; // expo-notifications module — permission aur token APIs dete hain
import { Platform } from "react-native"; // Platform check karne ke liye (Android 13+ specific logic ke liye)

// Ye function sirf permission ka CURRENT status check karta hai, bina user ko disturb kiye
export async function getNotificationPermissionStatus(): Promise<Notifications.PermissionStatus> { // return type: granted | denied | undetermined
  const { status } = await Notifications.getPermissionsAsync(); // OS se current permission state maang rahe hain (koi prompt nahi aata is call se)
  return status; // caller ko raw status wapas de rahe hain, taaki UI decide kar sake prompt dikhana hai ya nahi
} // function close

// Ye function ACTUAL prompt dikhata hai — sirf isko tabhi call karo jab user ne context ke saath action liya ho
export async function requestNotificationPermission(): Promise<boolean> { // true = granted, false = denied ya undetermined reh gaya
  const { status: existingStatus } = await Notifications.getPermissionsAsync(); // pehle check karo — pehle se granted toh dobara mat poocho

  if (existingStatus === "granted") { // agar already permission mil chuka hai
    return true; // seedha true return, prompt dikhane ki zaroorat nahi
  } // if block close

  const { status: newStatus } = await Notifications.requestPermissionsAsync({ // Ab actual OS-level prompt trigger hoga (iOS alert / Android 13+ dialog)
    ios: { // iOS-specific permission options object
      allowAlert: true, // banner/alert dikhane ki permission maang rahe hain
      allowBadge: true, // app icon pe badge count dikhane ki permission
      allowSound: true, // notification sound play karne ki permission
    }, // ios options object close
  }); // requestPermissionsAsync call close

  return newStatus === "granted"; // boolean return kar rahe hain caller ke liye
} // function close

Ab UI level pe context-aware prompting ka example — pehle app ka own custom modal dikhao explain karte hue ki notifications kis kaam ke liye hain, tabhi OS ka actual permission dialog trigger karo:

components/NotificationOptInCard.tsx

⚠️ Android 13+ Gotcha

Agar tumhara targetSdkVersion/compileSdkVersion 33 ya usse zyada hai (jo Expo SDK ke recent versions default karte hain), toh Android par bhi POST_NOTIFICATIONS permission runtime pe maangna zaroori hai — warna notifications silently nahi dikhengi, koi error bhi nahi milega. expo-notifications ka requestPermissionsAsync() internally isko handle karta hai, lekin bahut se developers jo purane Android behavior ke aadi hain, is call ko skip kar dete hain assuming "Android pe toh automatic hota hai" — jo ab sach nahi hai.

4. Token Registration & Backend Integration

Permission milne ke baad, agla step hai Expo push token generate karna — ye ek unique string hai jo Expo ke push service ko batata hai "is specific device+app installation ko notification deliver karo". Ye token backend ko bhejna zaroori hai aur logged-in user ke against store karna hai, taaki jab backend ko us user ko notify karna ho, use pata ho kis token pe bhejna hai.

lib/notifications/register.ts
import * as Notifications from "expo-notifications"; // token generate karne ke liye expo-notifications
import * as Device from "expo-device"; // physical device check karne ke liye (simulator pe push kaam nahi karta)
import Constants from "expo-constants"; // EAS project ID nikalne ke liye zaroori (managed workflow mein token ke saath chahiye)
import { requestNotificationPermission } from "./permissions"; // humara pehle wala permission wrapper

// Ye function poora registration flow karta hai: permission → token → backend ko save
export async function registerForPushNotificationsAsync(authToken: string): Promise<string | null> { // authToken = logged-in user ka session/JWT, backend call authenticate karne ke liye
  if (!Device.isDevice) { // simulator/emulator pe real push token nahi milta (khaaskar iOS simulator pe)
    console.warn("Push notifications sirf physical device pe kaam karte hain"); // dev ko warn kar rahe hain, silent fail nahi
    return null; // null return — caller ko pata chal jaayega registration nahi hua
  } // if block close

  const granted = await requestNotificationPermission(); // pehle permission confirm karo (agar already granted, turant true aayega)
  if (!granted) { // agar user ne deny kar diya
    return null; // token generate karne ka koi matlab nahi, null return
  } // if block close

  const projectId = Constants.expoConfig?.extra?.eas?.projectId; // app.json/app.config.ts se EAS project ID nikaal rahe hain
  const tokenResponse = await Notifications.getExpoPushTokenAsync({ projectId }); // Expo push service se unique token maang rahe hain is project ke liye
  const expoPushToken = tokenResponse.data; // actual token string yahan hai, format: "ExponentPushToken[xxxxxxx]"

  await savePushTokenToBackend(expoPushToken, authToken); // backend ko bata rahe hain ki is user ka token ye hai

  return expoPushToken; // caller ko bhi token de rahe hain (debugging/logging ke liye useful)
} // function close

// Ye helper backend ke saath actual network call karta hai
async function savePushTokenToBackend(pushToken: string, authToken: string): Promise<void> { // return type void — sirf side-effect hai
  const response = await fetch("https://api.myapp.com/users/me/push-token", { // user-specific endpoint, "me" batata hai server-side ki caller khud ke liye update kar raha hai
    method: "POST", // naya token register/update karne ke liye POST
    headers: { // request headers object
      "Content-Type": "application/json", // batata hai body JSON format mein hai
      "Authorization": `Bearer ${authToken}`, // logged-in user ka session token — backend isse pehchanega ki request kis user ki hai
    }, // headers object close
    body: JSON.stringify({ pushToken }), // sirf token bhej rahe hain, user ID NAHI bhej rahe (backend khud auth token se nikalega)
  }); // fetch call close

  if (!response.ok) { // agar server ne error status diya (4xx/5xx)
    throw new Error(`Push token save failed: ${response.status}`); // error throw karo, caller ise catch/log kar sake
  } // if block close
} // function close
🚨 Security Critical — Server-Side User Association

Notice karo upar ke code mein savePushTokenToBackend function body mein sirf pushToken bhej raha hai, koi userId nahi. Ye jaan-boojh kar hai — client ko kabhi bhi apna khud ka user ID batane ki authority nahi deni chahiye. Agar tum client se ek userId field accept karte ho aur backend usi ID ke against token save kar deta hai (bina proper verification ke), toh koi bhi malicious client crafted request bhej ke kisi aur user ke account pe apna push token register kar sakta hai — matlab wo attacker ab us doosre user ko intended notifications ke bajaye khud receive karna shuru kar sakta hai, ya worse, spoofed notifications trigger karwa sakta hai jo genuine lagengi. Sahi pattern: backend Authorization header se JWT/session ko verify kare, usi se authenticated user ID nikale (server-side, cryptographically verified), aur token ko sirf usi ID ke against store kare — client-supplied user ID pe kabhi bharosa mat karo.

Component mein use karna

app/(app)/_layout.tsx (registration trigger)
import { useEffect } from "react"; // mount hote hi registration trigger karne ke liye
import { registerForPushNotificationsAsync } from "../../lib/notifications/register"; // humara registration function
import { useAuth } from "../../context/AuthContext"; // logged-in user aur uska session token nikalne ke liye

export function PushRegistrationEffect() { // small dedicated component jo sirf ye side-effect handle karta hai
  const { sessionToken } = useAuth(); // AuthContext se current session token nikaal rahe hain

  useEffect(() => { // jab bhi sessionToken available ho (login ho chuka ho)
    if (!sessionToken) return; // abhi login nahi hua, kuch mat karo
    registerForPushNotificationsAsync(sessionToken).catch((err) => { // registration call karo, error ko catch karo taaki app crash na ho
      console.error("Push registration failed:", err); // sirf log karo, user-facing error mat dikhao (non-critical feature)
    }); // catch close
  }, [sessionToken]); // sessionToken change hone pe re-run (jaise re-login ke baad naya token generate ho)

  return null; // ye component kuch UI render nahi karta, sirf side-effect ke liye hai
} // component close

5. Firebase Cloud Messaging (FCM) Internals

FCM (Firebase Cloud Messaging) Google ka push delivery infrastructure hai Android devices ke liye — ye wahi persistent OS-level connection hai jo humne architecture section mein dekha. Har Android device jisme Google Play Services installed hai, wo automatically FCM se connected rehta hai.

Ab yahan confusion hoti hai: agar hum Expo Notifications use kar rahe hain, toh Firebase project kyun chahiye? Answer: kyunki Expo Push Service khud FCM/APNs ka replacement nahi hai — ye ek proxy hai. Jab tumhara backend Expo ko "notification bhejo" bolta hai, Expo internally Android devices ke liye FCM ki actual API call karta hai (uska server key/service account use karke), aur FCM hi asal mein device tak deliver karta hai. Isliye tumhe apna Firebase project banana padta hai, google-services.json download karke app mein daalna padta hai (ya EAS credentials mein upload karna padta hai), taaki Expo ke paas tumhare project ke liye FCM se baat karne ki authority ho.

FCM credential flow (conceptual)
1. Firebase Console mein project banao                              // Google ka Firebase project — free tier available
2. Android app add karo (package name match hona chahiye app.json se) // FCM ko pata chalega kaunsi app ye hai
3. google-services.json download karo                                // isme FCM sender ID, project config hota hai
4. EAS credentials mein FCM server key/service account upload karo   // "eas credentials" command se, ya EAS dashboard se
5. Ab Expo Push Service tumhare project ki taraf se FCM ko call kar sakta hai

iOS ke liye equivalent concept hai — Expo ko tumhare Apple Developer account se ek APNs auth key chahiye, jo ek .p8 file hoti hai jo tum Apple Developer portal se generate karte ho. Ye key EAS credentials mein upload hoti hai, aur Expo isi key se APNs ko authenticate karke tumhari taraf se push bhejta hai. Bina in credentials ke, Expo Push Service ke paas tumhare specific app ke liye FCM/APNs se baat karne ki permission hi nahi hoti — matlab tokens generate honge, lekin actual delivery fail hogi.

🧠 Senior Dev Note

Ye samajhna zaroori hai: Expo Push Service ek routing/abstraction layer hai, ek independent delivery mechanism nahi. FCM aur APNs hi asal "last mile" hain jo OS tak notification pahunchate hain. Isliye jab production mein push notifications nahi pahunch rahi hoti, debugging ka sahi order hai: pehle check karo Firebase/APNs credentials sahi se EAS mein configured hain ya nahi, phir Expo push receipt (delivery status) check karo, tabhi app-level code debug karo.

6. Foreground, Background & Killed States

App teen alag states mein ho sakta hai jab notification aati hai, aur har state mein behavior different hota hai:

  • Foreground (app open, user use kar raha hai) — by default OS notification tray mein kuch nahi dikhata (kyunki user already app mein hai); tumhe khud decide karna padta hai kya dikhana hai, setNotificationHandler() ke through.
  • Background (app minimize hai but killed nahi) — OS automatically notification tray mein dikhata hai, app ka koi JS code nahi chalta jab tak user tap na kare.
  • Killed (app process poori tarah band) — same, OS tray mein dikhata hai; tap karne pe OS app ko cold-start karta hai aur phir tumhara listener fire hota hai jaise app abhi launch hua ho.

Foreground behavior configure karna

lib/notifications/handler.ts
import * as Notifications from "expo-notifications"; // handler set karne ke liye expo-notifications

// Ye call app ke entry point (jaise App root file) mein ek baar honi chahiye, module-level pe
Notifications.setNotificationHandler({ // batata hai ki foreground mein notification aane pe kya karna hai
  handleNotification: async () => ({ // ye function har incoming notification ke liye call hota hai jab app foreground mein ho
    shouldShowAlert: true, // alert/banner dikhao (deprecated naming but still used) — user ko turant dikhe
    shouldPlaySound: true, // notification sound bhi bajao
    shouldSetBadge: false, // app icon badge count mat badhao (business logic ke hisaab se decide karo)
  }), // return object close
}); // setNotificationHandler call close

Yahan senior-level decision ye hai ki foreground mein notification dikhani hi chahiye ya nahi — agar tumhara app ek chat app hai aur user already us chat screen pe hai, toh redundant banner dikhana bura UX hai; is case mein tum notification data ko intercept karke seedha UI update kar sakte ho, banner suppress karke.

Tap handling + deep-linking via Expo Router

Jab user notification tap karta hai (background ya killed state se), addNotificationResponseReceivedListener fire hota hai. Yahan hum notification ke data payload se ek route nikaal ke Expo Router ke router.push() se us specific screen tak navigate karte hain.

components/NotificationTapHandler.tsx
import { useEffect, useRef } from "react"; // effect ke liye useEffect, subscription ko store karne ke liye useRef
import * as Notifications from "expo-notifications"; // listener register karne ke liye
import { useRouter } from "expo-router"; // deep-link navigate karne ke liye Expo Router ka imperative hook

// Notification payload ka expected shape — backend isi format mein "data" bhejega
type NotificationData = { screen?: string; orderId?: string }; // optional fields, backend ke payload design ke hisaab se

export function NotificationTapHandler() { // dedicated component, kuch render nahi karta, sirf side-effect ke liye
  const router = useRouter(); // Expo Router ka imperative navigation object
  const responseListener = useRef<Notifications.Subscription>(); // subscription reference, cleanup ke liye zaroori

  useEffect(() => { // mount pe listener register karo
    responseListener.current = Notifications.addNotificationResponseReceivedListener((response) => { // jab user notification TAP kare tab ye fire hota hai
      const data = response.notification.request.content.data as NotificationData; // backend ne jo custom data bheja tha, wo yahan milta hai

      if (data.screen === "order-details" && data.orderId) { // agar payload batata hai ki order details screen pe jaana hai
        router.push({ // Expo Router ke object-syntax se navigate kar rahe hain (typed routes ke saath compatible)
          pathname: "/orders/[id]", // dynamic route pattern jo app/orders/[id].tsx se match karega
          params: { id: data.orderId }, // actual order ID pass kar rahe hain params mein
        }); // push call close
      } // if block close
    }); // addNotificationResponseReceivedListener close

    return () => { // cleanup function — unmount hone pe chalega
      responseListener.current?.remove(); // listener ko remove karo, memory leak / duplicate firing avoid karne ke liye
    }; // cleanup function close
  }, [router]); // router reference change hone pe re-register (usually stable rehta hai)

  return null; // koi UI nahi, sirf listener attach karne ke liye component hai
} // component close
🧠 Senior Dev Note

Killed-state se app cold-start hoke agar user seedha kisi deep screen pe navigate ho raha hai (jaise order details), toh ye bilkul deep linking jaisa hi security consideration hai jo chapter 4 mein dekha tha — notification ke data payload ko bhi untrusted input ki tarah treat karo. orderId ko backend se validate karwao (ki ye actually logged-in user ka hi order hai) uss screen ke apne data-fetching logic mein, sirf notification payload pe bharosa karke UI mat bana do.

7. Rich Notifications (iOS Notification Service Extension)

Kabhi socha hai ki kuch apps ki notifications mein image thumbnail bhi dikhta hai (jaise ek chat message ke saath sender ki photo, ya news app mein article ka image)? Ye iOS Notification Service Extension se hota hai — ye ek chhota, separate native target hai jo tumhare main app ke saath bundle hota hai. Jab APNs se notification aati hai, iOS pehle isi extension ko chance deta hai payload ko modify karne ka — jaise ek remote image URL ko download karke usse notification ke saath attach karna — ispe se pehle ki notification actually user ko dikhe.

Ye ek genuinely native concept hai — isko Expo Go mein test nahi kar sakte, aur isko banane ke liye ek native/custom build chahiye (EAS Build ke through, ya bare workflow). expo-notifications ka config plugin isme partial help karta hai — app.json mein plugin config se kuch setup (jaise entitlements, extension target registration) automatically ho jaata hai, lekin agar tumhe truly custom image-processing logic chahiye extension ke andar, tumhe native Swift code likhna padega — ye is chapter ke scope se bahar hai (native modules chapter 16 mein aur depth milegi), lekin high-level samajhna zaroori hai ki "rich push" ka matlab hai ek extra native target, extra build step, aur Expo Go ki poori exit.

app.json — config plugin mention
{
  "expo": {
    "plugins": [
      [
        "expo-notifications",
        {
          "icon": "./assets/notification-icon.png",
          "color": "#d97757",
          "sounds": ["./assets/notification-sound.wav"]
        }

Legend — kyunki JSON mein comment nahi likh sakte, har key ka matlab neeche hai:

  • plugins — Expo config plugins ki list, jo build-time pe native project ko modify karte hain
  • "expo-notifications" — is plugin ka naam, jo notification-related native setup (permissions, icons, extension registration) automate karta hai
  • icon — Android notification tray mein dikhne wala small monochrome icon path
  • color — us icon ka accent color (Android notification UI mein use hota hai)
  • sounds — custom notification sound files jo bundle honge aur payload mein reference kiye ja sakte hain

8. OneSignal Integration

Agar decide kiya ki OneSignal chahiye (dashboard/segmentation ke liye), integration bhi seedha hai — apna SDK init karna padta hai app start pe:

lib/notifications/onesignal.ts
import { OneSignal } from "react-native-onesignal"; // OneSignal ka official React Native SDK import

// Ye function app root mein ek baar call honi chahiye, jitni jaldi ho sake startup pe
export function initializeOneSignal(appId: string): void { // appId OneSignal dashboard se milta hai, per-app unique

  }); // addEventListener close

Trade-off yahan clear hai: OneSignal SDK bundle size mein kuch add karta hai (native binary size thoda badhta hai), aur ek third-party vendor pe dependency create hota hai (unke uptime/pricing pe bharosa karna padta hai) — lekin badle mein tumhe ek poora dashboard milta hai jahan non-technical team members khud campaigns bana sakte hain, A/B test kar sakte hain, aur delivery analytics dekh sakte hain bina engineering involvement ke. Chhoti team/app ke liye ye overhead justify nahi hota; growth-focused product ke liye aksar worth it hota hai.

9. Real-World Gotchas

⚠️ Notifications physical device ke bina test nahi ho sakti

Push notifications ke liye real device chahiye hota hai zyadatar cases mein. Android emulator pe kaam karta hai agar usme Google Play Services installed hai (har emulator image mein nahi hota — "Google Play" wale images use karo, "Google APIs" wale nahi). iOS Simulator pe push notifications ka support Xcode 14+ (aur newer simulators) mein aaya hai, lekin abhi bhi reliability issues aa sakti hain — production testing hamesha real iPhone pe karo.

⚠️ Push token invalidate ho sakta hai

Expo push token permanent nahi hai — app reinstall, OS-level data clear, ya rarely FCM/APNs side invalidation ki wajah se token change ho sakta hai. Agar tumhara backend purana (dead) token pe bhejta rehta hai, delivery silently fail hogi. Isliye har app launch pe re-registration call karna best practice hai (jaise humne PushRegistrationEffect mein kiya) — agar naya token same hi hai toh backend ek simple upsert/no-op kar sakta hai, koi harm nahi; agar different hai toh automatically update ho jaayega.

⚠️ Permission denied ka silent failure

Agar user ne permission deny kar diya, getExpoPushTokenAsync() call fail hoga ya empty token dega — lekin agar tumne error handling properly nahi likhi, ye silently ho jaata hai aur tumhe production mein sirf itna pata chalega ki "kuch users ko notifications nahi mil rahi", debug karna mushkil ho jaata hai. Hamesha explicit fallback UX socho — jaise Settings page mein ek banner "Enable notifications in device settings" jab tumhe pata ho ki user ne pehle deny kiya tha (getPermissionsAsync() se check karke).

⚠️ Android Notification Channels missing — sabse common missed setup

Android 8 (API 26) se, har notification ek channel se belong karni chahiye — channels grouping aur importance level (sound, vibration, priority) define karte hain, aur user OS settings mein per-channel control kar sakta hai (jaise "Order Updates" channel on rakhe but "Promotions" channel off kar de). Agar tumne channel set hi nahi ki, notification ya toh default low-priority channel mein chali jaati hai (silently, bina sound ke) ya kabhi-kabhi dikhti hi nahi. Isko explicitly set karna padta hai:

lib/notifications/channels.ts
import * as Notifications from "expo-notifications"; // channel APIs bhi isi module mein hain
import { Platform } from "react-native"; // sirf Android pe channels ka concept hai, iOS pe iski zaroorat nahi

// App startup pe ek baar call karo, permission registration se pehle ya turant baad
export async function setupNotificationChannels(): Promise<void> { // return void, sirf setup side-effect hai
  if (Platform.OS !== "android") return; // iOS pe channels exist hi nahi karte, skip karo

  await Notifications.setNotificationChannelAsync("order-updates", { // channel ID — backend payload mein bhi yahi ID reference karega
    name: "Order Updates", // user-facing naam, Android Settings mein dikhega
    importance: Notifications.AndroidImportance.HIGH, // high priority — heads-up notification ke saath sound bhi dega
    vibrationPattern: [0, 250, 250, 250], // vibration timing pattern (ms mein): wait, vibrate, wait, vibrate
    lightColor: "#d97757", // LED light color (jin devices mein notification LED hai unke liye)
  }); // setNotificationChannelAsync call close

  await Notifications.setNotificationChannelAsync("promotions", { // dusra channel, low-priority marketing content ke liye
    name: "Promotions", // user-facing naam
    importance: Notifications.AndroidImportance.LOW, // low priority — silently tray mein jaayega, koi sound/heads-up nahi
  }); // setNotificationChannelAsync call close
} // function close
🧠 Senior Dev Note — User Opt-Out aur Notification Fatigue

Sirf technically notifications bhejna kaafi nahi hai — respect karo ki user ne kya opt-in kiya hai. Agar tum permission ek baar mil jaane ke baad har cheez ke liye notification bhejna shuru kar do (marketing, reminders, updates, sab kuch), users bahut jaldi notification fatigue mein chale jaate hain aur ya toh app-level settings se sab off kar dete hain, ya OS-level pe hi app ki notifications completely block kar dete hain (jahan se wapas on karwana bahut mushkil hota hai — user ko manually Settings mein jaana padta hai). Production-grade apps mein hamesha granular preferences do (jaise humne "Order Updates" vs "Promotions" channels alag rakhe), aur backend mein bhi per-category opt-out store karo, sirf ek global "notifications on/off" flag nahi. Ek engaged user jo sirf relevant notifications receive karta hai, unse zyada valuable hai jo sab kuch band kar chuka ho.

10. Advanced Deep-Dive — Beyond the Basics

Ab tak humne "happy path" dekha — permission maango, token lo, notification dikhao. Ye teen advanced patterns hain jo senior-level production apps mein aksar chahiye hote hain, aur interview mein bhi frequently pooche jaate hain kyunki inke andar real distributed-systems thinking hai — reliability, eventual consistency, aur platform constraints ke saath kaam karna.

10.1 Silent / Data-Only Push Architecture

Har push notification mein ek visible alert hona zaroori nahi hai. Ek "silent push" (iOS terminology) ya "data-only message" (FCM terminology) aisi notification hoti hai jisme koi banner, sound ya badge nahi hota — sirf ek data payload hota hai jo app ko background mein briefly wake karta hai taaki wo kuch kaam kar sake, jaise: naya data server se sync karna, local cache invalidate karna, ya phir khud decide karna ki is data ke basis pe user ko visible notification dikhani hai ya nahi (jaise "agar naya message current open chat ka nahi hai, tab hi banner dikhao").

iOS pe ye content-available: 1 flag se hota hai APNs payload mein (bina alert key ke) — jab wo receive hoti hai, OS app ko background mein thodi der ke liye launch karta hai aur expo-task-manager ke through registered handler ko call karta hai. Android/FCM pe iska equivalent hai data-only message — matlab payload mein sirf data object hai, notification key bilkul absent hai; FCM aisi message ko seedha app ke background handler tak deliver kar deta hai, OS khud koi tray notification generate nahi karta.

lib/notifications/silentSync.ts
import * as TaskManager from "expo-task-manager"; // background task ko register/define karne ke liye Expo ka task manager module
import * as Notifications from "expo-notifications"; // background notification task register karne ke liye Notifications ka helper

// Task ka ek unique naam define kar rahe hain — module-level constant, kyunki register aur define dono jagah same string chahiye
const BACKGROUND_SYNC_TASK = "background-notification-sync"; // arbitrary string ID, sirf tumhare app ke andar unique honi chahiye

// Ye task definition file ke top-level pe honi chahiye (module scope mein), component ke andar NAHI —
// warna OS jab app ko background mein launch karega, ye definition register hi nahi hogi
TaskManager.defineTask(BACKGROUND_SYNC_TASK, async ({ data, error }) => { // jab bhi silent push aayegi, OS is callback ko chalayega
  if (error) { // agar OS-level error aaya (jaise task setup fail hua)
    console.error("Background sync task error:", error); // log karo, silently fail mat hone do
    return; // aage kuch mat karo, data bhi trustworthy nahi hoga error ke case mein
  } // if block close

  const payload = data as { unreadCount?: number; syncSince?: string } | null; // backend ne jo silent push data bheja, uska expected shape

  try { // network call fail ho sakta hai (bad connectivity), isliye try/catch zaroori
    await fetch(`https://api.myapp.com/sync?since=${payload?.syncSince ?? ""}`); // naya data quietly fetch karke local cache/DB update karne ke liye call

    if (typeof payload?.unreadCount === "number") { // agar backend ne authoritative unread count bhi bheja hai is silent push mein
      await Notifications.setBadgeCountAsync(payload.unreadCount); // badge ko turant sync kar do — user ko dikhega bina koi banner dikhe (badge sync section mein detail hai)
    } // if block close

    return TaskManager.BackgroundFetchResult?.NewData; // OS ko batao ki naya data mila (kuch OS versions is signal se future scheduling adjust karte hain)
  } catch (err) { // agar fetch hi fail ho gaya (network down, server down, etc.)
    console.error("Silent sync failed:", err); // log karo debugging ke liye
    return TaskManager.BackgroundFetchResult?.Failed; // OS ko fail signal do, taaki wo retry strategy apna sake
  } // try/catch close
}); // defineTask call close

// App startup pe ye call karo taaki OS ko pata ho ki silent push aane pe kaunsa task chalana hai
export async function registerBackgroundSyncTask(): Promise<void> { // return void — sirf registration side-effect hai
  await Notifications.registerTaskAsync(BACKGROUND_SYNC_TASK); // OS-level registration — batata hai "silent notifications ke liye ye task use karo"
} // function close
⚠️ Silent Push Sirf "Hint" Hai, Guarantee Nahi

Yaad rakho — iOS bahut aggressively silent push execution ko throttle karta hai battery preserve karne ke liye. Agar tumhara app user ke device pe recently bahut zyada background CPU/network use kar chuka hai, ya device low-power mode mein hai, ya app ko user ne force-quit kiya hai, iOS silent push ko completely drop kar sakta hai, koi error signal ke bina. Isliye silent push ko kabhi bhi "guaranteed delivery mechanism" ki tarah architect mat karo (jaise "critical data sync sirf silent push se hoga") — ye ek best-effort optimization hint hai. Critical data ke liye hamesha ek fallback rakho: jab user app khole (foreground), turant ek explicit sync call bhi karo — silent push sirf "jaldi mil jaaye toh accha" wala latency improvement hai, primary reliability mechanism nahi.

10.2 Notification Categories & Interactive Actions

Kabhi dekha hoga ki kuch apps ki notification pe seedha action buttons hote hain — jaise ek message notification pe "Reply" aur "Mark as Read" buttons, bina app khole. Ye notification categories se hota hai — pehle tumhe ek category define karni padti hai jisme kaunse actions available hain, phir jab tum notification bhejte ho, us notification ko us category se tag karte ho.

lib/notifications/categories.ts
import * as Notifications from "expo-notifications"; // category registration bhi isi module se hoti hai

// App startup pe ek baar register karo — native OS ko batata hai ki is category ke actions kya hain
export async function setupMessageCategory(): Promise<void> { // return void, sirf setup side-effect hai
  await Notifications.setNotificationCategoryAsync("message", [ // category ID "message" — backend push payload mein isi ID ko reference karega
    { // pehla action object
      identifier: "mark-read", // unique action ID — response handler mein isse pehchanenge kaunsa button dabaya
      buttonTitle: "Mark as Read", // user-facing button label
      options: { opensAppToForeground: false }, // false = app ko foreground mein NAHI laana, sirf background mein action process karo
    }, // pehla action object close
    { // doosra action object
      identifier: "reply", // unique action ID
      buttonTitle: "Reply", // user-facing button label
      textInput: { submitButtonTitle: "Send", placeholder: "Type a reply…" }, // text input action — notification ke andar hi ek chhota text box dikhega
      options: { opensAppToForeground: false }, // reply bhi bina app khole submit ho sakta hai
    }, // doosra action object close
  ]); // setNotificationCategoryAsync call close
} // function close

// Action response handle karna — listener wahi hai jo tap handling mein use hota hai, bas ab actionIdentifier check karte hain
export function registerCategoryActionListener(): Notifications.Subscription { // return type Subscription — caller ko cleanup ke liye chahiye
  return Notifications.addNotificationResponseReceivedListener((response) => { // har notification response (tap ya action button) is se guzarta hai
    const { actionIdentifier, userText } = response; // actionIdentifier batata hai kaunsa button; userText sirf textInput action mein aata hai

    if (actionIdentifier === "mark-read") { // agar user ne "Mark as Read" dabaya
      const messageId = response.notification.request.content.data?.messageId; // payload se message ID nikaalo jise mark karna hai
      fetch(`https://api.myapp.com/messages/${messageId}/read`, { method: "POST" }); // silently backend ko update karo, koi UI change nahi (app khula bhi nahi hai)
    } else if (actionIdentifier === "reply" && userText) { // agar user ne reply likh ke submit kiya
      const messageId = response.notification.request.content.data?.messageId; // same tarah message ID nikaalo
      fetch(`https://api.myapp.com/messages/${messageId}/reply`, { // reply text ko backend ko bhejo
        method: "POST", // naya reply create karne ke liye POST
        headers: { "Content-Type": "application/json" }, // JSON body bhej rahe hain
        body: JSON.stringify({ text: userText }), // actual reply content
      }); // fetch call close
    } // if/else-if close
  }); // addNotificationResponseReceivedListener close, subscription return ho rahi hai
} // function close

Backend side pe jab notification bheji jaati hai, payload mein category ID include karni hoti hai (Expo payload mein categoryId: "message" field) — tabhi OS ko pata chalega ki is specific notification pe kaunse action buttons dikhane hain.

🧠 Senior Dev Note

Interactive actions ka sabse bada trap ye hai ki opensAppToForeground: false wale actions "headless" context mein chalte hain — matlab tumhare app ka koi UI mount nahi hai, koi React tree nahi hai, sirf ek bare-minimum JS environment hai jitni der ke liye OS allow karta hai (usually kuch seconds). Is context mein Redux store, React Context, ya kisi bhi UI-dependent state pe bharosa mat karo — sirf direct network calls ya local storage writes karo jo apne aap mein self-contained ho, jaise humne upar seedha fetch() use kiya, koi state management library nahi.

10.3 Badge Count Sync Architecture

App icon pe jo chhota number dikhta hai (badge count), wo OS automatically maintain nahi karta — tumhe explicitly Notifications.setBadgeCountAsync(n) call karke set karna padta hai. Bahut se developers galti se sochte hain ki har notification receive hone pe badge apne aap +1 ho jaata hai — ye sach nahi hai (kuch platforms pe kabhi partial default behavior tha, lekin production-grade apps isko kabhi bhi implicit nahi chhodte).

Yahan ek classic distributed-systems-jaisi bug aati hai: badge count drift. Scenario socho — user ke paas do devices hain (phone + tablet), dono pe app installed hai. User tablet pe 5 messages padh leta hai. Ab agar phone ka badge count sirf locally "+1 per notification" increment karke maintain ho raha hai, toh phone ka badge ab bhi purana (higher) number dikhayega — jab tak agla push na aaye. User ko confusing lagta hai: "maine toh padh liya, phir bhi 5 dikha raha hai".

Bad pattern vs Good pattern (conceptual)
// ❌ BAD — client-side increment, koi source of truth nahi, drift ho jaata hai
// Har naya push aane pe: currentBadge = currentBadge + 1
// Problem: dusre device pe read hone ka is device ko pata hi nahi chalega

// ✅ GOOD — server hi authoritative unread count maintain karta hai,
// aur HAR push payload (chahe visible ho ya silent) mein woh current total count included hota hai
// Client sirf "set karo is exact number pe" karta hai — kabhi "increment karo" nahi
lib/notifications/badgeSync.ts
import * as Notifications from "expo-notifications"; // badge API bhi isi module mein hai

// Ye payload shape backend se aana chahiye — HAR push (visible ya silent) mein authoritative count hona chahiye
type PushDataWithBadge = { // type definition — sirf documentation/type-safety ke liye
  authoritativeUnreadCount: number; // server ka current, ground-truth unread count — client ka apna calculation nahi
}; // type close

// Ye function har incoming notification (foreground listener ke andar se) call karo
export async function syncBadgeFromPushPayload(data: PushDataWithBadge): Promise<void> { // return void, sirf OS-level side-effect hai
  if (typeof data.authoritativeUnreadCount !== "number") { // defensive check — agar backend ne field bheji hi nahi (bug/old version)
    return; // kuch mat karo, purana badge waisa hi rehne do — galat number set karne se better
  } // if block close

  await Notifications.setBadgeCountAsync(data.authoritativeUnreadCount); // SET kar rahe hain (absolute value), INCREMENT nahi — yahi drift-proof pattern hai
} // function close

// Jab user app ke andar hi messages ko explicitly read maar de (foreground action)
export async function clearBadgeOnRead(): Promise<void> { // user ne chat khol ke sab padh liya, is case mein
  const response = await fetch("https://api.myapp.com/me/unread-count"); // server se fresh authoritative count maango (client ka apna guess mat lo)
  const { unreadCount } = await response.json(); // response body parse karo
  await Notifications.setBadgeCountAsync(unreadCount); // badge ko is fresh server value pe set karo — dusre devices pe hui activity bhi reflect hogi
} // function close
🧠 Senior Dev Note — Badge Ko "Set" Karo, "Increment" Nahi

Ye ek general distributed-state principle hai jo badge count mein bhi apply hota hai: jab bhi multiple sources (multiple devices, multiple push events) same counter ko update kar sakte hain, relative operations (increment/decrement) drift-prone hote hain, absolute operations (set to X) nahi. Server ko hamesha "current total unread count" ka single source of truth maintain karna chahiye, aur wo exact number har relevant push (visible ya silent) ke data payload mein bhejna chahiye. Client ka kaam sirf itna hai — "jo number mila, wahi set kar do". Isse multi-device consistency automatically theek rehti hai, bina kisi extra sync protocol ke.

11. 🎯 Interview Questions — Senior React Native Developer

Ye section un questions ko cover karta hai jo senior/staff-level React Native interviews mein push notifications ke topic pe aksar pooche jaate hain — sirf "API kaise call karte ho" wale surface-level nahi, balki internals, trade-offs, aur production debugging ki depth wale.

Q1. Backend se leke user ke lock screen tak — ek push notification ka poora path kya hai, step-by-step?

Answer: Poora path 6 broad stages mein todha ja sakta hai:

  • 1. Trigger — backend pe koi event hota hai (naya message, order update) jo notification bhejne ka decision leta hai, aur us user ke stored device token(s) ko DB se nikalta hai.
  • 2. Send request — backend Expo Push API (ya seedha FCM/APNs) ko ek HTTPS request bhejta hai jisme token, title/body, aur custom data payload hota hai.
  • 3. Proxy/routing — agar Expo use ho raha hai, Expo internally tokens ko dekh ke decide karta hai ye Android device hai ya iOS, aur respective platform (FCM/APNs) ki apni auth (service account / APNs .p8 key) use karke unki actual API ko call karta hai.
  • 4. Platform delivery — FCM ya APNs is notification ko us device ke saath maintain ki hui persistent OS-level connection pe queue karta hai. Agar device offline hai, wo store karke rakhte hain (limited time/count ke liye) aur jab device online aata hai deliver karte hain.
  • 5. OS handling — device pe OS ye notification receive karta hai apne background daemon mein (app ka JS process chal raha ho ya nahi, koi farak nahi padta), aur decide karta hai kya karna hai — agar visible alert hai, tray/lock-screen mein render karta hai; agar silent hai, app ko brief background wake dega.
  • 6. App-level handling — agar user tap karta hai, OS app ko launch/foreground karta hai aur expo-notifications ka response listener fire hota hai jahan se hum deep-link navigate karte hain.

Interview mein ye batana important hai ki step 1-3 hamesha tumhare control mein hai, step 4-5 completely OS/platform vendor ke control mein hai — isliye "notification nahi pahunchi" jaise bugs debug karte waqt in dono halves ko alag treat karna padta hai.

Q2. Expo apni khud ki push service kyun banata hai jab FCM/APNs already exist karte hain? Aur kab tum Expo ko skip kar doge?

Answer: Expo Push Service ek unification layer hai — FCM aur APNs ke payload format, authentication mechanism (service account JSON vs .p8 key), aur retry semantics bilkul alag hain. Expo ye differences abstract kar deta hai ek single REST API ke peeche, taaki tumhe do alag integrations maintain na karni pade. Trade-off ye hai ki: ek extra network hop (latency), rate limits (Expo ke apne push service pe), aur ek additional dependency/point-of-failure add ho jaata hai.

Skip karne ke valid reasons: (a) massive scale jahan Expo ka rate limit genuinely bottleneck ban raha ho, (b) compliance/data-residency requirement jo kisi third-party proxy se notification data guzarne ko disallow kare, (c) tumhe FCM/APNs ke advanced features chahiye jo Expo abhi expose nahi karta (jaise APNs ke kuch niche priority/collapse-id options). In sabke bina, raw FCM/APNs pe migrate karna sirf extra engineering overhead hai bina proportional benefit ke.

Q3. Expo ki jagah tum OneSignal kab choose karoge, jab Expo simpler hai setup karne mein?

Answer: Decision engineering complexity pe based nahi hota, business need pe hota hai. OneSignal tab justify hota hai jab non-engineering stakeholders (marketing/growth team) ko khud se campaigns banane, A/B test karne, ya user segments target karne ka dashboard chahiye ho — bina har baar engineering ko involve kiye. Agar aisa koi requirement nahi hai aur tum sirf transactional/product notifications bhej rahe ho (order updates, chat messages), Expo Notifications kaafi hai aur unnecessary bundle size + third-party dependency add nahi karta. Senior dev ka job yahan ye hai ki team ko ye samjhaye ki "powerful" aur "necessary" alag cheezein hain.

Q4. Users report karte hain ki notifications "kabhi-kabhi" nahi aati. Poori pipeline mein possible failure points kya hain, aur har ek ko kaise debug/instrument karoge?

Answer: Ye ek classic distributed-system-debugging question hai — approach hamesha pipeline ko stages mein todkar, har stage pe observability add karna hai:

  • Stale/invalid token — backend mein token store outdated ho sakta hai. Fix: Expo/FCM se aane wale push receipts ko check karo — agar receipt DeviceNotRegistered error deta hai, us token ko turant DB se remove karo.
  • Permission revoked — user ne baad mein Settings se permission off kar diya but backend ko pata nahi. Fix: app launch pe getPermissionsAsync() se current status backend ko sync karo, sirf token registration pe bharosa mat karo.
  • Credentials misconfigured — Firebase server key ya APNs .p8 key EAS mein expire/galat ho gayi. Fix: send response/receipt ka status code check karo (auth errors turant dikh jaate hain, sabhi users ke liye ek saath fail hoga — ye pattern isolate karne mein help karta hai).
  • OS-level throttling — iOS Low Power Mode ya Doze (Android) background delivery ko delay/drop kar sakte hain. Fix: is behavior ko accept karo, aggressive silent-push-dependent architecture na banao (jaisa Advanced Deep-Dive section mein discuss kiya).
  • Client-side listener bug — notification aa gayi lekin app crash ho gaya ya listener register hi nahi hua. Fix: Sentry/crash reporting ke saath breadcrumbs add karo notification lifecycle events pe (received, displayed, tapped) taaki funnel drop-off dikh sake.

Instrumentation ka golden rule: har stage pe apna khud ka logging/analytics event daalo — "push sent" (backend), "push delivered to Expo" (Expo response), "receipt confirmed" (async receipt check), "notification received on device" (client listener), "notification tapped" (client listener). Jahan funnel drop hota hai, wahi tumhara failure point hai.

Q5. Ek push token invalid ho jaata hai — backend ko iska poora lifecycle kaise handle karna chahiye?

Answer: Token lifecycle ek proper state machine ki tarah design karna chahiye:

Token lifecycle states (conceptual)
ACTIVE        → app launch pe register hua, backend ke DB mein saved, valid maana jaata hai
STALE?        → app reinstall/data-clear/OS-invalidation se naya token generate ho sakta hai purane ki jagah
                (backend ko pata nahi jab tak naya register call na aaye — isliye HAR launch pe re-register zaroori)
REJECTED      → push service (FCM/APNs/Expo) receipt mein "DeviceNotRegistered" jaisa error deta hai
                (matlab OS-level pe ye token ab kisi installed app se map nahi hota)
REMOVED       → backend is token ko turant DB se delete kare jab REJECTED signal mile — future sends
                is dead token pe waste nahi honge, aur error-rate metrics clean rahenge

Practically iska matlab hai backend mein do cheezein implement karna: (1) ek idempotent upsert endpoint jahan token registration hamesha safe hai dobara call karne ke liye (chahe same token ho ya naya), aur (2) ek async job/webhook jo push service ke delivery receipts poll/receive karta hai aur invalid tokens ko proactively clean karta hai — bina is cleanup ke, DB mein dead tokens accumulate hote rehte hain aur send-success rate metrics misleading ho jaati hain.

Q6. Foreground mein notification handling background/killed state se fundamentally kyun alag hai?

Answer: Jab app foreground mein hai, JS engine already running hai aur tumhara code directly control kar sakta hai ki OS notification tray mein kuch dikhaye ya nahi (setNotificationHandler ke through) — is stage pe tumhare paas full app state (Redux/Context) available hai, isliye tum smart decisions le sakte ho, jaise "agar user already isi chat screen pe hai, banner suppress karke seedha message list update kar do".

Background/killed state mein tumhara JS process ya toh suspended hai ya poora khatam ho chuka hai — OS khud hi tray mein notification dikhata hai bina tumhare app ko involve kiye (visible push ke case mein). Tumhara code sirf tab chalta hai jab user tap kare (response listener) ya ek silent push OS ko brief background execution grant kare. Is state mein tumhare paas koi live app state nahi hai — sab kuch fresh cold-start jaisa treat karna padta hai, koi in-memory assumption nahi chalegi.

Q7. Silent push ka use-case kya hai, aur is architecture ki reliability limitations kya hain?

Answer: Silent push (iOS content-available: 1, FCM data-only message) app ko briefly background mein wake karta hai bina user ko kuch dikhaye — common use-cases hain: naya data proactively sync karna taaki jab user app khole tab tak fresh ho, ya kisi visible notification se pehle server-side decision logic run karna (jaise "kya ye message abhi user ke liye relevant hai?").

Limitation ye hai ki ye ek best-effort mechanism hai, guaranteed delivery nahi. iOS battery preserve karne ke liye silent push frequency ko heavily throttle karta hai — agar app recently already background resources use kar chuka hai, ya device Low Power Mode mein hai, silent push bilkul deliver hi nahi ho sakti, koi error signal ke saath bhi nahi. Isliye kabhi bhi critical business logic (jaise payment confirmation processing) sirf silent push pe depend nahi honi chahiye — hamesha ek foreground-triggered explicit sync fallback rakho.

Q8. Multi-device badge count ka drift bug kya hota hai, aur usse kaise architect karke avoid karte ho?

Answer: Badge count ek per-device local value hai jo setBadgeCountAsync() se set hoti hai — OS khud automatically increment/decrement nahi karta. Bug tab hota hai jab tum client-side pe naive "+1 per notification" logic likhte ho: agar user ke multiple devices hain aur ek device pe messages read ho jaate hain, doosre device ka badge count us update se completely unaware rehta hai kyunki uska koi apna local counter hai jo kisi doosre device ki activity se sync hi nahi hai.

Sahi architecture: server ko single source of truth banao unread count ke liye. Har push payload (chahe visible ho ya silent) mein current authoritative count include karo, aur client sirf setBadgeCountAsync(receivedCount) — absolute set, kabhi relative increment nahi. Isse multi-device consistency automatically maintain rehti hai bina kisi extra sync protocol banaye — ye wahi principle hai jo distributed counters mein "last-write-wins with authoritative source" pattern kehlata hai.

Q9. Interactive notification actions (jaise "Reply" button) ko implement karte waqt sabse bada gotcha kya hai?

Answer: Sabse bada gotcha ye samajhna hai ki opensAppToForeground: false wale actions headless JS context mein chalte hain — app ka koi UI mounted nahi hota, koi React tree exist nahi karta us waqt. Agar tumhara action handler kisi Redux store, React Context, ya kisi bhi UI-bound global state pe dependency rakhta hai, wo undefined/uninitialized milega aur silently fail hoga ya crash karega. Sahi approach: action handlers ko fully self-contained rakho — sirf direct network calls, local storage reads/writes, ya AsyncStorage jaisi standalone APIs use karo jo bina app UI mount hue bhi kaam karti hain. Ye discipline bilkul waisi hi hai jaisi tum background task handlers (jaise silent push ke task) ke liye rakhte ho — assume karo ki tumhare paas sirf bare JS runtime hai, kuch seconds ke liye.
