1. Environment Variables in Production — The Full Picture

Chapter 1 mein humne ek line mein mention kiya tha ki EXPO_PUBLIC_ prefix wale env vars client mein bundle ho jaate hain, secret nahi hote. Ab is baat ko poori depth se samajhte hain, kyunki yehi galatfahmi production mein sabse zyada security incidents create karti hai.

Build-time inlining — actually hota kya hai

Jab tum app.config.ts ya kisi component mein process.env.EXPO_PUBLIC_SOMETHING likhte ho, Metro bundler build-time pe is expression ko literally replace kar deta hai uski actual string value se — bilkul waise jaise ek find-and-replace. Iska matlab ye value ab tumhari JS bundle file (.hbc Hermes bytecode ya plain JS bundle) ke andar plain text/bytecode ke roop mein permanently baked ho jaati hai. Runtime pe koi "environment" query nahi ho rahi — RN apps ke paas web ke Node.js jaisa server environment hota hi nahi hai jisse runtime pe env vars read ho sakein.

Iska practical result: koi bhi jo tumhari .ipa/.apk file ko decompile/unzip karega (jaise unzip app.apk, ya npx react-native-bundle-visualizer jaisa tool, ya sirf network traffic ko Charles Proxy/mitmproxy se inspect karega), wo tumhare saare EXPO_PUBLIC_* values plain text mein dekh sakta hai. Ye koi "hack" nahi hai — ye bas JS bundle padhna hai, jo har RN app ke liye technically possible hai.

🚨 Security Critical — EXPO_PUBLIC_ Secrets Kabhi Mat Rakho

Kabhi bhi ek true secret ko EXPO_PUBLIC_ prefix ke saath mat rakho. Concrete examples jo bahut common mistakes hain:

  • Stripe secret key (sk_live_...) — agar ye EXPO_PUBLIC_STRIPE_SECRET_KEY ban gayi, toh koi bhi attacker isse nikal ke tumhare Stripe account se seedha charges create kar sakta hai, refunds issue kar sakta hai, ya customer data dekh sakta hai. (Stripe ki publishable key — pk_live_... — public hone ke liye hi design hui hai, wo alag baat hai aur wo EXPO_PUBLIC_ mein theek hai.)
  • Unrestricted Google Maps/Cloud billing key — agar API key ko Google Cloud Console mein restrict nahi kiya (application restrictions + API restrictions dono), toh attacker isse nikal ke apne khud ke projects mein use kar sakta hai aur tumhare billing account pe charges daal sakta hai. Bundle se key nikalna trivial hai, isliye restriction hi asli defense hai — key ko "chupana" defense nahi hai.
  • Database admin/root credentials, third-party API keys jinke paas write ya billing-level access hai — ye sab client app mein kabhi bhi, kisi bhi prefix ke saath nahi jaane chahiye. In sabko sirf server-side code touch karna chahiye.

Do tarah ke "secrets" — differentiate karna seekho

Senior mental model ye hai ki har env var ko in do categories mein classify karo:

CategoryExampleKahan rakhein
Client-safe public identifiers Supabase URL, Supabase anon key, Stripe publishable key, analytics write-only key EXPO_PUBLIC_* — bundle mein jaana hi is design ka part hai, protection kisi aur layer (RLS, backend validation) se aata hai
True server-side secrets Stripe secret key, Supabase service_role key, unrestricted third-party API keys, DB admin creds App binary mein kabhi nahi — sirf server (Expo Router API route, separate backend, ya EAS Secret jo sirf build-server pe expose ho)

EAS Secrets — build-time secrets jo git mein nahi jaane chahiye

Kabhi kabhi tumhe ek value build ke waqt chahiye hoti hai (jaise ek native config file generate karne ke liye, ya app.config.ts ke andar kisi calculation ke liye) lekin wo git repo mein commit nahi honi chahiye (jaise ek self-hosted Sentry auth token). Iske liye EAS ka secrets system hai — ye alag hai EXPO_PUBLIC_* client-safe vars se.

terminal — EAS secret create karna
# EAS account pe ek naya build-time secret create kar rahe hain
eas secret:create \
  --scope project # sirf isi project ke liye scoped hai, doosre projects nahi dekh sakte \
  --name SENTRY_AUTH_TOKEN # secret ka naam, build ke andar isi naam se accessible hoga \
  --value "sntrys_xxxxxxxxxxxx" # actual secret value, ye kabhi git mein commit nahi hoga \
  --type string # plain string secret (file bhi ho sakta hai --type file se)

# saare configured secrets list karna, values hidden rehti hain
eas secret:list

Ye secret sirf EAS ke cloud build servers pe available hota hai build ke waqt (jaise app.config.ts ke andar Sentry source maps upload karne ke liye) — ye final app bundle mein khud automatically nahi jaata jab tak tum explicitly usse EXPO_PUBLIC_ var mein assign na karo. Yehi difference samajhna zaroori hai: EAS Secret ek build-time-only value store hai, jabki EXPO_PUBLIC_* ek runtime-client-visible value hai. Dono alag purpose solve karte hain.

🧠 Senior Dev Note

Ek common confusion: log kehte hain "maine EAS secret bana diya toh secure hai". Nahi — agar tumne us secret ko app.config.ts ke andar EXPO_PUBLIC_API_KEY jaisi variable mein assign kiya, toh wo build process ke through phir bhi final client bundle mein bake ho jaayega. EAS Secret sirf ye guarantee karta hai ki value git history mein plaintext nahi hai — ye client-side exposure se protect nahi karta. Wo do alag problems hain.

2. Expo Router API Routes

Ab jab humne dekh liya ki true secrets client app mein nahi ja sakte, sawaal ye hai — agar app ko kisi third-party API ko secret key ke saath call karna hai (jaise OpenAI, ya ek payment provider), toh wo call kahan se ho? Traditional answer hai "alag backend banao" (Express/Node server). Expo Router iske liye ek lightweight built-in solution deta hai: API Routes.

+api.ts convention — server function, same project mein

Agar tum app/ folder ke andar ek file banao jiska naam +api.ts pe end hota hai (jaise app/api/hello+api.ts), Expo Router use ek server route ke roop mein treat karta hai — matlab ye file Metro bundle mein client ke liye include hi nahi hoti. Ye sirf server (Node.js runtime) pe run hota hai, jab is route ka koi HTTP request aata hai. Yehi wajah hai ki secrets ko yahan safely use kar sakte ho — client bundle ise kabhi dekhta hi nahi.

app/api/hello+api.ts
// Ye file client bundle mein nahi jaati — sirf server (Node runtime) pe execute hoti hai
export async function GET(request: Request) {
  // "GET" naam ka export HTTP GET method ko handle karta hai — POST/PUT/DELETE bhi isi tarah export ho sakte hain
  const secretKey = process.env.OPENAI_SECRET_KEY; // server-only secret, yahan process.env se seedha readable hai (Node runtime hai)

  if (!secretKey) {
    // agar server pe env var missing hai (misconfiguration), fail fast karo
    return Response.json(
      { error: "Server misconfigured" }, // client ko generic error, internal detail leak nahi karte
      { status: 500 } // 500 = internal server error status code
    );
  }

  const upstream = await fetch("https://api.openai.com/v1/models", {
    // third-party API ko yahan call kar rahe hain, secret key ke saath — client ye key kabhi nahi dekhta
    headers: { Authorization: `Bearer ${secretKey}` }, // secret key sirf server-to-server request mein use ho rahi hai
  });

  const data = await upstream.json(); // upstream response ko JSON mein parse kiya

  return Response.json({ models: data.data }); // sirf safe/needed fields client ko wapas bhej rahe hain, poora upstream response nahi
}

Client side se is route ko call karna bilkul normal fetch jaisa hai — koi special client library nahi chahiye, kyunki ye ek standard HTTP endpoint hai jo tumhare hi app ke saath deploy hota hai:

calling the API route from a component
import { useEffect, useState } from "react"; // state aur lifecycle hooks import kiye

function ModelsScreen() {
  const [models, setModels] = useState([]); // fetched models ko local state mein store karenge

  useEffect(() => {
    fetch("/api/hello") // same-app API route ko relative path se call kar rahe hain, secret client mein kahin nahi hai
      .then((res) => res.json()) // response body ko JSON mein parse kiya
      .then((data) => setModels(data.models)); // safe data ko state mein daal diya
  }, []); // empty deps — sirf mount pe ek baar chalega

  return null; // yahan render logic simplified rakha hai, real UI baad mein add hoga
}
🧠 Senior Dev Note — BFF Pattern

Ye exactly Backend-for-Frontend (BFF) pattern hai — ek thin server layer jo client aur asli third-party services ke beech baithta hai, sirf isliye taaki secrets client se door rahein aur client ko sirf wahi minimal, safe data mile jiski use zaroorat hai. Expo Router API Routes iska sabse lightweight version hai — na alag repo chahiye, na alag deployment pipeline (agla section EAS Hosting dekhega), sab kuch ek hi Expo project ke andar colocated hai.

3. Streaming Data with Expo Fetch

React Native ka default fetch (jo whatwg-fetch polyfill pe based hai) historically poora response buffer karta tha before resolve karne — matlab agar server chunk-by-chunk data bhej raha hai (jaise ek LLM streaming response), RN app ko tab tak kuch nahi milta jab tak poora response complete na ho jaaye. Ye ek badi limitation thi jab AI/LLM streaming UIs (jaise ChatGPT-style token-by-token typing effect) RN mein banane the.

expo/fetch — true streaming support

Expo SDK ka expo/fetch module ek naya fetch implementation deta hai jo native networking stack (iOS pe URLSession, Android pe OkHttp) ko directly use karta hai, jisse Response.body ek actual streamable ReadableStream ban jaata hai — chunks aate hi turant JS ko deliver hote hain, poora response wait nahi karna padta.

streaming a response token-by-token
import { fetch } from "expo/fetch"; // RN ke default fetch ki jagah streaming-capable fetch import kiya

async function streamResponse(prompt: string, onToken: (text: string) => void) {
  const response = await fetch("/api/chat", {
    method: "POST", // hum ek Expo Router API route ko POST kar rahe hain jo LLM ko proxy karta hai
    headers: { "Content-Type": "application/json" }, // JSON body bhej rahe hain, isliye content-type set kiya
    body: JSON.stringify({ prompt }), // prompt ko JSON string mein serialize kiya
  });

  const reader = response.body?.getReader(); // response body se ek stream reader nikaala (optional chaining kyunki body null ho sakta hai)
  if (!reader) return; // agar body hi nahi mila (kabhi kabhi edge case), silently return

  const decoder = new TextDecoder(); // raw bytes (Uint8Array chunks) ko readable text mein convert karne ke liye decoder

  while (true) {
    const { done, value } = await reader.read(); // stream se agla chunk read kiya, "done" batata hai stream khatam hui ya nahi
    if (done) break; // stream complete ho gayi, loop exit karo

    const chunkText = decoder.decode(value, { stream: true }); // is chunk ke bytes ko text mein decode kiya, stream:true partial multi-byte chars handle karta hai
    onToken(chunkText); // caller ko naya text chunk turant de diya — UI isse turant render kar sakta hai
  }
}
💡 Quick Tip

Is streamResponse function ka onToken callback typically ek setState call karega jo existing text mein naya chunk append karta hai — isse UI mein wahi "typing effect" milta hai jo LLM chat apps mein dikhta hai, bina poore response ka wait kiye.

4. Deploying with EAS Hosting

Agar tumne section 2 mein dekhe gaye Expo Router API routes use kiye hain, unhe production mein kahin na kahin run hona padega — sirf apne phone/emulator pe local Metro server pe nahi. Iske liye Expo EAS Hosting deta hai — ek managed deployment target jo tumhare Expo Router project ke web output (jisme API routes bhi shamil hain) ko production servers pe deploy kar deta hai.

terminal — EAS Hosting pe deploy karna
# pehle project ko web ke liye export karte hain (static + server output dono generate hote hain)
npx expo export -p web # -p web = web platform target, API routes bhi is output mein include hoti hain

# phir EAS Hosting pe deploy karte hain
eas deploy # build ke exported output ko EAS ke hosting infra pe upload + deploy karta hai

# production alias ke saath deploy karna (stable production URL ke liye)
eas deploy --prod # --prod flag production environment/URL alias ko update karta hai

Ye kab matter karta hai, kab nahi — ye samajhna important hai:

  • Agar tumhara app sirf ek external backend (jaise Supabase, ya tumhara apna alag Node/ Django server) ko directly hit karta hai, aur tumne koi +api.ts route nahi likha, toh EAS Hosting ki zaroorat hi nahi hai — tumhara "backend" already kahin aur host ho raha hai.
  • Agar tumne Expo Router API routes use kiye hain (BFF pattern, secrets hide karne ke liye), toh unhe production mein kaam karne ke liye zaroor kisi server pe deploy hona padega — EAS Hosting sabse straightforward built-in option hai, kyunki wahi project structure jo dev mein local chal raha tha, wahi seedha deploy ho jaata hai bina extra config ke.

5. Supabase Overview and UI Tour

Supabase ek open-source Firebase alternative hai — lekin core difference ye hai ki Supabase ke peeche ek real Postgres database hai (Firebase ke proprietary NoSQL Firestore ki jagah), jo senior devs ko SQL, joins, foreign keys, aur relational integrity jaisi cheezein deta hai jo Firestore mein natively nahi milti.

Supabase ek hi platform mein ye sab bundle karta hai:

  • Postgres Database — full relational SQL database, extensions (PostGIS, pgvector) ke saath
  • Auth — email/password, magic links, OAuth (Google/Apple/GitHub), phone OTP — sab built-in
  • Storage — file/image uploads, bucket-level access policies
  • Realtime — Postgres changes (insert/update/delete) ko WebSocket ke through live subscribe kar sakte ho
  • Auto-generated REST + GraphQL API — table banate hi turant ek REST endpoint (PostgREST ke through) aur GraphQL schema mil jaata hai, koi backend code likhne ki zaroorat nahi

6. Creating Tables

Table banane ka sabse reliable tareeka SQL Editor mein raw SQL likhna hai (Table Editor UI bhi available hai, lekin SQL version-controllable hai — tum ise migration file ke roop mein git mein commit kar sakte ho, jo production discipline ke liye zaroori hai). Ek typical todos table:

SQL Editor — todos table create karna
create table todos ( -- naya table "todos" bana rahe hain public schema mein
  id uuid primary key default gen_random_uuid(), -- har row ka unique id, Postgres khud generate karega
  user_id uuid references auth.users(id) on delete cascade not null, -- kis user ka todo hai, Supabase Auth ke internal users table se foreign key link; user delete ho toh todos bhi delete ho jaayein
  title text not null check (char_length(title) > 0), -- todo ka text, empty string allow nahi karenge (constraint check)
  is_completed boolean not null default false, -- naya todo default false (incomplete) state mein banega
  created_at timestamptz not null default now() -- kab bana, default current timestamp (with timezone)
); -- statement close

create index todos_user_id_idx on todos(user_id); -- user_id pe index banaya, taaki "mere todos dikhao" query fast rahe (RLS filter bhi isi column pe hoga)

Notice karo user_id references auth.users(id) — Supabase Auth internally apne users ko auth.users naam ke ek special (protected) schema/table mein store karta hai. Apni tables ko isse foreign-key link karna Supabase ka standard pattern hai — isse Postgres khud enforce karta hai ki koi bhi todos row kisi non-existent user ko point nahi kar sakta.

7. Installation and CRUD Operations

Client setup

Sabse pehle SDK install karte hain aur client instance banate hain. Notice karo — yahan hum EXPO_PUBLIC_SUPABASE_ANON_KEY use kar rahe hain, jo section 1 ke danger callout ke against contradict nahi karta, kyunki ye key design se hi public/client-safe hai — iski protection RLS policies se aati hai, hiding se nahi (section 8 mein detail).

terminal — install
npx expo install @supabase/supabase-js # Supabase ka official JS client, expo install version-compatibility resolve karta hai
npx expo install @react-native-async-storage/async-storage # Supabase session ko persist karne ke liye storage adapter chahiye
lib/supabase.ts
import { createClient } from "@supabase/supabase-js"; // Supabase client banane ke liye function import kiya
import AsyncStorage from "@react-native-async-storage/async-storage"; // session token persist karne ke liye storage adapter import kiya

const supabaseUrl = process.env.EXPO_PUBLIC_SUPABASE_URL!; // Supabase project ka URL env var se le rahe hain, ! se TS ko bata rahe hain ye undefined nahi hoga
const supabaseAnonKey = process.env.EXPO_PUBLIC_SUPABASE_ANON_KEY!; // public "anon" key le rahe hain — ye client mein expose karna safe hai, RLS isse protect karta hai

export const supabase = createClient(supabaseUrl, supabaseAnonKey, { // client instance bana ke export kar rahe hain, poori app mein reuse hoga
  auth: { // auth-specific config block
    storage: AsyncStorage, // session (refresh token) yahan persist hogi taaki app restart pe login na todna pade
    autoRefreshToken: true, // expired access token ko background mein automatically refresh karega
    persistSession: true, // session ko disk pe persist karega, memory-only nahi
    detectSessionInUrl: false, // ye web-only feature hai (magic link URL parsing), RN mein false rakhte hain
  },
});

CRUD — full example component

Ab ek complete component dekhte hain jo Create, Read, Update, Delete — chaaron operations demonstrate karta hai ek todos list ke saath:

components/TodoList.tsx
import { useEffect, useState } from "react"; // state aur lifecycle hooks
import { View, Text, TextInput, Button, FlatList } from "react-native"; // UI primitives
import { supabase } from "../lib/supabase"; // hamara shared Supabase client instance

type Todo = { id: string; title: string; is_completed: boolean }; // row shape ka TypeScript type

function TodoList() {
  const [todos, setTodos] = useState<Todo[]>([]); // fetched todos ki list local state mein
  const [newTitle, setNewTitle] = useState(""); // naya todo type karne ke liye input state

  // ---------- READ ----------
  const fetchTodos = async () => {
    const { data, error } = await supabase
      .from("todos") // "todos" table target kiya
      .select("id, title, is_completed") // sirf zaroori columns select kiye, "*" se better practice
      .order("created_at", { ascending: false }); // naye todos sabse upar dikhenge

    if (error) { console.error(error); return; } // error ho toh log karo aur aage mat badho
    setTodos(data ?? []); // state update, data null ho toh empty array fallback
  };

  useEffect(() => {
    fetchTodos(); // component mount hote hi todos fetch karo
  }, []); // empty deps — sirf ek baar mount pe chalega

  // ---------- CREATE ----------
  const addTodo = async () => {
    const { data: { user } } = await supabase.auth.getUser(); // current logged-in user nikaala
    if (!user) return; // safety check — logged out user todo add nahi kar sakta

    const { error } = await supabase
      .from("todos") // "todos" table target kiya
      .insert({ title: newTitle, user_id: user.id }); // naya row insert kiya, user_id explicitly current user ka set kiya

    if (error) { console.error(error); return; } // insert fail hua toh log karo
    setNewTitle(""); // input field clear kiya
    fetchTodos(); // list ko refresh kiya taaki naya todo turant dikhe
  };

  // ---------- UPDATE ----------
  const toggleTodo = async (todo: Todo) => {
    const { error } = await supabase
      .from("todos") // "todos" table target kiya
      .update({ is_completed: !todo.is_completed }) // completed status flip kiya
      .eq("id", todo.id); // sirf isi specific id wali row update ho, WHERE id = todo.id ke barabar

    if (error) { console.error(error); return; } // update fail hua toh log karo
    fetchTodos(); // list refresh
  };

  // ---------- DELETE ----------
  const deleteTodo = async (id: string) => {
    const { error } = await supabase
      .from("todos") // "todos" table target kiya
      .delete() // delete operation
      .eq("id", id); // sirf isi id wali row delete ho

    if (error) { console.error(error); return; } // delete fail hua toh log karo
    fetchTodos(); // list refresh
  };

  return (
    <View>
      <TextInput value={newTitle} onChangeText={setNewTitle} placeholder="Naya todo..." />
      <Button title="Add" onPress={addTodo} />
      <FlatList
        data={todos}
        keyExtractor={(item) => item.id}
        renderItem={({ item }) => (
          <View>
            <Text onPress={() => toggleTodo(item)}>
              {item.is_completed ? "✅ " : "⬜ "}{item.title}
            </Text>
            <Button title="Delete" onPress={() => deleteTodo(item.id)} />
          </View>
        )}
      />
    </View>
  );
}

export default TodoList; // component export kiya reuse ke liye

8. Row Level Security (RLS) — The Core Security Model

Ab is chapter ka sabse important concept — jo samajh liya, wo Supabase ke saath production-ready ban jaata hai; jo nahi samjha, uski app ek data breach hai bas waiting to happen.

Traditional backend vs Supabase ka model — fundamental difference

Ek traditional architecture mein (jaise apna Express/Django backend), client kabhi database ko directly touch nahi karta. Har request pehle backend API se guzarti hai, jahan tum manually if (todo.user_id !== req.user.id) throw new Error("forbidden") jaisa authorization check likhte ho, phir hi database query chalti hai. Database khud "blindly trust" karta hai ki jo query aayi hai wo authorized hai — permission logic poora application code mein hoti hai.

Supabase ka model fundamentally different hai — hamare CRUD example mein React Native app directly Postgres ko query kar raha tha (via auto-generated REST API), koi custom backend beech mein nahi tha. Iska matlab agar database khud permission enforce nahi karti, toh koi bhi cheez enforce nahi kar rahi — client-side code ko toh trivially bypass kiya ja sakta hai (jaise Postman se seedha anon key ke saath request bhej ke).

Yahi gap Row Level Security (RLS) bharta hai — ye Postgres ka native feature hai jo table-level pe policies define karne deta hai: "kaunsi rows kaun dekh/edit/delete kar sakta hai". Jab RLS enabled ho, Postgres har single query pe automatically ye policies apply karta hai — chahe query REST API se aayi ho, GraphQL se, ya seedha SQL Editor se — koi bypass nahi hai (service_role key ke alawa, jo section 9 mein cover karenge).

RLS enable karna aur policy likhna

SQL Editor — RLS enable + policies
alter table todos enable row level security; -- is table pe RLS enforcement ON kar diya — ab default sabkuch DENY hai jab tak policy na ho

create policy "Users can view their own todos" -- policy ka descriptive naam
on todos -- kis table pe apply hogi
for select -- ye policy sirf SELECT (read) operations pe apply hogi
using (auth.uid() = user_id); -- condition: row tabhi visible hogi jab row ka user_id == current logged-in user ka id ho

create policy "Users can insert their own todos" -- doosri policy, insert ke liye
on todos -- same table
for insert -- ye INSERT operations pe apply hogi
with check (auth.uid() = user_id); -- naya row tabhi insert ho sakta hai jab uska user_id current user ke barabar ho (koi doosre ke naam se todo nahi bana sakta)

create policy "Users can update their own todos" -- teesri policy, update ke liye
on todos -- same table
for update -- UPDATE operations pe apply hogi
using (auth.uid() = user_id) -- kis row ko update karne ki permission hai (existing row check)
with check (auth.uid() = user_id); -- update ke baad bhi user_id same rehna chahiye (koi apna todo kisi aur ko transfer nahi kar sakta)

create policy "Users can delete their own todos" -- chauthi policy, delete ke liye
on todos -- same table
for delete -- DELETE operations pe apply hogi
using (auth.uid() = user_id); -- sirf apni khud ki row delete kar sakta hai

auth.uid() ek Postgres function hai jo Supabase provide karta hai — ye current request ke JWT (jo client ne apne login session se automatically bheja) se decode karke logged-in user ka id return karta hai. Isi wajah se ye check server-side (database ke andar) ho raha hai — client isko fake/bypass nahi kar sakta, kyunki JWT cryptographically signed hai aur Postgres khud isse verify karke auth.uid() derive karta hai.

🚨 Security Critical — RLS Bhoolna Sabse Common Real Bug Hai

Agar tum ek table banate ho aur RLS enable karna bhool jaate ho (ya enable karke policies add karna bhool jaate ho), toh default Postgres/Supabase behavior ye hai:

  • RLS disabled table pe — koi bhi jiske paas anon key hai (jo hum already client bundle mein daal chuke hain, kyunki wo public hone ke liye design hui hai) us table ke saare rows read/write/delete kar sakta hai, chahe wo koi bhi ho, authenticated ho ya na ho.
  • Ye koi theoretical risk nahi hai — ye Supabase ke saath sabse common, real-world reported security incident hai. Multiple companies ne production mein apni poori users table, orders table, ya payment-related data publicly exposed kar diya sirf isliye kyunki naya table banaya aur RLS enable karna bhool gaye.
  • Rule of thumb: jaise hi create table chalao, agle hi statement mein alter table ... enable row level security; chalao — isse ek habit bana lo, kabhi "baad mein karunga" mat socho.
🧠 Senior Dev Note

RLS enable karne ke baad agar tum koi bhi policy nahi banate, toh default deny-all lagu ho jaata hai — matlab table completely inaccessible ho jaayegi (khud apne liye bhi, service_role key ke alawa). Ye "RLS enable = fail-safe by default" design hai — ek missing policy sirf ek confusing empty result deti hai (jo debugging mein frustrating ho sakta hai, section 10 mein iska gotcha dekhenge), lekin ye galti se data leak hone se hamesha better hai.

10. Real-World Gotchas

⚠️ .env file git mein commit ho jaana

Sabse basic lekin sabse common mistake — .env file ko .gitignore mein daalna bhool jaana, jisse service_role key ya third-party secrets git history mein permanently commit ho jaate hain (aur ek baar git history mein aa gaye toh sirf file delete karna kaafi nahi, history rewrite karni padti hai). Har naye project mein sabse pehla step: .gitignore mein .env, .env.local confirm karo. Production teams git-secrets ya gitleaks jaisa pre-commit hook bhi use karte hain jo commit hone se pehle hi pattern-match karke secret-looking strings ko block kar deta hai — ek accidental commit se bhi bachne ka extra layer.

⚠️ RLS policy legitimate query ko silently block kar rahi hai

Ye ek bahut confusing dev-time bug pattern hai: tumne query sahi likhi hai, data database mein exist bhi karta hai, lekin app mein empty result aa raha hai — koi error bhi nahi throw ho raha. 99% cases mein ye "empty data" nahi hai, ye ek missing ya galat RLS policy hai jo silently rows ko filter kar rahi hai (Postgres RLS policy fail hone pe error nahi deti, bas row ko result set se exclude kar deti hai). Debug karne ka fastest tareeka: Supabase dashboard ke SQL Editor mein (jo service_role-level access rakhta hai) wahi query chala ke check karo ki data actually exist karta hai ya nahi — agar SQL Editor mein data dikhta hai but app mein nahi, toh confirm ho gaya ki ye RLS issue hai, data issue nahi.

⚠️ Free-tier connection limits production mein fail hona

Supabase ka free tier (aur lower-paid tiers) Postgres connections ki ek hard limit rakhte hain (typically kaafi kam, jaise ~60 direct connections). Agar tumhara app scale karta hai aur bahut saare concurrent users/serverless function invocations directly Postgres se connect karne lagte hain (especially agar tum server-side se bhi connect kar rahe ho, jaise ek serverless API route jo har request pe naya Postgres client banata hai), toh production mein achanak "too many connections" jaisa error milna shuru ho jaata hai. Solution: Supabase ka built-in connection pooler (PgBouncer, transaction mode) use karo server-side connections ke liye, aur client-side se hamesha REST API (jo already pooled hai) use karo, raw Postgres connection client app se kabhi mat banao.

11. Advanced Deep-Dive — Beyond the Basics

Ab tak humne CRUD, RLS, aur key management dekh liya — ye woh cheezein hain jo har Supabase app mein chahiye hoti hain. Ye section wahan se aage jaata hai: jab app real users ke saath production mein chalti hai, tab realtime updates, flaky mobile networks, aur duplicate requests jaisi problems surface hoti hain jo ek senior RN dev ko architecturally solve karni padti hain — sirf "code likhna" kaafi nahi hota, "kis trade-off ke saath likhna hai" samajhna padta hai.

11.1 Realtime subscriptions — actually kaam kaise karti hain

Jab tum supabase.channel(...).on("postgres_changes", ...) likhte ho, ek "magic" jaisa feature lagta hai, lekin under the hood ye ek well-defined pipeline hai:

  • Postgres har change (insert/update/delete) ko apni Write-Ahead Log (WAL) mein likhta hai — ye WAL Postgres ki crash-recovery aur replication ki backbone hai, har commit se pehle isi log mein durably likha jaata hai.
  • Supabase Realtime server Postgres ke logical replication protocol (WAL2JSON/pgoutput jaisa decoder plugin) ko subscribe karta hai — ye server khud ko Postgres ka ek "replica" jaisa present karta hai taaki har WAL entry usse stream ho.
  • Realtime server har WAL change-event ko ek structured JSON payload mein convert karta hai, phir check karta hai kaunse connected clients us table/row ke liye subscribed hain (RLS policies yahan bhi respect hoti hain — ek user ko sirf wahi realtime events milte hain jo uski apni RLS policy allow karti hai).
  • Matching clients ko ye event ek persistent WebSocket connection ke through push kiya jaata hai — isliye latency bahut kam hoti hai (polling ki tarah har few seconds mein request nahi bhejni padti), aur update near-instant feel hota hai.
components/LiveTodos.tsx — realtime subscription
import { useEffect, useState } from "react"; // state aur lifecycle hooks
import { supabase } from "../lib/supabase"; // hamara shared Supabase client instance

type Todo = { id: string; title: string; is_completed: boolean }; // row shape ka type

function LiveTodos() {
  const [todos, setTodos] = useState<Todo[]>([]); // realtime-synced list local state mein

  useEffect(() => {
    const channel = supabase
      .channel("todos-changes") // ek naam se channel bana rahe hain, ye sirf ek grouping label hai client-side
      .on(
        "postgres_changes", // Supabase Realtime ka special event type jo Postgres WAL changes ko wrap karta hai
        { event: "*", schema: "public", table: "todos" }, // "*" = INSERT+UPDATE+DELETE teeno sunenge, sirf public.todos table pe scoped
        (payload) => {
          // payload.eventType batata hai konsa operation hua, payload.new/payload.old mein actual row data hota hai
          if (payload.eventType === "INSERT") {
            setTodos((prev) => [payload.new as Todo, ...prev]); // naya row list ke top pe prepend kiya
          } else if (payload.eventType === "UPDATE") {
            setTodos((prev) => prev.map((t) => (t.id === payload.new.id ? (payload.new as Todo) : t))); // matching id wale row ko naye data se replace kiya
          } else if (payload.eventType === "DELETE") {
            setTodos((prev) => prev.filter((t) => t.id !== payload.old.id)); // deleted row ko list se hata diya
          }
        }
      )
      .subscribe(); // yahi call actually WebSocket connection open karti hai aur listening start karti hai

    return () => {
      supabase.removeChannel(channel); // CRITICAL: unmount pe unsubscribe karo, warna connection leak ho jaata hai (neeche senior note dekho)
    };
  }, []); // empty deps — subscription sirf ek baar mount pe set hoti hai

  return null; // render logic simplified rakha, real UI FlatList se banega jaisa CRUD section mein dikha
}

export default LiveTodos; // export kiya reuse ke liye
🧠 Senior Dev Note — Over-Subscribing Mat Karo

Har active realtime subscription ek persistent open connection hoti hai — Supabase project pe simultaneous realtime connections ki hard limit hoti hai (tier ke hisaab se), aur har naya channel server-side memory/CPU consume karta hai. Common mistake: har screen pe naya .channel() bana dena aur cleanup function bhool jaana — result: jaise-jaise user app mein navigate karta hai, purani subscriptions zombie ban ke background mein khuli reh jaati hain (memory leak + wasted connection quota). Rule of thumb: jitni zaroorat ho utni hi granular subscriptions rakho (poore table ke bajaye specific filter jaise filter: "user_id=eq.${userId}" use karo), aur useEffect ke cleanup mein hamesha removeChannel call karo — bina exception ke.

11.2 Offline-first sync strategies aur conflict resolution

Mobile apps ka fundamental problem — network hamesha available nahi hota. Agar user offline edit karta hai (jaise flight mode mein ek todo edit kiya), aur usi row ko kisi doosre device/user ne meanwhile online edit kar diya, toh jab pehla device wapas online aata hai, dono edits ko reconcile karna padta hai. Ye "conflict resolution" ka core problem hai, aur teen mainstream approaches hain:

StrategyKaise kaam karti haiTrade-off
Last-Write-Wins (LWW) Jo edit sabse aakhri mein server pe pahunchti hai (timestamp ke hisaab se), wahi final truth ban jaati hai — purani conflicting edit silently discard ho jaati hai Implement karna sabse simple hai, lekin silently data loss ho sakta hai — user ko pata bhi nahi chalta ki uska edit overwrite ho gaya
Operational Transforms (OT) / CRDTs Har edit ko ek mathematically composable operation ki tarah treat karte hain jo kisi bhi order mein apply ho toh bhi same final state deta hai (CRDT = Conflict-free Replicated Data Type) — Google Docs, Figma jaise collaborative editors isi pe based hain Zero data loss aur automatic merge milta hai, lekin implementation bahut complex hai — poori data model ko CRDT-compatible design karna padta hai, aur libraries (Yjs, Automerge) integrate karna non-trivial hai for a typical CRUD app
Pragmatic middle ground (most mobile apps) Optimistic local writes turant UI mein reflect karo, ek updated_at/version column har row pe rakho, aur sync ke waqt agar server ka version local version se newer hai (matlab koi aur change hua tha), sirf tabhi user ko conflict dikhao (merge UI ya "keep mine / keep theirs" prompt) — warna silently sync ho jaao Poora CRDT jitna robust nahi, lekin implementation cost bahut kam hai aur real-world mein 95%+ cases mein koi actual conflict hota hi nahi (do log rarely same row edit karte hain exact same window mein) — isliye conflict-handling sirf edge case ke liye reserve hoti hai
SQL Editor — version column add karna conflict detection ke liye
alter table todos add column version integer not null default 1; -- har row ka monotonically increasing version number, naya row version 1 se start hoga

create or replace function increment_version() -- ek trigger function bana rahe hain jo har update pe version auto-bump karega
returns trigger as $$ -- PL/pgSQL function body ka opening delimiter
begin -- function body start
  new.version = old.version + 1; -- update hone se pehle version ko purane version se 1 zyada set kar do
  return new; -- modified "new" row return karo, yahi actually save hogi
end; -- function body end
$$ language plpgsql; -- closing delimiter, batata hai ye PL/pgSQL language mein likha function hai

create trigger todos_version_trigger -- trigger ka naam
before update on todos -- todos table pe har UPDATE se pehle chalega
for each row execute function increment_version(); -- har affected row ke liye upar wala function invoke hoga

Client side pe sync logic ye check karta hai: local edit bhejte waqt apna last-known version bhi bhejo (update ... where id = X and version = local_version); agar update ki row-count 0 aati hai, iska matlab koi aur already newer version likh chuka hai — yehi signal hai user ko conflict prompt dikhane ka, warna silently proceed karo.

11.3 Optimistic updates with rollback

Har action pe server round-trip ka wait karna (spinner dikhana, phir UI update karna) app ko slow feel karata hai — chahe network fast bhi ho, human perception mein 200-500ms ka delay bhi "laggy" lagta hai. Optimistic update ka pattern hai: UI ko turant update kar do jaise server ne already success bola ho, request background mein bhejo, aur agar request fail ho jaaye toh UI ko wapas purani state pe rollback kar do.

optimistic toggle with rollback
const toggleTodoOptimistic = async (todo: Todo) => {
  const previousTodos = todos; // rollback ke liye current (pre-change) state ko snapshot mein save kar liya

  setTodos((prev) =>
    prev.map((t) => // list mein sirf matching todo ko update karenge, baaki as-is rahenge
      t.id === todo.id ? { ...t, is_completed: !t.is_completed } : t // UI turant flip ho gaya, server ka response wait nahi kiya
    )
  ); // yahi optimistic update hai — user ko instant feedback mila

  const { error } = await supabase
    .from("todos") // "todos" table target kiya
    .update({ is_completed: !todo.is_completed }) // actual server-side update, background mein chal raha hai
    .eq("id", todo.id); // sirf isi row ko target kiya

  if (error) {
    console.error("Update failed, rolling back:", error); // debugging ke liye error log kiya
    setTodos(previousTodos); // ROLLBACK: UI ko exact pehle wali state pe wapas le aaye, user ko galat "success" nahi dikhega
    // production mein yahan ek Toast/Snackbar bhi dikhana chahiye: "Update failed, try again"
  }
};

Ye pattern instant feel isliye deta hai kyunki user ko round-trip latency (network + server processing) kabhi dikhti hi nahi jab tak sab theek chal raha ho — sirf failure case mein hi thoda "flicker" wapas hota hai, jo rare hota hai. Waiting-for-server approach mein har single action pe ye latency hamesha visible hoti hai, chahe request succeed hi kyun na ho.

⚠️ Optimistic Updates Ka Hidden Cost

Agar tumhare paas ek saath multiple optimistic updates in-flight hain (jaise user ne fast-fast 3 todos toggle kar diye before pehla response aaya), aur beech mein ek fail ho jaaye, toh naive rollback (previousTodos wapas set karna) baaki successful updates ko bhi overwrite kar sakta hai. Production-grade implementation is case mein sirf us specific failed item ko revert karta hai, poori list ko nahi — TanStack Query jaisi library isi complexity ko onMutate/onError/onSettled callbacks ke through cleanly handle karti hai, isliye real apps mein raw useState ke bajaye aisi library use karna senior choice hai jaise app scale karta hai.

11.4 Rate limiting aur idempotency — mobile APIs ke liye kyun zaroori hai

Mobile networks web ke mukable bahut zyada flaky hain — user tunnel mein chala jaata hai, WiFi se cellular pe switch hota hai, ya app background mein chali jaati hai request ke beech mein. Client-side retry logic (jaise ek automatic 3-retry-on-timeout wrapper) is unreliability ko handle karne ke liye common hai — lekin agar wahi retry ek non-idempotent operation (jaise "create order") pe hoti hai, toh possible hai ki pehla request actually server tak pahunch gaya ho aur order create ho gaya ho, lekin response client tak wapas na pahuncha ho (timeout ki wajah se) — client retry karega, aur ab duplicate order ban jaayega.

Iska standard solution idempotency key pattern hai: client ek unique key (UUID) generate karta hai ek hi baar jab user action trigger hota hai (retry ke waqt wahi key reuse hoti hai, naya key nahi banta), aur server usse dedupe karne ke liye use karta hai.

app/api/orders+api.ts — idempotency key pattern
export async function POST(request: Request) {
  const idempotencyKey = request.headers.get("Idempotency-Key"); // client ne ye key header mein bheji, retries pe same rehti hai

  if (!idempotencyKey) {
    return Response.json({ error: "Idempotency-Key required" }, { status: 400 }); // key ke bina non-idempotent request allow nahi karte
  }

  const { data: existing } = await supabaseAdmin // service_role client, RLS bypass karke idempotency table dekhne ke liye
    .from("processed_requests") // pehle-processed keys track karne wala table
    .select("response_body") // agar pehle process ho chuka hai, uska saved response wapas denge
    .eq("idempotency_key", idempotencyKey) // isi key se match dhoondo
    .maybeSingle(); // 0 ya 1 row expect karte hain, error nahi throw karega agar 0 mile

  if (existing) {
    return Response.json(existing.response_body); // ye request pehle already process ho chuki thi — same saved response wapas do, naya order mat banao
  }

  const body = await request.json(); // request body parse kiya (jaise order details)
  const order = await createOrder(body); // actual business logic — naya order create karna (helper function, definition yahan nahi dikhaya)

  await supabaseAdmin
    .from("processed_requests") // isi key ko future retries ke liye save kar rahe hain
    .insert({ idempotency_key: idempotencyKey, response_body: order }); // key + response dono store kiye taaki retry pe seedha wapas mil jaaye

  return Response.json(order); // pehli baar ka fresh response client ko bhej diya
}
🧠 Senior Dev Note — Rate Limiting Bhi Isi Family Ka Problem Hai

Idempotency duplicate-writes ko rokta hai; rate limiting alag problem solve karta hai — ek client (buggy retry loop, ya malicious abuse) ko tumhare backend/database pe excessive requests bhejne se rokna. Practical mobile pattern: Expo Router API route ke andar (ya Supabase Edge Function mein) ek per-user/per-IP counter rakho (Redis ya Postgres ke upstash/ratelimit jaise library se), aur limit cross hone pe 429 Too Many Requests status return karo taaki client ko pata chale ki ye rate-limit hai, generic server error nahi — client phir exponential backoff ke saath retry kar sakta hai.

12. 🎯 Interview Questions — Senior React Native Developer

Ye section un questions ko cover karta hai jo senior/staff-level RN interviews mein backend integration, Supabase, aur data-architecture ke around pooche jaate hain — sirf "syntax kya hai" nahi, "kyun aisa design kiya" pe focus hai, jo hi senior-level differentiation hai.

Q1. Postgres Row Level Security query-level pe access control kaise enforce karta hai — ye application code hai ya database-level?

Ye purely database-level enforcement hai, application code nahi. Jab RLS enabled hota hai ek table pe, Postgres har incoming query (SELECT/INSERT/UPDATE/DELETE) ko rewrite karta hai taaki har policy ka USING (read-time filter) ya WITH CHECK (write-time validation) expression uss query ke WHERE clause mein effectively AND ho jaaye — ye query planner ke andar, execution se pehle hota hai. Iska matlab chahe query PostgREST (Supabase ka auto-REST layer) se aayi ho, GraphQL se, ya seedha psql se — koi bhi client Postgres tak pahunchne wala path isi rewrite se guzarta hai, sirf service_role (jo RLS ko explicitly bypass karne ki permission rakhta hai, roughly Postgres ke BYPASSRLS role attribute jaisa) iska exception hai. Isliye application code mein "if user owns this row" jaisa check duplicate karna zaroori nahi hai — database khud hi non-matching rows ko query result se exclude kar deta hai, jaise wo exist hi nahi karti.

Q2. Ek offline-first note-taking app design karo — kaunsa data model aur conflict-resolution approach choose karoge, aur kyun?

Main local-first writes + version/updated_at column + selective conflict surfacing approach choose karunga (section 11.2 wala pragmatic middle ground), full CRDT nahi — yahan reasoning hai: Note-taking app mein typical usage pattern ye hai ki ek hi user apne notes edit karta hai (rare hi hota hai ki do log/devices simultaneously exact same note edit kar rahe hon), isliye true concurrent collaborative editing (jahan CRDT/OT genuinely zaroori hote hain, jaise Google Docs) yahan overkill hai. Data model: local SQLite (ya WatermelonDB/expo-sqlite) mein har note ka full copy rakhunga with updated_at aur synced_at timestamps, ek background sync queue jo pending writes ko track karta hai. Jab online ho, queue process hoti hai — server ka updated_at check karke agar wo local synced_at se newer hai, matlab dusri jagah se bhi change aaya tha, tab hi user ko ek simple "This note changed elsewhere — keep mine / keep server's / view both" prompt dikhaunga, warna silently merge kar dunga. Agar future mein genuine real-time multi-device simultaneous typing chahiye ho (jaise ek shared collaborative doc feature add ho), tabhi CRDT library (Yjs) introduce karunga — YAGNI principle follow karte hue shuruaat simple se karna better hai.

Q3. Supabase anon key leak hone aur service_role key leak hone ke blast radius mein actual difference kya hai?

Anon key leak — practically koi naya risk nahi create karta, kyunki ye key already client bundle mein publicly present hoti hai by design (section 1 dekha). Ye key sirf ek "identity token" hai jo batata hai request kaunse Supabase project se aa rahi hai — actual access control poori tarah RLS policies pe depend karta hai. Agar RLS sahi se configured hai, anon key ke saath attacker wahi kar sakta hai jo ek legitimate unauthenticated/authenticated user kar sakta hai — kuch zyada nahi.

service_role key leak — ye catastrophic hai. Ye key RLS ko completely bypass karti hai (Postgres ke andar BYPASSRLS attribute wale role jaisi), matlab is key ke saath koi bhi table ki saari rows read/insert/update/delete ki ja sakti hain — chahe kitni bhi strict RLS policies kyun na ho, ye unhe ignore kar deti hai. Ye practically database ka root password hai. Isliye blast radius mein difference hai: anon key leak = "RLS jitna secure hai utna hi risk" (potentially zero agar policies tight hain), service_role leak = "poori database exposed, unconditionally".

Q4. Production mein ek query jo current user ka data return karni chahiye, empty aa rahi hai — lekin tumhare local testing mein kaam karti hai. Sabse pehle kya check karoge?

Ye classic RLS-silent-filtering symptom hai (section 10 gotcha), isliye systematic debugging order:

  1. Confirm karo data exist karta hai — Supabase Dashboard ke SQL Editor mein (jo service_role-level access rakhta hai, RLS bypass hota hai) wahi query manually chalao. Agar data yahan dikhta hai, confirm ho gaya ye RLS issue hai, "data missing" nahi.
  2. Check karo production auth session valid hai — kabhi kabhi production build mein token refresh fail ho raha hota hai (env mismatch, wrong Supabase URL project pointing to staging vs prod), isliye auth.uid() null resolve ho raha hota hai server-side, jisse RLS policy auth.uid() = user_id kabhi match hi nahi karti.
  3. Diff karo local vs prod RLS policies — bahut common: local/staging Supabase project pe manually ek policy add ki thi testing ke liye, lekin migration file mein commit nahi ki, isliye production project mein wo policy exist hi nahi karti. SQL migrations ko version control mein rakhna isi wajah se non-negotiable hai.
  4. Check karo env vars sahi project ko point kar rahe hain — agar EXPO_PUBLIC_SUPABASE_URL galti se staging project ka hai production build mein (ya vice versa), query "successfully" chalegi lekin galat database se, jahan expected data hai hi nahi.

Q5. Supabase Realtime WebSocket ke through data kaise deliver karta hai — poll karta hai ya push?

Push-based hai, poll-based nahi. Section 11.1 mein dekha — Realtime server Postgres ke logical replication stream (WAL-based) ko continuously sunta hai, aur jaise hi koi matching change commit hoti hai, wo event turant subscribed clients ko unke already-open WebSocket connection pe push kar deta hai. Isse compare karo naive "polling" approach se (jahan client har N seconds pe fetch karke khud check karta ki kuch naya hai) — polling mein latency N seconds tak ho sakti hai aur unnecessary requests bhi bante hain jab kuch naya nahi hota; WebSocket push mein latency near-instant hoti hai aur idle time mein koi extra request nahi jaati (connection khula rehta hai, lekin data tabhi flow hota hai jab actual change ho).

Q6. Optimistic updates ka trade-off kya hai, aur kab isse avoid karna chahiye?

Benefit clear hai — instant perceived responsiveness (section 11.3). Trade-off ye hai ki UI temporarily ek aisi state dikhati hai jo abhi server-confirmed nahi hai — agar request fail hoti hai, user ne shayad already us "fake success" ke aage aur actions le liye ho (jaise ek delete ko optimistic dikha ke user ne next screen navigate kar diya), rollback UX confusing ban sakta hai. Isliye main optimistic updates avoid karta hoon jab: (a) operation genuinely destructive/irreversible hai server-side (jaise payment processing — yahan galat "success" dikhana bahut costly hai), (b) success probability low hai (jaise ek known-flaky third-party integration), ya (c) UI itni complex hai ki partial rollback (multiple in-flight optimistic updates, jaisa section 11.3 ka warn callout tha) manage karna error-prone ho jaaye without a proper library (TanStack Query) ka support.

Q7. Expo Router API Route aur ek traditional separate backend (Express/Django) mein architecturally kya farak hai?

Functionally dono same kaam karte hain — server-side code jo secrets/business-logic ko client se door rakhta hai. Farak deployment aur ownership model mein hai: Expo Router API routes same repo/same deploy mein colocated hote hain app code ke saath (+api.ts files), deploy EAS Hosting se hota hai, aur ye best fit hai jab backend logic simple/thin hai (BFF pattern — secret hide karna, ek third-party API ko proxy karna). Traditional separate backend better fit hai jab: backend ko independently scale karna ho app se alag, backend ko multiple clients serve karne hon (web + mobile + partner APIs), ya backend team/deployment-cadence app team se decoupled ho. Senior decision yahan "complexity ke hisaab se right-size karo" hai — chhoti proxy-jaisi zaroorat ke liye poora alag Express server spin karna over-engineering hai; genuinely complex backend logic ke liye Expo Router routes mein sab kuch cram karna bhi galat hai.

Q8. Idempotency key ka lifecycle kya hona chahiye — kab generate hoti hai, kab reuse hoti hai?

Idempotency key user action trigger hone ke exact moment pe ek baar generate honi chahiye (jaise "Place Order" button dabate hi ek UUID banao), aur usi ek key ko us specific action ke saare retries ke liye reuse karna hai — chahe retry automatic ho (network timeout ke baad client khud retry kare) ya manual (user ne dobara button dabaya kyunki UI stuck lag rahi thi). Galat pattern ye hoga ki har retry pe naya UUID generate ho — isse idempotency ka poora purpose hi khatam ho jaata hai, kyunki server ke liye har retry ek "naya" unique request dikhegi. Key ko component state/ref mein store karo (jab tak action pending hai), aur success/definitive-failure ke baad hi discard karo.

Q9. Postgres ka WITH CHECK aur USING clause RLS policy mein kya alag kaam karte hain?

USING ek read-time filter hai — ye decide karta hai kaunsi existing rows query ko visible hain (SELECT ke liye, aur UPDATE/DELETE mein bhi "kaunsi row touch kar sakte ho" decide karne ke liye). WITH CHECK ek write-time validation hai — ye decide karta hai ki jo naya/modified row data ban raha hai (INSERT ka naya row, ya UPDATE ke baad ka resulting row) wo valid hai ya nahi. Yehi wajah hai ki humare todos UPDATE policy mein dono the: USING (auth.uid() = user_id) — "tum sirf apni row update kar sakte ho", aur WITH CHECK (auth.uid() = user_id) — "update ke baad bhi row ka owner tum hi raho, kisi aur ko transfer nahi kar sakte". Agar sirf USING hota aur WITH CHECK na hota, user apni row ko update karke uska user_id kisi aur ke id mein badal sakta tha (effectively apna todo kisi aur ko "gift" kar dena), jo ek unintended privilege escalation hoti.

Q10. Realtime, polling, aur webhook — in teeno mein se ek "order status updates" feature ke liye kaunsa choose karoge?

Depends on requirement ke exact shape pe: agar update client ko turant dikhni chahiye jab server-side kuch change ho (jaise "order out for delivery" status), Realtime (Postgres changes subscription) best fit hai — low latency, aur Supabase already isse manage karta hai. Agar update client ki activeness pe depend nahi karni chahiye aur ek external system (jaise payment gateway) ko backend ko inform karna hai ki kuch hua, webhook (server-to-server HTTP callback) sahi pattern hai — client isse directly involved nahi hota, backend hi webhook receive karke apna database update karta hai (aur phir wahi update Realtime ke through client tak forward ho sakta hai — dono patterns often saath use hote hain, alag layers pe). Polling ko main sirf tab choose karta hoon jab infrastructure constraint ho (jaise ek third-party API jo webhooks support hi nahi karta, aur WebSocket bhi available nahi), kyunki polling battery aur network dono waste karta hai mobile pe — ye almost hamesha last-resort option honi chahiye, first choice nahi.
