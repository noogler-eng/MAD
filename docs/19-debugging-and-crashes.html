Development-Time Debugging Tools

Pehle baat karte hain us duniya ki jahan aapke paas full control hota hai — local development. Yahan aapke paas kai tools available hain jo production mein simply exist hi nahi karte (kyunki release build mein performance/security ke liye inhe strip kar diya jaata hai). Senior dev banne ka ek hissa ye samajhna hai ki kaunsa tool kab reach karna hai — sirf console.log pe reliance karna ek junior habit hai.

React Native DevTools (Flipper ka successor)

Purane React Native versions mein Flipper official debugging platform tha — ek desktop app jo aapke device/emulator se connect hoke network requests, layout inspector, aur AsyncStorage jaisa data expose karta tha. New Architecture ke saath, React Native team ne apna khud ka React Native DevTools bana diya hai (Chrome DevTools jaisa interface, Hermes ke debugger protocol pe based) jo ab default debugging experience hai — j key dabao Metro terminal mein ya dev menu se "Open DevTools" select karo.

  • Network tab — har fetch/XHR request dikhata hai, request/response headers, body, timing — bilkul browser DevTools jaisa. Ye debug karne ke liye zaroori hai ki API call fail kyun hui, ya galat payload kyun gaya.
  • Console — console.log/warn/error yahan dikhte hain, filterable aur searchable.
  • Sources/Debugger — actual JS breakpoints laga sakte ho, step-through debugging kar sakte ho, call stack inspect kar sakte ho — real debugger experience, sirf print statements nahi.

AsyncStorage/MMKV contents inspect karna — agar Flipper legacy setup use kar rahe ho (kuch teams abhi bhi karte hain, especially jinke paas custom Flipper plugins hain), uska AsyncStorage plugin directly stored key-value pairs dikhata hai device pe — bahut useful jab debug karna ho "kya cached data corrupt hai ya stale hai".

React DevTools — component tree aur Profiler

Ye ek alag tool hai jo specifically React component tree ke liye hai — kaunse components render hue, unke props/state kya hain, aur (sabse important senior-level use case) Profiler tab jisse aap dekh sakte ho kaunsa component kitni baar re-render hua aur kyun. Chapter 2 mein humne component fundamentals dekhe the; yahan hum usi tree ko debug-lens se dekh rahe hain.

🧠 Senior Dev Note

Jab koi bole "app slow lag raha hai" — sabse pehla step React DevTools Profiler kholna hona chahiye, guess karna nahi. Profiler literally dikhata hai kaunsa component render mein kitna time le raha hai aur kis wajah se re-render trigger hua (props change, state change, ya parent re-render se cascade). Bina isko dekhe performance optimization karna almost hamesha galat jagah time waste karna hota hai.

console.log/console.warn ki limitation — production mein ye no-op hai

Ye ek critical cheez hai jo naye developers ko surprise karti hai: Hermes (default JS engine) release/production builds mein console.log calls ko strip kar deta hai ya unhe effectively no-op bana deta hai by default, kyunki logging ek performance aur binary-size cost hai jo production mein waste hai. Matlab agar aapki debugging strategy hai "main production issue console.log se dhoondh loonga" — wo strategy silently fail hogi, kyunki wo log kahin jaayega hi nahi jo aap dekh sako.

⚠️ "Maine log daala, kuch dikha nahi" — production build mein classic confusion

Development build mein console.log perfectly kaam karta hai (Metro terminal ya DevTools console mein dikhta hai). Lekin agar aap same code ko production/release build mein test kar rahe ho aur expect kar rahe ho ki log kahin dikhega — wo nahi dikhega, kyunki user ke device se connected koi terminal hai hi nahi jo use capture kare. Ye exact reason hai ki humein ek dedicated crash/error reporting tool (Sentry) chahiye — jo is section ke aage cover hoga.

Reactotron — ek alternative jo kuch teams prefer karti hain

Reactotron ek open-source desktop app hai jo React Native DevTools se pehle popular tha aur aaj bhi kuch teams use karti hain kyunki iska Redux/state-management integration bahut mature hai — har dispatched action, state diff, custom "display" commands (aap khud custom debug panels bana sakte ho) sab ek timeline mein dikhte hain. Agar aapki team heavy Redux use kar rahi hai (Chapter 18 ka topic), Reactotron ka action-timeline view React DevTools se zyada readable lag sakta hai state transitions ke liye.

ToolBest forKab reach karo
React Native DevTools Network requests, console, breakpoint debugging Default day-to-day debugging — API calls fail ho rahe hain, ya step-through debugging chahiye
React DevTools (Profiler) Component tree, props/state, re-render analysis "App slow hai" / "component bahut baar re-render ho raha hai" jaisi complaints
Reactotron Redux/state timeline, custom debug displays Heavy Redux-based apps jaha state transitions ka clear timeline chahiye

Setting Up Sentry for Crash Reporting

Ab dev-time se production tak jaate hain — aur ye is chapter ka sabse important practical section hai. Ek simple lekin bahut senior-level truth: jab aapka app production mein kisi user ke device pe crash karta hai, aap uska console nahi dekh sakte, uska terminal connect nahi kar sakte, aur unse pooch nahi sakte "exact steps batao kya kiya tha". Crash reporting tool (jaise Sentry) hi aapki only window hai us device pe actually kya hua ye jaanne ka.

🔒 Ye non-negotiable kyun hai

Bina crash reporting ke, aapka "monitoring" strategy literally ye hai: wait for user complaints on app store reviews or support tickets. Ye ek reactive, slow, aur incomplete signal hai — zyadatar users jinka app crash hota hai, wo review nahi likhte, sirf app delete kar dete hain (ya use karna band kar dete hain). Crash reporting ke bina aapko pata hi nahi chalega ki kitne users affected hain, kaunsa device/OS version pattern hai, ya crash exactly kis line pe ho raha hai. Har production RN app mein ye day-1 setup hona chahiye, feature launch se pehle.

Step 1 — Installation

Sentry ka official React Native SDK @sentry/react-native hai. Expo projects ke liye Sentry ka apna wizard bhi hai jo automatically config wire kar deta hai, lekin manual setup samajhna zaroori hai taaki aapko pata ho actually kya ho raha hai under the hood.

terminal
# Sentry ka official React Native SDK install karna — crash reporting, error tracking, performance monitoring sab isi package mein hai
npx expo install @sentry/react-native

# Sentry ka wizard chalana — ye automatically app.json/app.config.ts, EAS Build hooks, aur source-map upload config wire kar deta hai
npx @sentry/wizard@latest -i reactNative -p ios android

# Wizard aapse Sentry account login aur project selection maangega — DSN (Data Source Name, aage explain kiya gaya) automatically fetch ho jaata hai

Step 2 — App entry point mein initialize karna

Sentry ko app ke sabse pehle load hone wali file mein initialize karna hota hai — taaki agar app boot hone ke turant baad bhi crash ho, Sentry us crash ko already capture kar chuka ho. Neeche har line commented hai.

app/_layout.tsx (ya index.js — app ka entry point)
// Sentry ka poora React Native SDK import karna — init, ErrorBoundary, wrap jaise sab helpers isi se aate hain
import * as Sentry from '@sentry/react-native';
// React import — hooks aur JSX ke liye zaroori
import React from 'react';
// Expo Router ka root Slot component — poore app ki route tree yahin render hoti hai
import { Slot } from 'expo-router';

// Sentry.init — SDK ko configure karna, ye app boot ke bilkul shuru mein, module-level pe call hona chahiye (kisi component ke andar nahi)
Sentry.init({
  // dsn (Data Source Name) — Sentry project ka unique endpoint URL jahan crash reports bhejne hain, wizard ne ye automatically generate/inject kiya hoga
  dsn: 'https://examplePublicKey@o0.ingest.sentry.io/0',

  // environment — batata hai ye report kis environment se aayi (production/staging/development) — dashboard pe filter karne ke liye zaroori
  environment: __DEV__ ? 'development' : 'production',

  // release — current app version + build number, taaki crash report ko exact build se link kiya ja sake (symbolication ke liye critical, aage dekhenge)
  release: 'mad-app@1.4.0+42',

  // tracesSampleRate — performance monitoring transactions ka kitna percentage sample karna hai (1.0 = 100%, production mein aksar 0.2 jaisa lower value use karte hain cost control ke liye)
  tracesSampleRate: __DEV__ ? 1.0 : 0.2,

  // enableNative — native-level crash capture (Swift/Kotlin crashes) bhi enable karna, sirf JS errors nahi — Chapter ke JS-vs-native section mein iski importance dekhenge
  enableNative: true,

  // debug — sirf development mein true rakho, ye Sentry SDK ke apne internal logs console mein print karta hai taaki setup verify kar sako
  debug: __DEV__,
});

// RootLayout — app ka root component, is poore tree ko hum aage Sentry.wrap() se wrap karenge automatic error-boundary capture ke liye
function RootLayout() {
  // Slot — Expo Router ki current matched route ko yahan render karta hai
  return <Slot />;
}

// Sentry.wrap — root component ko wrap karta hai, ye automatically ek top-level error boundary + navigation breadcrumb tracking inject kar deta hai
export default Sentry.wrap(RootLayout);
💡 DSN kya hota hai, simple terms mein

DSN (Data Source Name) bas ek URL hai jo Sentry ko batata hai "ye crash report kis project ki hai". Isko public key treat karo — ye secret nahi hai (client-side code mein hi rehta hai), lekin ise galat project mein daalne se aapki team ko galat project ke dashboard pe crashes dikhenge, isliye har environment (dev/staging/prod) ke liye sahi DSN match karna zaroori hai agar alag Sentry projects use kar rahe ho.

Step 3 — EAS Build ke saath source-map aur symbol upload wire karna

Sentry wizard normally ye automatically eas.json aur native build files mein wire kar deta hai, lekin samajhna zaroori hai ki ho kya raha hai — har production build ke baad, ek build script automatically JS source maps aur native debug symbols (agla section) Sentry ko upload karta hai, taaki crash reports readable hon.

eas.json (teaching-annotated, real JSON mein comments nahi hote)
{
  // "build" — Chapter 10 mein dekhe gaye build profiles, yahan hum "production" profile ke andar hooks add kar rahe hain
  "build": {
    "production": {
      // "env" — build-time environment variables, SENTRY_AUTH_TOKEN yahan secret ke roop mein EAS secrets se aata hai (kabhi hardcode mat karo)
      "env": {
        "SENTRY_AUTH_TOKEN": "$SENTRY_AUTH_TOKEN"
      }
    }
  }
}
🧠 Senior Dev Note — automatic upload hi asli value hai

Bahut teams Sentry install karte hain lekin symbol/source-map upload step ko properly automate nahi karte — result: SDK crashes capture kar raha hai, lekin dashboard pe sirf minified/unreadable stack traces dikhte hain. Sentry install karna sirf aadha kaam hai — dusra aadha ye ensure karna hai ki har production build automatically apne symbols/source-maps Sentry ko bheje, bina kisi manual step ke. Ye CI/EAS Build pipeline ka permanent, automated hissa hona chahiye.

Crash Symbolication Deep-Dive

Chapter 16 mein humne isko brief mein touch kiya tha jab native module crashes discuss kiye the. Ab hum isko poori depth mein samjhenge, kyunki symbolication samajhna crash reports ko actually useful banane ke liye zaroori hai.

Problem statement — hex address kyun aata hai

Jab aap Swift/Kotlin/C++ code ko production ke liye compile karte ho, compiler optimize aur strip karta hai — readable function/variable names (jinhe "symbols" bola jaata hai) binary se hata diye jaate hain, taaki app ka size chhota rahe aur reverse-engineering thoda harder ho. Result: jab crash hota hai, operating system sirf ye bata sakta hai "crash hua memory address 0x0000000104a3f2c8 pe" — kyunki us address ka corresponding function name binary ke andar kahin store hi nahi hai.

dSYM files — iOS ka symbol table

dSYM (Debug SYMbol) file ek separate file hai jo Xcode build ke time generate hoti hai, alag se binary se — isme exactly wo mapping hoti hai jo strip ho gayi thi: "memory address X, function DeviceFingerprintModule.getBuildFingerprint(), file DeviceFingerprintModule.swift, line 305". Jab aap crash report ke saath sahi dSYM file upload karte ho (usi exact build version ka), Sentry (ya koi bhi crash tool) automatically hex address ko is readable stack trace mein convert kar deta hai — ise symbolication kehte hain.

mapping.txt / ProGuard / R8 — Android ka equivalent

Android side pe do alag cheezein symbolication ke liye chahiye hoti hain:

  • ProGuard/R8 mapping file (mapping.txt) — Android release builds code minification/obfuscation use karte hain (ProGuard ya naya R8 tool), jo Java/Kotlin class aur method names ko chhote, meaningless names mein rename kar deta hai (jaise DeviceFingerprintModule ban jaata hai a.b.c) taaki APK size chhota ho aur reverse-engineering harder ho. mapping.txt file wo mapping store karti hai original naam se obfuscated naam tak — bina iske, crash report mein sirf obfuscated (meaningless) class/method names dikhenge.
  • Native symbol files (.so ke liye) — agar crash native C++ code (jaise Hermes engine internal, ya JNI-level native module) mein hota hai, us native library (.so file) ke apne debug symbols alag se upload karne padte hain, dSYM ke concept jaisa hi lekin Android native libraries ke liye.
PlatformSymbol fileKab generate hoti haiBina iske kya dikhta hai
iOS dSYM (Debug Symbols) Har Xcode/EAS build ke saath automatically generate hoti hai Raw memory hex addresses, koi function/line info nahi
Android (JS/Java/Kotlin layer) ProGuard/R8 mapping.txt Har release build ke saath jab minification enabled ho (production mein almost hamesha) Obfuscated class/method names (a.b.c jaisa), unreadable
Android (native .so layer) Native debug symbols Native build ke saath, agar strip enabled hai to alag se export karni padti hai Raw hex addresses, native crashes ke liye

EAS Build + Sentry integration — automation pipeline

Manually har build ke baad ye files dhoondh kar upload karna impractical hai — isliye Sentry ka EAS Build integration (wizard ne jo setup kiya tha) ye automate karta hai: har production build complete hone ke baad, ek build hook automatically dSYM (iOS) aur mapping.txt (Android) ko locate karke, release field (jo humne Sentry.init() mein set kiya tha) ke saath tag karke Sentry ko upload kar deta hai. Matlab aapko kabhi manually koi symbol file dhoondh kar upload nahi karni padti — pipeline handle karta hai, bas usko properly wire hona chahiye.

🔒 Common failure mode — ek specific build version ke symbols missing

Ye ek bahut realistic aur frustrating scenario hai jo har production team kabhi na kabhi face karti hai: version 1.4.2 production mein ship hui, symbols upload pipeline mein koi transient failure hua (network issue, EAS secret expire ho gaya, ya koi CI misconfiguration) aur kisi ne notice nahi kiya. Ab agar version 1.4.2 crash karti hai kisi user ke device pe, Sentry dashboard pe sirf hex addresses/obfuscated names dikhenge — us exact build ke liye symbolication permanently impossible ho chuka hai (jab tak aapke paas locally wahi exact build artifact save na ho, jo rarely hota hai). Team ko us crash ka root cause kabhi pata nahi chalega jab tak koi naya build (jisme symbols sahi se upload hue) same crash reproduce na kare. Isi wajah se symbol-upload step ki health monitoring (build logs mein check karna ki upload step successfully complete hua) apne aap mein ek important CI discipline hai, sirf "set it and forget it" nahi.

JS Errors vs Native Crashes — Different Failure Modes

Ye ek senior-level distinction hai jo bahut developers surface-level samajhte hain lekin deeply nahi — aur jo interview mein bhi frequently poocha jaata hai. Teen alag categories hain, aur har ek ka debugging/recovery approach completely different hai.

Failure typeKya hota haiRecovery possible hai?Kaise track karte hain
JS-level unhandled error Ek JS exception jo kisi try/catch se catch nahi hui — jaise ek component render ke andar null pointer access Haan — ek Error Boundary (React ka built-in mechanism) is error ko catch kar sakta hai aur fallback UI dikha sakta hai, poora app crash nahi hota Sentry JS error capture (automatic, Sentry.wrap ke through)
Genuine native crash Native (Swift/Kotlin/C++) level pe ek fatal signal (jaise segmentation fault, null pointer dereference at native level) Nahi — poora app process immediately terminate ho jaata hai OS level pe. Koi JS-level recovery possible nahi hai kyunki JS runtime khud hi mar chuka hota hai us process ke saath Sentry native crash capture (enableNative: true), ya Crashlytics/Bugsnag ka native layer
ANR (Android-specific) Main/UI thread 5+ seconds tak blocked rehta hai, OS "app isn't responding" dialog dikhata hai Technically app crash nahi hota (process zinda rehta hai), lekin user experience severely degrade hoti hai — user aksar force-close kar deta hai Play Console's Android vitals dashboard (agla section)
🧠 Senior Dev Note — Error Boundary sirf JS errors ke liye hai

Ek bahut common misconception ye hai ki React ka Error Boundary "sab kuch" catch kar sakta hai. Ye galat hai — Error Boundary sirf React component tree ke render phase mein hone wale JS errors ko catch karta hai (aur kuch lifecycle methods mein). Ye event handlers ke andar errors catch nahi karta (unhe normal try/catch chahiye), aur ye bilkul bhi native crashes catch nahi karta — kyunki native crash ka matlab hai poora process hi mar gaya, JS runtime samet. Isi wajah se production app ko dono chahiye: JS-level error boundary (graceful degradation ke liye) aur native-level crash reporting (OS-level fatal signals capture karne ke liye) — dono alag mechanisms hain, ek dusre ka substitute nahi.

ANR ko is table mein separately isliye rakha hai kyunki ye technically "crash" nahi hai — process terminate nahi hota, JS bhi zinda hota hai — lekin user ke liye experience crash se zyada bura ho sakta hai (app poori tarah frozen dikhta hai, koi feedback nahi milta). Google Play Console ANR ko severity metric ke roop mein alag se track karta hai apne "Android vitals" dashboard mein, aur ek high ANR rate aapki Play Store ranking/visibility ko negatively affect kar sakta hai — isi wajah se ise seriously lena zaroori hai, chahe technically "crash" na ho.

Debugging ANRs (Android)

ANR actually hota kya hai

ANR (Application Not Responding) Android ka mechanism hai jo detect karta hai jab main/UI thread kaafi der tak (typically 5 seconds input events ke liye, ya kam broadcast receivers jaise cases mein) blocked rehta hai aur OS ko respond nahi kar pata. Jab ye hota hai, Android user ko ek dialog dikhata hai jisme "Wait" aur "Close app" options hote hain.

⚠️ Critical nuance — JS thread block hona ANR ke barabar NAHI hai

Ye ek bahut important distinction hai jo bahut RN developers confuse karte hain. React Native mein JS thread alag hota hai Android ke native main/UI thread se. Agar aapka JS thread block ho jaata hai (jaise ek heavy synchronous JS computation, ya Chapter 16 mein dekha gaya Function() jo bahut der leta hai) — result hota hai JS-driven UI frozen/jank (animations ruk jaati hain, taps respond nahi karte kyunki JS event handlers nahi chal pa rahe) — lekin ye ek true Android ANR nahi hai, kyunki native main thread khud technically responsive hai. Ek genuine ANR specifically tab hota hai jab native main thread block ho — jaise ek native module ka Function() jo synchronously kuch blocking I/O kare directly native side pe, ya koi native code jo main thread pe heavy kaam kare bina background thread pe offload kiye.

Ye distinction practically matter karta hai kyunki fix alag hota hai: agar problem JS thread blocking hai, fix hai JS-side code ko optimize karna ya heavy computation ko break karna (jaise InteractionManager use karna, ya computation ko chunks mein split karna). Agar problem genuine native main-thread blocking hai (jaise Chapter 16 mein discuss kiya gaya "native module ka blocking I/O jo background thread pe offload nahi hua"), fix hai us native code ko properly async banana — AsyncFunction() use karke, jaisa humne native modules chapter mein dekha tha.

ANR reports kahan dhoondhein

Google Play Console → Quality → Android vitals → ANR rate yahan aapko production devices se aggregate ANR data milta hai — kitne users affected hue, kaunse device/OS version pe zyada hue, aur (sabse important) ANR trace — ek stack-trace-jaisi report jo dikhati hai crash ke time har thread kya kar raha tha, especially main thread.

Systematic debugging approach

  1. ANR trace kholo aur main thread ka stack dekho — Play Console ka ANR trace exactly dikhata hai us moment pe main thread kis function/call ke andar "stuck" tha jab ANR trigger hua.
  2. Pattern dhoondo — kya ye ek specific screen/action se juda hai (jaise app launch ke turant baad, ya ek specific button tap ke baad)? Device/OS-version breakdown check karo — kya sirf low-end devices pe zyada hota hai (jo signal hai ki ye ek performance/timing issue hai, na ki pure logic bug)?
  3. Native module involvement check karo — agar koi custom native module hai jo main thread pe synchronous kaam karta hai (Chapter 16 ka blocking-Function() anti-pattern), ye pehla suspect hona chahiye.
  4. Fix karo aur re-measure karo — fix deploy karne ke baad, Android vitals dashboard mein ANR rate ko track karte raho agle kuch releases tak, confirm karne ke liye ki fix actually effective tha.

Debugging "Works Locally, Crashes in Production" Bugs

Ye category bugs sabse zyada frustrating hote hain — code aapke machine pe, aapke dev build mein perfectly kaam karta hai, lekin production build mein (ya kisi specific user ke device pe) crash karta hai. Ek senior dev ke paas iske liye ek systematic checklist honi chahiye, random guessing nahi. Ye checklist order mein run karo:

  1. Hermes vs JSC difference hai kya? — Hermes (default engine) aur JavaScriptCore kabhi kabhi subtly different JS engine behavior dete hain (jaise kuch bahut edge-case Intl API behavior, ya timing/GC-related differences). Agar aapka dev build kisi wajah se JSC use kar raha tha (purana setup, ya specific debug config) aur production Hermes use kar raha hai — ye divergence ka source ho sakta hai. Confirm karo dono builds same engine use kar rahe hain.
  2. Kya ek dev-only code path accidentally ship ho gaya? — if (__DEV__) { ... } guards ke andar rakha debug tooling kabhi kabhi assumption karta hai ki koi specific mock/stub data available hoga jo production mein nahi hota. Agar koi non-__DEV__-guarded code accidentally us dev-only assumption pe depend karta hai (jaise ek mock API response ka specific shape), production mein real API ka different response shape crash cause kar sakta hai.
  3. Minification/ProGuard ne kuch strip to nahi kiya jo runtime pe chahiye tha? — Ye bahut Android-specific gotcha hai. Agar aap reflection use kar rahe ho (jaise kuch libraries JSON parsing ke liye class names reflection se resolve karti hain), ProGuard/R8 minification us class ka naam change/remove kar sakta hai agar usko explicitly "keep rules" mein specify nahi kiya gaya — result: dev build (jahan minification disabled hoti hai) perfectly kaam karta hai, production build (minified) crash karta hai kyunki reflection ko wo class naam se milta hi nahi.
  4. Kya ek production environment variable missing hai? — Ek bahut common cause: dev .env file mein ek variable set tha (jaise ek API key ya feature flag), lekin EAS Build/CI secrets mein wahi variable production profile ke liye configure nahi kiya gaya. Code us variable ko undefined maan kar crash kar sakta hai jaha usne assume kiya tha wo hamesha set hoga.
  5. Kya ye ek timing-dependent race condition hai? — Development build slower hota hai (Metro bundler, debug instrumentation, wagera ki wajah se) — is slowness ki wajah se kabhi kabhi ek race condition "accidentally" mask ho jaati hai (jaise ek async operation jo dev mein itni der leti hai ki dusra operation pehle complete ho jaata hai, lekin production ki fast execution mein order badal jaata hai aur race condition expose hoti hai). Ye sabse debug-karne-mein-mushkil category hai kyunki reliably reproduce karna hard hota hai.
💡 Practical tip — production build ko locally bhi test karo

Sabse effective habit ye hai ki feature ship karne se pehle ek baar actual production/release build (eas build --profile production --local, ya npx expo run:android --variant release) local device pe chalao, sirf dev build pe reliance mat karo. Bahut saari is checklist ki cheezein (minification issues, missing env vars) tabhi surface hoti hain jab aap genuinely production-configured build test karte ho.

Performance Profiling

Crash aur ANR ke alawa, ek teesri category ki production issue hai — performance degradation jo crash nahi karta lekin user experience ko slowly kharab karta hai (jank, slow screens, memory bloat). Iske liye tools ka combination chahiye — JS-level aur native-level dono.

React DevTools Profiler (recap)

Chapter 2 mein humne is tool ko brief mein dekha tha. Ye JS/React level pe kaam karta hai — kaunsa component render ho raha hai, kitni der le raha hai, aur kyun re-render trigger hua. Ye excessive re-renders aur slow component render logic jaisi issues ke liye pehla tool hona chahiye.

Xcode Instruments aur Android Studio Profiler — native-level issues

Kuch performance issues genuinely native-level hote hain aur JS-level profiler unhe simply dikha hi nahi sakta — jaise ek memory leak jo native view creation se ho raha hai (agar koi list/screen har baar naya native `UIView`/Android `View` bana raha hai bina purane ko properly clean up kiye), ya native-level CPU/GPU bottleneck.

  • Xcode Instruments (iOS) — Apple ka native profiling suite, isme "Leaks" instrument memory leaks detect karta hai (retain cycles, jo humne Chapter 16 mein discuss kiya tha), "Time Profiler" CPU usage ko function-level granularity pe dikhata hai — sab native level pe, JS ke bahar.
  • Android Studio Profiler — Android ka equivalent, CPU/Memory/Network/Energy profiling native level pe. Memory profiler specifically useful hai excessive native view allocation ya JVM heap growth pattern dhoondhne ke liye.
🧠 Senior Dev Note — kab native profiler tak jaana chahiye

Rule of thumb: agar React DevTools Profiler mein sab kuch normal lag raha hai (components fast render ho rahe hain, unnecessary re-renders nahi hain) lekin app phir bhi slow/janky feel ho raha hai, ya memory usage time ke saath badhta ja raha hai (leak ka signal) — tabhi native-level profiler tak jaana chahiye. JS-level profiling "kya React slow hai" ka jawab deta hai; native profiling "kya underlying platform slow hai" ka jawab deta hai — dono alag layers hain.

why-did-you-render — unnecessary re-renders catch karna

Development ke dauran, why-did-you-render library ek useful addition hai — ye automatically console mein warn karta hai jab koi component re-render hota hai jiski props/state actually (deep-equality se) change nahi hui thi. Ye React DevTools Profiler se complementary hai — Profiler aapko dikhata hai kya re-render hua, ye library proactively bata deta hai kab ek re-render truly avoidable tha.

Real-World Gotchas

⚠️ console.log strip hone ka silent failure

Jaisa is chapter ke shuru mein dekha, release builds mein Hermes console.log ko strip kar deta hai. Iska matlab ye hai ki agar aapki debugging strategy purely logs pe based hai, wo production mein silently fail hogi — koi error nahi aayega, bas aapka signal simply exist nahi karega. Fix: production debugging ke liye Sentry breadcrumbs use karo (agle section mein full example hai) — ye Sentry SDK ke through explicitly record hote hain aur strip nahi hote, kyunki inka purpose hi crash reports ke saath travel karna hai.

⚠️ Source maps upload na hona — JS ka "dSYM problem"

Bilkul waise jaise dSYM/mapping files ke bina native crash reports unreadable hote hain, agar JS source maps Sentry ko properly upload nahi hue (ya release field match nahi karta jo build ke time use hua tha), Sentry dashboard pe minified JS stack traces dikhenge — jaise at t (index.android.bundle:1:45231), jo practically unreadable hai. Ye JS-level exact equivalent hai us native symbolication problem ka jo humne pehle dekha — same root cause (production build compressed/transformed code), same fix pattern (build pipeline mein automated, verified upload).

🔒 Sensitive data ko crash reports mein kabhi mat log karo

Ye ek security/privacy discipline hai jo bahut easily overlook ho jaata hai: crash reporting tools (Sentry included) third-party services hain — aapka crash data unke servers pe jaata hai. Agar aapke breadcrumbs, extra context, ya error messages mein accidentally auth tokens, passwords, credit card numbers, ya PII (personally identifiable information) log ho jaata hai, ye ek real data-exposure risk ban jaata hai — chahe Sentry khud secure ho, ye data ab ek additional third-party system mein exist karta hai jo aapke primary security perimeter se bahar hai. Sentry beforeSend hook offer karta hai jisse aap explicitly sensitive fields ko scrub/redact kar sakte ho bhejne se pehle — ye har production setup mein configure hona chahiye, "hum bas careful rahenge" ek reliable strategy nahi hai.

Advanced Deep-Dive — Beyond the Basics

Ab tak humne dekha crashes ko capture aur symbolicate kaise karte hain. Ab senior-level territory — context kaise capture karein taaki sirf "kaha crash hua" nahi balki "user kya kar raha tha jab crash hua" pata chale, releases ki health kaise ek KPI ke roop mein monitor karein, aur ek custom error boundary kaise banayein jo genuinely production-grade ho.

Sentry Breadcrumbs — crash tak pahunchne wala trail

Breadcrumbs Sentry ka mechanism hai user actions aur system events ka ek chronological trail record karne ka — screen navigations, button taps, network calls, console logs — sab automatically ya manually breadcrumbs ke roop mein collect hote hain. Jab crash hota hai, crash report ke saath ye poora trail attach hota hai, taaki aap sirf "crash kaha hua" nahi, balki "crash se pehle user ne exactly kya kiya" reconstruct kar sako — ye debugging speed ko dramatically improve karta hai kyunki aapko manually user se reproduction steps nahi poochne padte.

app/(tabs)/checkout.tsx — manual breadcrumbs ka example
// Sentry SDK import karna breadcrumb aur error-capture functions ke liye
import * as Sentry from '@sentry/react-native';

// handlePayment — checkout screen ka main payment-trigger function
async function handlePayment(amount: number, method: string) {
  // Sentry.addBreadcrumb — ek manual breadcrumb add karna jo batata hai user ne "pay" button dabaya, kis amount/method ke saath
  Sentry.addBreadcrumb({
    // category — breadcrumb ko group karne ke liye, dashboard filtering mein useful
    category: 'checkout',
    // message — human-readable description jo trail mein dikhega
    message: `User initiated payment: amount=${amount}, method=${method}`,
    // level — severity level, "info" normal flow events ke liye
    level: 'info',
  });

  try {
    // Actual payment API call — Chapter 15 mein dekha gaya Stripe/payment provider ka call jaisa
    const result = await processPayment(amount, method);

    // Success case ke liye bhi ek breadcrumb — taaki success/failure dono trail mein reflect hon
    Sentry.addBreadcrumb({
      category: 'checkout',
      message: 'Payment succeeded',
      level: 'info',
    });

    // Function ka result return karna, caller ko success signal dene ke liye
    return result;
  } catch (error) {
    // Sentry.captureException — actual error ko Sentry ko explicitly bhejna, saath mein wahi breadcrumb trail attach hoga automatically
    Sentry.captureException(error, {
      // extra context — is specific error ke saath additional data attach karna, jaise amount/method jo crash ke time relevant tha
      extra: { amount, method },
    });
    // Error ko re-throw karna, taaki calling code (jaise UI layer) bhi apna error-handling kar sake (jaise error toast dikhana)
    throw error;
  }
}

Automatic breadcrumbs bhi hote hain — Sentry SDK khud-ba-khud navigation changes (Expo Router ke saath integration se), network requests (fetch/XHR interception), aur console logs ko breadcrumbs bana deta hai bina manual code ke. Manual breadcrumbs (upar wale example jaisa) tab add karo jab aapko genuinely business-specific context chahiye ho (jaise "user ne kaunsa payment method select kiya") jo automatic tracking capture nahi karta.

Release Health — crash-free rate ek KPI ke roop mein

Ek senior-level practice ye hai ki crash reporting ko sirf "reactive debugging tool" na treat karo, balki ek proactive monitoring metric ke roop mein bhi use karo. Sentry (aur similar tools) Release Health dashboard provide karte hain jisme crash-free session rate aur crash-free user rate jaise metrics har release ke against track hote hain — matlab "is version ko use karne wale kitne % sessions/users ne bina kisi crash ke app use kiya".

🧠 Senior Dev Note — ye Chapter 12 aur 14 se directly connect hota hai

Chapter 12 mein humne EAS Update se OTA rollouts dekhe the, aur Chapter 14 mein phased/staged rollouts store submissions ke liye. Crash-free rate exactly wo metric hai jo in dono strategies ko meaningful banata hai — agar aap ek OTA update ya phased rollout kar rahe ho, crash-free rate ka real-time dashboard hi wo signal hai jisse aap decide karte ho "is rollout ko aage badhaana hai ya rollback karna hai". Ek badi problem wali release almost turant crash-free rate mein ek visible dip ke roop mein dikhegi — agar aap is metric ko actively watch kar rahe ho, aap issue ko un users tak pahunchne se pehle hi rollback kar sakte ho jinhe abhi update nahi mila (staged rollout ka poora point yahi hai).

Practical setup: production release ke turant baad (especially phased rollout ke pehle few hours), crash-free rate dashboard ko actively monitor karo. Agar rate baseline se meaningfully gir jaaye (jaise 99.5% se 97% pe), ye ek immediate signal hai ki release mein kuch break hua hai, chahe abhi tak individual crash reports detail mein na dekhe ho.

Custom Error Boundary — fallback UI + automatic Sentry reporting

Sentry.wrap() ek default error boundary provide karta hai, lekin production apps mein aksar ek custom error boundary chahiye hoti hai jisme aap apna khud ka fallback UI dikha sako (generic "Something went wrong" screen ki jagah kuch on-brand), aur explicitly control karo kya reporting hoti hai.

components/AppErrorBoundary.tsx
// React import — Component class aur ReactNode type ke liye
import React, { Component, type ReactNode } from 'react';
// RN ke basic View/Text/Button components — fallback UI banane ke liye
import { View, Text, Button, StyleSheet } from 'react-native';
// Sentry SDK — error ko explicitly capture karne ke liye
import * as Sentry from '@sentry/react-native';

// Props interface — children hi required prop hai, jo normal ek error boundary wrap karta hai
interface Props {
  // children — wo poora subtree jise ye boundary protect karega
  children: ReactNode;
}

// State interface — sirf ek boolean track karta hai ki koi error hua hai ya nahi
interface State {
  // hasError — jab true ho, fallback UI render hogi instead of children
  hasError: boolean;
}

// AppErrorBoundary — class component hona MANDATORY hai, kyunki error boundaries sirf class components mein hi kaam karte hain (React ka current limitation, hooks se possible nahi)
export class AppErrorBoundary extends Component<Props, State> {
  // Constructor — initial state set karna, boundary shuru mein "no error" state mein hoti hai
  constructor(props: Props) {
    // super(props) call karna React class components mein mandatory hai
    super(props);
    // Initial state — hasError false, matlab children normally render honge
    this.state = { hasError: false };
  }

  // getDerivedStateFromError — React lifecycle method, error hote hi turant call hota hai render se pehle
  static getDerivedStateFromError(_error: Error): State {
    // hasError ko true karna — agli render pe fallback UI dikhegi
    return { hasError: true };
  }

  // componentDidCatch — dusra lifecycle method, error aur react component stack info yahan milta hai, side-effects (jaise reporting) yahan karte hain
  componentDidCatch(error: Error, errorInfo: React.ErrorInfo) {
    // Sentry.captureException — error ko explicitly Sentry ko bhejna, saath mein component stack bhi extra context ke roop mein
    Sentry.captureException(error, {
      extra: {
        // componentStack — batata hai kaunse components ki tree mein error propagate hua, debugging mein bahut useful
        componentStack: errorInfo.componentStack,
      },
    });
  }

  // handleReset — user ke "Try Again" tap pe state reset karna, taaki boundary dobara children render karne ki koshish kare
  handleReset = () => {
    // hasError ko false karke fallback UI hataana aur children ko dobara mount karna
    this.setState({ hasError: false });
  };

  // render — agar hasError true hai, fallback UI dikhaana; warna normal children render karna
  render() {
    if (this.state.hasError) {
      // Fallback UI JSX — on-brand error screen, generic crash screen ki jagah
      return (
        <View style={styles.container}>
          // Fallback heading — user-friendly message, technical error detail nahi dikhaate end-user ko
          <Text style={styles.title}>Kuch galat ho gaya</Text>
          <Text style={styles.subtitle}>Hum isse fix karne ki koshish kar rahe hain. Please dobara try karo.</Text>
          // Retry button — handleReset call karta hai taaki user bina app restart kiye recover kar sake
          <Button title="Try Again" onPress={this.handleReset} />
        </View>
      );
    }
    // Normal case — koi error nahi hua, children ko as-is render karna
    return this.props.children;
  }
}

// StyleSheet — fallback UI ki basic styling
const styles = StyleSheet.create({
  // container — poori screen center mein content dikhane ke liye
  container: { flex: 1, justifyContent: 'center', alignItems: 'center', padding: 24 },
  // title — heading text style
  title: { fontSize: 20, fontWeight: '700', marginBottom: 8 },
  // subtitle — description text style
  subtitle: { fontSize: 14, color: '#666', textAlign: 'center', marginBottom: 16 },
});
app/_layout.tsx — custom boundary ko wire karna
// Apna custom error boundary import karna
import { AppErrorBoundary } from '../components/AppErrorBoundary';
// Expo Router ka root Slot component
import { Slot } from 'expo-router';

// RootLayout — ab poore Slot tree ko humare custom AppErrorBoundary se wrap kar rahe hain, Sentry.wrap() ke bajaye
function RootLayout() {
  return (
    // AppErrorBoundary ke andar Slot rakhna — agar kahin bhi is tree mein render error aaye, poori app crash hone ki jagah fallback UI dikhegi
    <AppErrorBoundary>
      <Slot />
    </AppErrorBoundary>
  );
}

// Export karte waqt Sentry.wrap() abhi bhi laga sakte ho — dono ek saath kaam karte hain, Sentry.wrap native-level aur navigation-tracking wire karta hai, humara custom boundary JS render-error UI handle karta hai
export default RootLayout;
💡 Sharad ke liye — class component kyun, hooks kyun nahi

Ye poore codebase mein shayad ek-do jagah hi hai jaha class component genuinely zaroori hai — React ka error boundary mechanism specifically getDerivedStateFromError aur componentDidCatch lifecycle methods pe based hai, jinka koi hook-based equivalent abhi tak exist nahi karta React mein. Isliye agar aap ek custom error boundary bana rahe ho, class component syntax use karna hi padega — ye ek deliberate exception hai, function components ki general philosophy se conflict nahi hai.

🎯 Interview Questions — Senior React Native Developer

Ye section un questions ko cover karta hai jo senior/staff-level React Native interviews mein debugging, crash analysis, aur production reliability ke around poochhe jaate hain. Har answer detailed hai, taaki aap concept genuinely samajh kar confidently explain kar sako, sirf "sahi jawab" ratt kar nahi.

1. Explain exactly why a crash report shows unreadable hex addresses without the right symbol files, and how uploading them fixes it.

Production build ke compilation ke time, compiler readable symbol names (function/variable/class names) ko binary se strip kar deta hai, size aur reverse-engineering resistance ke liye. Jab crash hota hai, OS crash report ko sirf raw memory addresses ke roop mein generate karta hai (jaise 0x0000000104a3f2c8) kyunki us address ka corresponding readable naam binary ke andar exist hi nahi karta. Ye mapping (address → function name + file + line number) ek alag file mein store hoti hai jo compile-time pe hi generate hoti hai — iOS pe dSYM, Android pe ProGuard/R8 mapping file. Jab aap us exact build version ka matching symbol file crash reporting tool ko upload karte ho, tool ye mapping use karke hex addresses ko readable stack trace mein convert kar deta hai — is process ko symbolication kehte hain. Bina matching symbol file ke (jaise galat build version ka file upload ho gaya, ya upload hua hi nahi), ye conversion possible nahi hai — mapping exist hi nahi karti tool ke paas.

2. A crash-free rate metric drops sharply right after a release — walk through your incident response.

Sabse pehle, severity assess karo — kitna bada drop hai (99.5% se 97% chhota signal hai, 99.5% se 80% emergency hai), aur ye kis platform/device pe concentrated hai. Agar aap phased/staged rollout use kar rahe ho (Chapter 14), immediately rollout ko pause/halt karo taaki aur users affected na hon — ye sabse pehla action hona chahiye, root cause investigation se bhi pehle, kyunki ye reversible damage-control hai. Phir crash reporting tool (Sentry) ke top crashes dekho us release version ke against — konsa specific crash sabse zyada frequency se aa raha hai. Symbolicated stack trace se root cause identify karo. Agar fix fast hai, hotfix release karo (ya agar ye pure JS change hai jo native code touch nahi karta, ek EAS Update OTA push bhi kar sakte ho, Chapter 12 ka concept). Agar fix complex hai, decide karo poori release ko rollback karna hai (Play Store/App Store pe previous version restore, ya staged rollout ko 0% pe le jaana) jab tak fix ready na ho. Poore incident ke throughout crash-free rate dashboard ko monitor karte raho confirm karne ke liye ki fix/rollback effective hai.

3. How would you debug a bug that only reproduces on one specific low-end Android device model?

Pehle Sentry/crash-tool ke device breakdown se confirm karo ki ye genuinely device-specific hai (na ki sirf coincidence — check karo kitne total crashes hain aur unka device-distribution). Phir, agar possible ho, exact wahi device model physically arrange karo testing ke liye — emulator low-end hardware constraints (limited RAM, slower CPU, specific GPU driver quirks) ko accurately replicate nahi karta. Common root causes jo specifically low-end/specific-OEM devices pe hote hain: memory pressure (device kam RAM ki wajah se app ko background mein kill kar raha hai, ya OOM crash), OEM-specific Android build differences (Samsung/Xiaomi custom ROMs kabhi kabhi standard Android behavior se deviate karte hain), ya ek specific chipset/architecture issue (ARM32 vs ARM64). ANR trace ya crash stack se pattern dekho — agar memory-related lagta hai, Android Studio Profiler us (ya similar) device pe use karke memory usage timeline observe karo.

4. Why can't a JS-level Error Boundary catch every kind of app failure?

Error Boundary React ka mechanism hai jo specifically React component tree ke render/lifecycle phase mein hone wale JS exceptions ko catch karta hai. Ye teen categories ki failures catch nahi karta: (1) event handler ke andar errors — jaise onPress callback ke andar thrown error, kyunki ye React render cycle ke bahar execute hota hai, isko normal try/catch chahiye; (2) async code ke andar errors jo directly render se trigger nahi hue (jaise ek setTimeout ke andar thrown error); aur sabse importantly (3) genuine native crashes — jaha poora app process hi OS level pe terminate ho jaata hai. Jab native crash hota hai, JS runtime khud us process ke saath mar jaata hai, isliye koi JS-level code (Error Boundary included) ko chance hi nahi milta react karne ka — process already gone hai. Isi wajah se production apps ko dono chahiye: Error Boundary (JS render errors ke liye graceful degradation) aur native-level crash reporting (genuine process-level crashes capture karne ke liye) — ye dono complementary hain, ek dusre ka replacement nahi.

5. What's the difference between a true Android ANR and JS-thread blocking that causes UI jank? Why does this distinction matter?

React Native mein JS thread aur Android ka native main/UI thread do alag threads hain. Agar JS thread block ho (jaise ek heavy synchronous JS loop, ya ek native Function() jo bahut der leta hai calling JS thread pe), result hota hai JS-driven UI frozen — animations ruk jaate hain, taps respond nahi karte — lekin native main thread khud technically responsive rehta hai, isliye Android OS ANR trigger nahi karta. Ek genuine ANR specifically tab hota hai jab native main thread khud block ho — jaise koi native module code jo synchronously blocking I/O kare directly main thread pe, bina background thread pe offload kiye. Distinction matter isliye karta hai kyunki fix bilkul different hai: JS thread blocking ka fix hai JS-side optimization (computation break karna, background threads pe JS-level kaam offload karna jaise `InteractionManager`), jabki genuine ANR ka fix hai native code ko properly async banana (jaise Chapter 16 ka AsyncFunction() pattern). Galat diagnosis (JS jank ko ANR samajh kar native code fix karna, ya vice versa) time waste karta hai galat jagah pe.

6. Your team ships a build where the symbol upload step silently failed in CI. What's your process for handling crashes from that specific version?

Ye ek genuinely hard situation hai kyunki us exact build ke symbols ab permanently missing hain (jab tak build artifact locally preserved na ho, jo rarely hota hai). Process: (1) Confirm karo ki genuinely symbols missing hain (Sentry dashboard mein us release ke "symbolication status" check karo — kabhi kabhi delay hota hai upload mein, immediately conclude mat karo failed hai). (2) Agar genuinely missing hain aur build artifact bhi retrievable nahi hai, dekho crash pattern (device/OS breakdown, frequency, kis screen/action se juda) se kuch inference nikal sakte ho bina full symbolication ke — jaise agar crash rate ek specific recently-changed feature ke around concentrated hai. (3) Immediate priority: agla hotfix release ship karo jisme symbol upload properly verify ho — taaki agar wahi crash phir se hoti hai naye build mein, ab aapke paas readable stack trace ho. (4) Root cause karo CI pipeline mein — kyun upload silently fail hua (auth token expire, network issue, misconfigured hook)? Fix ye add karo ki upload step ki failure build ko hi fail kare (loud failure), silent failure na rahe — taaki future mein ye issue immediately visible ho, kisi crash ke baad discover na ho.

7. What's the practical difference between how you'd set up crash reporting for JS errors vs native crashes in Sentry?

JS error capture Sentry mein largely automatic hai — Sentry.wrap() app root ko wrap karne se React render errors automatically capture hote hain, aur `Sentry.captureException()` explicit try/catch blocks ke andar use hota hai. Native crash capture ke liye, Sentry.init() mein enableNative: true set karna hota hai — ye Sentry ke native-level SDK layer (Swift/Kotlin side pe embedded) ko activate karta hai jo OS-level fatal signals (segfaults, native exceptions) ko intercept karta hai crash hone se pehle bhi (kyunki technically process crash ho raha hai, Sentry ko ek crash handler register karna padta hai jo process terminate hone se theek pehle report likh sake disk pe, aur agli app launch pe use upload kare). Iske alawa, native crashes ke liye dSYM/mapping file upload critical hai (jo JS ke liye source-map upload ke equivalent hai) — bina iske native crashes symbolicate nahi honge chahe capture ho bhi rahe hon.

8. Why is "it works in dev, crashes in production" often harder to debug than a crash that reproduces consistently everywhere?

Kyunki root cause almost hamesha koi environmental difference hota hai jo aapke local setup mein replicate karna hard hota hai — production minification/ProGuard obfuscation, production environment variables, ya timing differences jo dev ki slower execution mein race conditions ko mask kar dete hain. Aapko root cause dhoondhne ke liye systematically har possible difference ko rule out karna padta hai (Hermes vs JSC, dev-only code paths, minification stripping, missing env vars, race conditions) — ek checklist approach zaroori hai kyunki koi ek "obvious" jagah nahi hoti dekhne ki. Iske alawa, aap production issue ko locally reproduce hi nahi kar sakte agar aap sirf dev build test karte raho — jab tak aap explicitly ek genuine production-configured build (minified, real env vars) locally test na karo, aap us category ke bugs kabhi hit hi nahi karoge apne dev environment mein.

9. How do Sentry breadcrumbs improve debugging compared to just having a stack trace at the crash point?

Ek stack trace sirf batata hai "crash exactly kaha hua" — kaunsa function, kaunsi line. Ye batata nahi ki user crash tak pahuncha kaise — kaunsi screens navigate ki, kaunse buttons dabaye, kaunse API calls hue us se pehle. Breadcrumbs ye poora chronological trail capture karte hain (automatic — navigation, network requests, console logs; aur manual — business-specific events jo aap explicitly add karte ho jaise "payment initiated"). Result: jab crash report dekhte ho, aapke paas sirf ek isolated crash point nahi, balki ek poori story hai jo dikhati hai exact sequence of events jo crash tak leke gayi. Ye dramatically debugging time reduce karta hai kyunki aapko manually user se "kya kar rahe the crash se pehle" poochne ki zaroorat nahi padti — jo aksar unreliable/incomplete jawab deta hai kyunki users exact steps yaad nahi rakhte.

10. Why must a custom Error Boundary be a class component, and what does that tell you about a limitation in React's current hooks API?

Error Boundary mechanism specifically do lifecycle methods pe depend karta hai — static getDerivedStateFromError() (jo error hote hi turant, render se pehle state derive karta hai) aur componentDidCatch() (jo error aur component-stack info deta hai side-effects ke liye, jaise Sentry reporting). Ye dono class-component-specific lifecycle methods hain — React ne abhi tak inka koi hook-based equivalent introduce nahi kiya hai (jaise useDerivedStateFromError jaisa kuch exist nahi karta). Ye batata hai ki React ka hooks API, jitna comprehensive hai, har class-component capability ko fully replace nahi karta — error boundaries ek deliberate, acknowledged exception hain jaha class components abhi bhi genuinely zaroori hain, sirf legacy code ke liye nahi balki koi alternative na hone ki wajah se.
