1. Animation Fundamentals: Why RN Animations Are Different

Chalo pehle samajhte hain ki React Native mein animations "different" kyun hote hain compared to web ya native iOS/Android directly likhna. Iske liye pehle RN ki purani architecture ko samajhna padega — the Bridge.

Purana problem: the Bridge aur async messaging

Old React Native architecture mein teen "worlds" hote the: JS thread (jahan aapka React/JS code chalta hai), Native/UI thread (jahan actual rendering, touch handling, aur platform views hote hain), aur inke beech mein the Bridge — ek async, serialized (JSON stringify jaisa) messaging channel.

Jab aap old Animated API (bina useNativeDriver) use karte the, to har animation frame pe ye hota tha:

  • JS thread calculate karta hai naya value (e.g. translateX = 42.3)
  • Ye value serialize hoke bridge cross karti hai
  • Native side pe deserialize hoke actual view pe apply hoti hai
  • Ye poora cycle har single frame pe repeat hota hai — 60fps pe matlab har ~16ms mein

Problem ye hai ki agar JS thread kisi aur kaam mein busy hai — jaise ek heavy list re-render, ek API response process karna, ya koi expensive computation — to wo animation frame updates bhi delay ho jaate hain. Result: jank (animation stutter/frame drops), kyunki animation ka smoothness JS thread ki availability pe depend kar raha tha, jabki animation khud ek purely visual/native concern hai.

📌 useNativeDriver: true — ek partial fix

Facebook ne useNativeDriver: true add kiya jisme animation ki poori sequence (start value, end value, easing curve, duration) ek baar bridge cross karke native side ko de di jaati thi, aur phir native thread khud hi har frame calculate karta tha — JS thread ko baar baar involve kiye bina. Ye kaafi behtar tha, lekin limited tha: sirf specific non-layout properties (transform, opacity) animate ho sakti thi, aur gesture-driven interactive animations (jahan har frame ka value user ke finger position pe depend karta hai) is model mein fit nahi hoti thi kyunki gesture data JS thread pe hi aata tha.

Reanimated ka solution: Worklets aur JSI

Reanimated (specially v2 aur v3) ne is problem ko fundamentally different tareeke se solve kiya — bridge ko bypass karke. Iske liye do cheezein use hoti hain: JSI (JavaScript Interface) aur Worklets.

JSI New Architecture ka core piece hai — ye ek C++ layer hai jo JS engine (Hermes/JSC) ko directly native C++ objects ke saath talk karne deta hai, bina serialization/bridge ke. Isse JS values aur native functions ke beech synchronous, direct calls possible hote hain.

Reanimated isi JSI ka use karke ek trick karta hai: jab aap koi function ke andar 'worklet' directive likhte ho (ya use karte ho useAnimatedStyle/useAnimatedGestureHandler jaise hooks ke andar, jo automatically worklet-ize ho jaate hain via Babel plugin), Reanimated ka babel plugin us function ko compile-time pe parse karta hai aur uska ek serializable representation banata hai (basically function ka source string + closure variables). Runtime pe, ye worklet UI thread pe ek separate, chhota JS runtime (jise "UI runtime" kehte hain) mein directly execute hota hai — bina JS thread ko touch kiye, bina bridge cross kiye.

worklet-example.ts
// Ye function 'worklet' directive ki wajah se
// UI thread pe apna separate copy mein run hota hai
function myWorklet() {
  'worklet';
  // Ye code JS thread pe nahi, UI thread pe chalega
  console.log('Running on UI thread!');
}

Matlab ab animation ka poora logic — calculation, interpolation, spring physics — UI thread pe hi chal raha hai, jahan actual rendering bhi ho rahi hai. JS thread busy ho ya na ho, animation ka isse koi lena dena nahi. Isi wajah se Reanimated animations 60fps (aur ProMotion devices pe 120fps tak) consistently maintain kar paate hain even jab JS thread pe heavy work chal raha ho.

Purana Animated API abhi bhi codebase mein kahin kahin milega (legacy code, ya simple cases jaha bridge overhead matter nahi karta), aur usko samajhna important hai for history/context — lekin naye production RN apps mein complex ya gesture-driven animations ke liye Reanimated hi default choice honi chahiye. Interview mein bhi ye "why" wala explanation (bridge → JSI → worklets) senior-level differentiator hota hai.

2. Reanimated 3 Core Concepts

Ab hum Reanimated 3 ke building blocks dekhte hain — ye sab kuch upar wale worklet model ke upar bana hai.

useSharedValue — UI thread pe rehne wali value

useSharedValue ek special value banata hai jo UI thread aur JS thread dono se accessible hai, lekin uska storage UI thread ke memory mein hota hai. Jab aap .value ko mutate karte ho, React ka re-render trigger nahi hota — kyunki ye React state nahi hai, ye ek plain mutable container hai jo dono threads ke beech synced rehta hai.

Ye bahut important hai samajhna: agar har animation frame pe React re-render trigger hota (jaise useState se hota), to performance bahut kharab ho jaati — React reconciliation, diffing, ye sab heavy operations har frame pe chalte. Shared values isse bypass karte hain.

SharedValueBasics.tsx
import { useSharedValue } from 'react-native-reanimated';

function Example() {
  // scale.value UI thread pe store hoti hai
  const scale = useSharedValue(1);

  // Isse re-render trigger NAHI hoga
  scale.value = 1.2;
}

useAnimatedStyle — shared values ko style mein map karna

useAnimatedStyle khud ek worklet hai — ye ek function leta hai jo shared values read karke ek style object return karta hai, aur ye poora mapping UI thread pe run hota hai har frame jab bhi shared value change hoti hai. Kyunki ye directly UI thread pe chal raha hai, ye style directly native view pe apply ho jaata hai — bina JS thread ke involvement ke.

Animation functions: withTiming, withSpring, withDecay

  • withTiming — duration-based easing animation (jaise CSS transition), predictable time mein value A se B tak jaata hai.
  • withSpring — physics-based spring simulation (mass, damping, stiffness), natural/organic feel deta hai, duration fixed nahi hoti.
  • withDecay — velocity-based animation jo gradually decelerate hoti hai (jaise fling/scroll momentum) — gestures ke saath bahut use hota hai.

Ye teeno functions worklets ke andar call kiye jaate hain aur UI thread pe hi apna calculation karte hain.

runOnJS — worklet se wapas JS thread mein jaana

Worklets ek alag JS context/runtime mein run hote hain (UI runtime) — matlab wo aapke normal JS thread ke regular functions, closures, ya React state setters ko directly call nahi kar sakte, kyunki wo dusre runtime mein exist hi nahi karte. Agar aapko kisi worklet ke andar se koi normal JS function call karni hai — jaise setState, ek API call trigger karna, ya navigation — to aapko runOnJS() use karna padta hai. Ye Reanimated ko batata hai: "is function ko UI thread se JS thread pe schedule karke wahan run karo".

⚠️ Gotcha

runOnJS khud ek async bridge-jaisi hop hai (though lightweight, JSI ke through) — matlab isko har frame call karna phir se wahi bottleneck bana sakta hai jo hum avoid karne ki koshish kar rahe the. Isliye runOnJS ko sirf discrete events pe use karo (gesture end, animation complete callback), continuous frame updates ke liye nahi.

Full Example: Scale on Press Card

Ab ek complete example dekhte hain — ek card jo press karne pe scale down hoti hai spring animation ke saath.

PressableCard.tsx
import React from 'react';
import { Pressable, Text, StyleSheet } from 'react-native';
import Animated, {
  useSharedValue,
  useAnimatedStyle,
  withSpring,
} from 'react-native-reanimated';

export function PressableCard() {
  // UI thread pe rehne wali value, initial 1 (normal size)
  const scale = useSharedValue(1);

  // Ye worklet hai — UI thread pe run hoga jab bhi scale.value change ho
  const animatedStyle = useAnimatedStyle(() => {
    return {
      transform: [{ scale: scale.value }],
    };
  });

  const handlePressIn = () => {
    // withSpring ek worklet return karta hai jo UI thread pe animate hoga
    scale.value = withSpring(0.92, {
      damping: 15,
      stiffness: 180,
    });
  };

  const handlePressOut = () => {
    scale.value = withSpring(1);
  };

  return (
    <Pressable onPressIn={handlePressIn} onPressOut={handlePressOut}>
      <Animated.View style={[styles.card, animatedStyle]}>
        <Text style={styles.text}>Tap me</Text>
      </Animated.View>
    </Pressable>
  );
}

const styles = StyleSheet.create({
  card: {
    padding: 24,
    borderRadius: 16,
    backgroundColor: '#d97757',
  },
  text: { color: '#fff', fontWeight: '700' },
});

Notice karo: Animated.View (Reanimated ka export, plain RN Animated ka nahi) use ho raha hai — ye ek special component hai jo animatedStyle ko directly UI thread se apni native view pe apply kar sakta hai without going through React's render cycle.

3. Gesture Handler v2 + Reanimated Integration

PanResponder ka purana problem

RN ka original gesture system, PanResponder, gesture recognition logic (touch start/move/end detection, threshold calculation, conflict resolution between nested gestures) JS thread pe chalata tha. Har touch move event JS thread tak bridge cross karke aata tha, JS logic decide karta tha "ye pan hai ya tap", aur phir response wapas jaata tha. Isme bhi wahi latency/jank problem thi jo animations mein thi.

Gesture Handler v2: native thread pe gesture recognition

react-native-gesture-handler (v2) is problem ko solve karta hai gesture recognition ko native thread pe move karke. Touch events directly native gesture recognizers (iOS UIGestureRecognizer / Android GestureDetector jaise concepts, but library ka apna unified system) handle karte hain. Jab ye Reanimated ke saath combine hota hai, to gesture ka pura pipeline — recognition (native thread) → value update (UI thread via shared values) → style update (UI thread) — kabhi bhi JS thread ko touch hi nahi karta, matlab zero bridge crossings ek drag interaction ke during.

Naya Gesture API

Gesture Handler v2 ne ek naya declarative Gesture API diya hai (purane PanGestureHandler jaise component-based API ki jagah, jo ab legacy consider hota hai):

  • Gesture.Pan() — drag gestures ke liye
  • Gesture.Tap() — tap detection ke liye
  • Gesture.Pinch(), Gesture.Rotation(), Gesture.LongPress() — aur bhi types
  • Gesture.Simultaneous(g1, g2) — multiple gestures ek saath recognize karne ke liye (e.g. pan + pinch)
  • Gesture.Race(g1, g2) — jo pehle recognize ho jaaye wahi "win" kare, baaki cancel
  • Gesture.Exclusive(g1, g2) — priority-based, g1 pehle try hota hai, fail hone pe g2

Har gesture object ke callbacks (.onBegin(), .onUpdate(), .onEnd(), .onFinalize()) worklets hote hain — matlab inke andar directly shared values modify kar sakte ho, aur ye UI thread pe hi execute hoga.

In gestures ko component tree mein attach karne ke liye <GestureDetector gesture={...}> wrapper use hota hai, jo ek single child component ko wrap karta hai.

Full Example: Draggable Card

DraggableCard.tsx
import React from 'react';
import { StyleSheet } from 'react-native';
import { Gesture, GestureDetector } from 'react-native-gesture-handler';
import Animated, {
  useSharedValue,
  useAnimatedStyle,
  withSpring,
} from 'react-native-reanimated';

export function DraggableCard() {
  const translateX = useSharedValue(0);
  const translateY = useSharedValue(0);

  // Context values taaki drag start se relative offset track ho sake
  const startX = useSharedValue(0);
  const startY = useSharedValue(0);

  const panGesture = Gesture.Pan()
    .onStart(() => {
      'worklet';
      startX.value = translateX.value;
      startY.value = translateY.value;
    })
    .onUpdate((event) => {
      'worklet';
      // Ye pura UI thread pe chal raha hai — no bridge crossing
      translateX.value = startX.value + event.translationX;
      translateY.value = startY.value + event.translationY;
    })
    .onEnd(() => {
      'worklet';
      // Finger uthate hi origin pe wapas spring back
      translateX.value = withSpring(0);
      translateY.value = withSpring(0);
    });

  const animatedStyle = useAnimatedStyle(() => ({
    transform: [
      { translateX: translateX.value },
      { translateY: translateY.value },
    ],
  }));

  return (
    <GestureDetector gesture={panGesture}>
      <Animated.View style={[styles.card, animatedStyle]} />
    </GestureDetector>
  );
}

const styles = StyleSheet.create({
  card: {
    width: 120,
    height: 120,
    borderRadius: 16,
    backgroundColor: '#6fa8d8',
  },
});
🧠 Senior Dev Note

Notice karo — poore drag interaction mein (finger move se lekar card render hone tak) JS thread involved hi nahi hai. Native gesture recognizer touch events capture kar raha hai, worklet UI thread pe values update kar raha hai, aur useAnimatedStyle UI thread pe hi style laga raha hai. Yahi wo architecture hai jo native-app-jaisa "1:1 finger tracking" feel deta hai, jo old PanResponder ke saath achieve karna mushkil tha.

4. Composition & Interaction Patterns

withSequence — animations ko chain karna

withSequence multiple animations ko ek ke baad ek run karta hai — jaise ek button jo pehle bada ho, phir chhota ho ("bounce" effect):

sequence-example.ts
scale.value = withSequence(
  withTiming(1.2, { duration: 100 }),
  withTiming(1, { duration: 150 })
);

Parallel animations

Multiple shared values ko independently assign karke aap effectively parallel animations chala sakte ho — alag alag shared values apne apne timing pe animate hote rahenge, ek dusre ko block kiye bina:

parallel-example.ts
// Ye dono ek saath, parallel mein animate honge
opacity.value = withTiming(1, { duration: 300 });
translateY.value = withSpring(0);

interpolate() — ek range se dusri range mein map karna

interpolate() ek value (jaise scroll offset ya gesture progress) ko linearly ek input range se output range mein map karta hai — bahut common use case hai scroll position ko opacity/scale mein convert karna.

Full Example: Fading Header on Scroll

FadingHeader.tsx
import React from 'react';
import Animated, {
  useSharedValue,
  useAnimatedStyle,
  useAnimatedScrollHandler,
  interpolate,
  Extrapolation,
} from 'react-native-reanimated';

const HEADER_FADE_DISTANCE = 120;

export function ScreenWithFadingHeader({ children }: { children: React.ReactNode }) {
  const scrollY = useSharedValue(0);

  // Scroll handler bhi ek worklet hai — har scroll event UI thread pe process hota hai
  const scrollHandler = useAnimatedScrollHandler((event) => {
    scrollY.value = event.contentOffset.y;
  });

  const headerStyle = useAnimatedStyle(() => {
    const opacity = interpolate(
      scrollY.value,
      [0, HEADER_FADE_DISTANCE],
      [1, 0],
      Extrapolation.CLAMP
    );
    return { opacity };
  });

  return (
    <>
      <Animated.View style={headerStyle}>{/* header content */}</Animated.View>
      <Animated.ScrollView onScroll={scrollHandler} scrollEventThrottle={16}>
        {children}
      </Animated.ScrollView>
    </>
  );
}

useDerivedValue — computed shared values

useDerivedValue ek naya shared value banata hai jo automatically recompute hoti hai jab bhi uske andar use hone wali dependencies (dusri shared values) change hoti hain — useMemo ka UI-thread equivalent soch lo:

derived-value-example.ts
const progress = useSharedValue(0);

// derivedOpacity automatically update hoga jab progress badlega
const derivedOpacity = useDerivedValue(() => {
  return interpolate(progress.value, [0, 1], [0.3, 1]);
});
💡 Quick Tip

useDerivedValue tab use karo jab ek computed value multiple jagah (multiple useAnimatedStyle calls) mein use ho rahi ho — isse duplicate calculation avoid hoti hai aur code cleaner rehta hai.

5. Swipeable Components (Real Pattern)

Ab hum sab kuch combine karke ek real production pattern banate hain — swipe-to-delete list item, jo almost har chat app (WhatsApp, Gmail) mein milta hai. Logic: user card ko horizontally drag kare, agar threshold distance/velocity cross ho jaaye to card poori tarah swipe out ho jaaye aur delete callback fire ho, warna card wapas snap back ho jaaye.

SwipeToDeleteItem.tsx
import React from 'react';
import { StyleSheet, Text, Dimensions } from 'react-native';
import { Gesture, GestureDetector } from 'react-native-gesture-handler';
import Animated, {
  useSharedValue,
  useAnimatedStyle,
  withTiming,
  withSpring,
  runOnJS,
} from 'react-native-reanimated';

const SCREEN_WIDTH = Dimensions.get('window').width;
const SWIPE_THRESHOLD = SCREEN_WIDTH * 0.35;
const VELOCITY_THRESHOLD = 800;

type Props = {
  label: string;
  onDelete: () => void;
};

export function SwipeToDeleteItem({ label, onDelete }: Props) {
  const translateX = useSharedValue(0);
  const itemHeight = useSharedValue(60); // collapse ke liye

  // Delete confirm hone ke BAAD hi JS thread pe callback fire karna hai —
  // isliye runOnJS sirf animation complete hone ke baad, gesture ke andar nahi
  const triggerDelete = () => {
    onDelete();
  };

  const panGesture = Gesture.Pan()
    .onUpdate((event) => {
      'worklet';
      // Sirf left swipe allow karna hai is example mein
      translateX.value = Math.min(0, event.translationX);
    })
    .onEnd((event) => {
      'worklet';
      const shouldDelete =
        translateX.value < -SWIPE_THRESHOLD || event.velocityX < -VELOCITY_THRESHOLD;

      if (shouldDelete) {
        // Card ko poori tarah screen se bahar animate karo
        translateX.value = withTiming(-SCREEN_WIDTH, { duration: 200 });
        // Height collapse karo taaki list mein gap na dikhe
        itemHeight.value = withTiming(0, { duration: 200 }, (finished) => {
          // Ye callback bhi worklet context mein chalta hai —
          // isliye asli JS function call karne ke liye runOnJS zaroori hai
          if (finished) {
            runOnJS(triggerDelete)();
          }
        });
      } else {
        // Threshold cross nahi hua — wapas origin pe spring back
        translateX.value = withSpring(0);
      }
    });

  const animatedStyle = useAnimatedStyle(() => ({
    transform: [{ translateX: translateX.value }],
    height: itemHeight.value,
    opacity: itemHeight.value === 0 ? 0 : 1,
  }));

  return (
    <GestureDetector gesture={panGesture}>
      <Animated.View style={[styles.row, animatedStyle]}>
        <Text style={styles.label}>{label}</Text>
      </Animated.View>
    </GestureDetector>
  );
}

const styles = StyleSheet.create({
  row: {
    justifyContent: 'center',
    paddingHorizontal: 16,
    backgroundColor: '#262524',
    borderBottomWidth: 1,
    borderBottomColor: '#3a3835',
    overflow: 'hidden',
  },
  label: { color: '#e8e4dd', fontSize: 16 },
});

Yaha decision logic — distance threshold ya velocity threshold — dono check ho rahe hain, jo real apps mein important hai: agar user tez fling kare lekin bahut door tak drag na kare, phir bhi wo "intentional delete" count hona chahiye. Aur runOnJS sirf ek jagah, animation complete hone ke baad ka callback mein use ho raha hai — har frame pe nahi.

⚠️ Gotcha

withTiming/withSpring ka teesra argument (completion callback) khud bhi ek worklet hai — agar aapko uske andar se JS function call karni hai (jaise state update ya parent callback), to wahan bhi runOnJS hi lagana padega, direct call nahi chalega.

6. Performance Rules for 60fps

Ab kuch practical rules jo production mein jank avoid karne ke liye follow karne chahiye.

console.log worklets ke andar carefully use karo

Worklets ke andar console.log kaam karta hai (Reanimated isko special handle karta hai taaki output Metro console mein dikhe), lekin isme overhead hai — har call UI thread se JS thread tak ek message bhejta hai. Agar aap isse har animation frame pe (jaise onUpdate ke andar) chhod doge debugging ke baad, to ye silently performance degrade karega. Debug karne ke baad hamesha remove/comment karo.

runOnJS ko sparingly use karo — sirf gesture end pe, har frame pe nahi

Jaisa upar dekha, onUpdate (jo har frame fire hota hai during drag) ke andar runOnJS call karna — jaise React state update trigger karna har pixel move pe — poori purpose defeat kar deta hai jo hum achieve karna chahte the. Sirf discrete moments (gesture start/end, animation complete) pe hi JS thread involve karo.

useAnimatedStyle sirf shared values reference kare, regular state nahi

useAnimatedStyle ke andar agar aap koi regular React state ya prop use karte ho (non-shared-value), to worklet ko wo value capture karne ke liye JS thread se sync karna padega — jo phir se bridge-jaisa overhead introduce karta hai aur re-render bhi trigger kar sakta hai. Best practice: useAnimatedStyle ke andar sirf useSharedValue se aayi values use karo.

Layout animations — entering/exiting/Layout

Reanimated 3 layout animations bhi provide karta hai — entering aur exiting props (component mount/unmount pe automatic animation) aur layout prop (jab component ki position/size change ho, jaise list reorder). Ye bhi native thread pe hi chalte hain. Limitation: ye sab components ke saath consistently kaam nahi karte — kuch complex native components (jaise certain third-party wrapped views, ya Text ke kuch edge cases) mein layout animations properly apply nahi hoti, aur nested nested `Animated.View` ke saath conflicts ho sakte hain. Production mein use karne se pehle target components pe test zaroor karo.

🧠 Senior Dev Note

Performance debugging ke liye Reanimated ka _WORKLET global variable check kar sakte ho ye confirm karne ke liye ki code UI thread pe run ho raha hai ya JS thread pe. Aur agar list mein bahut saare swipeable items hain, to har item apna independent useSharedValue rakhega — koi shared/global state mat use karo warna sab items ek dusre ko affect karenge.

7. Real-World Gotchas

⚠️ Babel plugin order matters

Reanimated ka babel plugin (react-native-reanimated/plugin) hamesha plugins array mein sabse last hona chahiye babel.config.js mein. Agar ye last nahi hai, to worklets properly transform nahi hote aur aapko cryptic runtime errors milenge (jaise "value.value undefined" ya silent failures jahan animation bilkul kaam hi nahi karti) — ye ek bahut common setup mistake hai jo naye developers ko ghanto debug karwa deta hai.

babel.config.js
module.exports = function(api) {
  api.cache(true);
  return {
    presets: ['babel-preset-expo'],
    plugins: [
      // dusre plugins yaha upar
      'react-native-reanimated/plugin', // ⚠️ YE HAMESHA LAST HONA CHAHIYE
    ],
  };
};
🚨 GestureHandlerRootView zaroori hai

Poori app ke root pe (ya kam se kam wahan jahan bhi gestures use ho rahe hain) GestureHandlerRootView se wrap karna mandatory hai. Agar aap ye bhool jaate ho, to gestures silently kaam nahi karte — koi error nahi aata, bas onUpdate/onEnd callbacks fire hi nahi hote, jo debug karna bahut frustrating hota hai kyunki koi clear signal nahi milta ki problem kya hai.

App.tsx
import { GestureHandlerRootView } from 'react-native-gesture-handler';

export default function App() {
  return (
    <GestureHandlerRootView style={{ flex: 1 }}>
      {/* poori app yaha */}
    </GestureHandlerRootView>
  );
}
⚠️ Worklets closures ke saath careful raho

Worklets non-worklet regular functions ko directly call nahi kar sakte (sirf runOnJS ke through), aur complex objects (class instances, functions with their own closures) ko worklet ke andar capture karna issues create kar sakta hai kyunki babel plugin ko unhe serialize karna padta hai UI thread pe bhejne ke liye. Plain objects, primitives, aur dusre shared values capture karna safe hai — class instances ya complex nested closures avoid karo.

⚠️ Debugging worklets normal debugger se mushkil hai

Kyunki worklets UI thread pe ek separate JS runtime mein chalte hain, Chrome DevTools ya standard React Native debugger breakpoints inke andar reliably kaam nahi karte jaise regular JS code mein karte hain. Practical approach: console.log sparingly use karo (jaisa upar discuss kiya), ya Reanimated ke logger utilities, aur agar deeply stuck ho to logic ko temporarily runOnJS se JS thread pe move karke normal debugging tools se verify karo, phir wapas worklet mein daalo.

8. Advanced Deep-Dive — Beyond the Basics

Ab tak humne use kaise karna hai dekha. Ab hum ek level aur neeche jaake dekhte hain ki engine ke andar actually chal kya raha hai — ye wahi depth hai jo senior interviews mein differentiate karti hai.

Worklet transformation internals — Babel plugin actually karta kya hai

Upar humne bola tha ki 'worklet' directive wale functions UI thread pe run hote hain — lekin mechanism kya hai ye achieve karne ka? Ye sab compile-time pe hota hai, Reanimated ke Babel plugin (react-native-reanimated/plugin) ke through, aur process roughly ye steps follow karta hai:

  • Static analysis: Build time pe (Metro bundling ke dauraan) Babel plugin poori source code ko AST (Abstract Syntax Tree) ke form mein parse karta hai aur dhoondta hai un functions ko jinke body ka pehla statement 'worklet' string hai — ya jo kisi "worklet-izing" hook (jaise useAnimatedStyle, useDerivedValue, useAnimatedGestureHandler, ya Gesture.Pan().onUpdate(...) jaisi callback) ke andar pass kiye gaye hain — in hooks ke arguments ko plugin implicitly worklet mark kar deta hai, aapko manually 'worklet' likhne ki zaroorat nahi padti.
  • Serialization: Jo function worklet identify ho jaata hai, uska Babel plugin do cheezein extract karta hai — (1) function ka source code as a string (basically function ko stringify kar diya jaata hai), aur (2) uska closure — matlab outer scope ki wo variables jo function ke andar reference ho rahi hain (jaise useSharedValue se aayi values, constants, etc).
  • Re-creation on UI runtime: Runtime pe, jab worklet ko actually call karna hota hai, Reanimated us serialized string ko UI thread pe chal rahe ek separate, chhote JS runtime (JSC/Hermes ka ek dusra instance jo sirf UI thread ke liye hai) mein bhejta hai JSI ke through, wahan us string se function re-construct hota hai (basically eval jaisa kuch, lekin controlled), aur closure variables inject kiye jaate hain.

Yahi wajah hai ki worklets ke andar arbitrary outside functions ya complex objects casually reference nahi kiye ja sakte — kyunki ek function/object sirf tab UI thread pe available hoga jab wo bhi serializable ho (plain function jo khud worklet ho, ya primitive/plain-object closure variable). Agar aap kisi regular (non-worklet) JS function ko worklet ke andar directly call karne ki koshish karoge, wo function UI runtime pe exist hi nahi karta — isliye crash ya silent failure milega. Isi gap ko explicitly bridge karne ke liye do functions hain:

  • runOnJS(fn) — UI thread se JS thread pe schedule karke ek regular function call karta hai (jo humne swipe-to-delete example mein dekha).
  • runOnUI(fn) — iska ulta: JS thread se explicitly UI thread pe ek worklet schedule karta hai (kam common, lekin useful jab aapko JS thread se manually ek imperative worklet trigger karni ho, jaise ek button press pe bina gesture ke).
worklet-boundary.ts
import { runOnJS, runOnUI, useSharedValue } from 'react-native-reanimated'; // dono direction ke bridge functions import

function Example() {
  const progress = useSharedValue(0); // UI thread pe rehne wali shared value

  function logToAnalytics(value: number) { // ye ek NORMAL JS function hai — worklet nahi
    console.log('Analytics event:', value); // isko JS thread pe hi chalna hai (analytics SDK JS thread pe rehta hai)
  }

  function jsToUiExample() { // ye function JS thread pe call hota hai (e.g. button onPress se)
    runOnUI(() => { // runOnUI: JS thread se UI thread pe ek worklet schedule kar rahe hain
      'worklet'; // ye arrow function khud worklet hai, isliye UI thread pe run hoga
      progress.value = 1; // UI thread pe directly shared value set — imperative trigger, bina gesture ke
    })(); // runOnUI ek function return karta hai jise turant invoke kar rahe hain
  }

  function uiToJsExample() { // ye function worklet context se call hoga (e.g. gesture callback se)
    'worklet'; // ye poora function UI thread pe worklet hai
    runOnJS(logToAnalytics)(progress.value); // runOnJS: UI thread se JS thread pe wapas jump, non-worklet fn call ke liye
  }
}
🧠 Senior Dev Note

Interview mein agar puchha jaaye "worklet kya hai runtime pe" — sabse weak answer hai "ek function jo UI thread pe chalta hai". Strong answer ye include karega ki babel plugin compile-time pe static analysis karta hai, function ko string + closure ke roop mein serialize karta hai, aur runtime pe ek dusre JS engine instance (UI runtime) mein re-hydrate karta hai JSI ke through — aur isi wajah se worklets "sandboxed" feel hote hain (arbitrary closures/class instances allowed nahi).

Fabric + Reanimated layout animations — internals aur limitations

New Architecture ka renderer, Fabric, React tree changes ko ek "commit" lifecycle ke through process karta hai — jab bhi kuch mount/unmount/reposition hota hai, Fabric ek naya "shadow tree" commit karta hai jisme layout changes calculate hoti hain (Yoga layout engine se) native side pe, bina JS thread ko block kiye.

Reanimated ke entering, exiting, aur layout props isi commit lifecycle ke saath hook karte hain: jab Fabric detect karta hai ki ek component tree mein add ho raha hai, remove ho raha hai, ya uska layout (position/size) change ho raha hai, Reanimated ko ek callback milta hai before aur after values ke saath (purani position/size vs nayi), aur phir Reanimated in dono ke beech native thread pe ek transition animate kar deta hai — bina JS ko involve kiye, matlab list reorder ya conditional render bhi smoothly animate ho sakta hai.

LayoutAnimationExample.tsx
import Animated, { FadeIn, FadeOut, Layout } from 'react-native-reanimated'; // pre-built layout animation presets

function ListItem({ id, label }: { id: string; label: string }) {
  return (
    <Animated.View
      entering={FadeIn} {/* mount hote hi Fabric commit ke saath fade-in animate karega, native thread pe */}
      exiting={FadeOut} {/* unmount se pehle Fabric ko ye animation complete hone tak wait karwata hai */}
      layout={Layout.springify()} {/* position/size change (e.g. list reorder) pe spring transition */}
    >
      <Text>{label}</Text> {/* actual content, isse koi lena dena nahi animation logic se */}
    </Animated.View>
  );
}

Limitations jo production mein zaroor test karo:

  • Sab native component types equally support nahi karte — kuch third-party wrapped native views (jaise kuch complex map/video components) layout animations ko honor nahi karte kyunki unka native commit lifecycle Fabric ke expectations se match nahi karta.
  • FlatList/FlashList jaisi virtualized lists ke saath interplay issues hote hain — jab items recycle hote hain (virtualization ki wajah se), unka "identity" Fabric/Reanimated ke liye ambiguous ho sakti hai, isliye entering/exiting animations kabhi kabhi galat item pe fire hoti dikhti hain ya skip ho jaati hain.
  • Nested Animated.View jinke apne independent layout animations hain, ek dusre ke commit timing ko conflict kar sakte hain — deeply nested layout animations ko simple rakho.

Shared element transitions — screens ke beech "flying" element

Polished apps (jaise Instagram profile photo tap karne pe full-screen jaana, ya product list se product detail pe jaana) mein aksar ek element visually ek screen se dusre screen mein "fly" karta hua dikhta hai navigation ke dauraan — isse shared element transition kehte hain. Concept simple lagta hai: same element dono screens pe render ho, aur transition ke dauraan uske position/size ko interpolate karo.

Practically iske do approaches hain: dedicated library react-native-shared-element (jo native side pe screenshot/snapshot technique use karta hai transition ke dauraan), ya Reanimated-based manual approach jahan aap khud dono screens ke element ki measurements (measure()) track karke ek shared useSharedValue-driven animation drive karte ho jo navigation transition ke saath sync chale.

🧠 Senior Dev Note — ye genuinely hard kyun hai

Problem ye hai ki shared element transition ke liye aapko do alag screens (jo apne apne independent render/measure lifecycle pe hain, aur navigation library ka apna transition timing hai) ke beech coordination chahiye — screen A ka element unmount ho raha hai jabki screen B ka element mount ho raha hai, aur in dono ke measurements (position, size on screen) transition ke exact start/end frame pe accurately known hone chahiye. Timing thodi bhi off ho (jaise ek screen ka layout measure late aaya) to "jump" ya "flicker" dikhta hai. Yahi wajah hai ki production apps mein shared element transitions aksar buggy feel hoti hain edge cases mein (fast back-and-forth navigation, orientation change ke dauraan) — ye ek genuinely hard cross-screen synchronization problem hai, sirf ek animation prop laga dena kaafi nahi hota.

Gesture composition deep-dive — old imperative props vs naya declarative Gesture API

Purane PanGestureHandler/TapGestureHandler component-based API mein multiple gestures ko compose karne ke liye simultaneousHandlers aur waitFor props use hote the — jinme aapko har handler ko ek ref assign karke, dusre handler ki ref ko in props mein pass karna padta tha:

old-imperative-composition.tsx
const panRef = useRef(null); // pan handler ka ref — isko dusre handler mein reference karna padega
const pinchRef = useRef(null); // pinch handler ka ref — same reason

// Ye legacy component-based API hai — ab officially "legacy" consider hoti hai
<PinchGestureHandler ref={pinchRef} simultaneousHandlers={panRef}> {/* imperative: ref ke through dusre handler ko point karna */}
  <PanGestureHandler ref={panRef} simultaneousHandlers={pinchRef}> {/* dono taraf refs pass karne padte the — error-prone */}
    <Animated.View /> {/* actual animatable content, do handlers ke beech nested */}
  </PanGestureHandler>
</PinchGestureHandler>

Is approach mein problem: refs manually manage karna padta hai, dono directions mein wire karna padta hai (bhool jaane pe silent bug), aur nesting deep ho jaane pe (3+ gestures) ye combinatorially messy ho jaata hai — kaunsa handler kis dusre ke saath simultaneous hai, ye trace karna mushkil ho jaata hai.

Naya Gesture API isko declarative composition functions se solve karta hai — koi refs nahi, seedha gesture objects ko compose karo:

new-declarative-composition.tsx
const pan = Gesture.Pan() // pan gesture object bana rahe hain
  .onUpdate((e) => { // jab finger move ho
    'worklet'; // UI thread pe run hoga
    translateX.value = e.translationX; // pan se translation apply
    translateY.value = e.translationY; // dono axes update
  });

const pinch = Gesture.Pinch() // pinch gesture object bana rahe hain
  .onUpdate((e) => { // jab do fingers zoom karein
    'worklet'; // UI thread pe run hoga
    scale.value = e.scale; // pinch scale factor apply
  });

// Gesture.Simultaneous: dono gestures ek saath active reh sakte hain — koi ref, koi manual wiring nahi
const composed = Gesture.Simultaneous(pan, pinch);

return (
  <GestureDetector gesture={composed}> {/* single detector, composed gesture pass kiya */}
    <Animated.View style={animatedStyle} /> {/* pan aur pinch dono ka combined effect yahan apply hoga */}
  </GestureDetector>
);

Available composition functions: Gesture.Simultaneous(...) (sab ek saath active), Gesture.Race(...) (jo pehle recognize ho jaaye wahi win kare, baaki cancel — jaise tap vs long-press disambiguation), aur Gesture.Exclusive(...) (priority order — pehla try hota hai, fail hone pe agla).

🧠 Senior Dev Note

Naya Gesture API maintainable isliye hai kyunki composition data ke through express hoti hai (gesture objects ko compose karke ek naya gesture object banta hai) na ki imperative side-channel refs ke through. Isse code review mein bhi clearly dikhta hai ki kaunse gestures related hain, aur complex multi-gesture interactions (jaise photo viewer mein pinch-to-zoom + pan + double-tap-to-reset, teeno ek saath) likhna aur debug karna kaafi simpler ho jaata hai — ek common senior interview question bhi yahi hai: "pinch-to-zoom ke saath pan simultaneously kaise implement karoge" — answer Gesture.Simultaneous() hona chahiye, refs-based legacy approach nahi.

9. 🎯 Interview Questions — Senior React Native Developer

Ye section un questions ko cover karta hai jo senior/staff-level RN interviews mein animations aur gestures ke topic pe commonly puchhe jaate hain — internals, trade-offs, debugging approach, aur "why" wale questions.

1. Ek worklet actually runtime pe kya hai? Kya ye ek normal JS function hi hai?

Nahi, ye ek regular JS function nahi hai jahan tak runtime behavior ka sawaal hai — although source code mein ye ek normal function jaisa hi dikhta hai. Compile time pe Babel plugin isko static analysis se identify karta hai ('worklet' directive, ya kisi worklet-izing hook ke andar hone ki wajah se), function ko source string + captured closure mein serialize karta hai, aur runtime pe UI thread pe chal rahe ek separate JS runtime instance mein re-construct karta hai. Matlab ek hi function ke effectively do copies exist karte hain — ek JS thread ke normal runtime mein (agar wahan se bhi call ho raha ho), ek UI thread ke worklet runtime mein — aur ye dono independent hain, closures share nahi karte live reference se, sirf serialized snapshot share karte hain.

2. Aap kab abhi bhi purana Animated API use karoge, Reanimated ki jagah?

Kuch legitimate cases hain: (1) Bahut simple, one-off animations jaha performance-critical gesture-driven interaction nahi hai — jaise ek modal ka simple fade-in jo useNativeDriver: true ke saath already smooth hai, wahan Reanimated add karna extra dependency/complexity ho sakta hai bina real benefit ke. (2) Legacy codebase jaha already Animated API se heavily invested code hai aur migration cost/risk immediate benefit se zyada hai. (3) Kuch bahut chhote libraries/components jo sirf ek simple animated value expose karte hain aur Reanimated install karna unnecessary overhead lagta hai project size ke hisaab se. Lekin koi bhi gesture-driven ya complex/chained animation ke liye Reanimated hi default choice honi chahiye — ye trade-off samajhna, na ki blindly ek tool choose karna, senior thinking dikhata hai.

3. Ek animation sirf Android pe frames drop kar rahi hai, iOS pe nahi — diagnostic approach kya hoga?

Systematic approach: (1) Pehle confirm karo ki animation truly UI thread pe chal rahi hai — useAnimatedStyle ke andar koi non-shared-value (regular state/prop) to nahi use ho raha jo silently JS thread sync force kar raha ho. (2) Android-specific overdraw check karo — agar view hierarchy deep hai ya complex shadows/elevation use ho rahe hain, Android ka rendering pipeline (especially older devices, software rendering fallback) iOS se zyada expensive ho sakta hai same visual ke liye. (3) Hermes bytecode/JIT differences check karo — kabhi kabhi Android pe Hermes configuration (bytecode precompilation on/off) different hoti hai jo cold-start pe pehle few frames slow kar sakti hai. (4) Flipper/Android Studio Profiler se actual native-side frame timing dekho — confirm karo ki bottleneck UI thread (worklet execution) mein hai ya native rendering (Android's View hierarchy measure/layout/draw) mein hai — dono ka fix alag hoga. (5) Check karo ki koi heavy synchronous native module call (jaise bridge-based legacy native module) us gesture/animation ke saath overlap to nahi ho raha.

4. setState ko directly worklet ke andar call kyun nahi kar sakte? runOnJS actually kya kar raha hai?

setState (aur uska setter function) React ke JS thread runtime mein define hota hai — worklet ke UI thread runtime mein wo function exist hi nahi karta (serialize/re-create process sirf worklets ke liye hota hai, arbitrary React internals ke liye nahi). Agar aap directly call karne ki koshish karoge, ya to build-time error milega (agar Babel plugin detect kar paaye) ya runtime pe "function is not defined" jaisi error. runOnJS(fn) actually karta hai ye: UI thread se ek message JSI ke through JS thread ko schedule karta hai ("is function ko is argument ke saath JS thread pe call karo"), JS thread apni normal event loop mein us call ko process karta hai — jahan setState jaise React APIs safely accessible hain kyunki hum wapas JS thread ke context mein hain. Ye ek explicit, lightweight one-way hop hai (JSI ke through, bridge jaisa heavy serialization nahi), lekin phir bhi ek async scheduling step hai — isliye ise per-frame use karna avoid karna chahiye.

5. Fabric ke New Architecture mein aane se pehle vs baad mein, Reanimated ka behavior kaise different tha?

Old architecture (Bridge-based) mein bhi Reanimated 2/3 JSI ka use kar leta tha worklets ke liye (JSI old architecture mein bhi available tha, sirf components ka rendering pipeline bridge-based tha) — matlab worklets already UI thread pe chal rahe the even bina Fabric ke. Fabric specifically layout animations (entering/exiting/layout) ke liye important hai kyunki inko component ke mount/unmount/layout-change ka accurate native-side signal chahiye hota hai jo Fabric ke commit lifecycle se milta hai — old architecture mein layout animations ka support limited/hacky tha. General shared-value animations aur gesture-driven interactions Fabric se pehle bhi kaafi had tak UI-thread-native the.

6. useSharedValue aur useState mein fundamental difference kya hai — sirf "re-render trigger nahi karta" ke alawa?

Storage location bhi different hai — useState ki value JS thread ke React fiber mein store hoti hai, jabki useSharedValue ki value ek native/UI-thread-accessible memory location mein store hoti hai jo JSI ke through dono runtimes se readable/writable hai. Isliye useSharedValue.value ko UI thread pe worklet ke andar read/write karna synchronous aur zero-overhead hai, jabki agar aap useState ki value ko kisi tarah UI thread pe use karna chahte (jo directly possible nahi hai), wo ek cross-thread sync operation hoga. Dusra difference: useSharedValue mutation React's render cycle se completely bypass hoti hai — koi reconciliation, koi diffing — jabki useState ka har update poore React reconciliation pipeline se guzarta hai.

7. Gesture Handler v2 mein GestureDetector sirf ek child accept karta hai — is design constraint ka reasoning kya hai?

Ye constraint isliye hai kyunki GestureDetector apne single child ke underlying native view (native host component) ko directly gesture recognizer se attach karta hai — native gesture recognition (UIGestureRecognizer-jaisa concept) ek specific view instance pe register hota hai, multiple views pe ek saath ambiguous hota. Agar multiple elements pe gesture chahiye, unko ek common parent View mein wrap karke us parent ko single child banao, ya multiple GestureDetectors use karo (nested ya sibling) with composed gestures jahan zaroorat ho.

8. withTiming vs withSpring — kab kaunsa choose karoge, aur inke completion callback ka behavior kya hai?

withTiming deterministic duration ke saath chalta hai — use karo jab exact timing predictable honi chahiye (jaise ek fixed 200ms fade transition jo kisi dusre timed event, jaise navigation, ke saath sync honi hai). withSpring physics-simulated hai (mass/damping/stiffness parameters) — use karo jaha organic, "alive" feel chahiye (jaise drag-release ke baad snap-back, jahan exact duration matter nahi karta, natural deceleration curve matter karta hai). Dono ka teesra argument ek optional completion callback hai jo khud bhi ek worklet context mein invoke hota hai (UI thread pe) — isliye uske andar se agar JS-side effect chalana hai (state update, analytics, navigation), wahan bhi runOnJS zaroori hai, jaisa humne swipe-to-delete example mein dekha tha.

9. Ek nested ScrollView ke andar ek horizontal Pan gesture properly work nahi kar raha — konsa concept isse related hai, aur fix kaise karoge?

Ye classic gesture conflict / responder clash scenario hai — parent ScrollView (jo khud ek vertical pan gesture handle kar raha hai internally) aur child ka custom horizontal Gesture.Pan() dono touch events claim karne ki koshish karte hain. Fix approach: (1) Gesture.Pan().activeOffsetX([-10, 10]) jaisa "activation offset" set karo taaki gesture sirf tab activate ho jab horizontal movement ek threshold cross kare — isse vertical scroll intent clash nahi karta. (2) Agar dono simultaneously chalne chahiye (rare case), Gesture.Simultaneous() use karo. (3) Agar priority based behavior chahiye (pehle scroll try ho, fail hone pe pan), Gesture.Race() ya simultaneousWithExternalGesture() API use karo jo ScrollView ke internal native gesture ko reference kar sake. Ye samajhna ki gesture "activation" aur "recognition" alag concepts hain (activate hone se pehle offset thresholds check hote hain) senior-level gesture debugging ka core hai.

10. Reanimated worklets memory/GC ke perspective se kya consideration create karte hain?

Kyunki closures serialize hoke UI runtime pe copy hoti hain, agar worklet ke closure mein galti se ek bada object (jaise poori list ka data, ya ek large image buffer reference) capture ho jaaye jab sirf ek chhota primitive chahiye tha, to har worklet re-creation/re-registration pe wo poora closure duplicate/retain hota hai UI runtime ki memory mein bhi — do runtimes mein effectively do copies. Best practice: worklets ke closures ko minimal rakho — sirf jo shared values/primitives chahiye unhi ko reference karo, poore objects/props ko blindly capture mat karo. Ye especially list ke andar bahut saare items ke liye worklets banate waqt (jaise FlatList ke har row mein ek gesture) matter karta hai, jaha closures multiply ho jaate hain item count ke saath.
