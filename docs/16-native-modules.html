Kab Actually Native Module Chahiye

Chapter 1 mein humne JSI ka mental model banaya tha — JSI (JavaScript Interface) ek C++ layer hai jo JS engine (Hermes) ko native C++ objects ke saath directly, synchronously bind karta hai, aur TurboModules is JSI foundation ke upar native modules ko lazy-load karne ka mechanism dete hain. Jab hum "native module likhna" bolte hain, hum literally ek naya TurboModule bana rahe hote hain — koi native (Swift/Kotlin) capability jo JS side se ek clean, typed function call jaisi dikhti hai, lekin under the hood JSI ke through directly native code ko hit karti hai, bina Bridge ke purane JSON-serialization overhead ke.

Ab sabse important senior-level question — kab aapko khud native module likhna chahiye? Ye answer bahut clear hona chahiye kyunki galat decision (bahut jaldi native module likhna) unnecessary maintenance burden create karta hai jo aage is chapter mein hum dekhenge. Sahi decision tree ye hai:

SituationSahi approach
Capability already Expo SDK mein hai (camera, location, notifications, file system, etc.) Use karo directly — expo-camera, expo-location, wagera. Khud likhne ki zaroorat hi nahi.
Capability Expo SDK mein nahi hai, lekin npm pe koi maintained community package already available hai (jaise react-native-mmkv, react-native-vision-camera) Us package ko use karo. Kisi aur ne already ye native code likh, test aur maintain kiya hai — reinvent mat karo.
Capability ek niche hardware SDK, proprietary company SDK, ya bahut specific native API hai jiska koi RN/Expo wrapper exist hi nahi karta (jaise: company ka apna Bluetooth POS device SDK, ek internal biometric hardware ka native SDK, ya ek bahut specific OS-level API jo abhi tak kisi ne wrap nahi ki) Yahi genuine case hai jab aap khud native module likhoge. Ye is chapter ka focus hai.
🧠 Senior Dev Note

Native module likhna last resort hona chahiye, first instinct nahi. Har baar jab aapko lage "iske liye native code likhna padega", pehle npm pe 10 minute search karo (aur Expo SDK docs check karo) — kyunki har native module jo aap khud likhte ho, wo ek maintenance liability bhi ban jaata hai jo aapko har Xcode/Android Gradle update, har Expo SDK major upgrade ke saath khud maintain karni padegi (is chapter ke end mein "Gotchas" section mein isko detail se dekhenge). Ek community-maintained package use karna almost hamesha cheaper hai long-term mein — kisi aur ki team us maintenance cost ko already bear kar rahi hai.

Ek concrete example: agar aapko battery level chahiye, pehle check karo — kya expo-battery already exist karta hai? (Haan, karta hai). Is chapter mein hum jaan-boojh kar ek thoda deeper example use karenge jahan hume ek raw native API (device build fingerprint) chahiye jiske liye Expo SDK mein koi direct wrapper nahi hai — taaki example genuinely meaningful ho, sirf ek already-solved problem ko dobara solve na karein.

Expo Modules API — Modern Approach Kyun

Pehle samjhte hain purana tareeka native module likhne ka, taaki aapko pata chale Expo Modules API actually kitna time bacha raha hai. Raw TurboModule likhne ke liye aapko ye sab manually karna padta tha:

  • Ek Codegen spec file (TypeScript interface jisse Codegen tool C++ glue code generate karta hai) hand-write karna, with bahut strict typing rules.
  • babel.config.js, metro.config.js, aur native build files (Podfile, build.gradle) mein manual codegen wiring setup karna.
  • Native side pe raw C++/Objective-C++ (iOS) aur C++/Java (Android) boilerplate likhna jo JSI HostObject ko manually implement karta hai.
  • Auto-linking ke liye react-native.config.js jaisi files manually configure karna.

Ye poora process verbose, error-prone, aur frankly bahut senior React Native engineers ke liye bhi intimidating tha — kyunki isme C++ aur JSI internals ka deep knowledge chahiye hota tha, sirf ek simple function expose karne ke liye bhi.

Expo Modules API ne is poore complexity ko ek clean Swift/Kotlin-first DSL (Domain-Specific Language) ke peeche abstract kar diya. Aap ek high-level, declarative ModuleDefinition likhte ho Swift ya Kotlin mein — aur Expo Modules API background mein automatically saara JSI/TurboModule boilerplate, Codegen wiring, aur auto-linking generate kar deta hai. Aapko kabhi C++ nahi likhna padta, kabhi manually Codegen spec files nahi banani padti.

ℹ️ Important — ye sirf "Expo apps" ke liye nahi hai

Ek common misconception hai ki Expo Modules API sirf Expo-managed projects mein kaam karta hai. Ye galat hai — Expo Modules API ek standalone native-module-authoring framework hai jo bare React Native projects mein bhi equally kaam karta hai (Expo install kiye bina bhi). Isi wajah se Expo team ne npx create-expo-module ko har naye native module ke liye industry-recommended default bana diya hai, chahe aapka target project Expo-based ho ya pure bare RN CLI ho.

AspectRaw TurboModule (old way)Expo Modules API (modern way)
Spec/interface definition Manual Codegen TypeScript spec file, strict syntax rules Koi separate spec file nahi — Swift/Kotlin DSL khud hi type-safe interface define karta hai
Native implementation language C++/Objective-C++ (iOS), C++/Java (Android) — low-level Swift (iOS), Kotlin (Android) — modern, high-level, DSL-based
JSI/TurboModule glue code Aapko khud samajhna aur likhna padta tha Fully auto-generated, invisible to the author
Auto-linking setup Manual config files Automatic via expo-module.config.json
Works in bare RN (non-Expo) projects? Yes (it's the RN-native way) Yes — npx create-expo-module generates a package usable anywhere

Native Module Banana — Full Example

Hum ek real, useful module banayenge: device ka build fingerprint nikalna — ek unique string jo device ke exact OS build ko identify karta hai (iOS pe UIDevice ka combination, Android pe Build.FINGERPRINT). Ye deliberately aisa example hai jiske liye Expo SDK mein koi ready-made wrapper nahi hai, isliye ye genuinely dikhata hai ki native module kab likhna sensible hai.

Step 1 — Scaffold karna

Sabse pehla step hamesha same command hai — create-expo-module CLI ek poora working module skeleton generate kar deta hai, dono platforms (Swift + Kotlin) ke liye, TypeScript wrapper ke saath.

terminal
# Local module banane ke liye — apne existing Expo/RN project ke andar hi ye chalao
npx create-expo-module@latest --local device-fingerprint

# --local flag ka matlab: module "modules/device-fingerprint" folder mein banega, npm pe publish nahi hoga abhi
# CLI aapse module name, package name (iOS bundle-style) aur short description poochega

Is command ke baad generated folder structure kuch aisi dikhti hai — har file ka role samajhna zaroori hai, kyunki aage hum inhi files ko edit karenge:

Step 2 — expo-module.config.json samajhna

Ye file autolinking ka "map" hai — Expo CLI prebuild ke time is file ko padh kar samajhta hai ki iOS aur Android native project mein kya link karna hai. JSON comments support nahi karta, isliye neeche "teaching comments" style mein annotate kiya hai (jaise agar JS/JSON5 comments allowed hote) — real file mein ye comments nahi honge.

modules/device-fingerprint/expo-module.config.json (teaching-annotated, real JSON mein comments nahi hote)
{
  // "platforms": batata hai ye module kaunse platforms support karta hai — Expo CLI sirf inhi platforms ke liye linking try karega
  "platforms": ["ios", "android"],
  // "ios" object — iOS-specific linking config
  "ios": {
    // "modules" array — kaunsi Swift class(es) ko native module ke roop mein register karna hai
    "modules": ["DeviceFingerprintModule"]
  },
  // "android" object — Android-specific linking config
  "android": {
    // "modules" array — kaunsi Kotlin class ka fully-qualified name register karna hai
    "modules": ["expo.modules.devicefingerprint.DeviceFingerprintModule"]
  }
}

Step 3 — Swift implementation (iOS)

Ab asli implementation. ModuleDefinition DSL ek Swift builder-pattern hai jisme aap declaratively bolte ho "ye module ka naam hai, ye function hai jo ye karta hai" — aur Expo Modules API background mein JSI binding generate kar deta hai. Har line commented hai neeche.

ios/DeviceFingerprintModule.swift
// ExpoModulesCore import karna zaroori hai — ye ModuleDefinition, Module base class, Function() DSL, wagera provide karta hai
import ExpoModulesCore

// Har Expo native module ek class hai jo Module base class ko extend karti hai — ye Expo Modules API ka required contract hai
public class DeviceFingerprintModule: Module {
  // "definition" property override karna required hai — yahi wo jagah hai jaha module ka poora public surface declare hota hai
  public func definition() -> ModuleDefinition {
    // Name(...) — JS side se is naam se module access hota hai (requireNativeModule("DeviceFingerprint"))
    Name("DeviceFingerprint")

    // Function(...) — ek synchronous function expose karta hai jo JS se seedha, bina Promise ke, call ho sakta hai (JSI ki wajah se sync possible hai)
    Function("getBuildFingerprint") in
      // UIDevice.current — iOS ka system API jo current device ki info deta hai
      let systemName = UIDevice.current.systemName
      // systemVersion — jaise "17.4" — iOS version string
      let systemVersion = UIDevice.current.systemVersion
      // identifierForVendor — app-vendor-scoped unique device identifier (Apple ki privacy-safe alternative to old UDID)
      let vendorId = UIDevice.current.identifierForVendor?.uuidString ?? "unknown"
      // Sab pieces ko ek single fingerprint string mein combine karke return karna — ye value JS ko as-is milegi
      return "\(systemName)-\(systemVersion)-\(vendorId)"


    // AsyncFunction(...) — jab native operation genuinely async ho (jaise disk/network I/O), Promise-returning function expose karte hain
    AsyncFunction("getBuildFingerprintAsync") { (promise: Promise) in
      // DispatchQueue.global — background thread pe kaam karna, taaki main/UI thread block na ho
      DispatchQueue.global(qos: .userInitiated).async {
        // Same fingerprint logic, ab background thread ke andar (demonstrate karne ke liye ki AsyncFunction thread-safe pattern kaisa dikhta hai)
        let fingerprint = "\(UIDevice.current.systemName)-\(UIDevice.current.systemVersion)"
        // promise.resolve — JS side Promise ko successfully resolve karta hai is value ke saath
        promise.resolve(fingerprint)
      }
    }
  }
}
💡 Sharad ke liye Swift quick-notes

Agar Swift naya lag raha hai: let ek immutable variable declare karta hai (JS ke const jaisa), ?? "unknown" nil-coalescing operator hai (JS ke ?? jaisa hi behave karta hai), aur \(...) string interpolation syntax hai (JS ke template literal ${...} ka Swift equivalent). Trailing closure syntax ({ (promise) in ... }) JS ke arrow function jaisa hi ek callback-passing pattern hai.

Step 4 — Kotlin implementation (Android)

Same DSL concept, Kotlin mein. Notice karo structure Swift jaisa hi hai — Name(), Function(), AsyncFunction() — ye Expo Modules API ka jaan-boojh kar symmetric design hai, taaki dono platforms ka code mentally map ho sake.

android/.../DeviceFingerprintModule.kt
// Package declaration — Kotlin/Java convention, expo-module.config.json mein diya gaya fully-qualified name isi se match karna chahiye
package expo.modules.devicefingerprint

// android.os.Build — Android system class jisme device/OS build info static fields ke roop mein milti hai
import android.os.Build
// Expo Modules Kotlin API ka core Module base class
import expo.modules.kotlin.modules.Module
// ModuleDefinition builder DSL — Swift ke ModuleDefinition ka Kotlin equivalent
import expo.modules.kotlin.modules.ModuleDefinition

// Class Module ko extend karti hai — Expo Modules API ka required contract, Swift wale pattern jaisa hi
class DeviceFingerprintModule : Module() {
  // definition() override karna required hai — yahan module ka poora public API declare hota hai
  override fun definition() = ModuleDefinition {
    // Name(...) — JS side isi naam se module access karega, iOS wale Name() se match hona chahiye
    Name("DeviceFingerprint")

    // Function(...) — synchronous native function, JSI ke through direct call hota hai
    Function("getBuildFingerprint") {
      // Build.FINGERPRINT — Android ka apna unique build identifier string (manufacturer/product/device/version sab encode karta hai)
      val fingerprint = Build.FINGERPRINT
      // Build.MODEL — device ka model name, jaise "Pixel 8"
      val model = Build.MODEL
      // Sab combine karke return — ye value directly JS side promise/return value banti hai
      "$model-$fingerprint"
    }

    // AsyncFunction(...) — Kotlin coroutines ke through background execution, Promise JS ko automatically wire ho jaata hai
    AsyncFunction("getBuildFingerprintAsync") { promise: expo.modules.kotlin.Promise ->
      // Yahan bhi same fingerprint logic — real app mein ye kisi slow I/O call ki jagah hoti (jaise disk read)
      val fingerprint = "${Build.MODEL}-${Build.FINGERPRINT}"
      // promise.resolve — JS Promise ko is value ke saath resolve karta hai
      promise.resolve(fingerprint)
    }
  }
}
💡 Sharad ke liye Kotlin quick-notes

val Kotlin ka immutable variable keyword hai (Swift ke let, JS ke const jaisa). "$model-$fingerprint" string template hai (JS ke ${...} jaisa, bas $ ke baad seedha variable name likhte ho braces ke bina agar simple expression ho). Trailing lambda syntax ({ promise -> ... }) JS ke arrow function jaisa hi ek concept hai.

Step 5 — TypeScript wrapper

Ye woh file hai jo actually JS side se import hoti hai — requireNativeModule Expo Modules API ka function hai jo native side pe registered module ko naam se dhoondh kar JS proxy object return karta hai, jispe humare Swift/Kotlin Function() calls automatically methods ban jaate hain.

src/DeviceFingerprintModule.ts
// requireNativeModule — Expo Modules API ka helper jo naam se native module dhoondh kar JS proxy deta hai
import { requireNativeModule } from 'expo-modules-core';

// TypeScript interface — native module ka shape describe karta hai, taaki callers ko autocomplete/type-safety mile
interface DeviceFingerprintModuleType {
  // Synchronous function signature — Swift/Kotlin ke Function() se match hona chahiye
  getBuildFingerprint(): string;
  // Async function signature — Promise return karta hai, Swift/Kotlin ke AsyncFunction() se match
  getBuildFingerprintAsync(): Promise<string>;
}

// "DeviceFingerprint" string yahan wahi naam hona chahiye jo Swift/Kotlin ke Name() mein diya gaya tha — ye link banata hai JS aur native ke beech
export default requireNativeModule<DeviceFingerprintModuleType>('DeviceFingerprint');
modules/device-fingerprint/index.ts
// Package ke root se saara implementation re-export karna — consumers "modules/device-fingerprint" se hi import karenge
export { default } from './src/DeviceFingerprintModule';

Ab app code mein use karna bilkul normal JS import jaisa simple hai:

app/(tabs)/settings.tsx
// Apne local module se default export import karna — jaise koi bhi normal npm package import karte ho
import DeviceFingerprint from '../../modules/device-fingerprint';

// Synchronous call — JSI ki wajah se ye seedha, instantly, bina await ke return hota hai
const fingerprint = DeviceFingerprint.getBuildFingerprint();
// Result ko console pe print karna, debugging ke liye
console.log('Device fingerprint:', fingerprint);
⚠️ Expo Go mein nahi chalega

Ye code Expo Go mein kaam nahi karega — custom native module hai to aapko Development Build chahiye hi hoga (Chapter 1 mein dekha gaya trade-off yahan directly apply hota hai). npx expo prebuild chalao (ya eas build --profile development) taaki native code compile ho aur module link ho.

Native View Banana — Full Example

Ab tak humne sirf functions expose kiye — call karo, result milta hai. Lekin kabhi kabhi aapko ek poori native UI surface expose karni hoti hai — jaise ek native map view, ek camera preview surface, ya koi complex native rendering jise React ke declarative component model mein use karna ho. Iske liye Expo Modules API ka View DSL hai.

Concept simple hai: Swift side pe aap ek ExpoView subclass banate ho jo asal native UIView wrap karta hai, uske props declare karte ho, aur Expo Modules API automatically ek React Native "host component" bana deta hai jise JS side requireNativeViewManager se access karta hai. Hum yahan ek simplified native color-preview surface banayenge — concept dikhane ke liye ki native UIView/View kaise ek prop lekar khud ko render karta hai (real app mein ye ek map SDK ka camera view, ya kisi proprietary SDK ka rendering surface hota).

Swift — ExpoView subclass

ios/ColorSurfaceView.swift
// ExpoModulesCore import — ExpoView base class aur prop-related helpers isi se milte hain
import ExpoModulesCore

// ExpoView ko extend karna — ye Expo Modules API ka base class hai jo native view ko RN host component banane deta hai
class ColorSurfaceView: ExpoView {
  // Actual UIKit view jo hum wrap kar rahe hain — real case mein ye kisi SDK ka camera/map view hota
  let innerView = UIView()

  // Required initializer — appContext ExpoView ko chahiye hota hai module registry access karne ke liye
  required init(appContext: AppContext? = nil) {
    // Parent initializer call karna mandatory hai Swift mein subclass banate waqt
    super.init(appContext: appContext)
    // innerView ko is wrapper view ke andar add karna — taaki wo actual visible content ho
    addSubview(innerView)
  }

  // layoutSubviews — UIKit lifecycle method, jab bhi parent ka size/layout change ho, ye call hota hai
  override func layoutSubviews() {
    // super call karna zaroori hai default UIKit layout behavior preserve karne ke liye
    super.layoutSubviews()
    // innerView ko poore parent bounds tak stretch karna — taaki color surface full width/height le
    innerView.frame = bounds
  }

  // setColor — ye function JS se aane wale "color" prop ko receive karega aur native view update karega
  func setColor(_ hex: String) {
    // UIColor(hex:) — ek custom extension hoti (yahan simplify kiya) jo hex string ko UIColor mein convert karti
    innerView.backgroundColor = UIColor(hex: hex)
  }
}

Swift — module definition mein View register karna

ios/ColorSurfaceModule.swift
// ExpoModulesCore import — View() DSL yahi se milta hai
import ExpoModulesCore

// Module class jo is native view ko host karta hai
public class ColorSurfaceModule: Module {
  public func definition() -> ModuleDefinition {
    // Name — JS side requireNativeViewManager isi naam se view dhoondhega
    Name("ColorSurfaceView")

    // View(...) — batata hai ki ye module ek native view export karta hai, ColorSurfaceView.self class reference hai
    View(ColorSurfaceView.self) {
      // Prop(...) — "color" naam ka prop declare karna, jab JS se ye prop change ho, closure call hota hai with new value
      Prop("color") { (view: ColorSurfaceView, color: String) in
        // View ke setColor method ko call karke actual native update trigger karna
        view.setColor(color)
      }
    }
  }
}

Kotlin — equivalent Android implementation

android/.../ColorSurfaceView.kt
// Package declaration, config.json ke android.modules path se match karna chahiye
package expo.modules.colorsurface

// Android Context — har View ko chahiye hota hai construct hone ke liye
import android.content.Context
// android.view.View — base Android View class jo hum wrap/extend kar rahe hain
import android.view.View
// Color parsing helper class
import android.graphics.Color
// ExpoView — Expo Modules Kotlin API ka base class jo native view ko RN host component banane deta hai
import expo.modules.kotlin.views.ExpoView
// AppContext — module registry aur lifecycle access dene wala Expo context object
import expo.modules.kotlin.AppContext

// ExpoView subclass — constructor mein context aur appContext dono chahiye hote hain
class ColorSurfaceView(context: Context, appContext: AppContext) : ExpoView(context, appContext) {
  // Actual wrapped Android View — real case mein ye kisi SDK ka camera/map SurfaceView hota
  private val innerView = View(context)

  // init block — Kotlin class ka constructor body jaisa, class create hote hi chalta hai
  init {
    // innerView ko is wrapper ke andar add karna
    addView(innerView)
  }

  // setColor — JS se aane wale "color" prop ko yahi function receive karega
  fun setColor(hex: String) {
    // Color.parseColor — hex string (jaise "#FF0000") ko Android Color int mein convert karta hai
    innerView.setBackgroundColor(Color.parseColor(hex))
  }

  // onLayout override — Android View lifecycle method, layout pass hone pe call hota hai
  override fun onLayout(changed: Boolean, left: Int, top: Int, right: Int, bottom: Int) {
    // innerView ko poore parent bounds tak stretch karna, layout params ke through
    innerView.layout(0, 0, right - left, bottom - top)
  }
}

TypeScript wrapper — requireNativeViewManager

Function-based module se difference yahan ye hai — hume requireNativeViewManager chahiye (function ke liye jo requireNativeModule tha), aur result ek React component hota hai, na ki ek plain object.

src/ColorSurfaceView.tsx
// requireNativeViewManager — native View() ko React component ke roop mein load karne wala Expo helper
import { requireNativeViewManager } from 'expo-modules-core';
// React ki type import, sirf typing ke liye chahiye
import type { ViewProps } from 'react-native';

// Props interface — standard RN ViewProps extend karta hai plus humara custom "color" prop
interface ColorSurfaceViewProps extends ViewProps {
  // color prop — Swift/Kotlin ke Prop("color") se match hona chahiye
  color: string;
}

// requireNativeViewManager("ColorSurfaceView") — "ColorSurfaceView" wahi Name() hai jo Swift/Kotlin mein register kiya tha
const NativeColorSurfaceView = requireNativeViewManager<ColorSurfaceViewProps>('ColorSurfaceView');

// Export ek typed React component ke roop mein — consumers ko lagega ye ek normal RN component hai
export default function ColorSurfaceView(props: ColorSurfaceViewProps) {
  // Directly native view ko render karna, props ko pass-through karte hue
  return <NativeColorSurfaceView {...props} />;
}
app/(tabs)/preview.tsx
// Native view component ko normal RN component ki tarah import karna
import ColorSurfaceView from '../../modules/color-surface/src/ColorSurfaceView';

// JSX mein use karna — bilkul  jaisa dikhta hai, lekin backing implementation fully native hai

🧠 Senior Dev Note

Native views ka real-world use case almost hamesha "koi native rendering surface jo React's declarative view tree ke andar exist karni chahiye" hota hai — Apple/Google Maps SDK views, camera preview surfaces, video player surfaces, ya kisi proprietary SDK ka rendering canvas. Agar aapko sirf ek value chahiye (jaise humara battery/fingerprint example), Function() hi kaafi hai — View() tabhi reach karo jab genuinely ek visual native surface expose karni ho.

Native Modules Next Steps — Distribution aur Config Plugins

Packaging for reuse

Ek local module (--local flag se banaya gaya, jo modules/ folder mein rehta hai) sirf ek project ke liye theek hai. Agar aapko ye module multiple projects/teams ke beech share karna hai, do options hain:

  • Local npm workspace package — agar aapke saare projects ek monorepo (Turborepo/Nx/pnpm workspaces) mein hain, module ko ek workspace package bana do (jaise packages/device-fingerprint) aur usse har app "device-fingerprint": "workspace:*" se consume kare. Ye best option hai agar saare consumers same monorepo mein hain — no publishing overhead, changes turant sab jagah reflect hote hain.
  • Published npm package — agar module ko organization ke bahar ya alag-alag independent repos mein use karna hai, npm publish karo (private registry ya public npm pe). Ab ye exactly wahi tareeka hai jaise koi bhi third-party native module (jaise react-native-mmkv) consume hota hai — npx expo install your-org/device-fingerprint.

Config Plugins — kya aur kyun

Ek subtle problem hai jab custom native code likhte ho: kabhi kabhi aapke native module ko ek native project-level configuration change bhi chahiye hoti hai — jaise iOS Info.plist mein ek permission string add karna (NSCameraUsageDescription jaisa), ya Android AndroidManifest.xml mein ek permission ya intent-filter add karna. Agar aap ye manually ios//android/ folders edit karke karte ho, aap Expo ke poore "no manual native folder editing" workflow ko tod dete ho — kyunki jab bhi koi npx expo prebuild chalayega (native folders regenerate karne ke liye), aapke manual edits overwrite ho jaayenge.

Config Plugin is problem ka solution hai — ye ek JS/TS function hai jo app.config.ts mein register hota hai aur prebuild ke time programmatically generated native project ko modify karta hai. Matlab aap manual edit ki jagah code likhte ho jo har prebuild pe automatically wahi change apply kar deta hai — idempotent aur version-controlled.

modules/device-fingerprint/app.plugin.js
// @expo/config-plugins se helper functions import karna — ye Info.plist/AndroidManifest.xml ko safely modify karne ke tools dete hain

// withDeviceFingerprint — humara custom config plugin function, config object leke modified config return karta hai
function withDeviceFingerprint(config) {
  // withInfoPlist — iOS Info.plist ko modify karne ka wrapper, callback mein plist object milta hai
  config = withInfoPlist(config, (config) => {
    // NSUserTrackingUsageDescription jaisi koi custom permission string yahan add karna, prebuild ke time automatically inject hoga
    config.modResults.NSDeviceFingerprintUsageDescription =
      'App device build info use karta hai support diagnostics ke liye.';
    // Modified config object return karna mandatory hai — mod chain ko is return value pe continue karna hota hai
    return config;
  });

  // withAndroidManifest — same concept, ab AndroidManifest.xml ke liye
  config = withAndroidManifest(config, (config) => {
    // manifest.manifest — parsed XML tree ka root access
    const androidManifest = config.modResults.manifest;
    // Yahan real plugin mein permission tag push karte, jaise  node add karna array mein
    // (simplified rakha gaya hai example ke liye — production plugin mein XML tree manipulation helper functions use hote hain)
    return config;
  });

  // Final modified config return karna — Expo config resolution pipeline isi return value ko aage use karta hai
  return config;
}

Real-World Gotchas

⚠️ Har native change ke baad Development Build rebuild chahiye

JS-only changes hot-reload/Fast Refresh se turant reflect ho jaate hain — lekin native code (Swift/Kotlin/config plugin) mein koi bhi change ke baad, purani development build ab stale/invalid hai. Aapko fresh native build chahiye hi hoga (npx expo run:ios / npx expo run:android, ya eas build --profile development phir se). Ye ek bahut common confusion point hai naye developers ke liye jo "code change kiya, kuch nahi hua" wale symptom se struggle karte hain — root cause hamesha ye hoti hai ki native side rebuild hi nahi hua.

⚠️ Swift aur Kotlin implementations perfectly symmetric nahi honge

Ek senior-level acceptance ye honi chahiye ki iOS aur Android ke underlying platform APIs kabhi exactly same nahi hote — jaise humare example mein iOS identifierForVendor deta hai jabki Android Build.FINGERPRINT ek completely different concept hai. Ye bug nahi hai, ye platform reality hai. Aapka job ye hai ki JS-facing API (function signature, return type) symmetric rahe, lekin under-the-hood implementation platform ke hisaab se divergent ho sakta hai — isko chhupane ki koshish mat karo, documentation mein clearly likho ki dono platforms exactly kya return karte hain.

⚠️ Expo SDK upgrades ke saath custom module versioning

Aapka custom native module ek specific version ke expo-modules-core API ke against likha gaya hai. Jab aap Expo SDK ko major version upgrade karte ho (jaise SDK 51 → SDK 52), expo-modules-core ka underlying API surface change ho sakta hai (naye DSL features add hote hain, kabhi kabhi deprecated patterns remove bhi hote hain). Matlab har major Expo SDK upgrade ke time aapko apne custom native modules ko bhi test/update karna padega — ye ek recurring maintenance task hai jo aapke roadmap mein explicitly plan karna chahiye, "SDK upgrade" sirf package.json version bump nahi hai jab custom native code involved ho.

🔒 Sabse bada point — aap ab native build breakage ke bhi owner ho

Ye is poore chapter ka sabse important takeaway hai: jis din aap ek custom native module likhte ho, aap sirf ek feature nahi bana rahe — aap ek ongoing maintenance commitment le rahe ho. Xcode ka naya version aa sakta hai jo Swift syntax/API deprecate kar de. Android Gradle Plugin ka major upgrade ho sakta hai jo aapki build.gradle config ko incompatible bana de. Apple/Google ka koi naya OS version (iOS 19, Android 16) koi permission model change kar sakta hai jo aapke native code ko directly affect kare. Ye saari cheezein aisi hain jo agar aap ek existing, community-maintained package use kar rahe hote, koi aur team ke liye already solve kar chuki hoti. Isi wajah se chapter ke shuru mein humne bola tha — native module likhna last resort hona chahiye. Agar likhna zaroori hai, to us decision ko team ke saath explicitly document karo: "ye module humne isliye likha kyunki X capability kahin available nahi thi, aur iski maintenance responsibility Y team/person ki hai" — taaki 6 mahine baad jab Xcode update se build toot jaaye, koi confused na ho ki ye code kahan se aaya aur kaun fix karega.

Advanced Deep-Dive — Beyond the Basics

Ab tak humne dekha kaise native module likhte hain. Ab senior-level territory mein jaate hain — internally ye chalta kaise hai, kaha performance/memory ke landmines chhupe hote hain, aur jab production mein cheezein toot jaati hain (crashes, jank, hangs) to root cause tak kaise pahunchna hai. Ye wo knowledge hai jo interview mein bhi poocha jaata hai aur real incidents mein bhi kaam aata hai.

Threading model — kaunse thread pe aapka native code chalta hai

Ye sabse zyada misunderstood cheez hai naye native module authors ke liye. Default behavior samajhna zaroori hai: Expo Modules API mein Function() synchronously JS calling thread pe hi chalta hai — aur JS calling thread almost hamesha JS thread hota hai jisse aapki UI rendering bhi (indirectly, React reconciliation ke through) juri hoti hai. Matlab agar aapke Function() ke andar koi bhi slow, blocking operation hai (jaise ek bada file read, ek heavy CPU computation, ya koi synchronous network call), wo poore JS thread ko block kar dega jab tak wo function return nahi karta — is dauran aapki app ka UI freeze ho jaayega, animations ruk jaayengi, taps respond nahi karenge.

🔒 Danger — synchronous Function() mein heavy kaam mat karo

Agar aap Function("readHugeFile") jaisa kuch likhte ho jo synchronously ek bade file ko disk se poora read karke return kare, to ye call JS thread ko us poore duration ke liye block karega — chahe file 50MB ka ho aur read mein 2 second lage, aapki poori app 2 second ke liye "hung" dikhegi. Ye exactly wo scenario hai jaha aapko AsyncFunction() use karke background thread pe kaam offload karna chahiye.

Solution ye hai ki heavy/slow kaam ko explicitly ek background thread/queue pe offload karo, aur sirf result JS ko Promise ke through wapas do. iOS pe Swift's DispatchQueue.global() is kaam ke liye use hota hai (jo humne pehle bhi AsyncFunction example mein dekha tha), aur Android pe Kotlin coroutines ke saath ek background Dispatcher (jaise Dispatchers.IO) use hota hai. Neeche ek concrete "large file read" example hai jo dikhata hai galat (blocking) aur sahi (offloaded) dono tareeke:

ios/FileReaderModule.swift — sahi tareeka (background offload)
// Foundation import — FileManager aur Data types isi se milte hain, file I/O ke liye zaroori
import Foundation
// ExpoModulesCore import — ModuleDefinition, Function, AsyncFunction, Promise sab yahin se aate hain
import ExpoModulesCore

// Module base class extend karna, Expo Modules API ka standard contract
public class FileReaderModule: Module {
  public func definition() -> ModuleDefinition {
    // Module ka JS-facing naam
    Name("FileReader")

    // ❌ GALAT PATTERN (sirf dikhane ke liye, production mein mat likho): agar ye Function() hota aur seedha yahin synchronously bada file read karta,
    // to Data(contentsOf:) jaisa disk read call JS thread ko block kar deta jab tak file poori na padh li jaaye.

    // ✅ SAHI PATTERN — AsyncFunction se JS thread ko turant free kar dena, actual read background thread pe hoga
    AsyncFunction("readLargeFile") { (path: String, promise: Promise) in
      // DispatchQueue.global(qos: .utility) — ek background dispatch queue jo heavy I/O ke liye designed hai (main/UI thread se alag)
      DispatchQueue.global(qos: .utility).async {
        do {
          // URL(fileURLWithPath:) — string path ko Foundation URL object mein convert karna, file APIs ko yahi chahiye hota hai
          let url = URL(fileURLWithPath: path)
          // Data(contentsOf:) — actual blocking disk read yahan hota hai, lekin ab hum background thread pe hain isliye UI safe hai
          let data = try Data(contentsOf: url)
          // data.count — bytes ki total length, isse hum sirf size return kar rahe hain demonstration ke liye
          let sizeInBytes = data.count
          // promise.resolve — Promise ko resolve karna hamesha wapas kisi bhi thread se safe hota hai, Expo Modules API internally main-thread marshaling handle karta hai JS ko deliver karne ke liye
          promise.resolve(sizeInBytes)
        } catch {
          // Agar file read fail ho (file exist nahi karti, permission issue, etc.), promise.reject se JS side ko proper error milta hai (Promise reject ho jaata hai)
          promise.reject("E_FILE_READ", "File read failed: \(error.localizedDescription)")
        }
      }
    }
  }
}
android/.../FileReaderModule.kt — Kotlin coroutines ke saath background offload
// Package declaration, expo-module.config.json ke fully-qualified name se match hona chahiye
package expo.modules.filereader

// java.io.File — Android/JVM ka standard file-access class
import java.io.File
// Module base class
import expo.modules.kotlin.modules.Module
// ModuleDefinition DSL builder
import expo.modules.kotlin.modules.ModuleDefinition

// Class Module ko extend karti hai — standard Expo Modules API contract
class FileReaderModule : Module() {
  override fun definition() = ModuleDefinition {
    // JS-facing module name
    Name("FileReader")

    // AsyncFunction — Expo Modules Kotlin API internally isse coroutine ke andar, background dispatcher pe run karta hai by default,
    // isliye humein explicitly withContext(Dispatchers.IO) likhne ki zaroorat nahi — lekin senior awareness ke liye pattern yahan spell out kiya gaya hai
    AsyncFunction("readLargeFile") { path: String, promise: expo.modules.kotlin.Promise ->
      try {
        // File(path) — path string se File object banana
        val file = File(path)
        // file.readBytes() — poora file content ek ByteArray mein blocking read karta hai (ye "expensive" operation hai jo hum offload kar rahe hain)
        val bytes = file.readBytes()
        // bytes.size — total byte count, JS ko wapas bhejne ke liye
        val sizeInBytes = bytes.size
        // promise.resolve — JS Promise ko is value ke saath resolve karna
        promise.resolve(sizeInBytes)
      } catch (e: Exception) {
        // promise.reject — error code aur message ke saath JS Promise ko reject karna, taaki caller try/catch mein handle kar sake
        promise.reject("E_FILE_READ", "File read failed: ${e.message}", e)
      }
    }
  }
}
🧠 Senior Dev Note

Interview mein agar koi poochhe "Expo Modules API mein native function kis thread pe run hota hai by default", sahi answer ye hai: Function() synchronous hota hai aur calling JS thread pe hi directly execute hota hai (JSI ki wajah se ye possible hai, bina kisi serialization ke) — isliye ye sirf fast, non-blocking operations ke liye hai. AsyncFunction() apna kaam ek separate execution context mein karta hai (aapka explicit DispatchQueue/coroutine dispatcher) aur sirf final result JS thread ko Promise resolve/reject ke through deliver hota hai — ye hi asli "offloading" hai.

Memory management — JS-native boundary ke dono taraf

Ye ek conceptual awareness hai jo senior engineers se expect ki jaati hai, chahe aap din-pratidin JNI-level memory management na kar rahe ho. Do alag memory models hain jo aapke native module ke through interact karte hain:

PlatformMemory modelNative module author ke liye implication
iOS (Swift) ARC (Automatic Reference Counting) — compiler automatically retain/release calls insert karta hai, developer ko manually memory free nahi karni padti Objects ko JS se/JS ko pass karne mein aam taur pe koi manual memory management nahi chahiye. Lekin retain cycles ka risk hai — agar aapka native module kisi object (jaise ek delegate ya callback closure) ko strongly hold karta hai, aur wo object wapas module ko strongly reference karta hai, dono ek dusre ko zinda rakhte hain forever (memory leak), kyunki ARC ka reference count kabhi zero nahi hota. Common fix: delegate/callback references ko weak banao.
Android (Kotlin/JVM) JVM Garbage Collection — ek background GC thread periodically unused objects detect karke free karta hai Zyadatar cases mein GC sab handle kar leta hai automatically. Lekin agar aap kabhi raw JNI level tak jaate ho (bahut rare, sirf extreme low-level native-C/C++ integration cases mein), wahan JNI references (local/global refs) ko manually manage karna padta hai — ye is chapter ke scope se bahar hai, lekin senior awareness ke liye jaanna zaroori hai ki "agar kabhi JNI tak jaana pade, memory management automatic nahi rahega."
⚠️ Retain cycle ka practical example

Socho aapka native module ek delegate pattern use karta hai — module ek callback handler ko strongly store karta hai, aur wo handler apne closure ke andar module ka reference bhi strongly capture kar leta hai (jaise self ko strong capture karna Swift closure mein). Result: dono objects ka reference count kabhi zero nahi hoga, dono memory mein forever reh jaayenge chahe unhe kahin use na kiya jaa raha ho. Fix: closure mein [weak self] capture list use karo, ya delegate property ko weak var banao.

Synchronous vs async — performance ka rule of thumb

Ye decision har naye function ke liye lena padta hai, aur senior engineers ke liye ye almost muscle-memory hona chahiye:

  • Function() (synchronous) — JS thread ko block karta hai jab tak return na ho. Sirf tab use karo jab operation genuinely fast ho (microseconds se low-single-digit-milliseconds range) — jaise ek simple system property read karna (Build.MODEL, UIDevice info), ek in-memory calculation, ya koi cached value return karna.
  • AsyncFunction() (asynchronous) — Promise return karta hai, JS thread ko block nahi karta. Use karo kisi bhi operation ke liye jo network, disk I/O, heavy computation, ya kisi bhi unpredictable-duration kaam involve kare.
🧠 Rule of thumb

Agar operation kabhi bhi kuch milliseconds se zyada le sakti hai — chahe usually fast ho lekin edge case mein slow ho sakti ho (jaise ek file jo normally chhoti hoti hai lekin kabhi bahut badi ho sakti hai) — use hamesha async banao. "Usually fast hai" ek trap hai; production mein wahi 1% slow case aapki poori app ko freeze kar dega. Jab doubt ho, AsyncFunction() hi default choice honi chahiye — sync sirf tab jab aap 100% certain ho ki operation trivially fast hai.

Native crash symbolication — hex address se readable stack trace tak

Ye ek aisi cheez hai jo bahut teams ko production mein surprise leti hai jab unka pehla custom native module crash karta hai. JS-side crash (jaise ek unhandled exception in a React component) hamesha ek readable stack trace deta hai — file name, line number, function name — kyunki JS source maps available hote hain. Lekin native code (Swift/Kotlin/C++) crash jab production build mein hota hai, crash report mein aapko sirf ek memory address ya hex offset milta hai (jaise 0x0000000104a3f2c8), na ki function ka naam ya line number.

Iski wajah simple hai: production build ke liye compiler code ko optimize aur strip karta hai — readable symbol names (function/variable names) binary se strip ho jaate hain size aur reverse-engineering protection ke liye. Ye symbol-to-address mapping ek alag file mein store hoti hai: iOS pe dSYM (Debug Symbol) file, Android pe mapping file (ProGuard/R8 se, ya native .so files ke liye symbol files). Jab tak aap crash reporting tool (Sentry, Bugsnag, Firebase Crashlytics) ko us exact build ke matching dSYM/mapping file upload nahi karte, crash report hamesha unreadable hex addresses hi dikhayega — chahe aapka source code perfectly fine ho.

🔒 Common gap — custom native module crash aur "hume pata hi nahi chala kyun"

Ye exactly wo scenario hai jo custom native modules ke saath teams ko sabse zyada frustrate karta hai: module production mein kisi rare device/OS-version combination pe crash karta hai, crash reporting tool mein sirf hex addresses dikhte hain, aur symbols upload nahi hue the us exact build ke liye — result: team ko pata hi nahi chalta crash kaha ho raha hai, sirf itna pata hai ki ho raha hai. Fix: EAS Build/CI pipeline mein dSYM upload (iOS) aur mapping file upload (Android) ko automate karo har production build ke saath, seedha apne crash reporting tool (Sentry/Bugsnag) ko — taaki agli baar jab custom native code crash kare, aapke paas readable stack trace ho, hex address nahi.

🎯 Interview Questions — Senior React Native Developer

Ye section un questions ko cover karta hai jo senior/staff-level React Native interviews mein native modules aur architecture internals ke around poochhe jaate hain. Har answer detailed hai — sirf "sahi jawab" nahi, balki kyun wo sahi hai, taaki aap ye concepts genuinely samajh kar interview mein confidently explain kar sako.

1. JSI actually hai kya, low level pe? Ye JS ko C++/native code call karne kaise deta hai bina JSON serialization ke?

JSI (JavaScript Interface) ek C++ layer/API hai jo JS engine (Hermes, JavaScriptCore, V8) ke andar directly embed hoti hai. Purane Bridge architecture mein, JS aur native side ek dusre se completely isolated processes/threads ki tarah communicate karte the — har call ek message ban jaata tha jo JSON string mein serialize hota, ek async queue pe bhejta jaata, dusri taraf deserialize hota, phir process hota. Ye slow tha kyunki har cross-boundary call mein serialization/deserialization cost + queueing latency dono the.

JSI is poore overhead ko eliminate karta hai kyunki ye JS engine ko native C++ objects (called HostObjects) ko directly reference karne deta hai, jaise wo JS objects hi hon. Jab JS code ek native function call karta hai, JS engine literally ek C++ function pointer ko directly invoke karta hai — koi JSON string nahi banti, koi async message queue nahi, koi serialization nahi. Ye almost ek regular function call jaisa fast hota hai (same-process, same-memory-space call), sirf ek thin C++ interop layer ke through. Isi wajah se JSI synchronous native calls possible banata hai (jaise humara Function() jo directly return value deta hai) — Bridge architecture mein synchronous calls practically impossible the.

🧠 Interview tip

Agar interviewer deeper poochhe: TurboModules aur Fabric dono JSI ke upar bane hain. TurboModules native modules ko lazily (jab pehli baar use ho tabhi) load karte hain JSI HostObjects ke through, jabki purana Bridge sab modules ko app start pe eagerly initialize karta tha — ye startup time improvement ka bhi ek bada reason hai New Architecture mein.

2. Aap ek native module likh rahe ho jo ek bada file read karta hai — Function() use karoge ya AsyncFunction(), aur ye matter kyun karta hai?

Definitely AsyncFunction(). Reasoning: Function() synchronously calling thread (jo JS thread hota hai) pe hi directly execute hota hai — matlab jab tak file read complete na ho, poora JS thread block rahega. JS thread sirf JS code hi nahi run karta, ye React ke reconciliation aur event handling ka bhi core hai, isliye is thread ka block hona directly UI freeze/unresponsive taps/stuck animations ke roop mein dikhega user ko.

AsyncFunction() use karke, hum actual file-read kaam ko explicitly ek background thread (iOS pe DispatchQueue.global(), Android pe coroutine ka background dispatcher) pe daalte hain, aur JS side ko turant ek Promise mil jaata hai jo baad mein resolve/reject hota hai jab background kaam complete ho. Is se JS thread kabhi block nahi hota, chahe file 1KB ka ho ya 500MB ka.

Rule of thumb jo main hamesha follow karta hoon: agar operation ka duration file size, network condition, ya kisi external factor pe depend karta hai (matlab worst-case unpredictable hai), wo hamesha async honi chahiye — chahe average case mein wo fast lage.

3. Aapki app sirf production mein crash karti hai, sirf kuch Android devices pe, aur crash report ek hex address hai jo aap padh nahi sakte — process kya hoga readable banane ka aur cause dhoondhne ka?

Ye ek classic native-crash-symbolication problem hai. Mera process ye hoga:

  • Pehle confirm karo ki symbols upload ho rahe hain: crash reporting tool (Sentry/Bugsnag/Crashlytics) ke dashboard mein check karo ki us exact build/version ke liye mapping file (Android) already uploaded hai ya nahi. Agar nahi, ye pehla fix hai — CI/EAS Build pipeline mein mapping file upload step add/verify karo, taaki agli build se symbolicated crash reports milein.
  • Existing crash ko manually symbolicate karne ki koshish karo: agar us build ka mapping file locally available hai (build artifacts se), tools (jaise Android's retrace, ya Sentry CLI ka symbolication command) use karke hex addresses ko readable stack trace mein convert karo.
  • Device/OS pattern dhoondo: "sirf kuch devices pe" ka matlab hai probably ek specific OEM (Samsung/Xiaomi custom Android build), specific Android version, ya specific chipset/architecture (ARM vs x86) se related issue hai — crash reporting tool mein device/OS breakdown dekho, pattern isolate karo.
  • Native module code review karo un patterns ke against: jaise null pointer access jo sirf kisi specific OS version mein null return karta ho, ya ek native API jo sirf certain OEM builds mein deprecated/missing ho.
  • Long-term fix: future crashes ke liye ensure karo har production release automatically apne symbols upload kare — taaki next time ye pura investigation process skip ho jaaye aur seedha readable stack trace mile.

4. Ek teammate ek custom native module likhna chahta hai kisi cheez ke liye jo aapko lagta hai ek existing library already achhe se karti hai. Ye conversation kaise handle karoge?

Ye ek judgment/leadership question hai, technical se zyada. Mera approach hoga curiosity-first, blocking nahi:

  • Pehle unse poochna ki unhone kya specifically evaluate kiya — kaunsi library dekhi, usme kya missing laga jo unhe custom module likhne pe majboor kar raha hai. Kabhi kabhi genuine gap hota hai (library maintained nahi hai, ya ek bahut specific requirement support nahi karti) — is case mein unka decision sahi ho sakta hai.
  • Agar gap genuine nahi lagta, unhe is chapter ka wahi decision-tree share karna jo humne shuru mein dekha: Expo SDK → community package → sirf tabhi custom likho jab dono options genuinely fail karte ho. Aur ye reasoning explain karna ki custom native module ek one-time feature nahi, ek ongoing maintenance commitment hai — har Xcode/Gradle/OS update ke saath potential breakage, jisko koi na koi team ko forever maintain karna padega.
  • Agar unka concern library ki quality/maintenance ka hai (jaise "library 8 mahine se update nahi hui"), alternative suggest karna: ek aur maintained library dhoondo, ya us existing library mein contribute karo (PR bhejo) instead of poora naya module maintain karna.
  • Final decision agar phir bhi custom module likhna hi hai, to team ke saath explicitly document karna kyun ye decision liya gaya aur maintenance ownership kiski hai — taaki future mein koi confuse na ho.

Point ye hai ki main "na" nahi bolta seedha — main unhe wahi decision framework doon jo maine khud use kiya hota, aur unhe khud us conclusion pe pahunchne doon.

5. Prop() closure ke andar aap heavy computation kar rahe ho jab native view re-render hoti hai. Kya problem ho sakti hai?

Prop() callbacks har baar chalte hain jab wo specific prop JS side se change hoti hai — aur ye synchronously, UI thread pe hi chalta hai (kyunki native view updates hamesha main/UI thread pe hone chahiye, UIKit/Android View system ka requirement hai). Agar Prop() ke andar koi heavy computation hai (jaise complex image processing, large data transformation), ye directly UI thread ko block karega jab tak complete na ho — result: janky/stuttering UI, especially agar prop frequently change ho raha ho (jaise ek animation value jo har frame update hoti ho).

Fix: Prop() ke andar sirf lightweight, direct view-update logic rakho (jaise seedha background color set karna). Agar genuinely heavy computation chahiye, use kisi background thread pe offload karo aur result ko main thread pe wapas dispatch karke apply karo (iOS: DispatchQueue.main.async se wapas aana after background work; Android: similar main-thread dispatch pattern), ya better — computation ko JS side pe hi pre-compute karke ek simple value native ko bhejo, taaki native view sirf apply kare, compute na kare.

6. Config Plugins prebuild ke time exactly kya karte hain, aur inke bina custom native module ka Info.plist/AndroidManifest change kyun break hota hai?

Config Plugins JS/TS functions hain jo app.config.ts ke plugins array mein register hote hain. Jab npx expo prebuild chalta hai, Expo CLI native ios/ aur android/ folders ko from scratch generate karta hai (template files se) — aur phir har registered config plugin ko sequentially run karta hai, jisse wo generated config (Info.plist, AndroidManifest.xml, build.gradle, etc.) ko programmatically modify kar sake, mod-callback pattern (withInfoPlist, withAndroidManifest) ke through.

Agar aap manually ios//android/ folders ke andar files edit karte ho (bina config plugin ke), ye changes sirf tab tak survive karte hain jab tak koi prebuild dobara na chale. Kyunki prebuild folders ko regenerate karta hai from scratch based on app.config.ts + installed packages + config plugins — koi bhi manual edit jo in mechanisms se nahi aaya, silently overwrite ho jaata hai. Isi wajah se config plugins mandatory hain kisi bhi native-project-level change ke liye jab aap Expo ke managed prebuild workflow use kar rahe ho — ye changes ko idempotent aur version-controlled banate hain, "prebuild-safe" banate hain.

7. ARC (iOS) aur Garbage Collection (Android) mein basic difference kya hai, aur native module authors ko dono ke baare mein kya jaanna chahiye?

ARC (Automatic Reference Counting), jo iOS/Swift use karta hai, compile-time pe kaam karta hai — compiler khud har object ke retain/release calls insert kar deta hai code mein, based on static analysis of ownership. Isse memory deterministically aur turant free hoti hai jaise hi last strong reference chala jaata hai — koi runtime pause nahi hota memory collection ke liye.

Garbage Collection (GC), jo Android/Kotlin (JVM) use karta hai, runtime pe kaam karta hai — ek background GC thread periodically heap scan karta hai aur unreachable objects ko free karta hai. Ye developer se manual reference counting nahi mangta, lekin GC pause (chahe modern JVM GCs mein bahut chhote hote hain) ek unpredictable timing element add karta hai.

Native module author ke liye practical implication: ARC ke saath, retain cycles (do objects ek dusre ko strongly reference karte hue) ek real risk hai jo memory leak create karta hai — isliye delegate/callback patterns mein weak references use karna important hai. GC ke saath, cycles apne aap detect aur collect ho jaate hain (GC algorithms cycles handle karne ke liye designed hote hain), isliye ye specific concern Android side pe utna critical nahi hai — lekin overall memory footprint (bahut saare large objects hold karna) dono platforms pe equally matter karta hai.

8. Aapke native module ka Swift implementation kuch return karta hai jo iOS pe available hai lekin Android pe conceptually exist hi nahi karta (jaise humara fingerprint example). Iss asymmetry ko API design mein kaise handle karoge?

Ye ek real, common situation hai jo har senior native-module author face karta hai. Meri approach hai:

  • JS-facing function signature (naam, parameters, return type) hamesha symmetric rakho — dono platforms pe same function name, same TypeScript type. Consumer (app developer using the module) ko platform-specific branching nahi karni chahiye API level pe agar avoid kiya jaa sake.
  • Underlying semantic difference ko documentation mein explicitly likho — jaise "getBuildFingerprint() iOS pe vendor-scoped identifier + OS version return karta hai, Android pe manufacturer build fingerprint string return karta hai — dono unique-per-build-hain lekin exact format/uniqueness guarantees different hain."
  • Agar difference itna bada hai ki ek single unified API misleading hoga (jaise ek platform pe feature hi exist nahi karta), Platform.OS check ke saath explicitly null/undefined return karna ya ek separate optional method banana, taaki consumer ko compile-time/type-level pata chale ki ye platform-specific hai — silently wrong assumption na bane.

Point ye hai ki platform differences ko chhupana nahi, balki unhe explicitly, predictably surface karna — taaki consuming developer surprised na ho.

9. Aap Expo SDK ko major version upgrade kar rahe ho aur aapke paas 3 custom native modules hain. Iska risk assessment/testing process kya hoga?

Major Expo SDK upgrades expo-modules-core ke underlying API surface ko change kar sakte hain — naye DSL patterns, kabhi deprecated methods removed. Mera process:

  • Release notes/changelog padhna sabse pehle — Expo SDK release notes mein specifically "Breaking Changes" section check karo expo-modules-core ke against, dekho koi API deprecate/remove to nahi hui jo humare modules use kar rahe hain.
  • Ek isolated branch pe upgrade karke expo-doctor chalana — ye tool compatibility issues surface karta hai automatically, including native module related warnings.
  • Har custom module ko individually rebuild aur smoke-test karna — sirf JS side test karna kaafi nahi hai, kyunki native compile-time issues sirf actual native build (expo prebuild --clean + run:ios/run:android) chalane se pakde jaate hain.
  • Physical devices pe bhi test karna, sirf simulator/emulator nahi — kuch native-level issues (permissions, hardware APIs) sirf real devices pe reproduce hote hain.
  • Rollback plan rakhna — agar upgrade ke baad koi custom module reliably kaam nahi kar raha, ek clear decision point hona chahiye: fix karo abhi, ya upgrade ko temporarily hold karo jab tak module update na ho jaaye. Ye risk assessment pehle se team ke saath discuss karna chahiye, upgrade ke din nahi.

Bottom line: major SDK upgrade jab custom native modules involved hon, kabhi bhi "sirf package.json version bump" nahi hai — ye ek proper testing cycle deserve karta hai jo roadmap mein explicitly plan kiya gaya ho.
