Teen Pillars — Aur Har Ek Kis Sawaal Ka Jawab Deta Hai

"Logs, metrics, traces" har jagah likha milta hai, par asli baat ye hai ki teeno alag sawaal ke liye bane hain. Galat pillar se galat sawaal poochna hi observability ki sabse badi barbaadi hai.

Structured Logging

Sabse pehla practical change jo har codebase mein hona chahiye: logs text nahi, JSON hone chahiye. Wajah simple hai — logs machines padhti hain, insaan nahi. Production mein tum tail -f nahi kar rahe hote; tum 20 instances ke 50 lakh log lines mein query kar rahe hote ho.

unstructured vs structured
// ❌ Unstructured — insaan ke liye theek, machine ke liye bekaar
console.log(`User ${userId} created order ${orderId} for ₹${total}`);
// "user 42 ke saare orders dikhao jo ₹5000 se upar the" → regex likhna padega
// Aur message format badla toh saari dashboards/queries toot gayi.

// ✅ Structured — har field query-able hai
logger.info({
  event:     "order.created",   // stable event name — ISPE query karo, message pe nahi
  orderId, userId,
  totalPaise: 499900,          // number, formatted string nahi (ch 5)
  itemCount: 3,
  durationMs: 142,
  requestId: req.ctx.requestId,  // ← sab kuch isse judta hai (ch 8)
}, "order created");

// Ab ye sab possible hai:
//   event="order.created" AND totalPaise > 500000
//   avg(durationMs) by event
//   requestId="req_8f3a" → us ek request ki poori kahani
production logger setup
const logger = pino({
  level: config.LOG_LEVEL,          // ch 15 se — validated

  // REDACTION — ch 15 ka secrets rule yahan enforce hota hai
  redact: ["req.headers.authorization", "req.headers.cookie",
           "*.password", "*.token", "*.cardNumber", "*.otp"],

  // har log line mein base fields — filtering ke liye zaroori
  base: { service: "orders-api", version: process.env.GIT_SHA, env: config.NODE_ENV },
});
// version/GIT_SHA kyun? Kyunki incident ke waqt sabse pehla sawaal hota hai
// "kya ye naye deploy ke baad shuru hua?" — usse filter karke turant pata chalta hai.

// Child logger — request ke saare logs mein context apne aap aa jaata hai
req.log = logger.child({ requestId: req.ctx.requestId, userId: req.ctx.user?.id });
req.log.info({ event: "payment.started" });   // requestId apne aap included
⚠️ Logs mein kya kabhi nahi jaana chahiye

Passwords, tokens, card numbers, OTP, poore request bodies (usme sab kuch ho sakta hai), aur PII bina soche-samjhe. Logs aksar teesre-parties (Datadog, CloudWatch) ko jaate hain, lambe samay tak store hote hain, aur unka access control application se kahin dheela hota hai. Ek log line ek data breach ban sakti hai. Redaction ko logger config mein enforce karo — har call site pe yaad rakhne ke bharose mat chhodo.

🧠 error ka matlab "koi insaan dekhega"

Sabse common galti: har 404 aur har validation failure ko error pe log karna. Wo expected hain (ch 14) — warn ya info hain. Jab error level mein normal traffic ka shor bhar jaata hai, toh asli errors usme kho jaate hain aur log level apna matlab hi kho deta hai. Test: "kya main chahta hoon ki koi is line pe kaam kare?" Nahi → error nahi hai.

Metrics Aur Percentiles Ka Jaal

Chaar basic metric types, aur unka sahi use:

metric types
// COUNTER — sirf badhta hai (requests, errors, jobs processed)
http_requests_total{method="POST", route="/orders", status="201"}
// query mein rate() lagta hai: rate(http_requests_total[5m])

// GAUGE — upar-neeche jaata hai (memory, queue depth, active connections)
db_pool_active_connections     // ch 10 ka pool exhaustion yahan dikhta hai
queue_depth{queue="emails"}       // ch 12

// HISTOGRAM — distribution (latency, payload size) → percentiles isse nikalte hain
http_request_duration_seconds{route="/orders"}

// ⚠️ CARDINALITY — sabse mehnga metrics mistake
// ❌ label mein userId/orderId mat daalo
http_requests_total{userId="42"}   // 10 lakh users = 10 lakh time series → system phat jayega
// ✅ labels bounded hone chahiye: method, route TEMPLATE, status
http_requests_total{route="/orders/:id"}  // :id, actual ID nahi
// High-cardinality data logs aur traces ka kaam hai, metrics ka nahi.

Ab sabse important cheez is section ki — average latency ek jhooth hai.

percentiles kyun
// 100 requests: 99 requests 10ms, 1 request 5000ms
average = (99×10 + 5000) / 100 = 60ms
// Dashboard: "60ms — sab theek hai!" 😊
// Haqiqat: ek user 5 second baitha raha. Average ne usse CHHUPA diya.

p50 = 10ms      // aadhe users ka experience
p95 = 10ms      // 95% users theek hain
p99 = 5000ms    // ← YAHAN problem dikhti hai

// Aur p99 chhota nahi hai:
// 1% requests slow = 10 lakh requests/day pe 10,000 kharab experiences.
// Aur ek page 20 API calls karta hai? Toh ~18% chance hai ki user ko
// KAM SE KAM ek p99 call mile. Tail latency user-facing hai.

// ⚠️ Percentiles ko average mat karo!
// avg(p99 across 10 instances) mathematically MEANINGLESS hai.
// Histogram buckets ko add karke phir percentile nikalo
// (Prometheus: histogram_quantile(0.99, sum(rate(...)) by (le)))

Kya Measure Karein — Golden Signals & RED

Sab kuch measure karne ki koshish mat karo — do chhote frameworks 90% cover kar dete hain:

Google's 4 Golden SignalsKya batata haiExample metric
LatencyKitna time lag raha hai (successful aur failed alag!)p50/p95/p99 duration
TrafficKitna load aa raha hairequests/sec
ErrorsKitne fail ho rahe hain5xx rate
SaturationResources kitne bhare hain — ye future batata haipool usage, queue depth, CPU, memory

Services ke liye chhota version RED hai: Rate, Errors, Duration. Resources ke liye USE: Utilization, Saturation, Errors.

📌 Saturation sabse valuable signal hai

Latency aur errors batate hain ki abhi kya galat hai. Saturation batata hai ki kya galat hone wala hai — connection pool 85% pe hai, queue depth badh rahi hai, disk 90% bhar chuka hai. Yahi ek signal hai jo tumhe incident se pehle react karne deta hai. Ch 10 ka pool exhaustion aur ch 12 ka queue backlog — dono saturation metrics hain, aur dono ke alerts hone chahiye.

Distributed Tracing

Ek request 5 services se guzarti hai aur 800ms leti hai. Kahan gaye 800ms? Logs alag-alag services mein bikhre hain; metrics per-service aggregate hain. Trace hi wo cheez hai jo poori request ko ek picture mein dikhati hai.

trace ka structure
// TRACE = ek request ka poora safar. SPAN = us safar ka ek kaam.
Trace: 4bf92f3577b34da6   [ POST /orders — 842ms ]
│
├─ span: auth.verify              12ms   ▓
├─ span: validate                  3ms   ▏
├─ span: db.products.findByIds    45ms   ▓▓
├─ span: payment.charge          680ms   ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  ← YAHAN hai
│   └─ span: http POST stripe    675ms
├─ span: db.orders.insert         28ms   ▓
└─ span: queue.publish             8ms   ▏

// Ek nazar mein pata chal gaya: 80% time Stripe pe gaya.
// Ye baat 5 services ke logs padh ke pata karna ghanton ka kaam hai.

// Traces do aur patterns turant pakadte hain:
//   • N+1 → same span 100 baar repeat (ch 10)
//   • Serial calls jo parallel ho sakte the → seedhi seedhi staircase
context propagation — poora raaz yahi hai
// Trace tabhi juda rehta hai jab har hop trace context AAGE bheje.
// W3C standard header:
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  └── trace ID (poore safar ke liye ek) ──┘ └ parent span ┘ └ flags

// Service A → Service B
await fetch(url, { headers: { traceparent: currentContext() } });
// B naya span banata hai LEKIN wahi trace ID rakhta hai → ek hi picture

// ⚠️ Ek jagah bhi propagation toota → trace do tukdon mein bat jaata hai
// Sabse common toot: QUEUE ke aar-paar (ch 12). Producer ko trace context
// message ke andar daalna padta hai, aur worker ko usse resume karna padta hai —
// warna background jobs trace mein dikhte hi nahi.

// SAMPLING — 100% traces mehnge hote hain
// Head-based: shuru mein hi decide (1% rakho) — simple par slow requests miss ho sakti hain
// Tail-based: poora trace jama karke decide — SAARI slow/failed requests rakho + 1% baaki
// Tail-based behtar hai kyunki interesting traces wahi hain jo slow ya failed hain.

Alerting — Symptoms Pe, Causes Pe Nahi

Alerting ka sabse bada dushman alert fatigue hai. Jab 50 alerts roz aate hain aur 49 bekaar hote hain, toh 50th — jo asli hota hai — bhi ignore ho jaata hai. Isliye alerts kam aur meaningful hone chahiye.

causes vs symptoms
// ❌ CAUSE-based alerts — bahut zyada, aksar harmless
// "CPU > 80%"          → toh? shayad sab theek hai, ya autoscaling chal rahi hai
// "Memory > 70%"       → normal ho sakta hai
// "Ek pod restart hua" → k8s ka normal kaam

// ✅ SYMPTOM-based — user ko sach mein farq pad raha hai
// "5xx error rate > 1% for 5 min"
// "p99 latency > 2s for 10 min"
// "checkout success rate < 95%"       ← business metric, best alert
// "queue ka oldest message > 15 min"  ← ch 12

// Har alert ke saath ye teen cheezein honi chahiye:
//   1. Kya toota hai (user ki bhasha mein)
//   2. Runbook link — ab kya karna hai
//   3. Dashboard/trace link — kahan dekhna hai
// Bina inke alert sirf ghabrahat hai, information nahi.

// ⚠️ "for 5 min" wala hissa zaroori hai — instant alerts har spike pe bajte hain.
🧠 SLI, SLO, aur error budget

SLI = ek measurement ("successful requests ka %"). SLO = uska target ("99.9% over 30 days"). Aur error budget = jo bacha hua hai: 99.9% ka matlab hai 30 din mein ~43 minute downtime allowed hai. Ye framing bahut practical hai — budget bacha hai toh team tez chal sakti hai, naye features deploy kar sakti hai; budget khatam ho gaya toh focus reliability pe shift karna chahiye. Ye "100% uptime" wale unrealistic goal se kahin behtar hai, aur product vs reliability ki bahas ko ek number bana deta hai.

Ek Incident, Teeno Pillars Ke Saath

Poora chapter ek concrete flow mein — ye wahi hop-thinking hai jo ch 2 mein shuru hui thi:

  1. Alert (metric): "p99 latency > 2s on /orders for 10 min."
  2. Dashboard (metrics): error rate normal hai, traffic normal hai — matlab load spike nahi. Par saturation dekho: db_pool_active_connections max pe chipka hua hai. Ch 10 ka pool exhaustion ka signature.
  3. Deploy check: logs ko version se filter karo — kya ye naye GIT_SHA ke baad shuru hua? (Isliye base mein version daala tha.)
  4. Trace: ek slow request ka trace kholo. Dikha ki payment.charge span 680ms le raha hai, aur uske andar Stripe call. Ya phir 100 identical DB spans — N+1.
  5. Log: us trace ke requestId se saare logs nikalo — exact error, exact input, retry attempts.
  6. Fix: root cause ke hisaab se — Stripe pe timeout + circuit breaker (ch 14), ya N+1 ko batch load (ch 10), ya transaction se external call bahar (ch 10).
⚠️ Observability ko incident ke waqt "add" nahi kiya ja sakta

Ye ek build-time investment hai, run-time nahi. Jab production jal raha hai, tab tum requestId propagate karna, structured logging lagana, ya tracing instrument karna nahi kar sakte — us waqt sirf wahi kaam aata hai jo pehle se laga hua hai. Isiliye ch 8 mein request context, ch 14 mein error context, aur yahan structured logs — ye sab din 1 se lagti hain, incident ke din nahi.

Key Takeaways

  • Monitoring = pehle se soche gaye sawaalon ke jawab. Observability = jo sawaal tumne nahi soche, unke jawab nikaal pana.
  • Teen pillars alag sawaalon ke liye: metrics "kuch galat hai?", traces "kahan?", logs "kya hua?".
  • Inki value connection mein hai — ek requestId/traceId jo teeno ko jode.
  • Logs structured (JSON) hone chahiye, stable event names ke saath — message text pe query mat karo.
  • Logger ke base mein service + version (GIT_SHA) daalo — incident ka pehla sawaal "kya ye naye deploy se hai?" turant answer hota hai.
  • Redaction logger config mein enforce karo — ek log line ek data breach ban sakti hai.
  • error level ka matlab "koi insaan kaam karega". 404 aur validation failures warn/info hain.
  • Metrics mein cardinality bounded rakho — userId/orderId labels metrics system ko phaad dete hain. High-cardinality data logs/traces ka kaam hai.
  • Average latency ek jhooth hai — p50/p95/p99 dekho. 1% slow = 10 lakh req/day pe 10,000 kharab experiences.
  • Percentiles ko average mat karo — histogram buckets add karke percentile nikalo.
  • Golden signals: latency, traffic, errors, saturation. Saturation hi batata hai ki kya hone wala hai.
  • Trace = poora safar, span = ek kaam. Trace N+1 aur serial-calls turant dikha deta hai.
  • Context propagation (traceparent) ek jagah toota toh trace tukdon mein bat jaata hai — queue ke aar-paar sabse common toot hai.
  • Tail-based sampling behtar hai — interesting traces wahi hain jo slow ya failed hain.
  • Alerts symptoms pe, causes pe nahi: "5xx > 1% for 5 min", "CPU > 80%" nahi. Har alert ke saath runbook + dashboard link.
  • Error budget product-vs-reliability ki bahas ko ek number bana deta hai.
  • Observability ek build-time investment hai — incident ke waqt add nahi ho sakti.

🎯 Interview Questions

Q1. "Logs, metrics, traces — teeno kyun chahiye?"

Alag sawaal, alag cost profile. Metrics sasti aur aggregated hain — "kuch galat hai?" ka jawab dete hain aur alerts/dashboards inhi pe bante hain, par wo nahi bata sakte ki kaunsi request kharab thi. Traces ek request ka poora safar dikhate hain — "kahan slow/fail hua". Logs sabse zyada detail dete hain — "actually kya hua", par mehnge hain. Debugging ka flow: alert → trace → log, aur teeno ko traceId/requestId jodta hai.

Q2. "Average latency 60ms hai, sab theek hai?"

Nahi — average distribution chhupa deta hai. 99 requests 10ms aur 1 request 5000ms ka average bhi 60ms hai. Percentiles dekho: p50 (typical user), p95, aur p99 (tail). Aur tail chhoti baat nahi hai — 1% slow ka matlab 10 lakh requests/day pe 10,000 kharab experiences, aur agar ek page 20 API calls karta hai toh ~18% chance hai ki user ko kam se kam ek p99 call mile. Bonus point: percentiles ko instances ke across average mat karo — histogram buckets add karke nikalo.

Q3. "Distributed tracing kaise kaam karti hai?"

Entry point pe ek trace ID generate hoti hai; har operation ek span banata hai (parent span ID ke saath), aur trace context har hop pe aage bheja jaata hai — HTTP mein traceparent header (W3C). Sab spans ek collector pe jaate hain aur waterfall ban jaata hai. Do gotchas: propagation ek jagah bhi toota toh trace do tukdon mein bat jaata hai (sabse common toot queues ke aar-paar — trace context message mein daalna padta hai), aur sampling — tail-based better hai kyunki wo saari slow/failed requests rakhta hai.

Q4. "Alert kis cheez pe lagaoge?"

Symptoms pe, causes pe nahi. "CPU > 80%" ek cause hai aur aksar harmless — usse user ko farq pad hi nahi raha ho sakta. Symptom alerts: 5xx rate > 1% for 5 min, p99 > 2s, checkout success rate < 95%, queue ka oldest message > 15 min. Duration window ("for 5 min") zaroori hai warna har spike pe bajega. Har alert ke saath runbook aur dashboard link ho. Reason: alert fatigue — 49 bekaar alerts 50th asli wale ko bhi ignore kara dete hain.

Q5. "SLI, SLO, error budget kya hain?"

SLI ek measurement hai ("successful requests ka %"), SLO uska target ("99.9% over 30 days"), aur error budget wo allowed failure jo bacha hai — 99.9% = 30 din mein ~43 min. Iska practical use ye hai ki product vs reliability ki bahas ek number ban jaati hai: budget bacha hai toh tezi se ship karo, khatam ho gaya toh reliability pe focus karo. Aur ye "100% uptime" jaise unrealistic goal se behtar hai — 100% ka matlab hoga har change rok dena.
