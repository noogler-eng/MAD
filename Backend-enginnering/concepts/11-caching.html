Caching

Ch 10 mein query ko fast banaya. Par sabse fast query wo hai jo chalti hi nahi. Caching ka poora idea yahi hai — mehnga jawab ek baar nikaalo, aur usse baar-baar reuse karo. Problem ye hai ki cache ek duplicate copy hai, aur duplicate copy ka matlab hai ki wo galat ho sakti hai. Isliye ye chapter caching se zyada invalidation ke baare mein hai.

Kyun Kaam Karta Hai — Locality Aur Latency

Caching do observations pe khadi hai. Pehli — locality: real traffic uniform nahi hota. 1% products 50% views le jaate hain, ek viral post lakhon baar padha jaata hai, aur homepage har user ko wahi dikhta hai. Doosri — latency ka pyramid: har layer neeche wali se ek order of magnitude slow hai.

Kahan seApprox latencyComparison
Process ki apni memory (in-process cache)~100 ns1×
Redis, same datacenter~0.5–1 ms~5,000×
Postgres, indexed query~1–10 ms~10,000×
Postgres, complex aggregate~100 ms – 2 s~10⁶×
External API call~50–500 ms~10⁶×

Ek 800ms ka aggregate query jo 1ms ke Redis hit se replace ho jaaye — wo 800× improvement hai, aur saath hi DB pe load bhi hatta hai. Ye doosra faayda aksar pehle se zyada important hota hai: cache DB ko bachata hai, sirf user ko fast nahi karta.

Cache Layers — Ek Request Ke Raaste Pe

"Cache" ek jagah nahi hai — ch 2 ke har hop pe ek cache baith sakti hai. Sahi layer chunna aadha kaam hai.

Teen Patterns — Cache-Aside, Write-Through, Write-Behind

1. Cache-aside (lazy loading) — 90% cases mein yahi
async function getProduct(id) {
  const key = `product:v1:${id}`;

  // 1. cache dekho
  const cached = await redis.get(key);
  if (cached !== null) return JSON.parse(cached);   // HIT
  // ↑ `!== null` — `if (cached)` galat hai: cached "0" ya "" ho sakta hai

  // 2. MISS → asli source
  const product = await db.products.findById(id);
  if (!product) return null;

  // 3. cache mein daalo, TTL ke SAATH — TTL hamesha lagao
  await redis.setex(key, 300, JSON.stringify(product));
  return product;
}
// ✅ Simple, aur cache gir jaaye toh app sirf slow hoga, TOOTEGA nahi
// ❌ Har naye key pe pehli request slow (cold miss)
// ❌ Write ke baad cache stale — isliye invalidation chahiye (§5)
PatternWrite pe kyaKab use karoRisk
Cache-aside DB likho, cache delete karo Default — read-heavy, tolerable staleness Cold miss; short race window
Write-through DB aur cache dono likho Jab cache hamesha warm chahiye Write slow; wo data bhi cache hota hai jo shayad kabhi padha na jaaye
Write-behind Cache likho, DB baad mein async Bahut high write rate (counters, analytics) Cache gira toh data KHO gaya — durability nahi
⚠️ Write pe cache delete karo, update nahi

Sochne mein lagta hai ki update karna behtar hai (cache warm rahega). Par do concurrent writes mein order ulta ho sakta hai — A ne DB likha, B ne DB likha, phir B ne cache likha, phir A ne cache likha → cache mein purani value permanently baithi hai. Delete karne se worst case sirf ek extra DB read hai. Simple aur galat se simple aur sahi hamesha behtar hai.

Cache Keys — Design Rules

key design
// ✅ Structured, namespaced, versioned
`product:v1:${id}`
`user:v2:${userId}:orders:page:${cursor}`
`search:v1:${sha256(normalizedQuery)}`   // lambi query → fixed-size hash

// Version (`v1`) kyun? Kyunki cached object ka SHAPE badal sakta hai.
// Deploy ke baad naya code purane shape ka JSON padhega aur crash karega.
// Version badhao → poori purani cache automatically ignore ho jaati hai,
// bina manual flush ke. Ye ek FREE migration strategy hai.

// ⚠️ Per-user data ki key mein user ID HONA CHAHIYE
`dashboard:${userId}`     // ✅
`dashboard`               // ❌ ek user ka data doosre ko dikh jayega — REAL breach
// Yahi galti CDN pe bhi hoti hai: personalized response pe `Cache-Control: public`
// lagana matlab CDN use SABKO serve karega. `private` use karo (ch 3).

// ⚠️ KEYS ya SCAN production mein mat chalao — Redis single-threaded hai,
//    KEYS * poora server block kar deta hai. Prefix delete chahiye toh
//    ya to ek "generation" counter use karo, ya alag Redis DB/namespace.

Invalidation — Do Hard Problems Mein Se Ek

Phil Karlton ka mashhoor quote hai ki computer science mein sirf do mushkil cheezein hain: cache invalidation aur naming. Wajah ye hai ki tumhe har us jagah ka pata hona chahiye jahan wo data badal sakta hai — API, admin panel, migration script, cron job, doosri service. Ek jagah bhool gaye, toh stale data permanently baitha rahega.

StrategyKaiseTrade-off
TTL (time-based) Har entry apne aap expire Sabse simple, hamesha lagao. Par TTL tak stale data serve hota hai
Explicit delete Write ke baad DEL key Turant fresh. Par har write path pe yaad rakhna padta hai
Key versioning Key mein ek counter — user:42:v{n} Purani entries apne aap orphan; delete karne ki zaroorat hi nahi
Event-driven DB change → event (ch 12) → subscribers invalidate karein Har write path automatically covered. Par ek aur moving part
generation counter — prefix invalidation bina SCAN ke
// Problem: user 42 ke SAARE cached pages invalidate karne hain,
// par unki keys pata nahi (cursor har page pe alag hai).

// Solution: ek generation number key ka HISSA bana do
async function ordersKey(userId, cursor) {
  const gen = (await redis.get(`gen:user:${userId}`)) ?? "0";
  return `orders:${userId}:g${gen}:${cursor}`;
}

// Invalidate = sirf counter badhao. Ek O(1) operation.
await redis.incr(`gen:user:${userId}`);
// Ab saari purani keys (g5) kabhi generate hi nahi hongi — wo TTL pe apne aap
// mar jayengi. Koi SCAN nahi, koi key list maintain karne ki zaroorat nahi.

Cache Stampede Aur Uske Teen Fix

Sabse khatarnak cache failure. Ek popular key expire hoti hai. Us exact moment pe 5,000 concurrent requests aati hain. Sab miss hoti hain. Sab ek saath DB pe jaati hain — wahi mehnga query, 5,000 baar. DB girta hai. Aur DB girne se aur requests fail hoti hain, jo retry hoti hain… ye ek cascading failure hai.

teen fix — aksar teeno saath lagte hain
// ── Fix 1: JITTER — expiry ko faila do ────────────────────
const ttl = 300 + Math.floor(Math.random() * 60);   // 300–360s
await redis.setex(key, ttl, value);
// Bina jitter ke, ek saath cache ki gayi 1000 keys ek saath expire hoti hain.
// Ye deploy ke baad ya bulk warm-up ke baad bahut common hai.

// ── Fix 2: SINGLE-FLIGHT — sirf ek request DB tak jaaye ───
async function getWithLock(key, loader, ttl) {
  const cached = await redis.get(key);
  if (cached !== null) return JSON.parse(cached);

  // NX = "sirf tab set karo jab exist na kare" → ek ATOMIC lock
  const got = await redis.set(`lock:${key}`, "1", "NX", "EX", 10);
  // EX 10 zaroori hai — warna loader crash hua toh lock hamesha ke liye atka rahega

  if (!got) {
    await sleep(50);                       // koi aur laa raha hai — thoda ruko
    return getWithLock(key, loader, ttl);   // aur dobara cache dekho
  }

  try {
    const value = await loader();          // sirf YE request DB pe jaati hai
    await redis.setex(key, ttl, JSON.stringify(value));
    return value;
  } finally {
    await redis.del(`lock:${key}`);        // error pe bhi lock chhodo
  }
}

// ── Fix 3: STALE-WHILE-REVALIDATE — kabhi miss hi mat karo ─
// Do TTL rakho: ek "fresh tak", ek "asli expiry"
const entry = await redis.get(key);   // { data, freshUntil }
if (entry) {
  if (entry.freshUntil < now()) refreshInBackground(key);  // await NAHI
  return entry.data;   // thoda purana data turant — user kabhi wait nahi karta
}
// Ye wahi idea hai jo HTTP ke stale-while-revalidate header mein hai (ch 3).

Baaki Failure Modes

ProblemKya hota haiFix
Cache penetration Aisi key maangi jo exist hi nahi karti (/products/99999999) — har baar miss, har baar DB. Attacker ise deliberately kar sakta hai "Not found" ko bhi cache karo, chhote TTL (30–60s) ke saath. Bade scale pe bloom filter
Cache avalanche Poora Redis gir gaya / restart hua → saara traffic ek saath DB pe Jitter, in-process fallback layer, DB pe circuit breaker (ch 14)
Hot key Ek key itni popular ki ek Redis node hi bottleneck ban gaya Us key ko in-process bhi cache karo (chhota TTL); ya key ko shards mein todo
Big key 10 MB ka value — Redis single-threaded hai, ek badi serialize/transfer sabko block karti hai Value chhoti rakho; bade objects ko todo ya sirf ID list cache karo
Stale after deploy Naya code purane shape ka cached JSON padh ke crash Key mein version (:v2:) — §4
⚠️ Cache down hone pe app ko slow hona chahiye, down nahi

Redis call ko hamesha timeout aur try/catch ke saath wrap karo, aur fail hone pe seedha DB se serve karo. Bina iske ek cache outage ek full outage ban jaata hai — jo ironic hai, kyunki cache ka kaam availability badhana tha. Timeout aggressive rakho (50–100ms): agar Redis slow hai toh uska intezaar karna DB se seedha padhne se bhi mehnga hai.

Eviction Policies Aur Memory

Redis ki memory bharne pe kya ho — ye maxmemory-policy se decide hota hai, aur default galat hota hai:

  • noeviction (default) — memory full hone pe writes error dene lagte hain. Pure cache use-case ke liye ye galat hai.
  • allkeys-lru — sabse kam recently use hui keys hatao. Cache ke liye yahi sahi default hai.
  • volatile-lru — sirf un keys ko hatao jinpe TTL laga hai. Tab use karo jab ek hi Redis mein cache aur permanent data (jaise sessions) dono hon.
  • allkeys-lfu — frequency ke hisaab se. Behtar jab access pattern skewed ho (kuch keys hamesha popular).

Aur ek design decision: cache aur durable data ko mila mat do. Sessions (jo kho jaayein toh sab logged out) aur query cache (jo kho jaaye toh bas slow) ek hi Redis mein rakhne ka matlab hai ki eviction policy dono ke liye compromise karni padegi. Alag instance ya alag DB index use karo.

Kab Cache Nahi Karna Chahiye

Cache ek complexity ka trade hai — tum speed ke badle correctness ka risk le rahe ho. Wo trade hamesha faayde ka nahi hota:

  • Query already fast hai — 5ms ki indexed query ko 1ms banane ka koi matlab nahi jab request ka total budget 200ms hai. Pehle measure karo.
  • Data har baar badalta hai — hit rate itna kam hoga ki cache sirf overhead banegi.
  • Staleness allowed nahi hai — account balance, stock quantity checkout ke waqt, permission checks. Yahan galat jawab fast jawab se bura hai.
  • Asli problem N+1 ya missing index hai — cache us bug ko chhupa deti hai. Cache miss pe wo dobara dikhega, aur tab tak diagnose karna mushkil ho chuka hoga.
🧠 Order of operations

Pehle query theek karo (ch 10), phir cache lagao. Ek slow query ko cache karna use fast nahi banata — wo bas usse kam baar slow banata hai. Aur jab cache miss hoti hai (deploy, eviction, Redis restart), wo poori slowness ek saath wapas aati hai — sabse bure waqt pe. Cache ko optimization ki tarah use karo, fix ki tarah nahi.

Key Takeaways

  • Caching do cheezon pe khadi hai: locality (traffic uniform nahi hota) aur latency pyramid (har layer 10× slow).
  • Cache ka bada faayda aksar user ki speed nahi, DB pe load hatna hota hai.
  • In-process cache sabse fast hai par per-instance — invalidation multi-instance mein toot-ti hai. "Kabhi-kabhi purana data" ka yahi cause hai.
  • Cache-aside default pattern hai; write-behind mein cache girne pe data kho jaata hai.
  • Write pe cache delete karo, update nahi — concurrent writes ka order ulta ho sakta hai.
  • if (cached) galat hai — if (cached !== null) likho, warna 0 aur "" miss ban jaate hain.
  • Key mein version daalo (:v1:) — shape badalne pe ek free migration mil jaata hai.
  • Per-user data ki key mein user ID hona chahiye; personalized responses pe Cache-Control: private.
  • Production Redis pe KEYS/SCAN mat chalao — prefix invalidation ke liye generation counter use karo (O(1)).
  • Stampede = popular key expire, hazaaron requests ek saath DB pe. Fix: jitter + single-flight lock (SET NX EX) + stale-while-revalidate.
  • Lock pe hamesha TTL lagao, warna crash pe wo permanently atak jaata hai.
  • Penetration (missing key baar-baar) ke liye "not found" bhi cache karo, chhote TTL se.
  • Redis call pe timeout + try/catch — cache down = slow, down nahi.
  • maxmemory-policy cache ke liye allkeys-lru hona chahiye; default noeviction writes fail karta hai.
  • Sessions aur cache alag rakho — unki eviction requirements ulti hain.
  • Pehle query theek karo, phir cache lagao. Cache slow query ko chhupati hai, theek nahi karti.

🎯 Interview Questions

Q1. "Cache-aside kaise kaam karta hai? Write pe cache update karoge ya delete?"

Cache-aside: cache padho → miss pe DB se lao → TTL ke saath cache mein daalo. Write pe delete, update nahi — kyunki do concurrent writes mein cache-write ka order DB-write ke order se ulta ho sakta hai, jisse purani value permanently cache mein baith jaati hai. Delete ka worst case sirf ek extra DB read hai.

Q2. "Cache stampede kya hai aur kaise rokoge?"

Ek popular key expire hoti hai aur hazaaron concurrent requests ek saath miss karke same mehnga query DB pe maarti hain — DB girta hai, retries se aur load, cascading failure. Teen fix, aksar saath: (1) TTL mein jitter taaki keys ek saath expire na hon; (2) single-flight — SET NX EX se ek atomic lock, sirf ek request loader chalati hai, baaki thoda ruk ke cache dobara padhti hain; (3) stale-while-revalidate — thoda purana data turant do aur background mein refresh karo, toh miss hoti hi nahi.

Q3. "Cache invalidation mushkil kyun hai?"

Kyunki tumhe har us jagah ka pata hona chahiye jahan wo data badal sakta hai — API handler, admin panel, migration script, cron, doosri service. Ek raasta bhool gaye toh stale data permanently baitha rahega. Isliye layered defense: hamesha TTL (upper bound on staleness), write path pe explicit delete, key versioning shape changes ke liye, aur bade systems mein event-driven invalidation taaki har write path automatically cover ho.

Q4. "In-process cache vs Redis?"

In-process ~100ns hai aur serialization ka cost bhi nahi, par per-instance — 10 instances = 10 alag states, aur invalidation ka koi seedha tareeka nahi. Isliye wo sirf us data ke liye theek hai jo shayad hi badalta ho (config, feature flags, reference data). Redis ~1ms leta hai par shared hai — ek invalidate sabke liye — aur TTL, atomic ops, pub/sub deta hai. Default Redis; dono layers saath bhi use hoti hain (hot key ko in-process bhi chhote TTL se).

Q5. "Redis gir gaya toh app ka kya hoga?"

Design aisa hona chahiye ki app slow ho, down nahi — har Redis call pe aggressive timeout (50–100ms) aur try/catch, fail pe seedha DB se serve. Par saath mein ye bhi soch lo ki poora traffic ek saath DB pe jaayega (cache avalanche) — isliye DB pe circuit breaker/rate limit (ch 14) aur ek chhoti in-process fallback layer madad karti hai. Aur agar Redis mein sessions bhi hain toh outage ka matlab sab logged out — isliye sessions aur cache alag instances mein rakhne chahiye.
