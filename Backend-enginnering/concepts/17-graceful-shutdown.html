Graceful Shutdown

Ek chhota sa chapter, ek chhoti si window — 10–30 second — aur us window ka ek hi sawaal: jab process marta hai, tab jo requests beech mein chal rahi thi unka kya hota hai? Ye ek roz-ka event hai (har deploy, har autoscale, har pod reschedule), aur agar ye galat hai toh tumhare "successful" deploys chupchaap users ko 502 de rahe hain.

Problem — Ek Deploy Mein Kya Toot-ta Hai

Deploy ka matlab hai: purana process marta hai, naya chalu hota hai. Us "marne" ke lamhe pe server ke andar kya-kya adhoora pada hai:

  • Requests jo abhi handle ho rahi hain — DB query chal rahi hai, response likha ja raha hai.
  • Ek khula transaction jo commit hone wala tha (ch 10).
  • Ek payment ka external call jiska response aa raha tha (ch 14).
  • Ek worker jo message process kar chuka hai par ack nahi kiya (ch 12).
  • Keep-alive connections jo clients ne khule rakhe hain (ch 3).

Bina graceful shutdown ke ye sab beech mein katt jaate hain: users ko 502, aadhe likhe hue responses, aur worst case — aadha kaam jo na complete hai na retry hoga.

🧠 Ye "kabhi-kabhi" wala nahi, "har baar" wala event hai

Har deploy pe hota hai. Har autoscale-down pe. Har node drain pe, har spot instance reclaim pe, har OOM restart pe. Ek active service mein ye din mein dozens baar hota hai. Isliye ye "edge case" nahi hai — ye normal operation hai. Aur iska nuksaan chhupa rehta hai kyunki deploy "successful" dikhta hai; error rate ka chhota spike deploy ke shor mein kho jaata hai (ch 16 — isliye version label se filter karna kaam aata hai).

Signals — SIGTERM vs SIGKILL

SignalKya haiCatch kar sakte ho?Kab aata hai
SIGTERM (15)"Please band ho jao" — polite requestHaanDeploy, docker stop, k8s pod delete
SIGINT (2)Ctrl+CHaanLocal development
SIGKILL (9)"Abhi maro" — OS turant maar deta haiNahiGrace period khatam, OOM killer, kill -9

Poora graceful shutdown SIGTERM aur SIGKILL ke beech ki window mein hota hai. Default grace period Docker mein 10s hai, Kubernetes mein 30s. Us window mein cleanup pura na hua toh SIGKILL aata hai aur sab kuch waise hi katt jaata hai jaise pehle katta tha.

Sahi Sequence

Implementation

graceful shutdown — poora code
let isShuttingDown = false;

// ── Health endpoints — do ALAG (ch 14) ────────────────────
app.get("/health/live", (req, res) => res.send("ok"));
// liveness: "kya process zinda hai" — shutdown ke dauraan bhi OK rehta hai,
// warna k8s isse SIGKILL kar dega jabki hum saaf exit kar rahe hain

app.get("/health/ready", (req, res) => {
  if (isShuttingDown) return res.status(503).send("shutting down");
  return res.send("ok");   // readiness: "traffic bhejo" — YAHI LB dekhta hai
});

async function shutdown(signal) {
  if (isShuttingDown) return;      // double SIGTERM se bachao
  isShuttingDown = true;
  logger.info({ signal }, "shutdown started");   // ch 16 — ye log incident mein kaam aata hai

  // SAFETY NET: agar drain atak gaya toh bhi exit karo.
  // Ye grace period se KAM hona chahiye, warna SIGKILL pehle aa jayega.
  const forceExit = setTimeout(() => {
    logger.error("graceful shutdown timed out — forcing exit");
    process.exit(1);
  }, 25_000).unref();   // unref — ye timer khud process ko zinda na rakhe

  try {
    // STEP 2 — LB ko readiness fail dekhne ka WAQT do
    await sleep(10_000);   // = LB ka (check interval × failure threshold) + margin
    // Is dauraan requests NORMALLY serve hoti rehti hain — ye important hai

    // STEP 3+4 — naye connections band, purane poore hone do
    await new Promise((resolve, reject) =>
      server.close(err => err ? reject(err) : resolve()));
    // ⚠️ keep-alive idle connections close() ko rok sakte hain —
    //    Node 18+ mein server.closeIdleConnections() bhi bulao
    logger.info("http server drained");

    // STEP 5 — cleanup, DEPENDENCY ORDER mein (jo pehle chahiye wo baad mein bandh)
    await worker.close();     // chalu job poora karo, naya mat lo (ch 12)
    await redis.quit();       // quit() pending commands complete karta hai, disconnect() nahi
    await pool.end();         // DB pool — SABSE AAKHIR mein (in-flight queries ko chahiye tha)
    await logger.flush?.();   // buffered logs — warna aakhri log lines KHO jaati hain

    clearTimeout(forceExit);
    logger.info("shutdown complete");
    process.exit(0);
  } catch (err) {
    logger.error({ err }, "error during shutdown");
    process.exit(1);
  }
}

process.on("SIGTERM", () => shutdown("SIGTERM"));
process.on("SIGINT",  () => shutdown("SIGINT"));

Sabse Bada Gotcha — Load Balancer Ko Pata Nahi Hai

Ye wo cheez hai jo log sabse zyada miss karte hain, aur jiske bina baaki sab kuch bekaar ho jaata hai.

timing — do alag systems, koi coordination nahi
t=0.0s   SIGTERM aaya
t=0.0s   ❌ server.close() turant kar diya
t=0.1s   LB ko abhi tak KUCH pata nahi — uska agla health check t=5s pe hai
t=0.2s   LB ne ek request bheji → connection refused → 502 user ko
t=0.5s   LB ne aur requests bheji → aur 502s
t=5.0s   LB ko readiness fail dikha
t=15.0s  LB ne (3 consecutive failures ke baad) instance ko hataya
// → 15 second tak 502s. Har deploy pe. Har instance pe.

// ✅ Sahi timing
t=0.0s   SIGTERM → readiness = 503, par server CHALU hai
t=0.2s   LB ki request aayi → NORMALLY serve hui ✅
t=5.0s   LB ka health check fail hua (1/3)
t=10.0s  fail (2/3)
t=15.0s  fail (3/3) → LB ne instance hataya, ab traffic aana BAND
t=15.0s  ab server.close() — koi nayi request aa hi nahi rahi
t=17.0s  in-flight requests poori hui → drained
t=18.0s  cleanup → exit(0)                    // ZERO 502s

// Wait duration ka formula:
//   (health check interval × failure threshold) + network margin
//   AWS ALB default: 30s interval × 2 = 60s+ (ise kam karo, jaise 5s × 2)
//   k8s: readinessProbe periodSeconds × failureThreshold
⚠️ Grace period wait + drain se lamba hona chahiye

Agar tumhara wait 10s hai aur drain 5s le sakta hai, toh total 15s+ chahiye — par Kubernetes ka default terminationGracePeriodSeconds 30s hai aur Docker ka 10s. Docker default pe tumhara process wait ke beech hi SIGKILL ho jayega — matlab tumne graceful shutdown likha toh hai, par wo kabhi complete hi nahi hota. Ye budget ch 14 ke timeout budget jaisa hi hai: bahar wali seema andar wale sab kaamon se badi honi chahiye.

Kubernetes Lifecycle

k8s pod termination — aur ek race condition
# Pod delete hone pe k8s DO KAAM SAATH-SAATH karta hai (koi order guarantee nahi):
#   A. Pod ko Service endpoints se hataya jaata hai (kube-proxy/ingress update)
#   B. Container ko SIGTERM bheja jaata hai
# Endpoint propagation mein time lagta hai → SIGTERM ke BAAD bhi traffic aa sakta hai.
# Isiliye app ke andar wala wait (step 2) zaroori hai — ya preStop hook.

spec:
  terminationGracePeriodSeconds: 45   # SIGTERM se SIGKILL tak. wait+drain se BADA
  containers:
    - name: api
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 10"]
      # preStop SIGTERM se PEHLE chalta hai aur block karta hai —
      # endpoint propagation ka time yahan mil jaata hai.
      # ⚠️ preStop ka time bhi grace period ke ANDAR se hi jaata hai.

      readinessProbe:
        httpGet: { path: /health/ready, port: 3000 }
        periodSeconds: 5
        failureThreshold: 2       # 10s mein hat jayega

      livenessProbe:
        httpGet: { path: /health/live, port: 3000 }
        periodSeconds: 10
        failureThreshold: 3
        # ⚠️ liveness ko shutdown ke dauraan FAIL mat hone do —
        #    warna k8s container ko restart/kill kar dega beech mein hi
📌 PID 1 problem — Docker mein ek classic

Container mein tumhara process PID 1 hota hai, aur Linux mein PID 1 ke liye default signal handlers nahi chalte — agar tumne explicitly handler register nahi kiya toh SIGTERM chupchaap ignore ho jaata hai aur 10s baad SIGKILL aata hai. Aur agar tum CMD npm start likhte ho, toh npm PID 1 banta hai aur wo signals apne child (tumhare node process) ko forward nahi karta. Fix: CMD ["node", "server.js"] (exec form) use karo, aur docker run --init ya tini ko init process ki tarah lagao. Ye bug bilkul silent hota hai — tumhara shutdown code kabhi chalta hi nahi.

Workers Aur Cron Jobs

HTTP server ke liye "drain" ka matlab saaf hai. Workers (ch 12) ke liye thoda alag hai — aur unke liye ye zyada important hai, kyunki wahan kaam adhoora rah sakta hai:

worker shutdown
async function shutdownWorker() {
  // 1. Naye messages lena BAND karo (poll loop rok do)
  worker.pause();

  // 2. Chalu jobs ko poora hone do — bounded wait ke saath
  await Promise.race([
    worker.waitForActiveJobs(),
    sleep(20_000),
  ]);

  // 3. Jo abhi bhi chal rahe hain unhe ACK MAT karo —
  //    broker visibility timeout ke baad unhe dobara deliver karega,
  //    aur idempotent worker (ch 12) usse safely handle kar lega.
  await worker.close();
}
// YAHI wajah hai ki at-least-once + idempotency non-negotiable hai:
// shutdown ke waqt duplicate delivery ek NORMAL cheez hai, exception nahi.

// Long-running jobs (2 ghante wala import) grace period mein poore ho hi nahi sakte.
// Solution: unhe chhote chunks mein todo (ch 12) taaki progress bache aur
// restart ke baad wahin se continue ho.

🧠 Test karo — warna ye code sirf dikhawa hai

Graceful shutdown ek aisa code hai jo likhna aasaan hai aur galat hona bahut aasaan hai, kyunki wo normal testing mein kabhi chalta hi nahi. Simple test: load generator chalao (hey -z 60s http://localhost:3000/orders), beech mein kill -TERM <pid> maaro, aur dekho — zero non-2xx responses aane chahiye, aur logs mein "shutdown complete" dikhna chahiye. Agar 502 dikha, ya "shutdown timed out" dikha, toh kuch galat hai. Ye 5 minute ka test har service ke liye ek baar karna zaroori hai.

Key Takeaways

  • Shutdown ek roz ka event hai — har deploy, autoscale, node drain, spot reclaim pe.
  • Poora kaam SIGTERM aur SIGKILL ke beech ki window mein hota hai (Docker 10s, k8s 30s default).
  • Sahi order: readiness fail → wait → server.close() → drain → cleanup → exit(0).
  • Step 2 (jaanbujh ke wait) sabse zyada bhoola jaata hai — LB ko abhi pata hi nahi ki instance ja raha hai.
  • Wait duration = (health check interval × failure threshold) + margin.
  • Liveness fail mat karo shutdown ke dauraan — sirf readiness. Warna orchestrator beech mein hi maar dega.
  • Grace period wait + drain + cleanup se bada hona chahiye, warna shutdown code kabhi complete hi nahi hoga.
  • Cleanup dependency order mein: worker → redis → DB pool sabse aakhir → logs flush.
  • Force-exit timeout ek safety net hai (grace period se kam), aur .unref() ke saath.
  • PID 1 problem: CMD npm start signals forward nahi karta; exec form + --init/tini use karo. Ye bug bilkul silent hota hai.
  • k8s endpoint removal aur SIGTERM saath-saath hote hain — koi order guarantee nahi. preStop: sleep ya app-level wait chahiye.
  • Workers: pause → active jobs poore hone do → baaki ko ack mat karo (broker redeliver karega, idempotency bacha legi — ch 12).
  • Graceful shutdown ko test karo: load ke beech kill -TERM, aur zero non-2xx expect karo.

🎯 Interview Questions

Q1. "Graceful shutdown kaise implement karoge?"

SIGTERM/SIGINT pe: (1) readiness probe ko 503 karo par server chalu rakho; (2) LB ko instance hatane ka time do (health check interval × failure threshold + margin) — is dauraan requests normally serve karo; (3) server.close() — naye connections band, purane chalu; (4) in-flight requests drain hone do; (5) cleanup dependency order mein (worker → redis → DB pool → logs flush); (6) exit(0). Saath mein ek force-exit timeout safety net, jo grace period se kam ho.

Q2. "Deploy ke waqt users ko 502 mil rahe hain. Kyun?"

Sabse likely: process SIGTERM pe turant band ho raha hai, par load balancer ko abhi pata nahi chala — uska agla health check kuch second baad hai, aur usse pehle wo traffic bhejta rehta hai → connection refused → 502. Fix wo wait window hai: pehle readiness fail karo, phir LB ke hatane tak normally serve karte raho, uske baad close karo. Doosri possibility: CMD npm start ki wajah se SIGTERM node tak pahunch hi nahi raha, aur 10s baad SIGKILL aa raha hai.

Q3. "SIGTERM aur SIGKILL mein farq?"

SIGTERM (15) polite request hai — process usse catch karke cleanup kar sakta hai. SIGKILL (9) OS level pe turant maarta hai, catch ho hi nahi sakta, koi cleanup nahi. Orchestrator pehle SIGTERM bhejta hai aur grace period deta hai; us window mein exit na hua toh SIGKILL. Isliye poora graceful shutdown us window ke andar fit hona chahiye — warna wo likha hone ke bawajood kabhi complete nahi hoga.

Q4. "Shutdown ke waqt worker ka chalu job kya hoga?"

Pehle naye messages lena band karo (pause), phir chalu jobs ko bounded time tak poora hone do. Jo us waqt tak poore nahi hue unhe ack mat karo — broker visibility timeout ke baad unhe dobara deliver kar dega. Isi wajah se at-least-once + idempotent worker (ch 12) zaroori hai: shutdown ke waqt duplicate delivery normal hai, exception nahi. Lambe jobs ko chhote chunks mein todo taaki wo grace period mein fit ho jaayein aur progress bache.

Q5. "Container mein SIGTERM ignore ho raha hai. Kya problem hai?"

PID 1 problem. Container mein tumhara process PID 1 hota hai, aur PID 1 ke liye Linux default signal handlers nahi chalata — handler register na ho toh SIGTERM ignore ho jaata hai. Aur CMD npm start (shell form) mein npm/shell PID 1 banta hai aur signals apne child ko forward nahi karta. Fix: exec form CMD ["node", "server.js"], aur docker run --init ya tini ko init process banao.
