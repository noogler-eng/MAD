Parse Ho Gaya, Phir Validation Kyun

Ch 5 ke end pe ek line thi: "parse safal ≠ data valid". Usko concrete karte hain. JSON.parse() ke safal hone ka matlab sirf itna hai ki syntax theek tha — braces balanced the, quotes band the. Uske baad bhi ye sab ek "valid" JSON hai:

ye saara "valid JSON" hai — aur poora garbage bhi
POST /users
{
  "name":    "",                  // khali — DB mein NOT NULL hai par empty string allowed hai
  "age":     -5,                  // negative umar
  "email":   "hello",             // @ hai hi nahi
  "role":    "admin",             // ← privilege escalation ki koshish (ch 6)
  "balance": 99999999,            // server-controlled field, client bhej raha hai
  "bio":     "<script>…</script>", // stored XSS payload (ch 18)
  "tags":    [ … 50000 items … ]  // memory / DB blow up
}
// JSON.parse() → ✅ safal. Har field "theek se" parse hui.
// Business ke hisaab se → ❌ har ek line galat hai.

Bina validation ke ye object seedha service layer mein, phir DB mein chala jaayega. Aur asli problem ye hai ki nuksaan turant nahi dikhta — record ban jaata hai, aur mahine baad koi report ya email job crash karti hai age: -5 pe. Bad data ek delayed-action bug hai.

🧠 Validation "extra safety" nahi hai — wo type system ka extension hai

Tumhare code mein har function assume karta hai ki uske arguments sahi shape ke hain (user.email ek email hai, order.total positive hai). Compiler ye assumption tumhare code ke andar enforce karta hai. Par network se aane wale data pe compiler ka koi zor nahi — wahan any aata hai. Validation layer wo jagah hai jahan any ko ek asli type mein badla jaata hai. Iske bina tumhara poora type system ek jhooth hai.

Validation Ke Teen Alag Levels

"Validation" ek shabd mein teen bahut alag cheezein aati hain, aur ye teenon alag jagah hoti hain. Inko mila dena bahut common design galti hai:

LevelSawaalKahanKya chahiyeFail code
1. Syntactic Shape sahi hai? Field maujood hai? Type theek hai? Boundary — schema Sirf request 422
2. Semantic Values apne aap mein sensible hain? (age 0–150, endDate > startDate) Boundary — schema refinements Sirf request 422
3. Business rules Ye action abhi, is state mein allowed hai? Service layer (ch 8) DB access 409 / 403
teeno ka farq ek example mein
// 1. SYNTACTIC — request akeli dekh ke pata chal jaata hai
email is string?  quantity is number?  productId maujood hai?

// 2. SEMANTIC — abhi bhi sirf request se, par values ka matlab check
quantity > 0?  email mein "@" hai?  deliveryDate future mein hai?

// 3. BUSINESS — DB ke bina jawab dena NAAMUMKIN hai
kya ye product exist karta hai?          // → DB lookup
kya stock mein itni quantity hai?        // → DB lookup
kya is user ka credit limit bacha hai?   // → DB lookup
kya order pehle se cancel ho chuka hai?  // → DB lookup
⚠️ Business rules ko schema mein mat ghusao

Common galti: schema ke andar se DB call karna ("email unique hai kya?"). Isse do problem hoti hain — validation layer ab DB pe depend karti hai (test karna mushkil, aur slow), aur ek race condition paida hoti hai: check aur insert ke beech koi aur wahi email register kar sakta hai. Uniqueness ka sahi enforcement DB constraint hai; tum insert try karo aur unique-violation error ko pakad ke 409 Conflict mein badlo. Check-then-act pattern concurrency mein hamesha toot-ta hai (ch 10, ch 21).

Schema-First Approach — Zod Ke Saath

Manual if checks likhna teen wajah se haar jaata hai: wo verbose hote hain, ek jagah update karke doosri bhool jaate ho, aur wo type nahi dete — TypeScript ko abhi bhi nahi pata ki req.body kya hai. Schema libraries dono ek saath deti hain: runtime check aur static type.

manual checks vs schema — same rules
// ❌ MANUAL — 20 lines, aur TS ko ab bhi kuch pata nahi
if (!req.body.email) return res.status(400).json({ e: "email required" });
if (typeof req.body.email !== "string") return …
if (!req.body.email.includes("@")) return …
if (typeof req.body.age !== "number") return …
// … aur 16 lines. Ek naya field add karo → 4 aur lines, kahin bhoolne ka risk.
// Aur sabse bada issue: ye pehle error pe ruk jaata hai —
// user ko ek-ek karke 5 baar form bharna padega.

// ✅ SCHEMA — declarative, aur type FREE mein milta hai
const CreateUser = z.object({
  email: z.string().email().toLowerCase().trim(),  // validate + normalize ek saath
  name:  z.string().trim().min(1).max(100),        // min(1) — khali string reject
  age:   z.number().int().min(0).max(150),
  tags:  z.array(z.string()).max(20).default([]),      // upper bound = DoS defense
  bio:   z.string().max(500).optional(),
}).strict();   // ← CRITICAL: unknown fields pe ERROR do

// TypeScript type schema se khud nikal aata hai — ek hi source of truth
type CreateUserInput = z.infer<typeof CreateUser>;
// { email: string; name: string; age: number; tags: string[]; bio?: string }

// use karna
const result = CreateUser.safeParse(req.body);      // throw nahi karta
if (!result.success) return res.status(422).json(format(result.error));
const input = result.data;    // ← ab ye CreateUserInput hai, `any` nahi
⚠️ .strict() ya .strip() — ye choice security hai

Default mein zyadatar libraries unknown fields ko chupchaap rehne deti hain ya hata deti hain. Agar wo rehte hain aur tum {...req.body} DB mein daal dete ho, toh client {"role":"admin","balance":999999} bhej ke apne aap ko upgrade kar sakta hai — isko mass assignment vulnerability kehte hain (Rails, Django, Node — sab mein hua hai). Do safe options: .strict() (unknown field = error, best for APIs) ya .strip() (chupchaap hata do). Kabhi passthrough mat karo.

Coercion — Silent Killer

Ch 4 se yaad karo: URL mein types exist hi nahi karte. Query aur path params hamesha strings hote hain. Isliye coercion (type conversion) ek explicit step hona chahiye — aur wo bahut dhoke wala hota hai:

coercion ke classic traps
// GET /users?page=2&limit=50&active=false&ids=1,2,3
req.query
// → { page: "2", limit: "50", active: "false", ids: "1,2,3" }  ← SAB strings

// ── trap 1: boolean ─────────────────────────────────────────
Boolean("false")      // → true !! non-empty string hamesha truthy hai
if (req.query.active) // → hamesha chalega, chahe "false" ho

// ── trap 2: number ──────────────────────────────────────────
parseInt("12abc")     // → 12   (silently kaat deta hai!)
Number("")            // → 0    (khali string zero ban gayi)
Number(" ")           // → 0
parseInt("abc")       // → NaN  (aur NaN > 0 → false, NaN === NaN → false)

// ── trap 3: array — ek value vs kai values ──────────────────
// ?tag=a       → "a"          (string)
// ?tag=a&tag=b → ["a","b"]    (array!)
// tumhara .map() pehle case mein crash karega

// ✅ Sahi: coercion ko schema mein explicit karo, bounds ke saath
const ListQuery = z.object({
  page:   z.coerce.number().int().min(1).default(1),
  limit:  z.coerce.number().int().min(1).max(100).default(20),
  // ↑ max(100) zaroori hai — warna ?limit=999999999 se DB dump ho jayega
  active: z.enum(["true", "false"]).transform(v => v === "true").optional(),
  // ↑ Boolean() kabhi mat use karo — enum se explicitly map karo
  ids:    z.string().transform(s => s.split(",")).pipe(z.array(z.string().uuid()).max(50)),
});
📌 Pagination pe upper bound ek availability control hai

limit pe .max(100) na lagana ek real production incident ka nuskha hai: ek client (ya crawler) ?limit=1000000 bhejta hai, tumhari query poori table load karti hai, memory bharti hai, aur poora process gir jaata hai — ek hi request se. Ye ch 19 ka "one bad request can take down the service" wala pattern hai, aur iska fix yahan boundary pe hai.

"Parse, Don't Validate" — Sabse Bada Idea

Ye is chapter ka sabse important mental model hai, aur ye sirf ek naam ka farq nahi hai — ye poore codebase ka shape badal deta hai.

  • Validate = data ko dekho, "theek hai" bolo, aur wahi original data aage bhej do. Type nahi badla — toh downstream code ko pata hi nahi ki check hua tha, aur wo dobara check karta hai.
  • Parse = data ko dekho aur ek naya, narrower type return karo. Ab type system khud guarantee karta hai — downstream code check kar hi nahi sakta, kyunki karne ki zaroorat hi nahi.
farq — aur wo farq downstream mein kya karta hai
// ── VALIDATE style ──────────────────────────────────────────
function validateUser(data: any): boolean { … }

if (!validateUser(req.body)) return res.status(422).end();
createUser(req.body);   // type abhi bhi `any` hai

function createUser(data: any) {
  if (!data.email) throw …    // ← defensive check DOBARA
  // kyun? kyunki type kuch guarantee nahi karta.
  // Ye check har layer mein repeat hoga, aur ek din koi bhool jayega.
}

// ── PARSE style ─────────────────────────────────────────────
function parseUser(data: unknown): CreateUserInput { … }   // naya TYPE return

const input = parseUser(req.body);   // ab type CreateUserInput hai
createUser(input);

function createUser(input: CreateUserInput) {
  input.email.toLowerCase();   // ✅ safe — compiler jaanta hai ye string hai
  // koi defensive check NAHI. Invalid data yahan pahunch hi nahi sakta —
  // kyunki wo is type ka ho hi nahi sakta.
}
🧠 "Make illegal states unrepresentable"

Isko aur aage le jao: string ki jagah ek Email type banao jo sirf parseEmail() se hi ban sakta ho. Ab galat email wala Email exist hi nahi kar sakta — bug likhna compile hi nahi hoga. Ye TypeScript mein branded types se, Rust/Haskell mein newtypes se hota hai. Ek chhota practical version: ID types ko alag rakho (UserId vs OrderId), taaki galti se ek ki jagah doosra pass karna compile error ban jaaye — ye ek surprisingly common bug hai.

Transformation — Input, Domain, Output Alag Cheezein Hain

Validation ke saath hi doosra kaam hota hai: shape badalna. Beginners ek hi object ko poore stack mein ghumate hain — aur wahi data leak ka sabse common source hai.

teen alag models — teen alag zimmedariyan
// 1. INPUT model — client kya bhej SAKTA hai
type CreateUserInput = { email: string; name: string; password: string };
// note: koi `id`, `role`, `createdAt` nahi — ye server decide karta hai

// 2. DOMAIN model — DB mein / memory mein poora record
type User = {
  id: string; email: string; name: string;
  passwordHash: string;      // ← ye kabhi bahar nahi jaana chahiye
  role: "user" | "admin";   // ← server-controlled
  internalNotes: string;     // ← support team ke liye, user ke liye nahi
  createdAt: Date;
};

// 3. OUTPUT model — client ko kya DIKHNA chahiye
type UserResponse = { id: string; name: string; createdAt: string };

// ✅ EXPLICIT mapping — allowlist, denylist nahi
function toResponse(u: User): UserResponse {
  return { id: u.id, name: u.name, createdAt: u.createdAt.toISOString() };
}
// Naya sensitive field DB mein add hua? Automatically leak NAHI hoga,
// kyunki mapping explicit hai — usko yahan likhna padega.

// ❌ GALAT — delete se fields hatana (denylist)
const safe = { ...user }; delete safe.passwordHash;
// Kal koi `ssn` column add karega aur wo CHUPCHAAP API mein aa jayega.
// Denylist hamesha peeche reh jaati hai; allowlist nahi.

// ❌ GALAT — poora object bhej dena
res.json(user);   // passwordHash, internalNotes, sab wire pe. Real breach.

Error Responses Jo Actually Kaam Aate Hain

Validation fail hona expected hai — ye error nahi, normal flow ka hissa hai. Response ka kaam client ko theek karne layak banana hai: saari galtiyan ek saath, field ke naam ke saath, machine-readable code ke saath.

accha validation error response
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json

{
  "error": "validation_failed",     // machine-readable — client isse branch karta hai
  "message": "Request validation failed",
  "details": [                        // SAARI errors ek saath — pehli pe ruko mat
    { "field": "email",    "code": "invalid_format", "message": "Must be a valid email" },
    { "field": "age",      "code": "too_small",      "message": "Must be at least 0" },
    { "field": "tags.3",  "code": "invalid_type",   "message": "Expected string" }
    //        ↑ nested path — frontend seedha us field pe error dikha sakta hai
  ],
  "requestId": "req_8f3a2b"          // logs se jodne ke liye (ch 16)
}
❌ BuraKyun
400 "Bad Request"Kaunsa field? Client guess karega
Ek baar mein ek hi errorUser ko 5 baar form submit karna padega
Sirf English message, koi code nahiClient message string pe branch karega — text badla toh toota
500 validation fail peYe client ki galti hai; 5xx se alerts galat trigger honge (ch 3)

Validation Kahan-Kahan Lagti Hai

Sabse common blind spot: log sirf req.body validate karte hain. Par har jagah jahan bahar se data andar aata hai, wahan ek boundary chahiye:

  • Request body, query, params, headers — obvious wala.
  • Webhooks — koi bhi POST kar sakta hai. Payload validate karo aur signature verify karo.
  • Queue messages (ch 12) — purane format ka message queue mein pada ho sakta hai jab producer already deploy ho chuka ho. Consumer ko validate karna hi padega.
  • Third-party API responses — unka schema tumhare control mein nahi hai aur bina bataye badal sakta hai. Jo bhi unse aaye, use parse karo.
  • Environment variables (ch 15) — boot pe validate karo. Missing DATABASE_URL ka pata deploy ke waqt chalna chahiye, 3 ghante baad pehli request pe nahi.
  • File uploads — size, MIME type, aur actual content (extension jhooth bol sakti hai).
⚠️ Client-side validation security nahi hai

Frontend validation ek UX feature hai — user ko turant feedback deti hai. Wo security nahi hai, kyunki curl tumhare frontend se guzarta hi nahi. Rule ekdum simple: client pe validate karo UX ke liye, server pe validate karo correctness ke liye — aur server wali kabhi optional nahi hai. (Yahi baat ch 6 mein "button chhupana security nahi hai" ke roop mein aayi thi.)

Key Takeaways

  • JSON.parse() safal hona sirf syntax ki guarantee hai — age: -5 aur role: "admin" dono "valid JSON" hain.
  • Validation type system ka extension hai: wo jagah jahan network ka any ek asli type banta hai.
  • Boundary ke andar defensive checks nahi hone chahiye. Service layer mein if (!x) likhna pad raha hai = boundary leak kar rahi hai.
  • Teen levels: syntactic aur semantic boundary pe (422), business rules service layer mein (409/403) kyunki unhe DB chahiye.
  • Uniqueness ko schema mein mat check karo — wo race condition hai. DB constraint lagao aur violation ko 409 mein badlo.
  • Schema-first se runtime check aur static type ek hi source se milte hain.
  • .strict()/.strip() zaroori hai — passthrough mass assignment vulnerability hai.
  • Query/path params hamesha strings hain. Boolean("false") === true, parseInt("12abc") === 12, Number("") === 0.
  • limit pe upper bound ek availability control hai — uske bina ek request service gira sakti hai.
  • Parse, don't validate — narrower type return karo, boolean nahi. Tab downstream check karna possible hi nahi rehta.
  • Input / domain / output — teen alag models. Output mapping allowlist ho, delete wali denylist nahi.
  • Validation error: 422, saari errors ek saath, field path + machine-readable code ke saath.
  • Boundary sirf request pe nahi — webhooks, queue messages, 3rd-party responses, env vars, uploads sab pe.

🎯 Interview Questions

Q1. "Deserialization ke baad validation kyun chahiye?"

Parsing sirf syntax check karti hai — braces balanced the. Semantics uska kaam hai hi nahi: {"age": -5, "role": "admin"} perfectly valid JSON hai. Validation wo boundary hai jahan untrusted any ek trusted domain type banta hai, taaki uske aage ka poora code apne assumptions pe bharosa kar sake.

Q2. "'Parse, don't validate' ka matlab?"

Validation function boolean return karta hai — data ka type nahi badalta, isliye har downstream layer defensively dobara check karti hai aur ek din koi bhool jaata hai. Parsing ek naya narrower type return karta hai (unknown → CreateUserInput) — ab guarantee type system mein encode ho gayi hai, aur invalid data us type ka ho hi nahi sakta. Extreme version: branded types, jahan galat state represent hi nahi ho sakti.

Q3. "Mass assignment vulnerability kya hai?"

Jab request body ko bina filter kiye seedha model/DB mein spread kar diya jaaye (User.create({...req.body})). Attacker {"role":"admin"} ya {"balance":999999} add kar deta hai aur wo persist ho jaata hai. Fix: schema pe .strict()/.strip(), aur ek explicit input model jisme server-controlled fields (id, role, createdAt) hain hi nahi.

Q4. "Email uniqueness kahan check karoge?"

Schema mein nahi — wo ek business rule hai jise DB chahiye, aur check-then-insert ek race condition hai (do concurrent requests dono check pass kar lenge). Sahi jawab: DB pe UNIQUE constraint, insert try karo, aur unique-violation error ko catch karke 409 Conflict return karo. UX ke liye ek pre-check add kar sakte ho, par correctness constraint se aati hai, check se nahi.

Q5. "?limit=1000000 aa gaya toh?"

Bina upper bound ke wo query poori table memory mein le aayegi aur process gira degi — ek request se full outage. Isliye schema mein limit pe .max(100) aur ek sensible .default(20) hona chahiye. Ye validation ka availability wala pehlu hai, sirf correctness ka nahi.
