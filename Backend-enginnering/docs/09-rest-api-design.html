Ab tak sab kuch andar ka tha. API design bahar ka contract hai — aur contract ki ek khaas property hai: usse badalna sabse mehnga hota hai. REST Actually Kya Hai (Aur Kya Nahi)

REST ek architectural style hai (Roy Fielding, 2000), protocol nahi. Uske constraints mein se jo backend ke liye actually matter karte hain:

  • Client-server — alag-alag evolve kar sakte hain (ch 2).
  • Stateless — har request self-contained (ch 3). Yahi horizontal scaling deta hai.
  • Uniform interface — resources ki identity URL mein, manipulation standard methods se.
  • Cacheable — response batata hai ki wo cache ho sakta hai ya nahi.
  • Layered — client ko pata nahi ki wo proxy se baat kar raha hai ya origin se (ch 2 ka nginx).
📌 Practical sach — jise log "REST" kehte hain wo "HTTP + JSON + resource URLs" hai

Fielding ke original definition mein HATEOAS (response mein hi agle actions ke links) bhi zaroori tha. Practice mein 99% "REST APIs" wo nahi karti, aur wo theek hai. Purity ke chakkar mein mat pado — asli goal predictability hai: ek naya developer tumhari ek endpoint dekh ke baaki 50 ka behaviour guess kar sake. Consistency > correctness-by-the-book.

Resource Modelling — Noun, Verb Nahi

Central idea: URL ek cheez (noun) ko identify karta hai, aur method batata hai us cheez ka kya karna hai. Verb URL mein aana matlab tum method ka kaam URL se kara rahe ho.

RPC-style vs resource-style
// ❌ RPC style — har action ka apna endpoint, koi pattern nahi
POST /getUser?id=42
POST /createOrder
POST /updateOrderStatus
POST /deleteUserById
// 200 endpoints = 200 alag naam yaad rakhne padenge. Kuch bhi guess nahi kar sakte.

// ✅ Resource style — ek noun, standard methods
GET    /users          // collection — list
POST   /users          // collection pe create → 201 + Location
GET    /users/42       // ek resource
PATCH  /users/42       // partial update
PUT    /users/42       // full replace (idempotent — ch 3)
DELETE /users/42       // → 204 No Content

// Nesting — sirf jab child parent ke BINA meaningless ho
GET  /users/42/orders  // is user ke orders
POST /users/42/orders

// ⚠️ 2 level se zyada mat karo
// ❌ /users/42/orders/99/items/7/reviews/3   — bhayanak
// ✅ /reviews/3   — agar review ki apni identity hai toh usko top-level rakho
ConventionKaroKyun
Plural nouns/users, /users/42Consistent — collection aur item ek hi naam ke
Lowercase + hyphen/order-itemsURLs case-sensitive hote hain; underscore hyperlink underline mein chhup jaata hai
Trailing slash nahi/usersEk hi canonical form — warna 404 mysteries (ch 4)
File extension nahi/users + Accept headerFormat content negotiation se, URL se nahi
ID kabhi sequential guess-able na hoUUID / ULIDSequential IDs se total count leak hoti hai aur enumeration aasaan ho jaati hai (ch 18)

Wo Cheezein Jo Resource Mein Fit Nahi Hoti

Har operation ek noun nahi hota. "Password reset karo", "order cancel karo", "email bhejo" — ye actions hain. Teen approaches, badhte hue practicality ke saath:

actions ko model karne ke teen tareeke
// ── 1. State change ko ek FIELD ki tarah dekho (sabse RESTful) ──
PATCH /orders/99   { "status": "cancelled" }
// ✅ shuddh REST. ❌ par "cancel" ke saath aur logic ho (refund, email, restock)
//    toh ye chhupa deta hai ki ye ek simple field update NAHI hai.
//    Aur "status: shipped" client ko kabhi set nahi karne dena chahiye.

// ── 2. Sub-resource banao (accha jab action ka apna record ho) ──
POST /orders/99/cancellation   { "reason": "changed mind" }
// ✅ cancellation ek CHEEZ ban gayi — timestamp, reason, kisne ki, sab store hoga
// ✅ GET /orders/99/cancellation bhi ab meaningful hai

// ── 3. Action endpoint (pragmatic — sabse common) ──────────
POST /orders/99/cancel
POST /users/42/reset-password
POST /invoices/7/send
// "Pure REST" nahi hai, par SAAF hai. Stripe, GitHub, Slack — sab ye karte hain.
// Rule: POST use karo (side effect hai), aur verb ko resource ke NEECHE rakho —
// /cancelOrder?id=99 nahi.
🧠 Kab kaunsa

Agar operation sach mein ek field ka update hai → PATCH. Agar us action ka apna record banta hai (kisne kiya, kab, kyun) → sub-resource. Agar wo ek multi-step workflow trigger karta hai → action endpoint. Sabse bada red flag: client ko koi aisa field set karne dena jo actually server ka faisla hai (status: "paid"). Wo authorization bug hai, design taste ka sawaal nahi.

Pagination — Offset vs Cursor

Koi bhi collection endpoint jo saara data return karta hai, wo ek future outage hai (ch 7 ka limit wala point). Pagination optional nahi hai. Do tareeke hain, aur inka farq sirf performance ka nahi — correctness ka hai.

cursor pagination — implementation
// GET /orders?limit=20&cursor=eyJpZCI6IjAxSF...

// cursor ek OPAQUE base64 string honi chahiye — client usse parse na kare
const after = cursor ? JSON.parse(atob(cursor)) : null;

// Sorting key UNIQUE aur STABLE honi chahiye.
// created_at akela kaafi NAHI — same timestamp wale rows pe pagination toot-ti hai.
// Isliye tie-breaker ke saath composite key: (created_at, id)
const rows = await db.query(
  `SELECT * FROM orders
    WHERE user_id = $1
      AND ($2::timestamptz IS NULL OR (created_at, id) < ($2, $3))
    ORDER BY created_at DESC, id DESC
    LIMIT $4`,                          // ← index: (user_id, created_at DESC, id DESC)
  [userId, after?.createdAt, after?.id, limit + 1]
);                                       // ↑ limit+1 — ek extra row maango

const hasMore = rows.length > limit;    // extra row mila? matlab aur data hai
const items   = rows.slice(0, limit);   // extra row response se hata do
// Ye trick ek alag COUNT(*) query bacha leti hai — wo bade tables pe mehngi hai.

res.json({
  data: items.map(toResponse),
  "pagination": {
    nextCursor: hasMore
      ? btoa(JSON.stringify({ createdAt: last.createdAt, id: last.id }))
      : null,                          // null = aakhri page
    hasMore,
  },
});

Filtering, Sorting, Sparse Fields

query param conventions
// filtering — flat, predictable
GET /orders?status=paid&min_total=1000&created_after=2026-01-01

// sorting — "-" se descending
GET /orders?sort=-created_at,total

// sparse fields — sirf ye fields do (payload chhota)
GET /orders?fields=id,total,status

// embedding — N+1 requests bachane ke liye
GET /orders/99?include=items,customer

// ⚠️ SECURITY: filter aur sort fields ko ALLOWLIST karo
const SORTABLE = new Set(["created_at", "total", "status"]);
if (!SORTABLE.has(field)) throw new ValidationError("invalid sort field");
// Sort/filter column ko kabhi seedha SQL mein mat daalo — ye SQL injection ka
// wo raasta hai jise parameterized queries BACHA nahi sakti (column names
// parameterize ho hi nahi sakte). Aur bina index wale column pe sort allow
// karna ek performance DoS hai (ch 10).

Idempotency Keys — Mechanism

Ch 3 mein problem set ki thi: client ne POST /payments bheja, timeout ho gaya, aur ab wo jaanta hi nahi ki charge hua ya nahi. Retry kare toh double charge, na kare toh possible lost payment. Ab uska solution.

idempotency key — server side
// Client har LOGICAL operation ke liye ek unique key generate karta hai
// aur RETRY pe WAHI key dobara bhejta hai.
POST /payments
Idempotency-Key: 01HQ8Z3M2K4N5P6Q7R8S9T   // UUID/ULID, client-generated
{ "amount_paise": 199900, "order_id": "99" }

async function handlePayment(key, body, userId) {
  // 1. Key ko ATOMICALLY reserve karo. Ye INSERT hi lock ka kaam karta hai —
  //    "pehle SELECT karke dekho" wala pattern race condition hai (ch 7).
  const reserved = await db.query(
    `INSERT INTO idempotency_keys (key, user_id, request_hash, status)
     VALUES ($1, $2, $3, 'in_progress')
     ON CONFLICT (key) DO NOTHING
     RETURNING id`,
    [key, userId, sha256(body)]
  );

  if (reserved.rowCount === 0) {
    // Key pehle se hai → ye ek RETRY hai
    const prev = await db.query(`SELECT * FROM idempotency_keys WHERE key = $1`, [key]);

    // Same key par ALAG body? Client ki bug hai — chupchaap purana result mat do.
    if (prev.request_hash !== sha256(body))
      throw new ConflictError("idempotency key reused with different payload");

    if (prev.status === "in_progress")
      throw new ConflictError("request already in progress");   // 409

    return JSON.parse(prev.response_body);   // ✅ WAHI purana response wapas
  }

  // 2. Pehli baar — asli kaam karo
  const payment = await paymentService.charge(body);

  // 3. Result store karo taaki retry pe wahi mile
  await db.query(
    `UPDATE idempotency_keys SET status='completed', response_body=$2 WHERE key=$1`,
    [key, JSON.stringify(payment)]
  );
  return payment;
}
// Keys ko 24-48h baad expire kar do — ye table warna infinitely badhta hai.
⚠️ Fintech mein ye optional nahi hai

Har paisa-chhoone wala endpoint (POST /payments, /refunds, /transfers) mein idempotency key honi chahiye. Bina iske, ek network glitch ya client retry double charge banata hai — aur uska pata customer complaint se chalta hai, monitoring se nahi. Stripe, Razorpay, aur har serious payment API ye header support karti hai; tumhari API ko bhi karna chahiye. Aur key client generate karta hai, server nahi — kyunki server ko pata hi nahi ki do requests "same logical operation" hain.

Lost Update Problem Aur ETags

Do users ek hi resource ko ek saath edit kar rahe hain. A padhta hai, B padhta hai, A likhta hai, B likhta hai — A ka change chupchaap gayab. Isko lost update kehte hain, aur ye bug tab tak dikhta nahi jab tak koi shikayat na kare.

optimistic concurrency — ETag + If-Match
// 1. GET pe server current version ka tag deta hai (ch 3 ka ETag)
GET /documents/7
→ 200 OK
  ETag: "v12"              // version number ya content ka hash
  { "title": "Draft", "version": 12 }

// 2. Update ke waqt client wahi tag wapas bhejta hai
PATCH /documents/7
If-Match: "v12"            // "main v12 ke upar edit kar raha hoon"
{ "title": "Final" }

// 3. Server atomically check karta hai — WHERE clause hi lock hai
UPDATE documents SET title = $1, version = version + 1
 WHERE id = $2 AND version = $3;         // ← version match hua tabhi update

// rowCount === 0 → beech mein kisi aur ne badal diya
→ 412 Precondition Failed
  { "error": "stale_version", "message": "Resource modified; re-fetch and retry" }
// Client ko ab pata hai ki conflict hua — wo re-fetch karke merge kar sakta hai,
// ya user ko dikha sakta hai. Chupchaap data kho nahi raha.
🧠 Idempotency vs optimistic locking — do alag problems

Dono "concurrency" jaisa lagta hai par bilkul alag hain. Idempotency key ek hi client ki duplicate request se bachati hai (retry ke baad double charge). ETag/If-Match do alag clients ke conflicting updates se bachata hai (lost update). Ek payment endpoint pe pehla chahiye; ek collaborative document pe doosra. Interview mein ye distinction seedha differentiate kar deta hai.

Versioning — Chaar Tareeke

TareekaExampleTrade-off
URL path /v1/users Sabse saaf aur visible; browser/curl se test karna trivial. Purist kehte hain "resource wahi hai, URL alag kyun" — par practically ye sabse common hai
Header Accept: application/vnd.api.v2+json URL saaf rehta hai, par debug/share karna mushkil — curl mein header yaad rakhna padta hai
Query param /users?version=2 Aasaan par gandha; caching aur routing mein galtiyan hoti hain
Date-based Stripe-Version: 2026-08-17 Har client apni version pe pinned; sabse powerful, par server pe har version ka transformation layer maintain karna padta hai
📌 Sabse achhi versioning = version hi na banana

Ch 5 ka schema evolution rule yahan bhi lagta hai: additive changes breaking nahi hote. Naya optional field add karna, naya endpoint add karna, response mein naya field bhejna — in sab ke liye v2 ki zaroorat nahi. v2 sirf tab chahiye jab tumhe kuch hatana ya badalna ho. Isliye din 1 se clients ko ye batao: "unknown fields ko ignore karo" — tabhi tum aage aaram se evolve kar paoge.

Error Contract

Errors bhi API ka hissa hain — utne hi documented hone chahiye jitne success responses. Ek consistent shape rakho poore API mein:

consistent error shape
{
  "error":   "insufficient_stock",   // stable machine code — client isse branch karta hai
  "message": "Product 'X' has only 2 left",  // insaan ke liye, badal sakta hai
  "details": [ … ],                    // optional — field-wise (ch 7)
  "requestId": "req_8f3a2b"            // logs se jodne ke liye (ch 16)
}
// RULE: `error` code KABHI mat badlo — wo contract hai. `message` badal sakta hai.
// Client ko kabhi message string pe branch nahi karna chahiye.

Status codes ke liye ch 3 ka mapping use karo. Do aur cheezein jo API-level pe zaroori hain:

  • 429 ke saath Retry-After — warna client aggressive retry karta hai aur load aur badhta hai (ch 14).
  • 5xx pe internal details kabhi nahi — stack trace, SQL error, ya file path leak karna attacker ko tumhare stack ka map de deta hai (ch 18). Generic message bhejo, asli error requestId ke saath log karo.

Design Checklist

Naya endpoint banate waqt ye list pe ek nazar — zyadatar API bugs inhi mein se kisi ek se aate hain:

  • ☐ URL noun hai, verb nahi. Nesting 2 level se zyada nahi.
  • ☐ Method ka contract sahi hai — GET safe hai, PUT/DELETE idempotent (ch 3).
  • ☐ Success status theek hai — 201 + Location create pe, 204 delete pe.
  • ☐ Collection endpoint pe pagination hai, aur limit pe upper bound hai (ch 7).
  • ☐ Sort/filter fields allowlisted hain.
  • ☐ Paisa/side-effect wale POST pe Idempotency-Key support hai.
  • ☐ Concurrent edit possible hai toh ETag/If-Match hai.
  • ☐ Response ek explicit output model se banta hai (allowlist), domain object seedha nahi (ch 7).
  • ☐ Server-controlled fields (id, role, status) client set nahi kar sakta.
  • ☐ Ownership check query ke andar hai (ch 6).
  • ☐ Errors mein stable error code + requestId hai; 5xx mein internals nahi.
  • ☐ IDs guess-able nahi hain (UUID/ULID).

Key Takeaways

  • API ek contract hai — code se kahin zyada mehnga badalna. Isliye din 1 se soch ke banao.
  • Practical goal purity nahi, predictability hai: ek endpoint dekh ke baaki 50 guess ho jaayein.
  • URL = noun, method = verb. Nesting 2 level tak; child ki apni identity ho toh top-level rakho.
  • Actions ke liye teen options: PATCH field, sub-resource (jab record banta ho), ya POST /orders/99/cancel. Teesra pragmatic aur common hai.
  • Client ko kabhi server-controlled field (status, role) set mat karne do — wo authorization bug hai.
  • Offset pagination sirf slow nahi, galat hai — data badalne pe items duplicate/skip hote hain. Feeds pe cursor use karo.
  • Cursor key unique + stable honi chahiye — created_at akela nahi, (created_at, id).
  • limit + 1 maango — hasMore mil jaata hai bina mehngi COUNT(*) ke.
  • Sort/filter columns allowlist karo — parameterized queries column names ko bacha nahi sakti.
  • Idempotency key duplicate requests se bachati hai (client generate karta hai); ETag/If-Match lost updates se (412). Do alag problems.
  • Best versioning = version na banana. Additive changes breaking nahi hote — clients ko unknown fields ignore karna sikhao.
  • Error mein error code stable rakho, message badal sakta hai. 5xx mein internals kabhi nahi.

🎯 Interview Questions

Q1. "Ek endpoint design karo: user apne orders dekhe."

GET /orders?status=paid&limit=20&cursor=… — /users/42/orders nahi, kyunki user apna hi data dekh raha hai aur ID context se aati hai (URL se lene pe IDOR ka darwaza khulta hai, ch 6). Cursor pagination with limit capped at 100, sort fields allowlisted, response ek explicit output model se, aur ownership WHERE user_id = ctx.user.id mein — na ki alag check mein.

Q2. "Offset vs cursor pagination?"

Offset: LIMIT 20 OFFSET 10000 — DB ko 10,020 rows padh ke 10,000 fekni padti hain, toh deep pages slow hote hain. Aur usse bada issue correctness ka hai: data badalne pe items duplicate ya skip hote hain. Cursor: last item ki key se index pe seek — har page constant time, aur stable. Trade-off: cursor mein "page 7 pe jao" aur total count nahi milte. Admin tables pe offset theek hai, feeds pe cursor.

Q3. "Double charge kaise rokoge?"

Idempotency-Key header — client har logical operation ke liye ek unique key banata hai aur retry pe wahi bhejta hai. Server usse ON CONFLICT DO NOTHING ke saath atomically reserve karta hai (SELECT-then-INSERT race condition hai), pehli baar kaam karke response store karta hai, aur usi key pe dobara aane par wahi stored response laut​a deta hai. Same key par alag payload aaye toh 409. Keys 24–48h baad expire.

Q4. "Do users ek saath edit kar rahe hain — ek ka change kho raha hai."

Lost update problem. Optimistic locking: GET pe ETag (version/hash) do, client If-Match mein wapas bheje, aur update WHERE id = $1 AND version = $2 ho — rowCount === 0 matlab beech mein koi aur badal chuka hai, toh 412 Precondition Failed. Client re-fetch karke merge kare. Pessimistic locking (row lock) bhi option hai par wo concurrency ghata deta hai aur user-facing edits ke liye practical nahi.

Q5. "API versioning kaise karoge?"

Pehla jawab: jitna ho sake version banao hi mat — additive changes (naya optional field, naya endpoint) breaking nahi hote, bas clients ko unknown fields ignore karne chahiye. Jab sach mein breaking change chahiye: URL path versioning (/v1/) sabse practical hai — visible aur debug karne mein aasaan. Date-based (Stripe style) sabse powerful hai par har version ka transformation layer maintain karna padta hai. Aur purani version ke liye ek clear deprecation timeline do.
