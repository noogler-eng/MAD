HTTP Kahan Baithta Hai — Network Stack

HTTP khud data transfer nahi karta — wo sirf format define karta hai. Actual bytes ek TCP connection pe jaate hain, jo IP packets pe jaate hain. Ye layering samajhna zaroori hai kyunki har layer alag tarah se fail hoti hai (jaise ch 2 mein timeout vs refused vs 502 dekha tha).

Request & Response Ki Anatomy

HTTP/1.1 mein message literally plain text hai — tum use telnet se haath se type kar sakte ho. Structure fixed hai: ek start line, phir headers (har ek apni line pe), phir ek blank line, phir optional body.

raw HTTP request — jo actually socket pe jaata hai
# ── start line: METHOD  TARGET  VERSION ─────────────────────
POST /api/users?verbose=true HTTP/1.1

# ── headers: "Name: value", case-insensitive names ──────────
Host: api.example.com          # HTTP/1.1 mein MANDATORY — ek IP pe kai domains isi se alag hote hain
Content-Type: application/json # body ka format — server isse parser chunta hai
Content-Length: 46             # body kitne BYTES ki hai — server itne hi padhega
Authorization: Bearer eyJhbGc… # kaun bhej raha hai (ch 6)
Accept: application/json       # mujhe response is format mein chahiye
User-Agent: curl/8.4.0

# ── blank line: headers khatam, body shuru (\r\n\r\n) ───────
{"name":"Sharad","email":"sharad@example.com"}
raw HTTP response
# ── status line: VERSION  CODE  REASON-PHRASE ───────────────
HTTP/1.1 201 Created           # reason phrase sirf insaan ke liye; code hi authoritative hai

Content-Type: application/json; charset=utf-8
Content-Length: 61
Location: /api/users/42        # 201 ke saath: naya resource kahan bana
Cache-Control: no-store        # ise kahin cache mat karo
Date: Mon, 17 Aug 2026 09:14:22 GMT

{"id":42,"name":"Sharad","email":"sharad@example.com"}
📌 Khud dekhna ho toh

curl -v https://api.github.com/users/torvalds — > wali lines tumhari request hain, < wali response. Aur curl --http1.1 --trace-ascii - se literally raw bytes dikhte hain. Ek baar khud dekh lena poore chapter ko concrete bana deta hai.

Methods — Safe, Idempotent, Cacheable

Method server ko intent batata hai. Par yaad rakhna: HTTP enforce kuch nahi karta — tum GET /delete-user?id=5 bana sakte ho aur wo chal jayega. Ye rules contracts hain, aur poori internet infrastructure (browsers, proxies, CDNs, retry libraries) in contracts pe bharosa karke behave karti hai. Contract todo, toh infrastructure tumhare against kaam karne lagti hai.

Do properties sabse important hain:

  • Safe — server ka state badalta hi nahi. Sirf read.
  • Idempotent — ek baar bhejo ya paanch baar, end state wahi rehta hai. (Response body alag ho sakti hai — jaise doosri DELETE 404 de sakti hai — par state same hai.)
MethodKaamSafeIdempotentBodyCacheable
GETResource padho✅✅❌✅
HEADGET par sirf headers✅✅❌✅
POSTNaya banao / action trigger❌❌✅❌ (praktikal)
PUTPura resource replace❌✅✅❌
PATCHPartial update❌❌*✅❌
DELETEResource hatao❌✅optional❌
OPTIONSKya allowed hai (CORS preflight)✅✅❌❌

* PATCH idempotent ho sakta hai agar tum absolute values bhejo ({"count": 5}), par nahi hoga agar relative operation bhejo ({"increment": 1}). Spec ise idempotent guarantee nahi karta.

🧠 Idempotency sirf theory nahi — network ki majboori hai

Client ne POST /payments bheja aur timeout ho gaya. Ab wo jaanta hi nahi ki payment hua ya nahi — request server tak pahunche bina mari, ya server ne process karke response bhejte waqt connection toota. Dono cases client se identical dikhte hain. Retry kare toh double charge ka risk; na kare toh possible lost payment. Isiliye non-idempotent operations pe idempotency key pattern use hota hai: client ek unique key bhejta hai, server usko store karke duplicate request pe wahi purana result laut​a deta hai. Ye ch 9 aur ch 14 dono ka central idea hai — fintech mein toh ye non-negotiable hai.

⚠️ Classic bug — GET se state badalna

Agar GET /posts/5/delete banaya, toh: browser prefetch usse chala sakta hai, proxy/CDN use cache kar sakta hai, crawler use hit kar sakta hai, aur user ka "back" button dobara trigger kar sakta hai. Ek famous case tha jahan ek admin panel ke delete links GET pe the, aur Google Web Accelerator ne saara data delete kar diya — sirf links crawl karke. Method ka contract todna infrastructure ko hathiyaar bana deta hai.

Status Codes — Classes Aur Unka Asli Matlab

Pehla digit hi class batata hai, aur asli skill 2xx/4xx/5xx ke beech ki line theek se khींchna hai — kyunki wo line "kiski galti hai" define karti hai, aur monitoring/alerting usi pe khadi hoti hai.

Wo codes jo log rozana galat use karte hain:

CodeKab use karoCommon galti
201 Created POST se naya resource bana; Location header ke saath Har POST pe 200 bhej dena — client ko pata hi nahi chalta ki naya bana ya nahi
202 Accepted Kaam queue mein daal diya, abhi hua nahi (ch 12) 200 bhej dena, jisse client samjhe kaam pura ho gaya
204 No Content Success par body hai hi nahi (DELETE, PUT) 200 ke saath {} bhejna
401 vs 403 401 = "tum kaun ho pata nahi / token invalid". 403 = "pata hai tum kaun ho, par permission nahi" Dono jagah 401. Client retry-with-login loop mein fas jaata hai
400 vs 422 400 = request malformed (JSON hi toota hua). 422 = syntax theek, par values invalid Sab kuch 400 — client debug nahi kar paata
409 Conflict Current state se clash (duplicate email, version mismatch) 400 bhejna, jisse retry logic galat decide karta hai
429 Rate limit hit; Retry-After header zaroor bhejo 503 bhejna — client exponential backoff ki jagah aggressive retry karta hai
500 vs 503 500 = code phat gaya. 503 = temporarily overloaded/down, baad mein try karo Overload pe 500 — load balancer instance ko healthy samajhta rehta hai
⚠️ Anti-pattern — "200 OK" ke andar error

200 OK body {"success": false, "error": "not found"} — ye har HTTP-aware cheez ko andha kar deta hai. Monitoring ko error rate 0% dikhega, retry library retry nahi karegi, CDN error response cache kar lega, aur load balancer instance ko healthy maanega. Status code hi wo channel hai jise poori infrastructure padhti hai — usme sach bolo, details body mein daalo.

Headers — Woh Saat Jo Rozana Kaam Aate Hain

Headers request/response ka metadata hain — "content ke baare mein content". Sau se zyada standard headers hain, par backend engineer ko practically ye samajhne chahiye:

  • Host — HTTP/1.1 mein mandatory. Yahi wo header hai jiske bharose ek IP pe hazaaron domains chal sakte hain (ch 2 ka nginx server_name isi ko match karta hai). Iske bina virtual hosting exist hi nahi karti.
  • Content-Type — body ka format (application/json, multipart/form-data, application/x-www-form-urlencoded). Server isi se parser chunta hai. Galat bhejoge toh body undefined milegi — ek classic "mera POST body khali kyun hai" bug.
  • Content-Length — body ke exact bytes. Receiver itne hi bytes padhta hai, phir rukta hai. Ye galat ho toh connection hang ho jaata hai. Note: bytes, characters nahi — UTF-8 mein "नमस्ते" ke 6 characters 18 bytes hain.
  • Authorization — credentials. Bearer <token> (JWT/OAuth) ya Basic <base64>. Base64 encoding hai, encryption nahi — isiliye Basic auth sirf TLS ke upar hi meaningful hai (ch 6).
  • Cookie / Set-Cookie — server client pe chhota state rakhta hai jo har request pe wapas aata hai. Yahi HTTP ki statelessness ke upar sessions banata hai. Flags matter karte hain: HttpOnly (JS padh nahi sakta — XSS defense), Secure (sirf HTTPS pe), SameSite (CSRF defense). Detail ch 6, ch 18.
  • Cache-Control — cache ke rules. no-store (kahin mat rakho), no-cache (rakho par har baar revalidate karo), max-age=3600, private (sirf browser, CDN nahi). Naming confusing hai: no-cache ka matlab "cache mat karo" nahi hai.
  • ETag + If-None-Match — conditional requests. Server response ka ek version-tag bhejta hai; agli baar client wo tag bhejta hai; agar badla nahi toh server 304 Not Modified deta hai bina body ke. Bandwidth ki bachat, aur ch 9 mein yahi optimistic concurrency control ka base banta hai.
📌 Headers case-insensitive hain, values nahi

Content-Type, content-type, CONTENT-TYPE — teeno same header hain (spec ke hisaab se). HTTP/2 toh saare header names lowercase hi bhejta hai. Isliye apne code mein kabhi headers['Content-Type'] se seedha index mat karo — framework ka case-insensitive accessor use karo, warna HTTP/2 pe pahunchte hi code silently toot-ta hai.

Statelessness — Sabse Under-rated Idea

HTTP stateless hai: server ko do requests ke beech kuch yaad rakhna zaroori nahi. Har request apne saath saara zaroori context laati hai. Server ke liye request #1 aur request #1000 mein koi rishta nahi hai.

Pehli nazar mein ye kami lagti hai. Actually ye poore modern backend architecture ki neev hai:

  • Horizontal scaling possible hai — koi bhi request kisi bhi server pe ja sakti hai, kyunki kisi server ke paas special knowledge nahi hai. Sirf ek aur instance add kar do. (ch 19)
  • Crash sasta hai — server mar gaya toh us server ke saath kuch "kho" nahi gaya. Restart karo, kaam chalta rahega. (ch 17)
  • Load balancing simple hai — round-robin kaafi hai; sticky sessions ki zaroorat nahi.
  • Caching kaam karti hai — ek response self-contained hai, toh use store karke doosre client ko dena valid hai. (ch 11)

Cost ye hai ki har request thodi bhaari hoti hai — auth token har baar bhejo, aur user ka context har baar reconstruct karo. Ye trade deliberately accepted hai.

🧠 "Stateless" ka matlab "state hi nahi" nahi hai

State hoti hai — bas wo server ki memory mein nahi hoti. Wo teen jagah shift hoti hai: client pe (cookie, JWT), shared store mein (Redis session, database), ya request ke andar (query params). Anti-pattern ye hai ki tum user session ko process ki local memory mein rakh do — sab kuch chalta hai jab tak ek hi server hai; doosra instance add karte hi users random logout hone lagte hain. Isi ek galti ka naam hai "sticky session ki majboori".

CORS Aur OPTIONS — Preflight Ka Poora Workflow

Ch 2 mein CORS ko ek line mein chhoda tha: "browser ki security policy". Ab uska poora mechanism, kyunki ye rozana ka sabse zyada frustrating error hai aur uska 90% ilaaj log copy-paste se karte hain bina samjhe.

Sabse pehle do cheezein bilkul saaf kar lo:

  • CORS ek relaxation hai, restriction nahi. Default browser policy hai Same-Origin Policy (SOP) — domain A ka JS domain B ka response padh hi nahi sakta. CORS wo mechanism hai jisse server chhoot deta hai: "theek hai, A ko padhne do."
  • CORS request bhejne se nahi rokta — wo response padhne se rokta hai. Request server tak pahunch chuki hoti hai aur side effect ho chuka hota hai. (Yahi wajah hai ki CORS CSRF nahi rokta — ch 18.)
📌 "Origin" kya hai — teenon match karne chahiye

Origin = scheme + host + port. https://app.example.com aur http://app.example.com alag origins hain (scheme alag). example.com aur api.example.com alag hain (host alag). localhost:3000 aur localhost:3001 alag hain (port alag). Isiliye local development mein CORS itni baar takraata hai — frontend 3000 pe, backend 3001 pe.

Simple requests vs preflighted requests

Har cross-origin request preflight nahi karti. Browser pehle dekhta hai ki request "simple" hai ya nahi. Simple ki definition historical hai — wo requests jo ek HTML form bhi bhej sakta tha (aur form CORS se pehle se exist karta hai, isliye unhe rokna backwards compatibility todta):

  • Method GET, HEAD, ya POST ho, aur
  • Content-Type in teen mein se ho: text/plain, application/x-www-form-urlencoded, multipart/form-data, aur
  • Koi custom header na ho (Authorization, X-API-Key — inse preflight trigger hota hai).

Dhyan do: Content-Type: application/json us list mein nahi hai. Isliye practically har modern API call preflight karti hai — aur yahi wajah hai ki tumhe OPTIONS requests network tab mein dikhti hain.

CORS headers — dono taraf
# ── Browser bhejta hai (preflight mein) ─────────────────────
Origin: https://app.example.com          # kaun poochh raha hai (browser SET karta hai, JS nahi)
Access-Control-Request-Method:  POST     # main ye method use karna chahta hoon
Access-Control-Request-Headers: authorization, content-type

# ── Server jawab deta hai ───────────────────────────────────
Access-Control-Allow-Origin:  https://app.example.com   # ya "*" (par credentials ke saath nahi)
Access-Control-Allow-Methods: GET, POST, PATCH, DELETE
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Allow-Credentials: true   # cookies bhejne ki ijaazat (ch 6)
Access-Control-Max-Age: 86400            # preflight ka jawab 24h cache karo
Access-Control-Expose-Headers: X-Request-Id, X-Total-Count
#   ↑ ye NA ho toh JS in headers ko PADH nahi payega, chahe wo bheje gaye hon
⚠️ CORS ke chaar sabse common bugs

1. Allow-Origin: * + Allow-Credentials: true — browser ise reject karta hai, spec ke hisaab se. Credentials ke saath exact origin echo karna padta hai (allowlist se, har origin blindly nahi — ch 18).
2. Preflight pe CORS headers hain par actual response pe nahi — preflight pass ho jaata hai, phir asli response block hota hai. Confusing kyunki OPTIONS network tab mein green dikhta hai.
3. Error responses pe CORS headers missing — tumhara 500 handler (ch 14) CORS middleware ke baad chalta hai aur headers nahi lagata, toh browser mein error "CORS error" dikhta hai, asli 500 nahi. Ghanton debug hota hai.
4. Custom response header padh nahi paa rahe — Expose-Headers chahiye. Pagination count ya request ID bhejne pe ye zaroori hai.

🧠 CORS server-to-server pe lagta hi nahi

curl, Postman, ya tumhara backend jab doosri API call karta hai — wahan CORS ka naam bhi nahi aata. Ye poori tarah ek browser ki policy hai, network ki nahi. Isliye "CORS error aa raha hai" ka matlab hamesha ye hota hai ki request browser se ja rahi hai. Aur yahi ch 2 ke us point ka mechanism hai jahan bola tha ki frontend se third-party APIs call karna structurally toot-ta hai — kyunki wo headers unke control mein hain, tumhare nahi.

HTTP Caching — Freshness Aur Validation

HTTP ka apna caching model hai, aur wo do bilkul alag mechanisms pe khada hai. Ye samajhna zaroori hai kyunki browser, CDN, aur proxy — teenon isi ke hisaab se behave karte hain (ch 11 mein hum application-level caching dekhenge; ye protocol-level hai).

MechanismSawaalNetwork trip?Headers
Freshness "Kya ye abhi bhi taaza hai?" Koi request hi nahi — cache se seedha Cache-Control: max-age, Expires
Validation "Kya ye badla hai?" Request jaati hai, par body wapas nahi aati (304) ETag/If-None-Match, Last-Modified/If-Modified-Since
Cache-Control directives — jo actually matter karte hain
Cache-Control: max-age=3600          # 1 ghante tak fresh — koi request nahi jayegi
Cache-Control: s-maxage=86400        # SHARED caches (CDN) ke liye alag age
Cache-Control: no-cache               # cache karo, par HAR BAAR revalidate karo
Cache-Control: no-store               # kahin store mat karo (banking, PII)
Cache-Control: private                # sirf browser, CDN NAHI (personalized data)
Cache-Control: public                 # CDN bhi cache kar sakta hai
Cache-Control: immutable              # kabhi badlega hi nahi → revalidate mat karo
Cache-Control: stale-while-revalidate=60  # purana do, background mein refresh (ch 11)

# ⚠️ Naming trap: `no-cache` ka matlab "cache mat karo" NAHI hai —
#    wo "cache karo par use karne se pehle poochho" hai.
#    "Cache mat karo" wala directive `no-store` hai.

# ── Validation ka flow ──────────────────────────────────────
# Pehli baar:
GET /api/products
→ 200 OK
  ETag: "a3f2b8"              # content ka fingerprint
  Cache-Control: max-age=60
  [ 200 KB body ]

# max-age khatam hone ke baad — client apna tag wapas bhejta hai:
GET /api/products
If-None-Match: "a3f2b8"
→ 304 Not Modified          # BODY NAHI — sirf ~200 bytes headers
# 200 KB ki jagah 200 bytes. Bandwidth aur render dono fast.
🧠 Static assets ki classic strategy — "cache forever + rename"

Build tool filename mein content hash daalta hai: app.a3f2b8.js. Us file pe Cache-Control: max-age=31536000, immutable lagta hai — ek saal, kabhi revalidate nahi. Content badla? Toh hash badla, matlab filename hi naya hai — aur purani cache automatically irrelevant ho gayi. Isse invalidation ki poori problem gayab ho jaati hai. Sirf index.html pe no-cache lagta hai, kyunki wahi naye filenames ki taraf point karta hai. Ye pattern ch 11 ke "key versioning" jaisa hi idea hai, bas HTTP layer pe.

Content Negotiation

Ek hi URL, kai representations. Client apni preference batata hai aur server sabse achhi match chunta hai — isse format URL mein daalne ki zaroorat nahi padti (/users.json vs /users.xml).

negotiation ke chaar dimensions
# Client kya chahta hai — q = quality/preference (0 se 1)
Accept:          application/json;q=1.0, text/xml;q=0.5
Accept-Language: hi-IN, en;q=0.8
Accept-Encoding: br, gzip
Accept-Charset:  utf-8

# Server ne kya chuna
Content-Type:     application/json; charset=utf-8
Content-Language: hi-IN
Content-Encoding: br

# ⚠️ Vary header — cache ke liye CRITICAL
Vary: Accept-Encoding, Accept-Language
#   ↑ Cache ko batata hai: "ye response IN headers pe depend karta hai,
#     toh alag values ke liye alag entry rakho."
#   Ye na ho toh CDN ek Hindi user ka response ek English user ko de dega,
#   ya gzip response ek aise client ko jo gzip samajh hi nahi sakta.

# Client jo maange wo de na sako toh: 406 Not Acceptable
# (practically zyadatar APIs default JSON de deti hain — ye zyada friendly hai)

Ek aur jagah content negotiation kaam aati hai — API versioning (ch 9): Accept: application/vnd.myapi.v2+json. URL saaf rehta hai, par debug karna mushkil ho jaata hai.

Compression

Text responses (JSON, HTML, CSS, JS) bahut repetitive hote hain, isliye compression se 60–80% size kam ho jaata hai. Ye shayad sabse sasti performance win hai jo ek line config se milti hai.

compression ka flow aur trade-offs
# Client batata hai kya samajh sakta hai
Accept-Encoding: br, gzip, deflate

# Server compress karke batata hai kya kiya
Content-Encoding: br
Content-Length: 18432          # ye COMPRESSED size hai (ch 3 ka body reading)
Vary: Accept-Encoding             # cache ke liye zaroori (upar dekho)

# ── Algorithms ─────────────────────────────────────────────
# gzip — universal support, fast, achha ratio. Safe default.
# br (Brotli) — ~15-20% behtar ratio, par compress karna SLOW hai
#   → static files ke liye ideal (ek baar build time pe compress karo)
#   → dynamic responses ke liye low compression level use karo
# zstd — naya, fast + achha ratio, support badh raha hai

# ⚠️ Kya compress NA karein:
#   • already-compressed formats — jpg, png, mp4, zip, pdf
#     (CPU jalega aur size kabhi-kabhi BADH jaata hai)
#   • bahut chhote responses (<1 KB) — overhead faayde se zyada
#   • streaming responses jahan TTFB matter karta hai (ch 3 ka chunked)

# 📍 Kahan karein: aksar REVERSE PROXY pe (nginx — ch 2), app mein nahi.
#    App ka CPU business logic ke liye bacha rehta hai (ch 21), aur config
#    ek jagah rehti hai.
gzip on; gzip_types application/json text/css application/javascript;
gzip_min_length 1024;
⚠️ BREACH/CRIME — compression + secrets ek saath khatarnak hain

Agar ek response mein attacker ka diya hua input aur ek secret (jaise CSRF token) dono hain, toh compressed response ka size hi secret ke baare mein information leak kar deta hai — attacker guesses bhejta hai aur size dekh ke pata lagata hai ki guess sahi tha ya nahi. Practical defences: secrets ko compressed response body mein mat daalo, CSRF token ko har response mein randomize karo, aur sensitive endpoints pe compression band rakho.

HTTP/1.0 → 1.1 → 2 → 3 Ka Evolution

Har version ek specific performance problem solve karne aaya. Semantics (methods, status, headers) sab mein same hai — sirf wire pe bytes kaise jaate hain wo badla hai.

VersionProblem jo thiSolutionJo bacha rah gaya
HTTP/1.0 — Ek request = ek TCP connection, phir band Har request pe naya handshake — bohot mehnga
HTTP/1.1 Connection setup ka cost keep-alive default; Host header (virtual hosting); chunked transfer Head-of-line blocking — ek connection pe requests line mein, pehli slow toh baaki atki
HTTP/2 HOL blocking + text overhead Binary framing; ek connection pe multiplexed streams; HPACK header compression; server push TCP-level HOL blocking — ek packet kho jaaye toh saari streams rukti hain
HTTP/3 TCP-level HOL blocking QUIC — UDP ke upar, har stream independent; handshake + TLS ek saath (0–1 RTT) UDP kabhi-kabhi corporate networks mein block hota hai

Body Kaise Padhi Jaati Hai — Length vs Chunked

Ek chhoti par deep detail. TCP ek byte stream hai — usme "message khatam" jaisa koi concept nahi hai. Toh receiver ko kaise pata chalta hai ki body kahan khatam hui? Do tareeke hain:

  • Content-Length: 46 — "exactly 46 bytes padho, phir ruk jao". Simple, par sender ko poori body pehle se pata honi chahiye.
  • Transfer-Encoding: chunked — body tukdon mein aati hai, har tukde se pehle uska size hex mein. Size 0 ka matlab "khatam". Isse total size pehle se jaane bina bhejna possible hota hai.
chunked response — streaming ka mechanism
HTTP/1.1 200 OK
Content-Type: text/plain
Transfer-Encoding: chunked      # Content-Length nahi hai — abhi pata hi nahi total kitna

1a                              # agle chunk ke bytes, HEX mein (0x1a = 26)
processing your request… \n     # exactly 26 bytes
9                               # 9 bytes
step 1 ok
0                               # size 0 = body khatam
                                # final blank line

Yahi mechanism un sab cheezon ke neeche hai jo "live" lagti hain — log streaming, progress updates, Server-Sent Events, aur LLM token-by-token responses. Iska practical faayda hai time-to-first-byte: client ko pehla data turant milta hai, poora compute khatam hone ka wait nahi karna padta.

⚠️ Streaming aur reverse proxy — ek gotcha

nginx default mein responses buffer karta hai — matlab wo poora response jama karke tab client ko bhejta hai, jisse tumhari streaming ka poora fayda khatam ho jaata hai. SSE ya streaming endpoints ke liye proxy_buffering off; chahiye. Ye "local pe streaming chal rahi thi, production mein nahi" ka sabse common cause hai — aur ye ch 2 ke hop-thinking ka perfect example hai: bug tumhare code mein nahi, hop #4 pe hai.

Key Takeaways

  • HTTP sirf ek text format hai; reliability aur ordering TCP deta hai, encryption TLS.
  • Message structure fixed hai: start line → headers → blank line → body. HTTP/1.1 mein ye literally readable text hai.
  • Methods enforce nahi hote, par poori internet infrastructure unke contract pe bharosa karti hai — contract todo toh infra tumhare khilaf kaam karta hai.
  • Idempotent = repeat karne pe end state same. Network timeout ke baad safe retry ka yahi base hai; non-idempotent ke liye idempotency key.
  • 4xx vs 5xx ki line = "retry se theek hoga?" — yahi alerting aur client retry logic define karti hai.
  • 200 OK ke andar error bhejna monitoring, retries, aur caching — teeno ko andha kar deta hai.
  • Host header virtual hosting ki neev hai; Content-Type galat ho toh body parse hi nahi hoti.
  • Statelessness ka matlab "state nahi" nahi — state client, shared store, ya request mein shift hoti hai. Isi se horizontal scaling possible hai.
  • CORS ek relaxation hai, restriction nahi — default Same-Origin Policy hai; CORS server ko chhoot dene ka tareeka deta hai.
  • Origin = scheme + host + port; teenon match karne chahiye.
  • Content-Type: application/json "simple request" nahi hai — isliye lagbhag har modern API call preflight karti hai.
  • CORS headers preflight aur actual response dono pe chahiye — aur error responses pe bhi, warna asli 500 "CORS error" ban jaata hai.
  • Allow-Origin: * + Allow-Credentials: true browser reject karta hai; custom response headers ke liye Expose-Headers chahiye.
  • HTTP caching ke do mechanisms: freshness (koi request hi nahi) aur validation (304, body nahi aati).
  • no-cache ≠ "cache mat karo" — wo no-store hai.
  • Static assets: content-hashed filename + immutable — invalidation ki problem hi khatam.
  • Content negotiation ke saath Vary header zaroori hai, warna CDN galat variant serve karega.
  • Compression text pe 60–80% bachati hai; already-compressed formats pe mat karo, aur usse proxy pe rakho.
  • HTTP/2 ne semantics nahi, sirf transport badla — multiplexing se HOL blocking gaya; HTTP/3 ne TCP hi chhod diya.
  • Chunked transfer streaming ka mechanism hai — par proxy buffering usse chupchaap maar deti hai.

🎯 Interview Questions

Q1. "PUT aur PATCH mein farq? PUT idempotent kyun hai, POST nahi?"

PUT poora resource replace karta hai — wahi body 5 baar bhejo, resource wahi final state pe rahega, isliye idempotent. POST har baar naya resource banata hai — 5 baar bhejo, 5 records. PATCH partial update hai, aur uski idempotency payload pe depend karti hai ({"count":5} idempotent, {"increment":1} nahi).

Q2. "401 aur 403 mein kya farq hai?"

401 = authentication fail — server jaanta hi nahi tum kaun ho (token missing/invalid/expired). Sahi response ke saath WWW-Authenticate header aata hai, aur client ko login/refresh karna chahiye. 403 = authorization fail — identity clear hai, par is resource pe permission nahi. Dobara login karne se kuch nahi hoga. Practical impact: galat code bhejne pe client infinite re-login loop mein fas jaata hai.

Q3. "HTTP stateless hai toh login kaise kaam karta hai?"

State server ki memory se hatake kahin aur rakhi jaati hai. Do patterns: session — server ek opaque session ID cookie mein deta hai, asli data shared store (Redis/DB) mein rehta hai, har request pe lookup hota hai. Ya token — JWT jisme claims khud signed form mein hote hain, server ko lookup ki zaroorat hi nahi. Trade-off: session revoke karna aasaan par har request pe lookup; JWT fast par revoke karna mushkil. Detail ch 6.

Q4. "HTTP/2 ne kya solve kiya, aur usne kya nahi solve kiya?"

Solve kiya: HTTP-level head-of-line blocking (multiplexed streams ek connection pe), header overhead (HPACK), aur 6-parallel-connections wala hack. Nahi solve kiya: TCP-level HOL blocking — ek packet lost hone pe TCP saare streams rok deta hai, kyunki TCP ko streams ka pata hi nahi. Yahi wajah hai HTTP/3 ke UDP/QUIC pe jaane ki.

Q5. "Client ne POST bheja, timeout ho gaya. Retry karna chahiye?"

Blindly nahi — POST idempotent nahi hai, aur client ko pata hi nahi ki server ne process kiya ya nahi (request jaate hue mari ya response aate hue). Sahi answer: server ko idempotency key support karna chahiye — client ek unique key bhejta hai, server pehli baar result store karta hai aur same key pe wahi result laut​a deta hai. Tab retry safe ho jaati hai. Fintech mein ye mandatory hai (ch 9, ch 14).

Q6. "CORS error aa raha hai. Kya ho raha hai aur kaise fix karoge?"

Pehle framing theek karo: default policy Same-Origin Policy hai, aur CORS wo mechanism hai jisse server chhoot deta hai. Browser ne dekha ki request cross-origin hai aur "simple" nahi (application/json ya Authorization header ki wajah se), toh usne pehle OPTIONS preflight bheja. Fix server pe hai: preflight ka jawab Access-Control-Allow-Origin/Methods/Headers ke saath do, aur actual response pe bhi wahi origin header lagao — error responses samet. Common traps: * + credentials saath nahi chal sakte, aur custom response headers padhne ke liye Expose-Headers chahiye. Aur ek important line: CORS server-to-server calls pe lagta hi nahi — wo purely browser policy hai.

Q7. "HTTP caching kaise kaam karti hai? ETag ka kya role hai?"

Do mechanisms. Freshness: Cache-Control: max-age — us window mein browser request bhejta hi nahi, cache se serve karta hai. Validation: window khatam hone par client If-None-Match mein purana ETag bhejta hai; content na badla ho toh server 304 Not Modified deta hai bina body ke — 200 KB ki jagah ~200 bytes. Static assets ke liye best strategy content-hashed filename + immutable hai, jisse invalidation ki zaroorat hi nahi padti. Aur no-cache ka matlab "revalidate karo" hai, "cache mat karo" nahi — wo no-store hai.
