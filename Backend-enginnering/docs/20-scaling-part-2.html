Scaling Ka Sahi Order

Sabse important cheez pehle: order matter karta hai, aur zyadatar teams seedha step 7 pe kood jaati hain. Har step ka cost complexity mein exponentially badhta hai:

  1. Query optimize karo (ch 10) — index, N+1, SELECT *. Sabse sasta, aksar 10× faayda.
  2. Connection pooling tune karo (ch 10) — PgBouncer.
  3. Cache lagao (ch 11) — read load ka bada hissa DB tak pahunchta hi nahi.
  4. Vertical scale — sabse sasta step jab tak chhat na aaye.
  5. Read replicas — read-heavy workload ke liye (aur zyadatar apps read-heavy hain).
  6. Partitioning — ek hi machine, par chhoti tables.
  7. Sharding — aakhri option, sabse mehnga.
🧠 Sharding se pehle 1–6 khatam karo

Sharding ek one-way door hai — usse undo karna practically namumkin hota hai, aur wo har cheez todta hai: cross-shard joins, distributed transactions, unique constraints, ORDER BY across shards, aur schema migrations. Ek single Postgres instance modern hardware pe crores of rows aur hazaaron TPS handle kar leta hai jab indexes theek hon. Agar tum sharding soch rahe ho, pehle imaandaari se poocho: kya query optimization, caching, aur read replicas sach mein khatam ho chuke hain? 90% cases mein jawab "nahi" hota hai.

Read Replicas Aur Replication Lag

Primary sab writes leta hai aur apna change-log (Postgres mein WAL — ch 10) replicas ko stream karta hai. Replicas reads serve karti hain. Zyadatar apps 90:10 ya 99:1 read:write hoti hain, isliye ye ek bada jeet hai — aur code change bhi minimal hai.

routing — aur wo queries jo replica pe kabhi nahi jaani chahiye
// Repository layer (ch 8) is routing ke liye perfect jagah hai —
// service ko pata bhi nahi chalega ki replicas exist karte hain.
class OrderRepository {
  findById(id, { consistent = false } = {}) {
    const db = consistent ? this.primary : this.replica;
    return db.query(…);
  }
  create(data) { return this.primary.query(…); }   // writes HAMESHA primary
}

// ⚠️ PRIMARY se padhna zaroori hai jab:
//   • abhi-abhi write kiya hai (read-your-own-writes)
//   • paisa/balance check kar rahe ho — stale value se overdraft ho sakta hai
//   • SELECT ... FOR UPDATE (ch 10) — lock replica pe kaam hi nahi karega
//   • transaction ke andar ho jisme write bhi hai

// ✅ REPLICA ke liye perfect:
//   • analytics, reports, dashboards (bhaari queries jo primary ko bacha degi)
//   • search results, listings, public pages
//   • background jobs jo latency-sensitive nahi hain (ch 12)

// ⚠️ FAILOVER: primary gira toh replica promote hoti hai. Async replication mein
// jo writes abhi replicate nahi hui thi wo KHO jaati hain. Zero data loss chahiye
// toh synchronous replication chahiye — par uska cost ye hai ki har write ko
// replica ka ack chahiye, matlab write latency badh jaati hai.
⚠️ Replicas write scaling nahi dete

Har replica saare writes apply karti hai — wo sirf reads baant-ti hai. Agar tumhara bottleneck writes hai, toh 10 replicas add karke kuch nahi hoga; ulta primary pe replication ka aur load aayega. Write bottleneck ke liye sirf teen raaste hain: writes kam karo (batching, ch 12 se async), vertical scale, ya sharding.

Partitioning — Ek Hi Machine, Chhoti Tables

Partitioning ek badi table ko chhote physical tukdon mein todti hai — usi database ke andar. Ye sharding se bilkul alag cheez hai (aur bahut kam khatarnak).

Postgres declarative partitioning
CREATE TABLE events (
  id bigserial, created_at timestamptz NOT NULL, payload jsonb
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_07 PARTITION OF events
  FOR VALUES FROM ('2026-07-01') TO ('2026-08-01');
CREATE TABLE events_2026_08 PARTITION OF events
  FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

-- PARTITION PRUNING — planner sirf relevant partitions chhuta hai (ch 10)
SELECT * FROM events WHERE created_at >= '2026-08-01';
-- → sirf events_2026_08 scan hoti hai. Baaki 23 partitions chhui bhi nahi.

-- Sabse bada faayda aksar ye hota hai: purana data hatana INSTANT ho jaata hai
DROP TABLE events_2026_07;          -- milliseconds
-- vs DELETE FROM events WHERE created_at < '2026-08-01'
--    → ghanton lagti hai, WAL bharti hai, dead rows chhodti hai (ch 10 ka VACUUM)

-- ⚠️ Gotchas:
--   • partition key har UNIQUE constraint mein hona chahiye
--   • jis query mein partition key nahi hai wo SAARI partitions scan karegi
--   • future partitions pehle se banane padte hain (automate karo!)

Sharding — Aakhri Hathiyar

Sharding data ko alag-alag databases mein baant-ti hai. Ab har shard ke apne writes, apni memory, apni CPU — matlab yahi ek tareeka hai jo write scaling deta hai. Cost ye hai ki SQL ka bahut kuch kaam karna band kar deta hai.

StrategyKaiseTrade-off
Hash-based hash(userId) % N Even distribution. Par range queries sab shards pe jaati hain, aur resharding mushkil (isliye §5)
Range-based A–M shard 1, N–Z shard 2 Range queries efficient. Par hotspots — sequential IDs sab ek shard pe
Directory-based Ek lookup table batati hai kaunsa shard Sabse flexible, rebalance aasaan. Par lookup ek extra hop + single point of failure
Geo-based Region ke hisaab se Latency aur data residency (GDPR). Par cross-region queries mehngi
shard key — sabse important decision
// Ek achhi shard key ke teen gun:
//   1. HIGH CARDINALITY — bahut saari alag values
//   2. EVEN DISTRIBUTION — koi ek value zyada popular na ho
//   3. QUERY PATTERN SE MATCH — zyadatar queries mein wo key maujood ho

// ✅ userId — multi-tenant app ke liye aksar sahi
//    ek user ka SAARA data ek shard pe → uski queries single-shard rehti hain
// ❌ country — sirf ~200 values, aur India/US wale shard phat jayenge
// ❌ created_at — SAARE naye writes ek hi shard pe (hotspot)
// ❌ status — 5 values, aur wo BADALTI hai (row ko shard badalna padega!)
// ⚠️ Rule: shard key IMMUTABLE honi chahiye.

// ── Jo cheezein sharding TODTI hai ─────────────────────────
// ❌ Cross-shard JOIN — application mein manually karna padega
// ❌ Distributed transaction — 2PC ya saga pattern (dono complex)
// ❌ Global UNIQUE constraint — email uniqueness ab DB enforce nahi kar sakta
// ❌ ORDER BY + LIMIT across shards — har shard se lo, merge karo, phir cut karo
// ❌ COUNT(*) — sab shards se jodo
// ❌ Schema migration — ab N databases pe coordinate karni hai
// ❌ Auto-increment IDs — UUID/ULID ya Snowflake IDs pe jaana padega

// ── HOTSPOT: ek celebrity user, ek shard ────────────────────
// Even hashing ke bawajood ek "bhaari" tenant ek shard ko dubo sakta hai.
// Fix: composite key hash(userId + bucket), ya us tenant ke liye dedicated shard.

Consistent Hashing

Naive hash(key) % N ka ek fatal problem hai: N badalte hi lagbhag saara data move karna padta hai. 4 shards se 5 shards — ~80% keys ka mapping badal jaata hai.

Denormalization Aur Materialized Views

Normalization (data ek hi jagah) writes ke liye achhi hai aur reads ke liye mehngi — kyunki har read ko joins karne padte hain. Bade read scale pe hum ulta karte hain: data duplicate karo taaki read sasta ho.

teen techniques
-- 1. Counter denormalize karo — COUNT(*) har baar mehnga hai (ch 10)
ALTER TABLE posts ADD COLUMN comment_count int NOT NULL DEFAULT 0;
-- comment insert ke saath USI TRANSACTION mein increment (ch 10)
-- trade: ek extra write, par har read pe ek COUNT(*) bacha

-- 2. Materialized view — bhaari aggregate pehle se compute
CREATE MATERIALIZED VIEW daily_sales AS
  SELECT date_trunc('day', created_at) d, sum(total_paise), count(*)
  FROM orders GROUP BY 1;
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales;   -- reads block nahi hongi
-- Ye cache ka DB-level version hai — wahi staleness trade-off (ch 11)

-- 3. Read model alag rakho (CQRS ka halka version)
-- Writes normalized tables mein; ek worker (ch 12) denormalized read table
-- update karta hai jo UI ke shape se exactly match karti hai.
-- ⚠️ Cost: eventual consistency + ek aur cheez jo out-of-sync ho sakti hai (ch 13)

CDN Aur Edge

Sabse sasta scaling wo hai jisme request tumhare server tak pahunchti hi nahi. CDN geographically distributed cache hai — content user ke paas.

  • Static assets — JS, CSS, images. Content-hashed filenames (app.a3f2.js) + max-age=31536000, immutable. Naya deploy = naya filename, toh invalidation ki zaroorat hi nahi.
  • Public API GETs — cacheable responses pe Cache-Control: public, s-maxage. Par personalized responses pe private (ch 3, ch 11) — warna ek user ka data doosre ko serve ho jaayega.
  • TLS termination edge pe — handshake (ch 3) user ke paas hota hai, isliye connection setup bahut fast.
  • Origin shield — CDN nodes seedha origin ko hit karne ki jagah ek intermediate layer se guzarte hain, taaki cache miss pe origin pe stampede na ho (ch 11).

Edge Computing

CDN static content user ke paas laata hai. Edge computing agla kadam hai — code bhi user ke paas chalao, na ki ek central region mein.

edge pe kya theek hai, kya nahi
// Mumbai ka user, us-east-1 ka server → ~200ms round trip, khali network pe.
// Edge function 50+ locations pe chalta hai → ~10ms.

// ✅ EDGE ke liye achha — chhota, stateless, latency-sensitive kaam:
//   • auth token verify karna (JWT signature — ch 6, koi DB lookup nahi)
//   • A/B test bucketing, feature flags (ch 15)
//   • geo-routing, redirects, URL rewrites
//   • bot detection, rate limiting (ch 18) — origin tak pahunchne se pehle
//   • personalized headers / HTML fragments inject karna

// ❌ EDGE ke liye galat:
//   • koi bhi kaam jisme central DB chahiye — tumne latency BADHA di
//     (edge → DB ka trip abhi bhi 200ms hai, plus ek extra hop)
//   • CPU-heavy kaam (ch 21) — edge runtimes ki limits sakht hoti hain
//   • bade dependencies — edge runtime aksar full Node nahi hota

// ⚠️ Edge ka asli constraint: DATA GRAVITY
// Code ko distribute karna aasaan hai; DATA ko distribute karna mushkil hai
// (wahi replication/consistency problems — upar §2, §8).
// Isliye edge tabhi jeetta hai jab kaam ko central data chahiye HI NAHI.

CAP Aur Consistency Models

CAP theorem: jab network partition ho (P), toh tum consistency (C) aur availability (A) mein se ek hi chun sakte ho. Par ise samajhne ka practical tareeka alag hai:

⚠️ CAP ko galat samjha jaata hai

"CP ya AP chuno" ek system-wide permanent choice nahi hai — wo choice sirf partition ke dauraan matter karti hai, aur alag operations ke liye alag ho sakti hai. Aur normal (non-partition) time mein asli trade-off consistency vs latency hai — isliye PACELC zyada useful framing hai: if Partition then A-or-C, Else Latency-or-Consistency. Rozana ki engineering mein tum partitions se zyada isi "else" wale hisse se deal karte ho.

ModelGuaranteeKahan use
StrongHar read latest write dekhta haiBalance, inventory, auth — paisa aur permissions
Read-your-writesTum apna likha hua dekhte hoProfile edit, post karna — user-facing writes
Monotonic readsPeeche nahi jaogeTimelines, feeds
EventualKabhi na kabhi convergeView counts, likes, analytics, search index

Practical approach: poore system pe ek model mat thopo. Ek hi app mein order total strongly consistent ho sakta hai aur view count eventually consistent — aur yahi sahi design hai.

Monolith vs Microservices

Sabse pehle ek galatfehmi hataao: microservices ek scaling solution nahi hain. Ek monolith ko horizontally scale karna trivially aasaan hai — bas aur instances chala do (ch 19). Jo cheez scale nahi hoti wo team hai. Microservices ek organizational solution hain jiski technical keemat bahut zyada hai.

⚠️ Jo cheezein "free" thi, ab kaam ban jaati hain

Monolith mein ek function call: hamesha safal, nanoseconds, aur ek transaction ke andar. Microservice mein wahi call ab ek network call hai — matlab uspe timeout chahiye, retry chahiye, circuit breaker chahiye (ch 14), tracing chahiye (ch 16), aur wo fail ho sakti hai. Aur do services ke beech atomicity ab DB se nahi milti — tumhe saga pattern (har step ka compensating action) ya eventual consistency lagani padti hai. Ek simple "order banao + payment karo" ab ek distributed workflow ban jaata hai.

🧠 Practical raasta — modular monolith

Beech ka rasta sabse achha hai: monolith rakho, par usme saaf module boundaries banao — har module ka apna schema/tables, aur inter-module baat sirf explicit interfaces se (direct table access nahi). Ye tumhe microservices ke design discipline ka zyadatar faayda deta hai bina network, deployment, aur observability ki keemat chukaye. Aur agar kabhi sach mein ek module ko nikalna pada, toh boundary already maujood hai — extraction ek din ka kaam hai, ek saal ka nahi. Distributed monolith (services jo har request pe ek doosre ko sync call karti hain) sabse bura outcome hai: microservices ki saari complexity, monolith ki saari coupling.

Serverless ka matlab "server nahi hai" nahi — matlab tum server manage nahi karte. Tum ek function deploy karte ho; platform request aane pe usse chalata hai, aur idle hone pe band kar deta hai.

// ── TRAP 1: CONNECTION EXHAUSTION (ch 10 wapas) ────────────
// Serverless 1000 concurrent instances tak scale kar sakta hai.
// Har instance ek DB connection kholta hai → 1000 connections.
// Postgres max_connections = 100. DB gir gaya.
// ← Ye bilkul wahi problem hai jo ch 2 mein "browser se seedha DB" wali thi,
//   aur ch 19 ka "autoscaling downstream ko kuchal deti hai" wala point bhi.
// ✅ Fix: external pooler (RDS Proxy, PgBouncer) ya HTTP-based DB driver.

// ── TRAP 2: COLD START ─────────────────────────────────────
// Pehli request pe: container boot + runtime init + tumhara init code
// Node/Python: ~100-500ms · Java/.NET: 1-5s (JVM startup)
// Aur VPC ke andar ho toh aur zyada.

// ✅ Kam karne ke tareeke:
//   • handler ke BAHAR heavy init karo — wo warm invocations mein reuse hota hai
const db = createClient();          // ✅ module scope — ek baar
exports.handler = async (event) => {   // har invocation
  return db.query(…);
};
//   • bundle chhota rakho, provisioned concurrency (par tab idle cost wapas aa gayi)

// 💰 Cost curve: kam/spiky traffic pe serverless BAHUT sasta,
// par steady high traffic pe wo traditional servers se MEHNGA pad jaata hai.
// Ek crossover point hota hai — usse calculate karo, maano mat.
📌 Serverless kab sach mein achha hai

Spiky ya kam traffic (internal tools, admin jobs), event-driven kaam (S3 upload pe thumbnail banana, webhook receiver — ch 12 ke workers isme perfectly fit hote hain), cron jobs, aur glue code jahan poora service khada karna overkill ho. Kab galat: steady high traffic (cost), long-running jobs (duration limit), aur wo services jahan consistent low latency chahiye (cold starts). Ek accha pattern hai hybrid — main API traditional servers pe, aur background/event kaam serverless pe.

🧠 Aakhri baat — premature scaling ek real cost hai

Har scaling step complexity add karta hai, aur complexity ka bill roz aata hai: debugging mushkil, deploy mushkil, naye developer ka onboarding mushkil, aur bugs ke chhupne ki jagah zyada. Ek monolith + Postgres bahut door tak le jaata hai — bahut door, agar indexes aur queries theek hon. Jab tak ek concrete, measured problem na ho, agla step mat lo. Aur jab lo, toh ek step lo — do ek saath nahi.

Key Takeaways

  • App layer isliye scale karti hai kyunki wo stateless hai; DB stateless nahi hai — isliye wahi asli mushkil hai.
  • Order: query optimization → pooling → cache → vertical → replicas → partitioning → sharding sabse aakhir.
  • Sharding ek one-way door hai — joins, transactions, unique constraints, migrations, sab todti hai. Uski nौbat 90% cases mein aati hi nahi.
  • Read replicas read-heavy load ke liye bade jeet hain, par write scaling nahi deti — har replica saare writes apply karti hai.
  • Replication async hai → read-your-own-writes problem. Fix: write ke baad primary se padho, ya user-specific data hamesha primary se.
  • Primary se padhna zaroori: abhi-abhi likha data, paisa/balance, FOR UPDATE, write wale transaction ke andar.
  • Replica routing repository layer mein rakho (ch 8) — service ko pata bhi na chale.
  • Async failover mein unreplicated writes kho jaate hain; sync replication write latency badha deti hai.
  • Partitioning ≠ sharding — ek hi DB, chhoti tables. Pruning + instant DROP of old data.
  • Shard key: high cardinality, even distribution, query pattern se match, aur immutable.
  • hash % N mein node add karne pe ~80% keys move hoti hain; consistent hashing mein sirf ~1/N.
  • Denormalization = reads sasti karne ke liye data duplicate karna; materialized view cache ka DB-level version hai (wahi staleness trade-off).
  • CDN sabse sasta scaling hai — content-hashed filenames se invalidation ki zaroorat hi khatam; personalized responses pe private.
  • CAP ka choice sirf partition ke dauraan matter karta hai; normal time mein asli trade-off consistency vs latency hai (PACELC).
  • Ek consistency model poore system pe mat thopo — order total strong, view count eventual.
  • Edge computing tabhi jeetta hai jab kaam ko central data chahiye hi nahi — data gravity uski asli limit hai.
  • Microservices ek scaling solution nahi hain — monolith trivially horizontally scale hota hai. Wo ek organizational solution hain; trigger team coordination cost hai, traffic nahi.
  • Microservices mein jo free tha wo kaam ban jaata hai: function call → network call (timeout, retry, breaker, tracing), aur ACID transaction → saga.
  • Modular monolith best default hai — saaf boundaries, par ek deployment. Distributed monolith sabse bura outcome hai.
  • Serverless ke do asli traps: connection exhaustion (pooler chahiye) aur cold starts (init handler ke bahar rakho).
  • Serverless spiky/event-driven kaam pe sasta hai, steady high traffic pe mehnga — crossover point calculate karo.
  • Premature scaling ki complexity ka bill roz aata hai. Ek step lo, aur sirf measured problem pe.

🎯 Interview Questions

Q1. "Database bottleneck ban raha hai. Kya karoge?"

Order mein: pehle queries optimize karo (EXPLAIN, missing indexes, N+1 — ch 10, aksar sabse bada faayda yahin hota hai), phir connection pooling tune karo, phir caching (ch 11) taaki read load DB tak pahunche hi na, phir vertical scale, phir read replicas agar read-heavy hai, phir partitioning. Sharding aakhir mein — wo one-way door hai. Sabse important point: pehle measure karo ki bottleneck reads hain ya writes, kyunki replicas writes mein bilkul madad nahi karti.

Q2. "User ne profile update kiya par purana data dikh raha hai. Kya hua?"

Replication lag — write primary pe gaya, agla read replica se aaya jo abhi catch-up nahi hui. Fixes: write ke baad kuch seconds tak us user ke reads primary pe bhejo (session pinning), ya user-specific/user-owned data hamesha primary se padho, ya replica ka lag check karke threshold se zyada hone pe primary use karo. UI-level pe optimistic update bhi user experience theek kar deta hai. General principle: read-your-own-writes ek consistency model ka choice hai.

Q3. "Sharding kab karoge aur shard key kaise chunoge?"

Sirf tab jab writes ek machine pe fit na hon aur query optimization, caching, aur replicas exhaust ho chuke hon. Shard key ke teen gun: high cardinality, even distribution, aur zyadatar queries mein maujood hona — aur wo immutable honi chahiye (badalne pe row ko shard badalna padega). Multi-tenant apps mein userId/tenantId aksar sahi hota hai kyunki ek tenant ka data ek shard pe rehta hai. created_at galat hai (naye writes ka hotspot), country galat hai (low cardinality + skew). Aur bata do ki kya toot-ta hai: cross-shard joins, distributed transactions, global unique constraints, ORDER BY across shards, aur migrations.

Q4. "Consistent hashing kya hai aur kyun chahiye?"

hash(key) % N mein N badalte hi lagbhag saara mapping badal jaata hai — 4 se 5 nodes pe ~80% keys move karni padti hain, jo cache ke liye poori invalidation (stampede, ch 11) aur DB ke liye ghanton ka migration hai. Consistent hashing mein nodes aur keys dono ek circular hash space pe hote hain aur key clockwise agle node pe jaati hai — node add/remove pe sirf ~1/N keys move hoti hain. Virtual nodes se distribution even rakha jaata hai. Redis Cluster, Cassandra, DynamoDB, aur CDN routing sab yahi use karte hain.

Q5. "CAP theorem samjhao."

Network partition (P) hone par tum consistency aur availability dono nahi rakh sakte — ya to stale jawab do (AP) ya jawab dene se mana karo (CP). Par do nuances jo strong answer banate hain: (1) ye choice sirf partition ke dauraan lagti hai, aur alag operations ke liye alag ho sakti hai — system-wide permanent label nahi hai; (2) normal time mein asli trade-off consistency vs latency hai, isliye PACELC zyada useful hai. Practically: paisa/inventory strong consistency, view counts aur feeds eventual — ek hi app mein dono.

Q6. "Traffic badh raha hai — microservices mein tod dein?"

Nahi, kyunki microservices scaling problem solve nahi karte — ek monolith ko horizontally scale karna trivially aasaan hai, bas aur instances. Microservices ka asli trigger team hai: jab bahut saari teams ek hi codebase pe deploy karne ke liye ek doosre ko block kar rahi hon. Aur uski keemat: har inter-service call ab fail ho sakti hai (timeout, retry, circuit breaker — ch 14), cross-service atomicity saga pattern maangti hai, aur observability optional se mandatory ban jaati hai (ch 16). Mera default jawab: modular monolith — saaf module boundaries aur per-module schema, ek deployment. Tab extraction baad mein aasaan rehta hai, aur "distributed monolith" ka worst case nahi banta.

Q7. "Serverless use karna chahiye? Kya problems aati hain?"

Achha hai spiky/kam traffic, event-driven kaam (S3 trigger, webhooks, cron) aur glue code ke liye — idle cost zero, aur scaling automatic. Do bade traps: (1) connection exhaustion — 1000 concurrent instances = 1000 DB connections, jabki Postgres 100 pe hai (ch 10); fix external pooler ya HTTP-based driver; (2) cold starts — 100ms se seconds tak, isliye heavy init handler ke bahar rakho taaki warm invocations usse reuse karein. Aur cost curve dhyan se dekho: steady high traffic pe serverless traditional servers se mehnga pad jaata hai. Hybrid aksar sahi jawab hai — API servers pe, background/event kaam serverless pe.
