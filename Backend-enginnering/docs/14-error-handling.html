Error Handling & Fault Tolerance

Errors Ke Do Bilkul Alag Kism

Sabse pehla aur sabse important distinction — inhe mila dena poore error handling ko bekaar kar deta hai:

Expected (operational)Unexpected (programmer)
Kya haiValidation fail, 404, insufficient stock, downstream 503undefined is not a function, null deref, typo
Kya ye "bug" haiNahi — ye normal flow ka hissa haiHaan — code galat hai
Handle karnaExplicitly — client ko meaningful jawab doHandle nahi karna — fail fast, log, alert
HTTP4xx (ya specific 5xx jaise 503)500 — generic message (ch 3)
Alert?Sirf rate spike peHar ek pe
⚠️ Sabse mehnga anti-pattern — errors nigal jaana

try { … } catch (e) { console.log(e) } aur aage badh jaana. Ab code ek galat state mein chal raha hai, aur asli failure 3 layers baad kisi aur jagah dikhegi — jahan uska root cause dhoondhna bahut mushkil hai. Rule: ya toh error ko meaningfully handle karo, ya usse upar jaane do. Log karke swallow karna dono mein se kuch nahi hai. Aur khaali catch {} toh production mein hafton tak bugs chhupa deta hai.

Central Error Handling — Ch 8 Ka Wada

Ch 8 mein bola tha: service domain errors throw kare, HTTP status nahi — mapping ek central handler ka kaam hai. Ab wo poora setup.

domain error hierarchy + central mapping
// ── 1. Domain errors — HTTP ka naam tak nahi ──────────────
class AppError extends Error {
  constructor(code, message, { cause, context } = {}) {
    super(message, { cause });   // `cause` — original error chain bachaye rakho
    this.code = code;            // stable machine code (ch 9)
    this.context = context;      // debugging ke liye — orderId, userId etc.
    this.isOperational = true;   // ← "expected hai, bug nahi"
  }
}
class NotFoundError   extends AppError { /* code: "not_found"  */ }
class ConflictError   extends AppError { /* code: "conflict"   */ }
class ValidationError extends AppError { /* code: "validation" */ }
class UpstreamError   extends AppError { /* code: "upstream"   */ }

// ── 2. Ek jagah mapping — poore app mein consistent ───────
const STATUS = {
  validation: 422,  not_found: 404,  conflict: 409,
  forbidden:  403,  unauthorized: 401, rate_limited: 429,
  upstream:   503,  // downstream fail — 500 nahi, kyunki ye RETRYABLE hai (ch 3)
};

function errorHandler(err, req, res, next) {
  const status = err.isOperational ? (STATUS[err.code] ?? 400) : 500;

  // Log level severity se — 4xx ka spam alerts ko bekaar kar deta hai
  const log = { requestId: req.ctx.requestId, code: err.code, path: req.path };
  if (status >= 500) logger.error({ ...log, err, stack: err.stack });
  else                 logger.warn({ ...log });

  res.status(status).json({
    error: err.code ?? "internal_error",
    // 5xx pe asli message KABHI nahi — SQL/stack/paths leak hote hain (ch 18)
    message: status >= 500 ? "Something went wrong" : err.message,
    requestId: req.ctx.requestId,   // user support ko yahi batayega (ch 16)
  });
}

// ── 3. Wo errors jo middleware tak pahunchte hi nahi ──────
process.on("unhandledRejection", (reason) => {
  logger.fatal({ reason }, "unhandled rejection");
  gracefulShutdown();   // process ab unknown state mein hai — restart karo (ch 17)
});
process.on("uncaughtException", (err) => {
  logger.fatal({ err }, "uncaught exception");
  gracefulShutdown();
});
// Counter-intuitive par sahi: crash-and-restart ek corrupted process mein
// chalte rehne se BEHTAR hai. "Let it crash" — process manager restart karega.

Timeouts — Sabse Under-rated Defense

Har network call ka ek default timeout hota hai: infinity. Aur infinity hi wo cheez hai jo ek slow dependency ko poore outage mein badal deti hai.

bina timeout ke kya hota hai — poori chain
// Payment API slow ho gayi — down nahi, sirf SLOW (30s per request)
await fetch("https://payments.example.com/charge");  // koi timeout nahi

// 1. Har request 30s tak atki rehti hai
// 2. Har atki request ek DB connection pakde hai (agar txn khula hai — ch 10)
// 3. 30s × normal traffic = sainkdon concurrent atki requests
// 4. Connection pool khatam → ab wo endpoints bhi fail hone lage
//    jinka payment se koi lena-dena hi nahi tha
// 5. Health check bhi timeout → load balancer ne instance ko unhealthy maar diya
// 6. Traffic bache hue instances pe → wo bhi girre → POORA OUTAGE

// ← Ek non-critical dependency ne poora system gira diya. Ye REAL pattern hai.
timeout budget — har layer pe
// Rule: har layer ka timeout apne CALLER se KAM hona chahiye.
// Warna caller pehle timeout hoga aur tumhara kaam bekaar chala jayega.

nginx      proxy_read_timeout   30s     // bahar wali seema (ch 2)
  └─ app   server timeout       25s
       └─ DB  statement_timeout  10s     // (ch 10)
       └─ HTTP client            5s     // downstream API
       └─ Redis                100ms     // cache — fast fail (ch 11)

// Node mein — fetch pe timeout AbortSignal se lagta hai
const res = await fetch(url, {
  signal: AbortSignal.timeout(5000),   // 5s ke baad abort
});

// ⚠️ Do alag timeouts hote hain, dono chahiye:
//   connect timeout — connection banne ka intezaar (chhota: 1-2s)
//   read timeout    — response ka intezaar (bada: 5-30s)

Retries — Aur Wo Kab Nuksaan Karti Hain

Retry karna obvious lagta hai, par galat retry outage ko lamba kar deti hai. Teen rules hain, aur teeno zaroori:

retry ke teen rules
// ── Rule 1: sirf TRANSIENT errors retry karo ──────────────
const RETRYABLE = new Set([408, 429, 500, 502, 503, 504]);
// 4xx (429 chhod ke) retry mat karo — 400 100 baar bhejne se bhi 400 hi rahega
// Aur network errors: ECONNRESET, ETIMEDOUT, EAI_AGAIN → retryable

// ── Rule 2: sirf IDEMPOTENT operations retry karo (ch 3, ch 9) ──
// GET, PUT, DELETE → safe
// POST → sirf idempotency key ke saath, warna double charge

// ── Rule 3: exponential backoff + JITTER ──────────────────
async function withRetry(fn, { attempts = 3, base = 200 } = {}) {
  for (let i = 0; i < attempts; i++) {
    try { return await fn(); }
    catch (err) {
      if (!isRetryable(err) || i === attempts - 1) throw err;

      // server ne bataya hai toh uski suno (ch 3 ka 429 + Retry-After)
      const hinted = err.headers?.["retry-after"];
      const delay = hinted
        ? Number(hinted) * 1000
        : base * 2 ** i * (0.5 + Math.random());   // ← jitter
      await sleep(delay);
    }
  }
}
⚠️ Retry amplification — nested retries ka multiplication

Har layer 3 retries kar rahi hai: client → gateway → service A → service B. Total attempts = 3×3×3 = 27 requests, ek user action ke liye. Jab B already overloaded hai, tumne uska load 27× kar diya — retry ne outage banaya, theek nahi kiya. Do fixes: retry sirf ek layer pe karo (usually sabse bahar wali, jo user ke sabse paas hai), aur ek retry budget rakho (jaise "total requests ka max 10% retries ho sakti hain").

Circuit Breaker — Mechanism

Retry ek ek request ka faisla hai. Circuit breaker ek system-level faisla hai: agar downstream clearly down hai, toh usse call karna hi band kar do. Har failed call time, threads, aur connections barbaad karti hai — aur girti hui service pe aur load daalti hai.

breaker ka core logic
class CircuitBreaker {
  constructor({ threshold = 0.5, minCalls = 20, resetMs = 30_000 }) { … }

  async call(fn, fallback) {
    if (this.state === "OPEN") {
      if (now() - this.openedAt < this.resetMs) {
        return fallback?.() ?? reject(new UpstreamError("circuit_open"));
        // ↑ 0 ms mein fail — koi thread, koi connection block nahi hua
      }
      this.state = "HALF_OPEN";   // ek test call ki ijaazat
    }

    try {
      const result = await fn();
      this.onSuccess();     // HALF_OPEN → CLOSED, counters reset
      return result;
    } catch (err) {
      this.onFailure();     // rate threshold cross → OPEN
      if (fallback) return fallback();
      throw err;
    }
  }
}

// ⚠️ Threshold ABSOLUTE count pe nahi, RATE pe rakho — aur minimum calls ke saath.
// "5 failures" pe open karna low-traffic pe har thodi der mein trip karega.

Bulkhead — Failure Ko Ek Jagah Rokna

Naam jahaz se aaya hai: ship ke andar watertight compartments hote hain, taaki ek chhed poore jahaz ko na dubo de. Software mein wahi idea — resources ko partition karo, taaki ek slow dependency saare resources na kha jaaye.

bulkhead — alag pools
// ❌ Ek shared pool — payment ki slowness search ko bhi maar degi
const pool = { max: 50 };

// ✅ Alag pools per dependency

  payment:   { max: 10 },   // payment slow ho toh max 10 slots atkenge
  search:    { max: 20 },   // search ke apne 20 surakshit hain

Cascading Failure — Poora Anatomy

Production outages ka sabse common shape. Ek chhoti si cheez se shuru hota hai aur poore system ko le doobta hai. Isko step-by-step samajhna zaroori hai kyunki har step pe ek defense lagti hai:

StepKya hota haiYahan kaunsi defense lagti hai
1Ek downstream service slow hui (down nahi — slow)—
2Tumhare requests uska intezaar kar rahi hainTimeout
3Atki requests threads/connections pakde hainBulkhead
4Pool khatam — unrelated endpoints bhi failBulkhead
5Clients retry karte hain → load badhta haiBackoff + jitter, retry budget
6Health check timeout → LB instance ko maar deta haiAlag health-check path
7Traffic bache instances pe → wo bhi girte hainCircuit breaker, load shedding
8Poora outage—
🧠 "Slow" "down" se zyada khatarnak hai

Agar downstream down hai, toh connection turant refuse hota hai — tum fast fail karke aage badh jaate ho. Agar wo slow hai, toh tumhari requests atki rehti hain, resources pakde rehte hain, aur failure andar ki taraf failti hai. Isliye monitoring mein "up/down" check kaafi nahi hai — latency percentiles (p95, p99) dekhna zaroori hai (ch 16). Aur isiliye timeout har defense se pehle aata hai: wo "slow" ko "fail" mein badal deta hai, jo handle karna aasaan hai.

⚠️ Health check dependencies check mat karo

Agar tumhara /health DB, Redis, aur 3 downstream services ko check karta hai, toh kisi ek ke slow hone pe saare instances unhealthy mark ho jaayenge — aur load balancer sabko traffic se hata dega. Ek partial degradation poora outage ban gaya. Isliye do alag endpoints rakho: liveness (kya process zinda hai — koi dependency check nahi) aur readiness (kya ye traffic le sakta hai — sirf essential dependencies). Aur health check ko fast rakho, timeout ke saath (ch 17).

Graceful Degradation

Sabse achha failure handling wo hai jisme user ko pata hi na chale ki kuch fail hua. Har failure ka matlab error page nahi hona chahiye:

degradation ke tareeke
// ── 1. Fallback value — non-critical feature chup ho jaaye ──
const recommendations = await breaker
  .call(() => recoService.get(userId))
  .catch(() => []);   // reco service down → khali section, page phir bhi chalega

// ── 2. Stale data — thoda purana >> kuch bhi nahi (ch 11) ──
try { return await fetchFresh(); }
catch { return await cache.getStale(key); }

// ── 3. Async mein daal do (ch 12) ──────────────────────────
// Email service down? Queue mein daalo, baad mein bhej dena.
// User ka order phir bhi ban gaya.

// ── 4. LOAD SHEDDING — deliberately kuch requests reject karo ──
if (currentLoad > THRESHOLD && !req.isCritical) {
  return res.status(503).set("Retry-After", "5").json({ error: "overloaded" });
}
// Counter-intuitive par critical: 100% requests ko slowly fail karne se
// BEHTAR hai 80% ko theek se serve karna aur 20% ko saaf mana kar dena.
// Overload pe ek system jo "sab try karta hai" wo SAB fail karta hai.

Har External Call Ka Checklist

Jab bhi code apne process ke bahar kisi cheez ko call kare (DB, cache, HTTP, queue):

  • ☐ Timeout hai? (connect aur read dono)
  • ☐ Failure pe kya hoga — error, fallback, ya stale data?
  • ☐ Retry kar rahe ho? Toh — operation idempotent hai? Backoff + jitter hai? Sirf transient errors pe?
  • ☐ Ye dependency critical hai ya optional? Optional hai toh circuit breaker + fallback lagao.
  • ☐ Iske resources bulkheaded hain?
  • ☐ Failure log ho rahi hai requestId aur context ke saath? (ch 16)
  • ☐ Metric hai — success rate aur latency? Alert kis pe lagega?
  • ☐ Error client tak jaa raha hai toh — internals leak toh nahi ho rahe? (ch 18)

Key Takeaways

  • Sawaal "failure kaise roken" nahi, "fail hone pe system kaise behave karta hai" hai.
  • Expected (validation, 404, 503 — normal flow) aur unexpected (bug) errors alag hain: pehle ko handle karo, doosre pe fail fast + alert.
  • Error nigalna (catch { log } aur aage badhna) sabse mehnga anti-pattern hai — failure 3 layers baad dikhegi.
  • Service domain errors throw kare; central handler unhe status codes mein map kare. 5xx pe asli message kabhi na bhejo.
  • unhandledRejection/uncaughtException pe crash and restart — corrupted process mein chalte rehna zyada khatarnak hai.
  • Har network call ka default timeout infinity hai — yahi outage ka sabse bada single cause hai.
  • Timeout budget banao: har layer ka timeout apne caller se kam.
  • Retry ke teen rules: sirf transient errors, sirf idempotent operations, hamesha backoff + jitter.
  • Retry amplification: 3 layers × 3 retries = 27 requests. Retry sirf ek layer pe, aur retry budget rakho.
  • Circuit breaker OPEN state mein 0ms mein fail karta hai — tumhare resources bachte hain aur downstream ko recover karne ka mauka milta hai. HALF-OPEN recovery ko safe banata hai.
  • Breaker threshold rate pe rakho (absolute count pe nahi) + minimum call count.
  • Bulkhead — per-dependency alag pools, alag queues, alag deployments. Ek slow dependency sab resources na khaye.
  • "Slow" "down" se zyada khatarnak hai — isliye up/down nahi, latency percentiles monitor karo.
  • Health check mein dependencies check mat karo — liveness aur readiness alag rakho, warna ek slow DB saare instances ko unhealthy kar dega.
  • Load shedding: overload pe kuch requests deliberately reject karo. Sabko slowly fail karne se 80% ko theek serve karna behtar hai.

🎯 Interview Questions

Q1. "Ek downstream service slow ho gayi. Tumhare system pe kya asar hoga?"

Bina defenses ke: requests atki rahengi, threads/connections pakde rahenge, pool khatam hoga, aur unrelated endpoints bhi fail karne lagenge; health check timeout hoga toh LB instances ko maar dega, traffic bache instances pe jaayega, aur cascading failure ban jaayega. Defenses layer by layer: timeout (slow ko fail mein badlo), bulkhead (blast radius seemit karo), circuit breaker (0ms fail), backoff+jitter (retry storm rokо), aur fallback/degradation.

Q2. "Circuit breaker kya hai? Retry se kaise alag hai?"

Retry ek request ka faisla hai; breaker system-level hai. Teen states: CLOSED (normal, failures count ho rahi hain), OPEN (failure rate threshold cross — calls bheji hi nahi jaati, 0ms mein fail), HALF-OPEN (reset window ke baad 1–2 test calls; pass → CLOSED, fail → OPEN). Do faayde: tumhare resources bachte hain (5s timeout ki jagah instant fail) aur downstream ko recover karne ka space milta hai. Threshold rate pe rakho, absolute count pe nahi.

Q3. "Retries kab nuksaan karti hain?"

Teen cases: (1) non-idempotent operation retry karna — double charge (fix: idempotency key, ch 9); (2) bina jitter ke — ek saath fail hui requests ek saath retry karti hain, thundering herd; (3) amplification — har layer 3 retries kare toh 3 layers = 27 requests, matlab already-overloaded service pe 27× load. Retry sirf ek layer pe rakho (user ke sabse paas wali), retry budget lagao, aur permanent errors (4xx) kabhi retry mat karo.

Q4. "Health check endpoint mein kya check karoge?"

Do alag endpoints. Liveness: kya process zinda hai — koi dependency check nahi, bas 200. Fail hone ka matlab restart. Readiness: kya ye instance traffic le sakta hai — sirf essential dependencies (DB), fast timeout ke saath. Sabhi downstream services ko check karna ek anti-pattern hai: ek non-critical service slow hui aur saare instances unhealthy ho gaye — partial degradation poora outage ban jaata hai.

Q5. "System overloaded hai. Kya karoge?"

Load shedding — kuch requests deliberately 503 + Retry-After ke saath reject karo, priority ke hisaab se (critical paths pehle, analytics/bulk baad mein). Reason counter-intuitive hai par decisive: overload pe agar system sab requests serve karne ki koshish karta hai toh sabki latency badhti hai, timeouts hote hain, retries aati hain, aur sab fail hota hai. 80% ko theek serve karna 100% ko slowly fail karne se behtar hai. Saath mein rate limiting (ch 18), backpressure, aur autoscaling (ch 19).
