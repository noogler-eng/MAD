Concurrency ≠ Parallelism

Ye do shabd roz mila diye jaate hain, par inka matlab bilkul alag hai — aur ye farq baaki poore chapter ki neev hai.

  • Concurrency = kai kaam ek saath chalu hain (progress mein). Zaroori nahi ki wo ek hi lamhe mein execute ho rahe hon.
  • Parallelism = kai kaam literally ek hi lamhe mein execute ho rahe hain. Iske liye multiple CPU cores chahiye — ye ek hardware zaroorat hai.

Rob Pike ki mashhoor line ka saar: concurrency bahut saari cheezon ko sambhalne ke baare mein hai, parallelism unhe ek saath karne ke baare mein. Ek single-core machine concurrent ho sakti hai (task switch karke), par parallel nahi.

🧠 Ek cook wali analogy

Ek cook (single core) do dishes bana raha hai: chawal gas pe chadha diya, aur jab tak wo pak raha hai wo sabzi kaat raha hai. Ye concurrency hai — dono kaam chalu hain, par wo ek waqt mein ek hi cheez kar raha hai; usne bas waiting time ka istemal kar liya. Do cooks (do cores) do dishes saath banayein — wo parallelism hai. Aur yahi is chapter ka core hai: IO-bound kaam mein wait bahut hai, isliye ek cook kaafi hai. CPU-bound kaam mein wait hai hi nahi, isliye zyada cooks hi ek matra raasta hai.

📌 Ch 19 se connection

Yahi wajah thi ki ch 19 mein bola tha "sirf CPU pe autoscale karna galat hai". IO-bound app mein CPU 20% pe rehta hai jabki wo requests handle karne mein struggle kar raha hota hai — kyunki uski limit CPU nahi, concurrency (connections, pool slots, event loop lag) hai. Autoscaling metric workload ke type se match karna chahiye.

Teen Concurrency Models

🧠 C10K problem — event loop kyun paida hua

Thread-per-request mein 10,000 concurrent connections ka matlab hai 10,000 threads × ~1 MB stack = 10 GB RAM, aur uske upar OS ka context switching overhead — jo itne threads pe khud ek bottleneck ban jaata hai. Par yaad karo ki wo saare threads kar kya rahe hain: wait. Toh event loop ne ek badla hua sawaal poocha: "agar sab wait hi kar rahe hain, toh ek hi thread se sabka wait manage kyun na karein?" Isiliye Node aur nginx dono ek thread pe hazaaron connections handle kar lete hain. Ye "Node fast hai" ka asli matlab hai — wo CPU pe fast nahi hai, wo waiting pe efficient hai.

Event Loop — Andar Se

event loop ka core
// Concept mein event loop bas ye hai:
while (true) {
  const ready = poll(pendingIO);              // OS se poocho: kaunsa IO ready hai?
  for (const e of ready) runCallback(e);      // uska callback chalao
}
// Ye poll() OS ke epoll (Linux) / kqueue (BSD) pe khada hai — jo hazaaron
// file descriptors ko ek saath efficiently watch kar sakta hai.

// ── Non-blocking IO — yahan thread RUKTA NAHI ──────────────
const rows = await db.query("SELECT …");
// Andar kya hua:
//   1. query socket pe likh di gayi
//   2. callback register hua, aur ye function SUSPEND ho gaya
//   3. event loop ne DOOSRI requests handle karni shuru kar di  ✅
//   4. DB response aaya → OS ne loop ko bataya → callback resume hua

// ⚠️ Ek nuance jo log miss karte hain: Node "single-threaded" hai —
// par sirf TUMHARA JS single-threaded hai. Andar ek libuv threadpool
// (default 4 threads) hai jo file IO, DNS lookups, aur kuch crypto
// handle karta hai, kyunki wo operations OS level pe truly async nahi hain.
// UV_THREADPOOL_SIZE se badhaya ja sakta hai.

Event Loop Block Hona

Event loop ka poora model ek shart pe khada hai: har callback jaldi khatam hona chahiye. Ek callback jo 2 second CPU khaata hai, us dauraan poore server ko rok deta hai — har connection ke liye. Ye Node ka sabse bada failure mode hai.

blocking — aur uske fix
// ❌ Ye poore server ko 2 second ke liye MAAR deta hai
app.post("/thumbnail", (req, res) => {
  const out = sharp.resizeSync(req.body.image);   // CPU-heavy, synchronous
  res.send(out);
});
// Is dauraan: koi nayi request accept nahi hogi, koi callback nahi chalega,
// aur health check bhi timeout hoga (ch 17) → LB instance ko unhealthy maar dega.
// EK request ne POORA instance gira diya.

// Doosre chhupe hue blockers:
JSON.parse(hugeString);           // 50 MB JSON ≈ 1s block (ch 5 ka size limit yaad karo)
crypto.pbkdf2Sync(…);             // password hashing — async version use karo (ch 6)
bigArray.sort();                  // 10 lakh items
const re = /(a+)+$/;               // catastrophic backtracking — ReDoS (ch 4, ch 18)
while (Date.now() - t < 1000) {}   // koi bhi busy loop

// ✅ Fix 1: worker thread — CPU kaam alag thread mein
const out = await workerPool.run("resize", req.body.image);
// main loop free rehta hai; kaam ek alag thread/core pe chalta hai

// ✅ Fix 2 (aksar behtar): QUEUE mein daal do (ch 12)
await queue.add("thumbnail", { imageId });
res.status(202).json({ jobId });   // ch 12 ka 202 pattern
// Worker alag process/machine pe — API instance CPU work karta hi nahi.
// Aur ye ch 14 ka bulkhead bhi hai: CPU work API ko gira nahi sakta.

// 📊 Event loop lag ko MONITOR karo (ch 16, ch 19) —
// ye Node apps ka sabse important saturation metric hai.
const h = monitorEventLoopDelay(); h.enable();
// h.p99 > 100ms → kuch block kar raha hai. Alert lagao.

Async/Await Andar Se — State Machines

async/await jaadu jaisa lagta hai: code synchronous dikhta hai par blocking nahi karta. Jaadu ye hai — compiler tumhare function ko ek state machine mein badal deta hai. Ye samajhna do practical faayde deta hai: pata chalta hai ki "suspend" ka matlab kya hai, aur kyun await ek race-condition ka darwaza hai (§10).

tumne kya likha vs compiler ne kya banaya
// ── Tumne likha ────────────────────────────────────────────
async function createOrder(userId) {
  const user  = await db.getUser(userId);      // suspend point 1
  const items = await db.getCart(user.id);     // suspend point 2
  return db.insert({ userId, items });
}

// ── Compiler ne conceptually kya banaya ────────────────────
function createOrder(userId) {
  let state = 0, user, items;         // ← locals HEAP pe chale gaye

  function step(value) {
    switch (state) {
      case 0:
        state = 1;
        db.getUser(userId).then(step);   // callback register karke RETURN kar do
        return;                          // ← thread FREE ho gaya ✅
      case 1:
        user = value;                    // resume: yahin se aage
        state = 2;
        db.getCart(user.id).then(step);
        return;
      case 2:
        items = value;
        return db.insert({ userId, items });
    }
  }
  step();
}
// Har `await` = ek state, ek resume point.
// "Suspend" ka matlab: function ne RETURN kar diya aur baad mein resume hoga.
🧠 Isse teen cheezein saaf ho jaati hain

1. Stack sasta hai. Thread ko ~1 MB stack chahiye kyunki wo block hota hai aur uska poora stack bacha ke rakhna padta hai. Async function suspend hone pe sirf apne live variables heap pe rakhta hai — kuch bytes. Yahi wajah hai ki ek process lakhon pending async operations rakh sakta hai par 10,000 threads nahi.
2. Colored functions. async function ko sirf async context se hi await kar sakte ho — isliye ek sync function ko async banane pe uske saare callers async banane padte hain. Ye "function coloring" async/await ki asli ergonomic keemat hai.
3. await ek yield point hai. Wahan doosri request ghus sakti hai — isiliye single-threaded Node mein bhi race conditions hoti hain (§10).

concurrency ka sabse common galat use
// ❌ SERIAL — 3 independent calls, ek ke baad ek. 600ms.
const user    = await getUser(id);      // 200ms
const orders  = await getOrders(id);    // 200ms
const reviews = await getReviews(id);   // 200ms

// ✅ PARALLEL — teenon ek saath. 200ms.
const [user, orders, reviews] = await Promise.all([
  getUser(id), getOrders(id), getReviews(id),
]);
// Trace (ch 16) mein serial calls ek SEEDHI SEEDHI staircase dikhti hai —
// wo dekhte hi pata chal jaata hai ki yahan Promise.all lagna chahiye tha.

// ⚠️ Promise.all mein ek fail = sab reject. Partial results chahiye toh:
const results = await Promise.allSettled([...]);   // ch 14 ka degradation

// ⚠️ Aur unbounded parallelism bhi ek trap hai:
await Promise.all(tenThousandIds.map(fetchOne));
// → 10,000 ek saath: DB pool khatam (ch 10), downstream kuchal gaya (ch 14).
// ✅ concurrency limit lagao (p-limit, semaphore) — jaise 20 at a time.

Goroutines Aur Virtual Threads

Ek teesra raasta hai jo dono ke faayde deta hai: lightweight threads jo runtime manage karta hai — Go mein goroutines, Java 21+ mein virtual threads, Erlang/Elixir mein processes.

OS threadGoroutine / virtual thread
Kaun manage karta haiOS kernelLanguage runtime
Initial stack~1 MB (fixed)~2–8 KB (grow hota hai)
Kitne practicalHazaaronLakhon
Context switchKernel — ~1–2 µsUser space — ~100 ns
Code kaisa dikhta haiBlocking (simple)Blocking (simple)
Function coloringNahiNahi ✅
M:N scheduling — mechanism
// Runtime N goroutines ko M OS threads pe MULTIPLEX karta hai (M ≈ cores).
// Jab ek goroutine IO pe block hoti hai, runtime usse HATA ke us OS thread pe
// doosri goroutine chala deta hai — bilkul event loop jaisa,
// par ye tumhare code se CHHUPA hua hai.

// Go — dikhne mein blocking, andar se async
func handler(w http.ResponseWriter, r *http.Request) {
    user := db.GetUser(id)      // "blocking" dikhta hai...
    orders := db.GetOrders(id)  // ...par OS thread free hota hai
    json.NewEncoder(w).Encode(...)
}
// Har request ek goroutine — 1 lakh concurrent requests bilkul normal hai.
// Koi async/await nahi, koi function coloring nahi, koi callback nahi.

// Java 21+ — bilkul wahi idea
Thread.startVirtualThread(() -> { ... });
// Purana thread-per-request code bina badle lakhon connections handle karne lagta hai.

// ⚠️ Par ek cheez ye BHI nahi badalti: CPU-bound kaam.
// Goroutines IO wait ko efficient banati hain. Ek CPU-heavy goroutine
// abhi bhi ek core poora khaati hai — parallelism sirf cores se aati hai.
📌 Yahi wajah hai ki Go backend ke liye popular hua

Purana trade-off tha: simple blocking code (threads) ya high concurrency (event loop) — dono ek saath nahi. Goroutines ne wo trade-off hi khatam kar diya: code thread-per-request jaisa simple dikhta hai, par scale event-loop jaisa milta hai. Java ne virtual threads se yahi 2023 mein kiya, aur uska sabse bada faayda ye hai ki purana blocking code bina rewrite kiye fayda uthata hai — jabki async/await migration mein har caller badalna padta hai (function coloring).

Python Ka GIL

Python mein ek extra layer hai jo bahut confusion paida karti hai: Global Interpreter Lock. GIL ek mutex hai jo guarantee karta hai ki ek waqt pe ek hi thread Python bytecode chala sakta hai.

GIL ka practical matlab
# ❌ CPU-bound + threads = koi speedup NAHI
# 4 threads, 4 cores — par GIL ki wajah se ek waqt pe ek hi chalega.
# Ulta context switching ka overhead add ho jaata hai.
with ThreadPoolExecutor(4) as ex:
    ex.map(cpu_heavy_function, items)      # ~1x speed. Bekaar.

# ✅ CPU-bound + processes = asli parallelism
# Har process ka apna interpreter, apna GIL.
with ProcessPoolExecutor(4) as ex:
    ex.map(cpu_heavy_function, items)      # ~4x speed ✅

# ✅ IO-bound + threads = THEEK hai!
# Kyunki IO wait ke dauraan thread GIL CHHOD deta hai.
with ThreadPoolExecutor(50) as ex:
    ex.map(fetch_url, urls)                # achha speedup ✅

# ✅ IO-bound + asyncio = sabse efficient (Node jaisa event loop)
await asyncio.gather(*[fetch(u) for u in urls])

# Isiliye production Python servers (gunicorn) MULTIPLE WORKER PROCESSES
# chalate hain — har process ka apna GIL, toh cores actually use hote hain.
# gunicorn -w 4 -k uvicorn.workers.UvicornWorker app:app
#          └ 4 processes  └ har process ke andar async event loop
📌 Yahi baat Node pe bhi lagti hai

Node bhi ek process mein ek hi core use karta hai. Isliye production mein cluster mode chalta hai — PM2 -i max, ya Kubernetes mein har pod ko 1 CPU dekar zyada pods. Rule dono jagah same hai: process count ≈ core count. Ek 8-core machine pe ek Node process chalana 7 cores barbaad karna hai.

🧠 Sabse practical rule

API instances ko IO-only rakho. Jaise hi koi CPU-heavy kaam aaye — image resize, PDF, report generation, bulk export — usse queue ke through ek alag worker fleet pe bhej do. Isse teen faayde ek saath milte hain: API ki latency predictable rehti hai, dono cheezein alag-alag scale ho sakti hain (worker fleet CPU-optimized, API memory-optimized), aur ek CPU spike API ko gira nahi sakta. Ye ch 12 (queues), ch 14 (bulkhead), aur ch 19 (scaling) — teenon ka sangam hai, aur shayad is poore handbook ka sabse zyada kaam aane wala single architectural rule.

Shared State Ke Khatre

Jaise hi asli parallelism aata hai (threads ya processes), shared mutable state ek problem ban jaati hai. Node ka single-threaded model tumhe zyadatar se bachata hai — par poori tarah nahi:

Node mein bhi race condition possible hai
// JS ka har SYNCHRONOUS block atomic hai — koi usse beech mein nahi rok sakta.
// Par `await` ek yield point hai: wahan doosri request ghus sakti hai.

let balance = 100;
async function withdraw(amount) {
  const current = await db.getBalance();   // ← YIELD POINT
  if (current < amount) throw new Error("insufficient");
  await db.setBalance(current - amount);   // ← aur YIELD POINT
}
// Do concurrent withdraw(100) calls: dono ne 100 padha, dono ne check pass kiya,
// dono ne 0 likha → 200 nikal gaye. Single-threaded hone ke BAWAJOOD.

// ✅ Fix wahi hai jo ch 10 mein tha — atomicity DB se lo, code se nahi:
UPDATE accounts SET balance = balance - $1
 WHERE id = $2 AND balance >= $1;   // rowCount=0 → insufficient
// ya SELECT … FOR UPDATE, ya version column (optimistic locking)

Asli threads wale environments (Java, Go, Python threads) mein aur bhi khatre hain — data races, deadlocks (ch 10 ka lock ordering yahan bhi lagta hai), aur non-atomic read-modify-write. Isliye modern approach yahi hai: shared mutable state se bacho — immutable data, message passing (Go channels, actor model), ya state ko ek shared store mein rakho jahan atomic operations hon (Redis, DB).

⚠️ Poore handbook ka ek dohraya hua sabak

Ch 7 (uniqueness check), ch 9 (idempotency key), ch 10 (lost update), ch 11 (cache lock), ch 18 (rate limit) — paanchon jagah ek hi galti thi: check-then-act. Do steps ke beech koi aur ghus sakta hai. Aur paanchon jagah fix bhi ek hi tha: operation ko atomic banao — DB constraint, conditional UPDATE, ON CONFLICT, ya SET NX. Concurrency ke baare mein sochna seekhne ka matlab hi ye pattern pehchanna hai.

Locks, Mutexes, Aur Channels

Shared state ko safe banane ke do bilkul alag philosophies hain — aur inka farq samajhna concurrency ka sabse valuable mental model hai.

philosophy 1 — memory share karo, access ko lock karo
// MUTEX (mutual exclusion) — ek waqt pe ek hi "critical section" mein ja sakta hai
mu.Lock()
balance = balance - amount     // critical section
mu.Unlock()

// Variants:
//   RWMutex   — kai readers saath, par writer akela (read-heavy ke liye)
//   Semaphore — N tak concurrent allowed (rate/concurrency limiting)
//   Atomic    — single variable pe lock-free operations (counters)

// ⚠️ Locks ke teen classic khatre:
//   1. DEADLOCK — ulte order mein locks (ch 10 ka lock ordering yahan bhi lagta hai)
//   2. Bhoolna — ek code path Unlock() miss kar gaya → sab atak gaya
//      (defer/RAII/finally use karo)
//   3. CONTENTION — bahut saare threads ek hi lock pe → wo lock hi bottleneck
//      ban jaata hai, aur parallelism ka faayda khatam
philosophy 2 — memory share hi mat karo, message bhejo
// Go ka mashhoor motto:
//   "Don't communicate by sharing memory; share memory by communicating."

// CHANNEL — ek typed pipe. Ek goroutine bhejti hai, doosri padhti hai.
// Data ka OWNERSHIP transfer ho jaata hai — do jagah se ek saath
// chhua hi nahi jaata, isliye lock ki zaroorat hi nahi.
ch := make(chan Order)
go producer(ch)      // bhejta hai
order := <-ch       // padhta hai — yahan tak koi shared mutable state nahi

// Worker pool — ye pattern ch 12 ke queue jaisa hi hai, par process ke andar
jobs := make(chan Job, 100)
for i := 0; i < 10; i++ { go worker(jobs) }   // 10 workers, bounded concurrency

// Actor model (Erlang/Elixir, Akka) isi ka aur strict version hai:
// har actor ka apna PRIVATE state, aur baat sirf messages se.
// Shared mutable state exist hi nahi karta, isliye data race possible hi nahi.
🧠 Practical guidance — kaunsa kab

Sabse pehla option: shared mutable state rakho hi mat. Backend mein ye aksar aasaan hai — state DB/Redis mein hoti hai (ch 19 ka stateless rule), aur wahan atomicity DB deta hai (UPDATE … WHERE, ON CONFLICT, INCR). Agar in-process state zaroori hai: ek simple counter → atomic; chhota critical section → mutex; ek pipeline ya ownership transfer → channel. Aur jo cheez lock se hamesha behtar hai wo hai lock ki zaroorat hi khatam kar dena — immutable data structures, ya per-request state jo share hi na ho.

⚠️ Distributed lock ek alag (aur mushkil) cheez hai

In-process mutex bharosemand hai. Par kai instances ke beech "lock" (jaise Redis SET NX — ch 11) guarantee nahi hai: lock-holder GC pause mein atak sakta hai, uska TTL expire ho sakta hai, aur do instances khud ko lock-holder samajh sakte hain. Isliye distributed locks ko sirf optimization ki tarah use karo (jaise duplicate kaam kam karna — cache stampede), correctness ke liye nahi. Correctness DB ke atomic operations ya fencing tokens se aani chahiye — yahi ch 10 aur ch 12 ka bar-bar dohraya gaya point hai.

Key Takeaways

  • Concurrency = kai kaam progress mein; parallelism = kai kaam ek hi lamhe mein (multiple cores zaroori).
  • IO-bound mein CPU 97% time khali hai — isliye ek thread hazaaron connections sambhal sakta hai.
  • CPU-bound mein khali time hai hi nahi — async wahan zero faayda deta hai; sirf aur cores kaam aate hain.
  • Event loop C10K problem ka jawab tha: 10,000 threads = 10 GB RAM, jabki wo sab bas wait kar rahe the.
  • "Node fast hai" ka matlab CPU pe fast nahi — waiting pe efficient hai.
  • Node "single-threaded" sirf tumhare JS ke liye hai; libuv threadpool (default 4) file IO, DNS, crypto karta hai.
  • Ek blocking callback poore instance ko rok deta hai — health check bhi fail hota hai, aur LB use maar deta hai.
  • Chhupe blockers: bada JSON.parse, sync crypto, bade sorts, ReDoS regex, busy loops.
  • Event loop lag Node apps ka sabse important saturation metric hai — usse monitor aur alert karo.
  • async/await compiler ko function ko state machine mein badalne ko kehta hai — har await ek suspend/resume point, aur locals heap pe. Isliye async stack thread stack se hazaaron guna sasta hai.
  • Function coloring async/await ki asli ergonomic keemat hai — ek function async karo toh saare callers async karne padte hain.
  • Independent awaits ko Promise.all se parallel karo — serial chain trace mein seedhi staircase dikhti hai. Par unbounded parallelism pool aur downstream dono ko kuchal deta hai; concurrency limit lagao.
  • Goroutines / virtual threads purana trade-off khatam kar dete hain: blocking-jaisa simple code aur event-loop-jaisa scale. Runtime N goroutines ko M OS threads pe multiplex karta hai.
  • Par wo bhi CPU-bound kaam nahi bachate — parallelism sirf cores se aati hai.
  • GIL: Python threads CPU-bound kaam ko tez nahi karte (processes chahiye), par IO-bound ke liye theek hain kyunki IO wait mein GIL chhod diya jaata hai.
  • Sync ke do philosophies: lock the memory (mutex, RWMutex, semaphore, atomic) vs share by communicating (channels, actors — ownership transfer, isliye lock hi nahi chahiye).
  • Locks ke teen khatre: deadlock (ordering — ch 10), Unlock bhoolna, aur contention (lock khud bottleneck ban jaata hai).
  • Distributed locks correctness ke liye nahi hain — GC pause + TTL expiry se do holders ho sakte hain. Unhe optimization ki tarah use karo; correctness DB atomicity se lo.
  • Node aur Python dono mein production rule: process count ≈ core count (cluster mode / gunicorn workers).
  • API instances ko IO-only rakho; CPU work queue ke through alag worker fleet pe. Handbook ka sabse kaam aane wala architectural rule.
  • Single-threaded hone ke bawajood await ek yield point hai — race conditions Node mein bhi hoti hain.
  • Check-then-act hi wo dohraya hua bug hai jo ch 7, 9, 10, 11, aur 18 — paanchon mein tha. Fix hamesha atomicity hai.

🎯 Interview Questions

Q1. "Concurrency aur parallelism mein farq?"

Concurrency ka matlab kai kaam progress mein hain — zaroori nahi ki ek hi lamhe mein chal rahe hon; ek single core bhi task switch karke concurrent ho sakta hai. Parallelism ka matlab wo literally ek hi lamhe mein execute ho rahe hain, jiske liye multiple cores chahiye. Practical asar: IO-bound kaam ko sirf concurrency chahiye (wait ka istemal), CPU-bound ko asli parallelism chahiye.

Q2. "Node single-threaded hai, phir wo hazaaron requests kaise handle karta hai?"

Kyunki typical request ka 95%+ time wait mein jaata hai (DB, network), CPU mein nahi. Event loop non-blocking IO use karta hai: request ka IO issue karke wo callback register karta hai aur turant doosri request pe chala jaata hai; OS (epoll/kqueue) batata hai kab data ready hai. Isliye ek thread hazaaron connections ka wait manage kar leta hai. Nuance: sirf tumhara JS single-threaded hai — libuv ka threadpool file IO, DNS, aur kuch crypto alag threads pe karta hai. Aur ye poora model tabhi kaam karta hai jab koi callback CPU ko lambe samay tak na roke.

Q3. "Ek Node endpoint image resize karta hai. Kya problem hai?"

CPU-heavy synchronous kaam event loop ko block kar deta hai — us dauraan koi request handle nahi hoti, callbacks ruk jaate hain, aur health check bhi timeout hota hai, jiske baad LB instance ko unhealthy mark kar deta hai. Ek request poore instance ko gira deti hai. Fix: chhote kaam ke liye worker thread, par behtar hai queue mein daalna (ch 12) aur 202 Accepted return karna, taaki CPU work ek alag worker fleet pe chale. Ye bulkhead bhi hai (ch 14). Aur event loop lag ko monitor karo.

Q4. "Python ka GIL kya hai? Threads bekaar hain?"

GIL ek mutex hai jo ek waqt pe sirf ek thread ko Python bytecode chalane deta hai. Iska matlab CPU-bound kaam mein threads se koi speedup nahi milta — uske liye ProcessPoolExecutor chahiye (har process ka apna GIL). Par threads IO-bound kaam ke liye bilkul theek hain, kyunki IO wait ke dauraan thread GIL chhod deta hai — aur asyncio usse bhi efficient hai. Isiliye production mein gunicorn multiple worker processes chalata hai, har ek ke andar async event loop.

Q5. "Single-threaded Node mein race condition ho sakti hai?"

Haan. Synchronous block atomic hota hai, par har await ek yield point hai jahan doosri request ghus sakti hai. Classic example: await getBalance() → check → await setBalance(). Do concurrent calls dono purana balance padh lengi aur dono check pass kar jaayengi. Fix wahi hai jo ch 10 mein tha — atomicity DB se lo: conditional UPDATE … WHERE balance >= $1, FOR UPDATE, ya version column. Ye check-then-act pattern poore handbook mein baar-baar aata hai.

Q6. "async/await andar se kaise kaam karta hai?"

Compiler function ko ek state machine mein transform karta hai: har await ek state ban jaata hai. await pe function callback register karke return kar deta hai — thread free ho jaata hai — aur IO complete hone pe wo agli state se resume hota hai. Locals stack ki jagah heap pe rakhe jaate hain, isliye ek suspended async operation kuch bytes leta hai jabki ek blocked thread ~1 MB stack. Do consequences: function coloring (async ko sirf async se await kar sakte ho) aur await ek yield point hai, isliye single-threaded runtime mein bhi race conditions possible hain.

Q7. "Goroutines threads se kaise alag hain?"

Goroutines runtime manage karta hai, OS nahi. Stack ~2–8 KB se shuru hoke grow hota hai (thread ka ~1 MB fixed), context switch user space mein ~100ns (kernel switch ~1–2µs), aur runtime N goroutines ko M OS threads pe multiplex karta hai — jab ek IO pe block hoti hai, us thread pe doosri chal jaati hai. Isliye lakhon goroutines practical hain. Sabse bada faayda ergonomic hai: code blocking jaisa simple dikhta hai par scale event-loop jaisa milta hai — koi function coloring nahi. Java 21 ke virtual threads bilkul yahi hain. Par CPU-bound kaam yahan bhi nahi bachta — uske liye cores hi chahiye.

Q8. "Shared state ko safe kaise banaoge — mutex ya channel?"

Pehla jawab: shared mutable state se bacho. Backend mein state aksar DB/Redis mein honi chahiye (ch 19 stateless rule), aur wahan atomicity DB deta hai. In-process zaroori ho toh: simple counter → atomic; chhota critical section → mutex; pipeline/ownership transfer → channel (Go ka "share memory by communicating" — data ka ownership move hota hai, isliye lock hi nahi chahiye). Locks ke khatre bata do: deadlock (consistent lock ordering se bacho), Unlock bhoolna, aur contention. Aur ek strong closing point: Redis-jaise distributed locks correctness ke liye bharosemand nahi hain — GC pause + TTL expiry do holders bana sakte hain.
