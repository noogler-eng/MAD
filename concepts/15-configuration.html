Configuration Management

Config Kya Hai — Aur Kya Nahi

12-Factor App ki definition sabse saaf hai: config wo hai jo environments ke beech badalta hai. Ye test bahut practical hai:

test: "kya ye staging aur production mein alag hoga?"
// ✅ CONFIG — environment ke saath badalta hai
DATABASE_URL         // local: localhost, prod: RDS endpoint
REDIS_URL
STRIPE_SECRET_KEY    // test key vs live key
LOG_LEVEL            // debug vs info
PORT
RATE_LIMIT_PER_MIN   // dev mein dheela, prod mein sakht

// ❌ CONFIG NAHI — har environment mein same, ye CODE hai
MAX_RETRIES = 3              // business decision, environment ka nahi
DEFAULT_PAGE_SIZE = 20
routes ki list
validation rules

// ⚠️ Boundary case: agar kabhi environment ke hisaab se tune karna pada
// (jaise staging mein rate limit dheela), tab wo config ban jaata hai.
// Par pehle se "sab kuch configurable" banane ki galti mat karo — har
// config option ek aur cheez hai jo galat set ho sakti hai.
🧠 Litmus test — "kya ye repo open-source kar sakte ho?"

Agar tum apna codebase public kar do, aur usme koi credential ya environment-specific value nahi honi chahiye — toh config theek se separate hai. Agar config/production.js mein real DB password hai, toh nahi hai. Ye ek line poore chapter ka sabse practical rule hai, aur if (env === "production") jaise conditionals ko bhi pakad leta hai — wo bhi environment-specific logic hai jo code mein ghus gayi hai.

Layering — Precedence Ka Order

Config ek jagah se nahi aati — kai sources hoti hain, aur unka order fix hona chahiye. Neeche wali upar wali ko override karti hai:

📌 Environment variables kyun default choice hain

Wo har language aur har platform (Docker, Kubernetes, systemd, Heroku) mein same tareeke se kaam karte hain, code mein commit nahi hote, aur deploy ke waqt inject ho sakte hain bina rebuild kiye. Limitation: sab strings hote hain (bilkul query params ki tarah — ch 7), aur nested structures unme achhe se fit nahi hote. Isliye env vars flat rakho aur unhe parse/validate karke ek typed object banao.

Boot Pe Validate Karo — Sabse Important Rule

Ye is chapter ka core hai. Config galat hone ka pata process start hote hi chalna chahiye — 3 ghante baad us pehle request pe nahi jo us feature ko chhuti hai.

❌ lazy access — ye pattern har codebase mein hai
// Jahan zaroorat hai wahan process.env padh lo
const key = process.env.STRIPE_SECRET_KEY;
await stripe(key).charges.create(…);

// Problems:
// 1. Env var missing hai → `undefined` → app THEEK se start ho jaata hai
//    aur pehle payment pe fail hota hai. Deploy safal dikhta hai.
// 2. process.env.PORT hamesha STRING hai — "3000", 3000 nahi
// 3. process.env.DEBUG = "false" → truthy string! (ch 7 wala coercion trap)
// 4. Kaunse env vars chahiye — iski koi central list hi nahi hai
✅ ek config module — parse, validate, freeze
// config.ts — poore app mein SIRF ye file process.env chhuti hai
import { z } from "zod";

const Schema = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]),

  // coerce — env var string hai, humein number chahiye (ch 7)
  PORT: z.coerce.number().int().min(1).max(65535).default(3000),

  // .url() — typo turant pakda jayega, connect karte waqt nahi
  DATABASE_URL: z.string().url(),
  REDIS_URL:    z.string().url(),

  // length check — galat/truncated key ab boot pe pakdi jayegi
  JWT_SECRET: z.string().min(32, "JWT_SECRET must be ≥32 chars"),
  STRIPE_SECRET_KEY: z.string().startsWith("sk_"),

  // boolean — "false" ko theek se handle karo
  ENABLE_METRICS: z.enum(["true","false"]).default("true").transform(v => v === "true"),

  LOG_LEVEL: z.enum(["debug","info","warn","error"]).default("info"),
})
// cross-field rules — production mein extra sakhti
.refine(c => c.NODE_ENV !== "production" || c.STRIPE_SECRET_KEY.startsWith("sk_live_"), {
  message: "production mein test Stripe key nahi chalegi",
});
// ↑ Ye ek REAL incident rokta hai: prod deploy test keys ke saath

const parsed = Schema.safeParse(process.env);

if (!parsed.success) {
  // SAARI galtiyan ek saath dikhao (ch 7) — ek-ek karke fix karana zulm hai
  console.error("❌ Invalid configuration:");
  for (const i of parsed.error.issues)
    console.error(`  ${i.path.join(".")}: ${i.message}`);
  process.exit(1);   // ← FAIL FAST. Half-configured app mat chalao.
}

export const config = Object.freeze(parsed.data);
// freeze — runtime pe koi galti se config mutate na kar de
// Aur type bhi mil gaya: config.PORT number hai, string nahi.
⚠️ Fail fast = ek achhi deploy strategy

Config galat hone pe process ka exit(1) karna aggressive lagta hai, par ye actually safe hai: Kubernetes ya koi bhi orchestrator naye pod ko crash-loop mein dekhega aur rollout rok dega — purane healthy pods chalte rahenge. Agar app "theek se" start ho jaata hai aur baad mein fail hota hai, toh rollout complete ho jaata hai, purane pods mar jaate hain, aur tumhare paas ek toota hua production hai. Crash on boot ek feature hai.

Feature Flags — Runtime Config

Ab tak jo config dekhi wo boot-time thi — badalne ke liye restart chahiye. Kuch cheezein chalte hue badalni hoti hain: ek feature band karna jo production mein phat gaya, ya naya feature 5% users pe try karna. Ye feature flags hain.

flags ke chaar kaam
// 1. KILL SWITCH — sabse valuable use case
if (await flags.enabled("new-checkout-flow")) { … } else { … }
// Feature phat gaya? Flag off karo — 5 second. Rollback deploy = 15 minute.

// 2. GRADUAL ROLLOUT — 1% → 10% → 50% → 100%
if (await flags.enabled("new-search", { userId })) { … }
// Bucketing DETERMINISTIC honi chahiye: hash(userId + flagName) % 100 < pct
// Warna ek hi user ko har request pe alag experience milega.

// 3. TRUNK-BASED DEVELOPMENT — adhoora code merge karo, flag off rakho
//    Lambi feature branches aur unke merge conflicts se bach jaate ho.

// 4. A/B TESTING — do variants, metrics compare
⚠️ Flags technical debt hain — expiry ke saath aane chahiye

Har flag ek if/else hai, matlab code paths double ho jaate hain. 50 flags = 2⁵⁰ theoretical combinations, jinme se zyadatar kabhi test hi nahi hue. Isliye har flag ke saath ek owner aur ek removal date rakho, aur 100% rollout ke baad usse code se hata do. "Purane flags saaf karna" ek recurring task hona chahiye, warna 2 saal baad koi nahi jaanta ki enable_new_billing_v2_final off karne se kya tootega.

📌 Flag evaluation fail-safe hona chahiye

Flag service down ho jaaye toh kya? Last known values cache rakho aur ek safe default define karo — flag lookup fail hone se poora request fail nahi hona chahiye. Ye ch 14 ka graceful degradation hai, aur flags ke case mein zaroori hai kyunki flag check har request ke critical path pe hota hai.

Key Takeaways

  • Config = wo jo environments ke beech badalta hai. MAX_RETRIES config nahi, code hai.
  • Litmus test: "kya ye repo public kar sakte ho?" — nahi, toh config theek se separate nahi hai.
  • Precedence: defaults → config file → env vars → CLI flags. Neeche wali jeetti hai.
  • Env vars default choice hain (har platform pe same, commit nahi hote, rebuild ke bina inject), par sab strings hote hain.
  • Boot pe validate karo — schema se parse, coerce, aur fail pe exit(1). Saari errors ek saath dikhao.
  • exit(1) ek feature hai: orchestrator crash-loop dekh ke rollout rok deta hai, purane healthy pods bache rehte hain.
  • Cross-field validation se real incidents rukte hain — jaise "production mein sk_test_ key nahi chalegi".
  • Config object ko freeze karo, aur process.env ko sirf ek module chhue.
  • Critical config ko required rakho — ?? "localhost" jaisa default prod ko chupchaap galat DB pe chala deta hai.
  • Secrets alag category hain: never in git, redact in logs, rotate, least privilege, audit.
  • .env.example commit karo (structure, values nahi) — wo onboarding documentation bhi hai.
  • Git se secret hatane ke liye revert kaafi nahi — history mein reh jaata hai. Push ho gaya toh rotate karo.
  • Feature flags = runtime config. Sabse bada faayda kill switch — 5 second vs 15 minute rollback.
  • Flag bucketing deterministic honi chahiye (hash(userId + flag)), warna user ko har request pe alag experience milega.
  • Flags technical debt hain — owner aur removal date ke saath aayein, aur 100% ke baad hataye jaayein.
  • if (env === "production") business logic mein mat likho — wo code path kabhi test nahi hota.

🎯 Interview Questions

Q1. "Config kahan rakhoge — file, env vars, ya database?"

Layered: code defaults (safe fallbacks) → per-environment config file (non-secret, git mein) → env vars (deploy-time, secrets yahan) → CLI flags (one-off). Env vars primary hain kyunki wo har platform pe same kaam karte hain, commit nahi hote, aur rebuild ke bina inject ho sakte hain. Database/flag service sirf us config ke liye jo runtime pe badalni ho — feature flags, kill switches.

Q2. "Missing ya galat env var ko kaise handle karoge?"

Boot pe validate karo aur fail fast. Ek config module ho jo process.env ko ek schema se parse kare — types coerce kare (env vars strings hain), URLs/lengths/prefixes check kare, aur fail hone pe saari errors ek saath print karke process.exit(1) kare. Ye safe hai kyunki orchestrator crash-loop dekh ke rollout rok deta hai; agar app "start ho jaata" aur baad mein fail hota, toh purane pods mar chuke hote aur production toota hua hota. Critical config ko default mat do — required rakho.

Q3. "Secrets kaise manage karoge?"

Kabhi git mein nahi (.gitignore + CI secret scanning), kabhi logs mein nahi (logger mein redact paths). Production mein secret manager (Vault, AWS Secrets Manager, k8s Secrets) — rotation, audit trail, aur least-privilege access ke liye. .env.example commit karo taaki structure documented rahe. Aur ek important detail: agar secret push ho chuka hai toh commit revert kaafi nahi — wo history mein hai, isliye secret rotate karna padega.

Q4. "Feature flags kis liye? Unke saath kya dikkat hoti hai?"

Chaar kaam: kill switch (sabse valuable — 5s mein feature band vs 15min rollback), gradual rollout, trunk-based development (adhoora code flag ke peeche merge), aur A/B testing. Dikkat: har flag code paths double karta hai, aur combinations kabhi test nahi hote — flags technical debt hain. Isliye owner + removal date, aur 100% rollout ke baad cleanup. Saath mein flag evaluation fail-safe hona chahiye (cached last-known value + safe default), warna flag service ka outage tumhara outage ban jaata hai.

Q5. "if (env === 'production') mein kya problem hai?"

Wo code path sirf production mein chalta hai — matlab wo kabhi test nahi hota, aur uske bugs sirf production mein milte hain (jahan sabse mehnge hote hain). Aur ye dev/prod parity todta hai. Behtar: behaviour ko ek config value banao — config.RATE_LIMIT, config.LOG_LEVEL — taaki har environment mein same code path chale, bas values alag hon. Tab tum staging mein production-jaisi values daal ke asli behaviour test kar sakte ho.
