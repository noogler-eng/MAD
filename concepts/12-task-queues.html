Task Queues & Background Jobs

Ab tak sab kuch request ke andar ho raha tha — user bheja, server kaam kiya, response gaya. Par bahut saara kaam aisa hota hai jo user ke intezaar karne layak hai hi nahi: email bhejna, PDF banana, image resize karna, report generate karna. Queue ka poora idea ek line mein hai: kaam ko time mein aage dhakel do — request se decouple kar do.

Problem — Sync Request Mein Kya Ghalat Ho Raha Hai

Ch 8 ka order example yaad karo, par ab sab kuch sync mein:

❌ sab kuch request ke andar
app.post("/orders", async (req, res) => {
  const order = await db.orders.create(…);        //   20 ms  — asli kaam

  await sendgrid.send(confirmationEmail);         //  800 ms  — user ko kya matlab?
  await pdfService.generateInvoice(order);        // 2500 ms
  await analytics.track("order_created", order);   //  300 ms
  await warehouse.notify(order);                  // 1200 ms

  res.json(order);                                 // TOTAL: ~4.8 seconds
});

Chaar alag problems, aur teesri sabse buri hai:

  • Latency — user 4.8 second baitha hai jabki uska asli kaam 20ms mein ho gaya tha.
  • Resource waste — poore 4.8 second ek connection aur (ch 10 ka) pool slot bandha hai.
  • Reliability ulta ho gaya — SendGrid down hone se order fail ho raha hai. Ek non-critical dependency ne critical path ko todna shuru kar diya. Aur agar PDF step pe fail hua toh order ban chuka hai par user ko error mila — wo retry karega aur duplicate order banega.
  • Retry namumkin hai — email fail ho gayi toh usse dobara try karne ka koi mechanism hi nahi hai. Wo permanently kho gayi.
🧠 Decision rule — kya sync rehna chahiye

Ek hi sawaal poocho: "kya user ko is kaam ka result abhi chahiye, ya wo fail ho toh poora operation invalid hai?" Haan → sync. Nahi → queue. Order create karna sync hai (user ko order ID chahiye). Confirmation email async hai (30 second baad aaye toh kisi ko farq nahi padta). Payment charge sync hai (fail hua toh order nahi banna chahiye). Invoice PDF async hai.

API Contract Badal Jaata Hai (202 Accepted)

Ye wo hissa hai jo log bhool jaate hain: async karne se API ka contract badalta hai. Server ab ye nahi keh sakta "ho gaya" — wo keh sakta hai "le liya, hoga".

202 pattern — ch 3 ka status code yahan kaam aata hai
// Long-running kaam ke liye (report generate, bulk import)
POST /reports
→ 202 Accepted
  Location: /jobs/job_8f3a2b            // yahan status dekho
  { "jobId": "job_8f3a2b", "status": "queued" }

// Client poll karta hai (ya WebSocket/SSE se push milta hai)
GET /jobs/job_8f3a2b
→ { "status": "processing", "progress": 40 }
→ { "status": "completed", "result": { "url": "/reports/xyz.pdf" } }
→ { "status": "failed",    "error": "source data unavailable" }

// ⚠️ 200 OK bhejna jhooth hai — client samjhega kaam pura ho gaya (ch 3)

Fire-and-forget kaam (email, analytics) ke liye job ID ki zaroorat nahi — bas 201 se order return karo aur email chupchaap background mein chali jaaye. Job status endpoint sirf tab chahiye jab user ko result ka intezaar hai.

Delivery Guarantees — At-Most/At-Least/Exactly Once

Ye distributed systems ka core concept hai, aur queue mein rozana dikhta hai:

GuaranteeMatlabRiskKab
At-most-once Kaam se pehle message delete — 0 ya 1 baar chalega Worker crash = kaam kho gaya Sirf jab kaam kho jaana acceptable ho (metrics ping)
At-least-once Kaam ke baad ack — 1 ya zyada baar chalega Duplicates Practically har broker ka default. Yahi use karo
Exactly-once Theek ek baar Distributed system mein end-to-end possible nahi Jo log "exactly once" bolte hain wo actually at-least-once + idempotency hai
⚠️ "Exactly once" ek marketing shabd hai

Socho: worker ne kaam khatam kiya aur ack bhejne se pehle crash ho gaya. Broker ko kabhi pata nahi chalega ki kaam hua tha — wo message dobara dega. Isse bachne ka koi tareeka nahi, kyunki "kaam karna" aur "ack karna" do alag operations hain jo atomically nahi ho sakte (wo do alag systems mein hain). Isliye asli engineering answer ye hai: at-least-once accept karo, aur worker ko idempotent banao. Ye bilkul wahi logic hai jo ch 3/ch 9 ke idempotency key ka tha.

Idempotent Workers — Non-Negotiable

Kyunki duplicates aayenge hi, har worker ko ek hi message do baar aane pe safe hona chahiye. Teen practical tareeke:

worker ko idempotent banane ke 3 tareeke
// ── 1. Processed-IDs table (sabse general) ─────────────────
async function handleOrderCreated(msg) {
  // message ID ko atomically claim karo — INSERT hi lock hai (ch 9 wala pattern)
  const claimed = await db.query(
    `INSERT INTO processed_messages (message_id, handler)
     VALUES ($1, 'order_created') ON CONFLICT DO NOTHING RETURNING 1`,
    [msg.id]
  );
  if (claimed.rowCount === 0) return;   // pehle ho chuka — chupchaap chhod do

  await sendEmail(msg.data);
}
// Table ko purani entries se saaf karte raho (7 din se purani delete).

// ── 2. Naturally idempotent likho (sabse achha jab possible ho) ──
// ❌ increment — dobara chala toh count galat
UPDATE stats SET views = views + 1 WHERE id = 1;
// ✅ absolute set — kitni baar bhi chalao, wahi state
UPDATE orders SET status = 'shipped', shipped_at = $1 WHERE id = $2;
// ✅ upsert
INSERT INTO invoices (order_id, …) VALUES (…)
  ON CONFLICT (order_id) DO UPDATE SET …;

// ── 3. Downstream ki idempotency use karo ──────────────────
await stripe.charges.create(payload, {
  idempotencyKey: `order-${orderId}-charge`   // Stripe khud duplicate rok dega (ch 9)
});

Retries, Backoff, Aur DLQ

Kaam fail hoga — network glitch, downstream 503, timeout. Par blindly retry karna cheezon ko bigaad deta hai:

retry policy — teen zaroori hisse
// ── 1. Transient vs permanent errors ko ALAG karo ──────────
try {
  await processJob(msg);
} catch (err) {
  if (err instanceof ValidationError || err.status === 404) {
    // PERMANENT — 100 retries se bhi theek nahi hoga. Seedha DLQ.
    await moveToDLQ(msg, err);
    return;
  }
  throw err;   // TRANSIENT (timeout, 503, connection reset) — retry karo
}

// ── 2. Exponential backoff + JITTER ────────────────────────
const delay = Math.min(
  1000 * 2 ** attempt,           // 1s, 2s, 4s, 8s, 16s…
  300_000                        // cap: 5 min
) * (0.5 + Math.random());        // ← jitter
// Jitter ke bina: 1000 jobs ek saath fail hue → sab exactly 1s baad ek saath
// retry karenge → wahi thundering herd. Ch 11 ke cache jitter jaisa hi (ch 14).

// ── 3. Max attempts, phir DLQ ──────────────────────────────
if (attempt >= 5) await moveToDLQ(msg, err);
⚠️ DLQ ek alert hai, ek storage nahi

Dead letter queue = wo messages jo N attempts ke baad bhi fail hue. Ye silently jama nahi hone chahiye — DLQ ki depth pe alert lagao (ch 16), warna 3 mahine baad pata chalta hai ki 40,000 emails kabhi gayi hi nahi. DLQ ka poora point ye hai ki tum message inspect karo, root cause fix karo, aur phir usse replay karo. Isliye DLQ message ke saath original payload, error, aur attempt count store karo.

Message Design — Kya Bhejein

accha message
{
  "id":      "msg_01HQ8Z3M",        // idempotency ke liye zaroori
  "type":    "order.created",
  "version": 1,                       // schema evolution (ch 5)
  "data":    { "orderId": "99" },     // ← sirf ID, poora object NAHI
  "meta": {
    "requestId": "req_8f3a",       // trace jodne ke liye (ch 8, ch 16)
    "createdAt": "2026-08-17T09:14:22Z"
  }
}

ID bhejo, poora object nahi — kyunki message queue mein 30 second (ya retry ke baad 10 minute) pada rah sakta hai, aur tab tak data badal chuka hoga. Worker ko hamesha current state chahiye, snapshot nahi. Exception: agar tumhe deliberately us waqt ka snapshot chahiye (audit log, historical email content), tab data embed karo — par wo ek conscious decision ho.

Aur ch 7 ka rule yahan bhi: worker mein message ko validate karo. Producer deploy ho chuka hai naye format ke saath, par queue mein purane format ke messages pade hain — ye normal hai, bug nahi.

Dual Write Problem Aur Outbox Pattern

Ek subtle par important bug. Tum DB mein likhte ho aur queue mein push karte ho — do alag systems. Beech mein crash hua toh?

dual write — dono taraf toot-ta hai
// ❌ Order A
await db.orders.create(order);      // ✅ commit ho gaya
// 💥 process crash
await queue.push("order.created");   // ❌ kabhi nahi chala
// → order exist karta hai, par email/invoice kabhi nahi honge. SILENT loss.

// ❌ Order B (ulta karo toh ulta bug)
await queue.push("order.created");   // ✅ push ho gaya
await db.orders.create(order);      // ❌ transaction fail
// → worker ek aise order ko process karega jo exist hi nahi karta
✅ Outbox pattern — ek hi transaction
// Insight: message ko USI DATABASE mein likho, usi transaction mein.
// Ab do systems nahi rahe — atomicity DB se free mein mil gayi.
await db.transaction(async (tx) => {
  const order = await tx.orders.create(data);
  await tx.outbox.insert({                  // ← ek SAADI table
    id: ulid(), type: "order.created",
    payload: { orderId: order.id }, status: "pending",
  });
});
// Dono commit honge ya dono nahi. Beech ki koi state hai hi nahi.

// Ek alag relay process outbox se padh ke broker pe bhejta hai
const rows = await db.query(
  `SELECT * FROM outbox WHERE status = 'pending'
   ORDER BY id LIMIT 100
   FOR UPDATE SKIP LOCKED`            // ← kai relay instances safely chal sakte hain
);
for (const r of rows) {
  await broker.publish(r);
  await db.outbox.markSent(r.id);
}
// Relay crash hua publish ke BAAD, markSent se PEHLE? → duplicate.
// Isliye at-least-once hai — aur isiliye worker idempotent hona zaroori hai (§5).
📌 SKIP LOCKED — ek chhota par powerful Postgres feature

FOR UPDATE SKIP LOCKED kehta hai: "jo rows already kisi aur ne lock ki hain, unhe chhod do aur aage badho". Isse kai workers ek hi table se bina ek doosre ko block kiye kaam utha sakte hain — matlab tum Postgres ko hi ek queue ki tarah use kar sakte ho. Chhote aur medium scale pe ye ek genuinely accha option hai: ek kam infrastructure component, aur outbox atomicity free mein.

Key Takeaways

  • Queue ka idea: kaam ko time mein aage dhakelna, request se decouple karna.
  • Sync mein rakhne ka test: "user ko result abhi chahiye, ya fail hone pe poora operation invalid hai?"
  • Sabse bada faayda latency nahi — reliability: non-critical dependency (SendGrid) ab critical path ko nahi tod sakti.
  • Teen hisse: producer, broker, worker. Workers independently scale hote hain.
  • Async karne se API contract badalta hai — 202 Accepted + job status endpoint, 200 nahi.
  • Exactly-once possible nahi hai (ack aur kaam atomically nahi ho sakte). Asli answer: at-least-once + idempotent worker.
  • Idempotency ke 3 tareeke: processed-IDs table (ON CONFLICT DO NOTHING), naturally idempotent operations (absolute set/upsert, increment nahi), ya downstream ki idempotency key.
  • Retries mein transient aur permanent errors alag karo — validation error 100 baar retry karke bhi pass nahi hogi.
  • Exponential backoff + jitter — bina jitter ke ek saath fail hue jobs ek saath retry karte hain (thundering herd).
  • DLQ ek alert hai, storage nahi — uski depth pe monitoring lagao aur replay ka raasta rakho.
  • Message mein ID bhejo, poora object nahi — queue mein pade-pade data badal jaata hai.
  • Worker mein message ko validate karo — purane format ke messages queue mein padey hona normal hai.
  • Dual write problem: DB + queue do alag systems hain, beech mein crash = silent loss. Fix outbox pattern — message usi DB transaction mein likho, ek relay usse broker pe bheje.
  • FOR UPDATE SKIP LOCKED se Postgres khud ek accha queue ban jaata hai — chhote/medium scale pe ek kam moving part.
  • Monitor karo: queue depth aur oldest message age — dono.

🎯 Interview Questions

Q1. "Kaunsa kaam queue mein daaloge aur kaunsa sync rakhoge?"

Test: kya user ko result abhi chahiye, ya fail hone pe poora operation invalid hai? Order create aur payment charge sync (user ko order ID chahiye, charge fail = order nahi banna chahiye). Confirmation email, invoice PDF, analytics, warehouse notification async. Asli argument latency nahi hai — reliability hai: sync rakhne ka matlab SendGrid ka downtime tumhare order flow ka downtime ban jaata hai.

Q2. "Exactly-once delivery kaise achieve karoge?"

End-to-end nahi kar sakte — worker kaam karke ack se pehle crash ho sakta hai, aur broker ko farq pata nahi chalega, toh wo redeliver karega. "Kaam karna" aur "ack karna" do alag systems mein hain, atomically nahi ho sakte. Isliye practical answer: at-least-once delivery + idempotent processing — processed-message-IDs table, ya naturally idempotent operations (absolute set/upsert), ya downstream idempotency key (Stripe).

Q3. "DB mein order banaya aur queue mein push kiya — beech mein crash. Kya hoga?"

Dual write problem. Order commit ho gaya par message nahi gaya → email/invoice kabhi nahi honge, aur koi error bhi nahi dikhega. Ulta order karo toh worker ek non-existent order process karega. Fix: outbox pattern — message ko usi DB transaction mein ek outbox table mein likho, taaki dono ek saath commit hon; ek alag relay process FOR UPDATE SKIP LOCKED se rows uthake broker pe bheje. Relay publish ke baad crash ho sakta hai, isliye ye at-least-once hai — worker idempotent hona chahiye.

Q4. "Job baar-baar fail ho raha hai. Retry strategy?"

Pehle error classify karo: permanent (validation error, 404, malformed payload) → seedha DLQ, retry bekaar hai. Transient (timeout, 503, connection reset) → retry with exponential backoff + jitter, cap ke saath. Jitter zaroori hai warna ek saath fail hue 1000 jobs ek saath retry karke thundering herd banayenge. Max ~5 attempts ke baad DLQ, aur DLQ depth pe alert — wo inspect, fix, aur replay ke liye hai, silently jama hone ke liye nahi.

Q5. "Message mein poora object bhejoge ya sirf ID?"

Default sirf ID — message queue mein seconds se minutes tak pada rah sakta hai (aur retry ke baad aur zyada), tab tak data badal chuka hoga; worker ko current state chahiye. Exception: jab tumhe deliberately us waqt ka snapshot chahiye (audit trail, email ka exact content) — tab embed karo, par consciously. Saath mein message ID (idempotency), version (schema evolution), aur requestId (tracing) hamesha rakho.
