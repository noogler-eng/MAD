Routing

Request server tak pahunch gayi aur parse ho gayi — ab uske paas ek method (GET) aur ek path (/users/42/posts) hai. Routing wo layer hai jo is jodi ko ek specific handler function tak le jaati hai. Dekhne mein trivial lagta hai, par isme ek asli data-structure problem chupi hui hai — aur uska solution samajhne se route conflicts, 404 mysteries, aur middleware ordering sab clear ho jaate hain.

Problem Kya Hai — Ek Dispatch Table

Ch 3 se hume mila: ek method aur ek path. Ab ek application mein sainkdon handlers hote hain. Router ka kaam ek sentence mein:

router ka contract
// Input:  method + path
// Output: ek handler function + URL se nikale gaye params

match("GET", "/users/42/posts")
  --> { handler: getUserPosts, params: { userId: "42" } }

// Match na mile toh: 404 Not Found
// Path mile par method na mile toh: 405 Method Not Allowed
//   (+ Allow: GET, POST header — bahut kam log ye sahi karte hain)

Do cheezein dhyan do. Pehla — method bhi key ka hissa hai. GET /users aur POST /users do alag routes hain. Dusra — routing sirf lookup nahi hai, wo path se data extract bhi karti hai (42 → userId). Yahi wo cheez hai jo isse ek simple hashmap se zyada complex banati hai.

Naive Approach Aur Uski Limit

Pehla instinct — ek hashmap:

approach 1 — exact match hashmap
routes = {
  "GET /users":    listUsers,
  "POST /users":   createUser,
  "GET /health":   healthCheck,
}
handler = routes[method + " " + path]   // O(1) — bahut fast

Static paths ke liye ye perfect hai — O(1), simple. Par /users/42 pe ye phat jaata hai: tum har possible user ID ko map mein nahi daal sakte. Dynamic segments chahiye.

approach 2 — regex list (linear scan)
// har route ko regex mein compile karo, aur ek-ek karke try karo
routes = [
  { method: "GET", re: /^\/users$/,                 h: listUsers },
  { method: "GET", re: /^\/users\/([^/]+)$/,        h: getUser,   keys: ["id"] },
  { method: "GET", re: /^\/users\/([^/]+)\/posts$/,  h: getPosts,  keys: ["id"] },
]

// matching: pehla jo match kare, wahi jeeta
for (r of routes) {
  if (r.method !== method) continue;
  m = r.re.exec(path);
  if (m) return { handler: r.h, params: zip(r.keys, m.slice(1)) };
}
return notFound;   // O(n) — n = total routes

Ye kaam karta hai, aur Express jaisi frameworks aaj bhi asal mein yahi karti hain. Problem O(n) hai: 500 routes wali app mein har request pe upto 500 regex executions. Chhoti app mein farq nahi padta; API gateway ya high-throughput service mein ye seedha latency mein dikhta hai. Aur ek subtle issue — declaration order matter karta hai, jo ek poora bug class kholta hai (neeche §5).

Radix Tree — Asli Routers Kaise Kaam Karte Hain

Fast routers (Go ka httprouter/gin, Fastify, FastAPI ka Starlette, Rails ka journey) path ko ek string ki tarah nahi, segments ke rooop mein dekhte hain aur ek prefix tree (radix tree / trie) banate hain. Insight simple hai: bahut saare routes prefix share karte hain — /users, /users/:id, /users/:id/posts sab users se shuru hote hain. Toh users ko baar-baar match karne ki jagah, ek baar match karo aur us subtree mein utar jao.

🧠 Yahi pattern tumne pehle bhi dekha hai

Prefix tree pe lookup = database index pe lookup (ch 10 mein B-tree), = DNS ki hierarchical resolution (ch 2). Teenon ek hi idea hain: data ko aise structure karo ki har step search space ko kaat de, linear scan ki jagah. Jab bhi kahin "n cheezon mein se ek dhoondhni hai" dikhe, ye sawaal poocho — kya inme shared structure hai jisse tree ban sakta hai?

Params Ke Teen Alag Types

"Params" ek hi shabd hai par teen bilkul alag cheezein iske naam se aati hain — aur inhe mix karna beginners ka sabse common confusion hai:

TypeKahan seKis kaam ke liyeExample
Path params URL path ke andar, route pattern se extract Resource ki identity — kaunsa resource /users/42 → id=42
Query params ? ke baad, key=value pairs Resource ko modify karna — filter, sort, paginate /users?page=2&sort=name
Body params Request body (ch 5 mein deserialize hota hai) Bheja gaya data — create/update payload {"name":"Sharad"}

Design rule jo 90% cases decide kar deta hai:

  • Cheez kaunsi hai → path param. (/orders/1234)
  • Cheez kaisi chahiye → query param. (/orders?status=paid&limit=20)
  • Cheez kya bhej rahe ho → body.
⚠️ Path params hamesha strings hote hain

/users/42 se tumhe "42" milta hai, 42 nahi — URL mein types exist hi nahi karte. Isliye if (params.id === 42) chupchaap false dega, aur SQL query mein string bhejne se index skip ho sakta hai. Type coercion aur validation ek explicit layer ka kaam hai, router ka nahi — wahi ch 7 hai. Yahi cheez query params pe bhi lagti hai: ?active=false mein "false" ek truthy string hai.

📌 URL encoding — ek chhoti par kaat-ne wali detail

Path segment mein /, space, ?, # jaise characters percent-encoded hote hain (%2F, %20). Router decode ke baad match karta hai, warna ek email jaisa ID (/users/a%40b.com) kabhi match hi nahi karta. Aur ek security note: agar tum path param ko file path banane ke liye use kar rahe ho, toh %2e%2e%2f (../) path traversal ka classic attack vector hai — ch 18.

Precedence — Kaunsa Route Jeetega

Do routes ek hi path pe match kar sakte hain. /users/me aur /users/:id — request GET /users/me aaye toh kaun jeete? Iska jawab router ke type pe depend karta hai, aur yahi sabse common routing bug ki jadd hai.

Router typeRuleFramework
Order-based Jo pehle declare hua, wo jeeta. Tumhari file ka order = behaviour Express, Flask (mostly), Koa
Specificity-based Tree pe fixed priority: static > param > wildcard. Order irrelevant gin/httprouter, Fastify, Next.js app router
order-based router mein classic bug
// ❌ GALAT — :id pehle declare hai
app.get("/users/:id", getUser);     // "me" bhi ek valid :id hai!
app.get("/users/me",  getProfile);  // ye kabhi chalega hi nahi — dead code

// GET /users/me → getUser chalega, id = "me"
// → DB mein WHERE id = 'me' → 404 ya type error. Ghanton debug hota hai.

// ✅ SAHI — specific route pehle
app.get("/users/me",  getProfile);  // exact match pehle try hota hai
app.get("/users/:id", getUser);     // fallback

Specificity-based router mein ye bug ho hi nahi sakta — tree khud me (static child) ko :id (param child) se pehle try karta hai, chahe tumne kis order mein register kiya ho. Ye ek accha example hai ki data structure ka choice ek poori bug class ko mita deta hai.

Route Grouping Aur Mounting

Bade apps mein routes flat list nahi rehte — wo groups mein organize hote hain, aur har group ka apna prefix aur apni middleware chain hoti hai. Ye ch 8 (middleware) ka direct connection hai.

grouping — prefix + shared middleware
// ── admin sub-router: apna prefix, apni middleware ──────────
adminRouter = Router();
adminRouter.use(requireAuth);              // is group ki HAR route pe chalega
adminRouter.use(requireRole("admin"));    // authZ — ch 6
adminRouter.get("/stats",   getStats);   // final path: /admin/stats
adminRouter.delete("/users/:id", deleteUser);

// ── public routes: koi auth nahi ────────────────────────────
publicRouter = Router();
publicRouter.post("/login", login);

// ── mount: prefix yahan judta hai ───────────────────────────
app.use("/admin", adminRouter);      // tree mein "admin" ke neeche poora subtree
app.use("/auth",  publicRouter);

Iska asli faayda security hai: auth check ek jagah group pe lagta hai, har handler mein repeat nahi hota. Naya admin endpoint add karne wala developer auth lagana bhool hi nahi sakta — wo structurally inherited hai. Ye "secure by default" ka ek chhota par powerful example hai.

Rozana Milne Wale Routing Bugs

SymptomAsli wajahFix
Route hai par 404 aa raha hai Trailing slash mismatch (/users vs /users/), ya router mount hi nahi hua Router ka strict-slash setting check karo; redirect ya dono accept karo
Galat handler chal raha hai Order-based router mein param route specific route se pehle declare hai Specific pehle, param baad mein
405 ki jagah 404 Router method ko path se pehle match kar raha hai Path match par method na mile → 405 + Allow header
CORS preflight fail OPTIONS route register hi nahi hai CORS middleware ko routes se pehle mount karo
Middleware chal hi nahi rahi app.use() route registration ke baad likha hai Middleware upar, routes neeche — chain top-to-bottom banti hai
Wildcard sab kuch kha raha hai app.use("*") ya catch-all specific routes se pehle hai Catch-all hamesha sabse aakhir mein
⚠️ ReDoS — routing ka security angle

Agar router regex-based hai aur tum custom regex constraints likhte ho (/files/:name(.+)+ jaise nested quantifiers), toh ek specially-crafted URL catastrophic backtracking trigger kar sakta hai — ek request CPU ko seconds tak jaam kar deti hai. Single-threaded runtime (Node) mein iska matlab poora server block. Isliye route patterns simple rakho, aur user input pe regex chalane se pehle length cap lagao. Detail ch 18, aur "ek request ne server block kar diya" ka mechanism ch 21.

Key Takeaways

  • Router ka contract: (method, path) → handler + params. Method key ka hissa hai, sirf path nahi.
  • Static routes hashmap se O(1) match hote hain; dynamic segments ke liye regex list (O(n)) ya radix tree chahiye.
  • Radix tree lookup ko path ki lambai pe depend karta hai, routes ki ginti pe nahi — 50 ho ya 5000, same cost.
  • Tree mein priority fixed hai: static > param > wildcard — isliye declaration order irrelevant ho jaata hai.
  • Order-based routers (Express) mein /users/:id ko /users/me se pehle likhna ek poora endpoint dead kar deta hai.
  • Path param = kaunsa, query param = kaisa, body = kya.
  • Params hamesha strings hote hain — coercion aur validation alag layer ka kaam hai (ch 7).
  • Grouping/mounting se auth structurally inherit hoti hai — naya endpoint likhne wala usse bhool nahi sakta.
  • Path match par method na mile toh 405 + Allow, 404 nahi.

🎯 Interview Questions

Q1. "Router andar se kaise kaam karta hai? 5000 routes pe kaise fast rakhoge?"

Naive: regex list, O(n) per request. Better: path ko segments mein todo aur ek radix tree banao jahan common prefixes share hote hain — lookup O(segments), routes ki ginti se independent. Har node pe children static → param → wildcard priority mein try hote hain. Method ke liye ya toh per-node method map ho, ya alag tree per method.

Q2. "/users/me galat handler pe ja raha hai. Kya hua?"

Order-based router mein /users/:id pehle declare hai, aur "me" ek valid :id value hai — toh wahi match kar gaya. Fix: specific route pehle. Root cause samjhao: Express order pe chalta hai, specificity pe nahi; gin/Fastify jaise tree-based routers mein ye bug possible hi nahi.

Q3. "Path param vs query param — kab kaunsa?"

Path param resource ki identity hai — uske bina resource define hi nahi hota (/orders/1234). Query param collection ko modify karta hai — filter, sort, pagination — aur optional hota hai (/orders?status=paid&page=2). Test: param hatao, agar URL ka matlab hi khatam ho gaya toh wo path param tha.

Q4. "Ek endpoint pe auth check lagana bhool gaye — isse structurally kaise rokoge?"

Per-handler auth call ki jagah route grouping — protected routes ek sub-router pe mount ho jispe auth middleware group-level pe lagi ho. Naya route usi group mein add hoga toh auth automatically inherited. Aur strong answer mein ek line aur: default deny — public routes ko explicitly whitelist karo, protected ko nahi.
