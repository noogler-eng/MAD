Full-Text Search

Ch 10 mein ek line thi: LIKE '%query%' index use kar hi nahi sakta. Par asli problem usse bhi badi hai — LIKE se "running shoes" search karne pe "run shoe" nahi milta, spelling galti pe kuch nahi milta, aur results ka koi order nahi hota. Search sirf ek fast WHERE nahi hai; wo ek bilkul alag data structure aur ek bilkul alag problem hai — relevance.

LIKE Kyun Kaafi Nahi Hai

chaar alag failures, ek hi query mein
SELECT * FROM products WHERE description ILIKE '%running shoes%';

-- 1. PERFORMANCE — leading wildcard, toh B-tree seek kar hi nahi sakta (ch 10)
--    har row, har baar. 10 lakh products = 10 lakh string comparisons.

-- 2. LINGUISTICS — exact substring chahiye
--    "running shoes" ye sab MISS karega:
--      "shoes for running"      (word order alag)
--      "run shoe"               (word form alag)
--      "Running Shoe - Nike"    (ILIKE case bacha leta hai, par exact phrase chahiye)

-- 3. RANKING — koi order nahi. Ek product jiske TITLE mein "running shoes" hai
--    aur ek jiske 2000-word description mein ek baar aaya hai — dono barabar.

-- 4. TYPOS — "runing shoes" → 0 results. User ko lagta hai stock hi nahi hai.
🧠 Mental shift — search ek ranking problem hai, filtering nahi

Database query ka jawab binary hota hai: row match karti hai ya nahi. Search ka jawab graded hota hai: ye row kitni relevant hai. Isliye search engine ka output ek set nahi, ek sorted list with scores hota hai. Ye ek line poore chapter ka base hai — aur yahi wajah hai ki search ke liye alag index, alag pipeline, aur alag tooling chahiye.

Inverted Index — Poora Raaz

Normal (forward) index ye rakhta hai: document → uske words. Search ke liye tumhe ulta chahiye: word → un documents ki list jisme wo hai. Isi ulte mapping ka naam inverted index hai — aur ye poore search ka core hai, chahe Postgres ho ya Elasticsearch.

Analyzer Pipeline — Text Se Tokens Tak

Inverted index mein raw words nahi jaate. Text ek analyzer pipeline se guzarta hai jo use normalize karti hai. Aur sabse important rule: wahi pipeline query pe bhi chalti hai — tabhi dono match kar paate hain.

analyzer ke steps
Input:  "The Running Shoes aren't cheap!"

// 1. CHARACTER FILTER — HTML strip, unicode normalize
     "The Running Shoes aren't cheap!"

// 2. TOKENIZER — text ko tokens mein todo
     ["The", "Running", "Shoes", "aren't", "cheap"]

// 3. LOWERCASE
     ["the", "running", "shoes", "aren't", "cheap"]

// 4. STOPWORD REMOVAL — "the", "a", "is" har doc mein hain, koi info nahi dete
     ["running", "shoes", "cheap"]
// ⚠️ Par dhyan: "The Who", "to be or not to be" — stopwords hatane se ye
//    queries mar jaati hain. Modern engines aksar stopwords rakhte hain
//    aur scoring (IDF) se hi unka weight kam kar dete hain.

// 5. STEMMING — word ko uske root tak kaato
     ["run", "shoe", "cheap"]
// Ab "running", "runs", "ran", "runner" — sab "run" pe map hote hain.
// YAHI wo cheez hai jo LIKE kabhi nahi kar sakta.

// Query pe bhi WAHI pipeline:
"shoes for running" → ["shoe", "run"] → dono index mein hain → ✅ MATCH
⚠️ Analyzer mismatch = "search kaam hi nahi kar raha"

Agar index karte waqt ek analyzer use kiya aur query pe doosra, toh tokens match hi nahi karenge aur har search khali aayegi — bina kisi error ke. Ye Elasticsearch ka sabse common "kuch bhi nahi mil raha" wala bug hai. Aur ek aur baat: analyzer badalne pe poora index dobara banana padta hai, kyunki purane documents purane tokens ke saath store hain.

📌 Stemming vs lemmatization, aur Indian languages

Stemming rule-based kaat-chhaant hai — fast, par "university" → "univers" jaise galat roots bana deta hai. Lemmatization dictionary use karke asli root nikaalta hai ("better" → "good") — accurate par slow. English ke liye stemming (Snowball/Porter) kaafi hai. Hindi aur baaki Indian languages ke liye ye zyada complex hai (rich morphology, aur Hinglish mein transliteration variants — "khareedna" vs "kharidna"); wahan aksar n-gram based approach ya custom synonym lists behtar kaam karti hain.

Relevance Scoring — TF-IDF Se BM25

Ab asli sawaal: 5000 documents match kar gaye, unhe order kis hisaab se karein? Do intuitions se poori cheez ban jaati hai.

  • TF — Term Frequency: jis document mein wo word zyada baar aaya hai, wo shayad zyada relevant hai.
  • IDF — Inverse Document Frequency: jo word har document mein hai ("the", "product"), wo kuch batata hi nahi. Jo word kam documents mein hai ("vibranium"), wo bahut kuch batata hai. Isliye rare terms ko zyada weight.
score = TF × IDF, aur BM25 ke do sudhaar
// Query "running shoes" ke liye har matching doc ka score:
score(doc) = Σ over query terms [ TF(term, doc) × IDF(term) ]

// Example: 10,00,000 products ka corpus
//   "shoes"    9,00,000 docs mein  → IDF kam   → weight kam
//   "vibranium"      12 docs mein  → IDF zyada → weight BAHUT zyada
// Isliye "vibranium shoes" search mein vibranium wale docs upar aayenge.

// ── BM25 (aaj ka default: Lucene, ES, Postgres) do problems fix karta hai ──

// 1. TF SATURATION — word 100 baar aane ka matlab 10 baar se 10x relevant NAHI hai
//    Plain TF: 1 → 1, 10 → 10, 100 → 100   (linear, keyword stuffing se exploit hota hai)
//    BM25:     1 → 1, 10 → 2.4, 100 → 2.9  (saturate ho jaata hai)

// 2. LENGTH NORMALIZATION — 50-word title mein "shoe" aana zyada strong signal hai
//    bajaye 5000-word description mein aane ke. BM25 doc length se divide karta hai.

// ── Field boosting — practical relevance ka sabse bada lever ──
{ "multi_match": {
    "query": "running shoes",
    "fields": ["title^3", "brand^2", "description"]   // title 3× weight
}}
// Title mein match hona description mein match hone se kahin zyada matlab rakhta hai.

Postgres Ka Built-in FTS

Elasticsearch pe jaane se pehle: Postgres ke paas already full-text search hai, aur zyadatar apps ke liye wo kaafi hai. Ek kam infrastructure component, aur data hamesha in-sync (§7 ka poora problem hi nahi aata).

Postgres FTS — production setup
-- tsvector = analyzed tokens, tsquery = analyzed query
SELECT to_tsvector('english', 'The Running Shoes');
-- → 'run':2 'shoe':3        ← stemmed, stopwords hatt gaye, positions ke saath

-- ✅ Generated column — hamesha auto in-sync rehta hai
ALTER TABLE products ADD COLUMN search_vector tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce(title,'')),       'A') ||
    setweight(to_tsvector('english', coalesce(brand,'')),       'B') ||
    setweight(to_tsvector('english', coalesce(description,'')), 'C')
  ) STORED;
-- setweight A/B/C/D = field boosting ka Postgres version
-- coalesce zaroori hai — ek NULL poore vector ko NULL kar deta hai

CREATE INDEX CONCURRENTLY idx_search ON products USING GIN (search_vector);
-- GIN = inverted index ka Postgres implementation (ch 10)

-- Query + ranking
SELECT id, title, ts_rank_cd(search_vector, query) AS rank
  FROM products, websearch_to_tsquery('english', $1) query
 WHERE search_vector @@ query        -- @@ = "matches" operator
   AND status = 'active'            -- normal filters saath mein — ye ES pe mushkil hota hai
 ORDER BY rank DESC LIMIT 20;
-- websearch_to_tsquery user-friendly syntax samajhta hai: "quoted phrase" -exclude OR

-- TYPO tolerance ke liye pg_trgm (trigram similarity)
CREATE EXTENSION pg_trgm;
SELECT title FROM products
 WHERE similarity(title, 'runing shoe') > 0.3
 ORDER BY similarity(title, 'runing shoe') DESC;
-- Bonus: pg_trgm GIN index LIKE '%...%' ko bhi fast bana deta hai!

🧠 Practical rule

Postgres FTS se shuru karo. Elasticsearch tab lao jab ek concrete requirement aaye jo Postgres se nahi ho rahi — usually ye teen mein se koi ek: (1) real-time faceted navigation (har filter ke saath counts), (2) serious relevance tuning aur A/B testing, ya (3) scale jahan search load DB ko hi nuksaan pahuncha raha ho. Bahut saari teams din 1 se Elasticsearch le aati hain aur phir apni zindagi §7 wale sync problem ko debug karne mein guzaarti hain — ek aisi problem jo unke paas thi hi nahi.

Sabse Bada Operational Problem — Sync

Elasticsearch use karne ka matlab hai tumhare paas ab do source of truth hain — DB aur search index. Aur wo diverge karenge. Ye Elasticsearch ka sabse bada hidden cost hai, aur ye ch 12 ke dual-write problem ka bilkul wahi roop hai.

sync ke teen tareeke — badhte hue reliability ke saath
// ❌ 1. Dual write — DB aur ES dono ko seedha likhna
await db.products.update(id, data);
await es.index({ index: "products", id, body: data });
// Beech mein crash → permanently out of sync, aur koi error bhi nahi.
// Aur ES down hone se ab tumhara WRITE fail ho raha hai — ch 12 wali galti.

// ⚠️ 2. Outbox + worker (ch 12) — practical aur reliable
await db.transaction(async (tx) => {
  await tx.products.update(id, data);
  await tx.outbox.insert({ type: "product.updated", payload: { id } });
});
// Worker outbox se padhta hai, DB se FRESH data uthata hai, ES mein index karta hai.
// ID bhejna zaroori hai, snapshot nahi (ch 12) — warna out-of-order updates se
// purana data ES mein baith sakta hai.

// ✅ 3. CDC (Change Data Capture) — Debezium, Postgres logical replication
// WAL (ch 10) ko padh ke har change ko events mein badal deta hai.
// App code ko kuch karna hi nahi padta — koi write path miss ho hi nahi sakta.
// Sabse robust, par ek aur infra component.

// 🔁 Aur teeno ke saath: ek periodic RECONCILIATION job
// Raat ko DB aur ES ke counts/checksums compare karo, mismatch ko fix karo.
// Drift HOGA hi — sawaal sirf ye hai ki tumhe pata chalega ya nahi.
⚠️ Search index authoritative nahi hai

ES se sirf IDs aur ranking lo, aur asli data DB se fetch karo. Do wajah: (1) ES thoda stale ho sakta hai, toh usse dikhaya gaya price ya stock galat ho sakta hai; (2) permissions aur ownership checks (ch 6) DB pe hote hain — search results se seedha data serve karna ek data leak ka raasta hai. ES ka kaam "kaunse documents, kis order mein" batana hai, "unme kya likha hai" nahi.

Search Quality Ke Practical Levers

Search "kaam kar raha hai" aur search "achhi hai" mein bada farq hai. Jo cheezein sabse zyada farq lati hain, ranking ke order mein:

  • Field boosting — title > brand > description. Sabse sasta aur sabse bada improvement.
  • Business signals — popularity, rating, in-stock, recency ko score mein mix karo. Ek "perfectly relevant" out-of-stock product bekaar result hai.
  • Synonyms — "mobile" = "phone" = "smartphone", "kurta" = "kurti". Domain-specific list se bahut jaldi results better lagne lagte hain.
  • Typo tolerance — fuzzy matching, par edit distance ko chhota rakho (1–2), warna results shor ban jaate hain.
  • Autocomplete — user ko sahi query likhne mein madad karna aksar ranking theek karne se zyada effective hai.
  • Zero-result queries log karo — ye tumhara sabse valuable dataset hai. Har zero-result query ya toh missing synonym hai, ya missing product, ya typo handling ka gap.
📌 Measure karo, warna sirf andaaza hai

Search quality ka andaaza mat lagao — track karo: zero-result rate, click-through rate, average clicked position (neeche ja raha hai matlab ranking bigad rahi hai), aur search → conversion. Har relevance change ke baad ye numbers dekho. "Mujhe results behtar lag rahe hain" ek metric nahi hai — aur relevance tuning mein intuition aksar galat hoti hai.

Key Takeaways

  • LIKE '%x%' chaar tareeke se fail karta hai: slow (no index), no stemming, no ranking, no typo tolerance.
  • Search ek ranking problem hai, filtering nahi — output ek set nahi, scored sorted list hai.
  • Inverted index = word → documents ki posting list, jisme frequency (scoring ke liye) aur positions (phrase search ke liye) bhi hoti hain.
  • Multi-word query = sorted posting lists ka merge — O(n+m), bahut fast.
  • Analyzer pipeline: tokenize → lowercase → stopwords → stemming. Wahi pipeline index aur query dono pe chalti hai.
  • Analyzer mismatch = har search khali, bina error ke. Aur analyzer badalna = poora reindex.
  • TF-IDF: term jitna zyada baar aaya utna relevant, par jo term har doc mein hai wo kuch nahi batata (rare terms ka weight zyada).
  • BM25 do cheezein fix karta hai: TF saturation (keyword stuffing rokta hai) aur document length normalization.
  • Field boosting (title^3) relevance ka sabse sasta aur bada lever hai.
  • Postgres FTS real hai: tsvector generated column + GIN index + setweight se boosting + ts_rank_cd. Aur pg_trgm typo tolerance deta hai.
  • Postgres ka bada faayda: search aur normal SQL filters ek hi query mein, aur data hamesha in-sync.
  • Elasticsearch tab lao jab concrete zaroorat ho — faceting, serious relevance tuning, ya scale. Warna tum ek sync problem khareed rahe ho jo tumhare paas thi hi nahi.
  • ES ke saath do source of truth ho jaate hain — sync ke liye outbox/CDC use karo, dual write kabhi nahi. Aur reconciliation job zaroori hai; drift hoga hi.
  • ES se sirf IDs aur order lo, data DB se — staleness aur permission dono ke liye.
  • Zero-result queries log karo — wahi tumhara sabse valuable improvement dataset hai.

🎯 Interview Questions

Q1. "Search ke liye LIKE kyun kaafi nahi?"

Chaar wajah: (1) leading wildcard pe B-tree seek nahi kar sakta, toh har row scan hoti hai; (2) exact substring chahiye — "shoes for running" aur "run shoe" miss ho jaate hain; (3) koi ranking nahi — title match aur 2000-word description ka match barabar; (4) typo pe zero results. Search ko alag data structure (inverted index) aur alag concept (relevance score) chahiye.

Q2. "Inverted index kya hai aur kaam kaise karta hai?"

Normal index doc → words rakhta hai; inverted index ulta — term → posting list of documents. Posting list mein doc ID ke saath term frequency (scoring ke liye) aur positions (phrase search ke liye) bhi hoti hain. Terms sorted hote hain, toh lookup binary search/trie se hota hai, aur multi-word query sorted lists ka intersection/union hai — O(n+m). Ye ek book ke peeche wale index ki tarah hai.

Q3. "Relevance kaise calculate hoti hai?"

Base TF-IDF hai: term document mein jitna zyada aaya (TF) utna relevant, par jo term poore corpus mein har jagah hai (IDF kam) wo kuch nahi batata — rare terms ka weight zyada. Aaj ka standard BM25 hai jo do cheezein add karta hai: TF saturation (100 baar aana 10 baar se 10× behtar nahi — keyword stuffing rokta hai) aur document length normalization (chhote title mein match bade description ke match se strong hai). Uske upar practical layer: field boosting aur business signals (popularity, stock, recency).

Q4. "Postgres FTS vs Elasticsearch — kya choose karoge?"

Postgres se shuru — tsvector generated column + GIN index zyadatar apps (lakhon docs) ke liye kaafi hai, aur do bade faayde deta hai: search normal SQL filters/permissions ke saath ek hi query mein, aur data hamesha in-sync (koi sync pipeline nahi). Elasticsearch tab jab concrete requirement ho: real-time faceted navigation with counts, serious relevance tuning/A-B testing, multi-language + synonyms at scale, ya itna search load ki wo DB ko nuksaan pahunchaye. ES ka asli cost feature nahi, sync hai.

Q5. "DB aur Elasticsearch ko in-sync kaise rakhoge?"

Dual write kabhi nahi — beech mein crash pe permanent divergence, aur ES down hone se writes fail hone lagti hain. Do sahi options: outbox pattern (ch 12) — DB update aur outbox row ek transaction mein, worker outbox se ID uthake DB se fresh data laake index kare; ya CDC (Debezium / logical replication) jo WAL padh ke har change ko event banata hai — sabse robust kyunki koi write path miss ho hi nahi sakta. Dono ke saath ek periodic reconciliation job rakho — drift hoga hi, sawaal sirf detection ka hai.
