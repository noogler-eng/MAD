Serialization & Deserialization

Handler mil gaya (ch 4), par body abhi bhi ek byte buffer hai. Network sirf bytes bhej sakta hai — objects, pointers, aur classes usme exist hi nahi karte. Serialization wo translation layer hai jo memory ke structured object ko flat bytes banati hai, aur deserialization ulta karti hai. Ye chapter batata hai ki us translation mein kya kho jaata hai — kyunki asli bugs wahin paida hote hain.

Problem — Memory Object Network Pe Nahi Ja Sakta

Tumhare paas ek object hai. RAM mein wo kya hai? Ek memory address pe kuch bytes, jinme pointers hain doosre addresses ki taraf, ek type/class ka reference hai, aur layout tumhare language runtime ne decide kiya hai. Ye teeno cheezein us process ke bahar bekaar hain:

  • Pointer ek address hai is process ke memory space mein. Doosri machine pe wo address kisi aur cheez ko point karega ya crash karega.
  • Type information language-specific hai. Python ka dict Go ke map jaisa memory mein bilkul nahi dikhta.
  • Layout compiler/runtime, architecture, aur padding pe depend karta hai.

Toh network pe kuch bhejne ke liye object ko ek aisi cheez mein badalna padta hai jo self-contained, flat, aur language-neutral ho — matlab bytes ka ek aisa sequence jisme saari zaroori information andar ho, kisi external memory reference pe depend na kare. Yahi serialization hai.

📌 Ye sirf network ke liye nahi hai

Wahi problem har jagah aati hai jahan data process ki memory se bahar jaata hai — file mein likhna, Redis mein cache karna (ch 11), queue mein message daalna (ch 12), DB mein JSONB column. Sab jagah serialization hi hai. Isliye ye concept ek baar theek se samajh lo, poore stack mein kaam aata hai.

Poora Round Trip

JSON — Default Kyun Hai, Aur Isme Kya Nahi Hai

JSON aaj web APIs ka default hai. Iske jeetne ki wajah technical superiority nahi hai — simplicity hai. Insaan padh sakta hai, har language mein built-in support hai, browser mein native hai, aur debugging trivial hai (curl ka output seedha samajh aata hai).

Par iske types bahut kam hain. JSON mein sirf ye exist karte hain:

  • string, number, boolean, null
  • object (string keys), array

Bas. Koi date nahi. Koi integer/float ka farq nahi. Koi binary nahi. Koi comment nahi. Har baaki cheez ek convention hai jo tumne ya tumhari library ne upar se chipkayi hai — aur convention dono taraf match na kare toh data chupchaap galat ho jaata hai.

JSON Ke Chaar Classic Data-Loss Bugs

1. Large integers — precision chupchaap khatam

JSON ka number spec mein precision-less hai, par har JS parser use IEEE-754 double banata hai. Double sirf 2^53 - 1 tak integers exactly rakh sakta hai. Uske aage bits kho jaate hain — bina kisi error ke.

precision loss — koi exception nahi aata
// Server ne bheja: {"orderId": 9007199254740993}
JSON.parse('{"orderId": 9007199254740993}').orderId
// → 9007199254740992   ← last digit BADAL gaya. Silently.

// Ye Twitter ke saath actually hua tha — tweet IDs 2^53 cross kar gaye
// aur JS clients galat tweet fetch karne lage. Fix: id_str field add kiya.

// ✅ Rule: 64-bit IDs, paise ke amounts, aur bade counters STRING mein bhejo
{ "orderId": "9007199254740993", "amountPaise": "1999900" }
⚠️ Fintech mein ye sabse mehnga bug hai

Paisa kabhi float mein mat rakho — na JSON mein, na DB mein, na code mein. 0.1 + 0.2 binary floating point mein 0.30000000000000004 hota hai. Standard practice: smallest unit mein integer (rupaye nahi, paise) aur JSON mein string. DB mein NUMERIC/DECIMAL, kabhi FLOAT nahi (ch 10).

2. Dates — koi type hai hi nahi

date round-trip toot jaata hai
// JS: Date object → JSON
JSON.stringify({ createdAt: new Date() })
// → {"createdAt":"2026-08-17T09:14:22.000Z"}   ← ab ye ek STRING hai

// wapas parse karo:
JSON.parse(s).createdAt instanceof Date   // → false. String hi rahega.
// createdAt > someDate → string comparison chalegi, date comparison nahi

// ✅ Convention: hamesha ISO 8601 in UTC, aur receiving side pe explicitly parse karo
// ❌ Kabhi mat bhejo: "17/08/2026" (DD/MM ya MM/DD? ambiguous)
// ❌ Kabhi mat bhejo: local time bina timezone ke

3. undefined vs null vs missing — teen alag cheezein

PATCH mein ye farq critical ho jaata hai
JSON.stringify({ a: 1, b: undefined, c: null })
// → {"a":1,"c":null}     ← b poori tarah GAYAB ho gaya

// PATCH /users/42 mein teen alag intents hain:
{ "nickname": "sharad" }  // → is field ko set karo
{ "nickname": null }      // → is field ko KHAALI karo
{ }                          // → is field ko HAATH MAT LAGAO

// Agar tumhara code null aur missing ko same treat karta hai,
// toh user kabhi field clear nahi kar payega — ya galti se clear ho jayega.

4. Key order aur duplicate keys — undefined behaviour

JSON objects mein key order spec ke hisaab se meaningless hai, aur duplicate keys ka behaviour parser-specific hai (zyadatar last-wins, kuch first-wins). Isliye JSON string ka hash lekar signature verify karna ek classic bug hai — dono taraf key order alag ho sakta hai. Signing ke liye canonical JSON chahiye (keys sorted, whitespace fixed), ya better: raw bytes pe signature lo, parsed object pe nahi.

Binary Formats — Protobuf Ka Mechanism

JSON har field ka naam har message mein repeat karta hai. 10,000 records ka array bhejo, toh "createdAt" 10,000 baar wire pe jaata hai. Binary formats is redundancy ko hatate hain — schema dono taraf pehle se hai, isliye wire pe sirf values jaati hain.

user.proto — schema pehle define hota hai
syntax = "proto3";

message User {
  // har field ka ek NUMBER hai — yahi wire pe jaata hai, naam nahi
  string name  = 1;   // field tag 1
  int32  age   = 2;   // field tag 2
  string email = 3;   // field tag 3
}
// Is file se compiler har language ke liye classes generate karta hai —
// Go struct, Python class, TS interface. Ek hi source of truth.

Format Choose Kaise Karein

FormatKab use karoKab mat karo
JSON Public APIs, browser clients, webhooks, config, logs — jahan bhi human debuggability chahiye Bahut high throughput internal traffic; binary data
Protobuf / gRPC Internal service-to-service calls, high volume, strong contracts, polyglot teams Browser se seedha (proxy chahiye); public API jahan clients tumhare control mein nahi
MessagePack / CBOR JSON ka data model chahiye par chhota payload — schema ke bina Jahan human-readable hona chahiye
Avro Data pipelines, Kafka — schema registry ke saath, strong evolution rules Simple request/response APIs
multipart/form-data File uploads — binary + metadata ek saath Normal structured payloads
🧠 Practical default

JSON se shuru karo. Jab tak tum measure na kar lo ki serialization actually tumhara bottleneck hai, protobuf ka build-step, tooling, aur debugging cost faayde se zyada hai. Zyadatar apps mein latency DB queries aur network round-trips se aati hai (ch 10, 19), payload size se nahi. Premature binary format ek classic over-engineering hai.

📌 Binary data JSON mein — base64 ka cost

JSON mein raw bytes ja hi nahi sakte, toh log base64 use karte hain. Cost: ~33% size badh jaata hai plus encode/decode ka CPU. Chhoti cheezon ke liye theek hai; images/files ke liye galat design hai. Behtar: file ko object storage (S3) pe daalo aur JSON mein sirf URL bhejo — ya upload ke liye multipart/form-data use karo.

Schema Evolution — Purane Clients Ko Kaise Na Todein

Real system mein client aur server kabhi ek saath deploy nahi hote. Mobile app ka purana version mahine tak chalta rehta hai. Isliye har format change ka ek hi sawaal hai: kya purana code naya data padh sakta hai, aur naya code purana data?

ChangeSafe?Kyun
Naya optional field add karna✅Purane clients use ignore kar dete hain
Naya required field add karna❌Purane clients wo bhejte hi nahi → server reject karega
Field hatana❌Purane clients abhi bhi usko expect kar rahe hain
Field ka naam badalna❌Ye "hatao + add karo" hai — dono taraf toot-ta hai
Type badalna (int → string)❌Parse fail ya silent coercion
Enum mein nayi value add karna⚠️Tabhi safe jab clients unknown values handle karte hon
Protobuf mein field number reuse karna❌❌Purana data naye field ki tarah parse hoga — silent corruption

Isliye safe migration hamesha teen steps mein hoti hai — kabhi ek mein nahi: (1) naya field add karo, dono likhо/padho; (2) saare clients ko naye field pe shift hone do; (3) tab purana field hatao. Protobuf mein hatane par field number ko reserved mark karo taaki koi galti se reuse na kare.

Deserialization Ek Attack Surface Hai

Deserialization ka matlab hai untrusted bytes ko apne process ke andar object banana — ye definition se hi khatarnaak hai. Teen concrete risks:

  • Unbounded size — 500 MB ka JSON body memory mein parse karne ki koshish server ko OOM kar deti hai. Fix: body size limit lagao (nginx ka client_max_body_size aur app-level dono).
  • Deep nesting — 100,000 nested arrays parser ko stack overflow kar sakte hain. Fix: depth limit.
  • Unsafe deserializers — Python ka pickle, Java ki native serialization, PHP ka unserialize() deserialize karte waqt code execute kar sakte hain. Untrusted input pe inhe kabhi mat chalao. JSON is maamle mein safe hai — wo sirf data describe karta hai, behaviour nahi.
⚠️ Deserialize ≠ validate

JSON.parse() safal hone ka matlab sirf itna hai ki syntax theek tha. Uske baad bhi age -5 ho sakti hai, email mein "hello" ho sakta hai, aur ek extra isAdmin: true field aa sakta hai. Parsing aur validation do alag layers hain — aur agla chapter poora usi ke baare mein hai.

Key Takeaways

  • Memory object network pe nahi ja sakta — usme pointers, type identity, aur runtime layout hote hain jo process ke bahar meaningless hain.
  • Serialization sirf network ke liye nahi — file, cache, queue, DB column, sab jagah wahi problem hai.
  • JSON ke sirf 6 types hain. Date, integer/float ka farq, aur binary usme exist hi nahi karte — baaki sab convention hai.
  • Bade integers (IDs, paise) JSON number mein chupchaap precision kho dete hain (2^53 limit) — unhe string mein bhejo.
  • Paisa kabhi float mein nahi — smallest unit mein integer, DB mein NUMERIC.
  • undefined, null, aur missing key teen alag intents hain — PATCH semantics inhi pe khadi hai.
  • Protobuf field numbers bhejta hai, naam nahi — 50–70% chhota aur fast, par schema ke bina bytes bekaar.
  • Default JSON rakho; binary tabhi jab measure karke pata chale ki serialization hi bottleneck hai.
  • Schema evolution ka rule: add safe hai, remove aur rename nahi. Migration hamesha 3 steps mein.
  • Deserialization untrusted input ko object banata hai — size limit, depth limit, aur pickle-type deserializers se door raho.
  • Parse safal ≠ data valid. Wo agla chapter hai.

🎯 Interview Questions

Q1. "Serialization kyun chahiye? Object ko seedha kyun nahi bhej sakte?"

Kyunki memory object process-specific hai: usme pointers hain jo is address space mein valid hain, ek language-specific type identity hai, aur ek runtime-decided memory layout. Network sirf bytes bhej sakta hai. Isliye object ko flat, self-contained, language-neutral byte sequence mein badalna padta hai.

Q2. "JSON mein bada ID bhejne pe kya problem hai?"

JS parser JSON numbers ko IEEE-754 double banata hai, jo sirf 2^53-1 tak integers exactly rakhta hai. Uske aage precision bina error ke khatam ho jaati hai — ID badal jaati hai. Ye Twitter ke saath real mein hua tha (fix: id_str). Solution: 64-bit IDs aur monetary amounts string mein bhejo.

Q3. "JSON vs Protobuf — kab kya?"

JSON: public APIs, browser clients, webhooks — human-readable, schema-free, universal. Protobuf: internal service-to-service, high volume, strong typed contracts — 50–70% chhota, fast parse, generated code se compile-time safety. Trade: protobuf bytes schema ke bina bekaar hain aur curl se debug nahi hote. Default JSON, binary sirf measured need pe.

Q4. "API mein ek field ka naam badalna hai bina clients tode. Kaise?"

Ek deploy mein possible hi nahi — purane clients mahino chalte hain. Teen phase: (1) naya field add karo, server dono likhe aur dono padhe; (2) clients ko naye field pe migrate hone do, usage monitor karo; (3) usage zero hone par purana field hatao. Protobuf mein purana field number reserved karo taaki reuse pe silent corruption na ho.

Q5. "Deserialization security risk kyun hai?"

Wo untrusted bytes se tumhare process ke andar objects banata hai. Teen vectors: huge payload → OOM (body size limit chahiye), deeply nested structure → stack overflow (depth limit), aur language-native deserializers (pickle, Java serialization) jo deserialize karte waqt code execute kar sakte hain → RCE. JSON is maamle mein safe hai kyunki wo sirf data describe karta hai, behaviour nahi.
