Authentication & Authorization

Do alag sawaal, do alag layers, aur inhe mix karna sabse common security bug hai. Authentication (authN) = "tum kaun ho?" — identity prove karna. Authorization (authZ) = "tumhe iski permission hai?" — identity ke baad ka faisla. Pehla ek baar hota hai, doosra har request pe, har resource pe.

🧠 Sabse important line is chapter ki

AuthN ek jagah lag sakta hai, authZ nahi. "Kya ye user logged in hai" ek global sawaal hai — middleware mein ek baar. Par "kya ye user is order ko dekh sakta hai" ka jawab us order ke bina diya hi nahi ja sakta — matlab wo check data fetch karne ke baad hota hai, service layer mein. Jo log authZ ko sirf middleware mein daalte hain, wo IDOR (§10) wala bug likhte hain.

Problem — HTTP Stateless Hai

Ch 3 se yaad karo: HTTP stateless hai. Server ko request #2 ke waqt yaad nahi ki request #1 mein tumne login kiya tha. Toh phir har request pe username/password bhejein? Nahi — teen wajah se: password baar-baar network pe jayega, har request pe expensive hash verification hogi, aur client ko password memory mein rakhna padega.

Solution: login ek baar karo, aur badle mein ek credential ka substitute lo — ek token ya session ID. Uske baad har request wo substitute bhejti hai. Ab do design choices hain, aur poora farq ek hi sawaal pe hai: state kahan rahegi?

Session-Based Auth — Mechanism

Server ek random, unguessable session ID banata hai, asli data apne paas (shared store mein) rakhta hai, aur client ko sirf ID deta hai — cookie mein.

session flow — step by step
// ── 1. LOGIN ────────────────────────────────────────────────
POST /auth/login  { email, password }

user = db.users.findByEmail(email);              // user nikalo
ok   = await bcrypt.compare(password, user.passwordHash);
if (!ok) return res.status(401).json({ error: "invalid credentials" });
// ↑ email galat ho ya password — MESSAGE SAME rakho (user enumeration rokne ke liye)

sid = crypto.randomBytes(32).toString("hex");   // 256 bits — guess karna namumkin
await redis.setex(`sess:${sid}`, 86400,               // 24h TTL — expiry free mein
  JSON.stringify({ userId: user.id, role: user.role }));  // ASLI data server pe

res.cookie("sid", sid, {
  httpOnly: true,    // JS is cookie ko padh hi nahi sakta → XSS se churaya nahi ja sakta
  secure:   true,    // sirf HTTPS pe bheji jayegi
  sameSite: "lax",   // cross-site request pe apne aap nahi jayegi → CSRF defense
  maxAge:   86400000,
});

// ── 2. HAR AGLI REQUEST ─────────────────────────────────────
// browser cookie APNE AAP bhejta hai — client code ko kuch karna hi nahi
sess = await redis.get(`sess:${req.cookies.sid}`);   // ← LOOKUP (network hop)
if (!sess) return res.status(401).json({ error: "session expired" });
req.user = JSON.parse(sess);                        // context mein daalo (ch 8)

// ── 3. LOGOUT ───────────────────────────────────────────────
await redis.del(`sess:${sid}`);   // TURANT invalid. Ye JWT mein trivial nahi hai.

Ch 3 ki statelessness yaad hai? Session store Redis mein hona zaroori hai, process ki memory mein nahi — warna doosra instance add karte hi users random logout hone lagenge. Server abhi bhi stateless hai; state ek shared jagah pe hai.

JWT — Mechanism Aur Uska Asli Trade-off

JWT (JSON Web Token) ulta approach hai: state client ke paas hi rakh do, par usse cryptographically sign kar do taaki client usse chhed na sake. Server ko kuch store hi nahi karna padta.

JWT ka structure — teen base64 hisse, dot se jude
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiI0MiIsInJvbGUiOiJhZG1pbiJ9 . 4f9a2b…
└──── HEADER ────┘   └────────── PAYLOAD ──────────┘   └ SIGNATURE ┘

// HEADER — kaunsa algorithm
{ "alg": "HS256", "typ": "JWT" }

// PAYLOAD — "claims". Ye sirf BASE64 hai, ENCRYPTED NAHI.
// Koi bhi jwt.io pe paste karke padh sakta hai. Secret kabhi mat daalo.
{
  "sub":  "42",          // subject — kis user ka token
  "role": "admin",       // custom claim
  "iat":  1755421200,    // issued at
  "exp":  1755424800     // expiry — SIRF yahi cheez token ko marti hai
}

// SIGNATURE — yahi asli security hai
HMACSHA256(base64(header) + "." + base64(payload), SERVER_SECRET)
// payload badla → signature match nahi karega → token reject
// attacker signature bana hi nahi sakta kyunki SECRET uske paas nahi hai

Verification mein koi database lookup nahi — server sirf signature recompute karta hai aur exp check karta hai. Microseconds. Yahi JWT ka asli faayda hai: verification stateless aur fast hai, isliye har service independently verify kar sakti hai bina ek central session store pe depend kiye.

⚠️ JWT ka fundamental trade-off — revocation

Session delete karo → agli request pe user out. JWT ke saath aisa kuch nahi hai. Token self-contained hai; server ke paas usko "mitane" ka koi tareeka nahi. User ka role admin se hata do — uska purana token exp tak admin bana rehta hai. Isliye practical answer ye hai: access token bahut short-lived rakho (5–15 min) aur uske saath ek refresh token do jo lamba chalta hai aur DB mein store hota hai — matlab revocable hota hai. Dhyan do: iska matlab hai ki tum stateless-ness wapas chhod rahe ho, bas kam frequency pe.

Session vs JWT — Diagram Aur Decision

🧠 Practical default — JWT hype se bacho

Ek normal web app (ek backend, ek frontend) ke liye session + Redis simpler aur safer hai. Redis lookup ~1ms hai, aur uske badle tumhe instant logout, instant role change, aur "meri saari devices se logout karo" free mein milta hai. JWT tab जीतta hai jab tumhe stateless verification across many services chahiye — microservices, third-party API access, ya service-to-service auth. Bahut saari teams JWT isliye use karti hain kyunki wo "modern" lagta hai, aur phir ek Redis blocklist bana leti hain — jisse JWT ka poora faayda khatam ho jaata hai.

⚠️ Default: httpOnly cookie

Log kehte hain "cookie mein CSRF risk hai" — sahi hai, par CSRF ka ek solid, standard fix hai (SameSite + CSRF token); XSS-se-token-chori ka koi fix nahi hai. Agar attacker tumhare page pe JS chala paya, toh localStorage ka token gaya. Isliye web ke liye httpOnly; Secure; SameSite=Lax cookie default hona chahiye. localStorage sirf tab jab tum sach mein cross-domain ya mobile scenario mein ho.

Passwords — Hashing Ka Sahi Tareeka

password storage — kya karna hai aur kya nahi
// ❌ plain text — kabhi nahi (leak = sab kuch gaya, aur users doosri sites pe bhi)
// ❌ MD5 / SHA-1 / SHA-256 — ye FAST hash hain
//    GPU pe billions/sec try ho sakte hain → brute force trivial
// ❌ apna khud ka "clever" scheme

// ✅ SLOW, salted, memory-hard hash: bcrypt / scrypt / Argon2id
hash = await bcrypt.hash(password, 12);
// 12 = "cost factor" — 2^12 iterations. Har +1 se time DOUBLE.
// Target: ~200-300ms per hash. Users ko farq nahi padta,
// attacker ke liye brute force practically impossible ho jaata hai.

// salt bcrypt khud generate karke hash ke ANDAR store karta hai:
// $2b$12$N9qo8uLOickgx2ZMRZoMye....
//  │   │  └ salt (22 ch)   └ hash
//  │   └ cost                    ← isliye alag salt column ki zaroorat nahi
//  └ algorithm
// Salt ka kaam: do users ka same password → alag hash → rainbow table bekaar

// verify — hamesha library ka compare use karo
ok = await bcrypt.compare(input, hash);
// ye CONSTANT-TIME comparison karta hai — timing attack se bachne ke liye
// (naive === pehle mismatch pe return karta hai, jisse time se info leak hoti hai)
📌 Aur teen cheezein jo production mein zaroori hain

Rate limiting login endpoint pe (ch 18) — warna slow hash bhi credential stuffing nahi rokta. Same error message galat email aur galat password dono pe — warna attacker pata kar leta hai ki kaunse emails registered hain. Aur login timing dono cases mein similar rakho (user na mile tab bhi ek dummy hash chalao), warna response time hi bata deta hai.

OAuth 2.0 — "Google Se Login" Andar Se

OAuth ka asli maksad login nahi hai — wo delegated authorization hai: user apna password diye bina, ek app ko doosri service pe limited access deta hai. "Google se login" actually OIDC hai, jo OAuth ke upar ek identity layer hai.

⚠️ state parameter optional nahi hai

state ek random value hai jo tum step 2 mein bhejte ho aur step 4 mein wapas milti hai — match karna zaroori hai. Iske bina attacker apna authorization code victim ke browser mein inject kar sakta hai, jisse victim ka account attacker ke Google account se link ho jaata hai (login CSRF). Aur redirect_uri ko provider ke paas exact whitelist karo — wildcard ya open redirect se code churaya ja sakta hai.

AuthZ Models — RBAC, ABAC, Ownership

Identity confirm ho gayi. Ab actual faisla — teen models, badhte hue complexity ke saath:

teen authZ models
// ── 1. RBAC — Role Based. Sabse common, sabse simple. ───────
// user ka ek role hai, role ke paas permissions hain
roles = {
  admin:  ["user:read", "user:write", "user:delete"],
  editor: ["user:read", "user:write"],
  viewer: ["user:read"],
};
can(user, "user:delete")  // → roles[user.role].includes(perm)
// ✅ samajhna aasaan, audit karna aasaan
// ❌ "sirf apni team ke users" jaisa rule express nahi kar sakta

// ── 2. Ownership — sabse zyada zaroori, sabse zyada bhoola jaata hai ──
order = await db.orders.findById(id);
if (order.userId !== req.user.id) return res.status(403).end();
// ↑ Ye check middleware mein ho hi NAHI sakta —
//   order fetch kiye bina pata hi nahi chalega ki owner kaun hai.

// Behtar: query mein hi ownership daal do — bhoolna structurally impossible
order = await db.orders.findOne({ id, userId: req.user.id });
if (!order) return res.status(404).end();   // 404 — 403 se existence leak hoti hai

// ── 3. ABAC — Attribute Based. Flexible par heavy. ──────────
can(user, action, resource, context)
// "manager apni department ke expenses approve kar sakta hai,
//  ₹50,000 tak, sirf working hours mein"
// → policy engine (OPA/Cedar) jab rules sach mein complex hon

Key Takeaways

  • AuthN = tum kaun ho (401), authZ = tum ye kar sakte ho (403). Alag layers, alag codes.
  • AuthN middleware mein ek jagah lag sakta hai; authZ nahi — resource-level check data fetch ke baad hi possible hai.
  • Session: state shared store mein, har request pe ~1ms lookup, par instant revoke.
  • JWT: state token ke andar, zero lookup, par exp tak revoke nahi hota.
  • JWT payload sirf base64 hai, encrypted nahi — koi bhi padh sakta hai.
  • Practical: short access token (5–15 min) + DB-backed refresh token; ye stateless-ness ko kam frequency pe chhodta hai.
  • Web ke liye default: httpOnly; Secure; SameSite=Lax cookie. CSRF ka fix hai, XSS-se-chori ka nahi.
  • Passwords: bcrypt/scrypt/Argon2id, cost ~200–300ms. SHA-256 fast hai — isliye galat hai.
  • OAuth ka poora design ek cheez ke liye: token browser URL se na guzre. state aur exact redirect_uri mandatory hain.
  • Ownership check ko query ke andar daalo — tab bhoolna structurally impossible ho jaata hai. Not-found pe 404 do, 403 nahi.
  • Client se aaya role kabhi bharosa nahi; UI mein button chhupana security nahi hai.

🎯 Interview Questions

Q1. "Authentication aur authorization mein farq?"

AuthN identity establish karta hai ("tum kaun ho") — fail pe 401, client ko login/refresh karna chahiye. AuthZ us identity ke saath permission decide karta hai ("tum ye kar sakte ho") — fail pe 403, dobara try karna bekaar. Strong answer mein ye line add karo: authN ek baar aur ek jagah ho sakta hai, authZ har request pe aur har resource pe alag hota hai.

Q2. "JWT vs session — kya choose karoge aur kyun?"

Ye ek trade-off hai, "better" wala sawaal nahi. Session: har request pe store lookup (~1ms), badle mein instant revocation, instant role change, "sab devices se logout". JWT: zero lookup, services independently verify karti hain, par revocation nahi — role change exp tak effective nahi hota. Ek monolith ke liye main session chunoonga; multi-service ya third-party API access ke liye JWT with short expiry + DB-backed refresh token.

Q3. "JWT ko turant revoke kaise karoge?"

Poori tarah stateless rehte hue nahi kar sakte — yahi uska design trade-off hai. Practical options: (a) access token bahut short rakho aur revocation ko refresh time pe enforce karo; (b) revoked token IDs (jti) ki blocklist Redis mein rakho — par tab har request pe lookup wapas aa gaya, matlab JWT ka faayda khatam; (c) user record mein ek tokenVersion rakho aur usse claim se match karo — ye bhi ek lookup hai. Sahi answer trade-off naam se pehchanna hai.

Q4. "Password DB mein kaise store karoge?"

Slow, salted, memory-hard hash — bcrypt/scrypt/Argon2id, cost tuned to ~200–300ms. Salt per-user hota hai (bcrypt use hash ke andar hi rakhta hai) taaki same password ka hash alag ho aur rainbow tables bekaar ho jaayein. SHA-256 galat hai kyunki wo fast hai — GPU pe billions/sec. Verify ke liye constant-time compare. Plus: login pe rate limit, aur galat-email/galat-password pe identical response.

Q5. "OAuth mein authorization code alag step kyun hai? Token seedha kyun nahi?"

Kyunki redirect browser ke through hota hai — URL browser history, server logs, aur referrer headers mein leak ho sakta hai. Code akela bekaar hai; usse token banane ke liye client_secret chahiye jo sirf backend ke paas hai, aur wo exchange back-channel (server-to-server) pe hota hai. Public clients ke paas secret nahi ho sakta, isliye unke liye PKCE — ek per-request challenge/verifier pair. Aur state parameter login-CSRF rokta hai.

Q6. "User A, user B ka order dekh pa raha hai. Kya galat hai?"

Classic IDOR — authN check hua (logged in hai) par ownership check nahi hua. Fix ownership ko query mein daalna: findOne({ id, userId: req.user.id }), taaki koi handler usse bhool hi na sake. Aur not-found pe 404 do, 403 nahi — warna response se hi confirm ho jaata hai ki wo order exist karta hai.
