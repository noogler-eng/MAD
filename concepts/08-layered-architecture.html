Problem — "Fat Controller"

Shuru mein sab kuch ek handler mein likhna sabse fast hota hai. Ye rahi wo shakal jo har codebase mein 6 mahine baad milti hai:

❌ sab kuch ek jagah — kaam karta hai, par…
app.post("/orders", async (req, res) => {
  // auth
  const token = req.headers.authorization?.split(" ")[1];
  const user  = jwt.verify(token, SECRET);

  // validation
  if (!req.body.items?.length) return res.status(400).json({ e: "no items" });

  // SQL seedha handler mein
  const { rows } = await pool.query("SELECT * FROM products WHERE id = ANY($1)", [ids]);

  // business logic
  let total = 0;
  for (const item of req.body.items) {
    const p = rows.find(r => r.id === item.productId);
    if (p.stock < item.qty) return res.status(409).json({ e: "out of stock" });
    total += p.price * item.qty;
  }
  if (user.isPremium) total *= 0.9;

  // aur SQL
  await pool.query("INSERT INTO orders …");
  await stripe.charges.create({ amount: total });   // external call
  await sendgrid.send({ to: user.email });          // aur ek

  res.json({ ok: true });
});

Ye chalta hai. Problem tab shuru hoti hai jab:

  • Test karna namumkin hai — "premium user ko 10% discount milta hai" test karne ke liye ek HTTP server, ek database, aur Stripe/SendGrid ke mocks chahiye. Ek pure calculation ke liye poori duniya khadi karni padti hai.
  • Reuse namumkin hai — ab admin panel se bhi order banana hai, ya ek CLI script se, ya ek queue worker se (ch 12). Logic req/res ke saath chipki hui hai, toh copy-paste hoti hai — aur ek jagah bug fix hota hai, doosri mein reh jaata hai.
  • Transaction lagana mushkil hai — do INSERTs ke beech process crash ho gaya toh aadha order ban gaya. Handler ke andar transaction boundary khींchna gandha ho jaata hai.
  • Kuch bhi badalna dara deta hai — DB library badalni ho? Har handler chhoona padega.

Teen Layers Aur Unki Exact Zimmedari

Solution ek hi principle hai — har layer sirf ek kism ka kaam kare. Rule yaad rakhne ka sabse aasaan tareeka:

LayerKya jaanti haiKya nahi jaantiTest kaise
Controller
(handler)		 HTTP — request parse, status codes, headers, response shape Business rules, SQL Integration test (HTTP level)
Service
(use case)		 Business rules — discount, stock, workflow, orchestration HTTP aur SQL dono nahi Unit test — sirf function call, koi server nahi
Repository
(data access)		 Data store — SQL, queries, mapping Business rules, HTTP Integration test (real DB pe)
🧠 Ek line ka test — sabse useful heuristic

Service layer mein req, res, ya SQL string dikhe — toh galat hai. Service ko pata bhi nahi hona chahiye ki wo HTTP se bulaayi gayi hai ya ek cron job se. Yahi ek check 90% layering mistakes pakad leta hai. Aur iska direct faayda ye hai: wahi service ko ch 12 ka queue worker bina kisi badlaav ke call kar sakta hai.

Poora Flow

Ek Request, Teeno Layers Mein

controller — patla, sirf translation
// Controller ka poora kaam: HTTP ↔ domain ki translation. Bas.
app.post("/orders", requireAuth, validate(CreateOrderSchema), async (req, res, next) => {
  try {
    // 1. HTTP se input nikalo (auth aur validation middleware pehle ho chuke hain)
    const order = await orderService.createOrder({
      userId: req.ctx.user.id,     // context se — body se KABHI nahi (ch 6)
      items:  req.validated.items, // ch 7 se validated data
    });

    // 2. domain result ko HTTP mein badlo
    res.status(201)                       // 201 kyunki naya resource bana (ch 3)
       .location(`/orders/${order.id}`)  // 201 ke saath Location header
       .json(toOrderResponse(order));    // output mapping (ch 7) — allowlist
  } catch (err) {
    next(err);   // central error handler decide karega status (ch 14)
  }
});
service — business rules, HTTP se bilkul azaad
// Dependencies constructor se aati hain — hardcoded import nahi.
// Isse test mein fake repo/gateway pass karna trivial ho jaata hai.
class OrderService {
  constructor(orderRepo, productRepo, paymentGateway, eventBus) { … }

  async createOrder({ userId, items }) {
    // ── business rule 1: products exist karte hain? (ch 7 ka "level 3") ──
    const products = await this.productRepo.findByIds(items.map(i => i.productId));
    if (products.length !== items.length)
      throw new NotFoundError("product");   // DOMAIN error — 404 nahi

    // ── business rule 2: stock ──────────────────────────────
    for (const item of items) {
      const p = products.find(p => p.id === item.productId);
      if (p.stock < item.qty)
        throw new ConflictError(`insufficient stock: ${p.name}`);
    }

    // ── business rule 3: pricing — PURE function, alag se test ho sakta hai ──
    const total = calculateTotal(items, products, await this.userRepo.find(userId));

    // ── TRANSACTION BOUNDARY yahan hai — service pe, repo pe nahi ──
    // Kyunki "kaunse operations ek saath atomic hone chahiye" ek BUSINESS
    // decision hai, data-access detail nahi.
    const order = await this.db.transaction(async (tx) => {
      await this.productRepo.decrementStock(items, tx);
      return this.orderRepo.create({ userId, items, total }, tx);
    });

    // ── slow/external kaam SYNC path se BAHAR (ch 12) ───────
    await this.eventBus.publish("order.created", { orderId: order.id });
    // email/invoice worker sunega — user ko SendGrid ka wait nahi karna padega

    return order;
  }
}
repository — sirf data access
class OrderRepository {
  async create({ userId, items, total }, tx = this.pool) {
    // tx pass hua toh transaction ke andar, warna normal pool connection
    const { rows } = await tx.query(
      `INSERT INTO orders (user_id, total_paise, status)
       VALUES ($1, $2, 'pending') RETURNING *`,
      [userId, total]                // ← parameterized — SQL injection safe (ch 18)
    );
    return toDomain(rows[0]);   // snake_case row → camelCase domain object
  }
}
// Repository DB ke "vocabulary" ko domain ke vocabulary mein translate karta hai.
// Isi wajah se DB badalna (Postgres → doosra store) sirf is layer ko chhoota hai.
⚠️ Service se HTTP status codes throw mat karo

throw new ConflictError() likho, res.status(409) nahi. Service ko HTTP ka pata hi nahi hona chahiye — warna wahi service ek queue worker ya CLI se call karne pe bekaar ho jaati hai (wahan "409" ka koi matlab hi nahi). Domain errors ko HTTP status mein badalna ek central error handler ka kaam hai: NotFoundError → 404, ConflictError → 409, ValidationError → 422. Ye ch 14 ka core pattern hai.

Dependency Direction — Asli Rule

Layers ka asli faayda "3 folders" nahi hai — wo dependency ki direction hai. Arrows hamesha ek taraf jaate hain, aur wo rule tod dena poore pattern ko bekaar kar deta hai:

allowed vs forbidden
controller  ──→  service  ──→  repository  ──→  DB      // ✅ ek hi direction

// ❌ FORBIDDEN — ye teeno pattern ko tod dete hain:
repository  ──→  service      // circular; repo ko business ka pata nahi hona chahiye
service     ──→  controller   // service ab HTTP se bandh gayi
controller  ──→  repository   // service bypass — business rule chhoot jaayega

Wo aakhri wala sabse dhoke wala hai. "Ye toh simple GET hai, service kyun banayein" bolke controller seedha repo call karta hai. Chhe mahine baad us GET pe ek permission rule add hota hai — aur wo rule service mein likha jaata hai, jise ye endpoint call hi nahi karta. Bypass aaj shortcut hai, kal security bug.

Middleware — Onion Model

Middleware wo functions hain jo handler se pehle (aur baad mein) chalte hain — cross-cutting kaam ke liye jo har route pe chahiye: logging, auth, CORS, body parsing, rate limiting, error handling.

Mental model "list" nahi, onion hai: request bahar se andar jaati hai har layer ke through, aur response ulti direction mein wapas guzarti hai. Isliye ek hi middleware request se pehle aur response ke baad — dono jagah kaam kar sakta hai.

middleware ka mechanism — next hi poora raaz hai
// har middleware ka signature: (req, res, next)
function requestLogger(req, res, next) {
  const start = process.hrtime.bigint();

  res.on("finish", () => {                // ← response ke BAAD chalega
    const ms = Number(process.hrtime.bigint() - start) / 1e6;
    logger.info({ method: req.method, path: req.path, status: res.statusCode, ms });
  });

  next();   // ← agli layer ko control do (onion mein andar jao)
  // next() na bulao → request HANG ho jayegi, koi error nahi aayega.
  // Ye sabse common middleware bug hai: ek branch mein next() bhool jaana.
}

// error middleware ka signature 4 arguments ka hota hai — Express isi se pehchanta hai
function errorHandler(err, req, res, next) {
  const status = err.status ?? 500;
  if (status >= 500) logger.error({ err, requestId: req.ctx.requestId });
  res.status(status).json({
    error: err.code ?? "internal_error",
    // 5xx pe asli message KABHI mat bhejo — internals leak hote hain (ch 18)
    message: status >= 500 ? "Something went wrong" : err.message,
    requestId: req.ctx.requestId,   // user support ko yahi ID batayega
  });
}

// ORDER = onion ki layers. Ye sequence deliberate hai:
app.use(requestId);      // sabse bahar — har log line mein chahiye
app.use(requestLogger);
app.use(cors);
app.use(express.json({ limit: "100kb" }));   // body size cap (ch 5)
app.use(rateLimiter);
app.use("/api", apiRoutes);
app.use(errorHandler);    // SABSE AAKHIR mein register, par onion mein bahar

Request Context — Data Jo Saath Chalta Hai

Kuch data poori request ke saath chalna chahiye: kaun user hai, request ID kya hai, tenant kaunsa hai, locale kya hai. Isko har function mein argument banake pass karna 8 layers deep jaake bekaar ho jaata hai — isliye ek request context hota hai.

context banana aur use karna
// sabse bahar wali middleware context banati hai
app.use((req, res, next) => {
  req.ctx = {
    requestId: req.headers["x-request-id"] ?? crypto.randomUUID(),
    // ↑ upstream se aaya ID reuse karo — tabhi trace poore system mein judta hai (ch 16)
    startedAt: Date.now(),
  };
  res.setHeader("x-request-id", req.ctx.requestId);  // client ko wapas do
  next();
});

// auth middleware usko ENRICH karti hai
app.use(async (req, res, next) => {
  req.ctx.user = await verifyToken(req.headers.authorization);
  next();
});
⚠️ Context ko service tak explicitly pass karo

Ek tempting shortcut hai: context ko ek global/AsyncLocalStorage mein daal do taaki koi bhi function usse padh sake. Wo kaam karta hai, par service layer ab ek chhupi hui dependency pe khadi ho jaati hai — test karte waqt wo global set karna padta hai, aur queue worker se call karne pe wo hai hi nahi. Behtar: service ko wo cheezein arguments mein do jo usse chahiye (userId, requestId). Global context sirf observability (logging, tracing) ke liye theek hai, business logic ke liye nahi.

Kab Ye Overkill Hai

Har CRUD endpoint pe teen files banana bhi ek anti-pattern hai. Agar service sirf itna karta hai —

anemic service — koi value nahi jod raha
class TagService {
  list() { return this.tagRepo.findAll(); }   // bas pass-through
}
// Ye layer sirf indirection hai — koi business rule nahi.

— toh wo layer sirf ceremony hai. Practical rule: layer tab banao jab usme kuch rakhne ko ho. Ek simple lookup endpoint controller se seedha repo call kar sakta hai, jab tak koi business rule na ho. Par jaise hi pehla rule aaye (permission, calculation, multi-step workflow), turant service extract karo — usse baad mein karna hamesha mehnga padta hai.

🧠 Naam ke chakkar mein mat pado

Controller/service/repository sirf ek vocabulary hai. Dusri jagah inhe handler/use-case/gateway, ya route/domain/data-access kehte hain; hexagonal architecture, clean architecture, aur DDD sab isi idea ke variants hain. Asli invariant sirf do hain: (1) business logic HTTP aur SQL dono se azaad ho, aur (2) dependencies ek hi direction mein jaayein. Ye do cheezein hain toh folder ka naam kuch bhi rakh lo.

Key Takeaways

  • "Fat controller" ka asli nuksaan test aur reuse hai — pure calculation test karne ke liye HTTP server + DB + mocks chahiye ho jaate hain.
  • Controller = HTTP translation, service = business rules, repository = data access.
  • Ek line ka test: service mein req, res, ya SQL dikhe toh galat hai.
  • Service HTTP-agnostic hone ki wajah se hi queue worker (ch 12) aur CLI usko bina badle call kar sakte hain.
  • Service domain errors throw kare (ConflictError), HTTP status nahi — mapping central error handler ka kaam hai (ch 14).
  • Transaction boundary service pe hoti hai, repository pe nahi — kya atomic hona chahiye ye business decision hai.
  • Dependency direction ek-tarfa: controller → service → repository. Controller ka repo ko seedha call karna aaj shortcut, kal security bug.
  • Middleware ek onion hai — request andar, response bahar. Isliye order matter karta hai: errorHandler auth se bahar, requestId sabse bahar.
  • next() bhoolna = request silently hang. Sabse common middleware bug.
  • Request context upstream ka x-request-id reuse kare, aur response mein wapas bheje.
  • Global/ALS context sirf observability ke liye; business logic ko values explicitly pass karo.
  • Layer tab banao jab usme rakhne ko kuch ho — pass-through service sirf ceremony hai.

🎯 Interview Questions

Q1. "Controller, service, repository — kaunsi layer kya karti hai?"

Controller HTTP jaanta hai: request se input nikalna, service bulana, result ko status code + JSON banana. Service business rules jaanti hai aur HTTP/SQL dono se azaad hoti hai — isliye usse ek worker ya CLI bhi call kar sakta hai. Repository data access jaanti hai: queries aur row→domain mapping. Sabse crisp test: service mein req/res/SQL nahi dikhna chahiye.

Q2. "Transaction boundary kahan honi chahiye?"

Service layer pe. "Kaunse operations ek saath atomic hone chahiye" ek business decision hai — stock decrement aur order insert dono saath, ya dono nahi. Repository ko sirf ek optional transaction handle accept karna chahiye. Agar transaction repository ke andar hua, toh multi-repo atomicity possible hi nahi rahegi.

Q3. "Middleware kaise kaam karti hai? Order kyun matter karta hai?"

Har middleware (req, res, next) leti hai aur next() se control agli ko deti hai — ek onion, jisme request andar jaati hai aur response ulte order mein bahar. Order isliye matter karta hai: error handler ko auth se bahar hona chahiye taaki auth ke errors bhi pakde jaayein, body parser ko validation se pehle, aur requestId sabse bahar taaki har log line mein wo ho. Ek branch mein next() bhool jaana request ko silently hang kar deta hai.

Q4. "Request context kya hai aur usme kya rakhoge?"

Per-request data jo poore call stack ko chahiye: requestId, authenticated user, tenant, locale. Sabse bahar wali middleware banati hai (upstream ka x-request-id reuse karke, taaki distributed trace juda rahe — ch 16), aur aage wali middleware use enrich karti hain. Business logic ko values explicitly pass karo; global/AsyncLocalStorage sirf logging/tracing ke liye rakho, warna service ki dependency chhup jaati hai aur test/worker mein toot-ti hai.

Q5. "Kya har endpoint ke liye service layer chahiye?"

Nahi. Agar service sirf repo ko pass-through kar rahi hai toh wo indirection hai, abstraction nahi. Simple lookup endpoints controller se seedha repo call kar sakte hain. Par jaise hi pehla business rule aaye — permission check, calculation, multi-step workflow, transaction — service extract kar do. Baad mein extract karna hamesha mehnga hota hai kyunki tab tak logic 4 jagah copy ho chuki hoti hai.
