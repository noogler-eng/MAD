Disk Pe Data Kaise Pada Hai — Pages Aur Rows

Sabse pehla mental model: database rows ko ek-ek karke nahi padhta. Disk (aur OS) blocks mein kaam karte hain, isliye Postgres bhi pages mein kaam karta hai — default 8 KB ka ek page. Ek table disk pe pages ka ek sequence hai, aur har page mein kai rows ("tuples") hoti hain.

🧠 Poore chapter ka base — I/O ki ginti

Database performance ka 90% ek hi cheez hai: kitne pages disk se padhne padte hain. Ek page read ki cost (SSD pe ~100µs, HDD pe ~10ms) CPU ke kaam se hazaaron guna zyada hai. Isliye indexes, query plans, caching — sab ek hi goal ke liye hain: kam pages chhuo. Jab bhi koi optimization samajh na aaye, ye poocho: "isse kitne pages kam padhne padenge?"

Postgres ke paas ek shared buffer pool hota hai — RAM ka ek hissa jahan haal ke pages cache rehte hain. Ek query pehle wahan dekhti hai (cache hit, microseconds), na mile toh disk se laati hai. Isliye ek hi query pehli baar 200ms aur doosri baar 2ms le sakti hai — data ab RAM mein hai. Benchmark karte waqt ye sabse common galti hai.

Index — B-tree Andar Se

Bina index ke WHERE email = 'x@y.com' ka matlab hai sequential scan — har page padho, har row check karo. 10 lakh rows = poori table disk se. Index isko badal deta hai.

Postgres ka default index B-tree hai (actually B+tree) — ek balanced tree jisme saari actual keys leaf level pe hoti hain, aur leaves aapas mein linked hoti hain.

Index Ke Wo Rules Jo Sach Mein Kaam Aate Hain

1. Composite index mein column ka order sab kuch hai

leftmost prefix rule
CREATE INDEX idx ON orders (user_id, status, created_at);

-- Sochne ka tareeka: ye ek phone directory hai jo (sheher, mohalla, naam) se sorted hai.

-- ✅ USE hoga (leftmost prefix match karta hai):
WHERE user_id = 1
WHERE user_id = 1 AND status = 'paid'
WHERE user_id = 1 AND status = 'paid' AND created_at > '2026-01-01'
WHERE user_id = 1 ORDER BY status, created_at   -- sort bhi free

-- ❌ USE NAHI hoga (pehla column hi nahi hai):
WHERE status = 'paid'                -- sheher jaane bina mohalla dhoondhna
WHERE created_at > '2026-01-01'

-- ⚠️ AADHA use hoga — index sirf user_id tak seek karega,
--    phir baaki rows ko filter karega (status skip ho gaya)
WHERE user_id = 1 AND created_at > '2026-01-01'

-- Rule of thumb column order ke liye:
-- 1. Equality wale columns pehle (=)
-- 2. Range wale baad mein (>, <, BETWEEN)
-- 3. Sirf ORDER BY wale sabse aakhir

2. Column pe function lagate hi index mar jaata hai

sabse common index-killer
-- ❌ index bekaar — Postgres ke paas LOWER(email) ka index nahi hai
WHERE LOWER(email) = 'a@b.com'
WHERE DATE(created_at) = '2026-08-17'
WHERE user_id::text = '42'            -- implicit cast bhi wahi karta hai

-- ✅ Fix A: query ko re-write karo taaki column "naked" rahe
WHERE created_at >= '2026-08-17' AND created_at < '2026-08-18'

-- ✅ Fix B: expression index banao (jab function zaroori ho)
CREATE INDEX idx_email_lower ON users (LOWER(email));

-- LIKE ka bhi wahi rule:
WHERE name LIKE 'shar%'    -- ✅ prefix — B-tree seek kar sakta hai
WHERE name LIKE '%rad%'    -- ❌ leading wildcard — full scan
--    ↑ yahi wo problem hai jiske liye full-text search chahiye (ch 13)

3. Index muft nahi hain

Har index writes ko slow karta hai (INSERT/UPDATE/DELETE pe har index update hota hai), disk leta hai, aur planner ke liye options badhata hai. Ek table pe 15 indexes ek anti-pattern hai. Postgres mein pg_stat_user_indexes se dekho ki kaunse indexes kabhi use hi nahi hue (idx_scan = 0) — unhein hata do.

aur bhi index types — sirf jab zaroorat ho
-- PARTIAL index — sirf useful rows pe. Chhota = fast + kam write overhead.
CREATE INDEX idx_active ON orders (created_at) WHERE status = 'pending';
-- 1 crore orders mein sirf 5000 pending hain? Index 5000 rows ka banega.

-- COVERING index — INCLUDE se extra columns index mein hi rakho
CREATE INDEX idx_cov ON orders (user_id) INCLUDE (total, status);
-- Ab query heap ko chhue bina jawab de sakti hai → "index-only scan"

-- GIN — JSONB, arrays, full-text (ch 13)
CREATE INDEX idx_meta ON events USING GIN (metadata);

-- Production mein index banate waqt HAMESHA:
CREATE INDEX CONCURRENTLY idx_x ON big_table (col);
-- ↑ CONCURRENTLY ke bina table pe WRITE LOCK lag jaata hai —
--   bade table pe iska matlab hai minutes ka outage.

Query Planner Aur EXPLAIN Padhna

Postgres ka planner cost-based hai: wo statistics (ANALYZE se collected) dekh ke andaaza lagata hai ki kitni rows aayengi, aur phir sabse sasta plan chunta hai. Isliye index hone ka matlab index use hona nahi hai — agar planner ko lagta hai ki query aadhi table return karegi, toh sequential scan actually tez hai (random I/O se sequential I/O sasta hota hai).

EXPLAIN ANALYZE — ye exact form use karo
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;
-- ANALYZE = query sach mein chalao (asli timings)  ⚠️ writes pe transaction mein karo
-- BUFFERS = kitne pages padhe — YAHI asli metric hai

Limit  (cost=0.43..8.45 rows=20) (actual time=0.031..0.058 rows=20 loops=1)
  Buffers: shared hit=5                      -- 5 pages, sab cache se. Bahut accha.
  ->  Index Scan using idx_orders_user_created on orders
        Index Cond: (user_id = 42)

-- ── Padhne ka tareeka ──────────────────────────────────────
-- 1. ANDAR se BAHAR padho (sabse deep node pehle chalta hai)
-- 2. estimated `rows=` vs `actual rows=` compare karo
--    10x se zyada farq → statistics stale hain → ANALYZE chalao
-- 3. `loops=` dekho — loops=500 matlab wo node 500 baar chala (N+1 ka signature!)
-- 4. Buffers dekho: `read` = disk se, `hit` = cache se

Transactions Aur ACID

Transaction ka core idea: kai operations, ek atomic unit. Ya sab honge, ya kuch nahi.

  • A — Atomicity: beech mein crash hua toh sab rollback. Aadha kaam nahi bachta.
  • C — Consistency: constraints (FK, UNIQUE, CHECK) transaction ke end pe satisfy hone chahiye.
  • I — Isolation: concurrent transactions ek doosre ko kitna dikhte hain — ye sabse subtle hai (§7).
  • D — Durability: COMMIT return hua matlab data disk pe hai, power cut pe bhi bacha rahega. Ye WAL (write-ahead log) se aata hai — Postgres pehle change ko log mein likhta hai (sequential, fast), phir aaram se data pages update karta hai.
⚠️ Transaction ke andar external call kabhi mat karo

BEGIN → INSERT → await stripe.charge() → COMMIT — ye ek classic outage generator hai. Stripe 5 second le raha hai, matlab tumhara transaction 5 second tak locks pakde baitha hai aur ek connection pool se block kiye hue hai. 100 concurrent orders = pool khatam = poora app down. Rule: transactions chhote rakho, aur unme sirf DB kaam karo. External call transaction ke bahar, ya behtar — queue mein (ch 12).

MVCC — Postgres Ka Asli Raaz

Ek sawaal: agar A ek row update kar raha hai aur B usi row ko padh raha hai, toh B ko rukna padega? Postgres mein nahi — aur uski wajah hai MVCC (Multi-Version Concurrency Control).

Mechanism: Postgres row ko update nahi karta. Wo ek nayi version likhta hai aur purani ko "is transaction ID tak valid" mark kar deta hai. Har row ke saath do chhupe columns hote hain: xmin (kis transaction ne banayi) aur xmax (kis ne mitayi).

Isolation Levels Aur Unke Anomalies

Isolation level batata hai ki concurrent transactions ek doosre ka kaam kitna dekh sakte hain. Zyada isolation = zyada correctness, kam concurrency.

LevelDirty readNon-repeatable readPhantom readPostgres mein
Read Uncommittedpossiblepossiblepossibleexist hi nahi — Read Committed jaisa behave karta hai
Read Committed❌possiblepossibleDEFAULT
Repeatable Read❌❌❌*Snapshot isolation — MVCC se
Serializable❌❌❌SSI — conflict pe error deta hai, retry karna padta hai

* Postgres ka Repeatable Read phantom reads bhi rok deta hai (spec se strong), par write skew ab bhi possible hai — uske liye Serializable chahiye.

anomalies — concrete
-- NON-REPEATABLE READ (Read Committed mein possible)
BEGIN;
SELECT balance FROM accounts WHERE id=1;   -- 1000
   -- … koi aur txn commit karta hai …
SELECT balance FROM accounts WHERE id=1;   -- 500 !! usi txn mein alag jawab
COMMIT;

-- LOST UPDATE — ch 9 wali problem, DB level pe
-- ❌ read-modify-write: dono ne 1000 padha, dono ne 1100 likha → ek update KHO gaya
SELECT balance FROM accounts WHERE id=1;    -- app mein +100 kiya
UPDATE accounts SET balance = 1100 WHERE id=1;

-- ✅ Fix 1: atomic update — DB khud padhta aur likhta hai
UPDATE accounts SET balance = balance + 100 WHERE id=1;

-- ✅ Fix 2: explicit row lock (jab beech mein logic chahiye)
SELECT balance FROM accounts WHERE id=1 FOR UPDATE;  -- doosra txn yahan rukega

-- ✅ Fix 3: version column (ch 9 ka optimistic locking)
UPDATE accounts SET balance=1100, version=version+1
 WHERE id=1 AND version=12;   -- rowCount=0 → conflict → retry
🧠 Practical rule — kab kaunsa level

99% queries ke liye Read Committed (default) theek hai — bas read-modify-write pattern se bacho (atomic update ya FOR UPDATE use karo). Jab ek transaction mein kai reads ka consistent snapshot chahiye (report generate karna, balance reconciliation) → Repeatable Read. Jab correctness ka koi aur tareeka na ho (complex invariants, write skew) → Serializable, par tab tumhe serialization_failure pe retry logic likhna hi padega — wo optional nahi hai.

Locking, Deadlocks, Aur Lock Ordering

deadlock — kaise banta hai aur kaise rokte hain
-- Txn A                          -- Txn B
BEGIN;                            BEGIN;
UPDATE accounts SET … id=1;      UPDATE accounts SET … id=2;   -- alag rows, koi problem nahi
UPDATE accounts SET … id=2;      UPDATE accounts SET … id=1;   -- ← A ko 2 chahiye, B ko 1
-- DEADLOCK. Postgres ~1s baad detect karke EK txn ko maar deta hai.

-- ✅ Fix: HAMESHA ek consistent order mein lock lo (jaise ID ke ascending order)
SELECT * FROM accounts WHERE id IN (1,2) ORDER BY id FOR UPDATE;
-- Ab dono transactions same order mein lock lenge → deadlock possible hi nahi.
-- Money transfer code mein ye standard practice hai.

-- Timeouts — production mein ye set karna ZAROORI hai
SET lock_timeout = '3s';                     -- lock ke liye anant wait mat karo
SET statement_timeout = '30s';                -- runaway query ko maar do
SET idle_in_transaction_session_timeout = '60s'; -- bhoola hua txn band karo (MVCC!)

Connection Pooling — Ch 2 Ka Wada

Ch 2 mein bola tha ki connection pooling wo cheez hai jo client-to-DB direct connection ko structurally impossible banati hai. Ab uska mechanism.

Postgres mein har connection ek alag OS process hai (thread nahi) — ~5-10 MB RAM per connection. Isliye max_connections typically 100–200 hota hai. Connection banane mein TCP handshake + auth + session setup lagta hai (~10-50ms) — ek query se kahin zyada.

pool sizing — counter-intuitive part
const pool = new Pool({
  max: 20,                        // 20 connections, sab requests inhe SHARE karti hain
  idleTimeoutMillis: 30000,      // idle connection 30s baad chhod do
  connectionTimeoutMillis: 5000, // pool khali hai → 5s baad FAIL karo, anant wait nahi
});

// ⚠️ Bada pool = fast NAHI hota. Ulta ho sakta hai.
// 100 connections 4-core DB pe: sab context-switch karengi, lock contention
// badhegi, aur throughput GIR jayega.
// Rule of thumb: connections ≈ (CPU cores × 2) + effective_spindle_count
// Ek 4-core DB ke liye ~10 connections aksar 100 se BEHTAR perform karta hai.

// Aur math yaad rakho: 10 app instances × pool 20 = 200 connections DB pe.
// max_connections=100 hai? Toh aadhe app instances connect hi nahi kar payenge.
⚠️ "Pool exhaustion" ka signature pehchano

Symptom: latency suddenly phatt jaati hai (5ms → 30s), par DB ka CPU normal hai aur queries apne aap mein fast hain. Wajah: requests connection ka intezaar kar rahi hain, query ka nahi. Common causes — transaction ke andar external API call (§5), connection release na karna (error path pe finally missing), ya ek slow query jo poora pool jaam kar rahi hai. Diagnose: SELECT state, count(*) FROM pg_stat_activity GROUP BY state; — idle in transaction zyada dikha toh yahi problem hai. Ye ch 1 ke Q2 ka jawab tha.

Serverless ya bahut saare instances wale setup mein app-level pool kaafi nahi hota — tab PgBouncer (external pooler) lagta hai, jo hazaaron client connections ko chand actual Postgres connections pe multiplex karta hai. Uska transaction mode sabse efficient hai, par us mode mein session-level features (prepared statements, advisory locks, SET) toot-te hain — ye trade-off jaan ke choose karna.

N+1 Aur Doosre Rozana Ke Killers

N+1 — sabse common performance bug
// ❌ 1 + N queries — ORM ke saath ye BAHUT aasaani se ho jaata hai
const orders = await db.query("SELECT * FROM orders LIMIT 100");   // 1 query
for (const o of orders) {
  o.user = await db.query("SELECT * FROM users WHERE id=$1", [o.userId]);  // 100 queries!
}
// 101 round trips. Har ek 1ms bhi ho toh 101ms — sirf network latency mein.

// ✅ Fix 1: JOIN
SELECT o.*, u.name FROM orders o JOIN users u ON u.id = o.user_id LIMIT 100;

// ✅ Fix 2: batch load (2 queries — jab JOIN se duplicate rows aayein)

const byId = new Map(users.map(u => [u.id, u]));
orders.forEach(o => o.user = byId.get(o.userId));

Key Takeaways

  • Performance ka 90% ek sawaal hai: kitne 8KB pages padhne padte hain.
  • Shared buffer pool ki wajah se ek hi query pehli baar 200ms aur doosri baar 2ms le sakti hai — benchmarking mein ye sabse badi galti hai.
  • B-tree ki height ~3–4 rehti hai; rows 100× badhne pe reads sirf 1 badhta hai.
  • Index tumhe ctid deta hai, row nahi — heap pe ek aur read lagti hai (jab tak index-only scan na ho).
  • Composite index mein leftmost prefix rule: equality columns pehle, range baad mein, ORDER BY aakhir mein.
  • Column pe function/cast lagate hi index mar jaata hai — query rewrite karo ya expression index banao.
  • Har index writes slow karta hai; unused indexes (pg_stat_user_indexes) hata do. Production mein CREATE INDEX CONCURRENTLY.
  • EXPLAIN (ANALYZE, BUFFERS): estimated vs actual rows ka 10× farq = stale stats; loops=N = N+1 ka signature.
  • Index hone ka matlab index use hona nahi — bahut saari rows match karein toh seq scan sach mein tez hota hai.
  • Transaction mein external API call kabhi nahi — wo locks aur pool connection pakde rehta hai.
  • MVCC: update nayi row version banata hai; readers writers ko block nahi karte. Cost = dead rows + VACUUM.
  • Lamba khula transaction VACUUM ko rok deta hai → bloat → sab slow. idle_in_transaction_session_timeout set karo.
  • Read Committed default hai aur 99% ke liye theek — bas read-modify-write se bacho (atomic update ya FOR UPDATE).
  • Serializable use karo toh serialization_failure pe retry logic zaroori hai.
  • Deadlock ka fix: hamesha ek consistent order mein lock lo (ORDER BY id FOR UPDATE).
  • Har Postgres connection ek OS process hai. Bada pool fast nahi hota — ~(cores × 2) aksar behtar hai.
  • Pool exhaustion ka signature: latency phatti hai par DB CPU normal hai. pg_stat_activity mein idle in transaction dekho.
  • N+1 ka fix JOIN ya batch load (WHERE id = ANY($1)) hai.

🎯 Interview Questions

Q1. "Index kaise kaam karta hai? Har column pe kyun na bana dein?"

B-tree ek balanced tree hai jiski leaves sorted keys + row pointers (ctid) rakhti hain, height ~3–4 — isliye 10 lakh rows mein lookup 3–4 page reads mein ho jaata hai, poore scan ki jagah. Har column pe isliye nahi kyunki har index writes ko slow karta hai (har INSERT/UPDATE pe update hota hai), disk leta hai, aur planner ko confuse kar sakta hai. Indexes actual query patterns dekh ke banaye jaate hain, andaaze se nahi.

Q2. "Index hai par query slow hai. Kya dekhoge?"

EXPLAIN (ANALYZE, BUFFERS). Common causes: (a) column pe function/cast lag raha hai (LOWER(email)) toh index use hi nahi ho sakta; (b) composite index ka leftmost prefix match nahi kar raha; (c) statistics stale hain — estimated vs actual rows mein bada farq, fix ANALYZE; (d) query itni rows return kar rahi hai ki seq scan sach mein sasta hai; (e) loops=N dikhe toh problem query nahi, N+1 hai; (f) Sort … Disk dikhe toh work_mem kam hai.

Q3. "MVCC kya hai? VACUUM kyun chahiye?"

Postgres row ko in-place update nahi karta — nayi version likhta hai, purani ko xmax se mark karta hai. Har transaction apne snapshot ke hisaab se decide karta hai kaunsi version usse dikhegi, isliye readers writers ko block nahi karte. Cost: dead row versions jama hote hain, aur VACUUM unhe reclaim karta hai. Ek lamba khula transaction purane snapshot ko zinda rakhta hai, isliye vacuum kuch clean nahi kar paata → table bloat → sab slow. Isiliye idle_in_transaction_session_timeout production mein zaroori hai.

Q4. "Do users ek saath balance update kar rahe hain. Lost update kaise rokoge?"

Read-modify-write default (Read Committed) pe safe nahi hai. Teen options: (1) atomic update — SET balance = balance + 100, DB khud padhta-likhta hai, sabse simple; (2) SELECT … FOR UPDATE — row lock, jab beech mein logic chahiye; (3) version column (optimistic locking) — WHERE version = $n, rowCount=0 pe retry, ye ch 9 ka ETag/If-Match ka DB-level version hai. Pehla sabse sasta hai; teesra tab jab conflicts kam ho aur user ko batana ho.

Q5. "Connection pooling kyun? Pool bada karne se fast hoga?"

Postgres mein har connection ek OS process hai (~5–10 MB) aur setup mein 10–50ms lagte hain — per-request connect karna DB ko mar dega. Pool unhe reuse karta hai. Aur nahi, bada pool fast nahi karta: 4-core DB pe 100 connections context switching aur lock contention badha ke throughput ghata deti hain; ~(cores × 2) aksar behtar hai. Math bhi dekho — 10 instances × pool 20 = 200 connections, jo max_connections=100 se zyada hai. Bahut instances hon toh PgBouncer.

Q6. "Deadlock kaise hota hai aur kaise rokoge?"

Do transactions ulte order mein locks lete hain: A ke paas row 1 hai aur usse 2 chahiye, B ke paas 2 hai aur usse 1 chahiye. Postgres detect karke ek ko deadlock detected se maar deta hai. Prevention: hamesha consistent order mein lock lo — jaise ORDER BY id FOR UPDATE. Saath mein lock_timeout aur statement_timeout set karo, aur transactions chhote rakho — lock jitni der pakda rahega, collision ka chance utna hi zyada.
