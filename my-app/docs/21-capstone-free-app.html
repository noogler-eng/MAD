1. What We're Building and the Free Stack

App ka naam: "Streaks" — a Habit Tracker with Premium Themes. Chhota app hai lekin jaan-boojh ke choose kiya hai kyunki ye ek real product ke saare core pillars ko touch karta hai — auth, ek relational database jisme per-user data hai, aur ek genuine paid feature. Feature list:

  • Free tier: sign up/login, apne habits add karna (jaise "10 min padhna", "Paani piyo"), roz check-in maar ke complete mark karna, aur ek streak counter (kitne consecutive din se maintain kiya).
  • Premium tier (paid, one-time unlock): extra themes (dark neon, pastel, etc.) aur ek extended stats screen (monthly heatmap jaisa view) unlock ho jaate hain.

Poore build mein hum sirf wahi tools use karenge jinka ek genuinely usable free tier hai — koi credit card kahin bhi nahi maangi jaayegi (Razorpay/Stripe test mode ke liye toh bilkul nahi, wo permanently free hai chahe app kitna bhi scale kare, kyunki usme real paisa kabhi move hi nahi hota).

  id uuid primary key default gen_random_uuid(), -- unique id, Postgres auto-generate karega

create index habits_user_id_idx on habits(user_id); -- user_id pe index, "mere habits dikhao" query aur RLS filter dono fast rehte hain

create table habit_logs ( -- naya table "habit_logs" — har row ek "is din maine ye habit complete kiya" record hai
  id uuid primary key default gen_random_uuid(), -- unique id
  habit_id uuid references habits(id) on delete cascade not null, -- kis habit ka log hai — habit delete ho toh uske saare logs bhi delete ho jaayein

); -- statement close

create index habit_logs_habit_id_idx on habit_logs(habit_id); -- ek habit ke saare logs jaldi fetch karne ke liye (streak calculation isi query pe based hai)
create index habit_logs_user_id_idx on habit_logs(user_id); -- RLS filter aur "mere saare logs" query dono is index se fast honge

🚨 Security Critical — is_premium ko client-writable mat banao

Notice karo profiles table pe humne koi for update policy client ke liye nahi banayi. Ye accident nahi hai — agar humne using (auth.uid() = id) jaisi update policy bana di, koi bhi authenticated user seedha apni row mein is_premium = true set kar sakta tha bina kabhi payment kiye, sirf ek normal Supabase client call se (supabase.from("profiles").update({ is_premium: true })). Isi wajah se ye update sirf service_role key (ch.9) ke through, humare khud ke server-side API route se hoga — section 6 mein ye poora dekhenge.

4. Step 3 — Auth Flow

Ab Supabase email/password auth ko Expo Router ke auth-guard pattern (ch.4) ke saath jodte hain. Pehle Supabase client:

lib/supabase.ts
import { createClient } from "@supabase/supabase-js"; // Supabase client banane ka function
import AsyncStorage from "@react-native-async-storage/async-storage"; // session ko disk pe persist karne ke liye storage adapter

const supabaseUrl = process.env.EXPO_PUBLIC_SUPABASE_URL!; // .env se Supabase project URL liya, ! se TypeScript ko bataya ki ye undefined nahi hoga

Ab AuthContext — ye global state hai jo poori app ko batayega ki user logged in hai ya nahi, aur ch.4 ke useAuth() pattern ko follow karta hai:

context/AuthContext.tsx
import { createContext, useContext, useEffect, useState, type ReactNode } from "react"; // React context/state/lifecycle APIs, ReactNode children ke type ke liye
import type { Session, User } from "@supabase/supabase-js"; // Supabase ke TypeScript types, session/user shape ke liye
import { supabase } from "../lib/supabase"; // humara shared Supabase client instance

type AuthContextType = { // context ka shape define kiya, taaki consumers ko autocomplete/type-safety mile
  user: User | null; // current logged-in user, ya null agar logged out
  session: Session | null; // current auth session (JWT + refresh token wrapper)
  isLoading: boolean; // initial session check abhi ho raha hai ya complete ho chuka
  signIn: (email: string, password: string) => Promise<{ error: string | null }>; // login function, error string ya null return karega
  signUp: (email: string, password: string) => Promise<{ error: string | null }>; // signup function, same shape
  signOut: () => Promise<void>; // logout function
};

const AuthContext = createContext<AuthContextType | undefined>(undefined); // context banaya, default undefined taaki galat use pe error mile (neeche hook mein check karenge)

export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null); // current user state
  const [session, setSession] = useState<Session | null>(null); // current session state
  const [isLoading, setIsLoading] = useState(true); // shuru mein true, jab tak humein pata na chale user logged in hai ya nahi

  useEffect(() => {
    // app khulte hi existing session (agar disk pe persist thi) fetch karo
    supabase.auth.getSession().then(({ data }) => {
      setSession(data.session); // session state update — agar disk pe koi valid session mili toh yahan aa jaayegi
      setUser(data.session?.user ?? null); // session ke andar se user nikaala, session null ho toh user bhi null
      setIsLoading(false); // ab hume pata chal gaya user logged in hai ya nahi — loading complete
    });

    // future mein session change hone pe (login/logout/token-refresh) auto-listen karo
    const { data: listener } = supabase.auth.onAuthStateChange((_event, newSession) => {
      setSession(newSession); // naya session state mein daala
      setUser(newSession?.user ?? null); // naya user state mein daala
    });

    return () => listener.subscription.unsubscribe(); // cleanup — component unmount pe listener hata do, memory leak se bachne ke liye
  }, []); // empty deps — sirf ek baar mount pe setup hoga

  const signIn = async (email: string, password: string) => {
    const { error } = await supabase.auth.signInWithPassword({ email, password }); // Supabase ka email/password login call
    return { error: error?.message ?? null }; // caller ko readable error message ya null return kiya
  };

  const signUp = async (email: string, password: string) => {
    const { data, error } = await supabase.auth.signUp({ email, password }); // naya account banane ka call
    if (error) return { error: error.message }; // signup hi fail ho gaya (jaise weak password), turant return

    if (data.user) { // signup successful hua, ab isi user ke liye ek profile row bhi bana dete hain
      await supabase.from("profiles").insert({ id: data.user.id }); // is_premium default false ke saath naya profile row insert, id = user ka id
    }
    return { error: null }; // sab kuch successful
  };

  const signOut = async () => {
    await supabase.auth.signOut(); // Supabase session clear karo — onAuthStateChange listener khud user/session state ko null kar dega
  };

  return (
    <AuthContext.Provider value={{ user, session, isLoading, signIn, signUp, signOut }}>
      {children} {/* poori app tree yahan wrap hoga, sab consume kar sakenge useAuth() se */}
    </AuthContext.Provider>
  );
}

export function useAuth() {
  const ctx = useContext(AuthContext); // context value nikaala
  if (!ctx) throw new Error("useAuth must be used inside AuthProvider"); // safety check — Provider ke bahar use hua toh clear error, silent undefined nahi
  return ctx; // consumers ko poora auth state + actions milta hai
}

Ab root layout mein ch.4 ka wahi useSegments-based auth guard pattern lagate hain, bas ab route groups (auth) aur (app) hamari is app ke names hain:

app/_layout.tsx
import { useEffect } from "react"; // lifecycle hook
import { Slot, useRouter, useSegments } from "expo-router"; // Slot = child route render karta hai, useSegments current path ke segments deta hai, useRouter navigation ke liye
import { AuthProvider, useAuth } from "../context/AuthContext"; // humara auth context

function RootLayoutNav() {
  const { user, isLoading } = useAuth(); // current auth state nikaala
  const segments = useSegments(); // current URL path ke segments, jaise ["(auth)", "login"]
  const router = useRouter(); // programmatic navigation ke liye

  useEffect(() => {
    if (isLoading) return; // jab tak session check complete na ho, koi redirect decision mat lo — ye redirect-loop gotcha (ch.4) avoid karta hai

    const inAuthGroup = segments[0] === "(auth)"; // pehla segment check kiya — kya user abhi (auth) group ke andar hai

    if (!user && !inAuthGroup) { // user logged out hai lekin protected (app) area mein jaane ki koshish kar raha hai
      router.replace("/(auth)/login"); // login screen pe bhej do, "replace" isliye taaki back button se wapas protected screen pe na aa sake
    } else if (user && inAuthGroup) { // user already logged in hai lekin login/signup screen dekh raha hai
      router.replace("/(app)"); // seedha main app area pe bhej do
    }
    // NOTICE: agar dono conditions false hain (jaise user null hai aur already (auth) mein hai), koi redirect nahi hota — yahi cheez infinite loop rokti hai
  }, [user, isLoading, segments]); // in teeno mein se koi change ho toh dobara evaluate karo

  return <Slot />; // current matched route render karo — actual Stack/Tabs navigators (auth)/(app) ke apne _layout.tsx mein hain
}

export default function RootLayout() {
  return (
    <AuthProvider> {/* poori app ko auth context se wrap kiya, taaki RootLayoutNav aur har child useAuth() use kar sake */}
      <RootLayoutNav />
    </AuthProvider>
  );
}
⚠️ Redirect Loop Gotcha (ch.4 se recap)

Agar isLoading check upar wale useEffect mein sabse pehle na ho, toh initial render pe (jab session abhi fetch hi ho rahi hai aur user abhi null hai by default) guard galti se "user logged out hai" samajh ke login pe redirect kar dega — chahe user actually logged in ho aur session bas load ho rahi ho. Fir jab actual session load hoti hai, guard dobara fire hoke wapas (app) pe bhejta hai — is flicker/race ko hi "redirect loop" kehte hain. Fix wahi hai jo upar code mein hai: if (isLoading) return; sabse pehli line honi chahiye is effect ke andar.

5. Step 4 — Core Habit Tracking Feature

Ab main feature — habits list dikhana, aaj ka check-in maarna, aur streak count calculate karna. Pehle streak-calculation ko ek pure function ke roop mein alag lib/streaks.ts mein likhte hain — UI logic se alag rakhne se ise easily test bhi kiya ja sakta hai (ch.7 ke testing principles):

lib/streaks.ts
// "completed_on" dates ki ek list leke current streak (consecutive days including aaj/kal) calculate karta hai
export function calculateStreak(completedDates: string[]): number {
  if (completedDates.length === 0) return 0; // koi log hi nahi hai toh streak zero

  const uniqueSorted = Array.from(new Set(completedDates)) // duplicate dates hata diye (Set) agar galti se aa gaye ho
    .sort() // "YYYY-MM-DD" format string sort se hi chronological order aa jaata hai
    .reverse(); // sabse naya date pehle chahiye, isliye reverse kiya

  const today = new Date(); // aaj ki date object
  today.setHours(0, 0, 0, 0); // time-of-day zero kiya, taaki sirf calendar-day compare ho, hours/minutes se farak na pade

  const mostRecent = new Date(uniqueSorted[0]); // sabse latest completed date ko Date object mein convert kiya
  const daysSinceLast = Math.round((today.getTime() - mostRecent.getTime()) / (1000 * 60 * 60 * 24)); // aaj aur sabse recent check-in ke beech kitne din, milliseconds-to-days conversion

  if (daysSinceLast > 1) return 0; // agar last check-in 1 din se zyada purana hai (matlab kal bhi miss kiya), streak toot chuki hai — zero

  let streak = 1; // kam se kam ek din toh complete hai hi (sabse recent wala), isse count shuru
  for (let i = 0; i < uniqueSorted.length - 1; i++) { // consecutive pairs check karne ke liye loop, aakhri element tak nahi jaate kyunki pair chahiye
    const current = new Date(uniqueSorted[i]); // current date is iteration ka
    const previous = new Date(uniqueSorted[i + 1]); // usse ek din purana wala date (array reverse-sorted hai, isliye i+1 purana hai)
    const diff = Math.round((current.getTime() - previous.getTime()) / (1000 * 60 * 60 * 24)); // dono dates ke beech ka gap din mein

    if (diff === 1) { // exactly ek din ka gap matlab consecutive day hai, streak continue
      streak++; // streak count badhaya
    } else {
      break; // gap 1 se zyada mila matlab kahin beech mein miss hua tha, isliye streak yahin ruk jaati hai
    }
  }

  return streak; // final consecutive-days count return kiya
}
💡 Quick Tip — kal ka check-in bhi allow kyun kiya

daysSinceLast > 1 check isliye hai, na ki > 0 — agar user ne kal check-in kiya tha aur aaj abhi tak nahi kiya (lekin din khatam nahi hua), streak abhi "broken" nahi maani jaani chahiye, warna app "aaj kuch nahi kiya toh turant streak 0 dikha do" jaisa harsh/annoying UX de dega. Ye ek chhoti si business-logic decision hai jo real habit-tracker apps (jaise Duolingo) mein bhi is tarah handle hoti hai.

(e) Server-side signature verify karna — premium tabhi unlock jab genuinely verified ho

Ye poore flow ka sabse important security step hai. Razorpay checkout se aaya "success" client-side event hai — usse blindly trust karna bilkul waisi hi galti hai jaisa ch.15 mein StoreKit ke client-side success event ko blindly trust karna thi. Razorpay order_id + payment_id ko tumhare Key Secret se ek HMAC signature ke saath sign karke bhejta hai — server pe wahi signature dobara compute karke match karte hain, tabhi genuinely confirm hota hai ki payment tamper nahi hua.

app/api/verify-payment+api.ts
import crypto from "crypto"; // Node ka built-in crypto module, HMAC signature verify karne ke liye
import { createClient } from "@supabase/supabase-js"; // server-side Supabase client banane ke liye

// service_role key wala client — RLS bypass karta hai, isliye sirf yahan server pe, kabhi client bundle mein nahi
const supabaseAdmin = createClient(
  process.env.EXPO_PUBLIC_SUPABASE_URL!, // URL public hai, koi issue nahi
  process.env.SUPABASE_SERVICE_ROLE_KEY! // service_role key — sirf server, RLS ko bypass karke bhi safe hai kyunki humne khud user_id filter kiya hai code mein
);

export async function POST(request: Request) {
  const body = await request.json(); // client se aaya payment data parse kiya
  const { razorpay_order_id, razorpay_payment_id, razorpay_signature } = body; // teeno zaroori fields destructure kiye

  if (!razorpay_order_id || !razorpay_payment_id || !razorpay_signature) { // koi field missing ho toh aage mat badho
    return Response.json({ verified: false, error: "Missing fields" }, { status: 400 }); // 400 = bad request
  }

  // Razorpay ka documented signature-verification formula: HMAC-SHA256("order_id|payment_id", key_secret)
  const expectedSignature = crypto
    .createHmac("sha256", process.env.RAZORPAY_KEY_SECRET!) // SHA256 HMAC banaya, secret key ke saath — ye secret sirf server pe hai, isliye ye check kabhi client mein nahi ho sakta
    .update(`${razorpay_order_id}|${razorpay_payment_id}`) // exact wahi string format jo Razorpay docs specify karti hain
    .digest("hex"); // hex string ke roop mein final hash nikaala

  const isValid = expectedSignature === razorpay_signature; // hamara khud compute kiya hash, client se aaye signature se match hona chahiye

  if (!isValid) { // signature match nahi hui — ya toh tampered request hai, ya kuch galat gaya
    return Response.json({ verified: false }, { status: 400 }); // premium unlock BILKUL nahi hoga is case mein
  }

  // signature genuinely valid hai — ab hi database mein is_premium update karte hain, aur kabhi pehle nahi
  const authHeader = request.headers.get("Authorization"); // production mein yahan client ka JWT bhejwa ke us se user_id derive karna chahiye (simplified example)
  // NOTE: real app mein yahan supabaseAdmin.auth.getUser(token) se verified user_id nikaalo, client se raw user_id trust mat karo

  await supabaseAdmin
    .from("profiles") // "profiles" table target kiya
    .update({ is_premium: true, unlocked_at: new Date().toISOString() }) // premium flag ON + timestamp record kiya
    .eq("id", "USER_ID_DERIVED_FROM_VERIFIED_TOKEN"); // sirf isi (verified) user ki row update ho — service_role key RLS bypass karta hai isliye ye WHERE khud enforce karna zaroori hai

  return Response.json({ verified: true }); // client ko confirm kiya — ab premium genuinely unlock ho chuka hai DB mein
}
🚨 Security Critical — service_role key ek double-edged sword hai

service_role key RLS ko completely bypass karti hai — isi wajah se ye isi tarah ke server-side "trusted operation" ke liye zaroori hai (client khud is_premium update nahi kar sakta, section 3 mein dekha). Lekin isi wajah se, jab tum ye key use karte ho, RLS ka automatic protection gaya — matlab tumhe khud apne code mein WHERE clause se sunishchit karna padega ki update sirf sahi user ki row pe ho raha hai (upar wale .eq("id", verified_user_id) jaisa). Production code mein request ke Authorization header se JWT nikaal ke supabaseAdmin.auth.getUser(token) se verified user id nikaalna zaroori hai — client se raw user_id field accept karna khud ek security hole hai (koi bhi doosre ka id bhej ke uska account premium bana sakta hai).

ℹ️ Stripe Test Mode Equivalent (global readers ke liye)

Agar Stripe use kar rahe ho: pk_test_... (publishable, client) aur sk_test_... (secret, server) dono test keys hongi. Flow bilkul same shape ka hai — server pe (ch.15 ka create-payment-intent+api.ts) ek PaymentIntent banega Stripe's well-known published test card 4242 4242 4242 4242 se test kiya ja sakta hai (koi bhi future expiry date, koi bhi 3-digit CVC chalega). Signature-verification ka Stripe equivalent hai webhook signing secret se webhook events verify karna — client-side confirmPayment() success ko trust karne ke bajaye, backend Stripe se ek server-to-server webhook (payment_intent.succeeded) receive karke tabhi is_premium update kare. Mental model bilkul identical hai: kabhi bhi sirf client ka "success" mat maano, hamesha server-side, provider ke apne cryptographic proof se verify karo.

7. Step 6 — Debugging Steps at Each Stage

Real building mein pehli try mein kabhi kuch perfect nahi chalta. Yahan har stage ke sabse common bugs aur unhe systematically debug karne ka tareeka hai:

Supabase — "RLS policy blocking a query that should work"

Symptom: query error nahi deti, bas empty array return karti hai jab tumhe pata hai data DB mein exist karta hai.

  1. Sabse pehle confirm karo user actually authenticated hai — console.log(await supabase.auth.getSession()) chala ke dekho session null toh nahi hai.
  2. Supabase dashboard ke SQL Editor mein jaake, apne policy ke USING clause ko directly ek query se simulate karo: select * from habits where user_id = auth.uid(); — agar SQL Editor mein bhi empty aata hai (aur SQL Editor default service_role context mein chalta hai, isliye RLS bypass hota hai wahan), toh problem RLS nahi, data hi missing hai. Agar SQL Editor mein data dikhta hai lekin app mein nahi, toh RLS policy ya auth context ka issue hai.
  3. Dashboard mein Database → Policies pe jaake confirm karo ki policy ka naam, operation (select/insert/etc.), aur USING/WITH CHECK expression bilkul wahi hai jo tumne socha tha — copy-paste errors yahan bahut common hain.
  4. Confirm karo ki alter table ... enable row level security chala tha (ch.9 ka wahi common miss) — agar RLS enable hi nahi hai, koi bhi policy matter nahi karti.

Auth — "Auth guard redirect loop"

Symptom: app login aur main screen ke beech flicker karti rehti hai, ya white screen pe stuck ho jaati hai.

  1. Section 4 ke gotcha ko recap karo — app/_layout.tsx ke useEffect mein if (isLoading) return; line sabse pehle honi chahiye.
  2. console.log(segments) daal ke dekho actual segments kya aa rahe hain — kabhi kabhi route group ka naam typo ho jaata hai (jaise "auth" likh diya "(auth)" ki jagah, jo kabhi match hi nahi karega).
  3. useEffect ki dependency array check karo — agar segments missing hai deps se, redirect stale closures ke saath fire ho sakta hai.

Razorpay — "Test payment succeeds on Razorpay's side but app doesn't unlock premium"

Ye is chapter ka sabse "senior-level" debugging scenario hai — checkout dikhata hai success, lekin app mein is_premium false hi rehta hai.

  1. Signature verification silently fail toh nahi hui? — verify-payment+api.ts ke andar console.log({ expectedSignature, razorpay_signature }) daal ke dono values compare karo. Agar match nahi ho rahi, sabse pehla suspect: Key Secret galat hai (ya dashboard se copy karte waqt extra space aa gaya).
  2. Key mismatch check karo — ek bahut common real mistake: client mein Test Mode ka Key ID (rzp_test_...) use ho raha hai lekin server pe galti se Live Mode ka Key Secret paste ho gaya (ya vice versa). Test aur Live keys ek doosre se completely independent hote hain — mismatch hote hi signature kabhi match nahi karegi, chahe payment "successful" dikhe.
  3. Request backend tak pahuncha hi nahi? — client-side network tab/logs check karo (agla point) ki /api/verify-payment call actually fire hui aur 200 response aayi, ya kahin beech mein hi fail ho gayi (jaise app background mein chali gayi payment ke turant baad, request cancel ho gayi).
  4. Amount/order mismatch? — confirm karo ki client ne wahi order_id bheja jo server ne banaya tha, koi stale/cached order id toh nahi reuse ho raha.

General — "App works in Expo Go but not in a Dev Build"

Symptom: Expo Go mein sab theek chalta hai, lekin jaise hi react-native-razorpay jaisa native module use karte ho, error aata hai jaise "Cannot find native module".

  1. Ye ch.1 ka exact wahi gotcha hai — Expo Go ek fixed set of native modules ke saath aata hai, aur third-party native SDKs (jaise Razorpay checkout, jo actual native iOS/Android code use karta hai) usme included nahi hote.
  2. Fix: npx expo install expo-dev-client chalao, phir npx expo run:android ya eas build --profile development se ek dev build banao — Razorpay jaise native modules sirf dev build/production build mein hi kaam karenge.
  3. Rule of thumb (ch.1 se): jaise hi koi native SDK app mein aata hai, Day 1 se dev build pe shift ho jao, Expo Go sirf pure-JS prototyping ke liye best hai.

Network debugging — jab kuch silently fail ho raha ho

Jab upar ke sab checks ke baad bhi samajh nahi aa raha error kahan hai, actual HTTP request/response dekhna sabse reliable tareeka hai — "kya request gayi bhi thi, aur kya response mein aaya":

  • React Native DevTools ka Network tab (ch.19 ke debugging tools) khol ke /api/create-order aur /api/verify-payment dono requests ko inspect karo — request body sahi bheja gaya tha? Response status code kya tha? Response body mein koi error message hai?
  • Agar Supabase call fail ho rahi hai, wahi Network tab mein Supabase ke REST endpoint (*.supabase.co/rest/v1/...) ka actual response dekh sakte ho — Postgres ka raw error message wahan milta hai jo kaafi baar console.log se zyada specific hota hai (jaise exact constraint violation).
  • Supabase dashboard ke Logs section mein bhi jaake dekho — har API request, uska status, aur agar RLS ne reject kiya toh wo bhi yahan trace hota hai.

8. Step 7 — Building and Sharing for Free

Ab app ko ek real installable build mein convert karke ek dost ko test karne ke liye bhejte hain — sab kuch EAS ke free tier se, bina koi paid subscription liye.

terminal — EAS preview build (ch.10 ka profile)
# agar pehli baar EAS use kar rahe ho, CLI install/login karo
npm install -g eas-cli # EAS ka global CLI tool install kiya
eas login # Expo account se login (free account kaafi hai)

# project ko EAS se configure karo (eas.json ban jaayega, "preview" profile already default template mein hota hai)
eas build:configure # interactive setup — platform choose karega, eas.json generate karega

# Android ke liye ek preview (internal-distribution) build banao — ye .apk deta hai, seedha install ho sakta hai
eas build --profile preview --platform android # cloud pe build hota hai, EAS free tier ke build minutes use hote hain

Build complete hone pe EAS terminal mein aur dashboard pe ek install link deta hai (jaise https://expo.dev/accounts/.../builds/...) — ye link kisi ko bhi (dost, tester) seedha WhatsApp/email se bhej sakte ho. Android pe koi bhi is link ko apne phone pe khol ke .apk download aur install kar sakta hai — koi Play Store account, koi paid developer program, kuch bhi nahi chahiye.

🧠 Senior Dev Note — iOS ka honest reality check

Android + Expo Go + iOS Simulator (agar Mac hai) — ye poora loop 100% free hai. Lekin agar tumhe ye build ek real iPhone pe install karke dikhana hai (Expo Go ke bina, jaise Razorpay native module wale is app ke liye zaroori hoga), Apple ka rule hai ki bina App Store release ke bhi real device pe app install karne ke liye ek Apple Developer Program membership ($99/year) chahiye hi hoga — chahe wo sirf testing ke liye ho, App Store pe publish na bhi karo. Ye is poore pipeline ka ekmatra hissa jo genuinely free nahi hai — honestly bata dena zaroori hai, kyunki "poora free hai" bolna is ek exception ko chhupana hoga. Agar tumhare paas iPhone nahi hai ya sirf demo/learning purpose hai, Android + simulator/Expo Go se kaam chal jaata hai bina ek rupaya kharch kiye.

10. Closing — From Capstone to Production

Ye capstone tumhe ek genuinely working, end-to-end app deta hai — auth, database, aur ek real (test-mode) payment flow, sab kuch free tools se. Lekin ye ek foundation hai, final product nahi. Agar tum isse actual real users ko dena chahte ho, yahan se aage ka raasta poori handbook mein already likha hua hai:

  • ch.11 (EAS Submit) — App Store aur Play Store pe automate submission karne ke liye.
  • ch.14 (Publishing) — full submission checklists, screenshots, store listing requirements.
  • ch.15 (Payments) — Razorpay/Stripe Test keys ko Live keys mein switch karna, aur agar premium feature ko "digital good" maana jaaye toh StoreKit/Play Billing (RevenueCat) ke through jaana bhi consider karna — is chapter ka Category A/B distinction yahan dobara relevant ho jaata hai.
  • ch.19 (Debugging & Crashes) — real users ke saath Sentry crash reporting add karna, taaki production issues aane se pehle hi pata chal jaayein.

Baaki poori handbook — Style/Design, Animations, State Management, Accessibility — sab is capstone app ko polish karne mein directly apply hoti hai. Ye chapter ek starting point tha; asli seekhna tab hota hai jab tum khud is app mein naye features add karte ho, khud bugs debug karte ho, aur khud decide karte ho ki agla kya banana hai.
