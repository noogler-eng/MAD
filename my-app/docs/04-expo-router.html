1. File-Based Routing Fundamentals

Expo Router ka core idea simple hai — filesystem hi tumhara route config hai. Jitna bhi app/ folder ke andar file structure banaoge, utna hi tumhara navigation graph ban jaayega. Koi separate Navigator config file nahi likhni padti jaise React Navigation mein pehle likhte the.

Internally kya hota hai: build/dev time pe Expo CLI (Metro ke integration ke through) app/ directory ko recursively scan karta hai aur ek route manifest banata hai — basically ek tree data structure jisme har node ek file ya folder ko represent karta hai. Ye manifest phir expo-router ke runtime ko diya jaata hai jo internally React Navigation ke primitives ( NavigationContainer, Stack.Navigator, Tab.Navigator, linking config) use karke actual navigator tree render karta hai. Matlab Expo Router "React Navigation ke upar ek code-gen + convention layer" hai, replacement nahi.

File structure → Route mapping
app/                    // root routing folder — filesystem yahan se hi navigation tree derive karta hai
├── _layout.tsx          // Root layout — sabse pehle mount hota hai, isliye auth-check/splash-hold logic yahan likhi jaati hai
├── index.tsx            // "/" route — top-level pe rakha taaki app khulte hi koi default landing decision ho sake (redirect to auth/app)
├── (auth)/              // Route GROUP — URL mein "(auth)" nahi aata, sirf isliye group kiya taaki inka shared _layout + auth-guard target ho
│   ├── _layout.tsx      // sirf auth screens ke liye layout — logged-in screens ke layout se isolate, taaki dono independently evolve kar sakein
│   ├── login.tsx        // route: "/login" — is group ke andar isliye ki auth guard poore group ko ek unit ki tarah redirect kar sake
│   └── signup.tsx       // route: "/signup" — same reason, login/signup dono unauthenticated-only screens hain
├── (app)/               // dusra group — logged-in area, (auth) se alag naam isliye taaki dono tree clearly distinguish ho sakein guard logic mein
│   ├── _layout.tsx      // is group ka apna layout — yahan RBAC check bhi laga sakte hain kyunki har (app) route yahan se guzarta hai
│   ├── (tabs)/          // nested group — Tab navigator ke liye, (app) ke andar nested isliye taaki tabs sirf logged-in area mein hi ho
│   │   ├── _layout.tsx  // yahan <Tabs> component define hota hai — is level pe isliye kyunki sirf yahi files tab-bar mein dikhni hain
│   │   ├── index.tsx    // route: "/" (tab 1, home) — index.tsx naam se hi wo folder ka default route ban jaata hai
│   │   └── profile.tsx  // route: "/profile" — flat rakha (nested folder nahi) kyunki profile ka apna sub-navigation nahi hai
│   └── settings.tsx     // route: "/settings" — tabs ke bahar isliye kyunki ye tab-bar mein nahi dikhta, sirf profile se navigate hota hai
└── product/             // dynamic-route group — top-level isliye kyunki product detail kisi bhi tab se open ho sakta hai
    └── [id].tsx         // dynamic route: "/product/42" — [id] bracket syntax filename ko URL param mein convert karta hai

_layout.tsx — nested layouts ka backbone

Har folder mein ek _layout.tsx daal sakte ho jo us folder ke andar ke saare routes ko "wrap" karta hai — same jaise Next.js ke layout.tsx concept se inspired hai. Ye file <Slot />, <Stack /> ya <Tabs /> return karti hai, jo batata hai ki child routes kaise render/navigate honge.

app/_layout.tsx
import { Stack } from "expo-router";

export default function RootLayout() {
  return (
    <Stack screenOptions={{ headerShown: false }}>
      <Stack.Screen name="(auth)" />
      <Stack.Screen name="(app)" />
    </Stack>
  );
}

(group) folders — URL invisible, organisation visible

Parenthesis wale folders — jaise (auth), (app), (tabs) — sirf organizational purpose ke liye hote hain. Router in folder names ko URL segment nahi banata. Isliye app/(app)/(tabs)/profile.tsx ka actual route /profile hi rahega, na ki /(app)/(tabs)/profile. Ye extremely useful hai jab tum related screens ko alag layout/context ke andar group karna chahte ho bina URL ganda kiye.

index.tsx — default route resolver

Kisi bhi folder ke andar index.tsx us folder ke "root" URL ko resolve karta hai — exactly jaise web pe index.html. Toh app/(app)/(tabs)/index.tsx tab navigator ka default (pehla) tab render karega jab URL / hoga.

🧠 Senior Dev Note

Route tree build-time pe generate hota hai lekin dev mode mein Metro ke file-watcher ke through hot re-generate bhi hota hai — matlab naya file banate hi (bina restart kiye) naya route available ho jaata hai. Production build mein ye tree static ho jaata hai aur bundle mein bake ho jaata hai, isliye file naming conventions (jaise [id].tsx, _layout.tsx) ko strictly follow karna zaroori hai — typo kiya toh silently route match nahi hoga, koi build error nahi milega.

2. Dynamic Routes

Dynamic segments file name mein square brackets se define hote hain — [id].tsx. Router internally is filename ko regex-jaisa pattern bana ke store karta hai, aur URL match karte waqt us segment ki actual value ko params object mein daal deta hai.

app/product/[id].tsx
import { useEffect, useState } from "react";
import { View, Text, ActivityIndicator } from "react-native";
import { useLocalSearchParams } from "expo-router";

type Product = { id: string; title: string; price: number };

export default function ProductScreen() {
  // id yahan hamesha string | string[] type ka hota hai
  const { id } = useLocalSearchParams<{ id: string }>();
  const [product, setProduct] = useState<Product | null>(null);

  useEffect(() => {
    fetch(`https://api.myapp.com/products/${id}`)
      .then((res) => res.json())
      .then(setProduct);
  }, [id]);

  if (!product) return <ActivityIndicator />;

  return (
    <View>
      <Text>{product.title}</Text>
      <Text>₹{product.price}</Text>
    </View>
  );
}

Catch-all routes — [...missing].tsx

Agar koi route match hi nahi hota (galat URL, ya deep link jo exist nahi karta), toh usko handle karne ke liye ek catch-all file banate hain [...missing].tsx. Ye "rest params" jaisa syntax hai — jitne bhi extra segments URL mein honge sab ek array mein capture ho jaate hain.

app/[...missing].tsx
import { Link, useLocalSearchParams } from "expo-router";
import { View, Text } from "react-native";

export default function NotFoundScreen() {
  const { missing } = useLocalSearchParams<{ missing: string[] }>();
  return (
    <View>
      <Text>404 — Route not found: /{missing?.join("/")}</Text>
      <Link href="/">Go home</Link>
    </View>
  );
}

Typed Routes — compile-time route safety

Expo Router ka Typed Routes feature (app.json mein "experiments": { "typedRoutes": true } enable karke) build-time pe saare valid routes ka ek TypeScript union type generate karta hai (.expo/types/router.d.ts mein). Isse router.push("/product/42") jaisi calls compile-time pe hi check ho jaati hain — agar tumne typo kiya ya non-existent route diya, TS error dega, runtime crash nahi milega.

💡 Quick Tip

Typed routes ke saath dynamic segments ke liye tumhe object syntax use karna padta hai: router.push({ pathname: "/product/[id]", params: { id: "42" } }) — ye zyada verbose hai lekin autocomplete + type-check dono milte hain.

3. Stack & Tabs Navigation

<Stack /> aur <Tabs /> — ye dono _layout.tsx files ke andar use hone wale "layout primitives" hain jo React Navigation ke createNativeStackNavigator aur createBottomTabNavigator ko internally wire karte hain, bas declarative JSX API ke through.

Common pattern: Tabs at root, Stack inside each tab

Real apps mein bottom tabs hoti hain (Home, Search, Profile), aur har tab ke andar apna khud ka navigation stack hota hai (jaise Home tab se product detail pe push karna, but tab bar hamesha visible rehna chahiye). Isko achieve karte hain nested layouts se — ek folder ke andar dusra _layout.tsx.

app/(app)/(tabs)/_layout.tsx
import { Tabs } from "expo-router";
import { Ionicons } from "@expo/vector-icons";

export default function TabsLayout() {
  return (
    <Tabs screenOptions={{ headerShown: false }}>
      <Tabs.Screen
        name="index"
        options={{
          title: "Home",
          tabBarIcon: ({ color, size }) => <Ionicons name="home" size={size} color={color} />,
        }}
      />
      <Tabs.Screen name="profile" options={{ title: "Profile" }} />
    </Tabs>
  );
}
app/(app)/(tabs)/home/_layout.tsx (nested stack inside a tab)
import { Stack } from "expo-router";

export default function HomeStackLayout() {
  return (
    <Stack>
      <Stack.Screen name="index" options={{ title: "Home" }} />
      <Stack.Screen
        name="details/[id]"
        options={{ title: "Details", presentation: "modal" }}
      />
    </Stack>
  );
}

Yahan tab bar hamesha screen ke bottom pe rahega, chahe tum home/index pe ho ya home/details/42 pe — kyunki nested Stack sirf tab ke content area ko control karta hai, outer Tabs navigator ko affect nahi karta.

Header customization

Har screen apne Stack.Screen options prop se apna header customize kar sakta hai, ya screen component ke andar se hi navigation.setOptions() jaisa hook, useNavigation() ke through call kar sakte ho dynamically (jaise API se title fetch karke set karna).

4. Router Hooks Deep-Dive

useRouter() — push vs replace vs back vs dismiss

useRouter() ek imperative API deta hai navigation ke liye. Internally ye React Navigation ke underlying navigation object ko wrap karta hai, aur native stack ke actual behavior ko expose karta hai:

router methods
const router = useRouter();

router.push("/product/42");   // naya screen STACK PE ADD karta hai
router.replace("/login");   // current screen ko HATA ke naya daalta hai
router.back();                 // ek step peeche (pop)
router.dismiss();              // modal ko close karta hai
router.dismissAll();           // saare modals ek saath close

Difference clearly samjho: push native stack mein ek naya entry add karta hai — back button dabane pe user previous screen pe wapas ja sakta hai. replace current entry ko stack se hata ke uski jagah naya daal deta hai — matlab back button se wapas us screen pe nahi ja sakte. Isliye login ke baad home pe jaate waqt hamesha replace use karo, warna user back dabake login screen pe wapas pahunch jaayega (bad UX + security anti-pattern).

usePathname() aur useSegments()

usePathname() current URL path deta hai as a string (jaise "/product/42"). useSegments() usi path ko array of segments ke roop mein deta hai — including group names (jaise ["(app)", "(tabs)", "profile"]). Ye segments hook especially auth guarding ke liye critical hai, jo hum next section mein dekhenge.

segments example
// URL: /profile, actual file: app/(app)/(tabs)/profile.tsx
const segments = useSegments();
// segments = ["(app)", "(tabs)", "profile"]

const pathname = usePathname();
// pathname = "/profile"

useFocusEffect — screen-focus based logic

Native stack mein screens unmount nahi hoti jab tum push karte ho — wo bas background mein reh jaati hain memory mein (performance ke liye). Isliye agar tumhe kuch karna hai jab screen phir se focus mein aaye (bina full remount ke) — jaise list refresh karna — useEffect kaafi nahi hai, tumhe useFocusEffect chahiye.

useFocusEffect example
import { useCallback } from "react";
import { useFocusEffect } from "expo-router";

useFocusEffect(
  useCallback(() => {
    refreshFeed();
    return () => {
      // cleanup jab screen blur ho (dusri screen pe navigate ho jaaye)
    };
  }, [])
);
⚠️ Gotcha

useFocusEffect ke andar useCallback lagana mandatory hai — nahi lagaoge toh har render pe effect re-run hoga kyunki callback reference change hota rahega. Ye ek common perf bug hai.

5. Authentication Flow (Protected Routes)

Ye sabse important pattern hai kisi bhi production RN app mein. Standard architecture: ek AuthContext jo poore app ko wrap karta hai aur auth state (user, token, loading) provide karta hai, aur root _layout.tsx jo useSegments() dekh ke decide karta hai user (auth) group mein hona chahiye ya (app) group mein.

Step 1 — AuthContext

context/AuthContext.tsx
import { createContext, useContext, useEffect, useState } from "react";
import * as SecureStore from "expo-secure-store";

type User = { id: string; email: string; role: "admin" | "user" };
type AuthContextType = {
  user: User | null;
  isLoading: boolean;
  signIn: (email: string, password: string) => Promise<void>;
  signOut: () => Promise<void>;
};

const AuthContext = createContext<AuthContextType | null>(null);

export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const [isLoading, setIsLoading] = useState(true);

  useEffect(() => {
    (async () => {
      const token = await SecureStore.getItemAsync("session_token");
      if (token) {
        const me = await fetchCurrentUser(token);
        setUser(me);
      }
      setIsLoading(false);
    })();
  }, []);

  const signIn = async (email: string, password: string) => {
    const { token, user: u } = await loginApi(email, password);
    await SecureStore.setItemAsync("session_token", token);
    setUser(u);
  };

  const signOut = async () => {
    await SecureStore.deleteItemAsync("session_token");
    setUser(null);
  };

  return (
    <AuthContext.Provider value={{ user, isLoading, signIn, signOut }}>
      {children}
    </AuthContext.Provider>
  );
}

export const useAuth = () => useContext(AuthContext)!;
🚨 Security Critical — Token Storage

Kabhi bhi JWT ya session token ko AsyncStorage mein plain text mein mat rakho — especially sensitive apps (banking, fintech, health) ke liye. AsyncStorage unencrypted hota hai (SQLite/flat files ke roop mein disk pe), aur rooted/jailbroken device pe ya even ADB backup se koi bhi is data ko easily nikal sakta hai. Iski jagah expo-secure-store use karo — ye internally iOS pe Keychain aur Android pe Keystore use karta hai, jo hardware-backed encryption provide karte hain. Agar tumhara app financial ya highly sensitive data handle karta hai, toh ek layer aur add karo — SSL/certificate pinning (jaise react-native-ssl-pinning ya native config). Isse agar attacker MITM proxy laga ke TLS certificate bhi compromise kar de (jaise corporate proxy ya malicious wifi pe fake CA install karke), tab bhi app un requests ko reject kar dega kyunki server ka certificate pinned public key se match nahi karega.

Step 2 — Root layout guard logic

Ab asli magic yahan hota hai. Root _layout.tsx mein hum useSegments() se pata karte hain user currently kis group mein hai, aur auth state ke against compare karke redirect karte hain. Splash screen ko hold karke rakhte hain jab tak auth check complete na ho jaaye — isse "flash of wrong screen" (pehle login dikhna phir turant home pe switch ho jaana, ya vice versa) avoid hota hai.

app/_layout.tsx (auth guard)
import { useEffect } from "react";
import { Slot, useRouter, useSegments } from "expo-router";
import * as SplashScreen from "expo-splash-screen";
import { AuthProvider, useAuth } from "../context/AuthContext";

// Splash screen ko manually hide hone tak rokna — auto-hide off
SplashScreen.preventAutoHideAsync();

function RootLayoutNav() {
  const { user, isLoading } = useAuth();
  const segments = useSegments();
  const router = useRouter();

  useEffect(() => {
    if (isLoading) return; // auth state abhi resolve nahi hua, wait karo

    const inAuthGroup = segments[0] === "(auth)";

    if (!user && !inAuthGroup) {
      // user logged in nahi hai but protected area access kar raha hai
      router.replace("/(auth)/login");
    } else if (user && inAuthGroup) {
      // user login hai but login/signup screen dekh raha hai
      router.replace("/(app)/(tabs)");
    }

    // jab decision ho chuka, tab hi splash screen hataao
    SplashScreen.hideAsync();
  }, [user, isLoading, segments]);

  return <Slot />;
}

export default function RootLayout() {
  return (
    <AuthProvider>
      <RootLayoutNav />
    </AuthProvider>
  );
}

Notice karo — <Slot /> use kiya hai <Stack /> ki jagah, kyunki root level pe humein sirf child route render karna hai (auth ka decision hi navigator hai). Actual <Stack>/<Tabs> respective (auth)/_layout.tsx aur (app)/_layout.tsx mein define hoga.

🧠 Senior Dev Note

SplashScreen.hideAsync() ko useEffect ke andar, decision lene ke baad call karna critical hai. Agar tum ise turant component mount pe call kar doge (auth check se pehle), user ko ek split-second ke liye galat screen (login/home) dikh jaayegi, phir turant redirect hoga — isko hi "flash of wrong screen" bolte hain aur ye ek bahut common bug hai jo naye developers karte hain.

6. Role-Based Access Control (RBAC)

Auth guard ka extension — ab sirf "logged in hai ya nahi" nahi, balki "kis role ka user hai" bhi check karna hai. Pattern same rehta hai, bas condition mein role bhi add ho jaata hai.

app/(app)/_layout.tsx (role guard)
import { Redirect, Slot } from "expo-router";
import { useAuth } from "../../context/AuthContext";

export default function AppLayout() {
  const { user } = useAuth();

  // safety net — ideally root layout hi yahan tak nahi aane dega
  if (!user) return <Redirect href="/(auth)/login" />;

  return <Slot />;
}
app/(app)/admin/_layout.tsx (admin-only route group)
import { Redirect, Slot } from "expo-router";
import { useAuth } from "../../../context/AuthContext";

export default function AdminLayout() {
  const { user } = useAuth();

  if (user?.role !== "admin") {
    // unauthorized role → wapas home bhej do, admin screens tak pahunchne hi mat do
    return <Redirect href="/(app)/(tabs)" />;
  }

  return <Slot />;
}

Tab bar mein bhi role ke hisab se items conditionally render kar sakte ho — jaise "Admin" tab sirf admin role wale users ko dikhe:

conditional tab rendering
<Tabs.Screen
  name="admin"
  options={{
    title: "Admin",
    href: user?.role === "admin" ? undefined : null, // null = tab hide ho jaata hai
  }}
/>
⚠️ Gotcha

Sirf UI mein tab/button hide karna security nahi hai — ye sirf UX hai. Actual authorization hamesha backend API pe bhi enforce hona chahiye, kyunki client-side code ko kisi bhi reverse-engineer/proxy tool se bypass kiya ja sakta hai. Route guard + hidden tab sirf accidental access rokte hain, malicious access nahi.

7. Deep Linking

Deep linking ka matlab hai — ek external URL (custom scheme jaise myapp://product/42, ya universal/app link jaise https://myapp.com/product/42) directly app ke andar us specific screen tak navigate kare, jaise wo screen app ke andar se hi navigate ki gayi ho.

Ye internally kaise resolve hota hai

Expo Router ka poora linking config unified hai — jo route tree app/ se generate hota hai, wahi tree deep link resolution ke liye bhi use hota hai. Jab OS (iOS/Android) app ko ek URL ke saath launch/resume karta hai, React Navigation ka linking system us URL ko parse karke path segments nikalta hai, aur unhe exactly usi tarah route tree ke against match karta hai jaise ek in-app router.push() call match hoti. Matlab myapp://product/42 aur in-app router.push("/product/42") dono same code path se guzarte hain — app/product/[id].tsx render hoga aur id = "42" milega, chahe navigation kahin se bhi trigger hui ho.

app.json config

app.json
{
  "expo": {
    "scheme": "myapp",
    "ios": {
      "bundleIdentifier": "com.mycompany.myapp",
      "associatedDomains": ["applinks:myapp.com"]
    },
    "android": {
      "package": "com.mycompany.myapp",
      "intentFilters": [
        {
          "action": "VIEW",
          "data": [{ "scheme": "https", "host": "myapp.com" }],
          "category": ["BROWSABLE", "DEFAULT"]
        }
      ]
    }
  }
}

scheme custom scheme (myapp://) enable karta hai. Universal links (https://myapp.com/...) ke liye iOS pe associatedDomains chahiye (jo apple-app-site-association file host pe honi chahiye), aur Android pe intentFilters + assetlinks.json server pe honi chahiye — dono verify karte hain ki tumhare pass actually us domain ka ownership hai.

Testing deep links locally

🚨 Security Critical — Never Trust Deep Link Params

Deep link se aane wala koi bhi param untrusted input hai — bilkul waise hi jaise web pe query string untrusted hoti hai. Attacker bahut easily custom URL craft kar sakta hai (jaise message, email, ya malicious website ke through) aur usse tumhari app ko trigger kar sakta hai. Sabse common real-world mistake: deep link se ek arbitrary url param le ke seedha WebView mein load kar dena — myapp://open-webview?url=https://evil.com/phishing — isse attacker tumhari trusted app ke andar phishing page dikha sakta hai jo user ko legit lagega (kyunki app ka UI/chrome trusted hai). Hamesha: incoming params ko validate/sanitize karo, aur agar URL navigate karna hi hai toh strict allowlist against check karo (sirf apne known domains ko allow karo), IDs ko type/format check karo (jaise numeric product id), aur kabhi bhi deep link param ko directly kisi sensitive action (payment, account change) ko trigger karne ke liye mat use karo bina additional confirmation/auth ke.

safe deep link param validation example
const ALLOWED_HOSTS = ["myapp.com", "cdn.myapp.com"];

function isSafeUrl(rawUrl: string): boolean {
  try {
    const parsed = new URL(rawUrl);
    return parsed.protocol === "https:" && ALLOWED_HOSTS.includes(parsed.hostname);
  } catch {
    return false; // malformed URL — reject
  }
}

// usage in a deep-link-driven webview screen
if (!isSafeUrl(url)) {
  router.replace("/"); // silently bounce back, never load untrusted url
} else {
  setWebviewUrl(url);
}

8. Real-World Gotchas

⚠️ Infinite redirect loops

Agar tumhara auth guard logic dono conditions (logged-in check aur auth-group check) galat order mein likh do, ya segments dependency array mein missing ho, toh router.replace() baar-baar fire hota rehta hai aur app freeze/flicker karti hai. Hamesha ensure karo ki guard sirf tab fire ho jab actual mismatch ho (condition already-correct state pe dobara replace na kare), aur isLoading ka check sabse pehle ho.

⚠️ Deep link kaam nahi kar raha — but sirf dev build mein

Agar intentFilters (Android) ya associatedDomains (iOS) config karne ke baad bhi deep link kaam nahi kar raha, yaad rakho — Expo Go in native configs ko support nahi karta (kyunki Expo Go ek generic pre-built app hai jiska apna hi bundle ID/scheme hai). Ye configs sirf tab effective hote hain jab tum ek fresh native build banao — expo prebuild ya eas build ke through. Har baar jab in configs ko change karo, native project ko rebuild karna padega, sirf JS reload se kaam nahi chalega.

⚠️ Stale navigation state after hot reload

Fast Refresh/hot reload ke baad kabhi-kabhi navigation state "stuck" reh jaata hai — jaise ek screen jo already unmount ho chuki hai wo phir bhi navigation stack mein "ghost" entry ke roop mein dikhti hai, ya params purane values retain karte hain. Ye sirf dev-time cosmetic issue hai (production build mein nahi hota), lekin agar confusing lage toh full reload (r Metro terminal mein, ya simulator/device pe shake menu se "Reload") karke state reset kar do.

9. Advanced Deep-Dive — Beyond the Basics

Ab tak humne Expo Router ke "how to use" wale patterns dekhe. Is section mein hum wahi patterns internals level pe todenge — kyunki senior interview mein sirf "kaise likhte hain" nahi poocha jaata, "andar kya ho raha hai" poocha jaata hai. Ye 4 topics production RN apps mein sabse zyada confusion/bugs create karte hain: universal links ka actual verification mechanism, navigation state persistence ka deep-link ke saath interaction, auth-guard race conditions ka exact timeline, aur permission-based RBAC jab roles ki jagah granular permissions chahiye hote hain.

9.1 — Universal Links / App Links: exact verification mechanism

Section 7 mein humne dekha ki app.json mein associatedDomains (iOS) aur intentFilters (Android) daalte hain. Lekin ye config akela kaafi nahi hai — ye sirf app ko "batata" hai ki wo in domains ke liye universal link handler banna chahta hai. Actual proof of ownership ek alag mechanism se hota hai, aur yahi wo part hai jo interview mein depth test karta hai.

🧠 Senior Dev Note — Verification kyun zaroori hai

Agar sirf app.json ka config kaafi hota (bina server-side file verify kiye), toh koi bhi malicious app apne associatedDomains mein "applinks:instagram.com" daal ke Instagram ke links hijack kar sakta tha — bina Instagram ki domain pe kabhi access hue. Isliye Apple/Google ne ek server-side verification step mandatory kiya: OS khud us domain pe jaake ek well-known file fetch karke check karta hai ki domain ka actual owner ne is app ko explicitly authorize kiya hai. Ye ek security control hai — "sirf claim karna kaafi nahi, proof do."

iOS — apple-app-site-association (AASA): tumhe apne server pe (Vercel/Nginx/S3+CloudFront jo bhi) ek file host karni hoti hai https://yourdomain.com/.well-known/apple-app-site-association pe — notice karo, is file ka koi .json extension nahi hota, aur usse Content-Type: application/json header ke saath serve karna hota hai (kayi hosting providers default extension-less files ko galat content-type dete hain, isliye ye ek common gotcha hai).

.well-known/apple-app-site-association (JSON — asli file mein comments nahi chalte, ye sirf teaching ke liye hain)
{
  // "applinks" key — Apple universal links ke liye reserved top-level key hai
  "applinks": {
    // "details" — array of app configs jinhe is domain ke links handle karne ki permission hai
    "details": [
      {
        // appID = "." — TEAM_ID Apple Developer account se aata hai, isse spoof nahi kar sakte
        "appID": "AB12CD34EF.com.mycompany.myapp",
        // "paths" — kaunse URL paths is app ko route karne hain; "*" ka matlab sab paths
        "paths": [ "/product/*", "/reset-password/*" ]
      }
    ]
  }
}

Jab tum app install karte ho (ya OS periodically re-check karta hai), iOS khud Apple ke CDN (app-site-association.cdn-apple.com) ke through is file ko fetch karke cache kar leta hai. Us cached copy mein agar tumhare app ka appID list mein match karta hai, tabhi OS us domain ke links ko "universal link" treat karke seedha app open karega — warna wo link normal Safari mein khulega. Ye fetch-and-cache mechanism hi wo "verification" hai jo associatedDomains config ko akele se stronger banata hai.

Android — assetlinks.json: same idea, alag file. Host karna hota hai https://yourdomain.com/.well-known/assetlinks.json pe, aur isme tumhare app ke signing certificate ka SHA256 fingerprint hona chahiye — matlab jis keystore se tumne app sign kiya hai, uska hash yahan match hona chahiye.

.well-known/assetlinks.json (JSON — teaching comments)
[
  {
    // "relation" — batata hai ki kis type ki permission grant ho rahi hai app ko is domain ke against
    "relation": ["delegate_permission/common.handle_all_urls"],
    "target": {
      // namespace — Android app hone ka indicator
      "namespace": "android_app",
      // package_name — app.json ke android.package se match hona chahiye exactly
      "package_name": "com.mycompany.myapp",
      // sha256_cert_fingerprints — release keystore se generate hota hai (keytool se), yehi asli "proof" hai
      "sha256_cert_fingerprints": ["14:6D:E9:83:C5:73:06:50:D8:EE:B9:95:2F:34:FC:64:16:A0:83:42:E6:1D:BE:A8:8A:04:96:B2:3F:CF:44:E5"]
    }
  }
]
⚠️ Gotcha

Agar tum EAS Build use karte ho aur Play App Signing enabled hai, toh actual release signing key Google ke paas hota hai (tumhare upload key se alag) — matlab sha256_cert_fingerprints mein tumhe Google Play Console ke "App signing" tab se fingerprint nikal ke daalna hoga, apni local keystore se nahi. Ye ek bahut common "assetlinks match nahi ho raha" debugging trap hai.

9.2 — Navigation state persistence aur restoration

Expo Router ke neeche React Navigation ka NavigationContainer hi kaam kar raha hota hai, aur usme ek built-in capability hoti hai — navigation state ko serialize karke persist karna (jaise AsyncStorage mein), taaki app force-close hone ke baad bhi user wahin se resume kare jahan chhoda tha, instead of hamesha home screen pe restart hona.

app/_layout.tsx — navigation state persistence pattern
import AsyncStorage from "@react-native-async-storage/async-storage"; // persistence storage — state sensitive nahi hai isliye AsyncStorage theek hai (token ke liye nahi use karna, wo SecureStore mein)
import { useEffect, useState } from "react"; // state/ref hooks persistence flow manage karne ke liye

const NAV_STATE_KEY = "NAVIGATION_STATE_V1"; // versioned key — agar route tree structure change ho toh version bump karke purana corrupt state ignore kar sakte hain

function useNavigationPersistence() {
  const [isReady, setIsReady] = useState(false); // jab tak stored state load nahi ho jaata, navigator ko render hi mat karo
  const [initialState, setInitialState] = useState(); // AsyncStorage se load hua state yahan store hoga

  useEffect(() => {
    (async () => {
      try {
        const raw = await AsyncStorage.getItem(NAV_STATE_KEY); // disk se last-saved nav state fetch karo
        const state = raw ? JSON.parse(raw) : undefined; // agar kuch bhi save nahi hai toh undefined rakho (fresh start)
        if (state) setInitialState(state); // parsed state ko initial state ke roop mein set karo
      } finally {
        setIsReady(true); // parse fail ho ya succeed, ready mark karna zaroori hai warna app hamesha loading pe atki rahegi
      }
    })();
  }, []);

  const onStateChange = (state: unknown) =>
    AsyncStorage.setItem(NAV_STATE_KEY, JSON.stringify(state)); // har navigation change pe latest state disk pe likhte raho (debounce karna production mein better hai perf ke liye)

  return { isReady, initialState, onStateChange }; // root layout isse consume karke NavigationContainer/Slot ko wire karega
}
🚨 Security Critical — Deep link vs persisted state conflict

Ye interaction bahut logon ko surprise karta hai: agar app force-closed thi (persisted state disk pe hai) aur user ek deep link pe tap karke app open karta hai, toh race hoti hai — kaun jeetega, persisted state ya deep link? React Navigation ka default behavior: agar linking config ek incoming URL detect karta hai, toh wo usi URL se derived state ko priority deta hai, persisted initialState ko ignore kar diya jaata hai — lekin ye tumhe explicitly control karna chahiye, default pe blindly depend nahi karna chahiye, especially agar tumhara persisted state kisi auth-protected screen ko point karta ho. Sahi pattern: jab bhi ek incoming deep-link URL maujood ho, persisted state ko discard karo aur sirf link se navigate hone do — isse ek stale/wrong-permission screen restore hone ka risk khatam ho jaata hai (jaise koi purana admin-only screen state accidentally restore ho jaana kisi non-admin session mein).

deep link ko persisted state se priority dena
import * as Linking from "expo-linking"; // initial URL check karne ke liye (app kis URL se khula, agar khula)

async function getSafeInitialState(persisted: unknown) {
  const initialUrl = await Linking.getInitialURL(); // agar app ek deep link se cold-launch hua hai toh yahan URL milega, warna null
  if (initialUrl) {
    return undefined; // deep link maujood hai — persisted state ko explicitly discard karo, linking config ko navigate karne do
  }
  return persisted; // koi deep link nahi — normal case, persisted state restore karna safe hai
}

9.3 — Auth guard race condition: exact timeline

Section 5 mein humne "flash of wrong screen" fix dikhaya tha. Ab uski exact sequence samjho, kyunki interview mein "step by step batao" poocha jaata hai:

StepKya hota hai
1Native splash screen dikh rahi hai (OS-level, JS load hone se pehle hi visible)
2JS bundle load + execute hota hai — SplashScreen.preventAutoHideAsync() yahin call ho chuka hota hai, isliye native splash abhi bhi screen pe hold hai
3React tree mount hota hai — AuthProvider ka isLoading = true state ke saath render hota hai, SecureStore se token abhi fetch ho hi raha hai (async)
4Agar guard na ho: router ko pata nahi user logged in hai ya nahi, toh wo apna default/last-known route render kar sakta hai — ye galat screen frame ban sakta hai, bas splash ke peeche chhupa hua (abhi tak invisible hai kyunki native splash upar hai)
5SecureStore se token resolve hota hai (kuch milliseconds baad), isLoading = false ho jaata hai, useEffect fire hota hai jo actual redirect decide karta hai
6Redirect (agar zaroori ho) apply ho jaata hai — ab React tree "correct" state mein hai
7Tabhi jaake SplashScreen.hideAsync() call hota hai — native splash hatta hai aur user ko seedha final correct screen dikhti hai, koi flicker nahi

Bug tab aata hai jab step 4 ke baad hi (galat guess ke saath) splash hide kar di jaaye — user ko login screen ka ek frame dikhega, phir turant home pe switch hoga (ya vice versa). Isiliye loading spinner dikhana bhi galat fix hai agar wo content ke baad aata hai — asli fix ye hai ki galat content kabhi render hi na ho jab tak wo visible ho, aur splash ko exactly step 7 tak hold karna is guarantee ko deta hai, kyunki native splash ke peeche jo bhi render ho raha hai wo user ko dikhta hi nahi.

🧠 Senior Dev Note

Interview mein agar bola jaaye "spinner dikha do jab tak auth check ho raha hai" — ye partially sahi hai lekin subtle mismatch hai: spinner ka matlab hai content pehle se mount ho chuka hai aur uske upar spinner overlay hai — jo phir bhi ek flash create kar sakta hai agar layering sahi na ho. Sabse robust pattern hai native splash screen ko hi authoritative "loading gate" banana, kyunki wo pure JS render cycle se completely independent hai — usme kabhi bhi galat content leak nahi ho sakta.

9.4 — RBAC at scale: permission-based access control

Simple role check (user.role === "admin") chhoti apps ke liye theek hai, lekin jaise app grow karta hai (multiple teams, granular features — "can_edit_billing", "can_view_reports", "can_delete_users"), role string comparisons har jagah scatter ho jaate hain aur maintain karna nightmare ban jaata hai. Senior-level pattern: permission-based RBAC — roles ko permissions ke saath map karo (backend se aana chahiye, hardcode nahi), aur ek single centralized hook se sab jagah check karo.

hooks/usePermission.ts
import { useAuth } from "../context/AuthContext"; // current user + uske permissions yahan se milte hain

// Permission ek granular string hai, role nahi — backend hi decide karta hai kis role ko kaunsi permissions milengi
type Permission =
  | "can_edit_billing"
  | "can_view_reports"
  | "can_delete_users"
  | "can_access_admin_panel";

// Single source of truth — role → permissions mapping, ideally ye bhi backend se aata hai (JWT claims ya /me API)
export function usePermission(permission: Permission): boolean {
  const { user } = useAuth(); // current logged-in user context se nikalo
  if (!user) return false; // logged out user ke paas koi bhi permission nahi hoti

  // user.permissions backend se aata hai (array of granted permission strings) — isse role string kahin bhi compare nahi karna padta
  return user.permissions?.includes(permission) ?? false; // agar array missing ho toh safe default false
}
usage — kahin bhi component/layout mein
function BillingScreen() {
  const canEditBilling = usePermission("can_edit_billing"); // ek hi jagah se permission check — role string kahin nahi dikhta

  return (
    <View>
      <Text>Billing Details</Text>
      {canEditBilling && <Button title="Edit" onPress={openEditModal} />} // button sirf permission hone pe render hota hai
    </View>
  );
}
🧠 Senior Dev Note — Kyun ye scale karta hai

Role-based approach mein agar kal ko ek naya role "billing_manager" aata hai jo sirf billing edit kar sake but admin panel access na kare, toh tumhe har jagah role === "admin" || role === "billing_manager" jaisi conditions dhoondh ke update karni padti hain — error-prone aur scattered. Permission-based approach mein sirf backend pe naye role ki permissions define karni hain (["can_edit_billing"]), frontend code bilkul nahi badalta kyunki wo permission string se hi check kar raha hai, role name se nahi. Ye same principle hai jo large-scale systems (AWS IAM, Kubernetes RBAC) use karte hain — roles sirf permissions ka ek "bundle/label" hote hain, asli authorization decision permission granularity pe hoti hai.

10. 🎯 Interview Questions — Senior React Native Developer

Ye chapter security aur architecture heavy hai, isliye interview questions bhi usi weight ke hain. Neeche internals, security, trade-offs, aur real debugging scenarios ka mix hai — jaisa ek senior/staff RN round mein poocha jaata hai.

Q1. Universal link pe tap karne se leke correct screen render hone tak — step by step exact flow batao.

Answer: (1) User kisi link (Messages/email/browser) pe tap karta hai jo tumhare associatedDomains mein registered domain ka hai. (2) iOS check karta hai apne cached AASA verification data mein — agar tumhara app iss URL path ke liye authorized hai (verification pehle hi background mein ho chuki thi jab app install hui thi, actual network call is tap ke time nahi hoti). (3) Agar match hota hai, OS app ko launch/resume karta hai aur URL ko application(_:continue:restorationHandler:) (native side) ke through pass karta hai, jo Expo ke native module se React Native layer tak bubble hota hai. (4) expo-linking is URL ko parse karke path segments nikalta hai. (5) React Navigation ka linking config (jo Expo Router ne route tree se auto-generate kiya) is path ko match karke ek navigation state object banata hai — exactly wahi state jo router.push() call se bhi banta. (6) Agar root layout mein auth guard hai (jaisa humne Section 5 mein dekha), guard pehle apna decision le sakta hai (agar user logged-in nahi hai toh (auth)/login pe redirect, deep link ka target discard) — warna navigation state apply hoke matching screen component mount hoti hai, params (jaise id) us screen ko mil jaate hain.

Q2. Deep link se aaya hua ek url parameter directly WebView mein load karne mein kya risk hai? Concrete attack scenario do.

Answer: Deep link params untrusted user input hain — koi bhi attacker arbitrary URL craft karke SMS/email/WhatsApp/QR code ke through victim ko bhej sakta hai. Concrete attack: attacker myapp://open-webview?url=https://evil.com/bank-login-clone jaisa link bhejta hai. Agar app blindly is url ko WebView mein load kar deta hai, user ko lagta hai wo tumhari trusted app ke andar hi hai (app ka header/chrome/branding trusted dikhta hai) but actually ek phishing page dekh raha hai jo credentials churane ke liye bana hai. Agar WebView mein JS injection bhi allowed ho (injectedJavaScript, cookie sharing), toh attacker session hijacking ya XSS-style attacks bhi try kar sakta hai. Fix: hostname ko strict allowlist ke against validate karo (Section 7 ka isSafeUrl function), protocol https: hi allow karo, aur WebView ko sandboxed rakho (no arbitrary JS injection, restricted cookie access).

Q3. expo-secure-store mein token kyun rakhte hain, AsyncStorage mein kyun nahi? Kya ye poora token-theft problem solve kar deta hai?

Answer: AsyncStorage internally unencrypted SQLite/flat files use karta hai disk pe — koi bhi jo device ke filesystem tak physical/root access paa le (rooted device, jailbroken device, ADB backup extraction, ya malware jo sandboxing bypass kar de) us data ko plaintext mein padh sakta hai. expo-secure-store iOS pe Keychain aur Android pe Keystore use karta hai — hardware-backed encryption, aur OS-level access control jo sirf tumhari app (same signing identity) ko decrypt karne deta hai. Lekin ye poora solution nahi hai — agar device already compromised hai (malware ne UI automation/accessibility permissions le li hain, ya app khud memory-dump ke through token expose kar de jab wo runtime pe RAM mein hai), token phir bhi chhupaya nahi ja sakta. Isliye defense-in-depth chahiye: short-lived access tokens + refresh token rotation, SSL pinning (MITM se bachne ke liye), aur server-side pe suspicious session detection.

Q4. Deep link app khuli hone pe kaam karta hai but app killed state mein nahi — kya check karoge?

Answer: Ye ek classic "warm vs cold launch" bug hai. App already open hone pe Linking.addEventListener("url", ...) (runtime listener) fire hota hai, jo har naye incoming URL ko catch kar leta hai. Lekin jab app killed state mein hoti hai, tumhe Linking.getInitialURL() call karna padta hai app-launch ke time pe taaki wo URL nikal sako jisse app cold-launch hui thi — Expo Router ye internally handle karta hai, lekin agar tumne custom linking config likha hai ya kahin bahut jaldi navigation trigger kar diya (root layout mount hone se pehle hi), initial URL miss ho sakta hai. Check karne wali cheezein: (1) native config sahi hai ya nahi — Expo Go mein ye kabhi kaam nahi karega for custom schemes/universal links (Gotcha section mein dekha), fresh dev-build zaroori hai. (2) app.json mein intentFilters/associatedDomains rebuild ke baad hi effective hote hain — sirf JS reload se nahi. (3) Root layout ka guard logic isLoading resolve hone se pehle hi navigate toh nahi kar raha (initial URL ko overwrite kar sakta hai). (4) iOS pe AASA file cache-stale toh nahi (naya path add kiya but file update/CDN propagate nahi hui).

Q5. Navigation state persist karne ka pattern samjhao — aur ye deep linking ke saath kaise conflict kar sakta hai?

Answer: React Navigation/Expo Router ka underlying NavigationContainer onStateChange callback deta hai jisme current serialized nav state milta hai — usse AsyncStorage mein save karke, app restart pe initialState prop se restore kar sakte hain. Conflict tab hota hai jab app ek deep link se cold-launch hui ho aur disk pe purana persisted state bhi maujood ho — dono "initial state" ke candidate hain. Agar priority explicitly set nahi ki, framework/implementation defaults pe depend karna risky hai, especially agar persisted state kisi auth-sensitive screen ko point kare. Sahi approach: Linking.getInitialURL() check karo pehle — agar wo non-null hai, persisted state ko discard karo aur link ko priority do (Section 9.2 mein code example).

Q6. "Flash of wrong screen" bug ka exact root cause kya hai, aur loading spinner isko fully fix kyun nahi karta?

Answer: Root cause: JS bundle load hone ke turant baad, auth state abhi isLoading = true hoti hai (SecureStore se async fetch chal raha hai) — is window mein agar router ko koi definite decision nahi diya gaya, wo apna default/fallback route render kar sakta hai jo galat ho sakta hai (jaise logged-in user ko login screen dikhna, ek split second ke liye). Spinner ek alag layer render karke iss problem ko "mask" karta hai but underlying issue solve nahi karta — agar spinner ka mount/unmount timing thoda bhi off ho (race condition, animation ka ek frame), galat content ka glimpse phir bhi leak ho sakta hai. Robust fix: native SplashScreen.preventAutoHideAsync() se splash ko authoritative gate banao, aur hideAsync() sirf tabhi call karo jab auth decision definitively ho chuka ho (Section 9.3 ka 7-step timeline) — is tarah galat content kabhi user ko visible hi nahi hota, chahe render cycle mein kya bhi ho raha ho.

Q7. Role-based RBAC ki limitation kya hai jab app scale karta hai, aur permission-based approach kaise better hai?

Answer: Role-based check (role === "admin") mein role aur uske access ka mapping frontend code mein hardcoded/scattered ho jaata hai — jaise-jaise granular features badhte hain (billing edit, reports view, user delete — sab alag-alag), conditions role === "admin" || role === "manager" jaisi har jagah duplicate hone lagti hain, aur naya role add karne pe multiple files touch karne padte hain. Permission-based approach mein role sirf ek label hai — asli authorization decision granular permission strings ("can_edit_billing") pe hoti hai, jo backend se aati hain. Naya role add karna sirf backend config change hai, frontend code bilkul nahi badalta. Centralize karne ke liye ek single usePermission() hook use karo taaki koi bhi permission-check logic scattered na ho (Section 9.4).

Q8. Tumhare paas ek admin-only route group hai jo layout-level guard se protected hai. Kya ye kaafi hai security ke liye?

Answer: Nahi — client-side route guard sirf UX hai, security nahi. Koi bhi attacker app ke JS bundle ko decompile/patch kar sakta hai, ya API calls ko directly (bina app UI ke) Postman/curl se hit kar sakta hai, bypass karke guard ko completely skip kar sakta hai. Route guard sirf accidental access rokta hai (jaise normal user galti se admin URL type kar de) — malicious access sirf backend pe enforce hoke rukta hai: har admin API endpoint pe server-side authorization check hona chahiye (JWT claims verify karke, ya session lookup karke), regardless of what the client sent. Frontend guard + backend enforcement — dono zaroori hain, ek dusre ka substitute nahi.

Q9. Certificate pinning kya solve karta hai jo normal HTTPS/TLS nahi karta? Kab zaroori hai?

Answer: Normal HTTPS/TLS device ke trusted CA store pe depend karta hai — agar koi attacker ek malicious CA certificate device pe install karwa de (corporate MDM proxy, malicious wifi captive portal, ya user ko social-engineer karke "security certificate" install karwana), toh wo MITM proxy laga ke saara HTTPS traffic decrypt/read/modify kar sakta hai, kyunki device us fake CA ko "trusted" maanta hai. Certificate pinning is trust ko device ke CA store se hata ke app ke andar hardcoded kar deta hai — app sirf ek specific certificate/public-key ko hi accept karta hai, chahe device ka CA store kuch bhi kahe. Isse upar wala MITM attack fail ho jaata hai kyunki attacker ka certificate pinned value se match nahi karega. Zaroori hai fintech, banking, health apps ke liye jahan data-in-transit ka compromise directly financial/privacy damage kare. Trade-off: certificate rotation harder ho jaata hai (agar backend cert renew ho aur app update na ho, requests fail hone lagte hain) — isliye backup pins aur graceful update strategy chahiye hoti hai.

Q10. AASA file host karne ke baad bhi universal link Safari mein khul raha hai, app mein nahi — debug kaise karoge?

Answer: Systematic checklist: (1) File extension-less honi chahiye (apple-app-site-association, no .json) aur Content-Type: application/json ke saath serve honi chahiye — galat content-type (jaise text/plain) OS ko parse karne se rok sakta hai. (2) appID (TEAM_ID.bundleId) exact match hona chahiye — TEAM_ID Apple Developer account se lena, typo common hai. (3) paths array mein wo specific path included hai ya nahi jo tum test kar rahe ho. (4) iOS caches AASA file — naya deploy karne ke baad bhi turant reflect nahi hoga, device restart ya app reinstall se force-refresh karna padta hai testing ke waqt. (5) App ko Expo Go se nahi, ek fresh native build (eas build ya expo prebuild) se test kar rahe ho — Expo Go apna khud ka bundle ID use karta hai, tumhara associatedDomains config usme apply hi nahi hota. (6) Link ko directly type/paste karke test mat karo Notes app mein — universal links sirf tab trigger hote hain jab wo ek "trusted context" se aaye (jaise Messages, Mail) ya user ne khud tap kiya ho, address bar mein type karna kaam nahi karega.

Q11. push, replace, aur Redirect component mein kya farak hai — aur galat use se kya security/UX issue ban sakta hai?

Answer: router.push() stack mein naya entry add karta hai — back button se wapas ja sakte hain. router.replace() current entry ko hata ke naya daal deta hai — back se wapas nahi ja sakte. <Redirect /> ek declarative component hai jo render hote hi (render-time pe hi) replace-jaisa navigation trigger karta hai — layout guards ke andar imperative useEffect ki jagah use karna cleaner hota hai. Galat use ka security/UX issue: agar login ke baad push("/home") use kar do (replace ki jagah), login screen stack mein reh jaata hai — user back button dabaake login screen pe wapas pahunch sakta hai, jahan se agar session state stale ho (jaise ek dusra logged-out flow chal raha ho) confusing ya inconsistent UI state ban sakta hai. Isi tarah agar sensitive action ke baad (jaise password change) push use kiya, user back jaake dobara wahi form submit kar sakta hai — replace is class ke bugs ko structurally prevent karta hai.
