1. Kyun Accessibility Ek "Nice to Have" Nahi Hai

Bahut saare teams accessibility ko ek compliance checkbox ki tarah treat karte hain — "launch ke baad dekh lenge", ya "agar client ne specifically maanga toh add karenge". Ye mindset fundamentally galat hai, aur senior level pe iski wajah samajhna zaroori hai.

Ye ek legal/compliance issue se zyada, ek real user base hai

Accessibility ka matlab hai: vision-impaired users jo screen reader (VoiceOver on iOS, TalkBack on Android) use karke poora phone operate karte hain bina screen dekhe, motor-impaired users jo switch control ya external switches use karte hain touch gestures ke bajaye, aur low-vision users jinhe bada font size ya high contrast chahiye hota hai readable content ke liye. Ye koi "edge case" nahi hai — WHO ke estimates ke hisaab se duniya ki population ka significant percentage kisi na kisi form ki disability ke saath rehta hai, aur agar aapki app accessible nahi hai, ye users literally aapki app use hi nahi kar sakte — koi workaround nahi hai unke liye, jaise ek slow app ke liye "thoda wait kar lenge" wala workaround exist karta hai.

📌 Extra Context — Store policies aur legal requirements

Apple aur Google dono increasingly accessibility ko weigh kar rahe hain apne review guidelines aur discovery algorithms mein — Apple ka App Store "Accessibility Nutrition Labels" jaisi initiatives push kar raha hai. Kai countries (US mein ADA se related lawsuits, EU mein European Accessibility Act) mein digital products ke liye accessibility ab legal requirement ban rahi hai, especially agar aap public-facing services (banking, government, healthcare) bana rahe ho. Lekin ye chapter is legal angle pe focus nahi karega — senior framing ye hai ki legal requirement se pehle, ye simply sahi kaam hai aur ek real revenue-relevant user segment hai jo ignore ho raha hai.

Retrofit karna banane se kaafi zyada mehenga hai

Ye bilkul dark mode wale principle jaisa hai jo humne Chapter 3 mein dekha tha — agar aapne day-1 se semantic theme tokens use nahi kiye, dark mode retrofit karna 100+ files touch karne jaisa massive refactor ban jaata hai. Accessibility mein exactly wahi pattern hai: agar custom components bina accessibilityLabel, bina proper accessibilityRole ke bana diye gaye, aur gestures bina accessibility actions ke implement ho gaye, toh baad mein har ek component ko dobara khol ke retrofit karna padta hai — aur is process mein naye bugs introduce hone ka risk bhi hota hai. Jabki agar accessibility props shuru se hi component banate waqt add ho jaayein, incremental cost almost zero hai — ek button banate waqt accessibilityRole="button" add karna 2 second ka kaam hai.

🧠 Senior Dev Note

Jis tarah senior teams "security by design" ki baat karti hain (security ko afterthought na banao, architecture mein day-1 se socho), waise hi "accessibility by design" ek senior engineering mindset hai. Ek accessible component library banana, aur phir har feature team ko usi library ke top pe build karne dena — ye ek one-time investment hai jo poori app ko accessible bana deta hai bina har individual developer ko accessibility expert banaye. Isliye design system (Chapter 3) aur accessibility dono hath mein hath milake chalte hain — reusable, accessible primitives (Button, Card, Input) banao ek baar, sab jagah reuse karo.

2. Core Accessibility Props in React Native

React Native accessibility props ka ek set provide karta hai jo directly native accessibility APIs (iOS ka UIAccessibility, Android ka AccessibilityNodeInfo) pe map hote hain. Inhe samajhna zaroori hai kyunki ye "hint text" nahi hain — ye literally define karte hain ki screen reader user ko kya sunayi dega aur wo element kaise interact ho sakta hai.

PropKaam
accessibleBatata hai ki ye View ek single accessibility element hai — screen reader isse ek unit ki tarah focus karega, andar ke children ko separately announce nahi karega
accessibilityLabelWo text jo screen reader actually bolke sunayega — agar nahi diya, RN kabhi kabhi child Text content guess karta hai, lekin icon-only buttons ke liye ye zaroori hai
accessibilityHintExtra context ki ek line — "kya hoga agar user ye action perform kare" (e.g. "Double tap to delete this item")
accessibilityRoleElement ka semantic type — button, link, header, image, switch, etc. Screen reader isse batata hai user ko ki wo element kaisa "behave" karega
accessibilityStateCurrent state — disabled, selected, checked, busy, expanded — screen reader isse announce karta hai (e.g. "Add to cart, button, disabled")

Ab ek full example — ek properly accessible custom card component jo touchable bhi hai:

components/AccessibleProductCard.tsx
import { Pressable, View, Text, Image, StyleSheet } from 'react-native'; // core RN components

// Product card ke props — id, name, price, image aur ek out-of-stock flag
type ProductCardProps = {
  id: string;                 // unique product identifier
  name: string;               // product display name
  price: number;              // price in rupees, e.g. 1299
  imageUrl: string;           // product thumbnail URL
  inStock: boolean;           // stock availability — controls disabled state
  selected: boolean;          // whether this card is currently selected (e.g. in a comparison list)
  onPress: () => void;        // callback when card is tapped/activated
};

function AccessibleProductCard({ id, name, price, imageUrl, inStock, selected, onPress }: ProductCardProps) {
  return (
    <Pressable
      onPress={inStock ? onPress : undefined}          // out-of-stock hone pe press disable karo
      style={[styles.card, selected && styles.cardSelected]} // selected state ke liye visual highlight
      accessible                                             // pura card ek single accessibility element ban jaaye, andar ki 3 Text/Image alag se announce na ho
      accessibilityRole="button"                              // screen reader batayega "button" — user samajh jaayega ye tap-able hai
      accessibilityLabel={`${name}, price ₹${price}`}         // actual spoken text — image alt-text jaisa concept
      accessibilityHint={inStock ? 'Double tap to view product details' : undefined} // extra context sirf jab actionable ho
      accessibilityState={{ disabled: !inStock, selected }} // screen reader "disabled"/"selected" bhi bolega automatically
    >
      {/* Ye Image decorative hai (info already accessibilityLabel mein hai), isliye screen reader se hide karo */}
      <Image
        source={{ uri: imageUrl }}                        // product image ka remote URL
        style={styles.thumbnail}                          // fixed thumbnail size
        importantForAccessibility="no"                     // Android-specific — is image ko accessibility tree se poori tarah hata do (duplicate announcement avoid)
        accessibilityElementsHidden                       // iOS-specific equivalent — VoiceOver ko is image ko skip karne bolo
      />

      {/* Parent card pe accessible=true set hai, isliye ye Text elements individually focus nahi honge — */}
      {/* screen reader ke liye ye sirf visual content hain, spoken text upar accessibilityLabel se aa raha hai */}
      <Text style={styles.name} numberOfLines={2}>{name}</Text>
      <Text style={styles.price}>₹{price}</Text>

      {!inStock && (
        {/* Visual "out of stock" badge — spoken info already accessibilityState.disabled mein hai */}
        <View style={styles.outOfStockBadge}>
          <Text style={styles.outOfStockText}>Out of Stock</Text>
        </View>
      )}
    </Pressable>
  );
}

const styles = StyleSheet.create({
  card: { borderRadius: 12, padding: 12, backgroundColor: '#262524', gap: 6 }, // base card look
  cardSelected: { borderWidth: 2, borderColor: '#d97757' },              // visual selected indicator
  thumbnail: { width: '100%', height: 140, borderRadius: 8 },      // thumbnail sizing
  name: { color: '#e8e4dd', fontSize: 14, fontWeight: '600' },       // product name styling
  price: { color: '#d97757', fontSize: 15, fontWeight: '700' },      // price styling
  outOfStockBadge: { backgroundColor: '#d9756c22', borderRadius: 6, padding: 4 }, // out-of-stock badge bg
  outOfStockText: { color: '#d9756c', fontSize: 11, fontWeight: '600' }, // out-of-stock text
});

export default AccessibleProductCard;                                   // export the component

Screen reader user ke perspective se, jab wo is card pe focus karega, VoiceOver/TalkBack bolega kuch is tarah: "Nike Air Max, price ₹4999, button. Double tap to view product details." — pura ek clean single announcement, na ki 4 alag announcements (image, name text, price text, badge) jo confusing aur redundant hote. Agar out of stock hai, ye "Nike Air Max, price ₹4999, button, disabled" bolega, aur hint skip ho jaayega kyunki koi action possible nahi hai.

⚠️ Gotcha — accessible aur nested interactive elements

accessible={'{'}true{'}'} set karne ka side effect ye hai ki iske andar agar koi separate interactive element hai (jaise ek "Remove" button card ke andar), wo apna khud ka accessibility focus nahi paayega — pura parent ek hi unit ban jaata hai. Agar card ke andar multiple independently tappable actions chahiye (e.g. product card + ek chhota wishlist heart icon jo apna khud ka tap target hai), toh accessible parent pe mat lagao — instead har interactive sub-element ko apna khud ka accessibilityRole/accessibilityLabel do, aur parent ko plain View rehne do.

3. Testing with a Real Screen Reader

Ye sabse underrated senior practice hai: actually VoiceOver ya TalkBack on karke, screen band karke ya aankh band karke, apni app navigate karna. Ye "extra QA step" nahi hai — ye the real test hai. Automated linting tools sirf ek fraction of issues catch kar sakte hain; asli experience sirf manually navigate karke pata chalta hai.

Device pe screen reader on karna

PlatformKaise on karoBasic gestures
iOS (VoiceOver)Settings → Accessibility → VoiceOver, ya Siri se "Hey Siri, turn on VoiceOver"Swipe right/left = next/previous element, double-tap = activate, 3-finger swipe = scroll
Android (TalkBack)Settings → Accessibility → TalkBack, ya volume-key shortcut (dono volume buttons hold)Swipe right/left = next/previous, double-tap = activate, 2-finger swipe = scroll
🧠 Senior Dev Note — screen off karke test karo

Ek powerful practice: iOS pe VoiceOver on karke phone ka screen off kar do (side button dabao) — VoiceOver kaam karta rehta hai, screen totally black hai. Ab apni app navigate karke dekho: kya aap sirf audio se samajh sakte ho ki aap kahan ho, kya tap kar rahe ho, kya feedback mil raha hai. Ye exactly wo experience hai jo ek blind user roz face karta hai. Agar aap khud confuse ho jaate ho ki "main kis screen pe hoon", ya kaunsa button focus mein hai, samajh lo real users bhi confuse honge.

Automated linters — useful, lekin partial coverage

eslint-plugin-react-native-a11y jaisa ek ESLint plugin static analysis karke basic issues catch kar sakta hai — jaise ek TouchableOpacity jispe koi accessibilityLabel nahi hai, ya ek icon-only button jispe koi text alternative nahi hai. Ye CI mein wire karna valuable hai (Chapter 7 ke testing pipeline mein ek extra lint step ki tarah), kyunki ye "obvious misses" ko commit hone se pehle hi pakad leta hai.

Lekin linters sirf static, syntactic checks kar sakte hain — wo ye nahi bata sakte:

  • Focus order — kya screen reader logically top-to-bottom, left-to-right navigate kar raha hai, ya kisi absolutely-positioned overlay ki wajah se focus order illogical hai (jump kar raha hai)
  • Redundant ya missing context — kya ek label sirf "Button" bol raha hai, jo technically present hai (linter pass karega) lekin useless hai user ke liye
  • Custom gesture components — jaise ek swipe-to-delete row jo visually kaam karti hai lekin screen reader user ke paas koi tareeka hi nahi hai swipe gesture perform karne ka (Advanced Deep-Dive mein detail se)
  • Live announcements — jab koi async action complete hoti hai (e.g. "Item added to cart"), kya user ko wo pata chalta hai ya nahi bina screen dekhe
💡 Quick Tip

Practical senior workflow: naya feature ship karne se pehle, kam se kam ek baar poora flow VoiceOver/ TalkBack on karke navigate karo end-to-end (signup → checkout jaisa critical path). Isse "accessibility QA" apna khud ka dedicated pass ban jaata hai, na ki visual QA ka side-effect (jo Section 9 mein detail se discuss karenge).

4. Dynamic Font Scaling and Layout Resilience

iOS aur Android dono OS-level "text size" setting dete hain (Settings → Display/Accessibility → Text Size), jo low-vision users ke liye critical hai. React Native by default har fontSize ko is OS setting ke hisaab se automatically scale karta hai — allowFontScaling prop default true hai.

🚨 Critical Anti-Pattern — allowFontScaling={'{'}false{'}'}

Bahut saari teams jab bada font size layout ko "todta" hai (text overflow ho raha hai, cards misaligned dikh rahe hain), quick fix ke roop mein allowFontScaling={'{'}false{'}'} laga dete hain — matlab "chalo text ko fix size pe force kar dete hain, layout waisa hi rahega". Ye ek genuine accessibility violation hai, sirf design compromise nahi — aapne effectively wo user jisne apne phone mein bada font isliye set kiya hai kyunki wo chhota text padh nahi paata, uske liye text ko unreadable bana diya. Sahi fix ye hai ki layout ko is tarah design karo ki wo bade font ke saath bhi gracefully reflow ho — text overflow ho, wrap ho, container grow ho — clip ya force-shrink na ho.

Layout ko resilient banana — Chapter 3 ke Flexbox principles wapas kaam aa rahe hain

Yaad karo Chapter 3 mein humne dekha tha ki fixed pixel heights waale containers text overflow/clip kar sakte hain jab font scale badhta hai. Solution wahi hai: fixed heights avoid karo text-containing views pe, flexGrow/minHeight use karo instead of height, aur numberOfLines ko thoughtfully use karo (truncate karna theek hai kuch jagah, lekin critical info — jaise price, error messages — kabhi truncate mat karo).

components/ResilientListItem.tsx
import { View, Text, StyleSheet } from 'react-native'; // core components

// Ek list item jo bade font-scale ke saath bhi break nahi hoga
function ResilientListItem({ title, subtitle }: { title: string; subtitle: string }) {
  return (
    {/* height explicitly set NAHI hai — minHeight use kiya taaki content grow kar sake */}
    <View style={styles.row}>
      {/* allowFontScaling explicitly true hi hai (default), yahan sirf clarity ke liye likha */}
      <Text style={styles.title} allowFontScaling // OS font scale respect karo — kabhi false mat karo
      >
        {title}
      </Text>
      {/* subtitle truncate ho sakta hai — non-critical info, lekin numberOfLines flexible hai */}
      <Text style={styles.subtitle} numberOfLines={2} // 2 lines allow karo, 1 se bada font ke saath text turant cut ho jaata
      >
        {subtitle}
      </Text>
    </View>
  );
}

const styles = StyleSheet.create({
  row: {
    minHeight: 64,          // GUIDELINE height, hard limit nahi — content isse bada ho sakta hai
    paddingVertical: 10,    // breathing room jo bade text ke saath bhi maintain rahega
    justifyContent: 'center', // content vertically center, chahe row grow ho ya na ho
    gap: 4,                // title-subtitle ke beech consistent spacing
  },
  title: { fontSize: 16, fontWeight: '600', color: '#e8e4dd' }, // fixed pixel fontSize theek hai — RN isse khud scale karega
  subtitle: { fontSize: 13, color: '#b3aca1' }, // secondary text color
});
💡 Quick Tip

Test karne ka fastest tareeka: iOS Settings → Accessibility → Display & Text Size → Larger Text → slider ko poora right maximum pe le jao ("Larger Accessibility Sizes" range), phir apni app kholo. Agar kahin text clip ho raha hai, do lines ek dusre pe overlap ho rahi hain, ya buttons ka text cut ho raha hai — ye pakadne ka sabse fast tareeka yahi hai, code review se pehle hi.

5. Color Contrast and Visual Accessibility

WCAG (Web Content Accessibility Guidelines) ek contrast ratio standard define karta hai jo mobile apps pe bhi apply hota hai as best practice: normal text ke liye kam se kam 4.5:1 contrast ratio (text color vs background color), aur large text (18pt+ ya bold 14pt+) ke liye 3:1. Ye ek poori spec hai (AA vs AAA levels), lekin senior level pe itna kaafi hai: agar aapka text apne background ke against low-contrast dikh raha hai (jaise light gray text light background pe), low-vision users ke liye ye padhna mushkil ya impossible ho jaata hai.

Sirf color pe relying karna — colorblind users ke liye fails

Ek bahut common mistake: status ko sirf color se convey karna — jaise ek "success" row green text mein aur "error" row red text mein, without koi aur visual indicator (icon, label, shape). Red-green color blindness (deuteranopia/protanopia) sabse common form hai — aisi apps mein ye users literally difference nahi dekh sakte red aur green ke beech.

components/StatusRow.tsx
import { View, Text, StyleSheet } from 'react-native'; // core components

type Status = 'success' | 'error'; // only two possible statuses in this example

// ❌ GALAT — sirf color se status convey ho raha hai, colorblind user ko difference nahi dikhega
function BadStatusRow({ status, message }: { status: Status; message: string }) {
  return (
    <Text style={{ color: status === 'success' ? '#7fb069' : '#d9756c' }}>
      {message}
    </Text>
  );
}

// ✅ SAHI — color + icon + accessibilityLabel teeno mil ke redundant signal dete hain
function GoodStatusRow({ status, message }: { status: Status; message: string }) {
  const isSuccess = status === 'success';                    // derive boolean once for readability
  return (
    <View
      style={styles.row}
      accessibilityRole="text"                                // screen reader ko batao ye ek informational text block hai
      accessibilityLabel={`${isSuccess ? 'Success' : 'Error'}: ${message}`} // status word explicitly spoken, na ki sirf color implied
    >
      {/* Icon shape khud ek non-color signal hai — checkmark vs cross, colorblind users bhi shape se differentiate kar sakte hain */}
      <Text style={styles.icon}>{isSuccess ? '✓' : '✕'}</Text>
      {/* Color abhi bhi use ho raha hai — sighted users ke liye quick visual scan ke liye, lekin ab ye SOLE indicator nahi hai */}
      <Text style={[styles.message, { color: isSuccess ? '#7fb069' : '#d9756c' }]}>
        {message}
      </Text>
    </View>
  );
}

const styles = StyleSheet.create({
  row: { flexDirection: 'row', alignItems: 'center', gap: 6 }, // icon aur text ek row mein side by side
  icon: { fontSize: 14, fontWeight: '700' },                    // icon sizing
  message: { fontSize: 14 },                                     // message text sizing
});
💡 Quick Tip — contrast testing tools

Design phase mein hi contrast check karo — Figma plugins jaise "Stark" ya "Able" directly design file ke andar contrast ratio calculate karke dikhate hain, aur automatically flag karte hain agar koi text/background combo WCAG AA fail kar raha hai. Ye check karna developer ke haath mein aane se pehle, design stage pe hi ho jaana chahiye — retrofit karna (jaisa humne dark mode aur accessibility dono mein dekha) hamesha zyada expensive hota hai.

6. Internationalization (i18n) Fundamentals

i18n (internationalization) ka core architecture principle simple hai: koi bhi user-facing string kabhi directly component mein hardcode nahi honi chahiye. Har string ek translation file (ya "resource bundle") se aani chahiye, key ke through referenced. Isse naya language add karna sirf ek naya translation file add karne jaisa ho jaata hai — koi component code touch nahi karna padta.

Standard approach React Native/Expo ecosystem mein i18next plus react-i18next hai (web se hi popular hai, RN mein bhi first-class support hai), combined with expo-localization jo device ka current locale/language detect karta hai.

Translation file structure

project folder structure
src/
  i18n/                          // saara i18n-related code ek jagah — easy to find aur maintain
    index.ts                     // i18next setup/config — app entry point pe ek baar import hota hai
    locales/                     // har language ki apni JSON file, flat aur predictable structure
      en.json                    // English — hamesha "source of truth"/fallback language hoti hai
      hi.json                    // Hindi translations — same keys as en.json, translated values
      ar.json                    // Arabic translations — RTL language, Section 7 mein iska layout impact dekhenge
src/i18n/locales/en.json
{
  // "common" namespace — buttons/labels jo poori app mein reuse hote hain
  "common": {
    "save": "Save",                          // generic save button label
    "cancel": "Cancel",                      // generic cancel button label
    "loading": "Loading..."                  // generic loading indicator text
  },
  // "cart" namespace — screen-specific strings, grouped for clarity
  "cart": {
    "title": "Your Cart",                    // cart screen header
    "empty": "Your cart is empty",          // empty state message
    "itemCount_one": "{{count}} item",      // i18next pluralization convention — singular form (count === 1)
    "itemCount_other": "{{count}} items"     // plural form (count !== 1) — Section 8 mein detail se explain karenge
  }
}

(Note: real JSON comments support nahi karta — upar wale JSON block mein teaching-purpose ke liye comments dikhaye gaye hain samajhne ke liye, actual en.json file mein ye comments nahi honge, sirf valid JSON hoga.)

i18next setup

src/i18n/index.ts
import i18n from 'i18next';                                    // core i18next library
import { initReactI18next } from 'react-i18next';                // React bindings — hooks jaise useTranslation
import * as Localization from 'expo-localization';          // device locale detect karne ke liye

import en from './locales/en.json';                          // English translations bundle
import hi from './locales/hi.json';                          // Hindi translations bundle
import ar from './locales/ar.json';                          // Arabic translations bundle

// Device ki current locales list — first entry usually user ka preferred language hai
const deviceLocales = Localization.getLocales();               // e.g. [{ languageCode: 'hi', ... }]
const deviceLanguage = deviceLocales[0]?.languageCode ?? 'en'; // fallback to English agar detect na ho paaye

i18n
  .use(initReactI18next)                                    // i18next ko React ke saath wire karo (hooks enable karta hai)
  .init({
    resources: {                                        // saare available languages ka translation bundle
      en: { translation: en },                             // 'translation' default namespace hai i18next ka
      hi: { translation: hi },
      ar: { translation: ar },
    },
    lng: deviceLanguage,                                 // initial language — device ki setting se auto-detect
    fallbackLng: 'en',                                // agar koi key kisi language mein missing ho, English use karo
    interpolation: {
      escapeValue: false,                              // React already XSS-safe hai (JSX auto-escapes), i18next ki extra escaping ki zaroorat nahi
    },
    compatibilityJSON: 'v4',                            // RN environment ke liye recommended JSON compatibility mode
  });

export default i18n;                                             // app entry point (App.tsx/_layout.tsx) mein ek baar import karo taaki init chale

useTranslation hook ka usage

screens/CartScreen.tsx
import { View, Text } from 'react-native';                     // core components
import { useTranslation } from 'react-i18next';                // hook jo current language ke translations deta hai

function CartScreen({ itemCount }: { itemCount: number }) {
  const { t } = useTranslation();                            // 't' function — key deke translated string nikalta hai

  return (
    <View>
      {/* Dot notation se nested JSON key access ho raha hai — "cart.title" */}
      <Text>{t('cart.title')}</Text>

      {itemCount === 0 ? (
        {/* Empty state — simple key lookup, no interpolation needed */}
        <Text>{t('cart.empty')}</Text>
      ) : (
        {/* i18next automatically 'itemCount_one' vs 'itemCount_other' choose karega count ke basis pe */}
        <Text>{t('cart.itemCount', { count: itemCount })}</Text>
      )}
    </View>
  );
}

export default CartScreen;                                          // export the screen component
🧠 Senior Dev Note

Naming convention itemCount_one/itemCount_other koi arbitrary choice nahi hai — ye i18next ka plural rules convention hai jo CLDR (Unicode Common Locale Data Repository) standard follow karta hai. Har language apne plural categories khud define karti hai (English mein sirf 2: one/other; Arabic mein 6: zero/one/two/few/many/other), aur i18next automatically sahi form select karta hai based on the active language's rules — hum is detail ko Section 8 mein expand karenge.

7. RTL (Right-to-Left) Layout Support

Arabic, Hebrew, Urdu jaisi languages RTL (right-to-left) reading direction follow karti hain — matlab poora UI mirror hona chahiye: navigation back-arrow left ki jagah right pe, text right-aligned, list items right se start ho. React Native mein iske liye built-in support hai — lekin sirf tab jab aapne styles correctly likhe hon.

I18nManager aur automatic mirroring

src/i18n/rtl.ts
import { I18nManager } from 'react-native';    // RN ka RTL management API
import * as Updates from 'expo-updates';      // RTL switch ke baad app reload karne ke liye

// Ye function tab call hoga jab user language switch karke RTL language (jaise Arabic) select kare
export async function applyRTLIfNeeded(languageCode: string) {
  const rtlLanguages = ['ar', 'he', 'ur'];             // known RTL language codes — Arabic, Hebrew, Urdu
  const shouldBeRTL = rtlLanguages.includes(languageCode); // determine target direction

  if (I18nManager.isRTL !== shouldBeRTL) {                // sirf tab kuch karo jab actual change ho raha ho
    I18nManager.allowRTL(shouldBeRTL);                     // RTL support ko app-level pe enable/disable karo
    I18nManager.forceRTL(shouldBeRTL);                     // actual layout direction ko force flip karo

    // CRITICAL: I18nManager.forceRTL turant effect nahi karta — native layout engine ko
    // fresh initialize hona padta hai, isliye app reload zaroori hai
    await Updates.reloadAsync();                          // poori app ko reload karo taaki new direction se render ho
  }
}
⚠️ Gotcha — RTL switch ke liye app restart chahiye

I18nManager.forceRTL() call karne ke turant baad layout apne aap flip nahi hota — RN ki native layout engine (Yoga) sirf app launch ke time pe RTL/LTR direction decide karti hai. Isliye har production app RTL toggle hone pe user ko ek reload/restart karwati hai (jaisa upar expo-updates ke reloadAsync() se dikhaya). Ye ek one-time UX hiccup hai jo language-switch flow mein account karna zaroori hai — agar aap ye miss karte ho, user language switch karega lekin layout wahi LTR rahega jab tak wo manually app band-khol na kare.

Logical properties: start/end vs hardcoded left/right

Jab RTL active hota hai, Flexbox automatically flexDirection: 'row' ko mirror kar deta hai (row ka start ab right side hai, left nahi) — lekin sirf agar aap logical properties use kar rahe ho. Agar aapne kahin explicitly marginLeft/paddingRight/ left: 10 hardcode kiya hai, RN ko pata nahi chalega ki ye "start" ke liye hai ya literally "left" ke liye — wo hardcoded value ko as-is treat karega, aur RTL mein layout completely broken dikhega (spacing galat side pe chali jaayegi).

components/RTLSafeRow.tsx
import { View, Text, StyleSheet, Image } from 'react-native'; // core components

// Ek notification row — icon left mein (LTR) / right mein (RTL), text uske baad
function RTLSafeRow({ iconUrl, message }: { iconUrl: string; message: string }) {
  return (
    {/* flexDirection: 'row' RTL mein RN automatically mirror karega — icon apne aap right pe chala jaayega */}
    <View style={styles.row}>
      <Image source={{ uri: iconUrl }} style={styles.icon} />
      <Text style={styles.message}>{message}</Text>
    </View>
  );
}

const styles = StyleSheet.create({
  row: { flexDirection: 'row', alignItems: 'center', padding: 12 }, // RN RTL mode mein isse automatically mirror karega
  icon: {
    width: 32, height: 32, borderRadius: 16,
    marginEnd: 10,        // ✅ 'marginEnd' — LTR mein ye right margin hai, RTL mein ye automatically left margin ban jaata hai
    // marginRight: 10,           // ❌ agar ye likha hota, RTL mein bhi hamesha "right" hi rehta — galat side
  },
  message: { flex: 1, color: '#e8e4dd', textAlign: 'left' }, // note: better hai 'start' bhi consider karna kuch cases mein, neeche dekho
});

Ek bahut common real-world mistake hai: team apni app poore development cycle mein sirf LTR (English) mein test karti hai, sab jagah marginLeft/marginRight hardcode karke likhti hai kyunki "abhi toh koi RTL language support nahi kar rahe" — aur phir jab 6 months baad Arabic market expand hone ka decision hota hai, poori codebase mein ye hardcoded properties dhoondh dhoondh ke logical properties se replace karni padti hain. Agar aap already jaante ho ki future mein RTL language support karna pad sakta hai (Middle East market koi bhi consumer app ke liye realistic hai), logical properties day-1 se use karna ek chhoti si habit hai jo bahut bada future refactor bacha deti hai.

8. Pluralization and Locale-Aware Formatting

Pluralization: "1 item" vs "2 items" is not just an English swap

English mein plural rule simple hai: 1 = singular, baaki sab = plural. Lekin ye universal nahi hai. Kuch examples:

  • Russian — teen plural forms hain (one, few, many) based on complex number-ending rules
  • Arabic — chhe forms hain: zero, one, two, few, many, other — each apne specific number ranges ke liye
  • Japanese/Chinese — koi grammatical plural nahi hai — same word chahe count kuch bhi ho

Agar aap sirf string concatenation karke plurals handle karte ho (jaise count + " item" + (count !== 1 ? "s" : "")), ye sirf English ke liye kaam karta hai — kisi bhi doosri language mein ye completely galat output dega. Isiliye i18next jaisi library _one/_other (aur zyada complex languages ke liye _zero/_two/_few/_many) suffix convention follow karti hai — ye CLDR plural rules ke against automatically resolve hota hai based on active language, developer ko manually if/else likhne ki zaroorat nahi.

src/i18n/locales/ar.json (partial — Arabic ke saare plural forms)
{
  "cart": {
    "itemCount_zero": "لا توجد عناصر",     // count === 0 ke liye
    "itemCount_one": "عنصر واحد",        // count === 1 ke liye
    "itemCount_two": "عنصران",           // count === 2 ke liye — Arabic mein "dual" ek alag grammatical form hai
    "itemCount_few": "{{count}} عناصر",  // 3-10 range (approx) ke liye — CLDR rule Arabic ke liye ye range define karta hai
    "itemCount_many": "{{count}} عنصرًا", // 11-99 range (approx) ke liye
    "itemCount_other": "{{count}} عنصر"   // baaki sab cases ke liye — i18next fallback
  }
}

Developer ke code mein kuch change nahi karna padta — wahi t('cart.itemCount', {'{'} count {'}'}) call, i18next khud CLDR rules use karke sahi key resolve karta hai based on the active language. Ye poore i18n architecture ka core value hai: business logic language-agnostic rehta hai, saara language-specific complexity translation layer mein isolated hai.

Locale-aware date, number aur currency formatting

Sirf text translate karna kaafi nahi hai — numbers, dates, aur currency bhi region ke hisaab se differently format hote hain. Example: 1,234.56 (US format) vs 1.234,56 (many European countries) — same number, different separator convention. JavaScript ka built-in Intl API (Hermes engine mein RN pe supported hai) ye handle karta hai bina kisi extra library ke.

utils/formatters.ts
// ----------------------------------------------------------------
// formatCurrency — locale ke hisaab se currency format karta hai
// ----------------------------------------------------------------
export function formatCurrency(amount: number, locale: string, currency: string) {
  return new Intl.NumberFormat(locale, {         // locale-specific formatter banao, e.g. 'hi-IN', 'ar-AE', 'en-US'
    style: 'currency',                       // currency mode — symbol/grouping/decimal rules apply honge
    currency,                                // ISO currency code — e.g. 'INR', 'USD', 'AED'
  }).format(amount);                          // actual formatted string return karo
}

// ----------------------------------------------------------------
// formatDate — locale ke hisaab se date format karta hai
// ----------------------------------------------------------------
export function formatDate(date: Date, locale: string) {
  return new Intl.DateTimeFormat(locale, {       // locale-specific date formatter
    year: 'numeric',                         // e.g. 2026
    month: 'long',                           // e.g. "August" (en) ya "أغسطس" (ar)
    day: 'numeric',                          // e.g. 9
  }).format(date);                            // automatically sahi order/separators use karega (DD/MM vs MM/DD, etc.)
}

// Example usage:
// formatCurrency(1299, 'en-IN', 'INR')  ->  "₹1,299.00"
// formatCurrency(1299, 'ar-AE', 'AED')  ->  "١٬٢٩٩٫٠٠ د.إ.‏" (Arabic numerals + symbol placement)
// formatDate(new Date(), 'en-US')       ->  "August 9, 2026"
// formatDate(new Date(), 'hi-IN')       ->  "9 अगस्त 2026"
📌 Extra Context

Intl API RN mein Hermes engine ke through natively supported hai (RN 0.66+ recent versions mein full locale data bundled hai, purane versions mein kabhi kabhi polyfill — @formatjs/intl-* — chahiye padta tha specific locale data ke liye). Agar aap complex date manipulation bhi chahte ho (not just formatting — timezone math, relative time jaise "2 din pehle"), date-fns ya dayjs apne locale plugins ke saath is Intl foundation ke upar additional convenience layer provide karte hain.

9. Real-World Gotchas

⚠️ Gotcha #1 — String concatenation breaks word order

Ek common anti-pattern: sentence ko multiple translated pieces jodke banana — jaise t('userLikedYour') + ' ' + t('post') to build "User liked your post". Ye English mein kaam kar jaata hai, lekin languages jinka word order alag hai (verb-object order different hai), ye grammatically broken sentence generate karega. Sahi approach: poora sentence ek hi translation key mein rakho with interpolation — t('userLikedYourPost', {'{'} name: 'Sharad' {'}'}) jahan translation file mein poora "{'{'}{'{'}name{'}'}{'}'} liked your post" jaisa complete sentence template define ho. Isse translator ko poora context milta hai aur word order sahi rehta hai har language mein.

⚠️ Gotcha #2 — Text embedded in images/icons

Ek bahut common oversight: marketing team se reused images/banners (jaise ek promotional banner jispe "50% OFF" text image ke andar hi baked-in hai, separate Text component nahi hai) app mein directly use ho jaate hain. Ye text translate nahi ho sakta — koi bhi translation key isse fix nahi karegi kyunki text pixel data hai, string nahi. Jab app kisi doosre market mein launch ho, ye banners English mein hi reh jaate hain jabki poori app translated hai — ek jarring inconsistency. Solution: banners/promotional images ko hamesha layered banao (background image + overlay Text component separately), taaki text translatable rahe.

🚨 Gotcha #3 — Accessibility regressions invisible in visual QA

Ye sabse dangerous gotcha hai kyunki ye silently ship ho jaata hai: ek screen visually perfectly fine dikhti hai (design QA pass ho jaata hai, screenshot tests pass ho jaate hain), lekin screen reader ke liye completely broken hai — jaise ek naya icon button add hua bina accessibilityLabel ke, ya ek custom modal jo focus trap nahi kar raha (screen reader user modal ke "peeche" ke content ko bhi focus kar sakta hai jabki modal open hai). Chuki normal visual QA isse kabhi pakad hi nahi sakta (sab kuch visually sahi hai), accessibility ko apna khud ka dedicated QA pass chahiye — jaisa Section 3 mein discuss kiya, screen reader on karke manually navigate karna, na ki sirf visual checklist tick karna.

⚠️ Gotcha #4 — RTL testing as an afterthought

Bahut si teams RTL support "add" toh kar deti hain (i18n library setup, translation files) lekin kabhi actually Arabic/Hebrew locale set karke app test nahi karti until ek real user production mein broken UI report karta hai — icons galat side pe, text overlapping, swipe gestures ulti direction mein kaam kar rahe. RTL ek genuinely different layout mode hai, sirf "translation ka extension" nahi — isliye isko apna khud ka QA checklist item banao: har major release se pehle, app ko I18nManager.forceRTL(true) karke ek baar poora navigate karo, chahe aapki primary market abhi RTL na ho.

10. Advanced Deep-Dive — Beyond the Basics

10.1 — AccessibilityInfo: detecting a live screen reader and announcing dynamically

AccessibilityInfo API se aap runtime pe pata laga sakte ho ki screen reader currently active hai ya nahi, aur us basis pe behavior adapt kar sakte ho — jaise ek animation skip karna (kyunki screen reader users ke liye visual animation irrelevant hai aur unnecessary delay create karti hai), ya ek custom announcement trigger karna jab koi async action complete ho.

hooks/useScreenReaderStatus.ts
import { useEffect, useState } from 'react';         // React hooks
import { AccessibilityInfo } from 'react-native';         // screen reader detection API

// Hook jo current screen-reader status track karta hai reactively
export function useScreenReaderStatus() {
  const [isScreenReaderEnabled, setIsScreenReaderEnabled] = useState(false); // initial default false

  useEffect(() => {
    // Initial check — app load hote hi current status query karo
    AccessibilityInfo.isScreenReaderEnabled().then(setIsScreenReaderEnabled); // Promise resolve hone pe state update

    // Listener register karo — user runtime pe VoiceOver/TalkBack on/off kar sakta hai app khuli hone ke dauran bhi
    const subscription = AccessibilityInfo.addEventListener(
      'screenReaderChanged',                       // event name jab screen reader status change ho
      setIsScreenReaderEnabled                             // callback — naya boolean value directly state mein set karo
    );

    return () => subscription.remove();                  // cleanup — unmount pe listener hatao, memory leak avoid
  }, []);                                                    // empty deps — sirf mount pe ek baar setup

  return isScreenReaderEnabled;                            // component isse use karke behavior adapt kar sakta hai
}

// ----------------------------------------------------------------
// Custom live announcement — async action complete hone pe screen reader
// user ko batana, bina unke current focus ko disturb kiye
// ----------------------------------------------------------------
export function announceToScreenReader(message: string) {
  AccessibilityInfo.announceForAccessibility(message);      // VoiceOver/TalkBack turant ye message bolega, jahan bhi focus ho
}

10.2 — Custom gesture-based components aur accessibility actions

Chapter 5 mein humne Gesture Handler se swipeable/draggable components banaye the — jaise ek swipe-to-delete list row. Ye gestures visually intuitive hain sighted users ke liye, lekin ek screen reader user swipe-to-delete gesture perform hi nahi kar sakta — jab VoiceOver/TalkBack active hai, unke swipe gestures screen reader navigation ke liye reserved ho jaate hain (element se element move karne ke liye), aapke custom app-level swipe gesture ke liye nahi.

Solution: accessibilityActions prop use karke explicit, discoverable actions expose karo jo screen reader menu ke through trigger ho sakein (VoiceOver mein swipe-up/down se "actions rotor" khulta hai jahan ye custom actions list hoti hain).

components/AccessibleSwipeableRow.tsx
import { View, Text, StyleSheet } from 'react-native';                // core components
import { Gesture, GestureDetector } from 'react-native-gesture-handler'; // Chapter 5 se gesture system
import Animated, { useSharedValue, useAnimatedStyle } from 'react-native-reanimated'; // worklet-driven animation

type RowProps = { label: string; onDelete: () => void }; // row text + delete callback

function AccessibleSwipeableRow({ label, onDelete }: RowProps) {
  const translateX = useSharedValue(0);                       // horizontal swipe offset — UI thread pe live

  // Normal sighted-user swipe gesture — Chapter 5 pattern, sirf swipe-visible users ke liye kaam karta hai
  const panGesture = Gesture.Pan()
    .onUpdate((e) => { translateX.value = e.translationX; })    // finger ke saath row move karo
    .onEnd(() => {
      if (translateX.value < -100) { onDelete(); }                // threshold cross hua toh delete trigger
      translateX.value = 0;                                    // row wapas reset position pe
    });

  const animatedStyle = useAnimatedStyle(() => ({
    transform: [{ translateX: translateX.value }],               // live translateX apply karo
  }));

  return (
    <GestureDetector gesture={panGesture}>
      {/* accessibilityActions gesture ka ek DISCOVERABLE alternative expose karta hai */}
      <Animated.View
        style={[styles.row, animatedStyle]}
        accessible                                           // pura row ek accessibility element
        accessibilityLabel={label}                           // row content ka spoken label
        accessibilityActions={[
          { name: 'delete', label: 'Delete item' }, // screen reader actions-menu mein "Delete item" ka naam se dikhega
        ]}
        onAccessibilityAction={(event) => {                  // jab user actions menu se koi action select kare
          if (event.nativeEvent.actionName === 'delete') {   // hamare "delete" action ka match check karo
            onDelete();                                       // same delete callback jo swipe se trigger hota — DUPLICATE logic nahi, same function reuse
          }
        }}
      >
        <Text style={styles.label}>{label}</Text>
      </Animated.View>
    </GestureDetector>
  );
}

const styles = StyleSheet.create({
  row: { padding: 16, backgroundColor: '#262524', borderRadius: 8 }, // row visual style
  label: { color: '#e8e4dd', fontSize: 15 },                       // label text style
});

export default AccessibleSwipeableRow;                                    // export component

Yahan key insight ye hai ki onDelete function ek hi jagah define hai aur dono paths se reuse ho raha hai — swipe gesture se bhi, aur accessibility action se bhi. Ye ek important senior pattern hai: gesture aur accessibility action ko sirf "alag entry point" treat karo jo same underlying business logic ko trigger karte hain, code duplicate mat karo.

10.3 — Automated accessibility testing in CI

Poora accessibility coverage kabhi fully automate nahi ho sakta (jaisa Section 3 mein discuss kiya), lekin Chapter 7 ke testing pipeline mein kuch checks add karna high-value hai, jo "obvious misses" catch karte hain commit hone se pehle hi:

  • ESLint — eslint-plugin-react-native-a11y CI lint step mein wire karo, missing accessibilityLabel/invalid role jaisi cheezein PR stage pe hi flag ho jaayengi
  • React Native Testing Library — getByRole/getByLabelText queries use karke apne component tests likho (Chapter 7) — agar ye queries fail hoti hain, matlab element ka accessibility metadata missing/galat hai, jo apne aap ek regression test ban jaata hai
  • Maestro E2E flows — kuch teams critical flows mein accessibility-id based selectors use karte hain (jo internally accessibilityLabel pe depend karte hain) — agar ye E2E test break ho, ye ek signal hai ki accessibility label change/missing ho gaya, feature test ke saath incidentally accessibility bhi verify ho jaati hai
🧠 Senior Dev Note

Automated CI checks ka goal "accessibility guarantee karna" nahi hai — goal hai regression prevention. Ek baar manual screen-reader QA se ek component accessible verify ho gaya, CI checks (lint + RNTL queries) ensure karte hain ki future refactors accidentally us accessibility ko todh na dein (jaise koi developer accessibilityLabel hata de refactor karte waqt bina realize kiye). Manual testing "naya accessible banana", automated testing "already accessible cheez ko accessible bana kar rakhna" — dono complementary hain, ek dusre ka replacement nahi.

11. 🎯 Interview Questions — Senior React Native Developer

Ye questions accessibility aur i18n ke un aspects pe focus karte hain jo senior/staff interviews mein actually poochhe jaate hain — architecture decisions, trade-offs, aur "kyun" wale deep questions, sirf API syntax nahi.

Q1. Ek custom swipe-to-delete gesture component hai jo screen reader user ke liye poori tarah inaccessible hai kyunki wo swipe gesture perform nahi kar sakta. Aap isse accessible kaise banaoge?

Answer: Screen reader active hone pe swipe gestures navigation ke liye reserved ho jaate hain, isliye app-level swipe gesture unke liye discoverable nahi hai. Solution hai accessibilityActions prop use karke ek explicit "Delete item" action expose karna, aur onAccessibilityAction callback mein wahi delete logic call karna jo normal swipe gesture trigger karta hai. Isse VoiceOver/TalkBack ka "actions rotor"/custom actions menu se user ye action select kar sakta hai bina physically swipe kiye. Important cheez ye hai ki underlying delete logic ek hi jagah define ho aur dono paths (gesture handler ka onEnd, aur accessibility action ka callback) usi ko call karein — code duplicate nahi hona chahiye.

Q2. Kyun disabling font scaling (allowFontScaling={'{'}false{'}'}) ek real accessibility violation hai, sirf ek design compromise nahi?

Answer: OS-level text size setting specifically un users ke liye exist karti hai jinhe low vision ki wajah se default text size padhna mushkil hai. Jab developer allowFontScaling={'{'}false{'}'} lagata hai "layout todta hai" ki wajah se, ye effectively us user ki accessibility need ko override kar deta hai — user ne explicitly apne phone mein bada font set kiya tha kyunki unhe wo chahiye tha, aur app unhe force kar rahi hai chhota, unreadable text dekhne ke liye. Ye "design compromise" nahi hai kyunki design ka koi bhi consideration ek user ko literally content read karne se rokne se zyada important nahi ho sakta. Sahi fix hamesha layout ko resilient banana hai (flexible heights, wrap-friendly text), na ki accessibility feature ko disable karna.

Q3. Design karo ek multi-language app ke translation system ka file/data structure jisme pluralization aur RTL dono support karna ho.

Answer: Structure kuch is tarah hoga: src/i18n/index.ts jo i18next ko expo-localization se device locale detect karke initialize karta hai, aur src/i18n/locales/*.json mein har language ki apni file (en.json, hi.json, ar.json) — sab same key structure follow karte hain (namespace-based grouping jaise common, cart, checkout). Pluralization ke liye har countable string key ka multiple suffix variant hoga (_zero/_one/_two/ _few/_many/_other) jo language ke CLDR plural rules follow karta hai — i18next automatically sahi form resolve karta hai count parameter ke basis pe. RTL support translation files ka part nahi hai — ye ek separate concern hai jo I18nManager ke through language code check karke (['ar', 'he', 'ur'].includes(code)) handle hota hai, aur styling layer mein logical properties (marginStart/marginEnd) mandatory hain. Ek language-metadata registry bhi rakhna chahiye (e.g. {'{'} code: 'ar', isRTL: true, name: 'العربية' {'}'}) jo language-picker UI aur RTL-switch logic dono use kar sakein.

Q4. Ek PM kehta hai "accessibility launch ke baad add kar denge, abhi feature velocity zyada important hai" — aap kaise convince karoge ki isse abhi build karna chahiye?

Answer: Do angles se argue karna chahiye. Pehla, cost angle — accessibility ko day-1 se build karna marginal cost hai (ek button banate waqt accessibilityRole add karna 2 second ka kaam hai), jabki retrofit karna exponentially expensive hai kyunki har existing component wapas khol ke fix karna padta hai, exactly jaisa dark mode retrofit ke saath hota hai. Dusra, reach/revenue angle — accessibility koi niche edge case nahi hai, ye ek real, significant user segment hai jo currently app use hi nahi kar pa raha agar accessible nahi hai — ye literal churn/lost users hain, "nice to have" polish nahi. Concrete pitch: "hum ek naya button banate waqt 2 extra props add kar sakte hain abhi, ya 6 mahine baad ek poori sprint dedicate kar sakte hain sirf retrofit ke liye — trade-off clear hai."

Q5. Dimensions/hardcoded pixel layouts wale app mein RTL support add karna hai. Kya sirf I18nManager.forceRTL(true) call karna kaafi hoga?

Answer: Nahi. forceRTL() sirf Flexbox ke automatic mirroring ko enable karta hai (row direction flip, aur logical start/end properties ka correct resolution) — lekin ye kisi bhi hardcoded marginLeft/marginRight/left/right style ko automatically fix nahi karega, kyunki RN ko pata nahi ki ye "start/end" ke intent se likha gaya tha ya literally "left/right" ke intent se. Agar codebase mein ye hardcoded properties widely use ho rahe hain, sabse pehla step hai unhe systematically logical properties (marginStart/marginEnd) se replace karna, tabhi forceRTL() ka poora fayda milega. Iske alawa app ko reload/restart bhi chahiye hota hai RTL switch ke baad — Yoga layout direction sirf app launch time pe resolve karta hai.

Q6. String concatenation se ek translated sentence banayi jaa rahi hai — t('a') + ' ' + name + ' ' + t('b'). Ye approach kyun break hoti hai, aur sahi tareeka kya hai?

Answer: Ye approach English ke word order pe implicitly depend karti hai — hardcoded assume kar rahi hai ki subject-verb-object order har language mein same rahega. Languages jinka grammatical structure different hai (word order, gendered nouns jo surrounding words ko affect karte hain), is concatenation se ek grammatically broken ya confusing sentence generate hoga. Sahi approach hai poore sentence ko ek single translation key mein template ki tarah define karna, interpolation values ke saath — t('userAction', {'{'} name {'}'}) jahan translation file mein poora sentence "{'{'}{'{'}name{'}'}{'}'} ne aapko like kiya" jaisa likha ho. Isse translator ko poora sentence context milta hai aur wo apni language ke natural word order mein translate kar sakta hai, na ki fixed English structure follow karne ke liye majboor ho.

Q7. AccessibilityInfo.announceForAccessibility() kab use karoge, aur ye normal accessibilityLabel se kaise different hai?

Answer: accessibilityLabel ek static/semi-static property hai — ye tab hi announce hoti hai jab user us element pe focus kare (swipe navigate karke ya tap karke). announceForAccessibility() ek imperative, one-time announcement trigger karta hai jo turant bolа jaata hai, chahe user ka current focus kahin bhi ho — ye un cases ke liye hai jahan koi async event/state-change hui hai jo user ke current focus se unrelated hai lekin unhe pata chalna chahiye, jaise "Item added to cart", "Network connection restored", ya "3 new messages received". Agar aap sirf normal element focus pe depend karte, in async events ka koi natural "focus point" nahi hota, isliye screen reader user ko wo change kabhi pata hi nahi chalta bina explicit announcement ke.

Q8. Colorblind users ke liye ek "success/error" indicator design karo jo sirf color pe depend na kare. Kya-kya considerations honge?

Answer: Core principle: color ko kabhi sole information carrier mat banao — hamesha ek redundant, non-color signal saath do. Practical implementation: (1) Icon shape use karo jo khud differentiate kare (checkmark vs cross, up-arrow vs down-arrow) — shape colorblind users ke liye bhi clearly distinguishable hai. (2) Text label explicitly likho ("Success"/"Error"), sirf color-coded text mat chhodo. (3) Screen reader ke liye accessibilityLabel mein status word explicitly include karo (e.g. "Success: Order placed"), taaki blind users ko bhi pata chale — unke liye color ka toh koi matlab hi nahi hai. (4) Agar possible ho, WCAG contrast ratio bhi maintain karo taaki low-vision users (colorblind na hoke bhi) text easily padh sakein against background.

Q9. Aapki team ek accessible custom component library (Button, Card, Modal) already bana chuki hai. Ek naya developer join karta hai jo directly raw Pressable/View use karke naya feature bana raha hai bina library components ke. Iska accessibility impact kya hoga, aur aap process level pe isse kaise prevent karoge?

Answer: Impact ye hoga ki naya feature accessibility properties (labels, roles, states, focus management jo library components mein already baked-in hain) se miss ho jaayega — ek "accessibility gap" create hoga jo visual QA mein invisible rahega (Section 9 ka gotcha #3) lekin real screen-reader users ke liye us feature ko unusable bana dega. Process level solutions: (1) ESLint custom rule jo raw Pressable/TouchableOpacity import ko flag kare aur library Button component suggest kare. (2) Code review checklist mein accessibility ek explicit review item ho, na ki assume kiya jaaye ki "auto-handled hai". (3) Onboarding docs mein explicitly likha ho ki custom interactive elements banane se pehle library components check karo. (4) CI mein eslint-plugin-react-native-a11y jo missing labels catch kare bhale hi library bypass ho gayi ho.
