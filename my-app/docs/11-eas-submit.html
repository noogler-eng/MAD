EAS Submit — App Store aur Play Store Submission Automate Karna

Chapter 10 mein humne dekha ki EAS Build kaise ek signed .ipa/.aab file cloud pe generate karta hai. Lekin wo file khud store pe nahi pahunchti — koi na koi usse App Store Connect ya Play Console pe upload karega. Is chapter mein hum dekhenge ki EAS Submit is manual upload step ko kaise automate karta hai, kaunse credentials chahiye (App Store Connect API key, Google Service Account), aur kaise ek single command se poora build-to-store pipeline chain kar sakte hain.

What EAS Submit Does

Traditionally, ek build ready hone ke baad, upload karna ek manual, click-through process tha. iOS ke liye aapko Xcode Organizer kholna padta — build archive select karo, "Distribute App" click karo, App Store Connect option choose karo, aur upload wizard ke through manually navigate karo. Android ke liye aapko Play Console web dashboard pe login karna padta, apni .aab file manually drag-drop karni padti, release track select karna padta (internal/alpha/beta/production), aur submit karna padta. Dono hi processes mein ek insaan ke browser/Xcode session ke saamne baithna zaroori tha.

eas submit is poore process ko ek CLI command mein automate karta hai — ye aapki built binary (chahe wo local file ho ya EAS servers pe already-built artifact ho) leta hai, use App Store Connect ya Play Console ke official APIs ke through directly upload karta hai, aur submission trigger kar deta hai — sab kuch bina kisi GUI ko chhue.

Root level pe iska matlab ye hai ki ye ek headless, scriptable operation ban jaata hai — aur ye exactly wahi property hai jo CI/CD ke liye zaroori hoti hai. Agar aapka release process "kisi ko Xcode kholna padega aur manually click karna padega" pe depend karta hai, aap kabhi bhi fully-automated release pipeline nahi bana sakte — hamesha ek human-in-the-loop bottleneck rahega. eas submit is bottleneck ko hata deta hai: ek GitHub Actions workflow, ek cron job, ya koi bhi CI runner literally eas submit --platform ios --non-interactive chala sakta hai bina kisi insaan ke involvement ke (credentials ek baar setup karne ke baad).

🧠 Senior Dev Note

Ye distinction samajhna zaroori hai: EAS Build "compile karo" solve karta hai, EAS Submit "store ko bhejo" solve karta hai. Dono independent steps hain — aap chahe to sirf Build use karo aur manually Xcode/Play Console se upload karo, ya Build local artifact download karke Submit ko separately point kar sakte ho. Lekin jab dono chain hote hain (Section 5 mein dekhenge), poora "code commit se store review tak" pipeline ek single automated flow ban jaata hai — ye modern mobile CI/CD ka core idea hai.

Submitting to App Store (iOS)

iOS submission shuru karne se pehle teen prerequisites poore hone chahiye:

  • Active Apple Developer Program account — $99/year wala paid membership, jiske bina App Store Connect access hi nahi milta.
  • App Store Connect pe app already create ki hui — bundle identifier register karke, app record bana ke (name, primary language, SKU) — EAS Submit khud naya app record nahi banata, sirf existing record pe build attach karta hai.
  • Valid credentials jo EAS ko App Store Connect API access de sakein — isko detail se neeche dekhte hain, kyunki ye sabse important decision point hai.

Credentials ke do tareeke hain: Apple ID + app-specific password (legacy, interactive approach — aapko apna Apple ID email/password dena padta hai, plus 2FA), ya App Store Connect API Key (modern, recommended approach). Senior-level reasoning yahan clear hai:

🧠 API Key kyun better hai Apple ID/Password se

Apple ID + password automation ke liye fundamentally galat fit hai — ye aapki personal Apple account identity hai, jisme 2FA involved hota hai (jo CI mein handle karna painful/fragile hai), aur agar ye credential kahin leak ho jaye, attacker ko aapke poore Apple Developer account tak access mil jaata hai — sirf submission tak nahi, balki certificates revoke karna, team members remove karna, sab kuch. App Store Connect API Key iske bilkul opposite design karta hai: ye ek scoped, revocable, non-personal credential hai — aap ek specific role (jaise "App Manager") ke saath ek key generate karte ho jo sirf submission-related actions kar sakti hai, ye kisi individual insaan se tied nahi hai (koi bhi teammate leave kare, key valid rehti hai), aur agar CI secret leak ho jaye, aap bas us specific key ko App Store Connect se revoke kar sakte ho — baaki sab kuch untouched rehta hai. Yehi hi principle hai jo har production secret ke liye follow karna chahiye: scoped aur revocable credentials, kabhi bhi personal login credentials nahi.

API Key generate karne ke liye App Store Connect → Users and Access → Integrations → App Store Connect API mein jaake ek naya key banate hain — ye teen cheezein deta hai: Key ID, Issuer ID, aur ek .p8 private key file (sirf ek baar download hoti hai, dubara download nahi ho sakti — safe jagah save karna zaroori hai).

terminal
# iOS ke liye submission trigger karna — latest EAS build ko App Store Connect pe bhejta hai
eas submit --platform ios # Platform specify karna zaroori hai, CLI interactively pooch bhi sakta hai agar na diya

# Specific build ID ya local file explicitly point karna (agar latest wala nahi chahiye)
eas submit --platform ios --id <build-id> # EAS dashboard se specific build ka ID copy karke yahan use karo

# Non-interactive mode — CI environments ke liye zaroori (koi prompt nahi aayega)
eas submit --platform ios --non-interactive # Saari values env vars ya eas.json se already resolve honi chahiye

Pehli baar chalane par, EAS CLI aapse App Store Connect API Key details poochega (interactive mode mein) aur unhe encrypted store kar lega future submissions ke liye. CI mein ye env vars ke through pass hoti hain. Neeche eas.json ka annotated submit profile hai jo iOS ke liye API key credentials ko explicitly configure karta hai:

💡 Hinglish Tip

Practical mein bahut log .p8 file ko repo mein commit karne ke bajaye, EAS ke apne Environment Variables / Secrets feature (eas env:create) mein store karte hain aur CI mein us secret ko reference karte hain — isse local credentials/ folder aur .gitignore discipline pe depend nahi karna padta.

Submission trigger hone ke baad, build App Store Connect ke "TestFlight" section mein processing state mein dikhta hai (Apple binary ko validate karta hai — usually 5-30 minutes) — us ke baad hi aap use review ke liye submit kar sakte ho ya TestFlight testers ko distribute kar sakte ho.

Submitting to Google Play (Android)

Android submission ke prerequisites structurally similar hain, lekin credential mechanism alag hai:

  • Google Play Console account — one-time $25 registration fee wala developer account.
  • App already Play Console mein create ki hui — package name registered, app listing ka basic setup (name, default language) already ho chuka.
  • Google Service Account JSON key — Play Console ke API access ke liye ek machine identity, jise proper permissions diye gaye hon.

Google Play mein "Apple ID + password" jaisa koi legacy personal-login option hota hi nahi — Google har API access ko Service Accounts ke through force karta hai, jo already scoped/revocable design hai by default (Apple ke API Key approach jaisa hi philosophy). Service Account setup Google Cloud Console mein hota hai, phir Play Console mein us service account ko explicit permissions diye jaate hain (Release Manager ya equivalent role) — is step ke bina, valid JSON key hone ke bawajood submission "permission denied" error dega.

terminal
# Android ke liye submission trigger karna — latest build ko Play Console pe upload karta hai
eas submit --platform android # Default track internal hota hai jab tak eas.json mein specify na kiya ho

# Specific track (internal/alpha/beta/production) explicitly choose karna
eas submit --platform android --track production # Directly production track pe release karega — soch samajh ke use karo

# Non-interactive CI mode, credentials env/eas.json se resolve honge
eas submit --platform android --non-interactive # CI runner mein koi manual prompt nahi aayega

(comments added for teaching — real JSON doesn't support them, remove before use)

eas.json (submit.production.android)
{
  "submit": { // submit profiles ka root key
    "production": { // production submit profile
      "android": { // Android-specific submission config
        "serviceAccountKeyPath": "./credentials/android/service-account.json", // Google Cloud se generated service account key ka local path (gitignored)
        "track": "internal", // Kaunse Play Console release track pe jaana hai — internal safest default hai naye setup ke liye
        "releaseStatus": "completed" // "completed" = turant live/available; "draft" bhi option hai jo Play Console mein manual review ke liye chhod deta hai
      } // android block close
    } // production profile close
  } // submit block close
} // root object close
🔒 Service Account JSON kabhi commit mat karo

Ye service-account.json file bilkul wahi class ka secret hai jaisa koi bhi API key ya password hota hai — is JSON file ke andar ek private key hoti hai jo, agar leak ho jaye, kisi bhi attacker ko aapke naam se Play Console pe apps publish karne (ya existing app ke malicious update push karne) ki capability de sakti hai, depending on permissions scope. Ye galti bahut common hai kyunki developers ise "sirf ek config file" samajh lete hain, password nahi — lekin treat isse exactly ek password ki tarah karo: .gitignore mein add karo, kabhi bhi Slack/email pe raw file mat bhejo, aur EAS Secrets (eas env:create) ya kisi vault mein store karo. Agar galti se commit ho gaya (chahe private repo mein hi kyun na ho), turant Google Cloud Console se us key ko revoke karke naya generate karo — git history se hata dena kaafi nahi hai, key already compromised maani jaati hai.

Signing and Certificates Deep-Dive

Chapter 10 mein humne signing ka basic concept dekha tha — ab submission ke context mein isko extend karte hain, kyunki signing aur submission tightly coupled hain: agar signing mismatch ho, submission seedha reject ho jaata hai, chahe baaki sab kuch sahi ho.

iOS: Distribution Certificate + Provisioning Profile match

iOS pe build ko sign karne ke liye ek Distribution Certificate (aapki publisher identity) aur ek Provisioning Profile (jo batata hai ye build kis App ID/capabilities ke liye valid hai) chahiye — lekin submission ke waqt Apple ye bhi verify karta hai ki ye certificate/profile combination exactly us App Store Connect app record se match kare jisme aap submit kar rahe ho (same bundle identifier, valid distribution-type profile — not development/ad-hoc). Agar aapne kabhi bundle identifier change kiya without regenerating provisioning profile, ya galti se ek development-type profile se signed build submit karne ki koshish ki, Apple upload ko reject kar dega processing step pe hi ("Invalid Provisioning Profile" jaisi error).

Android: Upload Keystore aur Play App Signing

Android side pe ek important architectural shift samajhna zaroori hai jo modern Play Console default bana chuka hai: Play App Signing. Legacy model ("full keystore management ownership aapke paas") mein, wahi keystore jisse aap locally sign karte the, wo hi final key hoti thi jo end users ke devices pe verify hoti — matlab agar ye keystore kho gaya, jaisa Chapter 10 mein discuss kiya, app permanently unrecoverable ho jaata (naya package name banana padta).

Play App Signing is risk ko partially solve karta hai ek clever indirection ke through: aap Google ko ek upload key se signed .aab bhejte ho, Google use apne internally-held app signing key se re-sign karta hai before distributing to users devices. Matlab do alag keys involved hain — ek jo aap hold karte ho (upload key, sirf Play Console ko prove karne ke liye ki upload legitimately aap se aa raha hai), aur ek jo Google khud securely store karta hai (final signing key, jo actually users tak jaati hai).

ℹ️ Upload key reset ka matlab

Play App Signing ka sabse practical benefit ye hai ki agar aap apni upload key kho bhi dete ho, poori app "dead" nahi hoti — aap Google Play Console ke through ek upload key reset request file kar sakte ho (jisme identity verification process hota hai), aur ek naya upload key issue ho jaata hai jo same app signing key se link ho jaata hai. Risk poori tarah zero nahi hui (process mein time lagta hai, verification steps hain), lekin "permanently dead app, naya listing banao" wala worst-case scenario ab nahi hai — jo legacy model mein guaranteed tha.

🧠 Senior Dev Note

Naye projects mein hamesha Play App Signing enroll karo (EAS-managed credentials flow already isi ko default maanta hai) — legacy full-keystore-ownership sirf un edge cases ke liye reasonable hai jahan enterprise compliance requirement explicitly signing key ko third-party (Google included) ke paas rakhne se rokti ho, jo bahut rare hai.

Full Release Pipeline (Build + Submit Chained)

Ab tak humne Build aur Submit ko separate commands ki tarah dekha. Real CI/CD pipeline mein aap chahte ho ki ek hi trigger (jaise "release" branch pe merge, ya manual workflow dispatch) se poora "compile karo → store pe bhejo" flow chal jaye bina kisi manual intervention ke. EAS iske liye do approaches deta hai:

terminal (chained via --auto-submit)
# --auto-submit flag build complete hone ke turant baad, usi build ko automatically submit bhi kar deta hai
eas build --profile production --platform all --auto-submit # "all" dono platforms build karega, har ek complete hote hi submit trigger hoga

# Agar submit ke liye alag profile use karna ho (build profile se differ karta ho)
eas build --profile production --platform all --auto-submit --auto-submit-with-profile production # "submit" section mein specific profile name explicitly reference karta hai

Ye single-command approach simplest hai, lekin isme less control hota hai (build fail hone pe kya karna hai, submit se pehle koi extra validation step chahiye ya nahi, wagaira). Zyada explicit control ke liye, dono commands ko shell mein manually chain karte hain — ye pattern CI YAML files (jo Chapter 13 mein detail se dekhenge) mein common hai:

release.sh
#!/usr/bin/env bash # Shebang line — batata hai ye script bash interpreter se chalegi
set -e # Agar koi bhi command fail ho (non-zero exit), poori script turant ruk jayegi — partial/broken releases se bachne ke liye zaroori

# Step 1: Android production build trigger karo aur uska completion wait karo (default behaviour hai, --no-wait nahi diya)
eas build --profile production --platform android # Build queue mein jayega, terminal build khatam hone tak block karega

# Step 2: iOS production build bhi isi tarah, sequentially (parallel chahiye to --platform all use karo upar wale section jaisa)
eas build --profile production --platform ios # Ye bhi complete hone tak wait karega before aage badhna

# Step 3: Ab dono builds ready hain, Android ko Play Console pe submit karo
eas submit --platform android --non-interactive # Non-interactive zaroori hai CI mein — koi terminal prompt available nahi hota

# Step 4: iOS ko App Store Connect pe submit karo
eas submit --platform ios --non-interactive # Ye submission App Store Connect ke "processing" queue mein chala jayega

# Step 5: Success message print karo taaki CI logs mein clearly dikhe pipeline complete hui
echo "Release pipeline complete — both platforms submitted." # Sirf logging ke liye, koi functional effect nahi

Is script ka core idea ye hai ki "naya version release karna" ab ek single reproducible operation ban jaata hai — chahe wo ek developer apne terminal se manually chalaye, ya ek GitHub Actions workflow automatically kisi tag push pe trigger kare. Ye exactly wo shift hai jo Chapter 1 mein discuss ki gayi "works on my machine" class of problems ko release process ke level pe bhi eliminate karta hai — jab release ek script hai, wo deterministic hai; jab release "kisi ke Mac pe Xcode kholna" hai, wo nahi hai.

Real-World Gotchas

⚠️ App Store Connect API Key permissions galat/narrow hona

Ek bahut common first-time mistake: API Key banate waqt role "Developer" ya kisi read-only-ish role choose kar dena, jab actually "App Manager" (ya submission-capable equivalent) chahiye hota hai. Result — submission command chal jaata hai bina kisi obvious error ke shuru mein, lekin upload step pe "insufficient permissions" ya generic authorization error de deta hai. Fix: App Store Connect → Users and Access → Integrations mein jaake key ka role verify karo, aur zaroorat pade to naya key generate karo sahi role ke saath (purana role change nahi ho sakta, naya key banana padta hai).

⚠️ Play Console content/data-safety forms fill na hona

Ye pehli baar submit karne walon ke liye sabse common blocker hai, aur confusing isliye hai kyunki iska build se koi lena-dena nahi hota — build perfectly fine hoti hai, upload bhi successfully complete ho jaata hai, lekin Play Console submission ko production track pe release karne se rok deta hai jab tak App Content section (Data Safety form, Content Rating questionnaire, Target Audience declaration, Privacy Policy URL, wagaira) completely fill na ho jaye. Ye ek one-time Play Console dashboard task hai, EAS Submit CLI se iska koi relation nahi — isliye pehli submission attempt se pehle Play Console mein manually jaake ye saara App Content section poora karna senior-level checklist item hona chahiye, warna "submission stuck" dekh ke confusion hoti hai jab actual issue kahin aur hai.

⚠️ Review time expectations — Apple manual vs Google automated

Release planning karte waqt iska factor lena zaroori hai: Apple ka App Review largely manual hai — ek real insaan aapki app review karta hai, jisme typically 24-48 hours lagte hain (lekin edge cases mein kuch din bhi lag sakte hain, especially agar app rejection ho aur resubmit karna pade). Google Play ka review process mostly automated hai (machine-driven policy checks, kuch categories mein human review bhi hota hai) — usually kuch hours mein complete ho jaata hai, kabhi kabhi same-day. Practical implication: agar aapki team ek coordinated release plan kar rahi hai (jaise "dono platforms pe Friday ko launch"), iOS submission ko Android se pehle — kam se kam 1-2 din pehle — trigger karna chahiye taaki dono approximately same time pe live ho paayein, warna Android live ho jayega aur iOS abhi bhi review mein atka rahega.

Advanced Deep-Dive — Beyond the Basics

Ab tak humne eas submit ko "ek build ko store pe bhej do" tool ki tarah dekha hai. Senior level pe iska scope isse zyada bada hai — App Store Connect API key sirf submission ke liye nahi banta, staged rollouts ko automate kiya ja sakta hai, aur "submit fail ho gaya, kya main bas dubara chala doon" wala sawaal itna simple nahi hai jitna lagta hai. Ye teeno cheezein neeche detail se dekhte hain.

App Store Connect API automation — sirf submission tak limited nahi

Jo API key aapne Section 2 mein eas submit --platform ios ke liye banaya tha, wo actually App Store Connect ke poore REST API surface ka gateway hai — Apple ye ek hi key type use karta hai submission, metadata management, aur TestFlight operations, teeno ke liye. Iska matlab ye hai ki agar aapke paas ek valid API key hai, aap sirf binary upload karne se aage bhi kaafi kuch automate kar sakte ho:

  • TestFlight build management — kaunse builds kis testing group ko available hain, expired builds ko remove karna, external testing ke liye compliance info (export compliance) programmatically set karna — ye sab same API key se REST calls ke through possible hai, sirf eas submit command khud ye expose nahi karta.
  • App metadata automation via eas metadata — EAS ka apna separate command hai jo isi API key ko reuse karke app description, keywords, screenshots, aur release notes ko ek local store.config.json file se App Store Connect pe sync kar deta hai — matlab store listing bhi version-controlled ban jaati hai, "Store Connect dashboard mein manually type karo" wala step nahi rehta.
  • Release automation — agar aapki app "Manual release" mode pe hai (App Store Connect setting), same API key se aap programmatically decide kar sakte ho ki approved build kab actually publish ho — ye Section ke "Staged rollout automation" hisse se directly connect karta hai neeche.
🧠 Senior Dev Note — key ek hi hai, blast radius bada hai

Ye exact wahi reason hai jo key scoping aur rotation ko critical bana deta hai — jo key sirf "submission ke liye" bana tha, wahi key agar leak ho jaye, attacker TestFlight builds delete kar sakta hai, app metadata badal sakta hai (jaise malicious description push karna), ya manual-release apps ko apni marzi se publish kar sakta hai. Senior practice teen hisso mein hai: (1) minimum role assign karo — agar sirf submission chahiye, "App Manager" se upar mat jao, "Admin" role kabhi CI ke liye mat banao; (2) periodic rotation — key ko har few months mein revoke karke naya generate karna ek calendar reminder ban jaana chahiye, exactly password rotation jaisa; (3) immediate revocation on suspicion — agar CI logs mein galti se key print ho gayi, ya koi teammate leave kare jisne key generate ki thi, key ko turant App Store Connect → Users and Access → Integrations se revoke karo aur naya banao — "shayad koi issue nahi hai" wala assumption mat lo.

Staged rollout automation — poori tarah 100% pe ek saath mat jao

Dono stores staged/phased rollout support karte hain — matlab naya version pehle sirf ek chhote percentage of users ko milta hai, aur agar crash rates/ANR rates normal rahein, percentage gradually badhaya jaata hai. Ye blast radius control hai: agar naye version mein koi critical bug hai, sirf 5-10% users affected hote hain, 100% nahi. Senior teams ise manual dashboard clicking ki jagah automate karte hain.

Android pe ye eas.json ke submit profile mein directly configurable hai — rollout field ek 0 se 1 ke beech fraction leta hai:

(comments added for teaching — real JSON doesn't support them, remove before use)

eas.json (submit.production.android — staged rollout)
{
  "submit": { // submit profiles ka root key
    "production": { // production submit profile
      "android": { // Android-specific submission config
        "serviceAccountKeyPath": "./credentials/android/service-account.json", // Service account key ka path — same as before
        "track": "production", // Directly production track pe hi rollout ho raha hai, staged percentage ke saath
        "releaseStatus": "inProgress", // "inProgress" batata hai ki ye ek staged rollout hai, poori tarah "completed" nahi
        "rollout": 0.1 // Sirf 10% users ko naya version milega abhi; baaki 90% purane version pe rahenge
      } // android block close
    } // production profile close
  } // submit block close
} // root object close

Rollout ko badhane ke liye aapko dubara eas submit nahi chalana — ye ek naya build submit kar dega, jo galat hai. Rollout percentage badhane ka correct tareeka hai Play Console API ko directly google-play-scraper jaisi library se hit karna, ya ek chhoti follow-up script likhna jo same service account credential use kare:

bump-rollout.sh (annotated concept)
#!/usr/bin/env bash # Shebang — bash se chalegi ye script
set -e # Koi bhi step fail ho to poori script turant ruk jaye

# Step 1: Crash-free rate ko crash reporting tool (Sentry/Firebase Crashlytics) se check karo
# Ye ek real API call hoti — yahan concept ke liye placeholder hai
CRASH_FREE_RATE=check-crash-free-rate # Poora automation crash rate ke against decide karta hai, blind percentage badhaana nahi

# Step 2: Agar crash-free rate threshold (jaise 99.5%) se upar hai, tabhi rollout badhao
if [ "$CRASH_FREE_RATE" -gt 995 ]; then # Basis point comparison — 99.5% se zyada hona chahiye
  # Step 3: Play Developer API ke "Edits" resource ke through rollout fraction update karo (0.1 se 0.25)
  update-play-rollout --fraction 0.25 # Ye same service account JSON key use karta hai jo eas submit ne use kiya tha
else # Agar crash rate threshold se neeche hai
  # Step 4: Rollout ko halt karke on-call ko alert karo, aage mat badhao
  halt-rollout-and-page-oncall # Automated safety net — insaan ko turant pata chal jaye kuch galat hai
fi # if block close

iOS pe equivalent concept phased release hai — App Store Connect mein enable karne pe naya version automatically 7-day curve mein rollout hota hai (1% → 2% → 5% → 10% → 20% → 50% → 100%), aur agar koi issue mile to aap App Store Connect API se hi phasedReleaseState ko PAUSED set kar sakte ho — same API key jo submission ke liye use ho raha tha.

🧠 Senior Dev Note — rollout automation ek safety system hai, feature nahi

Staged rollout ka poora point ye hai ki rollback ki zaroorat hi kam pade — agar aap crash rate ko automatically monitor karke rollout ko pause/halt kar rahe ho, aap production incident ko us scale tak pahunchne hi nahi de rahe jaha manual EAS Update rollback (Chapter 12) zaroori ho. Root cause yahi hai ki release ek "all or nothing" event na ho — gradual, observable, aur reversible ho.

Submit retries aur idempotency — kya dubara chalana safe hai?

Ek practical scenario jo har senior dev ko pehle hi din face karna padta hai: eas submit chal raha tha, upload ke beech mein network drop ho gaya, ya CI runner timeout ho gaya. Command fail ho gaya — ab kya bas eas submit dubara chala doon? Answer "it depends on the store" hai, aur ye samajhna zaroori hai kyun.

Iska matlab senior practice ye hai: "submit command fail hua, bas dubara chala do" ek junior-level assumption hai. Correct approach pehle store console (App Store Connect / Play Console) mein actual state verify karna hai — kya upload partially complete ho gaya tha (binary already dikh raha hai, bas processing mein atka hai) ya poori tarah fail ho gaya (kuch bhi nahi pahuncha)? In dono cases mein different action chahiye:

  • Agar binary store console mein bilkul nahi dikh raha (upload network failure se pehle hi fail hua) — retry safe hai, kuch bhi duplicate nahi hoga.
  • Agar binary "Processing" ya "Invalid Binary" state mein atka hua dikh raha hai — pehle wait karo ya us specific build ko explicitly reject/remove karo store console se, phir hi retry karo; blind retry same version code/build number ke saath dusra upload attempt karega jo store reject kar sakta hai ek confusing error ke saath.
  • CI automation mein — ye exactly wo jagah hai jaha retry logic ko naive retry-on-failure loop nahi hona chahiye; ek proper implementation pehle store API se current state query karti hai (ya kam se kam ek short cooldown + single retry with alerting rakhti hai) bajaye infinite retry ke jo duplicate submissions ya confusing partial states create kar sakta hai.
🧠 Senior Dev Note — idempotency store-level concern hai, tool-level nahi

eas submit khud koi retry-safety guarantee nahi deta — wo bas ek thin client hai jo store ke API ko call karta hai. Actual idempotency (ya uski absence) us underlying store API ka behavior hai. Ye pattern sirf EAS Submit tak limited nahi — kisi bhi third-party API ke against automation likhte waqt senior-level habit yahi honi chahiye: pehle poochho "agar ye call do baar chali gayi, kya hoga?" — agar answer clear nahi hai, blind retry mat likho, state-check karke phir retry karo.

🎯 Interview Questions — Senior React Native Developer

Neeche kuch interview-style sawaal hain jo EAS Submit aur release automation ke context mein senior React Native roles mein poochhe jaate hain — practical, security, aur scenario-based mix.

1. Design a fully automated release pipeline from a git tag push to a live App Store submission — kya kya stages honge aur kaha kaha ye fail ho sakta hai?

Ek strong answer stages ko clearly separate karta hai aur har stage ka failure mode bhi bataata hai:

  • Trigger — CI workflow ek v* tag push pe fire hota hai. Failure mode: galat tag format se workflow trigger hi na ho, ya do tags race condition mein simultaneously push ho jayein.
  • Build — eas build --profile production --platform ios. Failure mode: signing credentials expire ho chuki hon, native dependency conflict, ya EAS build queue timeout.
  • Automated tests gate — Maestro E2E suite build ke against chalti hai before submit (Chapter 7 se connect). Failure mode: flaky test false-negative de de aur pipeline block kar de.
  • Submit — eas submit --platform ios --non-interactive. Failure mode: API key expired/revoked, ya network failure mid-upload (Section 7 ka idempotency discussion yahan directly apply hota hai).
  • Store-side review — Apple manual review, 24-48 hours. Failure mode: app metadata guideline violation — ye EAS ke control se bahar hai completely (agla sawaal isi pe hai).
  • Phased release — approved hone ke baad staged rollout auto-start ho, crash metrics monitor karte hue.

Senior answer mein ye bhi include hona chahiye ki har stage ke beech observability honi chahiye — Slack notification ya dashboard update jo bataye pipeline kis stage pe hai, taaki failure ko turant localize kiya ja sake bajaye "release atka hua hai" ke generic confusion ke.

2. App Store Connect API key CI automation ke liye Apple ID + password se better kyun hai?

Core answer credential design philosophy ke around hona chahiye, sirf "convenience" nahi: Apple ID + password ek personal identity credential hai jo 2FA involve karta hai (CI mein fragile), aur poori Apple Developer account tak access deta hai agar leak ho — certificates revoke karna, team members remove karna, sab. App Store Connect API Key ek scoped, revocable, non-personal machine credential hai — specific role assign hota hai, kisi individual se tied nahi (team member leave kare to bhi valid rehti hai), aur leak hone pe sirf us key ko revoke karna padta hai, poore account ko nahi. Ye same principle hai jo IAM roles/service accounts cloud infrastructure mein follow karte hain — never use personal credentials for machine-to-machine automation.

3. Ek submission EAS Submit step ke "success" report karne ke baad App Store Connect pe validation fail ho jaati hai — ye kya batata hai in dono systems ki responsibility split ke baare mein?

Ye ek boundary-understanding sawaal hai. eas submit ki responsibility sirf itni hai: binary ko successfully Apple/Google ke servers tak upload karna aur unke API se ek acknowledgment receive karna ki "upload accepted for processing hua hai". Ye success hai — lekin ye content/metadata validation ka success nahi hai. App Store Connect apna khud ka asynchronous binary processing pipeline chalata hai (usually 5-30 min) jo binary ko validate karta hai — missing icons, invalid entitlements, privacy manifest issues, wagaira. Ye validation EAS ke control ya visibility ke bahar hoti hai — EAS ke paas is stage ka koi insight nahi hai jab tak aap explicitly App Store Connect API/dashboard poll na karo. Senior-level takeaway: "submit succeeded" sirf "upload transport succeeded" ka matlab hai, "app store accepted the binary" ka nahi — pipeline automation mein ye do alag success conditions treat karni chahiye, aur processing state ko explicitly poll/notify karna chahiye before assuming release is safe.

4. Play App Signing enabled hone ke baad, agar aapki upload keystore compromise ho jaye, actual damage kya hai — aur ye legacy model se kaise different hai?

Legacy model mein keystore compromise ka matlab hota tha attacker directly malicious update sign karke publish kar sakta hai users tak — full control. Play App Signing ke saath, upload key sirf "upload legitimately mujhse aaya hai" prove karne ka mechanism hai — final signing Google apni khud ki securely-held app signing key se karta hai. Agar upload key compromise ho jaye, attacker Play Console pe malicious upload attempt kar sakta hai, lekin Google Play ka fraud/anomaly detection is upload pattern ko flag kar sakta hai, aur aap turant Google se upload key reset request kar sakte ho — jo purani key ko invalidate kar deta hai bina app signing key affect kiye. Damage window aur blast radius dono legacy model se significantly chhote hain, lekin "zero risk" nahi — isliye upload keystore ko bhi ek proper secret ki tarah treat karna zaroori hai, "sirf convenience wrapper hai" samajh ke casually handle nahi karna.

5. Google Play Data Safety form fail hone ka behavior EAS Build/Submit failure se kaise different hai, aur ye kaise batata hai ki store-level release blockers CI pipeline design ko kaise affect karte hain?

Build/Submit failures deterministic aur immediate hote hain — command non-zero exit code deta hai, CI pipeline turant red ho jaata hai, root cause usually logs mein directly visible hota hai. Data Safety form (ya App Content section) ka missing hona is tarah fail nahi hota — build successfully compile hoti hai, upload bhi successfully complete ho jaata hai, submit command bhi success return karta hai — lekin Play Console silently production track pe release hone se rok deta hai jab tak dashboard ka ye section manually complete na ho. CI pipeline design ke liye implication: pure "did the command exit 0" check kaafi nahi hai — production-grade pipeline ko store console ki actual release state bhi verify karni chahiye (via API polling) before "release successful" declare karna, kyunki store-side gating rules CI ke exit codes se completely independent hain.

6. Aapko ek staged rollout automate karna hai jo crash-free rate ke basis pe apne aap percentage badhaye ya halt kare. High-level design kya hoga, aur kaunsi cheez galat ho sakti hai agar naively implement kiya jaye?

High-level design: ek scheduled job (cron/CI scheduled workflow) periodically crash reporting tool (Sentry/ Crashlytics) se crash-free rate metric fetch karta hai us specific version ke liye, threshold ke against compare karta hai, aur agar healthy hai to Play Developer API/App Store Connect API se rollout percentage badhata hai; agar unhealthy hai to rollout halt karke alert fire karta hai. Naive implementation ki common mistakes: (1) sample size ignore karna — agar sirf 50 users ne update kiya hai, crash-free rate statistically meaningless hai, minimum sample size threshold hona chahiye; (2) lag ignore karna — crash reports real-time nahi aate, ek rollout bump ke baad kam se kam kuch ghante wait karna chahiye taaki naya data settle ho; (3) single metric pe depend karna — sirf crash-free rate check karna kaafi nahi, ANR rate, negative review spike, aur key business metrics (jaise checkout completion rate) bhi factor hone chahiye, warna ek "non-crashing but broken feature" bug silently 100% tak roll out ho jayega.

7. Aapka EAS Submit CI job secrets manage karta hai — .p8 API key aur Play service account JSON dono. In secrets ko manage karne ke liye kya production-grade approach hogi, aur kya galtiyan common hain?

Production-grade approach: dono secrets ko EAS Secrets (eas env:create) ya CI provider ke native secret store (GitHub Actions secrets, jaise) mein store karna — kabhi bhi repo mein commit nahi, chahe private repo hi kyun na ho. Secrets ko sirf woh CI jobs access dein jinhe actually zaroorat hai (least-privilege job scoping), aur secrets ko logs mein kabhi print na hone dena (CI tools usually secret values ko automatically mask kar dete hain agar properly registered ho, lekin agar aap unhe manually echo karte ho debugging ke liye, wo mask bypass ho jaata hai). Common mistakes: secrets ko .env file mein likh ke gitignore pe depend karna (ek galti se git add -f sab expose kar deta hai), secrets ko fork-based PR workflows mein expose karna (public repo ke forks ko by default secrets access nahi milna chahiye — CI provider settings verify karo), aur ek hi API key/service account ko multiple unrelated projects mein reuse karna (ek project compromise hone pe blast radius unnecessarily badh jaata hai — per-project scoped credentials better practice hai).

8. Chained --auto-submit flag vs manually chained shell script (Section 5) — ek senior engineer kab kaunsa choose karega?

--auto-submit simplest hai aur single-team, low-complexity setups ke liye perfectly fine — lekin isme control points kam hain: build fail hone pe kya specific action leni hai, submit se pehle koi extra gate (jaise Maestro E2E suite, ya manual QA sign-off) insert karna ho, ya conditional logic (jaise "sirf agar version bump hua hai tab submit karo") — in sab cases mein manually chained script/workflow zaroori ho jaata hai jaha har step explicit hai aur beech mein custom logic insert ki ja sakti hai. Senior decision framework simple hai: agar pipeline mein sirf "build ho gaya, ab submit kar do" hai bina kisi conditional logic ke, --auto-submit use karo — kam moving parts, kam maintenance. Jaise hi ek bhi gate/condition/notification step chahiye hota hai, explicit chaining (ya EAS Workflows, Chapter 13) better hai kyunki wo visibility aur control dono deta hai jo ek single flag nahi de sakta.
