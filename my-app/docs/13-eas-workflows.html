EAS Workflows — Expo ka apna CI/CD System

Ab tak humne eas build, eas submit, aur eas update ko manually terminal se run kiya hai — ya phir GitHub Actions jaisi external CI mein wire kiya hai. EAS Workflows isse ek step aage le jaata hai: Expo ka apna YAML-based CI/CD system, jo Expo ke hi infra pe chalta hai aur build/submit/update ko first-class steps ki tarah treat karta hai. Is chapter mein hum dekhenge ki ye kaam kaise karta hai, basic se full release pipeline tak, Maestro E2E gate ke saath, aur sabse zaroori — kab isko use karna hai aur kab GitHub Actions pe hi rehna hai.

1. EAS Workflows Kya Hai Aur Kyun Exist Karta Hai

EAS Workflows Expo ka apna CI/CD orchestration system hai — matlab tum YAML files likhte ho jo Expo ke infra pe run hoti hain (wahi machines jinpe tumhare EAS Builds chalte hain), na ki GitHub/GitLab ke apne CI runners pe. Ye conceptually GitHub Actions jaisa hi hai — triggers, jobs, steps — lekin ek key difference ke saath: EAS Workflows ke paas build, submit, aur update jaise first-class built-in step types hain jo directly EAS platform ke primitives ko call karte hain, bina tumhe khud eas CLI commands ko shell script mein wrap karna pade.

Isse samajhne ka sabse aasan tareeka: GitHub Actions mein agar tumhe build → submit chain karna ho, tum kuch aisa likhte ho —

GitHub Actions ka glue-code approach (for comparison)
steps: # GitHub Actions job ke andar steps ki list
  - name: Setup Node # Node.js runtime install karne wala step
    uses: actions/setup-node@v4 # third-party marketplace action use kiya
  - name: Install Expo CLI # eas-cli ko manually install karna padta hai
    run: npm install -g eas-cli # global install, GitHub runner pe koi built-in EAS support nahi hai
  - name: Build # actual build trigger karne wala step
    run: eas build --platform ios --non-interactive --no-wait # CLI command khud likhna padta hai, flags yaad rakhne padte hain
  - name: Submit # build complete hone ke baad submit karne wala step
    run: eas submit --platform ios --latest --non-interactive # phir se CLI ko manually orchestrate karna padta hai

Ye kaam karta hai, lekin har glue step tumhari zimmedari hai — CLI install karna, auth token wire karna, "--latest build use karo" jaisa logic khud likhna, aur agar build fail ho jaaye toh submit skip karne ka conditional logic bhi khud handle karna. EAS Workflows mein wahi cheez built-in step types ke through first-class treat hoti hai:

EAS Workflows ka native step approach (for comparison)
jobs: # workflow ke andar jobs ki list
  build: # job ka naam, dusre jobs isko reference kar sakte hain
    type: build # built-in "build" job type — seedha EAS Build primitive ko call karta hai
    params: # build job ke parameters
      platform: ios # kaunse platform ke liye build banani hai
  submit: # dusra job, submit ke liye
    type: submit # built-in "submit" job type — App Store/Play Store submission handle karta hai
    needs: [build] # dependency — build job pehle complete/success hona chahiye
    params: # submit job ke parameters
      build_id: ${{ needs.build.outputs.build_id }} # build job ka output directly reference kiya — koi "--latest" guesswork nahi

Notice karo — needs.build.outputs.build_id jaisa data-flow between jobs, credentials handling, aur "agar build fail ho toh submit skip karo" jaisa dependency-based sequencing sab platform ke andar built-in hai, kyunki EAS Workflows aur EAS Build/Submit/Update dono ek hi platform (Expo) ke primitives hain. Isliye kam glue code likhna padta hai — trade-off ye hai ki EAS Workflows ka ecosystem GitHub Actions jitna vast nahi hai (marketplace actions, third-party integrations, Slack notifications, custom runners waghera) — wo sab abhi limited ya absent hai.

AspectEAS WorkflowsGitHub Actions
Build/Submit/Update stepsFirst-class built-in job typesManual eas CLI calls
Runs whereExpo ka apna infraGitHub-hosted ya self-hosted runners
EcosystemChhota, EAS-specificBahut bada marketplace (10,000+ actions)
Non-mobile CI needsLimited (web dashboard deploy, lint on other services, etc.)General-purpose, kuch bhi orchestrate kar sakta hai
Setup effortKam — same platform, less glueZyada — CLI install, auth wiring, custom scripts
🧠 Senior Dev Note — ye "vs" nahi, "aur" bhi ho sakta hai

Bahut senior teams EAS Workflows aur GitHub Actions dono use karti hain — same time, different purposes ke liye. GitHub Actions repo ke baaki CI (lint, typecheck, unit tests on every PR, web dashboard deploy) handle karta hai, aur wahi se ek step EAS Workflows ko trigger kar deta hai jab actual mobile release banani ho. Hum section 6 mein isko detail se dekhenge.

2. Getting Started: Basic Workflow File

EAS Workflows ek strict convention follow karta hai — saari workflow YAML files .eas/workflows/ folder ke andar honi chahiye. EAS CLI aur EAS ka dashboard automatically is folder ko scan karte hain jab workflows list karni ho ya trigger karni ho.

Folder structure — .eas/workflows/
.eas/                              // EAS-specific config ka root folder — eas.json ke sath-sath yahan workflows bhi rehte hain
└── workflows/                    // EAS Workflows convention folder — CLI/dashboard automatically yahi jagah scan karte hain YAML files ke liye
    ├── build-and-submit.yml      // ek workflow = ek release pipeline, alag file isliye taaki ye independently trigger/edit ho sake bina doosre workflows ko touch kiye
    └── e2e-tests.yml             // testing workflow build-and-submit se alag rakha, taaki ye PR merge pe chale bina har build ke saath release trigger kiye

Ab ek sabse simple possible workflow likhte hain — jo main branch pe push hone par automatically ek iOS build trigger kare. Har line commented hai, kyunki YAML syntax mein indentation aur structure hi sab kuch hai — ek galat space se pura workflow silently fail ho sakta hai.

.eas/workflows/basic-build.yml
name: Basic build on push # workflow ka human-readable naam, EAS dashboard pe yahi dikhega

on: # "on" block define karta hai ki ye workflow kab automatically trigger hogi
  push: # git push event pe trigger karne ka config
    branches: [main] # sirf "main" branch pe push hone par hi ye workflow chalegi, feature branches pe nahi

jobs: # workflow ke andar actual kaam karne wale jobs ki list
  build_ios: # is job ka naam — descriptive rakho, dashboard aur logs mein yahi id dikhegi
    type: build # built-in job type "build" — EAS Build primitive ko directly invoke karta hai
    params: # build job ke configuration parameters
      platform: ios # iOS ke liye build banao — Android alag job mein karenge agle section mein
      profile: production # eas.json mein defined "production" build profile use karo (signing, env vars waghera us profile se aayenge)

Is file ko commit karke push karte hi, agli baar jab tum main pe push karoge, EAS automatically ek production iOS build trigger kar dega — bina tumhe manually eas build chalane ke. Workflow ko manually bhi trigger kar sakte ho, testing ke liye:

Manually run a workflow
eas workflow:run .eas/workflows/basic-build.yml # given workflow file ko turant, manually trigger karo — git push ka wait nahi karna
💡 Quick Tip

Naya workflow likhte waqt, pehle eas workflow:run se manually trigger karke test karo — automatic git-push triggers pe rely karke test karoge toh har chhoti si YAML mistake debug karne ke liye ek naya commit + push karna padega, jo bahut slow feedback loop hai.

3. Build and Submit Workflow (Full Release Pipeline)

Ab ek real release pipeline banate hain — jo iOS aur Android dono ke liye build kare, aur sirf tab submit kare jab build successfully complete ho. Ye needs field ke through automatically hota hai — agar build_ios job fail ho jaaye, uspe depend karne wala submit_ios job automatically skip ho jaata hai, EAS Workflows isko khud handle karta hai, tumhe manually "if build succeeded" jaisi condition likhne ki zaroorat nahi.

.eas/workflows/build-and-submit.yml
name: Build and Submit — iOS and Android # dashboard pe dikhne wala readable naam

on: # trigger conditions
  push: # git push based trigger
    tags: ['v*'] # sirf "v1.0.0" jaisa version tag push hone par hi trigger hoga — release-only pipeline, har normal commit pe nahi

jobs: # jobs ki list — kul 4 jobs honge: 2 build, 2 submit
  build_ios: # iOS build job
    type: build # built-in build job type
    params: # is job ke parameters
      platform: ios # iOS platform target
      profile: production # production signing/config profile eas.json se

  build_android: # Android build job, iOS se independent — parallel mein chalega
    type: build # same built-in type, different platform param
    params: # is job ke parameters
      platform: android # Android platform target
      profile: production # production profile

  submit_ios: # iOS submission job
    type: submit # built-in "submit" job type — App Store Connect ko push karta hai
    needs: [build_ios] # dependency — build_ios success hone tak wait karega, fail hone par automatically skip
    params: # submit job ke parameters
      platform: ios # kaunsi store pe submit karna hai
      build_id: ${{ needs.build_ios.outputs.build_id }} # build_ios job ka exact output build id use karo, "latest" guess nahi

  submit_android: # Android submission job
    type: submit # same built-in type, Android ke liye
    needs: [build_android] # build_android pe depend karta hai, isliye iOS build fail hone se ye affect nahi hoga
    params: # submit params
      platform: android # Play Store target
      build_id: ${{ needs.build_android.outputs.build_id }} # build_android job ka exact build id reference

Yahan ek important architectural point hai — build_ios aur build_android ke beech koi needs nahi hai, matlab ye dono jobs parallel mein chalenge (independent dependency graph nodes). Lekin submit_ios sirf build_ios pe depend karta hai, submit_android sirf build_android pe — is design se agar Android build fail ho jaaye, iOS ka poora build-submit chain unaffected rehta hai, aur vice versa.

🧠 Senior Dev Note — dependency graph ko explicit socho

Jab bhi ek naya job add karo, khud se poocho: "ye job kis output pe depend karta hai, aur agar uska dependency fail ho jaaye toh kya ye job chalna chahiye ya nahi?" needs: [] ka matlab hai job independently, doosre jobs ke saath parallel chalega. Galat dependency wiring ka common mistake: dono submit jobs ko dono build jobs pe depend kar dena (needs: [build_ios, build_android]) — isse Android build fail hone par iOS submit bhi rukk jaayega, jo waste hai jab dono platforms independent releases hain.

4. E2E Testing in a Workflow (Maestro Integration)

Ch.7 mein humne dekha tha ki Maestro E2E tests real device/simulator pe, real build ke against chalte hain — aur wo locally chalate the. Production-grade pipeline ka agla step: E2E tests ko automated gate banao, jo build hone ke baad khud-ba-khud chale, aur agar tests fail hon toh submit step ko block kar de. Isse ek poora "regression pehle hi pakdo, user tak pahunchne se pehle" safety net ban jaata hai.

Kyun ye local Maestro runs se better hai? Kyunki local runs developer discipline pe depend karte hain — koi bhool sakta hai run karna, "chhota change hai, skip karta hoon" bol sakta hai, ya apne local machine pe stale dependencies ke saath test kar raha ho sakta hai. CI mein E2E gate lagane se ye guarantee milti hai ki har single release, chahe kisi ne bhi push kiya ho, ek identical, reproducible environment mein poora critical user journey (login → home) pass karke hi store tak pahunchti hai.

.eas/workflows/e2e-tests.yml
name: Build, E2E Test, then Submit # dashboard naam — pipeline ka intent clearly bata raha hai

on: # trigger config
  push: # push-based trigger
    tags: ['v*'] # sirf release tags pe — E2E + submit ek costly pipeline hai, har commit pe nahi chalani

jobs: # jobs list — build → maestro gate → submit
  build_preview: # pehla job — ek internal-distribution preview build banata hai (device pe installable, store submission nahi)
    type: build # built-in build job
    params: # build parameters
      platform: ios # iOS ke liye E2E chalayenge is example mein
      profile: preview # "preview" profile — dev-client nahi, but production jaisa build, simulator/internal install ke liye

  maestro_e2e: # dusra job — Maestro flows ko preview build ke against run karta hai
    type: maestro # built-in "maestro" job type — EAS ka managed Maestro runner invoke karta hai
    needs: [build_preview] # preview build complete hone tak wait — usi build pe test chalana hai
    params: # maestro job ke parameters
      build_id: ${{ needs.build_preview.outputs.build_id }} # kaunsi build pe test chalana hai, exact reference
      flow_path: .maestro/login-to-home.yaml # ch.7 wala hi flow file reuse kiya — critical login→home journey

  submit_ios: # teesra job — sirf E2E pass hone ke baad chalega
    type: submit # built-in submit job
    needs: [maestro_e2e] # yehi "gate" hai — maestro_e2e fail hone par ye job automatically skip ho jaayega, App Store tak nahi pahuchega
    params: # submit parameters
      platform: ios # store target
      build_id: ${{ needs.build_preview.outputs.build_id }} # note: preview build id yahan reuse nahi karna chahiye production submit ke liye, real setup mein alag "production profile" build job hoga jo E2E pass hone ke baad trigger hota hai
⚠️ Gotcha — preview build ko directly store pe submit mat karo

Upar wale example mein submit_ios ne build_preview ka hi build id use kiya — ye sirf concept dikhane ke liye simplified hai. Real production pipeline mein "preview" profile wali build App Store submission ke liye sahi signing/config nahi rakhti. Sahi pattern: E2E gate ek preview build pe chalao (fast feedback), aur E2E pass hone ke baad ek alag build_production job trigger karo jo needs: [maestro_e2e] ke saath production profile use kare, phir usi ka output submit karo. Isse E2E gate aur actual store-bound artifact clearly separate rehte hain.

🧠 Senior Dev Note — CI mein E2E ka real value

Local Maestro run sirf ye prove karta hai ki "developer ke machine pe, uske current branch state mein, flow pass hua." CI-based E2E gate ye prove karta hai ki "exact commit jo release ban raha hai, ek clean/reproducible environment mein, poore critical journey ke saath, kaam karta hai." Fark subtle lagta hai lekin real incidents isi gap mein hote hain — jaise koi developer local env variable set karke bhool gaya, ya ek dependency uske machine pe cached thi jo fresh install mein missing thi. CI gate in "works on my machine" cases ko systematically eliminate karta hai.

5. Triggers and Conditions

EAS Workflows ko trigger karne ke teen main tareeke hain — manual, git-push-based, aur tag-based — aur inputs/parameters ka use karke ek hi workflow file ko multiple environments (dev/staging/prod) ke liye reusable bana sakte ho.

Trigger typeKab use karo
Manual (eas workflow:run)Testing/debugging ke waqt, ya ad-hoc "abhi ek build chahiye" cases mein
Push trigger (branch-based)Continuous builds — har baar main/develop pe merge hone par preview build
Tag-based triggerActual releases — sirf jab tum explicitly ek version tag (v1.2.0) push karo, tabhi production pipeline chale

Ek hi workflow file ko dev/staging/prod teeno environments ke liye reuse karne ke liye, hardcoded values ki jagah inputs define karo — phir manual run ke waqt ya dusre workflow se call karte waqt value pass kar do.

.eas/workflows/deploy-update.yml — reusable across environments
name: Deploy OTA update # workflow ka naam

on: # trigger config
  workflow_call: # "workflow_call" — matlab ye workflow manually ya kisi aur workflow se parameters ke saath invoke hoga, auto-trigger nahi
    inputs: # is workflow ke reusable inputs define kar rahe hain
      environment: # input ka naam — "environment" parameter
        required: true # bina environment specify kiye workflow run hi nahi hogi
        type: string # input ka data type — plain string expect ho raha hai

jobs: # jobs list
  publish_update: # OTA update publish karne wala job
    type: update # built-in "update" job type — EAS Update primitive ko invoke karta hai
    params: # job ke parameters
      branch: ${{ inputs.environment }} # update channel/branch ka naam dynamically input se aa raha hai — "dev"/"staging"/"production" jo bhi pass ho
      message: Deploy to ${{ inputs.environment }} # update ke saath attach hone wala descriptive message, dynamic bhi

Isko manually alag-alag environment ke liye run karna kuch aisa dikhega:

Run the same workflow for different environments
eas workflow:run .eas/workflows/deploy-update.yml --input environment=staging # staging channel pe OTA update publish karo
eas workflow:run .eas/workflows/deploy-update.yml --input environment=production # same workflow file, production channel pe — koi duplicate YAML nahi likhna pada
💡 Quick Tip

Inputs ka pattern especially valuable hai jab tumhare paas 3+ environments hon — bina inputs ke, tumhe deploy-dev.yml, deploy-staging.yml, deploy-prod.yml jaisi teen almost-identical files maintain karni padengi, jinme se koi ek mein galti se drift (stale params, missed update) ho sakta hai. Ek reusable file safer aur DRY dono hai.

6. EAS Workflows vs GitHub Actions — Senior Decision Framework

Ab jab dono systems dekh liye, senior-level decision yahan hai: kab kaunsa choose karein, aur kab dono ko combine karein.

SituationRecommendation
Small-to-mid team, already fully EAS-based (build/submit/update sab EAS se)EAS Workflows — minimal glue, ek hi platform pe sab kuch, kam maintenance surface
Need web dashboard/backend bhi deploy karna, alag services ke saathGitHub Actions — broader CI capability, ek hi pipeline mein web + mobile dono orchestrate ho sakta hai
Complex multi-repo orchestration (monorepo ya multiple related repos)GitHub Actions — cross-repo triggers, matrix builds, aur third-party integrations ka mature ecosystem
Already heavy investment in GitHub Actions (existing workflows, secrets, custom actions)Existing investment ko waste mat karo — GitHub Actions continue karo, EAS ko usmein call karo
Sirf mobile release automation chahiye, koi external CI dependency nahi rakhniEAS Workflows — koi separate CI account/runner setup ki zaroorat nahi

Aur jaisa pehle mention kiya, dono ko combine karna bhi ek perfectly valid pattern hai — GitHub Actions apna general-purpose CI (lint, typecheck, unit tests, web deploy) chalata rahe, aur jab actual mobile release banani ho, ek step se EAS ko invoke kar de:

.github/workflows/release.yml — GH Actions triggering EAS
name: Mobile release # GitHub Actions workflow ka naam

on: # trigger config
  push: # push event pe
    tags: ['v*'] # version tag pe hi ye release job chalega

jobs: # GitHub Actions ke apne jobs
  trigger_eas_workflow: # job ka naam
    runs-on: ubuntu-latest # GitHub-hosted Ubuntu runner pe chalega (ye khud build nahi karega, sirf EAS ko trigger karega)
    steps: # is job ke steps
      - name: Checkout repo # repo code checkout karne wala step
        uses: actions/checkout@v4 # official checkout action
      - name: Setup Node # Node.js setup step
        uses: actions/setup-node@v4 # official setup-node action
        with: # action ke inputs
          node-version: 20 # Node version pin kiya, reproducibility ke liye
      - name: Install eas-cli # eas-cli install karne wala step
        run: npm install -g eas-cli # global install kiya, taaki eas command available ho
      - name: Trigger EAS Workflow # actual trigger step — GH Actions se EAS Workflows ko call kar rahe hain
        run: eas workflow:run .eas/workflows/build-and-submit.yml --non-interactive # EAS ka apna build+submit pipeline yahan se invoke ho raha hai
        env: # environment variables is step ke liye
          EXPO_TOKEN: ${{ secrets.EXPO_TOKEN }} # GH Actions ke encrypted secrets se EAS auth token pass kiya — GH secret, EAS credential dono ki security boundary respect ho rahi hai
🧠 Senior Dev Note — "best of both worlds" architecture

Is pattern ka fayda: GitHub Actions apna strength (general-purpose orchestration, broad ecosystem, multi-repo/multi-service coordination) use karta hai, jabki actual mobile build/submit/update ka heavy-lifting EAS Workflows ko diya jaata hai jahan wo native primitives se seedha connect hai (kam glue, better error messages, EAS dashboard pe consolidated build history). Ye trade-off nahi hai — dono systems apna sabse strong use-case handle kar rahe hain.

7. Real-World Gotchas

⚠️ YAML syntax errors sirf run-time pe pakde jaate hain

EAS Workflows ke liye abhi tak koi mature local linter/validator nahi hai jo commit karne se pehle YAML structure ko validate kar de (jaisa GitHub Actions ke liye actionlint jaise tools hain). Iska matlab: agar tumne indentation galat kiya, ya ek job ka needs kisi non-existent job ko reference kar diya, ye galti sirf tab surface hogi jab workflow actually run hogi — aur agar ye main pe push trigger hai, matlab production pipeline break ho sakta hai bina warning ke. Practical mitigation: naya ya edited workflow hamesha ek feature branch pe banao, eas workflow:run se manually test karo, aur sirf jab wo clean run kare tabhi main/tag trigger wale path mein merge karo.

🔒 Secrets aur credentials workflow ke andar

Ch.9 mein humne dekha tha ki API keys/secrets ko kabhi bhi client bundle mein hardcode nahi karna chahiye — same principle workflows pe bhi lagu hota hai. Build/submit/update jobs ko jo bhi credentials chahiye (Apple API keys, Play Store service account JSON, Supabase service-role keys agar CI mein backend-side kaam ho raha hai), unhe hamesha EAS Secrets (eas secret:create) ke through store karo, YAML file ke andar plaintext ya even git history mein kabhi nahi. Workflow YAML ke andar secret ko sirf uska reference dikhna chahiye (${{ secrets.MY_SECRET }} jaisa syntax), actual value kabhi commit history mein nahi aani chahiye. Agar galti se ek secret plaintext commit ho jaaye, sirf file delete karna kaafi nahi — git history se bhi purge karna padega aur credential ko turant rotate karna padega, kyunki commit history public repo mein forever queryable hai.

⚠️ Build minutes aur concurrency limits

EAS ke free tier mein build minutes aur concurrent builds dono limited hain (paid plans mein zyada milte hain, lekin unlimited nahi). Agar tumhara workflow design "har single commit pe full E2E suite + iOS + Android build" karta hai, tum bahut jaldi apni monthly build minutes exhaust kar doge — aur phir actual urgent release ke waqt tumhe queue mein wait karna padega ya extra minutes purchase karne padenge. Senior-level mitigation: heavy pipelines (full Maestro E2E suite, dono platform production builds) ko sirf PR merge / tag-based trigger pe rakho, na ki har commit pe. Chhoti, fast checks (lint, unit tests, typecheck) GitHub Actions pe har commit pe chala sakte ho kyunki wo EAS build minutes consume nahi karte — sirf jab code actually release-ready ho tabhi EAS ke costly jobs (build/submit/E2E) trigger karo.

8. Advanced Deep-Dive — Beyond the Basics

Ab tak humne EAS Workflows ke fundamentals dekh liye — basic build, build+submit chain, Maestro gate, aur GitHub Actions ke saath decision framework. Ye section production-grade, multi-team scale pe le jaata hai: matrix builds (ek workflow ko multiple profiles/platforms pe parallel chalana), workflow composition/reuse (monorepo mein duplicate YAML se bachna), aur secrets scoping (least-privilege access per workflow). Ye wahi cheezein hain jo ek senior interview mein "aapne EAS Workflows production mein kaise scale kiya" jaisa follow-up sawaal aane par expect ki jaati hain.

8.1 Matrix Builds — Sequential Nahi, Parallel

Section 3 mein humne build_ios aur build_android ko do alag, explicitly likhe hue jobs ke through parallel chalaya tha. Jaise-jaise combinations badhte hain (2 platforms × 3 profiles = 6 jobs), har combination ko haath se likhna repetitive aur error-prone ho jaata hai — ek platform/profile add karna bhool jaana ek common mistake hai. Matrix builds is repetition ko eliminate karte hain: tum ek hi job definition likhte ho, aur ek matrix block bata deta hai ki kaunse combinations pe usko multiply karna hai — EAS Workflows internally har combination ke liye ek separate job instance spawn karta hai, sab parallel mein.

.eas/workflows/matrix-build.yml — same job, multiple platform+profile combos
name: Matrix build across platforms and profiles # dashboard pe dikhne wala naam

on: # trigger config
  push: # push-based trigger
    tags: ['v*'] # release tags pe hi ye poora matrix chalega — heavy pipeline hai, har commit pe nahi

jobs: # jobs list
  build_matrix: # ek hi job naam, lekin matrix ke through multiple instances mein expand hoga
    type: build # built-in build job type — matrix ke andar bhi wahi job type reuse hota hai
    strategy: # "strategy" block matrix expansion define karta hai
      matrix: # matrix ke axes yahan define hote hain
        platform: [ios, android] # pehla axis — ye do values
        profile: [preview, production] # dusra axis — ye do values, cross-product ho jaayega (2 x 2 = 4 job instances)
    params: # job ke parameters — yahan matrix variables ko reference kiya jaata hai
      platform: ${{ matrix.platform }} # current matrix instance ka platform value yahan inject hota hai
      profile: ${{ matrix.profile }} # current matrix instance ka profile value yahan inject hota hai

Ye single job definition 4 alag build jobs spawn karega — (ios, preview), (ios, production), (android, preview), (android, production) — sab EAS ke infra pe ek saath, parallel chalenge, na ki ek ke baad ek sequentially. Isse total pipeline wall-clock time drastically kam ho jaata hai (4 sequential builds ~40 min lete agar har ek 10 min ki ho, matrix mein sab parallel chalne se poora set ~10-12 min mein complete ho sakta hai, network/queue variance ke saath).

🧠 Senior Dev Note — matrix ka trade-off: speed vs concurrent minutes

Matrix builds "free lunch" nahi hain — ye sirf wall-clock time kam karte hain, total compute/build-minutes consumption same hi rehta hai (ya thoda zyada, queueing overhead ki wajah se), bas sab ek saath consume hota hai instead of spread over time. Agar tumhari EAS plan mein concurrent build ka limit hai (free/lower tiers pe common), toh 4-way matrix ek saath trigger karne se baaki team members ke builds queue mein wait karenge jab tak matrix ke sab jobs slots free nahi karte. Practical rule: matrix ka use tab karo jab latency critical ho (jaise ek release ko jaldi ship karna hai aur team chhota hai, concurrency contention low hai) — na ki har chhote commit pe habitually laga do, warna poori team ke build queue slow ho jaayenge.

8.2 Workflow Composition and Reuse — Monorepo Pattern

Bade orgs mein aksar ek monorepo hota hai jisme multiple RN apps rehte hain (jaise ek consumer app, ek internal admin app, ek partner-facing app) — teeno ka release process similar-but-not-identical hota hai: build steps almost same, lekin submit credentials, bundle identifiers, aur kabhi-kabhi E2E flows alag hote hain. Naive approach har app ke liye poora workflow YAML copy-paste kar dena hai — lekin isse jab bhi ek shared step change ho (jaise "Slack notification add karo har build ke baad"), teeno files mein manually edit karna padega, aur drift ka risk high ho jaata hai.

Do patterns is duplication ko kam karte hain — parameterized/reusable workflows (jo section 5 mein workflow_call ke through dekha tha, wahi concept ab multi-app scale pe) aur per-app thin wrapper workflows jo ek shared "core" workflow ko inputs ke saath call karte hain.

.eas/workflows/_shared-release.yml — parameterized, reusable core pipeline
name: Shared release pipeline # ye "core" workflow hai — direct trigger nahi hoga, sirf dusre workflows se call hoga

on: # trigger config
  workflow_call: # "workflow_call" — matlab ye sirf parameters ke saath invoke hoga, kabhi khud auto-trigger nahi hoga
    inputs: # is shared workflow ke reusable inputs
      app_slug: # kaunsa app hai — "consumer", "admin", "partner"
        required: true # har caller ko app_slug specify karna hi hoga
        type: string # plain string input
      working_directory: # monorepo mein is app ka path — jaise "apps/consumer"
        required: true # har app ka apna path hoga, isliye required
        type: string # plain string input

jobs: # shared jobs list — ye logic sab apps ke liye common hai
  build: # build job, jo caller-specific inputs use karega
    type: build # built-in build job type
    params: # job parameters
      platform: ios # is example mein sirf iOS, real setup mein matrix bhi ho sakta hai
      profile: production # production profile
      working_directory: ${{ inputs.working_directory }} # monorepo mein sahi app folder ke andar se build chalao — ye hi wo cheez hai jo per-app alag hai
.eas/workflows/release-consumer-app.yml — thin per-app wrapper
name: Release — Consumer App # is specific app ka readable naam

on: # trigger config, per-app alag ho sakta hai
  push: # push-based trigger
    tags: ['consumer-v*'] # app-specific tag prefix — teeno apps independently release ho sakte hain, ek dusre ko trigger kiye bina

jobs: # jobs list
  release: # is job ka naam
    uses: ./.eas/workflows/_shared-release.yml # yahan shared/core workflow ko call kiya, duplicate logic likhne ke bajaye
    with: # shared workflow ko pass hone wale inputs
      app_slug: consumer # is app ka slug
      working_directory: apps/consumer # monorepo mein iska path

Is pattern mein, teeno apps (consumer/admin/partner) ke apne chhote wrapper files hain (sirf trigger conditions aur app-specific inputs), lekin actual heavy-lifting logic ek hi _shared-release.yml mein centralized hai. Jab bhi shared logic change karni ho (naya step add karna, existing step ka behavior badalna), ek hi jagah edit karna padta hai — teeno apps automatically updated behavior pick karte hain agli release pe.

💡 Quick Tip

File naming convention _shared-release.yml mein leading underscore purely ek team convention hai (EAS ke liye technically zaroori nahi) — ye sirf ek visual signal hai ki "ye file directly trigger nahi hoti, sirf dusre workflows se called hoti hai." Bade monorepos mein .eas/workflows/ folder jaldi bada ho jaata hai, aur naming se distinguish karna zaroori hai ki kaunsi files entry-points hain aur kaunsi shared building-blocks.

8.3 Secrets Scoping Per Workflow — Least Privilege

Ch.9 mein humne backend secrets ke liye least-privilege principle dekha tha (anon key vs service_role key). Wahi principle EAS Secrets pe bhi apply hota hai, aur senior teams isko per-workflow scoping ke through enforce karte hain — matlab har workflow ko sirf utne hi secrets tak access diya jaata hai jitne uske specific jobs ko chahiye, na ki poore project ke saare secrets tak blanket access.

Concrete example: tumhare paas ek "build only" workflow hai jo sirf preview builds banata hai (internal testing ke liye, kabhi store pe submit nahi karta), aur ek alag "release" workflow hai jo build + submit dono karta hai. "Build only" workflow ko App Store Connect API key ya Play Store service-account JSON ki koi zaroorat hi nahi — wo sirf submission steps use karte hain. Agar phir bhi wo secrets har workflow ko globally available hon (EAS project-level secret ke through, bina scoping ke), toh:

RiskKyun matter karta hai
Larger blast radius agar workflow compromise hoAgar "build only" workflow ke andar koi malicious dependency ya compromised third-party script chal jaaye, aur usko submission credentials tak bhi access ho, toh attacker directly App Store/Play Store pe fraudulent submission bhi kar sakta hai — jabki unscoped access na hone se ye impossible hota
Accidental log leakage ka wider impactAgar koi debug step galti se environment variables print kar de (common mistake), aur workflow ke paas zyada secrets accessible hain, leak hone wale secrets ki list bhi badi hogi
Audit clarity kam ho jaati haiJab har secret har workflow ko available ho, "kaunsa workflow kaunsa credential actually use karta hai" trace karna mushkil ho jaata hai — incident response ke waqt ye slow-down create karta hai

EAS Secrets ko scope karne ka practical tareeka — secret ko environment-level ya specific workflow reference ke through wire karo, aur workflow YAML mein sirf wahi secrets reference karo jo us specific job ko chahiye:

.eas/workflows/build-only-preview.yml — sirf wahi secrets jo chahiye
name: Build only — internal preview # is workflow ka intent naam se hi clear hai — sirf build, koi submit nahi

on: # trigger config
  push: # push-based trigger
    branches: [develop] # develop branch pe har push — frequent, low-stakes internal builds

jobs: # jobs list
  build_preview: # preview build job — koi submit job is file mein hai hi nahi
    type: build # built-in build job type
    params: # job parameters
      platform: ios # iOS preview build
      profile: preview # preview profile — isko sirf signing secrets chahiye, App Store Connect API key bilkul nahi chahiye
      env: # is job ke liye explicitly available environment/secrets
        SUPABASE_URL: ${{ secrets.SUPABASE_URL_STAGING }} # sirf staging backend url — production secret is workflow mein reference hi nahi kiya gaya
        SUPABASE_ANON_KEY: ${{ secrets.SUPABASE_ANON_KEY_STAGING }} # staging anon key — App Store/Play Store submission credentials yahan kahin bhi reference nahi hain
🔒 Senior Dev Note — scoping ek "convention" hai, enforce khud karna padta hai

Important caveat: EAS Secrets khud automatically kisi workflow ko kisi secret se "block" nahi karta agar wo secret project-level available hai — scoping largely discipline aur naming/organization se enforce hoti hai (jaise environment-specific secret names use karna — _STAGING suffix — aur sirf wahi secrets reference karna jo us workflow ko chahiye, dusre available hone ke bawajood). Isliye code review ke waqt naye/edited workflow YAML mein explicitly check karo ki koi unrelated secret galti se reference toh nahi ho gaya — ye ek missable review item hai kyunki ${{ secrets.X }} syntax "harmless" dikhta hai jab tak tumhe pata na ho ki X kya hai aur kya-kya us tak access rakhta hai.

9. 🎯 Interview Questions — Senior React Native Developer

Ye section un sawaalon ko cover karta hai jo senior/staff RN role ke interviews mein CI/CD aur release-engineering discussion ke around aksar puche jaate hain — architecture design, trade-offs, aur incident-response scenarios. Har jawab ek strong senior engineer ki tarah socha gaya hai — sirf "kya karna hai" nahi, balki "kyun" aur "kis cheez ka trade-off hai" bhi.

Q1. Design a CI/CD pipeline for a monorepo with 3 separate RN apps sharing a common package — what would trigger what, and how would you avoid unnecessary rebuilds?

Setup: packages/shared-ui ek common package hai jo teeno apps (apps/consumer, apps/admin, apps/partner) use karte hain. Naive approach — shared-ui mein ek chhota sa change hone par teeno apps ki poori build+submit pipeline trigger kar do — bahut wasteful hai agar change sirf ek app ko relevant hai ya sirf ek internal refactor hai jisse behavior change nahi hua.

Mera design: path-based triggers use karunga (jaisa GitHub Actions paths: filter, ya EAS Workflows mein equivalent path-scoping) taaki har app ka workflow sirf tab trigger ho jab uske apne folder ya shared-ui mein change ho — dono ko watch karna zaroori hai kyunki shared package change teeno apps ko affect kar sakta hai. Isko section 8.2 wale shared/reusable workflow pattern ke saath combine karunga taaki release logic teeno apps mein duplicate na ho. Cache invalidation ke liye, shared-ui ka build output content-hash based cache key use karunga (jaise Turborepo/Nx remote caching), taaki agar shared-ui unchanged hai, downstream app builds usko cache se pull karein na ki rebuild karein. Aur sabse important — heavy jobs (actual EAS build/submit) ko sirf release-tag trigger pe rakhunga, jabki lint/typecheck/unit-test jaise cheap checks har PR pe chalte rahenge (GitHub Actions pe, EAS build minutes consume kiye bina).

🧠 Interviewer kya sunna chahta hai

Yahan interviewer dekh raha hai ki kya tum "trigger scoping" aur "build caching" dono ko alag concerns ki tarah samajhte ho, aur kya tum expensive operations (mobile builds) ko cheap operations (lint/typecheck) se deliberately alag treat karte ho cost-consciousness dikhane ke liye.

Q2. When would you still reach for GitHub Actions alongside EAS Workflows rather than doing everything in EAS Workflows?

Teen concrete scenarios: (1) non-mobile CI needs — agar same repo mein ek web dashboard ya backend service bhi hai jo Vercel/AWS pe deploy hoti hai, EAS Workflows uske liye designed hi nahi hai; GitHub Actions ek hi pipeline mein web + mobile dono orchestrate kar sakta hai. (2) Third-party ecosystem dependency — jaise Slack/Discord notifications, Jira ticket auto-linking, Datadog/Sentry release-marker creation — ye sab GitHub Actions marketplace mein ready-made actions ke through minutes mein wire ho jaate hain, EAS Workflows mein equivalent built-in support abhi limited hai. (3) Existing investment — agar team ke paas already mature, battle-tested GitHub Actions workflows hain (custom actions, secrets already wired, institutional knowledge), migrate karne ka cost aksar benefit se zyada hota hai — better hai ki GitHub Actions apna general CI role continue kare, aur ek step se EAS ko sirf actual build/submit ke liye invoke kare (jo hum section 6 mein dekh chuke hain).

Q3. A workflow accidentally exposed a secret in its logs — walk me through your incident response.

Sabse pehle containment — turant us secret ko rotate/revoke karna, chahe wo Apple API key ho, Play Store service-account JSON ho, ya backend service_role key. Ye sabse pehla step hai kyunki jab tak old credential valid hai, exposure active risk rehta hai — logs delete karne se pehle bhi rotation priority pe hai. Doosra, log cleanup — CI provider ke log retention settings check karo, agar possible ho toh us specific run ke logs delete/redact karo, lekin ye assume mat karo ki delete karne se exposure poori tarah undo ho gayi — agar logs kisi third party service (jaise external log aggregator) mein bhi forward ho rahe the, wahan bhi purge karna hoga. Teesra, root cause — pata karo secret log mein kaise aaya: kya kisi step ne echo $SECRET jaisa debug command chalaya, kya error message mein accidentally credential include ho gaya, ya kya secret masking (jo CI providers usually automatically karte hain known secret strings ke liye) is case mein fail hui. Chautha, prevention — us step ko fix karo (debug logging remove/redact karo), aur team-wide review karo ki kya similar pattern kahin aur bhi hai. Aakhir mein, agar exposure production credentials ka tha aur log kabhi public/wide-access repo mein visible tha, affected stakeholders ko inform karna aur security incident ko formally document karna — chhota lage toh bhi, "silent fix" karke aage badh jaana galat hai kyunki audit trail future incidents ke liye zaroori hota hai.

🔒 Order matters

Interview mein specifically order pe zor do — "rotate first, investigate after" — kyunki bahut candidates galti se "pehle investigate karunga ki kaise hua" bol dete hain, jabki har minute jo credential rotate hone mein delay hoti hai, exposure window badhata hai.

Q4. Explain how needs-based dependency resolution differs from a simple sequential script, and why that matters at scale.

Ek sequential script (jaise ek shell script jo line-by-line eas build phir eas submit chalata hai) mein control flow implicit aur linear hai — agar beech mein koi command fail ho, poora script fail ho jaata hai (ya explicit if [ $? -eq 0 ] checks likhne padte hain). needs-based dependency graph (jo hum section 3 mein dekh chuke hain) ek explicit DAG (directed acyclic graph) define karta hai — jobs bina dependency ke automatically parallel chalte hain, aur failure sirf downstream dependents ko affect karta hai, unrelated parallel branches ko nahi. Scale pe ye matter karta hai kyunki jaise-jaise jobs badhte hain (matrix builds, multiple platforms, E2E gates), manually sequential logic likhna exponentially complex ho jaata hai, jabki DAG approach mein sirf naye node ka needs define karna padta hai — graph khud resolve kar leta hai kaunse jobs parallel chalenge aur kaunse wait karenge.

Q5. Your team wants a "canary" release process — ship to 5% of users first via OTA update, monitor, then roll out to 100%. How would you architect this with EAS Update + Workflows?

Ch.12 ke channels/branches concept ko yahan extend karunga. Ek dedicated canary channel banaunga jo production build se link hai (same runtime version/fingerprint policy). Pipeline: pehle eas update --branch canary se OTA update publish karo — production app users ka koi fixed 5% is channel pe pointed hai (jo backend-side rollout config ya EAS ke rollout percentage feature se control hota hai). Ek monitoring window (jaise 2-4 hours ya jab tak enough crash/error telemetry na aa jaaye — Sentry ya similar tool se) rakhunga, is dauraan crash rate aur key metrics (jaise checkout completion rate agar e-commerce app hai) baseline se compare karunga. Agar metrics healthy hain, ek doosra workflow step (ya manual approval gate) full production channel pe wahi update publish kar dega. Agar metrics degrade hue, eas update:rollback (ch.12 mein dekha tha) canary channel pe turant chalega — bina naya native build banaye, kyunki ye pure OTA-level rollback hai.

🧠 Senior Dev Note — automated gate vs human gate

Ye sawaal deliberately open-ended hai — ek achha jawab explicitly mention karta hai ki "canary → full rollout" step ko fully automated (metrics threshold based) banaya ja sakta hai ya human approval gate rakha ja sakta hai. High-stakes apps (payments, healthcare) mein human gate safer hai; high-velocity, well-instrumented apps mein automated threshold-based promotion feasible hai. Interviewer isse tumhara risk-judgment dekhta hai, sirf technical implementation nahi.

Q6. What's the difference between build-time failure and OTA-update-time failure in terms of blast radius, and how does your CI/CD design account for that?

Build-time failure (jaise ek native build crash on launch, jo store review se bhi slip ho gaya) ka blast radius bounded aur slow hota hai — sirf naye installs/updates affected hote hain, aur App Store/Play Store review + staged rollout (ch.14 mein dekha) natural buffer dete hain. OTA update failure (jaise EAS Update se ek broken JS bundle publish ho jaana) ka blast radius immediate aur bahut zyada wide hota hai — jitne bhi users us channel pe hain, unko turant naya bundle mil jaata hai, aur agar wo crash karta hai, sab affected users ek saath crash experience karenge, bina kisi staged rollout buffer ke (agar percentage rollout use nahi kiya). Isliye mera CI/CD design OTA updates ke liye zyada conservative gates rakhta hai: mandatory Maestro E2E gate (section 4), staged percentage rollout jahan possible ho, aur ek fast, tested rollback path (eas update:rollback) jo bina naye build cycle ke seconds mein revert kar sake — jabki native build failures ke liye recovery path zyada dheema hai (naya build, naya App Store review cycle) isliye unpe zyada pre-release testing (TestFlight/internal testing tracks) invest karta hoon.

Q7. How would you prevent a workflow from accidentally submitting to production if a required E2E test was skipped due to a flaky infrastructure issue rather than a real failure?

Ye ek subtle risk hai — agar maestro_e2e job "skip" ho jaaye (jaise runner infra issue ki wajah se, na ki actual test failure), aur agar downstream submit job ki needs logic sirf "job fail nahi hua" check karti hai (na ki "job explicitly pass hua"), toh submit galti se chal sakta hai bina real E2E validation ke. Mitigation: workflow ko design karo taaki needs-based skip semantics explicitly verify ho — zyada platforms mein "skipped" aur "succeeded" alag states hote hain, aur dependent job ko sirf "succeeded" pe hi proceed karna chahiye, "not failed" pe nahi. Iske saath, infra flakiness ko reduce karne ke liye retry logic (jaise ek automatic retry agar Maestro runner infra-level error de, test-assertion failure na ho) aur alerting add karunga — agar E2E job baar-baar skip/retry ho raha hai, ye khud ek signal hai ki runner infra unhealthy hai aur usko investigate karna chahiye, na ki silently ignore karke release continue karna.

Q8. Design a rollback strategy that covers three failure modes: (a) bad native build already in store review, (b) bad OTA update already live, (c) a leaked secret used in a completed build.

Teeno alag layers pe hain, isliye teen alag responses chahiye. (a) Bad native build in review — App Store Connect/Play Console se submission ko reject/cancel karo agar review abhi pending hai (ch.14 ke submission checklist se related); agar already approved aur live ho chuka hai, ek hotfix build jaldi banao aur expedited review request karo (Apple expedited review process), aur agar OTA-fixable issue hai (JS-only bug), turant ek OTA update push karo taaki users ko fix mile bina store review wait kiye. (b) Bad OTA update live — eas update:rollback immediately chalao us channel pe — ye sabse fast recovery hai kyunki koi build/review cycle nahi chahiye, seconds-to-minutes mein revert ho jaata hai. (c) Leaked secret in completed build — ye sabse tricky hai kyunki build already distributed ho chuki hai; credential ko turant rotate karo (jaise Q3 mein discuss kiya), lekin note karo ki agar secret client-bundle mein embed tha (jaise galti se hardcoded API key jo bundle mein compile ho gaya), sirf rotation kaafi nahi — already-installed app instances still purane, ab-invalid secret ke saath chal rahe honge jab tak wo update na karein, isliye ek forced-update mechanism (OTA update jo naya secret-free code deploy kare, combined with app-side version-check jo purane clients ko update karne pe force kare) zaroori ho sakta hai depending on severity.

🧠 Interviewer kya test kar raha hai

Is sawaal ka goal ye dekhna hai ki kya tum samajhte ho ki native build, OTA update, aur credential/secret teeno alag "planes" pe exist karte hain, har ek ka apna recovery mechanism aur apna recovery speed hai — aur ek acha senior engineer in teeno ko conflate nahi karta, har situation ke liye sahi tool reach karta hai.
