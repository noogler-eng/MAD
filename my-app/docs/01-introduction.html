Kya hai React Native aur Expo

Chalo bilkul shuru se pakadte hain. React Native (RN) ek framework hai jo Facebook (ab Meta) ne 2015 mein release kiya tha, jiska idea simple tha — "aap React ka mental model (components, JSX, state, props) use karke actual native iOS aur Android apps bana sako, web view nahi, real native UI components (UIView, android.view.View)". Shuru mein iska architecture ek "Bridge" pe based tha — JavaScript thread ek alag thread pe chalta tha, aur native side (iOS/Android) ek alag thread pe. Dono ke beech communication hoti thi async, batched, JSON-serialized messages ke through. Matlab agar aapko JS se ek native button ka color change karna hai, to JS ek message JSON stringify karke bridge pe daalta tha, native side use parse karta tha, action perform karta tha, aur result wapas JSON serialize karke bhejta tha. Ye kaam karta tha, lekin jaise jaise apps complex hue (lists, animations, gestures), ye serialization overhead aur async nature bottleneck ban gaya — especially jab aapko synchronous, high-frequency communication chahiye thi (jaise scroll position ya gesture tracking). Isi problem ko solve karne ke liye Meta ne pichle kuch saalon mein poora "New Architecture" phir se likha — jisme Bridge ki jagah JSI (JavaScript Interface) aata hai, jo JS aur native code ko directly, synchronously call karne deta hai bina JSON serialize kiye (isko hum next section mein deeply dekhenge).

Ab baat karte hain Expo ki. Ye ek common misconception hai ki "Expo aur React Native do alag cheezein hain, ya Expo RN ka competitor/replacement hai" — ye bilkul galat hai. Expo ek platform aur toolchain hai jo React Native ke upar banaya gaya hai. Jab aap npx create-expo-app chalate ho, andar se still React Native hi chal raha hota hai — Expo bas aapko in cheezon ka ek batteries-included layer deta hai:

  • Expo SDK — pre-built native modules (camera, location, notifications, file system, etc.) jo already tested aur cross-platform consistent hain, taaki aapko har cheez ke liye khud native module likhna na pade.
  • Expo CLI + EAS (Expo Application Services) — build, submit aur OTA update ka poora cloud-based pipeline, bina aapko Xcode/Android Studio ki har config khud manage karne ki zaroorat ho (though aap chaho to still kar sakte ho).
  • Expo Router — file-based routing (Next.js jaisa mental model), jo hum Chapter 4 mein detail se dekhenge.
  • Config-based native project generation — app.json/app.config.ts se poora ios/ aur android/ native project generate ho jaata hai (isko "Prebuild" kehte hain), jisse aapko native folders ko manually maintain nahi karna padta.

Historically Expo ke do workflows the: Managed Workflow (jisme aapke paas ios//android/ native folders bilkul nahi hote, sab kuch Expo manage karta tha, lekin limitation ye thi ki aap custom native code add nahi kar sakte the) aur Bare Workflow (jisme aap poore native project ke owner ho, custom native modules likh sakte ho, lekin phir Expo ke convenience features kam mil paate the). Ye distinction ab largely obsolete ho chuka hai — modern Expo (SDK 45+) mein "Development Builds" concept aane ke baad, aap managed-jaisi DX rakhte hue bhi custom native modules add kar sakte ho (isko hum Section 4 mein detail se explain karenge). Yehi wajah hai ki Expo ab industry standard ban chuka hai — pehle "Expo sirf prototyping/hobby projects ke liye hai" wali reputation thi, lekin ab bade production apps (Discord jaisa scale bhi) Expo pe chal rahe hain, kyunki New Architecture, Dev Builds aur EAS ne wo saari limitations hata di jo pehle managed workflow mein thi.

🧠 Senior Dev Note

Jab koi interview mein pooche "Expo vs React Native, kaunsa use karoge?" — ye galat framing hai, sahi jawab hai "Expo hamesha use karunga, kyunki wo RN hi hai bas better DX ke saath". Sirf ek genuine case hai jahan aap "bare RN CLI" (bina Expo ke) choose karoge — agar aapko kisi legacy/brownfield native app mein RN ko integrate karna hai (existing native codebase ke andar), tabhi Expo ka poora tooling overkill ho sakta hai. Naye greenfield project ke liye, Expo hi default choice honi chahiye 2024+ mein.

Development Environment Setup

Environment setup ko "just run the installer" jaisa treat mat karo — samjho ki har piece kya kaam kar raha hai, taaki jab kal koi weird error aaye, aap root cause pakad sako.

Node, npm/yarn/pnpm, aur Expo CLI

React Native/Expo tooling (Metro bundler, CLI scripts, codegen) sab Node.js pe chalta hai — ye baat confuse mat karo ki "React Native to mobile app hai, Node kyun chahiye" — Node sirf build-time tooling ke liye chahiye, aapki actual app JS engine (Hermes) pe runtime mein chalti hai, Node pe nahi. Package manager (npm/yarn/pnpm) mein se koi bhi chalega, lekin senior teams mostly pnpm prefer karti hain bade monorepos mein kyunki wo disk space aur install speed dono mein better hai (content-addressable storage + symlinks), jabki chhote/solo projects ke liye npm hi kaafi hai (Expo docs bhi default npm assume karte hain). Expo CLI ab separately install karne ki zaroorat nahi — modern Expo mein CLI local devDependency ke through npx expo se hi chalti hai (global install ka pattern deprecated ho chuka hai, kyunki version mismatch issues create karta tha).

terminal
# Naya Expo project banane ka standard tareeka
npx create-expo-app@latest my-app --template

# Project ke andar CLI commands local se chalti hain
cd my-app
npx expo start

# Cache clear karke start (bahut common debugging step)
npx expo start -c

Android Studio + Emulator ka internal setup

Android emulator ko log log "bas ek app jo phone jaisa dikhta hai" samajhte hain, lekin actually ye AVD (Android Virtual Device) hai — ek full virtualized Android system image jo QEMU (Quick EMUlator) ke upar chalta hai, with hardware acceleration (macOS pe HAXM/Hypervisor.framework, Windows/Linux pe usually KVM ya WHPX). Jab aap Android Studio mein AVD Manager se ek device banate ho, aap effectively ek poora Android OS image (system.img) download kar rahe ho jo specific API level (jaise API 34 = Android 14) ke saath aata hai, aur wo image ek isolated virtual machine mein boot hota hai — isiliye emulator start hone mein time leta hai (poora OS boot ho raha hai) aur RAM/CPU zyada consume karta hai. Setup steps: Android Studio install karo → SDK Manager se ek Android SDK Platform + one system image install karo → AVD Manager se virtual device create karo → environment variables set karo (ANDROID_HOME, aur platform-tools ko PATH mein add karo) taaki adb command line se accessible ho.

Xcode + iOS Simulator

iOS Simulator, Android emulator jaisa full virtualization nahi hai — ye actually macOS pe hi native x86/ARM binaries compile aur run karta hai jo iOS APIs ko simulate karte hain (isiliye Simulator itna fast hai compare to real hardware testing ke, lekin isi wajah se kuch cheezein jaise camera, push notifications ka real behavior, ya performance profiling Simulator pe accurate nahi hoti — un cheezon ke liye real device chahiye hota hai). Setup: Mac App Store se Xcode install karo, Xcode → Settings → Platforms se ek iOS Simulator runtime download karo, aur command line tools (xcode-select --install) setup karo taaki expo run:ios jaise commands kaam karein.

⚠️ Gotcha

iOS Simulator sirf macOS pe available hai — Windows/Linux pe aap sirf Android emulator ya physical device (Expo Go ya dev build install karke) use kar sakte ho. Ye ek common reason hai ki teams M-series MacBooks ko standard dev machine banate hain.

Environment Variables: .env, app.json vs app.config.ts

Expo project mein config file do forms mein aa sakti hai — static app.json, ya dynamic app.config.js/app.config.ts. Beginner projects app.json se start karte hain kyunki wo simple JSON hai, lekin senior/production setup mein app.config.ts hi sahi choice hai, kyunki:

  • Ye ek JS/TS file hai, matlab aap ismein logic likh sakte ho — jaise environment ke hisaab se (dev/staging/prod) different bundle identifier, app name, ya API URL set karna.
  • TypeScript ke through aapko type safety aur autocomplete milta hai config likhte waqt, jisse typo-based bugs (jaise galat key name) build time pe hi pakad mein aa jaate hain.
  • Aap environment variables ko process.env se directly read karke config mein inject kar sakte ho, jo static JSON mein possible nahi hai.
app.config.ts
import { ExpoConfig, ConfigContext } from 'expo/config';

// Environment ke hisaab se alag values — CI/EAS in env vars ko inject karta hai
const APP_ENV = process.env.APP_ENV ?? 'development';

const ENV_CONFIG = {
  development: { name: 'MyApp (Dev)', bundleId: 'com.mycompany.myapp.dev' },
  staging:     { name: 'MyApp (Staging)', bundleId: 'com.mycompany.myapp.staging' },
  production:  { name: 'MyApp', bundleId: 'com.mycompany.myapp' },
};

export default ({ config }: ConfigContext): ExpoConfig => ({
  ...config,
  name: ENV_CONFIG[APP_ENV as keyof typeof ENV_CONFIG].name,
  slug: 'myapp',
  ios: {
    bundleIdentifier: ENV_CONFIG[APP_ENV as keyof typeof ENV_CONFIG].bundleId,
  },
  android: {
    package: ENV_CONFIG[APP_ENV as keyof typeof ENV_CONFIG].bundleId,
  },
  extra: {
    // runtime pe Constants.expoConfig.extra se accessible hota hai
    apiUrl: process.env.API_URL,
    eas: { projectId: 'your-eas-project-id' },
  },
});
🔒 Security Critical

Kabhi bhi .env file (real API keys/secrets ke saath) commit mat karo — hamesha .gitignore mein add karo aur ek .env.example (dummy values ke saath) rakho documentation ke liye. Aur ek aur important cheez: agar aap koi env variable EXPO_PUBLIC_ prefix ke saath likhte ho (jaise EXPO_PUBLIC_API_URL), to Expo use build-time pe JS bundle ke andar literally inline (hardcode) kar deta hai — matlab ye client-side JS bundle ke andar plaintext mein pada hoga, jise koi bhi decompile/inspect karke padh sakta hai. Isiliye EXPO_PUBLIC_ prefix wale variables mein kabhi secret keys, private tokens ya server-only credentials mat daalo — ye "public" hain by design, sirf public config (jaise ek public API base URL) ke liye use karo. Real secrets sirf server-side/backend mein rehne chahiye, kabhi client bundle mein nahi.

React Native New Architecture (Fabric + TurboModules + JSI)

Ye section is chapter ka sabse "root-level" hissa hai — chalo dekhte hain ki React Native internally actually kaam kaise karta hai, purane Bridge model se leke naye JSI-based model tak.

Old Architecture: The Bridge

Purane RN mein teen alag "worlds" the: JS thread (jahan aapka React code chalta hai), Native/UI thread (jahan actual native views render hoti hain), aur inke beech ek Bridge. Bridge ka kaam tha in dono worlds ke beech messages pass karna — lekin critical baat ye thi ki communication asynchronous thi aur har message JSON serialize karke bheja jaata tha. Matlab agar JS ko native se koi data chahiye (jaise "is view ka current width kya hai"), to: JS ek message queue mein request daalta → serialize hoti → bridge cross karti → native side deserialize karta → process karta → response phir serialize hoke wapas aata → JS deserialize karta. Ye poora round-trip async tha (kabhi turant nahi mil sakta result), aur high-frequency operations (jaise scroll events, gesture tracking, ya animations) ke liye ye serialization overhead ek real performance bottleneck ban jaata tha — isiliye purane RN mein complex gesture-driven animations ko native thread pe "offload" karna padta tha (Reanimated 1/2 ka poora design isi limitation ke around tha).

New Architecture: JSI, Fabric, TurboModules, Hermes

New Architecture ne is poore model ko replace kar diya. Core piece hai JSI (JavaScript Interface) — ye ek C++ layer hai jo JS engine (Hermes) ko directly native C++ objects ke saath bind karta hai. Isse JS code native functions ko synchronously, directly call kar sakta hai — bina JSON serialize kiye, bina async queue ke through jaaye. JS objects ab native C++ "Host Objects" ko directly hold kar sakte hain aur unke methods call kar sakte hain jaise wo normal JS objects hon.

Old Bridge vs New JSI (conceptual)
OLD ARCHITECTURE (Bridge)
┌─────────────┐        async, JSON-serialized        ┌──────────────┐
│  JS Thread   │ ───────────── queue ───────────────▶ │ Native Thread │
│ (React code) │ ◀──────────── queue ───────────────  │ (UIView etc.) │
└─────────────┘        batched, no sync calls         └──────────────┘

NEW ARCHITECTURE (JSI)
┌─────────────┐                                       ┌──────────────┐
│  JS Thread   │ ◀════ JSI: direct C++ binding ══════▶ │ Native Thread │
│  (Hermes)    │      synchronous, no serialization    │ (Fabric/C++)  │
└─────────────┘                                       └──────────────┘
        │                                                     │
        ▼                                                     ▼
   TurboModules                                          Fabric Renderer
 (lazy-loaded native                                 (concurrent, host-tree
  modules, on-demand)                                    reconciliation)

Is JSI foundation ke upar do bade pieces bane hain:

  • Fabric (naya renderer) — purana renderer JS aur native ke beech tree diffing ke liye bhi bridge use karta tha, batched aur async. Fabric ab JSI ke through directly kaam karta hai, aur React 18 ke concurrent rendering features (jaise priority-based updates) ko native side tak properly propagate karta hai. Fabric ek naya "Shadow Tree" (host component tree) maintain karta hai jo C++ mein hai aur JS thread ke saath synchronously interact kar sakta hai — isse layout calculations aur commits zyada predictable aur fast hote hain.
  • TurboModules — purane NativeModules system mein saare native modules app start hote hi eagerly initialize ho jaate the, chahe aap use karo ya na karo — isse app startup time badhta tha. TurboModules JSI use karke modules ko lazy-load karte hain — matlab ek native module tabhi initialize hota hai jab JS code use pehli baar actually require/access karta hai. Isse app startup fast hota hai, especially bade apps mein jahan dozens of native modules hote hain.

Hermes Engine

Hermes Meta ka apna JavaScript engine hai (V8 ya JSC ka alternative), jo specifically React Native ke liye optimize kiya gaya hai. Iska sabse bada trick hai bytecode precompilation — normal JS engines (jaise JSC) app ke JS source code ko device pe runtime mein parse aur compile karte hain (jo startup time lagata hai), jabki Hermes build time pe hi JS ko bytecode mein precompile kar deta hai. Runtime pe device sirf bytecode load aur execute karta hai — parsing step skip ho jaata hai. Isse app startup time (TTI — Time To Interactive) significantly improve hota hai, especially lower-end Android devices pe. Yehi wajah hai ki Hermes ab RN mein default engine hai (SDK 46+ se) — aur New Architecture ke saath Hermes hi best supported/tested combination hai.

🧠 Senior Dev Note

Interview mein agar pooche "New Architecture kyun better hai", sirf "fast hai" mat bolo — specifically bolo: "JSON serialization overhead khatam hua kyunki JSI synchronous, direct C++ bindings deta hai; TurboModules lazy-loading se startup improve karta hai; aur Fabric concurrent rendering ko properly support karta hai jo React 18 features (jaise useTransition) ko native side tak le jaata hai." Ye depth interviewer ko turant dikha degi ki aapne sirf marketing blog nahi padha, internals samjhe hain.

Expo Go vs Development Builds

Ye ek aisa topic hai jahan bahut saare beginners confuse ho jaate hain, aur agar aapne galat choice kiya to baad mein migration paining ho sakti hai. Chalo dono ko root se samajhte hain.

Expo Go ek generic, pre-built native app hai jo App Store/Play Store se directly install hoti hai. Ye ek "universal runtime" hai — iske andar already Expo SDK ke saare common native modules compiled/baked-in hain. Jab aap expo start chalate ho aur QR code scan karte ho, actually koi naya native binary nahi ban raha — Expo Go app aapke JS bundle ko download aur interpret kar rahi hai apne already-existing native shell ke andar. Isi wajah se Expo Go itna fast hai iterate karne ke liye (bina native rebuild ke, bas JS reload). Lekin yehi iski fundamental limitation bhi hai — kyunki native binary already fixed/pre-built hai, aap koi custom native module (jaise koi third-party library jisme native iOS/Android code ho, ya khud likha hua native module) add nahi kar sakte — Expo Go sirf wahi native modules support karta hai jo usme already bundled hain.

Development Build iska solution hai — ye aapki apni custom native binary hai, jisme expo-dev-client included hota hai (jo Expo Go jaisa hi dev experience deta hai — QR scan, fast refresh, error overlay — lekin ab ye binary aapke project ke specific native dependencies ke saath ban chuki hai). Ye binary ya to cloud mein EAS Build se banti hai, ya locally expo run:ios / expo run:android commands se (jo pehle native project generate karte hain — "prebuild" — aur phir Xcode/Gradle se actual build chalate hain). Development build ke saath aap koi bhi native module add kar sakte ho — chahe wo Expo SDK ka ho, third-party (jaise react-native-mmkv) ho, ya khud likha hua custom native module ho.

CriteriaExpo GoDevelopment Build
Custom native modules Nahi (sirf jo already Expo Go mein bundled hain) Haan, koi bhi native module add kar sakte ho
OTA updates N/A (Expo Go khud ek shared app hai) Haan, EAS Update se JS-only changes bina store review ke push kar sakte ho
Build time Zero — instantly connect ho jaata hai Pehli baar 5–20 min (cloud/local build), phir sirf JS reload fast hai
Use case Bilkul shuruaati prototyping, learning, quick demos Real projects — jaise hi ek bhi custom native dependency chahiye, migrate karo

Migration path: Naya project Expo Go se start karna bilkul fine hai jab tak aap sirf core Expo SDK modules use kar rahe ho. Jaise hi project ko koi aisi library chahiye jo Expo Go mein support nahi hai (error milega: "This module cannot be used in Expo Go"), ya jaise hi aapko production ke liye custom native config (jaise push notification certificates, ya native SDK integration jaise Firebase/Stripe) chahiye — npx expo install expo-dev-client karke development build pe switch kar do. Ye ek one-way, low-friction migration hai — aapka JS code same rehta hai, sirf ab aap Expo Go ki jagah apni khud ki dev build app use kar rahe ho.

💡 Quick Tip

Rule of thumb: agar aap ye chapter padh rahe ho aur real production app bana rahe ho, Day 1 se hi development build pe chale jao. Expo Go sirf learning/prototype ke liye best hai — real projects mein aksar koi na koi native dependency jaldi aa hi jaati hai.

Project Folder Structure (Scalable, Senior-Level)

Ek chhota project kaisa bhi structure ho chal jaata hai, lekin jaise jaise team aur codebase badhta hai, folder structure hi decide karta hai ki codebase maintainable rahega ya spaghetti ban jaayega. Yahaan ek production-grade Expo Router app ka recommended structure hai:

folder structure
my-app/
├── app/                      # Expo Router root — sirf routing/screens yahan, kyunki route resolution isi folder ke naam pe depend karta hai
│   ├── (auth)/               # route GROUP — login/signup ko isolate kiya taaki inka apna _layout ho aur auth guard inhe ek unit ki tarah treat kar sake
│   │   ├── login.tsx         # route "/login" — file ka naam hi URL path banta hai, isliye naming consistent rakhna zaroori hai
│   │   └── signup.tsx        # route "/signup" — auth group ke andar isliye ki logged-out user isi tree mein rahe
│   ├── (tabs)/               # dusra route group — logged-in tab navigation, alag rakha taaki auth vs main-app ka concern separate ho
│   │   ├── home.tsx          # tab ka pehla screen — feature logic yahan nahi likhi, sirf features/ se import karke render karta hai
│   │   └── profile.tsx       # dusra tab screen — isi wajah se thin, taaki route file sirf "wiring" kare, business logic nahi
│   └── _layout.tsx           # root layout — auth-guard redirect logic yahan likhi jaati hai kyunki ye sabse pehle mount hota hai
│
├── src/                      # saara "real" application code yahan — app/ se alag isliye taaki routing aur logic mix na ho
│   ├── features/             # feature-based grouping (NOT type-based) — reason: ek feature ka saara code ek jagah, easy onboarding + kam merge conflicts
│   │   ├── auth/             # "auth" feature ka apna self-contained folder — delete/refactor karna ho to bas ye ek folder touch karna hai
│   │   │   ├── components/   # feature-specific UI — isliye yahan rakha kyunki koi aur feature inhe reuse nahi karega
│   │   │   ├── hooks/        # useLogin, useAuthState, etc. — feature-scoped state/logic, global hooks/ mein nahi rakha kyunki sirf auth ko chahiye
│   │   │   ├── api/          # login(), refreshToken() calls — network calls ko component se alag rakha taaki UI aur data-fetching independently test ho sakein
│   │   │   └── types.ts      # is feature ke TypeScript types — colocated taaki type aur usage saath change ho, alag drift na kare
│   │   └── feed/             # dusra independent feature, same internal shape jitna possible — consistency se navigate karna easy hota hai
│   │       ├── components/   # feed-specific UI, auth/components se koi dependency nahi (features cross-import nahi karte)
│   │       ├── hooks/        # feed-scoped hooks
│   │       └── api/          # feed-related network calls
│   │
│   ├── components/           # truly shared/reusable UI (Button, Card, Input) — sirf tab jab 2+ features same component use karein, "rule of three"
│   ├── hooks/                # app-wide generic hooks (useDebounce, useAppState) — feature-agnostic hone chahiye, warna feature folder mein hi rakho
│   ├── lib/                  # third-party client setup (axios instance, mmkv, analytics) — alag rakha taaki config ek jagah se manage ho, spread na ho
│   ├── services/             # cross-cutting backend integration layer, features ke api/ folders se upar ki generic infra
│   │   └── api/               # base API client, interceptors — auth token attach jaisa cross-feature logic yahan, taaki har feature isse reuse kare
│   ├── store/                # global state (zustand/redux slices) — sirf genuinely cross-feature state yahan, feature-local state feature ke andar hi
│   ├── constants/             # colors, spacing, config constants — single source of truth taaki magic numbers/hex codes har jagah copy-paste na ho
│   └── types/                 # global/shared TypeScript types — sirf wahi types jo 2+ features share karte hain, warna feature-local types.ts behtar
│
├── assets/                    # fonts, images, lottie files — app/src code se alag isliye ki ye static binary assets hain, code nahi
├── app.config.ts              # typed Expo config — app.json ki jagah isliye kyunki isme TypeScript se env-based conditional config likh sakte hain
├── .env.example                # kaunse env vars chahiye uska template — real .env commit nahi hota (gitignored), ye sirf documentation ke liye hai
└── package.json                # dependencies aur scripts — root pe isliye kyunki poore project ka single dependency tree hona chahiye

Sabse important architectural decision yahaan hai "feature folder" pattern vs "type folder" pattern. "Type folder" pattern (jo bahut beginners default karte hain) ka matlab hai sab components ek components/ folder mein, sab hooks ek hooks/ folder mein, sab API calls ek api/ folder mein — bina feature ke hisaab se group kiye. Ye chhote projects mein theek lagta hai, lekin jaise hi project 50-100+ files tak badhta hai, problem ye hoti hai ki ek single feature (jaise "checkout flow") ka code teen-chaar alag folders mein bikhra hota hai — aur agar aapko us feature ko samajhna ya modify karna hai, aapko poore codebase mein jump karna padta hai.

Feature folder pattern is problem ko solve karta hai — har feature (auth, feed, checkout, profile) apna khud ka self-contained folder rakhta hai jisme uske components, hooks, API calls, aur types sab ek jagah hain. Ye ek senior architect ki tarah sochne wali baat hai: "cheezein jo saath mein change hoti hain, unhe saath mein rakho" (co-location principle) — isse (1) naye developer ko onboard karna easy hota hai (bas ek folder samjho, poora feature samajh aa jaata hai), (2) bade teams mein alag-alag developers alag features pe kaam karte waqt merge conflicts kam hote hain, aur (3) agar kabhi koi feature deprecate/remove karni ho, to bas ek folder delete karna hota hai, poore codebase mein dhoondhna nahi padta. Sirf genuinely shared, cross-feature cheezein (jaise ek generic <Button /> component ya ek useDebounce hook) top-level src/components ya src/hooks mein jaati hain.

ℹ️ Info

Notice karo app/ folder (Expo Router routes) mein hum bahut thin screens rakhte hain — actual logic src/features/* mein hota hai, aur route file bas us feature ke component ko import karke render karta hai. Isse routing layer aur business logic layer clearly separate rehte hain.

Real-World Gotchas & Anomalies (Day-1 se hi zaroori)

Ye wo cheezein hain jo docs mein kabhi properly explain nahi hoti, lekin har senior dev ne apne career mein kam se kam ek baar face ki hain — Day 1 se pata hona chahiye taaki hours waste na ho debugging mein.

⚠️ Metro Bundler Cache Issues

Metro (RN ka JS bundler) aggressively cache karta hai transformed files ko speed ke liye. Kabhi kabhi — especially jab aap babel.config.js, metro.config.js change karte ho, ya koi naya native module add karte ho — Metro purana cached bundle serve karta rehta hai aur aapko lagta hai "code change hua hi nahi". Fix simple hai: npx expo start -c (cache clear karke start). Agar wo bhi kaam na kare, node_modules/.cache aur .expo folder manually delete karo.

⚠️ Watchman Issues on Mac

macOS pe Metro file changes detect karne ke liye Watchman (Facebook ka file-watching service) use karta hai. Kabhi kabhi Watchman ka internal state corrupt ho jaata hai (especially bade monorepos mein, ya jab bahut saari files rapidly change hoti hain — jaise git branch switch), aur hot-reload kaam karna band kar deta hai bina koi error diye. Fix: watchman watch-del-all chala ke Watchman ka state reset karo, phir Metro restart karo.

🔒 "App sirf release build mein crash hoti hai, dev mein nahi"

Ye ek bahut common aur confusing anomaly hai. Common causes: (1) dev-only code paths — kabhi kabhi aap if (__DEV__) checks pe depend kar lete ho bina realize kiye, aur release build mein wo path hi nahi chalta; (2) console.log stripping — release builds mein console statements strip ho sakte hain configuration ke hisaab se, aur agar aapka code kisi console call ke side-effect pe accidentally depend karta hai, wo break ho jaata hai; (3) Hermes bytecode differences — dev mode mein JS interpret directly ho sakta hai jabki release mein precompiled Hermes bytecode chalta hai, aur kuch edge-case JS behaviors (jaise certain polyfills ya minification-related issues) sirf release build mein surface hote hain; aur (4) ProGuard/R8 minification (Android) jo release build mein class/method names rename kar sakta hai, aur agar koi native module reflection use kar raha hai class names pe, wo crash kar sakta hai. Debugging tip: hamesha ek local release build banao (eas build --profile preview ya expo run:android --variant release) aur usse test karo, sirf dev build pe bharosa mat karo before shipping.

⚠️ Expo SDK aur Native Module Version Mismatch

Har Expo SDK version ek specific React Native version ke saath paired hoti hai, aur Expo SDK modules (jaise expo-camera, expo-location) ki bhi specific versions us SDK ke saath compatible hoti hain. Agar aap manually koi Expo package ka version bump/downgrade karte ho bina npx expo install --check use kiye, aap version mismatch mein fasa sakte ho — jo aksar runtime crash (silent native crash, bina clear JS error ke) ke roop mein manifest hota hai, kyunki native binary ek version expect kar raha hota hai jabki JS side dusra version bhej raha hota hai. Hamesha npx expo install use karo naye Expo-aware packages install karne ke liye (npm/yarn install ki jagah), aur npx expo-doctor se periodically version health check karo.

Advanced Deep-Dive — Beyond the Basics

Ye section un cheezon ko cover karta hai jo aapko interview mein "impressive" nahi, balki genuinely useful banati hain jab production mein kuch ajeeb break ho — kyunki tab aapko internals pata honi chahiye, sirf "how to use" nahi. Chalo Hermes ke bytecode pipeline se shuru karte hain, phir prebuild/CNG ka poora mental model, ek JS engine comparison, aur monorepo setups.

Hermes Bytecode Compilation — Actually Kya Hota Hai Build Time Pe

Upar humne bola "Hermes bytecode precompile karta hai", lekin chalo isko step-by-step todte hain taaki ye sirf ek marketing line na lage, balki aapko pipeline samajh aaye. Normal JS engine jaisa JSC (JavaScriptCore) ek JIT (Just-In-Time) compiler hai — matlab jab app device pe launch hoti hai, JSC pehle poore JS bundle ko parse karta hai (text → AST), phir usse bytecode/machine code mein compile karta hai, aur phir execute karta hai — aur ye sab runtime pe, device pe hi, har baar app open hone pe hota hai (kuch caching JSC bhi karta hai, lekin cold start pe full parse+compile cost lagti hai). Isi wajah se bade JS bundles (jaise 5-10 MB ka production bundle) JSC pe slow cold-start dete hain, especially low-end Android devices pe jinka CPU parse+compile ke liye already slow hota hai.

Hermes iska ulta approach leta hai — ye AOT (Ahead-Of-Time) compilation model hai. Jab aap eas build ya expo run:android/ios chalate ho, build pipeline ke andar ek step hota hai jahan poora JS bundle (jo Metro ne banaya) hermesc (Hermes compiler binary) ke through pass hota hai, jo JS source ko parse karke usse Hermes Bytecode (HBC) format mein compile kar deta hai — ek compact, binary, stack-machine-style bytecode jo directly Hermes VM execute kar sakta hai. Ye compiled .hbc file (jo actually index.android.bundle ke naam se hi APK/IPA ke andar embed hoti hai, bas format bytecode hota hai text JS ki jagah) app binary ke andar ship hoti hai. Runtime pe, jab app launch hoti hai, Hermes VM sirf ye pre-compiled bytecode load aur execute karta hai — parse ya compile karne ka koi step hi nahi bachta device pe. Yehi wajah hai ki Hermes wale apps ka TTI (Time To Interactive) significantly better hota hai — aap ek poori compile-time cost ko build machine pe move kar rahe ho (jahan CPU powerful hai aur ek baar ka cost hai), device se hata ke (jahan har user, har launch pe wo cost bhugatta).

Hermes build pipeline (conceptual)
# Step 1 — Metro bundler poora JS/TS source ko ek single JS bundle mein resolve+transform karta hai
npx metro build --entry-file index.js --out bundle.js

# Step 2 — Hermes compiler (hermesc) is JS bundle ko binary bytecode mein AOT compile karta hai
# ye step build machine pe hota hai (CI/EAS build server), device pe nahi
hermesc --emit-binary bundle.js -o index.android.bundle

# Step 3 — ye .hbc (Hermes ByteCode) file hi final app binary (APK/IPA) ke andar embed hoti hai
# runtime pe Hermes VM isse directly load karke execute karta hai — koi parse/compile step nahi
# is wajah se cold-start time predictably fast hota hai, chahe JS bundle kitna bhi bada ho

Trade-offs bhi samajhna zaroori hai, kyunki "sab kuch free mein fast" jaisa kuch nahi hota:

  • Binary size thoda badhta hai — bytecode format kabhi kabhi raw minified JS se slightly bada hota hai (though gzip/compression ke baad difference kam ho jaata hai), aur Hermes VM khud bhi app binary mein bundled hota hai (ek statically linked library ki tarah), jo kuch MB add karta hai.
  • Runtime execution speed uniformly improve nahi hoti — ye ek common misconception hai jo interview mein bhi pooche jaata hai (neeche dekhenge). Hermes sirf startup/parse cost remove karta hai, lekin ek baar JS chal raha ho, uski raw execution speed (loops, math, array operations) JSC ya V8 se necessarily better nahi hoti — kabhi kabhi thodi slower bhi ho sakti hai kyunki Hermes ka bytecode interpreter, V8 jaise highly-optimized JIT ke comparison mein simpler hai.
  • Kuch JS features mein Hermes-specific caveats hain — jaise Intl API ka poora support pehle missing tha (ab largely fixed hai recent versions mein, lekin still kabhi Intl-heavy locale/date-formatting code mein polyfill chahiye ho sakta hai), aur regex engine mein kuch edge-case differences JSC ke comparison mein.
🧠 Senior Dev Note

Ye distinction bahut important hai: Hermes startup ko fast banata hai, steady-state execution ko nahi. Agar aapki app slow feel ho rahi hai kisi heavy computation (jaise large list sort, image processing) ke waqt (na ki app open karte waqt), Hermes on/off karne se wo problem solve nahi hogi — us case mein aapko algorithm optimize karna hoga, ya us kaam ko native module/worklet mein move karna hoga. Interview mein "Hermes se sab kuch fast ho jaata hai" bolna ek red flag hai — depth wale answer mein specifically "parse+compile cost" bolna zaroori hai.

Prebuild Internals — Continuous Native Generation (CNG)

Jab aap npx expo prebuild chalate ho, ye "magic" nahi hai — ye ek deterministic, step-by-step pipeline hai jise samajhna zaroori hai kyunki iski wajah se ek fundamental philosophy shift aata hai aapke native folders ke saath kaam karne ke tareeke mein. Chalo steps dekhte hain:

  1. Prebuild sabse pehle aapki config file (app.json ya app.config.ts) ko read aur evaluate karta hai — agar wo TypeScript file hai, to usse pehle compile/run karke final resolved JSON config nikaalta hai.
  2. Phir wo ek base native project template (Expo ka standard iOS Xcode project aur Android Gradle project skeleton) leta hai — ye templates Expo SDK version ke saath versioned hain.
  3. Us template ke upar, config mein jo bhi values hain (app name, bundle identifier, icons, splash screen, permissions) unhe inject karta hai — jaise Info.plist, AndroidManifest.xml, build.gradle jaise native files ko generate/modify karta hai.
  4. Sabse important step — config plugins ko unke declared order mein apply karta hai. Har config plugin ek function hai jo native project (Xcode project object model, Android Gradle files, Info.plist, etc.) ko programmatically modify karta hai — jaise ek plugin ho sakta hai jo Firebase config file (GoogleService-Info.plist) copy kare, ya ek native permission string add kare. Ye plugins ek "mod" system ke through native config files ko AST/object level pe safely modify karte hain (raw text find-replace nahi, isliye idempotent hote hain — dobara prebuild chalane pe duplicate entries nahi banti).
  5. End result: poori tarah generated ios/ aur android/ folders, jo ready hain ki inhe Xcode/Gradle se directly build kiya ja sake.
terminal — prebuild flow
# Prebuild command chalane se pehle: sirf app.config.ts + package.json exist karte hain, ios/android nahi
ls
# app/  app.config.ts  package.json   (ios/ android/ abhi absent hain)

# Prebuild chalao — ye config read karega, template lega, plugins apply karega
npx expo prebuild

# Ab ios/ aur android/ poori tarah generate ho chuke hain, native build ke liye ready
ls
# app/  app.config.ts  ios/  android/  package.json

# Agar aapne ios/ folder mein manually koi file edit ki thi (jaise Info.plist), aur ab dobara
# prebuild chalate ho, wo manual edit WIPE ho jaayegi — kyunki ios/ ek "derived output" hai,
# source of truth nahi. Isliye clean regenerate ke liye --clean flag bhi common hai:
npx expo prebuild --clean
# --clean flag purane ios/android folders delete karke bilkul fresh generate karta hai

Yahi hai CNG (Continuous Native Generation) ki poori philosophy — native folders ko ek source of truth ki tarah treat mat karo, unhe ek build artifact/output ki tarah treat karo, jaise aap dist/ ya build/ folder ko treat karte ho webpack se. Source of truth aapka app.config.ts + config plugins hain — jab bhi chaho, ek fresh, deterministic ios//android/ reproduce ho sakta hai unse. Isi wajah se bahut saare Expo-first teams ios/ aur android/ ko .gitignore mein daal dete hain (bilkul aise jaise node_modules/ ko ignore karte hain) — kyunki commit karne ka koi fayda nahi jab wo kabhi bhi regenerate ho sakte hain, aur commit karne se ulta problem hoti hai: agar do developers alag time pe prebuild chalate hain (ya CI chalata hai), generated files mein minor diffs (timestamps, ordering) aa sakte hain jo unnecessary merge conflicts create karte hain.

⚠️ Gotcha

Agar kabhi genuinely koi native file manually edit karni pade (rare case, jab config plugin available nahi hai kisi cheez ke liye), to sahi approach hai khud ek config plugin likhna jo wo modification programmatically kare — na ki directly ios/ folder mein jaake edit karna. Isse aapka edit "source of truth" (config plugin code) mein reh jaata hai aur har prebuild pe consistently reapply hota hai, kabhi lost nahi hota.

JS Engine Comparison — Hermes vs JSC vs V8

Interview mein aksar ye table-jaisa comparison poocha jaata hai — chalo teeno major JS engines ko side-by-side dekhte hain jo mobile/RN context mein relevant hain:

EngineCompilation ModelStartup TimeMemory UsageDebugging SupportDefault Platform Usage
Hermes AOT (bytecode precompiled at build time) Fastest — no parse/compile at runtime Lowest — compact bytecode, efficient GC tuned for mobile Chrome DevTools via Hermes debugger protocol, Flipper (legacy), source maps supported Default engine for RN (iOS + Android) since RN 0.70+/SDK 46+
JSC (JavaScriptCore) JIT (parse + compile at runtime, with tiered optimization) Slower cold start (parse+compile cost on device) Higher — JIT compiler cache + optimizing compiler overhead Safari Web Inspector (iOS), decent but RN-specific tooling weaker now that Hermes is default Legacy default on iOS pre-Hermes; still usable via config but rarely chosen now
V8 JIT (multi-tier: Ignition interpreter + TurboFan optimizing compiler) Moderate — some snapshotting but heavier than Hermes AOT Highest of the three — most memory-hungry, optimized for desktop-class execution speed Best-in-class (Chrome DevTools native home), extremely mature Not used in standard RN; powers Node.js, Chrome, and some custom/experimental RN engine setups

Key insight jo interview mein useful hai: V8 aur JSC dono raw peak execution speed mein Hermes se better ho sakte hain (kyunki unke JIT optimizing compilers hain jo hot code paths ko aggressively optimize karte hain over time), lekin mobile app ka dominant performance metric startup time hai, na ki peak throughput — kyunki ek average app session mein user app kholta hai, kuch seconds/minutes use karta hai, band kar deta hai. Is usage pattern mein, "fast cold start, decent steady-state" (Hermes) generally "slow cold start, very fast steady-state" (V8-jaisa) se better user experience deta hai — yahi reasoning hai ki Meta ne Hermes ko is trade-off ke saath specifically RN ke liye design kiya.

Monorepo Setups — Expo App Turborepo/Nx Ke Andar

Bade organizations mein aksar ek single repo mein multiple apps/packages hote hain — jaise ek Expo mobile app, ek Next.js web app, aur shared packages (ui, utils, api-client) jo dono use karte hain. Ye setup Turborepo ya Nx jaise tools se manage hota hai. Concept simple lagta hai, lekin Metro bundler (jo RN ka default bundler hai) ka default resolver monorepos ke liye design nahi hua tha shuru mein, isliye kuch specific challenges aate hain:

  • Symlink resolution — package managers (pnpm especially, yarn workspaces bhi) shared packages ko node_modules ke andar symlinks ke through link karte hain (actual code root package folder mein hota hai, node_modules mein sirf ek symlink hota hai). Metro ka default resolver symlinks ko properly follow nahi karta tha (real file location resolve nahi kar paata tha), isse "module not found" jaise errors aate the jab aap shared package import karte the.
  • watchFolders config — Metro by default sirf apne app root ke andar files watch karta hai. Monorepo mein, agar aap ek shared package (packages/ui) mein change karte ho jo repo root ke bahar hai app folder se, Metro us change ko detect hi nahi karega jab tak aap use explicitly watchFolders array mein add na karo.
  • nodeModulesPaths — monorepos mein dependencies hoisted ho sakti hain root node_modules mein (workspace hoisting ki wajah se), na ki app-level node_modules mein. Metro ko batana padta hai ki extra jagah pe bhi dependencies dhoondhe.
metro.config.js — monorepo-aware config
const { getDefaultConfig } = require('expo/metro-config'); // Expo ka default Metro config factory import kiya
const path = require('path'); // Node ka path module — folder paths resolve karne ke liye chahiye

const projectRoot = __dirname; // current app ka folder (jaise apps/mobile)
const workspaceRoot = path.resolve(projectRoot, '../..'); // monorepo ka root folder, do level upar

const config = getDefaultConfig(projectRoot); // Expo ka base Metro config load kiya, isi ko customize karenge

// Metro ko batao ki workspace root ke andar bhi files watch kare, sirf app folder nahi
// warna packages/ui jaise shared package mein change hone pe hot-reload trigger hi nahi hoga
config.watchFolders = [workspaceRoot];

// Metro ko batao ki node_modules do jagah dhoonde — app-level aur workspace-root-level
// kyunki pnpm/yarn workspaces dependencies ko root mein hoist kar sakte hain
config.resolver.nodeModulesPaths = [
  path.resolve(projectRoot, 'node_modules'), // pehle app-local node_modules check karo
  path.resolve(workspaceRoot, 'node_modules'), // phir workspace-root node_modules check karo
];

// Symlinks ko properly follow karne ke liye ye enable karna zaroori hai monorepo setups mein
// warna Metro symlinked shared package ka real path resolve nahi kar paata
config.resolver.unstable_enableSymlinks = true;

// Modified config ko export kiya — ab Metro isi config ke saath bundle banayega
module.exports = config;
🧠 Senior Dev Note

Modern Expo SDK versions mein unstable_enableSymlinks aur better monorepo defaults already largely built-in ho chuke hain (Metro team ne is pain ko upstream fix karna shuru kiya hai), lekin senior interview mein ye expect kiya jaata hai ki aap samjho ki problem kya thi aur kyun — sirf ye nahi ki "bas config copy-paste kar do". Agar aap kabhi ek naya monorepo bootstrap kar rahe ho, create-expo-app ke saath-saath Turborepo/Nx ke official Expo templates use karna sabse safe starting point hai, kyunki wo ye saari config already correctly wire kar chuke hote hain.

🎯 Interview Questions — Senior React Native Developer

Ye questions un cheezon pe focus karte hain jo actually ek senior/staff candidate ko mid-level se alag karti hain — depth of reasoning, trade-off awareness, aur real debugging instinct, na ki sirf definitions ratt lena.

1. Walk me through what happens when JS calls a native function under the New Architecture, step by step, compared to the old Bridge.

Old Bridge mein: JS ek native method call karta hai → ye call ek message object mein encode hota hai → JSON.stringify hoke ek queue mein daala jaata hai → ye queue batch mein, asynchronously, ek native thread pe deliver hoti hai → native side JSON.parse karke message decode karta hai → actual native method invoke hota hai → agar return value chahiye, to poora process reverse mein wapas hota hai (native → JSON serialize → queue → JS deserialize). Ye poora round-trip kam se kam ek event-loop tick lagata hai, aur bade payloads (jaise images/arrays) serialize karna khud CPU cost hai.

New Architecture (JSI) mein: JS engine (Hermes) ke paas ek direct C++ binding hoti hai native "Host Objects" ke saath. Jab JS ek TurboModule method call karta hai, JSI directly us C++ function ko synchronously invoke karta hai — same call stack pe, bina kisi queue/serialization ke. Data JSON string ki jagah directly memory mein pass hota hai (JS values → C++ jsi::Value representations, bina text conversion ke). Agar return value hai, wo turant, same synchronous call ke andar wapas mil jaata hai — async ka wait nahi karna padta (though aap chaho to still async pattern use kar sakte ho Promise ke saath, wo JS-level choice hai, architecture-level constraint nahi).

Key differentiator jo main interview mein highlight karunga: purane model mein har cross-boundary call ki cost thi (serialization + queue + async round trip), naye model mein sirf ek initial lazy-load cost hai (TurboModule pehli baar access hone pe initialize hota hai), uske baad calls near-zero-overhead hain — kyunki wo essentially native C++ function calls hain jinhe JS engine directly invoke kar raha hai.

2. Why does Hermes improve startup time specifically, not runtime execution speed uniformly?

Kyunki Hermes jo cost eliminate karta hai wo hai parse + compile cost — ye ek one-time, upfront cost hoti hai jo normally app launch ke exact waqt lagti (JSC jaisa JIT engine JS source ko parse karke bytecode/machine code banata hai runtime pe). Hermes ye poora kaam build time pe kar chuka hota hai (hermesc ke through), isliye device pe sirf bytecode load + execute hota hai — parse/compile step hi missing hai.

Lekin ek baar code chal raha ho (steady-state execution — loops, function calls, math), wahan Hermes ka koi special architectural advantage nahi hai. Actually, JIT engines jaise V8 ya JSC ka advantage hai wahan — wo runtime pe "hot" code paths ko detect karke unhe aggressively optimize (machine code mein recompile) kar sakte hain based on actual runtime behavior/types (jise "adaptive optimization" kehte hain). Hermes ka bytecode interpreter simpler hai — ye consistently interpret karta hai bina us tarah ke runtime profiling-based optimization ke. Isliye "startup fast, peak throughput thoda kam" ye ek deliberate, reasoned trade-off hai — mobile app ke usage pattern (short sessions, frequent launches) ke liye startup latency zyada matter karti hai peak compute throughput se, isliye Meta ne ye trade-off consciously choose kiya.

3. When would you choose to eject/prebuild vs stay fully managed? What are you giving up either way?

Ye framing thodi purani (managed vs bare) ho chuki hai — modern Expo mein har production app already prebuild use karti hai (CNG ke through), sirf ye choice hai ki "kab tak Expo Go pe stay karo before prebuild karna zaroori ho jaaye". Real decision point hai: jaise hi aapko koi native module chahiye jo Expo Go mein bundled nahi hai (chahe wo third-party ho jaise react-native-mmkv, ya koi native SDK integration jaise Stripe/Firebase ka kuch specific piece, ya khud likha hua custom native module), aapko Development Build pe move karna hi padega.

Fully Expo Go mein rehne ka fayda hai: zero build time, instant iteration, koi native toolchain (Xcode/ Android Studio) setup ki zaroorat nahi even non-Mac machines pe kaam ho sakta hai — ye choti team/ prototype phase ke liye ideal hai. Jo aap give up karte ho: koi custom native code, koi specific native SDK jo Expo Go mein missing ho.

Development Build/Prebuild pe move karne ka trade-off ulta hai: aapko ab native build infrastructure maintain karni padti hai (EAS Build cost/time, ya local Xcode/Gradle setup), pehli build 5-20 minutes legi, aur agar aap manually native folders edit karte ho (jo aapko nahi karna chahiye — config plugins use karo), to aapko CNG ke "disposable native folder" model ko discipline se follow karna padega. Lekin aap poori flexibility paate ho — koi bhi native capability add kar sakte ho jabki OTA updates (EAS Update) ka fayda bhi retain karte ho JS-only changes ke liye.

4. Your app works fine in Expo Go but crashes on a production build — what's your systematic debugging approach?

Sabse pehle main confirm karunga ki ye Expo Go vs dev/production build ka difference hai, ya dev vs release ka — dono alag categories of issues hain. Systematic approach:

  • Step 1 — Reproduce locally with same build type: ek local release build banao (eas build --profile preview ya expo run:android --variant release) taaki crash consistently reproduce ho bina cloud build wait kiye baar-baar.
  • Step 2 — Get real logs: Expo Go/dev build mein aapko nice red-box errors milte hain, release build mein aksar sirf "app crashed" milta hai. Android pe adb logcat se native crash logs, iOS pe Xcode Console/device logs se stack trace nikaalo — Hermes crashes ke liye source maps ke saath symbolicate karna padta hai (raw bytecode addresses readable nahi hote).
  • Step 3 — Check the usual suspects: (a) koi native module jo Expo Go mein available tha but config plugin properly wire nahi hua production build mein, (b) __DEV__ pe conditional code jo silently different path le raha hai, (c) environment variables ya EAS secrets jo local .env mein the but EAS build environment mein set nahi hain, (d) ProGuard/R8 minification (Android) ne kisi class ko rename/strip kar diya jo reflection-based native module use kar raha tha.
  • Step 4 — Bisect if needed: agar sab kuch pehle theek tha aur recently break hua, git bisect ya recent dependency changes check karo — aksar ek naya native module add hua hota hai jisne config plugin properly setup nahi kiya.

5. Why can't Metro's default resolver handle monorepo symlinks well, and how do you fix it?

Metro originally single-package RN apps ke liye design hua tha, jahan assumption thi ki saara code ek hi node_modules tree ke andar, ek hi root se resolve hoga. Monorepos mein pnpm/yarn workspaces shared packages ko symlinks ke through link karte hain — actual file kahin aur hai (jaise packages/ui/src/Button.tsx), aur node_modules/@myorg/ui sirf ek symlink hai us jagah ki taraf. Metro ka haystack-based module resolution symlink ko "follow" karke real file location tak nahi pahunchta tha by default — isse ya to module not found error milta, ya (worse) duplicate React instances load ho jaate the kyunki Metro symlinked aur non-symlinked path ko do alag modules samajh leta tha.

Fix hai metro.config.js mein unstable_enableSymlinks: true set karna (symlinks ko properly resolve karne ke liye), watchFolders mein monorepo root add karna (taaki file watching sirf app folder tak limited na rahe), aur nodeModulesPaths mein workspace-root node_modules bhi add karna (kyunki hoisted dependencies wahan reh sakti hain). Ye teeno pieces combined monorepo mein Expo app ko reliably kaam karne dete hain.

6. What actually happens when you run `npx expo prebuild`, and why shouldn't you hand-edit the generated ios/android folders?

Prebuild config file read karta hai, base native template leta hai, config plugins ko unke order mein apply karta hai (jo native files jaise Info.plist/AndroidManifest/build.gradle ko programmatically modify karte hain), aur end mein poori tarah fresh ios//android/ generate karta hai. Iska matlab hai ye folders deterministically derived output hain aapke config + plugins se — bilkul aise jaise webpack ek dist/ folder generate karta hai source code se.

Agar aap directly ios/YourApp/Info.plist mein jaake manual edit karo, wo edit tab tak survive karega jab tak koi dobara expo prebuild na chalaye — aur jaise hi koi (aap khud, ya CI, ya ek teammate) prebuild chalata hai, wo file config se dobara fresh generate hoti hai aur aapka manual edit silently wipe ho jaata hai, bina koi warning ke. Ye ek bahut common "production mein pehle kaam kar raha tha, ab nahi" bug ka source hai. Sahi tareeka hai ki jo bhi native modification chahiye thi, use ek config plugin ke through express karo — ab wo modification "source of truth" (aapka JS/TS config plugin code, jo version control mein hai) ka hissa ban jaati hai, aur har prebuild pe consistently reapply hoti hai.

7. How would you architect a large-scale RN app to minimize unnecessary re-renders, and how does the New Architecture change your reasoning here?

React-level optimization (memoization, stable references, avoiding inline objects/functions in render, splitting context providers so unrelated state changes don't cascade) remains fundamentally same regardless of old/new architecture — kyunki ye React's reconciliation ka concern hai, native bridge ka nahi. Jo change hota hai New Architecture mein wo hai Fabric ka concurrent rendering support — React 18 features jaise useTransition/startTransition ab properly native side tak propagate hote hain, matlab aap high-priority updates (jaise user typing) ko low-priority updates (jaise background list re-sort) se genuinely prioritize kar sakte ho at the rendering commit level, na sirf JS scheduling level pe.

Practically, main large lists ke liye FlashList (ya FlatList with properly tuned windowSize/getItemLayout) use karunga, expensive derived state ko useMemo se cache karunga, aur agar koi animation/gesture-heavy interaction hai, use Reanimated worklets mein move karunga taaki wo UI thread pe directly chale — JS thread ke render cycle se completely decoupled, jo ki khud JSI ki hi capability hai (worklets bhi JSI ke through UI thread pe directly JS-like code execute karte hain).

8. What's the difference between Expo's "Managed Workflow" of old and today's "Development Build" model — why did the old distinction become obsolete?

Purana Managed Workflow ek hard constraint tha — aap ios//android/ folders dekh hi nahi sakte the, aur agar aapko ek custom native module chahiye, aapko poora "eject" karna padta tha Bare Workflow mein, jisse aap permanently Expo tooling ke convenience features (jaise EAS ka managed build pipeline) kho dete the — ye ek one-way, painful migration thi.

Development Build model (SDK 45+ ke baad) ne ye distinction obsolete kar diya kyunki ab prebuild/CNG ki wajah se native folders hamesha derivable hain aapke config se — matlab aap "custom native module add karna" aur "Expo tooling ka convenience rakhna" dono simultaneously kar sakte ho. Aap apna khud ka dev client (expo-dev-client) build karte ho jisme aapke specific native dependencies hain, lekin still EAS Build, EAS Update, config plugins sab kaam karte hain same tarah. Ye ek reversible, incremental choice ban gaya hai — na ki ek permanent fork jaisa pehle tha.

9. If you had to explain JSI to a junior engineer in one analogy, and defend why that analogy holds up, how would you do it?

Main bolunga: "Bridge purane zamaane ke do deshon ke beech letter bhejne jaisa tha — aapko message likhna padta (serialize), post office (queue) mein daalna padta, wait karna padta jab tak wo deliver ho (async), aur reply bhi isi tarah wapas aata. JSI ek direct phone call jaisa hai — dono taraf ke log directly, real-time baat kar sakte hain, bina kisi intermediary ke."

Analogy ko defend karte hue: ye is tarah accurate hai ki dono cases mein "communication cost" ka structural difference capture hota hai — letter mein encoding/decoding overhead hai (serialization), aur inherent delay hai (async queue), jabki phone call mein dono directly ek dusre ka "representation" access kar rahe hain real-time (JSI ke Host Objects, jo C++ objects ko directly JS se accessible banate hain). Jahan analogy thodi break hoti hai: JSI calls sirf "conversation" nahi hain, wo actual memory-level, type-safe bindings hain — isliye main junior ko clarify karta ki analogy sirf latency/overhead ka intuition dene ke liye hai, actual mechanism C++ level binding hai, magic phone call nahi.

10. You're setting up a new Expo app inside an existing Turborepo with a Next.js web app and shared UI package. What are the first three things you'd configure, and why?

Pehla: metro.config.js ko monorepo-aware banana — watchFolders workspace root ki taraf point karna (warna shared package changes hot-reload trigger nahi karenge), nodeModulesPaths mein workspace root node_modules add karna (hoisted deps ke liye), aur unstable_enableSymlinks: true set karna (workspace symlinks properly resolve karne ke liye).

Dusra: shared UI package ko platform-aware banana agar wo web (DOM-based) aur native (RN-based) dono targets share kar raha hai — ya to package ke andar .native.tsx/web split rakhna, ya bilkul processing web-only components ko is package se exclude karke sirf truly-shared logic (types, utils, non-UI business logic) share karna, aur UI components har platform ke apne package mein rakhna. Ye galti bahut common hai jahan log soch lete hain "ek Button component web aur native dono mein chalega" bina realize kiye ki underlying primitives (`div` vs `View`) fundamentally different hain.

Teesra: TypeScript project references / path aliases ko consistently set karna taaki shared package se import karte waqt type-checking aur IDE autocomplete dono kaam karein across apps — aur build pipeline (Turborepo turbo.json pipeline) mein dependency order define karna (shared package pehle build ho, phir Expo app), taaki turbo run build ya turbo run dev chalane pe cheezein sahi order mein compile hon.
